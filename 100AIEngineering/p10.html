Architecture of an LLM Application in Production

50m video40m practice

In production the model call is one box among many. A reliable LLM application is a set of stateless services around that call: state lives in stores, behaviour lives in versioned configuration, and slow work moves off the request path into queues.

The reference architecture

Every serious LLM product converges on roughly the same parts. Naming them early tells you where each concern from Phases 2–9 lives, and stops it leaking into the wrong place. For example, retry logic belongs in the gateway, not in your prompt code.

Synchronous and asynchronous paths

A synchronous request holds a connection open until the answer is complete: the user asks, DocPilot retrieves, generates and streams. It needs a latency budget (L110) and must fail fast. An asynchronous request returns a job ID at once. A worker does the work, and the client polls, subscribes to progress events, or gets a webhook.

Choosing the path
  • Use the sync path for interactive answers that normally finish within tens of seconds and are cheap to redo if the connection drops.
  • Use the async path for anything that can outlive a connection or a deploy: ingesting a new docs release (L48), batch enrichment (L109), a research agent that runs for minutes, or any job that needs retries spread over hours.
  • Serverless platforms and load balancers enforce request time limits. A job that might hit one belongs on the async path.

Stateless services, state in stores

Any replica must be able to serve any request, because autoscaling, deploys and crashes will move traffic between replicas mid-conversation. So nothing a later request depends on may live in process memory. Conversation history goes in Postgres. Agent checkpoints go in a durable store (L74), caches in Redis, and uploaded files in object storage. The request carries only IDs: conversation_id, tenant_id, an idempotency key for anything with side effects (L107).

Definition

A service is stateless when its response depends only on the request and on external stores, never on earlier requests it happened to handle. You can then kill it, restart it, or run fifty copies without changing behaviour. In-process caches are allowed only if losing them costs time, not correctness.

Configuration and feature flags for prompts and models

Prompt text, prompt version, model ID, retrieval k and the reranker threshold are configuration, not code. Keep them in the prompt registry from L21 and choose among them with feature flags. You can then roll a new prompt out to 10% of users, compare it with the online evaluation from L94, and roll it back without a deploy (L112). Bucketing must be deterministic per user, so a person does not switch between prompt versions mid-conversation.

import hashlib
from dataclasses import dataclass

@dataclass(frozen=True)
class Flag:
    name: str
    default: str                     # value outside the rollout
    variant: str                     # value under test
    percent: int = 0                 # share of users (0-100) who get the variant
    allow: frozenset = frozenset()   # IDs that always get the variant (staff, test tenants)

def bucket(flag: str, user_id: str) -> int:
    """Stable bucket in 0..99; independent across flags because the flag name is hashed too."""
    digest = hashlib.sha256(f"{flag}:{user_id}".encode()).digest()
    return int.from_bytes(digest[:8], "big") % 100

def resolve(flag: Flag, user_id: str) -> str:
    if user_id in flag.allow or bucket(flag.name, user_id) < flag.percent:
        return flag.variant
    return flag.default

FLAGS = {

Log the resolved values (prompt version, model) on every request, as the chat() wrapper from L2 already does. Without them, a quality dip cannot be traced to the rollout that caused it.

Separate environments

Run at least three environments: dev, staging and prod. Each has its own provider API keys, so a runaway loop in dev cannot drain the production rate limit or budget. Each has its own vector index and database, so a half-finished re-chunking experiment cannot change production answers. And each has its own trace project, so test traffic does not pollute dashboards. Most providers let you group keys into workspaces or projects with separate spend limits. Staging should mirror production's configuration and flags exactly. Its data should be the real public corpus plus synthetic tickets, never copied customer data (L101).

Worked example

A developer runs a re-embedding job against the "docs" collection, meaning to target the dev cluster. With one shared index, half of production's chunks now carry new-model vectors while queries are still embedded with the old model, so retrieval quality collapses silently. With per-environment collection names (k8s-docs-dev, k8s-docs-prod) and per-environment credentials, the same mistake fails with an authorisation error.

What breaks in production
  • Hidden state. A module-level dict of conversations works on one replica. It loses context the first time a load balancer routes a follow-up elsewhere.
  • Model IDs in code. Changing a model means a deploy, and nobody can tell which requests used which model. Put them in config and log the resolved value.
  • Long jobs on the request path. An ingestion endpoint that works locally times out behind a proxy and gets retried by the client, so the job runs twice.
  • Shared keys and indexes across environments. Load tests trip production rate limits, and experiments change production retrieval.
  • No owner for cross-cutting concerns. Retries are implemented in three places with three policies. Retries multiply across layers (L107).

Streaming to Users: SSE, WebSockets and Partial Results

45m video50m practice

Users judge speed by when something useful first appears, not by when the answer finishes. Streaming turns a multi-second wait into a sub-second start. Done properly, it also tells users what the system is doing, and stops spending tokens the moment they leave.

Why streaming matters

A grounded DocPilot answer might be 400 output tokens. Decode speed varies by model and load, but at tens of tokens per second that is several seconds of generation after retrieval (L4, L8). Without streaming, the user stares at a spinner for the whole time. With streaming, they start reading after the time to first token (TTFT) and read at about the speed the text arrives. The total time is unchanged. Perceived latency drops to TTFT plus whatever you show before the first token: a "searching the docs" status, then the sources. L110 attacks TTFT itself.

Server-sent events vs WebSockets

Definition · SSE wire format

An SSE response is an ordinary HTTP response with Content-Type: text/event-stream that stays open. Each event is a few field: value lines (event, data, id, retry) ended by a blank line, so every event ends in \n\n. Lines starting with : are comments, used as keep-alive pings. The browser's EventSource reconnects automatically and sends Last-Event-ID.

Directionserver to client; the request carries the inputboth ways, any time
Transportplain HTTP; works through most proxies, CDNs and HTTP/2an upgraded connection (RFC 6455); some proxies need configuration

For DocPilot, SSE is the default. One caveat: EventSource only supports GET and cannot set custom headers, so a POST with a JSON body uses fetch and reads the response body as a stream. The wire format is identical. Voice agents (L125) are where WebSockets earn their complexity.

Streaming through FastAPI

A StreamingResponse wraps an async generator; each yielded string is sent as soon as it is produced. Use anthropic.AsyncAnthropic on an async server: the sync client would block the event loop for every other user. Typed events let the front end route each one to a different part of the UI.

# services/api.py
import asyncio, json
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from docpilot.llm import MODEL
from docpilot.search import search

app = FastAPI()            # at startup: app.state.llm = anthropic.AsyncAnthropic()

class Ask(BaseModel):
    question: str

def sse(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data)}\n\n"

async def answer_events(ask: Ask, request: Request):
    yield sse("status", {"step": "searching"})
    hits = await asyncio.to_thread(search, ask.question, k=5)   # search() is sync: keep it off the event loop
    yield sse("sources", {"urls": [h.url for h in hits]})
    context = "\n\n".join(f"[{i}] {h.text}" for i, h in enumerate(hits, 1))
    async with request.app.state.llm.messages.stream(
        model=MODEL, max_tokens=1024,
        messages=[{"role": "user", "content": f"{context}\n\nQuestion: {ask.question}"}],
    ) as stream:
        async for text in stream.text_stream:
            if await request.is_disconnected():
                return             # leaving the block closes the provider stream
            yield sse("delta", {"text": text})
        final = await stream.get_final_message()
    yield sse("done", {"stop_reason": final.stop_reason, "output_tokens": final.usage.output_tokens})

@app.post("/answer")
async def answer(ask: Ask, request: Request):
    return StreamingResponse(answer_events(ask, request), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})

X-Accel-Buffering: no stops nginx from buffering the whole stream, which would turn it back into one late response. FastAPI 0.143 also ships fastapi.sse.EventSourceResponse, which formats events and sends keep-alive pings for you.

Disconnects and cancellation

A cancel button calls AbortController.abort() on the fetch, which closes the connection. On the server, two things can notice. Starlette's StreamingResponse watches for the ASGI disconnect message (or a failed send) and cancels the generator. The explicit is_disconnected() check between chunks makes the behaviour visible and testable. Either way, the async with block exits and the SDK closes its HTTP stream to the provider, so generation stops instead of running on for an absent user. How cancelled requests are billed is provider-specific; check the docs. For agents, check for cancellation between steps too. A tool call already in flight should finish or be rolled back, never abandoned halfway (L78).

Streaming agent progress and structured output

Agents spend most of their time not producing answer text. Stream their steps as typed events, such as status, tool_call (name plus a short summary of the arguments, never secrets), tool_result, sources, delta, done and error. The UI can then show "Searching the docs…", then "Reading 3 pages…", then the answer (L113). Structured output is harder: a JSON prefix does not parse. Three options:

  • Stream the prose answer as text, and send the structured parts (citations, confidence, suggested actions) as separate events.
  • Use the SDK's parsed events. Iterating the stream directly yields InputJsonEvents (type="input_json") carrying partial_json and a parsed snapshot of a tool input so far.
  • Render only fields that are already complete, and validate the whole object at the end (L20).

Rendering partial Markdown

Re-render the accumulated text on each animation frame, not on every delta. Before rendering, repair the two artefacts of a cut-off stream. An unclosed code fence swallows the rest of the page. A half-written link shows raw syntax or points at a truncated URL. Always render with raw HTML disabled and sanitise the output: model text is untrusted input to your page (L100).

import re

def renderable(md: str) -> str:
    """Make a partial Markdown answer safe to render mid-stream."""
    md = re.sub(r"\[[^\]\n]*(\]\([^)\n]*)?$", "", md)   # hold back a half-written link
    if md.count("```") % 2:                             # close an open code fence
        md += "\n```"
    return md

for partial in ["See [the Pod docs](https://kubernetes.io/do",
                "Run:\n```bash\nkubectl get po",
                "[Pods](https://kubernetes.io/docs/concepts/workloads/pods/) are"]:
    print(repr(renderable(partial)))

What breaks in production
  • Buffering proxies. A reverse proxy, CDN or compression middleware collects the stream and delivers it all at the end. Test through the real ingress, not just locally.
  • Idle timeouts. A long tool call sends nothing for 60 s and a load balancer drops the connection. Send : ping comments every 15–30 s.
  • Orphaned generations. Ignoring disconnects means paying for answers nobody reads, multiplied by every impatient retry.
  • Errors after the 200. Once streaming starts, the status code is already sent. Report mid-stream failures as an error event, and make the client treat a stream without done as failed.
  • Guardrails on partial text. An output filter (L100) that only sees the final answer has let the user read everything before it. Check in windows as you stream, and be ready to retract.

Observability: Traces, Spans and GenAI Semantic Conventions

50m video50m practice

A bad answer is usually caused several steps before the model writes it: a missed chunk, a stale tool result, the wrong prompt version. One trace per request, with a span for every retrieval, model call and tool call, makes each answer explainable after the fact.

Why logs are not enough

The JSONL line that chat() has written since L2 records one model call. A single DocPilot request now makes several model calls, retrieves twice, calls tools and runs guardrails, sometimes across three services. When a user reports a wrong answer, you need the tree: which retrieval fed which call, what the tool returned, where the 6 seconds went. You can rebuild that by grepping log lines for a request ID. A trace records it directly, with timing and parent–child structure.

Definition
  • Trace: everything that happened for one request, identified by a trace_id.
  • Span: one timed operation in that trace (name, start, duration, status, a parent_id, and key–value attributes). Spans nest: the request span contains retrieval, model and tool spans.
  • Context propagation: passing the trace and parent IDs across process boundaries, for example in the W3C traceparent HTTP header or a queue message field. The search service and the workers then add their spans to the same trace.

Here is a trace in thirty lines of plain Python. A context variable holds the current span, so nested blocks find their parent automatically, including across await. OpenTelemetry does the same thing, plus standard IDs, propagation, sampling and export.

import contextvars, time, uuid
from contextlib import contextmanager

_current = contextvars.ContextVar("span", default=None)
SPANS: list[dict] = []                     # an exporter would ship these in batches

@contextmanager
def span(name: str, **attrs):
    parent = _current.get()
    s = {"name": name, "attrs": attrs, "span_id": uuid.uuid4().hex[:8],
         "trace_id": parent["trace_id"] if parent else uuid.uuid4().hex,
         "parent_id": parent["span_id"] if parent else None, "t0": time.perf_counter()}
    token = _current.set(s)                # children opened inside this block get s as parent
    try:
        yield s
    except Exception as e:
        s["attrs"]["error.type"] = type(e).__name__
        raise
    finally:
        s["ms"] = round((time.perf_counter() - s["t0"]) * 1000)
        _current.reset(token)
        SPANS.append(s)

def handle(question: str):
    with span("POST /answer", **{"docpilot.prompt_version": "answer@v8"}):
        with span("retrieve", **{"docpilot.k": 5}) as s:
            time.sleep(0.04)
            s["attrs"]["docpilot.hit_ids"] = ["pods#1", "pods#4"]
        with span("chat claude-sonnet-5-5", **{"gen_ai.operation.name": "chat"}) as s:
            time.sleep(0.09)
            s["attrs"].update({"gen_ai.usage.output_tokens": 41,
                               "gen_ai.response.finish_reasons": ["tool_use"]})
        with span("execute_tool kubectl_explain", **{"gen_ai.tool.name": "kubectl_explain"}):
            time.sleep(0.02)
        with span("chat claude-sonnet-5-5", **{"gen_ai.operation.name": "chat"}) as s:
            time.sleep(0.12)
            s["attrs"]["gen_ai.response.finish_reasons"] = ["end_turn"]

OpenTelemetry and the GenAI semantic conventions

OpenTelemetry (OTel) is the vendor-neutral standard for traces, metrics and logs: an API you call in code, an SDK that samples and batches, and the OTLP protocol that ships data to any backend. Its semantic conventions fix attribute names, so every tool reads gen_ai.usage.input_tokens the same way. As of late 2026 the GenAI conventions are still marked as in development (experimental), and names have changed between releases. For example, the provider attribute gen_ai.system became gen_ai.provider.name. Pin the version you follow.

AttributeExample
gen_ai.operation.namechat, embeddings, execute_tool, invoke_agent
gen_ai.request.model / gen_ai.response.modelthe ID you asked for / the one that answered
gen_ai.usage.input_tokens, gen_ai.usage.output_tokensfrom the response's usage
gen_ai.response.finish_reasons["end_turn"], ["max_tokens"]
gen_ai.tool.nameon tool execution spans

Span names follow the pattern {operation} {model}, e.g. chat claude-sonnet-5-5. Use your own namespace (docpilot.*) for what the conventions do not cover: prompt version, retrieved chunk IDs and scores, cache tokens, estimated cost, the flag variant from L104.

# OpenTelemetry SDK, API as documented; check your installed version (not installed here: untested)
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.sdk.trace.sampling import ParentBased, TraceIdRatioBased
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from docpilot.llm import MODEL, chat

provider = TracerProvider(sampler=ParentBased(TraceIdRatioBased(0.25)))
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint="http://localhost:4318/v1/traces")))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("docpilot")

def traced_chat(messages, *, model=MODEL, prompt_version="unknown", **kw):
    with tracer.start_as_current_span(f"chat {model}", kind=trace.SpanKind.CLIENT) as sp:
        sp.set_attribute("gen_ai.operation.name", "chat")
        sp.set_attribute("gen_ai.provider.name", "anthropic")
        sp.set_attribute("gen_ai.request.model", model)
        sp.set_attribute("docpilot.prompt_version", prompt_version)
        msg = chat(messages, model=model, **kw)
        sp.set_attribute("gen_ai.response.model", msg.model)
        sp.set_attribute("gen_ai.usage.input_tokens", msg.usage.input_tokens)
        sp.set_attribute("gen_ai.usage.output_tokens", msg.usage.output_tokens)
        sp.set_attribute("gen_ai.response.finish_reasons", [msg.stop_reason])
        return msg

Community instrumentation packages can create these spans for the provider SDKs automatically. Wrapping chat() yourself keeps the attributes you need under your control.

What to record, sampling and privacy

For every model span, record the prompt version and template variables, token usage including cache reads and writes, the stop reason, latency and TTFT, and the estimated cost. For retrieval, record the query actually sent (after rewriting), the hit IDs, their scores and the filters. For tools, record name, arguments, a truncated result and errors. The full prompt and output text are the most useful attributes and the most dangerous ones. The conventions make content capture opt-in for this reason.

Sampling and privacy
  • Head sampling decides at the start of a trace (keep 25%). It is cheap, but it drops most failures.
  • Tail sampling decides after the trace ends, for example in the OTel Collector. Keep every error, every trace with negative feedback, every guardrail hit and every slow trace, plus a small random share of the rest.
  • Redact PII before export, not in the viewer (L101). Set retention limits, restrict who can read traces with content, and store tenant IDs as attributes so you can delete a tenant's data.

Platforms, dashboards and alerts

LLM observability platforms add what generic tracing lacks: prompt and response viewers, token and cost roll-ups, sessions that group a conversation, user feedback linked to traces, and datasets built from production traces for your evals (L94). Langfuse and Arize Phoenix are open source and self-hostable. LangSmith is LangChain's hosted platform. Many others exist, and many accept OTLP, so instrumenting with OTel keeps you portable.

Worked example · dashboards

Request rate and error rate by type (429, 5xx, timeout, refusal). TTFT and total latency at p50, p95 and p99. Tokens per request and cost per day, split by feature and model. Share of max_tokens stops. Cache hit rate. Tool error rate. Thumbs-down rate. Alert on symptoms users feel: the error rate above 2% for 10 minutes, p95 latency over budget, daily spend over plan, or a spike in refusals or max_tokens stops after a deploy.

What breaks in production
  • Broken context. A thread pool, a queue hop or a raw httpx call drops the trace context, and the trace splits in two. Propagate it explicitly across every boundary.
  • Unbounded attributes. Full documents as span attributes blow up storage and hit exporter size limits. Store IDs and truncated text.
  • Secrets in traces. Authorisation headers or tool credentials recorded as arguments. Use an allow-list of attributes.
  • Sampling away the evidence. At 5% head sampling, the one trace a user complains about is usually gone.
  • Streaming spans that end too early. The span closes when the response object is returned, not when the last token is sent, so durations and token counts are wrong.

Reliability: Rate Limits, Retries, Timeouts and Fallbacks

45m video50m practice

Model providers fail in ordinary, predictable ways: rate limits, overload, slow responses, outages. A resilient client retries only what is worth retrying, spreads retries out, bounds how many it makes, stops calling a provider that is down, and always has a next-best answer.

Rate limits and the failures you will see

Providers limit each organisation or workspace in requests per minute and tokens per minute; Anthropic counts input and output tokens separately. Exceeding a limit returns 429 with a retry-after header. Provider-wide overload returns a 5xx; Anthropic uses 529 overloaded_error, which SDK 1.13 raises as anthropic.OverloadedError.

FailureRetry?Action
429 rate limitedyeswait at least retry-after; smooth traffic with a client-side token bucket
529 overloaded, 500, 502, 503, 504yesback off with jitter; fall back if it persists
408, connection error, timeoutyesretry within the request's deadline
400, 401, 403, 404, 413, 422noa bug or config error: fail fast, alert
stop_reason max_tokens or refusalnot blindlya successful response; handle it in logic (L84)

Backoff with full jitter, and retry budgets

If a thousand clients all retry exactly 1 s, 2 s and 4 s after an overload, they hit the recovering provider in synchronised waves. Jitter spreads them out. In Marc Brooker's simulation on the AWS Architecture Blog (2015), full jitter did the least work of the variants tested, with completion time close to the best.

Algorithm · Full jitter

For retry number \(n = 0, 1, 2, \dots\), with base delay \(b\) and cap \(c\):

$$\text{sleep}_n \sim \mathrm{Uniform}\big(0,\ \min(c,\ b \cdot 2^{n})\big)$$

If the server sent retry-after, wait at least that long instead.

Retries multiply across layers: if the browser, the API and the model client each try 3 times, one click can become \(3^3 = 27\) calls to a struggling provider. A retry budget caps retries at a fraction of recent traffic (say 20% extra), so an outage does not triple the load (SRE book, ch. 22). Retry in one layer, the gateway (L108), with a budget.

Timeouts per call and per request

Every request gets a deadline (DocPilot: 20 s interactive), and every call inside it a timeout no longer than the time remaining; three sequential 10 s timeouts would make a 30 s request. Configure the SDK's own retry layer deliberately:

import anthropic

# SDK 1.13 defaults: max_retries=2 (on 408, 409, 429, 5xx incl. 529 and connection errors,
# honouring retry-after; backoff 0.5 s doubling to 8 s, minus up to 25% jitter) and a
# 10-minute read timeout. Own the retry policy in one place, so set max_retries=0 here.
client = anthropic.Anthropic(max_retries=0, timeout=anthropic.Timeout(30.0, connect=5.0))
fast = client.with_options(timeout=10.0)        # per-call override for a small classifier call

For streaming, an HTTP read timeout limits the gap between chunks, not the total duration. Enforce the request deadline separately, for example with asyncio.timeout() around the whole stream.

Circuit breakers and fallbacks

In an outage, retries only add latency. A circuit breaker (Nygard, Release It!) counts consecutive failures per dependency. Past a threshold it opens and calls skip that dependency. After a cooldown it goes half-open and lets one probe through, which closes or re-opens it. Pair it with a fallback chain: primary model, smaller model, another provider (L108), degraded answer. Evaluate every fallback in advance (L93).

# docpilot/resilient.py
import random, time
import anthropic

RETRY_STATUS = {408, 409, 429, 500, 502, 503, 504, 529}      # 529 = Anthropic "overloaded"

def retryable(e: Exception) -> bool:
    if isinstance(e, anthropic.APIConnectionError):           # includes APITimeoutError
        return True
    return isinstance(e, anthropic.APIStatusError) and e.status_code in RETRY_STATUS

def full_jitter(attempt: int, base: float = 0.5, cap: float = 8.0) -> float:
    return random.uniform(0, min(cap, base * 2 ** attempt))   # Brooker 2015

class RetryBudget:
    """Token bucket: each request earns `ratio` tokens, each retry spends one."""
    def __init__(self, ratio: float = 0.2, cap: float = 5.0):
        self.ratio, self.cap, self.tokens = ratio, cap, cap
    def earn(self):
        self.tokens = min(self.cap, self.tokens + self.ratio)
    def spend(self) -> bool:
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

class Breaker:
    """Open after `threshold` consecutive failures; allow one probe after `cooldown` s."""
    def __init__(self, clock, threshold: int = 3, cooldown: float = 20.0):
        self.clock, self.threshold, self.cooldown = clock, threshold, cooldown
        self.failures, self.opened_at, self.state = 0, 0.0, "closed"
    def allow(self) -> bool:
        if self.state == "open" and self.clock() - self.opened_at >= self.cooldown:
            self.state = "half-open"                          # let one request probe
        return self.state != "open"
    def record(self, ok: bool):
        if ok:
            self.failures, self.state = 0, "closed"
            return
        self.failures += 1
        if self.state == "half-open" or self.failures >= self.threshold:
            self.state, self.opened_at = "open", self.clock()

def call(fn, models, *, breakers, budget, clock=time.monotonic, sleep=time.sleep,
         deadline_s=20.0, max_retries=2):
    """fn(model, timeout) -> result. Tries each model in order; returns (model, result, log)."""
    start, log = clock(), []
    budget.earn()
    for model in models:
        if not breakers[model].allow():
            log.append(f"{model}: open, skip")
            continue
        for attempt in range(max_retries + 1):
            remaining = deadline_s - (clock() - start)
            if remaining <= 0:
                return None, None, log + ["deadline"]
            try:
                result = fn(model, timeout=min(10.0, remaining))
                breakers[model].record(True)
                return model, result, log
            except Exception as e:
                if not retryable(e):
                    raise
                breakers[model].record(False)
                log.append(f"{model}: {getattr(e, 'status_code', type(e).__name__)}")
                delay = full_jitter(attempt)
                if (attempt == max_retries or breakers[model].state == "open"
                        or delay > remaining or not budget.spend()):
                    break                                     # give up on this model
                sleep(delay)
    return None, None, log                                    # caller degrades gracefully

Idempotency, graceful degradation and load shedding

  • Idempotency. Retrying a model call costs money; retrying an agent step can create a ticket twice. Give side-effecting tool calls a key such as request_id:step, and have the handler return the stored result on a repeat (L74).
  • Graceful degradation. When every model is down, return a cached answer labelled with its age (L111), the top documentation links without generation, or an honest "try again in a minute". Never a silent empty answer.
  • Load shedding. Over capacity, reject new requests at once with 503 and Retry-After instead of letting all of them time out. Shed batch work before interactive traffic (SRE book, ch. 21).
What breaks in production
  • Retry storms. SDK, wrapper and client retries multiply during the exact minutes the provider is weakest.
  • Retrying 400s. A too-long prompt fails identically every time; retrying triples the cost and hides the bug.
  • Untested fallbacks. The small model first sees the big model's prompt during the outage, and ignores the citation format.
  • One shared breaker. A rate limit on one model blocks every model and feature. Keep breakers per model and provider.
  • Timeouts longer than patience. The SDK's default read timeout is 10 minutes; the user left after 20 seconds.

LLM Gateways and Multi-Provider Routing

40m video40m practice

A gateway is the one place where every model call passes through: it holds the provider keys, enforces budgets, retries and falls back, and logs usage. Application code then names a feature alias, and the model behind it becomes configuration.

What a gateway does

By now DocPilot calls models from the answer path, the triage job, chunk enrichment, the judge and the agent. Without a gateway each caller carries a provider key and its own retry logic, and nobody can say what the triage job spent last week. A gateway centralises the cross-cutting concerns that L104 assigned to one box.

Definition

An LLM gateway is a proxy between your services and model providers that offers one API and handles:

  • Key management: provider keys live only in the gateway. Callers get virtual keys scoped to a team or feature, which you can rotate and revoke without touching provider accounts.
  • Quotas and budgets: rate and spend limits per virtual key.
  • Routing: an alias such as docpilot-answer maps to an ordered list of models, with retries, fallbacks and the circuit breakers of L107.
  • Logging and tracing: one usage record per call, tagged with feature and key (L106).
  • Caching: optionally, exact or semantic response caches (L111).

Open-source and hosted gateways

LiteLLM is the most widely used open-source option. It is both a Python library that translates one call format to many providers and a proxy server with virtual keys, budgets, fallbacks and logging callbacks. Other options include hosted or self-hostable gateways from API-management and observability vendors, edge-network gateways, OpenRouter-style hosted routers that resell many providers behind one key, and cloud model platforms (Bedrock, Vertex AI, Azure) that put several model families behind one cloud account. Compare them on where the data flows, whether you can self-host, latency overhead, which native features pass through, and how budgets are enforced.

The cost of abstraction

A common format is the intersection of what providers offer. Provider-specific features either disappear or travel as non-standard extensions.   • Use the common format for features that genuinely need to be portable, such as triage, enrichment and judges, and the native route for the answer path, which depends on caching.
  • Check that cache tokens appear in the gateway's usage records. If they are dropped, your cost reports overstate spend (L109).

Cost Engineering: Budgets, Routing and Batch Processing

50m video50m practice

Cost is a product metric like latency: measure it per request, user and feature, then pull the levers (smaller models, routing, shorter prompts and outputs, caching, batch processing) one at a time. Measure the quality change each one causes as well as the saving.

Cost per request, per user and per feature

The price of a call is tokens times per-token prices, summed over the token types the provider bills differently. Anthropic's usage reports uncached input_tokens, output_tokens, and separately cache_creation_input_tokens and cache_read_input_tokens (L24). Output tokens cost several times more than input tokens, so a verbose answer can cost more than a long prompt. Prices change often, so the code keeps them in a table you fill in from the current price page, and refuses to guess:

FIELDS = ("input", "output", "cache_write", "cache_read")
# USD per million tokens. Fill in from each provider's current price page; None on purpose.
PRICES = {
    "claude-haiku-5-5":  dict.fromkeys(FIELDS),
    "claude-sonnet-5-5": dict.fromkeys(FIELDS),
    "claude-opus-5-5":   dict.fromkeys(FIELDS),
}
BATCH_DISCOUNT = None            # fraction off for batch jobs; see the price page

def cost(model: str, usage: dict, *, batch: bool = False, prices=PRICES) -> float:
    p = prices[model]
    if None in p.values() or (batch and BATCH_DISCOUNT is None):
        raise ValueError(f"fill in prices for {model!r} from the provider's current price page")
    usd = (usage["input_tokens"] * p["input"] + usage["output_tokens"] * p["output"]
           + (usage.get("cache_creation_input_tokens") or 0) * p["cache_write"]
           + (usage.get("cache_read_input_tokens") or 0) * p["cache_read"]) / 1e6
    return usd * (1 - BATCH_DISCOUNT) if batch else usd

Routing by difficulty, and cascades

Derivation · expected cost

Let \(c_S, c_L\) be the costs of a request on the small and large model. A router sends a share \(s\) to the small model up front. A cascade always tries the small model and escalates a share \(e\) when a check fails (no citation, low confidence, schema error):

$$C_{\text{route}} = s\,c_S + (1-s)\,c_L, \qquad C_{\text{cascade}} = c_S + e\,c_L .$$

The cascade beats all-large only if \(e < 1 - c_S / c_L\). It also adds the small call's latency to every escalated request. The router costs nothing extra per request, but its mistakes are silent.

Start with a rule-based router and an evaluation on fixtures. The fixtures are your last offline eval run, which records for each question whether each model was judged correct. Cost is expressed relative to all-large with the price ratio \(r = c_L / c_S\) left as a parameter, because the real ratio comes from your price table.

Latency Engineering: Time to First Token, Parallelism and Speculation

45m video45m practice

Latency is a critical path through a graph of calls. Cut it by running independent calls concurrently, by making the calls on the path shorter (fewer output tokens, smaller models, cached prefixes), and by showing progress while the rest finishes.

Time to first token vs total time

Definition

For one model call, time to first token (TTFT) is network plus queueing plus prefill (plus thinking, if enabled). Total time adds one decode step per output token:

$$T_{\text{total}} \approx \underbrace{T_{\text{net}} + T_{\text{queue}} + T_{\text{prefill}}(n_{\text{in}})}_{\text{TTFT}} + n_{\text{out}}\, t_{\text{tok}}$$

Prefill grows with the input length \(n_{\text{in}}\) but runs in parallel across tokens. Decode is sequential, so total time is roughly linear in \(n_{\text{out}}\) (L8). For a request, TTFT is everything before the answer's first token: rewriting, retrieval, tools, guardrails, earlier model calls.

With streaming (L105), users feel the request's TTFT and then read at the decode rate. Without streaming, they feel the total. Track both at p50 and p95 per feature. The p95 is where users give up, and it is dominated by the slowest step plus tail jitter, not by averages.

Shorter outputs and small models for intermediate steps

Decode time scales with output tokens, so the cheapest latency win is often an instruction ("answer in at most five sentences, then the citations") plus a tighter max_tokens, checked with a completeness eval. Intermediate steps such as query condensation, routing and extraction rarely need the large model: a small model has lower TTFT and decodes faster. Ask intermediate steps for compact outputs, such as an ID or a short JSON object, not prose. For reasoning models, a lower effort or thinking budget on easy requests cuts the hidden decode time (L11).

Server-side techniques, caching and regions

  • Speculative decoding (overview). A small draft model proposes several tokens. The large model verifies them in one parallel forward pass and keeps the longest accepted prefix. The output distribution is unchanged, and decode gets faster when drafts are usually accepted (Leviathan et al. 2023; Chen et al. 2023). Providers and serving engines apply it internally; on your own models it is a serving option (L118). Related server-side work includes continuous batching and prefix caching.
  • Prompt caching for TTFT. A cached prefix skips most of its prefill, so long stable system prompts and tool definitions stop costing time on every request (L24). Order the prompt with stable parts first.
  • Regional endpoints. Run your API in the same region as the model endpoint (cloud platforms offer regional deployments), and keep a single long-lived client so connections are reused. Each cross-ocean round trip adds tens of milliseconds or more.

Perceived latency

When the critical path cannot get shorter, change what the user waits for. Stream the answer and status events (L105). Show the sources as soon as retrieval ends. Use optimistic UI: render the question, a skeleton for the answer and the cancel button immediately. Start retrieval on the raw query while the condensation call runs, and keep the result if the condensed query barely differs. That is speculation at the application level: you spend a little extra work to save time.

What breaks in production
  • Optimising averages. The p50 improves and the p95 does not, because the slow step is a tail event (cold index shard, rate-limit retry).
  • Unbounded fan-out. Parallel calls for every sub-question hit rate limits and create queueing, which is slower than sequential. Cap concurrency with a semaphore.
  • Orphaned tasks. With bare gather, one failure leaves siblings running and billing. Use TaskGroup or cancel explicitly.
  • Sync calls in async code. One blocking SDK or database call stalls every request on that worker. Use async clients or asyncio.to_thread.
  • Caching broken by a timestamp. Putting the current time at the top of the system prompt invalidates the prefix cache on every request, raising TTFT for everyone.

Caching Beyond Prompts: Exact, Semantic and Tool-Result Caches

40m video45m practice

A response cache skips the model entirely, which makes it the biggest cost and latency saving available, and the most dangerous one. A cached answer served to the wrong question, the wrong user or after the docs changed is a confident wrong answer. Measure the wrong-hit rate, not just the hit rate.

Exact-match response caches

Prompt caching (L24) still runs the model; it only skips prefill on a repeated prefix. A response cache returns a stored answer without calling the model at all. The safe version matches exactly: normalise the query (case, whitespace, trailing punctuation) and hash it together with everything else that can change the right answer. Exact caches pay off on FAQ-style traffic, page reloads, client retries and eval re-runs. They can never serve an answer to a different question, but they can serve one to a different context if the key is incomplete.

What goes in the key
  • Model ID and prompt version. A new prompt (L21) must not serve the old prompt's answers.
  • Permission scope. Tenant and the user's document-access set (L47). Two users asking the same words may be allowed to see different sources.
  • Index version. A blunt but safe way to invalidate everything on re-index. Tag-based invalidation, below, is finer.
  • Conversation state, if used. A follow-up such as "and for StatefulSets?" means nothing without its history. Cache only the condensed standalone query (L46).

Semantic caches and false hits

Definition

A semantic cache embeds each query and returns a stored answer when the most similar cached query has cosine similarity \(\cos(q, q') \ge \tau\). The threshold \(\tau\) trades hit rate against false hits: cached answers to queries that look similar but need a different answer.

Similarity is not equivalence. "Delete a Pod" and "delete a Deployment" differ in one word and need different commands. "All namespaces" and "one namespace" differ in one flag. Embedding models place such pairs close together, often closer than genuine paraphrases. The code below uses a character-trigram stand-in for an embedding model, so the replay runs anywhere. It adds a guard: the answer-changing terms (resource kind, verb, scope) must match exactly, as well as the tenant.

import hashlib, json, re
import numpy as np

def norm(q: str) -> str:
    return re.sub(r"\s+", " ", q.lower()).strip(" ?!.")

def cache_key(q: str, *, model: str, prompt_version: str, scope: str, index_version: str) -> str:
    """Everything that can change the right answer goes into the key."""
    return hashlib.sha256(json.dumps([norm(q), model, prompt_version, scope, index_version]).encode()).hexdigest()

def embed(text: str, dim: int = 512) -> np.ndarray:
    """Stand-in for an embedding model (L28): hashed character trigrams, unit length."""
    t = f"  {norm(text)}  "
    v = np.zeros(dim)
    for i in range(len(t) - 2):
        v[int(hashlib.md5(t[i:i + 3].encode()).hexdigest(), 16) % dim] += 1
    return v / np.linalg.norm(v)

CRITICAL = {"pod", "deployment", "node", "namespace", "all", "one", "cpu", "memory",
            "list", "delete", "drain", "cordon", "pending", "crashloopbackoff"}

def terms(q: str) -> set:
    """Words that change the answer if they differ: resource kind, verb, scope."""
    return {w.rstrip("s") for w in re.findall(r"[a-z]+", norm(q))} & CRITICAL

class SemanticCache:
    def __init__(self, threshold: float, guard: bool = False):
        self.threshold, self.guard, self.vecs, self.items = threshold, guard, [], []
    def get(self, q: str, scope: str):
        if not self.items:
            return None
        sims = np.array(self.vecs) @ embed(q)
        for i in np.argsort(-sims):
            if sims[i] < self.threshold:
                return None
            it = self.items[i]
            if it["scope"] == scope and (not self.guard or terms(it["q"]) == terms(q)):
                return it                                # same tenant, same critical terms
        return None
    def put(self, q: str, scope: str, answer: str, sources: set):
        self.vecs.append(embed(q))
        self.items.append({"q": q, "scope": scope, "answer": answer, "sources": sources})
    def invalidate(self, changed_docs: set):
        keep = [i for i, it in enumerate(self.items) if not it["sources"] & changed_docs]
        self.vecs, self.items = [self.vecs[i] for i in keep], [self.items[i] for i in keep]

Tool-result caches with expiry

Tool calls are often slower than the model, and many are pure reads: an API reference lookup, a docs fetch, cluster status. Cache them per (tool, scope, arguments), each tool with its own time to live. The TTL should match how fast the underlying data changes. Never cache tools with side effects.

import json, time

class ToolCache:
    """Tool results keyed by (tool, scope, args), each tool with its own time to live."""
    TTL = {"kubectl_explain": 24 * 3600, "cluster_status": 30, "create_ticket": 0}  # 0: never cache
    def __init__(self, clock=time.monotonic):
        self.clock, self.data = clock, {}
    def call(self, tool: str, fn, scope: str, **args):
        ttl = self.TTL.get(tool, 0)
        key = (tool, scope, json.dumps(args, sort_keys=True))
        hit = self.data.get(key)
        if ttl and hit and self.clock() - hit[0] < ttl:
            return hit[1]
        value = fn(**args)
        if ttl:
            self.data[key] = (self.clock(), value)
        return value

Invalidation when documents change

Tag every cached answer with the IDs of the documents it cited. When ingestion re-indexes or deletes a page (L48), it publishes the changed IDs, and the cache drops every entry tagged with them (invalidate above: 13 entries become 11). Also set a maximum age on every entry as a backstop for changes you failed to track, and bump the index version for a full re-embed.

What breaks in production
  • Cross-tenant leaks. A cache keyed on the question alone serves one customer's answer, with their sources, to another. Scope belongs in every key.
  • Thresholds tuned on paraphrases only. A test set without near-miss pairs reports no false hits. Include them on purpose.
  • Caching bad answers. A refusal, an error message or a thumbs-down answer gets cached and repeated. Store only answers that passed output checks, and evict on negative feedback.
  • Stale after re-index. No source tags, so updated docs keep producing old answers until the TTL expires.
  • Hidden personalisation. Answers that depend on the user's cluster or plan are cached as if they were general.

Queues and workers for agents and ingestion

A research agent that runs for minutes, a re-index of a new Kubernetes release (L48) and batch enrichment (L109) all go on the asynchronous path (L104). The API enqueues and returns a job ID; workers claim jobs; the client follows progress over SSE (L105). The queue must survive a worker crash, which means leases, not deletes.

Algorithm · Lease-based job queue
  1. Enqueue with a caller-chosen job ID, so a retried enqueue is a no-op.
  2. Claim one job atomically: mark it running, increment its attempts, and set a lease expiry.
  3. Complete marks it done. A worker that dies never completes, its lease expires, and another worker claims the job again.
  4. After the maximum attempts, the job stays put as dead-lettered, for a human to inspect.
import json, sqlite3, time, uuid

class JobQueue:
    """Durable queue on one table. A claim takes a lease; if the worker dies, the job reappears."""
    def __init__(self, path: str = ":memory:", clock=time.time):
        self.db, self.clock = sqlite3.connect(path, isolation_level=None), clock
        self.db.execute("""CREATE TABLE IF NOT EXISTS jobs (id TEXT PRIMARY KEY, kind TEXT, payload TEXT,
            status TEXT DEFAULT 'queued', attempts INT DEFAULT 0, lease_until REAL DEFAULT 0)""")
    def enqueue(self, kind: str, payload: dict, job_id: str | None = None) -> str:
        job_id = job_id or uuid.uuid4().hex
        self.db.execute("INSERT OR IGNORE INTO jobs (id, kind, payload) VALUES (?, ?, ?)",
                        (job_id, kind, json.dumps(payload)))           # same id twice = one job
        return job_id
    def claim(self, lease_s: float = 60, max_attempts: int = 3):
        now = self.clock()
        return self.db.execute("""UPDATE jobs SET status = 'running', attempts = attempts + 1,
            lease_until = ? WHERE id = (SELECT id FROM jobs WHERE attempts < ? AND (status = 'queued'
            OR (status = 'running' AND lease_until < ?)) ORDER BY rowid LIMIT 1)
            RETURNING id, attempts""", (now + lease_s, max_attempts, now)).fetchone()
    def complete(self, job_id: str):
        self.db.execute("UPDATE jobs SET status = 'done' WHERE id = ?", (job_id,))

Secrets management

Secrets live in the platform's secret manager and reach containers at runtime as environment variables or mounted files, never in the image, compose file, repo or logs. Each environment has its own (L104), provider keys live only in the gateway (L108), and each key has an owner and a rotation date. Scan commits in CI; a leaked key means rotation, not deletion.

Canary releases and rollbacks for prompts and models

A prompt edit or model swap changes behaviour as much as code, yet ships without a deploy (L104), so gate it. Pass the offline evals in CI (L93), then raise the flag's percentage in stages, comparing canary and stable on live signals at each.

def canary_verdict(base: dict, canary: dict, *, min_n: int = 400,
                   max_error_ratio: float = 1.5, max_thumbs_down_rise: float = 0.02) -> str:
    """Compare a canary prompt/model with the stable one on live traffic."""
    if canary["n"] < min_n:
        return "wait"
    rate = lambda m, k: m[k] / m["n"]
    if rate(canary, "errors") > max_error_ratio * max(rate(base, "errors"), 0.002):
        return "rollback: errors"
    if rate(canary, "thumbs_down") - rate(base, "thumbs_down") > max_thumbs_down_rise:
        return "rollback: feedback"
    if canary["p95_ms"] > 1.2 * base["p95_ms"]:
        return "rollback: latency"
    return "promote to next stage"

What breaks in production
  • Jobs lost on deploy. Without leases, killed workers leave jobs "running" forever. On SIGTERM, stop claiming and finish or release the current job.
  • Image drift. With :latest tags and unpinned dependencies, "roll back" deploys something new. Tag by SHA; build from the lockfile.
  • Rollbacks that cannot roll back. A release that migrated the database or re-embedded the index in place cannot be reverted. Make data changes additive.
  • Canary on the wrong traffic. Bucketing by request instead of user mixes versions inside one conversation and hides the effects of a prompt on follow-ups.

Product Patterns: UX for Uncertainty, Feedback and Trust

45m video35m practice

Users trust an assistant that shows its evidence, admits its limits and is easy to correct, and they stop using one that is confidently wrong. The interface has to carry the uncertainty that the model's prose hides.

Definition · appropriate reliance

The goal is not maximum trust but calibrated trust. Users should rely on DocPilot when it is right and notice when it is wrong. Over-reliance means accepting wrong answers; under-reliance means re-checking or ignoring right ones. Every pattern below either gives users evidence to tell the two cases apart, or makes acting on a wrong answer cheap to undo.

Designing for non-deterministic output

The same question can get differently worded answers on different days, and a regenerated answer may disagree with the first. Design so that this is unsurprising rather than alarming:

  • Keep the shape stable even when the words vary: a fixed answer structure (short answer, steps, citations) from structured output (L20) makes answers comparable.
  • Make regeneration explicit, and keep earlier versions visible, so users can compare and pick.
  • Never present an answer as a lookup result. Copy such as "DocPilot's answer, based on these pages" frames it correctly. "The answer" does not.
  • Treat formatting failures as failures: a half-rendered table or broken code block costs more trust than a slow answer (L105).

Showing sources and uncertainty

Inline citations that open the exact passage (L45) let users verify in seconds. They are the single most effective trust feature for a documentation assistant. Uncertainty is harder. A model's self-reported confidence is poorly calibrated (L12), so do not show "92% confident". Show evidence signals the system can actually measure: no relevant sources, sources that conflict, sources for a different version than the user asked about, an answer cut off by max_tokens.

Drive these states from signals in code, so they are testable and consistent:

from enum import Enum
from pydantic import BaseModel, Field, ValidationError

def ui_state(*, n_citations: int, top_score: float, stop_reason: str, version_match: bool) -> str:
    """Map evidence signals (not the model's self-reported confidence) to what the UI shows."""
    if stop_reason == "refusal":
        return "decline: say what DocPilot cannot help with, offer a human"
    if n_citations == 0 or top_score < 0.35:            # threshold tuned on the eval set (L44)
        return "no answer: say so, show nearest docs and example questions"
    if stop_reason == "max_tokens":
        return "partial: label as cut off, offer 'continue'"
    if not version_match:
        return "caveat: docs are for a different Kubernetes version"
    return "answer: with inline citations"

Letting users correct and steer, with undo and confirmations

Give users handles that map to things the system can act on. "Edit question" re-runs with the edited text. A version picker becomes a metadata filter (L33). "Shorter" or "show commands only" become format instructions. Suggested follow-ups move the conversation forward without typing. Thumbs-down asks for a reason in one tap, with an optional correction, and both are stored against the trace for evals (L94). For agent actions, show a preview before anything changes (the ticket that will be filed, the diff that will be applied) and confirm side effects explicitly (L78). Where possible, offer undo instead of a confirmation, because users click through confirmations they see too often.

Progressive disclosure of agent steps

Show agent work as one collapsed line by default ("Searched docs · read 3 pages · ran kubectl explain"). It expands into the step list from the streamed tool_call and tool_result events (L105), and each step expands into its inputs and a truncated output. Most users never open it. The ones who do are checking whether to trust the answer, and the steps tell them. Long-running jobs (L112) need the same view as a progress page, plus a notification when they finish.

Empty states, failure messages and stated limits

Patterns
  • Empty state. Three example questions that show the scope ("Why is my Pod Pending?", "How do I drain a node?", "What changed in v1.31?"). They also teach phrasing.
  • Stated limits. One line under the input box: what DocPilot reads (public Kubernetes docs and your tickets), and what it cannot do (see your cluster, make changes without approval).
  • No answer. "I couldn't find this in the docs" plus the nearest pages. This beats a fluent guess every time (L45).
  • Failures. Specific, honest and actionable: "The model provider is overloaded; here are the top matching pages, and you can retry in a minute" (L107). Never a raw stack trace, never a silent spinner.

Measuring trust and adoption

Thumbs ratings are sparse and skewed toward unhappy users, so combine them with implicit signals. Useful ones include citation click-through, copying an answer or command, immediate reformulation of the same question (a sign of failure), escalation to a human, and abandonment mid-stream. Adoption is the share of eligible users active weekly, and whether they come back. Watch for over-trust as well as distrust: a high thumbs-up rate on answers that sampled audits find wrong means users have stopped checking. Treat that as a defect in the citation and caveat design.

What breaks in production
  • Citations that do not support the claim. One unsupported citation, once noticed, discredits all the others. Check faithfulness (L51) before showing.
  • Caveats on everything. A warning on every answer is noise users learn to ignore. Show caveats only when a measured signal fires.
  • Feedback with no loop. Thumbs-down data that nobody triages teaches users that feedback is pointless. Close the loop visibly ("fixed in this week's update").
  • Hidden agent actions. An agent that files tickets without a preview loses trust permanently after its first wrong ticket.
