Orientation and the LLM API

Phase 0 builds the workbench the rest of the course stands on: a reproducible Python project, one logged door for every model call, and the habit of measuring before changing anything. You learn the shape of the Messages API, what tokens cost and how long they take, and how to choose a model on evidence, then start DocPilot with a frozen corpus, 30 eval questions and a baseline score. Phase 1 opens up the model to explain the behaviour you measure here.

By the end of this phase you can

L1 · DAY 1

What AI Engineering Is (and Isn't)

35m video30m practice

AI engineering is building products on top of foundation models that someone else trained. You rarely touch the weights. The work is in the system around the model, and because the model's outputs are open-ended and vary from run to run, measuring that system is the centre of the job.

Three jobs that share a toolbox

Data science, ML engineering and AI engineering all use Python, notebooks and statistics, but they start from different places and spend their time on different problems.

Data scienceML engineeringAI engineering
Starts froma question about dataa labelled dataseta pretrained model behind an API or in open weights
Main outputan analysis or a decisiona trained model in productiona product feature that uses a model
Model workfit and interpretdesign, train, tunechoose, prompt, ground, adapt; train only when needed
Hard partcausal and statistical validitydata pipelines, training, driftopen-ended outputs, evaluation, cost, latency, safety
Order of workdata → analysisdata → model → productproduct → data → model

The last row is the important one. In classical ML you could not ship anything until you had data and a trained model. With a foundation model you can put a working prototype in front of users on day one, then collect data and invest in models only when the product has earned it. Chip Huyen's AI Engineering (ch. 1) makes this point in detail.

Definition

Foundation model: a large model trained on broad data that can be adapted to many tasks by prompting, retrieval or fine-tuning. AI engineering: the discipline of turning foundation models into reliable, affordable, safe software: prompts and context, retrieval, tools and agents, evaluation, security and operations.

The three layers of the stack

An AI product has three layers. Most of this course lives in the top one, but you need enough of the other two to make good decisions about cost, latency and when to fine-tune.

  • Application: what the user sees and everything that shapes the model's input and checks its output. Prompts, retrieved context, tool definitions, agent loops, evaluators, guardrails, the UI.
  • Model: the weights and how they were made. You pick models here and, occasionally, adapt them (LoRA, distillation, preference tuning in Phase 11).
  • Infrastructure: serving, GPUs, vector databases, gateways, logging and tracing. Hosted APIs hide most of it until you self-host or scale.

Open-ended and non-deterministic outputs

Ordinary software maps an input to one correct output, so a unit test can assert equality. A model answering "how do I drain a node?" can be right in a hundred wordings, wrong in a thousand plausible ones, and give a different wording on every call. Four things change:

  • Tests become graders. You check properties (mentions kubectl drain, cites a real page, valid JSON) or ask a second model to judge (Phase 8), not exact strings.
  • Results are rates. "It works" means "it passes 92% of a representative set", and the set's size limits how precisely you know that.
  • Failures look like successes. A wrong answer is fluent and confident. Nothing throws an exception.
  • Inputs are unbounded. Users type anything, including instructions aimed at your model (Phase 9).
Worked example · reliability compounds

A pipeline rewrites the question, retrieves, answers, then formats. If each step is right 95% of the time and errors are independent, the whole pipeline is right \(0.95^4 \approx 0.81\) of the time; at five steps it is \(0.95^5 \approx 0.77\). Raising each step to 99% gives \(0.99^5 \approx 0.95\). Every step you add needs its own measurement, which is why agents (Phase 7) come after evaluation habits are in place.

The core loop: build, evaluate, improve

Algorithm · The AI engineering loop
  1. Build the simplest version that could work: one prompt, one model call.
  2. Evaluate it on a fixed set of realistic inputs with an explicit pass criterion. Read the failures yourself.
  3. Improve the component the failures point at (prompt, context, retrieval, tool, model), then re-run the same evaluation.
  4. Ship when the evaluation clears the bar you set before building; keep evaluating on live traffic.

Without step 2 the loop degenerates into editing a prompt until the last example you tried looks good. A small, honest eval set beats intuition from the first day. Here is the shape every evaluation in this course takes, with a stand-in for the model:

from dataclasses import dataclass
from typing import Callable

@dataclass
class Case:
    question: str
    must_mention: list[str]          # facts a correct answer has to contain

def evaluate(answer: Callable[[str], str], cases: list[Case]) -> float:
    """Fraction of cases whose answer mentions every required fact."""
    passed = 0
    for c in cases:
        out = answer(c.question).lower()
        ok = all(term.lower() in out for term in c.must_mention)
        passed += ok
        print("PASS" if ok else "FAIL", c.question)
    return passed / len(cases)

cases = [
    Case("How do I drain a node before maintenance?", ["kubectl drain"]),
    Case("What does a failing liveness probe cause?", ["restart"]),
    Case("Which object gives a set of pods a stable IP?", ["service"]),
]

def baseline(q: str) -> str:            # stand-in for a model call (L3)
    return "Run kubectl drain NODE --ignore-daemonsets." if "drain" in q else "Not sure."

print(f"pass rate: {evaluate(baseline, cases):.2f}")
PASS How do I drain a node before maintenance?
FAIL What does a failing liveness probe cause?
FAIL Which object gives a set of pods a stable IP?
pass rate: 0.33

Swap baseline for a real model call and this is the seed of DocPilot's eval suite (L6). Phase 8 replaces substring checks with stronger graders.

What breaks in production
  • The demo trap. Five hand-picked questions work, so it ships. Real traffic contains the other 95% of questions. Write the eval set before the prompt.
  • Starting at the wrong layer. Fine-tuning or self-hosting before a prompt-plus-retrieval baseline exists spends weeks to solve a problem you have not measured.
  • Ignoring the cost of being wrong. A wrong product description is an annoyance; a wrong dosage or a deleted cluster is an incident. That cost sets how much checking, human review and refusal the feature needs.
  • No logs. If you cannot say which model, prompt and context produced a bad answer, you cannot fix it. L2 makes logging the default.

Practice · 30 min

  1. Pick a product idea you care about (or use DocPilot). Name the user and the one task the model does for them, in a sentence.
  2. List the inputs the model sees (user text, documents, history, tool results) and the output it must produce (prose, JSON, an action).
  3. Write the cost of a wrong answer in concrete terms, and what the feature should do when unsure (refuse, ask, escalate to a human).
  4. Write how you would know it works: five example inputs with what a passing output must contain, and the pass rate you would need before shipping.
  5. Mark which stack layer each part of your canvas touches. If anything needs the model layer, write why prompting and retrieval would not be enough.

Ship: a one-page AI feature canvas, and a two-minute explanation of where AI engineering sits and why evaluation is at its centre.

L2 · DAY 1

Your Workbench: Python, uv, API Keys and Cost Tracking

40m video45m practice

Set up the project so that it is reproducible, keeps secrets out of git, and sends every model call through one function that records what the call cost. Retrofitting any of these later is far harder than starting with them.

Python 3.12 with uv

uv manages the Python version, the virtual environment and the dependencies of a project from one tool. Three files carry the state: pyproject.toml (what you asked for), uv.lock (exactly what was resolved, with hashes) and .python-version. Commit all three.

uv init docpilot && cd docpilot      # pyproject.toml, .python-version, git repo
uv python pin 3.12
uv add anthropic openai httpx           # updates pyproject.toml and uv.lock, syncs .venv
uv add --dev pytest
uv run python -m docpilot.ledger        # runs inside the project's env, syncing first
uv sync --locked                        # in CI: fail if uv.lock is out of date
uv lock --upgrade-package anthropic     # upgrade one dependency deliberately
Definition · lockfile

A lockfile pins every direct and transitive dependency to an exact version and hash. Two machines that run uv sync on the same lockfile get the same environment. This matters more than usual here: LLM SDKs ship often, and a minor release can change defaults or rename parameters.

Keys, environment variables and .env

The Anthropic client reads ANTHROPIC_API_KEY from the environment, so the key never needs to appear in code. Keep real values in a git-ignored .env, and commit a .env.example with the names only:

# .env.example  (copy to .env, which is in .gitignore along with logs/ and .venv/)
ANTHROPIC_API_KEY=
DOCPILOT_LOG=logs/calls.jsonl

uv run --env-file .env python -m docpilot.cli
Secrets hygiene
  • Use a separate key per project and per environment (dev, CI, prod), and set a spend limit on the dev key in the provider console.
  • Turn on secret scanning: GitHub secret scanning with push protection, or a pre-commit hook such as gitleaks. These tools recognise many providers' key formats.
  • If a key reaches a commit, revoke it in the console first. Rewriting git history does not help once it has been pushed or cloned.
  • Notebooks are the usual leak: a cell that prints the environment, saved with its output. Clear outputs before committing.

Notebooks for exploring, modules for keeping

Notebooks are good for poking at a response or plotting latencies. Anything you will run twice belongs in a module with a test, and notebooks import it. The repo follows the course layout:

docpilot/            # the package: llm.py today, search.py, tools.py later
prompts/  evals/  ingest/  services/  infra/  lab/  notebooks/
logs/calls.jsonl     # git-ignored; one line per model call

Three SDKs cover the course: anthropic for the reference provider; openai, used as a client for OpenAI-compatible servers such as Ollama and vLLM that serve open models (L5, Phase 11); and httpx for plain HTTP when no SDK fits. As of anthropic 1.13 the SDK is built on a package named httpx2, so a custom http_client= must be an httpx2.Client; the SDK raises a TypeError if you pass an httpx.Client.

One door for every model call

"""docpilot/llm.py: every model call goes through here and leaves one log line."""
import json
import os
import time
import uuid
from datetime import datetime, timezone
from pathlib import Path

import anthropic

MODEL, SMALL, LARGE = "claude-sonnet-5-5", "claude-haiku-5-5", "claude-opus-5-5"
client = anthropic.Anthropic()                       # reads ANTHROPIC_API_KEY
LOG_PATH = Path(os.environ.get("DOCPILOT_LOG", "logs/calls.jsonl"))

# USD per million tokens, copied by hand from the provider's price page.
# None means "not filled in yet": the log then says null, never a fake 0.
PRICES_AS_OF = "YYYY-MM-DD"
PRICES: dict[str, dict[str, float | None]] = {
    m: {"input": None, "output": None, "cache_write": None, "cache_read": None}
    for m in (MODEL, SMALL, LARGE)
}

def _tokens(u) -> dict[str, int]:
    return {"input": u.input_tokens, "output": u.output_tokens,
            "cache_write": u.cache_creation_input_tokens or 0,
            "cache_read": u.cache_read_input_tokens or 0}

def est_cost(model: str, usage) -> float | None:
    p = PRICES.get(model)
    if p is None or None in p.values():
        return None
    return sum(n * p[k] for k, n in _tokens(usage).items()) / 1e6

def _log(model, feature, prompt_version, t0, msg=None, err=None, **extra) -> None:
    rec = {"ts": datetime.now(timezone.utc).isoformat(timespec="seconds"),
           "trace_id": uuid.uuid4().hex[:16], "feature": feature,
           "prompt_version": prompt_version, "model": model,
           "latency_ms": round((time.perf_counter() - t0) * 1000), **extra}
    if msg is not None:
        rec |= {"served": msg.model, "stop_reason": msg.stop_reason,
                "usage": _tokens(msg.usage), "est_cost": est_cost(model, msg.usage)}
    if err is not None:
        rec["error"] = type(err).__name__
    LOG_PATH.parent.mkdir(parents=True, exist_ok=True)
    with LOG_PATH.open("a", encoding="utf-8") as f:
        f.write(json.dumps(rec) + "\n")

def chat(messages, *, system=None, model=MODEL, max_tokens=1024,
         feature="dev", prompt_version="none", **kw) -> anthropic.types.Message:
    if system is not None:              # omit rather than send null
        kw["system"] = system
    t0 = time.perf_counter()
    try:
        msg = client.messages.create(model=model, max_tokens=max_tokens,
                                     messages=messages, **kw)
    except anthropic.APIError as e:
        _log(model, feature, prompt_version, t0, err=e)
        raise
    _log(model, feature, prompt_version, t0, msg=msg)
    return msg

def text_of(msg) -> str:
    return "".join(b.text for b in msg.content if b.type == "text")

Tested against a local fake API (an httpx2.MockTransport, no network) with placeholder prices of 1.0 per million input and 5.0 per million output tokens, which are not real prices, one call logs:

{"ts": "2026-10-11T15:28:08+00:00", "trace_id": "bbe2e0cfc00f4fbe", "feature": "l2-demo",
 "prompt_version": "v0", "model": "claude-sonnet-5-5", "latency_ms": 2, "served": "claude-sonnet-5-5",
 "stop_reason": "end_turn", "usage": {"input": 412, "output": 96, "cache_write": 0, "cache_read": 0},
 "est_cost": 0.000892}
Worked example · the cost formula

With per-million prices \(p_\text{in}, p_\text{out}, p_\text{cw}, p_\text{cr}\) and the four token counts from usage,

$$\text{cost} = \frac{n_\text{in}\,p_\text{in} + n_\text{out}\,p_\text{out} + n_\text{cw}\,p_\text{cw} + n_\text{cr}\,p_\text{cr}}{10^6}.$$

Above: \((412 \times 1.0 + 96 \times 5.0)/10^6 = 0.000892\). input_tokens counts only the uncached part of the prompt; cache writes and reads are reported separately and priced differently, which is why the wrapper logs all four (caching is L24).

A tiny cost ledger

"""docpilot/ledger.py: what did we spend?  uv run python -m docpilot.ledger feature"""
import json
import sys
from collections import defaultdict
from pathlib import Path

from docpilot.llm import LOG_PATH

def ledger(path=LOG_PATH, by: str = "model") -> dict[str, dict]:
    rows = defaultdict(lambda: dict(calls=0, errors=0, tok_in=0, tok_out=0,
                                    cost=0.0, unpriced=0))
    for line in Path(path).read_text(encoding="utf-8").splitlines():
        r = json.loads(line)
        row = rows[str(r.get(by))]
        row["calls"] += 1
        if "error" in r:
            row["errors"] += 1
            continue
        u = r["usage"]
        row["tok_in"] += u["input"] + u["cache_write"] + u["cache_read"]
        row["tok_out"] += u["output"]
        if r["est_cost"] is None:
            row["unpriced"] += 1
        else:
            row["cost"] += r["est_cost"]
    return dict(rows)

if __name__ == "__main__":
    for key, r in ledger(by=sys.argv[1] if len(sys.argv) > 1 else "model").items():
        print(f"{key:18} {r['calls']:4} calls {r['errors']:2} err {r['tok_in']:8} in "
              f"{r['tok_out']:7} out  USD {r['cost']:.4f}  {r['unpriced']} unpriced")
l2-demo               3 calls  1 err      824 in     192 out  USD 0.0009  1 unpriced

Three fake calls: one before the price table was filled (unpriced), one priced, one rejected with a 400 (logged as an error, then re-raised).

What breaks in production
  • Silent zeros. A model missing from the price table that logs cost 0 makes the ledger look cheap. Log null and count unpriced calls, as above.
  • Uncounted cache tokens. Summing only input_tokens under-reports both tokens and spend once caching is on.
  • Bypassing the wrapper. One script that calls the SDK directly is one blind spot in the bill. Grep for messages.create in review.
  • Logging content by default. Prompts and answers can carry customer data. Log metadata now; content logging needs redaction and retention rules (Phase 9, Phase 10).
  • Stale prices. Record PRICES_AS_OF and re-check it when the bill and the ledger disagree.

  3. Write docpilot/llm.py and docpilot/ledger.py. Fill PRICES from the current price page and set PRICES_AS_OF.

L3 · DAY 2

The First API Call: Messages, Roles, Parameters and Streaming

45m video50m practice

A Messages API call is a stateless function from a transcript to the next assistant turn. Learn the request fields, read stop_reason and usage on every response, stream long outputs, and retry only the errors that can succeed on a second try.

The request

Definition · a Messages request
  • model: which model, by ID. max_tokens: a hard cap on output tokens for this call; generation stops there even mid-sentence.
  • system: instructions that frame the whole conversation. It is a separate field, not a role.
  • messages: the transcript, turns with role "user" or "assistant", normally starting with a user turn and alternating (consecutive same-role turns are merged into one).
  • Content: a string, or a list of typed content blocks: text, image and document (L14), tool_use and tool_result (Phase 6). A string is shorthand for one text block.
  • stop_sequences: strings that end generation when the model produces them.
from docpilot.llm import chat, text_of

msg = chat(
    [{"role": "user", "content": "How do I drain a node before maintenance?"}],
    system="You are DocPilot. Answer in at most five lines.",
    max_tokens=300,
    stop_sequences=["\n\nUser:"],
)
print(msg.stop_reason, msg.usage.input_tokens, msg.usage.output_tokens)
print(text_of(msg))

The response and why it stopped

A Message has content (a list of blocks: text, plus thinking or tool_use when those features are on), model (what actually served the call), stop_reason, stop_sequence (which one matched, if any) and usage (input_tokens, output_tokens, and the two cache counters from L2). Check stop_reason before you trust the text.

Stop reasonMeaningWhat your code does
end_turnthe model finished its answeruse it
max_tokenshit your cap; the output is truncatedraise the cap, ask for less, or continue; never parse truncated JSON as complete
stop_sequenceproduced one of your stop stringsread msg.stop_sequence; the string itself is not in the text
tool_usethe model wants you to run a toolrun it and reply with a tool_result (L61)
pause_turnthe API paused a long turn, typically one using server-side toolssend the conversation back, including the paused assistant content, to let it continue

model_context_window_exceededgeneration filled the context windowtrim the input (L4)

The quality and cost dials

Current Claude models do not expose sampling parameters. In anthropic 1.13, messages.create has no temperature, top_p or top_k argument, so passing one fails in Python before any request is sent:

TypeError: Messages.create() got an unexpected keyword argument 'temperature'

Sampling still matters for open models, and L9 teaches it there. On Claude, the dials are how much work the model does:

msg = chat(history, output_config={"effort": "low"})              # fewer tokens, faster, cheaper
msg = chat(history, thinking={"type": "adaptive"}, max_tokens=8000)  # model decides how long to think

output_config.effort takes "low" to "max"; thinking takes adaptive, enabled with a budget_tokens, or disabled. Thinking tokens are billed as output tokens and count toward max_tokens, so raise the cap when you turn thinking up. L11 covers when extra thinking pays for itself.

Statelessness: a conversation is history you resend

The API keeps no session. Each call sends the full transcript, and the reply is appended client-side before the next call. You can edit, trim or summarise history freely, and you pay for all of it on every turn.

Worked example · history grows quadratically

A 500-token system prompt, 150-token questions and 300-token answers. Turn \(n\) sends \(500 + 150n + 300(n-1) = 200 + 450n\) input tokens: 650 on turn 1, 4,700 on turn 10. Over ten turns that is \(\sum_{n=1}^{10}(200 + 450n) = 26{,}750\) input tokens against 3,000 output tokens. Context engineering (L23) trims this, and prompt caching (L24) makes the repeated prefix cheaper.

Streaming

With streaming the server sends the response as server-sent events while it is generated, so the user sees text after the time to first token rather than after the whole answer. The SDK's client.messages.stream(...) is a context manager: iterate .text_stream for text deltas, then call .get_final_message() for the assembled Message with stop_reason and usage. The SDK also refuses non-streaming requests it estimates could take longer than 10 minutes, so very large outputs must stream.

L3 adds stream_chat() to docpilot/llm.py. It reuses _log from L2 and records time to first token as well:

def stream_chat(messages, *, system=None, model=MODEL, max_tokens=1024, on_text=print,
                feature="dev", prompt_version="none", **kw) -> anthropic.types.Message:
    """Like chat(), but streams text to on_text as it arrives and logs ttft_ms."""
    if system is not None:
        kw["system"] = system
    t0, ttft = time.perf_counter(), None
    try:
        with client.messages.stream(model=model, max_tokens=max_tokens,
                                    messages=messages, **kw) as stream:
            for text in stream.text_stream:
                if ttft is None:
                    ttft = round((time.perf_counter() - t0) * 1000)
                on_text(text)
            msg = stream.get_final_message()
    except anthropic.APIError as e:
        _log(model, feature, prompt_version, t0, err=e)
        raise
    _log(model, feature, prompt_version, t0, msg=msg, ttft_ms=ttft)
    return msg

The SDK already retries connection errors, 408, 409, 429 and 5xx with exponential backoff, twice by default, and honours retry-after. Tune it with anthropic.Anthropic(max_retries=4, timeout=60) or per call with client.with_options(max_retries=0). Against the fake API, a single 429, 500, 503 or 529 succeeded on the second attempt; a 404 raised NotFoundError after one attempt. An error event in the middle of a stream raised APIStatusError after one request, with no retry and with the first chunk already printed. Your code has to handle that case itself. L107 adds budgets, circuit breakers and fallbacks.

The command-line client

"""docpilot/cli.py: uv run --env-file .env python -m docpilot.cli   (Ctrl-D quits)"""
import anthropic

from docpilot.llm import stream_chat

SYSTEM = "You are DocPilot, a concise assistant for Kubernetes questions."

def main() -> None:
    history: list[dict] = []
    billed_in = billed_out = 0
    while True:
        try:
            user = input("\nyou> ").strip()
        except EOFError:
            break
        if not user:
            continue
        history.append({"role": "user", "content": user})
        try:
            msg = stream_chat(history, system=SYSTEM, feature="cli",
                              on_text=lambda t: print(t, end="", flush=True))
        except anthropic.APIError as e:      # the SDK has already retried what it can
            history.pop()                    # keep user/assistant turns alternating
            print(f"\n[{type(e).__name__}: turn dropped, try again]")
            continue
        if msg.content:
            history.append({"role": "assistant", "content": msg.content})
        else:
            history.pop()
        u = msg.usage
        billed_in, billed_out = billed_in + u.input_tokens, billed_out + u.output_tokens
        print(f"\n[{msg.stop_reason} | turn {u.input_tokens} in, {u.output_tokens} out"
              f" | session {billed_in} in, {billed_out} out]")

if __name__ == "__main__":
    main()

What breaks in production
  • Ignoring max_tokens stops. Truncated answers and half-closed JSON get shown or parsed as if complete. Branch on stop_reason every time.
  • Retrying 400s. A malformed request fails identically forever and burns rate limit. Retry only the classes in the table.
  • Retry storms. Your loop around the SDK's retries multiplies attempts. Pick one layer to own retries and add jitter.
  • Broken alternation. After a failed turn the history ends with two user turns, which get merged into one confusing turn. Pop the failed turn, as the CLI does.
  • Unbounded history. Cost and latency grow every turn until the window overflows. Budget it.

L4 · DAY 3

Tokens, Context Windows, Pricing and Latency

45m video45m practice

Models read and write tokens, and you pay and wait per token. Once you can count the tokens a feature sends and receives, its cost is arithmetic on the price page, and its latency is roughly time to first token plus output length divided by output speed.

Tokenisation: why tokens are not words

A tokenizer maps text to integer IDs from a fixed vocabulary. Most LLM tokenizers use byte-pair encoding (BPE) or a close relative, usually over bytes so that any input can be encoded.

Algorithm · BPE training
  1. Start with every word split into single symbols (bytes or characters), weighted by word frequency.
  2. Count every adjacent symbol pair across the corpus and merge the most frequent pair into a new symbol.
  3. Repeat until the vocabulary reaches its target size. To tokenize new text, replay the merges in the order they were learned.
from collections import Counter

def merge(sym: tuple, pair: tuple) -> tuple:
    out, i = [], 0
    while i < len(sym):
        if sym[i:i + 2] == pair:
            out.append(sym[i] + sym[i + 1]); i += 2
        else:
            out.append(sym[i]); i += 1
    return tuple(out)

def train_bpe(words: dict[str, int], n_merges: int) -> list[tuple]:
    vocab = {tuple(w) + ("_",): f for w, f in words.items()}   # "_" marks end of word
    merges = []
    for _ in range(n_merges):
        pairs = Counter()
        for sym, f in vocab.items():
            for pair in zip(sym, sym[1:]):
                pairs[pair] += f
        best = max(pairs, key=pairs.get)                         # most frequent adjacent pair
        merges.append(best)
        vocab = {merge(sym, best): f for sym, f in vocab.items()}
    return merges

def tokenize(word: str, merges: list[tuple]) -> list[str]:
    sym = tuple(word) + ("_",)
    for pair in merges:                                          # replay merges in order
        sym = merge(sym, pair)
    return list(sym)

corpus = {"low": 5, "lower": 2, "newest": 6, "widest": 3, "pods": 4, "nodes": 4}
merges = train_bpe(corpus, 10)
for w in ["lowest", "nodes", "kubectl"]:
    print(w, tokenize(w, merges))
lowest ['low', 'est_']
nodes ['n', 'od', 'es', '_']
kubectl ['k', 'u', 'b', 'e', 'c', 't', 'l', '_']

Frequent strings become single tokens; rare ones fall apart. Real vocabularies are far larger, so common English words are usually one token each, but the same effects follow:

  • Words are not the unit. Leading spaces, capitalisation and punctuation create distinct tokens; numbers split into chunks, which is one reason models fumble digit-level arithmetic.
  • Languages differ. Tokenizers trained mostly on English text need more tokens for the same meaning in many other languages and scripts, so the same feature can cost several times more and run slower.
  • Code differs. Indentation, brackets and identifiers like kubectl or podAntiAffinity tokenise unlike prose. YAML and JSON are token-hungry.
  • Tokenizers differ between providers. Per-token prices are not comparable across vendors. Compare cost per task.

Counting before you send

Rules of thumb such as "about four characters per English token" are fine for a napkin and wrong for budgets. Count. For Claude, client.messages.count_tokens takes the same model, messages, system and tools as a real call and returns input_tokens. Anthropic documents the count as an estimate that can differ slightly from billed usage. For open models, load the model's own tokenizer and count locally, or read usage.prompt_tokens from an OpenAI-compatible server's response.

"""docpilot/budget.py: count before you send."""
from docpilot.llm import MODEL, client

    if system is not None:
        kw["system"] = system
    return client.messages.count_tokens(model=model, messages=messages, **kw).input_tokens

The context window

Definition · context window

The maximum number of tokens the model can attend to in one call. Input and output share it: system prompt, tool definitions, the whole message history, images and documents, retrieved context, thinking tokens, and the answer itself.

Treat \(n_\text{in} + \texttt{max\_tokens} \le W\) as the budget. Depending on the model and API version, a request that breaks it is either rejected with a 400 or runs and stops with model_context_window_exceeded; check the context-window page for your model. Fitting is not the same as working well: quality on details buried in very long inputs degrades (L13).

Pricing structure

Never hard-code a price in your head; the structure is stable even when the numbers change. As of late 2026, a Claude bill is built from these line items, each priced per million tokens (MTok) on the price page:

Server-side tools (such as web search) can add per-use charges, and some models have had different rates above a long-context threshold. Read the price page for the model you actually call.

Latency anatomy

$$T_\text{total} \approx T_\text{TTFT} + \frac{n_\text{out}}{r_\text{out}}$$

Time to first token covers network, queueing and prefill, which processes the whole prompt in parallel and so grows slowly with input length. After that the model decodes one token at a time at roughly \(r_\text{out}\) tokens per second. Output length therefore dominates total latency (L8 explains why).

Estimating a feature's monthly cost

$$C_\text{month} = R \cdot \frac{n_\text{in}\,p_\text{in} + n_\text{out}\,p_\text{out}}{10^6},\qquad R = \text{users} \times \text{requests per user per day} \times 30$$

Split \(n_\text{in}\) into uncached, cache-write and cache-read parts once caching is on, exactly as est_cost does in L2.

from dataclasses import dataclass

@dataclass
class Tier:
    name: str
    p_in: float        # USD per million input tokens  (price page)
    p_out: float       # USD per million output tokens (price page)
    ttft_s: float      # median time to first token    (your logs)
    tok_per_s: float   # median output tokens/second   (your logs)

def estimate(t: Tier, *, n_in: int, n_out: int, req_per_month: int) -> dict:
    per_req = (n_in * t.p_in + n_out * t.p_out) / 1e6
    return {"tier": t.name, "per_req": per_req, "monthly": per_req * req_per_month,
            "latency_s": t.ttft_s + n_out / t.tok_per_s}

# PLACEHOLDERS, not real prices or speeds: replace from the price page and your logs.
tiers = [Tier("small", 0.5, 2, 0.4, 150), Tier("mid", 2, 8, 0.7, 80), Tier("large", 8, 32, 1.2, 50)]

Worked example · where the money goes

For the mid tier: input \(3000 \times 2 = 6000\), output \(400 \times 8 = 3200\), so \(9200/10^6 = 0.0092\) per request and \(0.0092 \times 60{,}000 = 552\) a month. Input is 65% of the bill even though output is pricier per token, because RAG prompts are long. That is why caching the stable prefix (L24) and retrieving fewer, better chunks (Phase 4) are the big levers here, while for a chat feature with long answers, capping output would be.

What breaks in production
  • Estimating with averages only. A p95 request with five times the context sets your latency SLO and a good share of the bill. Estimate from the distribution in your logs.
  • Forgetting hidden input. Tool definitions, long system prompts and resent history are billed on every call.
  • Thinking without a cap. Thinking tokens are output tokens: the most expensive kind, and slow.
  • Generous max_tokens as a budget. It is a ceiling, not a target, but a runaway answer will use all of it. Set it per feature.
  • Comparing token counts across providers. Different tokenizers, different counts for the same text.

Choosing a Model: Frontier, Small and Open-Weights

40m video40m practice

Pick models with your own evaluation, not with leaderboards: the right model for a step is the cheapest one that passes that step's evals at the latency it needs. Then pin it, log what actually served each call, and plan for the day it is retired.

Tiers and the trade-off

Providers ship families in tiers. As of late 2026 the course uses three Claude tiers, already named in llm.py: claude-haiku-5-5 (SMALL: cheap and fast), claude-sonnet-5-5 (MODEL: the default) and claude-opus-5-5 (LARGE: the hardest tasks). Moving up a tier buys capability on hard reasoning, long multi-step work and subtle instructions, and costs more per token and usually more time per token. Many steps in a real system are easy: classifying a ticket, rewriting a query, extracting fields. Those belong on the small tier; a few steps earn the large one.

Model cards, system cards and benchmarks

A model card states what a model is for: intended uses, modalities, context window, knowledge cutoff, languages, evaluations and known limitations; for open weights, also the licence and training-data summary. A system card (Anthropic and OpenAI publish them for major releases) goes further into safety: red-teaming results, dangerous-capability evaluations, refusal behaviour and the safeguards around deployment. Read them for facts that rule a model out, such as a missing modality, a too-early cutoff or weak support for your language, not to rank models.

Why leaderboards don't answer "is it good for my task"
  • Distribution mismatch. MMLU-style exams and coding benchmarks are not Kubernetes support questions with your retrieval and your prompt.
  • Contamination and saturation. Public test items leak into training data, and top models cluster within noise of each other.
  • Setup differences. Vendors report scores with their own prompts, scaffolds and thinking budgets.
  • Preference arenas reward style. Human votes favour length and formatting, which may not be what your users need.

Use public numbers to build a shortlist. Use your evals to choose. Phase 8 (L92) treats benchmarks properly.

The rule: the cheapest model that passes your evals

Algorithm · Model selection
  1. Fix the eval set and the pass bar before you look at any results.
  2. Run every shortlisted model on the same prompts with the same settings; log cost and latency (the wrapper does).
  3. Grade blind to the model name where you can.
  4. Discard models that miss the latency budget. Of the rest, pick the cheapest whose pass rate clears the bar; break ties on latency.
  5. Re-run whenever a new model ships, a model is deprecated, or the prompt changes.
"""docpilot/choose.py: the cheapest model that clears the bar."""
import csv
import math
import statistics
from collections import defaultdict

def wilson(k: int, n: int, z: float = 1.96) -> tuple[float, float]:
    p, d = k / n, 1 + z * z / n
    c = (p + z * z / (2 * n)) / d
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return c - h, c + h

def choose(path="evals/compare.csv", bar=0.85) -> str | None:
    rows = defaultdict(list)
    for r in csv.DictReader(open(path, encoding="utf-8")):
        rows[r["model"]].append(r)                # uses id, model, latency_ms, est_cost, grade
    report = []
    for m, rs in rows.items():
        k, n = sum(int(r["grade"]) for r in rs), len(rs)
        cost = statistics.fmean(float(r["est_cost"]) for r in rs)
        p50 = statistics.median(int(r["latency_ms"]) for r in rs)
        lo, hi = wilson(k, n)
        report.append((cost, m, k / n))
        print(f"{m:18} pass {k}/{n} = {k/n:.2f}  95% CI [{lo:.2f}, {hi:.2f}]  "
              f"cost/req {cost:.5f}  p50 {p50:.0f} ms")
    passing = sorted(r for r in report if r[2] >= bar)
    return passing[0][1] if passing else None

claude-opus-5-5    pass 19/20 = 0.95  95% CI [0.76, 0.99]  cost/req 0.01056  p50 6165 ms

Worked example · twenty prompts is triage, not proof

With \(n = 20\), the Wilson interval for 17/20 is \([0.64, 0.95]\) and for 19/20 is \([0.76, 0.99]\). They overlap heavily, so the data cannot tell these models apart, yet the decision flips between a bar of 0.85 and 0.90. Twenty hand-graded prompts are enough to drop a model that clearly fails and to see what kinds of mistakes each makes. Settling a close call needs a larger set (L87). A 20× cost gap, though, is visible at any sample size.

Pinning versions and planning for deprecation

A model ID is a dependency, like a package version. Providers publish dated snapshot IDs, moving aliases, or both; where a snapshot ID exists, pin it in production so behaviour does not change under you. The wrapper logs served (the response's model field) next to the requested model, so you can see what actually ran.

Models also retire. In SDK 1.13, client.models.retrieve(id) returns lifecycle ("active", "deprecated" or "retired"), deprecated_at and retires_at; according to the SDK's docstrings, a deprecated model is still callable by existing users but closed to new ones, and the retirement date can move until it happens. Check it at startup and in CI:

from docpilot.llm import LARGE, MODEL, SMALL, client

for model_id in (MODEL, SMALL, LARGE):
    info = client.models.retrieve(model_id)
    if info.lifecycle != "active":
        print(f"WARNING {model_id} is {info.lifecycle}, retires_at={info.retires_at}: "
              "re-run the eval suite on a successor")
What breaks in production
  • One model for everything. The large model on every step multiplies cost and latency for steps the small model passes.
  • Choosing on vibes or leaderboards. The model that wins a public arena can lose on your task. Without your own evals, you cannot tell.
  • Unpinned aliases. A silent upgrade changes output format or length and breaks parsing or the budget overnight.
  • Deprecation surprises. Retirement turns into a 404 in production. Track retires_at and keep the eval suite ready to qualify a successor.
  • Self-hosting for cost at low traffic. An idle GPU costs the same as a busy one.

"""ingest/snapshot.py: record exactly which docs you froze.
git clone --depth 1 https://github.com/kubernetes/website.git data/website
uv run python -m ingest.snapshot data/website"""
import hashlib
import json
import subprocess
import sys
from pathlib import Path

DOCS = "content/en/docs"

def doc_url(rel: str) -> str:
    """concepts/overview/components.md -> https://kubernetes.io/docs/concepts/overview/components/"""
    path = rel.removesuffix(".md").removesuffix("_index").rstrip("/")
    return f"https://kubernetes.io/docs/{path}/" if path else "https://kubernetes.io/docs/"

def manifest(repo: Path) -> dict:
    root = repo / DOCS
    files = {p.relative_to(root).as_posix(): hashlib.sha256(p.read_bytes()).hexdigest()
             for p in sorted(root.rglob("*.md"))}
    commit = subprocess.run(["git", "-C", str(repo), "rev-parse", "HEAD"],
                            capture_output=True, text=True, check=True).stdout.strip()
    digest = hashlib.sha256(json.dumps(files, sort_keys=True).encode()).hexdigest()
    return {"source": "https://github.com/kubernetes/website", "path": DOCS, "commit": commit,
            "license": "CC BY 4.0", "n_files": len(files), "digest": digest, "files": files}

if __name__ == "__main__":
    m = manifest(Path(sys.argv[1]))
    Path("corpus").mkdir(exist_ok=True)
    Path("corpus/MANIFEST.json").write_text(json.dumps(m, indent=1))
    print(f"{m['n_files']} files at {m['commit'][:12]}  digest {m['digest'][:12]}")

The seed eval set

Thirty questions you would expect real users to ask, each with a reference answer written from the docs, one to three facts a correct answer must contain, and the page that supports it. """evals/cases.py: the seed eval set, validated on load."""
from typing import Literal

from pydantic import BaseModel, Field, HttpUrl

class EvalCase(BaseModel):
    id: str = Field(pattern=r"^q\d{3}$")
    kind: Literal["howto", "concept", "troubleshoot", "version"]
    question: str = Field(min_length=10)
    reference: str = Field(min_length=20)          # what a correct answer says
    must_mention: list[str] = Field(min_length=1)  # facts a substring check can test
    source: HttpUrl                                # the doc page that supports it

def load_cases(path="evals/seed.jsonl") -> list[EvalCase]:
    with open(path, encoding="utf-8") as f:
        cases = [EvalCase.model_validate_json(line) for line in f if line.strip()]
    ids = [c.id for c in cases]
    assert len(ids) == len(set(ids)), "duplicate ids"
    return cases

The no-retrieval baseline

Ask the model each question with a plain system prompt and no documents. The result says how much the model already knows about Kubernetes, which is a lot, and where it fails: exact flags, version-specific behaviour, recent features. RAG (L39) has to beat this number on the same questions.

"""evals/baseline.py: DocPilot with no retrieval.  uv run python -m evals.baseline"""

from datetime import date

    k, n = sum(r["auto_pass"] for r in results), len(results)
    lo, hi = wilson(k, n)
    commit = json.loads(Path("corpus/MANIFEST.json").read_text())["commit"]
    report = {"date": date.today().isoformat(), "model": model, "prompt_version": PROMPT_VERSION,
              "corpus_commit": commit, "pass": k, "n": n, "ci95": [round(lo, 2), round(hi, 2)],
              "results": results}
    out = Path(f"evals/reports/baseline-{report['date']}.json")
    out.parent.mkdir(parents=True, exist_ok=True)
    out.write_text(json.dumps(report, indent=1))
    print(f"baseline {model}: {k}/{n} = {k / n:.2f}  95% CI [{lo:.2f}, {hi:.2f}]  -> {out.as_posix()}")
    by_kind = {}
    for r in results:
        by_kind.setdefault(r["kind"], []).append(r["auto_pass"])
    print("  " + "  ".join(f"{kd} {sum(v)}/{len(v)}" for kd, v in sorted(by_kind.items())))
    return report

Worked example · what 30 questions can show

The 95% Wilson interval for 15/30 is \([0.33, 0.67]\), and for 21/30 it is \([0.52, 0.83]\). Thirty questions can show a large jump, such as RAG fixing the version-specific failures, but not a 3-point tweak. A paired comparison is more sensitive: on the same 30 questions, count how many flipped from fail to pass and how many from pass to fail. Phase 8 grows the set and adds proper tests (L87).

What breaks in production
  • An unpinned corpus. Scores drift because the docs changed, not because DocPilot did. Every report records corpus_commit.
  • Questions written after seeing answers. You unconsciously write questions the model already handles. Write them first.
  • Trusting the substring check. A correct answer that phrases the flag differently fails; a wrong answer that mentions the right term passes. Read all 30 answers and fill hand_pass; fix the checks where they disagree (L88).
  • An easy eval set. If the bare model scores 95%, the set cannot show what retrieval adds. Include questions that need the docs.
