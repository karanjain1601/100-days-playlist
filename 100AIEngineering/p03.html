L28 · DAY 20

Embeddings: Meaning as Geometry

50m video45m practice

An embedding model maps a piece of text to a point in \(\R^d\) so that texts that answer each other land close together. Search then becomes nearest-neighbour geometry, and its failures are predictable from how the model was trained.

What an embedding is

Definition

An embedding model is a function \(f:\text{text}\to\R^d\). In most text embedding models a transformer encoder (L7) reads the tokens and pools the final hidden states, by averaging them or by taking one special token, into a single vector. \(d\) is fixed per model: a few hundred to a few thousand dimensions. One vector per chunk is a lossy summary. Everything the model did not encode is invisible to search.

DocPilot will embed every documentation chunk once, at index time, and every query at request time. Retrieval returns the chunks whose vectors are nearest to the query vector. The rest of this phase is about doing that fast (L31), combining it with keyword search (L34) and measuring it (L37).

How embedding models are trained

Modern text embedders are trained contrastively. They see pairs that should match, such as a question and its answer, a title and its body, or a query and a clicked passage, and learn to pull matching pairs together and push everything else apart. The cheap source of “everything else” is the rest of the batch. With \(B\) pairs in a batch, each query has one positive and \(B-1\) in-batch negatives, and the loss is a softmax over the batch (InfoNCE):

$$\mathcal L = -\frac1B\sum_{i=1}^{B}\log\frac{\exp\big(s(q_i,p_i)/\tau\big)}{\sum_{j=1}^{B}\exp\big(s(q_i,p_j)/\tau\big)}$$

Here \(s\) is cosine similarity and \(\tau\) is a small temperature. Typical recipes pretrain on hundreds of millions of weakly paired texts mined from the web, then fine-tune on labelled pairs with hard negatives: passages that look relevant but are not. The consequence matters more than the recipe. “Similar” means whatever co-occurred as a matching pair in the training data, which is mostly topical relatedness, not logical equivalence.

import numpy as np

def normalize(X):
    return X / np.linalg.norm(X, axis=-1, keepdims=True)

def info_nce(Q, P, tau=0.05):
    """Q[i] matches P[i]; every P[j] with j != i is an in-batch negative."""
    S = normalize(Q) @ normalize(P).T / tau          # B x B similarity matrix
    S = S - S.max(axis=1, keepdims=True)             # numerical stability
    log_p = S - np.log(np.exp(S).sum(axis=1, keepdims=True))
    return float(-np.diag(log_p).mean())             # positives sit on the diagonal

rng = np.random.default_rng(0)
P = rng.normal(size=(32, 384))
print(round(info_nce(rng.normal(size=(32, 384)), P), 2))   # unrelated queries: 3.8
print(round(info_nce(P + 3 * rng.normal(size=(32, 384)), P), 3))   # near their passages: 0.174

Simulated with random vectors. Guessing among 32 candidates scores \(\log 32\approx 3.47\); unrelated pairs land near that, aligned pairs near 0. L36 uses this loss on a real model.

Cosine, dot product and Euclidean distance

Three scores are in common use: the dot product \(q\cdot d\), cosine similarity \(\cos\theta=\frac{q\cdot d}{\lVert q\rVert\,\lVert d\rVert}\), and Euclidean distance \(\lVert q-d\rVert\). They rank documents differently unless the vectors are normalised.

Derivation · when all three agree

If \(\lVert q\rVert=\lVert d\rVert=1\), then \(\cos\theta=q\cdot d\) and

$$\lVert q-d\rVert^2=\lVert q\rVert^2+\lVert d\rVert^2-2\,q\cdot d=2-2\cos\theta .$$

Distance is a decreasing function of cosine, so sorting by largest dot product, largest cosine or smallest distance gives the same order. Without normalisation the dot product also rewards long vectors, and Euclidean distance penalises them.

docs = rng.normal(size=(1000, 384)) * rng.uniform(0.5, 2.0, size=(1000, 1))  # unequal norms
q = rng.normal(size=384)
top5 = lambda s: np.argsort(-s)[:5].tolist()

print(top5(docs @ q) == top5(normalize(docs) @ normalize(q)))   # False: raw vectors
D, qn = normalize(docs), normalize(q)
print(top5(D @ qn) == top5(-np.linalg.norm(D - qn, axis=1)))    # True: normalised
Use the metric the model was trained with

The model card says which score the model was trained for. Most current models are trained with cosine. Normalise every vector once, at write time, and then use the dot product everywhere, because it is the cheapest of the three. A few models are trained with unnormalised dot products, where the norm carries information; normalising those throws it away.

Dimensionality, and why scores are not probabilities

More dimensions give the model more room to separate meanings, and cost storage and compute linearly in \(d\) (the storage maths and Matryoshka truncation are in L29). In high dimensions, random directions are nearly orthogonal: the cosine between two random unit vectors in \(\R^d\) has mean 0 and standard deviation about \(1/\sqrt d\), roughly 0.036 at \(d=768\). Trained models do not use the space evenly. Their vectors tend to occupy a narrow cone (anisotropy), so unrelated texts often score well above zero.

A cosine of 0.82 is therefore not “82% relevant”. The scale depends on the model, its training temperature, the text lengths and the domain. Two models give different numbers for the same pair, and so do short and long queries in one model. Use similarity for ranking. If you need a cut-off, calibrate it on labelled queries for that model (L44).

d = 384
u = normalize(rng.normal(size=d))
iso = normalize(rng.normal(size=(500, d)))                 # spread over the whole sphere
cone = normalize(rng.normal(size=(500, d)) + 15 * u)       # share one common direction
pair_mean = lambda X: float((X @ X.T)[np.triu_indices(len(X), 1)].mean())
print(round(pair_mean(iso), 3), round(pair_mean(cone), 3))  # 0.0 0.369

Symmetric and asymmetric retrieval

Symmetric tasks compare like with like: duplicate-ticket detection, paraphrase search, clustering. Asymmetric tasks compare a short query with a long passage that answers it, such as “why is my pod pending” against a scheduling page. The two sides look nothing alike, so models built for asymmetric search are trained on (query, passage) pairs and often expect a marker telling them which side they are encoding, such as a query: or passage: prefix or an instruction. L29 covers these conventions. DocPilot's main search is asymmetric; its ticket deduplication (L27 data) is symmetric.

What embeddings capture badly

What breaks in production
  • Negation and polarity. “Pods that are not ready” and “pods that are ready” share topic, vocabulary and context, so they embed close together. Contrastive training rarely contains pairs that teach the difference.
  • Numbers and versions. “v1.29” and “v1.31” are near neighbours, and so are “port 80” and “port 8080”. Put versions in metadata and filter on them (L33).
  • Exact identifiers. Error strings (CrashLoopBackOff, ErrImagePull), flag names (--dry-run=server) and resource kinds are split into sub-word tokens and blurred. A user pasting an exact error wants the page containing that string, which is what BM25 is for (L30).
  • Long chunks. Pooling a whole page into one vector averages several topics into a point that is near none of them (chunk sizing is L41).
  • Out-of-domain jargon. Words the model rarely saw in training get generic vectors (L36).

  3. Project to 2-D with PCA (Xc = X - X.mean(0); Xc @ np.linalg.svd(Xc, full_matrices=False)[2][:2].T) and scatter-plot coloured by section. Note which sections overlap.

Embedding Models in Practice: Choosing, Batching and Matryoshka

45m video50m practice

A public leaderboard gives you a shortlist; your own queries pick the model. After that the work is engineering: the right prefixes, batched calls, unit-length vectors, a byte budget, and an index that belongs to exactly one model.

Choosing a model: leaderboards shortlist, your data decides

MTEB (the Massive Text Embedding Benchmark) scores models on dozens of datasets across retrieval, classification, clustering, reranking and other tasks. Use it to build a shortlist of three or four candidates, and look only at the retrieval columns, because the overall average mixes in tasks DocPilot never runs. Then read each model card for what the leaderboard hides: licence, maximum input length (longer chunks are silently truncated), output dimension, languages, and whether you can host it. Benchmark averages are a weak predictor for one narrow domain, and some models are reported to have trained on data overlapping the benchmark's tasks. The decider is recall on your queries, which is why the practice block builds a 50-query set.

Query and document prefixes

Many retrieval models are trained asymmetrically (L28) and expect a marker saying which side is being encoded. The E5 family wants query: and passage: prefixes; BGE suggests an instruction before queries only; instruction-tuned embedders take a task description. Leaving the prefix off rarely raises an error. It just costs recall. Copy the exact strings from the model card and store them with the index.

# sentence-transformers: API as documented; check your installed version (untested here)
from sentence_transformers import SentenceTransformer

D = model.encode(["passage: " + c for c in chunks], batch_size=64, normalize_embeddings=True)
Q = model.encode(["query: " + q for q in queries], batch_size=64, normalize_embeddings=True)

Batching, rate limits and normalisation

Send many texts per request: embedding endpoints accept a list, and per-request overhead dominates for short chunks. Providers cap inputs per request and enforce requests-per-minute and tokens-per-minute limits, so a corpus job needs batching and backoff. The OpenAI SDK already retries 429s (max_retries, default 2). Add your own outer backoff for long jobs. Re-sort results by index, and normalise once at write time so that dot product equals cosine everywhere downstream.

import time
import numpy as np
import openai

def embed_batched(client, texts, *, model, dimensions=None, batch_size=128, prefix="", sleep=time.sleep):
    """Embed in batches, keep input order, back off on 429s, return unit-length float32 rows."""
    out = []
    for i in range(0, len(texts), batch_size):
        batch = [prefix + t for t in texts[i:i + batch_size]]
        kw = {"dimensions": dimensions} if dimensions else {}
        for attempt in range(6):
            try:
                resp = client.embeddings.create(model=model, input=batch, **kw)
                break
            except openai.RateLimitError:          # raised after the SDK's own retries
                sleep(min(60, 2 ** attempt))
        else:
            raise RuntimeError(f"still rate-limited at batch {i}")
        out.extend(e.embedding for e in sorted(resp.data, key=lambda e: e.index))
    E = np.asarray(out, dtype=np.float32)
    return E / np.linalg.norm(E, axis=1, keepdims=True)

Tested with a fake client that raises one RateLimitError and returns rows in reverse order: 3 texts, batch size 2, 3 calls, rows come back in input order and unit length.

Matryoshka embeddings and truncated dimensions

Definition · Matryoshka representation learning

Train with the contrastive loss applied to several prefixes of the vector at once, for a set of sizes \(\mathcal M\) such as \(\{64,128,256,512,1024\}\):

$$\mathcal L_{\text{MRL}}=\sum_{m\in\mathcal M} c_m\,\mathcal L\big(f(x)_{1:m}\big)$$

Each prefix is then a usable embedding by itself, with the most important information in the first coordinates. To shrink an index, keep the first \(m\) coordinates and renormalise. Some APIs do this server-side (the dimensions parameter).

Truncating a model that was not trained this way discards information at random. A synthetic test shows the difference. One corpus spreads variance evenly across dimensions; the other front-loads it, which is roughly what Matryoshka training produces. For each truncation we measure how much of the full-dimension top 10 survives:

rng = np.random.default_rng(0)
unit = lambda X: X / np.linalg.norm(X, axis=-1, keepdims=True)

def overlap_at_10(D, Q, m):
    full = np.argsort(-(Q @ D.T), axis=1)[:, :10]
    cut = np.argsort(-(unit(Q[:, :m]) @ unit(D[:, :m]).T), axis=1)[:, :10]
    return float(np.mean([len(set(a) & set(b)) / 10 for a, b in zip(full, cut)]))

n, d = 20_000, 1024
for name, s in {"flat": np.ones(d), "front-loaded": 1 / np.sqrt(np.arange(1, d + 1))}.items():
    D = unit((rng.normal(size=(n, d)) * s).astype(np.float32))
    Q = unit(D[:200] + 0.5 * unit(rng.normal(size=(200, d)) * s).astype(np.float32))
    print(name, [round(overlap_at_10(D, Q, m), 2) for m in (64, 128, 256, 512)])
# flat         [0.1, 0.12, 0.14, 0.22]
# front-loaded [0.61, 0.73, 0.83, 0.91]

Synthetic vectors, not a real model. On real models, measure recall on labelled queries rather than overlap with the full ranking.

Storage maths

Derivation · raw vector bytes $$\text{bytes}=n\times d\times\frac{\text{bits per dimension}}{8}$$

For \(n=10^6\) chunks at \(d=1024\): float32 \(=4.10\) GB, float16 \(2.05\) GB, int8 \(1.02\) GB, binary (1 bit) \(0.13\) GB. Truncating to 256 dimensions divides each by 4. ANN index structures add their own overhead on top (L31), and an in-RAM index needs all of it in memory.

What breaks in production
  • Mixing models in one index. Two models' vectors live in unrelated coordinate systems, even at the same dimension, so cross-model cosines are noise. The same applies to one model with a different prefix, truncation or normalisation. Store a manifest (model ID and revision, dimension, prefixes, normalised or not) with the index and refuse queries whose manifest differs. Changing models means re-embedding everything and swapping indexes atomically.
  • Silent input truncation. Text beyond the model's input limit is dropped without an error, so the end of a long chunk is never embedded.
  • Truncating without renormalising. A truncated vector is shorter than 1, so dot products are no longer cosines and rankings shift.
  • A hosted model that changes underneath you. Pin the model version where the provider allows it, and re-run your recall check after any provider notice.

Practice · 50 min

  1. Write DocPilot's 50-query retrieval set: real-sounding questions, each labelled with the chunk IDs that answer it. Include 10 queries containing exact error strings or flag names. L50 turns this into a proper golden set.
  2. Embed the corpus with two shortlisted models (for example one hosted, one local), using each model's documented prefixes, and save each index with its manifest.
  3. Compute recall@5 per model, \(\frac{|\text{relevant}\cap\text{top}_5|}{|\text{relevant}|}\) averaged over queries, and list the queries each model misses.
  4. Truncate the better model to 256 dimensions, renormalise, and re-measure. Compute the storage for each variant with the formula above.

Ship: a chosen embedding model, recorded with its recall@5 at full and truncated dimension and the storage cost of each.

Lexical Search: Inverted Indexes and BM25

45m video45m practice

Lexical search scores documents by the query terms they actually contain: rare terms count for more, repeats saturate, and long documents are discounted. That makes BM25 the right tool for error codes, flag names and exact identifiers, which are exactly the queries embeddings blur.

From text to terms: analysers

An analyser turns text into index terms. It runs at index time and at query time, and both must use the same one. Its usual stages:

  • Tokenising: split on whitespace and punctuation. Code-heavy text needs care: --dry-run=server, v1.31 and kube-proxy should survive as whole tokens and also be indexed as their parts.
  • Normalising: lowercase, Unicode-normalise, and fold accents if your users type without them.
  • Stop words: drop very common words (“the”, “is”). This matters less under BM25, whose IDF already makes them nearly worthless, and dropping them breaks phrase queries such as “to be or not to be”.
  • Stemming (rule-based suffix stripping, such as Porter's: “restarting” to “restart”) or lemmatisation (dictionary forms). Both raise recall and occasionally merge unrelated words.

The inverted index

Definition

An inverted index maps each term to its postings list: the documents containing it, with the term frequency \(\text{tf}(t,D)\) and optionally the positions (needed for phrase and proximity queries). It also stores document lengths \(|D|\) and the document frequency \(n(t)\) of each term. A query touches only the postings of its own terms, so the cost grows with how common those terms are, not with corpus size. That is why one machine can run keyword search over millions of documents.

From TF-IDF to BM25

TF-IDF weights a term by how often it appears in the document and how rare it is in the corpus, \(\text{tf}(t,D)\cdot\log\frac{N}{n(t)}\), with \(N\) documents in total. It has two defects. Score grows linearly with repetition, so a page that says “pod” forty times beats a precise one. And long documents win simply by containing more words. BM25 fixes both.

Definition · Okapi BM25 $$\text{BM25}(q,D)=\sum_{t\in q}\text{IDF}(t)\cdot\frac{\text{tf}(t,D)\,(k_1+1)}{\text{tf}(t,D)+k_1\left(1-b+b\,\frac{|D|}{\text{avgdl}}\right)}$$

IDF used here (Lucene's variant): \(\text{IDF}(t)=\ln\!\left(1+\frac{N-n(t)+0.5}{n(t)+0.5}\right)\). It is always positive. The classic Robertson–Spärck Jones form \(\ln\frac{N-n(t)+0.5}{n(t)+0.5}\) goes negative for terms in more than half the documents, so a document can lose score for matching a query term.

  • \(k_1\) controls term-frequency saturation. At \(k_1=0\) only presence counts; as \(k_1\to\infty\) it approaches raw tf. One term's contribution can never exceed \((k_1+1)\cdot\text{IDF}\).
  • \(b\in[0,1]\) controls length normalisation. At \(b=0\) length is ignored; at \(b=1\) tf is fully scaled by \(|D|/\text{avgdl}\).
  • Defaults in Lucene and Elasticsearch: \(k_1=1.2,\ b=0.75\). Tune them on your own queries; short, uniform chunks often want a lower \(b\).
Worked example · length normalisation

Take \(k_1=1.2\), \(b=0.75\) and a term that appears once. In an average-length chunk it contributes \(\frac{2.2}{1+1.2}=1.00\) times IDF. In a chunk twice the average length the denominator becomes \(1+1.2(0.25+1.5)=3.1\), giving 0.71. In a chunk half the average length it becomes \(1+1.2(0.25+0.375)=1.75\), giving 1.26. With \(b=0\) all three would score 1.00.

BM25 from scratch

import math
import re
from collections import Counter, defaultdict

STOP = {"a", "an", "and", "are", "be", "does", "for", "how", "in", "is", "it", "my", "of", "on", "or", "the", "to", "why", "with"}
TOKEN = re.compile(r"[a-z0-9]+(?:[-_.=/][a-z0-9]+)*")

def analyse(text: str) -> list[str]:
    """Lowercase; keep identifiers such as dry-run=server or v1.31 whole and also index their parts."""
    out = []
    for tok in TOKEN.findall(text.lower()):
        if tok in STOP:
            continue
        out.append(tok)
        parts = [p for p in re.split(r"[-_.=/]", tok) if p and p not in STOP]
        if len(parts) > 1:
            out += parts
    return out

class BM25:
    def __init__(self, docs: dict[str, str], k1: float = 1.2, b: float = 0.75):
        self.k1, self.b = k1, b
        self.postings: dict[str, dict[str, int]] = defaultdict(dict)   # term -> {doc_id: tf}
        self.dl = {}
        for doc_id, text in docs.items():
            toks = analyse(text)
            self.dl[doc_id] = len(toks)
            for term, tf in Counter(toks).items():
                self.postings[term][doc_id] = tf
        self.N, self.avgdl = len(docs), sum(self.dl.values()) / len(docs)

    def idf(self, term: str) -> float:          # Lucene's variant: always positive
        n = len(self.postings.get(term, {}))
        return math.log(1 + (self.N - n + 0.5) / (n + 0.5))

    def search(self, query: str, k: int = 5) -> list[tuple[str, float]]:
        scores: dict[str, float] = defaultdict(float)
        for term in set(analyse(query)):
            idf = self.idf(term)
            for doc_id, tf in self.postings.get(term, {}).items():    # only docs that contain the term
                norm = self.k1 * (1 - self.b + self.b * self.dl[doc_id] / self.avgdl)
                scores[doc_id] += idf * tf * (self.k1 + 1) / (tf + norm)
        return [(d, round(s, 2)) for d, s in sorted(scores.items(), key=lambda kv: -kv[1])[:k]]
docs = {
    "debug-pods": "A pod in CrashLoopBackOff is restarting repeatedly because its container exits. "
                  "Read the previous container's logs with kubectl logs --previous.",
    "images": "ErrImagePull or ImagePullBackOff means the kubelet could not pull the container image. "
              "Check the image name and the registry credentials.",
    "dry-run": "kubectl apply --dry-run=server sends the request to the API server without persisting it.",
    "scheduling": "A pod stays Pending when no node has enough CPU or memory. Describe the pod to see events.",
    "probes": "A failing liveness probe makes the kubelet restart the container, again and again.",
    "upgrade": "Kubernetes v1.31 removes deprecated beta APIs. Read the deprecation guide before you upgrade.",
}
index = BM25(docs)
for q in ["CrashLoopBackOff", "kubectl --dry-run=server", "pod restart", "why does my app keep rebooting"]:
    print(f"{q!r:34} {index.search(q, k=3)}")
# 'CrashLoopBackOff'                 [('debug-pods', 1.42)]
# 'kubectl --dry-run=server'         [('dry-run', 8.04), ('debug-pods', 0.95)]
# 'pod restart'                      [('probes', 1.77), ('scheduling', 1.39), ('debug-pods', 0.95)]

Search engines

You will rarely ship the class above. Elasticsearch and OpenSearch are distributed engines built on Lucene, with BM25 as the default similarity and configurable analysers. Tantivy is a Lucene-inspired library in Rust for embedding search in your own process. Postgres full-text search keeps everything in one database: a tsvector column, a GIN index and tsquery matching. Its built-in ts_rank is a frequency-based ranking, not BM25, and extensions add BM25 (for example ParadeDB's pg_search).

ALTER TABLE chunks ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('english', text)) STORED;
CREATE INDEX chunks_tsv ON chunks USING gin (tsv);

SELECT id, ts_rank(tsv, q) AS score
FROM chunks, websearch_to_tsquery('english', 'pod stuck pending') AS q
WHERE tsv @@ q ORDER BY score DESC LIMIT 10;
What breaks in production
  • An analyser that eats identifiers. A default English analyser can split ErrImagePull oddly, stem flag names, or drop --, so the queries BM25 should win silently degrade. Test your analyser's output on 20 real identifiers.
  • Different analysers at index and query time. Terms stop matching without any error.
  • Stale statistics. IDF and avgdl come from the corpus. Engines keep them per shard or segment, so small or skewed shards give different scores for the same document.
  • Treating BM25 scores as comparable across queries or with cosines. They are unbounded and depend on query length (L34).

Nearest-Neighbour Search: Exact, IVF, HNSW and Quantisation

55m video45m practice

Exact nearest-neighbour search compares the query with every vector. Approximate indexes avoid most of those comparisons, by visiting only a few clusters (IVF) or by walking a graph (HNSW), and quantisation shrinks each comparison. Every such index trades recall against latency and memory, so you choose its parameters from a measured curve.

Exact search and the triangle

Brute force costs \(n\cdot d\) multiply-adds per query, \(7.7\times10^8\) for a million 768-d chunks. Run as one matrix product it copes with a few hundred thousand vectors on a CPU, and it has perfect recall, so it is the ground truth for everything else. Past that, an approximate (ANN) index trades among three quantities:

Definition · the ANN triangle
  • Recall@k: the share of the true \(k\) nearest neighbours (from brute force) that the index returns.
  • Latency, or queries per second, at a stated recall.
  • Memory: vectors plus index structure, which usually must fit in RAM.

Report results as pairs (“recall@10 = 0.95 at 2 ms”), never recall or speed alone.

IVF: cluster, then probe a few lists

Algorithm · inverted file index (IVF)
  1. Train: run k-means on the vectors to get nlist centroids.
  2. Add: put each vector in the inverted list of its nearest centroid.
  3. Search: rank the centroids by distance to the query, scan only the vectors in the nprobe closest lists, and return the best \(k\).

The share of the corpus scanned is roughly nprobe / nlist. A query's true neighbour can sit just across a cluster boundary, so raising nprobe buys recall with linear cost.

import numpy as np

def kmeans(X, nlist, iters=10, seed=0):
    C = X[np.random.default_rng(seed).choice(len(X), nlist, replace=False)]
    for _ in range(iters):
        assign = np.argmin((C ** 2).sum(1) - 2 * X @ C.T, axis=1)     # nearest centroid per row
        for j in range(nlist):
            if (assign == j).any():
                C[j] = X[assign == j].mean(0)
    return C, assign

class IVF:
    def __init__(self, X, nlist):
        self.X = X
        self.C, assign = kmeans(X, nlist)
        self.lists = [np.flatnonzero(assign == j) for j in range(nlist)]   # inverted lists of row ids

    def search(self, q, k, nprobe):
        near = np.argsort((self.C ** 2).sum(1) - 2 * self.C @ q)[:nprobe]  # the nprobe closest centroids
        ids = np.concatenate([self.lists[j] for j in near])
        return ids[np.argsort(((self.X[ids] - q) ** 2).sum(1))[:k]], len(ids)

HNSW: a navigable layered graph

Definition · HNSW (Malkov & Yashunin)
  • Layers. Every vector is a node on layer 0. A new node is assigned a top layer \(\ell=\lfloor-\ln U\cdot m_L\rfloor\) with \(U\sim\text{Uniform}(0,1)\) and \(m_L=1/\ln M\), so each layer up holds about \(1/M\) as many nodes. The node appears on every layer from \(\ell\) down to 0. The sparse upper layers act like express lanes.
  • M is the number of links a node gets per layer, capped at \(M_{\max}=M\) on upper layers and \(M_{\max 0}=2M\) on layer 0. Larger M gives higher recall and more memory (about \(2M\times4\) bytes of neighbour IDs per vector on layer 0).
  • efConstruction is the beam width used while inserting. Wider beams find better neighbours, so build time rises and recall improves.
  • efSearch is the beam width at query time, at least \(k\). It is the main knob for trading recall against latency, and you can change it per query without rebuilding.
Algorithm · HNSW search and insert
  1. Search. Start at the global entry point on the top layer. On each layer above 0, move greedily (beam width 1) to whichever neighbour is closest to \(q\) until no neighbour is closer, then drop to the next layer from that node. On layer 0, run a beam search with width efSearch and return the best \(k\).
  2. Insert \(x\) with top layer \(\ell\): descend greedily to layer \(\ell+1\); on each layer from \(\ell\) to 0, beam-search with width efConstruction and link \(x\) both ways to M candidates, pruning any neighbour pushed over its cap.
  3. Neighbour heuristic. Add a candidate only if it is closer to \(x\) than to every neighbour already chosen. This keeps links pointing in different directions, including the long links between clusters that make the graph navigable.

The per-layer beam search is short:

import heapq

def search_layer(q, entry, graph, X, ef):
    """HNSW's per-layer search: best-first beam that keeps the ef closest nodes found so far."""
    dist = lambda i: float(((X[i] - q) ** 2).sum())
    visited = {entry}
    cand = [(dist(entry), entry)]             # min-heap of nodes still to expand
    best = [(-cand[0][0], entry)]             # max-heap (negated) of the ef best so far
    while cand:
        dc, c = heapq.heappop(cand)
        if dc > -best[0][0]:                  # closest unexpanded node is worse than our worst: stop
            break
        for nb in graph[c]:
            if nb in visited:
                continue
            visited.add(nb)
            dn = dist(nb)
            if len(best) < ef or dn < -best[0][0]:
                heapq.heappush(cand, (dn, nb))
                heapq.heappush(best, (-dn, nb))
                if len(best) > ef:
                    heapq.heappop(best)
    return [i for _, i in sorted((-dd, i) for dd, i in best)], len(visited)

On a single-layer two-way 16-NN graph over 5,000 random 64-d vectors, starting from node 0, recall@10 is 0.730 / 0.875 / 0.977 / 0.997 at ef = 10 / 20 / 50 / 100, visiting 1,072 to 3,411 nodes. On 200 well-separated clusters the same pure k-NN graph breaks down: it has almost no links between clusters, so at ef = 100 recall is 0.240. Adding just 4 random long-range links per node lifts it to 0.995. That is the job the neighbour heuristic and the upper layers do in real HNSW.

Quantisation: smaller vectors, cheaper distances

  • Scalar (int8): map each dimension's range to 0–255 for a 4× saving. Recall@10 against float32 was 0.983 on 20,000 random 256-d unit vectors.
  • Binary: keep one sign bit per dimension and compare with Hamming distance (XOR plus popcount), a 32× saving. On the same random vectors recall@10 was 0.106, so shortlist with bits and rescore the top few hundred with full vectors (0.456 with 200 rescored). Real embeddings are reported to fare much better than isotropic noise; measure on yours.
  • Product quantisation (PQ): split \(x\) into \(m\) sub-vectors, run k-means with 256 centroids on each sub-space, and store \(m\) one-byte codes. Distances are sums of table lookups, \(\lVert q-\hat x\rVert^2=\sum_{j=1}^{m}\lVert q^{(j)}-c^{(j)}_{i_j}\rVert^2\), with the \(m\times256\) table computed once per query. A 768-d float32 vector (3,072 bytes) becomes 96 bytes at \(m=96\). IVF-PQ combines the two ideas, and is how billion-scale indexes fit in memory.

Filters, and benchmarking honestly

Filtered search (“only version 1.31”, “only this tenant”) is hard for graph indexes. If you post-filter, the \(k\) results may all be rejected. If you skip disallowed nodes during traversal, a selective filter leaves a sparse, disconnected subgraph, which is the separated-clusters failure above, and recall collapses. Engines widen the beam, fall back to brute force over a small filtered subset, or add filter-aware links (L33). Benchmark the way ANN-Benchmarks does: exact ground truth, one knob swept (nprobe, efSearch), recall@k plotted against queries per second, all at your real \(k\), filters and concurrency.

What breaks in production
  • Benchmarking on the wrong data. Random vectors, or someone else's embeddings, give different curves. Use your own vectors and queries.
  • An index that no longer fits in RAM. HNSW performance falls apart when the graph is paged from disk. Budget vectors plus links plus headroom.
  • Deletes and updates. Graph deletes are tombstones that erode recall, and IVF centroids go stale as the corpus drifts. Plan rebuilds.
  • A metric mismatch. An L2 index over unnormalised vectors does not return cosine neighbours.

Vector Databases: Choosing and Using One

50m video60m practice

An ANN library answers “which vectors are nearest?”. A vector database also keeps the vectors safe, filters them, updates and deletes them, replicates them and often runs keyword search beside them. Choose one by your scale, your filtering needs and the operations you already run, then design the schema so that re-ingesting and re-embedding are routine.

What a database adds over a library

FAISS (L31) is a library: an index in your process's memory, fast and flexible, with no server. Everything around it is left to you: saving it to disk, mapping integer row IDs back to chunks, filtering by metadata, deleting a document, serving many readers, recovering after a crash. A vector database packages those concerns.

pgvector: vectors inside Postgres

pgvector adds a vector(n) column type, distance operators, and two index types to Postgres. Your chunks, metadata, permissions and vectors then live in one transactional database, and filters are ordinary SQL.

Definition · pgvector distance operators
  • a <-> b: Euclidean (L2) distance. Index ops class vector_l2_ops.
  • a <#> b: negative inner product, so that ascending order puts the largest dot product first. Ops class vector_ip_ops.
  • a <=> b: cosine distance, \(1-\cos\theta\). Ops class vector_cosine_ops; similarity is 1 - (a <=> b).

An index is used only when the query's operator matches the index's ops class and the query has the shape ORDER BY embedding <op> :q LIMIT k.

Schema design: IDs, payloads, versions

Design rules
  • Deterministic IDs. Derive each chunk's ID from its source, such as a UUIDv5 of URL, heading path and chunk index. Re-ingestion then upserts in place instead of duplicating. Qdrant accepts only unsigned integers or UUIDs as point IDs, so a UUID works everywhere.
  • A doc_id on every chunk, so that “document changed” becomes delete all its chunks, then insert the new ones.
  • A payload for filtering and citing: URL, heading path, section, product version, language, access labels, updated-at. L33 designs these.
  • The embedding model on every row, or one collection per model. A new model means a new collection, filled in the background and swapped in by alias.

To compare stores fairly, put one interface in front of all of them. Here is the in-memory reference that DocPilot's tests (and L37) use:

import uuid
import numpy as np

NS = uuid.UUID("6f1c2a52-6d0e-4c1b-9a59-2f8a3c1e0b7d")       # fixed namespace for DocPilot chunk IDs

def chunk_id(url: str, heading_path: str, i: int) -> str:
    return str(uuid.uuid5(NS, f"{url}#{heading_path}#{i}"))

def matches(payload: dict, where: dict) -> bool:
    return all(payload.get(k) in v if isinstance(v, (list, set, tuple)) else payload.get(k) == v
               for k, v in where.items())

class InMemoryStore:
    """Upsert, delete and filtered exact search; the contract the pgvector and Qdrant adapters must match."""
    def __init__(self, dim: int, model: str):
        self.dim, self.model, self.rows = dim, model, {}         # id -> (unit vector, payload)

    def upsert(self, id: str, vec, payload: dict) -> None:
        v = np.asarray(vec, dtype=np.float32)
        if v.shape != (self.dim,):
            raise ValueError(f"expected {self.dim} dims from {self.model}, got {v.shape}")
        self.rows[id] = (v / np.linalg.norm(v), payload)

    def delete(self, **where) -> int:
        doomed = [i for i, (_, p) in self.rows.items() if matches(p, where)]
        for i in doomed:
            del self.rows[i]
        return len(doomed)

    def search(self, q, k: int = 5, **where) -> list[tuple[str, float]]:
        ids = [i for i, (_, p) in self.rows.items() if matches(p, where)]   # filter first, then exact
        if not ids:
            return []
        s = np.stack([self.rows[i][0] for i in ids]) @ (q / np.linalg.norm(q))
        return [(ids[j], round(float(s[j]), 3)) for j in np.argsort(-s)[:k]]

What breaks in production
  • The query does not use the index. In pgvector, an operator that does not match the ops class, or an expression in ORDER BY, silently falls back to a sequential scan. Check with EXPLAIN.

Pre-filtering vs post-filtering

Definition · two ways to combine a filter with ANN
  • Post-filtering: retrieve the top \(k'\) by similarity, then drop rows that fail the filter. If a share \(s\) of rows pass and passing is unrelated to similarity, you get back about \(\min(k,\ k's)\) rows, so you need \(k'\approx k/s\) to fill \(k\) slots.
  • Pre-filtering: restrict the search to passing rows, then rank. Exact search over the subset has perfect recall at a cost that grows with subset size. Inside a graph index, skipping disallowed nodes can strand the search in a disconnected subgraph (L31).

Engines blend the two: they estimate selectivity, brute-force small subsets, widen the beam for medium ones, or keep filter-aware links. pgvector 0.8 added iterative index scans for filtered queries; check what your version does.

Answering for the right version

The Kubernetes site publishes documentation per release, and most pages barely change between releases, so the 1.29 and 1.31 versions of a page embed almost identically. Without a filter, retrieval mixes them freely. Resolve the version first, then filter on it. An explicit mention in the query wins, then the version known from the ticket (L27 extracts it), then the latest release. Record which rule fired so the answer can say “for 1.31”. Where a chunk is identical across releases, you can store it once with a versions list and filter by membership.

import re

SUPPORTED, LATEST = ("1.29", "1.30", "1.31"), "1.31"
VERSION = re.compile(r"\b(?:v|version\s*|kubernetes\s*)?(1\.\d{1,2})\b", re.I)

def resolve_version(query: str, cluster_version: str | None = None) -> tuple[str, str]:
    """Explicit mention beats the user's known cluster version, which beats the latest docs."""
    for m in VERSION.finditer(query):
        if m.group(1) in SUPPORTED:
            return m.group(1), "explicit"
    if cluster_version in SUPPORTED:
        return cluster_version, "ticket"
    return LATEST, "default"

print(resolve_version("is PodSecurityPolicy still in v1.29?"))            # ('1.29', 'explicit')
print(resolve_version("how do I drain a node", cluster_version="1.30"))   # ('1.30', 'ticket')
print(resolve_version("how do I drain a node"))                           # ('1.31', 'default')

What breaks in production
  • The forgotten filter. One code path, such as a new endpoint or an agent tool (L62), calls search without the tenant or version filter. Put filters inside the search function, not in its callers.
  • Post-filtered tenants. A small tenant in a shared HNSW index gets two results instead of ten and nobody notices. Alert on result counts below k.
  • Inconsistent values. “1.31” and “v1.31” in different chunks make an exact-match filter drop half the corpus.
  • Over-eager parsing. A version regex that also matches part of an IP address or a port number silently filters to the wrong release. Test it on real tickets.

Hybrid Search and Rank Fusion

45m video45m practice

BM25 and dense retrieval fail on different queries, so running both and merging the results recovers much of what each one misses. Their scores live on unrelated scales, so you fuse ranks (RRF) or carefully normalised scores, and then check on your own queries that the merge beats each part.

Why combine, and why not add scores

L30 ended with a table in which neither column was empty: BM25 wins on identifiers, error strings and rare terms, and dense retrieval wins on paraphrase and concepts. A real query stream mixes both kinds, and so do single queries (“CrashLoopBackOff after the upgrade”). Hybrid search runs both retrievers and merges their lists.

The tempting merge, adding the scores, fails because the scales are unrelated. BM25 is unbounded and grows with query length and term rarity, so 12.4 on one query means nothing on another. Cosine similarity sits in a narrow band, often 0.7 to 0.9 for a model's plausible hits (L28). Add them and BM25 decides almost everything.

Worked example · raw sum vs RRF

Query: “CrashLoopBackOff after upgrade”. BM25 returns debug-pods 12.4, upgrade 7.9, images 3.1, probes 1.2. Dense returns probes 0.83, debug-pods 0.81, scheduling 0.78, upgrade 0.74. The raw sum is simply the BM25 order with dense noise added: debug-pods 13.21, upgrade 8.64, images 3.10, probes 2.03. RRF with \(k=60\) gives debug-pods \(\frac1{61}+\frac1{62}=0.0325\), probes \(\frac1{64}+\frac1{61}=0.0320\), upgrade \(\frac1{62}+\frac1{64}=0.0318\), then images and scheduling at \(\frac1{63}=0.0159\). Documents both retrievers like rise to the top.

Reciprocal Rank Fusion

Definition · RRF (Cormack, Clarke & Büttcher 2009) $$\text{RRF}(d)=\sum_{r\in R}\frac{w_r}{k+\text{rank}_r(d)}$$

Here \(R\) is the set of ranked lists, ranks start at 1, a document absent from a list contributes nothing from it, and the weights \(w_r\) are 1 in the original method. \(k=60\) is the constant from the original paper and the common default. It damps the top of each list: at \(k=60\), rank 1 earns only 15% more than rank 10 (\(\frac{70}{61}\)), so agreement between lists outweighs any single list's top spot. At \(k=1\), rank 1 earns 5.5 times rank 10 and one list's favourite dominates.

RRF needs no score calibration, no training and no per-query normalisation, which is why it is the default hybrid method in many engines. Its blind spot is that it ignores how confident each retriever was. A BM25 hit that matched a rare error code exactly counts the same as a lucky rank 1.

Weighted fusion after normalisation

To keep score information, normalise each list and then take a weighted sum, \(s(d)=\alpha\,\tilde s_{\text{dense}}(d)+(1-\alpha)\,\tilde s_{\text{bm25}}(d)\). Min–max normalisation maps each query's top-\(k\) scores to \([0,1]\); z-scores use the list's mean and standard deviation. Both depend on what else came back for that query, and a single outlier stretches min–max. Tune \(\alpha\) on held-out queries, and consider a different \(\alpha\) for queries that contain identifiers.

from collections import defaultdict

def rrf(rankings: list[list[str]], k: int = 60, weights: list[float] | None = None) -> list[tuple[str, float]]:
    """Reciprocal Rank Fusion: score(d) = sum over lists of w / (k + rank), ranks starting at 1."""
    scores: dict[str, float] = defaultdict(float)
    for ranking, w in zip(rankings, weights or [1.0] * len(rankings)):
        for rank, doc in enumerate(ranking, start=1):
            scores[doc] += w / (k + rank)
    return sorted(scores.items(), key=lambda kv: -kv[1])

def minmax_fusion(score_lists: list[dict[str, float]], weights: list[float]) -> list[tuple[str, float]]:
    """Normalise each list's scores to [0, 1], then take a weighted sum; missing docs count as 0."""
    fused: dict[str, float] = defaultdict(float)
    for scores, w in zip(score_lists, weights):
        lo, hi = min(scores.values()), max(scores.values())
        for doc, s in scores.items():
            fused[doc] += w * (s - lo) / ((hi - lo) or 1.0)
    return sorted(fused.items(), key=lambda kv: -kv[1])

dense = {"probes": 0.83, "debug-pods": 0.81, "scheduling": 0.78, "upgrade": 0.74}

Learned sparse retrieval, and hybrid built in

SPLADE and similar models put a transformer in front of an inverted index. For each text the model outputs a weight for every vocabulary term, most of them zero. It keeps the terms present and adds related ones (“restarting” can activate “crash” and “loop”). Scoring is a sparse dot product, so you keep exact-term matching, gain some vocabulary expansion, and still use inverted-index machinery. The costs are a model at index and query time and larger postings than BM25.

Most engines now run hybrid queries natively. Weaviate combines BM25 and vectors with a weighting parameter; Qdrant fuses dense and sparse sub-queries, RRF included; Elasticsearch and OpenSearch offer RRF and score-normalisation pipelines. In Postgres you write it yourself as a full outer join of two ranked lists. Names and options change, so check current documentation.

Evaluating the combination against each part

Fusion is not free recall. RRF rewards agreement, so a distractor that both retrievers rank moderately high can beat a correct document that only one of them finds. The simulation below is synthetic: 50 queries, 20 suiting BM25 and 30 suiting dense, with distractors correlated across the two methods as they are in practice. p_weak controls how deep the weaker method buries the answer.

import numpy as np

def recall_at(ranking, relevant, k):
    return len(set(ranking[:k]) & relevant) / len(relevant)

def mrr(ranking, relevant):
    return next((1 / r for r, doc in enumerate(ranking, start=1) if doc in relevant), 0.0)

def simulate(p_weak, n_docs=1000, seed=0):
    rng, runs = np.random.default_rng(seed), {"bm25": [], "dense": [], "rrf": []}
    for lex_suits in [True] * 20 + [False] * 30:
        shared = rng.normal(size=n_docs)                  # distractors look relevant to both methods
        pair = []
        for suits in (lex_suits, not lex_suits):
            order = [f"d{i}" for i in np.argsort(-(shared + rng.normal(size=n_docs)))]
            order.insert(int(rng.geometric(0.5 if suits else p_weak)) - 1, "rel")   # where the answer lands
            pair.append(order[:50])
        runs["bm25"].append(pair[0]); runs["dense"].append(pair[1]); runs["rrf"].append([d for d, _ in rrf(pair)])
    return {m: (round(float(np.mean([recall_at(r, {"rel"}, 5) for r in rs])), 2),
                round(float(np.mean([mrr(r, {"rel"}) for r in rs])), 3)) for m, rs in runs.items()}

print(simulate(0.05))  # {'bm25': (0.54, 0.344), 'dense': (0.68, 0.462), 'rrf': (0.88, 0.564)}
print(simulate(0.02))  # {'bm25': (0.46, 0.291), 'dense': (0.6, 0.43), 'rrf': (0.7, 0.359)}

Pairs are (recall@5, MRR). In both settings RRF lifts recall@5. In the second, where the weak method usually misses the answer altogether, RRF's MRR (0.359) falls below dense alone (0.430): agreed-on distractors push the answer down. Measure it on real queries; don't assume it.

What breaks in production
  • Adding raw scores. One retriever silently dominates. Use ranks or normalised scores.
  • Fusing lists of very different depth. Top 5 from one retriever against top 100 from the other skews RRF. Retrieve the same depth from each.
  • Different filters on each branch. The version or tenant filter (L33) must apply to both retrievers, or fusion reintroduces the leak.
  • Reporting only the blend. Without per-retriever and per-query-type numbers you cannot tell which half regressed.

Rerankers: Cross-Encoders and Late Interaction

45m video45m practice

First-stage retrieval is built for speed over millions of documents, so it compares compressed summaries. A reranker reads the query and each candidate together, which is far more accurate and far too slow for the whole corpus. So you retrieve about 50 candidates cheaply and rerank them down to 5.

Bi-encoders and cross-encoders

Definition
  • Bi-encoder: query and document are encoded separately into vectors and compared by cosine (L28). Document vectors are computed once, offline, so search is an index lookup. But no query token ever attends to a document token.
  • Cross-encoder: the transformer reads the pair, [query ; document], with full attention across both, and outputs one relevance score. It sees negation, exact matches and which entity a phrase refers to. It also costs one forward pass per (query, document) pair, at query time.
  • Late interaction (ColBERT): both sides are encoded separately into one vector per token; relevance is computed from token-to-token similarities. It sits between the other two in accuracy and cost.

Two-stage retrieval

Algorithm · retrieve, then rerank
  1. Hybrid first stage (L34): fetch the top \(N\approx50\) with filters applied.
  2. Score every (query, candidate) pair with the reranker, batched.
  3. Sort by reranker score and keep the top 5 for the prompt. Optionally drop candidates below a score floor calibrated on labelled data.

The reranker can only reorder what stage 1 found, so recall@N of stage 1 is a ceiling on the final result. Choose \(N\) from a recall@N curve, then choose the reranker from nDCG@5 and latency.

Hosted rerank endpoints from several providers take a query and a list of documents and return relevance scores. Open cross-encoders, such as the MS MARCO MiniLM models in sentence-transformers or BAAI's bge-reranker family, run on your own hardware. Model names and quality change quickly; pick from current leaderboards and confirm on your own queries.

Late interaction: ColBERT and MaxSim

Definition · MaxSim $$s(q,d)=\sum_{i=1}^{|q|}\ \max_{1\le j\le|d|}\ \mathbf q_i\cdot\mathbf d_j$$

Each query token finds its best-matching document token, and the matches are summed. Document token vectors are precomputed, so the query-time cost is one encoder pass for the query plus a \(|q|\times|d|\) similarity matrix per candidate. The storage price is one vector per token: 300 tokens × 128 dimensions × 2 bytes is about 77 KB per chunk, versus 3 KB for one 768-d float32 vector. ColBERTv2 compresses token vectors to cut this substantially.

import numpy as np

def maxsim(Qt: np.ndarray, Dt: np.ndarray) -> float:
    """ColBERT late interaction: each query token takes its best document token; sum over query tokens."""
    return float((Qt @ Dt.T).max(axis=1).sum())

rng = np.random.default_rng(0)
unit = lambda A: A / np.linalg.norm(A, axis=-1, keepdims=True)
vocab = unit(rng.normal(size=(500, 128)))                       # synthetic token vectors
q = vocab[[7, 8, 9]]                                            # say "crashloopbackoff", "after", "upgrade"
d_exact = vocab[np.r_[7, rng.integers(20, 500, 199)]]           # long chunk containing token 7 once
d_topic = unit(vocab[rng.integers(20, 500, 30)] + 0.6 * vocab[8])   # short chunk loosely about token 8
pooled = lambda T: unit(T.mean(0))
print(round(maxsim(q, d_exact), 2), round(maxsim(q, d_topic), 2))                          # 1.44 0.98
print(round(float(pooled(q) @ pooled(d_exact)), 3), round(float(pooled(q) @ pooled(d_topic)), 3))  # 0.226 0.542

MaxSim prefers the chunk that contains the exact token; mean-pooled single vectors prefer the vaguely topical chunk. That is the token-level matching late interaction buys.

LLM-based reranking

Pointwise: ask a model to grade each passage on its own (0–3). Calls run in parallel and grades are comparable across queries, but you pay one call per candidate. Listwise: put all candidates in one prompt and ask for an ordering. One call sees everything, but long lists suffer position bias and context limits, so implementations slide a window over the list (RankGPT). Either way the input is roughly \(N\times\) passage length, about 15,000 tokens for 50 passages of 300 tokens, per query. It is usually the most expensive and slowest option, worth it for offline labelling or for low-volume, high-value queries.

    """Valid, unique indices in the model's order, then the rest in first-stage order."""
    order = []
    for i in json.loads(text).get("order", []):
        if isinstance(i, int) and 0 <= i < n and i not in order:
            order.append(i)
    return order + [i for i in range(n) if i not in order]

The latency budget, and measuring the gain

Reranking is usually the slowest step of retrieval. A small cross-encoder scoring 50 pairs typically takes tens of milliseconds on a GPU and noticeably longer on a CPU; measure yours. Give the reranker a fixed budget and fall back to first-stage order when it is exceeded, so a slow reranker degrades quality, not availability. Measure the gain with nDCG@5 using graded labels (0 to 3). Here the gain is \(2^{\text{grade}}-1\); L37 collects the metric helpers.

import math
import time
from concurrent.futures import ThreadPoolExecutor, TimeoutError as Timeout

def ndcg_at(ranking: list[str], grades: dict[str, int], k: int) -> float:
    dcg = lambda gains: sum(g / math.log2(i + 2) for i, g in enumerate(gains))
    ideal = sorted((2 ** g - 1 for g in grades.values()), reverse=True)[:k]
    return dcg([2 ** grades.get(d, 0) - 1 for d in ranking[:k]]) / dcg(ideal) if any(ideal) else 0.0

_pool = ThreadPoolExecutor(max_workers=4)

def rerank(query, hits, score_pairs, *, top_n=5, budget_s=0.3):
    """Reorder hits by reranker score; on timeout or error keep first-stage order. Returns (hits, info)."""
    t0, status = time.perf_counter(), "reranked"
    try:
        scores = _pool.submit(score_pairs, [(query, h["text"]) for h in hits]).result(timeout=budget_s)
        order = sorted(range(len(hits)), key=lambda i: -scores[i])
    except Timeout:
        order, status = list(range(len(hits))), "timeout"     # the worker thread still finishes in the background
    except Exception:
        order, status = list(range(len(hits))), "error"
    return [hits[i] for i in order[:top_n]], {"status": status, "ms": round(1000 * (time.perf_counter() - t0))}

print(round(ndcg_at(["x", "c", "a", "y", "b"], {"a": 3, "b": 2, "c": 1}, 5), 3))   # 0.563 before reranking
print(ndcg_at(["a", "b", "c", "x", "y"], {"a": 3, "b": 2, "c": 1}, 5))             # 1.0 after
What breaks in production
  • Reranking too few candidates. If the answer is at rank 80 and you rerank 20, the reranker cannot help. Check stage-1 recall@N first.
  • Truncated pairs. Cross-encoders have input limits (often 512 tokens). Long chunks are cut and the relevant sentence may be the part dropped.
  • Unbounded latency. A reranker without a timeout turns a slow GPU into an outage. Budget it, log status, and alert on the timeout rate.
  • Thresholds on reranker scores across models. Scores are model-specific logits, not probabilities (L28). Recalibrate after every model change.

Fine-Tuning Embeddings for Your Domain

45m video60m practice

A general embedding model learned someone else's idea of “similar”. Fine-tuning it on (query, relevant chunk) pairs from your domain, with hard negatives, can teach it yours. It pays off only if a held-out evaluation on real queries says so, and only after you count the cost of re-embedding everything.

When off-the-shelf embeddings underperform

The symptoms show up in the failure lists from L28 and L29:

  • Jargon and identifiers the model rarely saw. To a general model, “taint”, “toleration” and “cordon” may sit near their everyday meanings rather than near each other.
  • A domain-specific notion of similarity. For DocPilot, a ticket about ImagePullBackOff should be near the registry-credentials page, not near every page that mentions images.
  • Systematic confusions that hybrid search (L34) and reranking (L35) do not fix.

Try the cheaper fixes first: hybrid search, better chunking and chunk context (Phase 4), a reranker, a different base model. Fine-tune when those are exhausted and the remaining misses are about meaning, not about missing keywords.

Training data: pairs, synthetic queries and hard negatives

The unit of data is a (query, positive) pair, optionally with a hard negative. Real pairs come from search logs, tickets linked to the doc that resolved them, or your labelled set. Usually there are too few, so generate synthetic queries: show a model each chunk and ask for questions it answers. Ask for variety (an exact error string, a vague symptom, a precise how-to) and forbid copying sentences, or the pairs only teach lexical overlap.

Hard negatives are chunks the base model ranks highly for the query but which do not answer it. They carry the training signal, because random negatives are already easy. The risk is false negatives: a sibling chunk from the same page may answer the query too, and training would push it away. Exclude the positive's own document (the code below does), and consider skipping candidates that score above the positive, which are often unlabelled positives.

The loss: multiple-negatives ranking

Definition · multiple-negatives ranking loss

For a batch of anchors \(a_i\), positives \(p_i\) and optional hard negatives \(n_i\), every candidate in the batch competes for every anchor:

$$\mathcal L=-\frac1B\sum_{i=1}^{B}\log\frac{e^{\,s\cdot\cos(a_i,p_i)}}{\sum_{j}e^{\,s\cdot\cos(a_i,p_j)}+\sum_{j}e^{\,s\cdot\cos(a_i,n_j)}}$$

This is the InfoNCE loss from L28, with scale \(s=1/\tau\); sentence-transformers' default is \(s=20\). Larger batches give more negatives for free. Because every candidate serves every anchor, two pairs from the same chunk in one batch make each other false negatives, so use a no-duplicates batch sampler.

import numpy as np

unit = lambda X: X / np.linalg.norm(X, axis=-1, keepdims=True)

def mnrl_loss(A, P, N=None, scale=20.0):
    """Multiple-negatives ranking loss: anchor i must pick P[i] among every positive (and negative) in the batch."""
    C = unit(P) if N is None else unit(np.vstack([P, N]))      # B, or 2B, candidates shared by all anchors
    S = scale * unit(A) @ C.T                                   # scale 20 is a temperature of 0.05
    S = S - S.max(axis=1, keepdims=True)
    return float(-np.mean(np.diag(S) - np.log(np.exp(S).sum(axis=1))))

def mine_hard_negatives(Q, D, pos, doc_of, n=1):
    """Top-scoring chunks under the base model that are not from the positive's document."""
    return [[j for j in np.argsort(-row) if doc_of[j] != doc_of[pos[i]]][:n] for i, row in enumerate(Q @ D.T)]

rng = np.random.default_rng(0)
noise = lambda m, s: s * unit(rng.normal(size=(m, 384)))
sections = unit(rng.normal(size=(40, 384)))                    # 40 sections x 5 docs x 5 chunks
docs = unit(np.repeat(sections, 5, axis=0) + noise(200, 0.4))

Columns are read by position: anchor, positive, then negative. Older sentence-transformers code used model.fit.

Evaluation on held-out queries

  • Split by document, not by query. Three synthetic queries from one chunk land in train and test otherwise, and the test only measures memorisation.
  • Evaluate on real queries too. Synthetic test queries share the generator's style. The 50-query set from L29 is the number that matters.
  • Check for regressions. Measure recall@5 on queries outside the fine-tuning domain, such as general Kubernetes questions not covered by your chunks. Fine-tuning can overwrite general knowledge.
  • Compare against the cheap alternatives, such as hybrid plus reranker, not only against the base model.

The cost of re-indexing

A new embedding model means a new vector space (L29): every chunk must be re-embedded, the ANN index rebuilt, both indexes stored during cutover, and the query encoder switched in the same deploy. The re-embedding cost is total corpus tokens divided by encoder throughput, and you pay it again for every retrain and every corpus-wide change. One way to cut it is a query-side adapter, a small learned transform applied only to query vectors, which leaves document vectors untouched. It is weaker than full fine-tuning, but there is nothing to re-index.

What breaks in production
  • Leaky splits. Test chunks used as training negatives or positives inflate the gain.
  • Generator-shaped queries. The model gets very good at the LLM's phrasing and no better at users'.
  • False negatives in mining. Training pushes away chunks that were right, and recall on paraphrases drops.
  • Half-migrated indexes. Queries embedded with the new model against documents embedded with the old one return garbage (manifest check, L29).

  2. Mine one hard negative per training pair with the base model, excluding the positive's document and anything scoring above the positive.
  3. Fine-tune a small open model (for example a bge-small or MiniLM class model) for one epoch with MNRL.
  4. Report recall@5 for base and fine-tuned models on the held-out synthetic queries, on your 50 real queries, and on 20 out-of-domain queries.

import time
from dataclasses import dataclass, field

from docpilot.fusion import rrf                 # L34
from docpilot.lexical import BM25               # L30
from docpilot.rerank import rerank              # L35
from docpilot.store import matches              # L32
from docpilot.versions import resolve_version   # L33

@dataclass
class Hit:
    id: str
    text: str
    score: float
    url: str
    heading_path: str
    meta: dict = field(default_factory=dict)

class SearchService:
    def __init__(self, chunks: dict[str, dict], embed, store, score_pairs=None, depth: int = 50):
        self.chunks, self.embed, self.store, self.score_pairs, self.depth = chunks, embed, store, score_pairs, depth
        self.bm25 = BM25({cid: c["text"] for cid, c in chunks.items()})

    def run(self, query: str, *, k: int = 5, filters: dict | None = None, mode: str = "hybrid"):
        t0, ms, where = time.perf_counter(), {}, dict(filters or {})
        version, how = (where["version"], "filter") if "version" in where else resolve_version(query)
        where["version"] = version
        lex = [cid for cid, _ in self.bm25.search(query, k=len(self.chunks))
               if matches(self.chunks[cid], where)][:self.depth]
        qv = self.embed(query)
        dense = [cid for cid, _ in self.store.search(qv, k=self.depth, **where)] if qv.any() else []
        lists = {"bm25": [lex], "dense": [dense], "hybrid": [lex, dense]}[mode]
        cands = [{"id": cid, "text": self.chunks[cid]["text"], "score": s} for cid, s in rrf(lists)[:self.depth]]
        ms["retrieve"], status = round(1000 * (time.perf_counter() - t0), 1), "off"
        if self.score_pairs and cands:
            cands, info = rerank(query, cands, self.score_pairs, top_n=k)
            status, ms["rerank"] = info["status"], info["ms"]
        hits = [Hit(c["id"], c["text"], round(c["score"], 4), self.chunks[c["id"]]["url"],
                    self.chunks[c["id"]]["heading_path"],
                    {f: v for f, v in self.chunks[c["id"]].items() if f != "text"}) for c in cands[:k]]
        ms["total"] = round(1000 * (time.perf_counter() - t0), 1)
        return hits, {"version": version, "version_source": how, "rerank": status, "timings_ms": ms}

service: SearchService | None = None            # built once at start-up

def search(query: str, *, k: int = 5, filters: dict | None = None) -> list[Hit]:
    """The interface every later phase calls."""
    return service.run(query, k=k, filters=filters)[0]

Both retrievers get the same where: BM25 by exact pre-filtering, the store inside its own search. Fusion therefore cannot reintroduce a leak.

The API: services/api.py

from fastapi import FastAPI
from pydantic import BaseModel, ConfigDict, Field

from docpilot.search import Hit, SearchService

class Filters(BaseModel):
    model_config = ConfigDict(extra="forbid")          # callers cannot add tenant or acl filters
    version: str | None = None
    section: str | None = None
    lang: str | None = None

class SearchRequest(BaseModel):
    query: str = Field(min_length=1, max_length=2000)
    k: int = Field(5, ge=1, le=50)
    filters: Filters = Field(default_factory=Filters)

class SearchResponse(BaseModel):
    hits: list[Hit]
    version: str
    version_source: str
    rerank: str
    timings_ms: dict[str, float]

def create_app(service: SearchService) -> FastAPI:
    app = FastAPI(title="DocPilot search")

    @app.post("/search", response_model=SearchResponse)
    def do_search(req: SearchRequest) -> SearchResponse:
        hits, info = service.run(req.query, k=req.k, filters=req.filters.model_dump(exclude_none=True))
        return SearchResponse(hits=hits, **info)

    return app

extra="forbid" rejects filters the caller has no business setting. Tenant and permission filters will come from the authenticated user, server-side (L47). An entry point builds the service once and serves create_app(service) with uvicorn.

Metrics: docpilot/metrics.py

Definition · the three retrieval metrics

For a query with relevant set \(R\) (grade at least 1), ranked list \(L\) and graded labels \(g_i\in\{0,1,2,3\}\) for the item at position \(i\):

$$\text{recall@}k=\frac{|R\cap L_{1..k}|}{|R|},\qquad \text{RR}=\frac{1}{\text{rank of the first relevant item}}\ (0\text{ if none}),\qquad \text{nDCG@}k=\frac{\sum_{i=1}^{k}\frac{2^{g_i}-1}{\log_2(i+1)}}{\text{IDCG@}k}$$

MRR averages RR over queries; IDCG@k is the DCG of the ideal ordering. L50 adds precision@k and confidence intervals.

import math
import statistics

def recall_at_k(ranked: list[str], relevant: set[str], k: int) -> float:
    return len(set(ranked[:k]) & relevant) / len(relevant)

def mrr(ranked: list[str], relevant: set[str]) -> float:
    return next((1 / r for r, d in enumerate(ranked, start=1) if d in relevant), 0.0)

def ndcg_at_k(ranked: list[str], grades: dict[str, int], k: int) -> float:
    dcg = lambda gains: sum(g / math.log2(i + 2) for i, g in enumerate(gains))
    ideal = dcg(sorted((2 ** g - 1 for g in grades.values()), reverse=True)[:k])
    return dcg([2 ** grades.get(d, 0) - 1 for d in ranked[:k]]) / ideal if ideal else 0.0

def evaluate(run, golden: list[dict], k: int = 5) -> dict[str, float]:
    """run(query) -> ranked ids. Golden rows: {"query", "grades": {id: 0..3}}; relevant means grade >= 1."""
    rows = []
    for g in golden:
        ranked, rel = run(g["query"]), {d for d, s in g["grades"].items() if s >= 1}
        rows.append((recall_at_k(ranked, rel, k), mrr(ranked, rel), ndcg_at_k(ranked, g["grades"], k)))
    return {n: round(statistics.mean(c), 3) for n, c in zip((f"recall@{k}", "MRR", f"nDCG@{k}"), zip(*rows))}

def hashed_embed(text: str, dim: int = 256) -> np.ndarray:
    """Stand-in for an embedding model: hashed character trigrams."""
    v = np.zeros(dim, dtype=np.float32)

    return v
