How LLMs Work, for Engineers

This phase teaches just enough of how language models work inside to make sound engineering decisions: why long prompts are slow, why output tokens cost more, why temperature 0 still varies, what reasoning models spend their tokens on, and where hallucinations come from. It builds on the API workbench and cost logging of Phase 0, and every measurement here becomes a baseline that Phase 2's prompt and context engineering has to beat.

By the end of this phase you can

  • Compute KV-cache size for any published model configuration and explain prefill, decode and TTFT from your own latency logs.
  • Implement temperature, top-k, top-p and min-p sampling, and choose sampling or effort and thinking settings per task.
  • Attribute a model behaviour, such as sycophancy, refusals or a knowledge cut-off, to the training stage that most likely caused it.
  • Measure hallucination, abstention and calibration on your own probe set, and a model's length and position sensitivity with needle tests.
  • Estimate the token cost of images and PDFs and measure vision accuracy field by field.
  • Profile any new model with one command that reports pass rates with confidence intervals.

L7 · DAY 5

Transformers in One Sitting: From Tokens to Logits

55m video40m practice

A decoder-only transformer turns a sequence of token ids into one vector per token, lets each vector read from the ones before it (attention) and transform itself (MLP) a few dozen times, then maps the last vector to a score for every token in the vocabulary. Knowing where that work happens tells you where the compute and the memory go.

Tokens in, vectors out: embeddings and position

The tokenizer (L4) produces integer ids. The first layer is a lookup table of shape \(V \times d\): vocabulary size by model width. Row \(i\) is the embedding of token \(i\), a learned vector of a few thousand numbers. A prompt of \(T\) tokens becomes a \(T \times d\) matrix, and that matrix is the residual stream every later layer reads from and writes to.

Attention by itself treats its input as a set, so the model needs position information. The original transformer added sinusoidal position vectors to the embeddings; GPT-2 learned them. Most current open models use rotary position embeddings (RoPE): inside each attention layer, pairs of dimensions in every query and key are rotated by an angle proportional to the token's position. The dot product of a rotated query at position \(m\) and a rotated key at position \(n\) then depends on the offset \(m - n\), which is what attention needs. Context-extension tricks for long-context models mostly work by adjusting these rotation frequencies. Values are not rotated.

Self-attention as a soft lookup

Definition · Scaled dot-product attention

Each token's vector \(x_i\) is projected three ways: a query \(q_i = x_i W_Q\) ("what am I looking for?"), a key \(k_i = x_i W_K\) ("what do I contain?") and a value \(v_i = x_i W_V\) ("what do I hand over if chosen?"). Stacking the rows into \(Q, K, V\):

$$\operatorname{Attn}(Q, K, V) = \operatorname{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}} + M\right) V, \qquad M_{ij} = \begin{cases} 0 & j \le i \\ -\infty & j > i \end{cases}$$

Row \(i\) of the softmax is a probability distribution over earlier tokens; the output for token \(i\) is the weighted average of their values. A dictionary lookup returns the value of the one matching key. Attention returns a blend of all values, weighted by how well each key matches.

The \(\sqrt{d_k}\) keeps the scores at a sensible scale: if query and key components have unit variance, their dot product has variance \(d_k\), and without the division the softmax saturates into a near one-hot choice with tiny gradients. The mask \(M\) is causal masking: in a decoder-only model token \(i\) may only attend to positions \(j \le i\). That is what lets one forward pass train on every next-token prediction in a sequence at once, and it is why generation can reuse past keys and values (L8).

import numpy as np

def softmax(x, axis=-1):
    x = x - x.max(axis=axis, keepdims=True)          # stability; -inf stays -inf
    e = np.exp(x)
    return e / e.sum(axis=axis, keepdims=True)

def causal_attention(X, Wq, Wk, Wv):
    """X: (T, d_model). Returns the output (T, d_head) and the weights (T, T)."""
    Q, K, V = X @ Wq, X @ Wk, X @ Wv                  # three linear projections
    T, d = Q.shape
    scores = Q @ K.T / np.sqrt(d)                     # (T, T): query i against key j
    future = np.triu(np.ones((T, T), dtype=bool), k=1)
    scores = np.where(future, -np.inf, scores)        # token i may not see j > i
    A = softmax(scores, axis=-1)                      # each row sums to 1
    return A @ V, A

Multi-head attention

One head computes one weighting per token. Real layers run \(h\) heads in parallel, each with its own \(W_Q, W_K, W_V\) of width \(d_k = d/h\), so each head can track a different relation (syntax, coreference, position). The \(h\) outputs are concatenated back to width \(d\) and mixed by an output projection \(W_O\). Splitting \(d\) into heads costs about the same as one wide head. The number of key/value heads can be smaller than the number of query heads. That variant, grouped-query attention, matters for memory and is the subject of L8.

The block: MLP, residual stream and normalisation

A transformer block is two sub-layers, each of which adds its result back into the residual stream (pre-norm form, used by most current models):

$$x \leftarrow x + \operatorname{Attn}(\operatorname{Norm}(x)), \qquad x \leftarrow x + \operatorname{MLP}(\operatorname{Norm}(x)).$$
  • Attention is the only place information moves between positions.
  • The MLP acts on each position independently: expand to a hidden width (classically \(4d\); gated variants such as SwiGLU use three matrices and a smaller hidden width), apply a non-linearity, project back. Much of what the model "knows" is thought to be stored here.
  • Normalisation (LayerNorm or the cheaper RMSNorm) rescales each vector before a sub-layer reads it, which keeps training stable over many layers.
  • The residual stream is the running sum. Every layer reads it and adds a small update, so a 60-layer model is a long chain of edits to the same \(T \times d\) matrix.

After the last block comes a final norm and the output head: a \(d \times V\) matrix (sometimes shared with the embedding table) that turns each position's vector into \(V\) raw scores, the logits. During training every position's logits are scored against the actual next token. During generation only the last position's logits matter; L9 turns them into a choice.

Parameters vs activations: what "a 70B model" means

Parameters are the learned weights: fixed after training, and every one of them is used for every token. Activations are the intermediate values for a particular input; they scale with batch size times sequence length. In a classic GPT-style block, attention has four \(d \times d\) matrices (\(4d^2\)) and the MLP two \(d \times 4d\) matrices (\(8d^2\)), so a model has roughly \(12 L d^2\) parameters plus the embeddings.

Worked example

Check the formula. GPT-3's published configuration is \(L = 96\), \(d = 12288\): \(12 \times 96 \times 12288^2 \approx 174\) billion, against the reported 175B.

Weights for a 70B dense model: \(70 \times 10^9\) parameters × 2 bytes (bf16) = 140 GB; 70 GB at 8 bits; 35 GB at 4 bits (L117). That is before the KV cache and runtime overhead, so in bf16 it does not fit on a single 80 GB GPU.

Compute: a forward pass costs about \(2N\) FLOPs per token, roughly 140 GFLOPs per generated token for 70B, plus the attention term that grows with context length.

Mixture-of-experts models complicate the label. They route each token through a few of many MLP "experts", so they quote total parameters (which set memory) and active parameters (which set compute per token). Always check which number a model card means.

What breaks in production
  • Sizing hardware from the parameter count alone. Weights are only the floor. KV cache for long prompts and many concurrent users can rival the weights (L8).
  • Assuming the model sees words or characters. It sees token vectors. Spelling, counting letters and exact string manipulation are hard for that reason, not because the model is careless.
  • Treating attention weights as an explanation. A high weight says a head read from that position, not that the token caused the answer. There are dozens of heads per layer, and the MLPs do much of the work.

L8 · DAY 6

Inference Mechanics: Prefill, Decode and the KV Cache

50m video40m practice

A model reads your whole prompt in one parallel pass (prefill), then writes its answer one token per forward pass (decode). Prefill is limited by arithmetic, decode by how fast the GPU can stream the weights and the KV cache out of memory. That one asymmetry explains time to first token, output pricing and most latency advice.

Autoregressive generation, one token at a time

The forward pass of L7 yields logits for the next token only. To write 300 tokens, the server runs 300 forward passes, each time appending the chosen token to the input. Causal masking makes this cheap: the keys and values that earlier tokens produced in each layer never change, because a token can't see anything after it. The server stores them and each new step computes \(q, k, v\) for just the newest token, attends over the stored keys and values, and appends its own. That store is the KV cache.

Prefill vs decode: compute-bound vs bandwidth-bound

Derivation · Arithmetic intensity

A forward pass of an \(N\)-parameter model costs about \(2N\) FLOPs per token, and in bf16 the weights occupy \(2N\) bytes that must be read from GPU memory at least once per pass.

  • Prefill of \(T\) tokens: \(2NT\) FLOPs for one read of the weights, an intensity of about \(T\) FLOPs per byte.
  • Decode, one sequence: \(2N\) FLOPs per read of the weights (plus the whole KV cache), about 1 FLOP per byte.

An accelerator with roughly 1,000 TFLOP/s of bf16 compute and 3 TB/s of memory bandwidth (H100-class, order of magnitude) breaks even at about 300 FLOPs per byte. A prompt of a few thousand tokens is far above that: prefill keeps the arithmetic units busy. Decode is far below it: the arithmetic units mostly wait for memory.

The only ways to make decode efficient are to do more useful work per byte read: batch many users' sequences into each step so one read of the weights serves all of them, shrink the bytes (quantisation, L117), or guess several tokens per step and verify them at once (speculative decoding, L110).

def decode_ceiling(weight_bytes, kv_per_seq, batch, bandwidth=3.0e12):
    """Upper bound on tokens/s if every decode step must read all weights
    once plus each sequence's KV cache from memory (ignores compute)."""
    step_s = (weight_bytes + batch * kv_per_seq) / bandwidth
    return step_s * 1e3, batch / step_s

Batching multiplies throughput, but each user's stream slows down, and at large batch the KV caches, not the weights, dominate the bytes read. This is an idealised ceiling; real servers reach a fraction of it.

The KV cache and its size

Definition · KV-cache size $$\text{KV bytes} = 2 \times L \times n_{\text{kv}} \times d_{\text{head}} \times T \times b \times B$$

The 2 is one key and one value; \(L\) layers; \(n_{\text{kv}}\) key/value heads per layer; \(d_{\text{head}}\) dimensions per head; \(T\) tokens in context (prompt plus output so far); \(b\) bytes per value (2 for bf16/fp16, 1 for an 8-bit cache); \(B\) sequences in the batch.

Grouped-query attention (GQA) lets several query heads share one key/value head. With 32 query heads and 8 KV heads, each group of 4 query heads reads the same keys and values, and the cache is 4× smaller than full multi-head attention (MHA) of the same shape. Multi-query attention is the extreme case, a single KV head. Ainslie et al. (2023) report quality close to MHA at a fraction of the cache, which is why most recent open models use GQA.

from dataclasses import dataclass

One 128k-token conversation on Llama-3.1-8B needs 16 GiB of cache, about as much as the model's own bf16 weights. Ten such users on a 70B model need 400 GiB of cache. Long context is a memory problem before it is a compute problem.

Long prompts, long outputs and server-side batching

  • Long prompts raise TTFT. Prefill work grows linearly with \(T\) for the weight matmuls, plus an attention term that grows with \(T^2\) and starts to matter at long context. A rough estimate for an 8B model at 50% utilisation of 1,000 TFLOP/s: \(2 \times 8\!\times\!10^9 \times 8192 / 5\!\times\!10^{14} \approx 0.26\) s for an 8k prompt, before queueing.
  • Long outputs raise total latency. At the batch-1 ceiling above, 8,192 output tokens take \(8192 \times 5.5\) ms \(\approx 45\) s. Each step also reads a slightly bigger KV cache, so time per output token creeps up as the response grows.
  • Batching is the server's business. Inference servers use continuous batching: the scheduler adds new requests to the running batch at each decode step and removes finished ones, instead of waiting for a whole batch to finish (Yu et al. 2022). vLLM's PagedAttention stores the cache in fixed-size blocks so it can pack more sequences into memory (Kwon et al. 2023; L118). For you, this means latency depends on other people's traffic, so measure percentiles, not single calls.

Why output tokens cost more

Compare the two phases on the same hardware. In the rough numbers above, prefill handles about 31,000 tokens per second; decode at batch 1 handles 181. Even at batch 32, a decoded token takes about 0.35 ms of GPU time against roughly 0.03 ms for a prefilled one. Decode also holds KV-cache memory for the whole response, which caps how many users fit on a GPU. A plausible reading of API price sheets, which typically charge several times more per output token than per input token, is that they reflect this gap. Providers do not publish their cost models, and prices also carry business choices, so treat this as the engineering intuition rather than an accounting fact. Check the current price page for the actual ratio.

What this means for prompt design
  • Put stable content (instructions, tool definitions, documents reused across calls) first and the variable part last. A server that keeps the KV cache for a shared prefix can skip that prefill entirely; that is prompt caching (L24).
  • Every prompt token adds TTFT and occupies cache memory for the whole response. Trim what doesn't help.
  • Output length is the main latency dial. Ask for the format you need, cap max_tokens, and remember that thinking tokens are output tokens (L11).
What breaks in production
  • Capacity planning from weights only. A self-hosted model that fits comfortably at 4k context runs out of memory at 32k with the same concurrency. Size with the KV formula at your p95 context length and target batch.
  • Benchmarking latency with one call. Shared servers batch you with strangers. TTFT and time per output token vary with load and time of day.
  • "Make it shorter" by trimming the prompt. If the response is long, the decode phase dominates. Cut output first.

Sampling: Temperature, Top-p, Top-k and Logprobs

40m video45m practice

The model outputs a score for every token in the vocabulary; a sampler turns those scores into one choice. Temperature reshapes the distribution, top-k, top-p and min-p cut off its tail, and logprobs let you read it. Pick the settings per task, and know which APIs let you set them at all.

From logits to a distribution

Definition · Softmax with temperature $$p_i = \frac{\exp(z_i / \tau)}{\sum_j \exp(z_j / \tau)}, \qquad \tau > 0.$$

\(z\) is the logit vector from the output head (L7). \(\tau = 1\) is the model's own distribution. \(\tau < 1\) sharpens it towards the top token; \(\tau > 1\) flattens it. As \(\tau \to 0\) all the mass goes to \(\arg\max_i z_i\): greedy decoding, which servers implement directly when you pass temperature 0.

Temperature never changes the ranking of tokens, only how much probability the lower-ranked ones get. The trouble with high temperature is the long tail: a vocabulary has on the order of 100,000 tokens, and thousands of individually unlikely ones add up to a real chance of picking nonsense. The truncation rules below remove that tail before sampling.

Algorithm · Truncated sampling
  1. Top-k: keep the \(k\) most probable tokens (Fan et al. 2018).
  2. Top-p (nucleus): keep the smallest set of top tokens whose probabilities sum to at least \(p\) (Holtzman et al. 2020). The set is small when the model is confident and large when it isn't.
  3. Min-p: keep tokens with \(p_i \ge m \cdot \max_j p_j\) (Nguyen et al. 2024). The cut-off scales with the top token's probability, which holds up better at high temperature.
  4. Renormalise what is left and draw one token. Servers usually apply temperature first, then the filters.
import numpy as np

def softmax_t(logits, temperature):
    if temperature == 0:                              # greedy: all mass on the argmax
        p = np.zeros_like(logits)
        p[np.argmax(logits)] = 1.0
        return p
    z = logits / temperature
    e = np.exp(z - z.max())
    return e / e.sum()

def top_k(p, k):
    keep = np.argsort(p)[::-1][:k]
    out = np.zeros_like(p); out[keep] = p[keep]
    return out / out.sum()

def top_p(p, mass):
    order = np.argsort(p)[::-1]
    n = int(np.searchsorted(np.cumsum(p[order]), mass)) + 1   # smallest set with >= mass
    out = np.zeros_like(p); out[order[:n]] = p[order[:n]]
    return out / out.sum()

def min_p(p, ratio):
    out = np.where(p >= ratio * p.max(), p, 0.0)
    return out / out.sum()

Why temperature 0 is still not deterministic

Greedy decoding is a deterministic function of the logits, but the logits are not a deterministic function of your prompt on a shared server.

  • Floating point. Addition is not associative: in Python (0.1 + 0.2) + 0.3 gives 0.6000000000000001 and 0.1 + (0.2 + 0.3) gives 0.6. GPU kernels sum in different orders depending on matrix shapes.
  • Batching. Your request is batched with other people's (L8), and many kernels are not batch-invariant: the same row can come out with different low-order bits at a different batch size. Thinking Machines Lab (2025) argue this is the main source of run-to-run variation in practice.
  • Near-ties. When two tokens' logits differ in the fourth decimal place, those bits decide the argmax, and once one token differs the rest of the answer diverges.
  • Mixture-of-experts routing. In some implementations, which expert processes a token can depend on the other tokens in the batch, for example when experts have capacity limits.

Seeds help on a single server with fixed settings, but providers document them as best-effort. Design for variation: evaluate on distributions of outputs, not one run.

Logprobs as a confidence signal

OpenAI-compatible servers can return \(\log p\) of each generated token and its top alternatives (logprobs=True, top_logprobs=5). For a classifier that answers with one label token, \(\exp(\text{logprob})\) is the model's probability for that label, which you can threshold to send uncertain tickets to a human. Two caveats: post-trained chat models are often less well calibrated than their base models (OpenAI's GPT-4 technical report shows this), and a sequence's probability says nothing about whether it is grounded. L12 covers calibration properly.

def distinct_n(texts: list[str], n: int = 2) -> float:
    """Share of word n-grams that are unique across all outputs (Li et al. 2016)."""
    grams = [tuple(w[i:i + n]) for w in (t.lower().split() for t in texts)
             for i in range(len(w) - n + 1)]
    return len(set(grams)) / max(1, len(grams))

def first_token_prob(r: ChatCompletion) -> float | None:
    lp = r.choices[0].logprobs
    if lp is None or not lp.content:
        return None                                  # server ignored logprobs=True
    return math.exp(lp.content[0].logprob)

How Models Are Trained: Pretraining, Instruction Tuning, RLHF and DPO

50m video30m practice

A chat model is a next-token predictor trained on the internet, then taught to follow instructions by imitation, then pushed towards answers people (or other models, or verifiers) prefer. Each stage leaves fingerprints, and most of the strange behaviour you will debug is one of them.

Pretraining: next-token prediction and what it yields

Definition · Language-modelling objective $$\mathcal{L}_{\text{LM}}(\theta) = -\sum_{t=1}^{T} \log p_\theta(x_t \mid x_{<t})$$

Cross-entropy of the actual next token, averaged over trillions of tokens of web text, books and code. Nothing else is supervised.

Predicting the next token well forces the model to absorb facts, grammar, code conventions and a good deal of reasoning patterns. It also yields in-context learning: give a base model a few examples in the prompt and it continues the pattern (Brown et al. 2020). What it does not yield is instruction following. Ask a base model "How do I restart a deployment?" and a plausible continuation is another question from the same FAQ page. The data also has a knowledge cut-off: the model knows nothing after its crawl date, and it may not know where that date is.

Supervised fine-tuning on demonstrations

SFT uses the same loss on curated (prompt, ideal response) pairs, written by people or by stronger models, formatted with a chat template that marks the system, user and assistant turns. The loss is usually computed on the response tokens only. Thousands to tens of thousands of good examples are enough to turn a document-continuer into an assistant (Ouyang et al. 2022 used about 13,000 prompts for InstructGPT's SFT stage). The model learns the format and the persona, and it imitates the length, tone and confidence of the demonstrations, including their habit of always having an answer.

Reward models and RLHF

Demonstrations are expensive and cap the model at the demonstrators' level. Comparisons are cheaper: show raters two responses and ask which is better. A reward model \(r_\phi(x, y)\), usually the SFT model with a scalar head, is trained so that preferred responses \(y_w\) score above rejected ones \(y_l\) (a Bradley–Terry model):

$$\mathcal{L}_{\text{RM}}(\phi) = -\E_{(x, y_w, y_l)}\Big[\log \sigma\big(r_\phi(x, y_w) - r_\phi(x, y_l)\big)\Big].$$

The policy is then optimised with reinforcement learning to score highly, with a KL penalty that keeps it close to the SFT model \(\pi_{\text{ref}}\):

$$\max_{\pi_\theta}\ \E_{x,\ y \sim \pi_\theta(\cdot \mid x)}\big[r_\phi(x, y)\big] - \beta\, \KL\big(\pi_\theta(\cdot \mid x)\,\|\,\pi_{\text{ref}}(\cdot \mid x)\big).$$

InstructGPT used PPO (Schulman et al. 2017) for this step: sample responses, score them with the reward model, and take small, clipped policy-gradient steps. The KL term matters because the reward model is only an approximation. Optimise it too hard and the policy finds responses the reward model loves and people don't (reward hacking, or over-optimisation).

RLAIF, Constitutional AI and DPO

  • RLAIF replaces human preference labels with labels from a model. Constitutional AI (Bai et al. 2022) guides that model with a short written list of principles: a supervised phase where the model critiques and revises its own responses against the principles, then RL on AI-generated preference labels. It scales feedback and makes the target behaviour inspectable.
  • DPO (Rafailov et al. 2023) skips the explicit reward model and the RL loop. It shows that the KL-regularised objective above has a closed-form optimal policy, and turns the preference data into a classification loss on the policy itself:
$$\mathcal{L}_{\text{DPO}}(\theta) = -\E_{(x, y_w, y_l)}\left[\log \sigma\!\left(\beta \log \frac{\pi_\theta(y_w \mid x)}{\pi_{\text{ref}}(y_w \mid x)} - \beta \log \frac{\pi_\theta(y_l \mid x)}{\pi_{\text{ref}}(y_l \mid x)}\right)\right]$$ 
import numpy as np

def log_sigmoid(x):
    return -np.logaddexp(0.0, -x)                    # stable log(1 / (1 + e^-x))

def dpo_loss(pi_w, pi_l, ref_w, ref_l, beta=0.1):
    """Arguments: summed log-probs of the chosen (w) and rejected (l) responses
    under the policy being trained (pi) and the frozen reference (ref)."""
    margin = beta * ((pi_w - ref_w) - (pi_l - ref_l))
    return float(-log_sigmoid(margin).mean())

At initialisation the loss is \(\log 2\); it falls as the policy raises the chosen response's probability relative to the reference and lowers the rejected one's. That is all you need for now. L122 derives it and covers the relatives (IPO, KTO, ORPO) when you run it yourself.

Reinforcement learning with verifiable rewards

For maths, code and other tasks with checkable answers, the reward can come from a program instead of a learned model: 1 if the final answer matches, or if the unit tests pass, else 0. The model samples many attempts per problem and is updated towards the successful ones. DeepSeek-R1 (DeepSeek-AI 2025) showed this, with the GRPO algorithm (Shao et al. 2024), produces long chains of reasoning that were not demonstrated, and the Tülu 3 report (Lambert et al. 2024) named the approach RLVR. A verifier is much harder to hack than a reward model, though not impossible: a model rewarded for passing tests can learn to special-case the tests. This stage is what produces the reasoning models of L11; L123 applies it.

Reasoning Models and Test-Time Compute

50m video45m practice

A transformer does a fixed amount of computation per token, so the only way to make it think harder is to let it write more tokens before it answers. Reasoning models are trained to use those tokens well. You pay for them as output tokens and wait for them as decode steps, so spend them only where your evals show they help.

Chain of thought as extra computation

One forward pass has a fixed depth: \(L\) layers, whatever the question. A problem that needs ten dependent steps cannot be solved reliably in one pass if each step needs a few layers. Writing intermediate results down turns the output into a scratchpad: every generated token is another full forward pass that can read everything written so far (L8). That is why "let's think step by step" helped even untuned models (Kojima et al. 2022) and why few-shot examples with worked reasoning helped more (Wei et al. 2022). The prompting side of this, including self-consistency, is L19.

Test-time compute is the general idea: spend more inference compute per question, by thinking longer, sampling several answers and voting, or searching over candidates, instead of using a bigger model. Snell et al. (2024) study when that trade is worth it; the answer depends on problem difficulty.

Reasoning models: trained to think before answering

Prompted chain of thought imitates reasoning seen in pretraining. Reasoning models are trained for it with reinforcement learning on verifiable tasks (L10): sample long reasoning traces, reward the ones that end in a correct answer, repeat. The models learn to plan, check intermediate results, notice mistakes and backtrack, behaviours that were rarely demonstrated explicitly. The result is a model whose quality on maths, code and multi-step problems rises with the number of reasoning tokens it is allowed, with diminishing returns, and whose outputs are much longer.

How providers expose it

On Claude (SDK 1.13) there are two dials. thinking controls whether, and how, the model reasons in separate blocks before its answer; output_config={"effort": ...} sets how much work it puts into the whole response, with values low, medium, high, xhigh and max.

Definition · Thinking settings
  • {"type": "disabled"}: no thinking blocks.
  • {"type": "enabled", "budget_tokens": N}: think for up to about N tokens. The SDK documents N ≥ 1024 and less than max_tokens.
  • {"type": "adaptive"}: the model decides how much to think, guided by effort.
  • Both thinking modes accept "display": "summarized" (default, readable thinking text) or "omitted" (thinking content withheld; a signature is still returned for continuity).

The response then contains thinking blocks (fields thinking and signature), occasionally redacted_thinking blocks (opaque data), and finally text or tool_use blocks.

What you see is not necessarily the raw reasoning. The SDK calls the default display "summarized", and Anthropic's extended-thinking docs say you are billed for the full thinking tokens generated, not for the length of what is shown. Other providers make similar choices: OpenAI's reasoning models expose a reasoning-effort setting and summaries rather than raw traces, and open reasoning models served locally usually emit their full trace as text between special tags. Check each provider's current docs before you depend on the format.

Latency and cost

Thinking tokens are output tokens. They are billed at the output rate and generated at decode speed, one forward pass each. The arithmetic is simple: at 100 output tokens per second, 8,000 thinking tokens add 80 seconds before the first word of the answer. A budget is a ceiling, not a target; the model often uses less, and on adaptive settings the spend varies per question, so report medians and the 95th percentile, not just means. Put thinking on a task only after you have measured it, and set max_tokens high enough that the answer is not cut off after a long think (check stop_reason == "max_tokens").

  • Thinking everywhere. Turning it on globally multiplies latency and output cost on the many requests that are lookups.

Hallucination, Calibration and Knowing What the Model Knows

45m video40m practice

A language model always produces a fluent continuation, whether or not it knows the answer, and most of its training rewarded answering over abstaining. Hallucination is the expected result. You reduce it by grounding, by giving the model a real way out, and by measuring how often it takes that way out on your own questions.

Kinds of hallucination

Definition · Three kinds that matter in products
  • Fabricated facts: confident claims about the world that are false, such as a flag that doesn't exist on kubectl drain or the wrong default for a timeout.
  • Fabricated citations: references, URLs, document titles, API functions or quotations that were never written.
  • Unsupported by the context: the answer contradicts, or goes beyond, the documents you supplied. The summarisation literature calls these intrinsic and extrinsic hallucinations (Maynez et al. 2020). For a RAG product this is the kind you can measure most precisely, because you know what the model was given (L51).

Why it happens

Pretraining maximises the probability of the next token (L10). Text on the web rarely says "I don't know"; it states things. A fact seen once in training, such as a person's birthday or a minor config default, is hard to learn reliably, but the model still learns the shape of an answer and produces one. Post-training then teaches the assistant persona from demonstrations that almost always contain an answer.

Kalai et al. (2025, "Why Language Models Hallucinate") add an incentive argument. Most benchmarks grade answers right or wrong, with no credit for abstaining, and models are tuned to do well on them. Under that grading a guess is never worse than "I don't know".

Derivation · The incentive to guess

Let \(p\) be the model's probability of being right if it answers. Under 0/1 grading the expected score is \(p\) for answering and 0 for abstaining, so answering wins for every \(p > 0\). Now charge \(k\) points for a wrong answer:

$$\E[\text{score} \mid \text{answer}] = p - k(1 - p) > 0 \iff p > \frac{k}{1 + k}.$$

With \(k = t/(1 - t)\) the threshold is exactly \(t\). Kalai et al. propose stating such a confidence target in evaluation instructions ("answer only if you are more than \(t\) confident; mistakes cost \(t/(1-t)\) points"), so that abstaining is rewarded when it should be.

Knowledge cut-offs add a time dimension. Kubernetes removed PodSecurityPolicy in v1.25; a model whose data mostly predates that will describe it as current, fluently. Anything versioned, priced or recently changed needs retrieval (L38), and the system prompt should include today's date.

Calibration and verbalised confidence

A model is calibrated if, among answers given with confidence 0.8, about 80% are right. Expected calibration error measures the gap: bin the answers by stated confidence and average the difference between accuracy and confidence, weighted by bin size.

$$\text{ECE} = \sum_{b=1}^{B} \frac{|S_b|}{n}\,\big|\operatorname{acc}(S_b) - \operatorname{conf}(S_b)\big|$$ 
import numpy as np

def ece(confidence, correct, bins=10):
    """Expected calibration error: bin by stated confidence, average |accuracy - confidence|."""
    conf, ok = np.asarray(confidence, float), np.asarray(correct, float)
    idx = np.minimum((conf * bins).astype(int), bins - 1)
    return float(sum((idx == b).mean() * abs(ok[idx == b].mean() - conf[idx == b].mean())
                     for b in range(bins) if (idx == b).any()))

rng = np.random.default_rng(0)
conf = rng.uniform(0.5, 1.0, size=2000)                  # stated confidences
calibrated = rng.random(2000) < conf                     # right as often as it claims
overconfident = rng.random(2000) < conf - 0.2            # right 20 points less often
print(f"calibrated ECE {ece(conf, calibrated):.3f}   overconfident ECE {ece(conf, overconfident):.3f}")
calibrated ECE 0.013   overconfident ECE 0.200

Where do confidences come from? Token probabilities (L9) are one source; Kadavath et al. (2022) found large pretrained models reasonably calibrated on multiple-choice questions, while OpenAI's GPT-4 report shows post-training made that model's probabilities less calibrated. Verbalised confidence ("give a confidence from 0 to 1") is the other source and the only one on APIs without logprobs. Results in the literature are mixed: Tian et al. (2023) found verbalised confidence better calibrated than token probabilities for some RLHF models, and Xiong et al. (2024) found it often overconfident. Measure it on your data before you threshold on it.

Mitigations

  • Grounding with retrieval: put the relevant documents in the prompt and instruct the model to answer from them (Phases 4 and 5).
  • Permission to say "I don't know": say explicitly that abstaining is acceptable and what to say instead, and make sure your evals don't penalise it.
  • Quote before answering: ask the model to first extract the passages that support the answer, then answer only from those quotes. Missing quotes become a visible signal.
  • Verification passes: a second call checks each claim against the sources and removes or flags unsupported ones (Chain-of-Verification, Dhuliawala et al. 2023).
  • Constrained outputs: an enum of allowed labels, citations that must be IDs of documents you supplied, then a code check that each cited ID exists (L20, L45).

Measuring hallucination on your own data

Public hallucination benchmarks don't tell you how a model behaves on your corpus. A probe set does: questions in three kinds, each graded differently.

import re
from collections import Counter
from dataclasses import dataclass

ABSTAIN = re.compile(r"\b(i don['’]t know|i do not know|not (?:in|covered by) the "
                     r"(?:docs|documentation|context)|no information)\b", re.I)

@dataclass(frozen=True)
class Probe:
    id: str
    kind: str                       # "answerable" | "unanswerable" | "false_premise"
    question: str
    accept: tuple[str, ...] = ()    # substrings that mark a correct answer or correction

def grade(p: Probe, reply: str) -> str:
    hit = any(a.lower() in reply.lower() for a in p.accept)
    abstained = bool(ABSTAIN.search(reply))
    if p.kind == "answerable":
        return "correct" if hit else ("abstained" if abstained else "wrong")
    if p.kind == "unanswerable":
        return "abstained" if abstained else "hallucinated"
    return "corrected" if hit else "accepted_premise"

def report(probes, replies):
    out = {}
    for kind in ("answerable", "unanswerable", "false_premise"):
        g = Counter(grade(p, r) for p, r in zip(probes, replies) if p.kind == kind)
        out[kind] = dict(g) | {"n": sum(g.values())}
    return out

On three hand-written replies, one of each kind (a correct kubectl describe pod answer, an invented on-call rota, a correction of the PodSecurityPolicy premise), report returns {'answerable': {'correct': 1, 'n': 1}, 'unanswerable': {'hallucinated': 1, 'n': 1}, 'false_premise': {'corrected': 1, 'n': 1}}. Substring and regex grading is crude; read every reply the first time and refine accept and ABSTAIN, or move to an LLM judge later (L89).

What breaks in production
  • Abstention you never measured. An "I don't know" instruction can also make the model refuse answerable questions. Always report correct answers on answerable probes next to correct abstentions on unanswerable ones.
  • Citations that look right. A well-formatted link to a plausible docs page is the most convincing fabrication. Validate every cited URL or ID against your index in code.
  • Testing only on questions the model knows. An eval set with no unanswerable or false-premise questions cannot detect hallucination, however large it is.

Long Context: What Fits, What Gets Lost and Context Rot

45m video45m practice

A context window is the most a model will accept, not the amount it uses well. Quality depends on how much irrelevant text surrounds the part that matters and where that part sits, and every token costs prefill time and money on every call. Measure your model's length and position sensitivity before you design around a big number.

What "supports a million tokens" means

The advertised window is the maximum of input plus output tokens the API will accept (L4). Reaching it took training or fine-tuning on long sequences and usually adjusting the rotary position frequencies (L7). It guarantees that the request runs. It does not guarantee that a fact at token 600,000 is used as reliably as one at token 600. And because a request is stateless, the whole window is prefilled, cached in KV memory (L8) and billed again on every call unless you use prompt caching (L24). Some providers also charge a higher rate above a length threshold; check the price page rather than assuming linear pricing.

Worked example

A DocPilot question answered by stuffing 400,000 tokens of documentation costs 400,000 input tokens per question. Retrieval that sends 5 chunks of 500 tokens costs 2,500, so stuffing is 160× the input tokens, with a TTFT likely measured in tens of seconds rather than about one. At a few thousand questions a day, the difference decides the architecture before quality is even measured.

Needle-in-a-haystack tests and their limits

The standard probe hides one sentence (the needle) at a chosen depth inside filler text and asks for it back. Plotted over length × depth, it shows whether a model can find a literal fact anywhere in its window, and recent frontier models typically score near-perfectly on the simplest version. That is the problem with it as a quality signal:

  • The needle usually shares words with the question, so it is a lexical lookup. NoLiMa (Modarressi et al. 2025) removed that overlap and reported large drops as context grew.
  • Real tasks need several facts combined, aggregation over the whole context, or ignoring near-miss distractors. RULER (Hsieh et al. 2024) adds such tasks and reports that many models' effective context is much shorter than the claimed one.
  • The filler is often unrelated text (essays, repeated sentences). Your haystack will be documents that look like the needle.

Run needles anyway, as a cheap floor on your own documents. If a model fails the easy version at your target length, it will fail the hard ones.

Lost in the middle, and context rot

Definition · Two position and length effects
  • Lost in the middle (Liu et al. 2023; TACL 2024): on multi-document question answering and key-value retrieval, accuracy was highest when the relevant document was at the start or end of the context and lowest in the middle, a U-shaped curve.
  • Context rot: output quality falling as input length grows, even when the relevant information is present and the task is unchanged. It is widely reported by practitioners; Chroma's 2025 technical report "Context Rot" tested a range of current models on controlled tasks and found performance degrading with input length, more so when similar-looking distractors were present.

The effects vary by model, task and generation, and newer models reduce them. The direction has been consistent enough that you should assume they apply until your own measurements show otherwise. They also explain why stuffing more retrieved chunks into a RAG prompt can make answers worse: each extra chunk is another distractor (L44).

Position effects: documents first, question last

Anthropic's long-context prompting guidance recommends putting long documents at the top of the prompt and the question and instructions at the end, wrapping each document in tags with its source. Two reasons fit the mechanics: the question is then the most recent thing the model read when it starts generating, and the documents form a stable prefix that prompt caching can reuse across questions. Asking the model to quote the relevant passages before answering (L12) further helps it locate the needle.

import itertools, random

What breaks in production
  • Context that grows silently. Agent loops and chat histories accumulate tool results until the window is mostly stale text, quality drops, and the cost per turn climbs. Budget the window (L75).

Multimodal Inputs: Images, PDFs and Audio

45m video50m practice

Images and PDF pages go into the same context window as text, as content blocks that cost tokens according to their size. Vision is strong at reading screenshots, charts and document pages and weak at exact counting, tiny text and precise spatial relations, so measure it field by field on your own documents before trusting it.

Images as content blocks

A user turn's content can be a list of blocks instead of a string (L3). An image block carries its source either inline as base64 or as a URL the API fetches:

{"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": "iVBORw0..."}}
{"type": "image", "source": {"type": "url", "url": "https://example.com/diagram.png"}}

In SDK 1.13 the base64 media types are image/jpeg, image/png, image/gif and image/webp. Inside the model, an image encoder turns the picture into a sequence of vectors that sit in the residual stream next to text tokens (L7); you pay for them as input tokens.

Definition · Image token cost (planning estimate)

Anthropic's vision docs have given the approximation

$$\text{tokens} \approx \frac{w \times h}{750},$$

applied after the image is downscaled to fit a maximum size (a long edge of about 1,568 px in the docs at the time of writing). Treat both numbers as model-specific and confirm them with client.messages.count_tokens, which accepts image blocks. Other providers use different schemes, such as fixed-size tiles.

import base64, json, struct
from pathlib import Path

MEDIA = {".png": "image/png", ".jpg": "image/jpeg", ".jpeg": "image/jpeg",

def image_block(path) -> dict:
    p = Path(path)
    return {"type": "image", "source": {"type": "base64", "media_type": MEDIA[p.suffix.lower()],

    assert data[:8] == b"\x89PNG\r\n\x1a\n", "not a PNG"
    return struct.unpack(">II", data[16:24])          # IHDR width, height

def estimate_image_tokens(w, h, *, px_per_token=750, max_edge=1568):
    """Rough planning estimate: downscale so the long edge <= max_edge, then
    ~1 token per px_per_token pixels. Confirm with count_tokens for your model."""
    s = min(1.0, max_edge / max(w, h))
    return round(w * s * h * s / px_per_token)

PDFs: extracted text plus page images

A PDF goes in as a document block with source {"type": "base64", "media_type": "application/pdf", "data": ...} or a URL. Anthropic's PDF-support docs describe processing each page as both its extracted text and a rendered image of the page, so the model can use the text layer for exact wording and the image for layout, tables and charts. Both cost tokens, so a page costs its text tokens plus roughly one image's worth. A 100-page manual is a long-context request (L13) with all its costs; send the pages you need. The block also accepts title, context and citations fields, which L45 uses for grounded citations.

For an ingestion pipeline you will usually extract text yourself instead (L40) and send page images only for pages whose layout carries meaning (L58).

Audio: transcribe, or use a native audio model

The Claude Messages API in SDK 1.13 has no audio content block, so audio reaches Claude as text. The usual route is speech-to-text first: open models in the Whisper family (Radford et al. 2022) run locally, and OpenAI-compatible servers expose transcription as client.audio.transcriptions.create(file=..., model=...). A transcript is cheap, searchable, loggable and can be fed to any model; it loses tone, hesitation, overlapping speakers and timing unless the STT model adds them. Natively audio-capable models from some providers accept audio directly and can respond to how something was said; check which models your provider offers. Real-time voice agents are L125.

Prompts that combine images with instructions

Prompting with images
  • Put the image before the question, as with long documents. With several images, label them in text ("Image 1:", "Image 2:") and refer to them by label.
  • Say what the image is ("a terminal screenshot from kubectl describe") and what to ignore.
  • Ask for a transcription of the visible text first, then the answer from that transcription. It turns a vision problem into a reading problem and gives you something to check.
  • Ask for structured fields with an explicit "empty if not visible" rule, so missing fields can't be invented (L12).

  • Exact-match grading of free text. Field accuracy needs normalisation (case, whitespace, backticks), or a correct answer scores zero.

L15 · DAY 10

Scaling, Capability Trends and Planning for Next Year's Models

35m video25m practice

Model quality has improved predictably with compute, data and parameters, and the price of any fixed level of capability keeps falling. Build so that a better model makes your product better on the day it ships: evals you can re-run and a model layer you can swap, not prompt tricks tuned to today's weaknesses.

Scaling laws in one picture

Kaplan et al. (2020) trained many transformer language models and found that test loss falls as a power law in each of three quantities when the other two are not the bottleneck: parameters \(N\), training tokens \(D\) and training compute \(C\):

$$L(N) \approx \left(\frac{N_c}{N}\right)^{\alpha_N}, \qquad L(D) \approx \left(\frac{D_c}{D}\right)^{\alpha_D}, \qquad C \approx 6ND.$$

On log-log axes each is a straight line over many orders of magnitude. The exponents are small (below 0.1 in their fits), so each constant improvement in loss needs a multiplicative increase in resources. The \(6ND\) rule counts about \(2N\) FLOPs per token for the forward pass (L7) and \(4N\) for the backward pass. Loss is not capability, and specific skills can appear abruptly as loss falls smoothly, but the smooth curves are why labs could plan ever-larger training runs with confidence.

Compute-optimal training, and over-training for cheap inference

Result · Chinchilla

Hoffmann et al. (2022) asked: for a fixed compute budget, how should you split it between parameters and tokens? Their answer was to scale both roughly equally with compute, about 20 training tokens per parameter (an approximate rule of thumb, not a constant of nature). Chinchilla, 70B parameters trained on 1.4T tokens, outperformed the 280B-parameter Gopher, trained on 300B tokens with a similar budget.

import math

def train_flops(n_params, n_tokens):
    return 6 * n_params * n_tokens                    # forward 2N + backward 4N per token

def chinchilla_optimal(compute, tokens_per_param=20):
    """C = 6 N D with D = r N  =>  N = sqrt(C / (6 r))."""
    n = math.sqrt(compute / (6 * tokens_per_param))
    return n, tokens_per_param * n

C = train_flops(70e9, 1.4e12)
n, d = chinchilla_optimal(C)
print(f"Chinchilla budget {C:.2e} FLOPs -> N = {n / 1e9:.0f}B params, D = {d / 1e12:.1f}T tokens")

Chinchilla-optimal minimises training compute for a given loss. A model that will serve trillions of tokens should minimise training plus inference, and inference costs \(2N\) per token forever. Over the 10T served tokens above, the 70B model's inference compute is more than twice its training compute. So labs over-train small models far past 20 tokens per parameter: Meta reported pretraining Llama 3 8B on over 15T tokens, nearly 100× the Chinchilla ratio. The small model will not match a well-trained 70B on everything; the point is that for a fixed quality target, a smaller, longer-trained model is often cheaper over its lifetime (Sardana and Frankle 2023 formalise this).

The falling price of capability, and distillation

For a fixed level of capability, say "scores X on a benchmark you care about", the price per token has fallen steeply year on year. Analyses such as Epoch AI's report declines of roughly an order of magnitude per year or more, with wide variation by task and threshold. Over-trained small models, better data, quantisation (L117), serving optimisations (L118) and distillation all contribute.

Distillation trains a small student to imitate a large teacher: originally by matching its output distributions (Hinton et al. 2015), and for LLMs usually by fine-tuning on the teacher's generated answers. DeepSeek-R1's release included small models distilled from R1's reasoning traces. You will distil DocPilot's triage into a small open model in L124; check the teacher provider's terms first, since some restrict using outputs to train other models. The engineering consequence: a task that needs the largest model today will probably run on a small, cheap one within a year or two.

What to build so the product improves when models do

Build for the next model
  • Evals first. A golden set and automated grading (Phase 8) turn "is the new model better for us?" into a one-command answer. Without them, every upgrade is a gamble.
  • A swappable model layer. All calls go through llm.py; model IDs and per-task settings live in one table, not scattered string literals. Pin versions and re-run evals before changing them (L5).
  • Logged inputs. Keep enough of the call log (L2) to replay real traffic against a candidate model.
  • Thin scaffolding. Prefer simple prompts plus retrieval and tools over elaborate chains that compensate for a specific model's weakness.

What to avoid: brittle prompt hacks (all-caps warnings, magic phrases, instructions that only exist to dodge one model's quirk), and heavy engineering around today's limits, such as a five-step decomposition pipeline for reasoning that the next model does in one call. Such work often turns into a liability: it adds latency and cost, and it can make a stronger model perform worse. When you add a workaround, write down which weakness it addresses and an eval that would show it is no longer needed.

# docpilot/routes.py: the only place that maps tasks to models and settings
from dataclasses import dataclass
from docpilot.llm import LARGE, MODEL, SMALL, chat

@dataclass(frozen=True)
class Route:
    model: str
    effort: str | None = None
    max_tokens: int = 1024

    "triage": Route(SMALL, effort="low", max_tokens=400),
    "answer": Route(MODEL, effort="medium", max_tokens=1200),
    "judge":  Route(LARGE, effort="high", max_tokens=800),

    r = routes[task]
    extra = {"output_config": {"effort": r.effort}} if r.effort else {}
    return call(messages, model=r.model, max_tokens=r.max_tokens, **extra, **kw)

What breaks in production
  • Hard-coded model IDs. A deprecation notice turns into a hunt through the codebase, and some call sites get missed.
  • Upgrading without evals. A newer model that is better on average can be worse on your highest-value tasks, or format output differently enough to break a parser.
  • Prompts tuned to the old model. Workarounds that were needed for the previous model can confuse a better one. Re-test with the workarounds removed.

Small samples need intervals

Twenty probes per group is what a solo engineer can afford to write and pay for, and 15/20 against 17/20 is not a finding. Report every pass rate with an interval. The textbook \(\hat p \pm 1.96\sqrt{\hat p(1-\hat p)/n}\) behaves badly at small \(n\) and collapses to zero width at 0% or 100%. Use the Wilson interval instead.

Definition · Wilson score interval

For \(k\) passes in \(n\) trials, with \(\hat p = k/n\):

$$\frac{\hat p + \frac{z^2}{2n}}{1 + \frac{z^2}{n}} \;\pm\; \frac{z}{1 + \frac{z^2}{n}}\sqrt{\frac{\hat p(1-\hat p)}{n} + \frac{z^2}{4n^2}}, \qquad z = 1.96 \text{ for 95\%}.$$

It is the set of true rates \(p\) that a two-sided score test at the 5% level would not reject, so it stays inside [0, 1] and keeps a sensible width even when \(k = 0\) or \(k = n\).

To compare two configurations, run them on the same items and look at the per-item differences. Pairing removes the variation due to item difficulty, which is often most of it (Miller 2024 makes this case for LLM evals).

import math
import numpy as np

def wilson(k: int, n: int, z: float = 1.96) -> tuple[float, float]:
    """Wilson score interval (95% by default) for k successes in n trials."""
    if n == 0:
        return 0.0, 1.0
    p, z2 = k / n, z * z
    centre = (p + z2 / (2 * n)) / (1 + z2 / n)
    half = z * math.sqrt(p * (1 - p) / n + z2 / (4 * n * n)) / (1 + z2 / n)
    return max(0.0, centre - half), min(1.0, centre + half)

def paired_diff_ci(a, b, *, iters=10_000, seed=0):
    """Bootstrap 95% CI for mean(a - b) when a and b are scored on the same items."""
    d = np.asarray(a, float) - np.asarray(b, float)
    idx = np.random.default_rng(seed).integers(0, len(d), size=(iters, len(d)))
    boot = d[idx].mean(axis=1)
    return float(d.mean()), float(np.quantile(boot, 0.025)), float(np.quantile(boot, 0.975))

Reading the numbers

Zero failures in ten tries still allows a true failure rate of up to 28%. Eighty per cent on ten items is compatible with anything from about half to almost all. A configuration that fixes 3 of 20 items and breaks none has an interval reaching down to zero; the same improvement rate on 100 items is clearly above zero. Decide your sample size from the difference you need to detect, not from what fits in an afternoon.

The runner and the cache

import hashlib, json, time
from dataclasses import asdict, dataclass
from pathlib import Path
from typing import Callable

@dataclass(frozen=True)
class Reply:                       # what every backend returns
    text: str
    output_tokens: int

@dataclass
class Case:
    probe: str
    group: str                     # report row, e.g. "think-2k" or "32k @ 0.5"
    id: str
    messages: list
    settings: dict                 # backend-specific kwargs
    check: Callable[[str], bool]

@dataclass
class Result:
    probe: str
    group: str
    case_id: str
    passed: bool
    output_tokens: int
    latency_s: float
    text: str

def _key(model, c: Case) -> str:
    raw = json.dumps([model, c.probe, c.group, c.id, c.messages, c.settings],
                     sort_keys=True, default=str)
    return hashlib.sha256(raw.encode()).hexdigest()[:16]

def run_suite(probes, model, backend, *, call, cache_path: Path):
    cache = {}
    if cache_path.exists():
        for line in cache_path.read_text(encoding="utf-8").splitlines():
            row = json.loads(line)
            key = row.pop("key")                         # pop before Result(**row)
            cache[key] = Result(**row)
    results, skipped = [], [p.name for p in probes if backend not in p.backends]
    with cache_path.open("a", encoding="utf-8") as log:
        for probe in (p for p in probes if backend in p.backends):
            for c in probe.cases(backend):
                k = _key(model, c)
                if k not in cache:                       # re-runs are free
                    t0 = time.perf_counter()
                    r = call(c.messages, model=model, **c.settings)
                    cache[k] = Result(c.probe, c.group, c.id, c.check(r.text), r.output_tokens,
                                      time.perf_counter() - t0, r.text)
                    log.write(json.dumps({"key": k} | asdict(cache[k])) + "\n")
                results.append(cache[k])
    return results, skipped

What breaks in production
  • Cache keys that miss a setting. If the key omits the messages or settings, changing a prompt silently reuses old answers. Hash everything that affects the request, including the model ID.
  • Comparing groups of different sizes or items. A pass rate on 10 needles against one on 50 different needles is not a comparison. Keep the case set fixed across models.
  • A profile run that costs more than expected. 128k-token needles × 45 cases is millions of input tokens. Always --dry-run first and estimate with the L4 calculator.
