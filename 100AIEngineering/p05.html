L50 · DAY 36

Evaluating Retrieval: Recall@k, MRR, nDCG and Golden Sets

50m video60m practice

Retrieval is the stage you can measure without a model in the loop: given labelled relevant chunks for each query, four cheap formulas tell you how often the right evidence reaches the generator and how high it ranks. The numbers mean little without the labels behind them and the confidence interval around them.

Relevance judgements and the golden set

A relevance judgement is a label saying how useful a passage is for a query. A golden set is a list of real queries, each with its judged passages, a category, and ideally a reference answer (used in L51). You already wrote a small one for the search milestone (L37) and used recall@5 to choose a chunker (L41). This lesson makes the set and its metrics trustworthy enough to compare configurations.

Definition · graded relevance scale
  • 3: the passage answers the query on its own.
  • 2: needed for the answer, but not sufficient alone.
  • 1: on topic, adds context.
  • 0: not relevant (also the default for unjudged passages).

Binary relevance collapses this to grade > 0. Recall, precision and MRR use the binary view; nDCG uses the grades.

Sources of queries, best first: real user questions from logs or support tickets; questions written by people who know the docs; model-generated questions. To label, use pooling: run several retrievers (BM25, dense, hybrid), take the union of their top 10, and judge everything in the pool. Anything outside the pool counts as 0, so a new retriever that finds good unjudged passages is penalised. When a new configuration surfaces many unjudged passages, judge them before trusting its score.

The four metrics

For one query, let \(R\) be the set of relevant passages (grade > 0), \(d_1, d_2, \dots\) the ranked results, and \(g_i\) the grade of \(d_i\).

Formulas $$\text{recall@}k = \frac{|R \cap \{d_1,\dots,d_k\}|}{|R|} \qquad \text{precision@}k = \frac{|R \cap \{d_1,\dots,d_k\}|}{k}$$ $$\text{MRR} = \frac{1}{|Q|}\sum_{q \in Q} \frac{1}{\text{rank}_q}\quad(\text{rank}_q = \text{position of the first relevant result};\ 1/\text{rank}_q = 0 \text{ if none})$$ $$\text{DCG@}k = \sum_{i=1}^{k} \frac{g_i}{\log_2(i+1)} \qquad \text{nDCG@}k = \frac{\text{DCG@}k}{\text{IDCG@}k}$$

IDCG@k is the DCG of the ideal ranking: all judged grades sorted in descending order, truncated to \(k\). nDCG lies in \([0, 1]\). A common variant uses gain \(2^{g_i} - 1\) instead of \(g_i\), which rewards grade-3 hits more strongly; say which one you report.

Recall@k is the metric that matters most for RAG: the generator cannot cite what never reached it, and a reranker or the model can cope with some noise. Precision@k matters when the context budget is tight (L44). MRR rewards putting one good passage first, which suits single-fact lookups. nDCG rewards putting the best passages first and is the right choice when grades differ.

The evaluation module

# docpilot/evals/retrieval.py
import math, random
from statistics import mean

def recall_at_k(ranked, rel, k):            # rel: {chunk_id: grade}
    hits = {d for d, g in rel.items() if g > 0}
    return len(hits & set(ranked[:k])) / len(hits)

def precision_at_k(ranked, rel, k):
    return sum(rel.get(d, 0) > 0 for d in ranked[:k]) / k

def reciprocal_rank(ranked, rel):
    for i, d in enumerate(ranked, start=1):
        if rel.get(d, 0) > 0:
            return 1 / i
    return 0.0

def ndcg_at_k(ranked, rel, k):
    dcg = sum(rel.get(d, 0) / math.log2(i + 1) for i, d in enumerate(ranked[:k], start=1))
    ideal = sorted(rel.values(), reverse=True)[:k]
    idcg = sum(g / math.log2(i + 1) for i, g in enumerate(ideal, start=1))
    return dcg / idcg if idcg else 0.0

def bootstrap_ci(values, n_boot=5000, alpha=0.05, seed=0):
    rng, n = random.Random(seed), len(values)
    means = sorted(mean(rng.choices(values, k=n)) for _ in range(n_boot))
    return means[int(n_boot * alpha / 2)], means[int(n_boot * (1 - alpha / 2)) - 1]

def evaluate(run, golden, k=5):
    """run: qid -> ranked ids; golden: qid -> {"cat": str, "rel": {id: grade}}."""
    per_q = {q: {"recall": recall_at_k(run[q], g["rel"], k),
                 "precision": precision_at_k(run[q], g["rel"], k),
                 "rr": reciprocal_rank(run[q], g["rel"]),
                 "ndcg": ndcg_at_k(run[q], g["rel"], k)} for q, g in golden.items()}
    report = {m: (mean(v := [s[m] for s in per_q.values()]), *bootstrap_ci(v))
              for m in ("recall", "precision", "rr", "ndcg")}
    return report, per_q

Worked example · how many queries?

Per-query recall@5 values sit in \([0,1]\) with a standard deviation of roughly 0.3–0.4. The 95% half-width of a mean is about \(1.96\,\sigma/\sqrt{n}\): 0.18 at \(n = 12\), 0.06 at \(n = 100\), 0.03 at \(n = 400\). To detect a 0.05 change, unpaired, you need several hundred queries. Pairing helps a lot, because most per-query variance is "this query is hard for everyone" and cancels in the difference. That is why L16 told you to report intervals, and why the leaderboard below compares against a baseline with paired differences.

Report by query category as well as overall. In the fixture, hybrid+rerank is better on how-to queries and worse on troubleshooting (n = 4, so this is a hypothesis, not a finding). An average can hide a category that got worse. Show \(n\) next to every per-category number.

Synthetic queries and their biases

The cheap way to grow a golden set: give a model a chunk and ask for a question it answers, then label that chunk as relevant (grade 3). This works for coverage, but it is biased in known ways:

  • Lexical leakage. Generated questions reuse the chunk's words, which inflates BM25 and hides the vocabulary gap real users have (L43). Ask for paraphrases in user language and forbid copying headings.
  • One-chunk answerability. Every question has exactly one source chunk, so multi-hop questions (L54) are missing and recall looks better than it is. Other chunks that also answer the question are unlabelled and count as misses.
  • Topic skew. Models prefer to ask about definitions and well-structured sections. Sample chunks by stratum (page type, depth) and compare the category mix with real logs.

Keep synthetic and real queries in separate slices and report both. Phase 8 builds the full dataset workflow (L87).

What breaks in production
  • Labels tied to chunk IDs. Re-chunk the corpus and every judgement points at an ID that no longer exists. Store labels as (URL, heading path, character span) and map them to current chunks by overlap at evaluation time.
  • Unjudged winners. A new retriever finds a better passage nobody labelled, scores 0 for it and loses. Track the fraction of unjudged results in the top k per configuration.
  • Evaluating on the tuning set. If you tuned k, λ and the fusion weights on the golden set, its scores are optimistic. Hold out a test slice you only touch when you report results.
  • Recall over an empty set. Queries with no relevant passage (questions the docs do not answer) make recall undefined. Keep them in a separate abstention slice and score them on the generation side.

Evaluating Generation: Faithfulness, Relevance and Correctness

50m video60m practice

A RAG answer can fail because the evidence was missing or because the generator misused good evidence. Score the two separately: faithfulness asks whether every claim is backed by the retrieved context, correctness asks whether the answer matches an expert's reference. Both come down to splitting text into claims and checking each one.

Separate retrieval quality from generation quality

L50 measured retrieval against labels. Generation metrics answer different questions, and combining them tells you which stage to fix:

Context precision and recall are model-judged stand-ins for L50's metrics when you have reference answers but no chunk labels. Context recall is the fraction of reference claims attributable to some retrieved chunk. Low context recall points at retrieval; high context recall with low correctness points at the generator.

Faithfulness as claim extraction plus verification

Definition

Split the answer \(a\) into atomic claims \(c_1, \dots, c_n\). A verifier labels each claim against the context \(C\) as supported, contradicted or unsupported.

$$\text{faithfulness}(a, C) = \frac{|\{i : C \text{ supports } c_i\}|}{n}$$

Leave the score undefined when \(n = 0\), for example on a refusal. Score refusals separately rather than counting them as perfectly faithful.

# docpilot/evals/generation.py
import json
from typing import Literal
from pydantic import BaseModel
from docpilot.llm import client, SMALL

CLAIMS_PROMPT = """Break the ANSWER into atomic factual claims.
One claim = one checkable statement. Replace pronouns with the names they refer to.
Skip greetings, hedges and remarks about the documentation itself.
<question>{question}</question>
<answer>{answer}</answer>"""

VERIFY_PROMPT = """Judge each numbered claim against the CONTEXT only, not your own knowledge.
supported: the context states it, or it follows directly from the context.
contradicted: the context states something incompatible with it.
unsupported: the context does not say, even if you believe the claim is true.
Return one verdict per claim, with i = the claim number and a short supporting quote ("" if none).
<context>{context}</context>
<claims>{claims}</claims>"""

class Claims(BaseModel):
    claims: list[str]

class Verdict(BaseModel):
    i: int
    label: Literal["supported", "unsupported", "contradicted"]
    quote: str

class Verdicts(BaseModel):
    verdicts: list[Verdict]

def llm_judge(prompt: str, out: type[BaseModel], model: str = SMALL) -> BaseModel:
    msg = client.messages.parse(model=model, max_tokens=2048, output_format=out,
                                messages=[{"role": "user", "content": prompt}])
    return msg.parsed_output

def faithfulness(question, answer, hits, judge=llm_judge) -> dict:
    claims = judge(CLAIMS_PROMPT.format(question=question, answer=answer), Claims).claims
    if not claims:                       # a refusal has nothing to verify; score it elsewhere
        return {"score": None, "n_claims": 0, "verdicts": []}
    context = "\n\n".join(f"[{h.id}] {h.text}" for h in hits)
    numbered = json.dumps([{"i": i, "claim": c} for i, c in enumerate(claims)])
    verdicts = judge(VERIFY_PROMPT.format(context=context, claims=numbered), Verdicts).verdicts
    if sorted(v.i for v in verdicts) != list(range(len(claims))):
        raise ValueError("verifier must return exactly one verdict per claim")
    labels = [v.label for v in verdicts]
    return {"score": labels.count("supported") / len(claims), "n_claims": len(claims),
            "contradicted": labels.count("contradicted"), "verdicts": verdicts}

client.messages.parse(output_format=Model) (SDK 1.13) turns the Pydantic model into a native structured-output schema and returns a ParsedMessage whose parsed_output is a validated instance (L20). It bypasses the logging in chat(), so log judge calls yourself, with token usage, because evaluation spend adds up fast.

Answer relevance and correctness

Answer relevance catches answers that are faithful but beside the point. RAGAS scores it by asking a model to generate several questions the answer would answer, embedding them, and averaging their cosine similarity to the real question. A direct judge prompt ("does this answer address the question? which parts are padding?") is simpler and easier to audit. Correctness needs a reference answer from the golden set. Turn the reference into key points and gate the score on contradictions, because one confident wrong statement is worse than an omission:

CORRECT_PROMPT = """An expert wrote the REFERENCE answer. List its key points, and for each
say whether the ANSWER conveys it (wording may differ). Then list every statement
in the ANSWER that contradicts the REFERENCE.
<question>{question}</question>
<reference>{reference}</reference>
<answer>{answer}</answer>"""

class KeyPoint(BaseModel):
    point: str
    covered: bool

class Correctness(BaseModel):
    key_points: list[KeyPoint]
    contradictions: list[str]

def correctness(question, answer, reference, judge=llm_judge) -> float:
    r = judge(CORRECT_PROMPT.format(question=question, reference=reference, answer=answer), Correctness)
    if r.contradictions or not r.key_points:
        return 0.0                         # a confident wrong statement fails the answer
    return sum(k.covered for k in r.key_points) / len(r.key_points)

def agreement(metric_pass: list[bool], human_pass: list[bool]) -> tuple[float, float]:
    """Raw agreement and Cohen's kappa between a metric's pass/fail and your labels."""
    n = len(human_pass)
    po = sum(m == h for m, h in zip(metric_pass, human_pass)) / n
    pm, ph = sum(metric_pass) / n, sum(human_pass) / n
    pe = pm * ph + (1 - pm) * (1 - ph)
    return po, (po - pe) / (1 - pe) if pe < 1 else 1.0

RAGAS-style metrics and their caveats

RAGAS (Es et al., 2023) popularised reference-free RAG evaluation with three model-judged scores: faithfulness (claims in the answer supported by the context), answer relevance (the generated-question similarity above) and context relevance. Later versions of the library added context precision and recall and changed definitions over time, so pin the version and read its metric source before comparing numbers across projects. The ideas carry over; the exact numbers do not.

Caveats that apply to any judged metric
  • Claim granularity moves the score. Finer splitting yields more trivially supported claims. Fix the extractor prompt and model across compared runs.
  • Faithful is not correct. An answer faithful to an outdated chunk scores 1.0. Pair faithfulness with correctness.
  • Unsupported is not false. The back-off claim may be true; it still breaks the citation contract of L45.
  • Judges vary. Rerun a sample and count label flips. Phase 8 calibrates judges properly (L89, L90).

Human spot checks are the ground truth for the metric itself. Label 20 answers yourself (pass/fail on faithfulness and correctness) before you look at the metric's scores, then compute agreement and Cohen's kappa \(\kappa = (p_o - p_e)/(1 - p_e)\). In the run above, 90% raw agreement is only \(\kappa = 0.76\), because both raters pass 70% of answers and would agree 58% of the time by chance. Read every disagreement: each one is either a judge-prompt bug or a flaw in your own rubric.

What breaks in production
  • The judge sees more than the generator did. Pass the verifier exactly the chunks that were in the prompt, after truncation.
  • Same model judging itself. Prefer a different or larger judge, fixed across compared runs.
  • Silent judge failures. Truncated JSON and missing verdicts must raise and be counted, never become 0.0.
  • Cost. Two or three calls per answer per run. Cache verdicts keyed by (answer hash, context hash, prompt version).

L52 · DAY 37

Diagnosing RAG Failures: A Systematic Playbook

45m video45m practice

An aggregate score tells you that DocPilot is wrong; only reading failures tells you why. Trace each bad answer back to the first stage that went wrong, label it with a fixed taxonomy, count the labels, and fix the most common cause first.

A failure taxonomy

Every RAG failure has an upstream-most cause. Label that cause, not its downstream symptoms: if the right chunk never reached the prompt, the generator could not have been faithful to it. The stages are the ones on your L38 failure-mode map (L38).

Definition · seven failure classes
  • Missing from corpus. No document in the index contains the answer. Parsing bugs that drop a table or a page belong here too (L40).
  • Not retrieved. The answer is indexed but is not among the first-stage candidates (typically the top 50). Usual cause: vocabulary gap or a bad chunk.
  • Ranked too low. It is a candidate, but the reranker or the cut-off at \(k\) drops it before the prompt.
  • Lost in context. It is in the prompt, but buried among many other chunks, and the model misses it (L13).
  • Context ignored. It is in the prompt and easy to find, but the model answers from its own prior or misreads it.
  • Incomplete answer. The answer is right as far as it goes but misses parts of a multi-part question.
  • Wrong format. The content is right, but the shape is wrong: no citations, prose instead of steps, YAML that does not parse.

Tracing a bad answer back through the stages

Most of the trace can be checked automatically once each request logs its intermediate results. Treat the automatic label as a hypothesis that a person confirms by reading the trace:

# docpilot/evals/diagnose.py
from dataclasses import dataclass

@dataclass
class Trace:                    # one logged /ask request, joined with its golden-set row
    qid: str
    gold: set[str]              # relevant chunk ids (L50), mapped to the current index
    in_corpus: bool             # does the gold span exist in the index at all?
    candidates: list[str]       # pre-rerank top 50
    context: list[str]          # chunk ids sent to the generator, in prompt order
    context_tokens: int
    cited: set[str]             # chunk ids cited in the answer (L45)
    covered: float              # fraction of reference key points covered (L51)
    contradiction: bool
    format_ok: bool

def first_failure(t: Trace) -> str:
    """Upstream-most stage that failed. A hypothesis for a human to confirm, not a verdict."""
    if not t.in_corpus:
        return "missing_from_corpus"
    if not t.gold & set(t.candidates):
        return "not_retrieved"
    in_ctx = [t.context.index(g) for g in t.gold if g in t.context]
    if not in_ctx:
        return "ranked_too_low"
    if t.contradiction or not t.gold & t.cited:
        middle = 0 < min(in_ctx) < len(t.context) - 1
        return "lost_in_context" if t.context_tokens > 8000 and middle else "context_ignored"
    if t.covered < 1.0:
        return "incomplete_answer"
    return "wrong_format" if not t.format_ok else "pass"

Run on seven hand-built traces, one per class, it returns each label once. The weakest heuristic is lost versus ignored. To separate them, use an ablation: rerun the question with only the gold chunk in the prompt. If the answer is now right, the model was distracted (lost in context). If it is still wrong, the model overrode or misread the evidence (context ignored).

Error analysis: open coding, then counting

Algorithm · error analysis
  1. Sample about 50 failures: answers with correctness below 1, faithfulness below 1, or a thumbs-down. Stratify by query category so one category does not dominate.
  2. Open coding. Read each trace from question to answer. Write one free-text note about the first thing that went wrong, in your own words. Do not look at the taxonomy yet, because it would hide failure types it does not include.
  3. Axial coding. Group the notes into clusters and map each cluster to a taxonomy class. Add a class if a cluster fits none (for example "parser dropped the table").
  4. Count labels per class and per category. Have a second person relabel 10 traces to check the taxonomy is unambiguous.
  5. Prioritise by frequency × severity ÷ effort, write down the expected gain for the top fix, then measure it (L60).

Prioritising fixes

The most frequent class is not automatically first. The cheapest fix to a frequent class often wins: here, widening the reranker's candidate pool is a configuration change, while query rewriting adds a model call to every request. The 7 "missing" cases need two owners. The docs team can fill the gaps, but refusing cleanly (L45) is your job now. Before you fix anything, write the expected effect as a hypothesis ("recall@5 on troubleshooting queries +0.10") so that L60's harness can confirm or refute it.

What breaks in production
  • Labelling symptoms. "Hallucinated" is a symptom. Labelling it as the cause sends you to prompt tweaks when the chunk was never retrieved.
  • Taxonomy drift. Classes renamed or merged between rounds make counts incomparable. Version the taxonomy alongside the prompts.
  • Missing intermediate logs. Without pre-rerank candidates and the exact prompt context, half the classes cannot be told apart. Log them for every request, or at least for a sample.
  • One-off reading. Error analysis is a weekly habit. The failure mix changes after every fix, and the next fix depends on the new counts.

Small-to-Big Retrieval: Parent-Document, Sentence-Window and Multi-Vector

45m video50m practice

The unit that matches a query best is small, and the unit the generator needs to answer is big. Small-to-big retrieval separates the two: index small, precise entries that each point at a larger parent, match on the entries, and put the parents in the prompt.

Why decouple the matching unit from the context unit

L41 forced one chunk size to serve two jobs (L41). Small chunks embed sharply, because one idea per vector means the query is not diluted by neighbouring topics, but they arrive without the conditions, caveats and examples around them. Large chunks carry that context, but their embeddings average several topics and rank worse. Contextual enrichment (L42) patches the small chunk with a summary of its surroundings; small-to-big instead hands the generator the surroundings themselves.

Definition · the small-to-big family
  • Parent-document retrieval: index child chunks (or sentences), each tagged with a parent id such as a section's heading path. Retrieve children, map them to parents, deduplicate, and send the parents.
  • Sentence-window retrieval: index single sentences; return each hit with its \(w\) neighbours on either side, within the same section.
  • Multi-vector indexing: several entries per parent of different kinds (raw chunks, a model-written summary, hypothetical questions as in L42) all point to the same parent. A parent's score is the maximum over its entries: \(s(p) = \max_{e \in E(p)} s(q, e)\).
  • Hierarchical retrieval: first pick the top \(m\) sections by their summaries, then retrieve chunks only inside those sections.

Parent-document and sentence-window retrieval

# docpilot/small_to_big.py
from dataclasses import dataclass

@dataclass
class Entry:                     # one index entry; many entries point at one parent
    id: str
    text: str
    parent: str                  # section id (heading path) the entry came from
    kind: str = "chunk"          # chunk | sentence | summary | question
    pos: int = 0                 # sentence number inside the parent (sentence-window)

def to_parents(hits, parents, budget_tokens=3000):
    """Parent-document retrieval: score parents by their best entry (max), dedupe, fit a budget."""
    best = {}
    for s, e in hits:
        best[e.parent] = max(s, best.get(e.parent, 0.0))
    chosen, used = [], 0
    for pid in sorted(best, key=best.get, reverse=True):
        cost = len(parents[pid]) // 4                  # rough token count
        if used + cost <= budget_tokens:
            chosen.append(pid); used += cost
    return chosen, used

def sentence_window(hit, sentences, w=1):
    """Sentence-window retrieval: the hit sentence with w neighbours from the same section."""
    sents = sentences[hit.parent]
    return " ".join(sents[max(0, hit.pos - w): hit.pos + w + 1])

Multi-vector and hierarchical indexing

Multi-vector indexing generalises L42. Raw chunks match users who quote the docs; hypothetical questions match users who ask; summaries match broad queries that no single chunk covers. Store all of them in one collection with a kind field and the parent id as metadata (L33), so you can filter by kind when you measure which kind contributes the hits. Aggregating by maximum means one strong entry is enough. Use a sum of the top two or three entries only if you want parents with several weak matches to rise.

Hierarchical retrieval is the two-stage version for large corpora. Score section summaries, keep the top \(m\) (say 5), then rank chunks inside them. It cuts the search space and keeps hits topically coherent. The cost is that if the section stage misses, no chunk inside the missed section can be retrieved, so measure section-level recall first.

Storage and cost

Worked example · what small-to-big costs

Assume 2,000 sections averaging 1,500 tokens, with 1,024-dimensional float32 vectors (4,096 bytes each).

  • 200-token children: 15,000 vectors, about 61 MB. Single sentences (about 25 tokens): 120,000 vectors, about 492 MB, plus an ANN index on top (L31).
  • Multi-vector extras (1 summary + 3 questions per section): 8,000 more vectors, plus a one-off 2,000 model calls of about 1,500 input tokens each. Cache the section prefix (L24).
  • Query time: five 200-token children are 1,000 prompt tokens. Their parents, after deduplication to three sections, are about 4,500, so input cost per answer goes up roughly 4.5×. A budget cap like budget_tokens keeps this bounded.

Small-to-big is worth that cost only if correctness rises. Measure it with L51's correctness metric, not with recall alone: recall@k on parents is almost always higher, because the target is bigger.

What breaks in production
  • Giant parents. A 12,000-token reference page as a parent blows the budget and buries the answer (lost in context, L52). Cap parent size and fall back to the window around the hit.
  • Stale pointers. Re-ingesting a page re-creates parents with new ids, leaving children pointing at nothing. Derive parent ids from stable heading paths and update children and parents in one transaction (L48).
  • Citations to the wrong grain. The model cites the parent while your citation checker expects child ids. Decide which unit is citable and keep a span map from children to parent offsets.
  • Permissions on the parent. A public child inside a restricted page must not pull the restricted parent into the prompt. Check access on the parent you send, not only on the entry you matched (L47).

GraphRAG and Knowledge Graphs

55m video60m practice

Vector search finds passages that resemble the question. It cannot follow a chain of relations across documents, and it cannot summarise a whole corpus. A knowledge graph extracted by a model handles both, through explicit edges for multi-hop questions and community summaries for global ones, but you pay a model call per chunk to build it.

Questions vector search answers badly

  • Multi-hop: "Which objects decide what API calls a Deployment's Pods can make?" The answer chains Deployment → ReplicaSet → Pod → ServiceAccount ← RoleBinding across four pages. No single chunk resembles the question, and the RBAC page never mentions Deployments.
  • Global: "What are the main themes of the storage documentation?" or "Summarise every breaking change across these release notes." The answer depends on the whole corpus. Top-k retrieval returns k arbitrary pieces of it.

L52 files these as "not retrieved" or "incomplete", but no query rewrite fixes them: the information is spread out by nature.

Building a knowledge graph with a model

Algorithm · graph construction
  1. Extract. For each chunk, prompt a model for entities (name, type, description) and relations (head, relation, tail, description) as structured output (L20). Give a closed list of entity types (Kubernetes kinds, fields, CLI commands, feature gates) and relation types. Record the source chunk id on every element.
  2. Glean (optional). Ask again "did you miss any entities?" A second pass finds more on dense chunks, at the cost of another call each.
  3. Resolve entities. Merge "PVC", "persistent volume claim" and "PersistentVolumeClaims" into one node. Start with normalisation and an alias table, then embed the remaining names and ask a model to confirm candidate merges above a similarity threshold. Wrong merges are worse than missed ones.
  4. Store. For a few thousand nodes, networkx in memory and a JSON file are enough. For larger graphs, or ones you query concurrently and update, use a graph database such as Neo4j (property graph, Cypher queries).

Microsoft's GraphRAG and community summaries

Edge et al. (2024) target query-focused summarisation over a whole corpus. After extraction and entity summarisation (merging each entity's descriptions across chunks), they run Leiden community detection hierarchically, giving nested groups of densely connected entities. A model then writes a community summary (report) for every community at every level, bottom-up. A global question is answered by map-reduce:

  • Map: each community summary at the chosen level produces a partial answer plus a helpfulness score; zero-score partials are dropped.
  • Reduce: the best partials, sorted by score and packed into the window, are combined into the final answer.

On roughly million-token corpora (podcast transcripts, news) with model-generated sensemaking questions, the paper reports that GraphRAG beat a vector-RAG baseline on comprehensiveness and diversity, as judged by a model. The baseline was better on directness. The open-source implementation also has a local mode: match the question to entities, then gather their neighbours, relations, source chunks and community reports. That mode is the multi-hop half of the story.

The cost, and when it is worth it

Worked example · indexing bill

Embedding the same corpus costs one cheap batch job. Use the small model and batch pricing (L109), and price it from the current price page. What breaks in production
  • Extraction drift. Without a closed type list, the model invents "relates to", "is used with" and fifty other relations, and the graph becomes a hairball. Fix the schema and reject off-schema edges.
  • Bad merges. "Service" (the Kubernetes kind) merged with "service" (a generic word) connects everything to everything. Merge only within a type, and log every merge.
  • Uncited edges. An edge without a source chunk cannot be cited or checked, and may be a hallucination. Drop edges whose source does not mention both endpoints.
  • Path explosion. Hub nodes like Pod make the number of simple paths grow fast with the cutoff. Cap hops at 3–4, prefer shortest paths, and rank paths by edge relevance to the question.

Agentic RAG: Retrieval as a Tool

50m video50m practice

Single-shot RAG retrieves once, before the model has read anything. Agentic RAG turns search into a tool the model calls when it needs evidence, as many times as the question requires. That helps on multi-part and multi-hop questions, at the price of more model calls, more latency, and a loop that needs a budget and a stopping rule.

Letting the model decide when and what to retrieve

In L39–L49 the pipeline was fixed: condense the query, retrieve, generate. The first retrieval is a guess based on the user's wording. If it misses, the generator can only refuse or improvise. In iterative retrieval, the model reads what came back, notices what is missing ("the passage covers requests and limits but not init containers"), and searches again with better terms. The vocabulary gap from L43 shrinks, because after one search the model has seen the documentation's own vocabulary. Decomposition also happens naturally, one search per sub-question.

Search as a tool, with a budget

Phase 6 covers tool use in depth (L61, and the general loop in L62). Here is the minimum needed for retrieval: one tool, one loop, a hard cap on searches, and deduplication of passages already shown.

# docpilot/agentic.py
from docpilot.llm import chat
from docpilot.search import search

SEARCH_TOOL = {
    "name": "search_docs",
    "description": ("Search the Kubernetes documentation. Returns up to k passages, each with an id "
                    "and URL. Use Kubernetes terms. If results are off-topic, search again with "
                    "different terms. Search once per sub-question of a multi-part question."),
    "input_schema": {"type": "object", "additionalProperties": False, "required": ["query"],
                     "properties": {"query": {"type": "string"},
                                    "k": {"type": "integer", "minimum": 1, "maximum": 8}}},
}
SYSTEM = ("Answer questions about Kubernetes using only passages returned by search_docs, "
          "citing passage ids like [pods#restart]. If the passages do not answer it, say so.")

def agentic_answer(question, *, max_searches=4, llm=chat, search_fn=search):
    messages, log, seen = [{"role": "user", "content": question}], [], set()
    while True:
        out_of_budget = len(log) >= max_searches
        msg = llm(messages, system=SYSTEM, tools=[SEARCH_TOOL],
                  tool_choice={"type": "none"} if out_of_budget else {"type": "auto"})
        if msg.stop_reason != "tool_use":
            return msg, log
        messages.append({"role": "assistant", "content": msg.content})
        results = []
        for b in (b for b in msg.content if b.type == "tool_use"):
            if len(log) >= max_searches:          # parallel calls can overshoot the budget
                results.append({"type": "tool_result", "tool_use_id": b.id, "is_error": True,
                                "content": "Search budget used up. Answer with what you have."})
                continue
            hits = search_fn(b.input["query"], k=b.input.get("k", 5))
            new = [h for h in hits if h.id not in seen]
            seen.update(h.id for h in hits)
            log.append({"query": b.input["query"], "hits": len(hits), "new": len(new)})
            text = "\n\n".join(f"[{h.id}] ({h.url})\n{h.text}" for h in new) or "No new passages."
            results.append({"type": "tool_result", "tool_use_id": b.id, "content": text})
        messages.append({"role": "user", "content": results})

Self-RAG and CRAG: grading what was retrieved

  • Self-RAG (Asai et al., 2023) trains the generator to emit reflection tokens. These decide whether to retrieve at all, judge whether each retrieved passage is relevant, whether the generated segment is supported by it, and how useful the response is. At inference the model retrieves on demand, generates candidate segments for several passages in parallel, and keeps the best one according to its own critique scores. It needs a specially fine-tuned model; with an API model you can only copy the idea with prompts.
  • CRAG (Corrective RAG; Yan et al., 2024) adds a lightweight trained retrieval evaluator that scores the retrieved documents and triggers one of three actions. Correct: refine the documents by splitting them into strips and dropping irrelevant ones. Incorrect: discard them and fall back to web search with a rewritten query. Ambiguous: combine both. It is plug-and-play around any generator.

The DocPilot version of both ideas is a cheap grader: the small model labels each hit relevant or not before generation. If nothing is relevant, rewrite the query and search once more. If that also fails, refuse rather than fall back to the web, since L65 adds web tools with their own risks (L65).

Deep research, latency, cost and stopping

Deep-research loops stretch the same pattern to minutes: plan sub-questions, run many searches (often in parallel workers), take notes, and write a long cited report. They are worth it for open-ended research, not for a support bot answering in seconds. Phase 7 covers planning and long-horizon loops (L77).

Cost of n searches

Let \(b\) be the base prompt (system, tools, question) and \(r\) the tokens each search adds. Call \(i\) (for \(i = 0, \dots, n\)) re-reads the whole transcript, so total input tokens are

$$\sum_{i=0}^{n} (b + i\,r) = (n+1)\,b + r\,\frac{n(n+1)}{2}.$$

With \(b = 1{,}500\) and \(r = 2{,}000\): 1,500 for no search; 10,500 for two searches; 27,500 for four. Single-shot RAG with five passages is about 3,500. Growth is quadratic in \(n\), and prompt caching (L24) bills the repeated prefix at the cache-read rate. Latency is \(n+1\) sequential model calls plus \(n\) searches; parallel tool calls in one turn cut the number of rounds.

Stopping criteria, cheapest first
  • Hard budget: max searches, max tokens, wall-clock deadline. Always present, enforced in code.
  • Diminishing returns: a search that returns no new passage ids (the new count in the log) is evidence the model is circling. Two in a row should end the loop.
  • Coverage: for decomposed questions, stop when every sub-question has at least one cited passage.
  • The model's own end_turn: necessary but not sufficient. Models both stop early and over-search.
What breaks in production
  • Runaway loops. Without a code-enforced budget, one confused question can make a dozen calls. Log searches per question and alert on the p99.
  • Agentic everywhere. Most DocPilot questions are answered by one search. Route only multi-part or failed-first-search questions to the loop (L25), or pay 3–8× on everything.
  • Lost permissions. The tool must call search with the asking user's filters (L47). The model must never be able to choose them.
  • Untestable behaviour. The number of searches varies run to run. Evaluate on outcomes (correctness, citations) and on the trajectory (searches, tokens), as Phase 8 does (L91).

Long Context vs RAG: Stuffing, Caching and Hybrids

40m video45m practice

If the whole corpus fits in the context window, you can skip retrieval and send everything, cached, on every request. Whether you should depends on a cost curve that rises with corpus size and falls with cache hit rate, and on whether context rot hurts more than retrieval misses do.

When the whole corpus fits

Measure before you argue. client.messages.count_tokens(model=..., system=..., messages=...) returns the exact input size for a model's tokenizer (L4). Context-window sizes differ by model and change between releases, so read them from the model documentation rather than from memory. "Fits" also needs headroom: the system prompt, the conversation, tool definitions and the output all share the window, and quality drops well before the limit (L13). A 50-page slice of the Kubernetes docs, around 35,000 tokens, fits easily. The full documentation set does not, and never will at a sensible cost per request.

Cache-augmented generation

Definition

Cache-augmented generation (CAG): load the whole knowledge base into the model's context once, keep the processed prefix in a cache, and answer each question by appending it to that cached prefix, with no retrieval step. Chan et al. (2024) describe it with a precomputed KV cache on open models (L8). With an API model, the equivalent is prompt caching (L24): put the corpus in a stable prefix and mark it cacheable.

from docpilot.llm import chat

RULES = "Answer only from the documentation in <docs>. Cite page paths. Say so if it is not covered."

def ask_long_context(question: str, corpus_md: str):
    system = [
        {"type": "text", "text": RULES},
        {"type": "text", "text": f"<docs>\n{corpus_md}\n</docs>",
         "cache_control": {"type": "ephemeral", "ttl": "1h"}},     # breakpoint after the corpus
    ]
    msg = chat([{"role": "user", "content": question}], system=system)
    u = msg.usage                     # cache_read_input_tokens should be ~corpus size when warm
    return msg, {"read": u.cache_read_input_tokens, "write": u.cache_creation_input_tokens,
                 "uncached": u.input_tokens}

Everything before the breakpoint must be byte-identical across requests. Do not put a timestamp, the user's name or a per-user filter result in the system prompt ahead of the corpus. Check usage in your logs: a warm cache shows the corpus in cache_read_input_tokens, while a cold one shows it in cache_creation_input_tokens.

Cost at scale

Caching does not make the corpus free. Every request still pays for the whole prefix at the cache-read rate, and a request that arrives after the cache expired pays the higher write rate. RAG pays the full rate, but only for \(k\) chunks. The model below works in units of "base input tokens", so you can multiply by any provider's current price. The multipliers are parameters: Anthropic's docs have described cache writes at 1.25× the base input price for the 5-minute TTL (more for 1 hour) and reads at 0.1×. Check the current pricing page.

def rag_cost(question=300, system=1200, k=5, chunk=400):
    return system + question + k * chunk

def long_context_cost(corpus, question=300, system=1200, cold_fraction=0.02, r=Rates()):
    """Corpus + system cached; a fraction of requests arrive after the cache expired and rewrite it."""
    prefix = system + corpus
    cached = (1 - cold_fraction) * r.cache_read * prefix + cold_fraction * r.cache_write * prefix
    return cached + question

def hybrid_cost(question=300, system=1200, docs=3, doc_tokens=2500):
    return system + question + docs * doc_tokens        # retrieve 3 whole pages, no cache

Latency follows the same logic: a warm cached prefix skips most of the prefill (L8), and a cold one makes the user wait for the whole corpus to be processed. Measure time to first token for both.

Quality: context rot against retrieval misses

The two approaches fail in opposite ways. RAG misses evidence that was never retrieved: L52's "not retrieved" and "ranked too low" classes. Long context has every page in the window but suffers context rot: attention spreads across hundreds of irrelevant pages, facts in the middle are used less reliably, and similar pages (v1.29 vs v1.30 behaviour) get blended (L13). Long context tends to win on questions that need many pages at once (comparisons, "list every place X is configured") and on small corpora where retrieval is the weak link. RAG tends to win on precise lookups in large corpora. Your golden set decides, by category.

Hybrids

  • Retrieve documents, pass whole documents. Retrieve at chunk level, map to pages (the small-to-big idea from L53 at document grain), and send three to five complete pages. This fixes most "incomplete answer" failures without paying for the whole corpus.
  • Cached core plus retrieved tail. Cache the 20–30 pages that answer most questions (from your logs), and retrieve from the rest only when the question falls outside them.
  • Long context for the conversation's documents. When a user is working through one runbook, keep that runbook cached for the session and retrieve only for side questions.
Decision rules
  1. Corpus larger than about half the usable window, or growing: RAG or hybrid.
  2. Different users may see different documents (L47): RAG with filters. A shared cached corpus must contain only what every user may read.
  3. Corpus small, stable and queried often enough to keep the cache warm: try cached long context, and compare correctness by category.
  4. Questions span many pages at once: a hybrid with whole documents, or long context if the corpus fits.
  5. In every case, decide from your measured cost, latency and correctness, not from this list.
What breaks in production
  • Silent cache misses. A changed byte early in the prefix (a reordered page, a new date line) turns every request into a cache write. Alert when the share of input billed as cache_read_input_tokens drops.
  • Stale corpus. A cached corpus is a snapshot. Rebuild it on documentation releases and version it, or long context serves last month's docs with full confidence (L48).
  • Citations get vague. With 50 pages in view, models cite less precisely. Keep page paths in the corpus markup and check citations as in L45.
  • Window pressure in long conversations. Corpus plus a long chat history can hit the limit mid-conversation. Budget the window explicitly.

Structured Data: Text-to-SQL and Table Question Answering

55m video60m practice

"How many P1 tickets are still open?" has no answer in any document; it lives in a database. Have the model write SQL, but run it as an untrusted program: read-only connection, an authorizer that permits only reads of approved columns, a time limit and a row cap. Judge the result by executing it, not by reading the SQL.

Text-to-SQL prompting: schema, metrics and examples

The model needs three things it cannot guess. The schema: tables, columns, types, foreign keys, and the literal values of enum-like columns (is it 'open' or 'OPEN'?). The metric definitions: what "backlog" or "resolution time" means here. And a few examples of question-to-SQL pairs in your house style (L18). Together, the metric definitions form a small semantic layer: the business meaning of numbers is defined once, by people, and the model chooses a metric instead of inventing a formula.

Read-only execution and validation

Never let generated SQL run with write access. In production, that means a database role with SELECT on approved views only, a statement timeout and, ideally, a read replica. SQLite has no roles, so the same layers are built from the standard library: open the file read-only through a URI, install an authorizer callback that SQLite consults while compiling every statement, and abort long queries with a progress handler.

# docpilot/sql_tool.py: run model-written SQL read-only, validated, bounded
import sqlite3, time

READABLE = {"tickets": None, "customers": {"id", "name", "plan", "region"}}   # None = all columns
OK = {sqlite3.SQLITE_SELECT, sqlite3.SQLITE_READ, sqlite3.SQLITE_FUNCTION, sqlite3.SQLITE_RECURSIVE}

def authorizer(action, table, column, dbname, source):
    if action not in OK:
        return sqlite3.SQLITE_DENY                  # INSERT, UPDATE, DELETE, PRAGMA, ATTACH, CREATE ...
    if action == sqlite3.SQLITE_READ and dbname is not None:    # None = a CTE, not a stored table
        if table not in READABLE:
            return sqlite3.SQLITE_DENY              # sqlite_master or any table not on the list
        cols = READABLE[table]
        if cols is not None and column and column not in cols:
            return sqlite3.SQLITE_DENY              # a PII column such as customers.email
    return sqlite3.SQLITE_OK

def run_sql(sql: str, path="tickets.db", max_rows=200, timeout_s=2.0) -> dict:
    if not sql.lstrip().lower().startswith(("select", "with")):
        return {"error": "only SELECT queries are allowed"}
    con = sqlite3.connect(f"file:{path}?mode=ro", uri=True)       # read-only at the file level too
    con.set_authorizer(authorizer)
    deadline = time.monotonic() + timeout_s
    con.set_progress_handler(lambda: time.monotonic() > deadline, 10_000)   # non-zero aborts
    try:
        cur = con.execute(sql)                      # execute() refuses multiple statements
        rows = cur.fetchmany(max_rows + 1)
        return {"columns": [d[0] for d in cur.description], "rows": rows[:max_rows],
                "truncated": len(rows) > max_rows}
    except (sqlite3.Error, sqlite3.Warning) as e:
        return {"error": f"{type(e).__name__}: {e}"}
    finally:
        con.close()

Execute, check, retry; and plain tables

def answer_with_sql(question, schema, model, max_attempts=3):
    """model(question, schema, feedback) -> SQL string; feedback is the last error, or None."""
    feedback = None
    for attempt in range(1, max_attempts + 1):
        sql = model(question, schema, feedback)
        out = run_sql(sql)
        if "error" not in out and out["rows"]:
            return sql, out, attempt
        feedback = out.get("error") or "query returned no rows; check filters and literal values"
    return sql, out, attempt

Evaluation by execution accuracy

Definition

Execution accuracy is the fraction of questions where the predicted query's result equals the gold query's result on the same database. Compare as multisets of rows, or as ordered lists when the gold query has ORDER BY, with floats rounded. Comparing SQL strings is useless: COUNT(id) and COUNT(*) with the conditions swapped are the same query.

from collections import Counter

def normalise(rows, ordered):
    rows = [tuple(round(v, 2) if isinstance(v, float) else v for v in r) for r in rows]
    return rows if ordered else Counter(rows)

def execution_match(pred_sql, gold_sql, **kw) -> bool:
    gold, pred = run_sql(gold_sql, **kw), run_sql(pred_sql, **kw)
    if "error" in pred:
        return False
    ordered = "order by" in gold_sql.lower()
    return normalise(pred["rows"], ordered) == normalise(gold["rows"], ordered)

What breaks in production
  • Write access "just for now". One generated UPDATE on a production connection is an incident. Enforce read-only at the connection or role level, not with a prompt.
  • Expensive reads. A cross join over two large tables is read-only and still takes the database down. Use timeouts, row caps, a replica, and EXPLAIN cost checks where the database supports them.
  • Confidently wrong numbers. A plausible SQL query with the wrong metric definition (the backlog case) gives a clean-looking wrong answer. Show the SQL and the metric used next to every number.
  • Prompt injection through data. Ticket text returned in results can contain instructions. Treat row contents as data, not instructions (L97).

Multimodal RAG: Images, Charts and Page-Level Retrieval

45m video50m practice

Some answers live in a diagram, a chart or a page layout that text extraction flattens or drops. There are three ways to make them retrievable: caption the figures into the text index, embed images in a shared image–text space, or embed whole page screenshots as many patch vectors and score them by late interaction. In every case, send the retrieved page image to a vision-capable model at answer time.

When the meaning is in the figure

The Kubernetes docs explain the control plane, Service routing and the Pod lifecycle with diagrams. Vendor runbooks put the decisive information in screenshots, and incident reports put it in charts. L40's parser keeps the figure's alt text at best (L40). A question like "which component talks to etcd directly?" may be answered only by the arrows in a diagram. Before choosing a method, measure the size of the problem: label which golden-set questions need a figure to answer. If it is 3% of them, captions are enough. If it is 30%, page-level retrieval is worth a look.

Captioning images into the text index

For each figure, ask a vision model (L14) for a dense, literal description, giving it the page title, the surrounding paragraph and the alt text as context. Ask for every label, every arrow with its direction, the axes, units and notable values of a chart, and the question types the figure could answer. Index the caption as a chunk with kind="figure", the heading path and a pointer to the image file (multi-vector style, L53). This costs one vision call per figure, once, and needs nothing new in the retrieval stack. The risk is that a caption is a lossy summary written before anyone knew the question.

Multimodal embeddings and page-image retrieval

Multimodal embedding models in the CLIP family (Radford et al., 2021) map images and text into one vector space, so a text query can retrieve an image directly. They were trained mostly on natural photos with short captions. In general they handle text-dense diagrams and screenshots poorly, and one vector per image dilutes small details.

Definition · page-image retrieval, the ColPali approach

Faysse et al. (2024) embed a screenshot of each page with a vision-language model and keep one vector per image patch, on the order of a thousand low-dimensional vectors per page as described in the paper. No OCR or layout parsing is needed. A query is encoded into one vector per token, and the page score is ColBERT-style late interaction (L35):

$$s(q, P) = \sum_{i=1}^{|q|} \max_{j \in P} \langle q_i, p_j \rangle$$

The paper reports strong results against text-extraction pipelines on visually rich documents in its benchmark (ViDoRe). Treat that as a reason to test it on your pages, not as a guarantee. Successor models apply the same recipe to other vision-language backbones.

# docpilot/pages.py: late-interaction scoring over page-patch embeddings
import base64
import numpy as np

def maxsim(q: np.ndarray, page: np.ndarray) -> float:
    """q: (n_query_tokens, d), page: (n_patches, d), rows L2-normalised.
    Each query token takes its best-matching patch; the page score is the sum."""
    return float((q @ page.T).max(axis=1).sum())

def rank_pages(q, pages: dict[str, np.ndarray], k=3):
    return sorted(((maxsim(q, p), pid) for pid, p in pages.items()), reverse=True)[:k]

def page_block(png: bytes) -> dict:          # an image content block for the Messages API
    return {"type": "image",
            "source": {"type": "base64", "media_type": "image/png",
                       "data": base64.standard_b64encode(png).decode()}}

Costs

Worked example · three routes, priced in units
  • Storage. Page patches at 1,030 × 128 dims × 2 bytes: 5.3 MB for 20 pages, 2.6 GB for 10,000. A caption is one ordinary vector. Compression (pooling similar patches, binarising) is an active area; measure recall after any reduction.
  • Query time. Exact MaxSim touches every patch of every candidate page. At scale, use a cheap first stage (text hybrid, or one pooled vector per page) to pick about 50 pages, then MaxSim-rerank them. Some vector databases now support multi-vector late interaction natively.
  • Generation. Anthropic's vision docs have estimated image cost at about width × height / 750 tokens, which makes a 1000 × 1294 px page about 1,725 input tokens. Three pages are about 5,200 tokens, against about 450 for three captions. Check the current docs for resizing limits.
What breaks in production
  • Captions that hallucinate. A captioner can invent arrows or misread small labels. Spot-check captions against figures like any other ingestion output, and keep the image so the generator can check.
  • Unreadable renders. 72-dpi page renders turn 8-point labels into blur for both the retriever and the generator. Fix the render resolution, then measure.
  • Citations to pixels. "See page 13" is weaker than a quoted sentence. Ask the model to name the figure and describe the part it relied on, so a user can verify it.
  • Stale screenshots. Page images go stale when the source page changes. Hash the rendered page and re-embed on change (L48).

RAG at Scale: Latency Budgets, Caching and Cost

40m video40m practice

A RAG request is a chain of stages, and the user waits for the critical path through them. Instrument every stage, look at percentiles rather than averages, and remember that queues at shared components set the tail. Then spend the latency budget where users feel it: on time to the first token.

The latency budget across stages

DocPilot's /ask (L49) runs: embed the query → BM25 and vector search → fuse → rerank → generate (time to first token, then decoding) → check citations. A budget assigns each stage a p95 target that serves a product goal, for example first token under 1.5 s and full answer under 5 s.

Definition · critical path $$T_{\text{first token}} = t_{\text{embed}} + \max(t_{\text{bm25}}, t_{\text{vec}}) + t_{\text{fuse}} + t_{\text{queue}} + t_{\text{rerank}} + t_{\text{ttft}}$$ $$T_{\text{total}} = T_{\text{first token}} + t_{\text{decode}} + t_{\text{cite}}$$

Parallel stages cost their maximum, not their sum. Percentiles do not add: the p95 of \(T\) is below the sum of stage p95s, because stages are rarely all slow at once. Budget on measured end-to-end percentiles, and use stage percentiles to find the culprit.

Instrument every stage

# docpilot/timing.py: per-stage spans for one request
import asyncio, time
from contextlib import contextmanager

class Trace:
    def __init__(self):
        self.t0, self.spans = time.perf_counter(), []

    @contextmanager
    def stage(self, name: str):
        a = time.perf_counter()
        try:
            yield
        finally:
            self.spans.append((name, 1000 * (a - self.t0), 1000 * (time.perf_counter() - self.t0)))

async def demo():
    tr = Trace()
    with tr.stage("embed"):
        await asyncio.sleep(0.03)
    async def timed(name, secs):
        with tr.stage(name):
            await asyncio.sleep(secs)
    await asyncio.gather(timed("bm25", 0.02), timed("vector", 0.05))   # parallel retrieval
    return tr.spans

Load-testing with ten users: a simulation first

Before load-testing the real service, simulate it, so you know what the numbers should look like. Ten closed-loop users (each sends its next question when the last answer finishes) share one GPU reranker that serves one batch at a time. Stage times are lognormal around simulated medians, the query-embedding cache hits 30% of the time, and decoding emits 150–350 tokens at 10 ms each:

# docpilot/loadsim.py: simulated stage timings, closed-loop users, a shared reranker
import heapq, math, random

MEDIAN_MS = {"embed": 35, "bm25": 20, "vector": 45, "rerank": 120, "ttft": 650}   # simulated, not measured
SIGMA = {"embed": 0.3, "bm25": 0.3, "vector": 0.4, "rerank": 0.25, "ttft": 0.35}

def draw(rng, stage):                           # lognormal around the median
    return MEDIAN_MS[stage] * math.exp(SIGMA[stage] * rng.gauss(0, 1))

def simulate(users=10, per_user=20, rerank_slots=1, cache_hit=0.3, ms_per_token=10, seed=0):
    rng, slots, traces = random.Random(seed), [0.0] * rerank_slots, []
    events, done = [(0.0, u, "start", None) for u in range(users)], [0] * users
    while events:
        t, u, kind, tr = heapq.heappop(events)
        if kind == "start":
            tr = {"t0": t, "spans": []}
            e = 1.0 if rng.random() < cache_hit else draw(rng, "embed")
            b, v = draw(rng, "bm25"), draw(rng, "vector")          # run in parallel
            tr["spans"] += [("embed", 0, e), ("bm25", e, e + b), ("vector", e, e + v),
                            ("fuse", e + max(b, v), e + max(b, v) + 2)]
            heapq.heappush(events, (t + e + max(b, v) + 2, u, "rerank", tr))
        else:                                   # FIFO: earliest-free reranker slot
            free = heapq.heappop(slots)
            start, rr = max(t, free), draw(rng, "rerank")
            heapq.heappush(slots, start + rr)
            off = t - tr["t0"]
            q0, r1 = off + (start - t), off + (start - t) + rr
            g1 = r1 + draw(rng, "ttft")
            g2 = g1 + rng.randint(150, 350) * ms_per_token
            tr["spans"] += [("queue", off, q0), ("rerank", q0, r1), ("ttft", r1, g1),
                            ("decode", g1, g2), ("cite", g2, g2 + 15)]
            tr["ttfb"], tr["total"] = g1, g2 + 15
            traces.append(tr)
            done[u] += 1
            if done[u] < per_user:
                heapq.heappush(events, (tr["t0"] + tr["total"], u, "start", None))
    return traces

Parallelism, caching and streaming

  • Parallel calls. Run BM25 and vector search concurrently, and multi-query variants too (L43). Start the reranker model warm, and batch candidates in one call.
  • Query-embedding cache. Key it on the normalised query text plus the embedding model version. FAQ-style traffic repeats a lot, and a hit saves a network round trip.
  • Retrieval-result cache. Key it on (normalised query, filters, user permission set, index version), and invalidate it on every index update (L48). Leaving the permission set out of the key leaks documents across users. Answer and semantic caches come in L111.
  • Stream the answer. Time to first token is the number users feel. Stream tokens as they come, and run the citation check on the finished answer, marking it if the check fails (L105).

To scale the index, replicas (full copies) add throughput and availability, while shards (partitions) add capacity. A sharded query waits for the slowest shard: if each shard is slower than its own p99 with probability 0.01, a query fanning out to \(n\) shards hits at least one slow shard with probability \(1 - 0.99^{n}\), about 9.6% at \(n = 10\) (Dean & Barroso, 2013). Shard only when one node cannot hold the index (L31).

What breaks in production
  • Averages in dashboards. A mean of 1.0 s can hide a p99 of 9 s. Chart p50, p95 and p99 per stage.
  • Closed-loop tests that hide overload. Ten users who wait for each answer slow down when the service slows, so the test never overloads it. Also run an open-loop test at a fixed arrival rate.
  • Caches that outlive the index. A cached retrieval result from before an update serves deleted or restricted content. Include the index version in every key.
  • Unbounded queues. At high load, add a queue limit and a fast "busy, retry" response, or degrade (skip the reranker) rather than letting p95 grow without limit (L107).

Milestone: A RAG Evaluation Harness and a Measured Improvement

30m video120m practiceproject day

Phase 5 ends with one command: docpilot eval runs the retrieval and generation metrics on the golden set, saves the run, compares it with a baseline using paired confidence intervals per category, and fails when an overall metric regresses. Then use it to show that one fix from your L52 plan beats the noise.

What the harness does

Algorithm · docpilot eval
  1. Load the golden set and hash it; load the config and hash it.
  2. For each query: retrieve, answer, judge (with cached verdicts), and compute the per-query metrics.
  3. Write the run file. If there is no baseline, stop with exit 0.
  4. Refuse to compare if the golden hashes differ. Otherwise compute the paired bootstrap delta for every metric × slice (overall and each category).
  5. Mark a slice "better" or "WORSE" when its interval excludes zero. Overall WORSE means exit 1; a per-category WORSE is a warning to read.

The code

The pieces already exist. The retrieval metrics and bootstrap come from L50, faithfulness and correctness from L51 (with verdicts cached by answer hash, context hash and judge-prompt version), and the fix comes from L52's ranked list. The harness takes retrieve and answer_and_judge as parameters, so the same code runs against the real service or against deterministic fixtures in tests.

# docpilot/evals/harness.py: one command for retrieval + generation evals, diffed against a baseline
import argparse, hashlib, json, time
from pathlib import Path
from statistics import mean
from docpilot.evals.retrieval import recall_at_k, reciprocal_rank, ndcg_at_k, bootstrap_ci

METRICS = ["recall@5", "mrr", "ndcg@5", "correct", "faithful"]

def digest(obj) -> str:
    return hashlib.sha256(json.dumps(obj, sort_keys=True).encode()).hexdigest()[:10]

def run_eval(golden, retrieve, answer_and_judge, config: dict, k=5) -> dict:
    rows = []
    for g in golden:
        ranked = retrieve(g, config)                       # ranked chunk ids
        gen = answer_and_judge(g, ranked, config)          # {"correct": 0..1, "faithful": 0..1 | None}
        rows.append({"qid": g["qid"], "cat": g["cat"], "recall@5": recall_at_k(ranked, g["rel"], k),
                     "mrr": reciprocal_rank(ranked, g["rel"]), "ndcg@5": ndcg_at_k(ranked, g["rel"], k), **gen})
    return {"run_id": time.strftime("%Y%m%d-%H%M%S"), "config": config, "config_hash": digest(config),
            "golden_hash": digest(golden), "rows": rows}

def paired_delta(base_rows, new_rows, metric, cat=None):
    old = {r["qid"]: r[metric] for r in base_rows}
    diffs = [r[metric] - old[r["qid"]] for r in new_rows
             if (cat is None or r["cat"] == cat) and r[metric] is not None and old.get(r["qid"]) is not None]
    return (mean(diffs), *bootstrap_ci(diffs), len(diffs))

def compare(base, new, metrics=METRICS):
    if base["golden_hash"] != new["golden_hash"]:
        raise ValueError("golden set changed between runs; re-run the baseline first")
    cats = sorted({r["cat"] for r in new["rows"]})
    lines, regressions, warnings = ["| metric | slice | n | delta | 95% CI | verdict |", "|---|---|---|---|---|---|"], [], []
    for m in metrics:
        for cat in [None, *cats]:
            d, lo, hi, n = paired_delta(base["rows"], new["rows"], m, cat)
            verdict = "better" if lo > 0 else "WORSE" if hi < 0 else "~"
            if verdict == "WORSE":                   # gate on overall slices; per-category = warning
                (regressions if cat is None else warnings).append(f"{m}/{cat or 'all'}")
            lines.append(f"| {m} | {cat or 'all'} | {n} | {d:+.3f} | [{lo:+.3f}, {hi:+.3f}] | {verdict} |")
    return lines, regressions, warnings
def main(argv=None, *, golden, retrieve, answer_and_judge) -> int:
    p = argparse.ArgumentParser(prog="docpilot eval")
    p.add_argument("--config", required=True, help="JSON file: retrieval and prompt settings")
    p.add_argument("--baseline", help="a previous run JSON to diff against")
    p.add_argument("--out", default="evals/runs")
    a = p.parse_args(argv)
    run = run_eval(golden, retrieve, answer_and_judge, json.loads(Path(a.config).read_text()))
    out = Path(a.out) / f"{run['run_id']}-{run['config_hash']}.json"
    out.parent.mkdir(parents=True, exist_ok=True)
    out.write_text(json.dumps(run, indent=1))
    print(f"wrote {out}")
    if not a.baseline:
        return 0
    lines, regressions, warnings = compare(json.loads(Path(a.baseline).read_text()), run)
    print("\n".join(lines))
    print("warnings (per-category):", ", ".join(warnings) or "none")
    print("REGRESSIONS: " + ", ".join(regressions) if regressions else "no significant regressions")
    return 1 if regressions else 0

The noise floor

Worked example · reading the A/A run

Nothing changed in the A/A run except the judge's randomness, yet correctness is "better" by 0.133 with an interval that excludes zero. This is not a bug in the bootstrap. The report makes 20 comparisons (5 metrics × 4 slices), and at 95% you expect about one false flag by chance alone. Three consequences:

  • Gate only on a few headline metrics, declared before you run. That is why per-category flags are warnings here.
  • Cache judge verdicts so unchanged answers keep their scores. Judge noise then enters only where answers really changed.
  • Claim an improvement only when it clears the noise floor you measured. Here the fix's +0.267 correctness, with lower bound +0.150, is above the A/A swing of 0.133. Recall, which has no judge in it, is unambiguous.
What breaks in production
  • Moving golden sets. Adding questions between runs breaks pairing silently. The golden hash check refuses the comparison: re-run the baseline on the new set.
  • Untracked config. A run without its config, prompt versions (L21) and index version cannot be reproduced. Hash all three into the run record.
  • Generation variance. Real answers vary between runs too, so a real A/A includes answer variance as well as judge variance. Run it whenever the model, the judge or sampling settings change.
  • Fixtures that drift from reality. Fixtures test the harness, not DocPilot. Keep them small and deterministic, and never report fixture numbers as product results.
