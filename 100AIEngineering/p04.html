Phase 4 · Days 27–35 · Lessons 38–49

Retrieval-Augmented Generation

Phase 4 turns the Phase 3 search service into an assistant that answers questions from the Kubernetes docs with sources a reader can check. It goes stage by stage (parsing, chunking, enrichment, query transformation, retrieval tuning, grounded generation, conversation, permissions and freshness) and measures every change against the seed and retrieval eval sets. Phase 5 then measures retrieval and generation separately and adds advanced techniques only where those measurements point.

By the end of this phase you can

  • Trace a bad answer to the first pipeline stage that lost it (ingest, chunk, retrieve, assemble, generate or cite) and fix that stage before touching the prompt.
  • Parse HTML and PDFs into clean Markdown sections that keep tables, code blocks, heading paths, page numbers and source URLs, and spot-check the result by hand.
  • Choose a chunker and a chunk size by recall@5 on a span-labelled query set, never splitting code blocks or tables.
  • Enrich the index with heading paths and model-written chunk contexts using prompt caching, and report both the retrieval gain and the one-off cost.
  • Enable query rewriting, multi-query, HyDE and decomposition only where they measurably help, and tune k, score thresholds and MMR from a curve.
  • Generate grounded answers with checked inline citations, decline cleanly when the docs don't cover a question, and handle follow-up questions by condensing the conversation.
  • Enforce each user's permissions at retrieval time, keep the index fresh with incremental ingestion, and ship an /ask API with an eval report and per-answer cost and latency.

L38 · DAY 27

Why RAG: Grounding, Freshness and Private Knowledge

40m video30m practice

A model can only answer from what is in its weights or in its context window. Retrieval-augmented generation (RAG) puts the right few passages from your own corpus into the window at question time, so answers can be current, private and checkable. It is a pipeline of seven stages, and every stage can lose the answer.

The problems RAG solves

Phase 3 built a search service (L37). This phase wires it to a generator. The reasons to do so are concrete:

  • Knowledge cut-offs. A model knows nothing written after its training data was collected. Kubernetes ships several minor releases a year and deprecates APIs; a model trained on last year's docs will describe a removed field. Retrieval answers from this morning's snapshot.
  • Private data. DocPilot's ticket queue, internal runbooks and customer-specific configuration were never on the public web. No amount of scale puts them in the weights.
  • Citations. When the answer is assembled from retrieved chunks, each claim can point at a source the user can open. A wrong citation is easier to catch than a fluent wrong answer (L12).
  • Smaller models answering well. Reading a passage and restating it is easier than recalling a fact from parametric memory. With good context, a small, fast model such as SMALL often answers documentation questions about as well as a large one does without it. Measure this on your own eval set rather than assuming it (L5).

The original formulation and what we build today

Lewis et al. (2020) coined the term. Their model joined a retriever, Dense Passage Retrieval (DPR, Karpukhin et al. 2020: a BERT query encoder and a BERT passage encoder over a Wikipedia index), to a generator, the seq2seq model BART. They called the weights the model's parametric memory and the index its non-parametric memory, and treated the retrieved passage \(z\) as a latent variable to marginalise over.

The two RAG variants

With retriever \(p_\eta(z \mid x) \propto \exp\big(d(z)^\top q(x)\big)\) and generator \(p_\theta\), approximating the sum by the top-\(k\) passages:

$$p_{\text{RAG-Sequence}}(y \mid x) \approx \sum_{z \in \text{top-}k} p_\eta(z \mid x) \prod_{i=1}^{N} p_\theta(y_i \mid x, z, y_{1:i-1})$$ $$p_{\text{RAG-Token}}(y \mid x) \approx \prod_{i=1}^{N} \sum_{z \in \text{top-}k} p_\eta(z \mid x)\, p_\theta(y_i \mid x, z, y_{1:i-1})$$

RAG-Sequence uses one passage for the whole answer and mixes complete answers. RAG-Token may draw each output token from a different passage, which helps when an answer combines facts from several sources. The query encoder and generator were fine-tuned end to end on question–answer pairs; the passage encoder and its index were kept fixed, so the index never had to be rebuilt during training.

Production systems in 2026 keep the idea and drop the joint training. A general instruction-following model, used through an API and never fine-tuned, receives the top-\(k\) chunks concatenated into the prompt, and attention does the work the marginalisation did. Retrieval is usually hybrid (BM25 plus dense, L34) with a reranker (L35). Nothing trains the retriever to serve the generator any more; tuning that interface by measurement is most of this phase.

The pipeline

Algorithm · Retrieve-then-prompt
  1. Ingest: fetch documents and parse them to clean Markdown with source URL and heading path (L40).
  2. Chunk: split into retrievable units that keep tables and code whole (L41), optionally enriched with context (L42).
  3. Embed and index: dense vectors plus a BM25 index, with metadata for filters and permissions (L33, L47).
  4. Retrieve: optionally transform the query (L43), then hybrid search, rerank and tune k (L44).
  5. Assemble context: order, deduplicate and label each chunk with an id that fits the token budget.
  6. Generate: answer from the context only, or say the docs do not cover it (L45).
  7. Cite: attach chunk ids to claims and check that each cited chunk supports its sentence.

The failure surface, measured

Worked example · errors compound

Suppose (illustrative numbers) 97% of answers survive parsing, 95% are in a well-formed chunk, the gold chunk is in the top 5 for 85% of questions, and the generator answers faithfully 92% of the time when it has the chunk. If the stages fail independently, end-to-end accuracy is about \(0.97 \times 0.95 \times 0.85 \times 0.92 \approx 0.72\). A better prompt cannot raise the ceiling set by retrieval; raising recall@5 from 0.85 to 0.95 lifts the product to about 0.81. Evaluate each stage on its own (L50, L51) so you know which factor to work on.

The same order gives a debugging procedure: for a bad answer, find the first stage that lost the gold chunk. This is the seed of L52's playbook.

from dataclasses import dataclass

@dataclass
class Trace:
    question: str
    gold: set[str]            # chunk ids a human marked as containing the answer
    indexed: set[str]         # every chunk id currently in the index
    retrieved: list[str]      # ranked ids returned by search()
    in_prompt: list[str]      # ids that survived context assembly
    cited: list[str]          # ids the answer cites
    correct: bool             # graded against the reference answer

def first_failure(t: Trace) -> str:
    """Walk the pipeline in order and blame the first stage that lost the answer."""
    if not t.gold & t.indexed:
        return "ingest/chunk: answer is not in the index"
    if not t.gold & set(t.retrieved):
        return "retrieve: gold chunk not in top-k"
    if not t.gold & set(t.in_prompt):
        return "assemble: retrieved, then dropped from the prompt"
    if not t.correct:
        return "generate: right context, wrong answer"
    if not t.gold & set(t.cited):
        return "cite: right answer, unsupported citation"
    return "ok"

What breaks in production
  • Debugging the last stage first. Teams rewrite the generation prompt for a week when the gold chunk was never retrieved.
  • Silent corpus gaps. A crawler that skipped a section, or a PDF that parsed to empty text, produces confident "the docs don't cover this" answers. Count documents and chunks per section after every ingest (L48).
  • The model answers anyway. Given irrelevant chunks, the generator often falls back to parametric memory, which may describe an older Kubernetes version. Grounding and abstention (L45) are part of the pipeline.
  • Retrieval as a data leak. Anything in the index can end up in an answer. Permissions must be enforced at retrieval time (L47), before the model sees anything.

L39 · DAY 27

Naive RAG From Scratch in 100 Lines

50m video60m practice

The whole RAG loop fits in about a hundred lines of plain Python: chunk, embed, keep the vectors in a matrix, take the top k by cosine, paste them into a prompt with ids, and ask the model. Build it once without a framework. After that, every improvement is a change to a function you already understand, and every failure has a line number.

The minimal loop

Definition · naive RAG

Single-shot retrieval with no query transformation, reranking or filtering. Embed the question once, take the \(k\) chunks with the highest cosine similarity \(\cos(q, d_i) = q^\top d_i\) (for unit vectors), and condition one generation call on them. The rest of this phase fixes its failure modes one at a time.

Chunk, embed, store

The embedding below is a toy, a hashed bag of words, chosen because it is deterministic and needs no download. What matters is its contract: strings in, an \((n, d)\) array of unit vectors out. The model you chose in L29 has the same contract, so swapping it in changes one function. It uses hashlib because Python's hash() of a string changes from process to process.

import hashlib
import re
from dataclasses import dataclass

import numpy as np
from anthropic.types import Message

DIM = 1024
STOP = set("a an and are be by can do does for how i in is it of on or the to what when which with".split())

def tokens(text: str) -> list[str]:
    return [w for w in re.findall(r"[a-z0-9]+", text.lower()) if w not in STOP]

def embed(texts: list[str]) -> np.ndarray:
    """Toy model, real contract: n strings in, (n, DIM) unit vectors out."""
    out = np.zeros((len(texts), DIM), dtype=np.float32)
    for i, text in enumerate(texts):
        for w in tokens(text):
            h = int.from_bytes(hashlib.blake2b(w.encode(), digest_size=8).digest(), "little")
            out[i, h % DIM] += 1.0 if h >> 63 else -1.0      # signed hashing
    norms = np.linalg.norm(out, axis=1, keepdims=True)
    return out / np.where(norms == 0, 1, norms)

@dataclass
class Chunk:
    id: str
    url: str
    text: str

def chunk(url: str, text: str, size: int = 40, overlap: int = 10) -> list[Chunk]:
    """Fixed-size word windows with overlap: the baseline L41 improves on."""
    words, step = text.split(), size - overlap
    starts = range(0, max(len(words) - overlap, 1), step)
    return [Chunk(f"{url}#{i}", url, " ".join(words[s:s + size])) for i, s in enumerate(starts)]

class Store:
    """The whole 'vector database': a matrix in memory."""
    def __init__(self, chunks: list[Chunk]):
        self.chunks = chunks
        self.vecs = embed([c.text for c in chunks])

    def search(self, query: str, k: int = 3) -> list[tuple[Chunk, float]]:
        scores = self.vecs @ embed([query])[0]          # unit rows: cosine
        top = np.argsort(-scores)[:k]
        return [(self.chunks[i], float(scores[i])) for i in top]

Brute-force search is exact, and over tens of thousands of chunks it takes milliseconds (L31). Chunk ids are url#position, stable across runs, so citations and eval labels can refer to them.

The prompt template and returning sources

Template choices that matter
  • Sources first, question last. Anthropic's long-context guidance puts long documents above the query.
  • Numbered sources, cited by number. Code maps numbers back to chunk ids and URLs, so the model never has to copy a URL.
  • One exact refusal string. A fixed sentence is easy to detect, count and evaluate; free-form refusals are not.
  • Tags around retrieved text. They separate data from instructions, which matters once retrieved text is untrusted (Phase 9).
SYSTEM = ("You answer questions about Kubernetes using only the sources provided. "
          "Cite every claim with its source number, like [2]. If the sources do not "
          "contain the answer, reply exactly: The documentation I have doesn't cover this.")

def build_prompt(question: str, hits: list[tuple[Chunk, float]]) -> str:
    sources = "\n".join(f'<source id="{n}" url="{c.url}">\n{c.text}\n</source>'
                        for n, (c, _) in enumerate(hits, 1))
    return f"<sources>\n{sources}\n</sources>\n\nQuestion: {question}"

def text_of(msg: Message) -> str:
    return "".join(b.text for b in msg.content if b.type == "text")

def answer(question: str, store: Store, chat, k: int = 3) -> dict:
    hits = store.search(question, k)
    msg = chat([{"role": "user", "content": build_prompt(question, hits)}], system=SYSTEM)
    return {"answer": text_of(msg),
            "sources": [{"n": n, "id": c.id, "url": c.url, "score": round(s, 3)}
                        for n, (c, s) in enumerate(hits, 1)]}

The answer carries the chunks the model was shown, with scores, even when it refuses: they are the first thing you check when debugging (L38's Trace).

What breaks immediately

Seven questions show all three classic failures:

  • Answers that ignore the context. For the ConfigMap size question the top chunk contains "cannot exceed 1 MiB", yet the reader answered "A ConfigMap is an API object used to store non-confidential data in key-value pairs. [1]". A real model fails the same way with answers that paraphrase the sources without answering, or that come from memory.
  • Weak matches from a vocabulary gap. "Database passwords" never appears in the docs, which say "confidential" and "Secret". Retrieval found the ConfigMap page through one shared word, scoring 0.14, the same as the unanswerable etcd question, so no threshold separates them (L44). Real embeddings narrow this gap; query rewriting narrows it further (L43).
  • Bad chunks. Forty-word windows ignore sentences and headings. Two of the eight chunks start mid-sentence: pod-lifecycle#1 opens with "is Always. The restartPolicy applies…", cut off from its subject "The default value", and configmap#1 opens with "encryption. If the data…" (L41, L42).
What breaks in production
  • Lenient grading hides failures. The restartPolicy question "passed" with "…possible values Always, OnFailure and Never", which never says which is the default. Substring checks are a smoke test; correctness needs a reference-answer judge (L51).
  • Mismatched embeddings. Queries embedded with a different model or version from the index silently ruin retrieval. Store the model name with the vectors and check it.
  • Unbounded context. Big chunks times a big k can blow the token budget (L4). Cap the prompt in tokens, not in chunks.
  • No record of what the model saw. Without the sources logged next to the answer, a bad answer cannot be traced to a stage.

L40 · DAY 28

Ingestion I: Parsing HTML, PDFs, Office Files and Tables

50m video60m practice

Retrieval can only find what the parser kept. Turn every source into clean Markdown with its headings, tables and code blocks intact, and record where each section came from: URL, heading path, page. Every later stage is built on that output.

Parsing quality caps RAG quality

In L38's failure chain, parsing is the first factor, and nothing downstream recovers what it loses. A flattened table can't be retrieved as a table, a lost heading no longer gives its chunks context, a nav bar repeated on every page matches every vague query, and a scanned PDF with no text layer contributes nothing.

Definition · the target format

Markdown is the interchange format between parsers and the rest of the pipeline: it keeps the structure retrieval and generation use (headings, lists, tables, fenced code) in few tokens, is easy to chunk on (L41), and models read it fluently. Every parser emits Section records: heading path, Markdown body, source metadata.

HTML to clean Markdown

Two jobs: drop boilerplate (navigation, footers, sidebars, scripts) and keep structure. Where a site lacks semantic tags, select its main-content container with a per-site rule or a content-extraction library such as trafilatura. If the source exists as Markdown, parse that instead: the Kubernetes docs are Markdown in the kubernetes/website repository, though their Hugo shortcodes need handling. The parser below uses only html.parser and emits one Section per heading.

import re
from dataclasses import dataclass, field
from html.parser import HTMLParser

SKIP = {"head", "nav", "header", "footer", "aside", "script", "style"}
HEADINGS = {"h1": 1, "h2": 2, "h3": 3, "h4": 4}
BLOCKS = {"p", "li", "pre", "table", "img", *HEADINGS}

def squash(s: str) -> str:
    return re.sub(r"\s+", " ", s).strip()

@dataclass
class Section:
    url: str
    heading_path: str
    blocks: list[str] = field(default_factory=list)
    page: int | None = None                          # PDFs only

    @property
    def markdown(self) -> str:
        return "\n\n".join(self.blocks)

class HtmlToSections(HTMLParser):
    def __init__(self, url: str):
        super().__init__(convert_charrefs=True)
        self.url, self.skip, self.path, self.text = url, 0, [], ""
        self.pre, self.lang, self.row, self.rows = False, "", [], []
        self.sections = [Section(url, "")]

    def emit(self, block: str, li: bool = False):
        blocks = self.sections[-1].blocks
        if li and blocks and blocks[-1].startswith("- "):
            blocks[-1] += "\n" + block                  # keep list items together
        elif block:
            blocks.append(block)

    def handle_starttag(self, tag, attrs):
        self.skip += tag in SKIP
        if self.skip:
            return
        if tag in BLOCKS:
            self.emit(squash(self.text)); self.text = ""
        a = dict(attrs)
        if tag == "pre":
            self.pre = True
        elif tag == "code":
            m = re.search(r"language-(\w+)", a.get("class") or "")
            if self.pre: self.lang = m.group(1) if m else ""
            else: self.text += "`"
        elif tag == "img" and a.get("alt"):
            self.emit(f"[Figure: {a['alt']}]")      # stand-in until a model captions it

    def handle_endtag(self, tag):
        if self.skip:
            self.skip -= tag in SKIP
            return
        t, self.text = self.text, ""
        if tag in HEADINGS:
            level = HEADINGS[tag]
            self.path = [p for p in self.path if p[0] < level] + [(level, squash(t))]
            self.sections.append(Section(self.url, " > ".join(h for _, h in self.path)))
            self.emit("#" * level + " " + squash(t))
        elif tag == "pre":
            self.emit(f"```{self.lang}\n{t.strip(chr(10))}\n```"); self.pre = False
        elif tag in ("td", "th"):
            self.row.append(squash(t).replace("|", r"\|"))
        elif tag == "tr":
            self.rows.append(self.row); self.row = []
        elif tag == "table":
            head, *body = self.rows; self.rows = []
            self.emit("\n".join(["| " + " | ".join(head) + " |", "|" + " --- |" * len(head)]
                                + ["| " + " | ".join(r) + " |" for r in body]))
        elif tag in ("p", "li"):
            self.emit(("- " if tag == "li" else "") + squash(t), li=tag == "li")
        else:
            self.text = t                            # inline tag: keep accumulating
            if tag == "code" and not self.pre: self.text += "`"

    def handle_data(self, data):
        if not self.skip:
            self.text += data

def parse_html(url: str, html: str) -> list[Section]:
    p = HtmlToSections(url)
    p.feed(html); p.close()
    return [s for s in p.sections if s.blocks]

Ingestion II: Chunking Strategies and Their Trade-offs

55m video60m practice

A chunk is the unit you embed, retrieve and cite, so its boundaries decide what can be found. Good chunkers follow the document's own structure, never cut a code block or table in half, and record where each chunk came from. You find out which one is good by measuring retrieval, not by reading chunks and nodding.

Why chunk at all

Embedding models have an input limit, and many silently truncate past it. Even within the limit, one vector per page is a poor index: a page covers several topics, and a single vector cannot be close to all of them. Citations also need a unit smaller than a page. Chunking trades these off.

Why big chunks dilute

Model a chunk covering \(m\) unrelated topics as the normalised sum of orthonormal topic directions, \(c = \tfrac{1}{\sqrt m}\sum_{i=1}^m t_i\). A query about topic 1, \(q = t_1\), scores

$$\cos(q, c) = \frac{1}{\sqrt m},$$

so a four-topic chunk scores 0.5 while a focused chunk scores 1.0, even though both contain the answer. Real embeddings are not exact averages, but the direction holds: larger chunks match less sharply. Smaller chunks match sharply but carry less context to the generator, and \(k\) of them may miss the sentence that qualifies the answer. That is the precision–context trade-off. Small-to-big retrieval (L53) sidesteps it by retrieving small and generating with the parent.

Fixed-size and recursive splitting

Fixed-size windows of \(s\) tokens with overlap \(o\) are trivial and structure-blind; overlap reduces the damage when a boundary lands mid-sentence, at the cost of an index \(s/(s-o)\) times larger (512 with 64 overlap: 1.14×). Recursive splitting tries the coarsest separator first (section headings, then blank lines, lines, sentences), recurses only into pieces that are still too big, and merges small neighbours back up to the size limit. Both measure size in words here as a stand-in; in production, count tokens with the embedding model's tokenizer.

import re

import numpy as np
# tokens() and embed() are L39's toy model; a real embedding model replaces embed()

def n_words(s: str) -> int:                 # proxy for tokens
    return len(s.split())

def fixed(text: str, size: int = 50, overlap: int = 10) -> list[str]:
    words, step = text.split(), size - overlap
    return [" ".join(words[i:i + size]) for i in range(0, max(len(words) - overlap, 1), step)]

SEPS = [r"(?=\n## )", r"(?=\n### )", r"(?<=\n\n)", r"(?<=\n)", r"(?<=\. )"]

def recursive(text: str, size: int = 50, seps: list[str] = SEPS) -> list[str]:
    if n_words(text) <= size or not seps:
        return [text]
    out = []
    for piece in filter(str.strip, re.split(seps[0], text)):
        for p in recursive(piece, size, seps[1:]):
            if out and n_words(out[-1]) + n_words(p) <= size:
                out[-1] += p                       # separators were kept, so += restores the text
            else:
                out.append(p)
    return [c.strip() for c in out]

Structure-aware chunking

L40's parser already produced Markdown with headings, fenced code and tables, so the chunker can use them. Start a chunk at every heading, treat each fenced block and table as atomic, and when a section overflows, continue under the same heading path. Record the heading path and position as metadata (L42 prepends the path to the chunk text). An oversize table can still be split, by rows, with the header row repeated in each piece. An oversize code block can be split at blank lines, with the fence repeated.

def md_blocks(md: str) -> list[str]:
    """Blank-line-separated blocks; a fenced code block stays one block even with blank lines."""
    out, cur, fence = [], [], False
    for line in md.split("\n"):
        fence ^= line.startswith("```")
        if line.strip() or fence:
            cur.append(line)
        elif cur:
            out.append("\n".join(cur)); cur = []
    return out + ["\n".join(cur)] * bool(cur)

def by_heading(md: str, size: int = 50) -> list[dict]:
    path, chunks = [], []
    for b in md_blocks(md):
        if m := re.match(r"(#{1,4}) (.*)", b):
            level = len(m.group(1))
            path = [p for p in path if p[0] < level] + [(level, m.group(2))]
            chunks.append({"heading_path": " > ".join(t for _, t in path), "text": b})
        elif chunks and (n_words(chunks[-1]["text"]) + n_words(b) <= size
                         or re.fullmatch(r"#{1,4} .*", chunks[-1]["text"])):  # never leave a heading alone
            chunks[-1]["text"] += "\n\n" + b
        else:
            chunks.append({"heading_path": chunks[-1]["heading_path"] if chunks else "", "text": b})
    return [dict(c, position=i) for i, c in enumerate(chunks)]

Semantic chunking

Semantic chunking splits where the topic changes. Embed each sentence, compute the cosine between neighbours, and cut where it falls into the lowest few percent. Size limits are essential: without a minimum, ties produce one-sentence chunks; without a maximum, a long uniform passage becomes one chunk. It costs one embedding per sentence at ingestion. It ignores the headings the author already provided, so on well-structured docs it often just rediscovers them.

def semantic(text: str, pct: float = 30, min_words: int = 15, max_words: int = 50) -> list[str]:
    sents = [s for s in re.split(r"(?<=[.!?])\s+|\n{2,}", text) if s.strip()]
    v = embed(sents)
    sims = (v[:-1] * v[1:]).sum(axis=1)             # cosine of each adjacent pair
    cut = np.percentile(sims, pct)
    out, cur = [], [sents[0]]
    for s, sim in zip(sents[1:], sims):
        size = n_words(" ".join(cur))
        if (sim <= cut and size >= min_words) or size + n_words(s) > max_words:
            out.append(" ".join(cur)); cur = []
        cur.append(s)
    return out + [" ".join(cur)]

With the toy bag-of-words embedding, many neighbouring sentences share no words and score exactly 0, so the cut uses <=. A real embedding model gives smoother similarities.

Choosing a size

Common defaults are a few hundred tokens with 10–20% overlap; treat them as the centre of a grid, not the answer. Sweep size (for example 128, 256, 512, 1024 tokens) per chunker, measure recall@5 and the tokens sent to the generator, and pick the smallest size that keeps recall. Store chunker and chunker_version with every chunk so you can re-chunk and compare later (L48).

What breaks in production
  • Split code and tables. Half a YAML manifest or a table without its header row retrieves well and answers badly. Assert in tests that no chunk contains an odd number of fences.
  • Silent truncation. A chunk longer than the embedding model's input limit is embedded from its first part only, so the rest can never be retrieved.
  • Orphaned context. "Set it to true to enable this" means nothing without the heading. Keep the heading path, then use it (L42).
  • Evaluating with chunk-id labels. Gold labels tied to one chunker's ids make every other chunker look broken. Label spans or sections.

Contextual Retrieval and Chunk Enrichment

45m video50m practice

A chunk cut from a page loses what the page around it said: which feature, which resource, which version. Put that context back into the text you index (the heading path for free, a short model-written summary for a one-off cost) and keep the original text for the generator.

The lost-context problem

Docs are written to be read in order. Sentences like "Set this field to true to enable it", "The default is 3" or a bare YAML block rely on the heading and the previous paragraph. Once that sentence is a chunk, neither its embedding nor its BM25 terms say what "this field" or "it" refers to, and the right chunk loses to one that merely mentions the query's nouns. L41 ended on exactly this: the YAML chunk for "What command does the liveness probe run?" ranked second because the words "liveness command" were only in the heading.

Definition · index text vs display text

Store two strings per chunk. The index text is what you embed and put into BM25: the chunk plus whatever context helps it match queries. The display text is the chunk as written, which is what the generator quotes and the user sees in a citation. Enrichment changes only the index text, so it can't put words in the docs' mouth.

Prepending heading paths and titles

The cheapest enrichment is structural: prefix every chunk's index text with the document title and heading path L40 recorded. It costs no model calls and a few tokens per chunk. On L41's sample page:

Heading paths fix references to the section. They don't fix references that cross sections ("as described above"), and they add nothing when headings are generic ("Overview", "Example"). That is where a model helps.

Contextual retrieval

Anthropic's "Introducing Contextual Retrieval" (September 2024) gives the model the whole document and one chunk, and asks for a short context that situates the chunk within the document, typically a sentence or two. That context is prepended to the chunk before both embedding ("contextual embeddings") and BM25 indexing ("contextual BM25"). On the post's own datasets, it reports the top-20 retrieval failure rate falling by roughly 35% with contextual embeddings, roughly 49% with contextual BM25 added, and roughly 67% with reranking on top. Those are that post's results on its data; your corpus may gain more or less, which is why the practice measures it.

CONTEXT_PROMPT = """Here is the chunk we want to situate within the whole document
<chunk>

</chunk>

def contextualize(doc_md: str, chunks: list[dict], chat, model: str = SMALL) -> tuple[list[dict], dict]:
    """One call per chunk. The whole document is a cached system block shared by every call."""
    system = [{"type": "text", "text": f"<document>\n{doc_md}\n</document>",
               "cache_control": {"type": "ephemeral"}}]
    usage = dict.fromkeys(["input_tokens", "output_tokens",
                           "cache_creation_input_tokens", "cache_read_input_tokens"], 0)
    out = []
    for c in chunks:
        msg = chat([{"role": "user", "content": CONTEXT_PROMPT.format(chunk=c["text"])}],
                   system=system, model=model, max_tokens=200)
        for key in usage:
            usage[key] += getattr(msg.usage, key) or 0
        ctx = text_of(msg).strip()
        out.append(dict(c, context=ctx, index_text=f"{ctx}\n{c['heading_path']}\n\n{c['text']}"))

Keeping the cost down with prompt caching

Without caching, every chunk pays for the whole document again. With the document as a cached prefix (L24), the first call writes the cache at a premium and every later call reads it at a fraction of the input price. Let \(D\) be the document's tokens, \(n\) its chunks, \(u\) the uncached tokens per call (chunk plus instruction) and \(y\) the output tokens. With write multiplier \(w\), read multiplier \(r\) and output-to-input price ratio \(\rho\), in units of one uncached input token:

$$C_{\text{plain}} = n\,(D + u + \rho y), \qquad C_{\text{cached}} = wD + (n-1)\,rD + n\,(u + \rho y).$$ 
def enrichment_cost(doc: int, n: int, chunk: int, prompt: int = 60, out: int = 80,
                    write: float = 1.25, read: float = 0.1, out_ratio: float = 5.0) -> tuple[float, float]:
    """Input-token equivalents for one document, without and with the document cached.
    The multipliers are illustrative: take real ones from the current pricing page."""
    per_call = chunk + prompt + out * out_ratio
    return n * (doc + per_call), doc * write + (n - 1) * doc * read + n * per_call

Running it cheaply
  • Process one document's chunks back to back, within the cache TTL. Send the first call alone so the cache is written, then the rest in parallel; several first calls at once may each pay the write.
  • Documents shorter than the model's minimum cacheable length aren't cached at all; check the limit in the prompt-caching docs. For those, the uncached cost is small anyway.
  • This is a one-off backfill plus incremental updates, so Message Batches (L109) can cut the cost further if you can wait.
  • When one section of a document changes, its context, and every other chunk's context, may change too. Re-enrich the whole document (L48).

Hypothetical questions and summaries

Hypothetical questions: ask the model for three to five questions each chunk answers, and index each question as its own entry pointing to the chunk's id. Users ask questions, so question-to-question similarity often matches better than question-to-passage. This is document expansion in the spirit of doc2query (Nogueira et al. 2019) and the mirror image of HyDE (L43). Summaries as extra entries: embed a short summary per section or document. Broad questions ("what are probes for?") match summaries better than any single chunk; a hit on a summary returns the section's chunks or the whole section. Both are multi-vector indexing, which L53 develops. RAPTOR (Sarthi et al. 2024) takes summaries further, into a tree.

Worked example · what goes into each index

Chunk 2 of the probes page, after enrichment: display text is the YAML block and its note, unchanged. Index text is a model-written context such as "From the liveness-probe exercise; the busybox Pod's exec probe runs cat /tmp/healthy every 5 seconds", then the heading path, then the chunk. Extra entries: "How do I define a liveness command?", "What does periodSeconds do?", each pointing to chunk 2. A hit on any of the three returns chunk 2's display text to the generator.

What breaks in production
  • Hallucinated context. The model may assert a version or feature the chunk doesn't mention. Since context is index-only, the damage is a wrong match, not a wrong answer, but spot-check 30 contexts before indexing millions.
  • Generic context. "This chunk is from the Kubernetes documentation" on every chunk adds nothing. Ask for the specific entity, task and section.
  • Enriching one index only. Contexts added to the vectors but not to BM25 (or the reverse) give up part of the gain the post measured.
  • Leaking context into answers. If the generator is shown index text, model-written context can be cited as if it were documentation. Show display text.

Query Transformation: Rewriting, Multi-Query, HyDE and Decomposition

50m video50m practice

Users describe symptoms in their own words; documentation names things in its own. A query-transformation stage rewrites, multiplies, imagines or splits the question before retrieval so it meets the docs halfway. Each transformation costs a model call and latency and can make easy queries worse, so it should run only where measurement says it helps.

The vocabulary gap

"How do I make my app grow when traffic goes up?" shares no content word with the page that answers it, which talks about a HorizontalPodAutoscaler scaling replicas to match demand. Dense embeddings bridge some of this gap (L28), BM25 none of it, and short, chatty or symptom-first questions are where both fail. L42 attacked the gap from the document side. This lesson attacks it from the query side.

def rrf(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """Reciprocal Rank Fusion (L34): sum 1/(k + rank) over every ranking a document appears in."""
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, 1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda kv: -kv[1])

Rewriting, expansion and multi-query

Rewriting restates the question in the corpus's vocabulary: resource kinds, field names, the docs' terms for symptoms. Expansion appends synonyms and related terms instead of replacing words, which suits BM25. Multi-query generates several paraphrases, searches with each plus the original, and fuses the rankings with RRF. A document that several phrasings retrieve rises; one that only a bad paraphrase retrieves stays low. Keeping the original query in the set is cheap insurance against a rewrite that drifts.

HyDE: search with a hypothetical answer

Definition · HyDE

Hypothetical Document Embeddings (Gao et al. 2022, "Precise Zero-Shot Dense Retrieval without Relevance Labels") asks an instruction-following model to write a passage that answers the question, then searches with that passage's embedding. A passage looks like the documents in the index (same length, register and vocabulary), so it lands nearer the real answer than the short question does. The paper samples several passages and averages their embeddings together with the query's:

$$\hat v_q = \frac{1}{N+1}\Big(\sum_{j=1}^{N} f(\hat d_j) + f(q)\Big)$$

Here \(f\) is the document encoder; the paper used an unsupervised contrastive encoder (Contriever) and needed no relevance labels. The hypothetical passage may contain wrong details; the bet is that the encoder keeps the topic and discards the specifics.

HyDE costs an output-heavy call (a passage, not a few words), so it adds the most latency of the transformations here. The bet fails on identifier queries: a hallucinated flag name or a wrong error code pulls in exactly the wrong chunk. Use it for conceptual and "how do I" questions, not for "what does --dry-run=server do".

Decomposition, step-back and routing

  • Decomposition splits multi-part questions ("expose my Deployment on port 80 and autoscale it on CPU") into sub-questions, retrieves for each, and merges, ideally with a per-sub-question quota so one part can't crowd out the other.
  • Step-back prompting (Zheng et al. 2023, "Take a Step Back: Evoking Reasoning via Abstraction in Large Language Models") first asks the more general question behind a specific one, then reasons with both. For retrieval, "Why does my Pod restart every five minutes?" steps back to "How does the kubelet restart failed containers, and what is the back-off?", which retrieves the background chunk the specific question misses.
  • Routing sends the query to the right index (docs, past tickets, release notes), sets filters such as version (L33), or skips retrieval for small talk. Routing errors are silent, so measure routing accuracy on a labelled set of its own.

One small-model call can produce all of these at once with a structured output (L20). Downstream code then decides which to use.

Retrieval Tuning: k, Thresholds, MMR and Diversity

40m video45m practice

Retrieval hands you a ranked list; tuning decides how much of it reaches the prompt and what that space is spent on. Pick k and the context budget from a measured curve, prefer rank cut-offs to raw-score thresholds, and fill the slots with distinct evidence: drop duplicates, diversify with MMR, merge neighbouring chunks.

Choosing k

There are two k's. kretrieve is how many candidates the first stage hands the reranker (typically tens, L35). kcontext is how many passages go into the prompt. Raising kcontext buys recall: the chance that the passage you need is present. It also costs input tokens, latency, and attention. Models use a long context unevenly, and irrelevant passages can pull an answer off course (L13).

Recall@k rises quickly and then flattens. Precision@k falls. Tune kcontext on the eval set: take the smallest k whose recall is within a point or two of the plateau, then check that answer quality agrees (generation metrics arrive in L51). The right k depends on chunk size (L41): 3 large chunks and 10 small ones can hold the same evidence.

Thresholds, and why raw scores make poor ones

A cut-off like "keep hits with cosine ≥ 0.80" looks natural and rarely works. Cosine scores are not calibrated probabilities (L28). Their range depends on the embedding model, the query length and the corpus. One model puts every passage between 0.70 and 0.90; another spreads unrelated text across 0.1–0.4. The same 0.80 can be the best hit for a vague question and a weak hit for a precise one. BM25 scores aren't bounded at all, and fused RRF scores (L34) only encode rank.

Better cut-offs
  • Rank cut-off after reranking: a fixed kcontext. Simple and predictable for token cost.
  • Relative threshold: keep hits whose score is within δ of the top hit's score. This adapts to each query's score scale.
  • Reranker threshold, calibrated: cross-encoder scores compare better across queries than bi-encoder cosines. Fit the cut-off on labelled pairs from your eval set, and refit it whenever the model changes.
  • Use an absolute threshold mainly to detect "nothing relevant came back", which triggers the refusal path in L45, not to trim the list.

Maximal marginal relevance

Top-k by similarity often returns the same fact several times: the same page from two doc versions, a mirrored blog post, overlapping chunks. Each copy uses a slot that a different aspect of the answer could have used. MMR (Carbonell & Goldstein, 1998) picks greedily, trading relevance against redundancy with what is already selected:

$$d^{*} = \argmax_{d_i \in R \setminus S} \Big[\, \lambda\, \mathrm{sim}(d_i, q) \;-\; (1-\lambda) \max_{d_j \in S} \mathrm{sim}(d_i, d_j) \Big]$$
Algorithm · MMR selection
  1. \(R\) = the candidate list (after reranking), \(S = \varnothing\).
  2. Add the candidate with the best score to \(S\). While \(S\) is empty the redundancy term is zero, so the first pick is the most relevant hit.
  3. Repeat until \(|S| = k\). \(\lambda = 1\) is plain top-k; \(\lambda = 0\) ignores the query after the first pick.

Cost is \(O(kn)\) similarity look-ups for \(n\) candidates. Run it on the top 20–50 candidates, never the whole index. Relevance can be reranker scores rescaled to [0, 1]; redundancy needs chunk embeddings, so keep vectors for BM25-only hits too.

import numpy as np

def mmr(q, docs, k=3, lam=0.7):
    """Greedy MMR. q: (d,) and docs: (n, d), both unit-normalised. Returns row indices."""
    rel = docs @ q                                   # sim(q, d_i)
    sim = docs @ docs.T                              # sim(d_i, d_j)
    chosen, pool = [], list(range(len(docs)))
    while pool and len(chosen) < k:
        red = sim[np.ix_(pool, chosen)].max(axis=1) if chosen else np.zeros(len(pool))
        best = pool[int(np.argmax(lam * rel[pool] - (1 - lam) * red))]
        chosen.append(best)
        pool.remove(best)
    return chosen

def dedup(order, docs, threshold=0.98):
    """Walk hits best-first; drop any whose cosine to a kept hit is >= threshold."""
    kept = []
    for i in order:
        if all(docs[i] @ docs[j] < threshold for j in kept):
            kept.append(i)
    return kept

Near-duplicates and adjacent chunks

Duplicates come from mirrored pages, translated or versioned copies, boilerplate (navigation, licence footers) and the overlap between fixed-size chunks (L41). Remove exact copies at ingestion by hashing normalised text. Near-copies need a similarity test: cosine above a high threshold on embeddings, or Jaccard similarity of word shingles estimated with MinHash (Broder, 1997). MinHash catches copy-paste with small edits at corpus scale, without any embeddings. Choose the threshold by reading pairs just above and below it, not by guessing.

Adjacent chunks are the opposite case. Hits for positions 7 and 8 of the same page are not redundant: they are one passage that chunking split in two. Merge them into one block with one heading and one citation. That restores a sentence or code block cut at the boundary, and drops the overlapping text. Sort by (document, position), merge consecutive runs, and keep the best score of each run. L53 takes the idea further, retrieving small chunks and returning their parents.

Recency boosts and the context budget

For time-sensitive sources such as tickets, release notes and incident reports, blend relevance with an age decay of half-life \(h\). Use relevance that is already normalised, because raw scores are not on a fixed scale:

$$s'_i = (1-\beta)\,\hat s_i + \beta \cdot 2^{-a_i / h}, \qquad \hat s_i \in [0, 1],\ a_i = \text{age in days}$$

Alternatively, add a "newest first" list as one more input to RRF. For versioned documentation, a version filter (L33) is better than a boost: the newest page is not the right one for a user on an older release.

The context budget \(B\) is the number of tokens you allow for retrieved text. Start from the window, subtract the system prompt, the history and room for the answer, and then set \(B\) far lower, from measurements. Pack passages best-first while \(\sum_{i \in S} t_i \le B\), and skip any passage that doesn't fit rather than truncating it mid-sentence.

Worked example

DocPilot's chunks average about 350 tokens. With \(B = 3{,}000\), at most 8 full chunks fit. If MMR picks 6 and two of them are positions 7 and 8 of the same page, merging gives 5 passages. The 60-token overlap counted twice is gone, so the packed context is about \(6 \times 350 - 60 = 2{,}040\) tokens. You get the same evidence and 5 citations instead of 6, with room left for one more passage if the sweep says it helps.

What breaks in production
  • Thresholds outlive their model. A cosine cut-off tuned on one embedding model is meaningless after a model swap (L48). Store thresholds next to the embedding version and re-tune them together.
  • Dedup erases real differences. "Beta in v1.29" and "GA in v1.31" can be 0.99 similar. Those are different facts. Dedup within one version or source, never across versions.
  • Dedup before permissions. If the copy you keep is one the user cannot see, the visible copy has already been dropped. Filter by access first (L47), then dedup.
  • MMR with a thin pool. When few candidates are relevant, MMR fills the slots with off-topic text, as the λ = 0.5 run shows. Apply a relative threshold before MMR.
  • Unbounded merging. Merging a run of ten adjacent chunks can use the whole budget on one page. Cap the size of a merged block.

Prompting the Generator: Grounded Answers, Refusals and Citations

50m video50m practice

Good retrieval only helps if the generator uses it. Lay the prompt out so the model can find and cite its sources, make "the documentation doesn't cover this" an explicit, well-formed answer, and never trust a citation you haven't checked by code.

Answer-only-from-context, and its limits

The core instruction is short: use only the sources, cite them, and say so when they don't answer. It lowers the rate of unsupported claims but does not stop them. Pretrained knowledge still leaks in, most often when the context is partial, when the docs contradict what the model learned (renamed flags, deprecated APIs), or when the question invites general advice. The instruction is a request. Enforcement comes from checking the output (below, and in L51). Retrieved text is also untrusted input: a page that says "ignore your instructions" is an indirect prompt injection (L97).

Layout: sources first, question last, quotes before answers

  • Placement. Anthropic's long-context guidance puts long documents at the top and the question at the end, and reports better answers that way. Rules go in the system prompt.
  • Structure. Wrap each source in a tag with an id, title and URL, so the answer can cite [S2] and code can map the id back to a chunk.
  • Order. Strongest hits first. Models use the start and end of a long context more reliably than the middle (Liu et al., 2024), so a smaller k beats burying the best passage at position 9 (L44).
  • Quotes first. Asking for supporting quotes before the answer commits the model to evidence and gives you spans you can verify exactly. It costs output tokens. Strip the quotes before display, or show them as expandable evidence.

Checking citations programmatically

For each sentence, read its [S#] markers and ask: does the cited chunk support it? The cheapest local test is lexical support, the share of the sentence's content words found in the cited chunk, against a threshold. An embedding cosine is the other cheap option. Neither needs a model.

import re

STOP = set("a an and are as at be by can for from how if in is it its of on or that the this "
           "to was when with you your".split())
SENT = re.compile(r"(?<=[.!?])\s+")
CITE = re.compile(r"\[(S\d+)\]")

def words(text: str) -> set[str]:
    return {w for w in re.findall(r"[a-z0-9]+(?:[._/-][a-z0-9]+)*", text.lower()) if w not in STOP}

def check_citations(answer: str, sources: dict[str, str], threshold: float = 0.6):
    """Per sentence: (status, cited id, support). Support = share of the sentence's
    content words found in the cited source; the best of several cited sources counts."""
    rows = []
    for sent in SENT.split(answer.strip()):
        ids, claim = CITE.findall(sent), words(CITE.sub("", sent))
        if not ids:
            rows.append(("uncited", None, 0.0, sent)); continue
        sid, sup = max(((i, len(claim & words(sources.get(i, ""))) / max(len(claim), 1))
                        for i in ids), key=lambda t: t[1])
        status = "bad id" if sid not in sources else "ok" if sup >= threshold else "unsupported"
        rows.append((status, sid, round(sup, 2), sent))
    return rows

Saying "the documentation doesn't cover this" well

A refusal is an answer, and it has three cases. (1) Nothing relevant retrieved: the top reranker score is under the calibrated floor (L44), so skip the model and return a fixed message. Conversational RAG: Follow-Ups, History and Query Condensation

40m video45m practice

In a conversation, the retriever and the generator need different things. The retriever needs one standalone query, so rewrite every follow-up into one before searching. The generator needs a short slice of recent history plus fresh sources. Then measure whether follow-ups retrieve as well as first questions.

Follow-ups that don't stand alone

"And on Windows nodes?", "Does that work for StatefulSets?" and "Why?" mean something only with the previous turns. Embedded alone, "and on Windows nodes?" retrieves generic Windows pages. A pipeline that scores well on single questions can fail on every follow-up, and a single-turn eval never shows it.

Worked example

Turn 1: "How do I set CPU limits on a pod?" retrieves Resource Management for Pods and Containers.
Turn 2: "and on Windows nodes?"

  • Raw follow-up: Windows overview pages, no resource management.
  • Previous question + follow-up: better, but now two topics weighted equally.
  • Condensed "set CPU limits for pods on Windows nodes": Resource Management for Windows nodes, the page that answers it.

Query condensation

A small, fast model rewrites the latest message into one standalone query before retrieval. This is query rewriting (L43) with the conversation as extra input.

Algorithm · One conversational turn
  1. First turn: the message is the query. Skip the model call.
  2. Otherwise condense the recent turns and the new message into JSON {query, retrieve}, using a schema in output_config (L20). Resolve pronouns and ellipsis, copy identifiers exactly, and drop the old topic when the user switches.
  3. If retrieve is true, or there are no previous hits, search with the query and the profile's filters. Otherwise reuse the last hits.
  4. Generate from the last two exchanges plus this turn's sources. Store the answer with its citation markers stripped.
import json
from dataclasses import dataclass, field

from docpilot.llm import SMALL, chat, text_of
from docpilot.search import Hit

CONDENSE = """Rewrite the user's latest message as one standalone search query for the Kubernetes docs.
Resolve pronouns and ellipsis ("it", "that one", "and on Windows?") from the conversation.
Copy product names, versions, flags and error messages exactly.
If the latest message starts a new topic, ignore the earlier turns.
Set retrieve to false only when the message asks to rephrase or expand the previous answer."""
SCHEMA = {"type": "object", "additionalProperties": False, "required": ["query", "retrieve"],
          "properties": {"query": {"type": "string"}, "retrieve": {"type": "boolean"}}}

@dataclass
class Conversation:
    turns: list[dict] = field(default_factory=list)   # user/assistant pairs, citations stripped
    profile: dict = field(default_factory=dict)       # remembered facts, e.g. {"version": "1.31"}
    last_hits: list[Hit] = field(default_factory=list)

def condense(conv: Conversation, message: str, *, llm=chat, keep: int = 6) -> tuple[str, bool]:
    if not conv.turns:                                # first turn: nothing to resolve, no model call
        return message, True
    history = "\n".join(f"{t['role']}: {t['content'][:600]}" for t in conv.turns[-keep:])
    prompt = f"<conversation>\n{history}\n</conversation>\n<latest>{message}</latest>"
    fmt = {"format": {"type": "json_schema", "schema": SCHEMA}}
    try:
        out = json.loads(text_of(llm([{"role": "user", "content": prompt}], system=CONDENSE,
                                     model=SMALL, max_tokens=200, output_config=fmt)))
        return out["query"].strip() or message, bool(out["retrieve"])
    except (json.JSONDecodeError, KeyError, TypeError, AttributeError):
        last_user = next(t["content"] for t in reversed(conv.turns) if t["role"] == "user")
        return f"{last_user} {message}", True         # crude, but retrieval still sees the topic

A refusal, a max_tokens stop or a condenser outage should give a worse query, not a failed turn. Condensing also adds a small-model round trip before retrieval can start, so put it on the latency waterfall (L59).

Once the history outgrows its budget, replace the oldest turns with a running summary (L75). Prompt caching (L24) still pays off for the stable prefix, because each turn only appends.

Retrieve every turn, or reuse?

Retrieving on every turn is the safe default. Reuse saves a search only when the user asks about the answer itself: "shorter", "explain step 2", "as YAML". "And on Windows?" looks like a small change but needs a different page. Let the condenser decide, and retrieve when unsure. A middle path is to retrieve fresh and keep the previous turn's top one or two hits in the reranker's pool.

from docpilot.grounded import CITE, SYSTEM, build_prompt     # L45
from docpilot.search import search

def ask(conv: Conversation, message: str, *, llm=chat, retrieve=search) -> str:
    query, fresh = condense(conv, message, llm=llm)
    if fresh or not conv.last_hits:
        filters = {"version": conv.profile["version"]} if "version" in conv.profile else None
        conv.last_hits = retrieve(query, k=5, filters=filters)
    recent = conv.turns[-4:]                          # last two exchanges verbatim; older ones summarised (L75)
    msg = llm([*recent, {"role": "user", "content": build_prompt(query, conv.last_hits)}], system=SYSTEM)
    reply = text_of(msg)
    conv.turns += [{"role": "user", "content": message},
                   {"role": "assistant", "content": CITE.sub("", reply)}]
    return reply

Remembering user context

Some facts outlive a turn: the Kubernetes version, the node OS, the cloud provider, the user's role. Keep them in an explicit profile. Fill it when the user states a fact, or ask once when it matters. Use it for retrieval filters (L33) and as one line in the prompt. Keep it session-scoped. Cross-session memory needs consent, a way to see and clear it, and its own design (L76). Don't infer sensitive attributes.

Access Control, Permissions and PII in RAG

45m video40m practice

Anything that reaches the prompt can reach the answer. Permissions must therefore be enforced where chunks are selected, in the retrieval layer, for the authenticated user, and failing closed. The same holds for everything derived from those chunks: summaries, caches, logs and deletions.

Enforce permissions in retrieval, not in the prompt

"Don't reveal documents the user can't see" is not a control. The model doesn't know who is asking, and a restricted chunk in its context can be quoted or summarised by the next follow-up. The control is structural. Each chunk carries its source document's access list, copied at ingestion. search requires a Principal built from the authenticated session. The filter runs before ranking. An unlabelled chunk is visible to nobody.

Definition · Early and late binding

Early binding copies ACLs into the index and filters on them: fast, but only as fresh as the last ACL sync. Late binding asks the source system (wiki, ticket tool, Git host) about each returned document: always current, but one more call per request, and it fails when the source is down. Many systems filter early and late-check only the few sensitive documents that reach the prompt.

import logging
import re
from dataclasses import dataclass

from docpilot.search import Hit

log = logging.getLogger("docpilot.acl")

@dataclass(frozen=True)
class Principal:                    # built from the authenticated session, never from the request body
    user: str
    tenant: str
    groups: frozenset[str]

def allowed(p: Principal, meta: dict) -> bool:
    """Fail closed: a chunk with no ACL is visible to nobody."""
    acl = meta.get("acl")
    if not acl or acl.get("tenant") != p.tenant:
        return False
    allow = set(acl.get("allow", ()))
    return "*" in allow or p.user in allow or bool(allow & p.groups)

class SecureIndex:
    def __init__(self, chunks: list[Hit]):
        self.chunks = chunks

    def search(self, query: str, *, principal: Principal, k: int = 5) -> list[Hit]:
        terms = set(re.findall(r"\w+", query.lower()))
        pool = [c for c in self.chunks if allowed(principal, c.meta)]     # pre-filter, before ranking
        scored = [(len(terms & set(re.findall(r"\w+", c.text.lower()))), c) for c in pool]
        hits = [c for s, c in sorted(scored, key=lambda t: -t[0]) if s > 0][:k]
        leaked = [h.id for h in hits if not allowed(principal, h.meta)]  # defence in depth
        if leaked:
            log.error("ACL post-check dropped %s for %s", leaked, principal.user)
        return [h for h in hits if h.id not in leaked]

Toy term-overlap ranking so the tests run anywhere. In DocPilot the pre-filter becomes a metadata filter on both the BM25 and vector queries (L33); the post-check stays.

Summaries that cross permission boundaries

Enrichment creates new text from old: chunk contexts and summaries (L42), parents (L53), graph summaries (L54), memories, cached answers. A summary of a public page and an SRE runbook, labelled public, leaks the runbook to everyone. Each derived artefact records its source ids and admits only principals who could read every source. Cross-tenant derivation is refused.

def derive_acl(metas: list[dict]) -> dict:
    """ACL for a summary built from several chunks: only who could read every source."""
    tenants = {m["acl"]["tenant"] for m in metas}
    if len(tenants) != 1:
        raise ValueError("refusing to derive an artefact across tenants")
    allows = [set(m["acl"]["allow"]) for m in metas]
    specific = [a for a in allows if "*" not in a]
    allow = set.intersection(*specific) if specific else {"*"}
    return {"tenant": tenants.pop(), "allow": sorted(allow)}

Intersection is conservative: sources labelled {sre} and {dev} give an empty label even though some users are in both groups. That is the right direction to fail. Answers are derived artefacts too, so an answer cache must be keyed by the permission set as well as the query (L111).

PII: redact at ingestion or at answer time

Ingestion-time redaction keeps PII out of the index, embeddings, prompts and logs. It is the data-minimisation default, but it hides values from users entitled to see them. Answer-time redaction masks output per user, but PII then reaches the model provider and your traces. A common design redacts at ingestion with stable placeholders, and keeps the value map in the source system behind its own ACL.

import re

PATTERNS = {                                     # most specific first
    "EMAIL": re.compile(r"\b[\w.+-]+@[\w-]+(?:\.[\w-]+)+\b"),
    "IPV4": re.compile(r"\b(?:(?:25[0-5]|2[0-4]\d|1?\d?\d)\.){3}(?:25[0-5]|2[0-4]\d|1?\d?\d)\b"),
    "PHONE": re.compile(r"(?<![\w.])\+?\d{1,3}[ -]?\(?\d{2,4}\)?[ -]?\d{3,4}[ -]?\d{3,4}\b"),
}

def redact(text: str) -> tuple[str, dict[str, str]]:
    """Replace matches with stable typed placeholders; return the text and the value map."""
    mapping: dict[str, str] = {}
    for kind, rx in PATTERNS.items():
        def repl(m, kind=kind):
            n = sum(v.startswith(f"[{kind}_") for v in mapping.values())
            return mapping.setdefault(m.group(0), f"[{kind}_{n + 1}]")
        text = rx.sub(repl, text)
    return text, mapping

What breaks in production
  • Stale ACLs. Access is revoked in the wiki and the index syncs nightly. Push ACL changes as events, or late-bind sensitive documents.
  • Principal from the client. A tenant in the JSON body, or a tool argument an agent fills in (L62), lets callers choose their own permissions. Inject it server-side.
  • Cache keys without permissions. A semantic cache serves Bob's runbook answer to Alice.
  • Vectors treated as harmless. Embeddings can be partly inverted to text (Morris et al., 2023). Give vectors the same ACLs and deletion rules.
  • PII in traces. The index is redacted, but the traces log full prompts.

Keeping the Index Fresh: Updates, Deletes and Re-Embedding

45m video45m practice

An index is a cache of your documents, and every cache goes stale. Make ingestion incremental and idempotent: key chunks by content hash, so an edit re-embeds only what changed and a rerun does nothing. Treat a change of embedding model as a new index, built beside the old one and swapped in only after it passes the eval.

Detecting changes

There are three signals, from cheapest to most reliable. Webhooks and change feeds (a push to the docs repository, a wiki edit event) tell you what changed as it happens, but events get lost. Timestamps, ETag or Last-Modified headers on a conditional fetch, are cheap to check but lie: a git checkout resets mtimes, and a re-save changes the date without changing the content. Content hashes are the truth, and the only signal that also catches changes in your own pipeline. Use events and timestamps to decide what to fetch, and hashes to decide what to re-embed.

Definition · Content-addressed chunk key $$\text{key}(c) = H\big(v \,\|\, d \,\|\, \text{input}(c)\big)$$

Here \(H\) is a hash such as SHA-256, \(v\) is the pipeline version (embedding model plus chunker and enrichment versions), \(d\) is the document id, and \(\text{input}(c)\) is exactly the text that gets embedded, including any prepended heading path or context (L42). Equal keys mean equal vectors, so a key that already exists never needs re-embedding. Position-based ids such as jobs#2 do not have this property: inserting one paragraph at the top shifts every later id.

Incremental upserts, deletes and tombstones

Algorithm · Incremental sync
  1. Diff the source listing against the manifest. If an implausible share of documents vanished, stop: that is a broken crawl, not a mass deletion.
  2. Skip documents whose whole-document hash is unchanged.
  3. For a changed document, chunk it and key each chunk. Embed and upsert only the new keys, then delete the keys that disappeared. Upserting first means search never sees the document missing.
  4. For a deleted document, delete its chunks and write a tombstone (id plus time), so caches, replicas and the BM25 index learn about the deletion instead of inferring it from an absence.
import hashlib
import time
from dataclasses import dataclass, field

EMBED_VERSION = "embed-v1+chunker-v3"     # bump either part and every key changes

def sha(*parts: str) -> str:
    return hashlib.sha256("\x1f".join(parts).encode()).hexdigest()[:16]

def chunks_of(text: str) -> list[str]:     # stand-in for the L41 chunker
    return [p.strip() for p in text.split("\n\n") if p.strip()]

@dataclass
class Manifest:
    docs: dict[str, str] = field(default_factory=dict)          # doc_id -> hash of the whole doc
    chunks: dict[str, set[str]] = field(default_factory=dict)   # doc_id -> chunk keys in the index
    tombstones: dict[str, float] = field(default_factory=dict)  # doc_id -> deletion time

def sync(source: dict[str, str], m: Manifest, index, embed, *, max_delete_frac: float = 0.2) -> dict:
    gone = set(m.docs) - set(source)
    if m.docs and len(gone) > max_delete_frac * len(m.docs):
        raise RuntimeError(f"{len(gone)} of {len(m.docs)} docs vanished; partial crawl? not deleting")
    stats = {"unchanged_docs": 0, "embedded": 0, "deleted": 0, "tombstoned": len(gone)}
    for doc_id, text in source.items():
        doc_hash = sha(EMBED_VERSION, text)
        if m.docs.get(doc_id) == doc_hash:
            stats["unchanged_docs"] += 1
            continue
        new = {sha(EMBED_VERSION, doc_id, c): c for c in chunks_of(text)}   # content-addressed keys
        old = m.chunks.get(doc_id, set())
        add, drop = [k for k in new if k not in old], sorted(old - new.keys())
        if add:                                                   # upsert first, then delete
            vecs = embed([new[k] for k in add])
            index.upsert([(k, v, {"doc_id": doc_id, "embed_version": EMBED_VERSION}) for k, v in zip(add, vecs)])
        index.delete(drop)
        stats["embedded"] += len(add); stats["deleted"] += len(drop)
        m.docs[doc_id], m.chunks[doc_id] = doc_hash, set(new)
    for doc_id in gone:
        drop = sorted(m.chunks.pop(doc_id))
        index.delete(drop)
        stats["deleted"] += len(drop)
        del m.docs[doc_id]
        m.tombstones[doc_id] = time.time()                        # caches and replicas read these
    return stats

Re-embedding after a model change: blue/green

Vectors from two embedding models live in different spaces and cannot share an index (L29). A model upgrade, a new chunker or a Matryoshka truncation therefore means building a new index. Re-embedding cost is roughly the corpus's total tokens times the embedding price, plus the time to push every chunk through the rate limit, so estimate both before you start.

The steps: create green with the new EMBED_VERSION; backfill it from the parsed corpus; dual-write incremental changes to both indexes until the backfill catches up; run the retrieval eval against green; flip the alias in one operation (Elasticsearch, OpenSearch and Qdrant all support aliases; with pgvector, swap a view or a table name inside a transaction); keep blue until you are sure; then delete it. Thresholds and MMR settings tuned on blue need re-tuning on green (L44).

Stale answers from caches

A fresh index doesn't help while a response cache keeps serving last week's answer. There are three remedies, which combine. Lineage invalidation: store the cited chunk keys with each cached answer, and evict every answer whose keys were deleted or replaced. The sync's drop lists and tombstones are exactly the events you need. Epoch keys: put the index version in the cache key, so a swap flushes everything. It is simple, and heavy-handed. TTLs are the backstop when an event is missed. Semantic caches get the full treatment in L111.

For DocPilot: event-driven sync on pushes to the docs repository (re-ingest the changed files), a nightly conditional crawl for anything without events, and a weekly full reconciliation that re-hashes everything to catch missed events and pipeline bugs. Run ingestion as a queue worker with retries (L112), never inside the request path. Track index health on a dashboard and alert on it:

  • Counts: documents in the source, the manifest and the index. Chunks per document, with a sudden drop flagged.
  • Orphaned chunks (in the index, not in the manifest) and missing chunks (the reverse). Both should be zero.
  • Embedding versions present: exactly one per index. Two means a half-finished migration or a writer on the old config.
  • Freshness lag: the time from a source change to its being searchable, and the age of the last successful sync.
def health(m: Manifest, index) -> dict:
    expected, stored = set().union(*m.chunks.values()), set(index.rows)
    return {"docs": len(m.docs), "chunks": len(stored), "orphaned": len(stored - expected),
            "missing": len(expected - stored),
            "embed_versions": sorted({meta["embed_version"] for meta in index.rows.values()})}
What breaks in production
  • A partial crawl deletes half the index. A timeout returns 40% of the pages, and sync dutifully deletes the rest. The vanish guard exists for this. Alert when it trips; don't raise the limit.
  • A hash that misses an input. Prompt changes in contextual enrichment, or a new chunker, alter the embedded text but not the key. Every input to the embedded string belongs in \(v\).
  • Deletes that only reach the vector store. BM25, the enrichment store, caches and the eval set still hold the page. Fan tombstones out to every consumer (L47).
  • Re-embedding in place. For hours the index mixes two models, and search quality collapses without an error.

The answer pipeline

One function owns the order of operations, with llm and retrieve injected so tests can replace them. It returns everything the report needs.

import re
import time

from docpilot.acl import Principal
from docpilot.conversation import Conversation, condense
from docpilot.grounded import CITE, SYSTEM, build_prompt, check_citations
from docpilot.llm import MODEL, text_of

NO_ANSWER = "The documentation I have doesn't cover this."

def est_cost(u, prices: dict) -> float:
    return (u.input_tokens * prices["input"] + (u.cache_creation_input_tokens or 0) * prices["cache_write"]
            + (u.cache_read_input_tokens or 0) * prices["cache_read"] + u.output_tokens * prices["output"]) / 1e6

def answer(question: str, conv: Conversation, p: Principal, *, llm, retrieve, prices: dict) -> dict:
    t0 = time.perf_counter()
    query, fresh = condense(conv, question, llm=llm)                        # L46
    hits = retrieve(query, principal=p, k=5) if fresh or not conv.last_hits else conv.last_hits  # L47
    conv.last_hits, t1 = hits, time.perf_counter()
    if not hits:                                                            # L45: refuse, no model call
        return {"answer": NO_ANSWER, "citations": [], "unsupported": [], "cost": 0.0,
                "latency_ms": {"retrieve": round((t1 - t0) * 1000), "generate": 0}}
    msg = llm([*conv.turns[-4:], {"role": "user", "content": build_prompt(query, hits)}],
              system=SYSTEM, model=MODEL)
    t2, raw = time.perf_counter(), text_of(msg)
    m = re.search(r"<answer>(.*?)</answer>", raw, re.S)
    text = (m.group(1) if m else raw).strip()
    src = {f"S{i}": h for i, h in enumerate(hits, 1)}
    rows = check_citations(text, {sid: h.text for sid, h in src.items()})   # L45
    used = sorted({s for s in CITE.findall(text) if s in src}, key=lambda s: int(s[1:]))
    conv.turns += [{"role": "user", "content": question}, {"role": "assistant", "content": CITE.sub("", text)}]
    u = msg.usage
    return {"answer": text,
            "citations": [{"id": s, "title": src[s].heading_path, "url": src[s].url} for s in used],
            "unsupported": [r[3] for r in rows if r[0] != "ok"],
            "usage": {"input_tokens": u.input_tokens, "output_tokens": u.output_tokens},
            "cost": est_cost(u, prices),
            "latency_ms": {"retrieve": round((t1 - t0) * 1000), "generate": round((t2 - t1) * 1000)}}
Definition · Per-answer cost $$\text{cost} = \frac{t_{\text{in}}\,p_{\text{in}} + t_{\text{cw}}\,p_{\text{cw}} + t_{\text{cr}}\,p_{\text{cr}} + t_{\text{out}}\,p_{\text{out}}}{10^{6}}$$

The \(t\) come from usage; with prompt caching (L24), input_tokens excludes cache writes (cw) and reads (cr). Each \(p\) is a per-million-token price from config, taken from the current price page. Sum every call in the request: chat() (L2) logs the condenser call under the same request id.

The /ask API and a minimal web UI

from fastapi import Depends, FastAPI, Header, HTTPException
from fastapi.responses import HTMLResponse
from pydantic import BaseModel

from docpilot.acl import Principal
from docpilot.answer import answer
from docpilot.conversation import Conversation

class AskIn(BaseModel):
    question: str
    conversation_id: str = ""

def create_app(*, llm, retrieve, tokens: dict[str, Principal], prices: dict) -> FastAPI:
    app, conversations = FastAPI(title="DocPilot"), {}

    def principal(authorization: str = Header(default="")) -> Principal:
        p = tokens.get(authorization.removeprefix("Bearer "))     # stand-in for real session checks
        if p is None:
            raise HTTPException(status_code=401, detail="unauthenticated")
        return p

    @app.post("/ask")
    def ask(body: AskIn, p: Principal = Depends(principal)) -> dict:
        conv = conversations.setdefault((p.user, body.conversation_id), Conversation())  # per user
        return answer(body.question, conv, p, llm=llm, retrieve=retrieve, prices=prices)

    @app.get("/", response_class=HTMLResponse)
    def ui() -> str:
        return PAGE

    return app

The principal comes from the Authorization header, never the body (the token table stands in for real session checks). Conversations are keyed by (user, conversation_id), so a guessed id yields an empty conversation. Dependencies are arguments: production passes the real chat and search, tests pass fakes.
