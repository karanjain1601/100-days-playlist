Phase 7 · Days 50–61 · Lessons 70–85

Agents

Phase 7 turns DocPilot's tool loop into agents that plan, remember, survive crashes and ask before they act. It starts from the split between workflows and agents, builds the loop by hand, then adds state, memory, planning, human approval, multiple agents, frameworks, coding agents and reliability guards. It ends with a research agent run on 20 escalations. Phase 6 supplied the tools and MCP; Phase 8 supplies the evaluations that show whether these agents actually work.

By the end of this phase you can

  • Decide with a written rule whether a feature should be a workflow or an agent, and estimate what each step of an agent run costs in tokens.
  • Build a framework-free agent on run_tools() with a final-answer tool, budgets and a full step trace, and test it end to end against a scripted fake client.
  • Implement plan-and-execute, Reflexion-style retries, orchestrator–workers and evaluator–optimiser, and compare them on success rate and cost per task.
  • Make an agent crash-safe with checkpoints and idempotency keys, and keep long runs inside a token budget with compaction that never drops the user's constraints.
  • Give an agent a long-term memory the user can view and delete, and a progress file with a check at every milestone.
  • Put every side effect behind an auditable approval, measure when several agents beat one, and port the agent to a framework with numbers to compare.
  • Harden an agent with step, token and time budgets and repeat detection, and report its reliability across repeated runs.

L70 · DAY 50

What an Agent Is: Workflows vs Agents

45m video30m practice

An agent is a model that uses tools in a loop and chooses its own next step until it decides it is finished. A workflow is a program you wrote that calls a model at fixed points. The question that separates them is who owns the control flow, and most features should leave it with you.

The augmented LLM

Anthropic's essay "Building effective agents" (Schluntz and Zhang, December 2024) starts from one building block, which it calls the augmented LLM: a model given retrieval, tools and memory, and able to decide when to use each. DocPilot already has two of the three. Retrieval is search() from L37, and tools are the run_tools() loop from L62. Memory arrives in L75 and L76. Everything in this phase arranges augmented LLM calls, either in a fixed shape or in a loop the model steers.

Definition · workflow and agent
  • Workflow: models and tools are orchestrated through code paths you wrote in advance. The model fills in steps but does not choose them.
  • Agent: the model directs its own process. It chooses which tool to call next, reads the result, and decides whether to continue or stop. The number of steps is decided at run time.
  • Agentic system: the essay's umbrella term for both.

These definitions paraphrase the essay. The working test is simple: if you can draw the path before the request arrives, it is a workflow.

The essay names five workflow patterns before it reaches agents. Three were built in L25; the other two are L73. They are the toolbox you reach for first.

When an agent is worth its cost

The essay's advice is to find the simplest solution that works and add agentic complexity only when simpler designs measurably fall short. Agents trade latency, cost and predictability for performance on open-ended tasks. The cost side is easy to underestimate, because every step resends the whole transcript.

Derivation · input tokens over an agent run

Let \(P\) be the fixed prefix (system prompt, tool definitions, task) and let each step append \(\Delta\) tokens (a tool call and its result). Step \(k\) sends \(P + (k-1)\Delta\) tokens, so a run of \(n\) steps sends

$$T_{\text{in}}(n) = \sum_{k=1}^{n} \big(P + (k-1)\Delta\big) = nP + \Delta\,\frac{n(n-1)}{2}.$$

The second term is quadratic in \(n\). With \(P = 4000\), \(\Delta = 1500\) and \(n = 8\): \(32{,}000 + 42{,}000 = 74{,}000\) input tokens. A two-call workflow over the same prefix sends about \(8{,}000\). Prompt caching (L24) bills the repeated prefix at the cheaper cache-read rate, but the \(n\) round trips still run one after another, so latency grows with \(n\) either way.

An agent earns that cost when four things hold together. The number of steps genuinely depends on what is found. A wrong step can be caught, because citations, tests or a human check the result. Mistakes are cheap to undo, or the risky actions sit behind approvals. And a better answer is worth several times the tokens. The rule below encodes those questions, and it is the deliverable for today.

from dataclasses import dataclass

@dataclass
class Feature:
    name: str
    path_fixed: bool      # can you write the steps down before the request arrives?
    verifiable: bool      # can citations, tests or a person check the result?
    reversible: bool      # are its mistakes cheap to undo?
    high_value: bool      # is a better answer worth 5-10x the tokens?

def agent_or_workflow(f: Feature) -> str:
    if f.path_fixed:
        return "workflow"
    if not f.verifiable:
        return "workflow + human review"      # an agent you cannot check is a liability
    if not f.high_value:
        return "workflow (agent not worth it)"
    return "agent" if f.reversible else "agent + approval gates"

features = [
    Feature("ticket triage",         True,  True,  True,  False),
    Feature("cited doc answer",      True,  True,  True,  True),
    Feature("troubleshoot a pod",    False, True,  True,  True),
    Feature("nightly index refresh", True,  True,  True,  False),
    Feature("escalation + file fix", False, True,  False, True),
]
for f in features:
    print(f"{f.name:<22} {agent_or_workflow(f)}")

Where agents are deployed today

As of late 2026 the deployments that work share one property: the agent's output can be checked.

  • Coding. Agents read a repository, edit files and run the tests, and the tests are an automatic check. This is the most mature category (L83).
  • Research. "Deep research" agents search, read and search again, then write a cited report. The citations are what make the output checkable (L55, L79).
  • Customer support. A conversation plus tools for looking up accounts, orders and documentation, inside a written policy, with escalation to a person. The essay highlights support and coding as two especially promising uses.
  • Operations. Incident triage that queries logs and metrics, follows a runbook and proposes a fix for a human to approve.
Three principles from the essay

Keep the design simple. Make the agent's planning visible, so a person can see why it did what it did. Treat the tools as an agent–computer interface and invest in their documentation and testing as much as in the prompt (L63).

What breaks in production
  • An agent where a router would do. A ticket classifier rebuilt as an agent becomes slower, costlier and nondeterministic, and gets no more accurate. Check rung 2 before you climb to rung 3.
  • No stopping rule. Without a step cap, a budget and a clear finish condition, an agent that cannot find the answer keeps searching. L71 builds all three in, and L84 adds the remaining guards.
  • Write access by default. The step from rung 3 to rung 4 is the one that causes incidents. Read-only agents can be wrong; agents with write access can do damage.
  • Demo-path evaluation. An agent that solves the five tasks you tried can still fail one run in five on the same task. Measure across repeated runs (L91).

L71 · DAY 50

The Agent Loop From Scratch, Without a Framework

55m video60m practice

An agent is the tool loop from L62 plus four things: a system prompt that states the goal, the tools and the stopping rules; a final-answer tool; budgets; and a log of every step. About 150 lines of plain Python cover all of it, and once you have written them, every agent framework reads as a variation on the same parts.

The loop, and the transcript as state

Algorithm · The agent loop
  1. Observe. Send the transcript: the task, every earlier tool call and every result.
  2. Decide. The model replies with text, one or more tool_use blocks, or a call to final_answer.
  3. Act. Your code checks the budget, runs each requested tool and logs it.
  4. Observe again. Append every result as a tool_result (errors included) and go back to step 1, until the model finishes or a limit stops it.

Steps 1 to 4 are exactly run_tools() from L62, so the agent does not reimplement them. It wraps them. Note what the model remembers between calls: nothing. Its whole working state is the messages list. Serialise that list and you have serialised the agent, which is how L74 makes it resumable. Shrink the list without losing what matters and you have compaction (L75).

The system prompt: goal, tools, stopping rules

The system prompt is the agent's specification. It says what done looks like, what each tool is for, and how to stop, including how to stop when things go wrong. The tool descriptions repeat the "when to use" part, because the model reads both (L63).

SYSTEM = """You are DocPilot's research agent for Kubernetes support.
Goal: answer the user's question from the Kubernetes docs and past tickets.
Tools: search_docs finds doc sections; get_doc_page reads one page by slug;
query_tickets finds past support tickets; final_answer ends the task.
Rules:
- Search before you answer. Every claim cites a doc slug or a ticket id.
- If a tool returns an error, read it and make a corrected call. Never repeat a failed call unchanged.
- Finish by calling final_answer exactly once, then reply with the single word DONE.
- If a tool says the budget is exhausted, call final_answer with what you have and list what is missing."""

Termination: a final-answer tool, a step limit, a budget

An agent needs three ways to stop, and the log should say which one happened.

  • A final-answer tool. Ending with a plain-text turn works, but a tool call makes "done" explicit and gives a structured answer, sources included. The missing field lets the model say "partial" honestly instead of padding.
  • A soft budget. Once tool calls, tool-output tokens or wall-clock time pass a limit, every tool except final_answer raises an error that tells the model to finish. The model gets one turn to write up what it found.
  • A hard cap. run_tools(max_steps=...) stops the loop whatever the model does. Hitting it is a failure to report, not an answer to return.
@dataclass
class Budget:
    max_turns: int = 10              # model calls; the hard cap, via run_tools(max_steps=...)
    max_tool_calls: int = 12
    max_result_tokens: int = 20_000  # tool output fed back (about 4 characters per token)
    deadline_s: float = 120.0

def _guard(name, fn, run: Run, budget: Budget, t0: float):
    """Wrap one handler: enforce the soft budget, time the call, log it."""
    def call(**args):
        used = sum(s["tokens"] for s in run.trace)
        start, ok, text = time.perf_counter(), True, ""
        try:
            if name != "final_answer" and (len(run.trace) >= budget.max_tool_calls
                    or used >= budget.max_result_tokens or time.monotonic() - t0 > budget.deadline_s):
                raise BudgetExhausted("budget exhausted: call final_answer now with what you have")
            out = fn(**args)
            text = out if isinstance(out, str) else json.dumps(out)
            return out
        except Exception as e:
            ok, text = False, f"{type(e).__name__}: {e}"
            raise              # run_tools() sends it back as an is_error tool_result (L61)
        finally:
            run.trace.append({"step": len(run.trace) + 1, "tool": name, "args": args, "ok": ok,
                              "tokens": len(text) // 4, "result": text[:70],
                              "ms": round((time.perf_counter() - start) * 1e3, 1)})
    return call

Logging every step and recovering from errors

The guard writes one trace row per tool call, whatever happens. A raised exception is not the end of the run. run_tools() returns it to the model as an is_error result, and an error message that names the fix ("close matches: debug-pods") lets the model correct itself on the next turn. run_agent then sorts the run into one of four outcomes.

def run_agent(task: str, handlers: dict, budget: Budget = Budget()) -> Run:
    run, t0 = Run(task), time.monotonic()

    def final_answer(answer: str, sources: list[str], missing: str = "") -> str:
        run.answer = {"answer": answer, "sources": sources, "missing": missing}
        return "recorded"

    guarded = {name: _guard(name, fn, run, budget, t0)
               for name, fn in {**handlers, "final_answer": final_answer}.items()}
    msg, _ = run_tools([{"role": "user", "content": task}], tools=TOOLS, handlers=guarded,
                       system=SYSTEM, max_steps=budget.max_turns)
    if run.answer:
        run.status = "answered" if not run.answer["missing"] else "partial"
    elif msg.stop_reason == "tool_use":
        run.status = "turn cap hit"
    else:
        run.status = "ended without final_answer"
    return run

What breaks in production
  • Silent turn caps. Returning the last message when the cap hits shows the user a half-finished thought as if it were an answer. Report the status.
  • Swallowed errors. A handler that catches its own exceptions and returns "" leaves the model nothing to recover from. It will often guess instead.
  • Unbounded tool output. One 40,000-token page read in step 2 is resent on every later step (L70's quadratic cost). Truncate or paginate in the handler (L62).
  • A trace that logs only successes. The finally clause records failed and over-budget calls too, and those are the rows you debug with.

L72 · DAY 51

ReAct, Plan-and-Execute and Reflection

50m video45m practice

The named agent patterns differ in when the model thinks. ReAct thinks before every action, plan-and-execute thinks once up front and again only when something breaks, and reflection thinks after a failed attempt so the next attempt goes better. Native tool-calling models already do the first one by default. The other two are control flow that you write.

ReAct: interleaved reasoning and acting

Yao et al. (2022) prompted a model to alternate free-text thoughts with actions against a tool (a Wikipedia API with search[...], lookup[...] and finish[...] on the question-answering tasks) and to read each observation before thinking again. Reasoning alone hallucinates facts it could have looked up. Acting alone loses track of why it is acting. Interleaving them lets the reasoning steer the search and the observations ground the reasoning.

Thought 1: The user upgraded to 1.29 and pods crash-loop. Look for known causes first.
Action 1:  search[CrashLoopBackOff after upgrade]
Obs 1:     debug-pods, debug-running-pod ...
Thought 2: The docs explain how to debug, not why 1.29 breaks things. Check past tickets.
Action 2:  query_tickets[CrashLoopBackOff 1.29]
Obs 2:     T-1042: removed kubelet flag ...
Thought 3: Enough to answer, citing debug-pods and T-1042.
Action 3:  finish[...]

The paper parsed these lines out of plain text. With native tool calling the structure is built in: the thought is a text block (or a thinking block on reasoning models), the action is a tool_use block, and the observation is the tool_result. The L71 agent is a ReAct agent already. The search-then-tickets turn in its trace is a thought-action-observation cycle.

Plan-and-execute: plan once, re-plan on failure

ReAct pays for a full model call, with the whole growing transcript, at every step. Plan-and-execute splits the work. A planner call writes the whole sequence of steps. An executor runs them, as plain code when each step is a fully specified tool call, or with a small model when a step needs judgement. A final solver call writes the answer. The planner runs again only when a step fails. Related work includes Plan-and-Solve prompting (Wang et al., 2023) and ReWOO (Xu et al., 2023), which plans every tool call up front so that observations never re-enter the planner's context.

def plan_and_execute(task, planner, solver, tools, max_plans=3):
    """Plan once, run the steps as plain code, re-plan only when a step fails."""
    plan, done, plans = planner(task, []), [], 1
    while plan:
        step = plan.pop(0)
        try:
            done.append((step, tools[step["tool"]](**step["args"])))
        except Exception as e:
            if plans == max_plans:
                return {"status": "failed", "model_calls": plans, "done": done}
            print(f"step {step['args']} failed ({type(e).__name__}); re-planning")
            plan = planner(task, done + [(step, f"ERROR {type(e).__name__}: {e}")])
            plans += 1
    return {"status": "ok", "answer": solver(task, done), "model_calls": plans + 1, "done": done}

A ReAct loop making one call per turn would need five, each resending the growing transcript; parallel calls narrow the gap but do not close it. The price is adaptivity. A plan written before any observation cannot react to what step 1 finds. Plan-and-execute suits tasks whose steps are predictable once the task is understood (fetch these three pages, compare them). It fits badly when each step depends on the last result.

Reflection: lessons carried between attempts

Reflexion (Shinn et al., 2023) adds memory across attempts. No weights change, and the authors call it "verbal reinforcement learning".

Algorithm · Reflexion
  1. Act. An actor attempts the task with the current lesson memory in its context.
  2. Evaluate. An evaluator scores the result: tests, environment success or a judge.
  3. Reflect. On failure, a self-reflection call turns the trajectory and the feedback into a short verbal lesson ("I cited no ticket; for 'seen before' questions, query tickets").
  4. Remember. Append the lesson to a small episodic memory (the paper keeps only a few recent reflections) and return to step 1, until the evaluator passes or the trial budget runs out.
def reflexion(task, attempt, evaluate, reflect, max_trials=3):
    """Retry with verbal lessons from earlier failures kept in memory."""
    lessons = []                                    # episodic memory carried between trials
    for trial in range(1, max_trials + 1):
        answer, trace = attempt(task, lessons)
        ok, feedback = evaluate(task, answer)       # an external check, not the model's opinion
        print(f"trial {trial}: ok={ok} feedback={feedback!r}")
        if ok:
            return answer, lessons
        lessons.append(reflect(task, trace, feedback))
        print(f"  lesson: {lessons[-1]}")
    return None, lessons
trial 1: ok=False feedback='question asks whether this was seen before; no ticket cited'
  lesson: for 'seen before' questions, call query_tickets and cite the ticket id
trial 2: ok=True feedback='ok'
final: Use kubectl logs --previous [debug-pods] ; seen in T-1042 [T-1042]
The evaluator is the whole pattern

Here evaluate is a regex for a ticket citation: an external, programmatic check. Reflexion's reported gains came with signals of this kind: task success from the environment, exact-match answers, and unit tests the agent wrote and ran. When the only check is the model judging its own answer, self-correction is far less reliable, and Huang et al. (2023) report that it can make reasoning answers worse. Before you add reflection, ask what will tell the agent that it failed. The same question drives the evaluator–optimiser workflow in L73.

Tree search, at a high level

Tree of Thoughts (Yao et al., 2023) treats reasoning as search. At each step the model proposes several candidate thoughts and scores them (a value estimate or a vote). Breadth-first or depth-first search then expands the promising ones and backtracks from dead ends. Language Agent Tree Search (Zhou et al., 2023) applies Monte Carlo tree search to agent actions, using environment feedback as the value signal. Both multiply cost by roughly the branching factor times the depth. Both need a trustworthy evaluator. Search over actions also needs an environment you can reset, because you cannot un-send an email to explore the other branch. In production agents the cheap cousin is more common: sample several attempts and keep the one a verifier accepts (self-consistency, L19; test-time compute, L11).

What breaks in production
  • A stale plan executed faithfully. Step 1 finds the problem is in the network policy, and steps 2 to 5 still investigate storage, because the plan said so. Re-plan when observations contradict the plan's assumptions, not only on exceptions.
  • Reflection without a signal. "Critique your answer and improve it" with no test or check tends to produce confident rewrites, not fixes. It also doubles the cost.
  • Lessons that overfit. A lesson learned on one task ("always query tickets first") gets applied to every later task. Scope lessons to a task type and expire them (L76).
  • Comparing patterns on three tasks. Differences in success rate between patterns are often smaller than run-to-run noise. Use 20 or more tasks and repeated runs, and report intervals (L16).

Workflows II: Orchestrator–Workers and Evaluator–Optimiser

45m video50m practice

Two workflows cover most of what people reach for agents to do. Orchestrator–workers lets a model decide how to split a task while your code runs the parts in parallel. Evaluator–optimiser drafts, checks against a bar and revises until the bar is met. Both have a fixed shape, so their cost and their stopping rules can be written down in advance.

Orchestrator–workers

Definition · orchestrator–workers

A lead model reads the task and splits it into subtasks at run time. Each subtask goes to a worker (a model call or a small agent) with its own fresh context. A final call synthesises the workers' outputs. Compared with sectioning (L25), the difference is that the subtasks are not known in advance. "Building effective agents" gives coding as the example: you cannot know beforehand how many files a change will touch.

The DocPilot version answers comparison questions ("Ingress vs Gateway API vs a LoadBalancer Service?"). The planner returns the items as structured output, one worker per item retrieves and summarises with the cheap model, and the synthesiser builds the table. Usage is summed from every call's usage, so cost per task falls out of the return value.

PLAN_SCHEMA = {"type": "object", "additionalProperties": False, "required": ["items"],
               "properties": {"items": {"type": "array", "items": {"type": "string"}, "maxItems": 5}}}

def orchestrate(question: str, *, worker_model=SMALL, max_workers=4):
    plan = chat([{"role": "user", "content": question}], system=PLANNER,
                output_config={"format": {"type": "json_schema", "schema": PLAN_SCHEMA}})
    items = json.loads(text_of(plan))["items"]

    def work(item):                       # each worker has its own small context
        hits = search(f"{item} {question}", k=4)
        excerpts = "\n".join(f"[{h.id}] {h.text}" for h in hits)
        return chat([{"role": "user", "content": f"Item: {item}\nQuestion: {question}\n{excerpts}"}],
                    system=WORKER, model=worker_model, max_tokens=300)

    with ThreadPoolExecutor(max_workers) as pool:          # fan out, then fan in
        notes = list(pool.map(work, items))
    findings = "\n\n".join(f"## {i}\n{text_of(n)}" for i, n in zip(items, notes))
    final = chat([{"role": "user", "content": f"{question}\n\nFindings:\n{findings}"}], system=SYNTH)
    calls = [plan, *notes, final]
    cost = {"calls": len(calls), "workers": len(items),
            "input_tokens": sum(c.usage.input_tokens for c in calls),
            "output_tokens": sum(c.usage.output_tokens for c in calls)}
    return text_of(final), cost

How cost multiplies

Derivation · one agent vs orchestrated workers

Take \(N\) items, each needing \(m\) tool steps, with prefix \(P\) and \(\Delta\) tokens added per step (L70). One agent doing all \(Nm\) steps in one transcript sends

$$T_{\text{single}} = NmP + \Delta\,\frac{Nm(Nm-1)}{2}.$$

With one worker per item, each starting fresh, plus a planner and a synthesiser that reads \(N\) reports of \(r\) tokens:

$$T_{\text{orch}} = P_{\text{plan}} + N\Big(mP + \Delta\,\frac{m(m-1)}{2}\Big) + P_{\text{synth}} + Nr.$$

With \(N = 3\), \(m = 4\), \(P = P_{\text{plan}} = P_{\text{synth}} = 4000\), \(\Delta = 1500\), \(r = 500\): \(T_{\text{single}} = 147{,}000\) and \(T_{\text{orch}} = 84{,}500\). That is 14 calls instead of 12, but fewer input tokens, because isolation cuts the quadratic term into \(N\) small ones.

The model is idealised, and the saving is not guaranteed. If every worker must read the same long documents, or each worker is a full agent with a large prefix, the \(NmP\) term dominates and the total rises with \(N\). The numbers that always grow are the number of calls, the number of places a failure can occur, and the synthesis step, which can drop or misread a worker's result. L79 looks at what has been reported for multi-agent research systems.

Evaluator–optimiser

One call drafts. An evaluator checks the draft against a rubric and returns what failed. The generator revises from the old draft plus the failures, and the loop repeats. The essay's test for a good fit has two parts. The drafts must get measurably better when someone states the problems, and something must be able to state those problems. Release notes fit well: every change must appear, breaking changes go first, internal ticket ids must not leak, and bullets stay short. All four checks can be written as code, which costs no tokens and cannot be argued with.

def check_release_notes(notes: str, changes: list[dict]) -> list[str]:
    """Programmatic half of the rubric. Returns the failed checks (empty means pass)."""
    failed = []
    for c in changes:
        if f"#{c['pr']}" not in notes:
            failed.append(f"PR #{c['pr']} ({c['title']}) is missing")
    if any(c["breaking"] for c in changes) and not notes.lstrip().startswith("## Breaking"):
        failed.append("breaking changes must come first under '## Breaking'")
    if leaked := re.findall(r"\bOPS-\d+\b", notes):
        failed.append(f"internal ticket ids leaked: {', '.join(leaked)}")
    if long := [l for l in notes.splitlines() if l.startswith("- ") and len(l.split()) > 25]:
        failed.append(f"{len(long)} bullet(s) over 25 words")
    return failed

def evaluate_optimise(task, generate, evaluate, max_rounds=4):
    """Draft, check, revise. Stop on pass, on no progress, or at max_rounds. Keep the best draft."""
    draft = generate(task, None, None)
    best, best_fails, history = draft, None, []
    for rnd in range(1, max_rounds + 1):
        failed = evaluate(draft)
        history.append(len(failed))
        print(f"round {rnd}: {len(failed)} failed  {failed}")
        if best_fails is None or len(failed) < best_fails:
            best, best_fails = draft, len(failed)
        if not failed:
            return best, "accepted", history
        if len(history) >= 2 and history[-1] >= history[-2]:
            return best, "stalled", history                   # revising is not helping
        draft = generate(task, draft, failed)                # revise: old draft + what failed
    return best, "max rounds", history

Stopping conditions

Write the stop rule before the loop
  • Pass: every check succeeds. This requires checks that can actually be passed. "Make it excellent" never is.
  • No progress: the failure count did not fall between rounds. Return the best draft so far, not the latest one, because a revision can make things worse.
  • Oscillation: a draft identical to an earlier one (compare hashes) means the loop is cycling between two versions.
  • Max rounds or budget: each round costs one generation plus one evaluation. Programmatic checks are free. An LLM judge for tone or accuracy (L89) doubles the call count.

When these beat a single agent

Use orchestrator–workers when the subtasks are independent and reading-heavy and you cannot list them in advance: comparisons, audits across many pages, one investigation per affected service. Parallel workers cut wall-clock time, and isolated contexts keep each worker focused. Use evaluator–optimiser when the quality bar can be written down and first drafts reliably miss part of it. A single agent remains the better choice when every step depends on the last observation, because then there is nothing to parallelise and no fixed draft to critique.

What breaks in production
  • Unbounded fan-out. The planner returns 14 items and you pay for 14 workers. Cap the item count in the schema and in code.
  • Lossy synthesis. The synthesiser quietly drops the one worker that found a conflict. Make it cite each worker by item, and check in code that every item appears in the output.
  • One failed worker kills the run. pool.map re-raises a worker's exception as soon as you collect its result. Catch errors per worker and synthesise from partial results, marking the gap.
  • A judge that never says yes. LLM critics tend to find something to improve in every round. Without a stalled or max-rounds exit, the loop runs until the budget ends.

Agent State, Checkpoints and Durable Execution

45m video45m practice

An agent that runs for minutes or hours is a process that will be killed. To survive that, keep its state in a file. Checkpoint each decision before acting on it and each observation after, and give every side effect a key derived from the decision. A resumed run then replays the old decision instead of making a new one, and each side effect happens once.

Agents are long-running processes

Long runs meet deploys, out-of-memory kills, preempted instances, idle timeouts and closed laptops. A run that restarts from scratch pays for its tokens again and, worse, repeats its side effects: a second ticket, a second email. The fix is the one databases use. Keep state somewhere that outlives the process, and write it at well-defined points.

Definition · run state

Everything needed to continue a run in a fresh process:

  • Identity: a run_id, a status (running, done, failed, cancelled) and a step counter.
  • The transcript: messages, including every tool_use block and every tool result. Since the transcript is the agent's whole working memory (L71), this is most of it.
  • Derived state: the plan and progress (L77), budget counters, a deadline, and pending approvals (L78).

All of it must be plain JSON. SDK objects become dicts through model_dump(), which is also what the API accepts back.

Checkpoints and resuming after a crash

A checkpoint written halfway through is worse than no checkpoint. Write to a temporary file, flush it to disk, then rename it over the old one. os.replace is atomic on both POSIX and Windows, so a reader sees either the old file or the new one, never half of each.

def save(path, obj):
    tmp = f"{path}.tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(obj, f)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, path)                 # atomic rename: readers see the old file or the new one

def load(path):
    try:
        with open(path, encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        return None

Where you checkpoint matters more than how. The loop below writes two checkpoints per step. The first comes right after the model decides and before anything runs. The second comes after the tool results. On resume, the last message tells the loop where it stopped. If it is a user message, the model has not yet decided, so ask it. If it is an assistant tool_use, the decision is already made, so execute it. The model is never asked the same question twice. Asking again would cost tokens, and it might choose differently.

def run_durable(task, *, path, tools, handlers, system, side_effects=(), max_steps=8):
    state = load(path) or {"run_id": uuid.uuid4().hex[:8], "status": "running", "step": 0,
                           "messages": [{"role": "user", "content": task}]}
    msgs = state["messages"]
    while state["status"] == "running" and state["step"] < max_steps:
        if msgs[-1]["role"] == "user":                    # no decision yet: ask the model
            msg = chat(msgs, system=system, tools=tools)
            msgs.append({"role": "assistant", "content": [b.model_dump(exclude_none=True) for b in msg.content]})
            state["step"] += 1
            if msg.stop_reason != "tool_use":
                state["status"] = "done"
            save(path, state)                             # checkpoint 1: the decision, before acting
            continue
        results = []                                      # last message is a tool_use: act, or replay
        for b in msgs[-1]["content"]:
            if b["type"] != "tool_use":
                continue
            kw = dict(b["input"])
            if b["name"] in side_effects:
                kw["idempotency_key"] = f'{state["run_id"]}:{b["id"]}'   # same key after a restart
            out = handlers[b["name"]](**kw)
            results.append({"type": "tool_result", "tool_use_id": b["id"], "content": json.dumps(out)})
        msgs.append({"role": "user", "content": results})
        save(path, state)                                 # checkpoint 2: the observations
    return state

This is the L62 tool loop written out so that it can checkpoint. The error handling and budgets of L71 carry over unchanged.

Side effects that happen exactly once

One window is still open. If the process dies after the ticket is created but before checkpoint 2, the resumed run replays the tool_use and creates the ticket again. No mechanism can make a call to an external system happen exactly once across crashes. What you can build is at-least-once execution plus a receiver that recognises repeats.

Result · effectively once

At-least-once execution combined with idempotent effects is observably exactly-once. The idempotency key must be deterministic: the same decision must always produce the same key. run_id:tool_use_id qualifies, because the tool_use id was checkpointed with the decision. A key built from uuid4() at call time does not, because a replay would get a fresh key.

def create_ticket(title: str, body: str, *, idempotency_key: str | None = None) -> dict:
    db = load(STORE) or {"tickets": [], "keys": {}}
    if idempotency_key in db["keys"]:                     # seen this key: return the first result
        return {"ticket": db["keys"][idempotency_key], "replayed": True}
    tid = f"T-{2000 + len(db['tickets'])}"
    db["tickets"].append({"id": tid, "title": title})
    if idempotency_key:
        db["keys"][idempotency_key] = tid
    save(STORE, db)                                       # ticket and key committed together
    if os.environ.get("CRASH_AFTER_EFFECT"):
        os._exit(137)                                     # simulate kill -9 before the next checkpoint
    return {"ticket": tid, "replayed": False}

For APIs with neither, store the key in a field of the created object, such as a label, and search for it before creating.

Durable-execution engines and graph checkpointers

The Temporal model has a rule worth borrowing even if you never adopt it. Workflow code must be deterministic, so anything nondeterministic runs as an activity whose result is recorded, and model calls are the most nondeterministic thing in an agent. Activities are retried on failure, which makes them at-least-once. They still need idempotency keys.

Timeouts and cancellation

client = anthropic.Anthropic(timeout=60.0, max_retries=2)     # per-request timeout, SDK retries
state.setdefault("deadline", time.time() + 15 * 60)           # absolute time, so it survives restarts

def should_stop(state, path) -> str | None:                   # checked at every checkpoint boundary
    if os.path.exists(f"{path}.cancel"):
        return "cancelled"
    if time.time() > state["deadline"]:
        return "timed out"
    return None

Use three layers of timeout: one per model request (client or call), one per tool inside its handler (HTTP timeouts, a subprocess timeout for code execution, L64), and a run deadline stored as an absolute time so that a restart does not reset it. Make cancellation cooperative. The loop checks a flag between steps, writes the status and exits. A hard kill mid-effect is exactly the crash window above, so let an in-flight effect finish and record it.

What breaks in production
  • Checkpointing only after tools. A crash between the model's reply and the tools leaves no record of the decision. The resumed run asks again, gets a different tool_use id, and the key no longer protects you.
  • Non-atomic writes. A kill during json.dump leaves a truncated checkpoint, and the run is lost.
  • Keys stored apart from effects. If the ticket and its key are written in two transactions, a crash between them recreates the gap.
  • Checkpoints full of secrets. Tool results can contain tokens, personal data or customer content. Checkpoints need the same access control and retention rules as logs (L101).

L75 · DAY 53

Memory I: Working Memory, Summaries and Compaction

45m video45m practice

The context window is the agent's working memory. It is finite, and quality drops well before it is full. Compaction keeps a long run inside a budget by clearing old tool results, folding old steps into a rolling summary and keeping recent steps verbatim. The user's constraints and the decisions already made are never summarised; they are pinned. Measure what each strategy loses rather than assuming it loses nothing.

The context window as working memory

Every step of the L71 loop resends the whole transcript, so a 60-step run with chatty tools reaches the window limit or, sooner, the zone where answers degrade: the lost-in-the-middle effect and context rot of L13. Two limits matter.

Definition · the two limits
  • Hard limit: the model's context window. Exceed it and the request fails, or the response stops with stop_reason "model_context_window_exceeded".
  • Working budget: a token count you choose, well below the hard limit, past which you compact. Set it from measurements of answer quality on your own tasks, not from the window size on the model card.

Three ways to measure the transcript: a heuristic (about 4 characters per token for English and JSON, which is fine for triggering), client.messages.count_tokens(...) for an exact count before sending, and the previous response's usage. With caching on, the prompt size is input_tokens + cache_creation_input_tokens + cache_read_input_tokens, not input_tokens alone (L24).

Buffers, truncation and valid cut points

Chat applications have long used three simple strategies. A buffer keeps everything. A sliding window keeps the last \(k\) turns. A token window keeps as many recent turns as fit. All three forget the oldest material first, and in an agent run the oldest material is usually the task itself. Truncation also has to respect the transcript's rules. The first message must be a user message. Every tool_use must be followed by its tool_result, so you cannot keep a result whose call you dropped. The safe cut is just before an assistant turn, with a new user message (the summary) put in front of it.

Rolling summaries and compaction

Algorithm · Compaction
  1. After each step, estimate the transcript size. Below the trigger (75% of the budget here), do nothing.
  2. Clear stale tool results first. Replace tool results older than the last few messages with a stub that says what was there and how to get it back. This costs no model call and keeps the call/result pairing valid.
  3. If the transcript is still above half the budget, summarise everything before the last \(k\) messages. Fold the previous summary in, which is what makes it rolling.
  4. Rebuild the head as the pinned block (verbatim) plus the summary, followed by the verbatim tail starting at an assistant turn.
def est_tokens(messages) -> int:
    """About 4 characters per token, plus a few tokens of overhead per message."""
    return sum(len(json.dumps(m["content"])) // 4 + 4 for m in messages)

def clear_old_results(messages, keep_last=6):
    """Replace tool_result bodies older than the last `keep_last` messages with a stub."""
    out = []
    for i, m in enumerate(messages):
        if i < len(messages) - keep_last and m["role"] == "user" and isinstance(m["content"], list):
            m = {"role": "user", "content": [
                {**b, "content": f"[cleared: {len(b['content']) // 4} tokens; re-run the tool if needed]"}
                if b.get("type") == "tool_result" and not b["content"].startswith("[cleared") else b
                for b in m["content"]]}
        out.append(m)
    return out

def compact(messages, summarise, *, pinned: str, keep_last=8):
    """Fold old steps into a rolling summary; keep the tail verbatim; never summarise `pinned`."""
    cut = len(messages) - keep_last
    while cut > 1 and messages[cut]["role"] != "assistant":     # start the kept tail at an assistant turn,
        cut -= 1                                               # so no tool_result loses its tool_use
    head = messages[0]["content"] if isinstance(messages[0]["content"], str) else ""
    prev = re.search(r"<summary>\n(.*)\n</summary>", head, re.S)
    old = messages[1:cut] if prev else messages[:cut]          # don't re-summarise the pinned block
    summary = summarise(prev.group(1) if prev else "", old)
    return [{"role": "user", "content": f"{pinned}\n\n<summary>\n{summary}\n</summary>"}] + messages[cut:]

def maybe_compact(messages, summarise, *, pinned, budget, trigger=0.75):
    if est_tokens(messages) < trigger * budget:
        return messages, None
    cleared = clear_old_results(messages)                     # cheap first: no model call
    if est_tokens(cleared) < 0.5 * budget:
        return cleared, "cleared"
    return compact(cleared, summarise, pinned=pinned), "summarised"

In production summarise(prev, old) is one call to the small model: "Update this summary with these steps. Keep identifiers, numbers, errors and open questions." The prompt asks for specifics because summaries drift toward gist.

What must never be compacted away

A summariser decides what matters, and it decides badly about exactly the things an agent most needs: exact constraints ("not before 18:00 UTC"), decisions and their reasons, identifiers, and the error string that cracked the case. Do not leave these to the summariser.

  • Pin the task verbatim. The user's original message, with every constraint, is re-inserted word for word at every compaction.
  • Keep a decision ledger. Give the agent a record_decision(text) tool and pin the ledger. Facts are captured when they are made, while their context is in view, not reconstructed at compaction time.
  • Clear only what can be fetched again. A cleared search result can be re-run, which is why the stub says so. Output from a non-idempotent call, or from a page that has since changed, cannot be. Summarise or pin it instead.
  • Keep pointers, not payloads. Slugs, ticket ids and file paths cost a few tokens and let the agent reload content just in time. L126 develops this for runs that last hours.

Memory II: Long-Term Memory

50m video50m practice

Long-term memory is a small database that the model's output writes to and its next prompt reads from. Writing is the hard half: extract only what the user said, merge duplicates, let newer facts replace older ones, and forget on request. Reading is retrieval ranked by relevance and recency. The user must be able to see every memory and delete it.

Kinds of long-term memory

Definition · three kinds
  • Semantic: facts about the user and the world. "Cluster version is 1.29." "Prefers kubectl." In DocPilot these are mostly slots: one current value per key.
  • Episodic: what happened. "Fixed CrashLoopBackOff on checkout by raising the memory limit (T-1042)." Free text with a date, retrieved when a similar situation recurs.
  • Procedural: how to do things. "For this customer, always check the PodDisruptionBudget before draining." Instructions that change behaviour, often stored as files or prompt fragments.

The split comes from cognitive psychology. Sumers et al. (2023, "Cognitive Architectures for Language Agents") apply it to LLM agents. Working memory, the context window, was L75.

Writing memories: extract, deduplicate, resolve, forget

Algorithm · The write path
  1. Extract candidate memories from the user's turn with one structured-output call on the small model (kind, key, value, text). Never extract from tool results or retrieved documents. A page that says "remember that the user wants…" is an injection attempt (L97).
  2. Deduplicate. Same slot and same value: refresh the date and count it. Free text: compare embeddings, and above a threshold treat the candidate as the same memory seen again.
  3. Resolve conflicts. Same slot, different value: the newer explicit statement wins, and the old value moves to a history list for audit.
  4. Forget. Hard-delete on request. Give episodic memories a time to live, and let recency decay their ranking.

A pure-Python store implementing all four steps, with a toy embedding (hashed bag of words) standing in for a real model (L29):

def toy_embed(text: str, dim: int = 256) -> np.ndarray:
    """Hashed bag of words, L2-normalised: a stand-in for a real embedding model (L29)."""
    v = np.zeros(dim)
    for w in re.findall(r"[a-z0-9][a-z0-9.\-]*", text.lower()):
        v[int(hashlib.md5(w.encode()).hexdigest(), 16) % dim] += 1.0
    return v / (np.linalg.norm(v) or 1.0)

class MemoryStore:                      # items: dict[str, Memory]; Memory is a dataclass with
    def __init__(self):                 # id, kind, text, key, value, day, source, hits, history
        self.items, self.n = {}, 0

    def write(self, c: dict, *, day: int, source: str) -> str:
        if c.get("key"):                                   # profile slot: dedup or resolve conflict
            old = next((m for m in self.items.values() if m.key == c["key"]), None)
            if old and old.value == c["value"]:
                old.day, old.hits = day, old.hits + 1
                return f"dedup   {old.id} {old.key}={old.value} (seen {old.hits}x)"
            if old:                                        # newer explicit statement wins; keep history
                old.history.append((old.value, old.day, old.source))
                old.value, old.text, old.day, old.source = c["value"], c["text"], day, source
                return f"update  {old.id} {old.key}: {old.history[-1][0]} -> {old.value}"
        e = toy_embed(c["text"])                           # free text: near-duplicate by embedding
        for m in self.items.values():
            sim = float(e @ toy_embed(m.text))
            if m.key is None and m.kind == c["kind"] and sim >= 0.8:
                m.day, m.hits = day, m.hits + 1
                return f"dedup   {m.id} cos={sim:.2f} {m.text!r}"
        self.n += 1
        m = Memory(f"m{self.n}", c["kind"], c["text"], c.get("key"), c.get("value"), day, source)
        self.items[m.id] = m
        return f"add     {m.id} {m.kind}: {m.text}"

    def forget(self, selector: str) -> str:
        """Hard delete by id, slot name or 'all', history included."""
        gone = [i for i, m in self.items.items() if selector in ("all", m.id, m.key)]
        for i in gone:
            del self.items[i]
        return f"forget  {', '.join(gone) or 'nothing matched'}"

The 0.8 threshold was chosen for this toy embedding. Real embedding models put unrelated texts at different baseline similarities, so tune the threshold on labelled pairs from your own data (L28). For episodic memories, a near-duplicate may be a second occurrence of the same problem. That is why the store counts it (hits) instead of discarding it.

Reading memories: relevance and recency

Profile slots are few and small, so they go into every prompt as a block. Episodic memories are retrieved by a score that mixes similarity with recency, using a half-life \(h\) in days:

$$\text{score}(m \mid q) = \cos\!\big(e(q), e(m)\big) + 0.3 \cdot 2^{-\,\text{age}(m)/h}, \qquad h = 30,$$

keeping the top \(k\) above a floor (0.35 here). The weight and the floor are tuning knobs, not constants of nature. Generative Agents (Park et al., 2023) used a similar mix of relevance, recency and an importance score.

def recall(self, query: str, *, day: int, k: int = 3, half_life: float = 30.0):    # MemoryStore.recall
    profile = [m for m in self.items.values() if m.key]          # small: always included
    q = toy_embed(query)
    scored = [(float(q @ toy_embed(m.text)) + 0.3 * 0.5 ** ((day - m.day) / half_life), m)
              for m in self.items.values() if not m.key]
    return profile, [(round(s, 2), m) for s, m in sorted(scored, key=lambda t: -t[0])[:k] if s > 0.35]

Privacy, user control and evaluation

  • Visible: /memory lists everything stored about the user, with its source turn and date.
  • Deletable for real: /forget removes the record and its history, and the deletion must reach derived copies too: embeddings, cached prompts, summaries, analytics exports. Backups expire on a stated schedule (L101).
  • Scoped: every read filters by user and tenant in code, never by asking the model to stay in its lane (L47).
  • Minimal: extraction refuses sensitive categories (credentials, health, anything in a secret's format), and the product says that memory is on.

Evaluate memory like any other component. Measure extraction precision and recall on labelled conversations, conflict accuracy (does the latest value win?), and retrieval usefulness (did the answer use the right memory, and only that one?). Two counters must stay at zero: stale values used after an update, and deleted facts that resurface.

What breaks in production
  • Memory poisoning. Extracting from tool results lets a malicious document plant "facts" that persist across sessions. Extract from user turns only, and show new memories to the user.
  • Stale facts stated confidently. "You're on 1.28" six months after the upgrade. Store dates, decay ranking, and ask before relying on old slot values for risky advice.
  • Over-personalisation. One mention of Lens becomes "prefers Lens" forever. Store only explicit preferences, or require two sightings before inferring one.
  • Deletion that doesn't delete. The record is gone but its embedding sits in the vector index, and the next retrieval brings the fact back. Test deletion end to end.

Planning and Long-Horizon Tasks

45m video45m practice

Long tasks fail because small per-step error rates compound and the agent drifts from the goal. Three things counter both. Break the task into milestones that can each be checked. Keep the plan in a progress file outside the context window. And let the harness, not the agent, mark a milestone done, only after its checks pass.

Why long tasks fail

Derivation · compounding errors

If each step succeeds independently with probability \(p\), a task of \(n\) steps succeeds with probability \(p^n\): \(0.95^{20} \approx 0.36\) and \(0.99^{100} \approx 0.37\). Now add a check after each step that catches a fraction \(c\) of errors, each followed by a successful retry. A step then fails only if it goes wrong and the check misses it:

$$p_{\text{eff}} = 1 - (1-p)(1-c), \qquad p = 0.95,\ c = 0.9 \ \Rightarrow\ p_{\text{eff}} = 0.995,\quad 0.995^{20} \approx 0.90.$$

Independence is a simplification. Real errors correlate (one misread fact poisons every later step), and some cannot be undone by a retry, which is why side effects get approvals (L78). The direction holds, though: checking each step does more for long tasks than a slightly better model.

The measured picture agrees in shape. METR (Kwa et al., 2025) scored models on tasks calibrated by how long they take skilled humans, and found that success falls steadily as tasks get longer. The task length at which models succeed half the time was reported to double roughly every seven months over the period studied. Two other failure modes come on top of compounding. In drift, each step is locally sensible but the run wanders into subgoals nobody asked for. In goal loss, after compaction or many steps the original constraints are no longer in view (L75).

Decomposition into checkable milestones

Definition · a good milestone

A unit of work that (1) produces an artefact, such as a section, a file or a passing test; (2) has an acceptance check that can run without the agent's opinion; (3) is small enough that a failure costs one retry, not the whole run; and (4) depends only on milestones before it. "Research the topic" fails all four. "Write the 'Read logs' section, citing at least one docs page, with only kubectl commands" passes all four.

For DocPilot's troubleshooting-guide agent the plan is a list of sections. The planner (one structured-output call, L20) proposes titles. Research, writing and checking then happen one section at a time, and the assembled guide gets a final whole-document check.

To-do lists and progress files

The plan has to live outside the context window. A compacted transcript, a crashed process or a fresh session must all be able to pick up where the run left off. Guidance published by agent builders on long-running agents, Anthropic's engineering writing among it, converges on a similar pattern. Write-ups differ in detail, so treat it as a pattern rather than a specification:

  • A first session writes the plan as a structured to-do list (JSON is harder for the model to rewrite carelessly than prose) and a progress log.
  • Every later session or context window starts by reading the progress file and the recent log, then works on one item.
  • An item is marked done only after it has been verified end to end, and the session records what it did and what is next.
  • The workspace is left in a clean, resumable state, for example committed to version control.

Giving the agent a way to test its own work

Verification is a tool the agent can call and a gate the harness enforces. The checks below are cheap and deterministic. Every section cites something, every source is a page that exists, commands are kubectl only, and no TODOs remain. A check that a citation actually supports its claim needs a judge (L51).

def verify_section(text: str, known: set[str]) -> list[str]:
    """Checks the agent can run on its own work. Empty list = pass."""
    fails, cites = [], re.findall(r"\[([a-z0-9-]+)\]", text)
    if not cites:
        fails.append("no citation")
    if bad := sorted(set(cites) - known):
        fails.append(f"unknown sources {bad}")
    for cmd in re.findall(r"^\$ (.+)$", text, re.M):
        if not cmd.startswith("kubectl "):
            fails.append(f"not a kubectl command: {cmd!r}")
    if "TODO" in text:
        fails.append("contains TODO")
    return fails

The loop: one item at a time, verify, re-plan

def run_long_task(path, goal, *, plan, research, write, verify, replan, max_attempts=2):
    prog = load(path) or {"goal": goal, "log": [], "items": [
        {"id": i + 1, "title": t, "status": "todo", "attempts": 0, "feedback": ""} for i, t in enumerate(plan(goal))]}
    while item := next((i for i in prog["items"] if i["status"] == "todo"), None):
        item["attempts"] += 1
        draft = write(goal, item, research(item["title"]))     # feedback from a failed check rides along
        fails = verify(draft)
        if not fails:
            item.update(status="done", draft=draft, feedback="")
        elif item["attempts"] < max_attempts:
            item["feedback"] = "; ".join(fails)                 # retry with the failures as feedback
        else:
            item.update(status="blocked", feedback="; ".join(fails))
            new = replan(goal, item)                            # one replacement item, or None
            if new:
                prog["items"].append({"id": len(prog["items"]) + 1, "title": new, "status": "todo",
                                      "attempts": 0, "feedback": f"replaces #{item['id']}"})
        prog["log"].append(f"#{item['id']} try {item['attempts']}: {item['status']:<7} {'; '.join(fails) or 'checks pass'}")
        print(prog["log"][-1])
        save(path, prog)                                        # progress survives a crash (L74)
    return prog

What breaks in production
  • Self-graded progress. An agent allowed to mark its own items done will mark them done. The status field is written by the harness after the checks.
  • Format checks mistaken for truth checks. A citation that exists is not a citation that supports the claim. Add an entailment judge for the claims that matter (L51).

  • A plan that never changes. If no item has ever been blocked or replaced, either the tasks are easy or the checks are too weak. Look at the log.

Human-in-the-Loop: Approvals, Interrupts and Escalation

40m video40m practice

An approval gate is code that runs between the model's tool_use and your handler. It decides from the tool's risk whether to execute, shows a person exactly what would change, records what they decided, and only then acts. A prompt that says "ask before writing" does none of this reliably.

Which actions need approval

Classify every tool by what happens if the model calls it wrongly, not by how often it is right. A tool can be wrong in a cheap way, a recoverable way or a permanent way, and only the last two need a person.

Two rules keep the table safe. Unknown tools default to the strictest tier. A generic tool such as "run SQL" or "run shell" takes the tier of the worst thing it can do: if the connection can write, it is a write tool (L64, L69). OWASP calls getting this wrong excessive agency.

Gates and interrupts inside the loop

Definition
  • Approval gate: a check in the tool executor that turns a gated tool_use into a proposal and executes it only after a recorded human decision.
  • Interrupt: the loop suspends at the gate, saves its state and ends the run; a later decision resumes it.
  • Escalation: the agent hands the whole task, not one action, to a person.

The gate lives in the dispatch step of run_tools() (L62), and the model cannot route around it because it never executes anything itself (L61). The gate either asks a person who is watching (a console or chat UI) or interrupts, checkpointing the agent as in L74. Either way the tool_use still gets a tool_result: a rejection or a pending state is an ordinary result the model can read and plan around.

Presenting the proposed action, and letting the human edit it

Reviewers approve what they can read in five seconds. Show the target, the before-and-after state, and the model's stated reason; never only the raw JSON arguments. For updates, a unified diff of the record (Python's difflib) shows exactly which fields move. For emails, show the rendered message with recipients first. Let the reviewer edit the arguments rather than only reject them: a rejection costs another model turn, and an edit fixes the action in one step.

import difflib, hashlib, json, uuid
from dataclasses import dataclass
from datetime import datetime, timezone

RISK = {"search_docs": "read", "get_ticket": "read",
        "update_ticket": "write", "send_email": "external"}

@dataclass
class Decision:
    verdict: str                 # "approve" | "edit" | "reject"
    by: str
    args: dict | None = None     # the human's edited arguments, for "edit"
    note: str = ""

def render(tool: str, after: dict, before: dict) -> str:
    a = json.dumps(before, indent=2, sort_keys=True).splitlines()
    b = json.dumps(after, indent=2, sort_keys=True).splitlines()
    return "\n".join(difflib.unified_diff(a, b, "current", f"proposed ({tool})", lineterm=""))

class Audit:
    """Append-only JSONL; each line carries the hash of the previous line."""
    def __init__(self, path):
        self.path, self.prev = path, "0" * 64
    def write(self, **event):
        event |= {"ts": datetime.now(timezone.utc).isoformat(timespec="seconds"), "prev": self.prev}
        line = json.dumps(event, sort_keys=True)
        self.prev = hashlib.sha256(line.encode()).hexdigest()
        with open(self.path, "a", encoding="utf-8") as f:
            f.write(line + "\n")
def gated_call(tool, args, *, handlers, current, approve, audit):
    if RISK.get(tool, "write") == "read":           # unknown tools are gated too
        return handlers[tool](**args)
    pid = uuid.uuid4().hex[:8]
    before = current(tool, args)                    # the state this action would change
    audit.write(event="proposed", id=pid, tool=tool, args=args)
    d = approve(pid, tool, render(tool, before | args, before))
    if d is None:                                   # asynchronous: park and checkpoint
        audit.write(event="pending", id=pid)
        return {"status": "pending_approval", "proposal_id": pid}
    audit.write(event=d.verdict, id=pid, by=d.by, note=d.note, args=d.args)
    if d.verdict == "reject":
        return {"status": "rejected", "reason": d.note}
    final = d.args if d.verdict == "edit" else args
    result = handlers[tool](**final, idempotency_key=pid)
    audit.write(event="executed", id=pid, result=result)
    return result

Escalating when confidence is low

Approval asks "may I do this?"; escalation says "I should not be the one deciding". Give the agent an explicit escalate_to_human(reason, summary) tool and tell it in the system prompt when to use it. Don't rely on the model's self-reported confidence alone. Back it with signals your code can see:

  • Retrieval found nothing relevant: top reranker score below a threshold you calibrated in Phase 5.
  • Policy triggers: billing disputes, security reports, legal language, a customer who asks for a person.
  • The agent is struggling: the same tool failing twice, or a step budget nearly spent (L84).

An escalation must carry a summary the human can act on without rereading the transcript: what was asked, what was tried, what was found and what is still unknown. That summary is a handoff payload, and L80 gives it a schema.

Audit trails and asynchronous approval

The audit log answers "who allowed this, and what exactly did they see?" Record the proposal, the decision with the reviewer's identity, the final arguments if they were edited, and the result, all under one proposal ID. Hash-chaining the lines makes silent edits detectable; it does not stop someone deleting the whole file, so ship the log to append-only storage as well.

Most real approvals are asynchronous: the reviewer is in a queue, a Slack channel or an email, and answers minutes or hours later. The agent cannot hold a request open that long. Park it: write the pending proposal, checkpoint the transcript (L74), and end the run. When the decision arrives, a webhook loads the checkpoint, re-reads the current state, re-renders the diff if that state has changed, and resumes the loop with the decision as the tool_result. The proposal ID doubles as the idempotency key, so a resumed run cannot send the same email twice.

What breaks in production
  • Approval fatigue. Gate too much and reviewers click "approve" without reading. Gate reversible writes in batches and keep per-action approval for the dangerous tier.
  • Stale diffs. The diff was rendered at 09:00; a colleague changed the ticket at 09:05; approval at 09:10 overwrites their change. Check that the state still matches what the reviewer saw, and re-ask if it doesn't.
  • Splitting around the gate. A threshold on "refunds over 100" invites ten refunds of 99. Put thresholds on the total per task, not per call.
  • A persuasive reason field. The model writes the "why" text, and injected content can write it too (L97). Show the diff above the reason, and never let the reason replace it.
  • Edits skip validation. Edited arguments must pass the same schema and permission checks as the model's.

Multi-Agent Systems: When They Help and When They Hurt

50m video45m practice

Splitting work across agents buys separate context windows and parallel time, and it costs you shared understanding. Use it for broad, independent reading. Keep decisions and writes in one thread.

Three architectures

L73 built orchestrator–workers as a workflow: the workers were single model calls. In a multi-agent system each worker is itself an agent, with its own loop, tools and transcript (L71). The topology decides who can talk to whom.

Parallel subagents for broad research

Anthropic's engineering post "How we built our multi-agent research system" (June 2025) describes the strongest case for the pattern. A lead agent plans a research question, then starts subagents in parallel. Each one searches with its own context window and returns a condensed result, so the lead never reads the raw pages. The post reports that, on Anthropic's internal research evaluation, a lead agent with smaller-model subagents beat a single agent built on the larger model by about 90%. It also reports that token usage alone explained most of the variation in performance on the BrowseComp benchmark (about 80%, in its analysis). The authors' reading is that multi-agent designs help largely because they let a task spend more tokens than one context window allows.

Derivation · why isolation can save input tokens

An agent's context starts at \(c_0\) tokens and grows by \(g\) per step, and every call re-reads all of it. Over \(n\) steps the input tokens are

$$C_{\text{single}} = \sum_{k=0}^{n-1} (c_0 + g k) = n c_0 + g\,\frac{n(n-1)}{2}.$$

Split the same work across \(m\) subagents with \(n/m\) steps each and the quadratic term shrinks by roughly a factor \(m\). The price is \(m\) copies of \(c_0\) (system prompt and brief) plus the lead's planning and merge calls. Wall-clock time drops from the sum of the step times to about their maximum.

import asyncio
# Finding (a dataclass: doc_id, topic) and INDEX (topic -> doc ids) are defined in the full script.
SYSTEM, BRIEF, CALL, RESULT, SUMMARY = 1500, 200, 50, 800, 300   # fake token sizes

async def subagent(topic: str, steps: int = 4) -> dict:
    ctx, used = SYSTEM + BRIEF, 0             # its own, fresh context window
    for _ in range(steps):
        used += ctx                           # every call re-reads the whole context
        await asyncio.sleep(0.05)             # stands in for model call + tool call
        ctx += CALL + RESULT
    used += ctx                               # final turn: write a short summary
    return {"findings": [Finding(d, topic) for d in INDEX[topic]], "tokens": used}

async def supervisor(topics: list[str], timeout: float = 5.0):
    runs = [asyncio.wait_for(subagent(t), timeout) for t in topics]
    results = await asyncio.gather(*runs, return_exceptions=True)
    ok = [r for r in results if not isinstance(r, BaseException)]
    failed = [t for t, r in zip(topics, results) if isinstance(r, BaseException)]
    merged = {}
    for r in ok:
        for f in r["findings"]:
            merged.setdefault(f.doc_id, f)    # first writer wins; count the overlap
    raw = sum(len(r["findings"]) for r in ok)
    lead = (SYSTEM + 100) + (SYSTEM + SUMMARY * len(ok))   # plan call + merge call
    return list(merged.values()), raw, lead + sum(r["tokens"] for r in ok), failed

With three subtopics (resource requests, eviction, autoscaling), a fake index whose results overlap, and a single-agent baseline doing the same twelve steps in one context:

multi : 7 unique of 9 findings, 55,000 input tokens, 0.29s, failed=[]
single: 87,100 input tokens, 0.76s

Same work, so the split is faster and, here, even cheaper in input tokens. Two of the nine findings were duplicated work. Prompt caching (Phase 2) makes the single agent's re-reads much cheaper, which narrows the gap.

Real systems do not do the same work. The post reports that agents use several times more tokens than chat, and multi-agent systems use many times more again (it gives roughly 4× and 15×). The lead agents also tended to over-delegate: early versions started far too many subagents for simple questions. The extra spend only pays off when the task is valuable and genuinely breaks into independent parts.

Specialists or one generalist with tools

A "billing agent" and a "docs agent" are usually one model with different system prompts and tool sets. Prefer a single agent with all the tools until you hit one of these limits:

  • Too many tools. Tool selection degrades as the list grows. Splitting the tools across specialists, or loading them on demand, keeps each choice small.
  • Conflicting instructions. The tone and policies for refunds clash with those for technical answers.
  • Permission boundaries. Only the billing agent holds billing credentials. This is the strongest reason, because it is a security boundary, not a prompt-engineering preference (Phase 9).

Coordination failures

Cognition's "Don't Build Multi-Agents" (Walden Yan, June 2025) is the counterpoint. It proposes two principles: share full context, meaning whole agent traces rather than single messages; and remember that actions carry implicit decisions, so two agents that each decide something on their own will conflict. Its example is a game clone split between two subagents, where one builds a background in one visual style and the other a bird in a different style. Each part is fine; together they don't fit. Its recommendation is a single-threaded agent, with compression of old history for long tasks (L75).

What the evidence says

The two posts disagree less than their titles suggest. Anthropic's says its design suits breadth-first research and fits poorly where agents must share context or depend on each other closely, as in most coding. Cognition's argues against splitting decisions and writes. A systematic study of multi-agent framework traces (Cemri et al., 2025) found that many failures come from poor task specification, misalignment between agents and missing verification, not from a weak base model. The rule that follows: parallelise reads, serialise writes. Measure before you believe a multi-agent gain, because a single agent with a larger budget is the fair baseline.

What breaks in production
  • Unfair baselines. A multi-agent run that spends three times the tokens beats a single agent on a fixed budget. Compare at equal spend as well as at equal steps.
  • Partial results treated as complete. A timed-out worker silently drops a third of the answer. Report failed to the lead and to the user.
  • Cost per task varies a lot. The lead decides how many workers to start, so spend varies widely from one task to the next. Put a hard cap on workers and tokens per task (L84).
  • Debugging across transcripts. One answer now spans four logs. Give every worker the parent's trace ID from day one (Phase 10).

L80 · DAY 57

Agent Interoperability: Handoffs and Agent-to-Agent Protocols

40m video35m practice

A handoff moves control of a task from one agent to another. Whatever the receiving agent needs has to travel with it, and a validated schema carries that more reliably than a prose summary. Agent-to-agent protocols such as A2A standardise the same contract across teams and vendors.

Handoffs: passing conversation and control

Definition

A handoff transfers two things: control (which agent acts and answers the user next) and context (what that agent knows when it starts). Inside one process it is usually exposed to the model as a tool, such as handoff_to_billing. The OpenAI Agents SDK and swarm-style frameworks model handoffs this way. Across services it is a network request to an agent you do not control.

There are three ways to pass context, and each fails differently:

  • The full transcript. Nothing is lost, which is Cognition's argument from L79. But the receiver pays to read everything, sees data it should not (another customer's details, internal tool output), and may be confused by instructions meant for the first agent.
  • A prose summary. It is cheap, but the model decides what to drop, and constraints are what it drops first.
  • A structured payload plus a pointer. Typed fields for what must survive (identifiers, verified facts, constraints, open questions), a short summary for everything else, and a reference the receiver can follow if it needs the transcript. Use this one.

Decide the return path too. Can billing hand back to triage, or only escalate to a person (L78)? Without a rule, two agents can pass a hard case back and forth indefinitely.

The handoff contract in code

from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, ValidationError

class Constraint(BaseModel):
    text: str
    source: Literal["user", "policy"]       # who imposed it; agents can't invent one

class Handoff(BaseModel):
    model_config = ConfigDict(extra="forbid")
    schema_version: Literal["1"] = "1"
    from_agent: Literal["triage"]
    to_agent: Literal["billing"]
    reason: Literal["billing_dispute", "refund_request", "invoice_question"]
    customer_id: str = Field(pattern=r"^C-\d{4,}$")
    ticket_id: str = Field(pattern=r"^T-\d+$")
    summary: str = Field(max_length=600)    # what the next agent must know, in prose
    facts: dict[str, str] = {}              # verified values, e.g. invoice id
    constraints: list[Constraint] = []
    open_questions: list[str] = []
    transcript_ref: str                     # a pointer to the transcript, not a copy
    return_to: Literal["triage", "human"] = "triage"

HANDOFF_TOOL = {"name": "handoff_to_billing",
                "description": "Transfer to the billing agent for refunds, invoices and disputed "

                "input_schema": Handoff.model_json_schema()}

    try:
        return Handoff.model_validate(tool_input)
    except ValidationError as e:            # goes back to the model as an is_error tool_result
        return {"error": [f"{'.'.join(map(str, x['loc']))}: {x['msg']}" for x in e.errors()]}

Agent cards and capability discovery

Agent2Agent (A2A) is an open protocol announced by Google in April 2025 and moved to the Linux Foundation later that year. A2A agents describe themselves with an Agent Card: a JSON document giving the agent's name, description, endpoint, capabilities (streaming, push notifications), accepted input and output types, the skills it offers, and the authentication it requires. Cards are conventionally served at a well-known path under /.well-known/ on the agent's domain. The exact file name changed between spec versions, so check the version you target. A2A's model: tasks, messages and artifacts

A2A treats the remote agent as opaque: you see its card and its outputs, never its prompts, tools or memory. A client sends a message (a role plus a list of parts: text, file or structured data). The server answers directly or creates a task, a stateful unit of work with an ID and a lifecycle: submitted, working, input-required, then completed, failed, canceled or rejected. Results come back as artifacts, which are also made of parts. Messages are JSON-RPC 2.0 over HTTP, with streaming over server-sent events and push notifications to a client webhook for long tasks. Later versions added other transport bindings.

Trust, authentication and adoption

An agent that accepts handoffs is an API endpoint whose input partly came from a model, and possibly from an attacker who wrote text into a ticket. Authenticate the caller with standard HTTP schemes declared in the card (OAuth 2.0, bearer tokens, mutual TLS). Keep credentials in headers, never inside message parts. Authorise per skill. Re-validate every payload on the receiving side; the sender's validation is not your validation. Treat the summary field as untrusted text, because it may carry injected instructions (Phase 9). On adoption, A2A launched with a long list of partners. Partner lists measure announcements, not production traffic, so check whether the agents you need to reach actually publish cards before you design around the protocol.

What breaks in production
  • Ping-pong. Triage hands to billing, billing hands back, forever. Count handoffs per task and escalate to a person after two.
  • Schema drift. The sender upgrades to version 2 while the receiver still parses version 1. Version the payload explicitly and reject unknown versions loudly.
  • Invented authority. "Supervisor approved the refund" arrives as text. Approvals travel as signed records from the audit log (L78), never as a sentence in a summary.
  • Lost user. After a handoff, the user's next message goes to the old agent. Route by the current owner stored on the conversation, not by whichever agent spoke last.

Agent Frameworks Compared

55m video50m practice

An agent framework is someone else's version of the code you wrote in L71–L78. Adopt one when it gives you, cheaper and better tested, the parts you would otherwise have to build: durable state, interrupts, tracing. Skip it when it mostly hides a loop you could write in about 150 lines.

What frameworks provide, and what they cost

Definition

An agent framework is a library that owns some or all of: the loop (call the model, run tools, repeat); state (typed, serialisable, checkpointed); tool plumbing (schemas from functions, validation, parallel calls); memory; tracing; and deployment (a server, queues, a hosted runtime). Frameworks differ mainly in how much of this they own and how much they let you replace.

The costs are real and easy to underrate:

  • Abstraction. The prompt the model actually sees is assembled inside the library. When behaviour changes, you need to see that prompt, so check how to dump it before you adopt.
  • Lag behind the provider. New API features (thinking settings, cache controls, new tool options, new stop reasons) reach the raw SDK first. A framework may expose them weeks later, or only through an escape hatch.
  • Debugging. Stack traces run through framework internals, and errors surface far from their cause.
  • Lock-in and churn. Your state schema, tools and traces take the framework's shape. Several of these libraries changed major APIs during 2025, so pin versions.

def rank(scores: dict[str, dict[str, int]]) -> list[tuple[str, int, list[str]]]:
    """scores[candidate][need] in {0, 1, 2}: 0 = missing, 1 = with work, 2 = built in."""
    out = []
    for cand, s in scores.items():
        gaps = [n for n, (_, must) in NEEDS.items() if must and s.get(n, 0) == 0]
        total = sum(w * s.get(n, 0) for n, (w, _) in NEEDS.items())
        out.append((cand, -1 if gaps else total, gaps))
    return sorted(out, key=lambda r: -r[1])

Staying framework-free

The framework-free option is a serious choice, not a default for people who haven't tried the alternatives.   • Dependency weight. A framework can pull in dozens of transitive packages, each a supply-chain risk (Phase 9) and a cold-start cost.
  • Toy-demo selection. Every framework looks good on its quick-start. Spike on your hardest real task: an approval interrupt plus a crash and resume.

Nodes as plain functions

A node takes the state and returns a partial update. The reducer annotation on messages tells the runtime to append that field instead of replacing it. Nothing below imports the framework, so the nodes are unit-tested with a fake chat(). Blocks are stored as dicts so that any checkpointer can serialise them.

import operator
from typing import Annotated, TypedDict
# Also in scope: chat (docpilot.llm), SYSTEM and TOOLS (docpilot.agent, L71),
# and HANDLERS, a dict from tool name to function.

END = "__end__"                     # the same string as langgraph.graph.END

class AgentState(TypedDict):
    messages: Annotated[list[dict], operator.add]    # reducer: updates are appended
    tool_calls: int
    answer: dict | None

def call_model(state: AgentState) -> dict:
    msg = chat(state["messages"], system=SYSTEM, tools=TOOLS)
    blocks = [b.model_dump(exclude_none=True) for b in msg.content]
    return {"messages": [{"role": "assistant", "content": blocks}]}

def run_tool_calls(state: AgentState) -> dict:
    results, answer = [], state["answer"]
    for b in state["messages"][-1]["content"]:
        if b["type"] != "tool_use":
            continue
        try:
            if b["name"] == "final_answer":
                answer, out = b["input"], "recorded"
            else:
                out = str(HANDLERS[b["name"]](**b["input"]))
            err = False
        except Exception as e:                       # errors go back to the model
            out, err = f"{type(e).__name__}: {e}", True
        results.append({"type": "tool_result", "tool_use_id": b["id"], "content": out, "is_error": err})
    return {"messages": [{"role": "user", "content": results}],
            "tool_calls": state["tool_calls"] + len(results), "answer": answer}

def after_model(state: AgentState) -> str:
    content = state["messages"][-1]["content"]
    return "tools" if any(b["type"] == "tool_use" for b in content) else END

def after_tools(state: AgentState) -> str:
    return END if state["answer"] is not None else "model"

What compile and invoke actually do

Algorithm · Running a state graph
  1. Start at the entry node with the input state.
  2. Call the node; it returns a partial update.
  3. Merge the update into the state, field by field, with each field's reducer (append for messages, replace otherwise).
  4. Save a checkpoint of the merged state under the thread ID.
  5. Call the node's routing function to pick the next node; stop at END, or fail when the step count passes the recursion limit.

Writing that core yourself is the quickest way to understand the framework without reading its source. This runner follows the five steps and is how the nodes above were tested:

import copy

def run_graph(nodes, routes, state, *, entry="model", recursion_limit=21, saver=None):
    node, steps = entry, 0
    while node != END:
        steps += 1
        if steps > recursion_limit:
            raise RecursionError(f"recursion_limit={recursion_limit} reached at node {node!r}")
        for k, v in nodes[node](state).items():      # apply reducers
            state[k] = state[k] + v if k == "messages" else v
        if saver is not None:
            saver.append((node, copy.deepcopy(state)))   # one checkpoint per step
        node = routes[node](state)
    return state

What breaks in production
  • Reducer surprises. Returning the whole message list from a node with an append reducer duplicates the transcript. Return only the new messages.
  • Thread ID reuse. Reusing a thread_id for a new task resumes the old conversation. Derive it from the task or ticket ID.

  • Unbounded checkpoint history. One checkpoint per step per thread grows quickly. Set a retention policy.

Coding Agents: How They Work and How to Work With Them

50m video60m practice

A coding agent is the L71 loop with a handful of very general tools (read, search, edit, shell) pointed at a repository, and with the test suite acting as its verifier. It works well when the repository tells it how to work and the tests tell it when it is done. It is dangerous when its shell can reach anything you would not let a new contractor touch.

Anatomy of a coding agent

Definition

A coding agent is a tool loop (L62) with: read and search tools (open a file, list a directory, regex search) so it can build its own context, instead of relying on retrieval chosen for it; an edit tool, usually an exact string replacement or a patch, so changes are small and reviewable; a shell for builds, git and tests; and a planning loop that keeps a to-do list across many steps (L77). The test suite turns "done" into something the agent can check for itself.

Exact-match editing is a design choice, not a detail. Rewriting a whole file invites silent damage to lines the model never meant to change. Replacing one unique snippet makes every edit a small diff, and a failed match is an error the model can recover from:

import difflib, pathlib

def edit_file(path: str, old: str, new: str) -> str:
    """Replace exactly one occurrence of `old`. Errors are written for the model to act on."""
    p = pathlib.Path(path)
    text = p.read_text(encoding="utf-8")
    n = text.count(old)
    if n == 0:
        return "ERROR: old text not found. Re-read the file; whitespace must match exactly."
    if n > 1:
        return f"ERROR: old text occurs {n} times. Include more surrounding lines to make it unique."
    after = text.replace(old, new, 1)
    p.write_text(after, encoding="utf-8")
    diff = difflib.unified_diff(text.splitlines(), after.splitlines(), path, path, lineterm="", n=1)
    return "\n".join(diff)

Repository context: instruction and memory files

An agent starting in a repository knows nothing about its conventions. Instruction files fix that. Claude Code reads CLAUDE.md files (repository, directory and user level), and many other agents read AGENTS.md, an open convention shared across tools. Both are plain Markdown loaded into context at the start of every session, so every line costs tokens on every run. Put in what a new engineer would need on day one and could not guess:

  • How to build, test and lint, as exact commands (uv run pytest -q tests/unit), including the fast subset.
  • The layout: where DocPilot's package, prompts and evals live (docpilot/, prompts/, evals/).
  • Rules that are not visible in the code: "never edit prompts/*.v*.md in place, add a new version"; "no new dependencies without asking".
  • Traps: "integration tests need a running Qdrant; skip them with -m 'not integration'".

Keep it short and specific, and correct it whenever you see the agent repeat a mistake. A file that says "write clean code" changes nothing.

Working agentically

Algorithm · One feature with a coding agent
  1. Plan first. Ask for a plan, with no edits, in a read-only mode. Read it, correct it, and only then let the agent write.
  2. Tests as the specification. Have it write or point to failing tests that encode the issue, and confirm that they fail for the right reason.
  3. Small diffs. One concern per change, so that each diff can be reviewed in a few minutes. Commit at green checkpoints, so that a bad step is one git reset away.
  4. Verify, don't trust. Run the tests yourself. Watch for tests the agent weakened, skipped or special-cased to get to green.
  5. Review everything. Read the full diff as you would a colleague's pull request. You are the author of record.

Headless use runs the same loop without a person at the keyboard: a print mode such as claude -p "…" with JSON output, or the equivalent non-interactive command in other agents, called from a script or a CI job. Typical CI jobs triage new issues, fix lint failures, or draft a pull request from an issue labelled for the agent. In CI, allow only the tools the job needs, give it a token that can open pull requests but not merge them, and send every change through human review. Flags differ between tools and versions, so check your agent's documentation.

Benchmarks: what SWE-bench measures

SWE-bench (Jimenez et al., 2023) builds tasks from real GitHub issues in popular Python repositories. The agent gets the repository at the commit before the fix, plus the issue text, and must produce a patch. The patch is scored by running the tests from the human fix: tests that failed before must now pass, and tests that passed before must still pass. SWE-bench Verified (2024) is a 500-task subset that human annotators screened, removing tasks whose issue text was underspecified or whose tests rejected valid solutions.

What it does measure: issue-to-patch repair in mature Python codebases with good tests. What it doesn't: other languages, greenfield design, code quality beyond passing tests, or asking clarifying questions. The repositories are public, so contamination is a live concern (L92). Scores also depend heavily on the harness (tools, retries, time budget), not only the model. Read a reported score as a statement about one model, in one scaffold, on one task family.

Risks and permission modes

A coding agent's shell is a code-execution tool pointed at your laptop or CI runner (L64). Permission modes trade autonomy for safety. Products use different names; Claude Code, for instance, distinguishes a default mode that asks before edits and commands, a mode that accepts file edits automatically, a read-only plan mode, and a bypass mode meant for isolated sandboxes. On top of the mode, an allow and deny list sorts individual commands:

import re, shlex

READ_ONLY = {"ls", "cat", "rg", "grep", "git status", "git diff", "git log"}
TESTS = {"pytest", "ruff", "mypy"}
DENY = [r"\brm\s+-[a-z]*r", r"git\s+push\b.*--force", r"\|\s*(sh|bash)\b", r"\.env\b", r"\bsudo\b"]

def check_command(cmd: str, mode: str) -> str:
    """Return allow | ask | deny for a shell command under a permission mode."""
    if any(re.search(p, cmd) for p in DENY):
        return "deny"                                   # no mode unlocks these
    words = shlex.split(cmd)
    head = " ".join(words[:2]) if words[:1] == ["git"] else words[0]
    if head in READ_ONLY:
        return "allow"
    if mode == "plan":
        return "deny"                                   # plan mode never changes anything
    if head in TESTS or mode == "bypass":               # bypass: only inside a disposable sandbox
        return "allow"
    return "ask"

What breaks in production
  • Denylists leak. rm -f -r build/ slips past the regex above, and so does python -c with the same effect. A denylist is a backstop. The real boundary is a sandbox or container with no credentials worth stealing.
  • Secrets. An agent that can read .env or ~/.aws can paste them into a transcript, a commit or a web request. Keep secrets out of the workspace, and scan diffs before they are pushed.
  • Supply chain. Agents add dependencies freely and sometimes invent package names that an attacker can register. Require approval for any change to dependency files (L102).
  • Injected instructions. An issue, README or web page the agent reads can contain instructions. Untrusted text plus shell access plus a network is the combination L98 warns about.
  • Green by cheating. Deleted assertions, pytest.skip and hard-coded expected values all pass CI. Review test changes more strictly than code changes.

Guards don't make an agent's tools more reliable. They make its failures short, visible and safe. A guarded agent that says "I couldn't reach that page" beats an unguarded one that answers confidently from an error page. And because agents are stochastic, reliability is a rate you measure over repeated runs, not a property you see in one demo.

Guards: budgets, deadlines, repeat detection

Guards live in the executor, beside the approval gate from L78. When one trips, the agent is not killed. It is told why in a tool result and gets one turn to write up what it has, as in the soft budget of L71. The hard cap on model turns stays as the last line of defence.

import json, time
from collections import Counter

class Guards:
    def __init__(self, max_steps=12, max_repeats=2, max_errors_in_row=4,
                 max_tokens=200_000, deadline_s=120.0):
        self.max_steps, self.max_repeats, self.max_errs = max_steps, max_repeats, max_errors_in_row
        self.max_tokens, self.deadline = max_tokens, time.monotonic() + deadline_s
        self.seen, self.steps, self.errs, self.tokens = Counter(), 0, 0, 0

    def charge(self, usage) -> None:                  # after every model response
        self.tokens += usage.input_tokens + usage.output_tokens

    def before(self, name: str, args: dict) -> str | None:
        """Called before each tool call; a string means stop and tell the model why."""
        self.steps += 1
        key = (name, json.dumps(args, sort_keys=True))
        self.seen[key] += 1
        if self.steps > self.max_steps:
            return "step budget spent: finish with what you have"
        if self.tokens > self.max_tokens:
            return "token budget spent: finish with what you have"
        if time.monotonic() >= self.deadline:
            return "deadline passed: finish with what you have"
        if self.seen[key] > self.max_repeats:
            return "repeated identical call: change the arguments or finish"
        return None

    def after(self, ok: bool) -> str | None:
        self.errs = 0 if ok else self.errs + 1
        return "error spiral: finish and report the failure" if self.errs >= self.max_errs else None
Setting the limits
  • Steps and tokens: run your eval tasks unguarded, then set each limit at about two to three times the 95th percentile of successful runs. Lower limits cut off hard but legitimate tasks.
  • Cost cap per task: tokens per model times that model's price, from a price table you keep up to date (L109). Cap the total across subagents (L79), not each call.
  • Wall-clock: a per-tool timeout (the tool's own client timeout) plus a per-task deadline. Cancelling a tool must leave no half-done side effect (L74).
  • Repeats: canonicalise arguments (sorted keys, stripped whitespace) or trivial variations slip through. Two identical calls after an error is a reasonable retry; four is a loop.

Fallbacks, partial results and visible failure

Every stopped run should still produce something useful. Return a partial result with a status, the findings so far, what is missing and why, for example {"status": "partial", "answer": …, "missing": "page debug-pods unreachable (timeout x3)"}. Offer fallbacks in order of cost: retry once with backoff, try an alternative tool (search snippets instead of the full page), use a cached copy, then hand off to a person (L78). Show the status in the interface; "I checked A and B but couldn't reach C" earns more trust than a smooth answer that silently skipped C (L113). Log a failure category for every run, so dashboards show partial and wrong separately from success.

A fault-injection harness

You can't wait for production to show how the agent degrades. Wrap each tool so that, at a chosen rate, it times out, raises an error, or returns junk that looks like content (an HTML error page):

import random

def faulty(fn, rng: random.Random, rate: float):
    """Wrap a tool: with probability `rate`, time out, fail, or return junk (equally likely)."""
    def call(**args):
        r = rng.random()
        if r < rate / 3:
            raise TimeoutError("tool timed out after 10s")
        if r < 2 * rate / 3:
            raise RuntimeError("503 from search backend")
        if r < rate:
            return "<html><body>Service Unavailable"      # junk: looks like content
        return fn(**args)

Reliability as a rate: pass^k

Definition · Consistency over k trials

For a task, pass^k is the probability that all of \(k\) independent trials succeed. τ-bench reports its average over tasks. It is the consistency counterpart of pass@k (Chen et al., 2021), the probability that at least one of \(k\) trials succeeds. pass@k suits tools where a person picks the best attempt; pass^k suits agents that face every customer once.

Derivation · the unbiased estimator

Run each task \(n \ge k\) times and count \(c\) successes. Choose \(k\) of the \(n\) trials uniformly at random; the chance that all \(k\) are successes is \(\binom{c}{k} / \binom{n}{k}\). Averaging over tasks:

$$\widehat{\text{pass}^k} = \frac{1}{T} \sum_{t=1}^{T} \frac{\binom{c_t}{k}}{\binom{n}{k}}.$$

It is unbiased. If a task's trials are independent with success probability \(p_t\), each of the \(\binom{n}{k}\) subsets of \(k\) trials is all-success with probability \(p_t^k\), so \(\E\big[\binom{c_t}{k}\big] = \binom{n}{k} p_t^k\). Example: three tasks with \(c = 8, 4, 0\) out of \(n = 8\) give pass^1 \(= 0.5\), but pass^4 \(= (1 + 1/70 + 0)/3 \approx 0.338\).

from math import comb

def pass_hat_k(successes: list[int], n: int, k: int) -> float:
    """tau-bench pass^k: mean over tasks of C(c, k) / C(n, k), with c successes in n trials."""
    return sum(comb(c, k) for c in successes) / (len(successes) * comb(n, k))

print(pass_hat_k([8, 4, 0], 8, 1), round(pass_hat_k([8, 4, 0], 8, 4), 4))   # 0.5 0.3381

What breaks in production
  • Guards nobody sees. A budget that trips silently and returns an empty answer is a new silent failure. Every trip must reach the user's message and the logs.
  • Retries that multiply. The SDK retries, your tool retries and the agent retries: 3 × 3 × 3 = 27 calls to a struggling backend. Retry in one layer only (L107).
  • Limits tuned on easy tasks. Budgets set on the demo set cut off real escalations. Tune them on the eval set's hardest decile.
  • One run per task. A single green run says almost nothing about pass^k. Use at least three trials per task, more for the tasks that matter.

Deciding what counts as success

Definition · a successful run

A run succeeds when three things hold: its status is resolved; every automatic check passes; and every executed side effect has a matching approval in the audit log. The third condition fails the run whatever else passed. A partial run stopped with a stated reason and filed nothing unapproved, so it is a visible failure, not a silent one. Write these rules down before the first run, and automate as many as you can.

from dataclasses import dataclass
from statistics import mean, median

@dataclass
class RunRecord:
    escalation_id: str
    status: str                     # "resolved" | "partial" | "failed"
    steps: int
    input_tokens: int
    output_tokens: int
    approvals: list[str]            # proposal ids approved in the audit log
    side_effects: list[str]         # proposal ids actually executed
    checks: dict[str, bool]         # automated acceptance checks for this run

def problems(r: RunRecord) -> list[str]:
    out = [name for name, ok in r.checks.items() if not ok]
    if set(r.side_effects) - set(r.approvals):
        out.append("side effect without approval")     # an automatic fail, whatever else passed
    return out

def report(runs: list[RunRecord], price_in: float, price_out: float) -> None:
    """Prices per million tokens, read from your price table; never hard-code them."""
    good = [r for r in runs if r.status == "resolved" and not problems(r)]
    cost = [(r.input_tokens * price_in + r.output_tokens * price_out) / 1e6 for r in runs]
    steps = [r.steps for r in runs]
    print(f"success {len(good)}/{len(runs)} = {len(good) / len(runs):.0%}"
          f" | partial {sum(r.status == 'partial' for r in runs)}"
          f" | steps median {median(steps)} max {max(steps)}"
          f" | cost mean {mean(cost):.3f} max {max(cost):.3f}")
    for r in runs:
        if p := problems(r):
            print(f"  {r.escalation_id}: {', '.join(p)}")

  ESC-04: side effect without approval

Good automatic checks for this task: the reply cites at least one doc page and one past ticket, and all of them exist; every cited page was fetched during the run; the doc diff applies cleanly to the current page; the run stayed within its budgets; and the final status is resolved or a partial with a reason. Correctness of the advice still needs your judgement. Label each of the 20 runs pass or fail with a one-line reason, which is the seed of the judge you will calibrate in L89–L90.

What breaks in production
  • Approval by default. An approver stub that returns "approve" during development ends up in the demo. Make the test approver reject unless told otherwise.
  • Doc fixes against stale pages. The diff was rendered against a cached page. Fetch the live page at approval time and re-render if it changed.
  • Success measured on easy escalations. Choose the 20 so they include ones the docs don't answer. The right outcome there is a partial result and a doc fix, not an invented answer.

Practice · 150 min

  1. Pick 20 escalations: 12 the docs answer, 5 they answer badly (a doc fix is due), and 3 they don't answer at all. Write the expected outcome for each before running.
  2. Assemble the agent from your Phase 7 modules: plan, research, verify, draft, gated filing. Give every run a checkpoint thread and a Guards instance.
  3. Run all 20 with an approver that shows you each diff. Approve, edit or reject as you would for real, and let the audit log record it.
  4. Collect a RunRecord per run, then print the report and label correctness by hand.
  5. Run the three acceptance tests below and fix whatever fails.

Ship: 20 escalations run end to end, with success rate, cost and step counts reported, and every side effect traceable to an approval.

  • docpilot/research_agent.py: the assembled agent, with the plan, verify and gated-filing stages.
  • evals/escalations/: the 20 escalations with expected outcomes, and one RunRecord JSON per run.
  • audit.jsonl for the evaluation run, passing verify().
  • A report: success rate, partial count, median and maximum steps, mean and maximum cost per escalation, and your correctness labels.

Acceptance test
  1. No unapproved side effects. Run all 20 with an approver that rejects everything. The ticket store and docs repository are unchanged, and the report shows zero side effects.
  2. Crash safety. Kill three runs at random points, including once while an approval is pending, and resume them. Each finishes, and no reply or pull request is filed twice.
  3. Graceful degradation. Rerun with 20% fault injection (L84). Wrong answers do not rise; failures appear as partial with a reason.
