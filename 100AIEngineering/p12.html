Voice Agents: Speech-to-Text, Text-to-Speech and Realtime Models

50m video50m practice

A voice agent is a text agent with a hard real-time deadline. Users notice a pause of a second or more, so everything is about the time from the end of the user's speech to the first audio back. You meet that deadline by streaming every stage and by deciding well when the user has finished talking.

Cascaded pipelines and speech-to-speech models

There are two architectures. A cascaded pipeline chains three models: speech-to-text (STT) turns audio into a transcript, the LLM writes a text reply, and text-to-speech (TTS) speaks it. A speech-to-speech (realtime) model takes audio in and produces audio out in one model, usually over a persistent WebSocket or WebRTC session. Provider realtime APIs, such as OpenAI's Realtime API and Google's Gemini Live API (as of late 2026), are of this kind.

For DocPilot, the cascade wins by default. Retrieval, tools, guardrails (L100) and the eval suite (L95) all work on text, and you can swap in a realtime model later behind the same interface.

The latency budget

In conversation, people leave short gaps between turns. Stivers et al. (2009) studied ten languages and found that typical gaps cluster around roughly 200 ms. Listeners begin to read meaning into silences much longer than that. No production cascade gets close to 200 ms. Practitioner targets for voice-to-voice latency are usually quoted as "under about a second", with around 800 ms treated as good. Treat these as rules of thumb and set your own target from user tests.

Definition · voice-to-voice latency

The time from the end of the user's speech to the first audio the user hears. In a streaming cascade, each stage contributes its time to first output, not its total time:

$$T = t_{\text{endpoint}} + t_{\text{STT final}} + t_{\text{TTFT}} + \frac{w \cdot \tau}{r} + t_{\text{TTS first byte}} + t_{\text{transport}}$$

Here \(w\) is the number of words in the first speakable chunk, \(\tau\) is tokens per word (about 1.3 for English) and \(r\) is the decode rate in tokens per second.

from dataclasses import dataclass

@dataclass
class Stage:
    name: str
    ms: float

def decode_ms(words: int, tok_per_word: float = 1.3, tok_per_s: float = 80) -> float:
    """Decode time until `words` words of the reply exist."""
    return words * tok_per_word / tok_per_s * 1000

def report(label: str, stages: list[Stage], target_ms: float = 800) -> float:

    print(f"  total {t:.0f} ms vs target {target_ms:.0f} ms: {verdict}")
    return t

Streaming removes the two biggest bars: the whole reply and its whole synthesis. What remains is dominated by endpointing and time to first token, so the tuned plan attacks those with a turn-detection model, a small model and prompt caching (L24, L110).

Voice activity detection, endpointing and barge-in

Definition
  • VAD (voice activity detection): a small, fast classifier that labels each 10–30 ms audio frame as speech or not. Silero VAD and WebRTC's VAD are common open-source choices.
  • Endpointing: deciding that the user's turn is over. The simple rule is "N ms of silence after speech". A large N feels sluggish. A small N cuts people off when they pause mid-sentence ("my pod keeps… crashing"). Model-based turn detection looks at the words and asks whether the utterance sounds finished, which lets you use a shorter silence threshold safely.
  • Barge-in: the user starts talking while the agent is speaking, and the agent stops.
Algorithm · Handling barge-in
  1. While the agent's audio is playing, keep VAD running on the microphone. Only act after a minimum amount of speech (a few hundred ms, or STT words), so coughs and "mm-hm" do not trigger it.
  2. Stop playback at once and flush the client's audio buffer and the TTS queue.
  3. Cancel the in-flight LLM stream and any TTS requests still running.
  4. Truncate the assistant turn in the history to the text that was actually played, using per-chunk playback marks. Otherwise the model will think the user heard advice they never heard.
  5. Treat the new speech as the next user turn.

Streaming at every stage

Streaming STT emits interim hypotheses and a final transcript once the endpoint fires. Some systems start the LLM on a stable interim transcript and throw that work away if the final transcript differs. The LLM streams tokens (L3, L105), and TTS can start as soon as it has a clause. The piece in the middle is a chunker.

import re
from collections.abc import Iterable, Iterator

BOUNDARY = re.compile(r"[.!?;:](\s|$)|,\s")

def speakable_chunks(deltas: Iterable[str], min_words: int = 4,
                     max_words: int = 18) -> Iterator[str]:
    """Group streamed text deltas into chunks a TTS engine can start on."""
    buf = ""
    for delta in deltas:
        buf += delta
        while True:
            m = BOUNDARY.search(buf)
            words = len(buf.split())
            if m and len(buf[:m.end()].split()) >= min_words:
                cut = m.end()
            elif words >= max_words:
                cut = buf.rfind(" ")            # no punctuation yet: break at a space
            else:
                break
            chunk, buf = buf[:cut].strip(), buf[cut:]
            if chunk:
                yield chunk
    if buf.strip():
        yield buf.strip()

fake = ["Run kubectl", " describe pod", " on the failing pod, then", " check the Events",
        " section. If you see ImagePull", "BackOff, the image name is wrong."]
for c in speakable_chunks(fake):
    print(repr(c))
'Run kubectl describe pod on the failing pod,'
'then check the Events section.'
'If you see ImagePullBackOff,'
'the image name is wrong.'

In production the deltas are stream.text_stream from client.messages.stream(...). Leaving the with block closes the stream, which is how barge-in cancels generation. Give voice its own system prompt: short spoken sentences, no Markdown or code blocks. Normalise "kubectl", "etcd" and "v1.31" before TTS.

Transports, evaluation and frameworks

Telephony reaches users through SIP trunks or a carrier's media-stream WebSocket. The audio is narrowband (typically 8 kHz G.711 μ-law), which hurts STT, and the network adds latency you cannot remove. WebRTC carries Opus audio over UDP, with jitter buffers and browser echo cancellation. WebSockets over TCP are simpler but stall on packet loss. Without echo cancellation, the agent hears itself and interrupts itself.

Evaluate voice in layers. For STT, measure word error rate on your domain audio:

$$\text{WER} = \frac{S + D + I}{N}$$

where \(S\), \(D\) and \(I\) are word substitutions, deletions and insertions and \(N\) is the number of reference words. For latency, report p50 and p95 voice-to-voice, not averages. For turn-taking, count false endpoints, missed barge-ins and false barge-ins. For the task, run DocPilot's text evals on the transcripts. Simulated callers make this repeatable: scripted text goes through TTS into the agent, and a judge (L89) reads the transcript.

Frameworks. Pipecat (open source, started by Daily) models a voice app as a pipeline of processors that pass audio, text and control frames. An interruption is a frame that flushes everything downstream. LiveKit Agents runs your agent as a participant in a LiveKit WebRTC room, with plugins for STT, LLM, TTS and turn detection. Both handle the plumbing above, including buffering, cancellation and playback marks. Check their current docs for APIs.

What breaks in production
  • Reading Markdown aloud. "Asterisk asterisk step one" is what a text prompt sounds like through TTS. Voice needs its own prompt and a text normaliser.
  • History that includes unheard text. After barge-in, the model "remembers" saying things the user never heard. Truncate the turn to what was played.
  • Tail latency. A p50 of 800 ms with a p95 of 3 s feels broken. Keep connections warm and speak a short filler ("Let me check the docs") before slow tools.
  • Endpointing tuned in a quiet room. Background noise keeps VAD "in speech" and the agent never answers. Test with real phone audio and real noise.

  3. Run 20 spoken questions. Fill the calculator with your measured medians and report p50/p95 voice-to-voice.
  4. Implement barge-in with history truncation and test it by interrupting five answers.

Context Engineering for Long-Running Agents

50m video50m practice

Agents that work for hours usually fail on context before they fail on intelligence. Stale tool output fills the window, attention spreads thin, and every step pays again for every earlier step. Treat context as a budget. Load content just in time, keep durable state in files outside the window, and compact or isolate everything else.

Why long tasks break the window

Each model call re-reads the whole history. If the fixed prefix (system prompt and tools) is \(S\) tokens and each step adds \(c\) tokens, call \(i\) reads \(S + ic\) tokens.

Derivation · cumulative input tokens $$\sum_{i=0}^{N} (S + ic) \;=\; (N+1)\,S + c\,\frac{N(N+1)}{2}$$

The cost is quadratic in the number of steps. With \(S = 3{,}200\), \(c = 4{,}150\) (a 150-token tool call plus a 4,000-token search result) and \(N = 30\), that is \(31 \cdot 3{,}200 + 4{,}150 \cdot 465 = 2{,}028{,}950\) input tokens, and the last call reads 127,700. Prompt caching (L24) makes the repeated prefix cheaper but does not make it smaller. Accuracy also drops as context grows. L13 covered this "context rot".

Anthropic's engineering post "Effective context engineering for AI agents" (2025) puts it this way: context is a finite "attention budget" with diminishing returns, so the job is to find the smallest set of high-signal tokens that gets the task done. For long-horizon work it names three techniques: compaction, structured note-taking and sub-agent architectures. The rest of this lesson follows that outline, with numbers.

Just-in-time context and instruction files

Do not paste documents into the window in case they are needed. Keep lightweight identifiers instead: file paths, URLs, chunk IDs, saved queries. Then give the agent tools to load content when it decides to (L55, agentic RAG). A path like docs/tasks/debug-pods.md costs 10 tokens and carries meaning through its name and folder. The page behind it costs thousands. The post describes a hybrid as a practical default. A small set of always-loaded instructions goes in up front, and everything else is fetched on demand. Claude Code works this way: it loads CLAUDE.md at start and uses glob and grep to find the rest.

Project instruction files such as CLAUDE.md, or AGENTS.md (a convention several coding agents read), hold stable facts: build commands, conventions, where things live. Keep them short and current. They are paid for on every call.

Notes and progress files

An agent that writes its state to a file can lose its context window and carry on. That covers compaction, a crash, or a fresh session the next day. It pairs naturally with durable execution (L74) and long-term memory (L76).

# NOTES.md  (the agent owns this file; read it first, update it after each finding)

Ask for findings with sources, open questions and a single next step. A transcript-style log grows as fast as the context it was meant to replace. As of anthropic 1.13, the beta API also defines a client-side memory tool (memory_20250818). It has file commands (view, create, str_replace, insert, delete, rename) that your code executes against a directory you control.

Compaction and clearing old tool results

Definition
  • Tool-result clearing: replace old tool results with a short stub ("cleared; re-run the search if needed") and keep the call itself. The post calls it one of the safest, lightest-touch forms of compaction, because the agent can always fetch the content again.
  • Compaction: when the context passes a threshold, a model call summarises it. The summary should keep decisions, open issues and identifiers, and drop raw output. The agent then continues from the summary plus the most recent turns.

Beta names carry dates because they change, so check the docs. clear_at_least exists because any edit to old context invalidates the prompt cache from that point on. Clear in large batches so that each cache break buys a real saving.

Subagents as context isolation

A subagent gets a fresh window and one focused job, such as "find what the docs say about eviction priority". It can read 20,000 tokens and return a 300-token brief with sources. The lead agent's context only ever holds the briefs. This is the orchestrator–workers pattern (L73) used for context rather than parallelism. The cost is more calls, and detail the lead never sees. When a brief is wrong, the lead cannot tell. Have subagents return identifiers so that the lead can check a claim when it matters (L79).

Measuring context efficiency

A synthetic research task makes the trade-offs concrete. There are 30 searches, each returning 4,000 tokens with one needed fact. The script counts billed input tokens, peak context and how many facts are still reachable at the final call.

from dataclasses import dataclass, field

SYSTEM, STEP, RESULT, N = 3_200, 150, 4_000, 30   # tokens; N search steps

@dataclass
class Ctx:
    base: int = SYSTEM
    items: list = field(default_factory=list)     # (tokens, fact ids carried)
    billed: int = 0
    peak: int = 0
    calls: int = 0
    def size(self): return self.base + sum(t for t, _ in self.items)
    def facts(self): return set().union(*(f for _, f in self.items))
    def call(self):                               # a model call reads everything
        self.billed += self.size(); self.calls += 1; self.peak = max(self.peak, self.size())

def naive(c, i):
    c.items += [(STEP, set()), (RESULT, {i})]

def clear_old(c, i, keep=3, notes=False):
    c.items += [(STEP, set()), (RESULT, {i})] + ([(60, {i})] if notes else [])
    big = [k for k, (t, _) in enumerate(c.items) if t == RESULT]
    for k in big[:-keep]:
        c.items[k] = (25, set())                  # "[cleared: re-run search(...)]"

def compact(c, i, limit=60_000, summary=2_500):
    naive(c, i)
    if c.size() > limit:
        c.call()                                  # the summariser reads everything
        c.items = [(summary, c.facts())]          # optimistic: drops no facts

def subagent(c, i, sub):
    s = Ctx(base=1_600)                           # fresh window per search
    s.call(); s.items.append((STEP + RESULT, {i})); s.call()
    sub.billed += s.billed; sub.calls += 2; sub.peak = max(sub.peak, s.peak)
    c.items += [(STEP, set()), (300, {i})]        # the lead keeps a 300-token brief

def run(name, step, **kw):
    c, sub = Ctx(), Ctx(base=0)
    for i in range(N):
        c.call()
        step(c, i, sub) if step is subagent else step(c, i, **kw)
    c.call()                                      # final answer
    print(f"{name:<18}{c.calls + sub.calls:>6}{c.billed + sub.billed:>11,}"
          f"{max(c.peak, sub.peak):>9,}{len(c.facts()):>5}/{N}")

print(f"{'strategy':<18}{'calls':>6}{'input tok':>11}{'peak':>9}{'facts':>8}")
run("keep everything", naive)
run("clear old", clear_old)
run("clear old + notes", clear_old, notes=True)
run("compaction", compact)
run("subagents", subagent)
strategy           calls  input tok     peak   facts
keep everything       31  2,028,950  127,700   30/30
clear old             31    526,400   20,375    3/30
clear old + notes     31    554,300   22,175   30/30

The model is crude on purpose, and the facts column is a proxy, not a success rate. It assumes a perfect summariser and perfect briefs. Real compaction drops things, and a subagent can return a wrong brief. What it does show is the shape. Clearing plus notes, or subagents, cut input tokens by about 4× and peak context by about 6×. Subagents need three times as many calls, which adds latency unless they run in parallel. Measure task success with the agent evals from L91, and report input tokens per successful task, not tokens alone.

What breaks in production
  • Summaries that drop the one detail that mattered. An error message, a version number, a user constraint. Give the compactor explicit instructions about what to keep, and test it on transcripts where you know the answer.
  • Notes that rot. The agent writes notes but never reads them, or never deletes wrong findings. Make reading NOTES.md the first step of every session and every compaction.
  • Clearing what cannot be fetched again. A result from a non-idempotent tool, such as a ticket the agent created, must not be cleared unless its ID is written down somewhere.
  • Cache thrash. Editing early context on every call keeps invalidating the cache. That can cost more than doing nothing.

  4. Run baseline and refactored agents on all 10 tasks. Log input tokens from usage, peak context and pass/fail from your L91 checks.

Agent Skills: Packaging Reusable Capabilities

40m video45m practice

A skill is a folder of instructions, scripts and reference files that an agent loads only when a task needs it. Its one-line description is always in context; the rest stays on disk until the description matches. That lets you give an agent dozens of procedures without paying for them on every call.

What a skill is

Definition · Agent Skill

A directory with a SKILL.md file. The file starts with YAML front matter holding at least name and description, followed by Markdown instructions. Optional siblings include scripts/ (code the agent runs), reference documents and templates. As documented in late 2026, name is a short lowercase-hyphenated identifier (at most 64 characters) and description is at most 1,024 characters. Check the current spec for optional fields.

Anthropic introduced Agent Skills in October 2025 for Claude apps, Claude Code and the API, and later published the format as an open specification. Other agent tools have since announced support. Adoption varies, so check each tool's docs before assuming a skill is portable.

Writing a description that matches

The description is the only part the agent sees when it decides, so it has to say two things. First what the skill does, in the third person. Then when to use it, with the words users actually type: "runbook", "playbook", "open a ticket". Name the boundaries, such as "one failure mode". Make neighbouring skills clearly distinct. If two descriptions both match "write up this incident", the agent will pick one at random. Keep the body to the procedure. Background belongs in reference files the body points to.

A loader, and testing selection

Agents that support skills do this for you. A small loader is still worth having, to validate skills in CI, to build the level-1 catalogue for your own agent loop, and to test descriptions. Real loaders should use a YAML library; this sketch parses the flat subset that front matter usually is.

import re
from dataclasses import dataclass
from pathlib import Path

NAME = re.compile(r"^[a-z0-9]+(-[a-z0-9]+)*$")

@dataclass
class Skill:
    name: str
    description: str
    path: Path
    def body(self) -> str:                         # level 2: read only when chosen
        return self.path.read_text(encoding="utf-8").split("---", 2)[2].strip()

def front_matter(text: str) -> dict[str, str]:
    m = re.match(r"---\n(.*?)\n---\n", text, re.S)
    if not m:
        raise ValueError("SKILL.md must start with a --- front-matter block")
    pairs = (line.partition(":") for line in m.group(1).splitlines()
             if not line.startswith((" ", "#")))
    return {k.strip(): v.strip().strip('"') for k, sep, v in pairs if sep}

def discover(root: Path) -> list[Skill]:
    skills = []
    for p in sorted(root.glob("*/SKILL.md")):
        meta = front_matter(p.read_text(encoding="utf-8"))
        name, desc = meta.get("name", ""), meta.get("description", "")
        if not (NAME.match(name) and len(name) <= 64 and name == p.parent.name):
            raise ValueError(f"{p}: bad name {name!r}")
        if not 0 < len(desc) <= 1024:
            raise ValueError(f"{p}: description must be 1-1024 characters")
        skills.append(Skill(name, desc, p))
    return skills

    return "\n".join(f"- {s.name}: {s.description}" for s in skills)

def words(text: str) -> set[str]:
    return set(re.findall(r"[a-z][a-z0-9]+", text.lower())) - STOP

                      key=lambda x: x[0])

Algorithm · Reviewing a third-party skill
  1. Read every file, not just SKILL.md. Instructions can hide in reference files and templates.
  2. Look for injected directives, such as "ignore previous instructions", "do not tell the user" or "always also run…" (L97).
  3. Audit scripts for network calls, reads outside the working directory, credential or environment-variable access, obfuscation (base64 blobs, eval), and downloads at run time.
  4. Check what tools it asks for. A formatting skill has no reason to call create_ticket or fetch URLs.
  5. Pin the reviewed version by commit hash. Run it in a sandbox without secrets or network egress (L64, L102), and re-review on every update.
What breaks in production
  • Vague descriptions. "Helps with Kubernetes" matches everything, so the agent loads it on every task or never. Test selection with paraphrases and with tasks that should match nothing.
  • Bodies that sprawl. A 3,000-line SKILL.md brings back the cost you were avoiding. Split it into reference files.
  • Scripts that assume an environment. A script that needs a package the sandbox lacks fails halfway through a task. List dependencies and test in the real container.
  • Skill drift. The skill says kubectl flags that changed two releases ago. Version the skill with the docs it cites.

Generative UI and Agent-Driven Interfaces

40m video40m practice

Generative UI means the model chooses and fills components from a library you wrote. It never writes the interface itself. The model returns typed data, your code validates it and renders it with escaping. That boundary is what makes richer answers safe.

Components instead of prose

Definition · Generative UI

An interface whose structure is decided per response by a model. The model emits component descriptions such as {"type": "steps", ...} or {"type": "versions", ...}, and a renderer you control turns them into UI. There are two common routes:

  • Structured output. The whole answer is one schema-constrained object containing a list of components (L20). It is simple, and one validation covers the whole answer.
  • Tool calls that render. Each component is a tool (show_steps, show_version_table). The front end renders every tool_use block as it completes, and the tool result tells the model "rendered". It streams naturally and mixes with prose.

A component schema in Pydantic

from typing import Annotated, Literal
from pydantic import BaseModel, Field, field_validator

class Step(BaseModel):
    text: str = Field(max_length=400)
    command: str | None = None

class StepList(BaseModel):
    type: Literal["steps"]
    title: str
    steps: list[Step] = Field(min_length=1, max_length=12)

class Code(BaseModel):
    type: Literal["code"]
    language: Literal["bash", "yaml", "text"]
    code: str

class VersionRow(BaseModel):
    feature: str
    since: str = Field(pattern=r"^v1\.\d{1,2}$")
    state: Literal["alpha", "beta", "stable", "deprecated"]

class VersionTable(BaseModel):
    type: Literal["versions"]
    rows: list[VersionRow]

class Source(BaseModel):
    title: str
    url: str

    @field_validator("url")
    @classmethod
    def docs_only(cls, v: str) -> str:
        if not v.startswith("https://kubernetes.io/"):
            raise ValueError("sources must be https://kubernetes.io/ pages")
        return v

class Answer(BaseModel):
    summary: str
    components: list[Annotated[StepList | Code | VersionTable, Field(discriminator="type")]]
    sources: list[Source]

Pass Answer to client.messages.parse(..., output_format=Answer), or its JSON schema through output_config. In anthropic 1.13 the SDK's schema transform keeps types, enums and required fields. It moves constraints such as pattern, maxLength, const and the discriminator into field descriptions (checked locally against this model). The model sees those as hints, so Pydantic validation on the way back is the real gate.

Rules for rendering model output
  • Escape every string the model produced, every time. Never pass model text to innerHTML, dangerouslySetInnerHTML or a template's "safe" filter. Retrieved documents can carry markup the model repeats (L97).
  • Allow-list URL schemes and hosts. Escaping does not stop a javascript: link. If you render Markdown, run the HTML through a sanitiser and add a strict Content-Security-Policy.
  • Class names, styles and component types come from enums you defined, never from free text.
  • Buttons that act, such as "restart this deployment", go through the same approval path as any tool call (L78).

Streaming UI updates

Users should see something within a second (L105). With the tool-call route, each completed tool_use block is one finished component, so you can stream components as they arrive. With one big structured object, you either wait for the whole answer or parse partial JSON and render only components whose objects have closed. Show a skeleton for the component type as soon as its type field appears, and validate before replacing the skeleton with content.

Protocols between agents and front ends

When the agent runs on a server and the UI in a browser, they need an event protocol. It has to carry text deltas, tool-call start and end, state snapshots and diffs, approval requests and user actions coming back. As of late 2026 there are several open efforts. AG-UI (Agent–User Interaction protocol) defines a stream of typed events of this kind. MCP-based UI extensions (MCP-UI, and the MCP Apps extension) let an MCP server return an interactive UI resource that the host renders in a sandboxed iframe. These are young and still changing. Pick one only if your front end and agent framework already speak it. Otherwise a small typed SSE event schema of your own is fine, and the security rules above apply either way.

What breaks in production
  • Raw HTML injection. Someone adds "just render the Markdown" without a sanitiser, and a poisoned document turns into script in a user's session (OWASP LLM Top 10: improper output handling).
  • Schema drift. The front end adds a component the prompt never mentions, or the reverse. Generate the TypeScript types and the prompt's component list from the same Pydantic models.
  • Validation failures with no fallback. One bad field blanks the whole answer. Retry once with the error message, then fall back to rendering summary as plain text.
  • Untested rendering. Snapshot-test the renderer with hostile strings in every field.

Where the Field Is Heading: Open Problems in AI Engineering

40m video20m practice

The parts of this course that change fastest are model names and prices. The parts that change slowest are the open problems: long tasks fail by compounding error, open-ended work is hard to grade, agents with real permissions are hard to secure, and models do not learn from use. Know where those edges are, and keep learning through small experiments rather than headlines.

Reliability of long-horizon agents

Derivation · compounding step errors

Suppose each step of an \(n\)-step task succeeds independently with probability \(p\). Then the whole task succeeds with probability \(p^n\). If a checker catches a failed step with probability \(c\) and one retry then succeeds with probability \(p\), the per-step success becomes \(p' = p + (1-p)\,c\,p\).

$$P(\text{task}) = \big(p + (1-p)\,c\,p\big)^n$$

Independence is a simplification. Real errors cluster, and agents sometimes recover without help. The shape still holds: small per-step error rates dominate long tasks.

def task_success(p: float, n: int, catch: float = 0.0) -> float:
    """n independent steps; a checker catches a failed step with prob `catch`
    and one retry then succeeds with prob p."""
    step = p + (1 - p) * catch * p
    return step ** n

METR (Kwa et al., 2025) measured the length of tasks, in human working time, that frontier agents complete with 50% reliability. They reported that it had been doubling roughly every seven months over the period they studied. That is a measured trend, not a law. The paper discusses how its task suite differs from messy real work, and whether the trend continues is open. The engineering problems are open too: agents that notice their own mistakes, know when to stop and ask, and resume cleanly after failure (L77).

Evaluating open-ended work

Code-based checks (L88) need a known answer. A research report, a refactor or a support conversation has many acceptable answers and many subtle ways to be wrong. LLM judges help but carry biases you have to calibrate against humans (L89, L90). Human review is slow and expensive, and gets harder as outputs become longer and more expert. Public benchmarks saturate and leak into training data (L92). It is not settled how to grade work that is near or beyond the grader's own skill, sometimes called scalable oversight. In practice the best defence is still a domain-specific eval set you own and refresh.

Securing agents with real permissions

Prompt injection has no known general fix (L97). Simon Willison's "lethal trifecta" (2025) names the dangerous combination: access to private data, exposure to untrusted content, and a way to communicate externally. Current defences are architectural, not filters. You remove one leg of the trifecta, isolate untrusted content from the planner, as in the dual-LLM pattern and the CaMeL design (Debenedetti et al., 2025), and require approval for consequential actions (L98). They work by limiting what the agent can do, which is exactly the tension. More useful agents need more permissions. Fine-grained, auditable, revocable permissions for agents are an active design area in MCP and elsewhere (L102).

Cost curves and on-device models

Analyses such as Epoch AI's report that the price of reaching a fixed capability level has fallen steeply year on year. The rate varies a lot by task and period, so plan with your own measurements, not someone's trend line. Two consequences can be acted on today. Re-run your model-choice evals (L5) whenever a cheaper model appears, because a step that needed the large model last year may not now. And small open models, quantised, run on laptops and some phones (L116, L117). That opens up private, offline and zero-marginal-cost features, with routing between local and hosted models as the open design question.

Memory, continual learning and interoperability

Deployed models do not learn from use. What we call memory is retrieval over notes and summaries (L76, L126). It works, but deciding what to remember, when to forget, and how to keep personal memory private are unsolved product problems. Updating weights continually without degrading earlier skills (catastrophic forgetting) remains a research problem.

On interoperability, MCP (L66) became the common way to connect tools during 2025. Agent-to-agent protocols such as A2A (L80), the Agent Skills format (L127) and agent–UI protocols (L128) are younger. Several moved to neutral foundations, such as projects under the Linux Foundation, which tends to stabilise a standard but does not guarantee adoption. Build behind thin interfaces so that you can follow whichever ones win.

How to keep learning

A sustainable habit
  • Changelogs first. Provider release notes and SDK changelogs tell you what actually changed in the tools you use. Read them weekly; it takes 15 minutes.
  • Papers selectively. Read the abstract and figures of many and the full text of a few. Follow the references of the ones that matter to your system. Prefer papers with code and ablations.
  • Small experiments of your own. When a claim matters ("long context replaces RAG", "this model is better at tools"), test it on your eval set in an afternoon. Keep a lab notebook: hypothesis, setup, result, decision.
  • Write it down. A short public write-up of each experiment builds the judgement that headlines cannot.
What breaks in production
  • Shipping autonomy past your reliability. A 40-step workflow at 98% per step succeeds less than half the time. Add checkpoints and human approval before adding steps.
  • Trusting a headline number. A vendor's benchmark gain may not show up on your tasks. Re-run your own evals before switching.
  • Waiting for next year's model. "The model will get better" is not a mitigation for an injection path or a missing eval.
  • Framework churn. Rewriting the stack for every new framework costs more than the framework saves. Change only when an eval shows a gain.

Write the eval set first

Algorithm · A 100-item eval set in two hours
  1. Collect 30 or more real or realistic tasks: tickets, forum questions, your own past searches. Real items find the problems synthetic ones miss (L87).
  2. Expand to 100 with targeted synthetic items: 50 core, 20 edge (ambiguous, version-specific, no-answer-in-corpus), 10 multi-step, 10 out-of-scope and 10 adversarial (injection in a document, data-exfiltration attempts, L99).
  3. For each item, write what a grader needs: a reference answer or key facts, the source chunks that must be retrieved, the expected tool calls, or "must refuse".
  4. Hold out 25–40% as a test split. Iterate only on dev. Touch test once per milestone.
  5. Have someone else label 20 items blind and compare. Disagreements show where the spec is vague.

from pydantic import BaseModel, Field, ValidationError, model_validator

class EvalItem(BaseModel):
    id: str = Field(pattern=r"^ev-\d{3}$")
    kind: Kind
    question: str = Field(min_length=10)
    reference: str | None = None          # expected answer or key facts
    source_ids: list[str] = []            # chunks that must be retrieved
    expected_tools: list[str] = []        # e.g. ["search", "create_ticket"]
    must_refuse: bool = False
    split: Literal["dev", "test"]

    @model_validator(mode="after")
    def gradeable(self):
        if not (self.reference or self.must_refuse or self.expected_tools):
            raise ValueError("nothing to grade against")
        if self.kind in ("out_of_scope", "adversarial") and not self.must_refuse:
            raise ValueError(f"{self.kind} items must expect a refusal")
        return self

def coverage(items: list[EvalItem]) -> list[str]:
    problems = []
    if len({i.id for i in items}) < len(items):
        problems.append("duplicate ids")
    if len({i.question.strip().lower() for i in items}) < len(items):
        problems.append("duplicate questions")
    have = Counter(i.kind for i in items)
    problems += [f"{k}: {have[k]}/{n}" for k, n in TARGET.items() if have[k] < n]
    test = sum(i.split == "test" for i in items) / len(items)
    if not 0.25 <= test <= 0.40:
        problems.append(f"test split {test:.0%}, want 25-40%")
    return problems

Architecture and risk review

Definition · Threat model, capstone size

A table with one row per threat: asset (what could be harmed), entry point (which marked arrow), threat, likelihood and impact, mitigation, and the eval item IDs that test it. Start from L96.   • An eval set written after the system. It ends up testing what the system already does. Writing items first is the point.
  • Success criteria without thresholds. "Accurate and fast" cannot fail, so it cannot guide a decision.
  • Threats with no tests. A mitigation nobody tests is a hope. Link each threat row to eval IDs.

Wiring the components, with a trace for every request

Keep the pipeline a plain function whose dependencies are passed in. Production passes docpilot.search.search and docpilot.tools.run_tools. Tests pass fakes, so you can test the wiring, the guards and the trace without calling a model.

import time, uuid
from contextlib import contextmanager

TOOLS = [{"name": "search", "description": "Search the Kubernetes docs. Returns chunks with ids and URLs.",
          "input_schema": {"type": "object", "properties": {"query": {"type": "string"},
                           "k": {"type": "integer"}}, "required": ["query"]}}]
REFUSAL = "I can only help with Kubernetes and DocPilot questions."
FALLBACK = "I could not produce a cited answer. Here are the closest docs pages instead."

class Tracer:
    """Minimal span recorder; in the app these become OpenTelemetry spans (L106)."""
    def __init__(self):
        self.spans, self.depth = [], 0

    @contextmanager
    def span(self, name: str, **attrs):
        rec = {"name": name, "depth": self.depth, **attrs}
        self.spans.append(rec)
        self.depth, t0 = self.depth + 1, time.perf_counter()
        try:
            yield rec
        finally:
            rec["ms"], self.depth = round((time.perf_counter() - t0) * 1000, 1), self.depth - 1

def answer(q: str, *, search, run_tools, guard_in, check_out, tracer: Tracer) -> dict:
    with tracer.span("request", trace_id=uuid.uuid4().hex[:8]):
        with tracer.span("guard.input") as g:
            g["verdict"] = guard_in(q)
        if g["verdict"] != "allow":
            return {"refused": True, "answer": REFUSAL, "steps": []}

        def search_tool(query: str, k: int = 5) -> list[dict]:
            with tracer.span("tool.search", query=query) as t:
                hits = search(query, k=k)
                t["hits"] = len(hits)
                return [{"id": h.id, "text": h.text, "url": h.url} for h in hits]

        with tracer.span("agent") as a:
            msg, steps = run_tools([{"role": "user", "content": q}], tools=TOOLS,
                                   handlers={"search": search_tool})
            a["steps"], a["stop"] = len(steps), msg.stop_reason
        text = "".join(b.text for b in msg.content if b.type == "text")
        with tracer.span("guard.output") as o:
            o["ok"] = check_out(text, steps)
        return {"refused": False, "answer": text if o["ok"] else FALLBACK, "steps": steps}

Improvement comes from reading failures, not from trying ideas. Today runs two loops of error analysis followed by one targeted change each, measured on dev. Error analysis

Algorithm · From failures to a ranked fix list
  1. Open every failed dev item from yesterday's run, with its trace. Write one line saying what went wrong, in your own words. Do not pick categories yet.
  2. Group the lines into failure classes: retrieval miss, right chunk but wrong answer, missing citation, wrong tool or arguments, refused when it should not have, loop or budget hit. Use L52's playbook to locate the stage.
  3. Count each class and estimate the cost of a fix. Rank by count ÷ effort.
  4. For the top class, write a hypothesis that predicts which items will flip: "Adding the doc version to chunk metadata and filtering on it fixes the 6 version-mismatch items."

Two improvement iterations, measured properly

Pass rates on 30 or 70 items are noisy. Compare runs paired on the same items. Count what was fixed and what broke, and put a confidence interval on the change (L93).

import random

def paired_bootstrap(before: list[int], after: list[int], n: int = 10_000, seed: int = 0):
    """Change in pass rate with a 95% CI, resampling the same items for both runs."""
    rng, k = random.Random(seed), len(before)
    d = [a - b for a, b in zip(after, before)]
    means = sorted(sum(d[rng.randrange(k)] for _ in range(k)) / k for _ in range(n))
    return sum(d) / k, means[int(0.025 * n)], means[int(0.975 * n) - 1]

def compare(name: str, before: list[int], after: list[int]) -> None:
    fixed = sum(b == 0 and a == 1 for b, a in zip(before, after))
    broke = sum(b == 1 and a == 0 for b, a in zip(before, after))
    mean, lo, hi = paired_bootstrap(before, after)
    print(f"{name:<9} {sum(before)}/{len(before)} -> {sum(after)}/{len(after)}"
          f"  fixed {fixed:>2}, broke {broke}  change {mean:+.2f}  95% CI [{lo:+.2f}, {hi:+.2f}]")

def scenario(n: int, passing: int, fixed: int, broke: int) -> tuple[list[int], list[int]]:
    before = [1] * passing + [0] * (n - passing)
    after = before.copy()
    for i in range(passing, passing + fixed):
        after[i] = 1
    for i in range(broke):
        after[i] = 0
    return before, after

Reading the numbers

A 13-point gain on 30 test items has an interval that reaches zero. On the test split alone you cannot rule out "no change". Report it that way. Pair it with the dev result and with the per-item story ("5 version-mismatch items fixed, 1 regression in a multi-step item"). Do not claim a precise gain. For larger effects, or to detect smaller ones, you need more items, which is a good "next step" for the write-up.

Load and cost testing

Definition · What a load test must report

At a stated concurrency and request mix, report the p50, p95 and p99 latency, the error rate split by cause (timeouts, 429s, 5xx), retries per request, and tokens and cost per request and per successful task. Also confirm that the budget alert and rate limits actually trigger.

That flushes out connection-pool limits, missing timeouts and blocking calls in async handlers (L107). Then run a short, budget-capped test against the real provider at expected peak, with a load tool such as Locust or k6. Check that retries back off, that the fallback model engages (L108), and that the cost per request matches your L109 estimate within reason.
