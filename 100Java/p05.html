Concurrency & Multithreading

Thirty-two lessons on writing Java that is correct when many threads run it at once: the memory model that decides what each thread can see, the locks, atomics and concurrent collections built on it, and the executors, futures and virtual threads that backend services actually run on. It builds on the language, collections and lambdas of Phases 1–4, and everything after it (the JVM internals of Phase 6, every Spring request thread, every Kafka consumer) assumes it. The phase ends by building a bounded, instrumented, back-pressured job-processing engine with tests that prove it under load.

By the end of this phase you can

  • Explain a visibility or ordering bug in terms of happens-before edges, and fix it with the right tool: confinement, immutability, volatile, an atomic, or a lock.
  • Reproduce a lost update, a check-then-act race and a lock-ordering deadlock on demand, and find each one in a thread dump.
  • Choose between synchronized, ReentrantLock, read-write and stamped locks, and atomics or LongAdder, and justify the choice with a measurement.
  • Configure a ThreadPoolExecutor from scratch: size it from measured wait/compute ratios, bound its queue, pick a rejection policy, monitor it, and shut it down within a deadline.
  • Compose non-blocking service calls with CompletableFuture, with per-call timeouts and fallbacks, and without losing exceptions or logging context.
  • Handle interruption and cancellation correctly at every layer, from a worker loop up to an executor shutdown triggered by SIGTERM.
  • Decide when virtual threads, fork/join or a classic pool fits a workload, and test concurrent code deterministically rather than hoping it passes.

L121 · DAY 121

Concurrency vs Parallelism, Processes vs Threads

40m video30m practice

Concurrency is a property of how a program is structured (several tasks in progress at once); parallelism is a property of how it runs (several instructions executing at the same instant on different cores). In Java both are built from threads, and threads share one heap, which is exactly what makes them cheap to coordinate and easy to get wrong.

Dealing with many things vs doing many things

Rob Pike's phrasing is the one to remember: concurrency is dealing with lots of things at once, parallelism is doing lots of things at once. A web server on a single core is concurrent (it interleaves hundreds of requests, switching whenever one waits for the network) but not parallel, because only one instruction stream executes at any instant. A parallel merge sort on 16 cores is parallel.

Processes, threads and what each one owns

A process is an OS-level container: its own virtual address space, file descriptors, and security context. Two processes cannot read each other's memory, so they talk through inter-process communication: pipes, sockets, shared-memory segments, signals, or a database. A thread is a schedulable instruction stream inside a process; all threads of a process see the same address space. One JVM is one OS process, and in HotSpot every platform java.lang.Thread is backed one-to-one by an OS thread.

Definition · shared mutable state

A variable is shared if more than one thread can access it, and mutable if its value can change after construction. Every concurrency bug in this phase requires both. A local int is neither; a final field pointing at an immutable record is shared but not mutable; a non-final field of a singleton bean is both.

Scheduling, time slices and context switches

The OS scheduler decides which runnable threads occupy the cores. It is preemptive: a thread runs for a time slice of a few milliseconds, or until it blocks, and is then switched out. A context switch saves one thread's registers and program counter and loads another's. The direct cost is roughly 1–10 µs on current hardware; the indirect cost (cold caches and TLB for the incoming thread) is often larger. Switches are voluntary (the thread blocked) or involuntary (its slice expired). vmstat 1 shows the system-wide rate in the cs column; pidstat -w splits it per thread.

CPU-bound vs I/O-bound work

A CPU-bound task (JSON parsing, image resizing, hashing) is limited by instructions; it can use at most one core per thread, so running more threads than cores only adds switching. An I/O-bound task (calling a database, another service, a disk) spends most of its time waiting, holding no core at all; to keep the cores busy you need many more tasks in flight than you have cores. These two shapes need different pools (L138 gives the sizing formula) and, for I/O, cheaper threads (virtual threads, L150).

import java.util.concurrent.*;

public class BoundDemo {
    static volatile long sink;                          // keeps the JIT from deleting the loop

    static void burnCpu() {
        long x = 0;
        for (long i = 0; i < 300_000_000L; i++) x += i % 7;
        sink = x;
    }

    static void waitIo() {
        try { Thread.sleep(200); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    static void time(String label, int threads, int tasks, Runnable task) {
        long t0 = System.nanoTime();
        try (var pool = Executors.newFixedThreadPool(threads)) {
            for (int i = 0; i < tasks; i++) pool.execute(task);
        }                                               // close() waits for every task (Java 19+)
        System.out.printf("%-3s threads=%3d  %6d ms%n", label, threads, (System.nanoTime() - t0) / 1_000_000);
    }

    public static void main(String[] args) {
        int cores = Runtime.getRuntime().availableProcessors();
        for (int t : new int[] {1, cores, cores * 8}) time("cpu", t, cores * 2, BoundDemo::burnCpu);
        for (int t : new int[] {1, cores, cores * 8}) time("io", t, cores * 8, BoundDemo::waitIo);
    }
}

The CPU rows stop improving at threads = cores; the I/O rows keep improving until every task has its own thread.

Three laws for reasoning about speed-up and size

Theorem · Amdahl's law

If a fraction p of the work parallelises perfectly and 1 − p is serial, the speed-up on N cores is S(N) = 1 / ((1 − p) + p / N), which can never exceed 1 / (1 − p). With p = 0.95: S(8) ≈ 5.9, S(64) ≈ 15.4, and no number of cores beats 20×.

Theorem · Gustafson's law

If the problem grows with the machine, and s is the serial fraction measured on the N-core run, the scaled speed-up is S(N) = N − s(N − 1). With s = 0.05 and N = 64 that is about 60.9. Amdahl fixes the problem size; Gustafson fixes the time budget, which is closer to how backend throughput scales.

Theorem · Little's law

In any stable system, L = λ × W: the average number of requests in the system equals the arrival rate times the average time each spends inside. It needs no assumption about distributions.

Worked example · sizing with Little's law

A service receives λ = 800 requests/s and each takes W = 250 ms end to end. Then L = 800 × 0.25 = 200 requests are in flight on average, which in thread-per-request style means 200 busy threads: exactly Tomcat's default server.tomcat.threads.max. If a downstream dependency slows so that W becomes 1 s, L jumps to 800. The pool saturates and requests queue: a slow dependency exhausts threads while the CPU sits idle.

Why a backend engineer meets concurrency on day one

A servlet container serves each request on a thread from its pool (named like http-nio-8080-exec-17). Spring beans are singletons by default, so one instance of every @Service is shared by all of those threads at once. You are writing multithreaded code the moment you add a field to a bean, whether you meant to or not.

// Deliberately broken: imagine this class is a Spring @Service singleton.
class QuoteService {
    private int served;                                        // shared, mutable, unguarded
    private final java.text.SimpleDateFormat fmt =
        new java.text.SimpleDateFormat("yyyy-MM-dd");          // not thread-safe either

    String quote(java.util.Date d) {
        served++;                                              // lost updates (L126)
        return fmt.format(d) + " #" + served;                  // can corrupt output under load
    }
}
What breaks in production
  • More threads for CPU work. A pool of 200 threads doing CPU-bound work on 4 cores runs no faster than 4 threads and adds switching, cache misses and memory. Measure before you add threads.
  • Hidden serial fractions. One synchronized logger, a single shared connection, a global cache lock: each puts a hard Amdahl ceiling on the whole service, however many cores the pod has.
  • Containers. availableProcessors() follows cgroup CPU limits (container support has been on by default since JDK 10), so a pod limited to 2 CPUs reports 2 even on a 64-core node. Pools sized from it shrink accordingly; pools hard-coded for a laptop do not.
  • Little's law ignored. A thread pool sized for normal latency is undersized for degraded latency. Size for the W you will see during an incident, or bound it and fail fast (L139).

Creating Threads: Thread, Runnable & Good Hygiene

40m video45m practice

A Runnable is a task; a Thread is the machinery that runs one. Keep the two separate, start threads with start(), and give every thread a name and an exception handler, because the thread dump and the error log are the only places you will ever see it again.

Runnable wins over extends Thread

There are two ways to put code on a new thread: subclass Thread and override run(), or pass a Runnable to a Thread. Prefer the second, for four reasons:

  • Separation of task and mechanism. A Runnable can run on a raw thread today and on an executor, a virtual thread or a test's calling thread tomorrow without changing a line.
  • Single inheritance. Extending Thread spends your only superclass on plumbing.
  • Smaller surface. A Thread subclass inherits dozens of public methods (interrupt, setDaemon, join…) that callers can poke at; a Runnable has one.
  • Lambdas. Runnable is a functional interface, so the task is usually one expression.
Runnable task = () -> System.out.println("running on " + Thread.currentThread().getName());

Thread t = new Thread(task, "worker");
t.run();     // prints "running on main": an ordinary method call on the current thread
t.start();   // prints "running on worker": a new thread calls run()
t.join();
t.start();   // IllegalThreadStateException: a Thread object can be started only once

start() vs run(): the most common beginner bug

run() is just a method. Calling it executes the task synchronously, on your stack, and nothing concurrent happens; code that "works" this way is silently single-threaded. start() asks the JVM to create an OS thread, give it its own stack, and have that thread call run(). start() returns immediately, and from then on the two threads race. Thread.currentThread() always returns the thread executing the current line, which is how you tell the cases apart in a log.

Names, factories and the Thread.Builder API

An unnamed thread is called Thread-7, and a thread from an unconfigured pool is pool-3-thread-12. In a thread dump with 400 threads, those names tell you nothing about which subsystem is stuck. Name every thread after its job (invoice-export-2), and do it in one place: a ThreadFactory, which executors call whenever they need a thread (L137). Java 21's Thread.Builder builds one in a single expression; before 21 you write a small class.

import java.util.concurrent.ThreadFactory;
import java.util.concurrent.atomic.AtomicInteger;

public final class NamedThreadFactory implements ThreadFactory {
    private final String prefix;
    private final boolean daemon;
    private final AtomicInteger seq = new AtomicInteger();

    public NamedThreadFactory(String prefix, boolean daemon) {
        this.prefix = prefix;
        this.daemon = daemon;
    }

    @Override
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r, prefix + "-" + seq.getAndIncrement());
        t.setDaemon(daemon);                         // must be set before start() (L125)
        t.setPriority(Thread.NORM_PRIORITY);         // don't inherit an odd priority from the creator
        t.setUncaughtExceptionHandler((th, e) ->
            System.err.println(th.getName() + " died: " + e));
        return t;
    }

    // Java 21+: the same factory from the builder
    public static ThreadFactory modern(String prefix) {
        return Thread.ofPlatform().name(prefix + "-", 0).daemon(false).factory();
    }
}

What happens to an exception thrown in a thread

Definition · uncaught exception dispatch

If run() throws, the exception unwinds that thread's stack only. The thread terminates, and the JVM calls t.getUncaughtExceptionHandler().uncaughtException(t, e). That returns the thread's own handler if one was set, otherwise its ThreadGroup, which forwards to the parent group and finally to Thread.getDefaultUncaughtExceptionHandler(). If no default handler is installed, the message Exception in thread "name" and the stack trace go to System.err. No other thread is affected, and the JVM keeps running while any non-daemon thread is alive.

So the failure of a worker is not an error of the program; it is a quiet disappearance. A consumer thread that dies leaves its queue filling up, and the first symptom is an out-of-memory error an hour later. Install a default handler at startup that logs at ERROR level (and, in a service, increments a metric), and set per-thread handlers where a subsystem needs to react, for example by restarting its worker.

public class Crash {
    public static void main(String[] args) throws InterruptedException {
        Thread.setDefaultUncaughtExceptionHandler((t, e) ->
            System.err.printf("[default] %s died: %s%n", t.getName(), e));

        Thread bad = Thread.ofPlatform().name("parser-0")
            .unstarted(() -> { throw new IllegalStateException("bad input"); });
        bad.start();
        bad.join();
        System.out.println("main is fine; parser-0 is " + bad.getState());   // TERMINATED
    }
}
Executors change the rules

A task given to executor.execute(r) that throws kills its worker thread, reaches that thread's handler, and the pool replaces the worker. A task given to submit(r) never reaches any handler: the exception is caught and stored in the returned Future, and if nobody calls get() it is lost. L137 covers this trap.

Why raw threads disappear after L137

Raw threads are unbounded (each new Thread costs an OS thread and, by default, a stack reservation of about 1 MB), have no queue, no reuse, and no lifecycle management. From L137 onwards you hand tasks to executors and let a configured ThreadFactory create threads; from L150, virtual threads make one-thread-per-task cheap again. What carries over is everything in this lesson: tasks as Runnables, names, and handlers.

What breaks in production
  • Calling run(). Tests pass, the code is single-threaded, and the "parallel" batch job takes eight times longer than planned.
  • Silent worker death. No uncaught-exception handler, no log, no metric: a background consumer is gone and nothing notices until a queue or a disk fills.
  • Starting a thread in a constructor. If the new thread's Runnable captures this, it may see the object before the constructor finishes (an escaped this; L128). Construct first, then call a separate start() method.
  • Anonymous names. pool-7-thread-3 in a deadlock report costs an incident team the first twenty minutes.

L123 · DAY 123

Thread Lifecycle, States & Scheduling

35m video35m practice

Thread.State has six values, and each one tells you something precise about why a thread is not making progress. Reading them correctly, especially BLOCKED vs WAITING and the fact that RUNNABLE includes "stuck in a socket read", is most of what thread-dump analysis is.

The six states

Definition · the six thread states
  • NEW: constructed, start() not yet called.
  • RUNNABLE: executing in the JVM or ready to, waiting only for a core. A thread blocked inside a native call, such as a socket read, is also reported RUNNABLE: the JVM cannot see why native code is not returning.
  • BLOCKED: waiting to acquire an intrinsic monitor, that is, to enter a synchronized block or method, or to re-enter one after wait() returns.
  • WAITING: waiting indefinitely for another thread to act: Object.wait(), Thread.join(), LockSupport.park().
  • TIMED_WAITING: the same with a deadline: Thread.sleep(ms), wait(ms), join(ms), parkNanos, parkUntil.
  • TERMINATED: run() returned or threw.

RUNNABLE deliberately merges "running" and "ready". The JVM does not know whether the OS has the thread on a core at this instant, and by the time you printed the answer it would be stale anyway. If you need to know whether a RUNNABLE thread is burning CPU, look at the cpu= figure in a thread dump twice, a few seconds apart.

Exact transitions

Two facts from the diagram trip people up. First, the java.util.concurrent locks, queues and latches are all built on LockSupport.park (L132), so a thread queued on a ReentrantLock or a BlockingQueue.take() is WAITING or TIMED_WAITING, and only synchronized contention produces BLOCKED. Second, states only move forward through TERMINATED: a thread object cannot be restarted.

Observing states: getState() and jstack

public class States {
    public static void main(String[] args) throws InterruptedException {
        Object lock = new Object();
        Thread sleeper = new Thread(() -> pause(2_000), "sleeper");
        Thread joiner  = new Thread(() -> awaitEnd(sleeper), "joiner");
        Thread blocked = new Thread(() -> { synchronized (lock) { } }, "blocked");
        System.out.println("sleeper " + sleeper.getState());          // NEW

        synchronized (lock) {                                         // main owns the monitor
            sleeper.start(); joiner.start(); blocked.start();
            Thread.sleep(300);                                        // demo only: let them settle
            System.out.println("sleeper " + sleeper.getState());      // TIMED_WAITING
            System.out.println("joiner  " + joiner.getState());       // WAITING
            System.out.println("blocked " + blocked.getState());      // BLOCKED
        }
        blocked.join();
        joiner.join();
        System.out.println("sleeper " + sleeper.getState());          // TERMINATED
    }

    static void pause(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    static void awaitEnd(Thread t) {
        try { t.join(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

The sleep(300) makes the demo very likely, not guaranteed, to print the states shown. Sleep is never a correctness mechanism; L152 replaces it with latches.

Scheduling: preemption, priorities, spinning

Platform threads are scheduled by the OS, preemptively: the JVM does not decide who runs next. setPriority passes a hint that the OS may ignore; on Linux, HotSpot ignores Java priorities by default, so code must never depend on them for correctness (L125). Thread.yield() is likewise a hint (L124).

Spin-wait hints (Java 9+)

A busy-wait loop such as while (!ready) Thread.onSpinWait(); tells the JVM it is spinning, and on x86 the JIT emits a PAUSE instruction, which saves power and frees resources for the sibling hyper-thread. It does not make spinning a good idea: it is only sensible for waits expected to last well under a context-switch time, inside low-level libraries. The flag must also be volatile or the loop may never see the change (L129).

From green threads to virtual threads

Java 1.1 on Solaris used green threads: threads scheduled by the JVM in user mode on a single OS thread. They were cheap but could not use multiple cores, and one blocking system call froze them all. Java 1.3 moved to native 1:1 threads, which bought parallelism at the cost of an OS thread per Java thread. Java 21's virtual threads return to user-mode scheduling, but M:N: many virtual threads multiplexed onto a small pool of OS carrier threads, with blocking calls redirected so that only the virtual thread waits. L150 explains how; the six states above still apply to them.

What breaks in production
  • "All threads are RUNNABLE, so the app is busy." A pool of threads all RUNNABLE in SocketInputStream.read (or NioSocketImpl.read) is idle-waiting on a slow downstream with no timeout. Check stacks and CPU time, not states alone.
  • Hunting for BLOCKED to find lock contention. Contention on ReentrantLock appears as WAITING (parking) with AbstractQueuedSynchronizer frames. Search for the lock, not the state.
  • Using getState() or isAlive() for coordination. These race with the thread itself. Coordinate with join, latches or futures.

L124 · DAY 124

join, sleep, yield, interrupt & Interruption Policy

45m video45m practice

Java has no safe way to stop a thread from outside; it has a way to ask. Interruption is that request, and it only works if every layer of code honours it: blocking methods throw InterruptedException, and your code either propagates it or restores the flag. Swallowing it breaks cancellation for everyone above you.

sleep, join and yield

  • Thread.sleep(ms) (or sleep(Duration), Java 19+) moves the current thread to TIMED_WAITING. It keeps every lock it holds: sleeping inside synchronized blocks every other thread that needs that monitor for the whole nap. Contrast Object.wait(), which releases the monitor (L134).
  • t.join() waits until t terminates; join(0) also means "forever". join(ms) returns when the time is up whether or not t finished, so check t.isAlive() afterwards, or use join(Duration), which returns true only if the thread ended. Everything t did happens-before join returns (L128), so you may read its results without further synchronization.
  • Thread.yield() hints that the current thread is willing to give up its core. The scheduler may ignore it, and its effect varies by OS. Code that needs yield to be correct is broken; code that uses it for performance should be benchmarked on the target platform.

The interrupt flag

Definition · interruption

Every thread has a boolean interrupt status. t.interrupt() sets it. t.isInterrupted() reads it without changing it. The static Thread.interrupted() reads the current thread's flag and clears it. Blocking methods that declare InterruptedException (sleep, wait, join, BlockingQueue.take, Future.get, CountDownLatch.await…) check the flag on entry and while blocked; when it is set they clear it and throw.

InterruptedException: the two correct responses

An InterruptedException means "the owner of this thread wants you to stop what you are doing". It is not an error, and it is not yours to discard, because the code that called you (an executor shutting down, a request timing out) may be waiting for this thread to notice. There are exactly two correct responses:

  1. Propagate. Declare throws InterruptedException and let the caller decide. This is right for library and service code that is not the thread's top-level loop.
  2. Restore and exit. If you cannot throw (inside Runnable.run, say), catch it, call Thread.currentThread().interrupt() so code further up can still see the request, and stop the current activity promptly.
// Deliberately broken: the cancellation request is destroyed.
try {
    Thread.sleep(1_000);
} catch (InterruptedException e) {
    // ignored: the flag is now false and nobody above us will ever know
}

The only code entitled to swallow an interruption is code that owns the thread and has decided what interruption means for it, typically the top-level loop of a worker you wrote, which exits.

An interruptible worker loop

import java.time.Duration;
import java.util.concurrent.*;

public class InterruptDemo {
    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<String> inbox = new LinkedBlockingQueue<>();
        Thread worker = Thread.ofPlatform().name("poller").start(() -> poll(inbox));
        inbox.put("a");
        inbox.put("b");
        Thread.sleep(100);
        worker.interrupt();                                   // ask, don't force
        boolean ended = worker.join(Duration.ofSeconds(5));   // Java 19+
        System.out.println("stopped cleanly: " + ended);
    }

    static void poll(BlockingQueue<String> inbox) {
        try {
            while (!Thread.currentThread().isInterrupted()) { // catches interrupts between messages
                String msg = inbox.take();                    // catches interrupts while idle
                System.out.println("handled " + msg);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();               // response 2: restore, then fall out
        } finally {
            System.out.println("poller cleaning up");         // release resources here
        }
    }
}

Blocking calls that ignore interrupts

Not every blocking call listens. A read on a classic java.net.Socket in a platform thread ignores interrupt(); the standard workaround is to close the socket from another thread, which makes the read throw SocketException. (Virtual threads are an exception: interrupting one blocked in socket I/O closes the socket and unblocks it.) NIO channels implement InterruptibleChannel and do respond, by closing the channel, which surprises code that expected to keep using it. Monitor entry never responds; ReentrantLock.lockInterruptibly does (L132). In practice the robust answer is timeouts on everything: socket and HTTP timeouts, poll(timeout) instead of take(), get(timeout) instead of get().

Cooperative cancellation with a volatile flag, and its limits

class Ticker implements Runnable {
    private volatile boolean running = true;     // volatile: the write in stop() must be visible here

    void stop() { running = false; }

    @Override public void run() {
        while (running) {
            tick();                              // fine while tick() never blocks
        }
    }

    private void tick() { /* short, non-blocking work */ }
}

A volatile stop flag (L129) works when the loop body is short and never blocks. Once the body calls take() or sleep(), the thread can sit there indefinitely without re-reading the flag. The flag is also private to your class: an executor's shutdownNow() knows nothing about it and calls interrupt(). Prefer interruption as the cancellation mechanism, and if you keep a flag for clarity, set it and interrupt.

What breaks in production
  • Swallowed interrupts. shutdownNow() returns, the pool reports terminated after the timeout expires, yet a worker that ate its InterruptedException keeps running and holds the JVM open at shutdown.
  • Wrapping without restoring. catch (InterruptedException e) { throw new RuntimeException(e); } propagates the exception but loses the flag. Call Thread.currentThread().interrupt() first.
  • Sleeping while holding a lock. A retry loop that sleeps inside synchronized serializes every caller behind the sleep.
  • Interrupting a thread you don't own. Interrupting a pool worker that has moved on to another task cancels the wrong work. Cancel through the owner: Future.cancel(true) (L141) or shutdownNow().

Daemon Threads, Priorities & Shutdown Hooks

30m video30m practice

The JVM exits when its last non-daemon thread ends, and at that moment daemon threads simply stop, mid-instruction, with no finally blocks. Graceful shutdown is therefore something you build: non-daemon workers for work that matters, and a shutdown hook that drains them when the orchestrator sends SIGTERM.

Daemon vs user threads and JVM exit

Definition · daemon thread

A thread is either a user (non-daemon) thread or a daemon thread. The JVM keeps running while at least one user thread is alive. When the last one terminates (or System.exit is called, or the process receives SIGINT, SIGTERM or SIGHUP), the JVM runs its shutdown hooks and halts. Daemon threads still alive at that point are abandoned: their stacks are not unwound and their finally blocks never execute.

A new thread inherits daemon status from the thread that creates it, so threads made by main are user threads unless you say otherwise. setDaemon must be called before start(); afterwards it throws IllegalThreadStateException. Virtual threads are always daemon threads, and asking for a non-daemon one throws IllegalArgumentException. The JVM's own housekeeping threads (GC, JIT compiler, Reference Handler) are daemons too.

When daemon threads are right, and when they lose data

  • Appropriate: work that can be abandoned at any instant without harm, such as refreshing an in-memory cache, sampling metrics, or watching a file for changes.
  • Dangerous: anything with in-flight state: writing a file, sending a batch to Kafka, committing a transaction, flushing an audit log. Make these user threads and stop them deliberately.
public class ExitDemo {
    public static void main(String[] args) {
        Thread flusher = Thread.ofPlatform().name("metrics-flusher").daemon(true).unstarted(() -> {
            try {
                while (true) { pause(1_000); System.out.println("flushed"); }
            } finally {
                System.out.println("never printed: daemons are not unwound");
            }
        });
        flusher.start();

        Runtime.getRuntime().addShutdownHook(
            Thread.ofPlatform().name("shutdown-hook").unstarted(() -> System.out.println("hook runs")));

        pause(2_500);
        System.out.println("main ends; only a daemon is left");
    }

    static void pause(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

Output: two "flushed" lines, "main ends…", "hook runs". Make flusher a user thread and the program never exits.

Priorities and thread groups: mostly history

setPriority accepts 1 to 10 (MIN_PRIORITY, NORM_PRIORITY = 5, MAX_PRIORITY), capped by the thread group's maximum. What happens next is OS-dependent. On Linux, HotSpot ignores Java priorities by default (changing that needs -XX:ThreadPriorityPolicy and usually root). Windows maps them onto its own priority classes, so they have some effect there. Virtual threads always report NORM_PRIORITY and ignore the call. Treat priorities as decoration: if one kind of work must not starve another, give it its own pool or a bounded queue, not a higher number.

ThreadGroup was the Java 1.0 way to manage sets of threads. Most of its methods are deprecated or no longer do anything useful; the one behaviour that survives is its role in uncaught-exception dispatch (L122). Group work with executors instead.

Shutdown hooks

Runtime.getRuntime().addShutdownHook(thread) registers an unstarted thread. Rules: hooks run concurrently in no defined order, so they must be thread-safe and independent; they should finish quickly; calling System.exit from a hook blocks forever; registering a hook after shutdown has begun throws IllegalStateException. One hook that shuts down your components in a known order is easier to reason about than five that race.

ExecutorService workers = Executors.newFixedThreadPool(4, Thread.ofPlatform().name("job-", 0).factory());

Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    workers.shutdown();                                       // stop accepting, let queued jobs finish
    try {
        if (!workers.awaitTermination(20, TimeUnit.SECONDS)) {
            workers.shutdownNow();                            // interrupt whatever is left
        }
    } catch (InterruptedException e) {
        workers.shutdownNow();
        Thread.currentThread().interrupt();
    }
}, "graceful-shutdown"));

SIGTERM, containers and Kubernetes

When Kubernetes deletes a pod, the kubelet runs any preStop hook, sends SIGTERM to the container's main process, waits terminationGracePeriodSeconds (30 by default), and then sends SIGKILL. SIGTERM triggers your shutdown hooks; SIGKILL does not. So the whole drain (stop taking traffic, finish in-flight requests and jobs, flush, close connections) must fit inside the grace period, and the JVM must actually receive the signal: in a Dockerfile use the exec form ENTRYPOINT ["java", "-jar", "app.jar"], because the shell form runs sh -c as PID 1, which does not forward SIGTERM. Spring Boot closes its application context from a shutdown hook and supports server.shutdown=graceful; L427 wires this up to readiness probes.

What breaks in production
  • Daemon writers. An async audit-log writer marked daemon "so it doesn't block shutdown" loses its buffer on every deploy.
  • Drain longer than the grace period. A hook that waits 60 s inside a 30 s grace period is SIGKILLed halfway; set awaitTermination below the grace period.
  • Shell-form entrypoints. The JVM never sees SIGTERM, waits out the grace period doing nothing, and is killed with no hooks run.
  • Hooks that need other services. A hook that logs through a logging framework that has its own shutdown hook may find it already stopped. Order shutdown inside one hook.

Race Conditions & Atomicity: A Live Demo

40m video45m practice

A race condition is a bug whose outcome depends on how threads happen to interleave. They all come from shared mutable state touched by an operation that looks like one step but is really several, and you fix them by making that compound action atomic, or by removing the sharing or the mutation.

Shared mutable state and two kinds of race

Definitions

A race condition exists when the correctness of a computation depends on the relative timing of threads. An operation is atomic if, to every other thread operating on the same state, it appears to happen all at once or not at all. A data race (a memory-model term, JLS §17.4.5) is a pair of accesses to the same variable from different threads, at least one a write, not ordered by happens-before (L128).

The two overlap but are not the same. count++ on a plain field is both. A check-then-act on a ConcurrentHashMap has no data race at all, since every call is internally synchronized, yet it is still a race condition, because the pair of calls is not atomic. Removing data races is necessary; it is not sufficient.

count++ is three operations

Compile static int count; … count++; and run javap -c:

getstatic     #7    // Field count:I    1. read the shared value into this thread's operand stack
iconst_1
iadd                                     2. add one, privately
putstatic     #7    // Field count:I    3. write the result back

Between steps 1 and 3 another thread can read the same old value. Both then write the same new value, and one increment vanishes: a lost update. The JIT may compile the loop differently (keeping the value in a register for many iterations, for instance), which changes how many updates are lost but not the fact that they are.

The live demo: 10 threads × 100,000 increments

import java.util.concurrent.atomic.AtomicInteger;

public class LostUpdate {
    static int plain;                                   // Deliberately broken: shared, mutable, unguarded
    static final AtomicInteger atomic = new AtomicInteger();

    public static void main(String[] args) throws InterruptedException {
        Thread[] threads = new Thread[10];
        for (int i = 0; i < threads.length; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 100_000; j++) {
                    plain++;                            // read-modify-write, not atomic
                    atomic.incrementAndGet();           // one atomic hardware operation (L130)
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();              // join: the threads' writes are visible now
        System.out.printf("plain=%,d  atomic=%,d  (expected 1,000,000)%n", plain, atomic.get());
    }
}

On a multi-core machine plain comes out below a million, and differently on every run, while atomic is always exactly 1,000,000. With one thread, or with 1,000 increments per thread, the bug often disappears: each thread finishes inside its first time slice before the next one starts, so the threads never overlap. That is exactly why races survive testing.

Check-then-act, read-modify-write and TOCTOU

Almost every race has one of two shapes. Read-modify-write: read a value, compute a new one from it, write it back (count++, balance -= amount, appending to a shared list). Check-then-act: observe something, then act on the observation, which may be stale by the time you act.

class Registry {
    private static ExpensiveClient client;
    private final ConcurrentMap<String, Session> sessions = new ConcurrentHashMap<>();

    // Deliberately broken: lazy init. Two threads can both see null and build two clients.
    static ExpensiveClient client() {
        if (client == null) client = new ExpensiveClient();
        return client;
    }

    // Deliberately broken even on a ConcurrentHashMap: each call is atomic, the pair is not.
    Session openBroken(String id) {
        if (!sessions.containsKey(id)) sessions.put(id, new Session(id));
        return sessions.get(id);
    }

    // Fixed: a single atomic compound operation (L145)
    Session open(String id) {
        return sessions.computeIfAbsent(id, Session::new);
    }
}

record Session(String id) { }

TOCTOU (time of check to time of use) is check-then-act across a boundary you don't control: a file, a database row, another service. if (!Files.exists(p)) Files.createFile(p) races with every other process; call Files.createFile(p) directly, which is atomic, and handle FileAlreadyExistsException. SELECT then INSERT races with every other instance of your service; use a unique constraint or an upsert. A JVM lock cannot protect state that lives outside the JVM.

Compound actions

The unit of atomicity is the invariant, not the variable. If lower ≤ upper must always hold, updating lower and upper each atomically is not enough: a reader between the two updates sees a broken range. Every variable that takes part in one invariant must be updated under the same lock, in one atomic step.

Why races are non-deterministic, and vanish under a debugger

Whether a race fires depends on the scheduler, the number of cores, other load on the machine, cache state, and what the JIT has compiled so far. A breakpoint pauses one thread and lets the others run to completion, which serializes them. Adding System.out.println to "see what happens" adds a lock (PrintStream methods synchronize) and memory barriers, which can hide both the interleaving and the visibility problem. These are the classic Heisenbugs: test them with stress loops and tools built for the purpose (jcstress, L152), not with a debugger.

The three fixes

  • Don't share (confinement): each thread counts into its own local variable and the totals are combined once, after join. No coordination is needed at all (L136).
  • Don't mutate (immutability): if the state never changes after construction, there is nothing to race on (L136).
  • Synchronize: make the compound action atomic, with synchronized (L127), atomic variables (L130) or explicit locks (L132).
What breaks in production
  • "It passed 1,000 test runs." Low contention in tests, high contention in production. Races appear first under peak load, on bigger machines.
  • Thread-safe parts, unsafe whole. Two calls to a synchronized collection, or a check and an update on a ConcurrentHashMap, are not atomic together.
  • JVM locks around external state. A synchronized block around "read stock, then decrement stock" in the database protects nothing once you run two pods. Use the database's own atomicity.

synchronized, Monitors & Reentrancy

45m video45m practice

synchronized gives you two guarantees, not one: only one thread at a time runs code guarded by the same monitor, and everything a thread wrote before releasing the monitor is visible to the next thread that acquires it. Choose the lock object deliberately, hold it for exactly the compound action, and both guarantees come for free.

Every object has a monitor

Definition · intrinsic lock

Every Java object can act as a monitor (intrinsic lock). A monitor has an owner thread (or none), a recursion count, an entry set of threads BLOCKED waiting to acquire it, and a wait set of threads that called wait() on it. synchronized (obj) { … } acquires obj's monitor on entry and releases it on exit, including exit by exception. In bytecode that is a monitorenter/monitorexit pair plus an exception handler that also exits; a synchronized method is just flagged ACC_SYNCHRONIZED.

Methods, static methods and blocks

  • An instance synchronized method locks this.
  • A static synchronized method locks the Class object (Inventory.class). The two are different locks: a static synchronized method and an instance synchronized method can run at the same time, so a static field mutated from an instance method is not protected.
  • A synchronized (expr) block locks whatever object expr evaluates to, for the block only. Keep the block to the compound action: do validation, logging, formatting and I/O outside it.
import java.util.HashMap;
import java.util.Map;

public final class Inventory {
    private final Object lock = new Object();             // private and final: nobody else can lock it
    private final Map<String, Integer> stock = new HashMap<>();    // guarded by lock

    public boolean reserve(String sku, int qty) {
        if (qty <= 0) throw new IllegalArgumentException("qty " + qty);  // no shared state: outside
        synchronized (lock) {                              // the check-then-act, and nothing else
            int have = stock.getOrDefault(sku, 0);
            if (have < qty) return false;
            stock.put(sku, have - qty);
            return true;
        }
    }

    public void restock(String sku, int qty) {
        synchronized (lock) { stock.merge(sku, qty, Integer::sum); }
    }

    public int available(String sku) {
        synchronized (lock) { return stock.getOrDefault(sku, 0); }   // reads need the lock too
    }
}

Why a private lock object rather than synchronized methods? Locking this makes your lock part of your public API: any caller can write synchronized (inventory) { Thread.sleep(60_000); } and stall every method of the class, by accident or on purpose. A private final lock confines the locking protocol to the class. The exception is a class that documents client-side locking, such as Collections.synchronizedList, whose iterator must be used inside synchronized (list).

Reentrancy

Intrinsic locks are reentrant: a thread that already owns a monitor can acquire it again, which increments the recursion count; each exit decrements it, and the monitor is free at zero. Without reentrancy this classic pattern would deadlock on itself:

class Widget {
    public synchronized void doSomething() { /* ... */ }
}

class LoggingWidget extends Widget {
    @Override
    public synchronized void doSomething() {              // acquires the monitor of this
        System.out.println("before");
        super.doSomething();                               // same object, same monitor: count goes to 2
    }
}

Granularity, contention and striping

Uncontended locking is cheap (an atomic instruction or two). Contention is what costs: losers park, the OS switches them out and later back in, and throughput can fall below that of a single thread. You reduce contention by (1) holding locks for less time, (2) splitting one lock into several when state partitions naturally (one lock per account rather than one for the bank), and (3) lock striping: an array of N locks, with a key's lock chosen by hash(key) % N, so unrelated keys rarely collide. Java 7's ConcurrentHashMap used 16 striped segments; Java 8 went further, to CAS plus per-bin locks (L145). Finer locks bring their own risk, because acquiring several of them is how deadlocks start (L135).

You don't choose among these states; you only need to know that uncontended synchronized is cheap and contended locking is not.

The second guarantee: visibility

Theorem · monitor rule (JLS §17.4.5)

An unlock of monitor m happens-before every subsequent lock of m. Consequently, everything thread A wrote before leaving a synchronized (m) block is visible to thread B after B enters a synchronized (m) block.

This is why available() above takes the lock even though it only reads. An unsynchronized read has no happens-before edge to the last write, so it may see a stale value indefinitely, or a HashMap in a half-updated state. Locking is for readers too, and both sides must use the same lock (L128).

What breaks in production
  • Locking on a shared constant. synchronized ("lock") or on a boxed Integer locks an interned object that unrelated code may also lock. javac warns for value-based classes (JEP 390), and the JVM can diagnose it with -XX:DiagnoseSyncOnValueBasedClasses.
  • Locking on a field you reassign. synchronized (list) followed by list = new ArrayList<>() means two threads can lock two different objects. Lock fields must be final.
  • Synchronized writes, unsynchronized reads. Mutual exclusion is fine; visibility is gone.
  • I/O while holding the lock. A remote call inside synchronized turns one slow dependency into a global stall.

The Java Memory Model: Visibility, Reordering & happens-before

50m video40m practice

Without synchronization, a thread may see another thread's writes late, never, or in a different order from the one in the source code. The Java Memory Model says exactly when a write must be visible: when a chain of happens-before edges connects it to the read. Every correct concurrent program is a program in which those chains exist.

Why one thread can't see another's write

Each core writes into a private store buffer before the value reaches its cache, and reads from its own cache. Cache-coherence protocols eventually make the caches agree, but the store buffer means a core can read a stale value while its own write is still queued. On top of the hardware, the JIT may keep a field in a register for the whole of a loop, or move independent statements past each other, because within one thread nobody could tell. Both are legal optimisations, and both are invisible to single-threaded code.

public class NeverStops {
    static boolean stop;                     // Deliberately broken: not volatile

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long spins = 0;
            while (!stop) spins++;           // the JIT may hoist the read: while (true) spins++;
            System.out.println("saw stop after " + spins);
        });
        worker.start();
        Thread.sleep(1_000);
        stop = true;                         // no happens-before edge to the worker's read
        System.out.println("main set stop");
    }
}

On HotSpot this usually hangs once the loop is JIT-compiled. Declaring stop volatile fixes it (L129).

Reordering, and a demo that fails only on some machines

Two litmus tests show the two ways hardware reorders. Assume all fields start at 0 and are plain (not volatile).

The second test is the dangerous kind: code tested on an x86 laptop works, and the same jar fails on an ARM server (AWS Graviton, Apple silicon). That is why "it works on my machine" is no argument in concurrency, and why the JMM is defined without reference to any CPU.

The JMM is a contract, not a description of hardware

Definition · happens-before and data races (JLS §17.4.5)

If action A happens-before action B, then A's effects are visible to B and A appears ordered before B. Two accesses to the same variable, at least one a write, that are not ordered by happens-before form a data race. A program with no data races is correctly synchronized, and for such programs the JMM guarantees sequential consistency: every execution behaves as if all actions ran in one interleaved order.

Read that guarantee carefully: you don't need to reason about caches, store buffers or the JIT at all. Prove that every conflicting pair of accesses is ordered by happens-before, and the program behaves as if it ran on a simple, single-memory machine. Leave one data race and all bets are off for that variable.

Safe and unsafe publication

Publishing an object means making a reference to it reachable by another thread. If the reference travels through a data race, the reader can see the reference but stale values in the object's non-final fields: a partially constructed object.

class Holder {

    Holder(int n) { this.n = n; }
    void assertSanity() {
        if (n != n) throw new AssertionError("n changed between two reads");
    }
}

class Publisher {
    Holder holder;                                  // Deliberately broken: plain field, racy publication

Algorithm · the four safe ways to publish
  1. Initialize the reference from a static initializer (class initialization is synchronized by the JVM).
  2. Store it in a volatile field or an AtomicReference.
  3. Store it in a final field of a properly constructed object.
  4. Store it in a field guarded by a lock, including handing it over through a thread-safe collection or queue.

}

record Order(String id) { }

A constructor can also publish this before it finishes, by starting a thread, registering a listener, or storing this in a static field. Final-field guarantees do not cover an object whose this escaped during construction. Construct completely, then publish.

Final fields and immutable objects

Theorem · final field semantics (JLS §17.5)

If an object is properly constructed (this does not escape the constructor), every thread that obtains a reference to it, even through a data race, sees its final fields with the values set in the constructor, and sees the objects reachable through those final fields at least as up to date as they were when the constructor finished.

That is why immutable objects (all fields final, no mutation after construction, no escaping this) are thread-safe without any locking, and why records are such good messages between threads. Two caveats: the guarantee covers state reachable through finals as of the end of construction, so a final ArrayList that is mutated later is not protected; and racy publication still lets the reader see a stale reference (null, or an older object). Final fields protect the object's contents, not the field you published it through.

Interview trap
  • "volatile flushes caches." It does not describe hardware at all; it creates happens-before edges. Caches are coherent anyway; store buffers and the compiler are the problem.
  • "x86 is strongly ordered, so I don't need volatile." The JIT reorders and hoists regardless of CPU, and the same bytecode runs on ARM.
  • "Synchronizing the writer is enough." Edges join a release in one thread to an acquire in another. A reader that doesn't acquire the same lock, or read the same volatile, gets no edge.

volatile: Semantics, Use Cases & Limits

40m video40m practice

volatile makes a single variable's reads and writes visible and ordered across threads, which is exactly enough for flags and for publishing immutable snapshots, and exactly not enough for anything that reads a value and then writes a value computed from it.

What volatile guarantees, and what it does not

Definition · visibility, ordering, atomicity
  • Visibility: a write to a volatile field happens-before every subsequent read of that field (JLS §17.4.5). Once a reader sees the new value, it also sees everything the writer did before the write.
  • Ordering: a volatile write acts as a release (earlier memory operations cannot move after it), a volatile read as an acquire (later operations cannot move before it), and all volatile accesses form a single total order agreed by every thread.
  • Atomic 64-bit access: reads and writes of a volatile long or double are never split (JLS §17.7).

It does not make compound actions atomic. volatileCount++ is still read, add, write, and still loses updates exactly as in L126.

The stop flag, done right

final class Reporter implements Runnable {
    private volatile boolean running = true;       // written by one thread, read by another

    void shutdown() { running = false; }           // release: visible to the next read

    @Override
    public void run() {
        while (running) {                          // acquire on every iteration: cannot be hoisted
            sendBatch();                           // must not block for long (see L124)
        }
    }

    private void sendBatch() { /* bounded, non-blocking work */ }
}

This is the fix for L128's NeverStops. The flag fits volatile perfectly: one variable, written without reading it first, taking part in no invariant with other fields. If sendBatch can block, combine the flag with interruption, as L124 showed.

64-bit values and tearing

JLS §17.7 lets a JVM write a non-volatile long or double as two separate 32-bit halves, so a racing reader could see the high half of one value and the low half of another: a value nobody ever wrote. Declaring the field volatile (or guarding it with a lock, or using AtomicLong) forbids that. Current 64-bit HotSpot builds write longs atomically anyway, but the specification does not promise it, and 32-bit platforms really did tear. Note the related rule in JLS §17.6: the JVM must never "word-tear" adjacent fields or array elements, so updating one byte of a byte[] can never clobber its neighbour.

The barriers behind volatile

Doug Lea's JSR-133 Cookbook describes a conservative mapping from volatile accesses to four kinds of memory barrier. A barrier XY stops X-type operations before it from being reordered with Y-type operations after it.

Double-checked locking: broken, fixed, and replaced

// Deliberately broken (and broken in every Java version): instance is not volatile.

            }                                                       // before the constructor's writes
        }

                                                         // Resource, or in theory even null
    }
}

// Correct since Java 5 (JSR-133 strengthened volatile).
final class Lazy {
    private static volatile Resource instance;
    static Resource get() {
        Resource r = instance;                           // one volatile read on the fast path
        if (r == null) {
            synchronized (Lazy.class) {
                r = instance;
                if (r == null) instance = r = new Resource();
            }
        }
        return r;
    }
}

// Usually better for statics: initialization-on-demand holder.
final class HolderLazy {
    private static final class Holder { static final Resource INSTANCE = new Resource(); }
    static Resource get() { return Holder.INSTANCE; }    // Holder is initialized on first call, once
}

final class Resource { private int[] table = new int[1_024]; }    // non-final state

The holder idiom relies on class initialization instead: the JVM initializes Holder lazily, the first time get() touches it, and the initialization procedure (JLS §12.4.2) is synchronized, so every thread sees a fully built instance with no volatile read at all. Use DCL with volatile only for lazily initialized instance fields, where there is no class to hold.

Atomic Classes & Compare-And-Swap

45m video45m practice

Compare-and-swap is a single hardware instruction that says "set this to B, but only if it is still A". Wrapped in a retry loop it turns any read-modify-write on one variable into an atomic operation with no lock, which is what the java.util.concurrent.atomic classes give you, along with one subtle failure mode, ABA.

CAS in hardware, and the retry loop

Definition · compare-and-swap

CAS(address, expected, new) atomically compares the value at address with expected; if equal it stores new and reports success, otherwise it changes nothing and reports failure. On x86 it is lock cmpxchg; ARMv8.1 has a cas instruction, and older ARM builds it from a load-exclusive/store-exclusive pair. A CAS on a volatile field has volatile read and write semantics, so it also creates happens-before edges.

Every lock-free update follows the same shape: read the current value, compute a new one, CAS; if the CAS failed, someone else got there first, so read again and retry.

import java.util.concurrent.atomic.AtomicInteger;

final class Permits {
    private final AtomicInteger used = new AtomicInteger();
    private final int limit;

    Permits(int limit) { this.limit = limit; }

    /** Returns true if a permit was taken; never exceeds the limit, takes no lock. */
    boolean tryTake() {
        while (true) {
            int current = used.get();
            if (current >= limit) return false;               // decided on a fresh value
            if (used.compareAndSet(current, current + 1)) return true;
            // CAS failed: another thread changed 'used' after our get(); loop and re-read
        }
    }

    void release() { used.decrementAndGet(); }
}

The atomic classes and their operations

import java.util.concurrent.atomic.*;

public class AtomicTour {
    record Config(int timeoutMs) { Config withTimeout(int t) { return new Config(t); } }

    public static void main(String[] args) {
        AtomicLong requests = new AtomicLong();
        long now    = requests.incrementAndGet();          // like ++x: returns the new value (1)
        long before = requests.getAndIncrement();          // like x++: returns the old value (1)

        AtomicInteger maxLatency = new AtomicInteger(Integer.MIN_VALUE);
        maxLatency.accumulateAndGet(87, Math::max);         // running maximum without a lock

        AtomicReference<Config> cfg = new AtomicReference<>(new Config(2_000));
        cfg.updateAndGet(c -> c.withTimeout(5_000));       // the function may run more than once

        AtomicBoolean started = new AtomicBoolean();
        if (started.compareAndSet(false, true)) {
            System.out.println("exactly one caller ever gets here");
        }
        System.out.println(now + " " + before + " " + maxLatency.get() + " " + cfg.get());
    }
}

updateAndGet and accumulateAndGet are CAS loops in disguise: under contention your function is called again with a fresher value, so it must be pure, with no I/O, no logging, no increments of anything else. incrementAndGet and getAndAdd are JIT intrinsics; on x86 they compile to a single lock xadd, which cannot fail and needs no loop. Since Java 9 the classes also expose weaker accesses (getAcquire, setRelease, getPlain, weakCompareAndSetVolatile, compareAndExchange); L131 explains those modes.

For arrays, AtomicIntegerArray, AtomicLongArray and AtomicReferenceArray give every element volatile semantics and atomic operations. A volatile int[] does not: only the array reference is volatile, and the elements are plain.

Blocking, lock-free, wait-free

Definitions · progress guarantees
  • Blocking: a thread that is descheduled while holding a lock can stop every other thread from making progress.
  • Lock-free: whatever the scheduler does, some thread completes its operation in a finite number of steps. Individual threads can starve, retrying forever while others win. A CAS loop is lock-free.
  • Wait-free: every thread completes in a bounded number of its own steps. getAndIncrement implemented as lock xadd is wait-free; general wait-free data structures are rare and complicated.

A lock-free stack, and the ABA problem

Treiber's stack is the textbook lock-free structure: top is an AtomicReference, and push and pop are CAS loops on it.

import java.util.concurrent.atomic.AtomicReference;

public final class TreiberStack<E> {
    private record Node<E>(E item, Node<E> next) { }      // immutable, freshly allocated per push
    private final AtomicReference<Node<E>> top = new AtomicReference<>();

    public void push(E item) {
        Node<E> old;
        do {
            old = top.get();
        } while (!top.compareAndSet(old, new Node<>(item, old)));
    }

    public E pop() {
        Node<E> old;
        do {
            old = top.get();
            if (old == null) return null;
        } while (!top.compareAndSet(old, old.next()));
        return old.item();
    }
}

This version is correct in Java because every push allocates a new node, and the garbage collector never reuses a node's memory while any thread still holds a reference to it. Now "optimise" it by recycling popped nodes through a free list, with a mutable next field, to avoid allocation. CAS compares references, so it cannot tell "still A" from "A again":

Two classes exist for this. AtomicStampedReference<V> pairs the reference with an int stamp, and compareAndSet(expectedRef, newRef, expectedStamp, newStamp) succeeds only if both match; incrementing the stamp on every update makes "A again" distinguishable from "still A". AtomicMarkableReference<V> pairs it with a boolean, used to mark a node as logically deleted in lock-free linked lists. Both allocate an internal pair object on each update, so in Java the usual cure is simpler: don't recycle nodes, and let the GC guarantee that a reference you hold is never reused.

When CAS loses to a lock

A failed CAS is wasted work plus a cache miss, because the cache line holding the variable bounces between cores on every attempt. With a handful of threads that is still cheaper than parking. With dozens of threads hammering one variable, most attempts fail, and throughput can fall below that of a lock, which at least lets losers sleep instead of burning cores, especially if the update function is expensive. For hot counters the answer is not a lock either but spreading the contention across cells (LongAdder, L131). Measure with JMH (L168) before choosing.

What breaks in production
  • Side effects in updateAndGet. A lambda that sends a message or increments a metric runs once per retry, so under load it fires several times for one logical update.
  • Two atomics, one invariant. An AtomicInteger for count and another for total can be read in an inconsistent state. Put both in an immutable record behind one AtomicReference, or use a lock.
  • get() then set(). Using an atomic class without its atomic methods recreates L126's race.
  • volatile arrays. Elements are not volatile; use AtomicIntegerArray and friends.

LongAdder, Striped64, Field Updaters & VarHandle

35m video35m practice

An atomic variable is a single cache line, and under heavy contention every core spends its time fighting for that line. LongAdder spreads the fight across many padded cells and pays for it with a sum that is not a snapshot; field updaters and VarHandle give you atomics without an extra object, and with a choice of how much ordering you pay for.

One cache line, many cores

Caches move memory in lines, typically 64 bytes. To write a variable, a core must own its line exclusively, which invalidates every other core's copy. When 32 threads CAS one AtomicLong, the line bounces from core to core and most CAS attempts fail (L130). False sharing is the same effect without any logical sharing: two independent hot fields that happen to sit on one cache line, each written by a different thread, still ping-pong the line between their cores.

Padding against false sharing

The JDK marks hot fields with @jdk.internal.vm.annotation.Contended (it was sun.misc.Contended in JDK 8), which makes the JVM pad them onto their own cache lines. It is internal: ordinary code needs --add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED to compile against it and -XX:-RestrictContended for it to take effect. Hand-padding with dummy long fields is unreliable, because the JVM chooses field layout. In application code, prefer a class that already solves the problem, such as LongAdder.

LongAdder and Striped64

LongAdder, DoubleAdder, LongAccumulator and DoubleAccumulator all extend the package-private Striped64. Uncontended, an add is one CAS on base, as cheap as AtomicLong. On a failed CAS the thread moves to a cell; on a collision there it rehashes, and the cell array doubles, up to roughly the number of CPUs. Each cell is @Contended, so cells never false-share.

Definition · what the sum means

sum() returns base plus every cell, read one at a time. Updates that happen while it runs may or may not be counted, so the result is not an atomic snapshot: it is exact only when no updates are in flight. sumThenReset() is likewise not atomic with respect to concurrent adds. That is fine for request counts and metrics, and wrong for sequence numbers, IDs, or decisions like "reject once 1,000 are in flight".

import java.util.concurrent.atomic.LongAccumulator;
import java.util.concurrent.atomic.LongAdder;

final class EndpointStats {
    private final LongAdder requests = new LongAdder();
    private final LongAccumulator maxLatency = new LongAccumulator(Long::max, Long.MIN_VALUE);

    void record(long latencyMs) {
        requests.increment();
        maxLatency.accumulate(latencyMs);     // function must be associative, commutative, pure
    }

    String report() {
        return "requests=" + requests.sum() + " maxMs=" + maxLatency.get();   // approximate under load
    }
}

LongAccumulator generalises the adder to any function: it applies it to whichever cell a thread lands on and combines the cells when you read. Because the order of application is not defined, the function must give the same answer in any order (max, min, sum, bitwise OR), and the identity value must really be an identity for it.

Field updaters and VarHandle

An AtomicInteger field costs a reference plus a separate object with its own header, around 20 bytes per instance on a typical 64-bit JVM. With millions of instances (nodes, connections, cache entries) you can make a plain volatile int field atomic instead. AtomicIntegerFieldUpdater (and the Long and Reference versions) did that via reflection since Java 5; VarHandle (Java 9, JEP 193) is the modern, faster and more general mechanism, and the supported replacement for the memory-access methods of sun.misc.Unsafe, which JDK 23 deprecated for removal (JEP 471).

import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;
import java.util.concurrent.atomic.AtomicIntegerFieldUpdater;

final class Connection {
    private static final AtomicIntegerFieldUpdater<Connection> STATE_UPDATER =
        AtomicIntegerFieldUpdater.newUpdater(Connection.class, "state");   // field must be volatile int

    private static final VarHandle STATE;
    static {
        try {
            STATE = MethodHandles.lookup().findVarHandle(Connection.class, "state", int.class);
        } catch (ReflectiveOperationException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    private volatile int state;                       // 0 = idle, 1 = in use: no extra object

    boolean tryAcquireOld() { return STATE_UPDATER.compareAndSet(this, 0, 1); }
    boolean tryAcquire()    { return STATE.compareAndSet(this, 0, 1); }
    void release()          { STATE.setRelease(this, 0); }          // release is enough to publish
    int peek()              { return (int) STATE.getOpaque(this); } // monitoring read, no ordering
}

ReentrantLock: tryLock, Fairness & Lock vs synchronized

45m video45m practice

ReentrantLock has the same mutual-exclusion and visibility semantics as synchronized, plus the things a monitor cannot do: give up after a timeout, respond to interruption, queue fairly, and expose its state. You pay for those with an explicit unlock() that must be in a finally block every single time.

The Lock interface and the one idiom

import java.util.concurrent.locks.ReentrantLock;

final class Ledger {
    private final ReentrantLock lock = new ReentrantLock();
    private long balance;                                 // guarded by lock

    void deposit(long amount) {
        lock.lock();                                      // outside try: if lock() fails, don't unlock
        try {
            balance += amount;                            // the critical section
        } finally {
            lock.unlock();                                // always, even on exception
        }
    }
}

Unlike a monitor, nothing releases a Lock for you. Forget the finally and the first exception inside the critical section leaves the lock held forever, and the next caller hangs with no error. Call lock() immediately before try: if it were inside and threw, the finally would call unlock() on a lock you don't hold and throw IllegalMonitorStateException, hiding the original error.

  • tryLock(): acquire if free right now, otherwise return false immediately.
  • tryLock(timeout, unit): wait up to the timeout; throws InterruptedException if interrupted while waiting. The right tool on a request path that would rather fail fast than queue.
  • lockInterruptibly(): wait indefinitely, but abort with InterruptedException if interrupted, so a cancelled task stops waiting (a thread BLOCKED on a monitor cannot).
boolean tryUpdate(ReentrantLock lock, Runnable update) throws InterruptedException {
    if (!lock.tryLock(50, TimeUnit.MILLISECONDS)) {
        return false;                                     // caller can return 503 or retry later
    }
    try {
        update.run();
        return true;
    } finally {
        lock.unlock();
    }
}

Inside: AbstractQueuedSynchronizer

Definition · AQS

Almost every synchronizer in java.util.concurrent is built on AbstractQueuedSynchronizer: a volatile int state whose meaning each subclass defines (hold count for ReentrantLock, permits for Semaphore, the count for CountDownLatch, read and write holds packed into one int for ReentrantReadWriteLock), plus a FIFO queue of waiting threads derived from the CLH lock algorithm. The subclass implements tryAcquire/tryRelease as CAS operations on state; AQS handles queueing, parking with LockSupport.park, unparking, timeouts and interruption. Because state is volatile and updated by CAS, an unlock happens-before the next lock, exactly as with monitors.

Fair vs non-fair

new ReentrantLock() is non-fair; new ReentrantLock(true) is fair. Under contention a non-fair lock is usually much faster: when the owner releases, a thread that is already running can grab the lock immediately, while the queued thread it would otherwise go to is still waking up, and waking it costs a context switch. A fair lock forces every handoff to go through that wake-up. Fairness buys predictable ordering and no starvation, at a throughput cost that can be large. Choose it only when starvation is an observed problem. One quirk: the untimed tryLock() barges even on a fair lock; tryLock(0, TimeUnit.SECONDS) respects fairness.

Diagnostics

  • getHoldCount(): how many times the current thread holds it (0 if not the owner); isHeldByCurrentThread() is the usual assertion inside helper methods.
  • isLocked(): held by anyone. getQueueLength() and hasQueuedThreads(): an estimate of how many are waiting, useful as a contention gauge in metrics.
  • Thread dumps list a parked waiter as - parking to wait for <0x…> (a java.util.concurrent.locks.ReentrantLock$NonfairSync), and owners under "Locked ownable synchronizers" when you use jstack -l.

These are monitoring values: they may be stale by the time you read them, so never use them for control flow.

Avoiding deadlock with tryLock and backoff

import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

final class Account {
    final ReentrantLock lock = new ReentrantLock();
    long balance;                                         // guarded by lock
    Account(long balance) { this.balance = balance; }

    static boolean transfer(Account from, Account to, long amount, Duration timeout)
            throws InterruptedException {
        long deadline = System.nanoTime() + timeout.toNanos();
        while (true) {
            if (from.lock.tryLock()) {
                try {
                    if (to.lock.tryLock()) {
                        try {
                            if (from.balance < amount) return false;
                            from.balance -= amount;
                            to.balance += amount;
                            return true;
                        } finally {
                            to.lock.unlock();
                        }
                    }
                } finally {
                    from.lock.unlock();                   // never hold one lock while waiting for the other
                }
            }
            if (System.nanoTime() >= deadline) return false;
            TimeUnit.MICROSECONDS.sleep(ThreadLocalRandom.current().nextLong(50, 500));  // random backoff
        }
    }
}

Two threads transferring A→B and B→A can no longer deadlock: whoever fails to get the second lock releases the first. The random backoff matters, because two threads that retry in lock-step can fail forever (livelock, L135). Global lock ordering (L135) is still the cleaner primary fix; tryLock is the fallback when you cannot impose an order.

ReadWriteLock, StampedLock & Optimistic Reading

40m video40m practice

If reads vastly outnumber writes, letting readers run together should help, and a read-write lock does exactly that. It only pays off when read sections are long, because every reader still writes to the lock's shared state. StampedLock's optimistic read removes even that write, at the price of code that must tolerate seeing inconsistent data and retry.

ReentrantReadWriteLock: shared reads, exclusive writes

Definition · read-write lock

A ReadWriteLock is a pair of locks. The read lock may be held by many threads at once, provided no thread holds the write lock. The write lock is exclusive: it excludes every reader and every other writer. Both have the usual Lock semantics, so releasing the write lock happens-before any later acquisition of either lock.

Writer starvation is the classic failure of read-write locks: with continuous overlapping readers, the read lock is never fully released and a writer never gets in. ReentrantReadWriteLock's default non-fair mode mitigates this with a heuristic (an arriving reader blocks if the first queued thread is a writer) but promises no ordering; new ReentrantReadWriteLock(true) grants the lock roughly in arrival order, at a throughput cost. Its hold counts are packed into one 32-bit state, so each side is limited to 65,535 holds.

Downgrading works, upgrading deadlocks

A thread holding the write lock may take the read lock and then release the write lock: a downgrade, which keeps other writers out while it finishes reading what it just wrote. The reverse, taking the write lock while holding the read lock, deadlocks: the write lock waits for every reader to leave, including the thread that is waiting. Two readers that both try to upgrade would deadlock each other even with a smarter lock, which is why ReentrantReadWriteLock does not support upgrades at all.

import java.util.Map;
import java.util.concurrent.locks.ReentrantReadWriteLock;

final class CachedConfig {
    private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
    private Map<String, String> data = Map.of();          // guarded by rw
    private boolean valid;                                  // guarded by rw

    String get(String key) {
        rw.readLock().lock();
        if (!valid) {
            rw.readLock().unlock();                         // no upgrades: release read first
            rw.writeLock().lock();
            try {
                if (!valid) {                               // re-check: another writer may have won
                    data = load();
                    valid = true;
                }
                rw.readLock().lock();                       // downgrade: take read while holding write
            } finally {
                rw.writeLock().unlock();                    // now only the read lock is held
            }
        }
        try {
            return data.get(key);
        } finally {
            rw.readLock().unlock();
        }
    }

    void invalidate() {
        rw.writeLock().lock();
        try { valid = false; } finally { rw.writeLock().unlock(); }
    }

    private Map<String, String> load() { return Map.of("mode", "live"); }
}

When a read-write lock beats a plain lock, and when it loses

Acquiring a read lock is a CAS on the lock's shared state, so readers still contend for one cache line on every entry and exit, even though they never block each other. If the read section is a few nanoseconds (a field read, a small map lookup), that CAS dominates, and a read-write lock is no faster than a mutex and often slower, since its bookkeeping is heavier. It wins when read sections are long (tens of microseconds or more: scanning a structure, computing over it) and reads dominate (well above 90%). For small, hot, read-mostly data, the alternatives in L129 (an immutable snapshot behind a volatile) and L145 (ConcurrentHashMap) usually beat both.

StampedLock and optimistic reading

StampedLock (Java 8) offers three modes, each identified by a long stamp: writeLock()/unlockWrite(stamp), readLock()/unlockRead(stamp), and tryOptimisticRead(), which takes no lock at all. An optimistic read records the lock's version, reads the fields into locals, and calls validate(stamp); if no write lock was acquired in between, the copies are consistent. If validation fails, fall back to a real read lock.

Algorithm · optimistic read
  1. stamp = tryOptimisticRead() (returns 0 if a writer holds the lock, which then fails validation).
  2. Copy every field you need into local variables. Do nothing else with them yet: they may be torn or inconsistent.
  3. If validate(stamp) is true, the copies are a consistent snapshot; use them.
  4. Otherwise take readLock(), copy again, unlockRead, and use those.
import java.util.concurrent.locks.ReentrantReadWriteLock;
import java.util.concurrent.locks.StampedLock;

interface PointStore { void move(double dx, double dy); double distance(); }

final class SyncPoint implements PointStore {
    private double x, y;
    public synchronized void move(double dx, double dy) { x += dx; y += dy; }
    public synchronized double distance() { return Math.hypot(x, y); }
}

final class RwPoint implements PointStore {
    private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
    private double x, y;
    public void move(double dx, double dy) {
        rw.writeLock().lock();
        try { x += dx; y += dy; } finally { rw.writeLock().unlock(); }
    }
    public double distance() {
        rw.readLock().lock();
        try { return Math.hypot(x, y); } finally { rw.readLock().unlock(); }
    }
}

final class StampedPoint implements PointStore {
    private final StampedLock sl = new StampedLock();
    private double x, y;
    public void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; } finally { sl.unlockWrite(stamp); }
    }
    public double distance() {
        long stamp = sl.tryOptimisticRead();
        double cx = x, cy = y;                     // copies only: may be inconsistent
        if (!sl.validate(stamp)) {                 // a writer intervened: read again under the lock
            stamp = sl.readLock();
            try { cx = x; cy = y; } finally { sl.unlockRead(stamp); }
        }
        return Math.hypot(cx, cy);
    }
}

With a 95% read workload and 8 or more threads, a JMH run usually shows StampedPoint clearly ahead, because successful optimistic reads write nothing shared; RwPoint often trails even SyncPoint, because its read sections are tiny. Run the comparison yourself (practice 3): the ranking depends on read ratio, section length and core count.

Caveats
  • Not reentrant. A thread holding the write lock that calls writeLock() again deadlocks itself. Don't call out to other methods that might lock.
  • Not interruptible by default. readLock() and writeLock() ignore interrupts; use readLockInterruptibly() and writeLockInterruptibly() when cancellation matters.
  • No conditions, no owner. There is no newCondition(), and stamps are not tied to threads, so mistakes are not caught for you.
  • Optimistic code must be paranoid. Between the stamp and validate you may see any mix of old and new values, including a null reference. Don't dereference, index or loop on optimistically read values before validating.
What breaks in production
  • Upgrading a read lock. The thread hangs in writeLock().lock() forever, and a thread dump shows it waiting on a lock it partly holds.
  • Read-write lock for a hash-map lookup. More code, more cache traffic, no speed-up. Measure first.
  • Acting on an unvalidated read. An optimistic read that indexes an array with a torn value throws ArrayIndexOutOfBoundsException before validate runs.

Condition, await/signal & Legacy wait/notify

45m video45m practice

A lock gives mutual exclusion; a condition lets a thread wait, inside the lock, until the state it needs exists. Every correct use follows one shape: hold the lock, test the condition in a while loop, wait, re-test. Build a bounded buffer that way twice, then use the JDK's, because it is the same code, already tested.

wait, notify and notifyAll

Definition · monitor wait and notify
  • obj.wait() may be called only by the thread that owns obj's monitor (otherwise IllegalMonitorStateException). It atomically releases that monitor (any other monitors stay held) and puts the thread in the monitor's wait set.
  • obj.notify() moves one arbitrary thread from the wait set to the entry set; notifyAll() moves all of them. Either way the woken thread must re-acquire the monitor before wait() returns, so it runs only after the notifier leaves the synchronized block.
  • wait also returns on interrupt (throwing InterruptedException), on timeout for wait(ms), and spuriously, for no reason at all (JLS §17.2.1 allows it).

Always wait in a loop

synchronized (lock) {
    while (!conditionHolds()) {    // NOT "if": re-test after every wake-up
        lock.wait();
    }
    act();                         // the condition is true and we hold the lock
}

Three reasons the loop is mandatory: a spurious wakeup returns with nothing changed; a stale condition occurs when another thread re-acquired the monitor first and consumed what you were woken for; and with notifyAll you may be woken for a condition that is not yours. Testing the condition before the first wait, under the lock, also prevents the missed signal: if the notification happened before you arrived, the condition is already true and you never wait.

notify vs notifyAll and the lost wakeup

With one monitor there is one wait set. In a bounded buffer, producers wait for "not full" and consumers wait for "not empty" in the same set. Suppose the buffer is empty, two consumers are waiting, and a producer that also had to wait is in the set too. A consumer takes an item and calls notify(), intending to wake the producer, but the JVM picks the other consumer, which finds the buffer still empty and waits again. The one signal that mattered has been spent on the wrong thread, and if no one else signals, every thread ends up waiting: a lost wakeup, which looks exactly like a deadlock.

The rule: use notifyAll() unless all waiters are waiting for the same predicate and each notification enables at most one of them. notifyAll costs extra wake-ups; notify in the wrong place costs a hang.

Bounded buffer, version 1: wait/notifyAll

public final class MonitorBuffer<E> {
    private final Object[] items;
    private int head, tail, count;                          // guarded by this

    public MonitorBuffer(int capacity) { items = new Object[capacity]; }

    public synchronized void put(E e) throws InterruptedException {
        while (count == items.length) wait();               // wait for "not full"
        items[tail] = e;
        tail = (tail + 1) % items.length;
        count++;
        notifyAll();                                        // producers and consumers share one wait set
    }

    @SuppressWarnings("unchecked")
    public synchronized E take() throws InterruptedException {
        while (count == 0) wait();                          // wait for "not empty"
        E e = (E) items[head];
        items[head] = null;                                 // let the GC have it
        head = (head + 1) % items.length;
        count--;
        notifyAll();
        return e;
    }
}

Condition: await, signal and friends

lock.newCondition() returns a Condition bound to that Lock, and a lock may have as many as you like. The methods mirror the monitor ones and have the same rules (hold the lock, loop on the predicate): await(), signal(), signalAll(), plus awaitNanos(n), which returns the time remaining so a loop can keep an overall deadline; await(time, unit) and awaitUntil(date); and awaitUninterruptibly(), which ignores interrupts and restores the flag on return, for the rare code that cannot be cancelled.

import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public final class ConditionBuffer<E> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    private final Object[] items;
    private int head, tail, count;                          // guarded by lock

    public ConditionBuffer(int capacity) { items = new Object[capacity]; }

    public void put(E e) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();
            items[tail] = e;
            tail = (tail + 1) % items.length;
            count++;
            notEmpty.signal();                              // one item: wake one consumer
        } finally {
            lock.unlock();
        }
    }

    /** Waits at most the timeout; returns null if still empty. */
    public E poll(long timeout, TimeUnit unit) throws InterruptedException {
        long nanos = unit.toNanos(timeout);
        lock.lock();
        try {
            while (count == 0) {
                if (nanos <= 0) return null;
                nanos = notEmpty.awaitNanos(nanos);         // returns the time left
            }
            @SuppressWarnings("unchecked") E e = (E) items[head];
            items[head] = null;
            head = (head + 1) % items.length;
            count--;
            notFull.signal();                               // one slot: wake one producer
            return e;
        } finally {
            lock.unlock();
        }
    }
}

signal() is safe here because each condition's waiters are uniform and each operation frees exactly one item or one slot. This is, almost line for line, how ArrayBlockingQueue is written.

Now use ArrayBlockingQueue

new ArrayBlockingQueue<>(capacity) gives you this buffer plus offer with timeouts, drainTo, an optional fair mode, iteration, metrics-friendly remainingCapacity(), and years of production testing. Write your own condition-based code only for a predicate the JDK does not cover; for queues, latches, barriers and permits, L146–L148 have a ready-made class. This is Effective Java Item 81: prefer concurrency utilities to wait and notify.

Interview trap
  • "Why must wait be called in a loop?" Spurious wakeups, stale conditions and shared wait sets; and an if cannot handle any of them.
  • "Why must you hold the lock to call wait?" Otherwise the test of the condition and the decision to sleep are not atomic, and a notification can slip in between them and be lost.
  • "Does wait release all locks?" No, only the monitor it is called on. Waiting while holding a second lock is a deadlock waiting to happen.
  • "sleep vs wait?" sleep keeps every lock and needs none; wait needs and releases one monitor.

Deadlock, Livelock, Starvation & Detection

45m video45m practice

A deadlock needs four conditions at once, so you prevent it by breaking one, almost always circular wait, by acquiring locks in a single global order. The JVM never resolves a deadlock for you: the threads stay stuck until the process dies, so you also need the tools to see one in seconds.

The four Coffman conditions

Theorem · Coffman et al. 1971

A deadlock can occur only if all four hold simultaneously:

  1. Mutual exclusion: a resource is held by at most one thread.
  2. Hold and wait: a thread holds one resource while waiting for another.
  3. No preemption: a resource cannot be taken away; only its holder releases it.
  4. Circular wait: there is a cycle T1 → T2 → … → T1, each waiting for a resource the next one holds.

Break any one and deadlock is impossible. Lock ordering breaks (4); tryLock with release breaks (2) and (3); acquiring everything in one atomic step breaks (2).

A lock-ordering deadlock in 20 lines

public class Deadlock {                                  // Deliberately broken: hangs every time
    public static void main(String[] args) {
        Object a = new Object(), b = new Object();
        new Thread(() -> lockBoth(a, b), "t1").start();
        new Thread(() -> lockBoth(b, a), "t2").start();     // opposite order: a cycle
    }

    static void lockBoth(Object first, Object second) {
        synchronized (first) {
            pause(50);                                    // widen the window so it always deadlocks
            synchronized (second) {
                System.out.println(Thread.currentThread().getName() + " got both");
            }
        }
    }

    static void pause(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

The fixes: global ordering first, timeouts second

Global lock ordering is the primary fix: define one order over all locks that can be held together, and acquire them only in that order. A cycle then cannot form. Order by a stable unique key, such as an account ID; never by something that can change or collide.

final class Account {
    private final long id;
    private long balance;                                  // guarded by this
    Account(long id, long balance) { this.id = id; this.balance = balance; }

    static void transfer(Account from, Account to, long amount) {
        Account first  = from.id < to.id ? from : to;      // always lock the lower id first
        Account second = first == from ? to : from;
        synchronized (first) {
            synchronized (second) {
                if (from.balance < amount) throw new IllegalStateException("insufficient funds");
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }
}

When you cannot impose an order (locks chosen at runtime, code you don't own), fall back to timed acquisition with backoff: tryLock(timeout), release everything on failure, wait a random interval, retry (L132). It converts a permanent hang into a recoverable failure that you can log and count.

The third rule is open calls: never call code you don't control (listeners, callbacks, overridable methods, anything injected) while holding a lock. That code may take its own locks, creating an ordering you cannot see. Copy what you need under the lock, release it, then call out.

void setStatus(Status s) {
    List<Listener> toNotify;
    synchronized (lock) {
        status = s;
        toNotify = List.copyOf(listeners);                 // snapshot under the lock
    }
    for (Listener l : toNotify) l.onChange(s);             // open call: no lock held
}

Hidden locks: ORMs, pools, callbacks, databases

Most production deadlocks do not involve two synchronized blocks you can see. They involve hidden locks: a connection pool (every thread holds one connection and waits for a second from an exhausted pool), a lazy-loading ORM entity touched inside a synchronized section (which needs a connection, and the database's row locks), a ConcurrentHashMap.computeIfAbsent whose loader calls back into the same map (L145), a logging appender with its own lock, or two classes whose static initializers need each other on different threads.

The nastiest kind spans both: thread A holds a JVM lock and waits for a row lock; thread B's transaction holds that row and waits for the JVM lock. Neither the JVM nor the database sees the whole cycle. Only timeouts (on locks, statements and transactions) break it.

Livelock and starvation

Livelock: threads are not blocked, they keep reacting to each other and retrying, and nobody progresses, like two people in a corridor stepping aside in the same direction forever. Two tryLock loops with identical fixed backoff can do this; randomized backoff breaks the symmetry. A message redelivered forever because it always fails processing is the distributed version (L378's dead-letter topics). Starvation: a thread is perpetually denied a resource others keep getting: a writer behind an endless stream of readers (L133), a thread on a non-fair lock losing every race, or low-priority work behind a full queue. The cures are fair policies, bounded hold times, and separate pools for separate classes of work.

Detecting deadlocks

  • jstack <pid> or jcmd <pid> Thread.print: the dump ends with "Found one Java-level deadlock:" and lists the cycle, for monitors and for java.util.concurrent locks. Add -l to jstack to list the ownable synchronizers each thread holds.
  • ThreadMXBean.findDeadlockedThreads(): the same detection from inside the process (monitors and ownable synchronizers); findMonitorDeadlockedThreads() covers monitors only.
  • JFR: jdk.JavaMonitorEnter and jdk.ThreadPark events show long blocking leading up to the hang, and the periodic jdk.ThreadDump event captures stacks; JDK Mission Control's thread view shows the stuck threads.
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;
import java.time.Duration;
import java.util.concurrent.*;
import java.util.function.Consumer;

/** Drop-in watchdog: reports deadlocked threads (monitors and j.u.c locks) on a schedule. */
public final class DeadlockDetector implements AutoCloseable {
    private final ThreadMXBean mx = ManagementFactory.getThreadMXBean();
    private final ScheduledExecutorService timer = Executors.newSingleThreadScheduledExecutor(
        Thread.ofPlatform().name("deadlock-detector").daemon(true).factory());   // abandonable work

    public DeadlockDetector(Duration period, Consumer<String> alert) {
        timer.scheduleWithFixedDelay(() -> {
            try {
                long[] ids = mx.findDeadlockedThreads();               // null when there is none
                if (ids == null) return;
                StringBuilder report = new StringBuilder("Deadlock detected:\n");
                for (ThreadInfo info : mx.getThreadInfo(ids, true, true)) report.append(info);
                alert.accept(report.toString());
            } catch (RuntimeException e) {
                // swallow and keep running: an escaped exception cancels the schedule (L140)
            }
        }, period.toMillis(), period.toMillis(), TimeUnit.MILLISECONDS);
    }

    @Override public void close() { timer.shutdownNow(); }
}

Wire alert to your logger and a metric. ThreadInfo.toString() prints only the top few frames; loop over getStackTrace() for the full stack.

What breaks in production
  • Locks taken in data-dependent order. transfer(a, b) and transfer(b, a) at the same moment: the classic, and it only happens under load.
  • Pool-inside-pool. A task running on a pool submits a subtask to the same bounded pool and waits for it; when every worker does this, nobody is left to run subtasks (thread-starvation deadlock, L141).
  • No timeouts anywhere. Without lock, HTTP, JDBC and transaction timeouts, a cross-system cycle hangs until someone restarts the pod.

Immutability, Confinement & Thread-Safe Design

40m video40m practice

There are only three ways to make shared state safe: don't share it, don't mutate it, or synchronize every access to it. Good concurrent design chooses one of those deliberately for each piece of state, and writes the choice down where the next developer will see it.

The three strategies

Confinement: stack, thread, instance

  • Stack confinement. Local variables live in the thread's own stack frame, so they cannot be shared. An object created in a method and never stored in a field, passed to another thread, or returned is confined too, even a HashMap. Keep it that way: an innocent "cache it in a field" refactor breaks the confinement silently.
  • Thread confinement. State is reachable from many places but only touched by one thread. A ThreadLocal gives each thread its own copy (L149). A single-threaded event loop (Netty's event loops, a single-thread executor acting as an actor) owns its state; other threads submit tasks to it instead of touching the state.
  • Instance confinement. A non-thread-safe object is encapsulated in a class that never lets a reference escape, and every access goes through methods that hold the class's private lock. This is the Java monitor pattern, and it is how most thread-safe classes are written.
import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

/** Thread-safe: all state is confined to this instance and guarded by {@code lock}. */
public final class SessionRegistry {
    private final Object lock = new Object();
    @GuardedBy("lock") private final Map<String, Session> byId = new HashMap<>();   // never escapes
    @GuardedBy("lock") private long created;

    public Session open(String id) {
        synchronized (lock) {
            created++;
            return byId.computeIfAbsent(id, Session::new);   // Session is immutable: safe to return
        }
    }

    public Optional<Session> find(String id) {
        synchronized (lock) { return Optional.ofNullable(byId.get(id)); }
    }

    public Map<String, Session> snapshot() {
        synchronized (lock) { return Map.copyOf(byId); }    // a copy, never the guarded map itself
    }
}

record Session(String id) { }

@GuardedBy("lock") says which lock protects a field. It comes from the Java Concurrency in Practice annotations or, better, Error Prone (com.google.errorprone.annotations.concurrent.GuardedBy), whose compiler check flags any access made without holding the named lock. Pair it with class-level documentation of the thread-safety level.

Immutability

Definition · immutable class

An object is immutable if its state cannot change after construction, all its fields are final, and it is properly constructed (this does not escape the constructor). Effective Java Item 17 adds: no mutators, the class cannot be subclassed, fields are private, and any mutable component is copied in and never handed out.

import java.time.Instant;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

public record Order(String id, List<LineItem> items, Instant placedAt) {
    public Order {
        Objects.requireNonNull(id, "id");
        items = List.copyOf(items);               // defensive, unmodifiable copy: no outside alias
    }

    public Order withItem(LineItem extra) {       // "mutation" returns a new object
        var next = new ArrayList<>(items);
        next.add(extra);
        return new Order(id, next, placedAt);
    }
}

record LineItem(String sku, int qty) { }

Immutable objects are thread-safe with no locking, can be shared and cached freely, and, thanks to final-field semantics, are safe even if published through a data race (L128). The caveat is in the definition: final protects the reference, not the object it points to. A record holding a caller's ArrayList without List.copyOf is only as immutable as that caller's discipline.

Copy-on-write for mostly-read data

When reads vastly outnumber writes and the data is small, copy-on-write is the simplest scalable design: readers use the current immutable version with no lock; a writer copies, modifies the copy, and publishes it. CopyOnWriteArrayList does this for lists (perfect for listener lists: iteration never throws ConcurrentModificationException and sees a stable snapshot). For maps and configuration, a volatile reference to an immutable map, replaced on update, does the same (L129's RateTable). Every write costs a full copy, so this is wrong for large or write-heavy data (L145).

Delegating thread safety

A class can be thread-safe without any locking of its own if its state lives entirely in thread-safe components and there is no invariant linking them. Delegation fails the moment two components must change together.

import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.LongAdder;

/** Thread-safe by delegation: one thread-safe field, no cross-field invariant. */
final class PageHits {
    private final ConcurrentMap<String, LongAdder> hits = new ConcurrentHashMap<>();
    void hit(String page) { hits.computeIfAbsent(page, p -> new LongAdder()).increment(); }
    long count(String page) {
        LongAdder a = hits.get(page);
        return a == null ? 0 : a.sum();
    }
}

/** Deliberately broken: each field is thread-safe, the invariant lower <= upper is not. */
final class NumberRange {
    private final AtomicInteger lower = new AtomicInteger(0);
    private final AtomicInteger upper = new AtomicInteger(10);
    void setLower(int i) {                       // check-then-act across two variables
        if (i > upper.get()) throw new IllegalArgumentException("lower > upper");
        lower.set(i);
    }
    void setUpper(int i) {
        if (i < lower.get()) throw new IllegalArgumentException("upper < lower");
        upper.set(i);
    }
}

With the range at (0, 10), one thread calling setLower(5) and another setUpper(4) can both pass their checks and leave (5, 4). The fix is one lock over both fields, or one AtomicReference to an immutable Range record updated with a CAS.

Designing a thread-safe class

Algorithm · the design checklist
  1. Identify the state: every field, including the state of the objects fields refer to.
  2. Identify the invariants that constrain those variables, and the post-conditions of each operation. Variables in one invariant must be guarded by the same lock.
  3. Choose a policy for each piece of state: confined, immutable, guarded by a named lock, or delegated to a thread-safe component.
  4. Document it: the class's thread-safety level (immutable, unconditionally thread-safe, conditionally thread-safe, not thread-safe), which lock guards which field, and any locking clients must do themselves.
What breaks in production
  • Escaping internals. A getter returning the guarded HashMap itself hands callers unsynchronized access to it. Return a copy or an unmodifiable snapshot.
  • Undocumented policies. "Is this class thread-safe?" answered by reading the code: the next maintainer adds an unguarded field and nobody notices until load testing, or production.
  • Immutable-looking records. A record with a mutable list component that is shared and later modified.

The Executor Framework

45m video45m practice

An executor separates what to run (a task) from how it runs (which thread, when, how many at once). That separation is what lets you bound concurrency, reuse threads and shut down cleanly; it is also where the JDK's convenience factories quietly remove every bound.

Why raw threads don't scale

A thread per task works in a demo and fails under load. Each platform thread costs an OS thread, kernel bookkeeping and a stack reservation (about 1 MB by default), and creating one takes tens of microseconds. Nothing limits how many you create, so a traffic spike becomes thousands of threads, then memory pressure, then OutOfMemoryError: unable to create native thread, which usually takes the whole service down. There is also no queue to absorb bursts, no reuse, and no single place to stop everything at shutdown.

Executor, ExecutorService, ScheduledExecutorService

  • Executor: one method, void execute(Runnable). The task will run at some point, on some thread.
  • ExecutorService adds results and lifecycle: submit(Callable<T>) and submit(Runnable) return a Future (L141); invokeAll and invokeAny; shutdown, shutdownNow, awaitTermination, isShutdown, isTerminated; and since Java 19 it is AutoCloseable.
  • ScheduledExecutorService adds delayed and periodic execution: schedule, scheduleAtFixedRate, scheduleWithFixedDelay (L140).

The Executors factories, and why they are dangerous

The unbounded queue is the subtle one. When a fixed pool can't keep up, nothing fails; tasks just wait longer and memory climbs, so a latency problem becomes an outage hours later. In production, build a ThreadPoolExecutor yourself with a bounded queue, a named ThreadFactory and an explicit rejection policy (L138, L139). Spring's ThreadPoolTaskExecutor exposes the same knobs (queueCapacity, whose default is unbounded).

submit vs execute: the swallowed exception

import java.util.concurrent.*;

public class SwallowDemo {
    public static void main(String[] args) throws InterruptedException {
        try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
            pool.execute(() -> { throw new IllegalStateException("from execute"); });
            // ^ kills the worker; its uncaught-exception handler prints the stack trace

            Future<?> f = pool.submit(() -> { throw new IllegalStateException("from submit"); });
            // ^ prints nothing: the exception is stored inside the Future

            try {
                f.get();
            } catch (ExecutionException e) {
                System.out.println("only get() reveals it: " + e.getCause());
            }
        }
    }
}

execute runs your Runnable directly on the worker, so an exception escapes to the worker thread, reaches its uncaught-exception handler (L122), and the pool replaces the dead worker. submit wraps the task in a FutureTask that catches everything and stores it for get(). Fire-and-forget code that uses submit and never calls get() loses every failure silently. Either use execute for fire-and-forget tasks, wrap the task body in a try/catch that logs, or inspect the Future in afterExecute (L138).

Lifecycle and a correct shutdown

Definition · executor lifecycle
  • shutdown(): stop accepting new tasks (later submissions are rejected); already-queued and running tasks still complete. Returns immediately.
  • shutdownNow(): stop accepting, drain the queue and return the tasks that never started, and interrupt the running workers. Tasks that ignore interruption keep running (L124).
  • awaitTermination(t, unit): block until every task has finished after a shutdown, the timeout elapses (returns false), or the caller is interrupted.
  • close() (Java 19+): shutdown(), then wait for termination with no time limit; if interrupted while waiting, it calls shutdownNow() and keeps waiting. Ideal in try-with-resources for short-lived pools; wrong where shutdown must fit a deadline.
static void shutdownGracefully(ExecutorService pool, Duration grace) {
    pool.shutdown();                                            // 1. refuse new work, finish the queue
    try {
        if (!pool.awaitTermination(grace.toMillis(), TimeUnit.MILLISECONDS)) {
            List<Runnable> neverRan = pool.shutdownNow();      // 2. cancel the backlog, interrupt workers
            System.err.println(neverRan.size() + " queued tasks were dropped");
            if (!pool.awaitTermination(grace.toMillis(), TimeUnit.MILLISECONDS)) {
                System.err.println("pool did not terminate: a task is ignoring interrupts");
            }
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();                                     // we were interrupted: stop now
        Thread.currentThread().interrupt();                     // and keep the flag for our caller
    }
}

This is the pattern from the ExecutorService Javadoc. Call it from your shutdown hook (L125) with a grace period shorter than the orchestrator's.

From here on you will rarely write new Thread. You will create executors deliberately, give them names, bound them, monitor them (L139), and shut them down.

What breaks in production
  • One newCachedThreadPool per request. Pools are long-lived infrastructure; creating one per call leaks threads (and never shutting it down keeps the JVM alive).
  • A fixed pool in front of a slow dependency. The queue absorbs the slowdown invisibly, until the heap is full of pending tasks.
  • Lost failures. submit without get: the nightly job "succeeds" every night and has done nothing for a month.
  • No shutdown. Non-daemon pool threads keep the JVM alive after main returns, and on SIGTERM queued work is silently dropped.

ThreadPoolExecutor Internals & Sizing

50m video45m practice

ThreadPoolExecutor admits tasks by a fixed rule (core threads first, then the queue, then extra threads, then rejection), and the queue you pass in decides which of those steps ever happen. Size the pool from measured wait and service times, bound the queue, and instrument the hooks, and the pool becomes predictable.

The seven constructor parameters

ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8,                                         // corePoolSize: threads kept even when idle
    32,                                        // maximumPoolSize: hard ceiling on threads
    30, TimeUnit.SECONDS,                      // keepAliveTime + unit: idle time before an extra thread dies
    new ArrayBlockingQueue<>(500),            // workQueue: where tasks wait (bounded!)
    Thread.ofPlatform().name("pricing-", 0).factory(),     // threadFactory: names, daemon, handler
    new ThreadPoolExecutor.CallerRunsPolicy()  // handler: what happens when everything is full (L139)
);

The admission algorithm

So newFixedThreadPool(n), which is new ThreadPoolExecutor(n, n, 0, ms, new LinkedBlockingQueue<>()), never grows past n: its queue never refuses. Setting a large maximumPoolSize together with an unbounded queue is a classic mistake, because the maximum is unreachable. Two smaller details: until the pool reaches core size it starts a new thread for every task, even when existing threads are idle; and core threads are created lazily unless you call prestartAllCoreThreads() (or prestartCoreThread()), which is worth doing to avoid thread-creation latency on the first burst after a deploy.

keepAliveTime and allowCoreThreadTimeOut

Threads above the core size terminate after keepAliveTime without work, so the pool shrinks back after a burst. Core threads stay forever unless you call allowCoreThreadTimeOut(true), which applies the same timeout to them and lets an idle pool shrink to zero: useful for rarely used pools in a service with many of them, at the cost of re-creating threads on the next burst.

Sizing: formulas and measurement

Theorem · pool size (Goetz et al., §8.2)

To keep N CPUs at target utilisation U (0 to 1), with each task spending W waiting and C computing: threads ≈ N × U × (1 + W / C).

  • CPU-bound (W ≈ 0): about N + 1 threads. The extra one covers a thread stalled on a page fault or GC.
  • I/O-bound: with 8 cores, 10 ms of CPU and 90 ms waiting per task, W / C = 9 and threads ≈ 8 × 10 = 80 at full utilisation.

The formula is a starting point, not an answer. Two other limits usually bind first. Downstream capacity: 80 threads in front of a 20-connection database pool means 60 threads waiting for connections, which adds nothing. Little's law (L121): at the arrival rate and latency you must handle, how many tasks are in flight? Size for that, bound the queue at what you can tolerate as extra latency (queue length ÷ throughput = added wait), and load test.

To measure W/C, record wall-clock time and CPU time per task: ThreadMXBean.getCurrentThreadCpuTime() around the task (the pool below does this in its hooks), or a JFR or async-profiler recording in wall-clock vs CPU mode. W = wall − CPU.

Hooks: beforeExecute, afterExecute, context propagation

import java.lang.management.ManagementFactory;
import java.lang.management.ThreadMXBean;
import java.util.concurrent.*;
import java.util.concurrent.atomic.LongAdder;

public class InstrumentedPool extends ThreadPoolExecutor {
    private final ThreadMXBean mx = ManagementFactory.getThreadMXBean();
    private final ThreadLocal<long[]> start = new ThreadLocal<>();    // per worker: {wall, cpu}
    private final LongAdder wallNanos = new LongAdder(), cpuNanos = new LongAdder(), failures = new LongAdder();

    public InstrumentedPool(String name, int core, int max, int queueCapacity) {
        super(core, max, 30, TimeUnit.SECONDS, new ArrayBlockingQueue<>(queueCapacity),
              Thread.ofPlatform().name(name + "-", 0).factory(), new CallerRunsPolicy());
    }

    /** Captures the submitter's context; submit() also funnels through here. */
    @Override public void execute(Runnable task) {
        super.execute(new ContextTask(task, RequestContext.get()));
    }

    @Override protected void beforeExecute(Thread t, Runnable r) {
        start.set(new long[] {System.nanoTime(), mx.getCurrentThreadCpuTime()});
    }

    @Override protected void afterExecute(Runnable r, Throwable t) {
        long[] s = start.get();
        wallNanos.add(System.nanoTime() - s[0]);
        cpuNanos.add(mx.getCurrentThreadCpuTime() - s[1]);
        Runnable inner = r instanceof ContextTask c ? c.delegate() : r;
        if (t == null && inner instanceof Future<?> f && f.isDone()) {   // submit()ted task
            try { f.get(); }
            catch (ExecutionException e) { t = e.getCause(); }
            catch (CancellationException e) { /* cancelled, not failed */ }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
        if (t != null) failures.increment();                    // and log it: never lose a failure
    }

    /** Measured W/C for the sizing formula. */
    public double waitToCompute() {
        long cpu = cpuNanos.sum();
        return cpu == 0 ? 0 : (double) (wallNanos.sum() - cpu) / cpu;
    }

    record ContextTask(Runnable delegate, String requestId) implements Runnable {
        public void run() {
            String previous = RequestContext.get();             // CallerRunsPolicy may run us on the
            RequestContext.set(requestId);                      // submitter's own thread, so save...
            try { delegate.run(); } finally { RequestContext.restore(previous); }   // ...and restore
        }
    }
}

final class RequestContext {                                   // stands in for SLF4J's MDC here
    private static final ThreadLocal<String> ID = new ThreadLocal<>();
    static String get() { return ID.get(); }
    static void set(String id) { ID.set(id); }
    static void restore(String previous) {
        if (previous == null) ID.remove(); else ID.set(previous);    // never leak to the next task
    }
}

beforeExecute and afterExecute run on the worker thread around every task, which makes them the place for timing and failure metrics. They cannot see the submitter's thread-locals, so context such as an MDC correlation ID must be captured at submission and restored in a wrapper, as ContextTask does (with SLF4J: MDC.getCopyOfContextMap() and setContextMap; L149, L288). Restore the previous value rather than clearing it: with CallerRunsPolicy the wrapper can run on the submitting thread itself, and a blind clear() would wipe the caller's own context. Note that afterExecute's Throwable is null for submitted tasks; the failure is inside the Future.

What breaks in production
  • Max with an unbounded queue. "We set max to 200" and the pool has run 10 threads for a year while the queue held 50,000 tasks.
  • One pool size for every environment. A pool sized for a 32-core server, deployed in a 2-CPU container, oversubscribes the CPU by 16×; derive sizes from availableProcessors() and measured W/C.
  • Context leaks. Setting a thread-local in a task and not clearing it in finally leaks one user's ID into the next user's logs, or worse, their security context.

Rejection Policies, Backpressure & Pool Monitoring

35m video40m practice

Every system receives more work than it can do at some point. A bounded pool turns that moment into an explicit decision (fail, slow the producer, or drop) that you choose with a rejection policy and watch with metrics. An unbounded pool makes the decision for you, later, as an out-of-memory error.

Why unbounded queues turn latency into OOM

If tasks arrive at λ per second and the pool completes μ per second with λ > μ, an unbounded queue grows by λ − μ every second, forever. At 1,000 arrivals and 800 completions per second, that is 720,000 queued tasks after an hour; if each holds a 10 KB request payload, about 7 GB of heap. Long before memory runs out, latency is absurd: a new task waits queue length ÷ μ, here 900 seconds, for a response its client gave up on after 30. A bounded queue converts the same overload into immediate, visible rejections that callers can retry, shed or route elsewhere.

Definition · backpressure

Backpressure is any mechanism by which a saturated consumer slows down or refuses its producers, so that overload is felt where the work originates instead of being absorbed invisibly in a buffer. In a thread pool the mechanisms are a bounded queue plus a rejection policy, or a bound on submission itself. Without one, the queue between producer and consumer is the system's real, unmonitored capacity limit.

The four built-in handlers

PolicyOn saturationUse when
AbortPolicy (default)throws RejectedExecutionException to the submitterthe caller can fail fast (HTTP 503, retry with backoff)
CallerRunsPolicyruns the task on the submitting threadproducers can be slowed down: natural backpressure
DiscardPolicydrops the task silentlyalmost never: invisible data loss
DiscardOldestPolicydrops the oldest queued task and retries the new one"latest value wins" feeds (telemetry); never with a priority queue

CallerRunsPolicy deserves its reputation. While the producer thread is busy running a task itself, it cannot submit more, so the arrival rate drops to what the system can handle, automatically. Know its costs: the task runs outside the pool, so pool hooks, thread names and pool thread-locals don't apply; a caller that is a request thread now takes longer to respond; and a caller that is an event-loop thread (Netty, WebFlux) must never block, so this policy is wrong there. After shutdown() it discards instead.

Blocking the producer with a semaphore

A RejectedExecutionHandler that blocks by calling executor.getQueue().put(r) is a common hack and a fragile one: it bypasses the pool's shutdown checks and its thread-creation logic, and it blocks inside execute with no timeout. The robust way to make producers wait is to bound submission with a Semaphore, so the pool itself never needs to reject.

import java.time.Duration;
import java.util.concurrent.*;

/** Callers wait (up to a timeout) while 'bound' tasks are queued or running. */
public final class BoundedSubmitter {
    private final Executor executor;
    private final Semaphore permits;

    /** bound must not exceed the pool's max threads + queue capacity, or the pool can still reject. */
    public BoundedSubmitter(Executor executor, int bound) {
        this.executor = executor;
        this.permits = new Semaphore(bound);
    }

    public boolean submit(Runnable task, Duration maxWait) throws InterruptedException {
        if (!permits.tryAcquire(maxWait.toMillis(), TimeUnit.MILLISECONDS)) {
            return false;                                     // saturated for too long: shed the load
        }
        try {
            executor.execute(() -> {
                try { task.run(); } finally { permits.release(); }   // freed when the task ends
            });
            return true;
        } catch (RejectedExecutionException e) {
            permits.release();                                // never leak a permit
            throw e;
        }
    }
}

If you still want a custom handler, make it observable: count the rejection, include the pool's state in the exception message, then abort.

final class CountingAbortPolicy implements RejectedExecutionHandler {
    final LongAdder rejected = new LongAdder();

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor pool) {
        rejected.increment();
        throw new RejectedExecutionException("saturated: active=" + pool.getActiveCount()
            + " queued=" + pool.getQueue().size() + " max=" + pool.getMaximumPoolSize());
    }
}

Instrumenting a pool

  • getPoolSize() (threads now), getLargestPoolSize() (high-water mark: did we ever reach max?), getCorePoolSize(), getMaximumPoolSize().
  • getActiveCount(): approximately how many threads are running tasks right now. Active equal to max for minutes means saturation.
  • getQueue().size() and getQueue().remainingCapacity(): the backlog, and how close the pool is to rejecting.
  • getTaskCount() and getCompletedTaskCount(): approximate totals; their rates give throughput.

Several of these take the pool's main lock, so sample them every few seconds, not per task. In Micrometer (L410), one call registers them as gauges and counters:

import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Tags;
import io.micrometer.core.instrument.binder.jvm.ExecutorServiceMetrics;

    static void register(MeterRegistry registry, ThreadPoolExecutor pool, String name) {
        // registers executor.active, executor.queued, executor.queue.remaining,
        // executor.pool.size, executor.pool.max, executor.completed ... tagged name=<name>

Alerting on saturation

Alert on symptoms of saturation, not raw thread counts: queue fill ratio (queued ÷ (queued + remaining)) above about 80% for several minutes; any sustained rate of rejections; active threads at max for minutes; and task wait time (time from submit to start, recorded in a wrapper) above your latency budget. Wait time is the most direct: it is the latency the pool adds.

One shared pool, or a pool per bounded context?

A single shared pool is simple and uses threads efficiently, but one slow dependency can occupy every thread and starve unrelated work: the noisy-neighbour failure. Separate pools per downstream dependency or per bounded context are bulkheads: when the payment provider slows down, only the payment pool saturates, and catalog requests keep flowing. Use separate pools for different dependencies, for different priority classes, and for blocking vs CPU-bound work; avoid dozens of tiny pools, which waste memory and together oversubscribe the CPU. Resilience4j's bulkheads package the same idea.

What breaks in production
  • DiscardPolicy anywhere. Work vanishes without a log line, a metric or an error.
  • CallerRunsPolicy on an event loop. One saturated pool stalls every connection that loop serves.
  • Rejection treated as a bug. Catching RejectedExecutionException and retrying immediately in a tight loop turns backpressure into a CPU spike. Back off, or shed.
  • Monitoring the wrong number. CPU is at 20%, so "the service is fine", while the pool in front of a slow database is at max with a full queue.

ScheduledExecutorService & Recurring Work

35m video35m practice

A scheduled executor runs tasks later or repeatedly, on a monotonic clock, inside one JVM. Know three behaviours before you rely on it: fixed-rate tasks catch up in bursts after an overrun, a single uncaught exception silently ends a periodic task forever, and nothing about it survives a restart or coordinates across instances.

schedule, scheduleAtFixedRate, scheduleWithFixedDelay

ScheduledExecutorService ses = Executors.newScheduledThreadPool(2,
    Thread.ofPlatform().name("sched-", 0).factory());

ScheduledFuture<?> once  = ses.schedule(() -> System.out.println("in 5 s"), 5, TimeUnit.SECONDS);
ScheduledFuture<?> rate  = ses.scheduleAtFixedRate(this::pollPrices, 0, 1, TimeUnit.SECONDS);
ScheduledFuture<?> delay = ses.scheduleWithFixedDelay(this::syncInventory, 0, 30, TimeUnit.SECONDS);
Definition · rate vs delay
  • Fixed rate: executions are due at initialDelay + k × period. Each due time is computed from the previous due time, not from when the run finished.
  • Fixed delay: each execution starts delay after the previous one ended.
  • Either way, a periodic task never runs concurrently with itself: if a run is still going when the next is due, the next waits.

Choose fixed delay for anything that calls another system (polling, syncing, cleanup): it guarantees a gap and cannot hammer a dependency that just recovered. Choose fixed rate only when executions are cheap and the count matters (a metrics tick that must fire 60 times a minute), and make sure a burst is harmless. A long GC pause or a laptop waking from sleep produces the same catch-up burst.

The exception that eats production jobs

The ScheduledExecutorService Javadoc states it plainly: if any execution of a periodic task throws, subsequent executions are suppressed. The exception is stored in the ScheduledFuture, nothing is logged, and the job simply never runs again. One NullPointerException on one bad record at 03:00 and the nightly reconciliation is dead until someone notices the data is stale.

/** Wrap every periodic task: one escaped exception cancels the schedule forever. */
static Runnable guarded(String name, Runnable body) {
    return () -> {
        try {
            body.run();
        } catch (Exception e) {
            System.err.println(name + " failed; will run again next period: " + e);   // log + metric
        }
        // Errors (OutOfMemoryError…) still escape and stop the schedule, which is usually right
    };
}

ScheduledFuture<?> job = ses.scheduleWithFixedDelay(guarded("inventory-sync", this::syncInventory),
    0, 30, TimeUnit.SECONDS);

As a second line of defence, something should watch the future: get() on a periodic ScheduledFuture blocks forever while the task is healthy and throws ExecutionException when it dies, so a watchdog thread (or a health check reading isDone()) can alert.

Cancelling scheduled work

future.cancel(false) stops future executions and lets a running one finish; cancel(true) also interrupts it. Cancelled tasks stay in the executor's queue until their due time unless you call setRemoveOnCancelPolicy(true) on the ScheduledThreadPoolExecutor; with many long-delay tasks cancelled (timeouts that never fire, for example) that retention is a memory leak. shutdown() by default still runs pending delayed tasks but cancels periodic ones; both behaviours are configurable through setExecuteExistingDelayedTasksAfterShutdownPolicy and setContinueExistingPeriodicTasksAfterShutdownPolicy.

Clocks, clock changes and DST

The scheduled executor measures time with System.nanoTime(), a monotonic clock. That is good: an NTP step or someone changing the system clock does not make tasks fire early, late or twice. It also means "every 24 hours" is not "every day at 02:00": after a daylight-saving change, a 24-hour period lands at 01:00 or 03:00 local time. For wall-clock schedules, compute each run's delay from the calendar and schedule one run at a time:

static void scheduleDaily(ScheduledExecutorService ses, LocalTime at, ZoneId zone, Runnable job) {
    ZonedDateTime now = ZonedDateTime.now(zone);
    ZonedDateTime next = now.with(at);                    // in a DST gap, resolves to a later valid time
    if (!next.isAfter(now)) next = next.plusDays(1);      // plusDays keeps the local time across DST
    ses.schedule(() -> {
        try {
            job.run();
        } finally {
            scheduleDaily(ses, at, zone, job);            // recompute from the calendar every time
        }
    }, Duration.between(now, next).toMillis(), TimeUnit.MILLISECONDS);
}

Even this has edge cases: 02:30 does not exist on spring-forward night (it resolves to 03:30), and 01:30 happens twice on fall-back night. Real cron schedulers have explicit rules for both, which is one more reason to use one.

Callable, Future, invokeAll & Cancellation

40m video40m practice

A Future is a handle to a result that doesn't exist yet: you can wait for it, with or without a deadline, ask whether it's done, or cancel it. Its weakness is that the only way to use the result is to block, and blocking on a pool from inside the same pool is the most common way to deadlock one.

Callable vs Runnable

Runnable.run() returns nothing and cannot throw checked exceptions. Callable<V>.call() returns a V and declares throws Exception, so a task can fail with an IOException without wrapping it. submit(Callable) returns a Future<V>; submit(Runnable) returns a Future<?> whose result is null. A lambda becomes whichever interface fits: one that returns a value or throws a checked exception is a Callable.

Definition · the Future contract
  • get() blocks until the task completes and returns its result; get(timeout, unit) throws TimeoutException if it isn't done in time (the task keeps running).
  • If the task threw, get throws ExecutionException with the original exception as its cause. If it was cancelled, get throws the unchecked CancellationException.
  • isDone() is true once the task completed normally, exceptionally or by cancellation; isCancelled() only for the last.
  • cancel(mayInterruptIfRunning): a task that hasn't started will never run; a running one is interrupted only if the argument is true, and stops only if it honours interruption (L124). It returns false if the task had already completed.
  • Java 19 added state() (RUNNING, SUCCESS, FAILED, CANCELLED), resultNow() and exceptionNow() for inspecting completed futures without try/catch.

Completing a task happens-before get returns, so the caller sees everything the task wrote.

Unwrapping ExecutionException

static <T> T await(Future<T> f, Duration timeout) throws InterruptedException, TimeoutException {
    try {
        return f.get(timeout.toMillis(), TimeUnit.MILLISECONDS);
    } catch (ExecutionException e) {
        Throwable cause = e.getCause();                       // the exception the task threw
        if (cause instanceof RuntimeException re) throw re;
        if (cause instanceof Error err) throw err;
        throw new IllegalStateException("task failed", cause);   // a checked exception from call()
    } catch (TimeoutException e) {
        f.cancel(true);                                       // don't leave abandoned work running
        throw e;
    }
}

Never log or rethrow the ExecutionException itself as the error: its message is the cause's toString(), and its stack trace shows where you called get, not where the task failed. The cause's stack trace shows the worker's frames instead, so when you rethrow it, consider wrapping it (as the last line does) to keep both. And when you give up waiting, cancel: a timed-out get does not stop the task.

get() blocks: the thread-starvation deadlock

// Deliberately broken: thread-starvation deadlock.
ExecutorService pool = Executors.newFixedThreadPool(2);
Callable<String> page = () -> {
    Future<String> header = pool.submit(() -> "header");   // queued behind the outer tasks
    return header.get() + " + body";                        // waits for a worker that never frees up
};
pool.submit(page);
pool.submit(page);       // both workers now wait for tasks that can only run on... those workers

Both workers are busy running page, each blocked in get() on a subtask that sits in the queue behind them. Nothing will ever complete. The same thing happens with any pool size once enough outer tasks wait on inner ones, and it looks like a hang with every pool thread WAITING in FutureTask.get. Fixes: never block on a task submitted to the same bounded pool; use separate pools for dependent stages; use a timeout so the failure is at least visible; or compose asynchronously instead of blocking (L142). Fork/join solves the recursive case differently (L144).

invokeAll, invokeAny and timeouts

  • invokeAll(tasks) submits all, waits until every one has completed, and returns the futures in the same order as the tasks, all done.
  • invokeAll(tasks, timeout, unit) returns when all complete or the timeout expires; tasks still running are cancelled, so their futures report CANCELLED.
  • invokeAny(tasks) returns the result of one task that completed successfully (typically the first) and cancels the rest; it throws ExecutionException only if all of them failed. With a timeout it throws TimeoutException.
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.*;

public class QuoteAggregator {
    record Quote(String vendor, long cents) { }

    /** Asks every vendor; keeps whatever answered within 800 ms. */
    static List<Quote> quotes(ExecutorService pool, List<Callable<Quote>> vendors) throws InterruptedException {
        List<Future<Quote>> futures = pool.invokeAll(vendors, 800, TimeUnit.MILLISECONDS);
        List<Quote> result = new ArrayList<>();
        for (Future<Quote> f : futures) {
            switch (f.state()) {                                   // Java 19+
                case SUCCESS   -> result.add(f.resultNow());
                case FAILED    -> System.err.println("vendor failed: " + f.exceptionNow());
                case CANCELLED -> System.err.println("vendor timed out and was cancelled");
                case RUNNING   -> throw new AssertionError("invokeAll returns completed futures only");
            }
        }
        return result;
    }

    /** Asks every mirror for the same data; the first successful answer wins. */
    static String fastestMirror(ExecutorService pool, List<Callable<String>> mirrors)
            throws InterruptedException, ExecutionException, TimeoutException {
        return pool.invokeAny(mirrors, 2, TimeUnit.SECONDS);     // losers are cancelled
    }
}

FutureTask internals

FutureTask is the Runnable that submit actually queues. It holds a volatile int state, the Callable, an outcome field (the result or the exception), the runner thread (set by CAS, so run() executes at most once even if called twice) and a Treiber stack (L130) of waiting threads. get() on an incomplete task pushes a node and parks; completion writes outcome, publishes it with the state write, and unparks every waiter. Its run() catches every Throwable from the task into outcome, which is precisely why submit swallows exceptions (L137).

What Future cannot do

You cannot attach a callback ("when done, do X"), so someone must block or poll. You cannot chain ("then call B with A's result") or combine ("when both A and B are done") without parking a thread per step. You cannot complete one yourself from another source, such as a message arriving. There is no exception-handling pipeline, and cancelling a future does not cancel the work that depends on it. Every one of those gaps is filled by CompletableFuture, next lesson.

What breaks in production
  • Untimed get() on a remote call. One downstream hang and the calling thread waits forever; enough of them and the request pool is exhausted.
  • Timeout without cancel. The caller gave up, but the work keeps running and consuming a worker, so retries pile on top of abandoned attempts.
  • Nested submission to the same pool. The thread-starvation deadlock above, which only appears when the pool is busy.
  • Logging the wrapper. Alerts that say "ExecutionException" with the caller's stack and no hint of what failed.

CompletableFuture I: Creation & Chaining

45m video50m practice

A CompletableFuture is a Future you can complete yourself and attach callbacks to, so a chain of dependent steps runs as each result arrives instead of parking a thread per step. Master two things and the API stops being 50 confusing methods: map (thenApply) vs flatMap (thenCompose), and which thread runs each callback.

Creating one

  • CompletableFuture.completedFuture(v): already done; useful for cache hits and tests. failedFuture(t) (Java 9) is the failed equivalent.
  • supplyAsync(supplier, executor): runs the supplier on the executor and completes with its value. runAsync(runnable, executor): the same with no value (CompletableFuture<Void>).
  • new CompletableFuture<>() plus complete(v) / completeExceptionally(t): you decide when it completes. Only the first completion wins; later calls return false. This is how you adapt callback-style APIs.
interface Callback { void onSuccess(String value); void onError(Throwable error); }
interface LegacyClient { void fetch(String id, Callback cb); }

final class Adapters {
    /** Bridges a callback API into a CompletableFuture. */
    static CompletableFuture<String> fetch(LegacyClient client, String id) {
        CompletableFuture<String> cf = new CompletableFuture<>();
        client.fetch(id, new Callback() {
            public void onSuccess(String value) { cf.complete(value); }
            public void onError(Throwable error) { cf.completeExceptionally(error); }
        });
        return cf;                                  // returned at once; completed later by the client's thread
    }
}

The common pool, and why you pass your own executor

Definition · default async execution

Every *Async method without an executor argument runs on ForkJoinPool.commonPool(): one JVM-wide pool, sized to roughly the number of cores minus one, shared with parallel streams and anything else that uses it, made of daemon threads. If its parallelism is below 2 (a one- or two-CPU container), CompletableFuture instead starts a new thread for every async task.

That is the right home for short CPU-bound work and the wrong one for anything that blocks. Put a blocking HTTP or JDBC call in supplyAsync(supplier) and a handful of slow requests occupy every common-pool thread, stalling every parallel stream and every other async stage in the JVM; and because the threads are daemons, in-flight work is abandoned at shutdown. Always pass a dedicated, bounded, named executor for I/O (or a virtual-thread executor, L150), and keep it per dependency when isolation matters (L139).

thenApply, thenCompose, thenAccept, thenRun

Using thenApply with a function that itself returns a future gives you a CompletableFuture<CompletableFuture<Receipt>>: a future of a future, which callers must unwrap with a blocking join().join(). Whenever the next step returns a future, use thenCompose, exactly as you would use flatMap on an Optional or a Stream.

Which thread runs the callback

  • A non-async callback (thenApply) runs on whichever thread completes the previous stage; if that stage is already complete when you attach the callback, it runs immediately on your thread, inside the thenApply call.
  • thenApplyAsync(fn) always submits the callback to the common pool; thenApplyAsync(fn, executor) to the executor you name.
import java.util.concurrent.*;

public class WhichThread {
    static String where(String step) { return step + "@" + Thread.currentThread().getName(); }

    public static void main(String[] args) {
        ExecutorService io  = Executors.newFixedThreadPool(2, Thread.ofPlatform().name("io-", 0).factory());
        ExecutorService cpu = Executors.newFixedThreadPool(2, Thread.ofPlatform().name("cpu-", 0).factory());
        try {
            String chain = CompletableFuture
                .supplyAsync(() -> { pause(100); return where("supply"); }, io)
                .thenApply(s -> s + " " + where("thenApply"))              // the completing thread: io-0
                .thenApplyAsync(s -> s + " " + where("thenApplyAsync"), cpu) // hops to cpu-0
                .join();
            System.out.println(chain);

            String early = CompletableFuture.completedFuture("x")
                .thenApply(s -> where("already done"))                    // runs right here, on main
                .join();
            System.out.println(early);
        } finally {
            io.shutdown();
            cpu.shutdown();
        }
    }

    static void pause(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

A non-blocking service call chain

import java.util.concurrent.*;

record User(String id, String tier) { }
record Receipt(String userId, long chargedCents) { }

final class CheckoutService {
    private final ExecutorService io = new ThreadPoolExecutor(16, 16, 0, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1_000), Thread.ofPlatform().name("checkout-io-", 0).factory());

    CompletableFuture<User> findUser(String id) {                  // async: a remote call
        return CompletableFuture.supplyAsync(() -> new User(id, "gold"), io);
    }

    CompletableFuture<Receipt> charge(User u, long cents) {        // async: another remote call
        return CompletableFuture.supplyAsync(() -> new Receipt(u.id(), cents), io);
    }

    long discounted(User u, long cents) {                          // plain, cheap, synchronous
        return u.tier().equals("gold") ? cents * 9 / 10 : cents;
    }

    CompletableFuture<Receipt> checkout(String userId, long cents) {
        return findUser(userId)
            .thenCompose(u -> charge(u, discounted(u, cents)))        // flatMap: charge returns a future
            .thenApply(r -> { System.out.println("charged " + r); return r; });   // map
    }
}

No thread blocks anywhere in checkout: it returns immediately with a future that completes when the charge does. The caller (a controller returning CompletableFuture, say) never parks a request thread.

join() vs get()

Both block until completion. get() throws the checked InterruptedException and ExecutionException, and responds to interruption; get(timeout, unit) adds a deadline. join() throws the unchecked CompletionException (cause inside) or CancellationException and is not interruptible, which makes it convenient inside lambdas and in tests, and dangerous on any thread that must stay cancellable. getNow(fallback) never blocks. Whichever you use, block only at the edge of the system (a main, a test, a legacy synchronous API), never in the middle of a chain.

What breaks in production
  • Blocking I/O on the common pool. supplyAsync(() -> restTemplate.getForObject(…)) with no executor; under load every parallel stream in the JVM stalls behind it.
  • Futures of futures. thenApply where thenCompose was needed, followed by a blocking join() inside a callback to unwrap it.
  • Heavy work in a non-async callback. It runs on the completer's thread, perhaps an HTTP client's selector thread, and stalls every other response it should be delivering.
  • Uncancellable waits. join() on a request thread ignores interrupts, so timeouts and shutdowns can't free it.

CompletableFuture II: Combining, Errors & Timeouts

45m video50m practice

Real backend code fans out to several services and fans the answers back in, with a deadline on each call and a fallback when one fails. CompletableFuture has a combinator for each of those needs; the skill is knowing how failures flow through a chain, so that one slow dependency degrades a response instead of sinking it, and no exception disappears.

Combining two stages, or racing them

  • a.thenCombine(b, (x, y) -> …): when both complete, combine their results. thenAcceptBoth consumes both; runAfterBoth just runs afterwards.
  • a.applyToEither(b, x -> …): use whichever completes first; acceptEither and runAfterEither are the consuming variants. Caveat from the CompletionStage spec: if the first to finish fails, the result may fail too. For "first success wins", recover each input first, or use invokeAny (L141).
CompletableFuture<Integer> stock = CompletableFuture.supplyAsync(() -> 12, io);
CompletableFuture<Long> price    = CompletableFuture.supplyAsync(() -> 1_999L, io);
CompletableFuture<String> offer  = stock.thenCombine(price, (s, p) -> s + " left at " + p + " cents");

CompletableFuture<String> primary = CompletableFuture.supplyAsync(() -> "eu-west answer", io);
CompletableFuture<String> replica = CompletableFuture.supplyAsync(() -> "us-east answer", io);
CompletableFuture<String> fastest = primary.applyToEither(replica, answer -> answer);   // hedged request

allOf and anyOf

allOf(cfs…) returns a CompletableFuture<Void> that completes when all inputs have completed, exceptionally if any of them did. It carries no results, so read them from the inputs afterwards, where join() can no longer block. anyOf(cfs…) completes with the first input to complete, success or failure, typed as Object.

static <T> CompletableFuture<List<T>> allAsList(List<CompletableFuture<T>> futures) {
    return CompletableFuture.allOf(futures.toArray(CompletableFuture[]::new))
        .thenApply(done -> futures.stream().map(CompletableFuture::join).toList());   // all complete: no blocking
}

Handling errors: exceptionally, handle, whenComplete, exceptionallyCompose

Definition · propagation rules
  • When a stage completes exceptionally, every dependent stage that does not handle exceptions (thenApply, thenCompose, thenCombine…) is skipped and completes exceptionally too, with a CompletionException whose cause is the original exception.
  • A handler may therefore receive the original exception (if it is attached directly to the stage that failed) or a CompletionException wrapping it (if it is further down). Unwrap before inspecting the type.
  • After a handler recovers, the chain continues normally from the recovered value.

    return (t instanceof CompletionException || t instanceof ExecutionException) && t.getCause() != null

}

CompletableFuture<String> profile = CompletableFuture.supplyAsync(() -> fetchProfile("u42"), io)
    .exceptionallyCompose(ex -> CompletableFuture.supplyAsync(() -> fetchProfileFromCache("u42"), io))

Timeouts: orTimeout, completeOnTimeout, and before Java 9

orTimeout(t, unit) completes the future exceptionally with TimeoutException if it is not done in time; completeOnTimeout(value, t, unit) completes it with a default value instead. Both modify the future they are called on and return it. Caveats: they do not cancel the underlying work (the remote call needs its own client timeout too); and the timeout fires on one daemon thread shared by every CompletableFuture in the JVM, so non-async stages triggered by it run on that thread and must stay trivial.

/** Java 8 equivalent of orTimeout: complete with TimeoutException from a scheduler. */
static <T> CompletableFuture<T> within(CompletableFuture<T> f, Duration d, ScheduledExecutorService timer) {
    ScheduledFuture<?> alarm = timer.schedule(
        () -> f.completeExceptionally(new TimeoutException("after " + d)), d.toMillis(), TimeUnit.MILLISECONDS);
    f.whenComplete((v, ex) -> alarm.cancel(false));     // finished in time: disarm the alarm
    return f;
}

Fan-out / fan-in with per-call fallbacks

import java.util.List;
import java.util.concurrent.*;
import java.util.function.Supplier;

public class DashboardService {
    record Dashboard(String profile, List<String> orders, int points, List<String> recs, String weather) { }

    private final ExecutorService io = Executors.newFixedThreadPool(10, Thread.ofPlatform().name("dash-io-", 0).factory());

    CompletableFuture<Dashboard> dashboard(String user) {
        var profile = call("profile", () -> slow(50, "Ada"), "guest");
        var orders  = call("orders",  () -> slow(120, List.of("o-1", "o-2")), List.<String>of());
        var points  = call("loyalty", () -> { throw new IllegalStateException("loyalty down"); }, 0);
        var recs    = call("recs",    () -> slow(900, List.of("book")), List.<String>of());   // too slow
        var weather = call("weather", () -> slow(30, "sunny"), "n/a");
        return CompletableFuture.allOf(profile, orders, points, recs, weather)     // fan-in: all settled
            .thenApply(done -> new Dashboard(profile.join(), orders.join(), points.join(),
                                             recs.join(), weather.join()));
    }

    /** One downstream call: its own deadline and its own fallback, so it can never fail the page. */
    private <T> CompletableFuture<T> call(String name, Supplier<T> remote, T fallback) {
        return CompletableFuture.supplyAsync(remote, io)
            .orTimeout(300, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> {
                System.err.println(name + " degraded: " + ex);       // log + metric per dependency
                return fallback;
            });
    }

    static <T> T slow(long ms, T value) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return value;
    }

    public static void main(String[] args) {
        var svc = new DashboardService();
        System.out.println(svc.dashboard("u42").join());   // ~300 ms: recs and loyalty fall back
        svc.io.shutdownNow();                               // the abandoned 900 ms call is interrupted
    }
}

Total latency is bounded by the slowest deadline, not the slowest dependency, and the page renders with whatever arrived in time.

Debugging asynchronous chains

  • Lost exceptions. A chain ending in thenAccept that nobody joins swallows any failure upstream. End every fire-and-forget chain with whenComplete (or exceptionally) that logs, or return the future to something that will.
  • Stack traces without context. The trace shows a pool thread's frames, not the request that started the chain. Put the context in the message when you rethrow ("orders for u42"), and rely on distributed tracing (L411) for causality.
  • MDC propagation. MDC is thread-local, and every stage may run on a different thread, so log lines lose their correlation ID. Wrap the executor so each task carries the submitter's MDC:
import java.util.Map;
import java.util.concurrent.Executor;
import org.slf4j.MDC;

final class MdcExecutors {
    static Executor propagating(Executor delegate) {
        return task -> {
            Map<String, String> captured = MDC.getCopyOfContextMap();     // on the submitting thread
            delegate.execute(() -> {
                Map<String, String> previous = MDC.getCopyOfContextMap();
                if (captured == null) MDC.clear(); else MDC.setContextMap(captured);
                try {
                    task.run();
                } finally {
                    if (previous == null) MDC.clear(); else MDC.setContextMap(previous);
                }
            });
        };
    }
}

This covers async stages given that executor; non-async stages inherit whatever MDC the completing thread has. Micrometer's context-propagation library and OpenTelemetry's executor wrappers generalise the idea (L149).

What breaks in production
  • One timeout on the whole fan-out. A single slow dependency times out the entire page instead of one widget.
  • Type checks on wrapped exceptions. ex instanceof NotFoundException is false because ex is a CompletionException; unwrap first.
  • Timeouts that don't stop work. orTimeout fires, the user gets a fallback, and the pool stays full of calls still waiting on the slow service.
  • anyOf for "first success". The first failure wins just as readily.

Fork/Join, RecursiveTask & Work Stealing

40m video45m practice

Fork/join parallelises divide-and-conquer: split a problem until the pieces are small, solve the pieces sequentially, combine. ForkJoinPool makes that cheap with per-worker deques and work stealing, so a waiting join() helps instead of blocking; and it is built for CPU work, which is exactly why blocking I/O in it goes so badly.

Divide and conquer with RecursiveTask and RecursiveAction

A ForkJoinTask is a lightweight task, much cheaper than a thread. Subclass RecursiveTask<V> when the computation returns a value, RecursiveAction when it doesn't, and put the algorithm in compute(): if the problem is below a threshold, solve it directly; otherwise split it, fork() some parts (schedule them asynchronously), compute one part in the current thread, and join() the forked parts. Forking happens-before the subtask starts, and the subtask's completion happens-before join returns, so results flow back with no extra synchronization.

import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveTask;

final class SumTask extends RecursiveTask<Long> {
    static final int THRESHOLD = 10_000;          // measure this; see below
    private final long[] a;
    private final int lo, hi;

    SumTask(long[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }

    @Override
    protected Long compute() {
        if (hi - lo <= THRESHOLD) {                // small enough: plain sequential loop
            long s = 0;
            for (int i = lo; i < hi; i++) s += a[i];
            return s;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left = new SumTask(a, lo, mid);
        SumTask right = new SumTask(a, mid, hi);
        right.fork();                             // 1. fork right: onto this worker's deque
        long l = left.compute();                  // 2. compute left here, no scheduling cost
        return l + right.join();                  // 3. join right: often we just pop and run it ourselves
    }

    static long sum(long[] a) {
        return ForkJoinPool.commonPool().invoke(new SumTask(a, 0, a.length));
    }
}

The fork/join protocol, and getting the order right

Algorithm · fork right, compute left, join right
  1. If the problem is below the threshold, solve it sequentially and return.
  2. Split it; fork the right part (push it onto this worker's deque, where a thief may take it).
  3. Compute the left part directly in the current thread.
  4. Join the right part (if nobody stole it, pop it and run it here), then combine.

Computing one half directly keeps the current worker busy instead of handing both halves to the scheduler. Joining in reverse order of forking means the task you join is usually still on top of your own deque, so join() pops and runs it without any synchronization. The common mistakes are left.fork(); right.fork(); left.join(); right.join();, which wastes the current thread and joins the deeper task first, and a.fork(); a.join(); b.fork(); b.join();, which is just a slow sequential program. invokeAll(left, right) applies the correct protocol for you.

Work-stealing deques

A single shared queue (as in ThreadPoolExecutor) makes every worker contend on one lock for every tiny subtask, and gives no locality. Per-worker deques avoid both. They also solve L141's thread-starvation problem for recursive work: a worker waiting in join() on a stolen task does not simply block, it looks for other work to run (helping), and the pool can add a compensating thread when a worker really must wait.

Choosing a sequential threshold, and measuring it

Too small a threshold and task creation and scheduling cost more than the work; too large and there are too few pieces to balance across cores, so one slow chunk finishes last while others idle. The ForkJoinTask Javadoc's rule of thumb is that a leaf should perform roughly 100 to 10,000 basic computational steps. Start there, then measure: run the task with thresholds a factor of 4 apart under JMH (L168) and pick the flat bottom of the curve. Compare with the plain sequential loop too: for a sum over a few thousand elements, parallelism loses outright.

Parallel merge sort

import java.util.Arrays;
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveAction;

final class ParallelMergeSort extends RecursiveAction {
    static final int THRESHOLD = 8_192;
    private final int[] a, buf;                   // tasks write disjoint ranges: no data race
    private final int lo, hi;

    private ParallelMergeSort(int[] a, int[] buf, int lo, int hi) {
        this.a = a; this.buf = buf; this.lo = lo; this.hi = hi;
    }

    static void sort(int[] a) {
        try (ForkJoinPool pool = new ForkJoinPool(Runtime.getRuntime().availableProcessors())) {
            pool.invoke(new ParallelMergeSort(a, new int[a.length], 0, a.length));
        }
    }

    @Override
    protected void compute() {
        if (hi - lo <= THRESHOLD) { Arrays.sort(a, lo, hi); return; }
        int mid = (lo + hi) >>> 1;
        invokeAll(new ParallelMergeSort(a, buf, lo, mid), new ParallelMergeSort(a, buf, mid, hi));
        merge(mid);                               // both halves are sorted and visible after invokeAll
    }

    private void merge(int mid) {
        System.arraycopy(a, lo, buf, lo, hi - lo);
        int i = lo, j = mid, k = lo;
        while (i < mid && j < hi) a[k++] = buf[i] <= buf[j] ? buf[i++] : buf[j++];
        while (i < mid) a[k++] = buf[i++];
        while (j < hi) a[k++] = buf[j++];
    }
}

In practice, Arrays.parallelSort already does this (a parallel sort-merge on the common pool) and is the one to use.

The common pool, parallel streams and blocking

Parallel streams (L95), Arrays.parallelSort and every CompletableFuture async stage without an executor run on ForkJoinPool.commonPool(), whose parallelism defaults to the number of cores minus one (the calling thread also helps) and can be set with -Djava.util.concurrent.ForkJoinPool.common.parallelism. It is shared by the whole JVM, so anything slow placed there slows everything else.

If a fork/join task truly must block, tell the pool, via ForkJoinPool.managedBlock, so it can start a compensating thread and keep its parallelism:

static <E> E takeInPool(BlockingQueue<E> queue) throws InterruptedException {
    final class Taker implements ForkJoinPool.ManagedBlocker {
        E item;
        public boolean block() throws InterruptedException {
            if (item == null) item = queue.take();         // the pool may add a spare worker meanwhile
            return true;
        }
        public boolean isReleasable() {
            return item != null || (item = queue.poll()) != null;   // no need to block at all?
        }
    }
    Taker taker = new Taker();
    ForkJoinPool.managedBlock(taker);
    return taker.item;
}

That is a patch, not a design. Fork/join assumes tasks that compute and finish; a worker parked on a socket is a core's worth of parallelism lost, compensation can grow the thread count without much limit, and the scheduling advantages (LIFO locality, cheap stealing of big chunks) mean nothing for tasks that spend their life waiting. For I/O, use a dedicated executor or virtual threads (L150), whose scheduler happens to be a fork/join pool but which unmount from it while blocked.

What breaks in production
  • Blocking calls in parallel streams. ids.parallelStream().map(this::callRemote) occupies the common pool and stalls every other parallel stream and async stage in the service.
  • Thresholds of 1. Splitting down to single elements makes the "parallel" version many times slower than a loop.
  • Shared mutable accumulators. Adding into a shared long or ArrayList from leaves instead of returning and combining results is L126's race at higher speed.

Concurrent Collections In Depth

45m video45m practice

Concurrent collections make individual operations thread-safe and scalable, and the good ones also provide the compound operations you actually need (compute, merge, put-if-absent) as single atomic calls. Knowing how ConcurrentHashMap locks, what its iterators and size() promise, and what its compute functions must never do is most of what there is to know.

ConcurrentHashMap: from segments to per-bin locking

Java 7 split the map into Segments (16 by default, the concurrencyLevel), each a ReentrantLock guarding its own small hash table, so at most 16 writers could proceed at once. Java 8 rewrote it around a single table of bins:

Definition · what the map promises
  • Every single operation is atomic and thread-safe; a put happens-before any later get that sees it.
  • Null keys and null values are rejected: get returning null must unambiguously mean "absent".
  • size(), isEmpty() and mappingCount() are estimates under concurrent updates. The count is kept in LongAdder-style cells (L131), so it is summed, not snapshotted. Prefer mappingCount(), which returns a long.
  • Iterators and the bulk operations are weakly consistent (below).

Atomic composite operations

import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.LongAdder;

public class Composite {
    record Session(String id) { }

    public static void main(String[] args) {
        var sessions = new ConcurrentHashMap<String, Session>();
        var counts = new ConcurrentHashMap<String, Long>();
        var hits = new ConcurrentHashMap<String, LongAdder>();

        sessions.putIfAbsent("s1", new Session("s1"));         // value built even if unused
        sessions.computeIfAbsent("s2", Session::new);          // built only if absent, at most once
        counts.merge("GET /cart", 1L, Long::sum);              // insert 1 or add 1, atomically
        counts.compute("GET /cart", (k, v) -> v == null ? 1 : v * 2);   // returning null removes
        hits.computeIfAbsent("/home", k -> new LongAdder()).increment();  // hot counters: one adder per key

        long total = counts.reduceValuesToLong(Long.MAX_VALUE, Long::longValue, 0L, Long::sum);
        String big = counts.search(1, (k, v) -> v > 1 ? k : null);  // first match, may run in parallel
        counts.forEach(1, (k, v) -> System.out.println(k + "=" + v));
        System.out.println(total + " " + big + " " + sessions.keySet());
    }
}

The bulk operations (forEach, search, reduce and their typed variants) take a parallelism threshold: Long.MAX_VALUE runs sequentially, 1 splits as much as possible across the common pool (L144). They lock nothing, so their result reflects some mix of concurrent updates, not a snapshot.

The computeIfAbsent rule: don't block, don't recurse

The function passed to compute, computeIfAbsent, computeIfPresent and merge runs while the bin's lock is held. That is what makes it atomic, and it is also why the Javadoc requires it to be "short and simple" and forbids it from modifying the map.

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

final class Memo {
    private static final Map<Integer, Long> cache = new ConcurrentHashMap<>();

    // Deliberately broken: the function updates the same map from inside computeIfAbsent.
    static long fibBroken(int n) {
        if (n < 2) return n;
        return cache.computeIfAbsent(n, k -> fibBroken(k - 1) + fibBroken(k - 2));
    }

    // Correct: compute outside, then publish atomically. Duplicate work is possible; corruption is not.
    static long fib(int n) {
        if (n < 2) return n;
        Long hit = cache.get(n);
        if (hit != null) return hit;
        long value = fib(n - 1) + fib(n - 2);
        Long prev = cache.putIfAbsent(n, value);
        return prev != null ? prev : value;
    }
}

Recursive updates may throw IllegalStateException: Recursive update (Java 9+), may appear to work for small inputs, and on Java 8 could spin forever. Blocking inside the function (a database call, a remote load) holds the bin lock for the whole call, stalling every other thread that touches any key in that bin, and resizes as well. For loading caches, use a library built for it (Caffeine), or store a CompletableFuture as the value so the slow part runs outside the lock: cache.computeIfAbsent(k, key -> CompletableFuture.supplyAsync(() -> load(key), io)).

Sets, sorted maps and copy-on-write

  • Concurrent sets: ConcurrentHashMap.newKeySet() returns a KeySetView, a concurrent Set backed by a map; map.keySet(defaultValue) gives a view whose add inserts that value.
  • ConcurrentSkipListMap / ConcurrentSkipListSet: sorted and navigable (ceilingKey, headMap, subMap), lock-free via CAS, with expected O(log n) operations. Use them for leaderboards, time-ordered indexes and range queries. Their size() walks the whole structure: O(n).
  • CopyOnWriteArrayList / CopyOnWriteArraySet: every mutation copies the entire array under a lock; reads and iteration take no lock and see an immutable snapshot. Ideal for listener lists and rarely-changing configuration; ruinous for anything written often or large (each add to a 100,000-element list copies 100,000 references). The set's contains is a linear scan.

When Collections.synchronizedMap is still wrong

// Required by the Javadoc: iteration must hold the map's own lock for its whole duration.

    for (int v : m.values()) total += v;
}

A synchronized wrapper serializes every operation on one lock, including reads, and leaves every multi-call sequence and every iteration to client-side locking that is easy to forget. BlockingQueue & Producer–Consumer

45m video50m practice

A blocking queue moves work between threads and, if it is bounded, also moves pressure back: when consumers fall behind, producers block, and the system slows down instead of filling the heap. Choosing the bound and what happens when it is hit is the real design decision.

The contract and the four method families

BlockingQueue<E> is a thread-safe Queue that adds operations which wait: for space when inserting, for an element when removing. Every operation exists in four flavours, and picking the flavour is picking a policy for "the queue is full" or "the queue is empty".

Throws exceptionSpecial valueBlocksTimes out

Removeremove()poll() → nulltake()poll(time, unit)
Examineelement()peek() → nullnonenone
Definition · what the interface promises
  • No nulls. Inserting null throws NullPointerException, because null is the "nothing there" value of poll.
  • Happens-before. Everything a thread did before inserting an element happens-before everything another thread does after removing that element. A producer can build a mutable object, hand it over, and never touch it again: that is safe publication through the queue.
  • Blocking methods are interruptible. put, take and the timed forms throw InterruptedException, which is how a stuck producer or consumer is cancelled.
  • Bulk operations are not atomic. addAll or removeAll may fail half-way; only the single-element operations and drainTo are designed for concurrent use.

The implementations

Bounded queues are the backpressure mechanism

An unbounded queue does not remove the overload; it hides it as latency and then as an OutOfMemoryError. Little's law (items in system = arrival rate × time in system) turns a bound into a latency budget: if consumers drain 500 items/s, a queue of 10,000 means the newest item waits about 20 s. Size the queue for the wait you can tolerate, not for the burst you hope to absorb. When it is full you have four choices: block (put: right for internal pipelines), reject (offer → return 429/503 to the caller), wait a bit, then reject (timed offer), or drop something (oldest, lowest priority) when stale data is worthless.

Batching with drainTo, and poison-pill shutdown

drainTo(collection, max) moves up to max available elements in one operation without blocking (one lock acquisition on ArrayBlockingQueue). The idiom is take() to wait for the first element, then drainTo to grab the rest of what is ready: batches form naturally under load and shrink to one under light traffic, with no polling loop.

To stop consumers gracefully, put a sentinel (a poison pill) after the last real element; FIFO order guarantees every item ahead of it is processed first. With several producers, the coordinator waits for all of them to finish before putting the pill. The classic form puts one pill per consumer, but drainTo can swallow two pills into one batch, and then one consumer never stops. The version below avoids that with a single pill that each consumer passes on before exiting. With a priority queue, the pill must sort last.

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.*;
import java.util.concurrent.atomic.LongAdder;

public class Pipeline {
    sealed interface Msg permits Item, Stop { }
    record Item(int producer, int seq) implements Msg { }
    enum Stop implements Msg { PILL }

    static final int PRODUCERS = 3, CONSUMERS = 4, PER_PRODUCER = 100_000, BATCH = 64;
    static final BlockingQueue<Msg> queue = new ArrayBlockingQueue<>(1_000);
    static final LongAdder produced = new LongAdder(), consumed = new LongAdder(),
                           batches = new LongAdder(), blockedNanos = new LongAdder();

    public static void main(String[] args) throws InterruptedException {
        List<Thread> producers = new ArrayList<>(), consumers = new ArrayList<>();
        for (int p = 0; p < PRODUCERS; p++) {
            int id = p;
            producers.add(Thread.ofPlatform().name("producer-" + p).start(() -> produce(id)));
        }
        for (int c = 0; c < CONSUMERS; c++)
            consumers.add(Thread.ofPlatform().name("consumer-" + c).start(Pipeline::consume));
        for (Thread t : producers) t.join();      // every Item is in the queue now...
        queue.put(Stop.PILL);                     // ...so the pill sits behind all of them
        for (Thread t : consumers) t.join();      // join() makes the final counts visible
        System.out.printf("produced=%d consumed=%d batches=%d put-time=%d ms%n", produced.sum(),
                consumed.sum(), batches.sum(), blockedNanos.sum() / 1_000_000);
    }

    static void produce(int id) {
        try {
            for (int i = 0; i < PER_PRODUCER; i++) {
                long t0 = System.nanoTime();
                queue.put(new Item(id, i));       // waits while full: the backpressure
                blockedNanos.add(System.nanoTime() - t0);
                produced.increment();
            }
        } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    static void consume() {
        List<Msg> batch = new ArrayList<>(BATCH);
        try {
            while (true) {
                batch.add(queue.take());          // wait for the first element
                queue.drainTo(batch, BATCH - 1);  // then whatever else is ready
                boolean stop = false;
                for (Msg m : batch) {
                    switch (m) {
                        case Item item -> consumed.increment();   // process(item) goes here
                        case Stop pill -> stop = true;
                    }
                }
                batches.increment();
                batch.clear();
                if (stop) { queue.put(Stop.PILL); return; }      // pass the pill on, then exit
            }
        } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

Export the same metrics from any pipeline: items in and out (LongAdder is cheap under contention; its sum() is exact once the writers are joined), time spent in put (the backpressure signal), average batch size, and queue depth sampled with size(). Always full means consumers are the bottleneck; always empty, producers.

What breaks in production
  • Accidentally unbounded. new LinkedBlockingQueue<>(), a fixed thread pool's default queue, or a priority queue: memory climbs for hours, then the service dies.
  • Lost pills. One pill per consumer combined with drainTo, or a consumer that dies on an exception before reaching the pill: shutdown hangs on join.
  • Swallowed interrupts. A consumer that catches InterruptedException and loops again cannot be cancelled.
  • Mutating after handoff. The happens-before edge covers writes made before put. A producer that keeps modifying the object afterwards has a data race.
  • Blocking put on a request thread. Under overload every request thread parks on the queue; reject with a timed offer instead.

CountDownLatch & CyclicBarrier

35m video40m practice

A latch waits for events and opens exactly once; a barrier waits for threads and opens again every round. Ask two questions (are the waiters the same threads as the arrivers, and does it repeat?) and the choice makes itself.

CountDownLatch: a one-shot gate

Definition · the latch contract
  • The count is fixed at construction. countDown() decrements it, never blocks, and does nothing once the count is zero.
  • await() blocks until the count reaches zero; await(timeout, unit) returns false if it didn't. Both are interruptible.
  • getCount() is for logs and error messages. Reading it and then acting on it is a check-then-act race.
  • Actions before a countDown() happen-before actions after the corresponding await() returns, so results written by workers are visible to the waiter without further synchronization.

Underneath, a latch is a small AbstractQueuedSynchronizer in shared mode: the AQS state is the count, await succeeds only when it is zero, and countDown is a CAS decrement whose transition to zero releases every parked waiter. The counting threads and the waiting threads are independent: five workers can count down while two other threads wait, and one thread may count down several times.

Start gate and end gate

Threads started one by one in a loop give the first ones a head start. Two latches fix it: workers park on a start gate of 1, and an end gate of N tells the timer when the last one is done.

import java.util.concurrent.CountDownLatch;

public class TestHarness {
    /** Releases nThreads at once; returns nanoseconds until the last one finishes. */
    public static long timeTasks(int nThreads, Runnable task) throws InterruptedException {
        var startGate = new CountDownLatch(1);
        var endGate = new CountDownLatch(nThreads);
        for (int i = 0; i < nThreads; i++) {
            Thread.ofPlatform().start(() -> {
                try {
                    startGate.await();            // everyone parks here
                    task.run();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    endGate.countDown();          // even if the task threw
                }
            });
        }
        long start = System.nanoTime();
        startGate.countDown();                    // open the gate: all start together
        endGate.await();                          // wait for the slowest
        return System.nanoTime() - start;
    }
}

Waiting for N services at startup

The same shape gates an application's readiness: start each dependency (cache warm-up, connection pools, consumers) in parallel and wait for all of them, with a deadline. Two details make it production-grade: count down in finally, so a failure opens the gate instead of hanging it, and record failures separately so "opened" does not mean "succeeded".

import java.time.Duration;
import java.util.List;
import java.util.concurrent.*;

public class Startup {
    public interface Service { String name(); void start() throws Exception; }

    public static void startAll(List<Service> services, Duration timeout) throws InterruptedException {
        var ready = new CountDownLatch(services.size());
        var failures = new ConcurrentLinkedQueue<String>();
        for (Service s : services) {
            Thread.ofPlatform().name("init-" + s.name()).start(() -> {
                try {
                    s.start();
                } catch (Exception e) {
                    failures.add(s.name() + ": " + e);
                } finally {
                    ready.countDown();
                }
            });
        }
        if (!ready.await(timeout.toMillis(), TimeUnit.MILLISECONDS))
            throw new IllegalStateException(ready.getCount() + " service(s) still starting after " + timeout);
        if (!failures.isEmpty())
            throw new IllegalStateException("startup failed: " + failures);
    }
}

Why a latch cannot be reset

The count only moves down, and once it is zero every future await returns immediately, so a late arrival still sees the gate open. A reset would reintroduce the race the design removes: a waiter about to park could find the count reset to N and wait for a round it was never part of, or miss the opening altogether. For a second round, create a new latch and hand it out through a safely published reference (a final field of a per-round object, or a volatile field), or use a barrier or Phaser (L148).

CyclicBarrier: N parties, every round

Definition · the barrier contract
  • new CyclicBarrier(parties, action). Each party calls await() and blocks until parties threads have arrived.
  • The last thread to arrive runs the optional barrier action, then everyone is released and the barrier resets for the next generation automatically.
  • await returns the arrival index: parties - 1 for the first arrival, 0 for the last, handy for electing one thread to log.
  • Actions before await happen-before the barrier action, which happens-before the return from await in every party.

Iterative algorithms are the natural fit: each round, every worker updates its slice of a grid using the previous round's values, and nobody may start round s+1 until all have finished round s. The arrays below are plain, non-volatile fields; the barrier's happens-before edges are what make each worker see the others' writes and the swap.

import java.util.concurrent.BrokenBarrierException;
import java.util.concurrent.CyclicBarrier;

public class HeatRod {
    static final int N = 1_000, WORKERS = 4, STEPS = 5_000;
    static double[] cur = new double[N], next = new double[N];   // published by the barrier
    static int steps;

    public static void main(String[] args) throws InterruptedException {
        cur[0] = next[0] = 100.0;                                 // hot end; both ends stay fixed
        var barrier = new CyclicBarrier(WORKERS, () -> {          // runs in the last arrival
            double[] t = cur; cur = next; next = t;
            steps++;
        });
        var workers = new Thread[WORKERS];
        for (int w = 0; w < WORKERS; w++) {
            int lo = Math.max(1, w * N / WORKERS), hi = Math.min(N - 1, (w + 1) * N / WORKERS);
            workers[w] = Thread.ofPlatform().start(() -> {
                try {
                    for (int s = 0; s < STEPS; s++) {
                        for (int i = lo; i < hi; i++) next[i] = (cur[i - 1] + cur[i] + cur[i + 1]) / 3;
                        barrier.await();                          // all of round s is written
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } catch (BrokenBarrierException e) {
                    // another party failed: abandon the computation
                }
            });
        }
        for (Thread t : workers) t.join();
        System.out.printf("steps=%d T[10]=%.4f T[100]=%.4f%n", steps, cur[10], cur[100]);
    }
}

BrokenBarrierException: all or none

A barrier promises that all N parties take part in every round. If one cannot, the barrier breaks rather than leaving the others waiting forever. It breaks when a waiting party is interrupted (that party gets InterruptedException), when a timed await expires (TimeoutException), when the barrier action throws, or when reset() is called while parties are waiting. Every other waiting party, and every later await, then throws BrokenBarrierException at once. isBroken() reports the state; reset() starts a fresh generation, but coordinating who resets and when is hard, so failing the whole computation and building a new barrier is usually simpler.

  • A countDown on the happy path only. One exception and the latch never opens; startup hangs with no error.
  • Untimed await at startup. A dependency that never answers turns into a pod that never becomes ready and never logs why.

Semaphore, Phaser & Exchanger

35m video40m practice

A semaphore is a counter of permits, not a lock: it limits how many threads use something at once, and has no idea which ones. That one idea covers connection limits, bulkheads and simple rate limiting, which is why it is the synchronizer from this lesson you will use constantly; Phaser and Exchanger are specialist tools.

Semaphore: permits

Definition · the semaphore contract
  • acquire() takes a permit, blocking (interruptibly) until one is free; acquireUninterruptibly() ignores interrupts; acquire(n) takes several atomically.
  • tryAcquire() takes one only if free right now; tryAcquire(timeout, unit) waits up to a deadline and returns false if none came.
  • release() adds a permit, from any thread, whether or not that thread acquired one. Nothing caps the count at its initial value.
  • availablePermits(), getQueueLength() and drainPermits() exist for monitoring and for resets.
  • Actions before release() happen-before actions after a successful acquire in another thread.

It is an AbstractQueuedSynchronizer in shared mode with state = permits. Fairness is a constructor flag. new Semaphore(n, true) hands permits to waiters in FIFO order; the default, non-fair mode lets an arriving thread take a just-released permit ahead of the queue, which raises throughput but allows starvation. The untimed tryAcquire() barges even on a fair semaphore; tryAcquire(0, TimeUnit.SECONDS) respects fairness.

Bounding DB connections and outbound calls

A thread pool limits threads; a semaphore limits the use of one resource regardless of which pool the caller came from. Wrapping each downstream dependency in its own small semaphore is the bulkhead pattern: a slow inventory API can tie up at most its own 20 permits, and checkout keeps working. Resilience4j's semaphore bulkhead works the same way; connection pools such as HikariCP enforce an equivalent limit internally.

import java.time.Duration;
import java.util.concurrent.*;

public final class Bulkhead {
    private final Semaphore permits;
    private final Duration maxWait;

    public Bulkhead(int maxConcurrent, Duration maxWait) {
        this.permits = new Semaphore(maxConcurrent, true);
        this.maxWait = maxWait;
    }

    public <T> T call(Callable<T> work) throws Exception {
        if (!permits.tryAcquire(maxWait.toMillis(), TimeUnit.MILLISECONDS))
            throw new RejectedExecutionException("bulkhead full, " + permits.getQueueLength() + " waiting");
        try {
            return work.call();
        } finally {
            permits.release();            // reached only after a successful acquire
        }
    }
}

The acquire sits outside the try. Put it inside, and a timed-out caller runs the finally and releases a permit it never had, permanently raising the limit by one.

A simple rate limiter

A concurrency limit releases permits when work finishes; a rate limit releases them when time passes. Callers take permits and never return them, and a scheduler tops the semaphore up once per window:

import java.time.Duration;
import java.util.concurrent.*;

/** At most limit acquisitions per window (fixed-window algorithm). */
public final class FixedWindowLimiter implements AutoCloseable {
    private final Semaphore permits;
    private final ScheduledExecutorService refill = Executors.newSingleThreadScheduledExecutor();

    public FixedWindowLimiter(int limit, Duration window) {
        Semaphore s = new Semaphore(limit);
        this.permits = s;
        long ms = window.toMillis();
        refill.scheduleAtFixedRate(() -> {          // captures s, not this: no escape from the constructor
            int missing = limit - s.availablePermits();
            if (missing > 0) s.release(missing);    // callers only take, so this never overshoots
        }, ms, ms, TimeUnit.MILLISECONDS);
    }

    public boolean tryAcquire(Duration maxWait) throws InterruptedException {
        return permits.tryAcquire(maxWait.toMillis(), TimeUnit.MILLISECONDS);
    }

    @Override public void close() { refill.shutdownNow(); }
}

The top-up's read-then-release is safe only because concurrent callers can only lower the count in between. Fixed windows allow a burst of up to 2 × limit across a window boundary; token buckets (Guava's RateLimiter, Resilience4j) smooth that out.

Phaser and Exchanger

A Phaser is a reusable barrier whose party count can change. register() adds a party, arriveAndAwaitAdvance() is the barrier, arrive() signals without waiting, and arriveAndDeregister() leaves. Each advance increments the phase number, which wraps to 0 after Integer.MAX_VALUE. Overriding onAdvance(phase, parties) gives a per-phase action; returning true terminates the phaser (by default it terminates when the party count reaches zero). For thousands of parties, phasers can be tiered, children registered with a parent, to spread contention. As with a barrier, actions before arriving happen-before the advance and what follows it.

import java.util.concurrent.Phaser;

public class PhasedWork {
    public static void main(String[] args) {
        var phaser = new Phaser(1) {                       // party 1: the main thread
            @Override protected boolean onAdvance(int phase, int parties) {
                System.out.println("phase " + phase + " done, parties=" + parties);
                return phase == 2 || parties == 0;         // true terminates
            }
        };
        for (int i = 0; i < 3; i++) {
            phaser.register();                             // join before the thread starts
            int id = i;
            Thread.ofPlatform().start(() -> {
                while (!phaser.isTerminated()) {
                    System.out.println("worker " + id + " in phase " + phaser.getPhase());
                    phaser.arriveAndAwaitAdvance();
                }
            });
        }
        phaser.arriveAndDeregister();                      // main leaves; workers run 3 phases
    }
}

Main registers each worker before starting it and deregisters itself only afterwards, so phase 0 cannot complete before all four parties exist. An Exchanger<V> is a two-party rendezvous: exchange(x) waits for a partner and returns the partner's object, with happens-before in both directions. Its one classic use is double buffering: a filler thread trades a full buffer for an empty one, so neither side locks or allocates per element.

  • Untimed acquire on a request path. Under overload requests queue on the semaphore until clients time out; use tryAcquire with a short deadline and fail fast.
  • Nested acquire. A method holding a permit calls another that acquires from the same semaphore: with 1 permit it self-deadlocks; with N it deadlocks once N threads do it at once.

ThreadLocal, ScopedValue & Context Leaks

40m video40m practice

A ThreadLocal attaches a value to a thread, which is convenient until threads are reused: then it leaks memory, and worse, it leaks one request's data into the next. A ScopedValue attaches a value to a call, so it ends when the call returns and there is nothing to clean up.

How ThreadLocal works underneath

Definition · the per-thread map
  • Every Thread has a lazily created field threadLocals of type ThreadLocal.ThreadLocalMap. tl.get() looks up the current thread's map using tl as the key, so no locking is needed: only the owning thread touches its map.
  • The map uses open addressing with linear probing; successive ThreadLocal hash codes differ by 0x61c88647 (golden-ratio hashing) to spread them over power-of-two tables.
  • An entry extends WeakReference<ThreadLocal<?>> and holds its value strongly. If the ThreadLocal becomes unreachable, the GC clears the key, but the value stays until a later get/set/remove on that map happens to probe and expunge the stale slot, or the thread dies.

Weak keys protect you from forgetting the ThreadLocal, not from forgetting the value, and with the usual static final field the key never becomes unreachable at all.

The API and its classic uses

ThreadLocal.withInitial(supplier) runs the supplier on a thread's first get() and stores the result; set(v) replaces it; remove() deletes the entry, so the next get() re-initializes. Typical uses:

  • Per-thread copies of non-thread-safe objects: the legacy ThreadLocal<SimpleDateFormat>. Today use one immutable DateTimeFormatter constant instead.
  • Correlation IDs: SLF4J's MDC (backed by a thread-local map in Logback) puts the request ID on every log line written by that thread.
  • Transaction context: Spring's TransactionSynchronizationManager binds the connection to the current thread, which is why @Transactional does not follow work into threads you start yourself.
  • Security context: SecurityContextHolder uses a thread-local strategy by default.

The leak in thread pools and app servers

Pool threads never die, so a value that is set and not removed stays for the life of the process. That costs three ways. Memory: each pool thread retains its last value (a 1 MB buffer × 200 Tomcat threads = 200 MB). Data: the next task on that thread sees the previous request's user or tenant, which is a security bug. Class loaders: when a web application is redeployed, the server's threads still reference values whose classes came from the old application's class loader, so the whole old application, its classes and their static fields, stays in memory after each redeploy; Tomcat checks for this on undeploy and logs a warning naming the ThreadLocal. The fix is mechanical: every set has a remove in a finally.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class UserContext {
    private static final ThreadLocal<String> CURRENT_USER = new ThreadLocal<>();

    static String currentUser() { return CURRENT_USER.get(); }

    static void runAs(String user, Runnable work) {
        CURRENT_USER.set(user);
        try {
            work.run();
        } finally {
            CURRENT_USER.remove();          // remove(), not set(null): drop the entry
        }
    }

    public static void main(String[] args) {
        try (ExecutorService pool = Executors.newFixedThreadPool(1)) {
            pool.submit(() -> CURRENT_USER.set("alice"));      // deliberately broken: never removed
            pool.submit(() -> System.out.println("bob's request runs as " + currentUser()));  // alice
            pool.submit(() -> runAs("carol", () -> System.out.println("runs as " + currentUser())));
            pool.submit(() -> System.out.println("next task sees " + currentUser()));         // null
        }
    }
}

InheritableThreadLocal and executors

An InheritableThreadLocal is copied from parent to child when the child Thread is constructed (override childValue to transform it; the default copies the reference). After that the two are independent. With an executor this is almost always wrong: pool threads are created lazily, by whichever submission happens to need a new thread, so each worker inherits that submitter's value and keeps it for every later task. Spring Security's inheritable mode plus @Async on a pool is the classic case: tasks run as whichever user happened to trigger thread creation. Virtual threads inherit these values too, unless built with Thread.ofVirtual().inheritInheritableThreadLocals(false).

ScopedValue: an immutable binding for a call

public class RequestLog {
    static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

    static void handle(String requestId) {
        ScopedValue.where(REQUEST_ID, requestId).run(() -> {
            log("loading order");                                    // [req-1] loading order
            ScopedValue.where(REQUEST_ID, requestId + "/audit").run(() -> log("auditing"));
            log("done");                                             // [req-1] again
        });
    }

    static void log(String msg) {
        System.out.println("[" + REQUEST_ID.orElse("no-request") + "] " + msg);
    }

    public static void main(String[] args) {
        handle("req-1");
        log("outside any scope");                                    // [no-request]
    }
}

A binding exists only for the dynamic extent of run (or call, which returns a value): every method called inside sees it via get(), which throws NoSuchElementException if unbound (isBound() and orElse avoid that). There is no set; a nested where(...).run rebinds for an inner scope, and the outer value is back when it returns. Because the binding ends with the call, there is nothing to remove and nothing to leak, and forks of a StructuredTaskScope inherit it by sharing, not copying (L151). Scoped values were a preview API in Java 21–24 (compile and run with --enable-preview) and are final in Java 25 (JEP 506).

Propagating context across executors and CompletableFuture

Neither mechanism crosses an executor by itself: a task runs on a pool thread that knows nothing about the submitter. Capture the value at submission, restore it in the task, and put back whatever was there before, because with CallerRunsPolicy or a same-thread completion the "pool thread" may be the caller itself:

import java.util.concurrent.*;

public final class Contexts {
    static final ThreadLocal<String> REQUEST_ID = new ThreadLocal<>();

    static Executor propagating(Executor delegate) {
        return task -> {
            String captured = REQUEST_ID.get();               // on the submitting thread
            delegate.execute(() -> {
                String previous = REQUEST_ID.get();
                REQUEST_ID.set(captured);
                try {
                    task.run();
                } finally {
                    if (previous == null) REQUEST_ID.remove(); else REQUEST_ID.set(previous);
                }
            });
        };
    }

    public static void main(String[] args) {
        try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
            Executor ctx = propagating(pool);
            REQUEST_ID.set("req-42");
            String r = CompletableFuture.supplyAsync(() -> "loaded in " + REQUEST_ID.get(), ctx)
                    .thenApplyAsync(s -> s + ", priced in " + REQUEST_ID.get(), ctx)
                    .join();
            System.out.println(r);                            // both stages see req-42
            REQUEST_ID.remove();
        }
    }
}

Pass the wrapping executor to every *Async stage; a non-async thenApply runs on whichever thread completes the previous stage, so its context depends on timing. For a scoped value the wrapper is simpler: capture with orElse, then run the task inside ScopedValue.where(KEY, captured).run(task). In Spring you rarely write this by hand: TaskDecorator on ThreadPoolTaskExecutor, DelegatingSecurityContextExecutor, and Micrometer's context-propagation library do it for MDC, security and tracing.

What breaks in production
  • Set without remove on a pool thread. Requests run as the wrong user, logs carry the wrong correlation ID, and memory climbs.
  • Inheritable values with pools. Context frozen at thread creation, so it is wrong for most later tasks, and wrong differently on each worker.
  • Thread-local caches of large objects. Size is per-object × threads; harmless with 50 platform threads, enormous with a million virtual ones.
  • Async hops. Code after a CompletableFuture stage or a reactive operator runs on another thread, and the MDC is suddenly empty.

Virtual Threads I: The Loom Model

50m video45m practice

A virtual thread is an ordinary java.lang.Thread whose stack lives on the heap and which the JDK, not the OS, schedules onto a few carrier threads. A blocked virtual thread costs some heap rather than an OS thread, so one-thread-per-request blocking code scales again for I/O-bound work.

Platform threads: the 1:1 model and its ceiling

A platform thread is a thin wrapper around an OS thread. The kernel schedules it, and it gets a fixed-size stack reserved at creation (the -Xss default is 1 MB on 64-bit Linux and macOS; it is reserved address space, committed as pages are touched). Creating one is a system call, and every switch between them goes through the kernel. In practice a JVM manages a few thousand comfortably and runs into memory or OS limits (ulimit -u, pid_max) somewhere around the low tens of thousands. Hence thread pools.

That ceiling caps throughput through Little's law: requests in flight = throughput × latency. A server with 200 request threads and 100 ms per request tops out at 200 ÷ 0.1 s = 2,000 requests/s, however idle its CPUs are. When most of that 100 ms is spent waiting on a database or another service, threads, not CPU, are the scarce resource.

Virtual threads: the M:N model

Definition · virtual thread
  • A Thread not tied to an OS thread. Its stack is a continuation: while it is parked, its frames are stored in heap objects that grow and shrink with the actual call depth, typically hundreds of bytes to a few KB rather than a reserved megabyte.
  • It is scheduled by a dedicated ForkJoinPool in FIFO mode whose worker threads, the carriers, are platform threads; by default there is one per available processor.
  • Always a daemon thread, always NORM_PRIORITY (setPriority has no effect), and it supports everything else: locks, interrupts, ThreadLocal, stack traces, debuggers.
  • Final in Java 21 (JEP 444), after previews in Java 19 and 20.

Mounting and unmounting

Mounting copies the top frames of a virtual thread's continuation onto a carrier's stack (more are brought back lazily as it returns) and runs it. Unmounting happens when it blocks inside a JDK operation that knows how to yield; Thread.currentThread() still returns the same virtual thread afterwards, whichever carrier it lands on. Operations that unmount: socket I/O (Socket, SocketChannel, HttpClient, and so JDBC drivers that talk over sockets), Thread.sleep, and everything built on LockSupport.park: ReentrantLock, Condition.await, BlockingQueue put/take, latches, semaphores, Future.get. Some operations instead hold the carrier while they block. Most file I/O does, and the scheduler compensates by temporarily adding carriers. Blocking inside synchronized on Java 21–23 also holds it (pinning), and there it does not compensate (L151).

Creating them

Runnable task = () -> System.out.println(Thread.currentThread());   // VirtualThread[#22]/runnable@ForkJoinPool-1-worker-1
Thread a = Thread.ofVirtual().name("fetch-", 0).start(task);        // builder: fetch-0, then fetch-1, ...
Thread b = Thread.startVirtualThread(task);                          // shortcut, unnamed
ThreadFactory factory = Thread.ofVirtual().name("worker-", 0).factory();
try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(task);                                               // a new virtual thread per task
}                                                                    // close() waits for all of them

Never pool virtual threads. Pools exist to amortize expensive creation and to cap concurrency. Creating a virtual thread costs about as much as allocating a few small objects, so a pool saves nothing, and a reused virtual thread carries its ThreadLocal values from one task to the next. Concurrency limits belong on the scarce resource itself: a Semaphore (L148) sized to the connection pool or the partner's rate limit, acquired inside each per-task virtual thread.

Thread-per-request, made cheap again

Before Loom, scaling past the thread ceiling meant giving up sequential code: callbacks, CompletableFuture chains, reactive pipelines, all of which split one request across many threads and produce stack traces that no longer show what happened. Virtual threads keep the simple model (one request, one thread, straight-line blocking calls) and remove the ceiling. Little's law still holds; the in-flight limit now comes from what your downstream systems can absorb rather than from the thread count. Virtual threads make waiting cheap. They do not make code faster.

Benchmark: 10,000 concurrent calls, pool vs virtual

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse.BodyHandlers;
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class LoomBench {
    static final int CALLS = 10_000;

    public static void main(String[] args) throws Exception {
        Callable<Integer> call;
        if (args.length == 0) {                                   // stand-in: a 100 ms blocking call
            call = () -> { Thread.sleep(100); return 200; };
        } else {                                                  // a real endpoint, e.g. a delay server
            HttpClient client = HttpClient.newHttpClient();
            HttpRequest request = HttpRequest.newBuilder(URI.create(args[0])).build();
            call = () -> client.send(request, BodyHandlers.discarding()).statusCode();
        }
        time("fixed pool of 200", Executors.newFixedThreadPool(200), call);
        time("virtual per task ", Executors.newVirtualThreadPerTaskExecutor(), call);
    }

    static void time(String label, ExecutorService exec, Callable<Integer> call) throws Exception {
        long t0 = System.nanoTime();
        try (exec) {                                              // close() waits for every task
            var futures = IntStream.range(0, CALLS).mapToObj(i -> exec.submit(call)).toList();
            for (Future<Integer> f : futures) f.get();            // rethrows a failed call
        }
        System.out.printf("%s %,6d ms%n", label, (System.nanoTime() - t0) / 1_000_000);
    }
}

Predict before you run. The pool runs 200 calls at a time, so 10,000 calls take at least 50 rounds × 100 ms = 5 s. The virtual version has all 10,000 in flight at once, so its floor is one round, 100 ms, plus overhead. One run of the stand-in on a 12-core laptop printed about 5.6 s and 0.25 s; your numbers will differ, the ratio should not. With a real URL, run the delay server in a separate process and expect the gap to shrink: 10,000 simultaneous connections stress the OS listen backlog, file-descriptor limits (ulimit -n), ephemeral ports left in TIME_WAIT by previous runs, and the server itself. When the virtual run stops being faster, you have found the next bottleneck, which is the useful result.

Scheduler knobs, rarely needed: -Djdk.virtualThreadScheduler.parallelism=N sets the number of carriers (default: available processors), and -Djdk.virtualThreadScheduler.maxPoolSize=M caps how far compensation may grow it (default 256). Setting parallelism to 1 or 2 in a test is a cheap way to make pinning problems obvious.

What breaks in production
  • Unbounded fan-out. 10,000 virtual threads against a 10-connection database pool: the threads are fine, and 9,990 of them time out waiting for a connection. Put a semaphore in front of every scarce resource.
  • CPU-bound work. The scheduler does not time-slice: a virtual thread computing for a second holds its carrier for that second, and there are only as many carriers as cores.
  • Pooled or cached virtual threads. No benefit, plus context leaking between tasks.
  • Invisible threads. A classic jstack output doesn't list virtual threads; use jcmd <pid> Thread.dump_to_file -format=json dump.json.

  1. Run LoomBench with pool sizes 50, 200 and 1,000 and compare each result with the Little's law prediction.
  2. Start 1,000,000 virtual threads that each sleep 1 s; record wall time and peak heap. Try 20,000 platform threads doing the same and note how it fails or slows.
  3. Print Thread.currentThread() before and after a Thread.sleep(10) inside a virtual thread, many times, and find a case where the carrier changed.
  4. Add a Semaphore(10) around the stand-in call in the virtual version. Predict the new time (10 in flight at 100 ms each is 100 calls/s, so 1,000 calls take about 10 s) and confirm it.
  5. Write a delay server (com.sun.net.httpserver.HttpServer with a virtual-thread executor), run it in a second JVM, and benchmark against it. Explain what limits the virtual run.

Virtual Threads II: Pinning, Structured Concurrency & Migration

50m video45m practice

Virtual threads pay off only if they can unmount when they block. Pinning is the main thing that stops them, and structured concurrency is the API that makes "one virtual thread per subtask" safe, because it ties every subtask's lifetime, failure and cancellation to a block of code.

Pinning: when a virtual thread cannot let go

Definition · pinned

A virtual thread is pinned when it blocks but cannot unmount, so its carrier blocks with it. On Java 21–23 that happens when it blocks (I/O, sleep, park, wait) inside synchronized, because the JVM's monitors record the carrier as the owner, and whenever a native or foreign-function frame is on its stack. Java 24 (JEP 491) reimplemented monitors so that synchronized and Object.wait no longer pin; native frames still do, as do rare cases such as blocking in a class initializer.

The scheduler does not compensate for pinning: with one carrier per core, as many pinned threads as cores stall every virtual thread in the JVM. The demo is deliberately pinning. Each task has its own lock, so there is no contention, only pinning:

import java.util.concurrent.Callable;
import java.util.concurrent.Executors;
import java.util.concurrent.locks.ReentrantLock;

public class PinDemo {
    public static void main(String[] args) {
        System.out.println("carriers = " + Runtime.getRuntime().availableProcessors());
        time("synchronized ", () -> {
            Object lock = new Object();
            synchronized (lock) { Thread.sleep(100); }       // Java 21-23: pins the carrier
            return null;
        });
        time("ReentrantLock", () -> {
            var lock = new ReentrantLock();
            lock.lock();
            try { Thread.sleep(100); } finally { lock.unlock(); }   // unmounts
            return null;
        });
    }

    static void time(String label, Callable<Void> task) {
        long t0 = System.nanoTime();
        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000; i++) exec.submit(task);
        }
        System.out.printf("%s %,6d ms%n", label, (System.nanoTime() - t0) / 1_000_000);
    }
}

On JDK 21 with 12 carriers, runs printed 9 to 10 s and about 0.12 s. The first matches the prediction for pinning: 1,000 tasks ÷ 12 carriers ≈ 84 rounds × 100 ms ≈ 8.4 s, plus overhead. On Java 24+ both are fast.

Detecting pinning

# Java 21-23: stack trace when a virtual thread blocks while pinned (once per distinct stack)
java -Djdk.tracePinnedThreads=full -cp . PinDemo
    ...  PinDemo.lambda$main$0(PinDemo.java:10) <== monitors:1

# Any version: JFR event jdk.VirtualThreadPinned (on by default, 20 ms threshold)
java -XX:StartFlightRecording=filename=pin.jfr -cp . PinDemo

The trace marks the frame holding the monitor. The JFR event records the duration and stack of every pinned block over the threshold, so it is the one to use in production; Java 24 removed the trace property and reports the remaining causes through the same event.

Migrating synchronized to ReentrantLock

On 21–23 the monitors that matter are those held across a blocking call. A short synchronized block that updates a map never blocks and is fine. A token cache that refreshes over the network inside the monitor pins a carrier for every concurrent caller:

// Before: every virtual thread waiting in, or refreshing inside, token() pins a carrier.
public synchronized Token token() throws IOException, InterruptedException {
    if (cached == null || cached.isExpired()) cached = authClient.fetchToken();   // network call
    return cached;
}

// After: same mutual exclusion and visibility; waiters and the refresher unmount.
private final ReentrantLock lock = new ReentrantLock();
private Token cached;                                    // guarded by lock

public Token token() throws IOException, InterruptedException {
    lock.lock();
    try {
        if (cached == null || cached.isExpired()) cached = authClient.fetchToken();
        return cached;
    } finally {
        lock.unlock();
    }
}

Libraries matter as much as your code: older JDBC drivers, pools and HTTP clients held monitors around socket I/O, and many have been changed for exactly this reason, so upgrade them first.

ThreadLocal at a million threads

Each virtual thread has its own thread-local map. A thread-local 64 KB buffer costs 64 KB × live threads: harmless for 200 platform threads, about 64 GB for a million virtual ones. It also stops being a cache, since a per-task thread uses it once and dies. Inheritable thread-locals are copied into every new virtual thread. -Djdk.traceVirtualThreadLocals=true prints a stack trace whenever a virtual thread sets one. The answer is ScopedValue (L149), which forks share instead of copying.

Structured concurrency

Fan-out with a plain executor is unstructured: if one subtask fails, the others keep running; if the caller is interrupted, the subtasks never find out. StructuredTaskScope (preview in Java 21, JEP 453; use --enable-preview) gives fork-join a lexical scope: subtasks are forked inside a try-with-resources block, each in a new virtual thread, and none outlives it.

import java.time.Duration;
import java.util.List;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.StructuredTaskScope.Subtask;

public class Dashboard {
    record User(String name) { }
    record Page(User user, List<String> orders) { }

    static User findUser(long id) throws InterruptedException { Thread.sleep(80); return new User("u" + id); }
    static List<String> fetchOrders(long id) throws InterruptedException {
        Thread.sleep(50);
        if (id < 0) throw new IllegalStateException("orders service down");
        return List.of("o1", "o2");
    }

    static Page page(long id) throws InterruptedException, ExecutionException {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            Subtask<User> user = scope.fork(() -> findUser(id));
            Subtask<List<String>> orders = scope.fork(() -> fetchOrders(id));
            scope.join().throwIfFailed();        // wait for both or the first failure; rethrow it
            return new Page(user.get(), orders.get());
        }                                        // close(): no subtask outlives this block
    }

    static String fastest(List<Duration> latencies) throws InterruptedException, ExecutionException {
        try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
            for (Duration d : latencies)
                scope.fork(() -> { Thread.sleep(d); return "mirror@" + d.toMillis() + "ms"; });
            scope.join();
            return scope.result();               // first success; the others were interrupted
        }
    }
}

Scoped cancellation and error propagation. ShutdownOnFailure shuts down on the first failure; ShutdownOnSuccess on the first success, which result() returns (it throws ExecutionException if all failed). Shutdown interrupts unfinished forks and ignores later results. An interrupted owner gets InterruptedException from join, and close still waits. joinUntil(Instant) adds a deadline. Subtask.get() is legal only after join, on a successful subtask. Forks inherit the owner's scoped values. Java 25 (JEP 505, still preview) replaced both subclasses with StructuredTaskScope.open(...) and pluggable joiners: the ideas carry over, the class names do not.

When virtual threads do not help, and migrating

They do not help CPU-bound work (carriers = cores, no time-slicing: use a ForkJoinPool (L144) or a pool sized to the cores), downstream-bound work (a 20-connection database runs 20 queries at a time, whatever the thread count), or pinning-heavy code on 21–23. In Spring Boot 3.2+ on Java 21, spring.threads.virtual.enabled=true moves Tomcat/Jetty request handling, the @Async task executor and scheduling onto virtual threads (L287). Migration order: upgrade the JDK (24+ if possible) and drivers; load-test with JFR and fix pinned blocks around I/O; replace pools for blocking work with per-task virtual threads plus semaphores; audit thread-local caches; leave CPU pools alone.

What breaks in production
  • Throughput collapse after switching. A library holds a monitor around socket I/O; a few slow calls pin every carrier and the JVM stalls with idle CPUs.
  • Preview APIs across upgrades. StructuredTaskScope code for 21 does not compile on 25; hide it behind a small helper of your own.
  • Forks that ignore interruption. Shutdown interrupts them, but close waits for them, so one non-interruptible call delays the whole request.

  1. Run PinDemo with the trace property and with JFR, and find the pinned frame in both. Rerun with -Djdk.virtualThreadScheduler.parallelism=1 and explain the time. On Java 24+, confirm both variants are fast.
  2. Add a third fork to page (recommendations, 500 ms, logging in finally), make orders fail, and show that it is interrupted early.
  3. Add a 200 ms deadline with joinUntil and turn the TimeoutException into a partial page.
  4. In a Spring Boot app, log Thread.currentThread() in a controller with virtual threads off and on.

Phase 5 Capstone: Testing, Debugging & Building a Job Engine

55m video150m practice

Concurrency bugs are found with evidence, not by rereading code: thread dumps and JFR show what threads are doing, jcstress shows what the memory model allows, and latches make tests deterministic. The capstone puts every tool from this phase into one job engine, and its tests are half the deliverable.

Thread dumps: capture and read

jcmd                                     # list JVMs and their pids
jcmd <pid> Thread.print -l               # same as jstack -l <pid>; -l adds java.util.concurrent locks
jcmd <pid> Thread.dump_to_file -format=json threads.json    # includes virtual threads

Found one Java-level deadlock:           # appended automatically when there is a cycle
"transfer-1":
  waiting to lock monitor 0x0000028f1030ed30 (object 0x0000000624e04c90, a Bank$Account),
  which is held by "transfer-2"
"transfer-2":
  waiting to lock monitor 0x0000028f3759cdb0 (object 0x0000000624e04c78, a Bank$Account),
  which is held by "transfer-1"

Take three dumps a few seconds apart: a frame that is still there in all three is where time goes. Read each thread's state line together with its lock lines. BLOCKED with - waiting to lock <addr> is monitor contention; search for - locked <addr> to find the holder. If dozens of threads wait on one address, that lock is your bottleneck. WAITING with - parking to wait for <addr> (a ...ReentrantLock$NonfairSync) is a java.util.concurrent lock, condition or queue. RUNNABLE in a socket read is waiting for the network as far as the OS is concerned. Deadlocks among monitors and ownable synchronizers are reported automatically, as above.

JFR: locks and parking over time

A dump is a snapshot; a recording shows which waits cost the most. jcmd <pid> JFR.start duration=60s filename=locks.jfr settings=profile, then jfr print --events jdk.JavaMonitorEnter,jdk.ThreadPark locks.jfr or JDK Mission Control. jdk.JavaMonitorEnter is blocking on synchronized, jdk.JavaMonitorWait is Object.wait, jdk.ThreadPark is any java.util.concurrent wait, and jdk.VirtualThreadPinned is pinning (L151). Each event carries a duration, the monitor or blocker class and a stack trace; only waits above a threshold (tens of milliseconds by default) are recorded.

jcstress: testing the memory model

import org.openjdk.jcstress.annotations.*;
import org.openjdk.jcstress.infra.results.II_Result;

@JCStressTest
@Outcome(id = "1, 1", expect = Expect.ACCEPTABLE, desc = "saw the flag and the data")
@Outcome(id = {"0, 0", "0, 1"}, expect = Expect.ACCEPTABLE, desc = "flag not seen yet")
@Outcome(id = "1, 0", expect = Expect.ACCEPTABLE_INTERESTING, desc = "flag seen, data stale: no happens-before")
@State
public class PublicationTest {
    int data;
    boolean ready;                         // deliberately not volatile

    @Actor public void writer() { data = 1; ready = true; }
    @Actor public void reader(II_Result r) { r.r1 = ready ? 1 : 0; r.r2 = data; }
}

The harness runs the actors against each other millions of times on fresh state objects and prints a histogram of outcomes. Mark ready as volatile and change "1, 0" to Expect.FORBIDDEN: now the test fails if that outcome ever appears. Generate a project from the jcstress-java-test-archetype, build with mvn clean verify, and run java -jar target/jcstress.jar -t PublicationTest. On x86 the interesting outcome may never show up, because the hardware keeps stores in order; ARM machines and JIT reordering expose it. Not seeing a race proves nothing.

Deterministic tests: latches and Awaitility

A test that sleeps and hopes is flaky by construction. Use latches to force the interleaving you want to test, and Awaitility to wait for an eventual condition with a deadline:

@Test @Timeout(10)
void shutdownWaitsForInFlightJob() throws Exception {
    var engine = JobEngine.start(new Config(10, 2, false, Duration.ofMillis(1), Duration.ofMillis(10)));
    var started = new CountDownLatch(1);
    var release = new CountDownLatch(1);
    engine.submit(new Job("slow", Priority.NORMAL,
            () -> { started.countDown(); release.await(); return "ok"; }, 1, Duration.ofSeconds(5)), Duration.ZERO);
    assertTrue(started.await(1, SECONDS));                  // the job is running: no guessing
    var stopped = new FutureTask<>(() -> engine.shutdown(Duration.ofSeconds(5)));
    Thread.ofPlatform().start(stopped);
    assertThrows(TimeoutException.class, () -> stopped.get(100, MILLISECONDS));   // still draining
    release.countDown();
    assertTrue(stopped.get(1, SECONDS));                    // drained cleanly
    await().atMost(Duration.ofSeconds(1)).until(() -> engine.metrics.succeeded.sum() == 1);
}

Stress tests assert invariants, not timings: every job ends exactly once (succeeded + failed = submitted), concurrency never exceeds the limit, no job's attempts overlap. Shake the schedule with more threads than cores, -XX:ActiveProcessorCount=2 and @RepeatedTest(200).

Algorithm · flaky-test triage
  1. Measure: run it hundreds of times and record the failure rate, so you can tell later whether a fix worked.
  2. Capture: give every concurrent test a timeout and take a thread dump when one hangs.
  3. Classify: a timing assumption (replace the sleep with a latch or Awaitility), shared state between tests (static singletons, thread-locals), test-order dependence, or a real race.
  4. For a real race, write a stress or jcstress test that reproduces it, then fix the code. Never "fix" flakiness with a longer sleep or a retry annotation.

The capstone: a job-processing engine

Each requirement maps to a tool from this phase. The bounded queue is an admission Semaphore (L148) in front of a PriorityBlockingQueue ordered by (priority, sequence number), which gives priority tiers with FIFO inside each tier (L146). The worker pool is a second semaphore plus an executor: a fixed pool, or newVirtualThreadPerTaskExecutor when the virtual-thread toggle is on (L150). Per-job timeouts wrap each attempt in a FutureTask that a timer cancels with interruption (L141, L124). Retries go back through the timer with exponential backoff and full jitter. Graceful shutdown stops admission, waits on a Condition until the pending count reaches zero, retries included, and only then stops the dispatcher, the executor and the timer. Metrics are LongAdder counters plus queue-depth and in-flight gauges, the same shapes as Micrometer's counters, gauges and timers.

private void runAttempt(Entry e) {                  // runs on a worker thread
    FutureTask<?> attempt = new FutureTask<>(e.job().work());
    ScheduledFuture<?> alarm = timer.schedule(() -> attempt.cancel(true),
            e.job().timeout().toNanos(), TimeUnit.NANOSECONDS);
    long t0 = System.nanoTime();
    attempt.run();                                  // the job runs right here
    alarm.cancel(false);
    Thread.interrupted();                           // safe: cancel's interrupt lands before run() returns
    metrics.execNanos.add(System.nanoTime() - t0);
    switch (attempt.state()) {
        case SUCCESS   -> { metrics.succeeded.increment(); finish(); }
        case CANCELLED -> { metrics.timedOut.increment(); retryOrFail(e); }
        case FAILED    -> retryOrFail(e);
        case RUNNING   -> throw new AssertionError("run() has returned");
    }
}

private void retryOrFail(Entry e) {
    if (e.attempt() >= e.job().maxAttempts() || stopping) { metrics.failed.increment(); finish(); return; }
    metrics.retried.increment();
    Entry next = new Entry(e.job(), e.attempt() + 1, seq.getAndIncrement());
    long ceiling = Math.min(cfg.maxBackoff().toNanos(), cfg.baseBackoff().toNanos() << Math.min(e.attempt() - 1, 20));
    long delay = ThreadLocalRandom.current().nextLong(ceiling + 1);          // full jitter
    try {
        timer.schedule(() -> queue.put(next), delay, TimeUnit.NANOSECONDS); // put never blocks here
    } catch (RejectedExecutionException closed) {
        metrics.failed.increment(); finish();
    }
}

The shared state is deliberately small. pending and accepting are guarded by one ReentrantLock, stopping is volatile, and jobs and queue entries are immutable records handed over through the queue's happens-before edge. A static start(Config) factory starts the dispatcher only after construction completes, so this never escapes. A reference implementation of this design was loaded with 20,000 jobs (one in ten always times out, one in ten fails twice and then succeeds, one in ten always fails; three attempts each). In both modes it ended with exactly the expected counts, no overlapping attempts, and peak concurrency equal to the configured limit.

What breaks in production
  • Handing jobs to the pool's own queue. Priorities stop working: the executor's FIFO queue decides the order instead.
  • Synchronized retries. Backoff without jitter makes every failed job retry at the same instant and knock the dependency over again.
  • Jobs that ignore interruption. A timeout cannot stop them; they keep a worker until they return. Document it and alert on timedOut.

  • JobEngine with start(Config), submit(job, maxWait) returning false on rejection, and shutdown(grace) returning whether it drained.
  • Bounded admission; priority tiers, FIFO within a tier; stretch: aging, so LOW jobs cannot starve.
  • Retries with capped exponential backoff and full jitter; stretch: non-retryable exception types.
