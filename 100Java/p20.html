Caching & NoSQL

Phase 20 makes a Spring Boot service fast under read load and teaches you to pick the right datastore for each access pattern: caching theory, Spring's cache abstraction over Caffeine and Redis, Redis as a toolkit for locks, rate limits and streams, then MongoDB, Elasticsearch, Cassandra and DynamoDB. It builds on the JPA and transaction work of the persistence phases and ends with a measured multi-level cache, the shared and consistent state that the microservices of Phase 21 depend on.

By the end of this phase you can

  • Justify a datastore choice with CAP, PACELC and consistency models, or argue for Postgres alone.

L385 · DAY 385

Caching Theory & Strategies

40m video35m practice

A cache is a bet that the recent past predicts the near future; the hit ratio tells you whether the bet pays, and the read/write pattern you choose decides how wrong the cache is allowed to be.

Why caching works at all

Real access patterns are not uniform. Temporal locality: an item read now is likely to be read again soon (the product page that is trending, the session of a logged-in user). Spatial locality: items near it are likely to be read too (the next page of results, the other fields of the same row, the next cache line). On top of locality sits skew: in most catalogues, feeds and APIs a small fraction of keys receives most of the traffic, a Pareto- or Zipf-shaped distribution. Skew is why a cache holding 1–5% of the data can absorb most of the reads.

DefinitionA cache is a smaller, faster copy of data whose source of truth lives elsewhere. Every cache entry is a derived value: it may be lost at any time without data loss, and it may be stale. If losing it would lose data, it is not a cache, it is a database.

The hit ratio governs everything

With hit ratio h, cache latency tc and origin latency to, the average read costs h·tc + (1 − h)·to, and the origin sees (1 − h) of the traffic. Because to is usually 10–100 times tc, the miss term dominates. What matters is the miss ratio, not the hit ratio.

Worked exampleRedis hit ≈ 1 ms, database query ≈ 40 ms, 10,000 reads/s.
  • h = 80%: average = 0.8·1 + 0.2·40 = 8.8 ms; the database serves 2,000 queries/s.
  • h = 95%: average = 0.95·1 + 0.05·40 = 2.95 ms; the database serves 500 queries/s.
A 15-point gain in hit ratio cuts the miss ratio from 20% to 5%: the database load drops by a factor of four and the mean latency by about three. Going from 95% to 99% is another factor of five on the database. This is why a cache that "only" moves from 80% to 95% can turn a database that is about to fall over into one that idles.

Measure it per cache name, not globally: one cold cache with a 30% hit ratio hides inside a healthy global average. Spring Boot exports cache.gets{result=hit|miss} through Micrometer for caches that record statistics.

The caching layers in a real system

A request can be answered by any of several layers. Each hit stops the request; each miss falls through to the next, slower layer. Under all of them, the CPU's own L1–L3 caches decide how fast your in-process code runs.

Cache-aside is the default in Spring (@Cacheable is cache-aside with the method as the loader). Write-behind is rarely the right choice for business data; it fits view counters and metrics, where losing a few seconds of increments is acceptable.

import java.time.*;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Consumer;
import java.util.function.Function;

/** Cache-aside with a TTL; the loader and writer are the source of truth. */
public final class CacheAside<K, V> {
    private record Entry<T>(T value, Instant expiresAt) {}

    private final ConcurrentHashMap<K, Entry<V>> store = new ConcurrentHashMap<>();
    private final Function<K, Optional<V>> loader;   // e.g. repo::findById
    private final Duration ttl;
    private final Clock clock;

    public CacheAside(Function<K, Optional<V>> loader, Duration ttl, Clock clock) {
        this.loader = loader; this.ttl = ttl; this.clock = clock;
    }

    public Optional<V> get(K key) {
        Instant now = clock.instant();
        Entry<V> e = store.get(key);
        if (e != null && now.isBefore(e.expiresAt())) return Optional.of(e.value()); // hit
        Optional<V> loaded = loader.apply(key);                                      // miss
        loaded.ifPresent(v -> store.put(key, new Entry<>(v, now.plus(ttl))));
        return loaded;
    }

    /** Write path: update the source of truth first, then delete (not update) the entry. */
    public void write(K key, V value, Consumer<V> dbWriter) {
        dbWriter.accept(value);
        store.remove(key);
    }
}

Eviction and expiry

A bounded cache must choose a victim when full. LRU evicts the least recently used entry and handles recency well but is wrecked by one large scan. LFU evicts the least frequently used and protects popular items but clings to formerly hot keys. FIFO and random are cheap and close to LRU on very skewed loads. TinyLFU keeps a compact frequency sketch and admits a newcomer only if it is estimated to be more popular than the victim; Caffeine's W-TinyLFU (L387) adds a small LRU window so new bursts get a chance.

Size-based eviction protects memory; time-based expiry bounds staleness. TTL (time to live) expires an entry a fixed time after it was written; TTI (time to idle) expires it after a period without reads, which suits sessions but lets a constantly read entry live, and go stale, forever. Use both kinds of limit.

The hard problems, and what never to cache

  • Invalidation: every write path must delete the key, including batch jobs and manual SQL fixes that bypass the app. TTL is the backstop.
  • Staleness tolerance is a product decision: a price may be 30 s old, a stock count used to accept orders may not.
  • Stampede / dogpile: a hot key expires and hundreds of requests miss at once and all hit the database.
  • Hot keys: one key gets so much traffic that the single Redis shard holding it saturates; replicate it locally.
  • Thundering herd on restart: an empty cache after a deploy or flush sends 100% of reads to the origin. Warm up, or roll out gradually.

Never put per-user secrets or authorization-dependent data in a shared cache under a key that omits the user (one user sees another's data), and never cache data with strict consistency needs (balances or stock checked before accepting money). Measure instead of assuming: per-cache hit ratio, load penalty (time spent on misses), eviction count, origin QPS before and after, and memory. A cache that does not move origin load or p99 latency is pure risk.

What breaks in production
  • Caching without a TTL: one missed invalidation path and an entry is wrong forever.
  • Unbounded local maps: a ConcurrentHashMap used as a cache (like the sketch above) grows until the heap is full. Use a bounded cache.
  • Cache as primary store: a Redis restart or eviction loses data that existed nowhere else.
  • Write-behind on business data: the cache node dies and confirmed writes vanish. Stampedes and their fixes are in L391.

Spring's Cache Abstraction

45m video50m practice

Spring caching is cache-aside implemented by an AOP proxy: annotations describe keys and conditions, a CacheManager supplies the store, and every rule you already know about proxies applies.

How it works underneath

@EnableCaching registers a CacheInterceptor advisor. Beans with caching annotations get a proxy (JDK or CGLIB, as for @Transactional). On each call the interceptor computes a key, asks the CacheManager for the named Cache, and either returns the cached value or invokes the real method and stores its result. The SPI is small: CacheManager.getCache(name) and Cache.get/put/evict/clear, so any store can be plugged in.

@Cacheable, @CachePut, @CacheEvict

  • @Cacheable: look up first, run the method only on a miss. cacheNames (alias value) names the cache; key is SpEL over the arguments (#id, #user.id calls getId(), #user.id() for a record, #root.methodName, #root.args[0]); keyGenerator names a bean instead. condition is evaluated before the call (false means no lookup and no put); unless is evaluated after, on #result, and only vetoes the put. sync = true makes concurrent misses for the same key wait for one loader, the in-process stampede fix.
  • @CachePut: always run the method, always store the result. Use it on update methods so the cache holds the new value; never put it on the same method as @Cacheable.
  • @CacheEvict: remove key, or every entry with allEntries = true. beforeInvocation = true evicts even if the method throws; the default evicts only after success.
  • @Caching groups several of these on one method; @CacheConfig sets defaults (cache names, key generator, manager) for a class.
@Service
@CacheConfig(cacheNames = "products")
class ProductService {
    private final ProductRepository repo;
    ProductService(ProductRepository repo) { this.repo = repo; }

    @Cacheable(key = "#id", unless = "#result == null")
    public Optional<Product> find(long id) { return repo.findById(id); }

    @Cacheable(cacheNames = "productPages", sync = true,
               key = "#category + ':' + #page", condition = "#page < 5")
    public List<Product> page(String category, int page) {
        return repo.findByCategory(category, PageRequest.of(page, 20)).getContent();
    }

    @CachePut(key = "#result.id()")
    public Product update(Product p) { return repo.save(p); }

    @Caching(evict = {
        @CacheEvict(key = "#id"),
        @CacheEvict(cacheNames = "productPages", allEntries = true) })
    public void delete(long id) { repo.deleteById(id); }
}

For an Optional return type Spring caches the contained value (or null) and #result refers to the unwrapped value, so unless = "#result == null" works.

Nulls, wrappers and negative caching

Cache.get(key) returns a Cache.ValueWrapper: a null wrapper means "miss", a wrapper holding null means "we cached that it does not exist". That distinction enables negative caching: remembering misses so a flood of lookups for a missing id does not reach the database. Whether to allow it is a decision: unless = "#result == null" (or Redis's disableCachingNullValues) refuses to store nulls, so a row inserted later appears at once, but missing keys are never protected. A middle path is a separate short-TTL cache for misses.

Keys and the default generator

DefinitionSimpleKeyGenerator: no arguments gives SimpleKey.EMPTY; one argument is the key itself; several give a SimpleKey of all of them. The method name and class are not part of the key.

So two methods sharing a cache name with the same argument values collide: findById(42) and an overload find(42) returning a different type read each other's entries, and the second one gets a ClassCastException. Give every method its own cache name, or register a generator that includes the method:

@Configuration
@EnableCaching
class CacheConfig implements CachingConfigurer {
    private static final Logger log = LoggerFactory.getLogger(CacheConfig.class);

    @Bean
    KeyGenerator methodKey() {
        return (target, method, params) -> method.getDeclaringClass().getSimpleName()
                + "." + method.getName() + Arrays.deepToString(params);
    }

    @Override  // a cache outage becomes a miss instead of a 500
    public CacheErrorHandler errorHandler() {
        return new CacheErrorHandler() {
            public void handleCacheGetError(RuntimeException e, Cache c, Object k) {
                log.warn("cache get failed: {}", c.getName(), e); }
            public void handleCachePutError(RuntimeException e, Cache c, Object k, Object v) {
                log.warn("cache put failed: {}", c.getName(), e); }
            public void handleCacheEvictError(RuntimeException e, Cache c, Object k) {
                log.error("EVICT FAILED, entry may be stale: {} {}", c.getName(), k, e); }
            public void handleCacheClearError(RuntimeException e, Cache c) {
                log.error("clear failed: {}", c.getName(), e); }
        };
    }
}

The default SimpleCacheErrorHandler rethrows, so a Redis outage fails every cached endpoint. Swallowing get and put errors degrades to "no cache"; a failed evict deserves an alert, because it leaves stale data until the TTL.

What breaks in production
  • sync = true with unless: rejected with an IllegalStateException on the first call; sync also allows only one cache and no other cache annotations on the method.
  • Self-invocation: this.find(id) inside the service is never cached. Move the cached method to another bean.
  • SpEL names without -parameters: #id needs parameter names in the bytecode; Spring Boot's build plugins set the flag, hand-rolled builds may not. #p0 or #a0 always work.
  • Mutable cached objects: with a local cache, the caller gets the same instance that is cached; mutating it changes the cache for everyone. Cache records.
  • ConcurrentMapCacheManager in production: no size bound, no TTL, a slow memory leak.

Caffeine: High-Performance Local Caching

40m video45m practice

Caffeine gives each JVM a bounded, concurrent, near-optimal cache in the heap; the price is that every instance holds its own copy, which you must size against the heap and invalidate across pods yourself.

Why Caffeine, and how W-TinyLFU works

Caffeine is the successor to Guava's cache, written by one of Guava cache's authors, and is the local cache Spring Boot auto-configures. Its eviction policy, Window TinyLFU, keeps hit ratios close to the theoretical optimum on most real traces while staying O(1) per operation.

A one-off scan fills only the window and loses the admission contest, so it cannot flush the hot set, the classic LRU failure. A burst of new popular keys survives the window long enough to build frequency.

The builder

import com.github.benmanes.caffeine.cache.*;
import java.time.Duration;
import java.time.Instant;

record Rate(String pair, double value, Instant asOf) {}
record Token(String value, Instant expiresAt) {}

LoadingCache<String, Rate> rates = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(10))   // hard staleness bound
    .refreshAfterWrite(Duration.ofMinutes(1))   // serve old value, reload in background
    .recordStats()
    .build(pair -> fxClient.fetch(pair));       // CacheLoader: null means "absent"

Cache<String, byte[]> blobs = Caffeine.newBuilder()
    .maximumWeight(64L * 1024 * 1024)           // about 64 MB of payload
    .weigher((String k, byte[] v) -> v.length)
    .build();

Cache<String, Token> tokens = Caffeine.newBuilder()
    .expireAfter(new Expiry<String, Token>() {  // per-entry (variable) expiry
        public long expireAfterCreate(String k, Token t, long now) {
            return Duration.between(Instant.now(), t.expiresAt()).toNanos(); }
        public long expireAfterUpdate(String k, Token t, long now, long left) {
            return expireAfterCreate(k, t, now); }
        public long expireAfterRead(String k, Token t, long now, long left) {
            return left; }                      // reads do not extend it
    })
    .build();
  • maximumSize counts entries; maximumWeight + weigher bounds by cost (bytes, rows). Use one or the other.
  • expireAfterWrite is a TTL, expireAfterAccess a TTI; expireAfter(Expiry) gives each entry its own lifetime (inspect it through policy().expireVariably()).
  • weakKeys() switches key comparison to identity (==), so equal strings from different requests never match; softValues() lets the GC decide eviction, which is unpredictable and costly under pressure. Prefer explicit bounds.
DefinitionExpiry vs refresh. After expireAfterWrite the entry is gone: the next get blocks on the loader. After refreshAfterWrite the entry is merely eligible: the next get returns the old value at once and triggers an asynchronous reload; if the reload fails, the old value stays. Refresh needs a LoadingCache and only happens for keys that are actually read. Combine them: refresh at 1 minute for freshness, expire at 10 minutes as the hard limit.

Loading and async caches

LoadingCache.get(k) computes atomically per key: concurrent callers for one cold key wait for a single load, so Caffeine has stampede protection built in. getAll(keys) uses CacheLoader.loadAll for batch fetches if you override it. AsyncLoadingCache (buildAsync(loader)) stores CompletableFutures, so a caller never blocks a thread waiting for another caller's load, and a failed future is removed automatically.

AsyncLoadingCache<Long, User> users = Caffeine.newBuilder()
    .maximumSize(50_000).expireAfterWrite(Duration.ofMinutes(5))
    .buildAsync(id -> userClient.fetch(id));         // runs on ForkJoinPool.commonPool() by default
CompletableFuture<User> u = users.get(42L);

Spring integration and statistics

One spec applies to every cache. For different settings per name, build the manager yourself:

@Bean
CacheManager cacheManager() {
    var mgr = new CaffeineCacheManager();
    mgr.setCaffeine(Caffeine.from(CaffeineSpec.parse("maximumSize=1000,expireAfterWrite=10m,recordStats")));
    mgr.registerCustomCache("countries", Caffeine.newBuilder()
        .maximumSize(300).expireAfterWrite(Duration.ofDays(1)).recordStats().build());
    mgr.registerCustomCache("users", Caffeine.newBuilder()
        .maximumSize(50_000).expireAfterWrite(Duration.ofMinutes(5)).recordStats().build());
    return mgr;
}

CacheStats gives hitRate(), missCount(), averageLoadPenalty() (nanoseconds per load), and evictionCount(). With recordStats, Boot binds caches known at startup to Micrometer as cache.gets, cache.puts, cache.evictions; caches created lazily later are not bound, so declare cache names. Outside Spring, CaffeineCacheMetrics.monitor(registry, cache, "name") does the same. A high eviction count with a low hit ratio means the cache is too small for the working set.

The limits of a local cache

With N pods there are N independent copies. An update handled by pod 1 evicts pod 1's entry; pods 2..N keep serving the old value until their TTL. Fixes: a short TTL when staleness is acceptable, or a pub/sub broadcast of invalidations to every pod (built in L391). Each copy also multiplies origin load after a deploy, since every pod warms independently.

Sizing against the heap: entries are long-lived, so they are promoted to the old generation and enlarge the live set every GC must trace or copy. Estimate entry size (object headers, key, value graph, and roughly a few dozen bytes of cache node overhead), multiply by maximumSize, and keep the result a modest fraction of the heap. Measure with a heap histogram (jcmd <pid> GC.class_histogram) rather than guessing.

What breaks in production
  • refreshAfterWrite on a plain Cache: build() without a loader throws IllegalStateException.
  • Refresh without expiry: if the source is down, refreshes keep failing and a cold key's value can live forever.
  • Blocking loaders in AsyncLoadingCache on the common pool starve every other user of that pool; pass an executor(...).
  • Mutable cached values: callers share one instance; one mutation corrupts the cache for every thread.
  • Stale reads after writes on other pods, which surface as "random" bugs that disappear after the TTL.

Redis Fundamentals

45m video50m practice

Redis is a single-threaded server of in-memory data structures: each command is atomic because nothing else runs while it executes, and picking the right structure turns most "cache plus logic" problems into one command.

One thread, atomic commands

DefinitionRedis is an in-memory key-value server whose values are data structures (strings, hashes, lists, sets, sorted sets, streams…). Commands are executed one at a time on a single main thread; since 6.0 optional I/O threads read and write sockets, but command execution stays serial.

Consequences: every single command is atomic (an INCR can never lose an update); a slow command (KEYS *, HGETALL on a million-field hash, a long Lua script) blocks every client; and throughput comes from commands being O(1) or O(log n) on RAM, not from parallelism. Background threads handle lazy freeing (UNLINK), AOF fsync, and RDB snapshots run in a forked child.

    }

    }
    void markActive(long userId, LocalDate day) {            // 1 bit per user
        redis.opsForValue().setBit("dau:" + day, userId, true);
    }
    void visit(String page, String visitorId) {              // HyperLogLog
        redis.opsForHyperLogLog().add("uv:" + page, visitorId);
    }
    List<String> sessionKeys() {                             // SCAN, never KEYS
        var opts = ScanOptions.scanOptions().match("session:*").count(500).build();
        try (Cursor<String> c = redis.scan(opts)) { return c.stream().toList(); }
    }
}

Key commands

  • SET k v EX 60 NX sets with a TTL only if absent, in one atomic command; it subsumes SETEX and SETNX. SET k v GET replaces the deprecated GETSET.
  • EXPIRE sets a TTL, TTL reads it (−1 none, −2 missing key), PERSIST removes it. A plain SET without KEEPTTL clears an existing TTL.
  • DEL frees memory synchronously, which can block for a large collection; UNLINK removes the key at once and frees memory in the background.
  • KEYS pattern walks the whole keyspace in one blocking call; SCAN iterates with a cursor in small batches (it may return duplicates, so deduplicate).
  • MULTI/EXEC queues commands and runs them without interleaving, but there is no rollback and you cannot branch on intermediate results; EVAL runs a Lua script atomically, which is how you do compare-and-set logic.

Expiry, eviction and persistence

Expiry is lazy plus active: a read of an expired key deletes it and returns nothing; a background cycle samples keys that have TTLs and deletes expired ones, repeating while many in the sample were expired. So an expired key can occupy memory for a while after its TTL, though reads will not return it; replicas wait for the primary's DEL.

When maxmemory is reached, maxmemory-policy decides: noeviction (the default: writes fail with an OOM error), allkeys-lru/allkeys-lfu (any key; the right choice for a pure cache), volatile-lru/volatile-lfu/volatile-ttl (only keys with a TTL, for mixed cache and data), and random variants. LRU and LFU are approximated by sampling a few keys per eviction.

Persistence: RDB writes point-in-time snapshots from a forked child (copy-on-write can briefly double memory under heavy writes); AOF logs every write with appendfsync always (safest, slowest), everysec (lose up to about a second), or no (OS decides). A cache that can be rebuilt from the database usually needs neither.

# redis.conf for a pure cache
maxmemory 2gb
maxmemory-policy allkeys-lfu
save ""            # no RDB snapshots
appendonly no      # no AOF

Replication, Sentinel, Cluster and tooling

Replication is asynchronous: replicas can serve reads and lag, and a failover can lose the last writes. Cluster shards the keyspace into 16,384 hash slots (CRC16(key) mod 16384) spread over primaries; multi-key commands work only within one slot, which hash tags force: {user:42}:cart and {user:42}:profile share a slot.

Switching @Cacheable to Redis takes one dependency; making it production-safe means choosing serializers, TTLs per cache, a versioned key scheme, and a failure mode where Redis being down costs latency, not availability.

RedisCacheManager and RedisCacheConfiguration

DefinitionRedisCacheManager creates one RedisCache per cache name. Each is governed by an immutable RedisCacheConfiguration (every method returns a modified copy, so one base configuration can be specialised per cache), and all Redis I/O goes through a RedisCacheWriter.

The settings that matter: entryTtl (applied with each write), disableCachingNullValues (otherwise nulls are stored as a marker), prefixCacheNameWith("shop:") (keys become shop:users::42), computePrefixWith(name -> …) for full control of the prefix, and serializeKeysWith/serializeValuesWith.

Degrading gracefully when Redis is down

Three layers of defence: (1) a short command timeout so a call fails in about 100–250 ms rather than hanging; (2) the CacheErrorHandler from L386 so a failed get becomes a miss and a failed put is logged; (3) a circuit breaker around the cache (a Resilience4j breaker inside a Cache decorator, L408) so that when Redis is clearly down the app skips it instantly instead of paying the timeout on every request. Check that the database can take the full read load for a while; if it cannot, an outage of the cache is an outage of the service.

Redis Patterns: Locks, Rate Limits, Pub/Sub & Streams

50m video55m practice

Redis's atomic commands and Lua scripts make locks, rate limiters and queues a few lines each, but a Redis lock is a lease, not a guarantee: anything that must be correct, not just efficient, needs a fencing token or a database constraint behind it.

Distributed locks done carefully

Acquire with one atomic command, SET lock:report <token> NX PX 30000: set only if absent, with an expiry so a crashed holder cannot block forever. The value must be a unique token per acquisition, because release must delete the key only if you still own it. A plain DEL after your lease expired would delete someone else's lock; compare and delete must be one atomic step, hence Lua.

@Component
class RedisLock {
    private static final RedisScript<Long> RELEASE = RedisScript.of("""
        if redis.call('get', KEYS[1]) == ARGV[1] then
          return redis.call('del', KEYS[1])
        end
        return 0""", Long.class);
    private final StringRedisTemplate redis;
    RedisLock(StringRedisTemplate redis) { this.redis = redis; }

    Optional<String> tryAcquire(String name, Duration lease) {
        String token = UUID.randomUUID().toString();
        Boolean ok = redis.opsForValue().setIfAbsent("lock:" + name, token, lease); // SET NX PX
        return Boolean.TRUE.equals(ok) ? Optional.of(token) : Optional.empty();
    }
    boolean release(String name, String token) {
        Long n = redis.execute(RELEASE, List.of("lock:" + name), token);
        return n != null && n == 1L;
    }
}

Why the lock alone is unsafe, and fencing tokens

The holder cannot know its lease is still valid at the moment it acts. A stop-the-world GC pause, a slow network write, or a clock jump on the Redis host can let the TTL lapse mid-work; a second client acquires the lock and both now write.

DefinitionA fencing token is a number that strictly increases with every lock grant. The protected resource remembers the largest token it has accepted and refuses any request carrying a smaller one, so a holder whose lease silently expired can no longer do damage.

A fencing token can be an INCR counter issued with the lock, or simply the version column of an optimistic-lock update (UPDATE … WHERE version = ?). The Redlock algorithm (acquire on a majority of N independent Redis nodes) was criticised by Martin Kleppmann for depending on bounded pauses and clock behaviour and for lacking fencing; Salvatore Sanfilippo published a rebuttal. The practical conclusion holds either way: use a Redis lock for efficiency (avoid doing a job twice), and enforce correctness with a fencing token, a unique constraint, or a conditional update in the database.

Redisson

Redisson wraps these patterns in Java objects. RLock is reentrant; lock.tryLock(5, 30, SECONDS) waits up to 5 s for a 30 s lease, while calling lock() without a lease time enables the watchdog, which renews the lease (30 s by default) while the holding JVM is alive, so long jobs do not lose the lock, but a hung thread in a live JVM keeps it forever. Also: RReadWriteLock, RSemaphore, RRateLimiter, RBucket (a typed value), RLocalCachedMap (a map with a near cache invalidated over pub/sub), RBloomFilter, and RScheduledExecutorService (tasks scheduled across a cluster of workers).

Rate limiting

Sliding window log with a sorted set per client: ZREMRANGEBYSCORE key 0 now-window, then ZCARD; if under the limit, ZADD key now <unique-id> and PEXPIRE. Exact, but memory grows with the limit. A token bucket stores only two numbers and allows bursts up to capacity; it must run as one script so concurrent requests cannot both spend the last token:

-- KEYS[1] = bucket key; ARGV = capacity, refill tokens per ms, cost
local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local t = redis.call('TIME')                       -- server clock, not client clocks
local now = t[1] * 1000 + math.floor(t[2] / 1000)
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) * rate)
local ok = tokens >= cost
if ok then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate))
return ok and 1 or 0

Pub/sub and streams

Pub/sub is fire-and-forget: a message goes to the subscribers connected right now and is gone. That suits cache-invalidation broadcasts (a missed one is covered by the TTL) and nothing that must not be lost. In Spring, redis.convertAndSend("cache-inval", key) publishes and a RedisMessageListenerContainer with addMessageListener(listener, new ChannelTopic("cache-inval")) receives.

Streams are a durable append-only log. Producers XADD; a consumer group shares entries among consumers with XREADGROUP; each entry stays in the group's pending list until XACK; XPENDING shows stuck entries and XAUTOCLAIM hands entries idle too long to a live consumer. Delivery is at-least-once, so handlers must be idempotent (L416).

var options = StreamMessageListenerContainer.StreamMessageListenerContainerOptions
        .builder().pollTimeout(Duration.ofSeconds(1)).build();
var container = StreamMessageListenerContainer.create(connectionFactory, options);
container.receive(Consumer.from("billing", podName),                // group, consumer
        StreamOffset.create("orders", ReadOffset.lastConsumed()),
        msg -> {
            billing.handle(msg.getValue());                         // Map<String, String>
            redis.opsForStream().acknowledge("billing", msg);       // XACK after success
        });
container.start();

Create the group once (XGROUP CREATE orders billing $ MKSTREAM) and cap the stream with XADD … MAXLEN ~ 1000000. Streams are a lightweight queue, not Kafka: no partitions across nodes, and the data lives in RAM.

Other everyday uses: leaderboards with ZINCRBY/ZREVRANK; sessions with Spring Session (spring-session-data-redis), so any pod can serve any user; and idempotency keys stored with SET key response NX EX 86400.

What breaks in production
  • Lock value without a token, or release by plain DEL: you delete another client's lock.
  • Lease shorter than the work without fencing: two holders write concurrently and nobody notices.
  • Pub/sub for business events: a subscriber restart silently drops messages.
  • Never acknowledging stream entries: the pending list grows without bound and memory with it.
  • Rate limiting with client timestamps: clock skew between pods lets clients exceed the limit.

Cache Consistency, Stampedes & Multi-Level Caches

45m video50m practice

No invalidation scheme makes a cache exactly consistent with its database; you choose an ordering that makes stale windows rare and short, a TTL that bounds the worst case, and load-shaping tricks so expiry never becomes an outage.

The invalidation problem

For cache-aside the recommended write is update the database, then delete the key. Deleting rather than updating matters: two concurrent writers can update the database in one order and the cache in the other, leaving the older value cached indefinitely, and updating also fills the cache with data nobody may read. Even the recommended order has a race:

Delayed double delete narrows it: delete, write the database, then delete again after a delay longer than a typical load (and longer than replica lag). Run deletes after commit (@TransactionalEventListener(phase = AFTER_COMMIT)): a delete inside the transaction lets readers refill from the uncommitted, still-old row. To catch writes that bypass the app, drive invalidation from the database's change log (CDC, e.g. Debezium).

Replica lag (Day 220) widens the window: if a miss is filled from a read replica that has not yet applied the write, the cache is repopulated with old data right after the delete. Fill from the primary for keys written recently, or make the second delete wait longer than the replica lag. Read-your-own-writes for the writing user can be guaranteed by returning the new state from the write and skipping the cache for that user briefly.

The TTL is the safety net that bounds every bug above. Derive it from staleness tolerance: if the business accepts prices up to 60 s old, a 60 s TTL makes even a missed invalidation harmless.

Algorithm · XFetch
  1. Store with each value its expiry time and Δ, how long it took to compute.
  2. On every read, draw r uniformly from (0, 1] and recompute early if now − Δ·β·ln(r) ≥ expiry (β ≥ 1; 1 is the usual default).
  3. Otherwise serve the cached value.
Because −ln(r) is usually small but occasionally large, one request tends to refresh slightly before expiry while the rest keep hitting; expensive values (large Δ) refresh earlier (Vattani, Chierichetti & Lowenstein 2015).
static boolean recomputeEarly(long expiryMillis, long deltaMillis, double beta) {
    double r = 1.0 - ThreadLocalRandom.current().nextDouble();     // (0, 1]: log(0) is avoided
    return System.currentTimeMillis() - deltaMillis * beta * Math.log(r) >= expiryMillis;
}

Multi-level caching: Caffeine L1, Redis L2

An L1 hit costs nanoseconds and no network; the L2 keeps pods consistent with each other and protects the database when a pod starts cold. The difficulty is invalidating every pod's L1, which a Redis pub/sub broadcast solves well enough because a lost message is covered by the short L1 TTL.

@Component
class TwoLevelCache {
    private static final String CHANNEL = "cache-inval";
    private final Cache<String, String> l1 = Caffeine.newBuilder()
            .maximumSize(10_000).expireAfterWrite(Duration.ofSeconds(30)).build();
    private final StringRedisTemplate redis;

    TwoLevelCache(StringRedisTemplate redis, RedisMessageListenerContainer listeners) {
        this.redis = redis;
        listeners.addMessageListener((msg, pattern) ->
                l1.invalidate(new String(msg.getBody(), StandardCharsets.UTF_8)),
                new ChannelTopic(CHANNEL));
    }

    String get(String key, Function<String, String> dbLoader) {
        return l1.get(key, k -> {                                  // L1 miss
            String v = redis.opsForValue().get(k);                 // L2
            if (v == null && (v = dbLoader.apply(k)) != null)      // origin
                redis.opsForValue().set(k, v, jitter(Duration.ofMinutes(10)));
            return v;                                              // null is not stored
        });
    }

    void evict(String key) {                                       // call after commit
        redis.delete(key);
        l1.invalidate(key);
        redis.convertAndSend(CHANNEL, key);                        // every pod drops its L1
    }

    static Duration jitter(Duration base) {
        long spread = base.toMillis() / 10;
        return base.plusMillis(ThreadLocalRandom.current().nextLong(-spread, spread + 1));
    }
}

Declare a RedisMessageListenerContainer bean with the connection factory. Keep the L1 TTL much shorter than the L2 TTL: it bounds how long a pod that missed a broadcast can be wrong.

Warming, and whether it paid off

Warm at startup by loading the top-N keys (from yesterday's access stats) in small batches with bounded concurrency, before the readiness probe reports UP, so a rollout does not send every new pod's misses to the database at once. With an L2, new pods warm from Redis, not the database, which is often enough on its own.

Measure with L1 behind a feature flag: compare p50/p99 end-to-end latency, database QPS, Redis QPS and heap usage with it on and off, and count staleness bugs reported. If L1 saves 0.3 ms on a 40 ms request, the extra invalidation path is not worth its bugs.

What breaks in production
  • Evicting inside the transaction: a concurrent reader refills from the old row before commit.
  • Writes that bypass the app (migrations, admin SQL, other services) never invalidate; only the TTL saves you.
  • Synchronized TTLs after a cache flush or bulk load: the whole working set expires in the same second.
  • Remote I/O inside a Caffeine compute holds a lock for that key while it runs; keep loaders fast or use an AsyncCache.
  • Pub/sub as the only invalidation, with a long L1 TTL: one dropped connection leaves a pod serving stale data for hours.

MongoDB: Modeling, Indexes & Transactions

45m video50m practice

In MongoDB you design documents around how the application reads them: data read together is stored together, a single-document update is atomic, and indexes, not schemas, are where performance is won or lost.

When the document model fits

It fits aggregates that are read and written as a unit (an order with its lines, a product with its variants), variable or evolving attributes (catalogues where each category has different fields), and read-mostly nested data. It fits badly when the data is heavily relational (many-to-many links queried from every side), when you need ad-hoc joins across many collections, or when invariants span many documents (double-entry ledgers), which then need multi-document transactions on every write.

DefinitionDocuments are stored as BSON: typed binary JSON with types JSON lacks (ObjectId, Date, Decimal128, Int32/Int64, Binary). An ObjectId is 12 bytes: a 4-byte creation timestamp in seconds, a 5-byte random value fixed per process, and a 3-byte counter, so ids are roughly time-ordered and generated without coordination. A document may be at most 16 MB; designs that grow an array without bound will eventually hit it.

CRUD and update operators

Without $elemMatch, {"lines.sku": "A1", "lines.qty": {$gte: 2}} matches documents where some line has the sku and some possibly different line has the quantity. replaceOne swaps the whole document; updateMany/deleteMany act on all matches, each document atomically but not all together.

Schema design: embed or reference

Beyond cardinality, ask how often the child is read without the parent (favours reference) and how often it changes (frequently updated, widely shared data favours reference so one update suffices). Four standard patterns:

  • Subset: embed the 10 most recent reviews in the product, keep all reviews in their own collection.
  • Extended reference: copy the few fields of a referenced document you always display (customer name in the order) to avoid a lookup; accept that the copy can be stale.
  • Computed: maintain totals or counts on write ($inc) instead of recomputing on every read.
  • Bucket: group time-series points into one document per sensor per hour, cutting document and index counts by orders of magnitude.

Indexes and explain

Write concern, read concern, transactions

Write concern says when a write is acknowledged: w: 1 (primary only; lost if it fails before replicating), w: "majority" (the default since 5.0; survives failover), j: true (written to the on-disk journal), wtimeout (stop waiting; the write may still succeed). Read concern says what a read may see (local, majority, linearizable, snapshot), and read preference where it goes (primary, secondaryPreferred, nearest…); reading secondaries trades freshness for load.

Multi-document transactions need a replica set or sharded cluster (a standalone server rejects them). In Spring, declare a MongoTransactionManager bean and use @Transactional as usual. They cost extra round trips, hold locks and WiredTiger snapshots (60 s default lifetime), and abort on write conflicts that must be retried. If most writes need one, the data probably belongs in one document or in a relational database.

What breaks in production
  • Unbounded arrays (all comments in the post): documents grow, every update rewrites more, and the 16 MB limit arrives.
  • Indexes declared but never created because auto-index creation is off: everything is a COLLSCAN.
  • Unanchored or case-insensitive $regex scans the whole index or collection.
  • w: 1 for important writes: acknowledged data rolls back after a primary failover.
  • Transactions on a standalone dev server work nowhere: test against a single-node replica set (Testcontainers' MongoDB module starts one).

MongoDB Advanced: Aggregation, Change Streams & Scaling

45m video50m practice

The aggregation pipeline is MongoDB's query language for anything beyond lookups, change streams turn the oplog into an event feed, and sharding scales writes only as well as the shard key you choose once and live with.

The pipeline, stage by stage

A pipeline is a list of stages; each consumes the documents of the previous one. Shrink early: $match and $sort at the start can use indexes; after a $group or $unwind nothing can.

  • $project reshapes; $addFields/$set add computed fields and keep the rest; $replaceRoot promotes a sub-document to be the document.
  • $group with accumulators ($sum, $avg, $min, $max, $push, $addToSet, $first); $bucket groups into explicit ranges.
  • $unwind emits one document per array element; $lookup is a left outer join (an empty array when nothing matches) and has a pipeline form for correlated or filtered joins; $graphLookup walks hierarchies recursively.
  • $facet runs several sub-pipelines over the same input in one pass (results plus counts per filter); $merge upserts the result into a collection (an incrementally refreshed materialized view), $out replaces a collection.
db.orders.aggregate([
  { $match: { status: "PAID" } },
  { $lookup: { from: "shipments", let: { oid: "$_id" }, as: "lastShipment",
      pipeline: [ { $match: { $expr: { $eq: ["$orderId", "$$oid"] } } },
                  { $sort: { at: -1 } }, { $limit: 1 } ] } },
  { $facet: {
      byStatus: [ { $group: { _id: "$status", n: { $sum: 1 } } } ],
      bySize:   [ { $bucket: { groupBy: "$totalCents",
                               boundaries: [0, 5000, 20000, 100000], default: "large" } } ] } }
])

Change streams

Every event carries a resume token; store the last processed one and pass it to resumeAfter on restart, and you continue exactly where you stopped as long as the oplog still holds that point. This gives CDC-style reactions (cache invalidation, search indexing, outbound events) without Debezium.

Replica sets and sharding

A replica set is a primary plus secondaries replaying its oplog. If the primary is unreachable, the members elect a new one; an election needs a majority of voting members (so use an odd number) and typically completes within seconds, during which writes fail and drivers retry once (retryable writes). Read preference routes reads to secondaries for load or locality, at the cost of replication lag.

DefinitionSharding partitions a collection across shards by a shard key. The key's range is cut into chunks; the balancer migrates chunks to even out data, and mongos routes each query to the shards whose chunks it can touch (targeted) or to all of them (scatter-gather).

A good shard key has high cardinality (many distinct values), low frequency (no value owns a large share of documents), and is not monotonic: an ObjectId or timestamp key sends every insert to the last chunk on one shard. A hashed key spreads writes evenly but turns range queries into scatter-gather; a ranged key keeps ranges targeted but needs a naturally spread leading field, e.g. {tenantId: 1, createdAt: 1}. It is nearly impossible to fix later: refining the key can only append fields, and resharding (MongoDB 5.0+) rewrites the entire collection under load.

Search, validation and migrations

Atlas Search (a $search stage backed by Lucene) and Atlas Vector Search ($vectorSearch) add full-text and embedding similarity search inside the pipeline, mainly on MongoDB's managed Atlas service. Schema validation keeps "schemaless" from meaning "anything":

db.runCommand({ collMod: "orders", validationLevel: "moderate", validationAction: "error",
  validator: { $jsonSchema: { bsonType: "object", required: ["customerId", "status"],
    properties: { status: { enum: ["OPEN", "PAID", "CANCELLED"] },
                  schemaVersion: { bsonType: "int" } } } } })

Migrations: put a schemaVersion in every document; the code reads every live version and writes only the newest (lazy migration); a background job upgrades the remainder in batches; once none are left, drop the old read path and tighten the validator. moderate validation checks only inserts and documents that already pass, so old documents do not block the rollout.

What breaks in production
  • $lookup on an unindexed foreignField: a collection scan per input document.
  • $unwind before $match: multiplies documents before filtering them.
  • Resume token stored before processing: a crash loses that event; stored only after, events can repeat, so handlers must be idempotent.
  • Oplog too small: a consumer that is down longer than the oplog window cannot resume and must resync.
  • Monotonic shard key: one hot shard takes all writes while the others idle.

Elasticsearch & Full-Text Search

45m video50m practice

Search engines invert the data, from documents-containing-words to words-pointing-at-documents, after normalising text through analyzers; relevance, typo tolerance and facets all follow from that structure, and none of them can be bolted onto LIKE.

Why LIKE cannot search

WHERE name LIKE '%running shoe%' cannot use a B-tree index (leading wildcard), so it scans every row; it matches only that exact substring (not "shoes for running"); it has no notion of relevance (which of 4,000 matches is best); no stemming ("runs" vs "running"); no typo tolerance ("runing"); and no facets (counts per brand alongside the results).

The inverted index, built by hand

Each term's postings list also stores term frequency and positions (for phrase queries). Lookup cost depends on the number of matching terms, not the number of documents, which is why search stays fast at billions of documents.

Analyzers and mappings

An analyzer is character filters (strip HTML, map characters) → one tokenizer (split into tokens) → token filters (lowercase, stop words, stemming, synonyms, edge n-grams). The rule that breaks most search features: index-time and search-time analysis must produce compatible terms. If the index stems "running" to "run" but the query is not stemmed, nothing matches. The deliberate exception is autocomplete: index edge n-grams ("ru", "run", "runn"…) but search with a plain analyzer, or every query would match nearly everything.

match analyzes the input; match_phrase requires terms in order; multi_match searches several fields with boosts (^3); term and range are exact and unanalyzed (a term query on a text field is a classic bug); fuzzy, prefix and wildcard expand to many terms and are expensive. In bool, must and should contribute to the score, while filter and must_not only include or exclude, so they skip scoring and their results can be cached. Put every yes/no condition in filter.

DefinitionBM25, the default similarity, scores each query term as IDF × tf·(k1 + 1) / (tf + k1·(1 − b + b·len/avgLen)), with k1 = 1.2 and b = 0.75 by default. Rare terms (high IDF) count more; repeating a term has diminishing returns (saturation by k1); long fields are penalised (normalisation by b). function_score then blends in business signals such as popularity or recency.

Aggregations computed over the same matching set give the facet counts. For autocomplete, either query the edge-n-gram sub-field (flexible, matches mid-phrase words) or use a completion field with the completion suggester (an in-memory prefix structure: very fast, prefix only).

Cassandra, DynamoDB & Wide-Column Modeling

45m video45m practice

Wide-column stores buy near-linear write scaling by giving up joins and ad-hoc queries: the partition key decides where data lives, the sort order decides what one read can return, and so you design one table per query before you write a line of code.

Cassandra underneath

Cassandra has no primary node. Each node owns ranges of a hash ring; the partition key is hashed (Murmur3) to a token, and the node owning that token plus the next RF−1 distinct nodes clockwise hold replicas. Vnodes give each node many small token ranges so that adding a node takes a little data from every other node instead of a big slice from one neighbour. Any node can act as coordinator for a request.

  • Tunable consistency per request: ONE, QUORUM (majority of all replicas), LOCAL_QUORUM (majority in the local data centre, the usual production choice), ALL. With N replicas, if R + W > N every read set overlaps every write set, so a read sees the latest acknowledged write. Conflicts are resolved by cell timestamp: last write wins.
  • Hinted handoff: if a replica is down, the coordinator keeps a hint and replays it later. Read repair fixes stale replicas noticed during reads; scheduled anti-entropy repair (nodetool repair) fixes the rest.
  • LSM storage: a write appends to the commit log and updates an in-memory memtable, so writes never read or seek. Full memtables flush to immutable SSTables; reads merge the memtable with several SSTables (Bloom filters skip most); compaction (size-tiered, leveled, or time-window for time series) merges SSTables and drops obsolete cells.

Query-first modeling

DefinitionIn PRIMARY KEY ((a, b), c, d) the partition key (a, b) chooses the replicas and must be fully specified by every query; the clustering columns c, d fix the on-disk sort order inside the partition, so range scans and "latest N" over them are a sequential read. Everything else is unindexed.
CREATE TABLE chat.messages_by_conversation (
  conversation_id uuid,
  day             date,            -- bucket: bounds each partition to one day
  sent_at         timeuuid,
  sender_id       uuid,
  body            text,
  PRIMARY KEY ((conversation_id, day), sent_at)

A second access path ("messages sent by a user") is a second table, messages_by_sender, written alongside the first (a logged batch keeps the two in step). Duplication is the normal price. Lightweight transactions (IF) run Paxos among the replicas, several round trips each, so keep them to rare uniqueness and compare-and-set cases.

Anti-patterns: unbounded partitions (all of a sensor's readings forever in one partition; bucket by day instead and keep partitions well under ~100 MB); ALLOW FILTERING, which scans partitions and filters afterwards; secondary indexes on high-cardinality columns, which query every node; and deletes, which write tombstones that reads must skip until compaction after gc_grace_seconds, so queue-like tables become slower with every consumed item.

DynamoDB

A managed key-value and wide-column store. Each item has a partition key and optional sort key; a Query reads one partition, optionally a sort-key range. Single-table design stores several entity types in one table with generic keys so one query returns a related set: PK = CUSTOMER#42 with SK = PROFILE and SK = ORDER#2026-10-11#991 fetches the customer and their orders in a single request. Capacity: on-demand (pay per request) or provisioned (with auto scaling). When it is the right answer, and when it is a trap

Right: massive sustained write throughput (events, telemetry, messaging), time series with natural buckets, multi-region always-on availability, and access patterns that are known and few. Polyglot Persistence & Choosing a Datastore

45m video45m practicemilestone project

Every datastore is a bundle of trade-offs about consistency, latency and query flexibility; add one only when a concrete access pattern needs it, because each addition is another copy of the truth you must keep in sync and operate.

CAP, stated precisely, and PACELC

Theorem · CAPIn an asynchronous network that can lose messages between nodes (a partition), no replicated system can guarantee both linearizable consistency (every read sees the latest completed write, as if there were one copy) and availability (every request to a non-failed node eventually gets a non-error response). During a partition you must give up one of them (Gilbert & Lynch 2002).

Common misreadings: "pick any two of three" (partitions are not optional, so the real choice is C or A while partitioned); "C" meaning ACID consistency (it means linearizability); and "a CP system is unavailable" (it is unavailable only on the minority side of a partition). CAP also says nothing about the normal case, which is why PACELC (Abadi 2012) is more useful: if Partitioned, choose A or C; Else choose Latency or Consistency. Even on a healthy network, a synchronous replica or quorum read costs round trips. Dynamo-style stores (Cassandra, DynamoDB by default) are PA/EL; a single primary with synchronous replication is PC/EC.

Consistency models

  • Linearizable: once a write completes, every later read anywhere sees it. Sequential: all clients see the same total order consistent with each client's program order, but not necessarily real time.
  • Causal: if B could have been influenced by A (a reply to a comment), everyone sees A before B; unrelated writes may appear in different orders.
  • Read-your-writes: you always see your own updates. Monotonic reads: you never see time go backwards (an older value after a newer one), which load-balanced reads across lagging replicas violate.
  • Eventual: if writes stop, replicas converge; nothing is promised about what you read meanwhile.

A decision framework and comparison

Decide per access pattern, in this order: data shape (tables, documents, graph, time series, vectors, blobs); access patterns (point lookups, ranges, joins, full text, aggregates); consistency needed by the business invariant; scale (data size, write rate, regions); query flexibility (will new questions appear?); team expertise; and operational cost (backups, upgrades, on-call, licensing).

Polyglot persistence in practice

A typical shape: Postgres is the system of record; Redis holds caches and sessions; Elasticsearch serves search; Kafka carries change events between them; S3 stores blobs, with only keys in Postgres. Each addition brings a synchronization path (CDC or outbox into Kafka, an indexer, invalidation), a new failure mode (the index lags, the cache is stale), a backup and restore story, and on-call knowledge. Write down for each store: what is derived from what, the acceptable lag, and how to rebuild it from the source.

"Just use Postgres" as a serious default

One well-run Postgres covers far more than relational rows: JSONB with GIN indexes for document-style data, full-text search with tsvector, arrays, LISTEN/NOTIFY for lightweight signals, PostGIS for geospatial, pgvector for embeddings, declarative partitioning for large time-ordered tables, and SKIP LOCKED job queues. Until a measured limit is reached, one transactional store beats four eventually consistent ones.

Migrating between stores uses the strangler pattern: stream changes from the old store into the new one (CDC plus a backfill), shadow-read from both and compare, switch reads behind a flag, then switch writes, keep the old store as a fallback for a period, and only then decommission it.

What breaks in production
  • Résumé-driven stores: a graph database for data with two levels of relationships, now with its own backups and on-call.
  • Dual writes between stores without an outbox or CDC: they diverge on the first partial failure.
  • No rebuild path for a derived store: when the index corrupts, nobody knows how to regenerate it.
  • Assuming linearizability from an eventually consistent store: read-after-write bugs under load.
