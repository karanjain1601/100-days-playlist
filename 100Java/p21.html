Microservices & Spring Cloud

Phase 21 turns a single Spring Boot application into a system of services and teaches you when that is worth it: domain-driven boundaries, the current Spring Cloud stack (Config, Eureka or Kubernetes discovery, LoadBalancer, Gateway, OpenFeign or HTTP interfaces, Resilience4j), observability, sagas and idempotency, and how to test it all. It builds on the transactions, messaging and caching of earlier phases, and its five-service system is what Phase 22 ships to Kubernetes through a full CI/CD pipeline.

By the end of this phase you can

  • Argue for a modular monolith or for microservices from team and deployment constraints, and enforce module boundaries with Spring Modulith or ArchUnit.
  • Find bounded contexts with event storming, draw a context map, and extract a service behind a strangler façade with its own database.
  • Pick a matching Spring Cloud release train and name the current component for each job, knowing that Ribbon, Hystrix, Zuul 1 and Sleuth are gone.
  • Run centralized configuration, service discovery and client-side load balancing, or replace them with Kubernetes Services and ConfigMaps.
  • Route, secure and rate-limit traffic at a Spring Cloud Gateway, and call services through OpenFeign or @HttpExchange clients with timeouts, breakers, bulkheads and retries in the right order.
  • Trace a request across services, correlate its logs and metrics, and configure probes and graceful shutdown for an orchestrator.
  • Implement a saga with compensations and idempotent consumers, and verify service interactions with consumer-driven contract tests.

L397 · DAY 397

Monolith, Modular Monolith & Microservices

45m video35m practice

Microservices trade in-process calls and one ACID database for independent deployability and team autonomy; that trade pays only when those are your actual bottleneck, so a well-bounded modular monolith is the right default and the cheapest path to services later.

What a monolith is, and why most are fine

A monolith is one deployable unit: one build, one process type (possibly many replicas behind a load balancer), usually one database. It scales horizontally perfectly well. It gives you in-process calls measured in nanoseconds, a single transaction across everything, one place to debug, and refactoring with IDE support across the whole codebase. "Monolith" describes deployment, not quality; the thing people actually hate is the big ball of mud, a monolith with no internal boundaries, and splitting a ball of mud yields a distributed ball of mud.

The real reasons to split

  • Independent deployability: one team can ship without coordinating a release train with ten others.
  • Team autonomy: a team owns a service end to end, including its data and on-call, and changes it without negotiation.
  • Differing scaling or availability profiles: an image pipeline needing GPUs and burst scaling, or checkout needing stricter availability than reporting.
  • Technology heterogeneity: a component genuinely better served by another runtime or datastore.

"Microservices are modern", "the code is messy" and "we want to use Kubernetes" are not on the list. Messy code needs boundaries, which you can add without a network.

The costs nobody mentions on the first day

The bill
  • Distributed transactions: no ACID across services; you need sagas (L414) and compensations.
  • Network failure is now normal: timeouts, retries, circuit breakers (L408) on every call.
  • Eventual consistency between services' data, visible to users.
  • Operational complexity: N pipelines, N dashboards, N on-call rotations, service discovery, a gateway.
  • Distributed debugging: one request's failure spans logs on eight pods, so tracing becomes mandatory (L411).
  • Data duplication and synchronization through events.
  • Contract versioning: an API change is a multi-team migration, not a refactor.
  • Infrastructure: separate runtimes, databases, brokers and observability can multiply the bill several times over (the often-quoted 5× is a rule of thumb, not a law).

The modular monolith as the default

DefinitionA modular monolith is a single deployable whose code is split into modules with enforced boundaries: each owns its data and exposes a narrow API, and the build fails if another module reaches into its internals.

Each module is a top-level package with a small public API; everything else is internal.

Modules communicate through that API or through in-process events, own their tables (one database, a schema per module, no cross-schema joins or foreign keys), and are tested independently. Spring Modulith treats direct sub-packages of the application package as modules and verifies the rules:

// com.shop.orders — module API; com.shop.orders.internal is hidden from other modules
public record OrderPlaced(UUID orderId, BigDecimal total) {}

@Service
public class OrderService {
    private final ApplicationEventPublisher events;
    OrderService(ApplicationEventPublisher events) { this.events = events; }

    @Transactional
    public void place(UUID orderId, BigDecimal total) {
        // ... persist in schema "orders"
        events.publishEvent(new OrderPlaced(orderId, total));
    }
}

// com.shop.inventory — reacts without a compile-time dependency on orders' internals
@Component
class StockReservations {
    @ApplicationModuleListener            // async, after commit, in its own transaction
    void on(OrderPlaced event) { /* reserve stock in schema "inventory" */ }
}

class ModularityTests {
    @Test
    void boundariesHold() {
        ApplicationModules.of(ShopApplication.class).verify();  // cycles or internal access fail
    }
}

With the event publication registry (spring-modulith-starter-jpa), published events are stored with the transaction and redelivered if a listener fails, which is the same outbox thinking you will need between services. ArchUnit enforces the same kind of rule without Modulith: noClasses().that().resideInAPackage("..orders..").should().dependOnClassesThat().resideInAPackage("..billing.internal.."). Extraction later means replacing the event bus with Kafka and the API call with HTTP; the boundary already exists.

Conway's law and the distributed monolith

Conway's law: a system's structure mirrors the communication structure of the organisation that builds it. The inverse Conway maneuver designs team boundaries first so the architecture you want falls out of them; services that cut across team lines will drift back. The distributed monolith is the failure mode: services that must be deployed together, share a database, call each other synchronously in long chains, or break on each other's changes. It has every cost listed above and none of the independence.

A decision checklist

  1. When to split: several teams are blocked by one deployable (queued releases, merge conflicts, a failing test in another team's module stops your release), or a part needs a different scaling, availability or runtime profile. And you already have per-service CI/CD, centralized logs, metrics and tracing, and automated infrastructure.
  2. What first: a module with a stable, well-understood boundary, few inbound dependencies and a distinct profile (notifications, search, media processing), not the core domain everything touches.
  3. How to know it worked: the extracted team's deployment frequency and lead time rise, its change failure rate does not, and it releases without coordinating with others. If releases still need a joint plan, you built a distributed monolith.
Interview trap"Microservices let you scale." A stateless monolith scales horizontally just as well; what microservices let you scale independently is parts of the system, and above all teams. Name the organisational driver, the costs, and the modular-monolith alternative, and the answer stands out.

Practice · 35 min

  1. Restructure a small Spring Boot shop into orders, catalog and inventory modules; add the Modulith verify() test and break it on purpose with an internal import.
  2. Replace one direct call between modules with an event and an @ApplicationModuleListener.
  3. Write a one-page "should we split?" assessment for a system you know, answering each point of the checklist with evidence.

Domain-Driven Design: Strategic Patterns

45m video45m practice

Service boundaries drawn around nouns in a database schema couple everything; boundaries drawn around bounded contexts, where a word has one meaning, one model and one owning team, are the ones that survive.

Ubiquitous language

DDD starts with language. Within a context, developers and domain experts use the same terms with the same meaning, in conversation, in tickets and in code (class names, method names, events). Across an organisation, the same word drifts: in Sales an "Order" is a customer's commitment with prices, discounts and a payment method; in the Warehouse it is a pick list of SKUs, bin locations and parcels; in Finance it is a receivable with tax lines and due dates. A single Order class serving all three grows a hundred nullable fields and every change needs three teams' agreement.

Bounded contexts

DefinitionA bounded context is an explicit boundary within which one model and one ubiquitous language apply consistently. It is the unit of model consistency (inside it, terms and rules do not contradict each other) and, in practice, the unit of team ownership.

One physical thing becomes several context-specific models that share only an identifier:

// catalog context: what a shopper sees
record Product(String sku, String title, String description, List<URI> images) {}

// inventory context: what the warehouse tracks
record StockItem(String sku, String binLocation, int onHand, int reserved) {
    int available() { return onHand - reserved; }
}

// pricing context: what finance controls
record PriceRule(String sku, BigDecimal listPrice, Currency currency, Optional<BigDecimal> promo) {}

Each model is small, owned by one team, and free to change without asking the others; the cost is translation where contexts meet, which is what context maps describe.

The anti-corruption layer is the one you will write most often: a translator at the edge so that the upstream model's names, quirks and invariants never appear in your domain code.

// The ERP's model, as it arrives
record ErpOrderDto(@JsonProperty("ORDNO") String orderNo, @JsonProperty("SHIPZIP") String zip,
                   @JsonProperty("CTRY") String country, @JsonProperty("LINES") List<ErpLine> lines) {}
record ErpLine(@JsonProperty("ITEM") String item, @JsonProperty("QTY") int qty,
               @JsonProperty("WGT_G") int grams) {}

// Shipping's own model
record Shipment(String orderRef, String postcode, String countryIso, List<Parcel> parcels) {}
record Parcel(String sku, int qty, int grams) {}

@Component
class ErpShipmentTranslator {                      // the anti-corruption layer
    Shipment toShipment(ErpOrderDto dto) {
        var parcels = dto.lines().stream()
                .map(l -> new Parcel(l.item().trim(), l.qty(), l.grams())).toList();
        return new Shipment(dto.orderNo(), dto.zip().replace(" ", ""), iso(dto.country()), parcels);
    }
    private static String iso(String c) {
        return switch (c.trim().toUpperCase()) { case "UK", "GB" -> "GB"; default -> c.trim().toUpperCase(); };
    }
}

Event storming

A workshop technique (Alberto Brandolini) for discovering the domain with the people who know it. Everyone writes domain events (past tense, orange stickies) on a long wall in time order, then adds the commands that cause them (blue), the actors who issue commands, the aggregates that accept or reject commands (yellow), policies ("whenever X, do Y", lilac), read models needed to decide (green), external systems (pink) and hotspots where people disagree.

Worked exampleFor an e-commerce checkout, the big-picture session yields events such as ItemAddedToCart, OrderPlaced, PaymentAuthorized, StockReserved, OrderAllocatedToWarehouse, ParcelShipped, OrderDelivered, RefundIssued. Commands and aggregates attach to them (Place order → Order; Reserve stock → StockItem); policies link them ("when payment is authorized, allocate the order"); a hotspot appears where Sales and Finance disagree on when an order "counts". The clusters of aggregates with their own vocabulary (Sales, Inventory, Payments, Shipping) are the candidate bounded contexts.

Subdomains and mapping contexts to services

The problem space splits into subdomains: the core domain is what differentiates the business (pricing strategy, recommendation, routing) and deserves your best engineers and custom code; supporting subdomains are necessary and specific but not differentiating (returns workflow); generic subdomains are solved problems (identity, payments, email, tax calculation), so buy or adopt a product rather than build them.

Bounded contexts belong to the solution space. Map them to services usually one-to-one; a young system may start with several contexts in one service (or one modular monolith, L397) and split later, because a context boundary is cheap to keep inside a process and expensive to get wrong across a network. Never split one context across services: its invariants would need a distributed transaction.

What breaks in production
  • Entity services (CustomerService, ProductService, OrderService each wrapping a table) instead of contexts: every use case calls all of them synchronously.
  • A shared canonical model library imported by every service: a shared kernel nobody can change, a distributed monolith in disguise.
  • No anti-corruption layer around a legacy system: its field names and status codes spread through your domain and outlive the legacy system itself.

Practice · 45 min

  1. Run a 20-minute solo event storm for a food-delivery app: at least 20 events, then commands, aggregates and policies; draw the context boundaries.
  2. Write the "Order" model for two of your contexts as records and list which fields each has that the other does not.
  3. Draw a context map for your contexts with a relationship type on every arrow and one sentence of justification.
  4. Implement an anti-corruption layer for an external API response you have used, with a unit test of the translation.

Decomposition Strategies & Database Per Service

45m video45m practice

Extract services one capability at a time behind a routing façade, verify each step by running old and new side by side, and give every service its own data, because a shared database quietly undoes every boundary you drew.

Choosing what to cut

  • By business capability: what the business does (catalogue, ordering, billing, shipping). Capabilities are stable over years even as processes change, and they map onto teams.
  • By subdomain: the DDD view (L398): core, supporting and generic subdomains, refined into bounded contexts. In practice the two approaches mostly agree; subdomains add the language test.
  • By technical layer (a UI service, a business-logic service, a data-access service): every feature touches every service, and every release is coordinated. Avoid.

Strangler fig, branch by abstraction, parallel run

@Bean
RouteLocator strangler(RouteLocatorBuilder routes) {          // Spring Cloud Gateway as the façade
    return routes.routes()
        .route("billing-extracted", r -> r.order(0).path("/api/invoices/**").uri("http://billing:8080"))
        .route("monolith",          r -> r.order(100).path("/**").uri("http://monolith:8080"))
        .build();
}

Branch by abstraction handles calls inside the monolith: put an interface in front of the capability, make the old code one implementation, add a second implementation that calls the new service, and switch with a flag. Parallel run uses both: the old result is still returned while the new one is computed and compared, so you find differences with production traffic before anyone depends on them.

interface PricingPort { BigDecimal price(String sku, int qty); }

@Primary @Component                                       // callers inject PricingPort and get this
class ParallelRunPricing implements PricingPort {
    private static final Logger log = LoggerFactory.getLogger(ParallelRunPricing.class);
    private final PricingPort legacy, candidate;          // in-process code vs RestClient-based adapter
    private final Executor shadow;
    private final Counter mismatches;

    ParallelRunPricing(LegacyPricing legacy, PricingServiceClient candidate,
                       Executor shadow, MeterRegistry meters) {
        this.legacy = legacy; this.candidate = candidate; this.shadow = shadow;
        this.mismatches = meters.counter("pricing.parallel.mismatch");
    }

    @Override
    public BigDecimal price(String sku, int qty) {
        BigDecimal expected = legacy.price(sku, qty);      // users still get this answer
        CompletableFuture.supplyAsync(() -> candidate.price(sku, qty), shadow)
            .thenAccept(actual -> {
                if (actual.compareTo(expected) != 0) {
                    mismatches.increment();
                    log.warn("pricing mismatch sku={} legacy={} new={}", sku, expected, actual);
                }
            })
            .exceptionally(e -> { log.warn("candidate failed sku={}", sku, e); return null; });
        return expected;
    }
}

Shadow calls must be side-effect free (pricing, search, recommendations); never parallel-run a payment.

Database per service

DefinitionDatabase per service: a service's persistent data is private to it, reachable by others only through its API or the events it publishes. It may live on a shared server, but no other service reads or writes its tables.

A shared database recouples everything: a column rename breaks services you have never heard of, a slow query from one service hurts all, and every team must agree on schema migrations. Separation costs joins, foreign keys and ACID transactions across services. The replacements:

  • API composition: a composer calls several services and joins in memory; simple, but latency and availability are those of the slowest call.
  • CQRS read models: a service subscribes to others' events and maintains a denormalized view optimised for one query (the order-history page).
  • Data duplication with events: keep the copy of customer name you need, updated from CustomerRenamed; accept staleness.
  • Shared reference data (countries, currencies, tax codes, the product catalogue): either truly static data in a versioned library, or one owning service that publishes changes everyone caches. Not a shared table.

Splitting a database

  1. Find the seam: tables written mostly by one module. Query logs show which joins and foreign keys cross it.
  2. Break cross-seam joins in the monolith first: replace them with calls through the module's API or with replicated columns.
  3. Drop the foreign keys across the seam and enforce what matters in code or by events.
  4. Move the tables: a separate schema first, then a separate database owned by the new service.
  5. Synchronize during the transition (dual write with reconciliation, or better CDC from old to new), verify counts and checksums, cut over reads, then writes, then delete the old tables.

Granularity, ownership and repositories

Too big and several teams share one service again. Too small and one user action fans out into a chain of synchronous nano-service calls with all the network cost and none of the autonomy. Heuristics: one team can own it fully; a typical feature changes one service; it holds the data for its own decisions; synchronous call chains stay at two or three hops; it can be deployed alone. Start coarse; splitting a service is easier than merging two.

"You build it, you run it": the owning team is on call for its service, which pays for itself in better alerts and fewer midnight surprises. A service template (a generated skeleton with logging, metrics, tracing, health probes, CI pipeline and Dockerfile) keeps 20 services operable by the same rules. Monorepo vs polyrepo: a monorepo allows atomic cross-service changes and one version of shared tooling but needs build tooling that rebuilds only what changed; a polyrepo gives clear ownership and independent pipelines but lets libraries drift. Ownership and an independent pipeline per service matter more than which one you pick.

What breaks in production
  • "Temporary" shared tables between the monolith and the new service that become permanent coupling.
  • Dual writes without reconciliation: the stores drift and nobody notices until a customer does.
  • Extracting the core first: the most-coupled code with the most callers, so every mistake is maximally expensive.
  • API composition across five services on a hot page: availability is the product of theirs.

Practice · 45 min

  1. Take a monolith schema you know (or a sample shop) and mark the seams; list every cross-seam foreign key and join.
  2. Put a Spring Cloud Gateway in front of a monolith and move one route to a new service; switch it back without a deploy of either.
  3. Implement ParallelRunPricing and inject a deliberate rounding difference; watch the mismatch counter.
  4. Design a CQRS read model for "my orders with product names and shipment status" fed by three services' events.

Spring Cloud: Overview, Release Trains & Compatibility

35m video35m practice

Spring Cloud is a set of independently versioned projects shipped together as a release train that must match your Spring Boot version exactly; knowing which components are current, which are gone, and which your platform already provides saves most of the pain.

What it provides, and what it dropped

Spring Cloud packages distributed-systems patterns as Boot starters: externalized configuration, service discovery, client-side load balancing, an API gateway, declarative HTTP clients, circuit breakers, messaging bindings, contract testing. The original Netflix OSS stack is mostly gone:

If a tutorial uses @EnableHystrix, @RibbonClient or @EnableZuulProxy, it predates Spring Boot 3 and its code will not compile against a current train.

Release trains and the compatibility matrix

Each train bundles compatible versions of every sub-project. Early trains were named after London Underground stations in alphabetical order (Angel, Brixton, … Hoxton); since 2020.0 versions are calendar-based (YYYY.MINOR.PATCH) and the station codename lives on as a nickname (2020.0 Ilford, 2022.0 Kilburn, 2023.0 Leyton, 2024.0 Moorgate, 2025.0 Northfields).

DefinitionEvery train supports a specific Spring Boot minor line, for example 2022.0 with Boot 3.0, 2023.0 with Boot 3.2/3.3, 2024.0 with Boot 3.4, and 2025.0 with Boot 3.5. A mismatch is the most common reason a Spring Cloud app "doesn't start": a compatibility verifier fails fast at startup with a message naming the Boot version, or, if disabled, you get NoSuchMethodError and ClassNotFoundException deep inside auto-configuration. The bootstrap context and spring.config.import

Before 2020.0, a client read bootstrap.yml in a separate parent "bootstrap" application context that ran first, fetched remote configuration, and then started the real context. Boot 2.4's Config Data API replaced it: remote sources are declared in the normal application.yml with spring.config.import, ordered and optional like any other source. The bootstrap context is disabled by default; adding spring-cloud-starter-bootstrap brings it back for legacy setups, but new code should not use it.

spring:
  application:
    name: order-service
  config:
    import: "optional:configserver:http://config:8888"   # replaces bootstrap.yml

When you do not need Spring Cloud

On Kubernetes, a Service gives a stable DNS name with load balancing (discovery and LB), ConfigMaps and Secrets give configuration, and probes give health management. Many teams on Kubernetes use only the Gateway (or an ingress controller), RestClient with HTTP interfaces, and Resilience4j, which works without Spring Cloud at all. Eureka, Config Server and LoadBalancer earn their place on VMs, ECS or mixed estates.

The reference architecture for this phase

What breaks in production
  • Upgrading Boot alone: the app fails at startup, or worse, a disabled verifier lets it start and fail later at the first call into a mismatched library.
  • Copying 2019 tutorials: Hystrix, Ribbon and Zuul code does not exist on current trains.
  • A forgotten bootstrap.yml after an upgrade: silently ignored, so the service starts with local defaults instead of its real configuration.

Practice · 35 min

  1. Generate a project on start.spring.io with Gateway, Config Client and Eureka Client; read the generated BOM import and note the train for your Boot version.
  2. Change the Boot version one minor line forward without changing the train and record the startup failure; then fix it.
  3. Convert a legacy bootstrap.yml to spring.config.import and prove the remote properties still load.
  4. For your target platform, write down which of config, discovery and load balancing it provides natively, and which Spring Cloud modules you would therefore skip.

Spring Cloud Config Server & Client

45m video50m practice

Config Server turns a Git repository into an HTTP property source keyed by application, profile and label, so N services in M environments read versioned, reviewable configuration; refresh and the bus change it at runtime, but a ConfigMap plus a rolling restart is often the simpler answer.

Why centralize configuration

With 10 services in 4 environments there are 40 configurations. Baked into images, a timeout change means 10 rebuilds; scattered across deployment scripts, nobody can answer "what is production's payment timeout and who changed it?". A central, versioned store gives one place to look, history and review through Git, shared defaults with per-service overrides, and the same artifact promoted unchanged from test to production.

The server

@SpringBootApplication
@EnableConfigServer                                  // from spring-cloud-config-server
public class ConfigServerApplication {
    public static void main(String[] args) { SpringApplication.run(ConfigServerApplication.class, args); }
}
server:
  port: 8888

  cloud:
    config:
      server:

          default-label: main

          username: config-bot

Git is the default backend: labels are branches, tags or commit ids, so label=v2.3.1 pins a release to an exact configuration. Other backends: the file system (native profile, for local work), HashiCorp Vault, JDBC tables, AWS S3, and AWS Parameter Store or Secrets Manager; several can be combined with the composite profile.

How a request is resolved

DefinitionEvery configuration lookup is keyed by three coordinates: application (the client's spring.application.name), profile (its active profiles) and label (a Git branch, tag or commit). The answer is an ordered list of property sources, most specific first.

A client asks for /{application}/{profile}/{label}, e.g. /order-service/prod/main. The server checks out the label and returns property sources from most to least specific: order-service-prod.yml, order-service.yml, application-prod.yml, application.yml. Earlier sources win, so application.yml holds defaults shared by every service and per-service, per-profile files override them.

Encryption

Secrets are stored encrypted in Git as '{cipher}AQB…'. The server's /encrypt endpoint encrypts a value with the configured key (a symmetric encrypt.key, or better an RSA key from a keystore), /decrypt reverses it, and by default the server decrypts before sending, so clients receive plaintext over TLS. Alternatively clients decrypt themselves and the server never sees plaintext. Either way the key, not the repository, is the secret to guard and rotate.

# order-service-prod.yml

Refreshing at runtime

@RestController
@RefreshScope                       // a proxy; the target bean is rebuilt after a refresh

    CheckoutFlags(@Value("${features.new-checkout:false}") boolean newCheckout) {

POST /actuator/refresh re-fetches configuration, publishes an EnvironmentChangeEvent listing the changed keys, rebinds mutable @ConfigurationProperties beans, and discards @RefreshScope beans so the next call creates them with new values. That is one instance. Spring Cloud Bus (spring-cloud-starter-bus-kafka or -amqp) adds POST /actuator/busrefresh, which broadcasts the refresh to every instance over the broker; a Git webhook to the server's /monitor endpoint (spring-cloud-config-monitor) can trigger it on push. Not everything is refreshable: a HikariDataSource is excluded by default, so a database URL change still needs a restart.

Securing it, and the honest alternative

The config server can read every secret of every service: run it on a private network with TLS, require authentication (basic auth as above, or OAuth2 client credentials), give its Git token read-only access, never expose /encrypt, /decrypt or the clients' /actuator/refresh publicly, and run two or more replicas so it is not a startup single point of failure.

On Kubernetes, most teams skip all of this: configuration lives in ConfigMaps and Secrets (from Git through a GitOps tool, secrets from an external secret store), mounted as files or environment variables, and a change triggers a rolling restart. Restarts are cheap with several replicas, every pod runs a known configuration, and there is no runtime refresh to reason about.

What breaks in production
  • Plaintext secrets in the config repo: Git history keeps them forever, even after you encrypt them later.
  • Partial refresh: half the fleet refreshed, half not, because one instance missed the call; use the bus and watch for the changed-keys log.
  • Refreshing things that cache values at startup (thread pools, clients built in constructors outside refresh scope): the change is reported but never takes effect.
  • A config server outage during a deploy with optional:: new pods start with defaults and pass health checks.

Service Discovery with Eureka

45m video50m practice

Eureka is an AP registry: instances register and renew leases, clients cache the registry and choose an instance themselves, and every layer of caching makes the view eventually consistent, which is why a dead instance can keep receiving traffic for a while.

The problem, and two styles of discovery

With autoscaling and rolling deploys, instances appear and disappear and their IPs change; a hardcoded http://10.0.3.17:8080 is wrong within hours. Discovery maps a logical name (inventory-service) to the current healthy instances.

DefinitionClient-side discovery: the caller fetches the instance list from a registry and picks one itself (Eureka plus Spring Cloud LoadBalancer). Server-side discovery: the caller sends to one stable address and a load balancer or DNS-based proxy picks the instance (a Kubernetes Service, an AWS ALB). Client-side saves a hop and allows smart client policies; server-side keeps clients simple and language-agnostic.

Eureka Server

DiscoveryClient is the Spring Cloud abstraction, so the same code works on Consul or Kubernetes (L403). A @LoadBalanced RestTemplate or WebClient.Builder works the same way; instance selection is the subject of L404.

Self-preservation

The server computes how many renewals per minute it expects from its registered instances. If actual renewals fall below renewal-percent-threshold (85%) of that, it assumes a network problem between itself and the clients, not mass death, and stops expiring leases. The dashboard shows a red "EMERGENCY! EUREKA MAY BE INCORRECTLY CLAIMING INSTANCES ARE UP WHEN THEY'RE NOT" banner.

This is the right call during a partition (better to keep routing to instances that are probably alive than to erase the registry), and confusing everywhere else: in a small dev setup, stopping two of three instances drops renewals below the threshold and the dead ones stay listed forever. Disable it in development, keep it in production, and rely on client-side retries plus health-aware load balancing to cope with stale entries.

The eventual-consistency delay

Shorter renewal and expiry intervals (10 s / 30 s above), a shorter fetch interval and a shorter LoadBalancer cache TTL cut the window to well under a minute, at the cost of more heartbeat and fetch traffic on the servers. Whatever you tune, callers still need timeouts and retries on another instance, because the registry is never instantly right.

Zones and regions

Give each instance metadata-map.zone and list zones in eureka.client.availability-zones; clients then prefer Eureka servers in their own zone, and Spring Cloud LoadBalancer's zone-preference supplier (spring.cloud.loadbalancer.zone) prefers instances in the caller's zone, falling back to others when none are available. Regions are separate registries; cross-region calls should be explicit, not a load-balancer accident.

What breaks in production
  • Registering container hostnames that other hosts cannot resolve; set prefer-ip-address.
  • Duplicate instance ids: the default is host, name and port, so instances with identical hostnames or a random port (server.port=0 registers as 0) overwrite each other's registration.
  • A mutated shared builder: calling baseUrl() on the injected singleton RestClient.Builder changes it for every other client; clone first.
  • Self-preservation surprises after a large scale-down: dead instances stay listed and callers time out against them.

Consul, Kubernetes-Native Discovery & DNS

40m video40m practice

Discovery is a platform concern: Consul provides it for any estate through agents, gossip and DNS, and Kubernetes provides it built in through Services and CoreDNS, so on Kubernetes the best discovery library is usually none at all.

Consul

Consul runs an agent on every node (client mode) and a small cluster of servers (three or five). Servers hold the catalog and KV store and replicate them with Raft, so writes need a quorum (a CP design, unlike Eureka). Agents and servers form a membership pool with a gossip protocol (Serf, a SWIM variant): each member periodically probes random peers, so node failures are detected and spread in seconds without a central heartbeat target.

  • Registration with health checks: services register with their local agent, which runs the checks (HTTP, TCP, gRPC, or a TTL the app must refresh) and reports only state changes to the servers. Unhealthy instances are filtered out of queries.
  • KV store for configuration and feature flags, with blocking queries so watchers learn about changes immediately.
  • DNS and HTTP interfaces: dig @127.0.0.1 -p 8600 inventory.service.consul returns healthy instances, so even non-Java clients can discover; GET /v1/health/service/inventory?passing returns them with metadata.
# spring-cloud-starter-consul-discovery + spring-cloud-starter-consul-config

      port: 8500

        health-check-interval: 10s
        instance-id: ${spring.application.name}:${random.value}
        prefer-ip-address: true

Consul implements the same DiscoveryClient abstraction as Eureka, so @LoadBalanced clients and discovery.getInstances("inventory") work unchanged; switching registries is a dependency and configuration change, not a code change.

Kubernetes-native discovery

A Service selects pods by label and gets a stable virtual ClusterIP; kube-proxy (iptables or IPVS rules on every node) forwards connections to one of the ready pods. CoreDNS publishes inventory.shop.svc.cluster.local (and the short name inventory inside the same namespace). Pods also receive environment variables like INVENTORY_SERVICE_HOST, but only for Services that existed when the pod started, so prefer DNS. Discovery, health filtering and load balancing all happen without any library:

Headless Services and StatefulSets

DefinitionA headless Service (clusterIP: None) has no virtual IP: a DNS query returns the IPs of the ready pods themselves, and the client chooses. Stateful systems need this because their clients must reach a specific member (the Kafka broker leading a partition, the Postgres primary, a Cassandra seed), not any member. Client-side load balancers can also use a headless Service to get the full pod list for per-request balancing.

  selector: { app: kafka }
  ports: [{ name: broker, port: 9092 }]

The honest recommendation

On Kubernetes, use Services and DNS and skip Eureka entirely: running a second registry duplicates what the platform already does and introduces a second, less accurate source of truth. Eureka or Consul earn their place on VMs, ECS without a service mesh, or hybrid estates where some services run outside the cluster (Consul in particular spans all of them). A service mesh is the third option: sidecars receive endpoint lists from a control plane and balance per request with retries and mTLS (L417).

What breaks in production
  • Long-lived connections behind a ClusterIP: kube-proxy balances per connection, so HTTP/2, gRPC or keep-alive pools pin a client to one pod and load ends up uneven after scaling. Use a headless Service with client-side balancing, or a mesh.
  • Readiness that lies: a pod that reports ready before it can serve receives traffic at once; a pod that never reports ready is never discovered.
  • DNS caching in the JVM: a security manager or old setting with an infinite networkaddress.cache.ttl keeps resolving a headless name to dead pod IPs.
  • Two registries (Eureka inside Kubernetes) that disagree about which pods are alive.

Client-Side Load Balancing

35m video40m practice

Spring Cloud LoadBalancer, the replacement for Netflix Ribbon, rewrites http://inventory-service into a concrete instance per request: a chain of instance-list suppliers filters and caches the candidates, and a balancer picks one.

How a logical name becomes an address

Add spring-cloud-starter-loadbalancer (Eureka and Consul starters pull it in) and annotate a client builder with @LoadBalanced. For RestTemplate and RestClient this adds a LoadBalancerInterceptor; for WebClient.Builder it adds a ReactorLoadBalancerExchangeFilterFunction. Each takes the host part as a service id, asks the balancer for an instance, rewrites the URI, and sends the request.

@Configuration
class Http {
    @Bean @LoadBalanced
    RestClient.Builder lbRestClient() { return RestClient.builder(); }

    @Bean @LoadBalanced
    WebClient.Builder lbWebClient() { return WebClient.builder(); }   // reactive stack only

    @Bean
    RestClient inventory(@LoadBalanced RestClient.Builder lb) {
        return lb.clone().baseUrl("http://inventory-service").build();
    }
}

Balancers: built-in and custom

DefinitionA ServiceInstanceListSupplier produces the current candidate instances for a service id, usually as a chain of decorators around a discovery client. A ReactorServiceInstanceLoadBalancer picks one of them for each request and returns it wrapped in a Response (empty if there are none).

A balancer implements ReactorServiceInstanceLoadBalancer: given a request, return one instance. RoundRobinLoadBalancer is the default (a shared counter starting at a random position); RandomLoadBalancer is the alternative. Neither knows about load or latency, so a slow instance gets its full share. A custom one is a small class:

class WeightedRandomLoadBalancer implements ReactorServiceInstanceLoadBalancer {
    private final ObjectProvider<ServiceInstanceListSupplier> suppliers;

    WeightedRandomLoadBalancer(ObjectProvider<ServiceInstanceListSupplier> suppliers) {
        this.suppliers = suppliers;
    }

    @Override
    public Mono<Response<ServiceInstance>> choose(Request request) {
        var supplier = suppliers.getIfAvailable(NoopServiceInstanceListSupplier::new);
        return supplier.get(request).next().map(WeightedRandomLoadBalancer::pick);
    }

    private static Response<ServiceInstance> pick(List<ServiceInstance> instances) {
        if (instances.isEmpty()) return new EmptyResponse();
        int total = instances.stream().mapToInt(WeightedRandomLoadBalancer::weight).sum();
        int r = ThreadLocalRandom.current().nextInt(total);
        for (ServiceInstance i : instances) {
            r -= weight(i);
            if (r < 0) return new DefaultResponse(i);
        }
        return new DefaultResponse(instances.getLast());
    }

    private static int weight(ServiceInstance i) {             // e.g. eureka metadata-map.weight
        return Math.max(1, Integer.parseInt(i.getMetadata().getOrDefault("weight", "1")));
    }
}

Least-connections or latency-aware balancers follow the same shape but need feedback: register a LoadBalancerLifecycle bean to count in-flight requests or record response times per instance, and choose the best of two random candidates ("power of two choices") rather than scanning all.

Per-service configuration

Each service id gets its own child application context. A configuration class referenced from @LoadBalancerClient applies to one service, @LoadBalancerClients(defaultConfiguration = …) to all. Keep these classes out of component scanning (no @Configuration), or they leak into every client.

        String id = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new WeightedRandomLoadBalancer(f.getLazyProvider(id, ServiceInstanceListSupplier.class));
    }

    @Bean
    ServiceInstanceListSupplier candidates(ConfigurableApplicationContext ctx) {
        return ServiceInstanceListSupplier.builder()
                .withBlockingDiscoveryClient()                // withDiscoveryClient() on WebFlux
                .withZonePreference()
                .withCaching()
                .build(ctx);
    }
}

Supplier decorators

  • Caching (on by default with a cache provider): keeps the instance list for spring.cloud.loadbalancer.cache.ttl (35 s by default). Shorter means fresher and more registry calls.
  • Health checks: probes each instance's health endpoint and drops failing ones, useful with a registry that is slow to notice deaths.
  • Zone preference: keep only instances whose zone metadata matches spring.cloud.loadbalancer.zone, falling back to all if none match.
  • Same-instance preference: reuse the previously chosen instance while it is available.
  • Hints: filter by a hint metadata value, set per client or per request with the X-SC-LB-Hint header, e.g. to route beta users to canary instances.
  • Request-based sticky sessions: the instance id is carried in a cookie (sc-lb-instance-id by default) and that instance is chosen while it lives.

                                            #    request-based-sticky-session

Retries, metrics, and client vs server side

A retry on the next instance is what makes client-side balancing tolerant of stale registries. By default only GET requests are retried. Turning on retry-on-all-operations retries a POST that may already have been processed (the first instance charged the card, then its response timed out), so do it only for endpoints with idempotency keys (L416). With stats enabled, Micrometer exposes active, successful, failed and discarded request meters tagged by service and instance, which shows imbalance directly.

Client-side vs server-side: client-side balancing has no extra hop and allows per-request policies, but every client in every language must implement it and keep a registry view. A Kubernetes Service balances in kernel rules per connection without a hop; a mesh sidecar balances per request but adds two local proxy traversals per call. Small per-call costs matter in fan-out: a page that calls 10 services in sequence pays any added latency 10 times, and its p99 is set by the slowest of them.

What breaks in production
  • Per-client configuration with @Configuration picked up by component scan: it silently becomes the configuration for every service.
  • Retrying non-idempotent calls across instances: duplicate orders and double charges.
  • Round robin over unequal instances (different sizes, a noisy neighbour): the slow one sets your tail latency.
  • Caching plus a slow registry: dead instances stay candidates for the sum of both delays (L402).

Spring Cloud Gateway I: Routes & Predicates

45m video50m practice

Spring Cloud Gateway, the successor to Netflix Zuul, is a reactive reverse proxy built from routes: each route is an id, a destination URI, a set of predicates that must all match, and a chain of filters, and the first matching route in order wins.

The API gateway pattern

A gateway is the single entry point for external clients. It hides the internal service topology (clients see /api/orders, not five hostnames), applies cross-cutting concerns once (TLS termination, authentication, rate limiting, CORS, request logging), translates protocols where needed (HTTP to gRPC, WebSocket upgrades), and lets you move routes without clients noticing (L399). The backend-for-frontend variant runs one gateway per client type (web, mobile, partners), each shaped to that client's needs and owned by the team that builds the client.

Reactive underneath

The classic Gateway runs on Netty and WebFlux. A small number of event-loop threads (about one per core) serve every connection, which is why one gateway can hold tens of thousands of concurrent connections, and why nothing in a predicate or filter may block: one JDBC call, RestTemplate call or Thread.sleep stalls every request sharing that thread. Use reactive clients (WebClient, reactive Redis), or move blocking work to Schedulers.boundedElastic(); BlockHound detects violations in tests. For teams that prefer the servlet model, spring-cloud-gateway-server-webmvc is a blocking Gateway on Spring MVC (a good fit with virtual threads), with its own functional route API.

Evaluation order, discovery routes, and inspection

DefinitionRoutes are sorted by order (lower first) and the first route whose predicates all match handles the request; later routes are never consulted. Global filters, ordering and pre/post phases

@Component
class CorrelationIdFilter implements GlobalFilter, Ordered {
    private static final Logger log = LoggerFactory.getLogger(CorrelationIdFilter.class);
    static final String HEADER = "X-Correlation-Id";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String id = Optional.ofNullable(exchange.getRequest().getHeaders().getFirst(HEADER))
                .orElseGet(() -> UUID.randomUUID().toString());
        ServerWebExchange ex = exchange.mutate()
                .request(r -> r.headers(h -> h.set(HEADER, id))).build();   // pre phase
        ex.getResponse().getHeaders().set(HEADER, id);    // set before the response commits
        long start = System.nanoTime();
        return chain.filter(ex).then(Mono.fromRunnable(() ->                   // post phase
                log.info("{} {} {} {}ms id={}", ex.getRequest().getMethod(), ex.getRequest().getPath(),
                        ex.getResponse().getStatusCode(), (System.nanoTime() - start) / 1_000_000, id)));
    }

    @Override public int getOrder() { return Ordered.HIGHEST_PRECEDENCE; }
}

A GlobalFilter applies to every route; global and route filters are merged and sorted by Ordered, lower values first in the pre phase and therefore last in the post phase. Code before chain.filter(...) runs on the way in; code chained with .then(...) runs after the downstream response has been written, when response headers can no longer be changed.

  • Rate limiting by IP behind a load balancer: every request has the balancer's IP, so all users share one bucket.
  • Trusting the gateway alone: a service reachable inside the cluster without token checks is open to any compromised pod.
  • Retry plus CircuitBreaker in the wrong order, or retrying POST: duplicated writes and a breaker that counts the wrong thing.
  • ModifyResponseBody on large or streamed responses: buffered in memory, latency and heap spike.

Resilience4j I: Circuit Breakers

45m video50m practice

A circuit breaker watches the recent failure and slow-call rates of one dependency and, past a threshold, fails calls immediately instead of waiting on them, which turns a slow dependency from a fleet-wide outage into a local, visible degradation.

The cascading failure

Worked exampleCheckout receives 100 requests/s and calls inventory, normally in 50 ms. By Little's law the number of busy request threads is arrival rate × time in system: 100 × 0.05 = 5 of Tomcat's 200. Inventory degrades to 5 s per call: 100 × 5 = 500 threads would be needed. The pool saturates within about two seconds, requests queue, and every endpoint of checkout slows, including ones that never call inventory. The gateway's connections to checkout pile up next, and the outage climbs the call chain. With a breaker that opens on slow calls, rejected calls cost microseconds, busy threads fall back to near zero, and only the stock figure is degraded.

The fix has two parts: a timeout on every remote call, so no call can hold a thread indefinitely, and a breaker, so that once a dependency is clearly unhealthy you stop paying even the timeout on every request and give it room to recover.

The state machine

In CLOSED, calls pass and outcomes enter the sliding window. When the failure rate or slow-call rate reaches its threshold, the breaker moves to OPEN and rejects calls with CallNotPermittedException. After waitDurationInOpenState it moves to HALF_OPEN (on the next call, or by itself with automatic transition) and lets a fixed number of trial calls through; their rates decide between CLOSED and OPEN again. DISABLED (always allow, no metrics) and FORCED_OPEN (always reject) are manual states set through the registry, useful for incident response.

Annotation and functional API

Add io.github.resilience4j:resilience4j-spring-boot3 and spring-boot-starter-aop. The annotation is applied by an aspect, so the proxy rules apply: self-invocation is not protected.

DefinitionA call is a failure if it throws an exception matched by record-exceptions (all exceptions by default) and not by ignore-exceptions; it is slow if it takes longer than slow-call-duration-threshold, even when it succeeds. The library defaults are conservative (window and minimum of 100 calls, 60 s open), so a low-traffic dependency may never trip; size the window to your traffic.

Client errors such as 400 or 404 mean the dependency is working; exclude them, or a burst of bad input opens the circuit for everyone.

Fallbacks that degrade honestly

The fallback must live in the same class, return the same type, and take the original parameters plus one exception parameter; overloads for different exception types are allowed and the most specific is chosen. Good fallbacks say what they are: cached data marked stale (above), a safe default ("delivery estimate unavailable"), or a partial response the UI can render. Bad fallbacks hide failure: an empty list that looks like "no results", or a fake success for a write. A fallback that calls another remote service needs its own protection.

Events, Actuator and dashboards

/actuator/circuitbreakers shows each breaker's state and rates; /actuator/circuitbreakerevents the recent events (state transitions, errors, slow calls, rejections); with the health indicator, an open breaker can be reported in /actuator/health. Keep breaker health out of liveness and readiness groups, or one bad dependency restarts or unroutes your pods. Micrometer publishes resilience4j.circuitbreaker.state, resilience4j.circuitbreaker.calls (tagged kind: successful, failed, ignored, not permitted), failure.rate and slow.call.rate, so a Grafana panel can show state over time per dependency next to latency.

Why not Hystrix: Netflix moved Hystrix to maintenance in 2018 and Spring Cloud removed its integration in the 2020.0 train. Resilience4j is lightweight, modular (breaker, retry, bulkhead, rate limiter, time limiter as separate decorators), works with lambdas and reactive types, and does not force a thread pool per dependency as Hystrix's default isolation did.

What breaks in production
  • No timeout under the breaker: slow calls are only counted when they finish, so threads are still exhausted while the window fills.
  • Counting 4xx as failures: invalid input from one client opens the circuit for all.
  • One breaker for many dependencies, or one per endpoint of the same dependency: the wrong blast radius either way. One per downstream service is the usual unit.
  • Defaults on low traffic: 100 calls minimum means the breaker never opens during the incident.
  • Breaker state in readiness: a dependency outage takes every pod out of the load balancer.

Resilience4j II: Retry, Bulkhead, Rate Limiter & TimeLimiter

45m video50m practice

Each Resilience4j decorator bounds one thing (attempts, concurrency, rate, or time), and they only work together when stacked in the right order around a call that already has a transport timeout.

Retry, with backoff and jitter

resilience4j:
  retry:
    instances:
      partner:
        max-attempts: 3                      # total attempts, including the first
        wait-duration: 200ms
        enable-exponential-backoff: true     # 200 ms, 400 ms, ...
        exponential-backoff-multiplier: 2
        enable-randomized-wait: true         # jitter: spread retries out
        randomized-wait-factor: 0.5          # each wait is ±50% of the nominal
        retry-exceptions:
          - java.io.IOException
          - java.util.concurrent.TimeoutException
        ignore-exceptions:
          - io.github.resilience4j.circuitbreaker.CallNotPermittedException
        result-predicate: com.shop.partner.RetryWhilePending   # retry on a result, not only on exceptions

Without jitter, every client that failed at the same moment retries at the same moment, producing synchronized waves that keep a recovering service down. Exponential backoff spaces attempts out; randomisation desynchronizes them (in recent versions, enabling both gives randomized exponential backoff). retryOnResult (the result-predicate property) retries when a call succeeds but returns a "not ready yet" answer.

Rule · Retry amplificationIf each of k layers makes up to n attempts, one user request can become nk requests at the bottom layer: 3 attempts at 3 layers is 27. Retry at one layer (usually the one closest to the failing dependency), and only for idempotent operations: GET, PUT with full state, or writes carrying an idempotency key (L416). Retrying a non-idempotent POST after a timeout can execute it twice.

Bulkhead: bound the blast radius

DefinitionA bulkhead caps how much of your capacity one dependency can occupy. SEMAPHORE: at most max-concurrent-calls callers inside at once on their own threads, others wait up to max-wait-duration and then get BulkheadFullException. THREADPOOL: calls run on a dedicated bounded pool and queue (core-thread-pool-size, max-thread-pool-size, queue-capacity); the method must return CompletableFuture.

With 200 request threads and a semaphore of 20 on inventory, a hung inventory can tie up at most 20 threads; the other 180 keep serving everything else. A semaphore is cheap and works with virtual threads; a thread pool also isolates the caller's thread from the call, at the cost of a handoff and a pool to size.

Rate limiter and time limiter

@RateLimiter throttles your calls, typically to a partner API with a quota: at most limit-for-period calls per limit-refresh-period; a caller waits up to timeout-duration for a permit, then gets RequestNotPermitted. It is per JVM, so ten pods allow ten times the limit; a fleet-wide quota needs a shared limiter (Redis, L390).

@TimeLimiter fails a CompletableFuture (or reactive) call that takes longer than timeout-duration, optionally cancelling it. Cancelling a CompletableFuture does not interrupt the thread doing the work, and nothing closes the socket, so the request keeps running and holding resources after you gave up. That is why a transport-level timeout (connect and read timeouts on the HTTP client, a statement timeout on JDBC) is still mandatory; the time limiter only bounds how long the caller waits.

Stacking order

@Service
class PartnerQuotes {
    private final QuoteClient client;                   // HTTP client: 300 ms connect, 800 ms read
    PartnerQuotes(QuoteClient client) { this.client = client; }

    @Retry(name = "partner", fallbackMethod = "noQuote")   // the one fallback, on the outermost
    @CircuitBreaker(name = "partner")
    @RateLimiter(name = "partner")
    @TimeLimiter(name = "partner")
    @Bulkhead(name = "partner", type = Bulkhead.Type.THREADPOOL)
    public CompletableFuture<Quote> quote(String sku) {
        return CompletableFuture.completedFuture(client.fetch(sku));  // runs on the bulkhead pool
    }

    private CompletableFuture<Quote> noQuote(String sku, Throwable t) {
        return CompletableFuture.completedFuture(Quote.unavailable(sku, t.getClass().getSimpleName()));
    }
}

      inventory: { max-concurrent-calls: 20, max-wait-duration: 0 }

Rule · Decorator orderThe Spring Boot aspects apply, outermost first: Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( call ) ) ) ) ), whatever order you write the annotations in (each aspect's order is configurable). Read it from the inside: the bulkhead bounds concurrent real calls; the time limiter bounds each attempt; the rate limiter spends a permit per attempt; the breaker records every attempt's outcome; retry re-enters the whole stack, so a retry also passes the breaker check and is rejected cheaply when the circuit is open.

What goes wrong when inverted: with the breaker outside retry, it sees one outcome per three attempts and opens far too late while the retries keep hammering the dependency; with the time limiter outside retry, one timeout covers all attempts and later attempts never get a fair chance; with the bulkhead outside retry, a caller holds its permit through every backoff sleep. Also tell Retry to ignore CallNotPermittedException, BulkheadFullException and RequestNotPermitted: retrying a local rejection only adds delay.

Fallbacks on several annotations chain from the inside out: an inner fallback converts the failure into a normal return, so outer decorators never see it, which silently disables retries and hides failures from the breaker. Declare one fallback, on the outermost decorator.

Spring Retry, the simpler local option

For a single in-process retry (an optimistic-lock conflict, a deadlock victim) where breakers and bulkheads add nothing, Spring Retry is enough: @EnableRetry, then @Retryable(retryFor = OptimisticLockingFailureException.class, maxAttempts = 3, backoff = @Backoff(delay = 50, multiplier = 2, random = true)) and an optional @Recover method. Spring Framework 7 brings comparable retry and concurrency-limit annotations into the core framework. For remote dependencies, use Resilience4j so retries, breaker and metrics share one configuration.

What breaks in production
  • Retries at every layer: a short outage becomes a self-inflicted load spike of 9× or 27×.
  • No jitter: synchronized retry waves every backoff interval.
  • TimeLimiter as the only timeout: abandoned calls pile up on sockets and threads after the caller has moved on.
  • Per-pod rate limits sized as if global: the partner API sees N times the agreed rate and throttles or bans you.
  • A fallback on an inner annotation: the breaker never opens because every failure became a success.

Metrics: Micrometer, Prometheus & Grafana

50m video55m practice

A metric is a cheap, pre-aggregated number with a small, bounded set of labels. Micrometer records them in-process, Prometheus pulls and stores them as time series, and Grafana turns them into RED/USE dashboards and SLO alerts. The design rule that keeps all three alive is bounded cardinality.

Micrometer: SLF4J for metrics

Application code talks to a MeterRegistry; a backend-specific registry (PrometheusMeterRegistry, OTLP, Datadog…) decides how meters are stored and exported. Boot auto-configures one registry per backend jar on the classpath and wraps several in a CompositeMeterRegistry. Meter names are dot-separated lowercase (orders.placed); each registry applies its own naming convention, so Prometheus sees orders_placed_total, and a timer named http.server.requests becomes http_server_requests_seconds_count, _sum, _max and, if enabled, _bucket.

@Component
public class OrderMetrics {
    public enum Channel { WEB, MOBILE, PARTNER }               // bounded set, safe as a tag

    private final MeterRegistry registry;
    private final Timer charge;
    private final AtomicInteger inFlight;                       // strong reference held here

    public OrderMetrics(MeterRegistry registry) {
        this.registry = registry;
        this.charge = Timer.builder("payment.charge")
                .description("Time to charge the card")
                .publishPercentileHistogram()                   // export buckets, not p99s
                .serviceLevelObjectives(Duration.ofMillis(200), Duration.ofMillis(500))
                .register(registry);
        this.inFlight = registry.gauge("orders.in.flight", new AtomicInteger());
        DistributionSummary.builder("order.amount").baseUnit("eur").register(registry);
    }

        registry.counter("orders.placed", "channel", channel.name()).increment();
        inFlight.incrementAndGet();
        try {
            return charge.record(chargeCall);
        } finally {
            inFlight.decrementAndGet();
        }
    }
}

Tags and the cardinality explosion

DefinitionEvery distinct combination of name and tag values is a separate time series. The series count for a meter is the product of its tags' distinct values, multiplied again by the bucket count if it publishes a histogram.

http.server.requests with 40 URI templates, 4 methods, 8 statuses and 3 exceptions is already a few thousand series; with 60-odd histogram buckets each it is far more. Tag it with a raw URL (/orders/81723), a user id or an order id and every new value mints a new series. Prometheus holds recent series in memory, so this is how Prometheus servers run out of memory. Spring tags the template (/orders/{id}) for this reason; you guard custom meters with a filter.

    return MeterFilter.maximumAllowableTags("http.client.requests", "uri", 100, MeterFilter.deny());

High-cardinality detail (which order, which user) belongs in logs and traces, not metrics.

Histograms aggregate, percentiles don't

publishPercentiles(0.99) computes p99 inside each JVM and exports it as a gauge. You cannot combine those: the mean of three pods' p99s is not the fleet's p99, and nor is the max. publishPercentileHistogram() exports cumulative bucket counters (_bucket{le="0.5"}); counters can be summed across pods, and histogram_quantile then estimates the quantile of the combined distribution. The price is one series per bucket, so trim the range with minimumExpectedValue/maximumExpectedValue or export only the SLO boundaries you alert on.

Worked exampleSLI: the share of valid requests that are good (non-5xx and under 300 ms, counted from the le="0.3" bucket). SLO: 99.9% over 30 days. What breaks in production
  • Unbounded tags: an id or raw path as a tag; Prometheus memory climbs until it is OOM-killed and you lose all metrics during the incident.
  • NaN gauges from weakly referenced state that has been garbage-collected.
  • Averaged p99s on a fleet dashboard: a number that looks plausible and means nothing.
  • rate() over a window shorter than about four scrape intervals: gaps and jumpy graphs. Using rate on a gauge: nonsense.
  • /actuator/prometheus exposed on the public port. Serve management on a separate port or restrict it.

Distributed Tracing

50m video55m practice

A trace is the causal tree of every timed operation one request caused, stitched together by an id that travels in headers. In Boot 3, Micrometer Tracing (the successor to Spring Cloud Sleuth) creates the spans, propagates the context, and puts the trace id on every log line.

Why logs and metrics are not enough

A checkout goes gateway → orders → inventory → payment → Kafka → shipping. Metrics tell you checkout p99 rose from 300 ms to 2 s; they cannot tell you which hop. Each service's logs are complete but unconnected, and timestamps from eight hosts do not line up reliably. A trace answers the question directly: this request, these calls, in this order, this long each.

DefinitionA span is one timed operation: name, start and end, a 64-bit span id, its parent span id, a kind (server, client, producer, consumer), a status, attributes (key-value tags; high-cardinality values such as an order id are fine here) and events (timestamped notes inside the span, such as "retry 2" or "cache miss"). A trace is every span sharing one 128-bit trace id, which forms a tree through the parent links. Baggage is user-defined key-values propagated to every downstream service with the trace context; it costs bytes on every hop and is not recorded on spans unless you tag them.

@Service
public class PricingService {
    private final ObservationRegistry observations;
    private final Tracer tracer;
    private final PricingRules rules;

    public PricingService(ObservationRegistry observations, Tracer tracer, PricingRules rules) {
        this.observations = observations;
        this.tracer = tracer;
        this.rules = rules;
    }

    public Quote quote(Cart cart) {
        return Observation.createNotStarted("pricing.quote", observations)
                .contextualName("price cart")
                .lowCardinalityKeyValue("tier", cart.tier().name())      // metric tag and span tag
                .highCardinalityKeyValue("cart.id", cart.id().toString()) // span only
                .observe(() -> {
                    Span span = tracer.currentSpan();
                    Quote q = rules.price(cart);
                    if (span != null && q.discounted()) span.event("discount applied");
                    return q;
                });
    }
}

The fix is to capture the context on submit and restore it on run, which the io.micrometer:context-propagation library does for MDC, observations and Reactor.

Sampling, backends, and reading a waterfall

Head-based sampling decides at the root span (keep 10%) and the decision travels in the sampled flag, so every service agrees. It is cheap but random: the one failed checkout in a thousand is probably not kept. Tail-based sampling buffers complete traces in a collector (the OpenTelemetry Collector's tail-sampling processor) and keeps all errors and slow traces plus a sample of the rest; it costs collector memory and needs every span of a trace routed to the same collector instance. The tradeoff is storage cost against seeing the rare bad request.

Three pillars, one story: OpenTelemetry

The value comes from linking signals. Prometheus histograms can carry exemplars (a trace id attached to a sample bucket), so a Grafana latency panel jumps to an example slow trace; a trace view jumps to its logs by searching traceId in Loki or Elasticsearch; a log line links back to its trace. OpenTelemetry is the converging standard for the API, the SDK, the OTLP wire protocol and the Collector. What breaks in production
  • Orphan traces: work submitted to an undecorated executor, the common ForkJoinPool, or a hand-made new Thread.
  • Uninstrumented clients: RestClient.create() or new RestTemplate() instead of the injected builders, so the downstream service starts a fresh trace.
  • Mixed propagation formats between teams, which splits every trace at the boundary.
  • Baggage leaks: baggage goes to every downstream, third-party APIs included. Never put PII or tokens in it, and strip trace headers at your egress.
  • 100% sampling in production: exporter queues fill, spans are dropped at random, and the tracing bill rises steeply.
  • Clock skew: a child span can appear to start before its parent. Trust durations within one host, not offsets between hosts.

Centralized Logging

45m video50m practice

Each service writes one JSON object per line to stdout. Infrastructure collects, buffers, stores and indexes those lines, so any request can be found across every pod by its trace id, and nothing sensitive was ever written in the first place.

Why kubectl logs stops working

kubectl logs shows one container's stdout, and only while the pod exists (plus one previous restart with --previous). With three services at four replicas each you are grepping twelve streams by hand, the pod that crashed has taken its logs with it, nothing is retained past node log rotation, and nothing connects the gateway's line to the payment service's. Centralized logging moves logs off the pods the moment they are written.

The pipeline

The container runtime writes stdout to files under /var/log/containers. A collector running as a DaemonSet tails them, adds Kubernetes metadata (namespace, pod, container, labels) and ships them on. A buffer, either Kafka or the collector's own disk queue, absorbs bursts and store outages so an incident's log storm does not drop the very lines you need. The store indexes and retains them, and the UI queries them.

Health Checks, Probes & Graceful Shutdown in Orchestrators

40m video45m practice

Liveness, readiness and startup probes answer three different questions, and mixing them up turns a database blip into a fleet-wide restart. Graceful shutdown is a short protocol between Kubernetes and Spring: stop routing, finish in-flight work, exit before the grace period ends.

Three probes, three jobs

DefinitionLiveness: "am I wedged?" Failing it makes the kubelet restart the container. Readiness: "should I get traffic right now?" Failing it removes the pod from the Service's endpoints without restarting it. Startup: "have I finished booting?" Liveness and readiness checks are held off until it succeeds, and if it fails failureThreshold times the container is restarted. Each probe can be an HTTP GET, a TCP connect, a gRPC health check or a command.

The classic outage: liveness calls /actuator/health, which includes the database indicator. The database fails over and is unreachable for 40 seconds. Every pod fails liveness at about the same moment and Kubernetes restarts all of them. They come back cold, open connection pools at the same time against a database that is still recovering, and a 40-second blip becomes a 10-minute outage. Liveness must check only the process itself. Readiness on a shared dependency has a milder version of the same problem: every pod leaves rotation together, so clients get 503s from the ingress instead of a degraded answer from your fallback. Prefer circuit breakers and fallbacks for dependencies, and keep readiness for the pod's own state.

Actuator health groups as probes

With management.endpoint.health.probes.enabled=true (switched on automatically when Boot detects Kubernetes), Actuator exposes /actuator/health/liveness and /actuator/health/readiness. By default they contain only livenessState and readinessState, the application's own availability. The database, Redis and disk indicators stay in /actuator/health for dashboards and are not part of either probe unless you add them to a group.

server.shutdown: graceful                          # the default since Boot 3.4
spring.lifecycle.timeout-per-shutdown-phase: 20s
spring.task.execution.shutdown:
  await-termination: true
  await-termination-period: 15s
management.endpoint.health:
  probes:
    enabled: true
    add-additional-paths: true                     # /livez and /readyz on the main port
  group.readiness.include: readinessState          # add a local dependency only if the pod is useless without it

Use add-additional-paths when management runs on a separate port. A probe on the management port can pass while the main connector is wedged, so probe the port that serves traffic.

ApplicationAvailability and taking yourself out of rotation

Boot tracks availability as two states held by ApplicationAvailability. LivenessState becomes CORRECT once the context has refreshed. ReadinessState becomes ACCEPTING_TRAFFIC only after all ApplicationRunner and CommandLineRunner beans have finished, which makes a runner the natural place for cache warm-up. It flips to REFUSING_TRAFFIC when shutdown begins. You can change either state yourself by publishing an AvailabilityChangeEvent:

@Component
public class Availability {
    private final ApplicationEventPublisher events;
    private final ApplicationAvailability availability;

    public Availability(ApplicationEventPublisher events, ApplicationAvailability availability) {
        this.events = events;
        this.availability = availability;
    }

    public void enterMaintenance() {           // readiness probe now fails; no restart
        AvailabilityChangeEvent.publish(events, this, ReadinessState.REFUSING_TRAFFIC);
    }

    public void leaveMaintenance() {
        AvailabilityChangeEvent.publish(events, this, ReadinessState.ACCEPTING_TRAFFIC);
    }

    public void markBroken(String why) {        // e.g. a watchdog sees the consumer loop stalled
        AvailabilityChangeEvent.publish(events, why, LivenessState.BROKEN);
    }

    public boolean serving() {
        return availability.getReadinessState() == ReadinessState.ACCEPTING_TRAFFIC;
    }
}

@Component
class WarmUp implements ApplicationRunner {     // readiness waits for this to return
    private final ProductCatalog catalog;
    WarmUp(ProductCatalog catalog) { this.catalog = catalog; }
    @Override public void run(ApplicationArguments args) { catalog.preload(); }
}

Only publish LivenessState.BROKEN for states that a restart actually fixes, such as a deadlocked worker or a corrupted in-memory cache, and never for "a dependency is down".

Graceful shutdown end to end

Algorithm · Pod termination
  1. The pod is marked Terminating. The endpoints controller removes it from EndpointSlices, and the kubelet starts the preStop hook.
  2. preStop sleeps (5–15 s) to cover the propagation race. Without it, requests that are still being routed reach a server that has stopped listening and fail with 502s on every deploy.
  3. SIGTERM reaches the JVM, the shutdown hook closes the context, and readiness becomes REFUSING_TRAFFIC.
  4. The web server stops accepting connections and waits for in-flight requests, up to spring.lifecycle.timeout-per-shutdown-phase.
  5. SmartLifecycle beans stop in phase order: Kafka listener containers finish the current records and commit offsets; executors wait for their tasks (await-termination). Then pools and clients close.
  6. The JVM exits. All of this must fit in preStop + drain + margin < terminationGracePeriodSeconds (default 30 s), or SIGKILL ends it mid-request.
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: orders
      image: registry.example.com/orders:1.4.2
      startupProbe:
        httpGet: { path: /livez, port: 8080 }
        periodSeconds: 5
        failureThreshold: 30            # up to 150 s to boot, then liveness takes over
      livenessProbe:
        httpGet: { path: /livez, port: 8080 }
        periodSeconds: 10
        timeoutSeconds: 3
        failureThreshold: 3             # about 30 s wedged before a restart
      readinessProbe:
        httpGet: { path: /readyz, port: 8080 }
        periodSeconds: 5
        failureThreshold: 2
      lifecycle:
        preStop:
          exec: { command: ["sh", "-c", "sleep 10"] }   # newer clusters: preStop.sleep.seconds

The JVM must actually receive SIGTERM: use the exec form ENTRYPOINT ["java", "-jar", "app.jar"], or exec java … in a script, so Java is PID 1. A shell wrapper that does not forward signals turns every shutdown into a SIGKILL after the grace period. Kafka records polled but not committed are redelivered to another consumer after the rebalance, so consumers must be idempotent (L416).

Probe timing and JVM warm-up

Detection time is roughly periodSeconds × failureThreshold. The default timeoutSeconds is 1 s, which a full GC or a cold JIT can exceed, so set it explicitly. Use a startup probe rather than a large initialDelaySeconds: it lets fast boots become ready quickly and gives slow boots (first boot after a deploy, CPU-throttled under a low limit) the whole budget. A pod that is ready is not necessarily fast, because the first requests pay for class loading and JIT. Warm hot paths in an ApplicationRunner, and consider CDS or AOT caches to cut boot time.

What breaks in production
  • A liveness probe that includes the database or a downstream service: a mass restart during exactly the incident you needed capacity for.
  • No startup probe: liveness kills a slow first boot, and the pod sits in CrashLoopBackOff.
  • No preStop sleep: a burst of 502s on every rolling deploy.
  • A grace period shorter than preStop plus drain: SIGKILL cuts requests and Kafka batches off mid-way.
  • Shell-form ENTRYPOINT: SIGTERM never reaches Java.
  • A 1-second probe timeout combined with a 2-second GC pause: random restarts under load.

Saga Pattern I: Orchestration

45m video55m practice

With no distributed transaction across services, a business operation becomes a saga: a chain of local transactions, each with a compensating action. An orchestrator keeps the state machine in its own database, sends commands, reacts to replies and timeouts, and drives the saga either forward to completion or backward through compensations.

The problem: three services, no 2PC

Placing an order means reserving stock (the inventory service's database), charging the card (the payment service plus an external payment provider), and allocating a shipment (the shipping service). Each service owns its data. Two-phase commit would need every participant, Kafka and the payment provider to support XA, and it holds locks across network round trips while a coordinator failure blocks everyone. In practice it is not available, and you would not want it if it were.

DefinitionA saga (Garcia-Molina & Salem, 1987) is a sequence of local transactions T1 … Tn, each committed on its own and each paired with a compensating transaction Ci that semantically undoes it. If Tk fails, the saga runs Ck−1 … C1 in reverse. A saga gives you atomicity in the end (all steps happen, or the effects are undone) but no isolation: other transactions can see its intermediate states.

Orchestration: one coordinator, explicit state

In orchestration, a saga orchestrator (here in the order service) holds the saga's state machine. It sends a command to one participant on that participant's command channel (inventory.commands), then waits for a reply on its own reply channel (order-saga.replies). Each reply moves the machine one step. Participants know nothing about the saga; they just execute commands and answer.

Implementing it: table, channels, timeouts, idempotency

CREATE TABLE saga_instance (
  saga_id       UUID PRIMARY KEY,
  saga_type     VARCHAR(64)  NOT NULL,
  step          VARCHAR(32)  NOT NULL,
  payload       JSONB        NOT NULL,      -- order id, lines, total, address
  step_deadline TIMESTAMPTZ,                -- when the current step times out
  attempts      INT          NOT NULL DEFAULT 0,
  version       BIGINT       NOT NULL,      -- optimistic lock
  updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX saga_due ON saga_instance (step_deadline) WHERE step NOT IN ('COMPLETED', 'CANCELLED');

Keep the transition logic a pure function, which makes it trivial to unit-test, and keep the I/O in a thin handler:

public enum Step { RESERVING, CHARGING, ALLOCATING, REFUNDING, RELEASING, COMPLETED, CANCELLED }
public enum Outcome { OK, FAILED }

public final class OrderSagaDefinition {
    public static Step next(Step step, Outcome o) {
        boolean ok = o == Outcome.OK;
        return switch (step) {
            case RESERVING  -> ok ? Step.CHARGING   : Step.CANCELLED;   // nothing to undo yet
            case CHARGING   -> ok ? Step.ALLOCATING : Step.RELEASING;
            case ALLOCATING -> ok ? Step.COMPLETED  : Step.REFUNDING;
            case REFUNDING  -> ok ? Step.RELEASING  : Step.REFUNDING;   // retry, never give up
            case RELEASING  -> ok ? Step.CANCELLED  : Step.RELEASING;
            case COMPLETED, CANCELLED -> throw new IllegalStateException("terminal: " + step);
        };
    }

    public static Optional<Command> commandFor(Step step, OrderSaga s) {
        return switch (step) {
            case RESERVING  -> Optional.of(new ReserveStock(s.id(), s.orderId(), s.lines()));
            case CHARGING   -> Optional.of(new ChargePayment(s.id(), s.orderId(), s.total()));
            case ALLOCATING -> Optional.of(new AllocateShipping(s.id(), s.orderId(), s.address()));
            case REFUNDING  -> Optional.of(new RefundPayment(s.id(), s.orderId()));
            case RELEASING  -> Optional.of(new ReleaseStock(s.id(), s.orderId()));
            case COMPLETED, CANCELLED -> Optional.empty();
        };
    }
}

@Component
class OrderSagaOrchestrator {
    private final SagaRepository sagas;
    private final Outbox outbox;

    OrderSagaOrchestrator(SagaRepository sagas, Outbox outbox) { this.sagas = sagas; this.outbox = outbox; }

    @KafkaListener(topics = "order-saga.replies", groupId = "order-saga")
    @Transactional
    public void onReply(SagaReply reply) {
        OrderSaga saga = sagas.findById(reply.sagaId()).orElseThrow();
        if (saga.step() != reply.step()) return;              // duplicate or stale reply
        Step next = OrderSagaDefinition.next(saga.step(), reply.outcome());
        OrderSaga moved = sagas.save(saga.moveTo(next, Instant.now().plusSeconds(30)));
        OrderSagaDefinition.commandFor(next, moved).ifPresent(outbox::enqueue);  // same DB transaction
    }
}

The state change and the outgoing command commit together through a transactional outbox, so a crash can never leave the saga moved on with no command sent. Because each reply names the step it answers, a redelivered reply finds the saga already past that step and is ignored. Participants must be idempotent too: they key their work by sagaId, so a repeated ReserveStock returns the original reply without reserving twice. A scheduler picks up rows whose step_deadline has passed and re-sends the same command a bounded number of times. Only then does it treat the step as failed. A timed-out charge may well have succeeded, which is why RefundPayment must treat "no such charge" as success.

Frameworks: Spring Statemachine and off-the-shelf orchestrators

Spring Statemachine (4.x supports Boot 3) gives you states, events, guards, actions and a persistence hook. It is heavyweight for a seven-state saga, and many teams prefer the transition table above. Off-the-shelf options: Eventuate Tram Sagas (a step DSL: invokeParticipant, withCompensation, over an outbox), Axon Framework (event-sourced sagas with @SagaEventHandler), and the durable-execution engines Temporal (workflow code written as plain Java while the platform persists history, timers and retries) and Camunda (BPMN models, run on Zeebe in Camunda 8). They save you the table and the timeout scheduler, but you have to run and learn another platform.

Compensations are not rollbacks

A database rollback makes it as if nothing happened. A compensation is a new business action: a refund shows up on the customer's statement as a second line, a "your order is confirmed" email cannot be unsent (only followed by an apology), and a parcel handed to the courier cannot be un-shipped. Order the steps so that the ones most likely to fail come early and cheap-to-undo steps come before visible ones, and put irreversible steps last, when nothing after them can fail for business reasons. That is why stock reservation (an invisible counter) comes before the charge, and shipping comes last.

Semantic locksWith no isolation, a second saga or a "cancel order" request can interleave with the first. A semantic lock is an application-level flag: the order is created in PENDING, other operations on a PENDING order are rejected or queued, and only the saga's final step sets CONFIRMED or CANCELLED. Inventory keeps reserved separate from available for the same reason: other readers see a pessimistic but consistent number.

Observability: the saga dashboard

Export a gauge per step (count of non-terminal sagas), a counter of compensations started, and the age of the oldest non-terminal saga. Alert on age, not on volume, because a stuck saga is one that has stopped moving. The table answers the on-call question directly:

SELECT step, count(*) AS n, max(now() - updated_at) AS oldest, max(attempts) AS max_attempts
FROM saga_instance
WHERE step NOT IN ('COMPLETED', 'CANCELLED')
GROUP BY step;

Put the sagaId in MDC and on spans (L411) so one id leads from the dashboard row to every log line and hop.

What breaks in production
  • Updating the saga row and publishing the command in two separate steps: a crash between them leaves a saga that waits for ever.
  • Treating a timeout as failure without retrying or querying first: you refund a charge that never happened, or release stock the customer has paid for.
  • A compensation that can fail permanently, such as a refund rejected because the card has expired, with no manual-intervention path.
  • Non-idempotent participants: a redelivered ChargePayment charges twice.
  • No semantic lock: a cancellation that races the saga leaves a refunded order being shipped.

Saga Pattern II: Choreography & Compensation

45m video55m practice

In choreography there is no coordinator: each service reacts to other services' events and publishes its own, so the saga emerges from the subscriptions. It is loosely coupled and easy to extend, but the flow is written down nowhere. Either way, the saga is only as good as its compensations, which must be idempotent, retried until they succeed, and backed by a human when they cannot.

The same order flow, choreographed

The order service saves a PENDING order and publishes OrderCreated. Inventory reserves and publishes StockReserved or StockRejected. Payment, subscribed to StockReserved, charges and publishes PaymentCharged or PaymentDeclined. Shipping, subscribed to PaymentCharged, allocates. The order service listens for the terminal events and confirms or cancels. Compensation is choreographed too: inventory also subscribes to PaymentDeclined and releases the stock.

public sealed interface PaymentEvent permits PaymentCharged, PaymentDeclined, PaymentRefunded {
    UUID eventId();
    UUID orderId();
}

@Component
class InventoryPaymentListener {
    private final ProcessedEvents processed;
    private final Reservations reservations;
    private final Outbox outbox;

    InventoryPaymentListener(ProcessedEvents processed, Reservations reservations, Outbox outbox) {
        this.processed = processed; this.reservations = reservations; this.outbox = outbox;
    }

    @KafkaListener(topics = "payments.events", groupId = "inventory")
    @Transactional
    public void on(PaymentEvent event) {
        if (!processed.firstTime("inventory", event.eventId())) return;    // duplicate delivery
        switch (event) {
            case PaymentDeclined d -> release(d.orderId());
            case PaymentRefunded r -> release(r.orderId());
            case PaymentCharged c  -> { }                                  // not our concern
        }
    }

    private void release(UUID orderId) {
        // UPDATE reservation SET status = 'RELEASED' WHERE order_id = ? AND status = 'RESERVED'
        if (reservations.releaseIfReserved(orderId)) outbox.enqueue(new StockReleased(UUID.randomUUID(), orderId));
    }
}

The sealed interface makes the switch exhaustive, so when payment adds a new event type, this consumer stops compiling instead of silently ignoring it. Key every event by orderId so that all of one order's events on a topic land in one partition, in order.

Decision guideChoreography fits two to four simple, linear steps and fan-out reactions where nobody waits on the result (OrderPlaced → email, loyalty points, analytics). Use orchestration for anything longer, conditional ("if the order is above $1,000, run a fraud review"), time-bound, or business-critical enough that support must be able to answer what state it is in. Mixing them is normal: an orchestrated core saga that publishes domain events for choreographed side effects.

Designing compensations, and the pivot

A compensation must be idempotent (the release above is a conditional update, so running it twice changes nothing), retryable for ever with backoff, and must never fail permanently because of business logic: "already refunded" and "never charged" are both successes. When a machine really cannot finish one, for example because the card account has closed and the refund bounces, the saga moves to a manual-intervention queue: a table, a screen, an alert and an owner. It never just stops.

DefinitionSteps before the pivot transaction are compensatable: they can be undone. The pivot is the go/no-go step: once it commits, the saga will complete. Steps after it are retriable: designed so that they always succeed eventually, given retries. If shipping allocation can always be queued and retried, the charge is the pivot and nothing after it ever needs compensating. If allocation can fail for good, the charge has to be compensatable and allocation becomes the pivot.

Partial failure, duplicates, and out-of-order delivery

  • Partial failure: a service commits its local change and crashes before publishing. The transactional outbox makes "change and event" atomic.
  • Duplicates: Kafka delivers at least once. Record (consumer, event_id) in a processed_event table with a primary key, inserted in the same transaction as the effect. A conflict means the event was a duplicate, so skip it (L416).
  • Out of order: ordering holds only within one partition of one topic. The order service can see PaymentRefunded before ShipmentFailed. Make consumers state machines that accept only valid transitions. Park early events (or rely on redelivery) instead of applying them blindly, and record a tombstone for "cancelled before reserved" so that a late reservation is refused.

Idempotency, Retries & Distributed Correctness

45m video50m practice

Networks lose replies, not just requests, so every remote operation will sometimes be delivered twice. Correctness comes from operations that are safe to repeat (idempotency keys, conditional updates, dedup tables), retries that are bounded, jittered and owned by one layer, a timeout on every call, and never ordering events by wall-clock time.

At-least-once is the norm

The client sends POST /payments; the server commits; the response is lost or the client times out. From the client's side "failed" and "succeeded but I didn't hear" look identical, so it retries. A Kafka consumer that crashes after its database commit but before committing the offset gets the same record again. Exactly-once delivery over an unreliable network is impossible. What you can build is at-least-once delivery plus idempotent processing.

DefinitionAn operation is idempotent if performing it n ≥ 1 times leaves the system in the same state as performing it once. For an API that also means the repeated request gets an equivalent response. HTTP defines GET, HEAD, OPTIONS, PUT and DELETE as idempotent methods. POST and PATCH are not, unless you make them so.

The Idempotency-Key header

Algorithm · Idempotency key
  1. The client generates one random key (a UUID) per logical operation and sends it on the first attempt and on every retry.
  2. The server inserts (client, key, request hash) into a table with a unique constraint, or into Redis with SET NX and a TTL.
  3. If the key was new, perform the operation and store the response or a pointer to the result.
  4. If the key already exists and is complete, return the stored response. If the request hash differs, return 422 because the key was reused for a different request. If it is still in flight, return 409 with Retry-After, or wait.
  5. Expire keys after a TTL longer than any client's retry window (24 h is common).

When the effect lives in the same database, do the claim, the effect and the result in one transaction. A concurrent twin's insert then blocks on the unique index until the first transaction commits, sees the conflict, and replays:

@Service
public class IdempotentOrders {
    private final JdbcClient jdbc;
    private final OrderService orders;

    public IdempotentOrders(JdbcClient jdbc, OrderService orders) { this.jdbc = jdbc; this.orders = orders; }

    record Prior(String hash, UUID orderId) {}

    @Transactional
    public OrderResult place(String client, String key, String requestHash, PlaceOrder cmd) {
        int claimed = jdbc.sql("""
                INSERT INTO idempotency_key (client_id, idem_key, request_hash)
                VALUES (:client, :key, :hash)
                ON CONFLICT DO NOTHING""")
            .param("client", client).param("key", key).param("hash", requestHash)
            .update();
        if (claimed == 0) {
            Prior p = jdbc.sql("SELECT request_hash, order_id FROM idempotency_key WHERE client_id = :client AND idem_key = :key")
                .param("client", client).param("key", key)
                .query((rs, n) -> new Prior(rs.getString("request_hash"), rs.getObject("order_id", UUID.class)))
                .single();
            if (!p.hash().equals(requestHash)) throw new IdempotencyKeyReusedException(key);   // 422
            return OrderResult.replayed(orders.find(p.orderId()));                              // same body
        }
        Order order = orders.place(cmd);                                  // same transaction as the claim
        jdbc.sql("UPDATE idempotency_key SET order_id = :id WHERE client_id = :client AND idem_key = :key")
            .param("id", order.id()).param("client", client).param("key", key).update();
        return OrderResult.created(order);
    }
}

When the effect is an external call (the payment provider), you cannot hold a transaction open across it. Claim the key as IN_PROGRESS in a short transaction, answer twins with 409, pass the same key on to the provider, and record the outcome afterwards. Resolve a stale IN_PROGRESS row by asking the provider, not by assuming the call failed.

Natural idempotency and dedup on the consumer side

  • PUT with the full state: "set the address to X" can be repeated safely; "add 10 to the balance" cannot. Record a ledger entry with a unique id instead of incrementing a balance.
  • Conditional updates: UPDATE payment SET status = 'CAPTURED' WHERE id = ? AND status = 'AUTHORIZED'. Zero rows means it has already been done.
  • Upserts: INSERT … ON CONFLICT (order_id) DO NOTHING.
  • Unique business constraints as the backstop: UNIQUE (order_id, kind) on payments makes a double charge a constraint violation rather than a refund ticket.
@KafkaListener(topics = "payments.events", groupId = "ledger")
@Transactional
public void on(PaymentCharged e) {
    int fresh = jdbc.sql("INSERT INTO processed_event (consumer, event_id) VALUES ('ledger', :id) ON CONFLICT DO NOTHING")
        .param("id", e.eventId()).update();
    if (fresh == 0) return;                          // already applied, and the effect is committed
    ledger.credit(e.merchantId(), e.amount(), e.eventId());   // same transaction as the marker
}

The marker row and the effect commit or roll back together. That transaction boundary is what makes the dedup correct. The offset is committed after it, so a crash between the two causes a redelivery, which the marker then absorbs. Keep markers at least as long as you might replay the topic. If the effect is outside your database (an email, a webhook), the dedup cannot be atomic, so pass an idempotency key on or accept the occasional duplicate.

Retry safety: what, how often, and at which layer

Retry when the request provably never ran (connection refused), or when it is idempotent and the error is transient: 408, 429 (honour Retry-After), 502, 503, 504 and timeouts. Never retry 400, 401, 403, 404, 409 or 422: the next attempt will fail the same way. A read timeout on a POST is ambiguous, and is safe to retry only with an idempotency key.

RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)                                               // 1 call + 2 retries
        .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(Duration.ofMillis(200), 2.0, 0.5))
        .retryOnException(ex -> ex instanceof ResourceAccessException // I/O error or timeout
                || ex instanceof HttpServerErrorException.ServiceUnavailable
                || ex instanceof HttpClientErrorException.TooManyRequests)
        .build();
Retry retry = Retry.of("payment", config);
Receipt receipt = retry.executeSupplier(() -> payments.charge(idempotencyKey, cmd));  // same key every attempt

Exponential backoff spreads retries out, and jitter (randomizing each delay) stops a thousand clients that failed together from retrying together. A retry budget caps retries at a fraction of normal traffic (say 10%), so during a real outage retries stop instead of multiplying load.

Timeouts on every call

Many HTTP clients wait indefinitely by default. One hung dependency then pins every request thread, and the outage spreads to your callers. Give each call a connect timeout (about 1 s), a read timeout (the dependency's p99.9 plus a margin), and a total deadline across all attempts that fits inside your own caller's timeout:

var factory = new JdkClientHttpRequestFactory(
        HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(1)).build());
factory.setReadTimeout(Duration.ofSeconds(2));                // per attempt
RestClient payments = builder.requestFactory(factory).baseUrl("http://payment-service").build();

Clocks are not an ordering mechanism

System.currentTimeMillis() is wall-clock time. Machines drift apart, and NTP corrects them by slewing or by stepping, sometimes backwards. Skew between hosts is commonly milliseconds and can be far worse. Last-write-wins by timestamp silently discards writes, and two events on different machines cannot be ordered by their timestamps. Within one JVM, measure durations with the monotonic System.nanoTime(). Across machines, order with logical clocks or with ids handed out by a single authority: a database sequence, a version column, or a Kafka partition offset.

public final class LamportClock {                        // Lamport 1978
    private final AtomicLong time = new AtomicLong();
    public long tick() { return time.incrementAndGet(); }   // local event or before send
    public long onReceive(long remote) {                    // max(local, remote) + 1
        return time.accumulateAndGet(remote, (local, r) -> Math.max(local, r) + 1);
    }
}

If a happened before b, then L(a) < L(b), but the converse does not hold. Vector clocks are needed to detect concurrency. Time-ordered ids such as UUIDv7 or Snowflake are only roughly sortable and say nothing about causality.

Exactly-once, deconstructedKafka's exactly-once semantics combine an idempotent producer (producer id plus per-partition sequence numbers, so broker-side retries are deduplicated) with transactions (output records and consumer offsets commit atomically). That is exactly-once inside Kafka, for read-process-write pipelines. The moment processing touches a database, an HTTP API or an email server, you are back to at-least-once delivery with idempotent effects: "effectively once", which is the only kind there is.
What breaks in production
  • The client generates a new idempotency key on each retry, so every attempt is "new" and the customer is charged twice.
  • The key TTL is shorter than the mobile app's offline retry queue.
  • The dedup marker is written in a different transaction from the effect: a crash between them loses the event or applies it twice.
  • Retries with no jitter or budget: a synchronized retry storm finishes off a dependency that was recovering.
  • No read timeout: the thread pool fills with requests stuck on one dead socket.

Service Mesh vs Library-Based Resilience

40m video40m practice

A service mesh moves network policy (mTLS, load balancing, retries, timeouts, traffic splitting, golden metrics) out of each application and into a proxy next to it, configured by a control plane. That buys language-agnostic consistency at the cost of more infrastructure. Each concern needs exactly one owner, the mesh or the library, or the two layers multiply each other's retries.

The idea: policy in a proxy, not in your code

Phase 21 so far put resilience in libraries: Resilience4j for retries and circuit breakers, Spring Cloud LoadBalancer for client-side balancing, Micrometer for telemetry. These are the successors to Netflix's Hystrix, Ribbon and Zuul 1, which were retired from Spring Cloud in the 2020.0 release train (Hystrix had been in maintenance since 2018). Every service, in every language, has to embed and configure that stack. A mesh instead injects a proxy into each pod and redirects the pod's traffic through it (iptables rules set up by an init container or a CNI plugin). The application calls http://payment:8080 in plain HTTP, and the proxies handle the rest.

DefinitionThe data plane is the set of proxies that carry traffic: Envoy in Istio, and the Rust linkerd2-proxy in Linkerd. The control plane (istiod, or Linkerd's destination, identity and injector components) watches Kubernetes, turns your policy resources into proxy configuration, pushes it out (Envoy's xDS APIs), and acts as the certificate authority for workload identities.

What a mesh gives you

  • Language-agnostic policy: the Go, Python and Java services get identical timeouts and retries from one resource.
  • Zero-code mTLS: every workload gets a SPIFFE-style identity tied to its service account, with certificates rotated automatically; traffic between services is encrypted and authenticated.
  • Traffic splitting by weight or header, for canaries and blue/green releases.
  • Fault injection: add a 3 s delay to 10% of calls, or abort 5% with a 503, to test your resilience without changing code.
  • Uniform golden metrics: request rate, success rate and latency for every service pair, emitted by the proxies.

What it cannot do: trace propagation still needs your application to copy the trace headers from inbound to outbound requests (L411), and it cannot return a business fallback. A proxy can only retry, fail or eject.

Istio's Gateway resource configures the edge proxies for ingress and egress, with VirtualServices bound to it. Fault injection is a fault: block (delay or abort with a percentage) on a VirtualService route.

Linkerd, ambient mode, and what it costs

Linkerd is the smaller option: a purpose-built Rust micro-proxy, mTLS on by default, very little configuration, and a narrower feature set (no arbitrary L7 filter chains). Check its current release model before adopting it, because how stable builds are distributed changed in 2024. The current direction for both projects is to cut per-pod cost. Istio ambient mode (GA in 2024) replaces sidecars with a per-node ztunnel that handles L4 mTLS, authorization and telemetry, plus optional per-namespace waypoint Envoy proxies only where L7 policy is needed. Cilium offers an eBPF-based, sidecar-less mesh.

The costsSidecars add memory and CPU to every pod (tens of MB each, more with large configurations) and two proxy hops to every call (typically about a millisecond or less at the median, more at the tail). You also take on another control plane to upgrade, with every sidecar restarted to follow it, plus CRDs and a certificate authority to operate, and an extra hop to debug: is that 503 from the app or from Envoy? Check the proxy's response flags. Startup ordering matters too: an app that calls out before its sidecar is ready fails. Batch Jobs whose sidecar never exits are fixed by native sidecar containers in recent Kubernetes versions.

The overlap problem: one owner per concern

Resilience4j retries 3 times, the mesh retries 2 more per attempt (Istio retries some failures by default even if you configure nothing), and a single slow call becomes up to 9 requests (L416). Timeouts conflict the same way: if the mesh's per-try timeout is 800 ms and your client's is 2 s, the client never sees its own timeout. Decide explicitly:

What breaks in production
  • Retry multiplication between Resilience4j and mesh defaults, discovered during the first real outage.
  • Mesh timeouts tighter than the app's, so the client's fallback never runs and callers see bare 504s.

Testing Microservices: Contracts, Components & Chaos

50m video60m practicemilestone project

You cannot test a distributed system by deploying all of it and clicking through it. Test each service thoroughly on its own (component tests), pin down every interface between services with consumer-driven contracts, keep only a handful of end-to-end journeys, and use chaos experiments to test the resilience you built in this phase. The pyramid, redrawn for services

Why end-to-end tests don't scale: with N services, each at several versions, the combinations grow exponentially, yet an E2E suite tests exactly one of them. The shared staging environment is always broken by somebody else's half-deployed change. Asynchronous flows make the tests flaky, a run takes hours, and when one fails it is unclear which team owns the failure. What breaks in production
  • Contracts written by the provider alone. They test what it returns, not what consumers depend on, and miss the field a consumer actually parses.
  • Stubs that drift: a consumer pinned to an old stub version passes while production has moved on. Use + or broker-driven versions.
  • Chaos experiments without abort criteria, run in production on a Friday.

Milestone project: the Phase 21 system

Five services, gateway, orders, inventory, payment and shipping, on discovery and a config server, with everything from L410–L417 wired in. Use current components only: Spring Cloud Gateway, Spring Cloud LoadBalancer, Resilience4j, Micrometer Tracing, and OpenFeign or RestClient. There should be no Zuul, Ribbon, Hystrix or Sleuth anywhere in the dependency tree.

  • One command (Docker Compose or kind) starts all five services plus Eureka, Config Server, Kafka, a Postgres per service, Prometheus, Grafana, Loki and Zipkin or Tempo.
  • The gateway routes /api/** through lb:// service ids, validates JWTs, and rate-limits per client.
  • Each service registers with discovery and calls the others by logical name; configuration comes from a Git-backed Config Server with per-environment profiles, and one property is refreshed at runtime.
  • Each service owns its database; no service reads another's tables.
  • Resilience: connect and read timeouts on every client, a circuit breaker with a business fallback and a bulkhead on payment calls, and retries owned by exactly one layer.
  • Order placement runs as an orchestrated saga (saga_instance table, outbox, Kafka commands and replies) with a compensation for every failing step, plus one choreographed side effect such as the confirmation email.
  • Idempotency-Key on POST /orders, and processed-event dedup in every consumer.
  • End-to-end tracing: a single checkout is a single trace across the gateway, HTTP and Kafka hops, and every JSON log line carries its trace id.
  • A RED dashboard per service, a stuck-saga age panel, and one SLO with a burn-rate alert.
  • Liveness and readiness groups plus graceful shutdown, proven by a rolling restart under load with zero failed requests.
  • Tests: saga state-machine unit tests, component tests, contracts for orders → payment and orders → inventory, a failure-injection test for each saga step, and one Chaos Monkey experiment written up as hypothesis and result.
  • A README with the architecture diagram, the concern-ownership table from L417, and the stuck-saga runbook.

  2. Write a component test for the order service with Postgres in Testcontainers and WireMock stubs for inventory and payment, covering the happy path, a timeout and a 500.
  3. Run one Chaos Monkey latency experiment against inventory with a written hypothesis, and record whether the circuit breaker and SLO held.
  4. Start the milestone: get the Compose stack up and tick off the first three deliverables.
