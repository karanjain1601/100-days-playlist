Modern Java, I/O, Date-Time & Reflection

Phase 4 points the core language at the outside world: files and character encodings, NIO buffers and channels, dates, time zones and locales, regular expressions, and the annotations, reflection and modules that every framework is built on. It turns Phases 1–3's classes, collections and streams into code that survives real input, and it explains the proxies and metadata that Spring will rely on from Phase 12 onwards. The milestone is a CSV/JSON ETL tool whose transforms are plugins loaded by reflection.

By the end of this phase you can

  • Model time correctly: Instant for events, local and zoned types for calendar logic across DST, an injected Clock in tests, timestamptz in the database.
  • Parse and format dates, numbers and money for any locale without SimpleDateFormat races, YYYY bugs or default-locale surprises.
  • Write regexes with named groups and lookaround, and find and fix catastrophic backtracking before it reaches production.
  • Build a custom annotation, an annotation processor, a dynamic proxy and a small reflection-based DI container, and say what Spring adds on top.

java.io Overview, File & Byte Streams

40m video40m practice

java.io is four abstract classes and a pile of decorators. Once you see that every stream is either a source/sink or a wrapper that adds one capability to another stream, the hundred-odd classes in the package collapse into a small, predictable design.

The class map: bytes vs characters, in vs out

Everything in java.io descends from one of four abstract roots. Byte streams move raw octets (images, ZIP files, network protocols). Character streams move UTF-16 chars and exist because text needs an encoding step between bytes and characters (L100).

The decorator design

Definition · decorator

A decorator implements the same type as the object it wraps, holds a reference to it, and forwards calls while adding behaviour. In java.io, FilterInputStream and FilterOutputStream are the decorator base classes: they store the wrapped stream in a protected field in / out and delegate every method to it. Subclasses override only what they change.

So a stack like new DataInputStream(new BufferedInputStream(new FileInputStream(f))) is three objects, each one an InputStream. A call to readInt() asks the buffer for four bytes; the buffer, when empty, asks the file stream for up to 8,192 bytes at once; only the innermost object talks to the operating system. Capabilities compose without a class explosion: you never need a BufferedGzipDataFileInputStream.

The File API, and why it is legacy

java.io.File is a path name, not an open file: creating one touches nothing on disk. Its query and mutation methods report failure as a bare boolean or null.

import java.io.File;
import java.io.IOException;

public class FileTour {
    public static void main(String[] args) throws IOException {
        File dir = new File("data/../data/in");
        System.out.println(dir.getPath());           // data/../data/in  (exactly as given)
        System.out.println(dir.getAbsolutePath());   // /home/me/app/data/../data/in  (cwd prepended)
        System.out.println(dir.getCanonicalPath());  // /home/me/app/data/in  (.. resolved, symlinks followed)

        if (!dir.exists() && !dir.mkdirs())          // false = failed, with no reason given
            throw new IOException("could not create " + dir);

        File f = new File(dir, "orders.csv");
        System.out.println(f.exists() + " " + f.length() + " " + f.isDirectory()); // length() is 0 if missing

        File[] children = dir.listFiles();           // null on I/O error or if dir is not a directory
        if (children == null) throw new IOException("cannot list " + dir);
        for (File c : children) System.out.println(c.getName() + " " + c.length());

        boolean moved = f.renameTo(new File(dir, "orders.done")); // platform-dependent, may fail across disks
        boolean gone  = new File(dir, "orders.done").delete();    // false if missing or a non-empty dir
        System.out.println(moved + " " + gone);
    }
}

Absolute vs canonical. getAbsolutePath() is pure string work: it prepends the working directory and leaves ., .. and symlinks alone. getCanonicalPath() asks the filesystem, so it can throw IOException; it resolves .., follows symlinks and, on Windows, fixes the case of each name. Use canonical paths when checking that a user-supplied path stays inside an upload directory.

Why File is legacy
  • Failures are a boolean: delete() returning false could mean "missing", "permission denied" or "directory not empty", and you cannot tell which.
  • listFiles() returns null instead of throwing, and loads the whole directory into an array.
  • No symlink awareness, no real metadata (owner, POSIX permissions, creation time), no atomic move, and renameTo behaviour varies by OS.
  • It only knows the default filesystem; NIO.2 Path also works over ZIP files and in-memory filesystems.

New code uses Path and Files (L103). For old APIs, bridge with file.toPath() and path.toFile().

FileInputStream, FileOutputStream and the -1 contract

new FileInputStream(name) opens the file immediately and throws FileNotFoundException if it can't. new FileOutputStream(name) creates or truncates; pass true as the second argument to append. Both hold an OS file descriptor until closed.

Definition · the read contract

int read() returns the next byte as an int from 0 to 255, or -1 at end of stream. It returns int because 256 byte values plus one sentinel need 257 distinct results. int read(byte[] b) blocks until at least one byte is available, then returns how many it stored, which can be fewer than b.length, or -1 at end of stream.

static long copy(InputStream in, OutputStream out) throws IOException {
    byte[] buf = new byte[8192];
    long total = 0;
    int n;
    while ((n = in.read(buf)) != -1) {   // n is 1..buf.length; never assume a full buffer
        out.write(buf, 0, n);            // write only the bytes actually read
        total += n;
    }
    return total;
}

Reading byte by byte with read() on a raw FileInputStream makes one native call per byte; reading into an 8 KiB array makes one per 8 KiB. That difference is often two orders of magnitude, and L101 measures it. Since Java 9 you rarely write the loop yourself: in.transferTo(out), in.readAllBytes() and in.readNBytes(buf, off, len) do it for you.

Closing: try-with-resources

try (var in = new FileInputStream("in.bin");
     var out = new FileOutputStream("out.bin")) {   // closed in reverse order: out, then in
    in.transferTo(out);
}                                                    // closed even if transferTo throws

Any AutoCloseable declared in the header is closed when the block exits, in reverse declaration order. If the body throws and close() also throws, the body's exception propagates and the close failure is attached with addSuppressed, where the old try/finally idiom silently replaced the original exception with the close failure. Declare each layer as its own resource when a constructor in the middle of a wrapper chain can throw (L106).

In-memory streams

ByteArrayOutputStream is a growable byte array that implements OutputStream; ByteArrayInputStream reads from an existing array. Their close() does nothing, they never throw real I/O errors, and they make stream-handling code testable without touching disk.

var sink = new ByteArrayOutputStream();
try (var out = new DataOutputStream(sink)) {
    out.writeInt(42);
    out.writeUTF("héllo");                 // 2-byte length + 6 bytes of modified UTF-8
}
byte[] bytes = sink.toByteArray();         // 4 + 2 + 6 = 12 bytes
var in = new DataInputStream(new ByteArrayInputStream(bytes));
System.out.println(in.readInt() + " " + in.readUTF() + " " + bytes.length);  // 42 héllo 12
What breaks in production
  • Ignoring the count. in.read(buf); out.write(buf); writes stale bytes whenever the read was short. Sockets and pipes return short reads all the time.
  • Casting before the check. byte b; while ((b = (byte) in.read()) != -1) stops at the first 0xFF byte, because (byte) 255 == -1. Compare the int, then cast.
  • available() as file size. It is an estimate of what can be read without blocking, not the length. Use Files.size.
  • Unchecked File booleans. An ignored delete() or mkdirs() failure surfaces much later as a confusing error elsewhere.
  • Leaked descriptors. A stream opened in a loop without try-with-resources leaks one descriptor per iteration until the process hits its limit and every open fails with "Too many open files".

Character Streams, Encodings & Charset Pitfalls

40m video40m practice

Files hold bytes; Java strings hold UTF-16 code units. Every conversion between the two uses a charset, and every bug in this lesson comes from a conversion where nobody chose one explicitly.

The Reader/Writer hierarchy

Reader and Writer mirror InputStream/OutputStream one level up: the unit is a 16-bit char, not a byte. Sources and sinks include StringReader/StringWriter and CharArrayReader/CharArrayWriter; decorators include BufferedReader (adds readLine()), LineNumberReader, PushbackReader and PrintWriter. The two classes that matter most are the bridges.

Definition · bridges

InputStreamReader wraps an InputStream and decodes its bytes into chars with a CharsetDecoder. OutputStreamWriter wraps an OutputStream and encodes chars into bytes with a CharsetEncoder. They are the only places in java.io where bytes become text, so they are where the charset must be named. FileReader and FileWriter are just these bridges pre-wired to a FileInputStream/FileOutputStream.

Path p = Path.of("orders.csv");
try (var r = new BufferedReader(new InputStreamReader(new FileInputStream(p.toFile()), UTF_8));
     var w = new FileWriter("copy.csv", UTF_8)) {      // charset constructor added in Java 11
    r.transferTo(w);
}
try (BufferedReader r = Files.newBufferedReader(p)) {   // NIO: UTF-8 unless told otherwise
    r.lines().limit(3).forEach(System.out::println);
}

The platform-default trap and Java 18

new FileReader(name), new FileWriter(name), new InputStreamReader(in), String.getBytes() and new String(bytes) all use the default charset when you don't pass one. Until Java 17 that default came from the OS locale: usually UTF-8 on Linux and macOS, but windows-1252 on a Western-locale Windows machine. The same JAR wrote different bytes depending on where it ran. The common workaround was -Dfile.encoding=UTF-8, which was never officially supported.

JEP 400 · UTF-8 by default
  • Since JDK 18, Charset.defaultCharset() is UTF-8 on every platform.
  • -Dfile.encoding=COMPAT restores the old locale-derived default, for applications that relied on it.
  • System.getProperty("native.encoding") (JDK 17+) still reports what the OS would have chosen, e.g. Cp1252.
  • Console output is separate: System.out encodes with stdout.encoding (JDK 19+), which follows the terminal, so a Windows console can still garble output that is correct in a file.
  • Files.* methods that take no charset have always used UTF-8, independent of all of this.

The rule survives the change: always pass StandardCharsets.UTF_8 (or whatever the data contract says). It documents intent, and it protects code that runs on Java 17 or with COMPAT set. Prefer getBytes(Charset) over getBytes(String): the Charset overload cannot throw UnsupportedEncodingException.

Mojibake: reproduce it, then repair it

Mojibake is text that was encoded with one charset and decoded with another. UTF-8 "é" is the two bytes C3 A9; decode them as ISO-8859-1 and you get the two characters "Ã©".

byte[] utf8 = "café".getBytes(UTF_8);                              // 63 61 66 C3 A9
String wrong = new String(utf8, ISO_8859_1);                        // "cafÃ©": 5 chars
String fixed = new String(wrong.getBytes(ISO_8859_1), UTF_8);       // "café"
System.out.println(wrong + " -> " + fixed);

The repair works only because ISO-8859-1 maps all 256 byte values one-to-one, so the wrong decode lost nothing. With windows-1252 five byte values (0x81, 0x8D, 0x8F, 0x90, 0x9D) are undefined and decode to U+FFFD, the replacement character. UTF-8 "Á" is C3 81, so it comes back as "Ã" plus U+FFFD, and the original byte is gone. Once you see U+FFFD, the only fix is to go back to the source bytes.

Decoding with new String(bytes, cs) never throws: malformed input becomes U+FFFD. When corrupt input must be rejected, use a decoder configured to report errors:

static String decodeStrict(byte[] bytes) throws CharacterCodingException {
    CharsetDecoder strict = UTF_8.newDecoder()
            .onMalformedInput(CodingErrorAction.REPORT)
            .onUnmappableCharacter(CodingErrorAction.REPORT);
    return strict.decode(ByteBuffer.wrap(bytes)).toString();   // throws MalformedInputException
}

Files.readString and Files.newBufferedReader already report malformed input by throwing MalformedInputException, which is usually what you want for files you are about to parse.

Byte order marks

A BOM is U+FEFF written at the start of a file. In UTF-16 it tells the reader the byte order, and Java's UTF-16 decoder detects and consumes it. In UTF-8 it is optional and carries no information, but Excel and some Windows tools write it (EF BB BF). Java's UTF-8 decoder does not strip it: the first char of the first line is '﻿', so a CSV header reads as "﻿id" and header.equals("id") is false.

static BufferedReader openSkippingBom(Path p) throws IOException {
    BufferedReader r = Files.newBufferedReader(p, UTF_8);
    r.mark(1);
    if (r.read() != '﻿') r.reset();      // not a BOM: push the char back
    return r;
}
What breaks in production
  • Works on the laptop, garbled on the server. A no-charset FileWriter on Java 17 writes windows-1252 on Windows and UTF-8 on Linux. Moving that service to Java 21 changes the bytes again.
  • Upgrade breaks old files. Files written in Cp1252 by a pre-18 JVM decode as U+FFFD on 18+. Read them with Charset.forName("windows-1252") explicitly, or migrate them once.
  • Silent corruption. new String(bytes, UTF_8) on non-UTF-8 data "succeeds". Validate at the boundary with a strict decoder.
  • Splitting bytes. Truncating a UTF-8 byte[] at a fixed length, for example to fit a column limit, can cut a character in half.
  • Counting the wrong thing. String.length() counts UTF-16 code units: an emoji is 2. Use codePointCount for user-visible length limits.

Buffered Streams, PrintWriter & I/O Performance

35m video40m practice

I/O cost is dominated by how many times you cross into the kernel, not by how many bytes you move. A buffer turns millions of tiny crossings into thousands of large ones, and it also means your data sits in memory, not on disk, until something flushes it.

Why unbuffered I/O is slow

FileInputStream.read() is a native method that issues one read system call for one byte. Each call switches from user mode to kernel mode, validates arguments, copies from the page cache and switches back. That fixed overhead is hundreds of nanoseconds to microseconds, so per-byte reads of a 100 MiB file mean about 105 million round trips. A buffer pays the overhead once per 8 KiB.

Definition · buffered decorator

BufferedInputStream holds a byte[] (8,192 bytes by default) plus a position and a count. read() returns the next array element; only when the array is exhausted does it call the wrapped stream to refill it in one bulk read. A bulk request for at least a buffer's worth of bytes (with no mark set) bypasses the array and goes straight to the wrapped stream. BufferedOutputStream accumulates writes and calls the wrapped stream when the array fills or on flush(). BufferedReader and BufferedWriter do the same with a char[8192].

Benchmark: 100 MiB with and without a buffer

import java.io.*;
import java.nio.file.*;

public class ReadBench {
    interface Job { long run(Path p) throws IOException; }

    static long rawByte(Path p) throws IOException {          // one syscall per byte
        long sum = 0;
        try (var in = new FileInputStream(p.toFile())) {
            for (int b; (b = in.read()) != -1; ) sum += b;
        }
        return sum;
    }
    static long bufferedByte(Path p) throws IOException {     // one syscall per 8 KiB
        long sum = 0;
        try (var in = new BufferedInputStream(new FileInputStream(p.toFile()))) {
            for (int b; (b = in.read()) != -1; ) sum += b;
        }
        return sum;
    }
    static long bulk(Path p) throws IOException {             // one syscall per 64 KiB, no per-byte call
        long sum = 0;
        byte[] buf = new byte[64 * 1024];
        try (var in = new FileInputStream(p.toFile())) {
            for (int n; (n = in.read(buf)) != -1; )
                for (int i = 0; i < n; i++) sum += buf[i] & 0xFF;
        }
        return sum;
    }
    public static void main(String[] args) throws IOException {
        Path p = Path.of(args[0]);                            // a 100 MiB file of random bytes
        Job[] jobs = {ReadBench::bulk, ReadBench::bufferedByte, ReadBench::rawByte};
        for (Job job : jobs) {
            long t0 = System.nanoTime();
            long sum = job.run(p);
            System.out.printf("%6d ms  sum=%d%n", (System.nanoTime() - t0) / 1_000_000, sum);
        }
    }
}

One run on a Windows 11 laptop with JDK 21, file already in the OS cache: bulk about 90 ms, buffered read() about 1.9 s, raw read() about 18 minutes (roughly 10 µs per call). Your numbers will differ (Linux syscalls are cheaper; antivirus hooks make Windows ones dearer), but the ordering and the orders of magnitude are typical. Two lessons: buffering removes almost all of the syscall cost, and the remaining 20x gap is the per-byte method call (BufferedInputStream.read() takes a lock on every call). Process arrays, not bytes. Phase 6 redoes this properly with JMH.

Buffer sizing. 8 KiB is a good default. 32–64 KiB sometimes helps large sequential reads; beyond that returns flatten because the OS already reads ahead. Measure before changing it, and never allocate a buffer per call in a hot loop.

readLine() semantics

var r = new BufferedReader(new StringReader("a\r\nb\n\nc"));
for (String line; (line = r.readLine()) != null; )
    System.out.print("[" + line + "]");                       // [a][b][][c]
  • A line ends at \n, \r or \r\n; the terminator is stripped.
  • An empty line returns ""; end of stream returns null. A final line without a terminator is still returned, so you cannot tell whether the file ended with a newline.
  • lines() returns a lazy Stream<String> over the same logic.
  • A line has no length limit: a 2 GB file with no newline is one 2 GB string. Bound line length on untrusted input.

record Row(String name, int qty) {}

static void writeReport(Path out, List<Row> rows) throws IOException {
    try (var pw = new PrintWriter(Files.newBufferedWriter(out, UTF_8))) {
        for (Row row : rows) pw.printf("%s,%d\n", row.name(), row.qty());  // \n, not %n: fixed format
        if (pw.checkError()) throw new IOException("report write failed: " + out);
    }
}

Binary primitives and endianness

DataOutputStream writes Java primitives as fixed-width bytes, always big-endian (network byte order): writeInt emits the high byte first. DataInputStream reads them back, and readFully loops until the array is full, throwing EOFException if the stream ends mid-record. writeUTF writes a 2-byte length followed by modified UTF-8, so strings are limited to 65,535 encoded bytes. For little-endian formats (many file formats, x86 memory dumps), use ByteBuffer with ByteOrder.LITTLE_ENDIAN (L104) or Integer.reverseBytes.

var sink = new ByteArrayOutputStream();
try (var out = new DataOutputStream(sink)) {
    out.writeInt(0x0A0B0C0D);
    out.writeShort(1);
    out.writeDouble(1.5);
}
byte[] b = sink.toByteArray();     // 0A 0B 0C 0D | 00 01 | 3F F8 00 00 00 00 00 00   (14 bytes)
int little = ByteBuffer.wrap(b).order(ByteOrder.LITTLE_ENDIAN).getInt();
System.out.printf("%08X%n", little);                          // 0D0C0B0A: same bytes, other order

flush() and when data hits the disk

Flushing a decorator flushes the whole chain beneath it, and close() flushes first. Forget to close a BufferedWriter and up to 8 KiB at the end of the file never leaves the JVM. Fsync is slow (milliseconds on many devices), so call it at commit points, not per line.

What breaks in production
  • Truncated output. A writer that is never closed, or a process that exits via System.exit before the finally runs, loses its buffered tail.
  • Silent data loss. PrintWriter on a full disk keeps "succeeding". Check checkError(), or use a BufferedWriter, which throws.
  • Two buffers on one stream. Creating a new BufferedReader or Scanner over System.in per method call: the first one reads ahead 8 KiB, and the next one never sees those bytes.
  • Platform line separators in protocols. newLine(), println and %n write \r\n on Windows. Write the separator the format requires explicitly.
  • Autoflush assumptions. An autoflush PrintWriter does not flush on print(), so an interactive prompt without a newline never appears.

Practice · 40 min

  1. Run ReadBench on a 100 MiB file (generate it with Random.nextBytes; shrink the raw case to 10 MiB if it is too slow). Add bulk buffers of 512 B, 8 KiB, 64 KiB and 1 MiB and tabulate the times.
  2. Reproduce the double-buffer bug: pipe a three-line file into a program that creates a fresh BufferedReader(new InputStreamReader(System.in)) for each line it reads.
  3. Design a binary file: 4-byte magic, 2-byte version, 4-byte record count, then (long id, double amount) records. Write it with DataOutputStream, read it back with readFully, and decode the header once more with a little-endian ByteBuffer to see the byte order.
  4. Write 100,000 lines with a BufferedWriter and kill the process with kill -9 (or Task Manager) mid-way, without flushing. Compare the file size with what you wrote, then flush every 1,000 lines and repeat.

Serialization, transient, serialVersionUID & Its Risks

45m video40m practice

Java serialization writes an object graph, class names included, and reading it back creates objects without running their constructors. That makes it convenient for trusted round-trips and dangerous for anything else: whoever controls the bytes chooses which classes get instantiated.

The mechanism and the wire format

Serializable is a marker interface with no methods; it only grants permission. ObjectOutputStream.writeObject walks the graph reflectively, writing each class's descriptor once and then field values; shared references and cycles are preserved with back-reference handles. ObjectInputStream.readObject reverses it. For a Serializable class the constructor is not called: the runtime allocates the object, runs the no-arg constructor of the first non-serializable superclass (often Object), then assigns fields straight from the stream, final fields included.

transient, serialVersionUID and versioning

import java.io.*;

public class SerialDemo {
    static class Account implements Serializable {
        @Serial private static final long serialVersionUID = 1L;

    }

        var bytes = new ByteArrayOutputStream();

            out.writeObject(new Account("acc-1", 1250, "secret"));
        }

    }
}

transient fields are skipped and come back as 0/false/null; because no constructor or field initializer runs, audit is null, not an empty list. Re-create such fields in readObject.

Definition · serialVersionUID

A long written into the class descriptor. On read, the stream's value must equal the local class's value or readObject throws InvalidClassException: local class incompatible. If you don't declare one, the JVM computes a hash of the class's name, interfaces, fields and methods, so merely adding a method changes it. Declare private static final long serialVersionUID = 1L; and mark it @Serial (Java 14+) so -Xlint:serial checks the signature. With a fixed UID, adding a field is compatible (old streams leave it at its default) and removing one is compatible (the stream value is ignored); changing a field's type is not.

Hooks: writeObject, readObject, readResolve, writeReplace, Externalizable

Private writeObject(ObjectOutputStream) and readObject(ObjectInputStream) methods are found reflectively by exact signature. Call defaultWriteObject()/defaultReadObject() first, then add or validate. Because the constructor never runs, readObject is a second public constructor: re-check invariants and defensively copy mutable fields (Effective Java, Item 88).

final class Range implements Serializable {
    @Serial private static final long serialVersionUID = 1L;
    private final int lo, hi;

    Range(int lo, int hi) {
        if (lo > hi) throw new IllegalArgumentException(lo + " > " + hi);
        this.lo = lo; this.hi = hi;
    }
    @Serial private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
        in.defaultReadObject();                                   // assigns lo and hi, even though final
        if (lo > hi) throw new InvalidObjectException("lo > hi"); // a forged stream can say anything
    }
}

final class Registry implements Serializable {
    static final Registry INSTANCE = new Registry();
    private Registry() {}
    @Serial private Object readResolve() { return INSTANCE; }    // discard the copy, keep the singleton
}
  • writeReplace() substitutes another object before writing; with readResolve() on the substitute it gives the serialization proxy pattern (Item 90).
  • Externalizable replaces the reflective mechanism with writeExternal/readExternal: you write every byte yourself, and the class needs a public no-arg constructor, which deserialization calls.
  • Records are serialized by component and deserialized through the canonical constructor, so compact-constructor validation runs (a forged Range(9, 2) fails with InvalidObjectException). Their writeObject/readObject methods are ignored. Enums are written by name and always resolve to the existing constant.

Inheritance hierarchies

Subclasses of a Serializable class are serializable. If a Serializable class extends a non-serializable one, the parent's fields are not written; on read the parent's no-arg constructor runs and initialises them. It must exist and be accessible, or reading fails with InvalidClassException: no valid constructor. A non-transient field holding a non-serializable object fails at write time with NotSerializableException.

Why it is a security disaster

Gadgets are not bugs in your code. In 2015 a chain through Apache Commons Collections (published in Frohoff and Lawrence's ysoserial tool) gave remote code execution against WebLogic, WebSphere, JBoss and Jenkins, simply because the library was on the classpath and the server deserialized network input. Even without gadgets, nested HashSets can take exponential time to read, and a forged array length can exhaust the heap.

Serialization filters

ObjectInputFilter (Java 9, JEP 290; context-specific filter factories in Java 17, JEP 415) is consulted for every class, array length, depth and reference count before the object is created. Allow-list, never block-list:

static Object readTrusted(InputStream input) throws IOException, ClassNotFoundException {
    ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
            "maxdepth=10;maxrefs=1000;maxbytes=65536;maxarray=10000;com.example.dto.*;java.base/*;!*");
    try (var in = new ObjectInputStream(input)) {
        in.setObjectInputFilter(filter);    // first matching pattern wins; !* rejects the rest
        return in.readObject();             // InvalidClassException: filter status: REJECTED
    }
}

A JVM-wide default can be set with -Djdk.serialFilter=.... Even with a filter, Effective Java Item 85 is blunt: there is no reason to use Java serialization in a new system.

Path is a value: its methods manipulate names and never touch the disk. Files is where I/O happens, and unlike java.io.File it reports every failure as a specific exception and gives you lazy, closeable streams over directories.

Path: pure name manipulation

NIO.2 (JSR 203, Java 7) models a path as a sequence of name elements plus an optional root, bound to a FileSystem. Create one with Path.of (Java 11); Paths.get does the same thing, and its Javadoc recommends Path.of because Paths may be deprecated.

Path base = Path.of("/srv/app/in");                          // outputs as on Linux/macOS

  • Convert to and from the old API with path.toFile() and file.toPath().
static Path safeResolve(Path baseDir, String userSuppliedName) throws IOException {

Definition · failure as exceptions

FileVisitor and recursive delete

static void deleteTree(Path root) throws IOException {
    Files.walkFileTree(root, new SimpleFileVisitor<>() {
        @Override
        public FileVisitResult visitFile(Path file, BasicFileAttributes attrs) throws IOException {
            Files.delete(file);                    // a symlink is deleted itself, never followed
            return FileVisitResult.CONTINUE;
        }
        @Override
        public FileVisitResult postVisitDirectory(Path dir, IOException exc) throws IOException {
            if (exc != null) throw exc;            // listing this directory failed part-way
            Files.delete(dir);
            return FileVisitResult.CONTINUE;
        }
    });
}

Override visitFileFailed to log and return CONTINUE when one unreadable file should not stop the walk; return SKIP_SUBTREE from preVisitDirectory to prune (say, .git), or TERMINATE to stop.

What breaks in production
  • Unclosed Files.lines/list/walk. Each leaks a handle; on Windows the open handle also blocks deleting or moving that file or directory.

NIO Buffers, Channels & Memory-Mapped Files

40m video40m practice

NIO replaces "a stream hands you bytes" with "you hand a channel a buffer to fill or drain". The buffer is a fixed array plus three indices, and nearly every NIO bug is an index left in the wrong state.

ByteBuffer: capacity, position, limit, mark

Definition · buffer indices

A ByteBuffer has a fixed capacity; a position, the index of the next element to read or write; a limit, the first index that must not be touched; and an optional mark that reset() returns to. The invariant is 0 ≤ mark ≤ position ≤ limit ≤ capacity. Relative get()/put() advance the position; absolute get(i)/put(i, b) do not. remaining() is limit - position.

A buffer alternates between two modes. While filling (a channel read or your puts), position counts what has been written and limit is the capacity. While draining (a channel write or your gets), position counts what has been consumed and limit marks the end of valid data. Four methods move between the modes:

CallPositionLimitUse it
flip()0old positionafter filling, before draining
clear()0capacityafter draining everything, before refilling (data is not erased)
rewind()0unchangedto drain the same data again
compact()number of unread bytescapacityafter a partial drain: moves the unread bytes to the front, then keep filling
 
ByteBuffer buf = ByteBuffer.allocate(8);
buf.put("ABCDE".getBytes(US_ASCII));
buf.flip();
buf.get(); buf.get(); buf.get();
buf.compact();
System.out.println(buf);           // java.nio.HeapByteBuffer[pos=2 lim=8 cap=8]

Multi-byte reads such as getInt() use big-endian order unless you call order(ByteOrder.LITTLE_ENDIAN). slice() and duplicate() share the bytes but have independent indices.

Heap vs direct buffers

allocate(n) makes a heap buffer backed by a byte[] (hasArray() is true). allocateDirect(n) makes a direct buffer in native memory outside the Java heap. The OS can only do I/O on memory that will not move, and the GC moves heap arrays, so when you pass a heap buffer to a channel the JDK copies it through a temporary direct buffer. Direct buffers skip that copy but are expensive to allocate, are freed only when the ByteBuffer object is garbage-collected, and are capped by -XX:MaxDirectMemorySize.

When direct wins

Long-lived buffers reused for a lot of channel I/O: network servers, file copiers, anything that pools buffers (Netty does exactly this). Use heap buffers when buffers are short-lived, small, or when you will process every byte in Java anyway. Allocating a direct buffer per request is a classic way to run out of native memory while the heap looks healthy.

FileChannel and zero-copy transfer

Open a channel with FileChannel.open(path, options) or from RandomAccessFile/FileInputStream.getChannel(). read(buf) returns the byte count or -1; write(buf) may write fewer bytes than remain, so loop on hasRemaining(). Positional read(buf, pos) leaves the channel's position alone, so several threads can read one file concurrently. size(), truncate() and force() round it out.

static void copy(Path src, Path dst) throws IOException {
    try (FileChannel in = FileChannel.open(src, StandardOpenOption.READ);
         FileChannel out = FileChannel.open(dst, StandardOpenOption.CREATE,
                 StandardOpenOption.WRITE, StandardOpenOption.TRUNCATE_EXISTING)) {
        long pos = 0, size = in.size();
        while (pos < size) pos += in.transferTo(pos, size - pos, out);   // may move less than asked
    }
}

static long checksum(Path p) throws IOException {
    try (FileChannel ch = FileChannel.open(p)) {
        ByteBuffer buf = ByteBuffer.allocateDirect(64 * 1024);           // reused for every read
        long sum = 0;
        while (ch.read(buf) != -1) {
            buf.flip();                                                  // fill mode -> drain mode
            while (buf.hasRemaining()) sum += buf.get() & 0xFF;
            buf.clear();                                                 // drain mode -> fill mode
        }
        return sum;
    }
}

transferTo/transferFrom let the OS move bytes without copying them into the JVM at all. To a socket on Linux this can use sendfile, so file data goes from the page cache to the network stack without crossing into user space: that is what "zero-copy" means, and why static-file serving and Kafka's log transfer are fast.

Memory-mapped files

static long countNewlines(Path p) throws IOException {
    try (FileChannel ch = FileChannel.open(p)) {
        long count = 0, size = ch.size();
        for (long off = 0; off < size; off += Integer.MAX_VALUE) {     // one mapping is at most 2 GiB
            long len = Math.min(Integer.MAX_VALUE, size - off);
            MappedByteBuffer m = ch.map(FileChannel.MapMode.READ_ONLY, off, len);
            for (int i = 0; i < len; i++) if (m.get(i) == '\n') count++;
        }
        return count;
    }
}

map asks the OS to make part of the file addressable as memory. No data is read up front: touching a page triggers a page fault and the kernel loads it, and modified pages of a READ_WRITE mapping are written back by the OS (or by force()). This shines for random access into huge files and for sharing a file between processes. The costs: a ByteBuffer index is an int, so files over 2 GiB need several mappings; there is no public unmap, so the mapping lives until the buffer is collected, and on Windows the file cannot be deleted meanwhile; and if the file is truncated while mapped, access can fail with an unchecked InternalError rather than an IOException. Java 22's FFM API adds FileChannel.map(mode, offset, size, arena), returning a MemorySegment with long offsets that is unmapped when the arena closes.

Selectors and non-blocking I/O

A blocking socket read parks a thread until data arrives, so thread-per-connection needs 10,000 threads for 10,000 clients. A Selector lets one thread watch many channels in non-blocking mode and wake only for those that are ready (OP_ACCEPT, OP_READ, OP_WRITE, OP_CONNECT). The JDK implements it with epoll on Linux and kqueue on macOS. File channels are not selectable: a disk file is always "ready".

import java.net.InetSocketAddress;

static void echoServer(int port) throws IOException {
    try (Selector sel = Selector.open(); ServerSocketChannel server = ServerSocketChannel.open()) {
        server.bind(new InetSocketAddress(port)).configureBlocking(false);
        server.register(sel, SelectionKey.OP_ACCEPT);
        while (true) {
            sel.select();                                    // block until at least one channel is ready
            for (Iterator<SelectionKey> it = sel.selectedKeys().iterator(); it.hasNext(); ) {
                SelectionKey key = it.next();
                it.remove();                                 // otherwise it is reported again
                if (key.isAcceptable()) {
                    server.accept().configureBlocking(false)
                          .register(sel, SelectionKey.OP_READ, ByteBuffer.allocate(1024));
                } else if (key.isReadable()) {
                    var ch = (SocketChannel) key.channel();
                    var buf = (ByteBuffer) key.attachment();
                    if (ch.read(buf) == -1) { ch.close(); continue; }
                    buf.flip(); ch.write(buf); buf.compact();   // real servers register OP_WRITE for leftovers
                }
            }
        }
    }
}

This loop is an event loop. Netty wraps it with pooled direct buffers and pipelines of handlers, and Spring WebFlux runs on Reactor Netty (L363). The catch is the same at every level: a handler that blocks stalls every connection on that loop.

Decoding text from buffers

A multi-byte UTF-8 character can straddle two reads. CharsetDecoder.decode(in, out, endOfInput) decodes what it can and leaves an incomplete trailing sequence in in; compact() keeps it for the next read. This is what InputStreamReader does internally.

static String decodeChunks(ReadableByteChannel ch) throws IOException {
    CharsetDecoder dec = UTF_8.newDecoder();                 // REPORT on errors by default
    ByteBuffer in = ByteBuffer.allocate(4);                  // tiny, so characters straddle reads
    CharBuffer out = CharBuffer.allocate(4);
    var sb = new StringBuilder();
    boolean eof = false;
    while (!eof) {
        eof = ch.read(in) == -1;
        in.flip();
        CoderResult r;
        while ((r = dec.decode(in, out, eof)).isOverflow()) drain(out, sb);
        if (r.isError()) r.throwException();                 // malformed, or truncated at EOF
        in.compact();                                        // keep a half-read character
    }
    while (dec.flush(out).isOverflow()) drain(out, sb);
    drain(out, sb);
    return sb.toString();
}
static void drain(CharBuffer out, StringBuilder sb) { out.flip(); sb.append(out); out.clear(); }
What breaks in production
  • Forgetting flip(). Writing a just-filled buffer sends the empty region between position and capacity, or nothing at all.
  • clear() after a partial write. Unsent bytes are silently dropped; use compact().
  • Single write/transferTo call. Both may do less than asked. Loop.
  • Native memory exhaustion. OutOfMemoryError: Direct buffer memory or a container OOM-kill while heap usage is low: direct buffers or mappings that are never reused.

WatchService, Temp Files, Locks & Atomic Operations

35m video35m practice

The filesystem is shared with other processes and with crashes. This lesson's tools (change notification, private temp files, cross-process locks and atomic rename) let you write files that nobody ever sees half-finished.

WatchService: directory change events

Definition · watch keys

You register a directory with a WatchService for event kinds ENTRY_CREATE, ENTRY_MODIFY and ENTRY_DELETE, and get a WatchKey. When something happens the key is signalled and queued; take() or poll(timeout) returns it. pollEvents() gives the events, whose context() is the file name relative to the directory. You must call key.reset() to receive further events; it returns false once the key is invalid (the directory was deleted). If events are lost, you get one OVERFLOW event instead.

Platform quirks
  • Linux uses inotify and Windows uses ReadDirectoryChangesW, both native. On macOS the JDK has historically used a polling implementation, so events can arrive seconds late.
  • Registration is not recursive: register every subdirectory yourself, including new ones as they appear.
  • One save is rarely one event. Many editors write a temp file and rename it over the original (you see CREATE/DELETE, not MODIFY); others produce two MODIFY events, for content and timestamp.
  • Network filesystems and some container bind mounts deliver no events at all. Kubernetes ConfigMap volumes update by swapping a symlink, so react to any event in the directory.

A hot-reload config watcher

import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.*;
import java.util.Properties;
import java.util.concurrent.atomic.AtomicReference;
import static java.nio.file.StandardWatchEventKinds.*;

public class ConfigWatcher implements Runnable {
    private final Path file;
    private final AtomicReference<Properties> current = new AtomicReference<>();

    ConfigWatcher(Path file) throws IOException { this.file = file.toAbsolutePath(); current.set(load()); }

    Properties config() { return current.get(); }        // callers always see a complete config

    private Properties load() throws IOException {
        var p = new Properties();
        try (var r = Files.newBufferedReader(file)) { p.load(r); }
        return p;
    }

    @Override public void run() {
        try (WatchService ws = file.getFileSystem().newWatchService()) {
            file.getParent().register(ws, ENTRY_CREATE, ENTRY_MODIFY, ENTRY_DELETE);  // the directory
            while (!Thread.currentThread().isInterrupted()) {
                WatchKey key = ws.take();
                Thread.sleep(200);                          // debounce: let the burst of events land
                boolean relevant = false;
                for (WatchEvent<?> ev : key.pollEvents())
                    relevant |= ev.kind() == OVERFLOW || file.getFileName().equals(ev.context());
                if (!key.reset()) break;                    // directory gone
                if (relevant && Files.exists(file)) {
                    try { current.set(load()); }
                    catch (IOException | IllegalArgumentException e) { System.err.println("kept old config: " + e); }
                }
            }
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();             // shut down cleanly
        }
    }
}

Three design points carry over to every watcher: watch the parent directory and filter by name; debounce, because a burst of events should cause one reload; and validate before swapping, so a typo in the file leaves the old configuration running instead of crashing the service.

Temp files and cleanup

Files.createTempFile(prefix, suffix) creates a uniquely named empty file in java.io.tmpdir; createTempFile(dir, prefix, suffix) puts it in a directory you choose, and createTempDirectory does the same for directories. On POSIX systems they are created owner-only (rw------- for files, rwx------ for directories), so other users cannot read them.

Cleanup is your job. File.deleteOnExit() runs only on normal JVM shutdown, never after kill -9 or a crash, and every registration is held in memory until exit, which makes it a slow leak in a long-running server. StandardOpenOption.DELETE_ON_CLOSE is best-effort. Prefer try/finally with Files.deleteIfExists, and sweep stale temp files at startup.

Atomic publish: write temp, then rename

static void publish(Path target, byte[] content) throws IOException {
    Path dir = target.toAbsolutePath().getParent();
    Path tmp = Files.createTempFile(dir, target.getFileName() + ".", ".tmp");
    try {
        try (FileChannel ch = FileChannel.open(tmp, StandardOpenOption.WRITE)) {
            ByteBuffer buf = ByteBuffer.wrap(content);
            while (buf.hasRemaining()) ch.write(buf);    // a write may be partial
            ch.force(true);                              // durable before it becomes visible
        }
        Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE);
    } finally {
        Files.deleteIfExists(tmp);                       // no-op after a successful move
    }
}

With ATOMIC_MOVE the move is a single rename, which replaces an existing target atomically on Linux and macOS; on Windows the JDK uses a replacing move. Across filesystems it throws AtomicMoveNotSupportedException instead of silently copying, which is why the temp file must not live in /tmp. For full crash durability on Linux, also fsync the directory (FileChannel.open(dir, READ).force(true); this throws on Windows). Note that the published file inherits the temp file's owner-only permissions; set the ones you need before moving.

FileLock: coordination across processes

static void runExclusively(Path lockFile, Runnable job) throws IOException {
    try (FileChannel ch = FileChannel.open(lockFile, StandardOpenOption.CREATE, StandardOpenOption.WRITE);
         FileLock lock = ch.tryLock()) {                 // null if another process holds it
        if (lock == null) { System.out.println("another instance is running"); return; }
        job.run();
    }                                                    // released on close, or when the process dies
}
  • lock() blocks, tryLock() returns null immediately, and lock(pos, size, true) takes a shared (read) lock on a region.
  • Locks belong to the whole JVM, not a thread. A second lock on an overlapping region from the same JVM throws OverlappingFileLockException, and on some systems closing any channel to that file releases the JVM's locks on it.
  • On Linux and macOS locks are advisory: a process that never asks for the lock can still read and write. Windows locks are mandatory. Neither is dependable over NFS.

Typical uses are a single-instance guard for a batch job and serialising access to a shared file between processes on one host. For coordination across machines, use the database or a distributed lock.

A crash in the middle of a write leaves a truncated, "torn" file. There are two durable designs. Either never modify in place (write a new file, rename it into place), or make the file append-only and frame every record with its length and a checksum (java.util.zip.CRC32C), so recovery can find a torn final record and truncate it. Databases do the second; config and report files should do the first.

What breaks in production
  • Processing a file on ENTRY_CREATE. The producer may still be writing it. Producers should rename finished files into the watched directory; consumers should ignore *.tmp.
  • Ignoring OVERFLOW. Under load, events are dropped. Treat it as "rescan everything".
  • Temp file on another mount. /tmp to /data cannot be renamed atomically; REPLACE_EXISTING alone falls back to copy-then-delete, which is not atomic.
  • Locking within one JVM. Two threads using FileLock as a mutex hit OverlappingFileLockException. Use a ReentrantLock in-process.

Resource Management Patterns & Leak Detection

35m video35m practice

The garbage collector manages memory, not file descriptors, sockets or connections. Those are released only when someone calls close(), so every resource needs exactly one owner and a code path that closes it even when things go wrong.

Designing your own AutoCloseable

AutoCloseable.close() is declared throws Exception; Closeable.close() narrows it to IOException and requires idempotency. In your own class, declare the narrowest exception you can, ideally none, so a try-with-resources block needs no catch. A good resource class:

  • makes close() idempotent: the second call does nothing, because wrapper chains and defensive callers will call it twice;
  • makes it thread-safe when the object is shared, with AtomicBoolean.compareAndSet;
  • throws IllegalStateException from other methods after close, instead of failing deep inside;
  • releases what it holds in reverse order of acquisition.
import java.lang.ref.Cleaner;
import java.util.concurrent.atomic.AtomicBoolean;

public final class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    private static final class State implements Runnable {     // must not reference NativeBuffer
        private final long handle;
        State(long handle) { this.handle = handle; }
        @Override public void run() { System.out.println("freeing " + handle); }  // free(handle)
    }

    private final AtomicBoolean closed = new AtomicBoolean();
    private final Cleaner.Cleanable cleanable;

    public NativeBuffer(long handle) { cleanable = CLEANER.register(this, new State(handle)); }

    public void write(byte[] data) {
        if (closed.get()) throw new IllegalStateException("buffer closed");
        // ... use the handle
    }

    @Override public void close() {                           // no checked exception
        if (closed.compareAndSet(false, true)) cleanable.clean();   // State.run happens at most once
    }
}

Cleaner, PhantomReference and why finalize died

finalize() was deprecated in Java 9 and deprecated for removal by JEP 421 (Java 18). It ran at an unpredictable time or never, on a single finalizer thread, could resurrect the object, slowed allocation and GC, and enabled finalizer attacks on partially constructed objects.

Definition · Cleaner

Cleaner (Java 9) registers a cleaning action against an object. When the object becomes phantom-reachable, the Cleaner's thread runs the action; calling Cleanable.clean() earlier runs it immediately, and either way it runs at most once. The action must not hold a reference to the object, directly or through a captured this in a lambda or inner class, or the object never becomes unreachable and the action never runs.

A Cleaner is a safety net for callers who forget to close (Effective Java, Item 8), not a substitute for closing. With a large heap the GC may not run for hours, and the process can hit a 1,024-descriptor limit while the heap is nearly empty. The JDK itself uses Cleaners this way, for example to free direct buffer memory.

Wrapper stacks and closing in reverse order

import java.util.zip.GZIPInputStream;

// Leaks the FileInputStream if the gzip header is bad: the constructor throws before a resource exists
try (var in = new GZIPInputStream(new FileInputStream("data.gz"))) {
    in.transferTo(OutputStream.nullOutputStream());
}

// Safe: each layer is its own resource, closed in reverse; double close is harmless (idempotent)
try (var file = new FileInputStream("data.gz");
     var gzip = new GZIPInputStream(file);
     var reader = new BufferedReader(new InputStreamReader(gzip, UTF_8))) {
    reader.lines().limit(5).forEach(System.out::println);
}

Constructors that do I/O (GZIPInputStream reads the header, ObjectInputStream reads the stream magic) are where nested-constructor leaks happen. Reverse order matters because later resources depend on earlier ones: close the result set, then the statement, then the connection. When the number of resources is only known at run time, push them on a stack and unwind it:

static void closeAll(Deque<AutoCloseable> opened) throws Exception {   // filled with push() as opened
    Exception first = null;
    while (!opened.isEmpty()) {
        try { opened.pop().close(); }                                     // most recent first
        catch (Exception e) { if (first == null) first = e; else first.addSuppressed(e); }
    }
    if (first != null) throw first;                                       // keep every failure
}

Leaks in long-running servers

On Linux every open file, socket, pipe and epoll instance is a file descriptor, and each process has a limit. A leak of one descriptor per request is invisible in a unit test and fatal after a day in production: every open and accept then fails with IOException: Too many open files, so the service cannot even accept a health-check connection. Connection pools turn a JDBC leak into a different symptom, threads waiting until "connection is not available, request timed out".

$ ulimit -n                              # soft limit for this shell (often 1024)
$ cat /proc/4242/limits | grep "open files"   # the limit the running JVM actually got
$ ls /proc/4242/fd | wc -l               # descriptors open right now; sample it over time
$ lsof -p 4242 | awk '{print $5}' | sort | uniq -c | sort -rn   # by type: REG, IPv4, unix, ...
$ ss -tanp | grep 4242 | grep CLOSE_WAIT | wc -l   # peer closed, we never did: unclosed HTTP responses

The limit inside systemd units and containers comes from LimitNOFILE or the container runtime, not from your shell. From Java, com.sun.management.UnixOperatingSystemMXBean exposes the open and maximum descriptor counts, and Micrometer publishes them as process.files.open and process.files.max: graph them and alert on the trend, not the cliff. HikariCP's leakDetectionThreshold logs the stack trace of whoever borrowed a connection and held it too long.

Who owns closing?

API design rules
  • Whoever opens it closes it. A method that receives a stream as a parameter must not close it; the caller may still need it. Document this.
  • Wrappers take ownership. Closing a BufferedReader closes the stream it wraps. So never wrap System.out in a try-with-resources PrintWriter: you will close standard output.
  • Returning a resource transfers ownership. Files.lines returns a stream the caller must close; say so in the Javadoc and make the type AutoCloseable.
  • Prefer execute-around. Take a callback and keep the resource inside, as Spring's JdbcTemplate does. The caller cannot leak what it never holds.
static <T> T withLines(Path p, Function<Stream<String>, T> body) throws IOException {
    try (Stream<String> lines = Files.lines(p)) {     // opened here, so closed here
        return body.apply(lines);                     // body must not let the stream escape
    }
}
// long rows = withLines(Path.of("orders.csv"), s -> s.skip(1).count());
What breaks in production
  • Returning a lazy view of a closed resource. try (var r = Files.newBufferedReader(p)) { return r.lines(); } hands back a stream over a closed reader: UncheckedIOException: Stream closed at first use.
  • Leaks only on the error path. getConnection() outside try-with-resources works until the first exception between open and close; each failure then leaks one connection until the pool is empty.
  • Waiting for the GC. Code that relies on Cleaners or finalizers runs out of descriptors long before heap pressure triggers a collection.
  • Unread HTTP response bodies. Many HTTP clients return a connection to the pool only when the body is consumed or closed; skip that and sockets pile up in CLOSE_WAIT.

java.time: LocalDate, LocalTime & LocalDateTime

40m video40m practice

java.time gives each concept its own immutable type. The Local* classes are what a calendar on the wall and a clock on the desk show: a date, a time of day, or both, with no time zone and therefore no fixed point on the timeline.

Why Date and Calendar had to go

Date d = new Date(2024, 1, 29);     // deprecated: year is 1900 + 2024 = 3924, month 1 is February
System.out.println(d);              // Fri Feb 29 00:00:00 IST 3924 (prints in the JVM's zone)

Calendar c = Calendar.getInstance();
c.clear();
c.set(2024, Calendar.FEBRUARY, 30); // lenient by default: "February 30" silently becomes March 1
Date shared = c.getTime();
shared.setTime(0);                  // mutable: every holder of this reference now sees 1970
  • Mutability. Date and Calendar have setters, so a Date field returned from a getter can be changed by the caller (Effective Java Item 50 uses exactly this example).
  • Zero-based months and a 1900 year offset, with leniency that turns invalid input into a different valid date.
  • Thread safety. SimpleDateFormat keeps parse state in fields and corrupts results when shared (L111).
  • Confused concepts. Date is an instant but prints in a zone; there was no type for "a date with no time" or "a time with no date".

JSR 310, led by Joda-Time's author Stephen Colebourne, replaced them in Java 8. Every java.time class is immutable and thread-safe, months run 1–12, and invalid values throw DateTimeException instead of rolling over.

LocalDate

LocalDate today = LocalDate.now();                         // date in the JVM's default zone
LocalDate d = LocalDate.of(2024, Month.JANUARY, 31);
LocalDate p = LocalDate.parse("2024-02-29");               // ISO-8601 yyyy-MM-dd (patterns: L110)
System.out.println(d.plusMonths(1));                       // 2024-02-29: clamped to the month's end
System.out.println(d.plusMonths(1).plusMonths(1));         // 2024-03-29, not 03-31
System.out.println(d.plusMonths(2));                       // 2024-03-31
System.out.println(p.plusYears(1));                        // 2025-02-28
System.out.println(d.minusMonths(2).withDayOfMonth(1));    // 2023-11-01
System.out.println(p.getDayOfWeek() + " " + p.lengthOfMonth() + " " + p.isLeapYear());  // THURSDAY 29 true
// LocalDate.of(2023, 2, 29)  -> DateTimeException: Invalid date 'February 29' as '2023' is not a leap year
Definition · month arithmetic

plusMonths(n) changes the month field, then, if the day no longer exists in the new month, clamps it to the last valid day. So month arithmetic is not associative (two single-month steps from January 31 land on March 29, one two-month step on March 31) and not reversible (d.plusMonths(1).minusMonths(1) is January 29). For recurring schedules, always compute start.plusMonths(k) from the original anchor, never by chaining.

getDayOfWeek() returns the DayOfWeek enum with ISO numbering (MONDAY = 1 … SUNDAY = 7). isLeapYear() applies the Gregorian rule: divisible by 4, except centuries, unless divisible by 400. datesUntil(end) (Java 9) streams every date in a half-open range.

LocalTime and LocalDateTime

LocalTime t = LocalTime.of(23, 30, 15, 123_456_789);
System.out.println(t.plusHours(1));                        // 00:30:15.123456789: wraps at midnight
System.out.println(t.truncatedTo(ChronoUnit.SECONDS));     // 23:30:15
System.out.println(LocalTime.now());                       // e.g. 23:50:51.434607200

LocalDateTime ldt = LocalDate.of(2024, 3, 15).atTime(t);   // compose a date and a time
LocalDate datePart = ldt.toLocalDate();                    // and take them apart again
LocalTime timePart = ldt.toLocalTime();
System.out.println(ldt.plusHours(1));                      // 2024-03-16T00:30:15.123456789: the date rolls
System.out.println(datePart.atStartOfDay() + " " + timePart.getHour());   // 2024-03-15T00:00 23

LocalTime stores nanoseconds, but now() is only as precise as the system clock: milliseconds on Java 8, typically microseconds or better since Java 9. A LocalDateTime is a date plus a time and nothing else. "2025-03-30T02:30" is a perfectly valid LocalDateTime that never happened in Berlin, because clocks jumped from 02:00 to 03:00 that night (L109). Use it for things people schedule in local terms (a shop opening, a birthday party), not for recording when something happened.

Immutability and the with-er pattern

No java.time object ever changes. Methods that look like setters (withDayOfMonth, withYear, with(ChronoField.MONTH_OF_YEAR, 6)) and all arithmetic return a new instance, so calls chain fluently and values can be shared across threads and used as map keys without defensive copies. The cost is a classic bug: date.plusDays(1); on its own line computes a new date and throws it away.

TemporalAdjusters

A TemporalAdjuster is a function from a date to a date, applied with with(...). TemporalAdjusters provides the common ones; your own is one lambda.

import static java.time.temporal.TemporalAdjusters.*;

LocalDate m = LocalDate.of(2024, 5, 15);                         // a Wednesday
System.out.println(m.with(firstDayOfMonth()));                   // 2024-05-01
System.out.println(m.with(lastDayOfMonth()));                    // 2024-05-31
System.out.println(m.with(next(DayOfWeek.MONDAY)));              // 2024-05-20
System.out.println(m.with(nextOrSame(DayOfWeek.WEDNESDAY)));     // 2024-05-15
System.out.println(m.with(lastDayOfYear()));                     // 2024-12-31
System.out.println(m.with(dayOfWeekInMonth(2, DayOfWeek.TUESDAY)));  // 2024-05-14

TemporalAdjuster nextWorkingDay = ofDateAdjuster(date -> switch (date.getDayOfWeek()) {
    case FRIDAY -> date.plusDays(3);
    case SATURDAY -> date.plusDays(2);
    default -> date.plusDays(1);
});
System.out.println(m.with(lastDayOfMonth()).with(nextWorkingDay)); // 2024-06-03 (May 31 is a Friday)

Comparing dates and times

isBefore, isAfter and isEqual compare positions on the time-line; compareTo gives the natural order for sorting. For LocalDate and LocalDateTime in the ISO calendar, isEqual and equals agree. For offset and zoned types they do not, and the difference matters:

var utc = OffsetDateTime.of(2024, 1, 1, 12, 0, 0, 0, ZoneOffset.UTC);
var ist = utc.withOffsetSameInstant(ZoneOffset.ofHoursMinutes(5, 30));   // 2024-01-01T17:30+05:30
System.out.println(utc.isEqual(ist) + " " + utc.equals(ist));           // true false
long weekdays = LocalDate.of(2024, 1, 1).datesUntil(LocalDate.of(2024, 6, 1))
        .filter(x -> x.getDayOfWeek().getValue() <= 5).count();        // 110

isEqual asks "same instant?", while equals asks "same instant and same offset?". Use isEqual for business logic, and remember that a LocalDate never equals a LocalDateTime.

What breaks in production
  • Discarded results. invoice.getDueDate().plusDays(30); changes nothing. Enable your IDE's "result of method call ignored" inspection.
  • Chained month arithmetic. A subscription renewed by repeated plusMonths(1) from January 31 drifts to the 28th or 29th for ever.
  • "Today" depends on the server. LocalDate.now() uses the JVM's default zone: a container in UTC and a user in India disagree about the date for five and a half hours every day. Inject a Clock (L108).
  • Mixed numbering. Code ported from Calendar uses Calendar.SUNDAY == 1 and 0-based months; java.time uses MONDAY == 1 and 1-based months.

Instant, Duration, Period & Testable Clocks

40m video40m practice

An Instant is a point on the UTC time-line; a Duration is an exact number of seconds; a Period is a count of calendar units whose length in seconds depends on where you apply it. Getting "now" from an injected Clock is what makes code that uses them testable.

Instant: the machine's view of time

Definition · Instant

An Instant is a long count of seconds since the epoch 1970-01-01T00:00:00Z plus an int of nanoseconds (0–999,999,999). It has no time zone, no calendar and no fields such as year or month. The Java time-scale treats every day as exactly 86,400 seconds and smooths leap seconds away, so arithmetic is simple and matches what operating systems report.

Instant now = Instant.now();
System.out.println(now.getEpochSecond() + " s + " + now.getNano() + " ns");
Instant t = Instant.parse("2024-03-10T12:00:00Z");
System.out.println(t.plus(1, ChronoUnit.DAYS));               // 2024-03-11T12:00:00Z: exactly 86,400 s
System.out.println(t.toEpochMilli());                         // 1710072000000
System.out.println(Instant.ofEpochMilli(0));                  // 1970-01-01T00:00:00Z
// t.plus(1, ChronoUnit.MONTHS)  -> UnsupportedTemporalTypeException: Unsupported unit: Months
// t.get(ChronoField.YEAR)       -> UnsupportedTemporalTypeException: Unsupported field: Year

Use Instant for anything that records when something happened: created-at columns, event timestamps, token expiry, log lines. To show it to a human, add a zone (t.atZone(zone), L109).

Measuring elapsed time

long start = System.nanoTime();                 // monotonic; arbitrary origin; differences only
Thread.sleep(50);
Duration took = Duration.ofNanos(System.nanoTime() - start);

Instant startedAt = Instant.now();              // wall clock: record it, store it, log it
System.out.println(took.toMillis() + " ms, started " + startedAt);
nanoTime vs the wall clock

System.currentTimeMillis() and Instant.now() read the wall clock, which NTP, an administrator or a VM migration can move backwards or forwards at any moment. An elapsed time computed from it can be negative or off by hours. System.nanoTime() is monotonic within one JVM but has no meaning as a date and cannot be compared across processes or machines. Use nanoTime for timeouts, latencies, retries and benchmarks; use Instant for timestamps that leave the process.

Clock injection for testable time

Every now() in java.time has an overload that takes a Clock. A Clock supplies the current instant and a zone: Clock.systemUTC() and Clock.systemDefaultZone() read the real clock; Clock.fixed(instant, zone) always returns the same instant; Clock.offset(base, duration) shifts another clock; Clock.tick(base, duration) truncates it. Since Java 17, components that only need instants can depend on the narrower InstantSource interface, which Clock implements.

public final class InvoiceService {
    private final Clock clock;

    public InvoiceService(Clock clock) { this.clock = clock; }   // production: Clock.systemUTC()

    public boolean isOverdue(LocalDate dueDate) {
        return LocalDate.now(clock).isAfter(dueDate);            // never LocalDate.now()
    }
    public Instant stamp() { return clock.instant(); }
}

class InvoiceServiceTest {
    void overdueIsDecidedByTheInjectedClock() {
        Clock fixed = Clock.fixed(Instant.parse("2024-03-01T10:00:00Z"), ZoneOffset.UTC);
        LocalDate due = LocalDate.of(2024, 2, 29);
        assert new InvoiceService(fixed).isOverdue(due);
        assert !new InvoiceService(Clock.offset(fixed, Duration.ofDays(-2))).isOverdue(due);
    }
}

Why never call the no-argument now() in business logic: it hides a dependency on the system clock and on the JVM's default zone. Tests become flaky around midnight, month ends and DST changes, and "what happens on February 29?" can only be tested on February 29. In Spring, declare one @Bean Clock clock() { return Clock.systemUTC(); } and inject it everywhere; tests replace that bean with a fixed or mutable clock.

  • 24 hours is not a day. "Run tomorrow at the same time" computed with a Duration drifts by an hour twice a year.

Time Zones, ZonedDateTime & Storing Time in Databases

45m video45m practice

A time zone is a set of rules that maps instants to wall-clock readings, and the mapping is not one-to-one: some local times never happen and some happen twice. Store instants, keep the user's zone as data, and convert only at the edges.

ZoneId, ZoneOffset, ZonedDateTime, OffsetDateTime

Definition · offsets vs zones
  • ZoneOffset: a fixed difference from UTC, such as +05:30 or Z. It is a ZoneId with one never-changing rule.
  • ZoneId such as Europe/Berlin: a region whose offset changes with DST and with political decisions, described by ZoneRules.
  • OffsetDateTime = local date-time + offset. This is what ISO-8601 strings, JSON and JDBC carry. It pins an instant but knows nothing about DST.
  • ZonedDateTime = local date-time + region + the offset currently in force. Use it for calendar arithmetic in a place: "tomorrow at 09:00 in Berlin".
ZoneId berlin = ZoneId.of("Europe/Berlin"), kolkata = ZoneId.of("Asia/Kolkata");
Instant meeting = Instant.parse("2025-06-02T08:00:00Z");
ZonedDateTime inBerlin = meeting.atZone(berlin);                  // 2025-06-02T10:00+02:00[Europe/Berlin]
ZonedDateTime inKolkata = inBerlin.withZoneSameInstant(kolkata);  // 2025-06-02T13:30+05:30[Asia/Kolkata]
ZonedDateTime wrong = inBerlin.withZoneSameLocal(kolkata);        // 10:00 in Kolkata = 04:30Z: another instant
OffsetDateTime wire = inBerlin.toOffsetDateTime();                // 2025-06-02T10:00+02:00
System.out.println(inKolkata + " " + wrong.toInstant() + " " + wire);

Converting between zones correctly means withZoneSameInstant (same moment, different clock reading). withZoneSameLocal keeps the clock reading and changes the moment, which is almost never what you want. Never use three-letter abbreviations: ZoneId.SHORT_IDS maps "IST" to Asia/Kolkata, but people also use it for Irish and Israel Standard Time.

The IANA tz database

Region rules come from the IANA Time Zone Database (the "Olson" database), which records every offset change for each region since 1970 and many before. It is updated several times a year because governments change DST rules, sometimes with only weeks of notice. The JDK ships its own copy (lib/tzdb.dat), so a JVM that is not patched applies stale rules; Oracle's TZUpdater tool can refresh it in place. ZoneRulesProvider.getVersions("UTC").lastKey() prints the bundled version (a recent JDK 21 update reports 2026a). One consequence for design: an instant computed today for a meeting next year may be wrong by the time the meeting comes round.

DST gaps and overlaps

import java.time.zone.*;            // ZoneRules, ZoneOffsetTransition

ZoneId berlin = ZoneId.of("Europe/Berlin");
ZoneRules rules = berlin.getRules();
LocalDateTime gap = LocalDateTime.of(2025, 3, 30, 2, 30);
LocalDateTime overlap = LocalDateTime.of(2025, 10, 26, 2, 30);
System.out.println(rules.getValidOffsets(gap));                   // []
System.out.println(rules.getValidOffsets(overlap));               // [+02:00, +01:00]
System.out.println(ZonedDateTime.of(gap, berlin));                // 2025-03-30T03:30+02:00: pushed forward by the gap
ZonedDateTime first = ZonedDateTime.of(overlap, berlin);          // 2025-10-26T02:30+02:00: earlier offset wins
ZonedDateTime second = first.withLaterOffsetAtOverlap();          // 2025-10-26T02:30+01:00
System.out.println(Duration.between(first, second));              // PT1H
System.out.println(second.withEarlierOffsetAtOverlap().equals(first));   // true
ZoneOffsetTransition t = rules.getTransition(gap);
System.out.println(t + " " + t.isGap());     // Transition[Gap at 2025-03-30T02:00+01:00 to +02:00] true
// ZonedDateTime.ofStrict(gap, ZoneOffset.ofHours(1), berlin) -> DateTimeException: ... does not exist

ZoneRules answers every question about a region: getOffset(instant), getValidOffsets(localDateTime) (zero, one or two), getTransition, nextTransition(instant) and isDaylightSavings(instant). Resolution of a local time is lenient by default: gaps move forward by the gap length, overlaps take the earlier offset. When the choice matters (billing a night shift, deduplicating events), check getValidOffsets and decide explicitly.

The golden rule: store UTC, render in the user's zone

Golden rule

Record when something happened as an Instant in a timestamptz column. Store the user's preferred zone separately as a ZoneId string. Convert to a ZonedDateTime only to display, or for calendar logic. The one exception is a future event defined in local terms, such as "09:00 Berlin on 4 May next year": store the LocalDateTime plus the ZoneId and compute the instant when needed, so a rule change is picked up.

-- PostgreSQL
CREATE TABLE events (
  id          bigserial PRIMARY KEY,
  happened_at timestamptz NOT NULL,   -- an instant, stored as UTC microseconds
  local_wall  timestamp,              -- bare wall-clock fields, no zone at all
  user_zone   text NOT NULL           -- e.g. 'Asia/Kolkata'
);
SET TIME ZONE 'Asia/Kolkata';
INSERT INTO events (happened_at, local_wall, user_zone)
VALUES ('2025-06-02 08:00:00+00', '2025-06-02 08:00:00', 'Europe/Berlin');
SELECT happened_at, local_wall FROM events;
--  2025-06-02 13:30:00+05:30 | 2025-06-02 08:00:00

TIMESTAMP vs TIMESTAMPTZ. Despite its name, timestamptz does not store a zone. It converts input to UTC using the literal's offset (or the session's TimeZone if there is none) and converts output to the session zone. timestamp stores the fields you gave it and never converts, so the same value means different instants to clients in different zones. Both have microsecond precision, so a Java Instant with nanoseconds does not survive a round trip unchanged.

Scheduling across zones

import org.springframework.scheduling.annotation.Scheduled;

class Jobs {
    @Scheduled(cron = "0 0 9 * * MON-FRI", zone = "Europe/Berlin")   // business time: 09:00 in Berlin
    void morningReport() { }

    @Scheduled(cron = "0 30 2 * * *", zone = "UTC")                   // system job: no DST surprises
    void nightlyCleanup() { }

    static ZonedDateTime nextRun(LocalTime at, ZoneId zone, Clock clock) {   // per-user reminders
        ZonedDateTime now = ZonedDateTime.now(clock.withZone(zone));
        ZonedDateTime today = now.with(at);                 // resolved in the zone: gaps shift forward
        return today.isAfter(now) ? today : today.plusDays(1).with(at);
    }
}

Business schedules ("09:00 for the customer") belong in the customer's zone; machine schedules belong in UTC. A job at 02:30 in a DST zone is skipped or shifted one night in spring and has two candidate instants one night in autumn, so keep maintenance jobs out of the 01:00–03:00 local window or run them on UTC.

What breaks in production
  • The JVM's default zone. Laptops run in local time, containers usually in UTC. Any now(), Date.toString() or timestamp mapping that relies on the default produces different data in each environment.
  • LocalDateTime for event times. 02:30 on the October transition night is ambiguous, and every row becomes wrong if the server's zone changes.
  • Nanoseconds vs microseconds. assertEquals(saved, loaded) fails after a round trip through PostgreSQL. Truncate to microseconds before saving.
  • Stale tzdata. An unpatched JDK applies old DST rules after a country changes them, and every displayed time for that region is off by an hour.

DateTimeFormatter, Parsing, Locales & i18n

40m video40m practice

Machines exchange ISO-8601; humans read localized text. A DateTimeFormatter is an immutable, thread-safe description of one such text format, and most parsing bugs come from a wrong pattern letter or a forgotten locale.

ISO constants: the machine format

ZonedDateTime z = ZonedDateTime.of(2024, 3, 15, 10, 15, 30, 0, ZoneId.of("Europe/Paris"));
System.out.println(DateTimeFormatter.ISO_OFFSET_DATE_TIME.format(z));  // 2024-03-15T10:15:30+01:00
System.out.println(DateTimeFormatter.ISO_INSTANT.format(z));           // 2024-03-15T09:15:30Z
System.out.println(DateTimeFormatter.BASIC_ISO_DATE.format(z));        // 20240315+0100
System.out.println(DateTimeFormatter.ISO_WEEK_DATE.format(z));         // 2024-W11-5+01:00
System.out.println(DateTimeFormatter.RFC_1123_DATE_TIME.format(z));    // Fri, 15 Mar 2024 10:15:30 +0100

Every java.time type's toString() and one-argument parse() already use the matching ISO formatter (ISO_LOCAL_DATE, ISO_ZONED_DATE_TIME…). Use ISO for JSON, logs, file names and APIs: it sorts as text and needs no locale. RFC_1123_DATE_TIME is the HTTP header format.

ofLocalizedDate, ofLocalizedTime and ofLocalizedDateTime take a FormatStyle and produce whatever the locale's conventions say, using the Unicode CLDR data that is the JDK's default since Java 9 (JEP 252). LONG and FULL time styles include a zone name, so formatting a LocalTime with them throws "Unable to extract ZoneId". Localized formats are for display; don't parse them, and never store them.

DateTimeFormatterBuilder: optional parts, case-insensitivity, defaults

        .appendPattern("uuuu-MM-dd")
        .optionalStart().appendLiteral('T').optionalEnd()
        .optionalStart().appendLiteral(' ').optionalEnd()

    System.out.println(LocalDateTime.parse("2024-03-15 10:15", FLEXIBLE));     // 2024-03-15T10:15
    System.out.println(LocalDateTime.parse("2024-03-15T10:15:30", FLEXIBLE));  // 2024-03-15T10:15:30
    System.out.println(LocalDate.parse("15-MAR-2024", ORACLE_STYLE));          // 2024-03-15
}

ResolverStyle and DateTimeParseException

Definition · parse, then resolve

Parsing has two phases: the text is split into fields, then the fields are resolved into a date. ResolverStyle controls the second phase. SMART, the default for ofPattern, clamps a day-of-month of 29–31 to the month's end; LENIENT rolls over; STRICT rejects. The ISO constants are already STRICT.

var fmt = DateTimeFormatter.ofPattern("uuuu-MM-dd");
System.out.println(LocalDate.parse("2023-02-30", fmt));                                       // 2023-02-28
System.out.println(LocalDate.parse("2023-02-30", fmt.withResolverStyle(ResolverStyle.LENIENT))); // 2023-03-02
try {
    LocalDate.parse("2023-02-30", fmt.withResolverStyle(ResolverStyle.STRICT));
} catch (DateTimeParseException e) {
    System.out.println(e.getMessage());          // Text '2023-02-30' could not be parsed: Invalid date 'FEBRUARY 30'
    System.out.println(e.getParsedString() + " @" + e.getErrorIndex());
}
// ofPattern("yyyy-MM-dd").withResolverStyle(STRICT) rejects every input: yyyy is year-of-era and needs an era (G)

For user input, use STRICT with uuuu, catch DateTimeParseException at the boundary, and turn getErrorIndex() into a field-level validation message instead of a 500. DateTimeFormatter is immutable and thread-safe, so keep formatters in static final constants and share them across threads. The legacy SimpleDateFormat cannot be shared (L111).

Locales, bundles, money and the hard parts of i18n

A Locale is a language plus optional region, script and extensions: Locale.of("de", "DE") (Java 19+) or Locale.forLanguageTag("pt-BR"). In a server, the default locale belongs to the machine, not the user; resolve the user's locale (in Spring, a LocaleResolver reads Accept-Language) and pass it to every formatter.

# messages.properties          (read as UTF-8 since Java 9)
cart.summary={0} has {1,choice,0#no items|1#one item|1<{1,number,integer} items} in the cart
# messages_de.properties
cart.summary={0} hat {1,choice,0#keine Artikel|1#einen Artikel|1<{1,number,integer} Artikel} im Warenkorb
import java.math.BigDecimal;
import java.text.*;                                                          // MessageFormat, NumberFormat

ResourceBundle rb = ResourceBundle.getBundle("messages", Locale.GERMANY);   // de_DE, then de, then base
String text = new MessageFormat(rb.getString("cart.summary"), Locale.GERMANY)
        .format(new Object[]{"Ana", 1234});                                 // Ana hat 1.234 Artikel im Warenkorb

BigDecimal price = new BigDecimal("1234.5");                                 // money is never a double
NumberFormat.getCurrencyInstance(Locale.US).format(price);                   // $1,234.50
NumberFormat.getCurrencyInstance(Locale.GERMANY).format(price);              // 1.234,50 €
NumberFormat.getCurrencyInstance(Locale.JAPAN).format(price);                // ￥1,234 (0 decimals, half-even)
NumberFormat eurForUs = NumberFormat.getCurrencyInstance(Locale.US);

Spring's MessageSource (Phase 13) wraps exactly this lookup: getMessage("cart.summary", args, locale). Bundle lookup falls back through the requested locale, then the JVM default locale's bundles, then the base file, which surprises people on servers whose default is not English.

Pluralization and RTL
  • ChoiceFormat handles English's "one/other". Polish needs one/few/many/other and Arabic six forms; use ICU4J's plural rules for real coverage. Never build sentences by concatenation: word order differs, so translators must own the whole sentence with placeholders.
  • Arabic and Hebrew are right-to-left. Formatted output may contain direction marks and non-Latin digits: Egyptian Arabic currency output uses Arabic-Indic digits wrapped in U+200F marks. Request Latin digits with the extension ar-EG-u-nu-latn, and let the UI layer handle bidirectional layout.
  • Grouping is cultural too: DecimalFormat cannot express Indian lakh grouping (12,34,567), so en-IN output in the JDK shows 1,234,567.
What breaks in production
  • YYYY in a pattern. Works all year, then prints next year for the last days of December. Reports and file names roll over a year early.
  • Default-locale formatting. A pattern with MMM parses "Mar" on a developer laptop and fails in a container whose locale is different.
  • JDK upgrade changes output. CLDR updates alter localized strings (the U+202F space before AM/PM); snapshot tests and parsers of localized text break.
  • Currency from locale. The currency comes from the order, the format from the user; derive it from en-US and a Swiss customer sees dollars.

Legacy Date/Calendar & Migration Strategy

30m video30m practice

You will maintain code that uses Date, Calendar and SimpleDateFormat for years. Know what each one really is, convert to java.time at the boundary, and migrate the dangerous parts first.

What Date and Calendar really are

A java.util.Date is a mutable wrapper around one long: milliseconds since 1970-01-01T00:00Z. Despite the name it is an instant, not a date. Its year/month/day methods have been deprecated since Java 1.1, equals compares the millisecond values, and toString() renders the instant in the JVM's default zone, which is why the same Date "looks different" on two servers.

Date d = new Date(0);
System.out.println(d.getTime() + " " + d);       // 0 Thu Jan 01 01:00:00 CET 1970 on a Berlin JVM

Calendar c = new GregorianCalendar(2024, 12, 1);  // month 12 is the thirteenth month (0-based)...
System.out.println(c.get(Calendar.YEAR) + "-" + (c.get(Calendar.MONTH) + 1));   // 2025-1 ...so it rolls over
System.out.println(Calendar.getInstance(Locale.forLanguageTag("th-TH")).getClass().getSimpleName());
                                                  // BuddhistCalendar: YEAR is 543 ahead

Calendar is a mutable bag of fields (YEAR, MONTH 0–11, DAY_OF_WEEK with SUNDAY = 1) plus a time zone, recomputed lazily, and lenient by default. Calendar.getInstance() returns a GregorianCalendar for most locales but a BuddhistCalendar for Thai and a Japanese imperial calendar for ja-JP-u-ca-japanese. GregorianCalendar also switches to the Julian calendar before 15 October 1582, while java.time is proleptic ISO: a GregorianCalendar for 1 January 1500 converts to 1500-01-10.

SimpleDateFormat is not thread-safe

import java.text.SimpleDateFormat;

public class SdfRace {
    private static final SimpleDateFormat FMT = new SimpleDateFormat("yyyy-MM-dd");   // shared: the bug

    public static void main(String[] args) {
        List<String> inputs = IntStream.range(0, 10_000)
                .mapToObj(i -> LocalDate.of(2000, 1, 1).plusDays(i % 3650).toString()).toList();
        long wrong = inputs.parallelStream().filter(s -> {
            try {
                return !FMT.format(FMT.parse(s)).equals(s);
            } catch (Exception e) {                 // NumberFormatException, ArrayIndexOutOfBounds, ...
                return true;
            }
        }).count();
        System.out.println(wrong + " of " + inputs.size() + " wrong");
    }
}
Definition · why it races

DateFormat keeps a Calendar instance in a field and uses it as scratch space during every format and parse. Two threads interleaving on that field read each other's half-set values. On a multi-core laptop the program above reported between 8,600 and 9,100 of 10,000 round trips wrong in three runs. In a real service the failure rate is low enough to pass every test and high enough to corrupt a few records a day, sometimes with an exception, sometimes with a plausible wrong date.

The classic incident is exactly that static final SimpleDateFormat in a servlet, a Spring singleton or a utility class. Fixes in order of preference: replace it with a DateTimeFormatter constant; create a new SimpleDateFormat per call; use ThreadLocal.withInitial(() -> new SimpleDateFormat(...)). Synchronizing it works but serializes every request on one lock.

java.sql.Date, Time and Timestamp

  • java.sql.Date extends java.util.Date but means an SQL DATE: the time part is supposed to be midnight in the JVM zone, toString() prints yyyy-mm-dd, and getHours() throws.
  • java.sql.Time means an SQL TIME; its date part is meaningless.
  • java.sql.Timestamp adds a separate nanos field. Its equals returns false for any non-Timestamp, while Date.equals compares milliseconds, so date.equals(ts) can be true while ts.equals(date) is false. The Javadoc itself warns that the relation is not symmetric, so never mix them in a set or map.

A migration checklist

Algorithm · migrating a legacy codebase
  1. Inventory. Search for java.util.Date, Calendar, SimpleDateFormat, java.sql.Timestamp, TimeZone.getDefault, new Date(), System.currentTimeMillis.
  2. Fix the races first. Every shared SimpleDateFormat becomes a DateTimeFormatter constant. This is a bug fix, not a refactor.
  3. Pin behaviour. Write characterization tests around DST nights, month ends, leap days and the formats you parse, before changing types.
  4. Choose types by meaning. Event time to Instant; birthday to LocalDate; "09:00 Berlin" to LocalDateTime plus ZoneId.
  5. Convert at the boundary. Where a library still demands Date, convert at the call site with the bridges; keep java.time inside.
  6. Update persistence and JSON. JDBC 4.2 getObject, Hibernate's native java.time mappings, Jackson's JavaTimeModule with timestamps-as-numbers disabled (Spring Boot configures both).
  7. Inject a Clock and ban the legacy types in new code with a static check such as Error Prone's JavaUtilDate or an ArchUnit rule.

Java 6/7 systems. ThreeTen-Backport (org.threeten:threetenbp) is a backport of JSR 310 by the same author under the package org.threeten.bp. Code written against it migrates to Java 8+ by changing imports. Joda-Time, the library that inspired JSR 310, is in maintenance mode and its own documentation recommends moving to java.time.

What breaks in production
  • Same pattern, different meaning. In SimpleDateFormat, u is the day-of-week number; in DateTimeFormatter it is the year. Copying pattern strings across is not always safe.
  • Strictness changes behaviour. Lenient SimpleDateFormat parsed "2024-02-30" as 1 March; a strict DateTimeFormatter rejects it. Inputs that "worked" for years start failing, so decide deliberately.
  • rs.getDate(...).toInstant(). Throws UnsupportedOperationException at run time; use toLocalDate().
  • Hidden Timestamps. Hibernate may hand back a Timestamp for a Date field, so entity.getCreated().equals(someDate) is false even for the same millisecond.

Regex I: Pattern, Matcher & Core Syntax

45m video50m practice

A regular expression is a small program that a backtracking engine runs against your input. Pattern is the compiled program (immutable, thread-safe, worth caching); Matcher is one run of it over one input (stateful, cheap, never shared).

Literals, metacharacters and escaping

Most characters match themselves. Fourteen are metacharacters: \ ^ $ . | ? * + ( ) [ ] { }. Precede one with a backslash to match it literally, and remember that Java string literals need their own backslash escaping, so the regex \d is written "\\d" and a literal backslash is "\\\\". Text blocks process escapes the same way.

String price = "Total: $5.00 (incl. tax)";
Matcher m = Pattern.compile("\\$(\\d+)\\.(\\d{2})").matcher(price);    // regex: \$(\d+)\.(\d{2})
if (m.find()) System.out.println(m.group(1) + " dollars " + m.group(2) + " cents");  // 5 dollars 00 cents

String quoted = Pattern.quote("(incl. tax)");                          // \Q(incl. tax)\E
System.out.println(Pattern.compile(quoted).matcher(price).find());     // true
System.out.println(Arrays.toString("a.b.c".split(".")));              // []: "." matched every character
System.out.println("cost 5".replaceAll("\\d", Matcher.quoteReplacement("$9")));  // cost $9

Replacement strings have their own two metacharacters: $n is a group reference and \ escapes. "cost 5".replaceAll("\\d", "$9") throws IndexOutOfBoundsException: No group 9. Wrap any replacement that comes from data in Matcher.quoteReplacement, and any pattern built from data in Pattern.quote.

Definition · Pattern and Matcher

Hidden compiles. Matcher: matches, lookingAt, find, and replacing

Matcher m = Pattern.compile("\\b\\w+\\b").matcher("id=42 status=OK");
System.out.println(m.matches());      // false: matches() needs the whole input
System.out.println(m.lookingAt());    // true:  lookingAt() needs a prefix
m.reset();                            // both moved the matcher's state; start over
while (m.find())                      // find(): the next match anywhere after the last one
    System.out.print(m.group() + "@" + m.start() + "-" + m.end() + " ");  // id@0-2 42@3-5 status@6-12 OK@13-15

For search-and-replace with logic, loop with appendReplacement, which copies the text before the match plus your replacement into a buffer, then appendTail for the rest. What breaks in production
  • find() for validation. Pattern.compile("\\d+").matcher("abc123").find() is true. Validate with matches() or anchor with \A…\z; ^admin$ with find() also accepts "admin\n".
  • Data in a regex or replacement. A user-supplied search term containing ( throws PatternSyntaxException; a replacement containing $ throws or substitutes a group. Quote both.
  • ASCII-only classes. "José".matches("\\w+") is false. Use \p{L} or UNICODE_CHARACTER_CLASS for human text.
  • split drops trailing empties. "a,b,,".split(",") has 2 elements, so a CSV row loses its empty last columns. Use split(",", -1).
  • Shared Matcher. A static Matcher used by two request threads corrupts both results.

Regex II: Groups, Lookaround & Catastrophic Backtracking

45m video45m practice

Groups and lookaround make regexes expressive enough to parse log lines and enforce policies. The same backtracking that makes them expressive can make one request take seconds, so every regex that touches untrusted input needs a bound.

Capturing, named and non-capturing groups

Definition · group numbering

Each ( opens a capturing group, numbered 1, 2, 3… by the position of its opening parenthesis, left to right; group 0 is the whole match and groupCount() excludes it. A group that did not take part in the match returns null. A group inside a repetition keeps only its last iteration: (\w)+ on "abc" leaves group 1 = "c". (?<name>…) captures and also gets a number; (?:…) groups without capturing, so it does not shift the numbers and costs less.

Pattern date = Pattern.compile("(?<year>\\d{4})-(?<month>\\d{2})-(?<day>\\d{2})");
Matcher m = date.matcher("due 2024-03-15");
if (m.find()) System.out.println(m.group("month") + " " + m.group(2) + " " + m.groupCount());   // 03 03 3
System.out.println(date.matcher("due 2024-03-15").replaceAll("${day}/${month}/${year}"));     // due 15/03/2024

Matcher opt = Pattern.compile("(\\d+)(?:\\.(\\d+))?").matcher("42");
opt.matches();
System.out.println(opt.group(2));                                    // null: the optional part was absent

Backreferences and lookaround

A backreference \1 (or \k<name>) matches the exact text a group captured, so \b(\w+)\s+\1\b finds doubled words: "this is is a test the the end" becomes "this is a test the end" with replacement $1. Lookaround assertions are zero-width: they test what follows or precedes the current position without consuming it.

  • Email. The RFC 5322 address grammar allows comments and quoted local parts; a regex that implements it is enormous and still cannot say whether the mailbox exists. Check the rough shape ([^@\s]+@[^@\s]+\.[^@\s]+) and send a confirmation email.
  • URLs. Parse with java.net.URI and check getScheme() and getHost(); regex URL validators are a common source of both bypasses and ReDoS.
  • IP addresses. The IPv4 pattern above is fine. For IPv6 use a library such as Guava's InetAddresses; avoid InetAddress.getByName for validation, since it may do a DNS lookup.
  • Password policy. The lookahead trick works, but NIST SP 800-63B advises against composition rules; prefer a minimum length and a check against breached passwords.

ReDoS: catastrophic backtracking

The JDK's engine is a backtracking matcher, and recent JDKs memoize some simple shapes: on JDK 21, (a+)+$ fails instantly on 30 "a"s. Do not rely on that. A backreference disables the optimisation, and polynomial cases were never covered. Measured once on a laptop with JDK 21:

PatternInputTime
^(a+)+\1$18 / 22 / 26 "a" + "!"17 ms / 235 ms / 3.9 s
^[\s‌]+|[\s‌]+$"x" + 20,000 spaces + "x"5.3 s
.*.*=.*1,000 / 2,000 chars, no "="2.4 s / 14 s

The second row is the whitespace-trimming regex behind Stack Overflow's July 2016 outage, triggered by a post containing about 20,000 consecutive spaces. Cloudflare's global outage in July 2019 came from a WAF rule containing .*(?:.*=.*). Both took down systems with no attacker involved.

Defences
  • Remove ambiguity. Each character should be matchable in only one way: a+$ not (a+)+$; [^=]*= not .*=. Possessive quantifiers a++ and atomic groups (?>a+) discard backtracking points.
  • Mind the outer scan. find() retries at every start position, so even [\s]++$ stays quadratic on 20,000 spaces (1.5 s). Start matches only at a run's beginning, (?<!\s)\s+$ (14 ms), or skip regex: String.strip() takes microseconds.
  • Bound the input. Reject fields longer than they can legitimately be before matching.
  • Bound the time. java.util.regex has no timeout and ignores interrupts, but it reads input through CharSequence.charAt, which you can make check a deadline (below).
  • Untrusted patterns. If users supply the regex, use a linear-time engine such as RE2/J, which gives up backreferences and lookaround in exchange for a guarantee.
record Deadline(CharSequence text, long deadlineNanos) implements CharSequence {
    @Override public char charAt(int i) {
        if (System.nanoTime() > deadlineNanos) throw new IllegalStateException("regex took too long");
        return text.charAt(i);
    }
    @Override public int length() { return text.length(); }
    @Override public CharSequence subSequence(int s, int e) { return new Deadline(text.subSequence(s, e), deadlineNanos); }
    @Override public String toString() { return text.toString(); }
}
// Pattern.compile("^(a+)+\\1$").matcher(new Deadline(input, System.nanoTime() + 100_000_000L)).find()
// throws after about 100 ms instead of running for hours

When to stop and write a parser

Regex describes regular languages: flat sequences. Reach for a real parser when the input nests (JSON, HTML, arithmetic, balanced brackets), when the regex needs comments to be understood, when users need error messages better than "no match", or when you need a guaranteed running time. Use the existing parser where one exists (Jackson, jsoup, java.net.URI, DateTimeFormatter); otherwise a small recursive-descent parser is usually 50 lines of plain, debuggable Java.

What breaks in production
  • A validation regex as an attack surface. One request with a crafted 30-character field pins a CPU core; a few hundred pin the cluster.
  • "It was fast in the test." Catastrophic cases only appear on inputs that almost match. Test with long near-misses, not only valid and obviously invalid strings.
  • Group numbers shifting. Adding a group in the middle renumbers everything after it. Use named groups in anything that lives longer than a day.

Annotations: Built-in & Meta-Annotations

35m video35m practice

An annotation is data attached to a declaration or a type. It does nothing by itself; its effect comes entirely from whichever tool reads it (the compiler, an annotation processor, or a framework using reflection), and meta-annotations decide which of those tools can see it.

Metadata, not behaviour

Definition · annotation

An annotation interface is declared with @interface and implicitly extends java.lang.annotation.Annotation. Writing @Transactional on a method stores a marker (plus element values) in the class file or source; nothing in the JVM acts on it. Spring acts on @Transactional because it reflects over your beans and wraps them in proxies (L117). Without a reader, an annotation is a comment the compiler type-checks.

There are three kinds of reader. javac enforces a few built-ins. Annotation processors run inside javac and can generate code (L115). Run-time reflection (getAnnotation) is how JPA, Spring, Jackson and JUnit discover what to do.

The built-in annotations

  • @Deprecated gained since and forRemoval in Java 9.   • @SafeVarargs promises that a generic varargs method does not store into or expose its T[], which silences the heap-pollution warning at every call site (Item 32). It is only allowed where the method cannot be overridden.

Nullability annotations

Java has no null-safe types, so the ecosystem uses annotations that IDEs and static analysers check. Several incompatible families exist:

  • JSpecify (org.jspecify.annotations, 1.0 in 2024): @Nullable and @NonNull as TYPE_USE annotations, plus @NullMarked, which makes every unannotated type in a package, class or module non-null by default. It was designed by a group of vendors including Google, JetBrains, Uber and the Spring team; Spring Framework 7 adopted it, IntelliJ and Kotlin understand it, and NullAway enforces it at compile time.
  • JetBrains (org.jetbrains.annotations.@Nullable/@NotNull): IntelliJ's own, widely used in older code.
  • Jakarta (jakarta.annotation.Nullable/Nonnull) and the dormant JSR 305 javax.annotation set, still found in many libraries.
// package-info.java

What breaks in production
  • Forgotten @Retention(RUNTIME). The custom annotation compiles, the framework's getAnnotation returns null, and the feature silently does nothing.
  • Expecting @Inherited on interfaces. An annotation on an interface or an interface method is invisible to plain reflection on the implementing class. Spring searches interfaces and meta-annotations with its own MergedAnnotations API; your code using getAnnotation does not.
  • Ignored removal warnings. SecurityManager was deprecated for removal in Java 17 and permanently disabled in 24; Thread.stop throws UnsupportedOperationException since 20. Treat removal warnings as upgrade blockers.
  • Blanket suppression. @SuppressWarnings("all") on a class hides the next real unchecked cast as well.

Custom Annotations & Annotation Processors

A custom annotation is a typed configuration slot. Read it with reflection at run time and you have the core of Bean Validation; read it with an annotation processor at compile time and you have Lombok, MapStruct and Spring Boot's configuration metadata.

Declaring an annotation

import java.lang.annotation.*;

enum Severity { WARN, ERROR }

@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})

    String value();                                        // named "value": enables @Rule("...")
    Severity severity() default Severity.ERROR;            // enum element with a default

Definition · element rules

Elements are declared like no-argument methods with no throws clause and no type parameters. Their types may only be primitives, String, Class (optionally bounded), enums, other annotation types, or one-dimensional arrays of these. Defaults must be compile-time constants, and null is never allowed, which is why many libraries use sentinel defaults such as "" or Integer.MAX_VALUE. If the only element you set is called value, you may omit value =; a single-element array may omit its braces. An annotation with no elements is a marker.

Repetition works as in L114: mark the annotation @Repeatable(Rules.class), declare @interface Rules { Rule[] value(); } with compatible meta-annotations, and read the copies with getAnnotationsByType(Rule.class).

Reading annotations at run time

AnnotatedElement (implemented by Class, Field, Method, Constructor, Parameter, RecordComponent) offers isAnnotationPresent, getAnnotation, getAnnotationsByType and Declared variants. What you get back is a JDK-generated proxy implementing the annotation interface; call its element methods to read values. Annotations on a record component propagate to the field, accessor or constructor parameter that their @Target allows.

import java.lang.annotation.*;
import java.lang.reflect.Field;
import java.util.*;

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.FIELD)

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.FIELD)

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.FIELD)

record SignUp(@NotBlank String name,
              @Size(min = 8, max = 64) String password,

final class Validator {
    static List<String> validate(Object target) {
        List<String> errors = new ArrayList<>();
        for (Field f : target.getClass().getDeclaredFields()) {
            f.setAccessible(true);                                  // our own class, same module
            Object v;
            try { v = f.get(target); } catch (IllegalAccessException e) { throw new IllegalStateException(e); }
            if (f.getAnnotation(NotBlank.class) instanceof NotBlank nb && (v == null || v.toString().isBlank()))
                errors.add(f.getName() + " " + nb.message());
            if (f.getAnnotation(Size.class) instanceof Size s && v instanceof CharSequence cs
                    && (cs.length() < s.min() || cs.length() > s.max()))
                errors.add(f.getName() + " length must be " + s.min() + ".." + s.max());
            if (f.getAnnotation(OneOf.class) instanceof OneOf one && !Arrays.asList(one.value()).contains(v))
                errors.add(f.getName() + " must be one of " + Arrays.toString(one.value()));
        }
        return errors;
    }
}

@SupportedAnnotationTypes("com.example.fields.GenerateFields")
public class FieldsProcessor extends AbstractProcessor {
    @Override public SourceVersion getSupportedSourceVersion() { return SourceVersion.latestSupported(); }

    @Override
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment round) {
        for (Element e : round.getElementsAnnotatedWith(GenerateFields.class)) {
            if (!(e instanceof TypeElement type) || type.getKind() != ElementKind.RECORD) {
                processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR, "@GenerateFields needs a record", e);
                continue;                                          // a compile error pointing at e
            }
            String pkg = processingEnv.getElementUtils().getPackageOf(type).getQualifiedName().toString();
            String name = type.getSimpleName() + "Fields";
            try (var out = new PrintWriter(processingEnv.getFiler().createSourceFile(pkg + "." + name, type).openWriter())) {
                out.println("package " + pkg + ";");
                out.println("public final class " + name + " {");
                out.println("    private " + name + "() {}");
                for (RecordComponentElement c : type.getRecordComponents())
                    out.printf("    public static final String %S = \"%s\";%n", c.getSimpleName(), c.getSimpleName());
                out.println("}");
            } catch (IOException ex) {
                processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR, ex.toString(), e);
            }
        }
        return true;                                               // these annotations are claimed
    }
}

A processor works on javax.lang.model elements (TypeElement, ExecutableElement, VariableElement) and TypeMirrors: the compiler's view of source code, because there are no Class objects yet. Messager reports errors against an element so they look like compiler errors in the IDE; Filer creates sources, classes and resources. Package a processor with a META-INF/services/javax.annotation.processing.Processor file and put it on the processor path (Maven's annotationProcessorPaths). Since JDK 23, javac no longer runs processors it merely happens to find on the class path; configure them explicitly or pass -proc:full.

This is how Lombok, MapStruct and Spring metadata work

  • MapStruct is a standard processor: for each @Mapper interface it writes an ordinary OrderMapperImpl.java that you can open in target/generated-sources/annotations and debug.
  • Spring Boot's spring-boot-configuration-processor reads @ConfigurationProperties classes and writes META-INF/spring-configuration-metadata.json through Filer.createResource; IDEs use it to autocomplete application.yml. Hibernate's JPA metamodel generator (Order_) and Dagger work the same way.
  • Lombok is the exception. The processor API cannot modify existing classes, so Lombok uses internal javac APIs to rewrite the syntax tree of the class being compiled, adding getters and constructors in place. That is why it needs updates for new JDK releases and why its generated code never appears as a source file.
What breaks in production
  • Processor silently not running. No generated class and a "cannot find symbol CustomerFields" error after a JDK or build-plugin upgrade: the processor is not on the processor path, or implicit discovery is off.
  • Reflection on every request. A validator that calls getDeclaredFields and getAnnotation per object per call spends most of its time rediscovering metadata. Cache it per class.
  • Wrong retention for the reader. Processors can read SOURCE annotations; reflection needs RUNTIME. Pick the shortest retention that your reader can see.

Definition · the reflective call contract
  • Field.get(obj) and set(obj, value) box primitives (typed variants such as getLong avoid it); pass null as obj for static members.

A tiny dependency-injection container

final class TinyContainer {
    private final Map<Class<?>, Class<?>> bindings = new HashMap<>();
    private final Map<Class<?>, Object> singletons = new HashMap<>();
    private final Deque<Class<?>> resolving = new ArrayDeque<>();

    <T> TinyContainer bind(Class<T> type, Class<? extends T> impl) { bindings.put(type, impl); return this; }
    <T> TinyContainer instance(Class<T> type, T value) { singletons.put(type, value); return this; }

    <T> T get(Class<T> type) {
        Object existing = singletons.get(type);
        if (existing != null) return type.cast(existing);
        if (resolving.contains(type))
            throw new IllegalStateException("cycle: " + resolving.reversed() + " -> " + type.getSimpleName());
        Class<?> impl = bindings.getOrDefault(type, type);
        if (impl.isInterface() || Modifier.isAbstract(impl.getModifiers()))
            throw new IllegalStateException("no binding for " + type.getName());
        Constructor<?>[] ctors = impl.getConstructors();
        if (ctors.length != 1) throw new IllegalStateException(impl.getName() + " needs one public constructor");
        resolving.push(type);
        try {
            Object[] args = Arrays.stream(ctors[0].getParameterTypes()).map(this::get).toArray();  // recurse
            T bean = type.cast(ctors[0].newInstance(args));
            singletons.put(type, bean);
            return bean;
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException("cannot create " + impl.getName(), e);
        } finally {
            resolving.pop();
        }
    }
}

Reflection II: setAccessible, Proxies, MethodHandles & Performance

45m video40m practice

Frameworks use reflection for three things: reaching members they should not see, putting a proxy in front of your objects, and calling methods chosen at run time. Since Java 17 the first needs explicit permission, the second is how Spring adds transactions, and the third can be made nearly as fast as a direct call.

setAccessible and strong encapsulation

Field value = String.class.getDeclaredField("value");

Definition · deep reflection

setAccessible(true) suppresses Java's access checks for one member. Since the module system (L118), it only succeeds if the member's package is open to the caller's module; otherwise it throws InaccessibleObjectException. Java 9 allowed illegal access to JDK internals with a warning, JDK 16 denied it by default (JEP 396), and JDK 17 removed the escape hatch entirely (JEP 403): JDK internals are strongly encapsulated. Your own classpath code is all in one unnamed module, so reflecting on your own private members still works.

$ java --add-opens java.base/java.lang=ALL-UNNAMED -jar app.jar    # open one JDK package to classpath code
# or in an executable JAR's META-INF/MANIFEST.MF:
Add-Opens: java.base/java.lang java.base/java.util

Libraries that serialize arbitrary objects, mock classes or patch bytecode used to read JDK internals freely; on 17+ they use supported APIs or document the --add-opens flags they need. Treat each flag as owned technical debt: a dependency on internals that may change in any release. --add-exports is weaker: it exposes the public types of a non-exported package, not private members.

JDK dynamic proxies

final class Timing {
    @SuppressWarnings("unchecked")
    static <T> T wrap(T target, Class<T> iface) {
        InvocationHandler h = (proxy, method, args) -> {
            long t0 = System.nanoTime();
            try {
                return method.invoke(target, args);
            } catch (InvocationTargetException e) {
                throw e.getCause();                    // rethrow the real exception, not the wrapper
            } finally {
                System.out.printf("%s.%s took %d us%n", iface.getSimpleName(), method.getName(),
                        (System.nanoTime() - t0) / 1_000);
            }
        };
        return (T) Proxy.newProxyInstance(iface.getClassLoader(), new Class<?>[]{iface}, h);
    }
}

Limitations and CGLIB. JDK proxies only implement interfaces: they cannot stand in for a class, and the proxy is not an instance of the target's class. Libraries such as CGLIB and ByteBuddy instead generate a subclass at run time and override each method, so they can proxy classes, but not final classes or final/private methods. Spring uses a JDK proxy when you ask it to proxy interfaces and a CGLIB subclass otherwise; Spring Boot defaults to class-based proxies. The original CGLIB project is unmaintained, and Spring ships its own repackaged copy inside spring-core.

MethodHandle and VarHandle

A MethodHandle is a typed, directly executable reference to a method, constructor or field, created through a MethodHandles.Lookup. Access is checked once, when the handle is looked up, not on every call. invokeExact requires the call site's static types to match the handle's MethodType exactly (casting the result to Object instead of String throws WrongMethodTypeException: handle's method type (Person)String but found (Person)Object); invoke adapts types at some cost. A VarHandle (Java 9) does the same for fields and array elements, adding memory-ordering modes (plain, opaque, acquire/release, volatile) and atomic operations. It is the supported replacement for sun.misc.Unsafe and AtomicIntegerFieldUpdater.

final class Counter {
    private volatile int count;
    private static final VarHandle COUNT;
    static {
        try {
            COUNT = MethodHandles.lookup().findVarHandle(Counter.class, "count", int.class);
        } catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
    }
    int increment() { return (int) COUNT.getAndAdd(this, 1) + 1; }      // atomic, like AtomicInteger
    boolean resetIf(int expected) { return COUNT.compareAndSet(this, expected, 0); }
}

static {
    try {
        LENGTH = MethodHandles.lookup().findVirtual(String.class, "length", MethodType.methodType(int.class));

LambdaMetafactory: a lambda for a method found at run time

Lambdas compile to an invokedynamic instruction bootstrapped by LambdaMetafactory.metafactory. Calling it yourself turns a method found at run time into an ordinary functional-interface instance that the JIT treats like any lambda: useful when the target is not a constant, such as a getter chosen per CSV column.

record Person(String name) {}

static Function<Person, String> getterFor(String accessor) throws Throwable {
    MethodHandles.Lookup lookup = MethodHandles.lookup();
    MethodHandle getter = lookup.findVirtual(Person.class, accessor, MethodType.methodType(String.class));
    CallSite site = LambdaMetafactory.metafactory(lookup,
            "apply",                                               // the interface method to implement
            MethodType.methodType(Function.class),                 // factory type: () -> Function
            MethodType.methodType(Object.class, Object.class),     // erased signature of Function.apply
            getter,                                                // the implementation
            MethodType.methodType(String.class, Person.class));    // the specialized signature
    @SuppressWarnings("unchecked")
    Function<Person, String> f = (Function<Person, String>) site.getTarget().invokeExact();
    return f;                                                      // getterFor("name").apply(p)
}

Startup and native images

Reflection's bigger cost is often at startup: scanning the classpath, loading classes and reading annotations so a framework can wire beans. What breaks in production
  • JDK upgrade, then InaccessibleObjectException. A library that reached into JDK internals worked on 11 and fails on 17. Upgrade the library first; use --add-opens only as a documented stopgap.
  • Self-invocation. A method calls this.save(), which is annotated @Transactional: no proxy, no transaction, no error.
  • Swallowed causes. A proxy handler that lets InvocationTargetException escape turns every checked exception into UndeclaredThrowableException for the caller.
  • Missing native-image metadata. Works on the JVM, then fails at run time in the native binary on the one code path that reflects on an unregistered class.

The Java Module System (JPMS)

40m video40m practice

A module is a named set of packages that declares what it needs and what it shares. The JVM checks those declarations at startup and enforces them at run time, turning classpath accidents into startup errors and public into "public to the modules I chose".

What the classpath gets wrong

  • Classpath hell. The classpath is a flat list searched in order. Two versions of a library both "load", the first one wins class by class, and the mismatch surfaces as NoSuchMethodError deep in production. A missing JAR is only noticed when some code path first touches it (NoClassDefFoundError).
  • Split packages. The same package can come from several JARs and is silently merged.
  • No real encapsulation. public means public to everyone, so "internal" packages such as sun.misc or com.foo.impl become de facto APIs that can never change.

The Java Platform Module System (JSR 376, Project Jigsaw, Java 9) addresses all three with reliable configuration (every requires must be satisfied and no package may live in two modules, checked at startup) and strong encapsulation (only exported packages are accessible, and only opened packages allow deep reflection). It also split the JDK itself into about 70 modules, which is what makes jlink possible.

module-info.java

module com.acme.orders {
    requires transitive com.acme.money;      // our API returns Money, so our users must read it too
    requires java.sql;
    requires static org.jspecify;            // needed to compile, optional at run time
    exports com.acme.orders.api;             // the only package other modules can use
    exports com.acme.orders.spi to com.acme.orders.postgres;                 // qualified export
    opens com.acme.orders.internal.model to com.fasterxml.jackson.databind;  // deep reflection, one framework
    uses com.acme.orders.spi.OrderStore;     // consumes a service through ServiceLoader
}

    requires com.acme.orders;

Named, automatic and unnamed modules; module path vs classpath

Definition · three kinds of module
  • Named module: a JAR or directory with a module-info.class, placed on the module path.
  • Automatic module: a plain JAR placed on the module path. Its name comes from the Automatic-Module-Name manifest entry, or else is derived from the file name; it requires every other module and exports and opens all its packages. It is the migration bridge for libraries that are not modularized yet.
  • Unnamed module: everything on the classpath. It reads all modules and exports everything, but named modules cannot requires it. This is how pre-module code keeps working unchanged.

The module path (--module-path, -p) is resolved as a graph, starting from the root module named with --module (-m) or added with --add-modules; the classpath is still searched linearly. Both can be used at once.

Compiling, running, jdeps and jlink

jlink builds a runtime image containing only the modules you list plus their dependencies. On Windows with JDK 21, java.base alone came to about 30 MB and the four modules above to about 35 MB, against roughly 330 MB for the full JDK. It works for classpath applications too: let jdeps --print-module-deps list the JDK modules your JARs use, link those, and run your app on the classpath of the slim runtime. In a multi-stage Dockerfile that means running jdeps and jlink in a JDK build stage and copying only the generated runtime into a slim base image (Phase 22). For a Spring Boot fat JAR, unpack it first so jdeps can see the nested library JARs.

jlink does not follow services

Linking with --add-modules com.acme.app produced an image that failed at run time with "no OrderStore provider": jlink resolves requires but not uses/provides. Add the provider module explicitly, or pass --bind-services (which can pull in many JDK modules).

Why Spring apps mostly stay on the classpath

A typical Spring Boot service runs on the classpath, and that is a reasonable choice. Boot's executable JAR nests library JARs, which the module path cannot load; many dependencies are still automatic modules or have no module descriptor; the framework reflects into your packages, so you would need opens nearly everywhere; and an application deployed as one unit gains little from hiding packages from itself. Modules pay off when you publish a library and want a small, enforced API; in a large codebase where boundaries must not erode (though Spring Modulith and ArchUnit enforce package rules without JPMS); and indirectly, through jlink-trimmed runtimes, which any app can use.

What breaks in production
  • Split packages on the module path. Two JARs containing javax.annotation (a common legacy clash) make startup fail with a ResolutionException ("… reads package … from both …"). On the classpath the same setup "works" until the wrong class is loaded.
  • Reflection into a non-opened package. A framework fails with InaccessibleObjectException as soon as your code moves to a named module. Add opens for the packages it maps, to that framework only.
  • Missing modules in a jlink image. Code that works under the full JDK fails with ClassNotFoundException for java.sql.Timestamp or a JNDI class. Re-run jdeps after adding dependencies, and smoke-test the image itself.
  • Unstable automatic module names. A name derived from a file name changes when the JAR is renamed. Libraries should set Automatic-Module-Name before they ship a real module-info.

Definition · local variable type inference

var (Java 10) declares a local variable whose static type is the type of its initializer. It is still statically typed: nothing is dynamic. It works for locals with an initializer, for and enhanced-for variables, try-with-resources resources and (Java 11) lambda parameters, all or none. It is a reserved type name, not a keyword, so a variable can still be called var. Use it when the type is evident from the right-hand side or unimportant to the reader; spell the type out when the initializer is a method call whose result type matters, such as var result = service.process(input).

Pattern matching for instanceof, and flow scoping

static String describe(Object o) {
    if (o instanceof String s && !s.isBlank()) return "text of length " + s.length();   // s in scope after &&
    if (!(o instanceof Integer i)) return "something else";                             // exits when no match...
    return "int " + (i + 1);                                                             // ...so i is in scope here
}

A type pattern Integer i tests and binds at once (Java 16). The binding is in scope exactly where the compiler can prove the match succeeded: after &&, inside the if, or after an if (!(… instanceof …)) that returns or throws. It is not in scope on the right of ||.

switch patterns, guards, record patterns and _

import java.math.BigDecimal;

record Customer(String name, String tier) {}
record Order(Customer customer, BigDecimal total) {}

static String label(Object o) {
    return switch (o) {
        case null -> "nothing";                                       // without it, a null selector throws NPE
        case Order(Customer(var name, _), var total)                  // nested record pattern, _ ignores tier
                when total.compareTo(BigDecimal.valueOf(1000)) >= 0 -> "big order from " + name;
        case Order(Customer(var name, var tier), var total) -> name + " (" + tier + "): " + total;
        case String s -> "text: " + s;
        default -> "unknown " + o.getClass().getSimpleName();
    };
}
// label(new Order(new Customer("Ana", "PRO"), new BigDecimal("1500")))  -> big order from Ana
// label(new Order(new Customer("Bo", "FREE"), new BigDecimal("20.50"))) -> Bo (FREE): 20.50
  • Record patterns (Java 21) deconstruct a record through its accessors and nest to any depth; components can be typed patterns or var.
  • Guards (when) add a boolean condition. A guarded case does not count towards exhaustiveness, and cases are tried top to bottom: the compiler rejects a case that an earlier unguarded case dominates, such as case CharSequence c before case String s.
  • Unnamed patterns and variables _ (preview in 21, final in Java 22) mark components and variables you do not use: catch (NumberFormatException _), for (var _ : items), map.forEach((_, v) -> …). On a Java 21 baseline the code above needs --enable-preview, or a named variable instead of _.

Sealed hierarchies and exhaustive switches: replacing a visitor

The visitor pattern exists because Java once had no way to switch on a type safely. Each node class implements accept, each operation is a visitor class, and every call bounces twice:

interface Node { <R> R accept(NodeVisitor<R> v); }
interface NodeVisitor<R> { R visitLit(Lit n); R visitPlus(Plus p); }
final class Lit implements Node {
    final int value;
    Lit(int value) { this.value = value; }
    public <R> R accept(NodeVisitor<R> v) { return v.visitLit(this); }
}
final class Plus implements Node {
    final Node left, right;
    Plus(Node left, Node right) { this.left = left; this.right = right; }
    public <R> R accept(NodeVisitor<R> v) { return v.visitPlus(this); }
}
final class EvalVisitor implements NodeVisitor<Integer> {
    public Integer visitLit(Lit n) { return n.value; }
    public Integer visitPlus(Plus p) { return p.left.accept(this) + p.right.accept(this); }
}
sealed interface Expr permits Num, Add, Mul, Neg {}
record Num(int value) implements Expr {}
record Add(Expr left, Expr right) implements Expr {}
record Mul(Expr left, Expr right) implements Expr {}
record Neg(Expr operand) implements Expr {}

static int eval(Expr e) {
    return switch (e) {                                    // exhaustive over the sealed type: no default
        case Num(var v) -> v;
        case Add(var l, var r) -> eval(l) + eval(r);
        case Mul(var l, var r) -> eval(l) * eval(r);
        case Neg(var x) -> -eval(x);
    };
}

static Expr simplify(Expr e) {
    Expr s = switch (e) {                                  // children first
        case Add(var l, var r) -> new Add(simplify(l), simplify(r));
        case Mul(var l, var r) -> new Mul(simplify(l), simplify(r));
        case Neg(var x) -> new Neg(simplify(x));
        case Num n -> n;
    };
    return switch (s) {                                    // then one rewrite rule at this node
        case Add(var l, Num(var n)) when n == 0 -> l;      // x + 0 = x
        case Mul(var l, Num(var n)) when n == 1 -> l;      // x * 1 = x
        case Mul(Num(var n), _) when n == 0 -> new Num(0); // 0 * x = 0   (_ needs Java 22+)
        case Neg(Neg(var x)) -> x;                         // --x = x
        default -> s;                                      // a rule table: "no rule applies" is a real case
    };
}
// simplify(new Add(new Mul(new Num(7), new Num(1)), new Neg(new Neg(new Num(0)))))  ->  Num[value=7]

Adding record Div(Expr l, Expr r) implements Expr (and listing it in permits) makes eval and the first switch of simplify fail to compile until you handle it: that error list is your to-do list. If a client compiled against the old hierarchy meets a Div at run time, the compiler-inserted default throws MatchException. Nested patterns with guards make rewrite rules such as the ones above read like their algebraic definitions, which a visitor cannot express without manual instanceof chains.

String sql = """

        FROM orders o

String oneLine = """
        A long message that we \
        want on a single line.\s
        """;                                   // \ joins lines, \s keeps one trailing space

A text block (Java 15) starts with """ and a line break. The compiler strips incidental indentation, measured from the least-indented line including the closing delimiter, removes trailing spaces, normalises line endings to \n and then processes escapes. It is not a raw string: a regex inside one still needs \\d.

What breaks in production
  • A default in a sealed switch. It compiles today and silently swallows the next subtype tomorrow. Leave it out of "one case per type" switches; use it only for rule tables like simplify's second switch.
  • SQL built with formatted(). A text block makes the query readable, not safe: interpolating user input is SQL injection.
  • var plus diamond. var ids = new ArrayList<>() is an ArrayList<Object> that accepts anything.
  • Baseline mismatch. _ compiles on 22+ and fails on a 21 build server; decide the baseline (L120) before using new syntax.

  3. Model sealed interface Payment permits Card, Iban, Wallet as records and write fee(Payment) with nested patterns and guards (for example card payments over 1,000 cost more).

Choosing a baseline and migrating

What to adopt at each LTS
  • 17 is the floor for Spring Boot 3 and Spring Framework 6. Adopt records for DTOs and value objects, sealed interfaces for closed domains, switch expressions, text blocks, instanceof patterns and Stream.toList(). Clean up every --add-opens left over from 11.
  • 21 adds the big runtime win: virtual threads for blocking I/O-bound services (Phase 5), with care around synchronized pinning and ThreadLocal-heavy libraries until 24. Use switch patterns with record patterns, and sequenced collections. Generational ZGC for large heaps.
  • 25 removes the pinning caveat, finalizes gatherers, scoped values (a better ThreadLocal for virtual threads), module imports and compact source files, and adds compact object headers and AOT caches that cut memory and startup.
Algorithm · upgrading a service's JDK
  1. Pick the newest LTS that your framework, libraries, build plugins, base image, APM agent and cloud runtime all support. Libraries that generate bytecode (ByteBuddy, Mockito, Lombok, JaCoCo) are the usual blockers; upgrade them first.
  2. Scan: jdeps --jdk-internals for internal APIs and jdeprscan --release 25 for deprecated and removed ones.
  3. Build with the new JDK but keep --release (Maven's maven.compiler.release) at the old version; run the full test suite and a load test on the new runtime.
  4. Read the release notes for behaviour changes that tests miss: removed Java EE modules (11), strong encapsulation (16–17), UTF-8 default (18), CLDR locale data, GC defaults, annotation processing no longer implicit (23).
  5. Switch the runtime in production, watch GC, memory and latency dashboards, then raise --release and start using the new language features.
  6. Never ship --enable-preview to production: preview APIs can change or disappear in the next release.

What breaks in production
  • Compiling for the wrong target. -source 17 -target 17 on JDK 21 still links against 21's APIs, so a getFirst() call compiles and fails with NoSuchMethodError on a 17 runtime. --release 17 prevents it.
  • Agents and plugins first. The JDK upgrade "breaks" the service because an old APM agent, Lombok or ByteBuddy cannot handle the new class-file version.
  • Non-LTS in production without a plan. A feature release stops getting updates after six months; staying on it means running without security fixes.
