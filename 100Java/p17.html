Phase 17 · Days 335–356 · Lessons 335–356

Spring Security

Phase 17 builds Spring Security from the filter chain up: authentication with sessions, passwords, JWTs and OAuth2/OpenID Connect, authorization from URL rules down to object ownership, and the browser- and network-facing defences (CSRF, CORS, headers, TLS, rate limits) that keep a Java backend out of the OWASP lists. It relies on the web, data and transaction phases before it, and the identity, token and audit patterns it establishes are reused by the microservices and cloud phases that follow.

By the end of this phase you can

  • Trace any request through FilterChainProxy, name the filter that authenticates or rejects it, and configure multiple SecurityFilterChain beans with the lambda DSL.
  • Store passwords with Argon2id or BCrypt behind DelegatingPasswordEncoder, and run form login, remember-me and sessions without fixation or CSRF holes.
  • Issue and validate JWTs correctly, and implement refresh-token rotation with reuse detection and logout everywhere.
  • Integrate OAuth2 and OIDC as a client (social login), a resource server, and an authorization server, including Keycloak.
  • Design RBAC with role hierarchies and method security, and enforce object-level authorization in queries rather than after them.
  • Configure CORS, security headers, a Content Security Policy, forwarded headers, rate limits, login throttling and audit logging.
  • Ship an auth service that passes an OWASP-based release checklist, with secrets in a manager and sensitive columns encrypted.

L335 · DAY 335

Security Fundamentals & the Threat Model

45m video35m practice

Security work starts with vocabulary and an attacker's map, not with a framework: who is the caller, what may they do, what is recorded, and where does untrusted data cross into trusted code. Every Spring Security feature in this phase is a control for one entry on that map.

Authentication, authorization, accounting

Definition

Identification is claiming an identity ("I am alice"). Authentication proves the claim with credentials. Authorization decides what the authenticated principal may do with which resource. Accounting (audit) records who did what, when, from where, and with what outcome. Credentials come from three factor categories: knowledge (password, PIN), possession (phone with a TOTP app, hardware security key) and inherence (fingerprint, face). Multi-factor authentication means factors from different categories; a password plus a security question is still one factor. Passkeys (WebAuthn) are possession-based and resist phishing because the browser binds the signature to the site's origin.

The distinction matters in code: a 401 means "I do not know who you are" (authentication missing or failed) and a 403 means "I know who you are and the answer is no" (authorization). Mixing them leaks information and confuses clients.

Sessions vs tokens, honestly

For a browser talking to its own backend, a session cookie is usually simpler and safer. Tokens shine when many independent services or third parties must verify identity without calling a central store. Lessons L341, L346 and L348 develop both.

What you are protecting

Confidentiality: only authorized parties read the data (TLS, access control, encryption at rest). Integrity: data and code are not modified undetected (signatures, MACs, constraints, authorization on writes). Availability: the service keeps answering (rate limits, timeouts, capacity). Non-repudiation: an actor cannot credibly deny an action, which needs strong authentication plus tamper-evident audit records, or a digital signature only the actor's key could produce.

The attacker's view: threat modeling with STRIDE

Draw the data flow: actors, processes, data stores, and the trust boundaries where data passes from less-trusted to more-trusted code. Every boundary crossing is attack surface. Then walk each element through STRIDE:

The attacks this phase defends against

  • Credential stuffing (leaked passwords replayed at scale) and brute force: breached-password checks, rate limits, lockout (L339, L355).
  • Session fixation and CSRF: new session id on login, synchronizer tokens, SameSite (L341, L342).
  • XSS: output encoding, CSP, keeping tokens out of JavaScript-readable storage (L348, L354).
  • SQL injection: parameterized queries only (L356).
  • IDOR / broken object-level authorization and privilege escalation: ownership in the query, role checks on every path (L343, L344).
  • Token theft and replay: short expiry, rotation, jti, nonces, TLS everywhere (L346, L348, L349).

Principles that outlive frameworks

Defense in depth: assume each control fails sometimes, so layer them (gateway limits, filter-chain authentication, method security, ownership in queries, database grants). Least privilege: the app's database user cannot drop tables, a service token carries only the scopes it needs. Fail securely: deny by default, and make errors deny rather than allow. Never roll your own crypto: use vetted libraries and standard protocols. Security is a cross-cutting concern like transactions: retrofitted at the end, it misses the code paths nobody remembers. Java can help you fail closed:

enum Role { ADMIN, EDITOR, VIEWER }
enum Action { READ, WRITE, DELETE }

static boolean allowed(Role role, Action action) {
    // exhaustive switch: adding a Role is a compile error here, not a silent "allow"
    return switch (role) {
        case ADMIN  -> true;
        case EDITOR -> action != Action.DELETE;
        case VIEWER -> action == Action.READ;
    };
}
What breaks in production
  • A "temporary" debug endpoint, or an actuator endpoint, left outside every security rule.
  • Authorization checked in the UI or the controller for one route but not for the bulk-export route that reads the same data.
  • Error handlers that return stack traces or "user not found" versus "wrong password", turning a login form into an account oracle.
  • A catch block in an authorization check that logs and continues, failing open.

Practice · 35 min

  1. Draw a data-flow diagram of an app you know (browser, API, database, one third party) and mark every trust boundary.
  2. Run STRIDE over each boundary crossing and list at least one threat per letter with its control.
  3. For each attack in the list above, write one sentence on how it would appear in your logs.
  4. Find one place in an existing codebase where an error path fails open, and rewrite it to fail closed.

Spring Security Architecture & The Filter Chain

50m video45m practice

Spring Security for servlet apps is an ordered list of servlet filters that runs before your controller, plus a small set of core objects (Authentication, SecurityContext, AuthenticationManager) that those filters pass around. If you can name the filter that handles a given request and the object it produces, you can debug any configuration.

What the starter changes immediately

Add spring-boot-starter-security and restart: every endpoint now answers 401 or redirects to a generated /login page; the log prints Using generated security password: … for a user named user; HTTP Basic is accepted; POST /logout exists; CSRF protection is on for unsafe methods; and responses carry security headers such as X-Content-Type-Options: nosniff and Cache-Control: no-cache, no-store. All of this comes from Boot's default SecurityFilterChain, which backs off as soon as you define your own (L337).

From the servlet container to your filters

Definition

The servlet container knows nothing about Spring beans, so Boot registers a DelegatingFilterProxy named springSecurityFilterChain as an ordinary servlet filter. It looks up the bean of that name, the FilterChainProxy, and delegates to it. FilterChainProxy holds one or more SecurityFilterChains, picks the first whose request matcher matches, and runs that chain's filters in order. It also applies the StrictHttpFirewall (rejecting encoded slashes, path traversal and other ambiguous URLs) and clears the SecurityContextHolder when the request ends.

The default chain contains these filters, in this order (some appear only when the matching feature is configured):

Order is the design: headers are written even on errors, CSRF runs before any login or logout so those are protected too, anonymous authentication runs after every real mechanism had its chance, and the exception filter wraps the authorization filter so it can catch what that throws.

The core objects

An Authentication is both the request to authenticate and the result: it carries a principal (often a UserDetails), credentials, GrantedAuthoritys and an authenticated flag; it extends java.security.Principal. A SecurityContext holds one Authentication, and the SecurityContextHolder holds the context for the current thread. AuthenticationManager has one method, authenticate; its usual implementation ProviderManager asks each AuthenticationProvider that supports the token type. DaoAuthenticationProvider gets users from a UserDetailsService, which returns UserDetails.

Changed in Spring Security 6

SecurityContextHolderFilter only loads the context; it no longer saves it automatically at the end of the request as the old SecurityContextPersistenceFilter did. Built-in login filters save explicitly. If you authenticate in your own controller, you must call securityContextRepository.saveContext(context, request, response) or the login is forgotten on the next request.

Threads: @Async and virtual threads

The default holder strategy is MODE_THREADLOCAL, so the context is invisible on any other thread. MODE_INHERITABLETHREADLOCAL copies it to child threads, but pooled threads are created once and reused, so they carry a stale or wrong user: avoid it. The correct tool is a wrapping executor that captures the caller's context per task. Virtual threads are still threads with their own thread-locals, so the same wrapping applies.

@Configuration
@EnableAsync
class AsyncSecurityConfig implements AsyncConfigurer {
    @Override
    public Executor getAsyncExecutor() {
        var pool = new ThreadPoolTaskExecutor();
        pool.setCorePoolSize(8);
        pool.initialize();
        return new DelegatingSecurityContextAsyncTaskExecutor(pool);   // copies context per task
    }

    @Bean
    Executor virtualSecured() {
        return new DelegatingSecurityContextExecutor(Executors.newVirtualThreadPerTaskExecutor());
    }
}

Debugging the chain

logging.level.org.springframework.security=DEBUG   # TRACE also logs every filter invoked

# per request at DEBUG:

What breaks in production
  • A custom login endpoint that sets the holder but never saves the context: users are "logged out" on the next request.
  • Reading SecurityContextHolder inside a CompletableFuture task and getting null, or worse, someone else's user from an inheritable thread-local.
  • Two chains where the broad one is ordered first: the narrow one never matches.

Modern Configuration: SecurityFilterChain & the Lambda DSL

45m video50m practice

In Spring Security 6 you configure security by declaring SecurityFilterChain beans built with the lambda DSL; there is no base class to extend. Each chain says which requests it owns, and inside it the authorization rules are evaluated top to bottom with the first match winning, so order is part of your security policy.

WebSecurityConfigurerAdapter is gone

The adapter was deprecated in 5.7 and removed in 6.0. Its three overrides map to beans: configure(HttpSecurity) becomes a SecurityFilterChain @Bean that receives an HttpSecurity prototype; configure(WebSecurity) becomes a WebSecurityCustomizer bean; configure(AuthenticationManagerBuilder) becomes a UserDetailsService, PasswordEncoder or AuthenticationProvider bean that Boot wires into the global AuthenticationManager. The old chained style with .and() is deprecated too; every configurer now takes a Customizer lambda, and Customizer.withDefaults() means "enable with default settings".

A realistic configuration

@Configuration
@EnableWebSecurity
class SecurityConfig {

    @Bean
    @Order(1)
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .securityMatcher("/api/**")                       // this chain owns /api/** only
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
                .requestMatchers(HttpMethod.POST, "/api/orders").hasAuthority("SCOPE_orders:write")
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable())                     // bearer tokens only, no cookies
            .cors(Customizer.withDefaults());
        return http.build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain actuator(HttpSecurity http) throws Exception {
        http
            .securityMatcher(EndpointRequest.toAnyEndpoint())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(EndpointRequest.to(HealthEndpoint.class)).permitAll()
                .anyRequest().hasRole("OPS"))
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }

    @Bean
    @Order(3)
    SecurityFilterChain web(HttpSecurity http) throws Exception {   // no securityMatcher: everything else
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(PathRequest.toStaticResources().atCommonLocations()).permitAll()
                .requestMatchers("/", "/login", "/error").permitAll()
                .anyRequest().authenticated())
            .formLogin(form -> form.loginPage("/login").permitAll())
            .logout(Customizer.withDefaults())
            .headers(h -> h.contentSecurityPolicy(csp -> csp.policyDirectives("default-src 'self'")));
        return http.build();
    }
}

The other configurers follow the same shape: .exceptionHandling(e -> e.authenticationEntryPoint(...).accessDeniedHandler(...)) (L345), .httpBasic(...) and .sessionManagement(...) (L341), .headers(...) and .cors(...) (L354).

Request matchers

requestMatchers(...) replaced antMatchers, mvcMatchers and regexMatchers. Given strings, it builds a path matcher appropriate to the app (with Spring MVC present, one that matches the way MVC maps paths); given an HttpMethod first, it also restricts the method. You can pass any RequestMatcher object:

  • AntPathRequestMatcher.antMatcher("/files/**") and RegexRequestMatcher.regexMatcher("/v[0-9]+/.*") for explicit pattern styles. Recent 6.x releases deprecate the Ant and MVC matchers in favour of PathPatternRequestMatcher, so prefer the plain string form where you can.
  • EndpointRequest.toAnyEndpoint(), EndpointRequest.to(...), excluding(...) for Actuator endpoints, independent of the configured base path.
  • PathRequest.toStaticResources().atCommonLocations() for /css/**, /js/**, /images/**, /webjars/** and the favicon.

If the application registers more than one servlet (for example the H2 console next to the dispatcher servlet), a bare string pattern is ambiguous and recent versions fail at startup asking you to choose an explicit matcher.

Order is policy

Definition · first match wins

Inside authorizeHttpRequests, rules are checked in declaration order and the first matching rule decides. Put the most specific rules first and anyRequest() last; declaring a rule after anyRequest() fails at startup. Across chains, FilterChainProxy uses the first chain (by @Order) whose securityMatcher matches, and a chain without a securityMatcher matches everything, so it must have the lowest priority.

// WRONG: the broad rule shadows the admin rule; any authenticated user reaches /admin/**
.requestMatchers("/**").authenticated()
.requestMatchers("/admin/**").hasRole("ADMIN")

// RIGHT
.requestMatchers("/admin/**").hasRole("ADMIN")
.anyRequest().authenticated()

The outcomes available on a rule are permitAll(), authenticated(), denyAll(), hasRole/hasAnyRole, hasAuthority/hasAnyAuthority, and access(AuthorizationManager) for custom logic (L343). A good default for a new endpoint is to be denied until someone writes a rule for it; ending with .anyRequest().denyAll() enforces that in strict services.

Ignoring paths versus permitAll

@Bean
WebSecurityCustomizer ignoreFavicon() {
    return web -> web.ignoring().requestMatchers("/favicon.ico");
}

web.ignoring() removes the request from Spring Security entirely: no security headers, no SecurityContext (so error pages cannot see the user), no CSRF. Spring logs a warning recommending permitAll instead, which still runs the chain but lets everyone through. Ignore only truly static, public resources, and even then permitAll is usually the safer choice.

What breaks in production
  • Copy-pasted adapter-era code mixed with a SecurityFilterChain bean: on Boot 3 it does not compile; on Boot 2 the two configurations fight.
  • A chain without securityMatcher given @Order(1): it captures every request and the API chain never runs.
  • Forgetting /error in permitAll: a 500 for an anonymous user is rendered as a 401, hiding the real error.
  • Actuator protected by the web chain's form login: monitoring gets HTML login pages instead of health JSON.

Practice · 50 min

  1. Port an adapter-based configuration (form login, two in-memory users, ignored static paths) to beans.
  2. Build the three-chain configuration above and write MockMvc tests proving which chain handles /api/orders, /actuator/health, /actuator/env and /.
  3. Introduce the wrong rule order deliberately and write the test that catches it.
  4. Compare the response headers of an ignored path and a permitAll path.

UserDetailsService, UserDetails & Custom Principals

40m video50m practice

UserDetailsService is the one-method bridge between Spring Security and your user store: given a username, return a UserDetails with the password hash, authorities and account flags. Return your own UserDetails type carrying the domain identity you need, and every controller can receive a useful principal instead of a bare username.

The UserDetails contract

Definition

UserDetails exposes getUsername(), getPassword() (the stored hash), getAuthorities(), and four flags: isAccountNonExpired, isAccountNonLocked, isCredentialsNonExpired, isEnabled. DaoAuthenticationProvider checks locked, disabled and expired-account before comparing the password, and expired-credentials after. Each failure has its own exception (LockedException, DisabledException, AccountExpiredException, CredentialsExpiredException). User.builder() builds the standard immutable implementation: User.withUsername("ana").password(hash).roles("USER").build(), where roles("USER") becomes the authority ROLE_USER.

Built-in managers: in-memory and JDBC

@Bean
UserDetailsService users(PasswordEncoder encoder) {
    return new InMemoryUserDetailsManager(
        User.withUsername("ana").password(encoder.encode("demo-pass-1")).roles("USER").build(),
        User.withUsername("ops").password(encoder.encode("demo-pass-2")).roles("USER", "OPS").build());
}

InMemoryUserDetailsManager is for demos and tests. JdbcUserDetailsManager reads a default schema (shipped as users.ddl in the Spring Security jar) and also implements create, update, delete and change-password operations:

create table users(username varchar(50) primary key, password varchar(500) not null, enabled boolean not null);
create table authorities(username varchar(50) not null references users(username),
                         authority varchar(50) not null);
create unique index ix_auth_username on authorities (username, authority);
@Bean
UserDetailsManager jdbcUsers(DataSource ds) {
    var m = new JdbcUserDetailsManager(ds);
    m.setUsersByUsernameQuery("select email, password_hash, active from app_user where email = ?");
    m.setAuthoritiesByUsernameQuery("""
        select u.email, r.name from app_user u
        join user_role ur on ur.user_id = u.id join role r on r.id = ur.role_id
        where u.email = ?""");
    return m;
}

Your own UserDetailsService and principal

Most applications already have a User entity. Map it to a principal class that carries what controllers need (id, tenant, email) and not the entity itself: entities hold lazy proxies, change over time, and do not belong serialized in an HTTP session.

public final class AppUserPrincipal implements UserDetails, CredentialsContainer {
    private final UUID id;
    private final String tenantId;
    private final String email;
    private String passwordHash;
    private final Set<GrantedAuthority> authorities;
    private final boolean enabled;
    private final boolean locked;

    public AppUserPrincipal(UUID id, String tenantId, String email, String passwordHash,
                            Set<GrantedAuthority> authorities, boolean enabled, boolean locked) {
        this.id = id; this.tenantId = tenantId; this.email = email; this.passwordHash = passwordHash;
        this.authorities = Set.copyOf(authorities); this.enabled = enabled; this.locked = locked;
    }

    static AppUserPrincipal from(UserEntity u) {
        Set<GrantedAuthority> auths = u.getRoles().stream()
            .map(r -> new SimpleGrantedAuthority("ROLE_" + r.getName()))
            .collect(Collectors.toSet());
        return new AppUserPrincipal(u.getId(), u.getTenantId(), u.getEmail(), u.getPasswordHash(),
                                    auths, u.isActive(), u.isLocked());
    }

    public UUID getId() { return id; }
    public String getTenantId() { return tenantId; }

    @Override public String getUsername() { return email; }
    @Override public String getPassword() { return passwordHash; }
    @Override public Collection<? extends GrantedAuthority> getAuthorities() { return authorities; }
    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return !locked; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled() { return enabled; }
    @Override public void eraseCredentials() { passwordHash = null; }   // called after login
}

@Service
class JpaUserDetailsService implements UserDetailsService {
    private final UserRepository users;
    JpaUserDetailsService(UserRepository users) { this.users = users; }

    @Override
    @Transactional(readOnly = true)              // roles are lazy: map them inside the transaction
    public UserDetails loadUserByUsername(String email) {
        return users.findByEmailIgnoreCase(email)
            .map(AppUserPrincipal::from)
            .orElseThrow(() -> new UsernameNotFoundException("unknown user"));
    }
}
Do not leak which accounts exist

Throw UsernameNotFoundException for an unknown user, never return null. DaoAuthenticationProvider has hideUserNotFoundExceptions = true by default, so an unknown user and a wrong password both surface as BadCredentialsException ("Bad credentials"). Keep it that way in your error messages and response times (the provider's timing defence is in L345), so the login form cannot be used to test which emails are registered.

@AuthenticationPrincipal and a @CurrentUser annotation

@EnableWebSecurity registers AuthenticationPrincipalArgumentResolver, which resolves a controller parameter annotated @AuthenticationPrincipal from Authentication.getPrincipal(). Wrap it in a meta-annotation so controllers do not depend on Spring Security types directly:

@Target({ElementType.PARAMETER, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@AuthenticationPrincipal
public @interface CurrentUser {}

@RestController
class MeController {
    @GetMapping("/me")
    Map<String, Object> me(@CurrentUser AppUserPrincipal me) {
        return Map.of("id", me.getId(), "tenant", me.getTenantId(), "email", me.getUsername());
    }

    @GetMapping("/me/id")
    UUID myId(@AuthenticationPrincipal(expression = "id") UUID id) { return id; }   // SpEL on the principal
}

If the principal is not of the declared type (for example a Jwt under a resource-server chain), the parameter is silently null; set errorOnInvalidType = true to fail loudly instead.

Which extension point, and caching

Implement UserDetailsService when authentication is "look up a stored hash and compare". Implement an AuthenticationProvider (L345) when the verification itself differs: an LDAP bind, an API key, a one-time code, or a legacy system that checks the password for you. Loading the user on every login is cheap; loading it on every request (HTTP Basic on an API, for example) is not, and DaoAuthenticationProvider accepts a UserCache. Any cache, including the copy of authorities stored in a session or a token, creates an invalidation problem: a user whose role is revoked or whose account is locked keeps access until the entry expires or they log in again. Keep TTLs short, evict on change, and for sessions expire them through the SessionRegistry (L341).

What breaks in production
  • LazyInitializationException during login because roles were mapped after the repository's transaction closed.
  • Putting the JPA entity in the session: serialization failures, or a principal frozen with last week's data.
  • A fired employee still logged in for a day because authorities live in a long session and nobody expired it.
  • @AuthenticationPrincipal AppUserPrincipal silently null on token-authenticated routes.

Practice · 50 min

  1. Start with InMemoryUserDetailsManager, then switch to JdbcUserDetailsManager with custom queries over your own tables.
  2. Replace it with the JPA-backed service and AppUserPrincipal; write /me with @CurrentUser.
  3. Test that an unknown email and a wrong password return identical responses.
  4. Lock a user while they have a session; show they keep access, then expire their session on lock.

L339 · DAY 339

Password Storage: BCrypt, Argon2 & Upgrades

40m video40m practice

Store passwords so that a stolen database is expensive to crack one password at a time: a unique salt per password, a deliberately slow and preferably memory-hard function, and a format that records the algorithm so you can raise the cost later. In Spring that means a DelegatingPasswordEncoder over Argon2id or BCrypt, plus rehash-on-login.

Why the obvious options fail

Plaintext turns any read-only leak (a backup, a SQL injection, a log) into every account, and into other sites where users reused the password. Encryption is reversible by design; the key lives near the data, so whoever steals one usually steals both. Fast hashes (MD5, SHA-1, SHA-256) are built to be fast: a single GPU computes billions per second, so an 8-character password falls quickly, and without salt, identical passwords produce identical hashes and precomputed tables work across all users.

Definition

A salt is a random value (16 bytes is typical) generated per password and stored next to the hash. It is not secret; it makes every hash unique so attackers must crack each one separately. A pepper is a secret key kept outside the database (secret manager or HSM) and mixed in, typically as an HMAC before hashing; a database-only leak then reveals nothing crackable, at the price of a key you must protect and can hardly rotate. An adaptive hash has a work factor (iterations, memory) you can raise as hardware gets faster; a memory-hard one needs a lot of RAM per guess, which blunts GPU and ASIC attacks.

The encoders

DelegatingPasswordEncoder and upgrades

DelegatingPasswordEncoder encodes new passwords with one id and verifies stored ones by reading the {id} prefix, so rows hashed with old and new algorithms coexist. PasswordEncoderFactories.createDelegatingPasswordEncoder() gives the standard map with bcrypt as the default; build your own to prefer Argon2:

@Bean
PasswordEncoder passwordEncoder() {
    Map<String, PasswordEncoder> encoders = Map.of(
        "argon2", new Argon2PasswordEncoder(16, 32, 1, 19_456, 2),   // salt, hash, parallelism, KiB, iterations
        "bcrypt", new BCryptPasswordEncoder(12));
    return new DelegatingPasswordEncoder("argon2", encoders);       // new hashes: {argon2}...
}

@Service
class PasswordUpgrader implements UserDetailsPasswordService {
    private final UserRepository users;
    PasswordUpgrader(UserRepository users) { this.users = users; }

    @Override
    @Transactional
    public UserDetails updatePassword(UserDetails user, String newEncodedPassword) {
        users.updatePasswordHash(user.getUsername(), newEncodedPassword);
        return User.withUserDetails(user).password(newEncodedPassword).build();
    }
}

After a successful login, DaoAuthenticationProvider asks passwordEncoder.upgradeEncoding(storedHash); if it returns true (an older id, or a lower BCrypt strength) and a UserDetailsPasswordService is available, it re-encodes the password it just verified and saves it. Users migrate silently as they log in; accounts that never log in can be forced to reset. For a legacy table of unsalted SHA-1 hashes, prefix them with {sha1}-style ids mapped to a legacy encoder, or better, wrap them (store argon2(sha1hash)) so no weak hash stays at rest.

Choosing a work factor

Measure on production hardware and pick the highest cost that keeps one hash near a target such as 250 ms. Logins are rare per user, so this costs little, but it also makes your login endpoint an easy CPU-exhaustion target, which is one reason rate limiting is mandatory (L355).

public static void main(String[] args) {
    for (int strength = 10; strength <= 14; strength++) {
        var enc = new BCryptPasswordEncoder(strength);
        enc.encode("warm-up");
        long t0 = System.nanoTime();
        for (int i = 0; i < 5; i++) enc.encode("correct horse battery staple");
        System.out.printf("strength %d: %d ms%n", strength, (System.nanoTime() - t0) / 5 / 1_000_000);
    }
}

Policy that actually helps

Current NIST and OWASP guidance favours length over composition: require a minimum length, allow at least 64 characters and any Unicode, drop "one digit, one symbol" rules, allow paste and password managers, and do not force periodic rotation (change only on evidence of compromise). Do reject passwords known from breaches. Have I Been Pwned's range API uses k-anonymity: you send only the first five hex characters of the SHA-1 and compare the returned suffixes locally.

static boolean isBreached(HttpClient http, String password)
        throws IOException, InterruptedException, NoSuchAlgorithmException {
    byte[] sha1 = MessageDigest.getInstance("SHA-1").digest(password.getBytes(StandardCharsets.UTF_8));
    String hex = HexFormat.of().withUpperCase().formatHex(sha1);
    String prefix = hex.substring(0, 5), suffix = hex.substring(5);
    var req = HttpRequest.newBuilder(URI.create("https://api.pwnedpasswords.com/range/" + prefix))
            .header("Add-Padding", "true").build();          // padding rows have count 0
    String body = http.send(req, HttpResponse.BodyHandlers.ofString()).body();
    return body.lines().anyMatch(l -> l.startsWith(suffix + ":") && !l.endsWith(":0"));
}

Reset tokens: 32 random bytes from SecureRandom, sent once by email, stored only as a SHA-256 hash (fine here because the token has full entropy), single use, expiring within an hour, invalidated when the password changes, and requested through a form that answers identically whether or not the email exists.

What breaks in production
  • Passwords in logs: a request logger that dumps form bodies, or an exception message containing the submitted value. Mask at the logging layer.
  • Unprefixed legacy hashes after switching to DelegatingPasswordEncoder: "There is no PasswordEncoder mapped for the id null". Migrate the column or set a default encoder for matches.
  • A work factor tuned on a laptop that takes a second on a throttled container, turning a login burst into an outage.
  • "Your password was emailed to you": proof the system stores it recoverably.

  3. Add the breached-password check to registration and to password change, with a timeout and a fail-open decision you can justify.

Form Login, Logout & Remember-Me

40m video45m practice

Form login is a filter that accepts a POST of credentials, authenticates it, stores the result in the session and redirects; logout is a filter that undoes all of that; remember-me is a long-lived cookie that can recreate a weaker login later. Each step is configurable, and each has one security property you must not lose: CSRF protection on both POSTs, no open redirects, and remember-me logins that are never treated as fresh ones.

Replacing the generated login page

Spring's generated page appears only while no loginPage is configured. Once you set one, you own GET /login (a controller and template that includes the CSRF token as a hidden field), and the filter handles the POST:

@Bean
SecurityFilterChain web(HttpSecurity http, PersistentTokenRepository tokens) throws Exception {
    http
        .authorizeHttpRequests(a -> a
            .requestMatchers("/login", "/css/**").permitAll()
            .requestMatchers("/account/password", "/payments/**").fullyAuthenticated()
            .anyRequest().authenticated())
        .formLogin(f -> f
            .loginPage("/login")                     // GET: your page
            .loginProcessingUrl("/perform-login")    // POST: handled by the filter
            .usernameParameter("email")
            .defaultSuccessUrl("/", false)           // true would ignore the saved request
            .failureUrl("/login?error")
            .permitAll())
        .logout(l -> l
            .logoutUrl("/logout")
            .logoutSuccessUrl("/login?logout")
            .invalidateHttpSession(true)
            .deleteCookies("JSESSIONID", "remember-me")
            .addLogoutHandler(new HeaderWriterLogoutHandler(
                new ClearSiteDataHeaderWriter(ClearSiteDataHeaderWriter.Directive.COOKIES))))
        .rememberMe(r -> r
            .tokenRepository(tokens)
            .tokenValiditySeconds((int) Duration.ofDays(14).toSeconds())
            .useSecureCookie(true));
    return http.build();
}

@Bean
PersistentTokenRepository tokens(DataSource ds) {
    var repo = new JdbcTokenRepositoryImpl();   // table persistent_logins(username, series, token, last_used)
    repo.setDataSource(ds);
    return repo;
}

defaultSuccessUrl("/", true) always lands on /; with false the user returns to the page they first asked for. Error messages on /login?error should say "invalid email or password" and nothing more specific.

Handlers, saved requests and redirects

When an anonymous user requests /orders/7, ExceptionTranslationFilter stores the request in the RequestCache (the session by default) before redirecting to the login page. After login, the default SavedRequestAwareAuthenticationSuccessHandler redirects back to it. In Spring Security 6 the redirect carries a continue query parameter, and the saved request is only looked up when that parameter is present, which saves a session read on every other request. For SPAs, replace the redirects with JSON:

@Bean
AuthenticationSuccessHandler jsonSuccess(ObjectMapper mapper) {
    return (req, res, auth) -> {
        res.setContentType(MediaType.APPLICATION_JSON_VALUE);
        mapper.writeValue(res.getWriter(), Map.of("user", auth.getName()));
    };
}

@Bean
AuthenticationFailureHandler jsonFailure(ObjectMapper mapper) {
    return (req, res, ex) -> {
        res.setStatus(HttpStatus.UNAUTHORIZED.value());
        res.setContentType(MediaType.APPLICATION_JSON_VALUE);
        mapper.writeValue(res.getWriter(), Map.of("error", "invalid_credentials"));   // never ex.getMessage()
    };
}
// .formLogin(f -> f.successHandler(jsonSuccess).failureHandler(jsonFailure))

Failure auditing belongs in an event listener for AbstractAuthenticationFailureEvent (L345) rather than in the handler, so every mechanism is covered. If you add your own "return to" parameter, validate it against an allowlist of local paths; an unvalidated redirect target is an open redirect that phishing pages love.

Logout

LogoutFilter runs its LogoutHandlers (invalidate the session, clear the SecurityContext, delete cookies, clear remember-me tokens, plus anything you add), then the LogoutSuccessHandler. With CSRF protection on, logout accepts only POST with a CSRF token. A GET logout lets any third-party page log your users out with an <img src="https://bank.example/logout">, and it is often a step in a session-fixation or login-CSRF chain. For APIs, return a status instead of a redirect with logoutSuccessHandler(new HttpStatusReturningLogoutSuccessHandler(HttpStatus.NO_CONTENT)). The Clear-Site-Data header in the configuration above tells the browser to drop cookies for the origin as well.

Remember-me: two designs

Definition · hash-based token

TokenBasedRememberMeServices stores everything in the cookie: base64 of username, expiry time, algorithm name, and a hash of username, expiry, the user's current password hash and a server key (SHA-256 by default in 6.x). No server state; changing the password invalidates all cookies, but a stolen cookie works until it expires and cannot be revoked individually.

Definition · persistent token

PersistentTokenBasedRememberMeServices stores a random series (fixed per login) and a random token (rotated on every use) in the persistent_logins table. If a cookie arrives with a known series but a stale token, someone else already used it, which means the cookie was copied: the service throws CookieTheftException and deletes all of that user's remember-me tokens.

Either way, a remember-me login produces a RememberMeAuthenticationToken, not a fresh password login. Gate sensitive operations (changing the password or email, payments, viewing secrets) with fullyAuthenticated() so a remembered user is sent back to the login form first (L343). Keep the cookie HttpOnly and Secure, and keep validity short enough that a forgotten shared computer is not a two-month key. Lockout after repeated failures is built on L355.

What breaks in production
  • A custom login page without the CSRF hidden field: every login fails with 403 and looks like a credentials bug.
  • <a href="/logout"> links that stop working when CSRF is enabled; use a small POST form.
  • Remember-me users able to change the account email, and with it take over password reset.
  • The failure handler echoing ex.getMessage(), which distinguishes "locked" from "bad credentials".

  1. Build the custom login page with an email field and test the saved-request redirect.
  2. Switch to JSON success and failure handlers and drive the login from curl with the CSRF token.
  3. Enable persistent remember-me, copy the cookie into a second browser, use it in both, and observe the theft detection.
  4. Protect /account/password with fullyAuthenticated() and verify that a remembered session is asked to log in again.

HTTP Basic, Session Management & Fixation

40m video40m practice

HTTP Basic sends the password with every request, so it belongs only on TLS-protected machine-to-machine paths. Browser logins instead create a server-side session identified by a cookie, and protecting that cookie (its attributes, its rotation at login, how many exist per user, and where the session is stored) is most of session security.

HTTP Basic

GET /internal/reports HTTP/1.1
Host: reports.internal.example

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Realm"

GET /internal/reports HTTP/1.1
Host: reports.internal.example
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==      # base64("Aladdin:open sesame")

The challenge makes browsers show a native popup and then resend the credentials on every request until the browser closes; there is no real logout. Base64 is an encoding, not encryption, so without TLS anyone on the path reads the password. Every request also re-runs the password check, which with a 250 ms BCrypt cost is a CPU problem on a busy API. Spring's BasicAuthenticationFilter is enabled with httpBasic(Customizer.withDefaults()); for requests marked X-Requested-With: XMLHttpRequest the default entry point answers 401 without the WWW-Authenticate header, so scripts do not trigger the popup. Use Basic for internal service calls, Actuator scraping or CI tooling over TLS, and prefer tokens or mTLS when you can. Digest authentication tried to avoid sending the password, but it relies on MD5 and forces the server to store a plaintext-equivalent secret instead of a slow hash; treat it as obsolete.

Session creation policy

Definition

sessionManagement(s -> s.sessionCreationPolicy(...)) controls whether Spring Security creates or uses an HttpSession to store the SecurityContext. ALWAYS creates one for every request; IF_REQUIRED (the default) creates one when needed, such as at login; NEVER never creates one but uses an existing session; STATELESS neither creates nor reads one, so every request must authenticate itself, which is what token-based APIs want. The policy governs Spring Security only: your own code, or a library calling request.getSession(), can still create a session.

# application.yml
server:
  servlet:
    session:
      timeout: 30m              # idle timeout
      cookie:
        name: SID               # don't advertise the stack
        http-only: true         # not readable by JavaScript
        secure: true            # sent over HTTPS only
        same-site: lax          # not sent on cross-site POSTs

HttpOnly keeps an XSS payload from reading the cookie; Secure stops it leaking over plain HTTP; SameSite=Lax withholds it from cross-site subrequests and POSTs while keeping top-level links working, and Strict withholds it even from links arriving from other sites, which breaks "click the link in the email and land logged in".

Session fixation

Spring Security changes the session id on authentication by default: sessionFixation().changeSessionId() uses the Servlet HttpServletRequest.changeSessionId() and keeps the attributes. Alternatives are migrateSession() (new session, copied attributes), newSession() (new, empty session) and none(), which you should never choose. DisableEncodeUrlFilter already prevents ids in URLs. If you authenticate users in custom code, call the session-authentication strategy yourself, or the rotation does not happen.

Concurrent session control

@Bean
SecurityFilterChain web(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .formLogin(Customizer.withDefaults())
        .sessionManagement(s -> s
            .sessionFixation(f -> f.changeSessionId())
            .maximumSessions(1)
            .maxSessionsPreventsLogin(false)   // false: newest login wins, older session expires
            .expiredUrl("/login?expired"));
    return http.build();
}

@Bean
HttpSessionEventPublisher httpSessionEventPublisher() {   // lets the SessionRegistry see session ends
    return new HttpSessionEventPublisher();
}

The SessionRegistry tracks sessions per principal (so the principal needs sensible equals/hashCode; the built-in User compares usernames). maxSessionsPreventsLogin(true) rejects the new login instead, which locks out a user whose old session is on a lost laptop. The registry is also how you force-expire a user's sessions after a password change or role revocation.

Scaling sessions

  • Sticky sessions: the load balancer pins a user to one node. Simple; a node restart logs its users out, and load spreads unevenly.
  • Session replication between servlet containers: chatty and fragile beyond a few nodes.
  • Spring Session with Redis: add spring-session-data-redis; Boot installs a SessionRepositoryFilter ahead of Spring Security that swaps HttpSession for a Redis-backed one. Nodes become stateless, sessions survive deploys, and you can list and delete a user's sessions centrally.
spring:
  data:
    redis:
      host: redis.internal
  session:
    timeout: 30m
    redis:
      namespace: shop:session

Everything stored in the session, including the SecurityContext and your principal, is serialized into Redis. Keep the principal small and serializable, and consider a JSON serializer with Spring Security's Jackson modules rather than Java serialization. This gives "stateless-ish" application nodes without the revocation problems of tokens.

What breaks in production
  • Basic auth on a public endpoint behind a proxy that also accepts plain HTTP: passwords in the clear.
  • STATELESS set, yet sessions appear: a controller or library calls getSession().
  • Concurrent session control behind several nodes without a shared registry: the limit is per node, not per user.
  • Changing the principal class without a migration, so every session in Redis fails to deserialize after the deploy.

  2. Log the session id before and after login and confirm it changes; set none() and reproduce fixation by hand.
  3. Configure maximumSessions(1), log in from two browsers, and check which one is expired.
  4. Add Spring Session with Redis (Testcontainers), restart the app, and show the session survives.

CSRF: How It Works and How to Defend

40m video40m practice

Cross-site request forgery works because browsers attach cookies to every request for a site, no matter which page started the request. The defense is to require, on every state-changing request, a secret that a cross-site page cannot read: a CSRF token. If your API never authenticates with cookies, the attack does not apply and CSRF protection can legitimately be off.

The attack

The victim is logged in to bank.example in one tab. In another tab they open a page on evil.example containing:

<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker-account">
  <input type="hidden" name="amount" value="5000">
</form>
<script>document.getElementById("f").submit()</script>

The same-origin policy stops evil.example from reading the response, but the transfer has already happened. The attack needs credentials the browser adds automatically: session cookies, and also cached HTTP Basic credentials and client certificates. A request authenticated by an Authorization: Bearer header that JavaScript must add explicitly cannot be forged this way, because the attacker's page has no access to the token.

The synchronizer token pattern

Definition

The server issues an unpredictable token tied to the user's session and requires it, in a form field or a header, on every unsafe request. A cross-site page can make the browser send cookies but cannot read the token, so it cannot include it. In Spring, a CsrfToken has a token value, a parameter name (_csrf) and a header name; a CsrfTokenRepository stores it. HttpSessionCsrfTokenRepository (the default) keeps it in the session and expects header X-CSRF-TOKEN. CookieCsrfTokenRepository.withHttpOnlyFalse() writes it to a JavaScript-readable XSRF-TOKEN cookie and expects it back in X-XSRF-TOKEN, the convention Angular and Axios follow.

CsrfFilter checks every method except GET, HEAD, OPTIONS and TRACE, which is only safe if those methods never change state. A "delete" link implemented as GET is CSRF-able no matter what else you configure. Server-rendered Thymeleaf forms get the hidden _csrf field automatically.

The Spring Security 6 change that breaks SPAs

Two defaults changed in 6.0. Tokens are deferred: the repository loads or creates the token only when something asks for it, so a cookie-based SPA may never receive an XSRF-TOKEN cookie. And the default XorCsrfTokenRequestAttributeHandler adds BREACH protection: each time the token is rendered it is XOR-masked with fresh random bytes, so a secret reflected in a compressed response cannot be recovered by the BREACH compression attack. The handler then expects a masked value, but an SPA copies the raw cookie value into the header, and gets 403.

@Bean
SecurityFilterChain spa(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .formLogin(Customizer.withDefaults())
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler())  // accept the raw header value
            .ignoringRequestMatchers("/api/webhooks/**"));                     // authenticated by signature
    return http.build();
}

@RestController
class CsrfController {
    @GetMapping("/api/csrf")
    CsrfToken csrf(CsrfToken token) {   // resolving the token forces the cookie to be written
        return token;
    }
}

Plain CsrfTokenRequestAttributeHandler gives up masking, which is acceptable when the token never appears in a response body. The reference documentation's fuller SPA recipe keeps masking for tokens rendered into HTML and accepts raw values only from the header.

When disabling CSRF is legitimate

csrf(csrf -> csrf.disable()) is correct for a stateless API authenticated only by an Authorization header (bearer tokens, API keys), with SessionCreationPolicy.STATELESS and no authentication cookie anywhere. It is wrong for an SPA that uses a session cookie, for a BFF, and for an API that also accepts Basic auth from browsers. Webhooks are better handled by excluding just their paths and verifying the sender's HMAC signature.

SameSite and double-submit cookies

SameSite=Lax (the default in current browsers for cookies without the attribute) stops the cookie from riding along on cross-site POSTs, which defeats the form above. It is a complementary defense, not a replacement: "same site" means the same registrable domain, so a compromised or user-content subdomain is still same-site; top-level GET navigations still carry Lax cookies, so state-changing GETs remain exposed; and older clients ignore the attribute.

The double-submit cookie pattern skips server storage: put a random value in a cookie and require the same value in a header or field. Its weakness is that an attacker who can write cookies for your domain (from a sibling subdomain or a plain-HTTP response) can set both halves. OWASP recommends the signed variant, an HMAC of the value bound to the session, if you use it at all.

Testing

@Test
void transferRequiresCsrf() throws Exception {
    mvc.perform(post("/transfer").with(user("ana")).param("to", "x").param("amount", "5"))
       .andExpect(status().isForbidden());
    mvc.perform(post("/transfer").with(user("ana")).with(csrf()).param("to", "x").param("amount", "5"))
       .andExpect(status().is3xxRedirection());
    mvc.perform(post("/transfer").with(user("ana")).with(csrf().asHeader().useInvalidToken()))
       .andExpect(status().isForbidden());
}
What breaks in production
  • csrf().disable() copied from a JWT tutorial into an app that actually uses session cookies.
  • Upgrading to Boot 3 and every SPA POST returning 403: deferred loading plus the masked-token handler.
  • A GET endpoint with side effects (/unsubscribe?id=…, /cart/clear) that no CSRF filter protects.
  • Overbroad ignores (/api/**) added to "fix" a 403 during a deadline.

  2. Serve a small SPA that reads XSRF-TOKEN and sends X-XSRF-TOKEN; reproduce the 6.x 403, then fix it.

Authorization: Matchers, Roles, Authorities & Hierarchies

45m video50m practice

Every authorization decision in Spring Security 6 is an AuthorizationManager looking at the current Authentication's authority strings and the thing being accessed. Roles are just authorities with a ROLE_ prefix, hierarchies expand them, and the real design work is choosing what those strings mean and enforcing tenant and ownership rules where the data is read.

AuthorizationManager replaces voters

Definition

An AuthorizationManager<T> takes a Supplier<Authentication> and an object T (for requests, a RequestAuthorizationContext with the request and any path variables) and returns a decision. authorizeHttpRequests builds a RequestMatcherDelegatingAuthorizationManager from your rules and runs it in AuthorizationFilter. It replaces the old authorizeRequests model of AccessDecisionManager, voters and FilterSecurityInterceptor. Two behavioral details: the Authentication is looked up lazily, only if a rule needs it; and in 6.x authorization applies to every dispatch, including error and forward dispatches, which is why /error needs its own rule.

Roles versus authorities

A GrantedAuthority is a string. hasAuthority("order:write") checks for exactly that string. hasRole("ADMIN") checks for "ROLE_ADMIN", adding the prefix for you; passing "ROLE_ADMIN" to hasRole is rejected at startup. So a user built with .roles("ADMIN") passes hasRole("ADMIN") and hasAuthority("ROLE_ADMIN"), while a user given the authority "ADMIN" (common when roles come from a database or token) passes neither of those and only hasAuthority("ADMIN").

The full set of rule outcomes: permitAll, denyAll, authenticated (any non-anonymous user, including remember-me), fullyAuthenticated (authenticated and not via remember-me), rememberMe, anonymous, hasRole/hasAnyRole, hasAuthority/hasAnyAuthority, and access(...). IP checks use an expression manager, for example access(new WebExpressionAuthorizationManager("hasIpAddress('10.0.0.0/8')")); behind a proxy the remote address is the proxy's unless forwarded headers are configured, and a client-supplied X-Forwarded-For must never be trusted blindly.

Custom rules and composition

@Bean
SecurityFilterChain app(HttpSecurity http) throws Exception {
    AuthorizationManager<RequestAuthorizationContext> sameTenant = (auth, ctx) -> {
        String tenant = ctx.getVariables().get("tenant");
        boolean ok = auth.get().getPrincipal() instanceof AppUserPrincipal p
                     && p.getTenantId().equals(tenant);
        return new AuthorizationDecision(ok);
    };
    AuthorizationManager<RequestAuthorizationContext> user = AuthorityAuthorizationManager.hasRole("USER");

    http.authorizeHttpRequests(a -> a
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .requestMatchers("/tenants/{tenant}/**").access(AuthorizationManagers.allOf(user, sameTenant))
            .requestMatchers("/account/password").fullyAuthenticated()
            .requestMatchers("/error").permitAll()
            .anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());
    return http.build();
}

Role hierarchies

@Bean
static RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.fromHierarchy("""
        ROLE_ADMIN > ROLE_MANAGER
        ROLE_MANAGER > ROLE_USER""");
}

With this bean an admin satisfies hasRole("USER") without being granted it explicitly, so rules name the minimum role rather than listing every role that qualifies. fromHierarchy and the builder RoleHierarchyImpl.withDefaultRolePrefix().role("ADMIN").implies("MANAGER") are the 6.3+ API; older versions call setHierarchy. Recent 6.x versions apply a RoleHierarchy bean to both request rules and method security; on older ones check that it is wired into the method-security expression handler too.

Designing the authorization model

Coarse roles (USER, MANAGER, ADMIN) are easy to reason about but end up encoding permissions implicitly in code. Fine-grained permissions (order:read, order:refund, report:export) put the policy in data: tables role, permission, role_permission and user_role, with code checking permissions and admins composing roles from them. At login, load both role names (as ROLE_…) and the union of their permissions into the authorities. The catch: if those authorities go into a JWT, every request carries them, and a few hundred permissions push tokens past the 8 KB header limits common in servers and proxies. Put roles in tokens and resolve permissions server-side with a cache when the set is large.

When policy grows beyond what annotations express, externalize it: Open Policy Agent (Rego policies evaluated by a sidecar or library), Cedar (AWS's analyzable policy language), or OpenFGA (a Zanzibar-style relationship store). Your AuthorizationManager then becomes a thin client of the policy engine.

Multi-tenancy has to be enforced at the data layer, not only in the controller: every query filters by the tenant from the authenticated principal (Hibernate 6's @TenantId, a Hibernate filter, or PostgreSQL row-level security driven by a session variable). Controller checks miss batch jobs, exports, search indexes and the next endpoint someone adds.

What breaks in production
  • hasRole("ADMIN") against authorities loaded as "ADMIN": every admin gets 403, and someone "fixes" it with permitAll.
  • A role revoked in the database but still present in a 24-hour token or session.
  • Tenant checked on /tenants/{tenant}/orders but not on /orders/{id}, which loads any tenant's order by id.
  • hasIpAddress trusting a spoofed X-Forwarded-For.

  1. Create users with .roles("ADMIN") and with .authorities("ADMIN"); write tests showing which rules each passes.
  2. Add the role hierarchy and delete the now-redundant role lists from your rules.

Method Security & Object-Level Authorization

45m video50m practice

URL rules decide who may call an endpoint; they cannot decide whether this user may touch order 4711. Method security moves checks onto service methods where the arguments are known, and the strongest form of object-level authorization goes one step further: the query itself only returns rows the caller owns.

Enabling method security

@EnableMethodSecurity replaced @EnableGlobalMethodSecurity in 6.0. It is built on AuthorizationManager like request security, enables @PreAuthorize/@PostAuthorize/@PreFilter/@PostFilter by default (prePostEnabled = true), and enables @Secured and JSR-250 @RolesAllowed only with securedEnabled = true and jsr250Enabled = true. Like transactions, it works through a proxy (L333): a call from one method to another on the same bean via this skips the check entirely, and private or final methods are never intercepted.

        return auth.getPrincipal() instanceof AppUserPrincipal p
               && orders.existsByIdAndOwnerId(orderId, p.getId());
    }

SpEL sees the method arguments by name (#orderId), so the code must be compiled with -parameters; Spring Boot's Maven and Gradle setups do that, and since Spring Framework 6.1 there is no fallback to debug information. @bean.method(...) calls any bean, which keeps complex logic in testable Java instead of long expressions. @PostAuthorize checks the returned object, which means the method has already run: fine for a read, wrong for anything that writes, sends or charges, because the side effect happened before the denial.

Filtering, @Secured, @RolesAllowed and PermissionEvaluator

@PostFilter("filterObject.ownerId() == authentication.principal.id") removes elements from a returned collection; @PreFilter does the same to a collection argument. Both work in memory: loading 10,000 rows to return 12 wastes the database and the heap, and it breaks pagination (a page of 20 becomes a page of 3). Filter in the query instead. @Secured("ROLE_ADMIN") takes full authority names; @RolesAllowed("ADMIN") adds the prefix. Both are simpler and less expressive than @PreAuthorize.

hasPermission(#orderId, 'Order', 'refund') delegates to your PermissionEvaluator, a single place for domain permission logic:

@Component

    private final OrderRepository orders;
    OrderPermissionEvaluator(OrderRepository orders) { this.orders = orders; }

    @Override
    public boolean hasPermission(Authentication auth, Object target, Object permission) {
        return false;   // object-based form unused here
    }

    @Override
    public boolean hasPermission(Authentication auth, Serializable id, String type, Object permission) {
        if (!"Order".equals(type) || !(auth.getPrincipal() instanceof AppUserPrincipal p)) return false;
        return switch (String.valueOf(permission)) {
            case "read", "write" -> orders.existsByIdAndOwnerId((Long) id, p.getId());
            case "refund" -> auth.getAuthorities().stream()
                                 .anyMatch(a -> "order:refund".equals(a.getAuthority()));
            default -> false;
        };
    }
}

IDOR: broken object-level authorization

Definition

Broken object-level authorization (BOLA, also called IDOR) is an endpoint that accepts an object id from the client and returns or modifies that object without checking that the caller may access it. It is first in the OWASP API Security Top 10, because ids are easy to enumerate and every new endpoint is a new chance to forget the check.

public interface OrderRepository extends JpaRepository<Order, Long> {
    Optional<Order> findByIdAndOwnerId(Long id, UUID ownerId);
    boolean existsByIdAndOwnerId(Long id, UUID ownerId);
    List<OrderSummary> findSummariesByOwnerId(UUID ownerId);
}

@GetMapping("/orders/{id}")
OrderView get(@PathVariable Long id, @CurrentUser AppUserPrincipal me) {
    return orders.findByIdAndOwnerId(id, me.getId())          // ownership is part of the query
            .map(OrderView::from)
            .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
}

Fetch-then-check (findById, then compare owner) works until someone adds a second endpoint and forgets the comparison; ownership in the query fails closed. Answer 404 rather than 403 for objects the caller does not own, so ids cannot be probed for existence.

Newer annotations in 6.3+

@AuthorizeReturnObject wraps the returned object in a proxy so that @PreAuthorize annotations on its methods apply (for example, a customerEmail() getter requiring order:read-pii); the returned type must be proxyable, so not a record or final class. @HandleAuthorizationDenied names a handler that supplies a fallback value, such as a masked string, instead of throwing AccessDeniedException. Annotation templates let you define meta-annotations like @IsOwner with parameters, so the SpEL lives in one place.

What breaks in production
  • A @PreAuthorize method called internally via this: the check silently never runs.
  • @PostAuthorize on a method that also sends an email or marks something read.
  • Missing -parameters after a build change: #orderId resolves to null and the expression denies, or fails at runtime.
  • Sequential numeric ids plus one forgotten ownership check: the whole table can be downloaded by counting.

Custom Authentication: Providers, Filters & Entry Points

45m video50m practice

Any new authentication scheme in Spring Security is the same three pieces: a filter that turns the request into an unauthenticated Authentication token, a provider that verifies that token type, and an entry point that says what to send when authentication is missing. Getting the placement and the failure responses right matters as much as the verification.

ProviderManager and its providers

Definition

AuthenticationManager.authenticate(Authentication) returns a fully authenticated token or throws AuthenticationException. ProviderManager implements it by walking a list of AuthenticationProviders: for each one whose supports(tokenClass) is true it calls authenticate; a returned token ends the search, null means "not mine, try the next", an exception is remembered and the next provider is tried (except account-status failures such as a locked account, which stop the search). If none succeeds it asks an optional parent manager, then throws. On success it erases credentials and publishes an event.

DaoAuthenticationProvider, the username/password provider, does: load the user through the UserDetailsService (or its UserCache); run pre-checks (locked, disabled, account expired); compare with PasswordEncoder.matches; run post-checks (credentials expired); optionally upgrade the hash (L339). When the user does not exist it still runs matches against a precomputed dummy hash, so "no such user" takes about as long as "wrong password" and response timing cannot enumerate accounts.

A custom token and provider: API keys

public final class ApiKeyAuthentication extends AbstractAuthenticationToken {
    private final String key;          // credentials, before authentication
    private final ApiClient client;    // principal, after authentication

    private ApiKeyAuthentication(String key, ApiClient client, Collection<? extends GrantedAuthority> auths) {
        super(auths);
        this.key = key;
        this.client = client;
        setAuthenticated(client != null);
    }
    public static ApiKeyAuthentication unauthenticated(String key) {
        return new ApiKeyAuthentication(key, null, List.of());
    }
    public static ApiKeyAuthentication authenticated(ApiClient client) {
        return new ApiKeyAuthentication(null, client, client.authorities());
    }
    @Override public Object getCredentials() { return key; }
    @Override public Object getPrincipal() { return client; }
}

@Component
class ApiKeyAuthenticationProvider implements AuthenticationProvider {
    private final ApiClientRepository clients;
    ApiKeyAuthenticationProvider(ApiClientRepository clients) { this.clients = clients; }

    @Override
    public Authentication authenticate(Authentication auth) {
        String hash = sha256Hex((String) auth.getCredentials());   // keys are stored hashed
        ApiClient client = clients.findByKeyHash(hash)
                .filter(ApiClient::active)
                .orElseThrow(() -> new BadCredentialsException("invalid API key"));
        return ApiKeyAuthentication.authenticated(client);
    }

    @Override
    public boolean supports(Class<?> type) {
        return ApiKeyAuthentication.class.isAssignableFrom(type);
    }

    static String sha256Hex(String s) {
        try {
            byte[] d = MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(d);
        } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}

Hashing API keys with plain SHA-256 is fine because the keys are long random values, not human passwords; a slow hash would only add latency to every call. Write a provider instead of a UserDetailsService whenever verification is not "compare with a stored password hash": LDAP binds, one-time codes, a legacy system's check, signed requests.

A custom filter and its placement

class ApiKeyFilter extends OncePerRequestFilter {
    private final AuthenticationManager manager;
    private final AuthenticationEntryPoint entryPoint;
    private final SecurityContextHolderStrategy holder = SecurityContextHolder.getContextHolderStrategy();

    ApiKeyFilter(AuthenticationManager manager, AuthenticationEntryPoint entryPoint) {
        this.manager = manager;
        this.entryPoint = entryPoint;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String key = req.getHeader("X-API-Key");
        if (key == null || key.isBlank()) {               // not our scheme: let others try
            chain.doFilter(req, res);
            return;
        }
        Authentication result;
        try {
            result = manager.authenticate(ApiKeyAuthentication.unauthenticated(key));
        } catch (AuthenticationException e) {
            holder.clearContext();
            entryPoint.commence(req, res, e);              // 401 now, do not continue the chain
            return;
        }
        SecurityContext ctx = holder.createEmptyContext();
        ctx.setAuthentication(result);
        holder.setContext(ctx);
        chain.doFilter(req, res);
    }
}

@Bean
SecurityFilterChain partnerApi(HttpSecurity http, ApiKeyAuthenticationProvider provider,
                               ProblemEntryPoint entryPoint) throws Exception {

    http.securityMatcher("/partner/**")
        .authorizeHttpRequests(a -> a.anyRequest().hasAuthority("partner"))
        .addFilterBefore(filter, BasicAuthenticationFilter.class)

        .csrf(c -> c.disable())                             // header-authenticated only
        .exceptionHandling(e -> e.authenticationEntryPoint(entryPoint)
            .accessDeniedHandler((req, res, ex) -> res.sendError(HttpServletResponse.SC_FORBIDDEN)));

addFilterBefore/addFilterAfter position a filter relative to a known filter class, whether or not that filter is in this chain; addFilterAt puts it at the same position without replacing anything, so both run in unspecified order. Extend AbstractAuthenticationProcessingFilter instead when the scheme is a login endpoint (a URL that receives credentials and then redirects or returns tokens), since it brings success/failure handlers, session strategy and context saving. Do not annotate the filter with @Component: Boot would also register it as a plain servlet filter for every request, outside the security chain.

Entry points, denied handlers and events

ExceptionTranslationFilter catches what later filters throw. An AuthenticationException goes to the AuthenticationEntryPoint: a login redirect for UIs, a 401 for APIs. An AccessDeniedException goes to the AccessDeniedHandler (403) only if the user is fully authenticated; for anonymous users it is also treated as "authentication required", which is why an anonymous request to an admin URL gets 401, not 403.

@Component
class ProblemEntryPoint implements AuthenticationEntryPoint {
    private final ObjectMapper mapper;
    ProblemEntryPoint(ObjectMapper mapper) { this.mapper = mapper; }

    public void commence(HttpServletRequest req, HttpServletResponse res, AuthenticationException ex)
            throws IOException {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED, "Authentication required");
        pd.setInstance(URI.create(req.getRequestURI()));
        res.setStatus(HttpStatus.UNAUTHORIZED.value());

  • A custom filter declared as a @Component runs twice, once outside Spring Security where the context is empty.
  • A filter that throws on a missing header, breaking every other authentication scheme and every public endpoint in the chain.
  • Entry points that return the exception message ("User account is locked") and leak account state.
  • Logging the username on every failure: users sometimes type their password into the username field.

JWT I: Structure, Signing & Validation Pitfalls

45m video45m practice

A JWT is a set of claims, base64url-encoded and signed, that any holder can read and any party with the right key can verify without a database lookup. Every real-world JWT vulnerability comes from trusting something the verifier should have pinned: the algorithm, the key, the issuer, the audience or the expiry.

Anatomy

static void inspect(String jwt) {
    String[] parts = jwt.split("\\.");
    var dec = Base64.getUrlDecoder();                       // padding is optional for the decoder
    System.out.println(new String(dec.decode(parts[0]), StandardCharsets.UTF_8));
    System.out.println(new String(dec.decode(parts[1]), StandardCharsets.UTF_8));   // readable by anyone
}
// {"alg":"RS256","typ":"JWT","kid":"2025-10"}
// {"iss":"https://auth.example.com","sub":"42","aud":"orders-api","exp":1760190000,"iat":1760189100,"jti":"9f1c…","roles":["USER"]}

The registered claims of RFC 7519: iss (who issued it), sub (whom it is about), aud (who it is for), exp (expiry, seconds since the epoch), nbf (not before), iat (issued at) and jti (unique id). Anything else is a custom claim: roles, scopes, a tenant id. A JWT carried as a JWS (RFC 7515) is signed and readable; as a JWE (RFC 7516) it is encrypted. When people say "JWT" they nearly always mean JWS.

Choosing a signing algorithm

AlgorithmKeyUse when
HS256One shared secret (at least 256 random bits)The issuer is the only verifier. Anyone who can verify can also mint tokens.
RS256 / PS256RSA key pair (2048 bits or more)Many services verify; only the authorization server signs. Most widely supported; large signatures.
ES256ECDSA P-256 key pairSame as RSA with much smaller keys and signatures.
EdDSAEd25519 key pairFast and hard to misuse; check that every verifier supports it.

The deciding question is who needs to verify. If verifiers are other teams, other services or third parties, use an asymmetric algorithm so they only ever hold public keys. Issuers publish those keys as a JWKS (JSON Web Key Set) at the jwks_uri listed in their discovery document, often /.well-known/jwks.json. The header's kid says which key signed the token. Rotation: publish the new key next to the old one, wait until verifiers' caches have it, start signing with it, and remove the old key only after the longest-lived token signed with it has expired.

The attacks

  • alg: none. The spec defines unsecured JWTs; a library that trusts the header's alg accepts a token with the signature removed.
  • Algorithm confusion. A verifier configured with an RSA public key receives a token whose header says HS256. If it lets the header pick the algorithm, it computes an HMAC using the public key bytes as the secret, and since the public key is public, the attacker can produce that HMAC.
  • Missing claim checks. No exp check: stolen tokens work forever. No aud check: a token minted for the low-value newsletter-api is accepted by payments-api. No iss check: tokens from any issuer whose key you happen to trust are accepted.
  • Weak HMAC secrets. One captured token lets an attacker test guesses offline at GPU speed; secret123 falls in seconds.
  • Unverified tokens. Code that base64-decodes the payload to "read the user id" without verifying, often in a gateway or a logging filter, then makes a decision on it.
  • Header-supplied keys. Honouring jku or x5u URLs, or an embedded jwk, lets the attacker supply the verification key; a kid used unsanitized in a file path or SQL query is an injection point.
Algorithm · Validating a JWS
  1. Reject anything that is not three base64url parts, or larger than your limit.
  2. Select the key by kid from your own configured JWKS only; never from URLs or keys in the token.
  3. Require the algorithm you configured for that key; reject none and any other value.
  4. Verify the signature.
  5. Check exp and nbf with a small clock skew (30 to 60 seconds), iss equals your issuer, and aud contains this service.
  6. Only then read custom claims and map them to authorities.

What goes in, and how big it gets

Put the minimum: sub, the issuer and audience, expiry, and the few roles, scopes or tenant ids the resource server needs. Never put secrets, and avoid PII (email, name, address): tokens end up in logs, browser storage and debugging tools, and anyone holding one can read it. Every request carries the token, and many servers and proxies cap total request headers at around 8 KB (Spring Boot's default server.max-http-request-header-size is 8 KB), so a token stuffed with permissions fails with 400 or 431 in the most confusing places.

Revocation and the honest comparison

A signed token cannot be un-issued; it stays valid until exp. The options: keep access tokens short (5 to 15 minutes) and refresh them (L348); keep a jti denylist of revoked tokens, which every verifier checks per request; or include a token version claim compared with the user's current version, so bumping the version kills all of the user's tokens. The last two reintroduce a lookup, which is fine, as long as you admit that you no longer have purely stateless tokens.

OptionStrengthsWeaknesses
Server session + cookieInstant revocation, small cookie, mature toolingShared store to scale; CSRF to handle
Opaque token + introspectionRevocable, reveals nothing, central policyA network call per request unless cached
JWTLocal verification, no shared store, works across organizationsRevocation is hard, larger, many ways to validate wrongly

JWTs are a good fit between services and across trust domains (OAuth2 access tokens, ID tokens). For a single web application's own login, a session is usually simpler and safer.

What breaks in production
  • A shared HS256 secret copied into five services, so any of them, or anyone who reads one of their config files, can mint admin tokens.
  • Key rotation that removes the old key immediately: every live token fails at once.
  • Clocks drifting by minutes on a node, so fresh tokens are rejected as "not yet valid".
  • Email addresses in tokens that end up in an analytics tool through URL or log capture.

  1. Decode a real token from a provider you use and list every claim and what it is for.
  2. Write a deliberately naive verifier that trusts the header's alg; forge an alg: none token and an HS256 token signed with the RSA public key; then fix the verifier.
  3. Generate an HS256 secret properly (32 bytes from SecureRandom) and explain why a passphrase is not equivalent.
  4. Design a token-version scheme: where the version lives, when it increments, and how verifiers cache it.

JWT II: Implementing Stateless Auth in Spring Security

50m video60m practice

Spring Security already contains a correct, well-tested JWT verifier: the OAuth2 resource server support. Use it even for tokens your own app issues, configure the decoder's validators explicitly, and keep hand-written JWT filters for the rare case where you cannot. Either way the shape is the same: a stateless chain, a bearer token per request, claims mapped to authorities, and a clean 401 on anything invalid.

Algorithm · Stateless request
  1. Extract the bearer token; no header means anonymous, not an error.
  2. Verify signature and algorithm against configured keys, then exp/nbf, iss and aud.
  3. Map claims to GrantedAuthoritys and build the authenticated token.
  4. Set it in a fresh SecurityContext for this request only.
  5. Let the authorization rules decide; on any verification failure stop with 401.

The recommended path: resource server with your own keys

    @Bean
    JwtEncoder jwtEncoder(SecretKey key) {

        decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
                JwtValidators.createDefaultWithIssuer(ISSUER), audience));   // exp/nbf (60 s skew) + iss + aud
        return decoder;
    }

    JwtAuthenticationConverter jwtAuthenticationConverter() {
        var roles = new JwtGrantedAuthoritiesConverter();
        roles.setAuthoritiesClaimName("roles");     // default is scope/scp with prefix SCOPE_
        roles.setAuthorityPrefix("ROLE_");
        var converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(roles);
        return converter;
    }

            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(c -> c.disable());                 // tokens travel in a header, never a cookie

    }

Issuing the token: /auth/login

@RestController
class AuthController {
    record LoginRequest(String email, String password) {}
    record TokenResponse(String accessToken, String tokenType, long expiresIn) {}

    private final AuthenticationManager authManager;
    private final JwtEncoder encoder;
    AuthController(AuthenticationManager authManager, JwtEncoder encoder) {
        this.authManager = authManager;
        this.encoder = encoder;
    }

    @PostMapping("/auth/login")
    TokenResponse login(@RequestBody LoginRequest req) {
        Authentication auth = authManager.authenticate(
                UsernamePasswordAuthenticationToken.unauthenticated(req.email(), req.password()));
        Instant now = Instant.now();
        List<String> roles = auth.getAuthorities().stream().map(GrantedAuthority::getAuthority)
                .filter(a -> a.startsWith("ROLE_")).map(a -> a.substring(5)).toList();
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer(JwtConfig.ISSUER).audience(List.of("shop-api"))
                .subject(auth.getName()).id(UUID.randomUUID().toString())
                .issuedAt(now).expiresAt(now.plus(Duration.ofMinutes(10)))
                .claim("roles", roles)
                .build();
        JwsHeader header = JwsHeader.with(MacAlgorithm.HS256).build();
        String token = encoder.encode(JwtEncoderParameters.from(header, claims)).getTokenValue();
        return new TokenResponse(token, "Bearer", 600);
    }
}

A failed authenticate throws BadCredentialsException; map it with an @ExceptionHandler to a 401 problem detail with a generic message. The response says nothing about whether the email exists.

The manual path: jjwt and a OncePerRequestFilter

When you cannot use the resource server (an unusual token format, a legacy issuer), use a maintained library: jjwt-api at compile scope with jjwt-impl and jjwt-jackson at runtime (0.12 API shown), or nimbus-jose-jwt. Build the parser once; it is immutable and thread-safe.

@Component
class JwtService {
    private final SecretKey key;
    private final JwtParser parser;

    JwtService(SecretKey key) {
        this.key = key;
        this.parser = Jwts.parser().verifyWith(key)         // HMAC key: only HS* accepted
                .requireIssuer(JwtConfig.ISSUER).requireAudience("shop-api")
                .clockSkewSeconds(30).build();
    }

    String issue(String subject, List<String> roles) {
        Instant now = Instant.now();
        return Jwts.builder().issuer(JwtConfig.ISSUER).audience().add("shop-api").and()
                .subject(subject).issuedAt(Date.from(now)).expiration(Date.from(now.plusSeconds(600)))
                .claim("roles", roles).signWith(key).compact();
    }

    Claims verify(String token) {
        return parser.parseSignedClaims(token).getPayload();  // rejects unsigned and expired tokens
    }
}

class JwtFilter extends OncePerRequestFilter {
    private final JwtService jwt;
    private final AuthenticationEntryPoint entryPoint;
    private final SecurityContextHolderStrategy holder = SecurityContextHolder.getContextHolderStrategy();

    JwtFilter(JwtService jwt, AuthenticationEntryPoint entryPoint) { this.jwt = jwt; this.entryPoint = entryPoint; }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String header = req.getHeader(HttpHeaders.AUTHORIZATION);
        if (header == null || !header.startsWith("Bearer ")) { chain.doFilter(req, res); return; }
        try {
            Claims c = jwt.verify(header.substring(7));
            var authorities = ((List<?>) c.getOrDefault("roles", List.of())).stream()
                    .map(r -> new SimpleGrantedAuthority("ROLE_" + r)).toList();
            var ctx = holder.createEmptyContext();
            ctx.setAuthentication(UsernamePasswordAuthenticationToken.authenticated(c.getSubject(), null, authorities));
            holder.setContext(ctx);
        } catch (JwtException | IllegalArgumentException e) {
            holder.clearContext();
            entryPoint.commence(req, res, new BadCredentialsException("invalid token", e));
            return;
        }
        chain.doFilter(req, res);
    }
}

Refresh Tokens, Rotation & Revocation

45m video50m practice

Short-lived access tokens limit the damage of theft; a long-lived refresh token, stored and checked on the server, restores the revocation that JWTs lack. Rotating the refresh token on every use, and treating a reused one as proof of theft, turns a stolen credential into a detected incident instead of a silent compromise.

The standard shape

The access token (a JWT, 5 to 15 minutes) is sent on every API call and verified locally. The refresh token (an opaque random string, days to weeks) is sent only to /auth/refresh, where the server looks it up. So a stolen access token expires quickly, and the long-lived credential is one the server can revoke, rate-limit and audit. The refresh token does not need to be a JWT: 32 random bytes are better, because there is nothing to decode or misvalidate.

Definition · token family

Each login starts a family. Every refresh replaces the family's current token with a new one and marks the old one used. The server stores, per token: a SHA-256 hash of the token (never the token), the family id, user id, device name, IP and user agent, creation time, idle expiry, the family's absolute expiry, a revoked timestamp, and the id of the token that replaced it.

Rotation and reuse detection

@Service
class RefreshTokenService {
    private static final Duration IDLE = Duration.ofDays(14), ABSOLUTE = Duration.ofDays(90);
    private final RefreshTokenRepository repo;
    private final SecureRandom random = new SecureRandom();

    RefreshTokenService(RefreshTokenRepository repo) { this.repo = repo; }

    record Issued(String rawToken, RefreshToken entity) {}

    @Transactional
    public Issued issue(UUID userId, UUID familyId, Instant familyStart, ClientInfo client) {
        byte[] bytes = new byte[32];
        random.nextBytes(bytes);
        String raw = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
        Instant now = Instant.now();
        Instant idle = now.plus(IDLE), hardStop = familyStart.plus(ABSOLUTE);
        var token = new RefreshToken(UUID.randomUUID(), familyId, userId, sha256(raw), client,
                                     now, idle.isBefore(hardStop) ? idle : hardStop, familyStart);
        return new Issued(raw, repo.save(token));
    }

    @Transactional(noRollbackFor = TokenReuseException.class)   // the family revocation must commit
    public Issued rotate(String raw, ClientInfo client) {
        RefreshToken current = repo.findByHashForUpdate(sha256(raw))  // row lock: one rotation at a time
                .orElseThrow(InvalidRefreshTokenException::new);
        if (current.getRevokedAt() != null) {
            repo.revokeFamily(current.getFamilyId(), Instant.now());
            throw new TokenReuseException(current.getUserId());
        }
        if (current.getExpiresAt().isBefore(Instant.now())) throw new InvalidRefreshTokenException();
        Issued next = issue(current.getUserId(), current.getFamilyId(), current.getFamilyStartedAt(), client);
        current.revoke(Instant.now(), next.entity().getId());         // dirty-checked, flushed at commit
        return next;
    }

    static String sha256(String s) {
        try {
            byte[] d = MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(d);
        } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}

interface RefreshTokenRepository extends JpaRepository<RefreshToken, UUID> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select t from RefreshToken t where t.tokenHash = :hash")
    Optional<RefreshToken> findByHashForUpdate(String hash);

    @Modifying
    @Query("update RefreshToken t set t.revokedAt = :now where t.familyId = :family and t.revokedAt is null")
    int revokeFamily(UUID family, Instant now);
}

Note the Phase 16 details doing real work: noRollbackFor keeps the revocation when the method throws (L331), and the pessimistic lock stops two concurrent refreshes from both "winning" and creating two children of the same token.

The /auth/refresh endpoint and client storage

@PostMapping("/auth/refresh")
ResponseEntity<TokenResponse> refresh(@CookieValue("rt") String raw, HttpServletRequest req) {
    var next = refreshTokens.rotate(raw, ClientInfo.from(req));
    String access = accessTokens.issueFor(next.entity().getUserId());
    ResponseCookie cookie = ResponseCookie.from("rt", next.rawToken())
            .httpOnly(true).secure(true).sameSite("Strict")
            .path("/auth").maxAge(Duration.ofDays(14)).build();
    return ResponseEntity.ok()
            .header(HttpHeaders.SET_COOKIE, cookie.toString())
            .body(new TokenResponse(access, "Bearer", 600));
}

Keep the refresh token in an HttpOnly, Secure, SameSite=Strict cookie scoped to /auth, and the access token in JavaScript memory only. localStorage is readable by any script running on the origin, so a single XSS bug (or a compromised npm dependency) exfiltrates long-lived tokens that keep working after the tab closes. Because this endpoint is cookie-authenticated, it needs CSRF thinking too: SameSite=Strict plus a required custom header or CSRF token. The safest arrangement for SPAs is the backend-for-frontend (BFF): a small server-side component performs the OAuth flows and keeps all tokens, and the browser holds only a session cookie (L350).

Logout, logout everywhere and token versions

  • Logout on one device: revoke that family and clear the cookie. The current access token lives on for its few remaining minutes.
  • Logout everywhere (password change, "I lost my phone", admin action): revoke all of the user's families and increment users.token_version.
  • Token version: access tokens carry a ver claim; resource servers compare it with the user's current version (cached for a few seconds), so old access tokens die immediately instead of at expiry.
  • Device management: the family table is already a list of sessions; show device, location from IP, and last use, each with a "sign out" button.

Sliding versus absolute expiry, and parallel tabs

Sliding expiry extends the idle window on every refresh (active users stay signed in); absolute expiry caps the family's total life (everyone re-authenticates eventually, say after 90 days). Use both, as the service above does. Refresh races are the practical headache: two tabs notice an expired access token at the same moment and both send the same refresh token; the second looks exactly like reuse and logs the user out. Fix it on the client first (a single in-flight refresh shared across tabs with the Web Locks API or a BroadcastChannel), and optionally on the server with a short grace window (a few seconds) in which the just-replaced token returns the same new pair instead of triggering revocation. The grace window slightly weakens detection, so keep it short.

What breaks in production
  • Refresh tokens stored in plaintext: a database read is a session takeover for every user.
  • Rotation without reuse detection: the attacker and the user both keep refreshing indefinitely.
  • Reuse detection without a fix for parallel tabs: users with two tabs are randomly logged out, and support disables detection.
  • "Logout everywhere" that revokes refresh tokens but not access tokens, leaving a 15-minute window after a password reset.

Practice · 50 min

  2. Replay an old refresh token and verify the family is revoked and an audit event is written.
  3. Fire two concurrent refreshes with the same token; observe the race, then add the grace window and test again.
  4. Add a ver claim and a version check in the resource server; prove "logout everywhere" kills a live access token.

OAuth2 & OpenID Connect Fundamentals

50m video40m practice

OAuth2 lets a user grant an application limited access to an API without giving it their password; the application receives an access token, never the credentials. OpenID Connect adds the missing piece, a signed statement of who the user is. Almost every modern login and API integration is the authorization code flow with PKCE, so learn that one flow message by message.

Four roles, and what problem they solve

Definition

The resource owner is the user who owns the data. The client is the application that wants access (a web backend, an SPA, a mobile app, a CLI). The authorization server authenticates the user, asks for consent, and issues tokens. The resource server is the API that accepts access tokens. Before OAuth, a "contacts importer" asked for your email password and could do anything with it, forever. OAuth replaces that with a token limited by scope, lifetime and audience, revocable without changing the password.

The crucial distinction: OAuth2 is authorization. An access token says "the bearer may call this API with these scopes"; it is not, by itself, proof of who is at the keyboard, and the client is not even meant to parse it. OIDC is authentication: it adds an ID token, a JWT addressed to the client that states who the user is, when and how they authenticated.

state, nonce and PKCE

  • state: a random value the client stores in the user's session and checks on the redirect back. It stops login CSRF, where an attacker makes your browser complete their authorization response so you end up logged in as them.
  • nonce (OIDC): a random value echoed inside the ID token. The client rejects ID tokens whose nonce does not match the request it made, which blocks replay and injection of ID tokens.
  • PKCE (RFC 7636): the client invents a random code_verifier and sends only its SHA-256 hash as code_challenge. Redeeming the code requires the verifier, so a code stolen from a redirect (a malicious app registered for the same URL scheme, a leaky log) is useless to anyone else.
record Pkce(String verifier, String challenge) {
    static Pkce generate() throws NoSuchAlgorithmException {
        byte[] bytes = new byte[32];
        new SecureRandom().nextBytes(bytes);
        var b64 = Base64.getUrlEncoder().withoutPadding();
        String verifier = b64.encodeToString(bytes);                              // 43 characters
        byte[] hash = MessageDigest.getInstance("SHA-256").digest(verifier.getBytes(StandardCharsets.US_ASCII));
        return new Pkce(verifier, b64.encodeToString(hash));                      // S256 challenge
    }
}

Scopes, claims, authorities

Scopes are what the client asks to do on the user's behalf (orders:read), shown on the consent screen and recorded in the access token. Claims are statements about the user (email, name, a tenant id) in the ID token or from UserInfo. Authorities are Spring's internal strings derived from either: by default the resource server maps each scope to SCOPE_orders:read, and you write converters for role claims (L351). Scopes limit the client; they do not replace the user's own permissions, so an API checks both.

What OIDC adds

The ID token is a JWT with iss, sub (stable user id at that issuer), aud (the client id), exp, iat, nonce, and often auth_time and amr (how the user authenticated). The UserInfo endpoint returns profile claims for an access token. Discovery at {issuer}/.well-known/openid-configuration lists every endpoint (authorization_endpoint, token_endpoint, jwks_uri, userinfo_endpoint, end_session_endpoint), which is why Spring needs only an issuer-uri. Standard scopes: openid (required), profile, email, address, phone, and offline_access for a refresh token.

Never call an API with an ID token

The ID token's audience is the client; it tells the client who logged in. APIs must accept only access tokens issued for their audience. An API that accepts ID tokens accepts any token minted for any client of that issuer, including a malicious one.

What breaks in production
  • Treating "has a valid access token" as "is this user": the token may have been issued to a different client, or with no user at all (client credentials).
  • Using the email claim as the user key: emails change and may be unverified; key accounts on iss + sub.
  • Loose redirect URI matching at the authorization server (prefixes, wildcards): codes are delivered to attacker URLs.
  • SPAs still on the implicit flow because "it worked".

OAuth2 Resource Server: Protecting Your API

45m video50m practice

A resource server's whole job is to turn a bearer token into a trustworthy Authentication: verify it locally (JWT) or ask the authorization server about it (opaque), check that it was meant for this API, and map its claims to authorities. Spring does each step; you decide the validators, the mapping and what happens when a call fans out to other services.

Two validation modes

JWT mode

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://sso.example/realms/shop     # discovery: finds jwks_uri, validates iss
          audiences: orders-api                           # aud must contain this
          # jwk-set-uri: https://sso.example/.../certs    # no discovery; set issuer-uri too to check iss
          # public-key-location: classpath:issuer.pub     # a single static RSA key
Definition

With issuer-uri, Spring fetches the issuer's metadata, takes its jwks_uri, caches the signing keys (refetching when an unknown kid appears), and validates exp/nbf with 60 seconds of clock skew plus iss. Boot defers the discovery call until the first request, so the API can start while the IdP is down. With jwk-set-uri no discovery happens; with public-key-location one static key is used. The decoder is the place for anything stricter:

@Bean
JwtDecoder jwtDecoder(@Value("${spring.security.oauth2.resourceserver.jwt.issuer-uri}") String issuer) {
    NimbusJwtDecoder decoder = JwtDecoders.fromIssuerLocation(issuer);   // discovery happens here
    OAuth2TokenValidator<Jwt> audience = new JwtClaimValidator<List<String>>(
            JwtClaimNames.AUD, aud -> aud != null && aud.contains("orders-api"));
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
            new JwtTimestampValidator(Duration.ofSeconds(30)),   // tighter skew than the default
            new JwtIssuerValidator(issuer),
            audience));
    return decoder;
}

Note that setJwtValidator replaces the defaults, which is why the timestamp and issuer validators are listed again. JwtValidators.createDefaultWithIssuer(issuer) gives you those two in one call.

Spring's OpaqueTokenIntrospector (SpringOpaqueTokenIntrospector) performs the RFC 7662 call and builds a principal from the response; "active": false becomes a 401. One network round trip per request is expensive, so cache positive results briefly. The cache TTL is exactly how long a revoked token keeps working, so keep it short and never longer than the token's own exp:

@Bean
OpaqueTokenIntrospector introspector(OAuth2ResourceServerProperties props) {
    var o = props.getOpaquetoken();
    var delegate = new SpringOpaqueTokenIntrospector(o.getIntrospectionUri(), o.getClientId(), o.getClientSecret());
    Cache<String, OAuth2AuthenticatedPrincipal> cache = Caffeine.newBuilder()
            .expireAfterWrite(Duration.ofSeconds(30)).maximumSize(10_000).build();
    return token -> cache.get(token, t -> delegate.introspect(t));   // failures are thrown, not cached
}

Claims to authorities

By default each entry of the scope or scp claim becomes SCOPE_…, so rules read hasAuthority("SCOPE_orders:read"). For roles in a flat claim, use JwtGrantedAuthoritiesConverter with setAuthoritiesClaimName("roles") and setAuthorityPrefix("ROLE_"). Keycloak nests realm roles under realm_access.roles, which needs a small converter; combine it with scopes:

@Bean
JwtAuthenticationConverter jwtAuthenticationConverter() {
    Converter<Jwt, Collection<GrantedAuthority>> realmRoles = jwt -> {
        Map<String, Object> realm = jwt.getClaimAsMap("realm_access");
        if (realm == null || !(realm.get("roles") instanceof Collection<?> roles)) return List.of();
        return roles.stream().map(r -> (GrantedAuthority) new SimpleGrantedAuthority("ROLE_" + r)).toList();
    };
    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(
            new DelegatingJwtGrantedAuthoritiesConverter(new JwtGrantedAuthoritiesConverter(), realmRoles));
    converter.setPrincipalClaimName("preferred_username");   // getName() returns this instead of sub
    return converter;
}

Multiple issuers and downstream calls

A multi-tenant API trusting several issuers (one realm per customer, or a migration between IdPs) uses JwtIssuerAuthenticationManagerResolver.fromTrustedIssuers("https://sso.example/realms/a", "https://sso.example/realms/b") passed to oauth2ResourceServer(o -> o.authenticationManagerResolver(resolver)). It reads iss only to pick an issuer from the allowlist, then fully verifies the token with that issuer's keys; never build the issuer list from the token itself.

When the API calls another service on the user's behalf, the simplest option is to relay the token:

@Bean
RestClient inventoryClient(RestClient.Builder builder) {
    return builder.baseUrl("https://inventory.internal")
            .requestInterceptor((request, body, execution) -> {
                if (SecurityContextHolder.getContext().getAuthentication() instanceof JwtAuthenticationToken jwt) {
                    request.getHeaders().setBearerAuth(jwt.getToken().getTokenValue());
                }
                return execution.execute(request, body);
            })
            .build();
}

Relaying requires the token's audience to include the downstream service, which pushes tokens toward broad audiences and scopes. The cleaner alternative is token exchange (RFC 8693): trade the incoming token at the authorization server for a new one scoped to the downstream audience; recent Spring Security versions support the token-exchange grant as an OAuth2 client. For calls that are not on behalf of a user, use the service's own client-credentials token.

Bearer errors

HTTP/1.1 403 Forbidden

What breaks in production
  • No audience check: any token from your IdP, issued to any client, is accepted by every API.
  • Calling setJwtValidator with only an audience validator, silently dropping expiry and issuer checks.
  • An introspection cache with a 10-minute TTL that makes "revoke now" mean "revoke in 10 minutes".
  • Relaying the user's token to a third-party service, which can now replay it against your other APIs.

Spring Authorization Server: Running Your Own IdP

50m video60m practice

Spring Authorization Server implements the authorization-server side of OAuth 2.1 and OpenID Connect as Spring Security filters, so you can issue tokens to your own clients with the same flows the big providers use. Running an identity provider is an operational commitment (keys, recovery, MFA, availability), so first be sure you need one.

Build or buy

Reasons to run your own: several first-party apps that need single sign-on and shared tokens, third parties calling your API with user consent, data-residency or regulatory constraints, deep customization of login, or avoiding a vendor's pricing and lock-in. Reasons not to: Keycloak (L353) gives you a full self-hosted IdP with admin UI, MFA and federation; Auth0, Okta, Cognito and Microsoft Entra ID run it for you. With your own server you own password storage, MFA, account recovery, brute-force protection, key rotation, patching and uptime; every client in the company is down when it is.

Setup and default endpoints

Add spring-boot-starter-oauth2-authorization-server (Boot 3.1+). Clients can be declared under spring.security.oauth2.authorizationserver.client.*, but beans give you full control:

@Configuration
class AuthServerConfig {

    @Bean
    @Order(1)
    SecurityFilterChain authorizationServer(HttpSecurity http) throws Exception {
        OAuth2AuthorizationServerConfiguration.applyDefaultSecurity(http);       // protocol endpoints
        http.getConfigurer(OAuth2AuthorizationServerConfigurer.class)
            .oidc(Customizer.withDefaults());                                   // OIDC: discovery, userinfo, logout
        http.exceptionHandling(e -> e.defaultAuthenticationEntryPointFor(
                new LoginUrlAuthenticationEntryPoint("/login"),
                new MediaTypeRequestMatcher(MediaType.TEXT_HTML)))
            .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults()));    // /userinfo takes access tokens
        return http.build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain userLogin(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
            .formLogin(Customizer.withDefaults());                              // how users authenticate
        return http.build();
    }

    @Bean
    AuthorizationServerSettings settings() {
        return AuthorizationServerSettings.builder().issuer("https://auth.shop.example").build();
    }
}

That chain serves /oauth2/authorize, /oauth2/token, /oauth2/jwks, /oauth2/introspect, /oauth2/revoke, /oauth2/device_authorization, /.well-known/oauth-authorization-server and, with OIDC enabled, /.well-known/openid-configuration, /userinfo and /connect/logout. Newer releases deprecate applyDefaultSecurity in favour of http.with(OAuth2AuthorizationServerConfigurer.authorizationServer(), ...) plus a securityMatcher for its endpoints; the behavior is the same.

A public client (SPA or mobile app) uses ClientAuthenticationMethod.NONE with requireProofKey(true); by default the server does not issue refresh tokens to public clients, which is one more argument for a BFF. Beyond clients, two stores matter: OAuth2AuthorizationService (issued codes and tokens, needed for introspection, revocation and refresh) and OAuth2AuthorizationConsentService (what each user approved). The defaults are in memory; use JdbcOAuth2AuthorizationService and JdbcOAuth2AuthorizationConsentService with the schema scripts shipped in the jar, or every restart logs everyone out.

Keys and key rotation

@Bean
JWKSource<SecurityContext> jwkSource() throws NoSuchAlgorithmException {   // demo only: new key per start
    KeyPairGenerator gen = KeyPairGenerator.getInstance("RSA");
    gen.initialize(2048);
    KeyPair kp = gen.generateKeyPair();
    RSAKey key = new RSAKey.Builder((RSAPublicKey) kp.getPublic())
            .privateKey((RSAPrivateKey) kp.getPrivate())
            .keyID(UUID.randomUUID().toString())
            .build();
    return new ImmutableJWKSet<>(new JWKSet(key));
}

A key generated at startup invalidates every token on restart and differs between instances. In production, load keys from a keystore, a secret manager or a KMS, and rotate them on a schedule.

Algorithm · Signing-key rotation
  1. Generate key N+1 and add it to the published JWKS next to key N; keep signing with N.
  2. Wait at least as long as resource servers cache the JWKS, so every verifier knows N+1.
  3. Switch signing to N+1, selecting it explicitly by kid (an encoder that sees two matching keys refuses to choose).
  4. Keep N published until the longest-lived token signed with it has expired, then remove it.

Custom claims, federation and consent

@Bean
OAuth2TokenCustomizer<JwtEncodingContext> tokenCustomizer() {
    return ctx -> {
        if (OAuth2TokenType.ACCESS_TOKEN.equals(ctx.getTokenType())
                && ctx.getPrincipal().getPrincipal() instanceof AppUserPrincipal user) {
            ctx.getClaims()
               .claim("tenant", user.getTenantId())
               .claim("roles", user.getAuthorities().stream().map(GrantedAuthority::getAuthority).toList());
        }
    };
}

The instanceof check skips client-credentials tokens, where the principal is the client. For federated login, add oauth2Login to the user-login chain so users can sign in with Google or a corporate IdP (L350) and map that identity to a local user before tokens are issued. For third-party clients, keep consent on and point authorizationEndpoint(a -> a.consentPage("/oauth2/consent")) at your own page listing the requested scopes in plain language. Your SPA or mobile app then runs the code flow with PKCE against this issuer, and the resource server from L351 needs only issuer-uri: https://auth.shop.example.

What breaks in production
  • In-memory authorization and consent services behind a load balancer: codes issued by one node cannot be redeemed at another.
  • Keys regenerated on every deploy: all sessions and tokens die at once, every release.
  • Redirect URIs registered loosely, or localhost URIs left on production clients.
  • Client secrets in source code; load them from a secret store and keep only hashes in the client table.

Keycloak Integration

45m video55m practice

Keycloak is a full open-source identity provider that speaks standard OIDC, so Spring Boot integrates with it through the same resource-server and OAuth2-client support you already know. The Keycloak-specific work is modelling realms, clients and roles correctly, getting the right claims (including the audience) into tokens, and flattening its nested role claims into authorities.

Running it and the model

docker run --name kc -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:26.0 start-dev
# older releases use KEYCLOAK_ADMIN / KEYCLOAK_ADMIN_PASSWORD
# admin console: http://localhost:8080/admin   issuer: http://localhost:8080/realms/shop

start-dev uses an embedded database and HTTP; production uses start with a real database, TLS, a fixed hostname and at least two nodes.

Definition

A realm is an isolated tenant with its own users, clients, keys and issuer URL; never put applications in the master realm, which administers Keycloak itself. A client is an application registered in the realm. A confidential client (client authentication on) has a secret and suits a backend or BFF; a public client (an SPA or mobile app) has none and must use PKCE with S256, set in the client's advanced settings. Realm roles appear in tokens under realm_access.roles; client roles under resource_access.<clientId>.roles. Groups bundle roles; identity providers let users log in through Google or a corporate IdP while Keycloak issues your tokens (brokering).

Client scopes and protocol mappers

What goes into a token is controlled by client scopes (default ones always applied, optional ones when requested) and their protocol mappers. Two mappers matter immediately: a user attribute mapper that copies a tenant_id attribute into a claim, and an audience mapper that adds orders-api to the access token's aud. Without the audience mapper, Keycloak access tokens are not addressed to your API, and the audience validation from L351 correctly rejects them. Keep tokens lean: fine-grained permissions belong in your API, not in dozens of mapped claims.

Spring Boot as a resource server

@Configuration
class KeycloakJwtConfig {
    @Bean
    JwtAuthenticationConverter jwtAuthenticationConverter() {
        var converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(new DelegatingJwtGrantedAuthoritiesConverter(
                new JwtGrantedAuthoritiesConverter(),          // SCOPE_ authorities from "scope"
                keycloakRoles("orders-api")));                 // ROLE_ from realm and client roles
        converter.setPrincipalClaimName("preferred_username");
        return converter;
    }

    static Converter<Jwt, Collection<GrantedAuthority>> keycloakRoles(String clientId) {
        return jwt -> {
            Map<String, Object> resources = jwt.getClaimAsMap("resource_access");
            Stream<Object> clientRoles = resources != null && resources.get(clientId) instanceof Map<?, ?> m
                    ? rolesIn(m) : Stream.empty();
            return Stream.concat(rolesIn(jwt.getClaimAsMap("realm_access")), clientRoles)
                    .distinct()
                    .map(r -> (GrantedAuthority) new SimpleGrantedAuthority("ROLE_" + r))
                    .toList();
        };
    }

    static Stream<Object> rolesIn(Map<?, ?> m) {
        return m != null && m.get("roles") instanceof Collection<?> c ? c.stream().map(o -> (Object) o) : Stream.empty();
    }
}

Local logout alone leaves the Keycloak SSO session alive, so the next login is silent. OidcClientInitiatedLogoutSuccessHandler redirects to the provider's end_session_endpoint with id_token_hint and post_logout_redirect_uri, ending the SSO session. Back-channel logout (supported by Spring Security from 6.2) works the other way: when the user logs out in another app or an admin kills the session, Keycloak POSTs a signed logout token to your app, which invalidates the matching local session.

CORS with Security, Security Headers & TLS

45m video45m practice

CORS, response headers and TLS are where your application meets the browser and the network. Each is a small piece of configuration with one ordering or trust rule that, when missed, produces confusing failures: preflights must be answered before authentication, a Content Security Policy must be rolled out in report-only mode first, and forwarded headers may only be trusted from your own proxy.

CORS and the filter chain

A browser script on https://app.shop.example calling https://api.shop.example with a JSON body or an Authorization header first sends a preflight OPTIONS request, without cookies or credentials, asking whether the real request is allowed. If authentication runs first, the preflight gets 401 without CORS headers and the browser reports a "CORS error". http.cors(Customizer.withDefaults()) puts CorsFilter near the start of the chain, ahead of authentication; it answers valid preflights itself and adds CORS headers to actual responses, using your CorsConfigurationSource bean.

@Bean
CorsConfigurationSource corsConfigurationSource() {
    var cfg = new CorsConfiguration();
    cfg.setAllowedOrigins(List.of("https://app.shop.example"));          // exact origins, no "*"
    cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    cfg.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-XSRF-TOKEN"));
    cfg.setExposedHeaders(List.of("Location", "Retry-After"));
    cfg.setAllowCredentials(true);                                      // cookies; forbids "*" origins
    cfg.setMaxAge(Duration.ofHours(1));                                 // cache the preflight
    var source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", cfg);
    return source;
}
// http.cors(Customizer.withDefaults())

Debugging: the browser hides the real status of a failed cross-origin response, and error responses (a 401 from the entry point, a 500) often lack CORS headers, so a "CORS error" is frequently an authentication or server error in disguise. Read the status in the network tab, or reproduce with curl:

curl -i -X OPTIONS https://api.shop.example/api/orders \
  -H "Origin: https://app.shop.example" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization,content-type"

Configure CORS in one place: @CrossOrigin on controllers, a global WebMvcConfigurer or CorsConfigurationSource, or the API gateway. Two layers each adding Access-Control-Allow-Origin produce a duplicated header, which browsers reject.

Security headers

HeaderWriterFilter writes these by default: Cache-Control: no-cache, no-store, max-age=0, must-revalidate (with Pragma and Expires), X-Content-Type-Options: nosniff (no MIME sniffing of uploads into scripts), X-Frame-Options: DENY (no framing, against clickjacking), Strict-Transport-Security on HTTPS responses, and X-XSS-Protection: 0. That last value deliberately disables the old browser XSS auditor, which was removed from modern browsers and could itself be abused; CSP is the real defense.

http.headers(h -> h
    .httpStrictTransportSecurity(hsts -> hsts.maxAgeInSeconds(31_536_000).includeSubDomains(true).preload(true))
    .frameOptions(f -> f.sameOrigin())
    .referrerPolicy(r -> r.policy(ReferrerPolicyHeaderWriter.ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN))
    .crossOriginOpenerPolicy(c -> c.policy(
        CrossOriginOpenerPolicyHeaderWriter.CrossOriginOpenerPolicy.SAME_ORIGIN))
    .addHeaderWriter(new StaticHeadersWriter("Permissions-Policy", "camera=(), microphone=(), geolocation=()")));

HSTS tells browsers to use HTTPS only for max-age seconds; includeSubDomains extends that to every subdomain, and preload asks to be compiled into browsers' built-in lists, which is hard to undo, so enable it only when every subdomain serves HTTPS. Referrer-Policy stops full URLs (with ids or tokens) leaking to other sites. Permissions-Policy switches off powerful browser features you do not use. Cross-Origin-Opener-Policy, -Embedder-Policy and -Resource-Policy isolate your pages and resources from other origins' windows and embeds.

Content Security Policy

Definition

A Content Security Policy tells the browser which sources may supply scripts, styles, images, frames and connections for a page. An XSS payload injected as <script> then fails to run unless it matches the policy. A nonce policy allows only script tags carrying a fresh random nonce attribute issued with that response; a hash policy allows inline scripts whose SHA-256 matches a listed hash. frame-ancestors in CSP supersedes X-Frame-Options.

class CspNonceFilter extends OncePerRequestFilter {
    private final SecureRandom random = new SecureRandom();

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        byte[] bytes = new byte[16];
        random.nextBytes(bytes);
        String nonce = Base64.getEncoder().encodeToString(bytes);
        req.setAttribute("cspNonce", nonce);                    // template: <script nonce="${cspNonce}">
        res.setHeader("Content-Security-Policy-Report-Only",    // switch to Content-Security-Policy when clean
            "default-src 'self'; script-src 'nonce-" + nonce + "' 'strict-dynamic'; object-src 'none'; "
            + "base-uri 'none'; frame-ancestors 'none'; form-action 'self'; report-uri /csp-reports");
        chain.doFilter(req, res);
    }
}
// http.addFilterBefore(new CspNonceFilter(), HeaderWriterFilter.class)

Roll it out in report-only mode: browsers report violations to your endpoint without blocking anything. Fix or allowlist each legitimate source (analytics, fonts, inline handlers that must become scripts), then switch to the enforcing header and keep reporting on. For pure JSON APIs, default-src 'none'; frame-ancestors 'none' is enough.

TLS, proxies and forwarded headers

A server presents its certificate chain: the leaf certificate for the hostname plus the intermediates up to a root the client already trusts; a missing intermediate works in some browsers and fails in Java clients. Let's Encrypt issues short-lived certificates through the ACME protocol, so renewal must be automated. Most deployments terminate TLS at the load balancer or ingress; terminating in the app (Boot's server.ssl.* or SSL bundles under spring.ssl.bundle.*) is common for end-to-end encryption. mTLS adds client certificates so services authenticate each other; service meshes automate issuing and rotating them.

server:
  forward-headers-strategy: native     # Tomcat RemoteIpValve; "framework" uses Spring's ForwardedHeaderFilter
  tomcat:
    remoteip:
      internal-proxies: 10\.0\.\d{1,3}\.\d{1,3}   # only trust X-Forwarded-* from these addresses

Behind a TLS-terminating proxy the app sees plain HTTP from the proxy's address. With forwarded headers honored, request.isSecure(), redirects, OAuth2 {baseUrl} and the client IP are correct; without them, HTTPS redirects loop and HSTS is never written. With them honored from anyone, a client can spoof its IP and scheme. To force HTTPS in the app, requiresChannel(c -> c.anyRequest().requiresSecure()) redirects plain-HTTP requests (newer Spring Security versions offer redirectToHttps instead); it only works once forwarded headers are configured.

What breaks in production
  • allowedOrigins("*") with credentials (rejected at startup) "fixed" with allowedOriginPatterns("*"), which lets any site make credentialed calls.
  • CORS configured in both the gateway and the app: duplicated headers, every cross-origin call fails.
  • An enforced CSP shipped without a report-only phase, breaking checkout scripts on launch day.
  • HSTS preload enabled while an internal subdomain still serves HTTP only.

Practice · 45 min

  1. Serve a page from another port that calls your API; reproduce the preflight 401, then fix it with http.cors.
  2. Compare response headers before and after the header configuration with curl -I, and score the site with a header-checking tool.
  3. Deploy the nonce CSP in report-only mode, collect reports, fix the violations, and enforce it.
  4. Put the app behind a local TLS-terminating proxy (nginx or Caddy); verify scheme, client IP and redirects with and without forwarded-header support.

Rate Limiting, Brute Force Protection & Audit Logging

45m video50m practice

Most attacks on authentication are volume attacks: millions of leaked passwords tried against your login, ids enumerated, expensive endpoints hammered. Rate limits and failed-login throttling make volume expensive, and an audit trail makes what got through visible. All three are security controls first and capacity controls second.

Why rate limiting is a security control

Without limits, a login endpoint is an oracle for credential stuffing, a password-reset endpoint is an email bomb, a search endpoint is a scraping API, and an endpoint that hashes passwords or renders PDFs is a cheap way to burn your CPU. OWASP's API list names this "unrestricted resource consumption" and "unrestricted access to sensitive business flows" (L356).

Implementation with Bucket4j

class RateLimitFilter extends OncePerRequestFilter {
    private static final long LIMIT = 60;
    private final Cache<String, Bucket> buckets = Caffeine.newBuilder()      // bounded: no memory leak
            .expireAfterAccess(Duration.ofMinutes(10)).maximumSize(100_000).build();

    private Bucket newBucket(String key) {                                   // Bucket4j 8.x builder API
        return Bucket.builder().addLimit(l -> l.capacity(LIMIT).refillGreedy(LIMIT, Duration.ofMinutes(1))).build();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        String key = auth != null && !(auth instanceof AnonymousAuthenticationToken)
                ? "user:" + auth.getName() : "ip:" + req.getRemoteAddr();
        ConsumptionProbe probe = buckets.get(key, this::newBucket).tryConsumeAndReturnRemaining(1);
        res.setHeader("RateLimit-Limit", Long.toString(LIMIT));
        res.setHeader("RateLimit-Remaining", Long.toString(probe.getRemainingTokens()));
        if (probe.isConsumed()) {
            chain.doFilter(req, res);
            return;
        }
        long wait = Math.max(1, TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill()));
        res.setHeader("Retry-After", Long.toString(wait));
        res.setHeader("RateLimit-Reset", Long.toString(wait));
        res.setStatus(429);
        res.setContentType(MediaType.APPLICATION_PROBLEM_JSON_VALUE);
        res.getWriter().write("{\"title\":\"Too Many Requests\",\"status\":429}");
    }
}
// http.addFilterAfter(new RateLimitFilter(), AnonymousAuthenticationFilter.class)   // user is known here

This keeps buckets in one JVM; with several instances each enforces its own share. For a distributed limit, Bucket4j's proxy managers keep bucket state in Redis, Hazelcast or a database with atomic compare-and-swap, at the cost of a network call per request. 429 Too Many Requests with Retry-After is standard HTTP; the RateLimit-* headers come from an IETF draft that clients increasingly understand. A Spring MVC HandlerInterceptor works as well when limits depend on the matched handler.

Keys: limit by user for authenticated traffic, by API key for partners, and by IP for anonymous traffic. Weight expensive endpoints (tryConsume(10) for an export). IP limits have a shared-NAT problem: a university, a mobile carrier's carrier-grade NAT or a corporate proxy puts thousands of users behind one address, so IP limits must be generous, and IPv6 clients should be grouped by /64 prefix. Behind a proxy, getRemoteAddr() is only the real client once forwarded headers are configured (L354). Limit coarsely at the gateway or CDN, which absorbs floods before they reach the JVM, and finely in the app, which knows the user and what an endpoint costs.

Brute-force protection on login

@Component
class LoginThrottle {
    private final Cache<String, AtomicInteger> failures = Caffeine.newBuilder()
            .expireAfterWrite(Duration.ofMinutes(15)).maximumSize(1_000_000).build();

    @EventListener
    void onFailure(AuthenticationFailureBadCredentialsEvent e) {
        for (String k : keys(e.getAuthentication())) failures.get(k, x -> new AtomicInteger()).incrementAndGet();
    }

    @EventListener
    void onSuccess(AuthenticationSuccessEvent e) {
        failures.invalidate("user:" + e.getAuthentication().getName().toLowerCase(Locale.ROOT));
    }

    /** Seconds the caller must wait before another attempt: exponential after five failures. */
    long delaySeconds(String username, String ip) {
        int n = Math.max(count("user:" + username.toLowerCase(Locale.ROOT)), count("ip:" + ip) / 10);
        return n < 5 ? 0 : Math.min(900, 1L << Math.min(n - 5, 10));
    }

    private int count(String k) { AtomicInteger c = failures.getIfPresent(k); return c == null ? 0 : c.get(); }

    private static List<String> keys(Authentication a) {
        String user = "user:" + a.getName().toLowerCase(Locale.ROOT);
        return a.getDetails() instanceof WebAuthenticationDetails d
                ? List.of(user, "ip:" + d.getRemoteAddress()) : List.of(user);
    }
}

A small filter in front of the login URL consults delaySeconds and, when it is positive, returns the same 401 as a wrong password plus Retry-After. Counting per username stops a targeted attack; counting per IP (with a higher threshold) stops one source spraying many usernames. Prefer progressive delays and a temporary lock over a permanent one, and publish the policy. Every choice has an enumeration angle: an "account locked" message for existing users only reveals which emails are registered, and hard lockout lets an attacker lock victims out deliberately. Notify the account owner by email instead. CAPTCHA is a last resort: it hurts accessibility and is solved cheaply by commercial services.

Against credential stuffing specifically: reject breached passwords at registration (L339), offer or require MFA, flag logins from new devices, and alert on anomalies such as one IP trying hundreds of usernames, a sudden rise in the failure ratio, or impossible travel between logins.

Audit logging

Definition

An audit record answers who (user id, client id, impersonator if any), what (action and target resource id), when (UTC timestamp), from where (IP, user agent, request or trace id) and with what outcome (success, failure, denied, with a reason code). Record authentication events, authorization denials, privilege and role changes, password and MFA changes, data exports and administrative actions.

Make it tamper-resistant: write to an append-only store or ship to a separate SIEM that application admins cannot edit, optionally hash-chain records, and restrict who can read them. Set retention by policy and regulation, then delete on schedule. Never log passwords, tokens, session ids, API keys, full card numbers or reset links, and neutralize log injection by using structured (JSON) logging rather than concatenating user input into lines. Spring Boot Actuator offers an AuditEventRepository fed by authentication events, useful as a starting point but not a durable audit store.

What breaks in production
  • An unbounded ConcurrentHashMap of buckets keyed by IP: an attacker rotating addresses exhausts the heap.
  • IP-based limits behind a proxy without forwarded headers: every user shares the proxy's bucket and the site rate-limits itself.
  • Lockout that responds differently for real accounts, turning protection into enumeration.
  • Audit logs on the same database the attacker just compromised, edited along with everything else.

Practice · 50 min

  1. Add the rate-limit filter, hammer an endpoint with a load tool, and check the 429s and headers; then move bucket state to Redis.
  2. Implement LoginThrottle plus the pre-login filter; test per-user and per-IP thresholds and identical responses for real and fake users.
  3. Write an audit listener for login success and failure, authorization denial and role changes, producing structured JSON records.
  4. Run a credential-stuffing simulation (1,000 usernames, one password each) and design the alert that would catch it.

Encryption at rest

Definition · envelope encryption

Data is encrypted with a data key; the data key is encrypted ("wrapped") by a master key that never leaves the KMS. Only the wrapped data key is stored. The app asks the KMS to unwrap it at startup, so a database leak yields only ciphertext, and rotating the master key means re-wrapping one small key rather than every row.

@Converter   // Boot lets Hibernate obtain converters from Spring, so the key can be injected
public class EncryptedStringConverter implements AttributeConverter<String, String> {
    private static final SecureRandom RANDOM = new SecureRandom();
    private final SecretKey dataKey;
    public EncryptedStringConverter(SecretKey dataKey) { this.dataKey = dataKey; }

    @Override
    public String convertToDatabaseColumn(String plain) {
        if (plain == null) return null;
        byte[] iv = new byte[12];
        RANDOM.nextBytes(iv);
        byte[] ct = run(Cipher.ENCRYPT_MODE, iv, plain.getBytes(StandardCharsets.UTF_8));
        return Base64.getEncoder().encodeToString(ByteBuffer.allocate(12 + ct.length).put(iv).put(ct).array());
    }

    @Override
    public String convertToEntityAttribute(String stored) {
        if (stored == null) return null;
        byte[] all = Base64.getDecoder().decode(stored);
        byte[] pt = run(Cipher.DECRYPT_MODE, Arrays.copyOf(all, 12), Arrays.copyOfRange(all, 12, all.length));
        return new String(pt, StandardCharsets.UTF_8);
    }

    private byte[] run(int mode, byte[] iv, byte[] input) {
        try {
            Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
            c.init(mode, dataKey, new GCMParameterSpec(128, iv));
            return c.doFinal(input);
        } catch (GeneralSecurityException e) { throw new IllegalStateException(e); }
    }
}
// @Convert(converter = EncryptedStringConverter.class) private String taxId;

Never reuse an IV with the same GCM key. Encrypted columns cannot be indexed or searched; for equality lookups store a keyed HMAC of the value (a "blind index").
