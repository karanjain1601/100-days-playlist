Databases, SQL & JDBC

Phase 9 teaches the relational database the way a backend engineer uses it: data modeling, SQL from simple filters to window functions, indexes and query plans, transactions and locking, and raw JDBC. Every exercise runs against real PostgreSQL, using the Testcontainers skills from Phase 8, and the JDBC data layer you build at the end is the baseline that JPA and Hibernate must match, statement for statement, in Phase 10.

By the end of this phase you can

  • Turn a domain into an ER diagram and then a normalized PostgreSQL schema with deliberate keys, column types and named constraints.
  • Write correct SQL for joins, aggregates, subqueries, recursive CTEs and window functions, including NULL-safe filters and keyset pagination.
  • Design composite, partial, covering and expression indexes, and justify each one with EXPLAIN (ANALYZE, BUFFERS).
  • Reproduce lost updates, write skew and deadlocks in two sessions, and fix them with the right isolation level, locks or version columns.
  • Change a live schema without downtime using expand–contract migrations, concurrent index builds and batched backfills.
  • Build a JDBC data layer with transactions, batching, streaming, HikariCP pooling and SQL that injection can't alter.
  • Decide when partitioning, read replicas or sharding is the right next step, and what each one costs.

L199 · DAY 199

The Relational Model & ER Modeling

40m video40m practice

A relational schema states facts as rows in tables and ties tables together with keys. Most of your backend's correctness is settled when you choose the entities, keys and cardinalities, long before any Java is written.

Relations, tuples, attributes, domains

Definition · Codd's vocabulary
  • Domain: the set of values an attribute may take (integers, ISO country codes, non-negative money amounts).
  • Attribute: a named column with a domain.
  • Tuple: one assignment of values to the attributes, a row. Each tuple states one fact: "user 42 has email a@b.com".
  • Relation: a set of tuples with the same attributes, a table. Being a set, it has no row order and no duplicate rows.

SQL bends the theory in two places you will meet often. A table is a bag: without a key it can hold duplicate rows, and SELECT returns duplicates unless you ask for DISTINCT. And SQL has NULL, which needs three-valued logic (L204). Rows also have no order: a query without ORDER BY may return them in any order, and that order can change between runs.

Why relational databases still dominate backend work. You describe what you want and the optimizer picks access paths, so new questions don't need new code paths. Transactions make multi-row changes atomic. Constraints enforce invariants for every client, not only your service. And because the data is normalized and joined at query time, you can answer questions nobody planned for when the schema was designed. Fifty years of tooling (replication, backups, query planners, ORMs, drivers) comes with it. Document and key-value stores win for particular access patterns, but a typical system of record (orders, money, inventory) is relational, and PostgreSQL now covers many document use cases with jsonb.

Keys

Definition · Keys
  • Superkey: any set of columns whose values are unique per row.
  • Candidate key: a minimal superkey (drop any column and it stops being unique). A table can have several: users.id and users.email.
  • Primary key: the candidate key you choose as the row's identity. It must be unique and not null, and other tables point at it. Enforce the remaining candidate keys with UNIQUE.
  • Composite key: a key of two or more columns, e.g. (order_id, line_no).
  • Foreign key: columns whose values must match a key in another (or the same) table. It is how a relationship is stored.
ChoiceExampleForAgainst
Natural keyISO currency code, ISBN, emailmeaningful; saves a lookup join; no extra columnreal-world values change (people change email) and every referencing row must change with them; often wider than 8 bytes
Surrogate keybigint identity, UUIDnever changes; compact; uniform across tables; what ORMs expectcarries no meaning, so you still need a UNIQUE on the natural candidate key or duplicates creep in

The usual rule: surrogate primary keys for entities, plus UNIQUE constraints on the natural keys. Natural keys work for small, stable code tables (currency(code char(3))) and composite keys suit junction tables. L215 returns to bigint vs UUID.

Cardinality and how each kind is stored

A relationship lives in a foreign key, and where you put the foreign key decides the cardinality.

  • One-to-many (a user has many orders): foreign key on the "many" side, orders.user_id → users.id. This is the default shape.
  • One-to-one (a user has at most one cart): a foreign key with a UNIQUE constraint, or a shared primary key where user_profile.user_id is both PK and FK. Ask first whether it should just be columns of the same table; split only for optionality, size (large rarely-read blobs), or different access rights.
  • Many-to-many (products in categories, if a product may sit in several): a junction table holding two foreign keys, with their pair as the primary key. Columns that describe the link (quantity, position, added_at) belong on the junction table.
-- 1:N   the FK sits on the many side
CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users(id)
);
-- 1:1   FK + UNIQUE: at most one cart per user
CREATE TABLE carts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL UNIQUE REFERENCES users(id)
);
-- M:N   junction table; the composite PK forbids duplicate links
CREATE TABLE product_categories (
  product_id  bigint NOT NULL REFERENCES products(id),
  category_id bigint NOT NULL REFERENCES categories(id),
  PRIMARY KEY (product_id, category_id)
);

ER diagrams and crow's foot notation

An entity-relationship diagram draws entities as boxes (with their attributes listed inside on detailed diagrams) and relationships as lines. Chen's original 1976 notation used diamonds for relationships; crow's foot (Information Engineering) notation, used by most tools, marks cardinality on the line ends. Each end has two marks: the inner one (next to the box) is the maximum, the outer one the minimum. A bar means one, a ring means zero, and the three-pronged foot means many.

Modeling the e-commerce domain

Walk through the nouns from the figure and question every line on the diagram:

  • users / addresses: 1:N, since people keep a home and a work address. A is_default flag needs a rule that at most one address per user is the default (a partial unique index, L212).
  • carts / cart_items vs orders / order_items: keep them separate. A cart is mutable and disposable; an order is a legal record. Checkout copies cart rows into order rows inside one transaction.
  • order_items stores unit_price and product_name at the time of purchase. Referencing products.price would silently reprice past orders. Orders likewise snapshot the shipping address instead of pointing at a row the user can edit.
  • payments: 1:N, because attempts fail and get retried, and refunds are extra rows. Use a status column, never a boolean paid.
  • shipments: 1:N, because orders split across warehouses. Which items went in which parcel is another junction (shipment_items).
  • categories: a self-referencing tree, with product to category as 1:N or M:N depending on the business.

Running heavy reports on the primary OLTP database competes with checkout for CPU, I/O and buffer cache. The usual path is a read replica first (L220), then a separate warehouse.

What breaks in production
  • Mutable natural key as PK. Email as the primary key turns "change my email" into an update across every referencing table, under locks.
  • Live references instead of snapshots. An invoice that joins to products.price changes when marketing edits the price.
  • Junction table without a composite key. The same product lands in a category twice and every count is wrong.
  • Polymorphic foreign keys (owner_type + owner_id pointing at different tables) can't be declared as FKs, so orphans pile up unnoticed.

  2. List every candidate key of users, products, order_items and cart_items. Choose a primary key for each and say which other candidates become UNIQUE constraints.
  3. Add wishlists (a user has many named lists; a list holds many products; a product sits on many lists). Write the logical tables with keys.
  4. Decide whether product to category is 1:N or M:N for a marketplace and for a single-brand store. Write the DDL for both.

L200 · DAY 200

Installing PostgreSQL & MySQL, and the Tooling

40m video45m practice

A database is a server process you connect to over a socket with a user, a password and a database name. Get one running in a container, learn the client's dozen essential commands, and know which SQL you write is portable and which is dialect.

Running the servers: native and Docker

Native installs suit a long-lived local server: the EDB installer or Postgres.app on Windows/macOS, brew install postgresql@16, or apt install postgresql (add the PGDG apt repository for a specific major version); for MySQL, the MySQL Installer, brew install mysql or apt install mysql-server. For development, containers are easier: one command, a pinned version per project, and nothing left behind.

# PostgreSQL 16, data kept in a named volume
docker run -d --name pg16 -p 5432:5432 \
  -e POSTGRES_PASSWORD=secret -e POSTGRES_DB=shop \
  -v pgdata:/var/lib/postgresql/data postgres:16
docker exec -it pg16 psql -U postgres -d shop

# MySQL 8.4 LTS
docker run -d --name my84 -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=secret -e MYSQL_DATABASE=shop \
  -v mydata:/var/lib/mysql mysql:8.4
docker exec -it my84 mysql -uroot -p shop

Pin the major version (postgres:16, never latest): a new major version cannot open an old data directory without pg_upgrade or a dump and restore. The POSTGRES_* variables only take effect when the volume is empty; changing the password later means ALTER ROLE, not a new environment variable.

GUI tools

DBeaver (free Community edition) and DataGrip (JetBrains; the same engine is in IntelliJ IDEA Ultimate's Database tool window) connect to almost anything through JDBC drivers they download for you; both have ER diagram views, result-grid editing, and visual EXPLAIN. pgAdmin is Postgres-only and adds server administration (roles, backups, monitoring). MySQL Workbench plays the same role for MySQL. Set the GUI to manual commit for production connections, and remember that an open transaction left in a GUI tab holds its locks until you commit or close it.

Databases, roles and grants

Definition · Role and privilege

In Postgres a role is both a user and a group: a role with LOGIN can connect, and granting role A to role B gives B all of A's privileges. A privilege is a right on one object (CONNECT on a database, USAGE on a schema, SELECT on a table). Every object has an owner, who can do anything to it, including DROP.

Never let an application connect as the postgres superuser. A common split is an owner role that runs migrations and an application role limited to DML.

CREATE ROLE shop_owner LOGIN PASSWORD 'owner-secret';
CREATE ROLE shop_app   LOGIN PASSWORD 'app-secret';
CREATE DATABASE shop OWNER shop_owner;
\c shop shop_owner
CREATE SCHEMA app;
GRANT USAGE ON SCHEMA app TO shop_app;
-- tables created later by shop_owner get these grants automatically
ALTER DEFAULT PRIVILEGES IN SCHEMA app
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO shop_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA app
  GRANT USAGE, SELECT ON SEQUENCES TO shop_app;

-- MySQL: users are 'name'@'host'
CREATE USER 'shop_app'@'%' IDENTIFIED BY 'app-secret';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'shop_app'@'%';

Since PostgreSQL 15, ordinary users can no longer create objects in the public schema by default, which is one more reason to create your own schema. In MySQL "database" and "schema" are synonyms.

Why this course standardizes on PostgreSQL. It is open source under a permissive license, close to the SQL standard, and has transactional DDL (a failed migration rolls back cleanly, which MySQL and Oracle don't give you). It has rich types (jsonb, arrays, ranges, uuid), extensions (PostGIS, pg_stat_statements, pgvector), a strong planner, and managed offerings on every cloud. It has also ranked as the most-used database in recent Stack Overflow developer surveys. Where MySQL differs in ways that matter, the lessons say so.

What breaks in production
  • No volume. docker rm on a container without a volume deletes the database.
  • Port clash. A native Postgres already on 5432 answers instead of your container, and you debug the wrong server. Map to -p 5433:5432.
  • Superuser apps. An application connected as postgres can DROP anything and turns any SQL injection into a full compromise.
  • MySQL utf8 is the 3-byte utf8mb3: emoji fail to insert. Use utf8mb4.
  • Oracle's empty string is NULL, so code that works on Postgres can break NOT NULL columns when ported.

L201 · DAY 201

DDL: Databases, Schemas, Tables & Data Types

45m video45m practice

Column types are the first constraint you write: they decide which values can exist, how much each row costs, and which bugs are impossible. Choose exact types for money, timestamptz for instants, and treat every ALTER TABLE on a live table as a locking operation.

Databases, schemas and search_path

Definition · Cluster, database, schema

A Postgres cluster (one server) holds several databases; a connection is bound to exactly one, and a query cannot join across databases. Inside a database, schemas are namespaces: app.orders and audit.orders can coexist, and you can join across schemas freely. An unqualified name is resolved by walking search_path, which defaults to "$user", public.

CREATE DATABASE shop OWNER shop_owner ENCODING 'UTF8';
CREATE SCHEMA IF NOT EXISTS app AUTHORIZATION shop_owner;
SHOW search_path;                               -- "$user", public
ALTER ROLE shop_app SET search_path = app, public;  -- applies to new sessions

Setting search_path per role keeps application SQL unqualified. Migrations and functions should qualify names (app.orders), so they behave the same whatever path the session has.

CREATE TABLE

CREATE TABLE app.products (
  id          bigint        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku         varchar(32)   NOT NULL UNIQUE,
  name        text          NOT NULL,
  price       numeric(12,2) NOT NULL CHECK (price >= 0),
  vat_rate    numeric(4,3)  NOT NULL DEFAULT 0.200,
  gross_price numeric(12,2) GENERATED ALWAYS AS (round(price * (1 + vat_rate), 2)) STORED,
  active      boolean       NOT NULL DEFAULT true,
  tags        text[]        NOT NULL DEFAULT '{}',
  attributes  jsonb         NOT NULL DEFAULT '{}',
  public_id   uuid          NOT NULL DEFAULT gen_random_uuid(),
  image       bytea,
  created_at  timestamptz   NOT NULL DEFAULT now()
);

Each column is name type [column constraints]; table constraints (composite keys, multi-column checks) follow the columns. Other clauses you will meet: IF NOT EXISTS, TEMP (dropped at session end), UNLOGGED (faster writes, no WAL, truncated after a crash), LIKE other_table INCLUDING ALL, and PARTITION BY (L220).

Floating point can't represent 0.1 exactly: SELECT 0.1::float8 + 0.2::float8 = 0.3::float8 is false, and summing a million prices drifts. Money goes in numeric(12,2) (mapped to BigDecimal) or in bigint minor units. Avoid Postgres's money type, whose formatting depends on the server locale. Start ids at bigint: migrating an integer key that is about to pass 2.1 billion means rewriting the table and every foreign key.

Note · Text types in Postgres

text, varchar(n) and varchar use the same storage and perform the same; the docs say so explicitly. varchar(n) only adds a length check (n counts characters, not bytes). char(n) pads with spaces, wastes space and compares in surprising ways, so don't use it. Use varchar(n) where the limit is a real rule (an ISO code, a SKU format), and text otherwise. Widening a varchar or changing it to text needs no table rewrite. MySQL is different: VARCHAR lengths count toward its 65,535-byte row limit, and TEXT columns have indexing and temp-table restrictions.

boolean takes true, false or NULL. Make it NOT NULL with a default unless "unknown" is a real third state, and prefer a status column when a flag is likely to grow a third value.

Time, UUIDs, JSON, arrays, enums, bytes

  • timestamptz stores an absolute instant (internally UTC) and shows it in the session's TimeZone; timestamp stores a wall-clock reading with no zone. The rule from L109: events that happened are instants, so store them as timestamptz, and read them in Java as OffsetDateTime or Instant. Use date for birthdays and business dates, time for opening hours, and interval for durations (now() - interval '30 days'). Avoid timetz.
  • uuid: 16 bytes, native comparison. gen_random_uuid() (v4) is built in since PostgreSQL 13; time-ordered v7 IDs (built in as uuidv7() from 18) are covered in L219.
  • json vs jsonb: json stores the text exactly as written (whitespace, key order, duplicate keys) and reparses it on every access. jsonb stores a parsed binary form: duplicate keys collapse to the last one, key order is not kept, and it supports GIN indexes and operators such as @> and ?. Use jsonb unless you must keep the original bytes.
  • Arrays (text[], bigint[]): fine for small, opaque lists queried with = ANY(tags) or tags @> '{sale}'. If you need to join on the elements or reference them with foreign keys, use a child table.
  • enum: CREATE TYPE order_status AS ENUM ('pending','paid','shipped') stores 4 bytes and rejects typos. ALTER TYPE ... ADD VALUE is cheap, but removing or renaming values is painful. A text column with a CHECK, or a lookup table, is easier to evolve.
  • bytea: binary data, fine for small payloads (hashes, thumbnails). Large files go to object storage with only the key in the database.

ALTER TABLE on a live table

Most ALTER TABLE forms take an ACCESS EXCLUSIVE lock, which conflicts with everything, plain SELECT included. The statement may finish in a millisecond, but it has to acquire the lock first, and while it waits, every later query on the table queues behind it.

L215 turns this into the expand–contract migration recipe.

DROP, TRUNCATE, DELETE; identity and generated columns

  • DELETE FROM t WHERE ... removes rows one at a time: it fires row triggers, checks foreign keys, can use RETURNING, and leaves dead tuples for VACUUM.
  • TRUNCATE t throws away the table's files and starts empty. It is fast at any size, frees space immediately, skips ON DELETE triggers, takes ACCESS EXCLUSIVE, refuses if another table references it (unless CASCADE), and with RESTART IDENTITY resets the counters. In Postgres it is transactional and can be rolled back; in MySQL it commits implicitly.
  • DROP TABLE removes the definition too, along with its indexes, constraints and grants.

Identity columns are the SQL-standard replacement for serial. GENERATED ALWAYS AS IDENTITY rejects explicit values unless the insert says OVERRIDING SYSTEM VALUE; BY DEFAULT accepts them, which suits data imports. Generated columns (GENERATED ALWAYS AS (expr) STORED) are computed on write from other columns of the same row using immutable functions, and can't be written directly. PostgreSQL 18 adds VIRTUAL generated columns, computed on read.

What breaks in production
  • double precision money: invoices off by a cent, and reconciliation that never balances.
  • timestamp without zone written by servers in different time zones: the same instant stored as two different values, and every DST change doubles or skips an hour of data.
  • integer keys running out: inserts fail at 2,147,483,647 and the fix is a rewrite of the biggest table you have.
  • Unguarded ALTER TABLE during traffic: a lock queue outage (figure above).

  3. Insert now() into a timestamp and a timestamptz column, then SET TimeZone = 'Asia/Kolkata' and select both again. Explain the difference.
  4. Store the same object in json and jsonb with a duplicate key and extra whitespace; compare what comes back. Query attributes @> '{"color":"red"}'.
  5. Reproduce the lock queue: in session A run BEGIN; SELECT * FROM products; and leave the transaction open; in B run ALTER TABLE products ADD COLUMN x int; in C run a SELECT. Inspect pg_stat_activity, then retry B with SET lock_timeout = '2s'.

L202 · DAY 202

Constraints: The Database as the Last Line of Defense

40m video45m practice

A constraint is an invariant the database checks on every write, from every client, under every interleaving of concurrent transactions. Application validation gives users friendly messages; constraints keep the data true.

Primary keys, NOT NULL and defaults

PRIMARY KEY means UNIQUE plus NOT NULL, and Postgres enforces it with a unique B-tree index it creates for you (orders_pkey by default). Make every column NOT NULL unless absence is a real, meaningful state: each nullable column is a three-valued-logic hazard in every query that touches it (L204).

DEFAULT is evaluated per inserted row when the column is omitted. Function defaults are common: gen_random_uuid() for public ids, now() for timestamps. Note that now() is the transaction start time, so every row inserted in one transaction gets the same value; clock_timestamp() is the actual time at that moment. A default does not apply when the client explicitly inserts NULL, and pairing it with NOT NULL makes that an error.

CREATE TABLE app.users (
  id         bigint      GENERATED ALWAYS AS IDENTITY,
  public_id  uuid        NOT NULL DEFAULT gen_random_uuid(),
  email      text        NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT users_pk         PRIMARY KEY (id),
  CONSTRAINT users_email_key  UNIQUE (email),
  CONSTRAINT users_public_key UNIQUE (public_id)
);

CREATE TABLE app.order_items (
  order_id   bigint        NOT NULL,
  line_no    smallint      NOT NULL,
  product_id bigint        NOT NULL,
  quantity   integer       NOT NULL,
  unit_price numeric(12,2) NOT NULL,
  CONSTRAINT order_items_pk  PRIMARY KEY (order_id, line_no),
  CONSTRAINT order_items_order_fk   FOREIGN KEY (order_id)
    REFERENCES app.orders (id) ON DELETE CASCADE,
  CONSTRAINT order_items_product_fk FOREIGN KEY (product_id)
    REFERENCES app.products (id) ON DELETE RESTRICT,
  CONSTRAINT order_items_quantity_positive CHECK (quantity > 0),
  CONSTRAINT order_items_price_nonneg      CHECK (unit_price >= 0)
);
CREATE INDEX order_items_product_idx ON app.order_items (product_id);

Foreign keys and referential actions

Definition · Referential actions

When a referenced parent row is deleted (or its key updated), the FK's ON DELETE / ON UPDATE action decides what happens to the children:

  • NO ACTION (the default): fail if children still exist, checked at the end of the statement, or at commit if the constraint is deferred.
  • RESTRICT: fail immediately; can't be deferred.
  • CASCADE: delete (or update) the children too, recursively.
  • SET NULL / SET DEFAULT: detach the children; the FK column must be nullable or have a default.

Postgres does not index the referencing column automatically (MySQL InnoDB does). Without order_items_product_idx, every delete of a product scans order_items to look for children, and joins from products to items have no index to use. Index every FK column unless the table is tiny.

When cascade is a footgun. CASCADE fits composition, where children mean nothing without the parent: order lines, junction-table rows. It is dangerous on association: users → orders with cascade means one "delete account" call silently destroys financial records, and a chain of cascades can delete and lock millions of rows in a single statement that nobody reviewed. Use RESTRICT for anything with legal or business value and delete deliberately, in order, in application code (or don't delete at all, L203).

UNIQUE, NULLs and CHECK

A UNIQUE constraint is backed by a unique index. A composite UNIQUE (user_id, label) forbids repeating the pair, so the same label under different users is fine. NULLs get special treatment: two NULLs are not equal, so by default any number of rows may have NULL in a unique column, and a composite key with any NULL component never conflicts. PostgreSQL 15 added UNIQUE NULLS NOT DISTINCT to treat NULLs as equal. For "unique among live rows only", use a partial unique index (L212).

CHECK (expr) enforces a rule on each row. It may compare columns of the same row, but it can't use subqueries or look at other rows. Typical domain invariants:

CHECK (quantity > 0)
CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled'))
CHECK (discount_cents BETWEEN 0 AND price_cents)
CHECK (shipped_at IS NULL OR shipped_at >= created_at)
CHECK ((status = 'paid') = (paid_at IS NOT NULL))   -- state and timestamp agree

A CHECK passes when its expression is true or NULL, so CHECK (price > 0) accepts a NULL price; add NOT NULL as well. On a large existing table, add the constraint NOT VALID (instant, checks only new writes), then run VALIDATE CONSTRAINT, which scans the old rows under a lock that still allows reads and writes.

Deferrable constraints and naming

By default a constraint is checked at the end of every statement. DEFERRABLE INITIALLY DEFERRED (or SET CONSTRAINTS name DEFERRED inside a transaction) moves the check to COMMIT. This works for UNIQUE, PRIMARY KEY, FOREIGN KEY and EXCLUDE, not for CHECK or NOT NULL. Legitimate uses: inserting two rows that reference each other, and swapping unique values (reordering position columns) where the intermediate state collides. Deferred checks fail at commit, far from the statement that caused them, so use them only where you need them.

Postgres generates names such as order_items_quantity_check and orders_user_id_fkey. Name constraints yourself, table_meaning_kind, because the name is the only machine-readable detail in the error:

shop=# \set VERBOSITY verbose
shop=# INSERT INTO app.order_items VALUES (1001, 1, 42, 0, 19.99);
ERROR:  23514: new row for relation "order_items" violates check constraint "order_items_quantity_positive"
DETAIL:  Failing row contains (1001, 1, 42, 0, 19.99).
(further lines trimmed)

Why application validation is not enough

Application checks also miss every other writer: a second service, a batch job, a migration, a support engineer's manual UPDATE, last year's version of your own code. So validate in the application for good messages and fewer round trips, and declare the same rules as constraints so the data stays correct anyway. Then turn violations into clean API errors instead of 500s, using the SQLState class 23 codes and the constraint name:

import java.sql.SQLException;
import java.util.Map;
import java.util.Optional;
import org.postgresql.util.PSQLException;

public final class ConstraintErrors {
    public record ApiError(int status, String code, String message) {}

    private static final Map<String, ApiError> BY_CONSTRAINT = Map.of(
        "users_email_key", new ApiError(409, "EMAIL_TAKEN", "An account with this email already exists"),
        "order_items_quantity_positive", new ApiError(422, "BAD_QUANTITY", "Quantity must be at least 1"),
        "order_items_product_fk", new ApiError(422, "UNKNOWN_PRODUCT", "Product does not exist"));

    public static Optional<ApiError> map(SQLException e) {
        if (e instanceof PSQLException p && p.getServerErrorMessage() != null) {
            String name = p.getServerErrorMessage().getConstraint();
            if (name != null && BY_CONSTRAINT.containsKey(name)) return Optional.of(BY_CONSTRAINT.get(name));
        }
        String state = e.getSQLState() == null ? "" : e.getSQLState();
        return switch (state) {
            case "23505" -> Optional.of(new ApiError(409, "DUPLICATE", "Resource already exists"));
            case "23503" -> Optional.of(new ApiError(409, "REFERENCE", "Related resource missing or still in use"));
            case "23502", "23514" -> Optional.of(new ApiError(422, "INVALID", "Request breaks a data rule"));
            default -> Optional.empty();   // not a constraint problem: let it become a 500
        };
    }
}

Spring later wraps the same errors as DataIntegrityViolationException and DuplicateKeyException; the mapping idea carries over unchanged.

What breaks in production
  • Unindexed foreign keys: deleting one parent row scans the child table while holding locks.
  • Cascade chains: DELETE FROM categories WHERE id = 7 removes products, order lines and reviews in one statement.
  • Nullable "unique" column: thousands of rows with NULL pass the constraint, and lookups by that column return many rows.
  • Leaking constraint text: returning raw DETAIL to clients exposes table names and other users' data (the failing row). Map to your own messages.

DML: INSERT, UPDATE, DELETE, UPSERT & RETURNING

40m video45m practice

Every write is a set operation: the WHERE clause chooses the rows, and the database changes all of them at once. Write DML so that it returns what it changed, resolves races inside the statement, and can be checked before it is committed.

INSERT and RETURNING

-- single row; RETURNING hands back generated values in the same round trip
INSERT INTO app.orders (user_id, status) VALUES (42, 'pending')
RETURNING id, created_at;

-- multi-row: one statement, one round trip, one commit
INSERT INTO app.order_items (order_id, line_no, product_id, quantity, unit_price)
VALUES (1001, 1, 7, 2, 19.99),
       (1001, 2, 9, 1, 5.00);

-- INSERT ... SELECT: copy a cart into an order at checkout, snapshotting prices
INSERT INTO app.order_items (order_id, line_no, product_id, quantity, unit_price)
SELECT 1001, row_number() OVER (ORDER BY ci.added_at), ci.product_id, ci.quantity, p.price
FROM app.cart_items ci JOIN app.products p ON p.id = ci.product_id
WHERE ci.cart_id = 55;

Without RETURNING you would need a second query to learn the new id, and SELECT max(id) is wrong under concurrency. RETURNING works on UPDATE and DELETE too (DELETE ... RETURNING * is how you move rows to an archive), and JDBC's getGeneratedKeys uses it underneath on Postgres (L222).

UPDATE ... FROM and DELETE ... USING

Postgres lets an UPDATE join other tables in FROM, and a DELETE join them in USING:

UPDATE app.products p
   SET price = s.new_price
  FROM staging.price_list s
 WHERE s.sku = p.sku
   AND s.new_price <> p.price;          -- skip no-op writes: they still create row versions

DELETE FROM app.cart_items ci
 USING app.carts c
 WHERE ci.cart_id = c.id
   AND c.updated_at < now() - interval '30 days';

If a target row matches several FROM rows, Postgres applies just one of them, and which one is unpredictable. Make sure the join key is unique on the source side. MySQL writes the same thing as UPDATE products p JOIN price_list s ON ... SET ...; standard SQL uses a correlated subquery or MERGE.

Algorithm · Safe manual write
  1. Write the SELECT with the exact WHERE you intend, and check the row count and a sample of rows.
  2. BEGIN; then run the UPDATE/DELETE with RETURNING (or read the reported count, UPDATE 37).
  3. Verify: does the count match step 1? Re-select a few rows.
  4. COMMIT; if it matches, otherwise ROLLBACK;. Keep the gap short: the touched rows stay locked until you finish.

A missing or wrong WHERE updates every row, and autocommit makes that permanent the moment you press Enter. MySQL's --safe-updates mode refuses UPDATE/DELETE without a key condition or LIMIT; in psql, the habit of typing BEGIN first is the guard.

Upsert: ON CONFLICT, ON DUPLICATE KEY, MERGE

-- PostgreSQL: add to cart, or increase the quantity if the product is already there
INSERT INTO app.cart_items (cart_id, product_id, quantity)
VALUES (55, 7, 1)
ON CONFLICT (cart_id, product_id)
DO UPDATE SET quantity = app.cart_items.quantity + EXCLUDED.quantity
RETURNING quantity;

INSERT INTO app.processed_events (event_id) VALUES ('evt_81f2')
ON CONFLICT DO NOTHING;               -- idempotent consumer: 0 rows means "seen before"

-- MySQL 8.0.19+: row alias instead of the deprecated VALUES()
INSERT INTO cart_items (cart_id, product_id, quantity) VALUES (55, 7, 1) AS new
ON DUPLICATE KEY UPDATE quantity = cart_items.quantity + new.quantity;

-- SQL standard MERGE (PostgreSQL 15+, Oracle, SQL Server)
MERGE INTO app.products p
USING staging.price_list s ON s.sku = p.sku
WHEN MATCHED THEN UPDATE SET price = s.new_price
WHEN NOT MATCHED THEN INSERT (sku, name, price) VALUES (s.sku, s.name, s.new_price);

ON CONFLICTa named unique index or constraint (the arbiter); EXCLUDED is the rejected rowatomic: two concurrent upserts never both insert, and neither fails
ON DUPLICATE KEY UPDATEany unique key on the table, so with several keys it may update a row you didn't expectatomic in InnoDB; reports 1 affected row for an insert, 2 for an update

Two details: an ON CONFLICT ... DO UPDATE statement may not touch the same row twice (deduplicate the input first), and the identity sequence is consumed even when the insert turns into an update, so ids have gaps (L219).

Bulk loading

Per-row INSERT statements in autocommit pay a network round trip and a WAL flush per row. In rough order of speed, from slowest:

  • Batched INSERTs in one transaction (JDBC batching, L222).
  • Multi-row VALUES lists of a few hundred to a few thousand rows. The protocol's 16-bit count of bind parameters caps one statement at 65,535 parameters.
  • COPY, Postgres's streaming bulk path, which skips per-statement parsing and planning:
COPY app.products (sku, name, price) FROM STDIN WITH (FORMAT csv, HEADER true);
\copy app.products (sku, name, price) FROM 'products.csv' WITH (FORMAT csv, HEADER true)

COPY ... FROM 'file' reads a file on the server and needs elevated privileges; psql's \copy streams a local file through the connection. From Java, pgJDBC exposes the same stream through CopyManager. For very large loads, also drop or defer secondary indexes and build them afterwards.

Soft deletes and optimistic concurrency

A soft delete sets deleted_at = now() instead of removing the row. It gives you undo and an audit trail, but the costs grow over time: every query needs AND deleted_at IS NULL (forget it once and deleted data reappears), unique constraints must become partial indexes or a deleted user's email blocks re-registration, foreign keys still accept references to "deleted" rows, tables and indexes only grow, and erasure requests such as GDPR's still need a real delete. Use soft deletes where restore is a product feature; otherwise hard-delete and keep history in an archive or audit table.

Optimistic concurrency detects lost updates without holding locks. Each row carries a version; a writer sends the version it read and the update matches only if nobody changed the row since.

import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.SQLException;

final class ProductPrices {
    static final class StaleUpdateException extends RuntimeException {
        StaleUpdateException(long id, long version) {
            super("product " + id + " was modified after version " + version);
        }
    }

    static void changePrice(Connection conn, long id, long expectedVersion, BigDecimal price)
            throws SQLException {
        var sql = """
            UPDATE app.products
               SET price = ?, version = version + 1
             WHERE id = ? AND version = ?
            """;
        try (var ps = conn.prepareStatement(sql)) {
            ps.setBigDecimal(1, price);
            ps.setLong(2, id);
            ps.setLong(3, expectedVersion);
            if (ps.executeUpdate() == 0) throw new StaleUpdateException(id, expectedVersion);
        }
    }
}
What breaks in production
  • The forgotten WHERE in an autocommit console, and the restore from last night's backup.
  • Check-then-insert upserts (SELECT, then INSERT or UPDATE) that race and throw duplicate-key errors under load. Use ON CONFLICT.
  • Huge single-statement updates (UPDATE events SET ... over 200M rows): hours of row locks, WAL growth, replica lag, and table bloat. Batch by key ranges of a few thousand rows.
  • Soft-delete leaks: one query without the deleted_at filter shows deleted accounts in search results.

SELECT: Projection, Filtering & NULL Semantics

40m video45m practice

WHERE keeps a row only when its predicate is true, not when it is merely "not false". Because SQL logic has a third value, UNKNOWN, every nullable column can make rows disappear without an error.

Projection: name your columns

SELECT * is fine at a psql prompt and a hazard in application code:

  • It fetches columns nobody uses, including large text/jsonb values stored out of line, which the server must read, decompress and send.
  • It rules out index-only scans (L212), because the query needs every column.
  • It couples the code to the table's current shape. Adding or reordering a column breaks positional mapping and INSERT INTO a SELECT * FROM b, and a view defined with * keeps the column list it had on the day it was created.

Aliases and quoting. SELECT o.id AS order_id, o.total_cents / 100.0 AS total FROM app.orders AS o. Single quotes are string literals; double quotes are identifiers. Unquoted identifiers fold to lower case in Postgres (to upper case in Oracle and the standard), so CREATE TABLE "Orders" creates a name you must quote, with the same capitalisation, forever after. Use snake_case and never quote. MySQL quotes identifiers with backticks. A column alias can't be used in WHERE, because WHERE runs before SELECT computes it (L207).

Filtering predicates and precedence

WHERE total_cents >= 5000
  AND status IN ('paid', 'shipped')
  AND created_at >= '2026-01-01' AND created_at < '2026-02-01'  -- half-open range
  AND email ILIKE '%@example.com'                               -- case-insensitive, Postgres only
  AND sku ~ '^[A-Z]{3}-[0-9]{4}$'                               -- POSIX regex (~* ignores case)
  • BETWEEN a AND b includes both ends. For timestamps, BETWEEN '2026-01-01' AND '2026-01-31' misses everything after midnight on the 31st; use the half-open form.
  • LIKE: % matches any run of characters, _ exactly one; ESCAPE sets the escape character for literal ones. A prefix pattern ('abc%') can use a B-tree index (with text_pattern_ops or C collation); a leading wildcard ('%abc') cannot and scans the table. The pg_trgm extension with a GIN index makes leading-wildcard and ILIKE searches indexable.
  • SIMILAR TO is the standard's hybrid of LIKE and regex. It is rarely the clearest choice; use LIKE or ~.

Precedence is NOT, then AND, then OR. WHERE status = 'paid' OR status = 'shipped' AND total_cents > 10000 means paid OR (shipped AND big), which returns every paid order, small ones included. Parenthesise every mixed AND/OR.

Three-valued logic

Definition · NULL and UNKNOWN

NULL marks a missing or inapplicable value. Any comparison with it (=, <>, <, LIKE, IN) yields UNKNOWN, the boolean NULL. That includes NULL = NULL: two unknown values are not known to be equal. WHERE, JOIN ... ON and HAVING keep a row only when the condition is TRUE; CHECK constraints are the opposite and reject only FALSE (L202).

The practical consequence: WHERE status <> 'cancelled' also drops rows whose status is NULL, and WHERE discount > 10 plus WHERE NOT (discount > 10) together do not cover the table.

Tools for NULL

The NOT IN trap

-- "users who never ordered"
SELECT id FROM app.users
WHERE id NOT IN (SELECT user_id FROM app.orders);    -- one NULL user_id: zero rows, no error

SELECT u.id FROM app.users u
WHERE NOT EXISTS (SELECT 1 FROM app.orders o WHERE o.user_id = u.id);   -- correct

42 NOT IN (1, 2, NULL) expands to 42 <> 1 AND 42 <> 2 AND 42 <> NULL, which is TRUE AND TRUE AND UNKNOWN, which is UNKNOWN, so the row is dropped. One NULL in the subquery empties the whole result, and the query runs for months until the first guest checkout writes an order with a NULL user_id. NOT EXISTS has no such problem and is usually planned as an efficient anti-join (L206, L208).

CASE and CAST

SELECT id,
       CASE                                    -- searched CASE: first true WHEN wins
         WHEN total_cents >= 100000 THEN 'large'
         WHEN total_cents >= 10000  THEN 'medium'
         ELSE 'small'                          -- without ELSE the result is NULL
       END AS size_band,
       CASE status WHEN 'paid' THEN 1 WHEN 'shipped' THEN 2 ELSE 0 END AS stage,   -- simple CASE
       CAST(total_cents AS numeric) / 100 AS total,   -- same as total_cents::numeric / 100
       created_at::date AS order_day
FROM app.orders;

Postgres is strict about types. A quoted literal is "unknown" until context gives it a type, so WHERE id = '42' works, but comparing a bigint column with a text column is an error rather than a silent conversion. MySQL coerces freely: WHERE varchar_code = 123 converts every row's string to a number, which can't use the index and matches '123abc'. Integer division truncates (7 / 2 = 3), so cast one side to numeric; and 2.7::integer rounds to 3, unlike Java's (int) 2.7, which truncates to 2.

What breaks in production
  • NOT IN over a nullable subquery: reports and cleanup jobs that quietly return nothing.
  • <> drops NULLs: "all non-cancelled orders" misses every order whose status was never set.
  • Leading-wildcard search (name ILIKE '%term%') on a big table without a trigram index: a full scan per keystroke of an autocomplete box.
  • BETWEEN on timestamps: end-of-month revenue reports short by a day.

ORDER BY, LIMIT/OFFSET, DISTINCT & Pagination Basics

35m video40m practice

Rows have no order until ORDER BY gives them one, and pagination is correct only if that order is total. OFFSET makes the database read and discard every skipped row; a keyset cursor jumps straight to the next page.

ORDER BY

SELECT id, status, shipped_at, total_cents
FROM app.orders
ORDER BY status ASC,                    -- first key
         shipped_at DESC NULLS LAST,    -- tie-breaker; unshipped orders at the end
         id DESC;                       -- unique final key: the order is now total
  • Keys apply left to right; each later key only breaks ties of the earlier ones. ASC is the default.
  • NULLs: Postgres sorts NULL as larger than every value, so last in ASC and first in DESC, unless you say NULLS FIRST/NULLS LAST. MySQL treats NULL as smallest and has no NULLS clause (sort by col IS NULL first instead).
  • You can order by an expression (ORDER BY lower(name)), a select-list alias (ORDER BY total), or an ordinal (ORDER BY 2). Ordinals break silently when someone edits the select list; avoid them outside ad-hoc queries.
  • An index can deliver rows already sorted only if its column order, directions (or their exact reverse) and NULLS placement match the ORDER BY. Otherwise the plan has a Sort node (L213).

Collation: what "alphabetical" means

Definition · Collation

A collation is the rule for comparing and sorting strings. "C" compares bytes: 'B' < 'a', accents sort after z. Linguistic collations (en-US, de-DE, sv-SE) follow a language's rules: case and accents are secondary differences, and 'ä' sorts in a different place in German and Swedish.

Postgres takes the database's default collation from the operating system's libc unless you choose ICU (default provider option since 15) or the built-in provider (17). Override per column or per expression: name COLLATE "C", or ORDER BY name COLLATE "de-x-icu". An index helps an ORDER BY only if the collations match. Java's String.compareTo compares UTF-16 code units, which is close to "C", so a list sorted in the database with en-US and re-sorted in Java comes out in a different order; use java.text.Collator when Java must agree.

Note · Collation versions

libc collation rules change between OS releases (glibc 2.28 changed many orderings). A B-tree built under the old rules is then sorted wrongly for the new ones, and lookups can miss rows. After such an upgrade, REINDEX text indexes; Postgres records collation versions and warns about mismatches.

DISTINCT and DISTINCT ON

SELECT DISTINCT a, b removes duplicate rows over all selected columns, by sorting or hashing the whole result. When you add DISTINCT to "fix" duplicates from a join, the join is usually wrong (the fan-out trap, L206), and you pay for deduplication on every run.

Postgres's DISTINCT ON (expr) keeps the first row of each group, as defined by the ORDER BY, whose leftmost keys must match the DISTINCT ON expressions:

-- latest order per user
SELECT DISTINCT ON (user_id) user_id, id, created_at, total_cents
FROM app.orders
ORDER BY user_id, created_at DESC, id DESC;

It is compact and fast with an index on (user_id, created_at DESC, id DESC). The portable version uses ROW_NUMBER() (L210).

LIMIT, OFFSET, and why deep pages are slow

LIMIT 20 OFFSET 10000 is easy to write and to map to "page 501". But the database cannot jump to row 10,001: it has to produce the first 10,020 rows in order, through the index or by sorting, and throw away 10,000 of them. Page n costs O(n), so crawlers that walk deep pages cause load that grows with the size of the table. Offsets also drift. If a row is inserted before the page you are on, the next page repeats a row, and a delete makes you skip one.

Keyset (seek) pagination

Remember where the last page ended and ask for rows strictly after it. With a non-unique sort key such as created_at, add the primary key to make the cursor unique:

CREATE INDEX orders_user_created_idx ON app.orders (user_id, created_at DESC, id DESC);

-- first page
SELECT id, created_at, total_cents FROM app.orders
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- next page: (?, ?) are created_at and id of the last row already shown
SELECT id, created_at, total_cents FROM app.orders
WHERE user_id = ? AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;

The row comparison (a, b) < (x, y) is lexicographic and means a < x OR (a = x AND b < y); Postgres turns it into a single index range. Write the expanded form for databases whose planners handle row values poorly, and when the keys sort in mixed directions. Hand the cursor to clients as an opaque token so they can't build their own or depend on its format:

import java.nio.charset.StandardCharsets;
import java.time.Instant;
import java.util.Base64;

record PageCursor(Instant createdAt, long id) {
    String encode() {
        var raw = createdAt + "|" + id;
        return Base64.getUrlEncoder().withoutPadding()
                     .encodeToString(raw.getBytes(StandardCharsets.UTF_8));
    }

    static PageCursor decode(String token) {
        var raw = new String(Base64.getUrlDecoder().decode(token), StandardCharsets.UTF_8);
        int bar = raw.lastIndexOf('|');
        if (bar < 0) throw new IllegalArgumentException("malformed cursor");
        return new PageCursor(Instant.parse(raw.substring(0, bar)),
                              Long.parseLong(raw.substring(bar + 1)));
    }
}

Keyset pages can't jump to page 37 and don't come with a total count. That suits feeds, infinite scroll, exports and API cursors; "page n of m" UIs over small result sets can keep OFFSET. Spring Data's Window/ScrollPosition support builds the same thing in L324.

Note · FETCH FIRST WITH TIES

The standard spelling of LIMIT is FETCH FIRST 3 ROWS ONLY. Postgres 13+ also supports FETCH FIRST 3 ROWS WITH TIES, which returns the top three plus every row tied with the third on the ORDER BY keys (so "top 3 sellers" returns 4 rows when two products share third place). It requires an ORDER BY, and the number of rows it returns varies.

What breaks in production
  • Non-total ordering: ORDER BY created_at LIMIT 20 OFFSET 20 with tied timestamps returns some rows on two pages and others on none, and the result can differ between runs.
  • Nullable sort keys in a cursor: (shipped_at, id) < (NULL, 7) is UNKNOWN, so pagination stops early. Keyset columns must be NOT NULL, or you must handle NULLs separately.
  • Deep offsets from bots: ?page=90000 requests that each scan most of the table.
  • OS upgrade, collation drift: unique text indexes that let duplicates in until you REINDEX.

Joins: Every Kind, With Diagrams

50m video55m practice

A join pairs rows from two inputs according to a condition: inner joins keep the matching pairs, and outer joins also keep unmatched rows, padded with NULLs. Most join bugs come from rows multiplying when you didn't expect it, or from NULL-padded rows being filtered out by accident.

Inner and outer joins

Definition · Join kinds
  • INNER JOIN ... ON cond: every pair (a, b) for which cond is true. A row with no partner disappears; a row with three partners appears three times.
  • LEFT [OUTER] JOIN: the inner result, plus each left row that matched nothing, with NULLs for the right side's columns. RIGHT JOIN is the mirror image; write it as a LEFT JOIN with the tables swapped, which reads more easily.
  • FULL [OUTER] JOIN: the inner result plus the unmatched rows from both sides.
  • CROSS JOIN: every pair, with no condition: |A| × |B| rows.

Reading NULL-padded rows. In a LEFT JOIN, a NULL in a right-side column means either "no partner" or "partner with a NULL value". Test the right side's primary key (o.id IS NULL) to tell them apart. Count partners with COUNT(o.id), not COUNT(*), which counts Cy's padded row as one order.

-- every user with their paid-order count, including users with none
SELECT u.id, u.name, COUNT(o.id) AS paid_orders
FROM app.users u
LEFT JOIN app.orders o ON o.user_id = u.id AND o.status = 'paid'   -- filter in ON
GROUP BY u.id, u.name;
-- moving "o.status = 'paid'" to WHERE rejects the NULL-padded rows
-- and silently turns the LEFT JOIN back into an INNER JOIN

CROSS, self, USING and NATURAL

CROSS JOIN is legitimate when you want every combination: sizes × colours for product variants, or every day × every product to fill gaps in a sales report (L209). An accidental Cartesian product comes from a forgotten condition, usually in the old comma syntax FROM a, b, c WHERE ..., where three tables of 10,000 rows produce 1012 candidate pairs. Prefer explicit JOIN ... ON.

A self-join uses one table twice under two aliases, typical for hierarchies:

SELECT e.name AS employee, m.name AS manager
FROM app.employees e
LEFT JOIN app.employees m ON m.id = e.manager_id;   -- LEFT: the CEO has no manager

JOIN orders USING (user_id) is shorthand for equality on same-named columns and outputs the column once. NATURAL JOIN joins on every column the two tables share by name. Add an updated_at to both tables next year and every natural join starts requiring equal timestamps, without an error. Avoid it.

Semi-joins and anti-joins

-- semi-join: users who have at least one order (each user once, however many orders)
SELECT u.* FROM app.users u
WHERE EXISTS (SELECT 1 FROM app.orders o WHERE o.user_id = u.id);

-- anti-join: products never ordered
SELECT p.* FROM app.products p
WHERE NOT EXISTS (SELECT 1 FROM app.order_items oi WHERE oi.product_id = p.id);

A semi-join returns each left row at most once, so it never fans out; using JOIN plus DISTINCT for the same question is slower and less clear. Postgres plans EXISTS and IN (subquery) as Semi Joins and NOT EXISTS as an Anti Join. It cannot do that for NOT IN, whose NULL semantics differ (L204), which is one more reason to write NOT EXISTS.

Many tables and join order

For inner joins the result doesn't depend on the order you write them in, but the cost does: joining the two tables that produce the smallest intermediate result first keeps every later step small. The Postgres planner searches join orders itself, exhaustively for up to join_collapse_limit (8) tables and with the genetic optimizer from geqo_threshold (12) tables. Past those limits, the order you wrote starts to matter. Outer joins restrict reordering, because moving a LEFT JOIN can change the result. When a five-table query is slow, the cause is usually a wrong row estimate for one join, which leads to a bad order (L213).

The fan-out trap

Worked example · Double counting

Order 1001 has 2 items (totals 30 and 70, so 100) and 3 payment attempts (100 failed, 100 failed, 100 captured). The query below joins both children and aggregates:

SELECT o.id, SUM(oi.line_total) AS items, SUM(p.amount) AS paid
FROM app.orders o
JOIN app.order_items oi ON oi.order_id = o.id
JOIN app.payments    p  ON p.order_id  = o.id
WHERE o.id = 1001
GROUP BY o.id;            -- items = 300, paid = 600: both wrong

Each of the 2 item rows pairs with each of the 3 payment rows, giving 6 rows. Every item is counted 3 times and every payment twice. Two independent one-to-many joins from the same parent always multiply. Fix it by aggregating each child before joining:

SELECT o.id, i.items, pay.paid
FROM app.orders o
JOIN (SELECT order_id, SUM(line_total) AS items FROM app.order_items GROUP BY order_id) i
  ON i.order_id = o.id
LEFT JOIN (SELECT order_id, SUM(amount) AS paid FROM app.payments
           WHERE status = 'captured' GROUP BY order_id) pay
  ON pay.order_id = o.id
WHERE o.id = 1001;        -- items = 100, paid = 100

The symptom is "totals that are a multiple of what they should be", and the cover-up is SUM(DISTINCT ...), which breaks the first time two lines have the same amount. ORMs produce the same fan-out when you fetch two collections in one query (Phase 10).

LATERAL, and join vs subquery vs CTE

A LATERAL subquery may refer to columns of tables to its left, so it runs once per left row, like a for-each loop. It is the clean way to write "the top N children per parent":

SELECT u.id, recent.id AS order_id, recent.created_at
FROM app.users u
LEFT JOIN LATERAL (
  SELECT o.id, o.created_at FROM app.orders o
  WHERE o.user_id = u.id
  ORDER BY o.created_at DESC
  LIMIT 3
) recent ON true;

With an index on orders (user_id, created_at DESC) each inner query is a short index scan. That is ideal when there are few users and many orders each, and poor when there are millions of users and you need most of them (then use window functions, L210).

Join vs subquery vs CTE. The Postgres planner flattens simple subqueries in FROM into joins, turns IN/EXISTS into semi-joins, and since version 12 inlines non-recursive CTEs that are referenced once (L209). So equivalent formulations often get the same plan. Pick the clearest form and check with EXPLAIN rather than relying on rules of thumb. The real exceptions are correlated subqueries the planner can't flatten (a scalar subquery in the select list runs once per row, L208) and CTEs that are materialized.

What breaks in production
  • WHERE on the outer side: a filter on the right table in WHERE silently converts a LEFT JOIN into an inner join, and users with no orders vanish from the report.
  • Fan-out aggregates: dashboards that report double or triple revenue as soon as a second child table is joined.
  • DISTINCT as a band-aid: it hides a wrong join, costs a sort or hash on every run, and stops hiding it when two rows really are equal.
  • Accidental Cartesian product: a missing condition that produces billions of rows and fills the temp disk.

Aggregation: GROUP BY, HAVING & Grouping Sets

45m video50m practice

GROUP BY collapses the rows that share a key into one row per group, and only the key and aggregates over the group survive. Knowing the logical order in which a query is evaluated explains nearly every "column must appear in GROUP BY" and "column does not exist" error.

Aggregate functions

COUNT(*)rows in the groupcounts NULL-padded rows of an outer join

       json_agg(json_build_object('sku', p.sku, 'qty', oi.quantity) ORDER BY oi.line_no) AS items
FROM app.orders o
JOIN app.order_items oi ON oi.order_id = o.id
JOIN app.products p     ON p.id = oi.product_id
WHERE o.id = 1001
GROUP BY o.id;

GROUP BY semantics

Definition · The grouping rule

After GROUP BY k1, k2, each output row stands for one distinct (k1, k2) combination (all NULL keys form one group). An expression in SELECT, HAVING or ORDER BY must be a grouping expression, an aggregate, or built only from those. Otherwise there would be several candidate values per group and no rule for choosing one.

Postgres relaxes the rule for functional dependency: GROUP BY u.id, where u.id is the primary key, lets you select u.name and u.email, because they are determined by the key. MySQL before 5.7.5 accepted any column and returned a value from an arbitrary row of the group; since then ONLY_FULL_GROUP_BY is on by default, and ANY_VALUE(col) is the explicit way to say "I don't care which". Don't turn the mode off to make an old query run: that query has a real ambiguity in it.

Logical evaluation order

So SELECT total_cents / 100.0 AS total ... WHERE total > 50 fails, while ORDER BY total works. Postgres also accepts output-column names and ordinals in GROUP BY, an extension that the standard doesn't define.

WHERE vs HAVING, and FILTER

WHERE removes rows before grouping: fewer rows to aggregate, and the condition can use an index. HAVING removes groups after aggregation, so it is the only place a condition on an aggregate can go:

SELECT user_id, COUNT(*) AS orders, SUM(total_cents) AS spent
FROM app.orders
WHERE status = 'paid' AND created_at >= now() - interval '90 days'   -- rows
GROUP BY user_id
HAVING COUNT(*) >= 5                                                -- groups
ORDER BY spent DESC;

A condition without aggregates written in HAVING still gives the right answer, and Postgres quietly moves such conditions into WHERE. Other engines may aggregate everything first, and readers expect row filters in WHERE, so put them there.

Conditional aggregates. FILTER (WHERE ...) restricts one aggregate to some of the group's rows, which gives several differently-filtered numbers in one pass:

SELECT date_trunc('day', created_at) AS day,
       COUNT(*)                                          AS all_orders,
       COUNT(*) FILTER (WHERE status = 'cancelled')      AS cancelled,
       SUM(total_cents) FILTER (WHERE channel = 'mobile') AS mobile_cents,
       SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled_portable  -- MySQL form
FROM app.orders
GROUP BY 1;

GROUPING SETS, ROLLUP, CUBE

Reports need subtotals: per month and category, per month, and overall. Instead of three queries joined with UNION ALL, list the groupings:

  • GROUPING SETS ((month, category), (month), ()): exactly those three levels; () is the grand total.
  • ROLLUP (month, category): shorthand for that hierarchy. ROLLUP (a, b, c) yields (a,b,c), (a,b), (a), ().
  • CUBE (a, b): every subset, here (a,b), (a), (b), (). That is 2n groupings, so use it for small cross-tabs only.

Subtotal rows have NULL in the rolled-up columns. GROUPING(col) returns 1 when col was rolled up and 0 otherwise, which tells a subtotal apart from a real NULL key. MySQL supports only GROUP BY a, b WITH ROLLUP.

Worked report: monthly revenue

Worked example · Revenue by month and category 
SELECT date_trunc('month', o.created_at AT TIME ZONE 'Europe/Berlin')::date AS month,
       c.name                                   AS category,
       SUM(oi.quantity * oi.unit_price)          AS revenue,
       COUNT(DISTINCT o.id)                      AS orders,
       SUM(oi.quantity * oi.unit_price) FILTER (WHERE o.channel = 'mobile') AS mobile_revenue,
       GROUPING(c.name)                          AS is_subtotal
FROM app.orders o
JOIN app.order_items oi ON oi.order_id = o.id
JOIN app.products p     ON p.id = oi.product_id
JOIN app.categories c   ON c.id = p.category_id
WHERE o.status IN ('paid', 'shipped')
  AND o.created_at >= '2026-01-01 00:00 Europe/Berlin'
  AND o.created_at <  '2027-01-01 00:00 Europe/Berlin'
GROUP BY ROLLUP (date_trunc('month', o.created_at AT TIME ZONE 'Europe/Berlin'), c.name)
ORDER BY month NULLS LAST, is_subtotal, revenue DESC;
  • Month boundaries depend on a time zone. AT TIME ZONE turns the stored instant into the business's local time before truncating (L109).
  • Revenue comes from the order_items snapshot prices, never from current products.price.
  • COUNT(DISTINCT o.id) is needed because the join produces one row per item; summing the item lines is safe because every item appears exactly once (no second child table, so no fan-out, L206).
  • The rollup adds one subtotal row per month (is_subtotal = 1) and a grand-total row in which month is also NULL.
What breaks in production
  • NULL sums: a day with no sales produces NULL, and Java's rs.getLong() silently turns it into 0, or getBigDecimal returns null and the code throws an NPE.
  • Truncated GROUP_CONCAT in MySQL: lists cut at 1,024 bytes with no error.
  • Server-time-zone months: date_trunc('month', created_at) on a timestamptz uses the session's TimeZone, so the report changes depending on which server ran it.
  • Turning off ONLY_FULL_GROUP_BY: reports that show the name from one arbitrary row of each group.

Subqueries & Correlated Subqueries

40m video45m practice

A subquery is a query used as a value, a list or a table inside another query. A correlated subquery refers to the outer row, so it is defined to run once per outer row. Whether it actually does depends on whether the optimizer can rewrite it as a join.

Where subqueries go

  • Scalar subquery (one row, one column) anywhere a value fits: SELECT name, (SELECT count(*) FROM app.orders o WHERE o.user_id = u.id) AS orders FROM app.users u. Zero rows yield NULL; two or more rows raise "more than one row returned by a subquery used as an expression".
  • In WHERE: compared with a scalar (price > (SELECT avg(price) FROM app.products)), or tested with IN, EXISTS, ANY, ALL.
  • Derived table in FROM: FROM (SELECT ...) AS t. MySQL and older Postgres require the alias ("every derived table must have its own alias"); PostgreSQL 16 made it optional. Always write one, since you need it to refer to the columns anyway.

IN, EXISTS, ANY and ALL

x IN (subquery) and EXISTS (correlated subquery) answer the same question when nothing is NULL, and Postgres plans both as a semi-join. Their negations differ: NOT IN returns nothing if the subquery produces a single NULL, while NOT EXISTS only asks whether a matching row exists (L204). EXISTS ignores the select list, so write SELECT 1.

Definition · Quantified comparisons
  • x op ANY (subquery) is true if x op v holds for at least one value v. = ANY is IN; SOME is a synonym.
  • x op ALL (subquery) is true if it holds for every v. <> ALL is NOT IN, with the same NULL trap. Over an empty subquery, ALL is true and ANY is false.

Postgres also accepts an array: WHERE id = ANY (?) takes one array parameter, so a single prepared statement works for any number of ids, instead of generating IN (?, ?, ?, ...) with a different SQL text (and plan cache entry) for each list length:

import java.sql.Connection;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

final class ProductLookup {
    record ProductName(long id, String name) {}

    static List<ProductName> byIds(Connection conn, List<Long> ids) throws SQLException {
        var sql = "SELECT id, name FROM app.products WHERE id = ANY (?)";
        try (var ps = conn.prepareStatement(sql)) {
            ps.setArray(1, conn.createArrayOf("bigint", ids.toArray()));
            try (var rs = ps.executeQuery()) {
                var out = new ArrayList<ProductName>();
                while (rs.next()) out.add(new ProductName(rs.getLong("id"), rs.getString("name")));
                return out;
            }
        }
    }
}

Correlated subqueries: the per-row model

"Employees who earn more than their department's average":

SELECT e.id, e.name, e.salary
FROM app.employees e
WHERE e.salary > (SELECT avg(e2.salary) FROM app.employees e2
                  WHERE e2.dept_id = e.dept_id);     -- refers to the outer row

The inner query depends on e.dept_id, so it is defined per outer row, and Postgres executes it that way. The plan shows a SubPlan under the filter, and EXPLAIN ANALYZE reports it with loops= equal to the number of outer rows:

Seq Scan on employees e
  Filter: (salary > (SubPlan 1))
  SubPlan 1
    ->  Aggregate
          ->  Index Scan using employees_dept_idx on employees e2
                Index Cond: (dept_id = e.dept_id)

With 100,000 employees in 50 departments, that is 100,000 aggregates over about 2,000 rows each, when 50 aggregates would do. Rewritten, the department averages are computed once:

-- derived table + join: one pass to aggregate, one hash join
SELECT e.id, e.name, e.salary
FROM app.employees e
JOIN (SELECT dept_id, avg(salary) AS avg_salary
      FROM app.employees GROUP BY dept_id) d ON d.dept_id = e.dept_id
WHERE e.salary > d.avg_salary;

-- window function: one scan, no join (L210)
SELECT id, name, salary
FROM (SELECT e.*, avg(salary) OVER (PARTITION BY dept_id) AS dept_avg
      FROM app.employees e) t
WHERE salary > dept_avg;

When the optimizer decorrelates for you

Postgres pulls up some subqueries into joins on its own:

  • EXISTS / NOT EXISTS and IN (subquery) at the top level of WHERE (ANDed with other conditions) become Semi Joins and Anti Joins.
  • Simple uncorrelated derived tables in FROM are flattened into the outer query.
  • An uncorrelated NOT IN can become a hashed SubPlan: the subquery runs once and is probed per row, which is fast only if the hash table fits in work_mem.

It does not decorrelate scalar subqueries in the select list or in comparisons (the example above), nor sublinks under OR or NOT. Those stay per-row SubPlans. Other engines (SQL Server, Oracle, and to a lesser extent MySQL 8) decorrelate more aggressively, so a pattern that is fine on one engine can be slow on another. Postgres 14's Memoize node can cache repeated inner lookups in nested-loop joins, which softens per-row costs for LATERAL joins but not for SubPlans.

Three patterns to know cold

Worked example · Common shapes

Latest row per group. The correlated form returns several rows per user when two orders tie on the maximum created_at:

SELECT o.* FROM app.orders o
WHERE o.created_at = (SELECT max(o2.created_at) FROM app.orders o2 WHERE o2.user_id = o.user_id);

-- deterministic, one row per user
SELECT * FROM (
  SELECT o.*, row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC) AS rn
  FROM app.orders o) t
WHERE rn = 1;          -- or DISTINCT ON (L205), or LATERAL ... LIMIT 1 (L206)

Records with no children. WHERE NOT EXISTS (SELECT 1 FROM child c WHERE c.parent_id = p.id), which is planned as an anti-join and is safe with NULLs.

Above-average earners. Company-wide, an uncorrelated scalar subquery runs once and is fine: WHERE salary > (SELECT avg(salary) FROM app.employees). Per department, use the derived-table or window rewrite above.

What breaks in production
  • Scalar subqueries in a list endpoint: (SELECT count(*) ...) per row for a 500-row page means 500 extra index scans per request, the N+1 problem inside one SQL statement.
  • "Works in dev": a correlated subquery over 1,000 test rows is instant; over 10M production rows it times out.
  • Scalar subquery that starts returning two rows after a data change: the query that worked for a year now fails with an error.
  • Huge IN (...) lists built in Java with thousands of literals: very long SQL texts, slow parsing, and a different statement for every list length. Use = ANY(?) or a join against a temp table.

CTEs & Recursive Queries

40m video45m practice

A common table expression names a subquery so a long query reads top to bottom as a series of steps. Its recursive form, an anchor plus a step repeated until no new rows appear, lets plain SQL walk trees and hierarchies.

WITH: naming the steps

WITH paid AS (                         -- step 1
  SELECT user_id, total_cents FROM app.orders
  WHERE status = 'paid' AND created_at >= now() - interval '1 year'
),
per_user AS (                          -- step 2 reads step 1
  SELECT user_id, sum(total_cents) AS spent, count(*) AS orders
  FROM paid GROUP BY user_id
)
SELECT u.email, p.spent, p.orders      -- final query reads any earlier CTE
FROM per_user p JOIN app.users u ON u.id = p.user_id
WHERE p.spent > 100000
ORDER BY p.spent DESC;

Compared with nesting derived tables three deep, each step has a name, appears before it is used, and can be run alone while you debug. CTEs are separated by commas, and each may reference those defined before it. A data-modifying CTE (WITH moved AS (DELETE ... RETURNING *) INSERT INTO archive SELECT * FROM moved) runs exactly once, and every part of the statement sees the same snapshot.

Materialization and the old optimization fence

Definition · Materialized vs inlined CTE

A materialized CTE is computed once into a temporary result that the outer query then reads; filters in the outer query can't be pushed into it. An inlined CTE is merged into the outer query like a derived table, so the planner can push predicates down and use indexes.

Before PostgreSQL 12, every CTE was materialized. That made CTEs an optimization fence: WITH t AS (SELECT * FROM big) SELECT * FROM t WHERE id = 5 scanned all of big. Some people relied on this to stop the planner from making bad choices. Since 12, a non-recursive, side-effect-free CTE referenced once is inlined by default, and one referenced more than once is materialized. You can override either way:

WITH t AS MATERIALIZED     (SELECT ...)   -- compute once (expensive, reused)
WITH t AS NOT MATERIALIZED (SELECT ...)   -- inline even if referenced twice

MySQL 8 may merge a CTE into the outer query or materialize it, at the optimizer's discretion.

Recursive CTEs

Algorithm · WITH RECURSIVE evaluation
  1. Evaluate the anchor (the non-recursive term before UNION ALL). Its rows are the first result rows and the initial working table.
  2. Evaluate the recursive term, in which the CTE's name refers to the working table only (the rows produced by the previous step).
  3. Append the new rows to the result; they become the next working table.
  4. Repeat from step 2 until a step produces no rows. With UNION instead of UNION ALL, rows already seen are discarded first.
-- the subtree under "Electronics", indented, depth-first
WITH RECURSIVE subtree AS (
  SELECT id, parent_id, name, 0 AS depth, ARRAY[id] AS path
  FROM app.categories
  WHERE id = 1                                        -- anchor
  UNION ALL
  SELECT c.id, c.parent_id, c.name, s.depth + 1, s.path || c.id
  FROM app.categories c
  JOIN subtree s ON c.parent_id = s.id                -- one level down per step
  WHERE NOT c.id = ANY (s.path)                       -- cycle guard
    AND s.depth < 20                                  -- depth guard
)
SELECT repeat('  ', depth) || name AS tree
FROM subtree
ORDER BY path;                                        -- arrays sort element-wise: depth-first

Trees, org charts, bills of materials

Walking up instead of down only flips the join. To list a person's management chain, anchor on the employee and step with JOIN chain c ON e.id = c.manager_id. Bills of materials add a quantity that multiplies along the path:

-- total parts needed to build one assembly 100
WITH RECURSIVE bom AS (
  SELECT component_id, quantity::numeric AS qty
  FROM app.bom_lines WHERE assembly_id = 100
  UNION ALL
  SELECT b.component_id, bom.qty * b.quantity
  FROM app.bom_lines b JOIN bom ON b.assembly_id = bom.component_id
)
SELECT component_id, sum(qty) AS total_qty FROM bom GROUP BY component_id;

Date series for gap-filling

A daily revenue report built with GROUP BY day has no row for days without sales, and a chart then draws a straight line across the gap. Generate the calendar and outer-join the facts to it:

SELECT d::date AS day, COALESCE(sum(o.total_cents), 0) AS revenue_cents
FROM generate_series(date '2026-03-01', date '2026-03-31', interval '1 day') AS g(d)
LEFT JOIN app.orders o
       ON o.created_at >= d AND o.created_at < d + interval '1 day'
      AND o.status = 'paid'
GROUP BY d ORDER BY d;

-- MySQL 8 has no generate_series; a recursive CTE builds the calendar
WITH RECURSIVE days(day) AS (
  SELECT DATE '2026-03-01'
  UNION ALL
  SELECT day + INTERVAL 1 DAY FROM days WHERE day < '2026-03-31'
)
SELECT day FROM days;

Cycles and the limits of SQL graph traversal

If the data contains a cycle (A is B's parent and B is A's, through a bad update), a UNION ALL recursion never terminates, and Postgres has no default depth limit: the query runs until statement_timeout or the temp disk stops it. Carry a path array and refuse to revisit (above), or use the standard clause added in PostgreSQL 14:

WITH RECURSIVE g AS (...)
  CYCLE id SET is_cycle USING path      -- marks and stops cyclic paths
SELECT * FROM g WHERE NOT is_cycle;

MySQL stops at cte_max_recursion_depth (1,000 by default) with an error. Recursive CTEs are fine for trees (category menus, org charts, threaded comments) where each step touches a few rows. They struggle with real graphs: in a social network the frontier grows by the average degree at every hop, so "friends within 4 hops" can touch millions of rows, and each hop is a full join. Alternatives inside Postgres: a closure table, a materialized path (ltree) for read-heavy trees, or the Apache AGE extension. When the product is the graph (recommendations, fraud rings, shortest paths), use a graph database such as Neo4j alongside the relational system of record.

What breaks in production
  • Runaway recursion after one bad parent_id update creates a cycle. Always add a cycle or depth guard.
  • Accidental fence: a CTE referenced twice is materialized, so a filter in the outer query no longer reaches the index. Check with EXPLAIN, or mark it NOT MATERIALIZED.
  • Unordered tree output: recursion order isn't guaranteed. Without ORDER BY path the menu comes back shuffled.
  • Gap-free charts that aren't: a WHERE o.status = 'paid' on the outer side of the calendar join removes the empty days again (L206), so it belongs in ON.

Window Functions

50m video55m practice

A window function computes a value for each row from a set of related rows (its window) without collapsing those rows into one. Rankings, running totals, previous-row comparisons and "top N per group" become one pass over sorted data instead of self-joins.

Aggregate without collapsing

SELECT id, user_id, total_cents,
       sum(total_cents) OVER (PARTITION BY user_id)                    AS user_total,
       round(100.0 * total_cents / sum(total_cents) OVER (PARTITION BY user_id), 1) AS pct_of_user,
       row_number()     OVER (PARTITION BY user_id ORDER BY created_at) AS nth_order
FROM app.orders;
Definition · The OVER clause
  • PARTITION BY splits the rows into independent groups (the whole result if omitted). Unlike GROUP BY, every row stays in the output.
  • ORDER BY orders rows within each partition. Ranking and offset functions need it, and it changes the default frame of aggregates (below).
  • A frame clause picks which rows around the current one an aggregate sees.

Window functions are evaluated after WHERE, GROUP BY and HAVING (L207), so you can't filter on them in WHERE. Wrap the query in a subquery or CTE and filter outside.

Ranking

For four rows ordered by score 100, 90, 90, 80:

ntile(2)1, 1, 2, 2splits the partition into n buckets of near-equal size (quartiles: ntile(4))

Offsets: LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE

SELECT day, revenue,
       revenue - lag(revenue) OVER w           AS change_vs_yesterday,  -- NULL on the first day
       lag(revenue, 7, 0) OVER w               AS same_day_last_week,   -- offset 7, default 0
       lead(revenue) OVER w                    AS tomorrow,
       first_value(revenue) OVER w             AS first_day_revenue,
       nth_value(revenue, 2) OVER w            AS second_day_revenue    -- NULL on day 1 (frame!)
FROM daily_revenue
WINDOW w AS (ORDER BY day);

lag/lead count rows, not days: if a day is missing, "7 rows back" is not "a week ago". Fill the gaps first (L209). The WINDOW clause names a window definition once; OVER w uses it, and OVER (w ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) extends it with a frame.

Aggregates over a frame

SELECT day, revenue,
       sum(revenue) OVER (ORDER BY day)                                   AS running_total,
       avg(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg_7_rows,
       avg(revenue) OVER (ORDER BY day RANGE BETWEEN INTERVAL '6 days' PRECEDING
                                              AND CURRENT ROW)            AS avg_7_days,
       count(*)     OVER (ORDER BY day)                                   AS days_so_far
FROM daily_revenue;
Definition · Frame modes
  • ROWS: offsets count physical rows. 6 PRECEDING means the six rows before this one.
  • RANGE: offsets are distances in the value of the single ORDER BY key (INTERVAL '6 days' PRECEDING, supported since PostgreSQL 11). Rows with an equal key, called peers, are always in or out together.
  • GROUPS: offsets count peer groups. 1 PRECEDING means the previous distinct key value with all its rows.
  • Bounds: UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING, UNBOUNDED FOLLOWING.
  • Default: with an ORDER BY, RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which runs to the current row and its peers. Without an ORDER BY, the whole partition.

The fix for last_value is an explicit frame: last_value(v) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING), or simply first_value with the order reversed. Make running totals deterministic by using a total order (ORDER BY day, id) with ROWS.

Patterns: top N, deduplication, sessions, funnels

-- top 3 products per category by units sold (dense_rank keeps ties; row_number gives exactly 3)
SELECT category_id, product_id, units
FROM (SELECT category_id, product_id, units,
             dense_rank() OVER (PARTITION BY category_id ORDER BY units DESC) AS rnk
      FROM product_sales) t
WHERE rnk <= 3;

-- deduplicate an import: keep the newest row per email
DELETE FROM app.customer_import c
USING (SELECT id, row_number() OVER (PARTITION BY lower(email)
                                     ORDER BY updated_at DESC, id DESC) AS rn
       FROM app.customer_import) d
WHERE c.id = d.id AND d.rn > 1;
Worked example · Sessionization and a funnel

A session is a run of a user's events with no gap longer than 30 minutes. Mark each event that starts a session, then a running sum of the marks numbers the sessions:

WITH marked AS (
  SELECT user_id, ts, kind,
         CASE WHEN lag(ts) OVER w IS NULL
                OR ts - lag(ts) OVER w > interval '30 minutes' THEN 1 ELSE 0 END AS starts
  FROM app.events
  WINDOW w AS (PARTITION BY user_id ORDER BY ts)
),
sessions AS (
  SELECT user_id, ts, kind,
         sum(starts) OVER (PARTITION BY user_id ORDER BY ts ROWS UNBOUNDED PRECEDING) AS session_no
  FROM marked
),
steps AS (                -- first time each funnel step happened in each session
  SELECT user_id, session_no,
         min(ts) FILTER (WHERE kind = 'view')        AS viewed,
         min(ts) FILTER (WHERE kind = 'add_to_cart') AS carted,
         min(ts) FILTER (WHERE kind = 'purchase')    AS bought
  FROM sessions GROUP BY user_id, session_no
)
SELECT count(viewed)                              AS sessions_viewed,
       count(*) FILTER (WHERE carted > viewed)     AS then_carted,
       count(*) FILTER (WHERE bought > carted AND carted > viewed) AS then_bought
FROM steps;

The comparisons require each step to come after the previous one; a NULL step makes the comparison UNKNOWN, so that session drops out of the later counts, which is exactly what a funnel means.

Window functions need their input sorted by the partition and order keys. An index on (user_id, ts) can provide that order; otherwise the plan has a Sort under the WindowAgg node, which spills to disk when it exceeds work_mem.

What breaks in production
  • The default frame: last_value that returns the current row, and running totals that jump on tied timestamps.
  • Non-total ordering in row_number(): dedup jobs that keep a different row on every run. Always end the window's ORDER BY with a unique column.
  • Rows are not days: ROWS 6 PRECEDING over data with missing days averages more than a week. Use RANGE INTERVAL or fill the gaps.
  • Windows over the whole table in a request path: a sort of millions of rows per call. Filter first, in an inner query.

Views & Materialized Views

30m video35m practice

A view is a named query that is expanded into every statement that uses it. A materialized view stores the query's result and serves it until you refresh it. The first is about abstraction and access control; the second trades freshness for read speed.

Views: encapsulation and column-level access

CREATE VIEW app.order_summary AS
SELECT o.id, o.user_id, o.status, o.created_at,
       count(oi.*)                        AS item_count,
       sum(oi.quantity * oi.unit_price)   AS total
FROM app.orders o
JOIN app.order_items oi ON oi.order_id = o.id
GROUP BY o.id;

-- support staff see customers without password hashes or payment tokens
CREATE VIEW app.customer_directory AS
SELECT id, email, display_name, created_at FROM app.users;
GRANT SELECT ON app.customer_directory TO support_role;   -- no grant on app.users
Definition · View

A view stores query text, not rows. When a query mentions it, the rewriter substitutes the definition as a subquery, and the planner optimizes the combined statement, so filters on the view can still reach the base tables' indexes. By default the view accesses its base tables with the view owner's privileges, which is what makes the access-control pattern above work. PostgreSQL 15 added WITH (security_invoker = true) to check the caller's privileges instead.

For row-level restrictions in a view (WHERE tenant_id = current_setting('app.tenant')::bigint), add WITH (security_barrier); otherwise a user-supplied function in the outer query could be evaluated before the view's filter and see hidden rows. Row-level security policies are the fuller answer.

Updatable views and WITH CHECK OPTION

Postgres can update through a view automatically when it is simple: one table (or updatable view) in FROM; no DISTINCT, GROUP BY, HAVING, LIMIT, OFFSET, WITH, UNION/INTERSECT/EXCEPT; no aggregates, window functions or set-returning functions in the select list. Columns that are plain references are writable; computed ones are read-only. order_summary above is not updatable. To make a complex view writable, define INSTEAD OF triggers (L219).

CREATE VIEW app.active_products AS
SELECT id, sku, name, price, active FROM app.products WHERE active
WITH CHECK OPTION;

UPDATE app.active_products SET price = 9.99 WHERE id = 7;     -- fine
UPDATE app.active_products SET active = false WHERE id = 7;   -- ERROR: violates check option

Without the check option, the second statement would succeed and the row would vanish from the view that was just used to write it. WITH CHECK OPTION rejects inserts and updates whose resulting row the view could not see. CASCADED (the default) also checks the conditions of views this one is built on; LOCAL checks only its own.

Views as a compatibility layer

When a schema change would break deployed code, a view can keep the old shape alive during the transition (part of expand–contract, L215). Rename users to accounts and create CREATE VIEW app.users AS SELECT id, email AS email_address, ... FROM app.accounts. It is simple and auto-updatable, so old code keeps reading and writing while new code moves over; then drop the view. Two constraints: Postgres records view dependencies, so you can't drop or change the type of a column a view uses without dropping the view first (or CASCADE, which drops it silently), and CREATE OR REPLACE VIEW can only add columns at the end, not remove, rename or retype existing ones.

Materialized views

CREATE MATERIALIZED VIEW app.daily_sales AS
SELECT date_trunc('day', o.created_at AT TIME ZONE 'UTC')::date AS day,
       p.category_id,
       sum(oi.quantity * oi.unit_price) AS revenue,
       count(DISTINCT o.id)             AS orders
FROM app.orders o
JOIN app.order_items oi ON oi.order_id = o.id
JOIN app.products p     ON p.id = oi.product_id
WHERE o.status IN ('paid', 'shipped')
GROUP BY 1, 2;

CREATE UNIQUE INDEX daily_sales_pk ON app.daily_sales (day, category_id);  -- needed for CONCURRENTLY
REFRESH MATERIALIZED VIEW app.daily_sales;               -- reads blocked while it runs
REFRESH MATERIALIZED VIEW CONCURRENTLY app.daily_sales;  -- reads continue

A plain REFRESH rebuilds the result and swaps it in under an ACCESS EXCLUSIVE lock, so readers wait for the whole duration. CONCURRENTLY computes the new result, diffs it against the old one and applies the changes as ordinary row operations, so readers keep the old data until it commits. It needs a unique index on plain columns (no WHERE clause) to match rows, is slower, writes more WAL, and doesn't work on a view created WITH NO DATA that has never been populated.

Scheduling, and matview vs cache

Refresh with the pg_cron extension inside the database, or from the application:

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

@Component
class DailySalesRefresher {
    private final JdbcTemplate jdbc;

    DailySalesRefresher(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Scheduled(cron = "0 */15 * * * *")      // Spring cron: seconds first; every 15 minutes
    void refresh() {
        jdbc.execute("REFRESH MATERIALIZED VIEW CONCURRENTLY app.daily_sales");
    }
}

With five instances of the service, all five fire on schedule. Concurrent refreshes of one matview queue on its lock and redo the same work, so guard the job with ShedLock or pg_try_advisory_lock (L218), and alert when the last successful refresh is too old.

  • Views on views on views: each layer adds joins the planner must untangle, and a small edit at the bottom changes plans everywhere.

Indexes: Types, Structure & Design

55m video55m practice

An index is a second, sorted copy of some columns with pointers back to the rows, so a lookup becomes a short tree descent instead of a full scan. Each index speeds up the queries whose shape matches it and adds a cost to every write.

From O(n) to O(log n): the B-tree

Without an index, WHERE email = ? reads every page of the table. A B-tree keeps keys sorted in fixed-size pages (8 KB in Postgres). Internal pages hold separator keys and child pointers; leaf pages hold (key, row pointer) entries and are linked to their neighbours. With a few hundred entries per page, the fan-out is a few hundred per level: three levels reach tens of millions of keys and four reach billions, so a lookup costs about 3–4 page reads, most of them cached.

Page splits and fill factor. Inserting into a full leaf splits it into two half-full pages and adds a separator to the parent (and, rarely, the split propagates up to a new root). Random keys such as UUIDv4 split pages all over the tree; ever-increasing keys only touch the rightmost leaf, and Postgres packs those splits tightly. fillfactor (default 90 for B-tree indexes, 100 for tables) leaves free space in each page at build time to absorb updates. Since PostgreSQL 13, B-trees also deduplicate repeated keys, which shrinks indexes on low-cardinality columns.

Heap vs clustered: Postgres and InnoDB

That is why random UUID primary keys hurt InnoDB the most: inserts land on random pages of the table itself (L215, L219). Postgres's CLUSTER reorders a heap once by an index, but the order isn't maintained afterwards.

Composite indexes, leftmost prefixes, column order

Rule · Leftmost prefix

An index on (a, b, c) is sorted by a, then b within equal a, then c. It serves efficiently any predicate that pins a leftmost prefix: a; a, b; a, b, c; equality on a with a range on b; and ORDER BY a, b. For WHERE b = ? alone the matching entries are scattered through the whole index. (PostgreSQL 18 can skip-scan a leading column that has few distinct values, but don't design around it.) Once a column is used for a range, the columns after it can only filter entries, not narrow the scan.

Choose the order from the queries, not from habit. Equality columns first, then the one range or sort column. For WHERE user_id = ? AND status = ? ORDER BY created_at DESC, the index is (user_id, status, created_at DESC): the scan seeks to one (user, status) prefix and reads rows already in order. Between equality columns, put first the one that other queries also filter on alone, so one index serves several queries. The "most selective column first" advice matters much less than matching the query shape.

Covering, partial, expression and unique indexes

-- covering: answer from the index alone (Index Only Scan)
CREATE INDEX orders_user_created_idx ON app.orders (user_id, created_at DESC) INCLUDE (status, total_cents);

-- partial: index only the rows queries ask for; smaller and cheaper to maintain
CREATE INDEX users_live_email_idx ON app.users (email) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX users_live_email_key ON app.users (lower(email)) WHERE deleted_at IS NULL;

-- expression: the query must use the same expression
CREATE INDEX users_email_lower_idx ON app.users (lower(email));
SELECT id FROM app.users WHERE lower(email) = lower(?);

-- at most one default address per user
CREATE UNIQUE INDEX addresses_one_default ON app.addresses (user_id) WHERE is_default;

INCLUDE columns (PostgreSQL 11+) are stored in the leaves but are not part of the sort key, so they make index-only scans possible without widening the tree. An index-only scan still checks the visibility map and visits the heap for pages not marked all-visible, so it pays off on tables that VACUUM keeps up with. A partial index is used only when the planner can prove the query's WHERE implies the index predicate. The unique variants express rules a plain UNIQUE constraint can't: case-insensitive emails, and uniqueness among live rows only.

What indexes cost, and keeping them in check

Every INSERT writes an entry into every index, and so does any UPDATE that can't be done as a heap-only tuple update (which is impossible once an indexed column changes). Each entry produces WAL, takes disk and cache space, and adds work for VACUUM, which must remove dead entries. A table with twelve indexes writes many times as many pages per insert as the same table with one. Indexes also bloat: page splits followed by deletes leave half-empty pages that only REINDEX reclaims.

-- indexes never used since stats were last reset (check every replica too)
SELECT s.relname AS tbl, s.indexrelname AS idx, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0 AND NOT i.indisunique
ORDER BY pg_relation_size(s.indexrelid) DESC;

-- exact duplicates (same table, columns, opclasses, expressions, predicate)
SELECT indrelid::regclass AS tbl, array_agg(indexrelid::regclass) AS same_definition
FROM pg_index
GROUP BY indrelid, indkey::text, indclass::text,
         coalesce(indexprs::text, ''), coalesce(indpred::text, '')
HAVING count(*) > 1;

Also look for prefix-redundant indexes: (user_id) is usually redundant next to (user_id, created_at), unless it enforces uniqueness.

Note · CREATE INDEX CONCURRENTLY

Plain CREATE INDEX holds a SHARE lock that blocks all writes until the build finishes. CREATE INDEX CONCURRENTLY allows reads and writes during the build: it scans the table twice and waits for older transactions to finish, so it takes longer. It can't run inside a transaction block, so many migration tools need a per-migration setting to run it outside one. If it fails, it leaves an INVALID index that still slows down writes; drop it and retry. DROP INDEX CONCURRENTLY and REINDEX ... CONCURRENTLY (12+) follow the same pattern.

What breaks in production
  • Index on every column "just in case": write throughput falls, WAL and replica lag grow, and most of the indexes are never used.
  • Wrong column order: (created_at, user_id) for a per-user query scans every user's rows in the date range.
  • Expression mismatch: an index on lower(email) and a query on email, so the index is never used.
  • Non-concurrent build on a hot table: writes stall for the whole build.

EXPLAIN, Query Plans & Statistics

50m video55m practice

The planner picks a plan by estimating how many rows each step will produce and pricing the alternatives. When a query is slow, the cause is usually a wrong row estimate; EXPLAIN ANALYZE shows where the estimate and reality diverge.

EXPLAIN and its options

  • EXPLAIN query: the chosen plan with estimates; nothing is executed.
  • EXPLAIN ANALYZE query: runs the query and adds actual times, row counts and loops per node. For INSERT/UPDATE/DELETE, wrap it in BEGIN; ... ROLLBACK;, because the changes really happen.
  • EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT JSON): BUFFERS adds page counts (on by default with ANALYZE since PostgreSQL 18), VERBOSE adds output columns and schema-qualified names, and FORMAT JSON produces output for visual tools. SETTINGS lists non-default planner settings, and TIMING OFF reduces the overhead of timing every row.

Run it with realistic data and parameters: a plan on a 1,000-row dev table says little about 50M rows in production. For a statement your Java code prepares, explain it with the actual parameter values, because the plan can depend on them (L221).

Estimated vs actual rows

Every choice above depends on row counts. If the planner expects 1 row from a filter and gets 50,000, it picks a Nested Loop that runs the inner index scan 50,000 times where a Hash Join would have been far faster. Scan the plan for the lowest node where estimate and actual differ by 10× or more; everything above it was planned on a wrong number. Common causes: stale statistics after a bulk load, correlated columns (the planner multiplies selectivities as if columns were independent), predicates on expressions, functions it can't see into, skewed values outside the most-common list, and generic plans for prepared statements.

Statistics: ANALYZE, targets, extended statistics

Planner statistics come from ANALYZE, which samples about 300 × default_statistics_target rows (100 by default, so 30,000 rows) and stores per column: null fraction, number of distinct values, most common values with frequencies, a histogram, and physical correlation. They are visible in pg_stats. Autovacuum re-analyzes a table after roughly 10% of it has changed; after a big load or delete, run ANALYZE yourself. These are different from the cumulative activity statistics (pg_stat_user_tables, pg_stat_user_indexes: scan counts, tuples, last vacuum). Those were gathered by a separate "statistics collector" process until PostgreSQL 15 and now live in shared memory.

ALTER TABLE app.orders ALTER COLUMN status SET STATISTICS 1000;   -- finer histogram for a skewed column
ANALYZE app.orders;

-- city and postcode are strongly correlated; tell the planner
CREATE STATISTICS addresses_city_zip (dependencies, ndistinct, mcv)
  ON city, postcode FROM app.addresses;
ANALYZE app.addresses;

Without the extended statistics, WHERE city = 'Berlin' AND postcode = '10115' is estimated as P(city) × P(postcode), far fewer rows than the real count, because every row with that postcode is in Berlin.

  • Plan flips: a query is fast for months, then statistics change after a bulk load and the planner switches to a Nested Loop over 10M rows. Compare estimates with actuals, then fix the statistics (ANALYZE, targets, extended stats) before reaching for hints.

Query Optimization Patterns & Anti-Patterns

50m video55m practice

Most slow queries match a handful of recognisable shapes, each with a standard fix. The skill is to measure first, recognise the shape in the plan, apply the smallest fix that works, and measure again.

Sargable predicates

Definition · Sargable

A predicate is sargable ("search-argument-able") when the indexed column stands alone on one side of the comparison, so the index can be searched for a range of key values. Wrapping the column in a function or arithmetic hides it: the database must compute the expression for every row.

Implicit casts are the hardest to spot because the SQL looks right. Look for a cast on the column side in the plan's Filter line, for example Filter: ((id)::numeric = '42'::numeric).

OR, NOT IN, and IN vs EXISTS

WHERE email = ? OR phone = ? with an index on each column is often fine in Postgres: it combines both indexes with a BitmapOr. OR causes trouble when it spans tables (WHERE o.status = 'open' OR u.vip), mixes indexed and unindexed columns, or has to produce ordered output for a LIMIT (bitmap scans return rows in physical order, not index order). The standard fix splits it into index-friendly branches:

SELECT id FROM app.users WHERE email = ?
UNION ALL
SELECT id FROM app.users WHERE phone = ? AND email IS DISTINCT FROM ?;  -- no row twice

Use UNION (which deduplicates) if writing the exclusion condition is awkward. For subqueries, replace NOT IN with NOT EXISTS for correctness with NULLs and to get an anti-join (L204, L208). The old advice "use EXISTS instead of IN" comes from engines that executed IN (subquery) once per row (MySQL before 5.6); modern Postgres plans both as the same semi-join, so check the plan before rewriting.

N+1 queries and unbounded results

N+1 is one query for a list plus one query per element, usually hidden in a loop or a lazy-loading ORM. Each query may take 0.2 ms in the database, but each also costs a network round trip, a pool checkout, and parsing and binding, so the total grows linearly with page size.

import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.SQLException;

import java.util.HashMap;

final class OrderItemsBatch {
    record Item(int lineNo, long productId, int quantity, BigDecimal unitPrice) {}

    /** One query for all orders on the page instead of one per order. */
    static Map<Long, List<Item>> itemsByOrder(Connection conn, List<Long> orderIds) throws SQLException {
        var sql = """
            SELECT order_id, line_no, product_id, quantity, unit_price
            FROM app.order_items
            WHERE order_id = ANY (?)
            ORDER BY order_id, line_no
            """;
        try (var ps = conn.prepareStatement(sql)) {
            ps.setArray(1, conn.createArrayOf("bigint", orderIds.toArray()));
            try (var rs = ps.executeQuery()) {
                var out = new HashMap<Long, List<Item>>();
                while (rs.next()) {
                    out.computeIfAbsent(rs.getLong("order_id"), k -> new ArrayList<>())
                       .add(new Item(rs.getInt("line_no"), rs.getLong("product_id"),
                                     rs.getInt("quantity"), rs.getBigDecimal("unit_price")));
                }

            }

}

Unbounded result sets are the other half: SELECT ... WHERE user_id = ? is fine for a typical user and fatal for the one account with two million orders, whose result is materialized in the JVM heap. Every list query needs a LIMIT or keyset pagination (L205); exports should stream with a fetch size (L222). SELECT * makes both problems worse (L204).

Counting large tables

Postgres can't keep an exact row count in metadata: under MVCC each transaction may see a different number of rows (L218), so COUNT(*) must visit the rows (or an index plus the visibility map). Showing "page 1 of 48,213" on every request means a full count on every request. Alternatives:

  • Don't count: fetch LIMIT n + 1 rows and show "next" if row n + 1 exists.
  • Approximate count for a whole table: SELECT reltuples::bigint FROM pg_class WHERE oid = 'app.orders'::regclass, maintained by VACUUM/ANALYZE (−1 if never analyzed). For a filtered estimate, read the top-level rows from EXPLAIN (FORMAT JSON). Show it as "about 48,000".
  • Denormalized counter: products.review_count, updated in the same transaction as the insert, or by a trigger (L219). It is exact, but every writer updates the same row, which serializes them on that row's lock. Spread very hot counters over several rows and sum them.

Algorithm · Optimization checklist
  1. Find the query from evidence (pg_stat_statements, slow log, traces), not from guesses, and decide whether total time or latency is the goal.
  2. Reproduce with production-like data and the real parameter values. Run EXPLAIN (ANALYZE, BUFFERS) twice (cold and warm) and save the output.
  3. Find the node with the most exclusive time and the lowest node with a large estimate error.
  4. Match the shape: non-sargable predicate, missing or misordered index, N+1, unbounded rows, fan-out join, deep offset, stale statistics.
  5. Apply one change. Re-run, compare times and buffers, and keep the before and after plans in the pull request.
  6. Check the cost of the fix: write overhead of a new index, staleness of a cache, consistency of a denormalized column.
  7. Add a guard: a test that asserts the query count, a plan check in CI, or an alert on mean_exec_time.
What breaks in production
  • Fixing the wrong query: optimizing the slowest-looking query while a 1 ms query called 3M times an hour uses most of the CPU.
  • Wrong bind types: a Java BigDecimal or String bound against a bigint or uuid column turns an index lookup into a scan or an error.
  • Index for every slow query: each one is fine on its own, and together they halve write throughput.
  • Counts on every page view: the most expensive query on the site is the pagination footer.

Normalization, Denormalization & Schema Evolution

45m video45m practice

Normalization stores each fact once, so it can't contradict itself. Denormalization stores a fact twice on purpose to make reads cheaper, and the price is code that keeps the copies consistent. Either way, a live schema changes only through small steps that are compatible with the code already running.

Functional dependencies and anomalies

Definition · Functional dependency

X → Y ("X determines Y") holds when any two rows that agree on X must agree on Y: sku → product_name, order_no → order_date. Normal forms are rules about which dependencies a table may contain, and keys are the attributes everything else should depend on.

A table that stores dependent facts redundantly suffers anomalies. Update: a product's name appears in 40,000 order lines, so a rename must touch all of them, and a partial update leaves contradictions. Insert: you can't record a new product until somebody orders it. Delete: deleting a customer's only order also deletes the only record of the customer's address.

The normal forms

  • 1NF: every value is atomic, with no lists in a cell ('A1, B2') and no repeating column groups (sku1, sku2, sku3). A jsonb or array column is acceptable only if you never need to query, constrain or join on its elements.
  • 2NF: 1NF, and no non-key column depends on part of a composite key. This matters only when the key has more than one column.
  • 3NF: 2NF, and no non-key column depends on another non-key column (no transitive dependency key → A → B). In short: every non-key column depends on "the key, the whole key, and nothing but the key".
  • BCNF: for every non-trivial dependency X → Y, X is a superkey. It differs from 3NF only in rare tables with overlapping candidate keys, for example (student, course, instructor) where each instructor teaches one course.
  • 4NF / 5NF: no independent multi-valued facts in one table (a person's skills and languages together in (person, skill, language)), and no join dependencies beyond those implied by keys. Splitting one table per independent relationship avoids both.

Normalizing a spreadsheet, step by step

One column stays put on purpose: unit_price. It looks as if it depends on sku, but the price charged on this line depends on the line, because list prices change. Getting the dependency right is a domain question, not a mechanical one (L199).

Denormalize only after measuring a read problem, keep the normalized source of truth, and write down how each copy is kept in sync: in the same transaction, by a trigger, or eventually by an asynchronous job.

Note · Entity–attribute–value

EAV stores (entity_id, attribute_name, value text) rows so that "users can add any field". Every value becomes text, with no types, no NOT NULL, no foreign keys and no per-attribute checks. Reading one entity takes a pivot or one self-join per attribute, and the planner's estimates are wrong because all the attributes share one column's statistics. It usually ends in a rewrite. Use real columns for known attributes and jsonb for genuinely open-ended ones.

Keys: natural vs surrogate, bigint vs UUID

The L199 rule stands: surrogate primary keys, with UNIQUE on natural keys. Which surrogate?

  • bigint identity: 8 bytes, monotonically increasing, so inserts go to the right edge of the B-tree and recently written rows stay together in cache. But ids are generated centrally, and they are guessable and reveal volume (/orders/1042 tells a competitor your order rate).
  • UUIDv4: 16 bytes, random, can be generated anywhere without coordination. Random inserts land on random index pages, so more pages are dirty at once, there are more page splits and more WAL after checkpoints (full-page writes), and in InnoDB the table itself is scattered (L212).
  • UUIDv7 (RFC 9562, 2024): a 48-bit millisecond timestamp followed by random bits. New ids sort roughly by creation time, so the index behaves almost like a bigint one, while the ids stay globally unique and hard to guess. The costs: still 16 bytes, and it exposes creation time. Postgres 18 has uuidv7(); otherwise generate it in Java (L219).

A common compromise: a bigint primary key for joins, and a UUID public_id with a unique index for URLs and APIs.

Zero-downtime migrations: expand and contract

Algorithm · Expand–contract (rename name to full_name)
  1. Expand: ALTER TABLE users ADD COLUMN full_name text, nullable with no volatile default, so it is instant. Run every DDL statement with SET lock_timeout = '3s' and retry (L201).
  2. Dual write: deploy code that writes both columns and still reads name (or let a trigger copy writes).
  3. Backfill in batches of a few thousand rows by key range, each batch its own short transaction, watching replica lag.
  4. Enforce: ADD CONSTRAINT full_name_nn CHECK (full_name IS NOT NULL) NOT VALID, then VALIDATE CONSTRAINT (reads and writes continue), then SET NOT NULL, which uses the validated check instead of scanning (12+). Build indexes CONCURRENTLY.
  5. Switch reads to full_name and deploy; then stop writing name.
  6. Contract: once no running version references it, drop name.
import java.sql.Connection;
import java.sql.SQLException;

final class Backfill {
    /** Copies name into full_name in id ranges; each batch commits on its own. */
    static void copyNames(Connection conn, long maxId) throws SQLException, InterruptedException {
        conn.setAutoCommit(true);
        var sql = "UPDATE app.users SET full_name = name WHERE id > ? AND id <= ? AND full_name IS NULL";
        try (var ps = conn.prepareStatement(sql)) {
            for (long from = 0; from < maxId; from += 5_000) {
                ps.setLong(1, from);
                ps.setLong(2, from + 5_000);
                ps.executeUpdate();
                Thread.sleep(100);        // leave headroom for live traffic and replicas
            }
        }
    }
}

Never do the one-step version on a hot table: ALTER COLUMN id TYPE bigint rewrites the table and every index under an ACCESS EXCLUSIVE lock. To widen a key, add a new column, backfill it, build its index concurrently, then swap the columns in a short transaction.

What breaks in production
  • Renames in one deploy: the new code expects full_name while old pods still running during the rollout query name, so half the traffic fails until the rollout ends.
  • Single-statement backfill: UPDATE users SET full_name = name over 80M rows means one huge transaction, long row locks, bloat, and replicas hours behind.
  • Unsynchronized copies: a denormalized total_cents that one code path forgets to update, and invoices that disagree with their lines.
  • EAV reporting: a 30-way self-join to produce one CSV export.

Transactions & ACID

40m video40m practice

A transaction groups statements into one unit that either takes effect completely, durably and with its invariants intact, or not at all. The database delivers that through a write-ahead log, and you pay for it in locks and retained row versions for as long as the transaction stays open.

Transaction control

BEGIN;                                                   -- or START TRANSACTION
INSERT INTO app.orders (user_id, status) VALUES (42, 'pending') RETURNING id;   -- 1001
SAVEPOINT before_coupon;
INSERT INTO app.order_coupons (order_id, code) VALUES (1001, 'NOPE');           -- FK violation
ROLLBACK TO SAVEPOINT before_coupon;                     -- undo only the coupon; order survives
INSERT INTO app.order_items (order_id, line_no, product_id, quantity, unit_price)
VALUES (1001, 1, 7, 2, 19.99);
COMMIT;                                                  -- all of it, or (on ROLLBACK) none of it

In Postgres, an error inside a transaction block aborts the whole transaction. Every later statement fails with "current transaction is aborted, commands ignored until end of transaction block" until you ROLLBACK (or roll back to a savepoint taken before the error), and a COMMIT on an aborted transaction actually performs a rollback. MySQL behaves differently: for most errors only the failed statement is rolled back and the transaction carries on (a deadlock rolls back the whole transaction), which surprises people moving in either direction. RELEASE SAVEPOINT discards a savepoint you no longer need.

ACID, precisely

Definition · ACID
  • Atomicity: all of the transaction's changes become visible, or none do. A crash halfway leaves no partial writes. It is "abortability" more than anything to do with concurrency.
  • Consistency: a transaction moves the database from one state satisfying its constraints to another. The database enforces the invariants you declared (L202); the rest is your code's job. This is not the "C" of the CAP theorem.
  • Isolation: concurrent transactions don't see each other's partial work, to the degree the isolation level promises (L217).
  • Durability: once COMMIT returns, the change survives a crash or power loss.

The write-ahead log

The WAL turns many random data-page writes into one sequential append per commit, and several sessions committing at the same moment share one flush (group commit). The same log feeds replication (L220) and point-in-time recovery. After each checkpoint, the first change to a page writes the whole page into the WAL (full_page_writes), so a page torn by a power cut can be repaired.

Durability also depends on the disk honouring flushes: consumer drives with volatile write caches and no power-loss protection can acknowledge an fsync that hasn't reached stable storage.

Autocommit, scope and long transactions

Autocommit is the default for psql, the MySQL client and every new JDBC connection: each statement is its own transaction, committed when it finishes. Two updates that must happen together (debit one account, credit another) are two separate transactions unless you open one explicitly with BEGIN, or setAutoCommit(false) in JDBC (L222). Python's DB-API is the reverse (a transaction is open until you commit), which is how people coming from it leave transactions open by accident.

Long transactions are toxic. While one is open:

  • its row locks block every writer that touches the same rows, and its DDL locks block everyone;
  • its snapshot stops VACUUM from removing any row version newer than the transaction's start, in every table of the database, so bloat accumulates (L218);
  • it pins a pooled connection, so ten slow requests can exhaust a pool of ten.

Keep transactions short: read and validate first, then open the transaction, write, and commit. Never wait on an HTTP call, a message broker or a user inside one. Look for state = 'idle in transaction' in pg_stat_activity, and set guard rails: idle_in_transaction_session_timeout, statement_timeout, and transaction_timeout (PostgreSQL 17+).

Read-only and "nested" transactions

BEGIN READ ONLY (or SET TRANSACTION READ ONLY) rejects any write, which documents intent and catches bugs, and it can be used to route work to a replica. With autocommit off, pgJDBC turns JDBC's Connection.setReadOnly(true) into BEGIN READ ONLY, and Spring's @Transactional(readOnly = true) builds on that. At SERIALIZABLE, a READ ONLY DEFERRABLE transaction waits for a safe snapshot and then can never fail with a serialization error.

Note · There is no true nesting

A BEGIN inside a transaction only produces a warning in Postgres ("there is already a transaction in progress"). The only nesting is savepoints: rolling back to one undoes the inner work, but "committing" the inner part commits nothing, since the outer ROLLBACK still discards everything. Spring's Propagation.NESTED is a savepoint; REQUIRES_NEW is a separate transaction on a second connection. Each savepoint is a subtransaction with its own cost, and performance cliffs are widely reported once a transaction has more than 64 subtransactions (the size of a per-backend cache), so don't open one per row in a loop.

What breaks in production
  • Half-applied business operations: autocommit JDBC code debits an account, throws, and never credits the other.
  • An "idle in transaction" session left over a weekend: no locks visible in the dashboard, but vacuum is blocked database-wide and tables have doubled in size.
  • HTTP calls inside the transaction: the payment provider slows to 10 s, every checkout holds a connection and row locks for 10 s, and the pool runs dry.
  • Ignoring the aborted state: code that catches an exception and carries on in the same Postgres transaction gets "current transaction is aborted" on every following statement.

Isolation Levels & Concurrency Anomalies

50m video50m practice

Isolation levels say which interleavings of concurrent transactions you are allowed to observe. The standard names four levels, but each database implements them differently, so you have to know which anomalies your database actually prevents at the level you use.

The anomalies

Definition · Six anomalies
  • Dirty read: T1 reads a value T2 wrote but hasn't committed. If T2 rolls back, T1 acted on data that never existed.
  • Non-repeatable read: T1 reads a row, T2 updates it and commits, and T1's second read returns a different value.
  • Phantom read: T1 runs WHERE status = 'open', T2 inserts a matching row and commits, and T1's re-run returns an extra row.
  • Lost update: T1 and T2 both read stock = 10 and both write stock = read − 1. The result is 9 instead of 8, and one decrement is gone.
  • Read skew: T1 reads account A, T2 moves 100 from A to B and commits, T1 reads B. T1 sees a total that never existed at any single moment.
  • Write skew: T1 and T2 read overlapping data, each makes a decision from it, and they update different rows. Each write is fine alone; together they break an invariant that spans rows.

Demonstrate each with two psql sessions, side by side. Lost update, in the default READ COMMITTED:

-- session A                                   -- session B
BEGIN;                                         BEGIN;
SELECT stock FROM app.products WHERE id = 7;   SELECT stock FROM app.products WHERE id = 7;
-- 10                                          -- 10
UPDATE app.products SET stock = 9 WHERE id = 7;
COMMIT;
                                               UPDATE app.products SET stock = 9 WHERE id = 7;
                                               COMMIT;     -- stock = 9: A's sale is lost
-- fixes: SET stock = stock - 1 (atomic in one statement), SELECT ... FOR UPDATE (L218),
-- a version column (L203), or REPEATABLE READ, where B's UPDATE fails with 40001

The standard defines its levels by three phenomena only, which is why lost update, read skew and write skew are missing from its table, and why Berenson et al. (1995) criticised the definitions. Two consequences matter in practice. "Repeatable read" in Postgres and in MySQL are different guarantees: Postgres aborts a lost update, MySQL lets it through. And Oracle's "serializable" is not serializable in the sense the standard intends.

How Postgres read committed handles a write conflict: if B's UPDATE finds a row that A has updated but not yet committed, B waits. When A commits, B re-checks its WHERE against the new row version and applies its change to that version. That is why SET stock = stock - 1 is safe at read committed while read-then-write in application code is not.

Write skew, and serializable in Postgres

Postgres SERIALIZABLE (SSI, since 9.1) takes no extra blocking locks. It records read dependencies as SIREAD "predicate locks" and aborts a transaction when it finds a dangerous pattern of read–write dependencies, with ERROR: could not serialize access due to read/write dependencies among transactions (SQLState 40001). That contract has three practical consequences:

  • Every serializable transaction must be retryable: the whole transaction re-runs from the start, including its reads. Retrying only the last statement is wrong.
  • Aborts can be false positives (the dependency tracking is conservative), so expect some even when no real anomaly occurred, more of them under heavy contention, and more when sequential scans lock whole tables.
  • It protects only transactions that run at SERIALIZABLE. A read committed transaction on the same rows is not checked.
import java.sql.Connection;
import java.sql.SQLException;
import java.util.concurrent.ThreadLocalRandom;
import javax.sql.DataSource;

final class SerializableTx {
    @FunctionalInterface
    interface Work<T> { T run(Connection conn) throws SQLException; }

    static <T> T run(DataSource ds, Work<T> work) throws SQLException, InterruptedException {
        for (int attempt = 1; ; attempt++) {
            try (Connection conn = ds.getConnection()) {
                conn.setAutoCommit(false);
                conn.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
                try {
                    T result = work.run(conn);
                    conn.commit();
                    return result;
                } catch (SQLException e) {
                    conn.rollback();
                    boolean retryable = "40001".equals(e.getSQLState())    // serialization failure
                                     || "40P01".equals(e.getSQLState());   // deadlock detected
                    if (!retryable || attempt == 5) throw e;
                }
            }
            Thread.sleep(ThreadLocalRandom.current().nextLong(5, 20L * attempt));  // jittered backoff
        }
    }
}

Note that the work runs again on retry, so it must have no side effects outside the transaction (no emails, no HTTP calls). A pool such as HikariCP resets the isolation level when the connection is returned. Spring expresses the same thing as @Transactional(isolation = Isolation.SERIALIZABLE) plus a retry policy (L331).

Set it per transaction in SQL (BEGIN ISOLATION LEVEL SERIALIZABLE, or SET TRANSACTION as the first statement) or in JDBC with conn.setTransactionIsolation(...) before the transaction starts. default_transaction_isolation changes the default for a role or database.

Interview trap
  • "Repeatable read prevents lost updates." In Postgres it does, by aborting; in MySQL's default repeatable read the second writer silently overwrites.
  • "Serializable means lots of locking." Not in Postgres: SSI doesn't block readers or writers; it aborts, and you retry.
  • "Read uncommitted is faster in Postgres." It is the same as read committed.
  • "Snapshot isolation is serializable." Write skew is the counterexample, and Oracle's SERIALIZABLE allows it.

Locking, MVCC & Deadlocks

50m video50m practice

Postgres keeps old versions of rows so that readers and writers never wait for each other; only writers to the same row queue. Those old versions must later be vacuumed away, and explicit locks taken in inconsistent orders produce deadlocks.

MVCC: row versions and snapshots

Definition · Tuple versions

Every row version (tuple) carries xmin, the id of the transaction that created it, and xmax, the id of the transaction that deleted or replaced it (0 if none). An UPDATE never overwrites a row: it writes a new version and sets xmax on the old one. A snapshot records which transactions had committed when it was taken. A version is visible to it if its xmin committed before the snapshot and its xmax did not.

You can watch it happen: SELECT xmin, xmax, ctid, price FROM app.products WHERE id = 7 before and after an update shows a new ctid (physical location) and a new xmin. Writers still conflict with writers: a second UPDATE of the same row waits for the first transaction to end (L217).

Vacuum, bloat and wraparound

VACUUM scans for dead tuples, removes their index entries, marks the space reusable, and updates the visibility map (which index-only scans rely on) and the free space map. It doesn't return space to the OS except at the end of the file; VACUUM FULL rewrites the table under an ACCESS EXCLUSIVE lock (the pg_repack extension does it online). Autovacuum runs it once dead tuples exceed about 50 + 20% of the table by default, which is too late for large hot tables, so tune per table: ALTER TABLE app.jobs SET (autovacuum_vacuum_scale_factor = 0.01).

Bloat builds up when vacuum can't keep up or isn't allowed to: a long-open transaction, an abandoned replication slot, or a forgotten prepared transaction all hold back the oldest visible snapshot, so nothing newer can be removed (L216). HOT (heap-only tuple) updates help: if no indexed column changes and the page has room, the new version goes on the same page with no index writes. A table fillfactor below 100 leaves that room.

Note · Transaction ID wraparound

Transaction ids are 32-bit, and visibility compares them modulo 232, so only about 2 billion ids of history can be ordered. Vacuum freezes old tuples (marks them visible to everyone) so their xmin no longer matters. If freezing falls behind, autovacuum starts aggressive anti-wraparound vacuums when a table's oldest unfrozen id passes autovacuum_freeze_max_age (200 million). Close to the limit, Postgres stops assigning new transaction ids, and every write fails until a vacuum completes. Monitor SELECT datname, age(datfrozenxid) FROM pg_database.

Worked example · A deadlock in two sessions 
-- A                                            -- B
BEGIN;                                          BEGIN;
UPDATE accounts SET bal = bal - 10 WHERE id = 1;
                                                UPDATE accounts SET bal = bal - 10 WHERE id = 2;
UPDATE accounts SET bal = bal + 10 WHERE id = 2;   -- waits for B
                                                UPDATE accounts SET bal = bal + 10 WHERE id = 1;   -- waits for A
                                                -- after deadlock_timeout (1 s):
                                                ERROR:  deadlock detected   (SQLSTATE 40P01)
-- A's update now proceeds

Each transaction holds the lock the other needs, so neither can proceed. Postgres checks for such cycles once a lock wait exceeds deadlock_timeout and aborts one participant. The fix is lock ordering: every code path locks rows in the same global order (lowest id first), so a cycle can't form. In Java, sort the ids before updating, or take all the locks in one statement: SELECT ... WHERE id IN (1, 2) ORDER BY id FOR UPDATE. Keep transactions short, and treat 40P01 as retryable (L217).

A safe work queue, and when not to lock

CREATE INDEX jobs_ready_idx ON app.jobs (run_at, id) WHERE status = 'queued';

WITH next AS (
  SELECT id FROM app.jobs
  WHERE status = 'queued' AND run_at <= now()
  ORDER BY run_at, id
  LIMIT 10
  FOR UPDATE SKIP LOCKED                 -- workers never wait for each other or take the same job
)
UPDATE app.jobs j
SET status = 'running', locked_by = ?, locked_until = now() + interval '5 minutes'
FROM next
WHERE j.id = next.id
RETURNING j.id, j.payload;

Commit the claim, process the jobs outside the transaction, then mark each one done. A sweeper re-queues jobs whose locked_until has passed, which covers crashed workers. Many workers can poll this concurrently without blocking, which makes Postgres a reasonable job queue at moderate volume (Java job libraries such as db-scheduler offer this as a polling strategy). The alternative, holding the row lock while processing, is simpler but keeps a transaction open for the whole job.

Optimistic locking is usually the better answer for edits made by people and for low-contention updates: no lock is held across requests, and the rare conflict becomes a 409 (L203). Use pessimistic locks for short, high-contention critical sections inside one transaction: claiming jobs, decrementing scarce stock, allocating gapless invoice numbers.

What breaks in production
  • Lock queues behind DDL: a waiting ACCESS EXCLUSIVE request blocks every later reader (L201).
  • Vacuum held back: a replication slot nobody consumes keeps every dead row, and disk usage climbs until the server stops.
  • Deadlocks from unordered batches: two jobs updating the same accounts in different orders deadlock at random under load.
  • Session advisory locks in a pool: the lock outlives the request and blocks the next run of the job for good.

Functions, Triggers, Sequences & Key Strategies

40m video40m practice

Code that runs inside the database runs on every write, from every client, and is invisible from the application's source. Use functions and triggers for mechanics such as timestamps, audit trails and counters, not for business rules. Key generation is a separate choice: who creates the id, how big it is, and whether new ids arrive in order.

Functions: SQL and PL/pgSQL

-- SQL function: a parameterized query the planner can often inline
CREATE FUNCTION app.top_products(p_category bigint, p_limit int DEFAULT 10)
RETURNS TABLE (product_id bigint, units bigint)
LANGUAGE sql STABLE AS $$
  SELECT oi.product_id, sum(oi.quantity)
  FROM app.order_items oi JOIN app.products p ON p.id = oi.product_id
  WHERE p.category_id = p_category
  GROUP BY oi.product_id
  ORDER BY 2 DESC
  LIMIT p_limit
$$;
SELECT * FROM app.top_products(3, 5);

-- PL/pgSQL: variables, IF, loops, exceptions
CREATE FUNCTION app.apply_discount(p_order bigint, p_pct numeric) RETURNS numeric
LANGUAGE plpgsql AS $$
DECLARE
  v_total numeric;
BEGIN
  IF p_pct NOT BETWEEN 0 AND 50 THEN
    RAISE EXCEPTION 'discount % out of range', p_pct USING ERRCODE = '22023';
  END IF;
  UPDATE app.orders SET total_cents = round(total_cents * (1 - p_pct / 100))
  WHERE id = p_order
  RETURNING total_cents INTO v_total;
  RETURN v_total;
END
$$;

The body is a string, usually written with dollar quoting so it needs no escaping. Parameters can be IN, OUT or INOUT, with defaults. A function returns a scalar, a composite, SETOF type, or RETURNS TABLE (...), which you can select from like a table. Declare the volatility honestly: IMMUTABLE (same inputs, same output, forever; required for expression indexes), STABLE (constant within one statement; may read tables), or VOLATILE (the default; may change data or return different results, like random()). A wrong IMMUTABLE label gives wrong query results and corrupt expression indexes.

Definition · Function vs procedure

A function returns a value, can be called from any SQL expression, and runs inside the caller's transaction; it can't COMMIT. A procedure (CREATE PROCEDURE, PostgreSQL 11+) is invoked with CALL, returns nothing except OUT parameters, and, when called outside an explicit transaction block, may COMMIT and ROLLBACK partway through. That makes procedures suitable for batch maintenance loops that commit each batch. JDBC calls both through CallableStatement or a plain SELECT/CALL (L221).

Triggers

CREATE FUNCTION app.touch_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();       -- BEFORE ROW trigger: modify the row being written
  RETURN NEW;                    -- returning NULL would silently skip the write
END $$;
CREATE TRIGGER products_touch BEFORE UPDATE ON app.products
FOR EACH ROW EXECUTE FUNCTION app.touch_updated_at();

CREATE TABLE app.audit_log (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  table_name text NOT NULL, op text NOT NULL,
  old_row jsonb, new_row jsonb,
  changed_by text NOT NULL DEFAULT current_user,
  changed_at timestamptz NOT NULL DEFAULT now()
);
CREATE FUNCTION app.audit() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO app.audit_log (table_name, op, old_row, new_row)
  VALUES (TG_TABLE_NAME, TG_OP, to_jsonb(OLD), to_jsonb(NEW));   -- OLD/NEW are NULL where not applicable
  RETURN NULL;                   -- AFTER trigger: the return value is ignored
END $$;
CREATE TRIGGER orders_audit AFTER INSERT OR UPDATE OR DELETE ON app.orders
FOR EACH ROW EXECUTE FUNCTION app.audit();
  • Timing: BEFORE triggers can change NEW or cancel the row; AFTER triggers see the final row and are where you write to other tables; INSTEAD OF triggers make complex views writable (L211).
  • Granularity: FOR EACH ROW fires per row with NEW/OLD; FOR EACH STATEMENT fires once per statement, and with REFERENCING NEW TABLE AS new_rows it sees all affected rows as a set, which is much cheaper for bulk writes.
  • Legitimate uses: updated_at, audit trails (every writer is captured, including psql sessions), denormalized counters kept in the same transaction (L215), and invariants that constraints can't express.

Why business logic in triggers goes wrong. A developer reading orderRepository.save(order) can't see that it also reserves stock, sends a notification row and updates a loyalty balance. Triggers fire during bulk loads, backfills and migrations, where nobody wanted them. Several triggers on one table fire in alphabetical order of name. They chain into one another, their cost shows up as a "slow insert" with no visible cause, and an ORM's in-memory entity doesn't know that a trigger changed its row unless it re-reads it. Put business rules in application code, where they are versioned, reviewed, tested and visible.

Sequences, IDENTITY and SERIAL

CREATE SEQUENCE app.ticket_seq START 1000 INCREMENT 1 CACHE 20;
SELECT nextval('app.ticket_seq');     -- 1000
SELECT currval('app.ticket_seq');     -- last value this session got
SELECT setval('app.ticket_seq', 5000);

A sequence is a single-row counter that is deliberately not transactional: nextval is never rolled back, so concurrent transactions never wait for each other to get an id. The consequence is gaps: from rollbacks, from failed ON CONFLICT inserts, from CACHE n (each session reserves n values and discards the unused ones when it disconnects), and after a crash, since sequences log a few values ahead. Gaps are harmless for surrogate keys, which carry no meaning. If the business really needs gapless numbers (some invoice regulations), keep a counter row and take it with SELECT ... FOR UPDATE in the invoice transaction, which serializes every invoice on that row.

UUIDs and index locality

UUIDv4 (gen_random_uuid(), Java's UUID.randomUUID()) has 122 random bits. UUIDv7 (RFC 9562) starts with a 48-bit Unix millisecond timestamp, so it sorts by creation time and keeps the index locality of a sequence. PostgreSQL 18 has uuidv7(); the JDK has no generator, but the layout is simple:

import java.security.SecureRandom;
import java.util.UUID;

final class UuidV7 {
    private static final SecureRandom RANDOM = new SecureRandom();

    /** RFC 9562 version 7: 48-bit ms timestamp, version, 12 + 62 random bits, IETF variant. */
    static UUID next() {
        long millis = System.currentTimeMillis();
        long randA = RANDOM.nextInt(1 << 12);
        long randB = RANDOM.nextLong() & 0x3FFF_FFFF_FFFF_FFFFL;
        long msb = (millis << 16) | (0x7L << 12) | randA;
        long lsb = (0x2L << 62) | randB;
        return new UUID(msb, lsb);           // UUID.version() == 7
    }
}

This version is only ordered to the millisecond; libraries such as uuid-creator add a counter so that ids generated within the same millisecond also sort in creation order.

Partitioning, Replication, Read Replicas & Sharding

45m video40m practice

Partitioning splits one big table into smaller ones on the same server. Replication copies the whole database to other servers. Sharding splits the data across independent servers. Each solves a different scaling problem, and each adds complexity you should take on only when the simpler option has run out.

Declarative partitioning

Definition · Partitioned table

A partitioned table (PostgreSQL 10+) has no storage of its own; it routes each row to one partition, an ordinary table, by a partition key. RANGE assigns contiguous ranges (months of occurred_at), LIST assigns explicit values (region IN ('eu', 'uk')), and HASH assigns by hash(key) mod n to spread writes evenly. Primary keys and unique constraints must include the partition key, because uniqueness is enforced per partition.

CREATE SEQUENCE app.events_id_seq;
CREATE TABLE app.events (
  id          bigint      NOT NULL DEFAULT nextval('app.events_id_seq'),
  occurred_at timestamptz NOT NULL,
  user_id     bigint      NOT NULL,
  kind        text        NOT NULL,
  payload     jsonb,
  PRIMARY KEY (id, occurred_at)                       -- must contain the partition key
) PARTITION BY RANGE (occurred_at);

CREATE TABLE app.events_2026_10 PARTITION OF app.events
  FOR VALUES FROM ('2026-10-01 00:00+00') TO ('2026-11-01 00:00+00');   -- upper bound exclusive
CREATE INDEX ON app.events (user_id, occurred_at);                     -- created on every partition

For a 500M-row events table, monthly partitions of roughly 20–40M rows each keep every index small enough to stay in cache, let autovacuum work on one month at a time, and make retention a metadata operation. Create future partitions ahead of time with a scheduled job or the pg_partman extension; a missing partition makes inserts fail. A DEFAULT partition can catch stray rows, but it rules out DETACH ... CONCURRENTLY and has to be scanned every time a new partition is attached. Keep the count in the hundreds rather than thousands, because planning time grows with the number of partitions.

Partition pruning is the payoff. When a query filters on the partition key, the planner reads only the matching partitions, and the plan shows only those. Pruning also happens at execution time for parameters (Subplans Removed: 23). A query that doesn't filter on the key, such as WHERE id = ? alone, must probe every partition, so partitioning can make some queries slower.

-- archive a month in seconds instead of DELETE-ing 40M rows
ALTER TABLE app.events DETACH PARTITION app.events_2025_10 CONCURRENTLY;   -- PostgreSQL 14+
-- pg_dump it to cold storage, then:
DROP TABLE app.events_2025_10;

-- bulk-load a month offline, then attach it
ALTER TABLE app.events ATTACH PARTITION app.events_2026_11
  FOR VALUES FROM ('2026-11-01 00:00+00') TO ('2026-12-01 00:00+00');

ATTACH scans the new table to check its rows fit the bounds, unless a matching CHECK constraint already proves it, so add one before attaching a large table.

Streaming replication and lag

Physical streaming replication ships the WAL (L216) to standbys, which replay it into a byte-for-byte copy that can serve reads (hot standby). It is asynchronous by default: the primary acknowledges a commit before any standby has it, so failing over to a standby can lose the last moments of commits. With synchronous_standby_names = 'ANY 1 (r1, r2)' commits wait for one standby to confirm. That adds a network round trip to every commit, and if no synchronous standby is reachable, commits wait. Monitor write_lag, flush_lag and replay_lag in pg_stat_replication.

The read-your-writes bug. A user saves their address (primary), the page reloads, and the read goes to a lagging replica that still has the old one. Fixes, from cheapest: route reads to the primary for a few seconds after that user's writes; route by the consistency each endpoint needs, not by "is it a GET"; or return the commit's WAL position (pg_current_wal_lsn()) and have the read wait until the replica's pg_last_wal_replay_lsn() has passed it.

Failover needs three things: detecting that the primary is gone, promoting the most up-to-date standby without ending up with two primaries (split brain), and moving clients to it. Patroni (leader election through etcd, Consul or ZooKeeper) and pg_auto_failover (a monitor node) automate the first two, as do managed services such as RDS Multi-AZ. Clients follow through a DNS name or virtual IP, HAProxy health-checking Patroni's REST endpoint, PgBouncer repointed to the new primary, or the multi-host JDBC URL above. Expect a failover to take tens of seconds and to fail any in-flight transactions, so writes must be retryable.

Logical replication and CDC

Logical replication decodes the WAL into row-level changes (insert, update, delete per table) and applies them to a subscriber through CREATE PUBLICATION / CREATE SUBSCRIPTION. Unlike physical replication it can copy selected tables, between major versions (near-zero-downtime upgrades) and into databases with other tables of their own. The same logical decoding feeds change data capture: Debezium reads a replication slot and publishes each committed change to Kafka (L383). A replication slot keeps WAL until its consumer confirms it, so a stopped consumer fills the primary's disk; alert on pg_replication_slots lag.

Sharding, and when to do it

Sharding puts different rows on different, independent database servers, chosen by a shard key (tenant id, user id). It is the only way to scale writes and storage past one machine, and it costs a lot:

  • Shard key choice decides everything: queries and transactions that stay within one shard are cheap, and everything else is expensive. A tenant much larger than the rest makes a hot shard.
  • Cross-shard queries become scatter-gather; cross-shard transactions need two-phase commit or sagas; unique constraints and foreign keys no longer span the data; ids must be globally unique (L219).
  • Resharding, moving data live when a shard fills up, is a project in itself. Starting with many logical shards mapped onto a few servers makes it a move rather than a split.

Citus (a Postgres extension) distributes tables by a key, co-locates related tables on the same shard and pushes queries down to the workers; Vitess does the same for MySQL (it came from YouTube). When to shard: much later than you think. Before that come query and index work, a bigger server (single machines now offer hundreds of cores and terabytes of RAM), read replicas, caching, partitioning with archival, moving analytics to a warehouse, and splitting data by service. Many large products run on one primary plus replicas.

What breaks in production
  • Stale reads after writes: "I saved it and it's gone", caused by blanket routing of GETs to a replica.
  • Abandoned replication slot: WAL accumulates until the primary's disk fills and it stops accepting writes.
  • No future partitions: on the 1st of the month inserts start failing (or pile into the default partition).
  • Queries that ignore the partition key: an index lookup per partition, so 120 partitions mean 120 lookups.
  • Synchronous replication to one standby: when that standby goes down, every commit hangs.

JDBC is a set of interfaces in java.sql that a vendor driver implements over the database's wire protocol. Every Java data layer, from JdbcTemplate to Hibernate, eventually calls the same handful of methods: get a connection, prepare a statement, bind parameters, read a result set, close everything.

Definition · DriverManager vs DataSource

DriverManager.getConnection(url, user, pw) opens a new physical connection on every call: a TCP handshake, TLS, authentication, and a forked backend process on the server, which takes milliseconds to tens of milliseconds each time. javax.sql.DataSource is an interface for "something that hands out connections", configured once and injected. Production implementations are pools (HikariCP, L222) that keep connections open and lend them out, so close() returns a connection to the pool instead of closing it. Code written against DataSource works unchanged with a pool, a test container, or Spring's transaction-bound connections, so always program against it.

Statement, PreparedStatement, CallableStatement

  • Statement sends finished SQL text. Building that text by concatenating values is how SQL injection happens (L222), and every distinct text is parsed and planned anew. Keep it for fixed DDL.
  • PreparedStatement sends SQL with ? placeholders and the values separately (Parse, then Bind and Execute in the extended protocol). Values can never change the statement's structure, and the parsed statement can be reused: after prepareThreshold executions pgJDBC uses a named server-side statement and caches it per connection, so the server skips parsing. The server may then also switch to a generic plan that ignores the actual values after five executions (plan_cache_mode); usually that saves planning time, but occasionally it is a bad plan for skewed values.
  • CallableStatement calls stored routines with the escape syntax {call app.archive_orders(?)} or {? = call app.order_total(?)}. With Postgres you can also just SELECT app.order_total(?) or CALL app.archive_orders(?) through a PreparedStatement (L219).

ResultSet, metadata and closing everything

import java.math.BigDecimal;
import java.sql.ResultSet;
import java.sql.ResultSetMetaData;
import java.sql.SQLException;
import java.sql.Types;
import java.time.OffsetDateTime;
import java.util.ArrayList;
import java.util.List;
import java.util.UUID;
import javax.sql.DataSource;

public final class OrderQueries {
    public record OrderRow(long id, UUID publicId, String status, BigDecimal total,
                           OffsetDateTime createdAt, Long couponId) {}

    private final DataSource ds;

    public OrderQueries(DataSource ds) { this.ds = ds; }

    public List<OrderRow> recentForUser(long userId, int limit) throws SQLException {
        var sql = """
            SELECT id, public_id, status, total, created_at, coupon_id
            FROM app.orders WHERE user_id = ?
            ORDER BY created_at DESC, id DESC LIMIT ?
            """;
        try (var conn = ds.getConnection();                 // closed last
             var ps = conn.prepareStatement(sql)) {          // closed second
            ps.setLong(1, userId);
            ps.setInt(2, limit);
            try (ResultSet rs = ps.executeQuery()) {         // closed first
                var out = new ArrayList<OrderRow>();
                while (rs.next()) out.add(map(rs));
                return out;
            }
        }
    }

    public long insert(long userId, Long couponId) throws SQLException {
        var sql = "INSERT INTO app.orders (user_id, status, coupon_id) VALUES (?, 'pending', ?) RETURNING id";
        try (var conn = ds.getConnection(); var ps = conn.prepareStatement(sql)) {
            ps.setLong(1, userId);
            if (couponId == null) ps.setNull(2, Types.BIGINT); else ps.setLong(2, couponId);
            try (var rs = ps.executeQuery()) { rs.next(); return rs.getLong(1); }
        }
    }

    private static OrderRow map(ResultSet rs) throws SQLException {
        long coupon = rs.getLong("coupon_id");
        Long couponId = rs.wasNull() ? null : coupon;      // getLong returns 0 for SQL NULL
        return new OrderRow(rs.getLong("id"), rs.getObject("public_id", UUID.class),
                rs.getString("status"), rs.getBigDecimal("total"),
                rs.getObject("created_at", OffsetDateTime.class), couponId);
    }

    static void dump(ResultSet rs) throws SQLException {    // generic: no knowledge of the columns
        ResultSetMetaData md = rs.getMetaData();
        while (rs.next()) {
            var line = new StringBuilder();
            for (int i = 1; i <= md.getColumnCount(); i++) {
                line.append(md.getColumnLabel(i)).append('=').append(rs.getObject(i)).append("  ");
            }
            System.out.println(line);
        }
    }
}
  • A ResultSet starts before the first row; next() moves forward and returns false at the end. The default is forward-only and read-only.
  • Getters by label ("total", or the alias) survive reordering of the select list; getters by index are marginally faster and break silently when the list changes.
  • Primitive getters can't return null: getLong and getInt give 0 and getBoolean gives false for SQL NULL. Call wasNull() right after, or use getObject(col, Long.class).
  • ResultSetMetaData gives column count, labels, type names and nullability, which is enough to write generic exporters and mappers.
Note · What leaks without try-with-resources

Resources close in reverse order of declaration, even when an exception is thrown. Forget the Connection with a pool and it is never returned; after maximumPoolSize leaks, every request waits for connectionTimeout and fails. Without a pool, the server keeps a backend process for every leaked connection until max_connections is reached. A forgotten Statement or ResultSet holds driver memory and server-side prepared statements or portals on that connection; closing the connection closes them according to the JDBC spec, but a pooled connection is never really closed, so close each resource yourself. The garbage collector is not a resource manager.

What breaks in production
  • No socketTimeout: a firewall silently drops a connection and request threads hang until the pool is exhausted.
  • Zeroes for NULLs: getLong("coupon_id") without wasNull() turns "no coupon" into coupon 0.
  • DriverManager per request: connection setup dominates latency and the server runs out of backends.
  • Leaked connections on the exception path: code that closes in a finally it never reaches, or not at all.

JDBC II: Batching, Transactions, Pooling & SQL Injection

50m video55m practicemilestone project

Production JDBC is plain JDBC plus discipline: explicit transaction boundaries, batched writes, streamed reads, pooled connections, and SQL whose structure user input can never change. Today's repository is also the baseline that JPA must match tomorrow.

A correct transaction template

import java.sql.Connection;
import java.sql.SQLException;
import javax.sql.DataSource;

public final class Tx {
    @FunctionalInterface
    public interface SqlWork<T> { T run(Connection conn) throws SQLException; }

    private final DataSource ds;

    public Tx(DataSource ds) { this.ds = ds; }

    public <T> T inTransaction(SqlWork<T> work) throws SQLException {
        try (Connection conn = ds.getConnection()) {
            conn.setAutoCommit(false);                       // BEGIN happens implicitly
            try {
                T result = work.run(conn);
                conn.commit();
                return result;
            } catch (SQLException | RuntimeException e) {
                try { conn.rollback(); } catch (SQLException re) { e.addSuppressed(re); }
                throw e;                                     // never swallow the cause
            }
        }
    }
}

Rollback on every failure, unchecked exceptions included, and attach a failing rollback as a suppressed exception instead of hiding the original. Inside the work, Savepoint sp = conn.setSavepoint() and conn.rollback(sp) undo part of it (L216). The pool (HikariCP) restores auto-commit when the connection is returned. Spring's @Transactional is this template, generated for you (L329).

Batching and generated keys

Algorithm · Batched insert
  1. Turn autocommit off, so the whole batch commits, and flushes the WAL, once.
  2. For each row, bind the parameters and call addBatch(). Every N rows (a few hundred to a few thousand), call executeBatch() so the driver never buffers the whole list.
  3. Execute the remainder (executeLargeBatch() if update counts can exceed int), check the returned counts, and commit.

10,000 inserts in autocommit cost 10,000 round trips and 10,000 WAL flushes; batched in one transaction they cost a handful of each. Speedups of 10–50× over row-by-row autocommit are commonly measured, and pgJDBC's reWriteBatchedInserts=true adds more by rewriting each batch into multi-row INSERTs. Measure the best batch size on your own data.

For keys, conn.prepareStatement(sql, new String[] {"id"}) (or Statement.RETURN_GENERATED_KEYS) makes pgJDBC append RETURNING id, and ps.getGeneratedKeys() returns a result set of the new keys (L203).

Streaming large results with setFetchSize

By default pgJDBC reads the entire result into memory before executeQuery returns, so a 20M-row export needs gigabytes of heap. With a fetch size, the driver uses a server-side cursor and fetches N rows per round trip, but only when autocommit is off, the result set is forward-only, and the SQL is a single statement:

static long exportCsv(DataSource ds, java.io.Writer out) throws SQLException, java.io.IOException {
    try (var conn = ds.getConnection()) {
        conn.setAutoCommit(false);                          // required for cursor-based fetching
        try (var ps = conn.prepareStatement("SELECT id, user_id, total FROM app.orders ORDER BY id")) {
            ps.setFetchSize(1_000);                         // rows per round trip; 0 means all at once
            try (var rs = ps.executeQuery()) {
                long n = 0;
                while (rs.next()) {
                    out.write(rs.getLong(1) + "," + rs.getLong(2) + "," + rs.getBigDecimal(3) + "\n");
                    n++;
                }
                conn.commit();
                return n;
            }
        }
    }
}

The export holds one transaction (and its snapshot) open for its whole duration, so run big ones on a replica (L220). MySQL Connector/J streams with setFetchSize(Integer.MIN_VALUE), or with useCursorFetch=true and a positive fetch size.

import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.util.Map;

final class OrderSql {
    // VULNERABLE: the input becomes SQL text.
    //   email = x' OR '1'='1                                   returns every user
    //   email = x' UNION SELECT id, password_hash FROM app.users --   leaks hashes
    static String unsafeByEmail(String email) {
        return "SELECT id, email FROM app.users WHERE email = '" + email + "'";
    }

    // SAFE: the structure is fixed; the value travels separately and can't become SQL
    static PreparedStatement byEmail(Connection conn, String email) throws SQLException {
        var ps = conn.prepareStatement("SELECT id, email FROM app.users WHERE email = ?");
        ps.setString(1, email);

The baseline: JdbcOrderRepository

import java.math.BigDecimal;
import java.sql.SQLException;
import java.util.List;

public final class JdbcOrderRepository {
    public record NewItem(long productId, int quantity, BigDecimal unitPrice) {}

    private final Tx tx;

    public JdbcOrderRepository(Tx tx) { this.tx = tx; }

    public long place(long userId, List<NewItem> items) throws SQLException {
        BigDecimal total = items.stream()
                .map(i -> i.unitPrice().multiply(BigDecimal.valueOf(i.quantity())))
                .reduce(BigDecimal.ZERO, BigDecimal::add);
        return tx.inTransaction(conn -> {
            long orderId;
            try (var ps = conn.prepareStatement(
                    "INSERT INTO app.orders (user_id, status, total) VALUES (?, 'pending', ?)",
                    new String[] {"id"})) {
                ps.setLong(1, userId);
                ps.setBigDecimal(2, total);
                ps.executeUpdate();
                try (var keys = ps.getGeneratedKeys()) { keys.next(); orderId = keys.getLong(1); }
            }
            try (var ps = conn.prepareStatement("INSERT INTO app.order_items "
                    + "(order_id, line_no, product_id, quantity, unit_price) VALUES (?, ?, ?, ?, ?)")) {
                int line = 0;
                for (var it : items) {
                    ps.setLong(1, orderId);
                    ps.setInt(2, ++line);
                    ps.setLong(3, it.productId());
                    ps.setInt(4, it.quantity());
                    ps.setBigDecimal(5, it.unitPrice());
                    ps.addBatch();
                    if (line % 500 == 0) ps.executeBatch();
                }
                ps.executeBatch();
            }
            return orderId;
        });
    }
}

JDBC makes you write SQL text, binding, key retrieval, batching, transaction scope and object mapping by hand. In return, each place call costs a known, fixed number of round trips: one insert, one batch per 500 items, one commit. Record it: tomorrow's JPA port (L223) must prove from SQL logs that it issues no more.

What breaks in production
  • maxLifetime above the network idle timeout: intermittent "connection reset" errors on the first query after a quiet period.
  • Pool size × instances above max_connections: a scale-out event starts failing new connections across every service.
  • Fetch size with autocommit on: silently ignored by pgJDBC, and the export runs out of memory at 3 a.m.
  • "Sanitized" concatenation: escaping quotes by hand misses encodings and edge cases. Bind values and allowlist identifiers.
