L473 · DAY 473

Java Core Interview Questions

60m video60m practice

Core Java questions test whether you understand the rules well enough to predict behaviour, not whether you memorised definitions. Every answer below follows one shape: state the rule, show a small example, name the gotcha, mention the trade-off.

How to answer

Algorithm · Four-part answer
  1. Rule in one sentence, precisely ("Java is always pass-by-value").
  2. Example: two or three lines of code you could write on the board.
  3. Gotcha: the bug this rule causes in real code.
  4. Trade-off or modern alternative ("records remove most of this boilerplate").

Platform and startup

JDK vs JRE vs JVM?

The JVM loads, verifies and executes bytecode (interpreter plus JIT compilers, garbage collector, threads) and is specified by the JVMS. The JRE is a JVM plus the standard class library: enough to run programs. The JDK adds development tools: javac, jar, jlink, jshell, jcmd, JFR. Gotcha: bytecode is portable; the JVM itself is platform-specific. Modern JDKs no longer ship a separate JRE download; you build a trimmed runtime with jlink.

What happens between typing java Main and main() running?

The launcher parses options, loads the JVM library and creates the VM (heap, GC, JIT, system threads). The bootstrap loader brings up java.base; the application class loader finds Main on the class path. Main is loaded, linked (verified, static fields set to defaults, symbolic references resolved lazily) and initialised (static initialisers run in textual order, superclasses first). The launcher then looks up public static void main(String[]) and invokes it on the main thread. Gotcha: an exception in a static initialiser surfaces as ExceptionInInitializerError, and later uses of that class as NoClassDefFoundError.

Equality, strings and boxing

== vs equals, and the equals/hashCode contract?

== compares primitive values or object identity; equals is logical equality defined by the class (identity by default). Equal objects must have equal hash codes; equals must be reflexive, symmetric, transitive, consistent, and false for null.

class Point {                                  // equals overridden, hashCode forgotten
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) { return o instanceof Point p && p.x == x && p.y == y; }
}
Set<Point> seen = new HashSet<>();
seen.add(new Point(1, 2));
seen.contains(new Point(1, 2));               // false in practice: identity hashes pick different buckets

Fix with Objects.hash(x, y), or make it record Point(int x, int y).

Why is String immutable? What are the pool and intern()? When does StringBuilder matter?

A final class with a private array and no mutators, so strings can be shared freely, cache their hash, serve as safe map keys, and be passed across threads and security checks. Literals are interned in the string pool (on the heap), so "a" == "a" is true while new String("a") == "a" is false; intern() returns the pooled instance. A single a + b + c expression compiles to an efficient invokedynamic concatenation (JEP 280); s += x inside a loop copies the whole string every iteration, which is quadratic, so use a StringBuilder there.

Autoboxing and the Integer cache?

Integer a = 127, b = 127; gives a == b true because Integer.valueOf must cache −128 to 127 (JLS §5.1.7); with 128 it is normally false. Compare boxed values with equals. Two more traps: unboxing null throws NullPointerException (int n = map.get(k); for a missing key), and a Long accumulator in a loop allocates on every addition.

Values, references and copies

Does Java pass objects by reference?

No. Java is always pass-by-value; for object types, the value copied is a reference. That is why a method can change the object's fields but cannot make the caller's variable point somewhere else, and why a swap(a, b) method on references cannot work. "By reference" would mean reassigning the parameter changes the caller's variable, as with C++ references.

Shallow vs deep copy?

A shallow copy duplicates the outer object and shares everything it references: new ArrayList<>(list) and the default clone() are shallow, so mutating an element is visible through both lists. A deep copy duplicates the reachable graph. Prefer immutable values (records with List.copyOf), where sharing is safe and copying unnecessary; use copy constructors rather than clone() (Effective Java Item 13).

Language rules

static and final everywhere, and initialisation order?

static field: one per class; method: no this, hidden rather than overridden; nested class: no outer instance; block: runs once at class initialisation. final local or parameter: assigned once; field: assigned by the end of construction, with safe-publication guarantees; method: cannot be overridden; class: cannot be extended. Order: static initialisers when the class is first used (superclass first); then, per new: superclass constructor, then this class's field initialisers and instance blocks in textual order, then the constructor body.

class Base { Base() { describe(); } void describe() {} }
class Child extends Base {
    private String name = "child";
    @Override void describe() { System.out.println(name); }   // new Child() prints null
}

Gotcha: never call overridable methods from a constructor (Effective Java Item 19).

Overloading vs overriding, covariant returns, dispatch?

Overloads are chosen at compile time from the static argument types; overrides at run time from the receiver's class. With Object o = "hi", f(o) calls f(Object) even if f(String) exists. An override may return a subtype (covariant return), may not reduce visibility, and may not throw broader checked exceptions. Static methods and fields are not polymorphic. Classic trap: List<Integer>.remove(1) removes index 1, not the value 1.

Abstract class vs interface, now that interfaces have default methods?

Interfaces carry no instance state, allow multiple inheritance of type, and can have default, static and private methods. Abstract classes have fields, constructors, protected members and single inheritance. A class method always wins over a default; two conflicting defaults must be resolved explicitly with A.super.m(). Use an interface for a type or capability and an abstract class for a skeleton with shared state (Effective Java Item 20).

Access modifiers, and nested class kinds?

private: the top-level class and its nested classes; no modifier (package-private): the same package; protected: package plus subclasses; public: everyone. A static nested class has no outer instance (builders); an inner class holds a hidden reference to its outer instance, a classic memory leak when it outlives it; a local class lives in a method and captures effectively final locals; an anonymous class is mostly replaced by lambdas, where this means the enclosing instance instead (Effective Java Item 24).

Exceptions, Optional and modern types

Checked vs unchecked, try-with-resources, and the finally trap?

Checked exceptions (subclasses of Exception outside RuntimeException) must be caught or declared and signal recoverable conditions; unchecked ones signal programming errors. Try-with-resources closes each AutoCloseable in reverse order and attaches exceptions from close() as suppressed instead of losing the original.

static int f() {
    try { throw new IllegalStateException("lost"); }
    finally { return 42; }            // compiles; the exception is discarded and f() returns 42
}
Rules for Optional?

Use it as a return type for results that may be absent. Never return a null Optional; do not use it for fields, parameters or collections (return an empty collection). Prefer map, orElseThrow and orElseGet over get(); note that orElse(expensive()) evaluates its argument even when a value is present (Effective Java Item 55).

Records, sealed classes and enums with behaviour?

A record is a transparent, shallowly immutable carrier: private final fields, canonical constructor, accessors, equals/hashCode/toString; validate and copy mutable components in the compact constructor. A sealed type lists its permitted subtypes, so a switch over it is checked for exhaustiveness. Enum constants can have fields, constructors and constant-specific method bodies (ADD { int apply(int a, int b) { return a + b; } }) and pair with EnumMap/EnumSet.

Interview trapReciting "String is immutable and stored in the pool" and stopping. The follow-up is always "so what?": thread safety, hash caching, map-key safety, and the quadratic loop. An answer without the consequence sounds memorised.

Practice · 60 min

  1. Answer every question aloud in under two minutes using the four-part shape; record yourself and note where you hesitated.
  2. Reproduce the Point bug in a HashSet, then fix it two ways (manual hashCode, record).
  3. Write a three-class hierarchy with static blocks, instance blocks and constructors printing their names; predict the output before running it.
  4. Capture the finally trap, Integer 127 vs 128, and List.remove(1) as JUnit tests.

L474 · DAY 474

Collections & Concurrency Interview Drills

60m video60m practice

Collections questions probe whether you know what the data structure does in memory; concurrency questions probe whether you know what is guaranteed and what is merely likely. Answer both with the mechanism, then the consequence.

Collections internals

ArrayList vs LinkedList?

ArrayList is a contiguous array: O(1) indexed access, amortised O(1) append, cache-friendly iteration. LinkedList allocates a node object per element with two links: more memory, pointer chasing, O(n) get(i). Even "fast insertion in the middle" first needs an O(n) walk to the position. As a queue or stack, ArrayDeque beats it too, so LinkedList almost always loses.

Walk me through HashMap internals. What does a bad hashCode do?

A power-of-two array of bins, allocated lazily (16 by default). hash() XORs the high 16 bits into the low ones so (n − 1) & hash uses them. Colliding entries chain in a list; at load factor 0.75 the table doubles and each bin splits into two lists by one hash bit, with no rehash. A bin with 8 or more entries becomes a red-black tree if the table has at least 64 bins, otherwise the table resizes. A constant hashCode puts everything in one bin: lookups degrade to O(n), or O(log n) in a tree bin when keys are Comparable.

HashMap vs LinkedHashMap vs TreeMap vs ConcurrentHashMap; HashSet vs TreeSet?

HashMap: no order, O(1) average, one null key allowed. LinkedHashMap: insertion or access order; with accessOrder = true and removeEldestEntry it is an LRU cache. TreeMap: red-black tree, sorted, O(log n), navigation (floorKey, ceilingEntry). ConcurrentHashMap: thread-safe with CAS and per-bin locking, atomic compute/merge, weakly consistent iterators, no null keys or values. HashSet and TreeSet are the key sets of HashMap and TreeMap.

Contracts and traps

Fail-fast vs fail-safe iterators?

ArrayList's iterator checks a modification count and throws ConcurrentModificationException on best effort when the list is structurally changed other than through the iterator. It happens in a single thread too: removing inside a for-each loop. Use iterator.remove() or removeIf. CopyOnWriteArrayList iterates a snapshot; ConcurrentHashMap iterators are weakly consistent: no exception, updates may or may not appear.

Comparable vs Comparator, and "consistent with equals"?

Comparable is the natural order inside the class; a Comparator is an external order. Sorted collections use compareTo, not equals: new BigDecimal("1.0") and "1.00" are not equal but compare as 0, so a HashSet holds both and a TreeSet holds one. A TreeSet ordered by last name silently drops a second person named Smith.

Why are mutable keys dangerous? Arrays.asList vs List.of vs new ArrayList<>()?

Mutate a field used by hashCode after insertion and the entry sits in the wrong bucket: get and remove miss it, and it leaks. Use immutable keys. Arrays.asList is a fixed-size view over the array: set writes through, add throws, nulls are allowed. List.of is unmodifiable, rejects nulls (even contains(null) throws), and is not a view. new ArrayList<>(…) is a mutable copy.

Concurrency fundamentals

Definition · Happens-beforeIf action A happens-before B, B sees A's effects. Edges: program order within a thread, unlock to a later lock of the same monitor, a volatile write to a later read of that variable, Thread.start to the started thread, a thread's actions to join returning; the relation is transitive. Without an edge, another thread may see a stale value or never see the write.
Process vs thread; thread states?

A process has its own address space; threads in it share the heap and each has its own stack and program counter, so sharing is cheap and needs synchronisation. States: NEW, RUNNABLE (running, ready, or in blocking I/O as far as Java can tell), BLOCKED (waiting for a monitor), WAITING (wait, join, park), TIMED_WAITING (sleep, timed waits), TERMINATED.

synchronized vs ReentrantLock vs volatile vs atomics?

synchronized: mutual exclusion plus visibility, reentrant, block-structured. ReentrantLock: the same plus tryLock with timeout, interruptible locking, fairness and several Conditions; unlock in finally. volatile: visibility and ordering of one variable, no atomicity (count++ still races). Atomics: lock-free compare-and-set on one variable; LongAdder for hot counters.

Deadlock: conditions, detection, prevention?

All four must hold: mutual exclusion, hold-and-wait, no preemption, circular wait. Detect with jstack or jcmd <pid> Thread.print ("Found one Java-level deadlock") or ThreadMXBean.findDeadlockedThreads(). Prevent by breaking one condition: a global lock order, tryLock with timeout and back-off, and never calling unknown code while holding a lock.

Pools, futures and virtual threads

How do you size a pool, and what are the ThreadPoolExecutor parameters?

CPU-bound: about the number of cores. I/O-bound: cores × (1 + wait time ÷ compute time), then measure. Parameters: core size, max size, keep-alive, work queue, thread factory, rejection handler. Gotcha: threads beyond core are created only when the queue is full, so with an unbounded queue the max is never reached and the queue can grow until the heap runs out; Executors.newFixedThreadPool does exactly that. Use a bounded queue and CallerRunsPolicy as backpressure.

Compose two remote calls with a timeout and fallback. 
CompletableFuture<Quote> quote = CompletableFuture.supplyAsync(() -> pricing.quote(cart), ioPool)
    .thenCombine(CompletableFuture.supplyAsync(() -> tax.rate(address), ioPool), Quote::withTax)
    .orTimeout(500, TimeUnit.MILLISECONDS)
    .exceptionally(ex -> Quote.fallback(cart));

thenApply maps, thenCompose chains a dependent async call, thenCombine joins two independent ones, allOf waits for many. Pass an executor: the default common pool is sized for CPU work and starves on blocking I/O.

How does ThreadLocal leak? What did virtual threads change?

Pooled threads never die, so a value set and not removed stays reachable for the life of the pool and leaks into the next task (a previous user's security context); on redeploys it can pin a whole class loader. Always remove() in finally. Virtual threads make blocking cheap: thread-per-request scales to very many concurrent requests, and they should not be pooled. Unchanged: CPU-bound code is no faster, races and the memory model are the same, and downstream limits remain (cap concurrency with a Semaphore or the connection pool). JDK 21–23 pin a carrier thread inside synchronized; JDK 24 removed that (JEP 491).

Whiteboard problems

Write a bounded blocking queue (producer-consumer). 
final class BoundedQueue<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition(), notEmpty = lock.newCondition();
    BoundedQueue(int capacity) { items = new Object[capacity]; }

    void put(T t) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();     // while, not if: spurious wake-ups
            items[tail] = t; tail = (tail + 1) % items.length; count++;
            notEmpty.signal();
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T t = (T) items[head]; items[head] = null; head = (head + 1) % items.length; count--;
            notFull.signal();
            return t;
        } finally { lock.unlock(); }
    }
}

Producers call put, consumers take; stop consumers with a poison-pill value. In real code use ArrayBlockingQueue.

Print 1 to 10 alternately from two threads. 
Semaphore odd = new Semaphore(1), even = new Semaphore(0);
Thread.ofPlatform().start(() -> { for (int i = 1; i <= 9; i += 2) { odd.acquireUninterruptibly(); System.out.println(i); even.release(); } });
Thread.ofPlatform().start(() -> { for (int i = 2; i <= 10; i += 2) { even.acquireUninterruptibly(); System.out.println(i); odd.release(); } });

For a thread-safe singleton, give the enum or holder idiom (L440); for a rate limiter, a synchronized token bucket, then the distributed version (L454).

Interview trap"volatile makes it thread-safe." It makes one variable's reads and writes visible; it does nothing for check-then-act or read-modify-write. Say which invariant needs protecting, then pick the tool.

  3. Build a 10,000-key HashMap whose keys share one hashCode, with and without Comparable, and time the lookups.
  4. Create a two-lock deadlock, find it with jcmd Thread.print, and fix it with lock ordering.

Spring & Spring Boot Interview Questions

60m video60m practice

Almost every hard Spring question reduces to two mechanisms: the container builds and post-processes beans in a fixed order, and cross-cutting features (transactions, security, caching) are proxies around those beans. Explain those two well and the rest follows.

The container

IoC and DI in your own words, and why constructor injection?

Inversion of control: my classes do not create or look up their collaborators; the container constructs the object graph and hands each object what it needs (dependency injection). Constructor injection makes dependencies explicit and final, keeps objects valid from construction, allows plain unit tests with new, and surfaces cycles at startup. A single constructor needs no @Autowired.

Bean scopes, and the singleton thread-safety obligation?

singleton (default, one per context), prototype (new per lookup; the container does not destroy it), and web scopes request, session, application, websocket. A singleton serves every request thread at once, so it must hold no mutable per-request state in fields: keep state in locals, immutable fields, or thread-safe structures.

BeanFactory vs ApplicationContext; @Component vs @Bean?

BeanFactory is the basic DI container with lazy getBean. ApplicationContext extends it with eager singleton creation, automatic registration of post-processors, events, message sources, resource loading and the Environment; applications always use it. @Component (and @Service, @Repository) marks your own classes for scanning; a @Bean method in a @Configuration class is for third-party types you cannot annotate, conditional or computed construction, or several differently configured beans of one type.

How does scanning find a class, and what is the package trap?

@SpringBootApplication includes @ComponentScan of its own package and sub-packages. A @Service in com.acme.billing is invisible to a main class in com.acme.app, and startup fails with NoSuchBeanDefinitionException. Put the main class in the root package.

Circular dependencies; @Qualifier vs @Primary?

With field or setter injection Spring can complete a cycle by exposing an early reference to a half-built singleton. With constructor injection neither bean can be built first, so creation fails with BeanCurrentlyInCreationException, and since Boot 2.6 circular references are rejected by default anyway. Fix the design (extract a third bean, publish an event) or, as a stopgap, inject one side @Lazy. With two candidate beans of a type, @Primary marks the default and @Qualifier at the injection point selects one explicitly, overriding @Primary.

AOP and the self-invocation trap

Definition · Proxy-based AOPSpring replaces an advised bean with a proxy (a CGLIB subclass by default in Boot; a JDK dynamic proxy needs an interface). Other beans receive the proxy, which runs the interceptor chain (transaction, security, cache) and then calls the target object. Only calls that go through the proxy are advised.
How does @Transactional work, and why does this not start a new transaction? 
@Service
class ReportService {
    public void nightly() {
        for (long id : pendingIds()) generate(id);      // this.generate(): no proxy, no new transaction
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void generate(long id) { /* ... */ }
}

A call through this never touches the proxy, so the annotation is ignored. Fix: move generate to another bean, use TransactionTemplate, or inject the bean's own proxy lazily. The same applies to @Async, @Cacheable and @PreAuthorize, and to private or final methods, which CGLIB cannot override.

Why don't checked exceptions roll back? What do isolation and readOnly do?

The default rule rolls back on RuntimeException and Error only, a convention that treats checked exceptions as expected business outcomes; use rollbackFor = Exception.class when that is wrong. isolation sets the database isolation level for the transaction (anomalies in L476). readOnly = true is an optimisation hint: Hibernate skips dirty checking and flushing, the JDBC connection is flagged read-only, and routing data sources can send it to a replica. It is not a security guarantee.

Spring Boot

What is auto-configuration, and how do you override it?

@EnableAutoConfiguration loads the classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports of every jar. Each is guarded by conditions (@ConditionalOnClass, @ConditionalOnProperty, @ConditionalOnMissingBean) and is processed after your configuration, so declaring your own bean of the type makes the auto-configured one back off. Run with --debug or open /actuator/conditions to see why each matched. A starter is a dependency descriptor that pulls in the library plus its auto-configuration; it usually contains no code.

Property precedence, the embedded server, and @SpringBootApplication?

Highest first, simplified: command-line arguments, SPRING_APPLICATION_JSON, Java system properties, OS environment variables, then config files (external profile-specific, external, packaged profile-specific, packaged), then @PropertySource, then defaults. SpringApplication.run creates a web application context; during refresh it obtains the auto-configured ServletWebServerFactory (Tomcat by default), creates and starts the server, and registers the DispatcherServlet. @SpringBootApplication is @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan.

Which Actuator endpoints would you expose in production?

health (with liveness and readiness groups for the orchestrator), info, and prometheus or metrics, ideally on a separate management port not reachable from the internet. Never expose env, configprops, heapdump, threaddump or shutdown publicly: they leak secrets or hand over control.

Security and Data

The filter chain, authentication vs authorization, and JWT validation?

The container's DelegatingFilterProxy hands requests to FilterChainProxy, which picks the first matching SecurityFilterChain and runs its filters: CSRF, authentication (form login, bearer token), exception translation, and finally authorization. Authentication answers "who are you" (failure: 401); authorization answers "may you do this" (failure: 403). A resource server validates a JWT by checking its signature with the issuer's public key from the JWKS endpoint (selected by kid, cached, with the algorithm pinned), then exp/nbf, iss and aud, and maps scopes or roles to authorities. No session is needed; the trade-off is that revocation requires short lifetimes and refresh tokens.

CSRF: when to disable it, and when never to?

CSRF works because browsers attach cookies automatically to cross-site requests. A stateless API authenticated only by an Authorization: Bearer header has no ambient credential, so CSRF protection can be disabled there. Never disable it for anything authenticated by a session cookie, including SPAs that use cookie sessions; use a cookie-based CSRF token repository instead.

How does a repository interface become an implementation?

At startup Spring Data scans for interfaces extending Repository and creates a JDK proxy for each, backed by SimpleJpaRepository for the CRUD methods. Query methods are parsed from their names (findByEmailAndStatusOrderByCreatedAtDesc) into criteria queries, or taken from @Query (JPQL, or SQL with nativeQuery = true; updates need @Modifying). A misspelled property fails at startup, not at first call.

"Design this" follow-ups: run a @Scheduled job once across instances (ShedLock), cache and invalidate product lookups, make a payment retry idempotent, isolate tenants in every query. Name the mechanism and its failure mode.

Interview trap"Put @Transactional on the method and it is transactional." Interviewers expect the conditions: called through the proxy, public, non-final, on a bean, with rollback rules that ignore checked exceptions. Name them before being asked.

  1. Answer every question aloud in two minutes; redo the ones where you skipped the mechanism.
  2. Reproduce the self-invocation trap with a test that asserts a new transaction did not start, then fix it two ways.
  3. Write one test per propagation mode in the table, logging transaction names with TransactionSynchronizationManager.
  4. Override an auto-configured bean with your own and confirm the back-off in the conditions report.

SQL, JPA & Hibernate Interview Questions

60m video60m practice

Data-layer interviews check two things: that you can write correct SQL under pressure, and that you know exactly which SQL Hibernate will issue for your entity code. The N+1 problem sits where those meet, so expect it.

SQL semantics

Logical execution order; WHERE vs HAVING; GROUP BY rules?

FROM and JOIN, WHERE, GROUP BY, HAVING, SELECT (window functions run here), DISTINCT, ORDER BY, LIMIT/OFFSET. So WHERE filters rows before grouping and cannot use aggregates; HAVING filters groups after. A SELECT alias is unusable in WHERE but usable in ORDER BY, and filtering on a window function needs a subquery. Every non-aggregated selected column must be grouped or functionally dependent on the grouped key (Postgres accepts a grouped primary key).

EXISTS vs IN with NULLs?

x NOT IN (SELECT manager_id …) returns no rows if the subquery yields any NULL, because x <> NULL is unknown. NOT EXISTS behaves as intended. Modern planners often turn both IN and EXISTS into the same semi-join, so pick by semantics.

Indexes, leftmost prefix, sargability, EXPLAIN, normalization?

A B-tree on (a, b, c) serves predicates on a, a, b or a, b, c, with a range allowed on the last column used; it does not generally serve b alone (some engines can skip-scan a low-cardinality leading column; do not count on it). Non-sargable predicates hide the column inside an expression: lower(email) = ? without an expression index, created_at::date = ?, LIKE '%x', arithmetic on the column, implicit casts. In EXPLAIN ANALYZE, read from the innermost node out, check scan types (sequential, index, index-only, bitmap) and join types (nested loop, hash, merge), and compare estimated with actual rows; a large gap means stale statistics. Normalise to 3NF (no partial or transitive dependencies) for writes; denormalise deliberately for read paths, with a mechanism that keeps the copy in sync.

JPA and Hibernate

Persistence context, dirty checking and entity states; persist vs merge vs save?

States: transient (new), managed, detached, removed. Managed entities are snapshotted on load; at flush (before a conflicting query, and at commit) Hibernate compares each with its snapshot and issues UPDATEs, with no save() needed. persist makes a transient object managed and fails for a detached one. merge copies the argument's state onto a managed instance (loading it if needed) and returns that instance; the argument stays detached. Spring Data's save calls persist when the entity is new (null id or version) and merge otherwise, so assigned ids cause an extra SELECT unless you implement Persistable.

Definition · The N+1 problemOne query loads N parent rows, then touching a lazy association on each parent issues one more query per parent: N+1 round trips for what one or two queries could fetch.
Lazy vs eager, LazyInitializationException, and every N+1 fix?

@ManyToOne and @OneToOne default to eager, collections to lazy; make everything lazy and fetch per use case. LazyInitializationException is touching an uninitialised proxy after the session closed, often during JSON serialisation. Fixes for N+1: JOIN FETCH in JPQL; @EntityGraph on the repository method; @BatchSize or hibernate.default_batch_fetch_size (loads associations in IN (…) batches); a DTO projection query; FetchMode.SUBSELECT. Detect it with SQL logging or a test asserting the statement count.

Why does a fetch join plus pagination break?

Fetching a collection multiplies rows per parent, so SQL LIMIT would cut a parent's children. Hibernate instead loads everything and paginates in memory, logging a warning, which is correct but can load the whole table. Query a page of parent ids first, then fetch-join those ids, or use batch fetching.

First vs second level cache; equals/hashCode on entities?

The first-level cache is the persistence context itself: per transaction, always on, an identity map. The second-level cache is shared across sessions, opt-in per entity (JCache providers), and brings invalidation problems across nodes. For entity equality, use a natural key if one exists; otherwise compare non-null ids with instanceof (Hibernate proxies are subclasses) and return a constant hashCode, so an entity does not change buckets when its generated id is assigned.

Cascades, orphan removal, @Version, bulk updates, open-session-in-view?

Cascade propagates operations from parent to children; orphanRemoval deletes a child removed from the collection. Never cascade REMOVE from a @ManyToOne or across @ManyToMany. @Version gives optimistic locking. JPQL bulk UPDATE/DELETE (@Modifying) bypass the persistence context: managed entities go stale, so use clearAutomatically = true. Spring Boot enables open-session-in-view by default (with a startup warning): the session stays open through rendering, hiding N+1 and holding a connection for the whole request. Set spring.jpa.open-in-view=false.

When would you choose JDBC or jOOQ over JPA?

Reporting and analytics, heavy use of window functions and CTEs, bulk operations, table-shaped data with few invariants, or whenever predictable SQL matters more than object mapping. JdbcClient is enough for a few queries; jOOQ generates type-safe SQL from the schema. Many services use JPA for writes and SQL for reads (L447).

Interview trapAnswering "how do you fix N+1" with "use FetchType.EAGER". Eager loading still issues the extra queries for lists, and now on every load. The expected answer is a fetch plan per use case plus a way to detect regressions.

Microservices & System Design Interviews

60m video60m practice

Microservices questions test whether you know the price of distribution; design rounds test whether you can make and defend trade-offs under a clock. In both, the strongest signal is naming what you would give up and why.

Conceptual questions

Monolith vs microservices, and when not to split?

Microservices buy independent deployment, team autonomy, independent scaling and fault isolation. They cost network failures, eventual consistency, distributed transactions, and the platform to deploy, observe and test many services. Do not split with a small team, an early product whose domain boundaries are still moving, or without automated deployment and observability. A modular monolith with enforced boundaries (L397) keeps the option to split later.

How do you decide service boundaries?

Start from bounded contexts (L398): areas where a term has one meaning and one owning team. Check each candidate: does it own its data, do most changes stay inside it, can it serve its main use cases without synchronous calls to three others? A boundary that forces chatty calls or shared tables is in the wrong place.

Database per service: what happens to joins and transactions?

Joins become API composition (call both services, join in memory, fine for small result sets) or a local read model kept current by the other service's events. Transactions become sagas with compensations, plus the outbox for reliable events; and the best fix is drawing boundaries so that each invariant lives inside one service.

Saga orchestration vs choreography, with an example?

Order placement. Orchestration: an order saga calls Inventory to reserve, then Payment to authorize; on decline it tells Inventory to release and marks the order rejected. The flow is explicit, its state is queryable, and it is easy to monitor. Choreography: OrderCreated makes Inventory reserve and emit StockReserved, Payment reacts and emits PaymentFailed, Inventory and Order react to that. Services are decoupled, but the flow exists only implicitly across listeners, which is hard to follow past three or four steps (L414).

Why do dual writes fail, and what is the outbox?

Commit to the database, then publish to Kafka: a crash between the two loses the event. Publish first: a failed commit leaves an event for something that never happened. The outbox writes the event into a table in the same transaction as the state change; a relay (a poller, or CDC with Debezium) publishes it afterwards. Delivery is at least once, so consumers must be idempotent.

Idempotency and at-least-once delivery?

A consumer that crashes after processing but before acknowledging receives the message again. Make processing idempotent: record the message id in a processed-messages table in the same transaction as the effect, or make the effect naturally idempotent (SET status = 'PAID' rather than balance = balance + 10). APIs get the same property from idempotency keys.

Definition · Resilience orderingResilience4j's default nesting is Retry( CircuitBreaker( RateLimiter( TimeLimiter( Bulkhead( call ))))). The timeout applies per attempt; the circuit breaker records every attempt and, once open, fails fast; the bulkhead caps concurrent calls to one dependency so it cannot take every thread.
Circuit breakers, retries, timeouts, bulkheads: how do they fit together?

Timeouts on every remote call, sized from the dependency's p99 and the caller's own budget. Retry only idempotent operations, with exponential backoff, jitter and a small attempt count, and do not retry when the circuit is open. A retry outside a per-attempt timeout can never finish in time; a retry outside an open circuit stops at once; retries at every layer of a deep call chain multiply load during an outage. Details in L409.

Service discovery, load balancing, and the API gateway?

Discovery: a registry (Eureka, Consul) with client-side balancing (Spring Cloud LoadBalancer), or on Kubernetes the platform's DNS names and Services, plus an L7 proxy or mesh for per-request balancing. The gateway handles cross-cutting edge concerns: routing, TLS termination, token validation, rate limiting, CORS, request ids, and sometimes aggregation for one client (a backend for frontend). It should hold no business logic.

How would you debug one slow request across eight services?

Get its trace id (from the response header or the access log) and open the trace. Find the critical path in the waterfall and look for sequential calls that could run in parallel, the same downstream call repeated (a cross-service N+1), retries, slow database spans, and gaps between a client span and its server span (queueing or connection-pool waits). Confirm with that service's latency and saturation metrics, then profile it. This only works if trace context (W3C traceparent) propagates through HTTP and messaging.

What would you sacrifice under a partition for payments vs a feed?

Payments give up availability: refuse or queue a charge rather than risk a double spend, keep the ledger in a strongly consistent store, and make every step idempotent. A feed gives up consistency: show slightly stale or incomplete timelines from caches and replicas rather than an error page.

Coding rounds reward recognising a small set of patterns and executing them cleanly in Java while talking. Fifteen or so patterns cover most questions; the rest is a consistent way of working through a problem and a working set of collections you can use without thinking.

Complexity you can justify

Definition · Justified big-OState the cost of each loop, call and data-structure operation, then combine: nested loops multiply, sequential phases add, and the dominant term wins. "Sorting is O(n log n), the scan is O(n), each map operation is O(1) on average, so O(n log n) time and O(n) extra space."

Know the hidden costs in Java: list.contains and list.remove(0) on an ArrayList are O(n); substring copies, so it is O(k); s += c in a loop is O(n²) overall; HashMap is O(1) only on average. Amortised O(1) (an ArrayList append) means occasional O(n) resizes averaging out. Constraints hint at the target: n ≤ 20 allows exponential search, n ≈ 10³ allows O(n²), n ≈ 10⁵ to 10⁶ needs O(n log n) or O(n).

// Sliding window: longest substring without repeating characters, O(n)
static int longestUniqueRun(String s) {
    int[] nextStart = new int[128];                  // ASCII assumed; use a HashMap otherwise
    int best = 0;
    for (int lo = 0, hi = 0; hi < s.length(); hi++) {
        char c = s.charAt(hi);
        lo = Math.max(lo, nextStart[c]);             // jump past the previous occurrence of c
        nextStart[c] = hi + 1;
        best = Math.max(best, hi - lo + 1);
    }
    return best;
}

The Java specifics

Your working set: HashMap/HashSet (counting, membership), ArrayDeque (stack and queue; never Stack or LinkedList), PriorityQueue (a min-heap; pass Comparator.reverseOrder() for a max-heap), and TreeMap (sorted keys with floorKey/ceilingKey). Arrays.sort on primitives uses a dual-pivot quicksort and is not stable; on objects, and in Collections.sort/List.sort, it is a stable TimSort. Prefer int[] to List<Integer> in hot loops: every boxed Integer is a separate object, so memory and cache misses multiply. Build strings with StringBuilder, and pass indices instead of calling substring in recursion. Compute midpoints as lo + (hi - lo) / 2 to avoid int overflow, and compare boxed values with equals.

How to perform

Algorithm · Working a problem aloud
  1. Restate the problem in your own words with one example.
  2. Ask about constraints and edge cases: input size, empty input, duplicates, negatives, overflow, sorted or not.
  3. State a brute force and its complexity before optimising, so there is always a working answer.
  4. Optimise out loud: name the bottleneck and the pattern that removes it.
  5. Write clean, compilable code with meaningful names and small helpers.
  6. Dry-run your example and one edge case by hand, then state time and space complexity.

When you are stuck: solve a smaller instance by hand and watch what you do, ask which pattern's signal is present, relax one constraint, or say what you are trying and ask whether the direction is reasonable. A clear brute force with a correct complexity analysis scores better than silence.

    LruCache(int capacity) { super(16, 0.75f, true); this.capacity = capacity; }   // access order

static List<String> runOrder(Map<String, List<String>> dependsOn) {    // Kahn's algorithm
    Map<String, Integer> indegree = new HashMap<>();
    Map<String, List<String>> dependents = new HashMap<>();
    dependsOn.forEach((task, reqs) -> {
        indegree.merge(task, reqs.size(), Integer::sum);
        for (String r : reqs) {
            indegree.putIfAbsent(r, 0);
            dependents.computeIfAbsent(r, k -> new ArrayList<>()).add(task);
        }
    });
    ArrayDeque<String> ready = new ArrayDeque<>();
    indegree.forEach((t, d) -> { if (d == 0) ready.add(t); });
    List<String> order = new ArrayList<>();
    while (!ready.isEmpty()) {
        String t = ready.poll();
        order.add(t);
        for (String next : dependents.getOrDefault(t, List.of()))
            if (indegree.merge(next, -1, Integer::sum) == 0) ready.add(next);
    }
    if (order.size() != indegree.size()) throw new IllegalArgumentException("dependency cycle");
    return order;
}

Expect the interviewer to ask for the LRU cache by hand as well: a HashMap from key to node plus a doubly linked list, moving a node to the head on access. Other backend variants: a rate limiter (a token bucket, L454); an in-memory key-value store with TTL (a map of value plus expiry, lazy expiry on read, and a PriorityQueue or DelayQueue sweep, with an injected Clock for tests); and log or stream processing (top-K frequent with a map plus a size-k min-heap, counts per sliding time window with a deque, merging k sorted log files with a heap).

A realistic plan: 60–80 curated problems over the phase, grouped by pattern (four or five each), easiest first. Keep a written log per problem: pattern, the key insight in one sentence, complexity, the mistake you made. Re-solve each from a blank page after about a day, a week and a month; the ones you cannot redo go back in the queue.

The code review round

You are handed a service and asked what you would flag. This one has eight problems:

@Service
public class InvoiceService {
    private static final String LEDGER_URL = "http://ledger/entries";
    private final InvoiceRepository invoices;
    private final JdbcTemplate jdbc;
    private final RestTemplate rest = new RestTemplate();                   // built here, no timeouts
    private final ExecutorService pool = Executors.newCachedThreadPool();   // unbounded threads
    private BigDecimal lastTotal;                                           // mutable field in a singleton

    public InvoiceService(InvoiceRepository invoices, JdbcTemplate jdbc) { this.invoices = invoices; this.jdbc = jdbc; }

    public List<InvoiceDto> forCustomer(String customerId) {
        List<Invoice> list = jdbc.query(
            "SELECT * FROM invoices WHERE customer_id = '" + customerId + "'",
            new BeanPropertyRowMapper<>(Invoice.class));
        return list.stream().map(i -> new InvoiceDto(i.getId(), invoices.findLines(i.getId()))).toList();
    }

    public void settle(long invoiceId, BigDecimal amount) {
        invoices.markPaid(invoiceId);
        invoices.insertPayment(invoiceId, amount);
        lastTotal = amount;
        pool.submit(() -> {
            try { rest.postForObject(LEDGER_URL, amount, Void.class); }
            catch (Exception e) { }
        });
    }
}
Model review, in priority order
  1. SQL injection: customerId is concatenated into SQL. Bind it: WHERE customer_id = ?.
  2. Missing transaction boundary: markPaid and insertPayment can half-succeed. Make settle @Transactional.
  3. Swallowed exception: a failed ledger call disappears without a log, metric or retry. Use an outbox (L477), or at least log and count failures.
  4. Missing timeout: a hung ledger service holds a thread forever. Build the client from RestClient.Builder with connect and read timeouts.
  5. Unbounded thread pool: newCachedThreadPool creates a thread per concurrent task under load. Use a bounded executor, or none at all if the outbox replaces it.
  6. Mutable singleton field: lastTotal is shared by every request thread, a data race with no purpose. Remove it.
  7. N+1: one findLines query per invoice. Load all lines for the invoice ids in one query and group them.
  8. Untestable design: the HTTP client, executor and URL are created inside the class. Inject them (and the URL from configuration) so tests can substitute fakes.
Phrasing feedbackState the observation, its impact, and a suggestion, as a question where you can: "This concatenates customerId into the SQL, so a crafted id could read other customers' invoices. Could we bind it as a parameter?" Lead with correctness and security, label nits as nits, and say what is good about the code too.

The debugging round

With the toolbox from L169: for a memory leak, show that heap occupancy after each full collection keeps rising (jstat -gcutil or the GC log), take a heap dump with jcmd <pid> GC.heap_dump, and find the dominating retainer in Eclipse MAT (typically a static map or cache with no eviction, or a ThreadLocal never removed). For a hot lock, when latency is up and CPU is low, take three thread dumps a few seconds apart with jcmd <pid> Thread.print; many threads BLOCKED on the same monitor identify the lock, and a JFR recording's monitor-enter events show who holds it and for how long. Then propose the fix (eviction, narrower lock scope, a concurrent structure) and how you would verify it.

  • A two- or three-minute demo video for reviewers who will not run anything.
  • A blog post on the hardest problem in it: the post is shareable, searchable, and shows you can explain your work.

Pin those three repositories on GitHub, archive or hide abandoned experiments, and give each pinned repository a one-line description and topics. Writing compounds: each post is a link for your resume, material for interview stories, and a reason for strangers to contact you.

Open source and public track record

Start where you are already a user: a library from this playlist whose behaviour you understand. Read CONTRIBUTING.md and the code of conduct, look for issues labelled for newcomers, and comment before starting so effort is not duplicated. The best first pull requests are small and useful: a reproducible bug report with a failing test, a documentation fix for something that confused you, a narrowly scoped bug fix. Follow the project's style, respond to review promptly, and expect it to take a while. A handful of merged contributions to tools people recognise is a strong signal that you can work in an unfamiliar codebase with strangers.

The resume, LinkedIn and GitHub

Definition · Impact statementA resume line of the form action + what you changed + measurable result + how: "Cut checkout p99 latency from 900 ms to 250 ms by replacing per-item price lookups with one batched query and a Caffeine cache (Spring Boot, Postgres)." Every number must be one you can explain in an interview.
  • Length: one page is the usual expectation for under about ten years of experience.
  • Skills: list what you can discuss under questioning, ordered to match the job description honestly. A keyword you cannot defend costs more than it gains.
  • Format: single column, standard headings (Experience, Projects, Skills, Education), real text in the PDF, no skill bars, photos or text inside images, so applicant-tracking systems and humans both parse it.
  • Instant-rejection mistakes: typos, duties instead of outcomes, unexplained jargon, broken links, and claims that the first technical question disproves.

Recruiters open two profiles: LinkedIn (headline that states what you do, the same experience as the resume, an "open to work" setting if appropriate) and GitHub (pinned projects, a profile README with three lines and links). Make them consistent with the resume.

The search and the negotiation

Target a list of companies whose product, stack and stage fit you, rather than applying everywhere. Referrals are usually the highest-yield channel: ask people you know, and people you have helped, specifically ("Would you be comfortable referring me for the backend role on the payments team?"). Cold outreach works when it is short and specific: one line on why that team, one line of evidence (a link to a relevant project or post), and a clear small ask. Track every application in a spreadsheet: company, role, contact, date, stage, next action, notes. Rejection is routine and mostly says nothing about you; record what you learned from each loop and move on.

  • Know your number before any call: a target and a walk-away, from market data for the role and location and from your own needs.
  • Do not anchor first: "I'd like to understand the role and the full package first. What range has been budgeted for this position?" Rules on salary-history questions and pay-range disclosure vary by location.
  • Look at total compensation: base, bonus (target and how it is actually paid), equity, sign-on, benefits, and the value of remote work or learning. Get the offer in writing before negotiating: "Thank you, I'm excited about this. Could you send the full details, including equity and its vesting schedule? I'd like a couple of days to review."
  • Value equity realistically: grants usually vest over several years, often with a one-year cliff. Shares or units in a public company have a market price; options in a private company are a right to buy at a strike price and are worth something only if the company's value exceeds it and there is a way to sell, after dilution and investor preferences. Tax treatment varies, so get local advice. Plan your finances on base pay.
  • Counter with a reason: "Given the scope we discussed and my other conversations, I was hoping for a base closer to X. Is there flexibility?" With a genuine competing offer: "I'd prefer to join you; is there anything you can do on base or sign-on to close the gap?" Never invent an offer.

The first 90 days, and the next 365

Days 1–30: get the development environment running, ship a small change to production early, read the architecture documents and runbooks, hold one-to-ones with your team and neighbours, and learn the domain vocabulary. Days 31–60: own a small feature end to end, shadow on-call, and fix one thing that annoys everyone (a flaky test, a missing doc). Days 61–90: write a short design document for something real, propose one improvement backed by data, and agree with your manager what success at six months looks like. Keep a running log of what you shipped and learned; it makes reviews and the next resume easy.

The senior skills are learnable like any other: write a design document with alternatives and a decision record for every non-trivial change; mentor one person deliberately; volunteer as incident lead and write blameless postmortems; and practise influencing without authority by bringing data, writing the proposal, and doing the first part of the work. To keep learning without a curriculum, choose a theme per quarter, read the source of one tool you use daily, follow JDK and Spring release notes, build one small project with an explicit learning goal, and teach what you learn, in posts, talks or reviews.

What breaks in practiceA portfolio of demos that are down when the recruiter clicks, a resume line the candidate cannot explain, and a negotiation conducted verbally without the offer in writing. All three are avoidable with a checklist and an afternoon.
