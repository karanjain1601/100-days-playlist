Messaging: Kafka & RabbitMQ

L369 · DAY 369

Messaging Fundamentals

40m video35m practice

A message broker lets the sender finish before the receiver starts, which buys decoupling in time, load and failure. The price is that delivery can no longer be "exactly once" by itself: networks force a choice between losing messages and duplicating them, and correct systems choose duplication and make consumers idempotent.

Why asynchronous messaging

  • Temporal decoupling: the order service publishes OrderPlaced and returns; the email service can be down for ten minutes and catch up later.
  • Load leveling: a flash sale produces 5,000 orders per second, the warehouse system handles 500; the queue absorbs the burst and the consumer drains it at its own pace.
  • Resilience to downstream failure: a failing consumer stops consuming instead of failing the producer's request.
  • Independent scaling: add consumers to drain a backlog without touching producers.

The broker and the message

The broker stores messages durably, routes them, tracks which consumers have them, and redelivers when a consumer fails. A message has four parts, and getting them right matters more than the broker choice:

Neither broker gives each message a business identity for you. Put a unique event id in a header or the payload; deduplication depends on it.

Delivery semantics

Definition · The three guarantees
  • At-most-once: acknowledge (or commit the offset) before processing. A crash after the ack loses the message; it is never redelivered. No duplicates, possible loss.
  • At-least-once: process, then acknowledge. A crash between the two causes redelivery, so the effect may happen twice. No loss, possible duplicates.
  • Exactly-once: the effect of each message is applied once. Achievable only when recording "this message is consumed" and applying its effect are one atomic step, or when applying it twice is harmless.

Why exactly-once delivery is impossible end to end: a sender that gets no acknowledgement cannot tell "lost before processing" from "processed, ack lost" (the Two Generals problem). It must either resend (risking a duplicate) or not (risking a loss). Systems that advertise exactly-once really provide at-least-once delivery plus deduplication or atomic commit within a boundary they control. Kafka transactions do this for consume-transform-produce inside Kafka (L379); once a side effect leaves that boundary (a database row, an email, a card charge), you need an idempotent consumer:

@Component
public class ReserveStockHandler {
    private final JdbcTemplate jdbc;
    public ReserveStockHandler(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    public record OrderPlaced(UUID eventId, String sku, int qty) {}

    @Transactional                                   // dedupe row and effect commit together
    public void handle(OrderPlaced e) {
        int fresh = jdbc.update("""
            INSERT INTO processed_message (message_id, processed_at)
            VALUES (?, now()) ON CONFLICT (message_id) DO NOTHING""", e.eventId());
        if (fresh == 0) return;                      // duplicate delivery: already applied
        jdbc.update("UPDATE stock SET reserved = reserved + ? WHERE sku = ?", e.qty(), e.sku());
    }                                                // acknowledge only after this commits
}
Which to pick

Default to at-least-once with idempotent consumers for anything that matters (orders, payments, stock). Use at-most-once only where loss is acceptable and duplicates are not (high-volume telemetry, some metrics). Use broker-level exactly-once when the whole pipeline lives in the broker, as in Kafka Streams.

Ordering and its cost

A single queue with one consumer, or a single Kafka partition, gives total order, and therefore no parallelism. The practical compromise is order per key: all events for order-42 go to the same partition (or queue) and are processed in sequence, while different orders run in parallel. Ordering costs throughput (parallelism capped by partitions), costs availability (a poison message blocks everything behind it, head-of-line blocking), and is fragile: competing consumers, requeues and retries to a separate retry topic all reorder. Ask whether consumers can instead tolerate disorder, for example by carrying a version number and ignoring stale updates.

What breaks in production
  • Auto-acknowledge (RabbitMQ autoAck=true, Kafka auto-commit with async processing): at-most-once without anyone deciding it.
  • Trusting "exactly-once" in broker settings to cover database writes or emails: duplicates appear on the first rebalance or redeploy.
  • Assuming global order across a topic with several partitions or a queue with several consumers.
  • Messages with no event id: once duplicates arrive there is no way to detect them.

RabbitMQ: Exchanges, Queues & Routing

45m video50m practice

In RabbitMQ a producer never writes to a queue: it publishes to an exchange with a routing key, and bindings decide which queues get a copy. Routing is the design surface; durability, acknowledgements and prefetch decide whether messages survive and whether work is shared fairly.

The AMQP 0-9-1 model

Clients open one TCP connection and multiplex many lightweight channels over it. A producer publishes to an exchange with a routing key; the exchange compares the key with its bindings and copies the message into each matching queue; the broker pushes messages from a queue to its consumers, each message going to exactly one consumer of that queue.

Design keys from the domain, most general word first: <aggregate>.<region>.<event> such as order.eu.created, order.us.shipped, payment.eu.failed. Consumers then subscribe by pattern (order.#, *.eu.*, #.failed) and producers never need to know who listens. Name queues after what they feed (order.billing, order.audit), not after the producer.

Queue properties and queue types

Definition · Queue arguments
  • durable: the queue definition survives a broker restart. Messages survive only if they are also published as persistent (delivery_mode=2).
  • exclusive: usable by one connection and deleted when it closes. auto-delete: deleted when its last consumer unsubscribes.
  • x-message-ttl (ms) expires messages; x-expires deletes an unused queue.
  • x-max-length / x-max-length-bytes with x-overflow: drop-head (default), reject-publish or reject-publish-dlx.
  • x-dead-letter-exchange (and x-dead-letter-routing-key): where rejected, expired or overflowing messages go (L372).
  • x-queue-type: classic, quorum or stream.

Quorum queues replicate every message to a majority of nodes with Raft. They are the right default for anything you cannot lose: always durable, survive node failure, and enforce a delivery limit that dead-letters poison messages (RabbitMQ 4 sets a default limit of 20). Classic queues live on one node; they are fine for transient, exclusive or very high-churn queues. Classic mirrored queues were removed in RabbitMQ 4.0. Streams are an append-only, replayable queue type, closer to a Kafka log.

Confirms, acknowledgements and prefetch

import com.rabbitmq.client.*;
import java.nio.charset.StandardCharsets;
import java.util.Map;
import java.util.UUID;

public class RawAmqp {
    public static void main(String[] args) throws Exception {
        var factory = new ConnectionFactory();
        factory.setHost("localhost");
        factory.setVirtualHost("orders");
        factory.setUsername("order-svc");
        factory.setPassword(System.getenv("RABBIT_PASS"));
        try (Connection conn = factory.newConnection(); Channel ch = conn.createChannel()) {
            ch.exchangeDeclare("orders.events", BuiltinExchangeType.TOPIC, true);
            ch.exchangeDeclare("orders.dlx", BuiltinExchangeType.TOPIC, true);       // must exist, or dead letters vanish
            ch.queueDeclare("order.billing", true, false, false,
                Map.<String, Object>of("x-queue-type", "quorum", "x-dead-letter-exchange", "orders.dlx"));
            ch.queueBind("order.billing", "orders.events", "order.*.created");

            ch.confirmSelect();                                     // publisher confirms on this channel
            var props = new AMQP.BasicProperties.Builder()
                .contentType("application/json").deliveryMode(2)    // persistent
                .messageId(UUID.randomUUID().toString()).build();
            ch.basicPublish("orders.events", "order.eu.created", true, props,   // mandatory = true
                "{\"orderId\":42}".getBytes(StandardCharsets.UTF_8));
            ch.waitForConfirmsOrDie(5_000);                          // broker has taken responsibility

            ch.basicQos(20);                                        // at most 20 unacked per consumer
            ch.basicConsume("order.billing", false, (tag, d) -> {   // autoAck = false
                long dt = d.getEnvelope().getDeliveryTag();
                try {
                    System.out.println(new String(d.getBody(), StandardCharsets.UTF_8));
                    ch.basicAck(dt, false);
                } catch (RuntimeException e) {
                    ch.basicReject(dt, false);                       // requeue = false: dead-letter it
                }
            }, tag -> { });
            Thread.sleep(2_000);
        }
    }
}

Publisher confirms: once a channel is in confirm mode, the broker answers each publish with basic.ack after it has taken responsibility (for persistent messages in durable queues, after writing to disk; for quorum queues, after a majority has it) or basic.nack if it could not. An unroutable message is acked and dropped unless it was published with mandatory=true, in which case it is first returned with basic.return. Consumer acknowledgements: basicAck(tag, multiple); basicNack(tag, multiple, requeue); basicReject(tag, requeue). With requeue=false the message is dead-lettered (or discarded if there is no DLX). Unacked messages are redelivered, flagged redelivered, when the channel closes, which makes RabbitMQ at-least-once.

Prefetch (basic.qos) caps unacked messages per consumer. With no limit, the broker pushes the whole backlog round-robin into consumers' memory as fast as the network allows: a slow consumer sits on thousands of messages while a fast one idles, and they are not redelivered until it dies. A small prefetch (1 to a few dozen, tuned by processing time) gives fair dispatch; Spring AMQP defaults to 250.

What breaks in production
  • Durable queue, transient messages: everything in it vanishes on a broker restart.
  • mandatory=false with a typo in the routing key: confirms say "ack", the messages are gone.
  • Unbounded prefetch with slow handlers: one consumer hoards the queue, memory grows, latency is uneven.
  • basicNack(tag, false, true) on a message that always fails: a hot requeue loop at full CPU.

Spring AMQP: RabbitTemplate & @RabbitListener

45m video55m practice

Spring AMQP wraps the raw client in three pieces: topology declared as beans, a RabbitTemplate that converts objects into messages, and listener containers that call your @RabbitListener methods and acknowledge for you. Two defaults need overriding on day one: Java serialization as the message format, and requeue-on-exception as the error policy.

Connection and topology as beans

    @Bean TopicExchange ordersExchange() {
        return ExchangeBuilder.topicExchange(EXCHANGE).durable(true).build();
    }

    @Bean Queue billingQueue() {
        return QueueBuilder.durable("order.billing").quorum().deadLetterExchange("orders.dlx").build();
    }

    @Bean Binding billingBinding(Queue billingQueue, TopicExchange ordersExchange) {
        return BindingBuilder.bind(billingQueue).to(ordersExchange).with("order.*.created");
    }

    @Bean MessageConverter jsonConverter(ObjectMapper mapper) {   // Boot applies it to template and listeners
        var converter = new Jackson2JsonMessageConverter(mapper);

Boot auto-configures a CachingConnectionFactory (one connection, cached channels) and a RabbitAdmin. The admin collects every Queue, Exchange, Binding and Declarables bean and declares them when the first connection opens, and again after every reconnect, so a broker restart does not lose non-durable topology. Declaring is idempotent, but declaring an existing queue with different arguments fails with PRECONDITION_FAILED.

RabbitTemplate and the converter you must register

@Service

        rabbit.convertAndSend(RabbitConfig.EXCHANGE, "order." + e.region() + ".created", e, m -> {
            m.getMessageProperties().setMessageId(e.eventId().toString());   // for consumer dedupe
            m.getMessageProperties().setHeader("x-correlation-id", e.correlationId());
            return m;                                                       // persistent by default
        });
    }

    PriceQuote quote(QuoteRequest request) {     // RPC: blocks until the reply or replyTimeout (5 s), else null
        return rabbit.convertSendAndReceiveAsType("pricing", "quote.request", request,
                new ParameterizedTypeReference<PriceQuote>() {});

}

Without a converter bean, the template uses SimpleMessageConverter: strings become text/plain, byte arrays pass through, and any other Serializable object is Java-serialized. That couples producer and consumer to the same classes and versions and makes deserialization a security risk (recent versions refuse classes outside an allowed list). Register Jackson2JsonMessageConverter. The MessagePostProcessor lambda edits properties after conversion: message id, correlation id, custom headers. convertSendAndReceive uses RabbitMQ's direct reply-to and blocks the caller; for non-blocking RPC use AsyncRabbitTemplate, and think twice before doing RPC over a broker at all.

On a method, the converter infers the target type from the parameter. On a class, @RabbitHandler methods are chosen by the payload's type after conversion, so the converter needs type information from the __TypeId__ header. @Headers Map<String, Object> gives all headers; Channel and Message parameters give raw access. Inline bindings declare the queue, exchange and binding for you.

Definition · Type mapping and the type id header

Jackson2JsonMessageConverter writes a __TypeId__ header, by default the producer's fully qualified class name, and the consumer uses it when it cannot infer the type. Class names leak packages across services and break on refactoring; setIdClassMapping (on both sides) maps stable logical ids such as order.created to local classes instead. When falling back to class names, restrict them with setTrustedPackages.

Acknowledge modes: AUTO (the default) means the container acks when your method returns and rejects when it throws; MANUAL means you call basicAck/basicNack; NONE is RabbitMQ's autoAck=true, at-most-once. By default a rejected message is requeued, which loops forever on a poison message: set default-requeue-rejected: false, or throw AmqpRejectAndDontRequeueException. Conversion failures are treated as fatal and rejected without requeue. Tune prefetch against processing time: 250 is good for millisecond handlers and bad for ten-second ones.

What breaks in production
  • No JSON converter: Java-serialized bodies that no other language, or the next version of your own class, can read.
  • Requeue on exception (the default) plus one malformed message: 100% CPU and no progress on the queue.
  • __TypeId__ carrying com.shop.orders.v1.OrderCreated: the consumer's package differs and every message fails conversion.
  • Changing a queue's arguments in code while it already exists: PRECONDITION_FAILED at startup.

RabbitMQ Reliability: Confirms, DLQ & Retries

45m video50m practice

Reliable messaging with RabbitMQ is at-least-once assembled from parts: publisher confirms and returns prove the broker accepted and routed each message, manual or container-managed acks prove the consumer finished, dead-lettering stops poison messages from looping, and idempotent consumers absorb the duplicates all of this produces.

Publisher side: confirms and returns

spring:
  rabbitmq:
    publisher-confirm-type: correlated   # none | simple | correlated
    publisher-returns: true
    template:
      mandatory: true                    # unroutable messages are returned, not silently dropped
@Service
class ReliablePublisher {
    private final RabbitTemplate rabbit;
    private final OutgoingMessages outgoing;     // table: id, exchange, routing_key, payload, status, updated_at

    ReliablePublisher(RabbitTemplate rabbit, OutgoingMessages outgoing) {
        this.rabbit = rabbit;
        this.outgoing = outgoing;
    }

    void publish(OutgoingMessage msg) {
        var cd = new CorrelationData(msg.id().toString());          // ties the confirm to our record
        rabbit.convertAndSend(msg.exchange(), msg.routingKey(), msg.payload(), cd);
        cd.getFuture().whenComplete((confirm, ex) -> {
            if (ex != null)                    outgoing.markFailed(msg.id(), ex.toString());
            else if (cd.getReturned() != null) outgoing.markFailed(msg.id(), "unroutable: " + cd.getReturned().getReplyText());
            else if (confirm.isAck())          outgoing.markSent(msg.id());
            else                               outgoing.markFailed(msg.id(), confirm.getReason());
        });
    }

    @Scheduled(fixedDelay = 30_000)
    void resendStale() {                                            // no confirm within 30 s: try again
        outgoing.findPendingOlderThan(Duration.ofSeconds(30)).forEach(this::publish);
    }
}

With correlated confirms, every publish that carries a CorrelationData gets a Confirm (ack or nack with a reason) on its future, or on a template-wide ConfirmCallback set with setConfirmCallback((cd, ack, cause) -> ...). An ack means the broker took responsibility; it does not mean the message was routed. That is what returns are for: with mandatory=true an unroutable message comes back through the ReturnsCallback (setReturnsCallback(returned -> ...), one per template) and on cd.getReturned() before the ack arrives. Callbacks run on the client's I/O thread, so keep them short, and resend anything left pending; the resend makes publishing at-least-once, and the message id lets consumers drop the duplicates.

Consumer side: acks and the requeue loop

@RabbitListener(queues = "order.billing", ackMode = "MANUAL")
void onCreated(OrderCreated event, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) long tag)
        throws IOException {
    try {
        billing.charge(event);
        channel.basicAck(tag, false);
    } catch (TransientDownstreamException e) {
        channel.basicNack(tag, false, true);      // requeue: only for failures that can heal
    } catch (Exception e) {
        channel.basicNack(tag, false, false);     // never requeue the unprocessable: dead-letter it
    }
}

The trap: a message that can never succeed (bad payload, missing reference data), nacked with requeue=true, goes straight back to the head of the queue and is redelivered immediately, thousands of times a second, starving every message behind it. Even "transient" requeues have no delay. Quorum queues cap this with a delivery limit (dead-lettering with reason delivery_limit), but the real fix is to dead-letter and retry with a delay.

Definition · Dead-lettering

A message is dead-lettered when it is rejected or nacked without requeue, when its TTL expires, when the queue overflows its max length, or when a quorum queue's delivery limit is exceeded. RabbitMQ adds an x-death header: a list with one entry per queue and reason, holding queue, reason (rejected, expired, maxlen, delivery_limit), count, exchange, routing-keys and time. That count is how a consumer knows how many times a message has already cycled. Give every work queue its own DLQ so you know where a dead message came from.

Retry with delay

  • TTL + DLX (above): uses only core features and survives restarts. Use a queue-level x-message-ttl and one retry queue per delay step (10 s, 1 min, 10 min); per-message TTLs only expire at the head of a queue, so a long delay blocks short ones behind it.
  • The rabbitmq_delayed_message_exchange plugin: an x-delayed-message exchange that holds messages for the x-delay header's milliseconds. Simple, but a community plugin with documented limits: delayed messages are stored on one node and are not replicated, so it suits modest volumes and short delays.
  • Spring Retry in the container: retries in-process before the message is ever rejected.

Every mechanism above can deliver twice, so consumers deduplicate on the message id. A dedupe table written in the same database transaction as the effect (L369) is exact. Watch per queue: ready depth (backlog), unacked (in flight; stuck at prefetch × consumers means hung handlers), consumer count, and consumer utilisation (the share of time the queue could push to consumers immediately; low means consumers are the bottleneck). Kafka Architecture: Brokers, Topics & Partitions

50m video45m practice

Kafka is a distributed, replicated, append-only log, not a queue: reading a message does not remove it, every consumer group keeps its own position, and data stays until retention removes it. The partition is the unit of everything: parallelism, ordering, replication and storage.

A log, not a queue

A topic is a named log split into partitions. Each partition is an ordered, immutable sequence of records; each record gets the next offset (0, 1, 2, …) in its partition. Producers append to the end; consumers read from a position they choose and advance it themselves. Because reads are non-destructive, ten consumer groups can read the same data at their own speeds, a new service can replay last week's events, and a bug fix can be followed by reprocessing. A queue (L370) deletes on acknowledgement; a log deletes on retention.

Brokers, the controller and KRaft

A broker is a server that stores partition replicas and serves reads and writes. The controller manages cluster metadata: which brokers are alive, which replica leads each partition, topic configs. Kafka used to keep that metadata in ZooKeeper; KRaft (KIP-500) replaced it with a Raft quorum of controller nodes that replicate a metadata log (__cluster_metadata). ZooKeeper mode was deprecated in 3.5 and removed in Kafka 4.0, so every new cluster is KRaft: one system to run, faster failover, and far more partitions per cluster.

Partitions, keys and ordering

Definition · Ordering guarantee

Kafka guarantees order within a partition only: records in one partition are stored and delivered in offset order. Across partitions there is no order at all. To keep related events in order, give them the same key: the default partitioner sends a keyed record to murmur2(keyBytes) mod partitionCount, so equal keys always land in the same partition (as long as the partition count does not change). Records with a null key are spread by the sticky partitioner, which fills a batch for one partition before moving to the next.

import java.nio.charset.StandardCharsets;
import org.apache.kafka.common.utils.Utils;

final class Partitions {
    static int partitionFor(String key, int partitionCount) {     // what the default partitioner does
        byte[] bytes = key.getBytes(StandardCharsets.UTF_8);
        return Utils.toPositive(Utils.murmur2(bytes)) % partitionCount;
    }
}

Choosing the key is choosing the ordering you need. Order id: all events of one order (created, paid, shipped) stay in sequence, and orders spread evenly. Customer id: all of a customer's orders are sequenced relative to each other, at the cost of coarser parallelism and hot partitions for very active customers. No key: maximum spread, no ordering. Partitions also cap parallelism: a group can have at most one active consumer per partition.

Replication, ISR and the data-loss tradeoff

Every partition has a replication factor (3 in production). One replica is the leader and handles all writes; followers fetch from it. The ISR (in-sync replicas) is the set of replicas caught up with the leader within replica.lag.time.max.ms (30 s by default). A record is committed when every ISR member has it; the partition's high watermark marks that point and consumers only read below it. A producer with acks=all is acknowledged only once the record is committed (L374).

Theorem · Durability arithmetic

With replication factor R, min.insync.replicas = M and acks=all, an acknowledged write exists on at least M replicas, so it survives the loss of any M − 1 brokers; writes keep being accepted while at least M replicas are in sync, so up to R − M brokers can be down. The standard R = 3, M = 2 tolerates one failure for both, and below two in-sync replicas producers get NotEnoughReplicasException rather than silently weaker durability.

Unclean leader election (unclean.leader.election.enable, false by default) decides what happens when every ISR member is gone. False: the partition stays offline until an in-sync replica returns (consistency). True: an out-of-sync replica becomes leader and the committed records it never received are lost (availability). Leave it false for business data.

A partition is stored as segments rolled by size (segment.bytes, 1 GiB) or age (segment.ms, 7 days). Retention deletes whole closed segments, never the active one. Delete policy (cleanup.policy=delete): drop segments older than retention.ms (7 days by default) or beyond retention.bytes per partition (unlimited by default). Compaction (cleanup.policy=compact): a background cleaner keeps at least the latest record for each key and discards older ones, so the topic becomes a changelog of current state (Kafka's own __consumer_offsets works this way). A record with a null value is a tombstone that deletes its key after delete.retention.ms. compact,delete combines both.

Consumers sharing a group.id split a topic's partitions between them: each partition goes to exactly one member, so six partitions support at most six busy consumers and a seventh sits idle as a hot standby. Different groups are independent and each sees every record (L375).

What breaks in production
  • Adding partitions to a keyed topic: the modulo changes, keys move, and per-key ordering breaks during the transition.
  • acks=all with min.insync.replicas=1: "all" can mean one replica, and losing that broker loses acknowledged data.
  • Retention shorter than the longest consumer outage: the group comes back to deleted offsets and auto.offset.reset silently skips or replays.
  • One hot key (a marketplace's biggest seller) pinning one partition at 100% while the rest idle.

Kafka Producers: Batching, Acks & Idempotence

45m video50m practice

KafkaProducer.send() does not send anything: it serializes, picks a partition, and appends to an in-memory batch that a background thread ships later. Durability is decided by acks plus the topic's min.insync.replicas; duplicates and reordering from retries are removed by the idempotent producer, which is on by default since Kafka 3.0.

The producer pipeline

The serializer turns key and value into bytes. The partitioner picks a partition (key hash, or sticky for null keys). The record accumulator keeps one open batch per partition inside buffer.memory (32 MiB); when it is full, send() blocks for up to max.block.ms (60 s) and then throws. The sender thread drains batches that are full (batch.size) or old enough (linger.ms), groups them per leader broker, compresses each batch, and sends.

Only with min.insync.replicas>=2 on the topic does the broker refuse writes (NotEnoughReplicasException) instead of acknowledging them on one copy, so the pair acks=all + min.insync.replicas=2 + replication factor 3 is what "durable" means in Kafka (L373).

Retries, timeouts and reordering

Transient errors (leader moved, not enough replicas yet, timeouts) are retried by the sender: retries defaults to Integer.MAX_VALUE, so the real limit is delivery.timeout.ms (2 min), the total time from send() to success or failure, which must be at least linger.ms + request.timeout.ms. request.timeout.ms (30 s) bounds one request. max.in.flight.requests.per.connection (5) is how many unacknowledged requests may be outstanding per broker.

Worked example

Without idempotence and with 5 requests in flight: batch A (offsets for order-42 "created") fails with a timeout, batch B ("paid") succeeds, then A is retried and succeeds. The log now holds "paid" before "created". Worse, if A had actually been written and only its response was lost, the retry writes it a second time. Retries plus pipelining give you both reordering and duplicates. The old fix, max.in.flight=1, preserves order by giving up pipelining.

The idempotent producer

Definition · Idempotence

With enable.idempotence=true the broker assigns the producer a producer id and epoch, and every batch carries a per-partition sequence number. The partition leader keeps the last sequences per producer id: a batch it has already written is acknowledged again without being stored (no duplicate), and a batch that arrives out of sequence is rejected so the producer resends in order. This keeps order and removes retry duplicates with up to 5 requests in flight. It requires acks=all, retries above 0, and in-flight at most 5.

Its scope is narrow and precise: it deduplicates retries by the internal sender within one producer session, per partition. A restarted producer gets a new id, so a record the application re-sends after a crash is a new record; and it says nothing about consumers. Exactly-once across restarts and across consume-transform-produce needs transactions (L379). One more trap: idempotence is the default only while nothing conflicts with it; setting acks=1 without mentioning idempotence quietly turns it off, while explicitly setting enable.idempotence=true with conflicting values fails at startup.

Throughput tuning

  • linger.ms: how long a batch may wait to fill. The default was 0 until Kafka 4.0 raised it to 5; 5 to 20 ms usually multiplies throughput for a few ms of latency.
  • batch.size: maximum bytes per partition batch (16 KiB default). 64 to 256 KiB for high volume.
  • compression.type: lz4 or snappy for speed, zstd for ratio; compression is per batch, so bigger batches compress better. Brokers store batches compressed.
  • buffer.memory: the total budget; raise it with many partitions or large batches.
  • max.request.size: largest request (1 MiB); larger records also need the broker's message.max.bytes or the topic's max.message.bytes raised. Prefer storing big blobs elsewhere and sending a reference.

Kafka Consumers: Groups, Offsets & Rebalancing

45m video50m practice

A Kafka consumer's delivery guarantee is decided by one thing: when it commits its offset relative to finishing the work. Commit after processing and you get at-least-once with duplicates after crashes and rebalances; commit before and you get at-most-once. Rebalancing is when those choices are tested, so the commit strategy and the rebalance strategy have to be designed together.

The poll loop

public class OrderConsumer implements Runnable {
    private final KafkaConsumer<String, String> consumer;
    private final Map<TopicPartition, OffsetAndMetadata> done = new HashMap<>();

    public OrderConsumer(Properties props) { this.consumer = new KafkaConsumer<>(props); }

    @Override public void run() {
        try {
            consumer.subscribe(List.of("orders.events"), new ConsumerRebalanceListener() {
                @Override public void onPartitionsRevoked(Collection<TopicPartition> parts) {
                    consumer.commitSync(done);                 // commit finished work before losing it
                    parts.forEach(done::remove);               // no longer ours: never commit them again
                }
                @Override public void onPartitionsAssigned(Collection<TopicPartition> parts) { }
            });
            while (true) {
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
                for (ConsumerRecord<String, String> r : records) {
                    handle(r);                                 // must fit inside max.poll.interval.ms
                    done.put(new TopicPartition(r.topic(), r.partition()),
                             new OffsetAndMetadata(r.offset() + 1));   // next offset to read
                }
                if (!records.isEmpty()) consumer.commitAsync(Map.copyOf(done), null);
            }
        } catch (WakeupException e) {
            // shutdown requested
        } finally {
            try { consumer.commitSync(done); } finally { consumer.close(); }
        }
    }

    public void shutdown() { consumer.wakeup(); }               // the only thread-safe method

    private void handle(ConsumerRecord<String, String> r) { System.out.println(r.key() + " " + r.value()); }
}

poll(Duration) fetches records, and it also drives the group protocol: rebalance callbacks run inside it, and auto-commits happen inside it. KafkaConsumer is not thread-safe: calling it from two threads throws ConcurrentModificationException. Use one consumer per thread; the one exception is wakeup(), which makes a blocked poll throw WakeupException for a clean shutdown. If you hand records to a worker pool, you must also track which offsets are finished and pause partitions to bound memory.

Consumer groups

Consumers with the same group.id share a subscription: the group coordinator (a broker) tracks members and the assignor maps each partition to exactly one member. Scaling out means adding members, up to the partition count; beyond it extra members idle. Different groups are independent readers of the same data, each with its own committed offsets stored in the compacted __consumer_offsets topic.

Offsets: what to commit and when

Definition · Committed offset

The committed offset for a partition is the next offset the group will read, that is, the last processed offset + 1. After a restart or rebalance, the new owner of the partition starts exactly there. Everything processed but not yet committed is processed again; everything committed but not yet processed is skipped.

  • enable.auto.commit=true (the default, every auto.commit.interval.ms = 5 s) commits, during poll, the offsets of records the previous poll returned, whether or not you finished them. With strictly synchronous processing in the loop this is at-least-once with up to 5 s of duplicates after a crash or rebalance. With asynchronous processing (records handed to other threads, or buffered) it commits work that has not happened: after a crash or a rebalance the new owner starts past those records and they are lost.
  • commitSync() blocks and retries until it succeeds or hits a fatal error. commitAsync() does not block and does not retry (a retried old commit could overwrite a newer one). The standard pattern is the one above: async in the loop, sync on revoke and on shutdown.
  • External offsets for an exactly-once sink: write the effect and the offset in one database transaction, and on assignment seek(tp, storedOffset). A crash then rolls back both, so the effect and the position can never disagree.

auto.offset.reset decides where to start when the group has no committed offset for a partition, or its offset no longer exists because retention deleted it: latest (default, only new records), earliest (from the oldest retained record), or none (throw NoOffsetForPartitionException, so a human decides).

Rebalancing

A rebalance reassigns partitions. Triggers: a member joins; a member leaves cleanly; a member is declared dead because no heartbeat arrived within session.timeout.ms (45 s; heartbeats every heartbeat.interval.ms, 3 s, from a background thread); a member did not call poll within max.poll.interval.ms (5 min) and left the group; the subscription or partition count changes.

  • Eager assignors (RangeAssignor, RoundRobinAssignor) revoke all partitions from all members, then reassign: the whole group stops.
  • CooperativeStickyAssignor (incremental cooperative rebalancing, KIP-429) keeps assignments sticky and revokes only partitions that move. Kafka 4.0 also made the next-generation protocol (KIP-848, group.protocol=consumer) generally available, which moves assignment to the broker and avoids group-wide barriers.
  • Static membership (group.instance.id, KIP-345): a restarted instance that returns within session.timeout.ms gets its partitions back with no rebalance, which makes rolling deploys quiet.
  • ConsumerRebalanceListener: commit in onPartitionsRevoked; seek or load state in onPartitionsAssigned; in onPartitionsLost the partitions already belong to someone else, so do not commit.

The rebalance loop and lag

Worked example

max.poll.records=500 and a handler that sometimes takes 1 s per record (a slow downstream): one batch takes up to 500 s, more than max.poll.interval.ms = 300 s. The consumer is removed, its partitions move, and the new owner starts from the last commit, gets the same slow batch, and is removed too. Throughput falls to zero while CPU looks busy. Fixes: make max.poll.records × worst-case time per record comfortably smaller than the interval (here 50 records), raise the interval, put timeouts on downstream calls, or pause the partition and process asynchronously.

Consumer lag (log-end offset minus committed offset, per partition) is the primary health metric: it captures slow handlers, stuck partitions, rebalance storms and too few consumers in one number. Alert on lag that keeps growing over minutes, not on a fixed value, and watch the maximum across partitions, since a single stuck partition hides inside a healthy average.

What breaks in production
  • Auto-commit plus an executor service: records are "committed" before processing; a deploy loses them.
  • Committing r.offset() instead of r.offset() + 1: the last record of every partition is reprocessed on every restart.
  • Slow handlers with a large max.poll.records: an endless rebalance loop.
  • Twelve pods on a six-partition topic: six idle pods, and no extra throughput.

Definition · Listener container

A KafkaMessageListenerContainer owns one KafkaConsumer and the one thread that runs its poll loop: it polls, invokes your listener per record (or per batch), commits according to the ack mode, and hands exceptions to the container's error handler. A ConcurrentMessageListenerContainer creates concurrency such children in the same group, and the factory builds one of those per @KafkaListener endpoint. Because each child is single-threaded, records of one partition are always processed in order.

@Component
class BillingListener {
    private final BillingService billing;
    BillingListener(BillingService billing) { this.billing = billing; }

    @KafkaListener(id = "billing", topics = "orders.events", groupId = "billing", concurrency = "3")
    void on(@Payload OrderEvent event,
            @Header(KafkaHeaders.RECEIVED_KEY) String key,
            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
            @Header(KafkaHeaders.OFFSET) long offset) {
        billing.apply(event);                     // returns normally: offset committed per ack mode
    }

    @KafkaListener(topics = "payments.events", groupId = "billing-payments", containerFactory = "manualAckFactory")
    void manual(ConsumerRecord<String, PaymentEvent> record, Acknowledgment ack) {
        billing.record(record.value());
        ack.acknowledge();                        // MANUAL_IMMEDIATE: commit offset + 1 now
    }

    @KafkaListener(topics = "clicks", groupId = "analytics", batch = "true")
    void batch(List<ConsumerRecord<String, Click>> records) {
        billing.storeClicks(records);             // one call per poll, e.g. a JDBC batch insert
    }
}

@Configuration

Serialization, Schema Registry & Evolution

45m video50m practice

Kafka stores bytes; the format of those bytes is the real API contract between teams, and it outlives every service that reads it. A schema registry turns that contract into something machine-checked: every message names its schema, and incompatible changes are rejected before they reach consumers.

Serializers, JSON, and the poison record

Producer and consumer must agree on a serializer/deserializer pair for key and value. StringSerializer and ByteArraySerializer are trivial. Spring's JsonSerializer writes JSON and, by default, a __TypeId__ header naming the Java class; JsonDeserializer only instantiates classes from spring.json.trusted.packages. Setting it to * lets whoever can write to the topic choose which class your consumer instantiates, which is the classic shape of a deserialization vulnerability, and it couples consumers to the producer's package names. Prefer logical type ids:

spring:
  kafka:
    producer:
      properties:
        spring.json.type.mapping: orderPlaced:com.shop.events.OrderPlaced,orderCancelled:com.shop.events.OrderCancelled
    consumer:
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.value.delegate.class: org.springframework.kafka.support.serializer.JsonDeserializer
        spring.json.trusted.packages: com.shop.events
        spring.json.type.mapping: orderPlaced:com.billing.events.OrderPlaced,orderCancelled:com.billing.events.OrderCancelled
Definition · Poison record

A record whose bytes the deserializer cannot decode. Deserialization happens inside poll(), before your listener sees anything, so without protection the container fails on the same offset on every poll and the partition stops. ErrorHandlingDeserializer wraps the real deserializer, catches the failure, returns a null value with the exception in a header, and lets the container's error handler skip the record or send it to a dead-letter topic without retrying (L378).

Definition · The four modes
  • BACKWARD (the registry default): a consumer on the new schema can read data written with the previous one. Upgrade consumers first.
  • FORWARD: a consumer on the previous schema can read data written with the new one. Upgrade producers first.
  • FULL: both, so any deployment order works; in practice only optional fields (with defaults) may be added or removed.
  • NONE: no checks. The _TRANSITIVE variants check against every earlier version, not just the latest, which is what long-retention topics need.

Rules that keep old consumers working: give every new field a default; never change a field's meaning while keeping its name; never reuse a removed name (or Protobuf tag); treat a rename as add-new plus remove-old. For keyed topics, never change the key format: it changes partitioning and breaks compaction.

Worked example

The event above with a 36-character UUID, order-123456, 129900 and EUR. As JSON with field names it is 112 bytes. As Avro: 37 (UUID string) + 13 (order id) + 3 (zig-zag varint of 129900) + 4 (currency) + 1 (null union branch) = 58 bytes, plus the 5-byte header = 63. As Protobuf: 38 + 14 + 4 + 5 = 61 bytes, plus header and message index = 67. Storing the UUID as 16 raw bytes would cut another 20. Batch compression narrows the gap with JSON, so measure throughput with your own payloads before choosing on size alone.

Versioning events: compatible changes stay in the same subject and topic. For a breaking change, expand then contract: (1) expand: add the new field (with a default) and have producers write both old and new; (2) migrate every consumer to the new field; (3) contract: stop writing the old field, then remove it. When a change cannot be made compatible at all, publish a new event type or a .v2 topic, dual-publish during the migration, and retire the old one when its consumer lag reaches zero for good.

  • No ErrorHandlingDeserializer: one malformed record stops a partition until someone moves the offset by hand.
  • auto.register.schemas=true plus compatibility NONE: a producer deploy breaks every consumer at once.
  • Non-transitive BACKWARD on a topic retained forever: v3 is compatible with v2, but not with the v1 data a replay will read.
  • Trusting * packages with type headers on a topic other teams can write to.

Kafka Error Handling: Retries, DLT & Idempotency

45m video55m practice

A partition is a sequence, so a record that cannot be processed blocks everything behind it unless you decide what happens to it. Classify failures (retryable or not), retry the transient ones with backoff, park the rest in a dead-letter topic with enough context to fix and replay them, and make consumers idempotent because every one of these paths can redeliver.

Why one bad record stops a partition

Offsets are committed in order: the consumer cannot commit offset 101 while 100 is unprocessed without declaring 100 done. A hand-written loop that seeks back on failure therefore retries the same record forever, and the partition's lag grows without bound while the other partitions look healthy. Spring's DefaultErrorHandler avoids the infinite loop, but its default is not what you want either: 10 delivery attempts with no delay, then the record is logged and skipped. That is a hot retry loop followed by silent data loss.

Blocking retries with DefaultErrorHandler

@Configuration
class KafkaErrorHandling {
    @Bean                                              // Boot wires a CommonErrorHandler bean into the factory
    DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
        var recoverer = new DeadLetterPublishingRecoverer(template,
            (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));
        var backOff = new ExponentialBackOffWithMaxRetries(4);    // 4 retries after the first attempt
        backOff.setInitialInterval(500);
        backOff.setMultiplier(2.0);
        backOff.setMaxInterval(5_000);                            // 0.5, 1, 2, 4 s
        var handler = new DefaultErrorHandler(recoverer, backOff);
        handler.addNotRetryableExceptions(ValidationException.class, UnknownProductException.class);
        handler.setCommitRecovered(true);                         // commit the offset once it is in the DLT
        return handler;
    }
}
Definition · Blocking retry

When the listener throws, DefaultErrorHandler seeks the partition back to the failed record (and re-seeks the rest of the polled batch), waits the next backoff interval, and lets the next poll redeliver it. Other partitions on the same consumer wait too, and the total backoff must stay well inside max.poll.interval.ms. After the last attempt, or immediately for a not-retryable exception, the recoverer runs and the record is skipped. Deserialization and conversion failures are not retryable by default; add your own validation and "will never succeed" exceptions with addNotRetryableExceptions.

FixedBackOff(1000L, 3L) gives three retries a second apart; ExponentialBackOffWithMaxRetries grows the delay and caps the count. setCommitRecovered(true) commits the recovered record's offset straight away, so a crash right after recovery does not send it to the DLT twice.

DeadLetterPublishingRecoverer and the DLT

The recoverer publishes the failed record, with its original key and value bytes, to <topic>.DLT on the same partition number by default, so create the DLT with at least as many partitions, or return partition -1 from the resolver to let Kafka choose. It adds headers describing the failure:

Non-blocking retries with @RetryableTopic

@Component
class PaymentListener {
    private final PaymentGateway gateway;
    private final Alerts alerts;
    PaymentListener(PaymentGateway gateway, Alerts alerts) { this.gateway = gateway; this.alerts = alerts; }

    @RetryableTopic(
        attempts = "4",                                             // first try + 3 retries
        backoff = @Backoff(delay = 1_000, multiplier = 3.0, maxDelay = 30_000),
        exclude = {ValidationException.class, CardDeclinedException.class},  // straight to the DLT
        dltStrategy = DltStrategy.FAIL_ON_ERROR)
    @KafkaListener(topics = "payments.requests", groupId = "payments")
    void charge(PaymentRequest request) {
        gateway.charge(request);                                    // throws on gateway 5xx / timeout
    }

    @DltHandler
    void parked(PaymentRequest request,
                @Header(name = KafkaHeaders.DLT_EXCEPTION_MESSAGE, required = false) String reason) {
        alerts.paymentParked(request.paymentId(), reason);
    }
}

Spring creates payments.requests-retry-0, -retry-1, -retry-2 (delays 1 s, 3 s, 9 s) and payments.requests-dlt, plus a listener container for each. A failed record is republished to the next retry topic with a due-time header and the main offset is committed, so the main partition keeps flowing. A retry-topic consumer that sees a record not yet due pauses that partition and resumes when the delay has passed. include/exclude classify exceptions; dltStrategy decides what happens if the @DltHandler itself fails (ALWAYS_RETRY_ON_ERROR, the default, or FAIL_ON_ERROR), or turns the DLT off (NO_DLT).

Choosing: use blocking retries for short transient failures on order-sensitive streams (state changes of one aggregate keyed by its id), where processing r3 before r2 would be wrong. Use non-blocking retries when records are independent and outages can last longer than a poll interval (payment gateway, email provider), and make handlers tolerate reordering, for example by checking a version.

Idempotent consumers

-- 1. dedupe on a business key, in the same transaction as the effect
INSERT INTO processed_event (event_id) VALUES (:eventId) ON CONFLICT DO NOTHING;   -- 0 rows: skip

-- 2. upsert instead of insert
INSERT INTO shipment (order_id, status) VALUES (:orderId, 'CREATED')
ON CONFLICT (order_id) DO NOTHING;

-- 3. conditional update: ignore stale or repeated versions
UPDATE order_view SET status = :status, version = :version
WHERE order_id = :orderId AND version < :version;

A processed-message table keyed by topic-partition-offset catches redelivery of the same record (after a crash, rebalance or retry). It does not catch a duplicate the producer wrote as a new record, which has a new offset; a business idempotency key (event id, or payment id plus operation) catches both. Where the effect is naturally idempotent (upsert, set-to-value, versioned update), no table is needed at all.

  • The default error handler: ten immediate attempts, then the record is logged and skipped.

  • A DLT with fewer partitions than its source and the default same-partition resolver: publishing to the DLT fails, so recovery fails.
  • @RetryableTopic on order-state events: "shipped" applied before "paid", and a stuck order.

Kafka Transactions & Exactly-Once Semantics

45m video45m practice

Kafka's exactly-once semantics make one thing atomic: the records a consume-transform-produce step writes to Kafka and the consumer offsets it commits. Either both become visible or neither does. Anything outside Kafka (a database row, an email, an HTTP call) is not covered; for those, the answer is an outbox plus idempotent consumers.

What EOS guarantees, precisely

Definition · Exactly-once in Kafka

For an application that reads from Kafka, writes results to Kafka, and commits its input offsets inside one transaction, and for downstream consumers reading with isolation.level=read_committed: each input record's effects on the output topics appear exactly once, even across producer retries, crashes and rebalances. The input may be processed more than once (an aborted attempt is retried), but aborted outputs are never seen. The guarantee ends at Kafka's boundary.

Mechanics: transactional.id, coordinator, transaction log

  • transactional.id: a stable name for one logical producer, which survives restarts. It implies idempotence (L374).
  • Transaction coordinator: a broker chosen by hashing the transactional id. It stores transaction state in the internal transaction log, the compacted topic __transaction_state.
  • Commit is two-phase inside Kafka: the coordinator records PREPARE_COMMIT in its log, writes a commit marker (a control record) into every partition the transaction touched, including __consumer_offsets, then records completion. An abort writes abort markers instead.
  • read_committed consumers read only up to the last stable offset (the first offset of the oldest open transaction), skip control records, and drop records of aborted transactions using each partition's aborted-transaction index. The default, read_uncommitted, sees everything, including aborted records.

The raw API

producer.initTransactions();                        // fences older instances, finishes their open tx
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(200));
    if (records.isEmpty()) continue;
    producer.beginTransaction();
    try {
        Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
        for (ConsumerRecord<String, String> r : records) {
            producer.send(new ProducerRecord<>("orders.enriched", r.key(), enrich(r.value())));
            offsets.put(new TopicPartition(r.topic(), r.partition()), new OffsetAndMetadata(r.offset() + 1));
        }
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
        producer.commitTransaction();
    } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException e) {
        producer.close();                           // fatal: a newer instance owns this transactional.id
        throw e;
    } catch (KafkaException e) {
        producer.abortTransaction();                // outputs and offsets discarded together
        for (TopicPartition tp : records.partitions())
            consumer.seek(tp, records.records(tp).get(0).offset());   // reprocess the batch
    }
}

The consumer runs with enable.auto.commit=false and isolation.level=read_committed, and never commits offsets itself: sendOffsetsToTransaction does it as part of the transaction, and passing consumer.groupMetadata() lets the broker reject commits from a consumer that has been rebalanced away.

Zombie fencing and epochs

A "zombie" is an instance that the rest of the system believes dead (a long GC pause, a network partition) but that wakes up and keeps writing. Each initTransactions() with a given transactional.id bumps the producer epoch at the coordinator; any request carrying an older epoch is rejected with ProducerFencedException, so the zombie cannot commit. On the consumer side, EOS v2 (KIP-447) fences by the group generation in the consumer group metadata, which is why one transactional producer per application instance is enough. A random transactional.id per start disables fencing entirely.

Theorem · No atomic DB plus Kafka commit

Kafka does not take part in XA two-phase commit, so a database transaction and a Kafka transaction are committed one after the other. There is always a window: if the database commits and the Kafka commit then fails, the record is redelivered and the database effect is applied again; if Kafka commits first and the database then fails, an event is published for a change that never happened. Ordering the commits (database first) only chooses the failure: duplicates, which an idempotent handler can absorb, instead of phantom events, which nothing can.

The correct pattern: transactional outbox

@Transactional                                      // ONE database transaction
public Order place(PlaceOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(OutboxEvent.of("Order", order.getId(), "OrderPlaced", json(order)));
    return order;                                   // no Kafka call here
}

@Scheduled(fixedDelay = 200)
@Transactional
public void relay() {                               // FOR UPDATE SKIP LOCKED: safe with several relays
    for (OutboxEvent ev : outbox.lockNextBatch(100)) {
        kafka.send("orders.events", ev.aggregateId(), ev.payload()).join();   // idempotent producer
        ev.markProcessed(Instant.now());
    }
}

The business change and the event are written atomically in the database (the outbox from L334); a relay publishes afterwards. If it crashes after sending but before marking, the event is sent again, so publication is at-least-once and consumers deduplicate on the event id. Kafka Streams and the cost of transactions

Kafka Streams wraps all of the above in one setting: processing.guarantee=exactly_once_v2 (brokers 2.5+; the older exactly_once and exactly_once_beta values are deprecated). State-store changelogs, output topics and offsets then commit in one transaction per task, and commit.interval.ms drops from 30 s to 100 ms by default. The cost is per transaction, not per record: coordinator round trips and a marker per touched partition, plus latency for read_committed readers, who wait until a transaction commits. Large transactions amortize the overhead; tiny ones can cut throughput sharply. Measure on your cluster with transactions of 1, 100 and 1,000 records before deciding.

What breaks in production
  • Believing exactly_once covers the database writes or emails in your listener.
  • Downstream consumers left on the default read_uncommitted: they see aborted records.
  • A random or per-thread-random transactional.id: no fencing, and zombies commit.
  • A transaction held open for a slow external call: read_committed readers stall behind it, and past transaction.timeout.ms (60 s) the coordinator aborts it.

Kafka Streams

50m video55m practice

Kafka Streams is a Java library, not a cluster: your application instances are the stream processor, Kafka's partitions are the unit of parallelism, and local state stores are made fault-tolerant by changelog topics. Everything else (windows, joins, exactly-once) follows from treating streams and tables as two views of the same log.

Library, topology, and the stream-table duality

You describe a topology with StreamsBuilder: source nodes read topics, processor nodes transform, sink nodes write topics. new KafkaStreams(topology, props) runs it inside your JVM. The input partitions are split into tasks, tasks are spread over all running instances sharing the same application.id (a consumer group underneath), and adding an instance rebalances tasks onto it.

Definition · Streams and tables
  • KStream: an unbounded sequence of independent events. Two records with the same key are two facts ("order-1 placed", "order-1 paid").
  • KTable: a changelog interpreted as current state. A record is an update to its key; a null value deletes it. Each instance holds only the partitions it owns.
  • GlobalKTable: a table replicated in full to every instance, for small reference data; joining against it needs no co-partitioning.

Duality: aggregating a stream by key yields a table; the stream of a table's updates is a stream. That is why a compacted topic can back a table and why a table can always be turned back into a stream with toStream().

Stateless and stateful operations

Stateless: filter, map (new key and value), mapValues (value only: keeps partitioning), flatMap/flatMapValues, selectKey, peek (side effects such as logging), merge (two streams into one), split().branch(...) (the replacement for the deprecated branch), and to for writing a topic. through is deprecated in favour of repartition().

Stateful: groupByKey() or groupBy(...), then count, reduce or aggregate. Results live in a state store, RocksDB on local disk by default, and every update is also written to a compacted changelog topic (<application.id>-<store>-changelog). When a task moves to another instance, the store is rebuilt from the changelog; num.standby.replicas keeps warm copies elsewhere to shorten that restore.

Windows and event time

@Configuration
@EnableKafkaStreams
class OrderStreams {
    @Bean
    KStream<String, OrderPlaced> ordersPerMinute(StreamsBuilder builder) {
        var orderSerde = new JsonSerde<>(OrderPlaced.class);
        KStream<String, OrderPlaced> orders =
            builder.stream("orders.events", Consumed.with(Serdes.String(), orderSerde));

        orders.filter((id, o) -> o.totalCents() > 0)
              .selectKey((id, o) -> o.region())                          // new key: repartition
              .groupByKey(Grouped.with(Serdes.String(), orderSerde))
              .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(1), Duration.ofSeconds(30)))
              .count(Materialized.as("orders-per-minute-by-region"))
              .toStream()
              .map((win, n) -> KeyValue.pair(win.key() + "@" + win.window().startTime(), n))
              .to("orders.per-minute", Produced.with(Serdes.String(), Serdes.Long()));
        return orders;
    }
}
WindowBuilderShape
TumblingTimeWindows.ofSizeAndGrace(1 min, 30 s)Fixed, non-overlapping: each record in exactly one window
HoppingTimeWindows.ofSizeWithNoGrace(5 min).advanceBy(1 min)Fixed size, overlapping: each record in several windows
SlidingSlidingWindows.ofTimeDifferenceAndGrace(10 min, 1 min)Windows defined by records within a time difference of each other
SessionSessionWindows.ofInactivityGapAndGrace(30 min, 5 min)Per key, a burst of activity closed by an inactivity gap; windows merge

Windows use event time, the record timestamp (set by the producer, or extracted from the payload with a TimestampExtractor), not the time of processing. Records arrive out of order; the grace period is how long after a window's end late records are still accepted. Stream time only advances with incoming records, and records later than the grace period are dropped and counted in a metric. Windowed aggregations emit an updated result per change (reduced by caching); suppress(Suppressed.untilWindowCloses(...)) emits only the final value when the window closes.

Joins and repartitioning

KTable<String, Customer> customers = builder.table("customers", Consumed.with(Serdes.String(), customerSerde));

KStream<String, EnrichedOrder> enriched = orders
    .selectKey((id, o) -> o.customerId())                         // co-partition with the table's key
    .join(customers, (o, c) -> new EnrichedOrder(o, c.tier()),   // stream-table: a lookup, no window
          Joined.with(Serdes.String(), orderSerde, customerSerde));

    (o, p) -> new PaidOrder(o, p),
    JoinWindows.ofTimeDifferenceAndGrace(Duration.ofMinutes(10), Duration.ofMinutes(1)),
    StreamJoined.with(Serdes.String(), orderSerde, paymentSerde));

KStream-KStream joins are windowed, because both sides are unbounded. KStream-KTable joins look up the table's current value for each stream record. KTable-KTable joins produce a table that updates when either side changes. Foreign-key joins (orderTable.join(customerTable, Order::customerId, joiner)) join tables on a value field, handled internally with subscription topics. Key-based joins require co-partitioning: same key, same partition count, same partitioner, so matching keys meet in the same task. That is why repartitioning happens: whenever you change the key (selectKey, map, groupBy) before a stateful operation or join, Streams writes the stream to an internal -repartition topic keyed the new way. It costs a network round trip and storage, so re-key once and early, and use mapValues when the key does not change.

Spring Cloud Stream

40m video45m practice

Spring Cloud Stream lets you write message handlers as plain java.util.function beans and moves every broker detail into binding configuration, so the same code can run on Kafka or RabbitMQ by swapping a binder dependency. Whether that indirection is worth it depends on how much of the broker's specific power you need.

Binders and the functional model

Definition · Binder and binding

A binder is the adapter to one broker (spring-cloud-stream-binder-kafka, -rabbit, and community or vendor binders for Kinesis and Google Pub/Sub). A binding connects one input or output of your function to a destination (a Kafka topic, a RabbitMQ exchange). Each function bean gets bindings named <function>-in-<index> and <function>-out-<index>; a Supplier is a source, a Function a processor, a Consumer a sink.

@SpringBootApplication
public class EnrichmentApp {
    public static void main(String[] args) { SpringApplication.run(EnrichmentApp.class, args); }

    @Bean Supplier<Heartbeat> heartbeat() {                // source: polled every second by default
        return () -> new Heartbeat("enricher", Instant.now());
    }

    @Bean Function<OrderPlaced, OrderValidated> validate() {
        return o -> {
            if (o.totalCents() <= 0) throw new IllegalArgumentException("empty order " + o.orderId());
            return OrderValidated.of(o);
        };
    }

    @Bean Function<OrderValidated, OrderEnriched> enrich(CustomerClient customers) {
        return v -> OrderEnriched.of(v, customers.tier(v.customerId()));
    }

    @Bean Consumer<OrderEnriched> audit() {                 // sink
        return e -> System.out.println("audit " + e.orderId());
    }
}

Function beans are discovered automatically; when there is more than one, spring.cloud.function.definition lists which to bind, separated by ;. | composes functions into one pipeline with one input and one output binding, named by concatenating the names: validate|enrich binds as validateenrich-in-0 and validateenrich-out-0. Payloads are converted by content type (JSON by default) before your function sees them.

Errors, retries and the DLQ

@ServiceActivator(inputChannel = "orders.events.enricher.errors")   // <destination>.<group>.errors

    System.err.println("gave up: " + error.getPayload().getMessage());

An exception thrown by the function is retried in-process max-attempts times with the configured backoff (a blocking retry, like L378). After that, the failure goes to the binding's error channel <destination>.<group>.errors, which is publish-subscribe: with enable-dlq the binder's DLQ handler publishes the original record to the dead-letter topic, and any @ServiceActivator subscribed to the channel receives the ErrorMessage too. The honest question

For: little boilerplate, uniform configuration across services, functions that are trivially unit-testable, and genuine portability when a platform standardizes on it. Against: another abstraction to learn and debug, broker features reached through binder-specific properties (transactions, @RetryableTopic-style non-blocking retries, Kafka Streams have their own binder or none), behaviour that differs subtly between binders, and portability that most teams never use. What breaks in production

  • Two function beans and no function.definition: nothing is bound, and no error tells you why.
  • Expecting retries and a DLQ around a reactive Function<Flux, Flux>: the first exception ends the stream.
  • Renaming a function bean: its binding names change and the configuration silently stops applying.

Event-Driven Architecture: EDA, CQRS & Event Sourcing

50m video45m practice

"Event-driven" covers several different designs: telling others that something happened, shipping them the data, or storing the events themselves as the source of truth. Each solves a different problem at a different price, and CQRS and event sourcing in particular are powerful tools that most systems should apply to a few aggregates, not everywhere.

Three things called "events"

PatternThe event carriesConsumersTrade-off
Event notificationAn id and the fact: OrderPlaced{orderId}Call back the source for detailsThin and decoupled, but callbacks recouple at runtime and add load
Event-carried state transferThe relevant state: items, totals, addressKeep a local copy; no callbacksAutonomy and resilience; data duplicated and eventually consistent
Event sourcingEvery state change of an aggregate, foreverThe owning service rebuilds state from themFull history and audit; much harder to evolve and operate

The first two are about integration between services; event sourcing is about persistence inside one service, and you can do either without the other.

Choreography vs orchestration

Choreography is loosely coupled and needs no extra component: adding a consumer touches no one else. But the business process exists only implicitly, spread across subscriptions, so "why did this order not ship?" means correlating logs across five services, and cycles appear by accident. Orchestration puts the process in one coordinator (a saga, a workflow engine): visible, testable, easy to add compensations to, at the cost of a central component that knows every participant. A common split: choreography between bounded contexts, orchestration for a multi-step process inside one.

Designing good events

public record EventEnvelope<T>(
        UUID eventId,            // unique: the consumer's dedupe key
        String eventType,        // past tense: "OrderPlaced", not "PlaceOrder"
        int schemaVersion,
        String aggregateId,      // also the Kafka key: per-aggregate ordering
        long aggregateVersion,   // position in that aggregate's history
        Instant occurredAt,      // event time, not publish time
        UUID correlationId,      // the whole business flow (e.g. one checkout)
        UUID causationId,        // the command or event that directly caused this one
        T data) {}

An event is an immutable fact in the past tense, named in the domain's language. A request for someone to do something (SendEmail) is a command, even if it travels on a topic. Give it a stable, versioned schema (L377). The correlation id is copied unchanged through every message of one flow; the causation id is the id of the message that triggered this one, which lets you reconstruct the causal tree. Thin vs fat: thin events (ids only) leak nothing but force callbacks; fat events let consumers work alone but become a public copy of your internal model that is hard to change. A good middle ground is the data a consumer needs to act on this fact, and no more.

CQRS: separate write and read models

Definition · CQRS

Command Query Responsibility Segregation uses one model to change state (normalized, enforcing invariants, usually the aggregate) and one or more different models to read it (denormalized, shaped per query, possibly in another store such as Elasticsearch or Redis). Read models are projections built by consuming the write side's events, so they are eventually consistent.

                e.data().get("totalCents").asLong(), e.aggregateVersion());
        case "OrderPaid" -> jdbc.update(
                "UPDATE order_summary SET status = 'PAID', version = ? WHERE order_id = ? AND version < ?",
                e.aggregateVersion(), e.aggregateId(), e.aggregateVersion());
        default -> { }                               // unknown types are ignored: forward compatible
    }
}

Idempotent and version-guarded, the projection can be rebuilt at any time by replaying the topic with a new group id. In the UI, eventual consistency shows up as "I saved it and it is not in the list". Tactics: return the new state from the command itself, let the client wait until the projection's version reaches the command's version, or update the UI optimistically.

Event sourcing

sealed interface OrderEvent permits OrderPlaced, ItemAdded, OrderPaid, OrderCancelled {}
record OrderPlaced(String orderId, String customerId) implements OrderEvent {}
record ItemAdded(String sku, int qty, long priceCents) implements OrderEvent {}
record OrderPaid(String paymentId) implements OrderEvent {}
record OrderCancelled(String reason) implements OrderEvent {}

final class Order {
    enum Status { NEW, PLACED, PAID, CANCELLED }
    private Status status = Status.NEW;
    private long totalCents;
    private long version;                            // events applied so far

    static Order replay(List<OrderEvent> history) {
        var order = new Order();
        history.forEach(order::apply);
        return order;
    }

    List<OrderEvent> pay(String paymentId) {        // command: decide against current state
        if (status != Status.PLACED) throw new IllegalStateException("cannot pay an order that is " + status);
        return List.of(new OrderPaid(paymentId));
    }

    void apply(OrderEvent e) {                       // evolve: never validates, never fails
        switch (e) {
            case OrderPlaced placed    -> status = Status.PLACED;
            case ItemAdded item        -> totalCents += item.qty() * item.priceCents();
            case OrderPaid paid        -> status = Status.PAID;
            case OrderCancelled cancel -> status = Status.CANCELLED;
        }
        version++;
    }
}

The event store (a table with a unique constraint on (aggregate_id, version), or a dedicated store such as EventStoreDB) is the source of truth; current state is a left fold over the events. Appending at expectedVersion + 1 gives optimistic concurrency for free. Snapshots (state plus version every N events) bound replay time. The hard parts are real: schema evolution over years (stored events are never rewritten, so old versions are upcast on read, forever); GDPR deletion in an immutable log (keep personal data out of events, or encrypt it per person and delete the key, "crypto-shredding"); debugging state that only exists as a fold; and projections that take hours to rebuild. Note that Kafka is a fine transport for events but a poor event store: it has no per-aggregate reads and no optimistic append per key.

Worth it or theatre

Worth it when the history is the domain: ledgers, payments, compliance-driven audit, "what did we know at time T" queries, or several very different read models over the same changes. Theatre when the domain is CRUD, there is one read model, nobody will ever query history, or the motivation is "flexibility". Applying it to one or two core aggregates is far more common than a fully event-sourced system, and far more likely to succeed.

Transactional Outbox & CDC with Debezium

45m video55m practice

A service cannot atomically write to its database and to Kafka, so it writes the event into its own database in the same transaction as the change, and something else moves it to Kafka afterwards. That relay, a polling publisher or Debezium reading the write-ahead log, delivers at least once, so consumers deduplicate with an inbox.

The dual-write problem, with a crash

@Transactional
public void placeOrderDualWrite(Order order) {
    orders.save(order);
    kafka.send("orders.events", order.getId().toString(), OrderPlaced.from(order));  // goes out now
    if (chaos.enabled()) Runtime.getRuntime().halt(1);   // the DB transaction never commits
}

Run it with chaos on: consumers receive OrderPlaced for an order that does not exist (a phantom event). Move the send to an after-commit hook and crash between commit and send instead: the order exists and nobody ever hears about it (a lost event). With two independent systems, some crash point always leaves them disagreeing (L379). The outbox removes the second system from the transaction.

Implementing the outbox

CREATE TABLE outbox_event (
  id             uuid        PRIMARY KEY,           -- event id: the consumers' dedupe key
  aggregate_type text        NOT NULL,              -- 'orders': selects the topic
  aggregate_id   text        NOT NULL,              -- becomes the Kafka key: per-order ordering
  event_type     text        NOT NULL,              -- 'OrderPlaced'
  payload        jsonb       NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now(),
  processed_at   timestamptz                        -- polling relay only
);
CREATE INDEX outbox_unprocessed ON outbox_event (created_at) WHERE processed_at IS NULL;
@Transactional                                           // ONE local transaction
public Order place(PlaceOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(new OutboxEvent(UUID.randomUUID(), "orders", order.getId().toString(),
                                "OrderPlaced", toJson(OrderPlaced.from(order))));
    return order;                                        // both rows commit, or neither
}

The polling publisher

@Component
class OutboxRelay {
    record Row(UUID id, String aggregateType, String aggregateId, String eventType, String payload) {}

    private final JdbcTemplate jdbc;
    private final KafkaTemplate<String, String> kafka;     // acks=all, idempotent
    OutboxRelay(JdbcTemplate jdbc, KafkaTemplate<String, String> kafka) { this.jdbc = jdbc; this.kafka = kafka; }

    @Scheduled(fixedDelay = 250)
    @Transactional
    public void publishBatch() {
        List<Row> rows = jdbc.query("""
            SELECT id, aggregate_type, aggregate_id, event_type, payload::text AS payload
            FROM outbox_event
            WHERE processed_at IS NULL
            ORDER BY created_at
            LIMIT 100
            FOR UPDATE SKIP LOCKED""",
            (rs, n) -> new Row(rs.getObject("id", UUID.class), rs.getString("aggregate_type"),
                               rs.getString("aggregate_id"), rs.getString("event_type"), rs.getString("payload")));
        if (rows.isEmpty()) return;
        var sends = rows.stream().map(r -> {
            var record = new ProducerRecord<>(r.aggregateType() + ".events", r.aggregateId(), r.payload());
            record.headers().add("event-id", r.id().toString().getBytes(StandardCharsets.UTF_8));
            record.headers().add("event-type", r.eventType().getBytes(StandardCharsets.UTF_8));
            return kafka.send(record);
        }).toList();
        CompletableFuture.allOf(sends.toArray(CompletableFuture[]::new)).join();   // all acknowledged
        jdbc.batchUpdate("UPDATE outbox_event SET processed_at = now() WHERE id = ?",
                         rows.stream().map(r -> new Object[] { r.id() }).toList());
    }
}
Definition · Polling publisher properties
  • FOR UPDATE SKIP LOCKED lets several relay instances take disjoint batches without blocking each other.
  • Delivery: if the relay crashes after Kafka acknowledged but before the update commits, the batch is sent again. At-least-once, never lost.
  • Ordering per aggregate: one relay publishes in created_at order, and the idempotent producer keeps per-key order. Two relays with SKIP LOCKED can publish two events of the same order in either order. Use a single active relay (a pg_try_advisory_lock leader), or split work by hash(aggregate_id); a bigserial sequence column orders more exactly than timestamps.
  • Latency and load: up to one poll interval of delay, and a query every interval even when idle. Updates and deletes create dead tuples, so clean up in batches (DELETE ... WHERE processed_at < now() - interval '7 days') or partition the table by day and drop old partitions.

CDC with Debezium

Debezium is a set of Kafka Connect source connectors. The PostgreSQL connector needs wal_level=logical; it creates a replication slot and a publication and decodes the write-ahead log with the built-in pgoutput plugin, emitting a change event per committed row. The MySQL connector reads the row-based binlog instead. Kafka Connect workers run the connector and store its source offsets (the log position) in an internal topic. The outbox event router SMT turns each outbox insert into a clean record: key from aggregate_id, topic from aggregate_type, value from payload, event id and type as headers.

With CDC, processed_at is unnecessary and the service may even delete each outbox row in the same transaction that inserted it: Debezium reads the insert from the WAL, and the table stays tiny. Snapshots: on first start snapshot.mode=initial (the default) reads existing rows before streaming; no_data (formerly never) streams only new changes, which is right for an outbox; when_needed re-snapshots if the stored log position is no longer available; initial_only snapshots and stops.

Replication slots fill disks

PostgreSQL keeps every WAL segment a slot has not confirmed. If the connector stops (a crash, a paused Connect cluster, a deleted connector that left its slot behind), WAL piles up until the database's disk is full and the primary goes down. Watch retained WAL per slot, cap it with max_slot_wal_keep_size (PostgreSQL 13+, at the price of invalidating the slot), drop slots you no longer use, and use heartbeat.interval.ms so the slot advances even when the outbox is quiet but other tables are busy.

SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS retained_wal
FROM pg_replication_slots;

At-least-once, the inbox, and the embedded engine

CDC is at-least-once: after a connector restart it resumes from its last committed offset and re-emits what came after. Recent Debezium versions can use Kafka Connect's exactly-once source support (KIP-618) for some connectors, but design consumers for duplicates regardless. The inbox pattern is the consumer half of the outbox: record each incoming event id in an inbox table (primary key on the id) in the same transaction as the effect, and skip ids already present (L369, L378).

Order service: writes the order and an OrderPlaced outbox row in one local transaction (L383), and stores the current W3C traceparent in an outbox column so tracing survives the CDC hop. Relay: the Debezium connector with the outbox event router, keyed by order id; a polling relay is the acceptable fallback.

@KafkaListener(topics = "orders.events", groupId = "inventory")
@Transactional                                              // inbox, stock and outbox in ONE DB transaction
public void onOrderPlaced(OrderPlaced e) {
    if (!inbox.firstTime(e.getEventId())) return;          // INSERT ... ON CONFLICT DO NOTHING
    boolean reserved = stock.tryReserve(e.getOrderId(), e.getItems());   // UPDATE ... WHERE available >= qty
    outbox.save(reserved
        ? OutboxEvent.of("inventory.reserved", e.getOrderId(), "InventoryReserved", reservedPayload(e))
        : OutboxEvent.of("inventory.rejected", e.getOrderId(), "InventoryRejected", rejectedPayload(e)));
}

Inventory is the model consumer: deduplicate, apply, and emit the result through its own outbox, all in one database transaction, so a redelivered OrderPlaced can neither reserve twice nor lose its reply. Payment consumes inventory.reserved with @RetryableTopic (L378): gateway timeouts and 5xx are retryable with exponential backoff; declined cards and invalid requests are excluded and go straight to the DLT; the @DltHandler increments a metric and opens an incident. The gateway call carries the order id as its idempotency key, because a retry topic is at-least-once too. Non-blocking retry is acceptable here because there is one charge per order and nothing behind it depends on its order.

The guarantee, stated precisely

Theorem · Effectively-once effects

If (1) the order and its outbox row commit atomically, (2) every relay and retry path delivers at least once, and (3) every consumer applies its effect and records the event id in one transaction (or calls an idempotent external API keyed by a business id), then every accepted order's side effects occur exactly once, while individual messages may be delivered more than once. Kafka EOS (L379) additionally makes the streams job's counts exact inside Kafka; it is not what makes the database effects exact.

Contracts, observability, and proof

  • Schemas: Avro for every topic, registered from CI, FULL_TRANSITIVE on orders.events, auto.register.schemas=false in services, and a pipeline step that fails on an incompatible change (L377).
  • Lag: Spring Kafka binds the clients' metrics to Micrometer, including kafka.consumer.fetch.manager.records.lag.max per consumer; alert on lag that keeps growing, per group.
  • DLT: a counter incremented in each @DltHandler, plus an alert on any DLT whose end offset moves.
  • Tracing: spring.kafka.template.observation-enabled and spring.kafka.listener.observation-enabled propagate trace context in record headers on every hop you produce; the outbox's traceparent column, placed as a header by the router, bridges the CDC hop. One checkout should appear as one trace across all services.
