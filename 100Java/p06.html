JVM Internals, GC & Performance

Phase 6 opens up the JVM that has been running your code since Phase 1, covering how classes load, how objects are laid out in memory, how bytecode becomes machine code, and how the garbage collectors reclaim it. It builds on the concurrency model of Phase 5 (threads, safepoints, locks) and gives you the diagnostic skills that the Spring and production phases later depend on. Every lesson ends with something you can measure on a running process: a log, a dump, a recording or a benchmark.

By the end of this phase you can

  • Trace a class from .class file through loading, linking and initialization, and diagnose class-loader leaks and OutOfMemoryError: Metaspace.
  • Predict an object's size from its header, fields and padding, check it with JOL, and explain the cost of boxing and the 32 GB compressed-oops cliff.
  • Read javap output and -XX:+PrintCompilation logs, and explain inlining, escape analysis and deoptimization in terms of tiered compilation.
  • Choose between Serial, Parallel, G1, ZGC and Shenandoah for a given heap, pause goal and CPU budget, and justify the choice from a GC log.
  • Size a JVM inside a container so that heap plus native memory stays under the pod limit, using MaxRAMPercentage and Native Memory Tracking.
  • Find a memory leak with a heap dump and MAT, and a hotspot with JFR and async-profiler flame graphs.
  • Write a JMH benchmark that reports an honest score with its error, and work through a "service is slow" runbook with jcmd, jstack and jstat.

L153 · DAY 153

JVM Architecture End To End

45m video30m practice

A JVM is three cooperating subsystems: a class loader that turns bytes into classes, runtime data areas that hold everything the program owns, and an execution engine that runs bytecode and reclaims memory. Every topic in this phase is a zoom into one box of that picture, and every tuning decision starts with knowing which flags the JVM actually chose for you.

The three subsystems

Definition
  • Class loader subsystem. Finds class bytes (a jar, the module image, the network), then loads, links (verify, prepare, resolve) and initializes each class. L154–L155.
  • Runtime data areas. Per thread: a PC register, a JVM stack of frames and a native stack. Shared: the heap, the method area (Metaspace in HotSpot) and the code cache. L156–L157.
  • Execution engine. An interpreter, two JIT compilers (C1 and C2) that turn hot bytecode into machine code, and the garbage collector. It reaches native libraries through JNI or the FFM API. L158–L164, L170.

HotSpot, OpenJ9, GraalVM, Azul Prime

The JVM is a specification (JVMS); several implementations exist. The vendor name on your JDK download (Temurin, Corretto, Zulu, the Microsoft Build of OpenJDK, Oracle JDK) is almost always HotSpot underneath. Only the VM column below changes behaviour.

Startup, step by step

Algorithm · what happens on java -jar app.jar
  1. The java launcher parses the command line and the JDK_JAVA_OPTIONS environment variable, finds libjvm (jvm.dll on Windows) and calls JNI_CreateJavaVM on a fresh thread. The VM itself also reads JAVA_TOOL_OPTIONS.
  2. The VM parses its options, then runs ergonomics: picks a collector, heap sizes and thread counts from the CPUs and memory it can see.
  3. It reserves the heap address range, maps the CDS archive (pre-parsed JDK classes, on by default since JDK 12) and creates Metaspace and the code cache.
  4. The bootstrap loader loads core classes (Object, String, Class, Thread…). The JVM creates the main thread object and runs System.initPhase1..3, which sets up properties, the module system and the system class loader.
  5. Service threads start: VM thread, GC workers, JIT compiler threads, Reference Handler, Finalizer, Signal Dispatcher, Common-Cleaner.
  6. The launcher loads the main class through the application loader, checks for main, and invokes it. When main returns, DestroyJavaVM waits for every non-daemon thread, then runs shutdown hooks.

Flag categories

  • Standard options work on every JVM: -cp, -jar, --module-path, -version.
  • -D sets a system property for the program (-Dspring.profiles.active=prod, read with System.getProperty). It never tunes the VM.
  • -X options are non-standard but stable: -Xmx, -Xms, -Xss, -Xlog, -Xint.
  • -XX options are HotSpot internals. Booleans read -XX:+UseG1GC / -XX:-UseG1GC; values read -XX:MaxGCPauseMillis=100.

Inside -XX there are tiers. Product flags are supported. Diagnostic flags need -XX:+UnlockDiagnosticVMOptions first (e.g. PrintInlining). Experimental flags need -XX:+UnlockExperimentalVMOptions (e.g. UseEpsilonGC, G1NewSizePercent). Manageable flags can be changed on a running VM with jinfo (L169). Develop flags exist only in debug builds. When a flag appears twice, the last occurrence wins.

Ergonomics and default heap sizing

If you set nothing, HotSpot sizes itself. On a "server-class" machine (at least 2 CPUs and about 2 GB of memory) it picks G1, which has been the default since JDK 9. On anything smaller it picks Serial. The default maximum heap is MaxRAMPercentage = 25% of the memory the JVM can see; the initial heap is InitialRAMPercentage = 1/64. On very small machines (below roughly 250 MB) MinRAMPercentage = 50% applies instead. On Linux, "memory it can see" is the container limit, not the host (L165). On a laptop with 32 GB this gives a 7.9 GB maximum heap; in a 1 GiB pod it gives 256 MB. That is why a default-sized service behaves differently in each place.

What breaks in production
  • Flags that outlive their JDK. A flag that has been removed is first obsolete (the VM warns and ignores it), then expired (the VM refuses to start with "Unrecognized VM option"). Upgrading the JDK with an old JAVA_OPTS left in place can therefore stop a service from starting, or quietly drop a setting such as -XX:+UseConcMarkSweepGC on JDK 14+.
  • JAVA_TOOL_OPTIONS applies to every JVM. Set it in a container image and Maven, your health-check tool and the app all get the same -Xmx. Each prints "Picked up JAVA_TOOL_OPTIONS".
  • Trusting laptop defaults. Ergonomics on 1 CPU picks Serial GC and a small heap. Pin the collector and heap percentage explicitly in production images.
  • Runtime.maxMemory() is not -Xmx. Under Serial and Parallel it leaves out one survivor space, so it reads lower than the flag.

Class Loading: Loading, Linking, Initialization

45m video40m practice

A class becomes usable in three phases: loading creates it from bytes, linking checks it and lays out its statics, and initialization runs its static code exactly once. Initialization is lazy and happens only on a short list of triggers, which explains both "why did my static block run now?" and the error pair everyone confuses.

Loading

A class loader (L155) finds the bytes for a binary name such as com.acme.Order, and the JVM parses them: magic number 0xCAFEBABE, class-file version (65 for Java 21), constant pool, fields, methods, attributes. A malformed file fails here with ClassFormatError, and a file compiled for a newer Java fails with UnsupportedClassVersionError (on JDK 17: "…compiled by a more recent version of the Java Runtime (class file version 65.0), this version of the Java Runtime only recognizes class file versions up to 61.0"). The result is a java.lang.Class object in the heap and the class's metadata in Metaspace. Its superclass and interfaces are loaded first.

Linking: verify, prepare, resolve

Definition · what the verifier checks (JVMS §4.10)
  • Every instruction gets operands of the right type: no iadd on two references, no treating an int as an object reference.
  • The operand stack never underflows and never exceeds the declared max_stack; locals stay within max_locals.
  • Branch targets land on instruction boundaries inside the method; exception handlers cover valid ranges.
  • An object created with new is not used until its constructor (invokespecial <init>) has run.
  • Methods are called with arguments that match their descriptors; final classes are not subclassed and final methods are not overridden; protected access rules hold.

It does not check null dereferences or array bounds; those are runtime checks. Since class-file version 50 the verifier reads a StackMapTable attribute (L158) so it can type-check in one linear pass.

Preparation allocates the static fields and sets each one to its default value: 0, false, null. No user code runs. Resolution turns symbolic references in the constant pool ("method Inventory.count:()J") into direct references to runtime structures. It can fail with NoSuchMethodError, NoSuchFieldError, IllegalAccessError or IncompatibleClassChangeError, all subclasses of LinkageError, which is what version skew between jars looks like at runtime (L174).

Initialization and the <clinit> guarantee

javac collects every static field initializer and every static { } block, in textual order, into one synthetic method named <clinit>. Before running it, the JVM sets any static final field that has a ConstantValue attribute, meaning a compile-time constant. Then it runs <clinit> under a per-class initialization lock (JVMS §5.5):

  • If another thread is initializing the class, the caller blocks until it finishes. <clinit> therefore runs once, and every thread sees its writes. The lazy holder idiom (private static class Holder { static final Foo INSTANCE = new Foo(); }) gets thread-safe lazy initialization for free (Effective Java Item 83).
  • If the same thread re-enters, for instance through a circular static reference, it proceeds immediately and sees default values. This is how a static field can read as null "after" it was assigned.
  • If <clinit> throws, the class is marked erroneous for good. The first caller gets ExceptionInInitializerError; every later use gets NoClassDefFoundError: Could not initialize class X.

public class InitOrder {
    static class Parent {
        static { System.out.println("Parent <clinit>"); }
        static int counter = 1;
    }
    static class Child extends Parent {
        static { System.out.println("Child <clinit>"); }
        static final String CONST = "compile-time constant";
        static final Object NOT_CONST = new Object();
    }
    public static void main(String[] args) throws Exception {
        System.out.println(Child.CONST);                  // inlined: nothing initialized
        Child[] none = new Child[3];                      // arrays don't initialize
        Class<?> c = Child.class;                         // neither does a class literal
        Class.forName("InitOrder$Child", false, InitOrder.class.getClassLoader());
        System.out.println(Child.counter);                // declared in Parent: Parent only
        System.out.println(Child.NOT_CONST != null);      // now Child initializes
    }
}
// Output (JDK 21): compile-time constant / Parent <clinit> / 1 / Child <clinit> / true

The two often appear together: an NCDFE whose cause is a CNFE means resolution asked a loader, and the loader didn't find the class. An NCDFE that says "Could not initialize class" means the class was found, but its static initializer failed earlier. Search the log for the first ExceptionInInitializerError; newer JDKs also attach it as the cause.

What breaks in production
  • A poisoned class. static final int PORT = Integer.parseInt(System.getenv("PORT")); throws once at first use, then every request fails with NCDFE until the process restarts. Keep static initializers trivial, or move fallible setup into an explicit init() that can be retried.
  • Class-initialization deadlock. Thread 1 initializes A, whose <clinit> touches B; thread 2 initializes B, which touches A. Both wait forever, and a thread dump shows threads waiting in <clinit> with no lock owner you can find in Java code.
  • Stale inlined constants. Change public static final int LIMIT in a library and ship it. Callers compiled against the old jar keep the old value until they are recompiled (JLS §13.4.9).
  • Turning off verification. -Xverify:none and -noverify have been deprecated since JDK 13. Startup gains are small, and a broken bytecode generator can then crash the VM instead of throwing VerifyError.

ClassLoaders, Delegation & Custom Loaders

40m video40m practice

At runtime a class is identified by its name and the loader that defined it. Parent delegation keeps core classes unique; containers deliberately break delegation to isolate applications; and almost every confusing class-loading bug comes from two loaders holding "the same" class.

The loader hierarchy (JDK 9+)

  • Bootstrap loader: part of the VM, written in C++. Loads java.base and other core modules from the runtime image. In Java it appears as null: String.class.getClassLoader() == null.
  • Platform loader (ClassLoader.getPlatformClassLoader()): the remaining Java SE and JDK modules such as java.sql. It replaced JDK 8's extension loader and its jre/lib/ext directory.
  • Application (system) loader (ClassLoader.getSystemClassLoader()): your class path and module path. Since JDK 9 it is no longer a URLClassLoader.

Parent delegation, and why it protects java.lang.String

Algorithm · ClassLoader.loadClass(name)
  1. findLoadedClass(name): return it if this loader already defined (or was recorded as initiating) this name.
  2. Ask the parent: parent.loadClass(name), recursively up to bootstrap.
  3. Only if the parent throws ClassNotFoundException, call this loader's own findClass(name).

Because the request always travels up first, a java/lang/String.class on your class path is never consulted: bootstrap answers first. As a second line of defence, defineClass refuses any name in a java.* package with SecurityException: Prohibited package name. Core types therefore stay unique, which matters because String, Object and Class appear in the signatures of everything. In JDK 9+ the built-in loaders also delegate by module: a class in a package that belongs to a named module goes straight to that module's loader.

Breaking delegation on purpose

  • Servlet containers. Tomcat gives each WAR a WebappClassLoader that looks in WEB-INF/classes and WEB-INF/lib before its parent ("child-first"), but still delegates java.* and the Servlet API upward. Applications can then carry conflicting library versions.
  • OSGi. Every bundle has its own loader, and loading follows declared Import-Package/Export-Package wiring: a graph, not a tree. Several versions of one package can coexist.
  • Spring Boot executable jars. The JVM's application loader sees only the Boot loader classes. JarLauncher creates a loader over BOOT-INF/classes and the nested jars in BOOT-INF/lib (LaunchedURLClassLoader up to Boot 3.1; Boot 3.2 rewrote it as org.springframework.boot.loader.launch.LaunchedClassLoader). It delegates parent-first, but your classes now live one level below the system loader. Code that calls ClassLoader.getSystemClassLoader() to find application classes breaks.

The context class loader and the SPI problem

A service API often lives high in the tree while its implementations live low. java.sql.DriverManager is loaded by the platform loader; the PostgreSQL driver is on your class path; JAXP, JNDI and ServiceLoader have the same shape. A parent cannot see its children's classes, so these frameworks look up implementations through Thread.currentThread().getContextClassLoader() (the TCCL). The TCCL is a per-thread back door the caller sets, normally to the application or web-app loader. ServiceLoader.load(Class) uses it. New threads inherit their creator's TCCL. When a framework runs your code on a thread it created earlier, from another context, the lookup fails with "No suitable driver" or a missing provider. The fix is to pass the loader explicitly (ServiceLoader.load(type, loader)), or to set and restore the TCCL around the call.

A custom loader, and identity = (name, loader)

Override findClass, not loadClass, and you keep delegation. Below, two loaders define the same bytes. Their parent is the platform loader, which cannot see the class path, so each one defines its own copy:

import java.util.Map;
import java.util.function.Supplier;

public class Isolation {
    public static class Greeter implements Supplier<String> {
        public String get() { return "hello from " + getClass().getClassLoader().getName(); }
    }

    static final class BytesLoader extends ClassLoader {
        private final Map<String, byte[]> classes;
        BytesLoader(String name, Map<String, byte[]> classes) {
            super(name, ClassLoader.getPlatformClassLoader());   // parent cannot see the class path
            this.classes = classes;
        }
        @Override protected Class<?> findClass(String name) throws ClassNotFoundException {
            byte[] b = classes.get(name);
            if (b == null) throw new ClassNotFoundException(name);
            return defineClass(name, b, 0, b.length);
        }
    }

    public static void main(String[] args) throws Exception {
        String name = Greeter.class.getName();                    // "Isolation$Greeter"
        byte[] bytes;
        try (var in = Isolation.class.getResourceAsStream("Isolation$Greeter.class")) {
            bytes = in.readAllBytes();
        }
        Class<?> a = new BytesLoader("a", Map.of(name, bytes)).loadClass(name);
        Class<?> b = new BytesLoader("b", Map.of(name, bytes)).loadClass(name);
        System.out.println(a.getName().equals(b.getName()) + " " + (a == b));   // true false
        Object g = a.getDeclaredConstructor().newInstance();
        System.out.println(((Supplier<?>) g).get());               // "hello from a": Supplier is shared
        Greeter direct = (Greeter) g;                              // ClassCastException
    }
}
java.lang.ClassCastException: class Isolation$Greeter cannot be cast to class Isolation$Greeter
  (Isolation$Greeter is in unnamed module of loader 'a' @5caf905d;
   Isolation$Greeter is in unnamed module of loader 'app')

The cast to Supplier works because Supplier came from bootstrap for both sides. Shared interfaces loaded high in the tree are how plugin systems talk across loaders. The cast to Greeter fails because the two Greeters are different types. Packages work the same way: a runtime package is (package name, loader), so package-private access does not cross loaders either.

LinkageError, jar hell, shading, hot reload

Jar hell is two versions of a library on one flat class path. The application loader takes each class from the first jar that has it, so you can end up with classes from both versions mixed together. Loader-level conflicts surface as LinkageError: loader constraint violation: two loaders that must agree on a type in a method signature resolved it differently. Shading (L176) copies a dependency into your jar and rewrites its package (com.google.common → com.acme.shaded.guava), so your copy cannot collide with anyone else's.

Hot reloading is hard because a loader can define a name only once. Reloading means creating a new loader, defining fresh classes, migrating state, and dropping every reference to the old instances and classes. If anything keeps a reference (a static cache, a ThreadLocal, a JDBC driver registration), the old loader and all its classes stay in Metaspace (L166). JVMTI RedefineClasses, which the IDE debugger uses for HotSwap, only allows method bodies to change. Spring Boot DevTools uses two loaders: a base loader for jars that don't change and a restart loader for your classes, which it throws away on each change.

What breaks in production
  • (URLClassLoader) ClassLoader.getSystemClassLoader(): old JDK 8 code that adds jars at runtime this way throws ClassCastException on JDK 9+.
  • "X cannot be cast to X" under DevTools: an object created by the restart loader, cached, and read back after a restart by code in the new loader. Exclude the cache from DevTools' restart, or serialize the object instead of caching the instance.
  • TCCL in pools. ServiceLoader or JAXB lookups that work in a test but fail in a parallelStream() or a library-owned executor whose threads carry a different TCCL.
  • Metaspace that grows with every redeploy. A leaked loader (L166). The heap dump shows several instances of the same web-app loader.

Runtime Data Areas: Heap, Stacks, Metaspace, Code Cache

45m video35m practice

Every byte a Java process uses lives in one of a few areas: per-thread stacks, the shared heap, Metaspace, and the code cache. Each has its own size flag and its own failure message, so when the JVM runs out of memory, the error text tells you which area to look at.

Per-thread areas

Definition · JVM stack frame (JVMS §2.6)

Each thread has a PC register (the bytecode index it is executing; undefined in native code) and a JVM stack of frames, one per active method call. A frame holds:

  • the local variable array: slot 0 is this for instance methods, then the parameters, then locals; long and double take two slots;
  • the operand stack, where bytecode pushes and pops intermediate values (L158);
  • frame data: a link to the class's runtime constant pool, the return address, and what the JVM needs to unwind for exceptions.

The native method stack serves JNI calls. HotSpot uses one OS thread stack for both Java and native frames, sized by -Xss (typically 1 MB on 64-bit platforms). JIT-compiled frames live on the same stack, laid out by the compiler instead of the interpreter.

Shared areas

  • Heap: every object and array, and the only area the GC compacts. Since JDK 7 the interned-string table points into the heap (it was in PermGen before), and static fields live inside the java.lang.Class mirror object, also on the heap.
  • Metaspace (JDK 8+, replacing PermGen): class metadata, method bytecode, runtime constant pools, annotations. It is native memory and grows as classes load. Class pointers go into a separate compressed class space (default 1 GB reserved).
  • Code cache: machine code from the JIT, plus interpreter templates and stubs. Since JDK 9 it is segmented into non-method, profiled and non-profiled parts (L159).

Young and old generations

New objects go into eden. A minor GC copies the survivors of eden and the active survivor space into the other survivor space, so S0 and S1 swap roles every collection, and one is always empty. Objects that survive enough collections (the tenuring threshold, up to 15) are promoted to the old generation. Defaults for Serial and Parallel: NewRatio=2 (old is twice young) and SurvivorRatio=8 (eden is eight times each survivor). L161–L162 explain why this split pays off.

TLABs: why allocation is a pointer bump

If every thread allocated from one shared eden pointer, each new would need an atomic operation. HotSpot instead hands each thread a thread-local allocation buffer, a private chunk of eden. Allocating inside it is: obj = top; top += size; if (top > end) slowPath();, then write the header and zero the fields. The slow path retires the TLAB and takes a new one with a single CAS on the shared eden pointer. Very large objects skip the TLAB. The result is that allocating a short-lived object costs a handful of instructions. Allocation rate still matters, because it decides how often minor GCs run, but a single allocation is cheap.

Object Memory Layout, Headers & Compressed Oops

40m video35m practice

A Java object is a header plus its fields, padded to 8 bytes, and on most heaps every reference is a 4-byte compressed pointer. Once you can add these numbers up you can predict what a data structure really costs, and you can see why boxing, small strings and a 32 GB heap all cost more than they look.

The object header

Definition · Header (64-bit HotSpot, JDK 21)

Every object starts with two header words:

  • the mark word (8 bytes): for an unlocked object it holds the identity hash (31 bits, written lazily the first time System.identityHashCode or the default hashCode() runs), the GC age (4 bits, so a tenuring threshold can never exceed 15) and 2 lock bits. When the object is locked or being moved by the GC, the mark word is replaced by a pointer to a lock record, an inflated monitor, or a forwarding address;
  • the klass pointer: a reference to the class's metadata in Metaspace. It is 4 bytes with compressed class pointers (the default) and 8 bytes without.

So the header is 12 bytes on a default JVM. Arrays add a 4-byte length field, which gives a 16-byte array header. JDK 24 added compact object headers as an experimental option (JEP 450), and JDK 25 made it a product flag (JEP 519, -XX:+UseCompactObjectHeaders, off by default). It folds the class pointer into the mark word, so the header is 8 bytes.

The lock bits read 01 for unlocked, 00 for a thin (stack or lightweight) lock, 10 for an inflated monitor and 11 while the GC is marking. Biased locking used one more bit. It was deprecated in JDK 15 and removed in JDK 18, so in JDK 21 that bit is unused.

Fields: reordering, alignment and padding

HotSpot does not lay fields out in source order. It places the largest primitives first, puts smaller fields into the gaps (including the 4-byte gap right after a 12-byte header), and keeps references together so the GC can scan them as one block. Superclass fields come before subclass fields. JDK 15 rewrote this algorithm (JDK-8237767) so that subclass fields can also fill holes the superclass left. Every object is then padded to -XX:ObjectAlignmentInBytes, which defaults to 8.

Worked example

class C { byte a; long b; byte c; long d; }. In source order: header 12, a at 12, pad to 16, b 16–23, c at 24, pad to 32, d 32–39, which is 40 bytes. HotSpot puts b at 16 and d at 24 and drops both bytes into the header gap at 12 and 13: 32 bytes. For a million instances that is 8 MB saved without changing any code.

Compressed oops and the 32 GB cliff

An oop ("ordinary object pointer") is a reference. Objects are 8-byte aligned, so the low 3 bits of every address are zero. HotSpot stores a reference as a 32-bit value and decodes it as base + (narrow << 3). That reaches 2³² × 8 = 32 GB. The JVM picks a mode from the maximum heap size: unscaled (heap below 4 GB, no shift), zero-based (below 32 GB, shift only), or heap-based (non-zero base, shift plus add).

$ java -Xmx31g -XX:+PrintFlagsFinal -version | grep UseCompressedOops
     bool UseCompressedOops                        = true     {product lp64_product} {ergonomic}
$ java -Xmx32g -XX:+PrintFlagsFinal -version | grep UseCompressedOops
     bool UseCompressedOops                        = false    {product lp64_product} {default}

Above the limit every reference field and every reference-array slot doubles from 4 to 8 bytes. The klass pointer stays at 4 bytes: since JDK 15, compressed class pointers no longer depend on compressed oops. A reference-heavy heap (maps, lists, object graphs) can grow by roughly a fifth to a half, so a 32 GB heap may hold less live data than a 31 GB one. The rule: stay below about 31 GB, or go well past it (48 GB and up) so the extra space pays for the bigger pointers. -XX:ObjectAlignmentInBytes=16 stretches compressed oops to 64 GB, but it adds more padding to every object.

Cache lines, false sharing and lean data structures

The CPU moves memory in cache lines, 64 bytes on x86 and most ARM cores. If two threads write two different fields on the same line, each write invalidates the other core's copy, and the line bounces between cores. This is false sharing: no data is shared, but throughput can collapse. The JDK avoids it in LongAdder cells and Thread fields with @jdk.internal.vm.annotation.Contended, which pads a field onto its own line. Application code can use it only with --add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED and -XX:-RestrictContended. Padding with dummy long fields in the same class is unreliable, because the JVM may reorder them. Padding through a superclass chain works, since superclass fields always come first.

For memory-efficient design: use primitive arrays rather than boxed collections, and parallel arrays (one array per field) rather than millions of small objects. Prefer EnumMap, BitSet and right-sized ArrayLists. Share repeated immutable values. Remember that a record costs exactly what the equivalent final class costs. Project Valhalla's value classes are meant to remove the header and the indirection, but they are not in JDK 21.

What breaks in production
  • Moving from -Xmx30g to -Xmx32g. Compressed oops switch off, live data grows, and GC runs more often than before. Check VM.current().details() or -XX:+PrintFlagsFinal on every heap-size change.
  • Boxed collections on hot paths. Map<Long, Long> with ten million entries costs several hundred MB in node, key and value objects. Primitive collections (Eclipse Collections, fastutil) or plain arrays use a fraction of that.
  • Estimating size from field types alone. Headers, padding and the backing arrays are often more than half the total. Measure with JOL or a heap-dump histogram (L166) before you size a cache.
  • Hot counters side by side. A per-thread statistics array (long[] hits, one slot per thread) can run slower with more threads because every slot sits on the same cache line. Use LongAdder.

Bytecode & javap

45m video45m practice

javac turns Java into instructions for a simple stack machine, and javap prints them. Reading that output answers questions about boxing, lambdas, string concatenation and dispatch that are otherwise argued from memory.

A stack machine with typed instructions

Definition · Stack machine

The JVM has no general-purpose registers. Each frame (L156) has a local-variable array and an operand stack. Instructions push values onto the stack, pop their inputs and push the result.

The opcode prefix gives the type: i int, l long, f float, d double, a reference, and b c s for byte, char and short array access. So iload_1 pushes int local 1, astore_2 pops a reference into local 2, iadd pops two ints and pushes their sum, and iinc 2, 1 adds 1 to local 2 without using the stack. Branches compare and jump (if_icmpge, ifnull, goto), and every method ends in one of ireturn lreturn freturn dreturn areturn return.

Desugaring you can see

  • Autoboxing: t += x with Integer x shows up as invokevirtual Integer.intValue, and returning an int as Integer as invokestatic Integer.valueOf. Each boxing site is a possible allocation (L157).
  • Enhanced for over a List: invokeinterface List.iterator, then a hasNext/next loop with a checkcast. Over an array it is the indexed loop above, with no iterator.
  • String switch: hashCode(), a lookupswitch on the hash, equals() to rule out collisions, then a second switch on a temporary index (the iconst_m1; istore_2 at the top).
  • Try-with-resources: close() on the normal path, plus a handler for Throwable that calls close(), then addSuppressed if close also throws, then rethrows. In javap that is two close calls, one addSuppressed and an exception-table entry.

StackMapTable and why bytecode settles arguments

Since class-file version 50 (Java 6), and mandatorily since version 51 (Java 7), each method carries a StackMapTable. It records the types of the locals and the stack at every branch target, so the verifier checks a method in one linear pass instead of inferring types. For sum it has two frames: offset 4 (the loop head) appends [int, int] for s and i, and offset 22 drops i again. Hand-written bytecode (ASM, ByteBuddy) without correct frames fails with VerifyError: Expecting a stackmap frame at branch target, which is why ASM offers COMPUTE_FRAMES.

Bytecode answers "does this allocate?", "which overload runs?", "is this call virtual?" with evidence. It does not show what the JIT later does (L159–L160). A boxing call in bytecode may be removed by escape analysis, so use bytecode to understand the code and a profiler or JMH to measure it.

Interview trap
  • "Concatenation in a loop is fine now, it's invokedynamic." Each s += x still builds a new String and copies all of s, so the loop is still quadratic. Use one StringBuilder outside the loop.
  • "Lambdas allocate on every call." On current JDKs a non-capturing lambda's call site returns one cached instance. A capturing lambda creates a new object on each evaluation unless escape analysis removes it. The JLS allows either behaviour, so don't rely on identity.
  • "Private methods use invokespecial." That was true until JDK 10. From JDK 11, javac emits invokevirtual (or invokeinterface in interfaces) for private instance methods, and nestmates can call each other's private members without synthetic accessors.

JIT Compilation: Interpreter, C1, C2 & Tiered

45m video35m practice

HotSpot starts every method in an interpreter, counts how often it runs, and compiles the hot ones twice: first quickly with C1 while collecting a profile, then aggressively with C2 using that profile. Warmup, OSR and code-cache trouble all follow from this pipeline.

Interpret, JIT or compile ahead of time

  • Interpreter: HotSpot's template interpreter runs bytecode directly (L158), with no compile cost but at perhaps 10 to 50 times slower than compiled code. It also does the profiling.
  • JIT: compiles hot methods to machine code at run time. It can use what it has seen (receiver types, branch frequencies, values that never change) and speculate on them, with a way back if the guess turns out wrong (L160).
  • AOT: compiles before the program runs. GraalVM native-image produces a standalone binary with fast startup but only static knowledge (L170). The experimental jaotc (JDK 9) was removed in JDK 17. Project Leyden is taking another route: JDK 24 caches loaded and linked classes (JEP 483), and JDK 25 adds cached method profiles (JEP 515). Both shorten warmup without giving up the JIT.

Counters, thresholds and the five tiers

Each method has an invocation counter, incremented on entry, and a back-edge counter, incremented each time a loop jumps backwards. When the counters cross a threshold, the method is queued for compilation on a background compiler thread, and the caller keeps interpreting until the compiled code is installed.

Definition · Tiered compilation levels
  • Level 0: interpreter, gathering a profile.
  • Level 1: C1, full optimization, no profiling. Used for trivial methods such as getters, where a profile would teach C2 nothing.
  • Level 2: C1 with invocation and back-edge counters only.
  • Level 3: C1 with full profiling: receiver types at each call, branch counts, and types at casts and instanceof. This code runs perhaps 30% slower than level 2 because of the profiling.
  • Level 4: C2, built from the level-3 profile.

The JDK 21 defaults (from -XX:+PrintFlagsFinal): level 3 after roughly 200 invocations (Tier3InvocationThreshold), or 2,000 invocations plus back-edges, or 60,000 back-edges. Level 4 after roughly 5,000 invocations, or 15,000 invocations plus back-edges, or 40,000 back-edges. The JVM scales these thresholds up when the compile queues are long. With -XX:-TieredCompilation, C2 alone compiles after CompileThreshold=10000 calls, which is where the old "first 10,000 requests" rule comes from.

On-stack replacement

A method that is called once but loops for minutes (main, a batch job) never reaches an invocation threshold. When its back-edge counter overflows, the JVM compiles a special version with an entry point at the loop header, and the running interpreter frame is moved into compiled code mid-loop. This is on-stack replacement. PrintCompilation marks OSR compiles with % and the bytecode index of the loop:

    public static void main(String[] args) {
        long total = 0;
        for (int i = 0; i < 50_000_000; i++) total += square(i);
        System.out.println(total);
    }
}

The code cache, warmup and the tools

Compiled code lives in the code cache (L156): 240 MB reserved by default with tiered compilation, split since JDK 9 into non-method (about 5.6 MB), profiled and non-profiled segments. If it fills, the VM logs CodeCache is full. Compiler has been disabled. and newly hot code stays interpreted. Throughput falls with no exception and no crash. Check with jcmd <pid> Compiler.codecache and raise -XX:ReservedCodeCacheSize if a large application gets close.

Warmup is why a freshly started service is slow for its first thousands of requests. Classes load and link, methods run interpreted and then at level 3 with profiling overhead, the compiler threads compete with request threads for CPU, and caches and pools are still cold. Ways to reduce it: send synthetic traffic before the instance joins the load balancer, use CDS archives, use the Leyden caches on JDK 24+, or use a native image.

What breaks in production
  • Latency spikes after every deploy. New pods take full traffic while still interpreting. Add a warmup phase to readiness checks, or ramp traffic up gradually.
  • A one-CPU container. With one CPU the JVM may start very few compiler threads, and they share the core with the application. Warmup can take minutes. Give pods at least 2 CPUs, or a CPU limit that allows short bursts.
  • Silent code-cache exhaustion in huge Spring or app-server deployments, often after months of uptime. Alert on the code cache's used/max ratio.
  • -Xint or -XX:TieredStopAtLevel=1 left in a startup script. They are fine for a quick local tool and terrible for a server.

JIT Optimizations: Inlining, Escape Analysis & Deopt

40m video35m practice

Inlining is the optimization that makes the others possible. Once a callee's body is pasted into the caller, C2 can see that an object never escapes, that a lock is never shared, that a branch is never taken. It compiles on the bet that the profile stays true, and deoptimizes when it doesn't.

Inlining and why small methods are free

A call costs a jump, a frame and a return. Worse, it hides the callee's body from the optimizer. C2 inlines a callee when:

  • its bytecode is at most MaxInlineSize (35 bytes), whatever its frequency. Getters, setters and small helpers are always inlined, so splitting code into small methods costs nothing;
  • or the call site is hot and the callee is at most FreqInlineSize (325 bytes on x86-64, JDK 21);
  • and the inlining depth stays within MaxInlineLevel (15 since JDK 14, 9 before), and the callee is not already compiled to more than InlineSmallCode (2,500 bytes of machine code).

-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining prints each decision: inline (hot), too big, hot method too big, already compiled into a big method. Methods over 8,000 bytes of bytecode (HugeMethodLimit) are never compiled at all, which is a trap for generated code.

Call-site shapes and inline caches

A virtual call can be inlined only if C2 knows which method it will reach. The level-3 profile (L159) records up to two receiver classes per call site (TypeProfileWidth=2). Class hierarchy analysis helps too: if only one loaded class implements a method, the call is devirtualized with no guard, and the code is deoptimized if a second implementation is loaded later.

Below the compiler, call sites also use inline caches. A monomorphic site's stub compares the receiver's class with the one it saw last and jumps straight to the target. On a miss it is patched into a megamorphic vtable or itable stub.

Escape analysis: allocation that disappears

Definition · Escape states

After inlining, C2 classifies each allocation as NoEscape (never leaves the compiled method), ArgEscape (passed to a callee that was not inlined but does not store it), or GlobalEscape (stored in a field or static, returned, or thrown). A NoEscape object is scalar-replaced: its fields become locals or registers, and no allocation happens. HotSpot does not allocate objects on the stack. Scalar replacement goes further than that, because the object never exists at all. GraalVM's partial escape analysis also handles objects that escape only on some paths.

import org.openjdk.jmh.annotations.*;
import java.util.concurrent.TimeUnit;

    }
    int a = 3, b = 4;

Escape analysis is fragile: if an allocation reaches a call that is not inlined, a merge point it can't resolve, or a large array, it stays on the heap.

The same analysis drives lock elision: synchronized on an object that never escapes is removed (a local StringBuffer, for example). Lock coarsening merges adjacent synchronized blocks on the same lock (a chain of StringBuffer.append calls) into one acquire and one release.

Loops, constants and dead code

  • Counted loops (an int index, a fixed bound, stride 1 or another constant) get the most optimization. C2 splits them into pre, main and post loops so that range checks are hoisted out of the main loop, unrolls the main loop (often 4 to 16 times), and auto-vectorizes simple array arithmetic with SIMD instructions (SuperWord). The incubating Vector API makes vectorization explicit when the auto-vectorizer gives up.
  • Constant folding: static final fields are true constants, so if (DEBUG) with DEBUG = false compiles to nothing. Instance final fields are generally not trusted, because reflection can change them. Record fields and hidden-class fields are the exceptions.
  • Dead-code elimination: a computation whose result is unused is deleted. That is why a naive benchmark loop "runs" in zero nanoseconds.

Deoptimization and uncommon traps

C2 compiles only what the profile has seen. A branch that was never taken, a receiver class never seen, or a null never observed becomes an uncommon trap: a stub that, if reached, rebuilds interpreter frames from the compiled frame's state, marks the code not entrant and resumes in the interpreter. The method is then profiled again and recompiled. The usual reasons are unstable_if, class_check, null_check, range_check, and CHA invalidation when a new subclass loads. A few deopts at startup are normal. A deopt storm, where the same method is compiled, trapped and recompiled again and again, shows up as a steady flow of "made not entrant" lines, or as jdk.Deoptimization events in JFR (JDK 14+).

What breaks in production
  • Benchmarks without JMH. A hand-written timing loop meets dead-code elimination, constant folding, OSR, and profiles polluted by earlier tests in the same JVM. It measures the optimizer, not your code (L168).
  • A hot call site that turns megamorphic when a third implementation (a decorator, a mock, a new strategy) starts passing through it. Throughput can drop several times with no code change on that line.
  • Very large generated methods (parsers, mappers, rule engines) over 8,000 bytes run interpreted forever.
  • Micro-optimizing too early. In a typical backend, time goes to I/O, serialization and GC. Write clear code with small methods and stable types, then use a profiler (L167) before tuning anything for the JIT.

GC Theory: Reachability, Generations & Safepoints

45m video35m practice

A garbage collector keeps everything reachable from a small set of roots and reclaims the rest. Every production collector is built from three tracing algorithms, a bet that most objects die young, and a mechanism for stopping threads at safe points.

Reachability, not reference counting

Manual memory management (malloc/free) gives control but invites use-after-free, double free and leaks of lost pointers. Reference counting (CPython, Swift ARC) frees objects promptly, but it pays on every pointer write and cannot reclaim cycles without help. The JVM uses tracing: an object is live if and only if it is reachable from a root. Anything else is garbage, cycles included, and no code ever frees anything explicitly.

Definition · GC roots
  • local variables and operand-stack slots in every frame of every thread (interpreted and compiled, using the JIT's oop maps);
  • static fields, which live in Class mirrors kept alive by their class loader;
  • JNI local and global references held by native code;
  • live Thread objects, objects used as monitors by synchronized, and VM-internal references (system classes, the class-loader graph).

Three ways to reclaim

AlgorithmHowCost and trade-off
Mark-sweepmark live objects, then put the gaps on free listsno copying, but the heap fragments and allocation needs a free-list search
Mark-compactmark, then slide live objects together and fix every pointerno fragmentation and bump-pointer allocation, but several passes over the heap. Used for old generations and full GCs
Copying (Cheney)copy live objects from one space into an empty one, leaving forwarding pointerscost proportional to live data, not heap size, and compacts as it goes, but needs spare to-space. Ideal when most objects are dead

The generational bet

Hypothesis · Weak generational

Most objects die young. Few references point from old objects to young ones.

Ungar's 1984 "Generation Scavenging" paper and decades of studies since (summarized in Jones, Hosking and Moss, The Garbage Collection Handbook) found that in typical programs the large majority of objects become unreachable soon after allocation. Request-scoped DTOs, iterators, lambdas and temporary strings are the backend examples. So the heap is split. A small young generation is collected often by copying, and since almost everything in it is dead, the copy is cheap. Survivors age and are eventually promoted to the old generation, which is collected rarely. You can measure your own service: -Xlog:gc+age=trace prints how many bytes survive at each age, and the curve usually drops steeply after age 1 or 2.

  • Minor (young) GC: collects only the young generation. It is frequent and short.
  • Major GC: an ambiguous term. Usually it means old-generation work, which may be concurrent (G1 marking).
  • Full GC: the whole heap, usually stop-the-world and compacting. In G1 a full GC is a fallback that you want to never see (L163).

Cross-generation pointers: card tables and remembered sets

A minor GC must not scan the entire old generation looking for references into young. Instead, every reference store runs a write barrier, a few instructions added by the JIT, that marks a byte in the card table. Each card covers 512 bytes of heap. At a minor GC, only the dirty cards in old space are scanned as extra roots. G1 extends this into remembered sets: per region, the set of cards elsewhere that point into it, so any region can be collected on its own.

Safepoints and stop-the-world

Definition · Safepoint

A point in execution where a thread's state is fully described: every live reference is in a known slot. To stop the world, the VM arms a poll (a thread-local handshake page since JDK 10, JEP 312). Each thread notices it at its next poll, at a method return or a loop back-edge, and blocks. Threads in native code count as already safe. Time to safepoint (TTSP) is the wait for the slowest thread to arrive. During it, threads that have already stopped do nothing.

C2 removes polls from counted loops (an int index with a known bound) to make them faster. Such a loop can run for seconds without polling. JDK 10 added loop strip mining: an outer loop with a poll every LoopStripMiningIter iterations, enabled by default for G1, ZGC and Shenandoah, but not for Serial or Parallel.

public class Ttsp {
    static long sink;
    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> {
            long acc = 0;
            for (int i = 0; i < Integer.MAX_VALUE; i++) acc += i % 7;   // counted int loop
            sink = acc;
        });
        t.start();
        Thread.sleep(500);                     // let the loop get JIT-compiled (OSR)
        long t0 = System.nanoTime();
        System.gc();                           // needs every thread at a safepoint
        System.out.printf("System.gc() took %d ms%n", (System.nanoTime() - t0) / 1_000_000);
    }
}
$ java Ttsp                         # JDK 21, G1: strip mining on
System.gc() took 9 ms
$ java -XX:+UseParallelGC Ttsp      # JDK 21, Parallel: no polls in the loop
System.gc() took 3950 ms
$ java -Xlog:safepoint ...          # names the culprit phase
[info][safepoint] Safepoint "G1CollectFull", ... Reaching safepoint: 5044343601 ns, ... Total: 5050511101 ns

Those numbers are from one laptop run, so the exact values will differ on your machine. The pattern will not: the GC itself took about 6 ms, and the other 5 seconds were spent waiting for one thread to reach a poll.

Vocabulary and the triangle

  • Stop-the-world: application threads are paused at a safepoint while the GC works.
  • Parallel: several GC threads share the work during a pause.
  • Concurrent: GC threads work while application threads run. This needs extra barriers to keep the two consistent.
  • Incremental: the work is split into small pieces spread over time, like G1's mixed collections that each take a few old regions.

Collectors trade throughput (the share of CPU time left for the application), latency (pause length, particularly the tail) and footprint (extra memory and CPU). You can usually optimize two. Parallel picks throughput, ZGC picks latency, and Serial picks footprint (L162–L164).

What breaks in production
  • Long pauses with short GC times. The log shows a 2 s pause, but GC work was 20 ms. That is TTSP: a long counted loop, a huge System.arraycopy, or a mapped-file page fault. Turn on -Xlog:safepoint.
  • Calling System.gc() in application code (or in a library). It forces a full GC. Use -XX:+DisableExplicitGC if you cannot remove the call, but note that NIO uses explicit GC to free direct buffers.
  • Assuming objects are freed at the end of scope. A local that is still in a frame slot, or an entry in a static map, keeps the whole graph under it alive (L166).

Serial, Parallel & CMS Collectors

35m video30m practice

Serial and Parallel are the classic generational collectors: copy the young generation, mark-compact the old one, and stop the world for both. CMS tried to make old-generation work concurrent and was removed after JDK 13 because of the problems that design caused. All three share the young-generation mechanics: survivor spaces, ageing and promotion.

Serial: one thread, smallest overhead

-XX:+UseSerialGC collects the young generation by copying (log name Copy) and the old generation with a sliding mark-compact (MarkSweepCompact), both on a single thread and both stop-the-world. It has the least barrier cost and the smallest memory overhead. It is a good fit for heaps of a few hundred MB, CLI tools, and containers limited to one CPU, where extra GC threads would only compete with the application.

Ergonomics · Which collector you get

If you choose nothing, JDK 9+ uses G1 on a "server-class machine" (at least 2 CPUs and about 1.75 GB of memory) and Serial otherwise. In a container these are the container's limits. A pod with cpu: 1 therefore silently runs Serial GC. Check from inside the process:

Parallel: the throughput collector

-XX:+UseParallelGC uses the same algorithms but runs them on ParallelGCThreads threads: N on machines with up to 8 CPUs, and 8 + 5/8 × (N − 8) above that. Young and old collections are both parallel. JDK 21 has no separate "ParallelOld" switch, because UseParallelOldGC was removed in JDK 15. Parallel has no concurrent phases and only cheap card-marking barriers, so it gives the best raw throughput of any HotSpot collector. The price is that every old collection is a full stop-the-world compaction, which takes roughly a second per few GB of live data.

Definition · Parallel ergonomics

With UseAdaptiveSizePolicy (on by default), Parallel resizes eden, the survivors and the old generation to meet three goals, in priority order:

  1. Pause: -XX:MaxGCPauseMillis=N. It has no default. If set, the generations shrink until pauses fit.
  2. Throughput: -XX:GCTimeRatio=N targets GC time ≤ 1/(1 + N) of the total. The default for Parallel is 99, so 1%. (G1's default is 12, about 8%.)
  3. Footprint: if both goals are met, the heap shrinks.

A tight pause goal makes the young generation small, so collections happen more often and objects are promoted sooner. That is how a pause goal can lower throughput.

CMS, and why it was removed

Concurrent Mark Sweep (-XX:+UseConcMarkSweepGC, with ParNew for the young generation) ran old-generation collection in phases:

  1. Initial mark (STW, short): mark objects directly reachable from roots and from the young generation.
  2. Concurrent mark: trace the old generation while the application runs. A card-marking write barrier records what changes.
  3. Concurrent preclean: rescan dirty cards to shrink the work left for remark.
  4. Remark (STW): finish marking the objects that changed. Often the longest CMS pause.
  5. Concurrent sweep and reset: put dead space on free lists and prepare for the next cycle.

It never compacted. Over days the old generation fragmented until a promotion found no free block large enough (a promotion failure). If the old generation filled before a concurrent cycle finished (a concurrent mode failure), CMS fell back to a single-threaded full mark-compact, which could pause for tens of seconds on large heaps. Tuning meant CMSInitiatingOccupancyFraction and UseCMSInitiatingOccupancyOnly to start cycles early enough. CMS was deprecated in JDK 9 (JEP 291) and removed in JDK 14 (JEP 363). G1 replaced it.

Survivor spaces, tenuring and premature promotion

Each young collection copies live objects from eden and the active survivor space into the empty survivor space, and adds one to their age (stored in the mark word, L157). An object is promoted when its age reaches the tenuring threshold. The JVM recomputes that threshold after every collection: it is the smallest age at which the surviving bytes would fill more than TargetSurvivorRatio (50%) of a survivor space, capped by MaxTenuringThreshold (15). -Xlog:gc+age=trace prints the result as Desired survivor size … new threshold N (max threshold 15), followed by the bytes at each age.

Premature promotion happens when survivors are too small for the medium-lived objects (a request's data, a batch being processed). The threshold drops to 1 or 2, or objects overflow straight into the old generation. They die there soon after, but only an old or full GC can reclaim them. The symptoms: the old generation grows steadily under constant load, old collections become frequent, and the age table has a threshold that stays at 1. Fixes: a larger young generation (-Xmn, or let ergonomics grow it), a smaller SurvivorRatio for bigger survivors, or less retention per request.

What breaks in production
  • Upgrading with CMS flags still set. On JDK 21, -XX:+UseConcMarkSweepGC gives Unrecognized VM option 'UseConcMarkSweepGC' and the JVM does not start. JDK 14 printed a warning and ignored the flag, and later releases reject it. Remove all CMS* and ParNew flags before you migrate.
  • Accidental Serial GC in small pods, which shows up as long pauses on a 2 GB heap. Name the collector explicitly in the image's JAVA_TOOL_OPTIONS.
  • Parallel on a latency-sensitive API. Throughput looks great until the first old collection pauses all requests for a second or more.
  • Copying old tuning by habit. -Xmn, SurvivorRatio and MaxTenuringThreshold from a JDK 8 CMS setup usually hurt G1, which sizes the young generation itself to meet its pause goal.

G1 GC Internals & Tuning

50m video40m practice

G1 divides the heap into equal regions, marks the old generation concurrently, and in each pause evacuates only as many regions as it predicts it can copy within the pause goal, starting with the regions that hold the most garbage. Most G1 tuning comes down to keeping that prediction possible and keeping enough free regions for it to work.

Regions

G1 (the default since JDK 9, JEP 248) splits the heap into equal regions, each a power of two in size. Ergonomics aim at about 2,048 regions with sizes from 1 MB to 32 MB (an 8 GB heap gets 4 MB regions). Since JDK 18, -XX:G1HeapRegionSize accepts up to 512 MB. Every region has a role at any given moment: eden, survivor, old, humongous or free. Young and old are sets of regions, not fixed address ranges, so G1 resizes the young generation after every pause.

Humongous objects

An object of at least half a region is humongous. It is allocated straight into one or more contiguous free regions, marked as old, and is never copied. The costs: the unused tail of its last region is wasted. Contiguous free regions can run out while plenty of memory is free in total. Each humongous allocation can trigger a concurrent cycle. Since JDK 8u60, G1 can reclaim a dead humongous primitive array at any young GC ("eager reclaim"). Other humongous objects wait for marking. A 2 MB byte[] buffer on a heap with 4 MB regions is humongous. The fixes: reuse or pool large buffers, stream instead of materializing whole payloads, or raise G1HeapRegionSize so those objects become ordinary.

The concurrent marking cycle and SATB

When old occupancy passes the IHOP threshold, G1 marks the whole heap to learn how much of each old region is live:

  1. Initial mark: done during a young pause, logged as Pause Young (Concurrent Start). It marks from the roots.
  2. Root region scan (concurrent): scans the survivor regions, which must finish before the next young GC.
  3. Concurrent mark: traces the heap on ConcGCThreads threads (3 on a 12-CPU machine with JDK 21) while the application runs.
  4. Remark (STW): drains the remaining SATB buffers, processes references and unloads classes.
  5. Cleanup (STW, short): frees regions that turned out entirely empty, and chooses mixed-collection candidates after the remembered sets are rebuilt.
Definition · Snapshot at the beginning

While marking runs, the application keeps overwriting references, and could hide a live object from the marker. G1's pre-write barrier records the old value of a reference field before it is overwritten (into a per-thread SATB buffer) whenever marking is active. Objects allocated during marking count as live automatically. The result: everything that was live when marking started gets marked. Some objects that die during marking survive one extra cycle (floating garbage). A post-write barrier separately records cross-region pointers in the remembered sets (L161).

Evacuation pauses, the pause goal and mixed collections

Every G1 pause is an evacuation: copy the live objects out of the collection set (CSet) into free regions, then free the CSet's regions. G1 uses the remembered sets to find references into the CSet without scanning the heap. A young pause's CSet is all eden and survivor regions. G1 predicts copying cost per region from past pauses and sizes the young generation so the next pause fits -XX:MaxGCPauseMillis (default 200 ms, a goal, not a guarantee), within G1NewSizePercent to G1MaxNewSizePercent (5% to 60% of the heap; both are experimental flags).

After a marking cycle, G1 runs up to G1MixedGCCountTarget (8) mixed collections. Each takes all young regions plus a slice of the old candidates, least live first. Regions more than 85% live are skipped, and mixing stops once the reclaimable space is below G1HeapWastePercent (5%). A real JDK 21 log from a 256 MB heap that was too tight:

Full-GC fallback, the knobs, and when G1 is the wrong default

When evacuation finds no free region to copy into (logged as Evacuation Failure, called "to-space exhausted" in older logs), or a humongous allocation finds no contiguous space, G1 falls back to a full GC. That is a stop-the-world compaction of the whole heap. It has been multithreaded since JDK 10 (JEP 307), but it is still the pause you tuned to avoid. In the log above, the heap held 111 MB of live data in 256 MB, which left too little room to evacuate into. The ways out, in order:

  • More headroom. A heap at least 2 to 3 times the live set is the most effective fix.
  • Start marking earlier. Adaptive IHOP (G1UseAdaptiveIHOP, on by default) learns the threshold, with InitiatingHeapOccupancyPercent=45 only as the starting value. Raise G1ReservePercent (10) for a bigger safety margin, or add ConcGCThreads so marking finishes sooner.
  • Fewer humongous objects, or a bigger G1HeapRegionSize.
  • A realistic pause goal. 10 ms on a 30 GB heap forces a tiny young generation and constant GCs. If you need that, use ZGC (L164).

G1 is the default because it is a good compromise: pauses that are predictable and proportional to the young generation and the CSet rather than the whole heap, incremental compaction, and decent throughput across heaps from a few hundred MB to tens of GB. It is the wrong choice for a one-CPU container or a heap of a few hundred MB (Serial), for an offline batch job where only total time matters (Parallel, whose cheaper barriers usually give somewhat higher throughput), and for strict p99 pauses under 10 ms or very large heaps (ZGC).

What breaks in production
  • Setting -Xmn or NewRatio with G1. A fixed young size disables G1's pause-goal sizing. Leave it alone and set only the pause goal.
  • Large JSON or file uploads read into one byte[]. A storm of humongous allocations triggers concurrent cycles back to back, then a full GC. Look for G1 Humongous Allocation in the log.
  • Heap sized to the live set. A 1 GB heap with 900 MB live works in testing, then evacuation fails under peak load.
  • Copying tuning from a blog post. Many G1 flags are experimental or interact with each other. Change one thing at a time, against a log (L165).

ZGC & Shenandoah: Low-Latency Collectors

40m video30m practice

ZGC and Shenandoah move objects while the application is running, so pauses no longer grow with the heap or the live set. The application pays instead: a barrier on every reference load, extra CPU for the concurrent GC threads, and with ZGC, no compressed oops.

Why moving concurrently is hard

G1 pauses grow with how much it copies, because it relocates objects only while the world is stopped. To relocate concurrently, a collector must deal with application threads holding, loading and writing references to an object that is halfway through moving. Both collectors use a read-side barrier for this: every time the application loads a reference from the heap, a few added instructions check it and, if it is stale, fix it before use. The remaining pauses only handle a few roots and synchronize phases. Since JDK 16 (JEP 376) ZGC also scans thread stacks concurrently, so its pauses are typically well under a millisecond whether the heap is 1 GB or several TB.

ZGC: coloured pointers and load barriers

Definition · Coloured pointer

ZGC stores GC metadata inside each 64-bit reference: a few bits record whether the pointer is known-good for the current phase (marked in this cycle, remapped after relocation). Every reference is a full 64-bit pointer, so ZGC does not use compressed oops (L157), and reference fields cost 8 bytes.

A ZGC cycle runs concurrent mark, then picks a relocation set of mostly-empty pages (small pages are 2 MB, medium ones larger, and large objects get a page each), then relocates live objects concurrently. Each page's forwarding table records where its objects went. Whichever thread first loads a stale reference, GC or application, copies the object (or looks up the copy) and heals the field. References that nobody touched are remapped later, during the next marking pass, when it walks the graph anyway.

Generational ZGC

The original ZGC (production since JDK 15, JEP 377) was single-generation: each cycle marked the entire live set. With a high allocation rate it could fall behind, and when allocation outpaced collection the application thread had to wait for memory (an allocation stall, logged as such). The usual cure was a much larger heap. Generational ZGC (JDK 21, JEP 439) adds young and old generations, collected independently and concurrently, with store barriers to track old-to-young pointers. It gets the generational win from L161 and still has sub-millisecond pauses. JEP 439's stated goals are lower heap overhead, lower GC CPU overhead and fewer allocation stalls than single-generation ZGC. That made ZGC a reasonable default for latency-sensitive services instead of a special case for huge heaps.

# JDK 21: generational mode is opt-in
-XX:+UseZGC -XX:+ZGenerational -Xmx16g -XX:SoftMaxHeapSize=12g
# JDK 23: generational is the default (JEP 474)
# JDK 24+: non-generational mode removed (JEP 490); just use -XX:+UseZGC

SoftMaxHeapSize asks ZGC to try to stay below a soft limit while keeping -Xmx as headroom for spikes. ZGC also returns unused memory to the OS by default (ZUncommitDelay, 300 s).

Shenandoah: forwarding and concurrent evacuation

Shenandoah (Red Hat; JDK 12, JEP 189, production in JDK 15, JEP 379) also compacts concurrently, but it keeps compressed oops. Its first design used Brooks pointers: an extra word before every object holding its forwarding address, which pointed to the object itself until the object was copied. Every access went through it. Shenandoah 2.0 (JDK 13) removed that word. It now stores the forwarding pointer in the mark word of the old copy and uses a load-reference barrier that resolves a reference to the to-space copy when it is loaded. A cycle has short pauses for init mark, final mark and the update-references steps, with concurrent marking, concurrent evacuation (application threads that touch an object being moved copy it themselves) and concurrent reference updating between them. Oracle JDK builds do not include Shenandoah. Most other OpenJDK distributions do, and -XX:+UseShenandoahGC tells you which kind you have.

The bill, Epsilon, and choosing

Barriers on every reference load and the concurrent GC threads cost throughput, commonly reported at around 5–15% compared with G1 or Parallel on CPU-bound work, and more if CPU is scarce. Without compressed oops, ZGC also uses more memory for reference-heavy data. Neither collector can make up for too little CPU: concurrent GC needs spare cores.

Epsilon (JDK 11, JEP 318, experimental: -XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC) allocates and never collects. When the heap is full the JVM exits with an OOM. It is useful as a zero-barrier baseline for measuring other collectors' overhead, for memory-pressure tests, and for short jobs whose total allocation fits in the heap.

What breaks in production
  • Switching to ZGC without enough CPU. In a 2-vCPU pod the concurrent threads fall behind and allocation stalls appear. Those are pauses, just under a different name. Watch for Allocation Stall in -Xlog:gc.
  • Moving to ZGC at the same -Xmx. Without compressed oops the live set grows. Re-measure the heap after the switch.
  • Keeping -XX:+ZGenerational when moving to JDK 24+. From JDK 24 the flag is obsolete. It prints a warning, and a later release will reject it the way JDK 21 rejects the CMS flags (L162). Scripts that turn it off (-XX:-ZGenerational) no longer get the old mode.
  • Blaming GC for latency without checking. If p99 latency doesn't change after a switch to ZGC, the pauses were never the problem. Look at TTSP (L161), locks and I/O.

GC Logs, Tuning Flags & Containers

GC tuning starts from a log, not from a flag list. Turn on unified logging everywhere, reduce it to five numbers (pause p99, overhead, allocation rate, promotion rate and live set), and in containers size the heap as a share of the pod limit, leaving room for the native memory that also counts against that limit.

Unified logging

Since JDK 9 (JEP 158, JEP 271) all JVM logging goes through -Xlog, with four colon-separated parts: what (tag selectors with levels), where (stdout, stderr or a file), decorators (the prefix on each line) and output options (rotation).

#     │                            └ write to gc.log (use %p in the name for the pid, %t for start time)

Containers: what the JVM sees

UseContainerSupport (on by default since JDK 10, and backported to 8u191) makes the JVM read cgroup limits instead of the host's. cgroup v2 support arrived in JDK 15 and was backported to 11 and 8. Inside a pod with a 2 GiB limit, the defaults give MaxRAMPercentage=25, a 512 MB heap, which is usually too small. Use percentages rather than a fixed -Xmx, so the same image works at any pod size:

JAVA_TOOL_OPTIONS="-XX:InitialRAMPercentage=70 -XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError \
  -Xlog:gc*:file=/logs/gc-%p.log:time,uptime,level,tags:filecount=5,filesize=20M"

For CPU, the JVM derives availableProcessors() from the cgroup CPU quota, rounded up. Since JDK 19 it no longer uses CPU shares (requests) for this. That count decides GC worker threads, JIT compiler threads and the common ForkJoinPool size. A limit of 500m means 1 CPU: Serial GC (L162) and a single-threaded common pool. -XX:ActiveProcessorCount=N overrides the detection when the quota doesn't reflect what the pod can really use.

Why the pod is OOMKilled while the heap looks fine

The cgroup limit counts resident memory for the whole process: heap, Metaspace, code cache, thread stacks (about 1 MB reserved per thread, partly committed), GC data structures (G1 remembered sets and mark bitmaps, often a few percent of the heap), direct ByteBuffers (Netty, NIO; by default capped at -Xmx), JNI and glibc malloc arenas. Rule of thumb: heap 50–75% of the limit, a lower share for small pods, and cap Metaspace and direct memory. When an OOM kill happens, start with Native Memory Tracking (L170).

Algorithm · Tuning loop
  1. Write down the goal: p99 latency, throughput, or cost (memory per pod).
  2. Reproduce production-like load and record a baseline: GC log, JFR, the five numbers.
  3. Find the bottleneck metric. Most fixes are in code (allocation rate, retention), not in flags.
  4. Change one thing: heap size first, then the pause goal, then the collector.
  5. Re-run the same load, compare, then keep or revert. Write the reason down next to the flag.
What breaks in production
  • Hard-coded -Xmx in the Dockerfile. Someone halves the pod limit, the heap stays the same, and the pod is OOMKilled at peak.
  • MaxRAMPercentage=90. It leaves no room for native memory.
  • GC logs on the container filesystem. They disappear with the pod that crashed. Write them to a mounted volume or ship them.
  • Tuning from averages. A 20 ms average pause can hide a 1.5 s p99.9 pause. Always look at the distribution.

Memory Leaks: Heap Dumps, MAT & Common Patterns

50m video50m practice

A Java leak is memory the program can still reach but will never use again. You find it by taking a heap dump, looking at the dominator tree for the object that retains the most memory, and following its path to a GC root. The path almost always ends at one of about ten familiar patterns.

What a leak looks like

A C program leaks by losing the pointer. A Java program cannot do that: anything unreachable is collected (L161). Java leaks are unintentional retention. A static map, a cache, a listener list or a thread keeps a reference that nobody will use again. The signature is in the heap graph after each GC: the troughs of the sawtooth climb. The peaks only show how much the application allocates between collections.

Capturing a heap dump

jcmd <pid> GC.heap_dump /dumps/app.hprof          # live objects only (runs a full GC first)
jcmd <pid> GC.heap_dump -all -gz=1 /dumps/all.hprof.gz   # include unreachable, gzip
jmap -dump:live,format=b,file=/dumps/app.hprof <pid>      # older equivalent
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps    # automatic, java_pid<pid>.hprof

A dump stops the JVM while it writes and is roughly as large as the used heap. Write it to a volume with enough free space, and treat it as sensitive: it contains every password, token and customer record that was in memory. Take two or three dumps some minutes apart. The class that grows between them is the suspect.

Eclipse MAT

Definition · Shallow, retained, dominator

An object's shallow size is its own bytes (L157). Its retained size is everything that would be freed if it were collected. Object X dominates Y if every path from the GC roots to Y passes through X. The dominator tree arranges the heap so that each node's subtree is exactly its retained set.

  • Histogram: object count, shallow size and retained size per class. byte[], String and HashMap$Node are almost always at the top. That tells you what is retained, not who retains it.
  • Dominator tree: sort by retained size. In a leaking service the top entry is usually one map, cache or list that holds most of the heap.
  • Path to GC Roots (excluding weak and soft references): the chain of fields from a root to the suspect, for example Thread → threadLocals → ThreadLocalMap → Entry.value. That chain names the leaking pattern.
  • Leak Suspects report: MAT's automatic first pass, which points at large dominators and their accumulation points.
  • OQL for targeted questions: SELECT * FROM java.util.ArrayList a WHERE a.size > 100000, or SELECT * FROM INSTANCEOF java.lang.ClassLoader to count loaders after a redeploy.

VisualVM opens the same .hprof files and is enough for a quick look. JFR can find leaks without a dump: the jdk.OldObjectSample event samples allocations that stay alive. Record with path-to-gc-roots=true and JMC shows the reference chain for each sample. That is safer in production than writing a 30 GB dump.

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.concurrent.CopyOnWriteArrayList;

public class LeakFixes {
    // Unbounded static HashMap -> bounded LRU (in real code: Caffeine with maximumSize/expireAfterWrite)
    static <K, V> Map<K, V> lru(int max) {
        return new LinkedHashMap<>(16, 0.75f, true) {          // static context: no outer instance captured
            @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) { return size() > max; }
        };
    }

    // ThreadLocal on pooled threads -> always remove in finally
    static final ThreadLocal<String> TENANT = new ThreadLocal<>();
    static void handle(String tenant, Runnable work) {
        TENANT.set(tenant);
        try { work.run(); } finally { TENANT.remove(); }
    }

    // Listener without deregistration -> registration returns a handle that removes it
    static final List<Runnable> LISTENERS = new CopyOnWriteArrayList<>();
    static AutoCloseable subscribe(Runnable listener) {
        LISTENERS.add(listener);
        return () -> LISTENERS.remove(listener);
    }
}

The LRU map is not thread-safe. Wrap it with Collections.synchronizedMap or, better, use Caffeine. A ThreadLocal that is never removed also causes correctness bugs: the next request on that pooled thread sees the previous tenant.

What breaks in production
  • No dump when it matters. Without HeapDumpOnOutOfMemoryError and a writable HeapDumpPath, the evidence dies with the process. Add -XX:+ExitOnOutOfMemoryError so the orchestrator restarts the process instead of leaving it half-broken.
  • Dumping a 30 GB heap on a live node. It can pause the JVM for many seconds, fill the disk, and make health checks fail. Take the node out of the load balancer first, or use JFR's old-object sampling.
  • Calling an OOM caused by high load a leak. If the troughs are flat and the OOM comes at peak traffic, the live set is simply bigger than the heap. Size the heap, or limit concurrency.
  • Leaks that are not on the heap. RSS grows but the heap troughs are flat: direct buffers, threads, or malloc. See L170.

Profiling with JFR & async-profiler

JFR records what the JVM already knows (samples, allocations, locks, GC, I/O) at low enough cost to leave it on in production. async-profiler adds OS-level CPU, wall-clock and allocation profiles without safepoint bias. Both produce flame graphs, and reading a flame graph comes down to finding the widest frame that is your code.

Java Flight Recorder

JFR is built into HotSpot (open-sourced in JDK 11, JEP 328, and backported to 8u262). It writes binary events into thread-local buffers and flushes them to a chunked file, so recording does not go through Java objects or the GC. The default settings are designed for about 1% overhead, low enough to run all the time. profile samples more often and turns on more events, at roughly 2%.

jcmd <pid> JFR.dump  name=incident filename=/rec/incident.jfr

Custom events for business operations

import jdk.jfr.Category;
import jdk.jfr.Event;
import jdk.jfr.Label;
import jdk.jfr.Name;
import jdk.jfr.StackTrace;
import java.math.BigDecimal;

public class Orders {
    @Name("shop.OrderPlaced")
    @Label("Order Placed")
    @Category({"Shop", "Orders"})
    @StackTrace(false)
    static class OrderPlaced extends Event {
        @Label("Order ID") String orderId;
        @Label("Items") int items;
        @Label("Total") String total;
    }

    static BigDecimal place(String id, int items) {
        var event = new OrderPlaced();
        event.begin();                                        // start the clock
        BigDecimal total = BigDecimal.ZERO;
        for (int i = 0; i < items; i++) total = total.add(new BigDecimal("19.99").multiply(BigDecimal.valueOf(i + 1)));
        if (event.shouldCommit()) {                           // false if disabled or below threshold
            event.orderId = id;
            event.items = items;
            event.total = total.toPlainString();
        }
        event.commit();                                       // records duration + fields
        return total;
    }
}

The event then appears in JMC's Event Browser on the same timeline as GC pauses and lock waits, so you can ask questions like "were the slow orders the ones that overlapped a pause?". When the event is disabled, commit() does almost nothing, and the JIT can remove the unused event object through escape analysis (L160). Add @Threshold("50 ms") in a custom .jfc file to record only slow operations.

async-profiler and safepoint bias

Definition · Safepoint bias

Profilers built on Thread.getAllStackTraces or JVMTI stack sampling (the VisualVM sampler, for example) can take stacks only at safepoints (L161). Time spent in a counted loop with no poll is charged to wherever the next poll is, often a different method. The profile is wrong in a consistent way, which makes it convincing.

async-profiler (Linux and macOS) avoids this. It uses perf_events or timer signals to interrupt a thread at any instruction, then walks the Java stack with HotSpot's AsyncGetCallTrace and the native stack itself, so it also shows JIT compiler threads, GC threads and native frames such as memcpy or epoll. JFR's execution sampler is also not safepoint-biased, but it covers only Java code.

asprof -e cpu   -d 30 -f cpu.html   <pid>   # on-CPU time (perf_events, else a timer mode)
asprof -e wall  -d 30 -t -f wall.html <pid>  # all threads, running or blocked, split per thread
asprof -e alloc -d 30 -f alloc.html <pid>   # allocation sampling by TLAB events
asprof -e lock  -d 30 -f lock.html  <pid>   # contended monitor and ReentrantLock waits
asprof -e cpu -d 30 -o collapsed -f before.txt <pid>   # folded stacks for diffing
# for accurate line attribution in inlined code
java -XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints ...

Wall-clock mode is the right one for latency problems: a request that takes 800 ms but uses 20 ms of CPU spent the rest waiting, and only a wall profile shows where.

Reading flame graphs

  • The x-axis is sorted alphabetically, not by time. Only widths matter.
  • A frame's own (self) time is the part of its width with nothing stacked on top. Wide flat tops are where the CPU actually is.
  • Look for the widest frame that belongs to your code, then ask why it calls what it calls. Optimizing BigDecimal is not an option. Calling it 10 times less often is.
  • Differential flame graphs: collect folded stacks before and after a change, then run Brendan Gregg's difffolded.pl before.txt after.txt | flamegraph.pl > diff.svg. Frames are coloured by whether they grew or shrank.
What breaks in production
  • Profiling in CPU mode for a latency problem. A service waiting on a database looks idle in a CPU profile. Use wall-clock mode, or JFR's thread-park and socket events.
  • async-profiler in a locked-down container. perf_event_paranoid or missing capabilities block perf_events. Use a timer-based mode (-e itimer), or run with the right security context, and test this before the incident.
  • Unbounded recordings. Without maxage/maxsize, a continuous recording keeps growing. Always cap it, and write it to a volume.
  • Trusting one sample window. Profile for 30–60 s under representative load, on one instance, more than once.

JMH: Microbenchmarking Done Right

45m video50m practice

A microbenchmark measures the JIT as much as your code. JMH controls for this with forks, warmup, measurement iterations, and ways to keep results alive and inputs opaque. Read the error column as seriously as the score, and publish the setup together with the numbers.

Why a timing loop is always wrong

long t0 = System.currentTimeMillis();
for (int i = 0; i < 1_000_000; i++) Math.log(i);              // result unused
System.out.println((System.currentTimeMillis() - t0) + " ms");
  • Warmup: the first iterations run in the interpreter, then C1, then C2 (L159). One run averages all three.
  • OSR: the loop body is compiled as an OSR version of main, which C2 can optimize differently from the method-entry version that real callers would get.
  • Dead-code elimination: the result is never used, so C2 may delete the computation and time an empty loop (L160).
  • Constant folding: if the inputs are compile-time constants, the answer may be computed at compile time.
  • Loop unrolling and hoisting: work from the loop body is spread across iterations, or moved out of the loop entirely.
  • The clock: currentTimeMillis is wall time with coarse resolution, and it can jump. Use nanoTime for intervals. JMH handles all of this for you.
  • Profile pollution: benchmark B, run in the same JVM after A, inherits A's type profiles. Its call sites may already be bimorphic or megamorphic.

Setting up JMH

mvn archetype:generate -DinteractiveMode=false \
  -DarchetypeGroupId=org.openjdk.jmh -DarchetypeArtifactId=jmh-java-benchmark-archetype \
  -DgroupId=dev.example -DartifactId=bench -Dversion=1.0
cd bench && mvn clean verify
java -jar target/benchmarks.jar ListBench -prof gc -rf json -rff list.json

The archetype sets up jmh-core and the jmh-generator-annprocess annotation processor, which generates the measuring harness, and the shade plugin builds the runnable benchmarks.jar. Run benchmarks from that jar on a quiet machine, not from the IDE.

    @Param({"10", "1000", "100000"})
    int size;

    @Setup(Level.Trial)

        linked = new LinkedList<>();

Reading the output, and the profilers

Definition · Score and error

Each row reads Benchmark (size) Mode Cnt Score Error Units. Score is the mean over all measurement iterations from all forks (Cnt of them). Error is the half-width of the 99.9% confidence interval. If two scores' intervals overlap, you have not shown a difference. A large error usually means the machine is noisy, there are too few forks, or the code is bimodal (for example GC hitting some iterations).

  • -prof gc: gc.alloc.rate.norm in bytes per operation. It is often more stable and more useful than the time, and it shows escape analysis at work (L160).
  • -prof perfasm (Linux perf plus the hsdis disassembler): the hottest compiled code regions annotated with assembly. It is the final answer to "what did the JIT actually do?".
  • -prof stack, and -prof async if async-profiler is installed (L167).

Four classic comparisons, honestly

  • StringBuilder vs +: for one expression, + compiles to invokedynamic (L158) and is as fast as a hand-written builder or faster. In a loop, use a single builder: each s += x copies the whole string.
  • ArrayList vs LinkedList: expect ArrayList to win iteration by a wide margin at every size, because its elements are contiguous and each LinkedList element costs a 24-byte node and a pointer chase (L157). It often wins middle insertion too for moderate sizes, because System.arraycopy is fast and finding the position in a linked list is slow.
  • stream vs for: streams have fixed setup costs that dominate for small collections. For large, simple pipelines the gap after JIT is usually small. Measure your shape at your sizes.
  • AtomicLong vs LongAdder: run with @Threads(1) and then @Threads(8). Uncontended, the two are close. Under contention, AtomicLong's CAS retries collapse and LongAdder's striped cells keep scaling. In exchange, sum() is not an atomic snapshot.
Publishing honest numbers

State the JDK build, JVM flags, JMH version, CPU model and core count, OS, power and turbo settings, forks and iterations. Show the full table including the error column, and link the benchmark source. Report the result of the comparison, not a percentage taken from overlapping intervals. Say what the benchmark does not show: a 30% gain in a method that takes 1% of request time is a 0.3% gain for the service.

What breaks in production
  • Micro-optimizing from a microbenchmark. Inlining, profiles and cache state in the real service differ from the benchmark. Confirm the effect with a profile or a load test of the service (L167).
  • Loops inside @Benchmark. Your own loop brings back unrolling and hoisting. Let JMH do the repetition, or follow the JMHSample_34_SafeLooping pattern.
  • Benchmarking on a laptop running on battery or under thermal throttling. The error column grows, and the scores mostly reflect the power settings.

The CLI Toolbox: jcmd, jstack, jmap, jstat & Friends

Every JDK includes command-line tools that can inspect a running JVM without a restart, an agent or a GUI. jcmd covers most of them. Learn which commands are safe, which ones pause the JVM, and the order to run them in during an incident.

Finding the process, and jcmd as the front door

jps -l lists local JVMs with their main class or jar, and jps -v adds the JVM flags. Both read /tmp/hsperfdata_<user>, so they see only JVMs owned by the same user, in the same PID and /tmp namespace. In a container, run the tools inside it (kubectl exec) as the application's user. -XX:+PerfDisableSharedMem hides the process from jps and jstat.

Definition · Attach mechanism

jcmd, jstack, jmap and jinfo use the attach API: they ask the target JVM, through a socket file on Linux, to start its Attach Listener thread and run a diagnostic command inside the process. Whether a command is safe depends on that command: Thread.print needs only a brief safepoint, while GC.heap_dump stops the JVM for as long as the dump takes. jcmd <pid> help lists about 50 commands on JDK 21, and jcmd <pid> help GC.heap_dump shows a command's options and its impact.

Algorithm · The service is slow: what to run first
  1. Is it this process? top -H -p <pid>: high CPU with a few hot threads (go to 2), or low CPU (go to 3).
  2. Hot threads: three jcmd <pid> Thread.print, then map the hot nids. If the hot threads are GC Thread# or G1 Conc#, go to 4.
  3. Low CPU but slow: the same three dumps. Look for many threads BLOCKED on one lock or parked in a pool (database, HTTP client), and for deadlocks.
  4. GC: jstat -gcutil <pid> 1s for 30 s, and the GC log (L165). Is old usage climbing, are there frequent full GCs, a high GCT rate?
  5. Record: jcmd <pid> JFR.start duration=60s settings=profile filename=/tmp/slow.jfr, then analyse it in JMC (L167).
  6. Memory suspected: GC.class_histogram twice a few minutes apart. Take a heap dump only after taking the instance out of rotation (L166). If RSS is growing, use VM.native_memory (L170).

  • Running jmap -histo:live or GC.class_histogram casually. Both force a full GC, which on a 32 GB Parallel heap is a multi-second pause.
  • Only one thread dump. One dump shows where threads are at one moment, but not whether they are moving. Take three.
  • A minimal JRE image without jdk.jcmd. When the incident comes, there are no tools. Include jdk.jcmd and jdk.jfr in the jlink module list, or keep a debug sidecar image.

Native Memory, FFM, GraalVM & Phase 6 Capstone

50m video120m practicecapstone

A container kills a Java process for its resident set size, not for its heap, and the heap is often less than half of it. Native Memory Tracking shows where the rest goes. Then the capstone puts the whole phase to work: diagnose a broken service with real tools and prove every fix with numbers.

Where non-heap memory goes

Definition · Native Memory Tracking

NMT is HotSpot's own accounting of every allocation the JVM makes, grouped into categories (Java Heap, Class, Thread, Code, GC, Compiler, Internal, Symbol, Other…). It has to be switched on at startup with -XX:NativeMemoryTracking=summary (or detail, which also records call sites). Oracle documents a 5–10% performance cost, so it is a diagnosis setting more than a default. It reports reserved (address space) and committed (backed by memory) bytes. Only committed counts toward RSS.

Direct buffers and the malloc arena problem

ByteBuffer.allocateDirect takes native memory and records it against a limit, -XX:MaxDirectMemorySize. If you do not set the flag, the limit equals the maximum heap size. The memory is freed only when the small on-heap ByteBuffer object becomes unreachable and its Cleaner runs, that is, after a GC. A quiet old generation can therefore hold gigabytes of dead direct memory. At the limit, the JDK calls System.gc(), waits for cleaners, retries, and then throws OutOfMemoryError with a "direct buffer memory" message. Watch usage with BufferPoolMXBean (pool direct). Netty's pooled buffers are reference-counted, so a missing release() leaks them. Its leak detector reports these.

Memory NMT does not see usually comes from glibc. It gives threads separate malloc arenas (up to 8 per core on 64-bit), and each arena fragments on its own. RSS creeps up as a result. The standard fix is the environment variable MALLOC_ARENA_MAX=2. The alternatives are jemalloc or jcmd <pid> System.trim_native_heap.

The Foreign Function & Memory API (Java 22+)

FFM (java.lang.foreign, final in JDK 22 via JEP 454) replaces JNI for most uses. You don't write C glue code. You describe the native function's signature in Java and get a MethodHandle. Off-heap memory is a bounds-checked MemorySegment whose lifetime belongs to an Arena, so it is freed when the arena closes, not whenever a GC happens to run.

import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;
import static java.lang.foreign.ValueLayout.*;

public class Strlen {                       // java --enable-native-access=ALL-UNNAMED Strlen.java
    public static void main(String[] args) throws Throwable {
        Linker linker = Linker.nativeLinker();
        MethodHandle strlen = linker.downcallHandle(
                linker.defaultLookup().find("strlen").orElseThrow(),
                FunctionDescriptor.of(JAVA_LONG, ADDRESS));

        try (Arena arena = Arena.ofConfined()) {             // one thread, deterministic free
            MemorySegment text = arena.allocateFrom("hello, panama");
            long n = (long) strlen.invokeExact(text);
            MemorySegment squares = arena.allocate(JAVA_INT, 1_000);
            for (int i = 0; i < 1_000; i++) squares.setAtIndex(JAVA_INT, i, i * i);
            System.out.println(n + " " + squares.getAtIndex(JAVA_INT, 999));
        }                                                    // both segments freed here
    }
}

An access after the arena closes throws IllegalStateException, and an access outside the segment's bounds throws IndexOutOfBoundsException. JNI and Unsafe would crash the process instead. jextract generates these bindings from a C header. Linker methods are restricted: they print a warning unless you grant --enable-native-access.

GraalVM native image

Definition · Closed-world assumption

native-image runs a points-to analysis from main and compiles only the code it can prove is reachable into a standalone executable, ahead of time. It also snapshots an image heap of objects created at build time. Anything the analysis cannot see must be declared in reachability metadata (META-INF/native-image/…): reflection targets, resources, dynamic proxies, JNI and serialization. Otherwise it is missing at run time.

  • Build-time initialization. --initialize-at-build-time=… runs a static initializer during the build and bakes the result into the image. Startup is faster, but whatever it captured stays frozen: random seeds, timestamps, environment values.
  • Tracing agent. java -agentlib:native-image-agent=config-output-dir=… -jar app.jar records reflection, resources and proxies while you exercise the app. Spring Boot 3's AOT engine generates most of this metadata itself (mvn -Pnative native:compile).
  • The tradeoff. Startup takes tens of milliseconds instead of seconds, and memory use is lower. Peak throughput is usually below C2's, because there is no run-time profiling. Builds take minutes and GBs of RAM, and JVMTI agents don't work. Native images fit CLIs and scale-to-zero services, not long-running hot services.

import java.util.*;

            served++;

        for (int i = 0; i < 2_000; i++) boxed.add(i);
        return String.join(",", boxed.stream().map(String::valueOf).toList()).length();
    }

    public static void main(String[] args) {
        var pool = Executors.newFixedThreadPool(16);
        for (int t = 0; t < 16; t++) pool.execute(() -> { for (int n = 0; ; n++) handle(n); });
    }
}
Algorithm · One fault at a time
  1. Leak. Run with -Xmx256m -XX:+HeapDumpOnOutOfMemoryError. In Eclipse MAT, the dominator tree puts CACHE's HashMap on top, and "path to GC roots" ends at a static field. Fix: a bounded cache (size-capped LRU, or Caffeine with maximumSize) and a real key.
  2. GC thrash. With -Xlog:gc*:file=gc.log you see back-to-back young collections and a high allocation rate. Size the heap (-Xms = -Xmx, enough young generation), then cut the allocation itself: no boxing, a reused StringBuilder. Compare allocation per operation with JMH's -prof gc.
  3. Hot lock. asprof -e lock -d 30 -f lock.html <pid> shows almost all wall time blocked on LOCK. Fix: ConcurrentHashMap plus a LongAdder for the counter.
  4. Proof. Record JFR before and after (-XX:StartFlightRecording=duration=120s,filename=after.jfr) and compare GC pause totals, jdk.JavaMonitorEnter events and allocation rate. Add a JMH benchmark of handle at 1 and 16 threads.
  • A heap-dump screenshot or MAT report naming the leaking field, and the bounded-cache fix with a stable heap over 30 minutes of load
  • GC logs before and after, with allocation rate and total pause time per minute
  • async-profiler lock flame graphs before and after
  • JMH results (ops/s and B/op at 1 and 16 threads) for the old and new handle
  • Two JFR recordings and a one-page write-up: symptom, evidence, fix, measured gain, for each fault
  • An NMT summary.diff from the fixed app under load showing flat native memory
What breaks in production
  • Sizing the container to -Xmx. A 1 GB heap in a 1 GB container gets OOM-killed. Leave room for Metaspace, the code cache, threads and direct memory, or use -XX:MaxRAMPercentage=70 and measure with NMT.
  • -XX:+DisableExplicitGC with NIO-heavy code. Direct-buffer reservation relies on its System.gc(). Without it, slow cleanup becomes an OOM.
  • RSS creeping while the NMT total stays flat. The cause is native libraries or arena fragmentation, not Java code.
  • A native image that passes tests and fails in production. A code path the agent never exercised used reflection. Run the integration tests against the native binary.
