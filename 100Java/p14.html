Spring MVC & REST APIs

Phase 14 turns a Spring Boot application into a production REST API: how DispatcherServlet routes each request, how parameters, bodies and validation are bound, and how errors, versions and documentation become a contract that clients can rely on. It builds on the container and Boot auto-configuration from the earlier Spring phases, and the controllers written here are what the Spring Data repositories of Phase 15 sit behind. The milestone is a fully documented, validated, versioned REST API with consistent error handling and a committed OpenAPI spec.

By the end of this phase you can

  • Trace a request through filters, DispatcherServlet, handler mapping, interceptors, argument resolvers and message converters, and say where each customization hooks in.
  • Design resource-oriented controllers that return the right status codes and headers (201 with Location, 204, 409, ETags) using ResponseEntity.
  • Validate request DTOs with Bean Validation, including custom, cross-field and grouped constraints, and know which exception and status each validation site produces.
  • Implement one @RestControllerAdvice that renders every error, Spring's and yours, as RFC 9457 problem details with a stable code and trace id.
  • Write correlation-id and logging filters, interceptors, safe file upload/download, and SSE or long-polling endpoints, and choose between async MVC and virtual threads.
  • Version and deprecate an API with Deprecation/Sunset headers, and export, lint and commit its OpenAPI spec.
  • Call other services with RestClient, HTTP interfaces or WebClient, with connection pools, timeouts and safe retries, and test them with MockRestServiceServer.

L299 · DAY 299

Spring MVC Architecture & DispatcherServlet

45m video40m practice

Spring MVC is one servlet, DispatcherServlet, that receives every request and hands each step (find the handler, call it, convert the result, handle errors) to a replaceable strategy bean. Once you know the order of those steps, you know where every customization hooks in and why some of them run too late.

The Front Controller pattern

Definition · Front Controller

A single entry point that receives every request, applies common handling (decoding, security, locale, error mapping), then dispatches to a per-request handler. The alternative, one servlet per URL in web.xml, scatters those cross-cutting concerns across every servlet. Fowler names the pattern in Patterns of Enterprise Application Architecture.

DispatcherServlet is Spring's implementation. Its hierarchy is HttpServlet → HttpServletBean → FrameworkServlet → DispatcherServlet. FrameworkServlet overrides every doGet/doPost/… and funnels them into processRequest → doService → doDispatch, the method worth reading once in full. The servlet holds a WebApplicationContext and looks up its collaborators there. Classic deployments had a root context plus a child context per servlet; Spring Boot uses one application context for everything, and registers the servlet through a DispatcherServletRegistrationBean mapped to /.

The complete request flow

Algorithm · doDispatch, simplified
  1. Container. Tomcat accepts the connection, parses HTTP, takes a worker thread (default pool max 200, server.tomcat.threads.max) and builds HttpServletRequest/Response.
  2. Filters. Servlet filters run in order (encoding, Spring Security's FilterChainProxy, yours). Each calls chain.doFilter; code after that call runs on the way out.
  3. Multipart check. If the request is multipart, the MultipartResolver wraps it.
  4. getHandler. Each HandlerMapping is asked in order; the first non-null answer is a HandlerExecutionChain: the handler (a HandlerMethod for annotated controllers) plus the matching interceptors. No match → 404; in Boot 3.2+ an unmapped path usually lands on the static-resource handler and surfaces as NoResourceFoundException.
  5. getHandlerAdapter. Find the adapter that supports this handler type; for HandlerMethod it is RequestMappingHandlerAdapter.
  6. preHandle on each interceptor in order. false stops processing.
  7. handle. Each parameter is filled by a HandlerMethodArgumentResolver (@PathVariable, @RequestParam, @RequestBody via an HttpMessageConverter, validation), then your method is invoked by reflection.
  8. Return value. A HandlerMethodReturnValueHandler processes it: @ResponseBody/ResponseEntity are written immediately by a message converter; a view name becomes a ModelAndView.
  9. postHandle on interceptors in reverse order (skipped if step 7 threw).
  10. processDispatchResult. Exceptions go to the HandlerExceptionResolver chain; a ModelAndView is resolved by a ViewResolver and rendered.
  11. afterCompletion in reverse order, always, for every interceptor whose preHandle returned true. Then filters unwind and Tomcat flushes the response.

The special beans

At startup DispatcherServlet.initStrategies collects its collaborators from the context. Handler mappings, adapters, exception resolvers and view resolvers are detected by type and sorted by Ordered; LocaleResolver and MultipartResolver are looked up by bean name (localeResolver, multipartResolver), so a bean with the wrong name is silently ignored. Anything missing falls back to DispatcherServlet.properties.

WebMvcAutoConfiguration and what Boot configures

DispatcherServletAutoConfiguration creates the servlet and its registration (spring.mvc.servlet.path, spring.mvc.servlet.load-on-startup; the default -1 initializes it lazily on the first request). WebMvcAutoConfiguration is guarded by @ConditionalOnMissingBean(WebMvcConfigurationSupport.class) and contributes the infrastructure plus a WebMvcConfigurer that adds: message converters from the HttpMessageConverters bean (so Boot's Jackson ObjectMapper is used), static resource locations (classpath:/static/, /public/, /resources/, /META-INF/resources/) and webjars, the welcome page, content-negotiating view resolution, spring.mvc.format.* date formats, and auto-registration of every Converter, Formatter and GenericConverter bean. Neighbouring auto-configurations add the CharacterEncodingFilter, the FormContentFilter and the /error handling.

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new TimingInterceptor()).addPathPatterns("/api/**");
    }

    public void addFormatters(FormatterRegistry registry) {

class TimingInterceptor implements HandlerInterceptor {
    private static final Logger log = LoggerFactory.getLogger(TimingInterceptor.class);

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        req.setAttribute("t0", System.nanoTime());
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        long ms = (System.nanoTime() - (Long) req.getAttribute("t0")) / 1_000_000;
        String target = handler instanceof HandlerMethod hm ? hm.getShortLogMessage() : handler.toString();
        log.info("{} {} -> {} in {} ms [{}]", req.getMethod(), req.getRequestURI(), res.getStatus(), ms, target);
    }
}

Customize, don't replace

Three levels: properties (spring.mvc.*, spring.jackson.*) for the common knobs; a WebMvcConfigurer bean to add interceptors, converters, CORS, resource handlers; a WebMvcRegistrations bean to swap in a custom RequestMappingHandlerMapping or adapter while keeping the rest. @EnableWebMvc is a fourth level that means "I'll configure all of MVC myself".

What breaks in production
  • @EnableWebMvc added "to configure MVC". It imports DelegatingWebMvcConfiguration, a WebMvcConfigurationSupport, so Boot's condition fails and the whole auto-configuration backs off: static files return 404 and responses are serialized by a fresh ObjectMapper that ignores spring.jackson.*, so date formats silently change.
  • Setting headers in postHandle for a JSON endpoint. The body was already written in step 8 of the algorithm; if the response is committed, the header is dropped. Use a ResponseBodyAdvice or a filter.
  • Trusting the exception argument of afterCompletion. It is non-null only when no exception resolver handled the error. Once your @ExceptionHandler maps it to a 4xx/5xx, afterCompletion receives null; read the status code instead.
  • Slow first request after deploy because the servlet initializes lazily; set load-on-startup or send a warm-up request before taking traffic.
  • Thread starvation. Each blocking request holds a Tomcat thread for its full duration, including downstream calls. A slow dependency with no timeout exhausts the pool and the whole service stops answering.

@Controller, @RestController & Request Mapping

40m video45m practice

A request mapping is a set of conditions (path pattern, method, params, headers, consumes, produces) that a request must satisfy. Spring registers every mapping at startup, matches each request against all of them, and picks the most specific match, so understanding the conditions and the precedence rules explains every 404, 405, 406 and 415 you will see.

@Controller vs @RestController

Definition · stereotypes

@Controller is a @Component that RequestMappingHandlerMapping scans for @RequestMapping methods. A returned String is a view name resolved by a ViewResolver. @RestController is meta-annotated with @Controller and @ResponseBody, so every return value is written to the body by an HttpMessageConverter (JSON for objects, text/plain for a String).

@Controller
class HomePage {
    @GetMapping("/")
    String home(Model model) {
        model.addAttribute("now", Instant.now());
        return "home";                    // view name: templates/home.html with Thymeleaf
    }
}

Mixing the two in one class works (@ResponseBody on single methods of a @Controller), but keep server-rendered pages and JSON APIs in separate classes: their error handling, security and tests differ.

Composing mappings

@RestController
@RequestMapping(path = "/api/orders", produces = MediaType.APPLICATION_JSON_VALUE)
class OrderController {
    private final OrderService orders;
    OrderController(OrderService orders) { this.orders = orders; }

    @GetMapping                                        // GET /api/orders
    List<OrderDto> list(@RequestParam(defaultValue = "OPEN") OrderStatus status) {
        return orders.findByStatus(status);
    }

    @GetMapping("/{id:\\d+}")                          // GET /api/orders/42 only digits
    OrderDto get(@PathVariable long id) { return orders.get(id); }

    @GetMapping(path = "/{id:\\d+}", produces = "application/pdf")   // same path, other Accept
    byte[] invoice(@PathVariable long id) { return orders.invoicePdf(id); }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    @ResponseStatus(HttpStatus.CREATED)
    OrderDto create(@RequestBody CreateOrder cmd) { return orders.create(cmd); }

    @PostMapping(path = "/{id}", params = "action=cancel")         // POST /api/orders/42?action=cancel
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void cancel(@PathVariable long id) { orders.cancel(id); }

    @PatchMapping(path = "/{id}", headers = "X-Client=backoffice")
    OrderDto patch(@PathVariable long id, @RequestBody OrderPatch patch) { return orders.patch(id, patch); }
}

The class-level path is a prefix: /api/orders + /{id} = /api/orders/{id}. For the other attributes the combine rules differ: params and headers combine (both must hold), while a method-level consumes or produces overrides the class-level one, which is why invoice can produce PDF inside a JSON controller. The shortcuts @GetMapping, @PostMapping, @PutMapping, @PatchMapping and @DeleteMapping are @RequestMapping(method = …) with aliases; use them on methods and plain @RequestMapping on the class.

  • params: "action=cancel", "debug" (present), "!debug" (absent).
  • headers: the same syntax for headers. Don't use it for Accept/Content-Type; that is what produces/consumes are for.
  • consumes is checked against Content-Type, produces against Accept; both accept negation ("!text/plain").

Path pattern syntax

Boot 3 matches paths with PathPattern: patterns are parsed once at startup into a tree of path elements and matched against a pre-parsed request path, which is faster than string matching and has clearer rules. The older AntPathMatcher is still available via spring.mvc.pathmatch.matching-strategy=ant-path-matcher, mainly for legacy patterns.

Boot 3 changes

Trailing slashes no longer match. Spring Framework 6 turned trailing-slash matching off by default, so GET /api/orders/ is a 404 where Boot 2 served it. Either map both explicitly (@GetMapping({"", "/"})), redirect at the proxy, or, on Spring 6.2+, register a UrlHandlerFilter that redirects or rewrites. Suffix pattern matching is gone too: /files/{name} captures report.pdf whole, and /orders.json no longer selects JSON. And /**/legacy, legal under AntPathMatcher, fails to parse under PathPattern at startup.

Ambiguity and precedence

Two methods with identical conditions fail at startup: IllegalStateException: Ambiguous mapping. Cannot map 'orderController' method … There is already 'legacyOrderController' bean method … mapped. That's the good case. When different patterns both match one request, Spring sorts them by specificity: fewer URI variables and wildcards wins, a literal segment beats {var}, {var} beats *, and /** loses to everything. Ties on the pattern are broken by the other conditions in order (params, headers, consumes, produces, method); if two candidates are still equal for a given request, the request fails at runtime with Ambiguous handler methods mapped for '/api/orders/42'.

$ curl -i localhost:8080/api/orders/42 -H 'Accept: application/pdf'    -> 200, invoice()
$ curl -i localhost:8080/api/orders/42 -H 'Accept: text/csv'           -> 406 Not Acceptable
$ curl -i -X DELETE localhost:8080/api/orders/42                       -> 405 + Allow header
$ curl -i -X POST localhost:8080/api/orders -H 'Content-Type: text/xml' -> 415 Unsupported Media Type
$ curl -i localhost:8080/api/orders/                                   -> 404 in Boot 3

Organizing controllers

  • One controller per resource: OrderController for /api/orders, OrderItemController for /api/orders/{orderId}/items. URLs name nouns; actions that don't fit CRUD become sub-resources or explicit commands (POST /orders/{id}/cancellation).
  • Thin controllers. A controller method translates HTTP into a call and the result back into HTTP: bind, validate, call one service method, choose the status. No business rules, no loops over entities, no @Transactional.
  • Layering rule: controller → service → repository, never upward and never skipping a layer. Services own transactions and invariants; repositories own persistence; controllers deal in DTOs and never return JPA entities (lazy-loading and over-exposure problems, L302).
What breaks in production
  • Mobile clients built against Boot 2 send trailing slashes and get 404s after the Boot 3 upgrade. Check access logs for /-terminated paths before upgrading.
  • A @Controller (not @RestController) returns a DTO: Spring treats it as a model attribute and tries to render a view named after the path, producing a template-not-found or "circular view path" error.
  • A catch-all @GetMapping("/**") for an SPA swallows typos in API paths and returns HTML with 200 to API clients. Scope it, e.g. to paths without a dot outside /api.
  • Relying on produces without sending Accept: */* matches every candidate and the choice falls to specificity rules you didn't intend.

  3. Request /api/orders/; fix it once with an explicit mapping and once with a redirect, and decide which you would ship.
  4. Switch to ant-path-matcher, map /**/legacy, switch back and read the parse error.
  5. Take a 60-line controller method that queries a repository and computes totals; move the logic into a service and leave the controller at 3 lines.

Request Data: Path Variables, Params, Headers & Cookies

40m video45m practice

Every controller parameter is filled by a HandlerMethodArgumentResolver that reads one part of the request and converts it through the ConversionService. The annotations only say where to read from; the conversion, defaults and error statuses are shared machinery you can extend with your own resolver.

@PathVariable

@RestController
@RequestMapping("/api/customers/{customerId}/orders")
class CustomerOrderController {

    @GetMapping("/{orderId:\\d+}")
    OrderDto one(@PathVariable long customerId, @PathVariable long orderId) { ... }

    @GetMapping("/{orderId}/lines/{lineNo}")
    LineDto line(@PathVariable Map<String, String> vars) {   // all variables, unconverted
        return lines.find(Long.parseLong(vars.get("orderId")), Integer.parseInt(vars.get("lineNo")));
    }
}
Definition · name inference

Without an explicit name, @PathVariable long customerId uses the Java parameter name, which exists at runtime only if the code was compiled with -parameters. Boot's Maven parent and Gradle plugin set it. Spring 6.1 removed the old bytecode-debug-info fallback, so a project with a hand-written compiler config fails with "Name for argument of type [long] not specified, and parameter name information not available via reflection". Fix the build, or name it: @PathVariable("customerId").

required = false only makes sense when two patterns share one method (@GetMapping({"/orders", "/orders/{id}"})); a missing path variable on a single pattern is a server bug, so MissingPathVariableException maps to 500, not 400. A regex such as {orderId:\d+} moves validation into routing: /orders/abc becomes a 404 instead of a conversion error.

@RequestParam, and query vs path

@GetMapping
List<OrderDto> search(@PathVariable long customerId,
                      @RequestParam(defaultValue = "OPEN") OrderStatus status,   // implies required=false
                      @RequestParam(required = false) List<String> tag,         // ?tag=a&tag=b or ?tag=a,b
                      @RequestParam Optional<Integer> minTotal,                  // Optional = not required
                      @RequestParam MultiValueMap<String, String> all) { ... }  // every param, all values

A missing required parameter is MissingServletRequestParameterException (400). defaultValue is a string run through the same conversion, and it also applies to an empty value (?status=). Map<String, String> keeps the first value of each parameter; MultiValueMap keeps all of them.

Path or query?

Identity in the path, filters in the query. /customers/7/orders/42 names one resource; caches, logs and authorization rules key on it. Filtering, sorting and paging (?status=OPEN&sort=createdAt,desc&page=2) are optional, combinable and order-independent, so they belong in the query string. If a segment is optional or there could be several, it isn't identity.

A non-simple parameter without an annotation is treated as @ModelAttribute: Spring binds query (and form) parameters to it by name, using the canonical constructor for records. Once you have more than three or four filters, this is cleaner than a long @RequestParam list, and @Valid validates the whole object. A failure raises a BindException (in Spring 6, its subclass MethodArgumentNotValidException), unless the next parameter is a BindingResult, in which case you get the errors and must handle them yourself (L304, L305).

Matrix variables are name=value pairs inside a path segment: GET /cars/red;year=2020;owners=2, read with @MatrixVariable int year. Semicolon content is stripped by default; the reference documentation's recipe re-enables it:

@Override

    var helper = new UrlPathHelper();
    helper.setRemoveSemicolonContent(false);
    configurer.setUrlPathHelper(helper);
}

They are rare in public APIs; prefer query parameters unless you need per-segment parameters.

Custom resolution: @CurrentUser

@Target(ElementType.PARAMETER) @Retention(RetentionPolicy.RUNTIME)
@interface CurrentUser {}

record AuthUser(String id, boolean admin) {}

class CurrentUserResolver implements HandlerMethodArgumentResolver {
    @Override
    public boolean supportsParameter(MethodParameter p) {
        return p.hasParameterAnnotation(CurrentUser.class) && p.getParameterType() == AuthUser.class;
    }

    @Override
    public Object resolveArgument(MethodParameter p, ModelAndViewContainer mav,
                                  NativeWebRequest req, WebDataBinderFactory binders) {
        Principal principal = req.getUserPrincipal();
        if (principal == null) throw new ResponseStatusException(HttpStatus.UNAUTHORIZED);
        return new AuthUser(principal.getName(), req.isUserInRole("ADMIN"));
    }
}

// WebMvcConfigurer: resolvers.add(new CurrentUserResolver());
// Controller:       OrderDto mine(@CurrentUser AuthUser user, @PathVariable long id)

Register it in WebMvcConfigurer.addArgumentResolvers. Custom resolvers run after the built-in ones, so you can't use this hook to change how, say, Principal is resolved; use your own annotation or type instead.

What breaks in production
  • Unbounded lists. ?id=1&id=2… with 50,000 values becomes a 50,000-element IN clause. Cap collection sizes with @Size.
  • Trusting identity headers. X-User-Id is only safe if the gateway strips client-supplied copies and sets it after verifying a token.
  • Logging headers wholesale leaks Authorization and session cookies into logs.
  • Enum parameters are case-sensitive: ?status=open is a 400. Register a case-insensitive Converter if clients need it, and document it.

Request/Response Bodies & ResponseEntity

40m video45m practice

Bodies cross the HTTP boundary through HttpMessageConverters: @RequestBody asks one to read the request stream into an object, and @ResponseBody asks one to write your return value. ResponseEntity is the return type you use when the status and headers depend on what happened, and it is how a REST API states 201, 202, 204 and 404 precisely.

@RequestBody and the read-once stream

For a @RequestBody parameter, RequestResponseBodyMethodProcessor takes the request's Content-Type and the parameter's type and asks each converter canRead(type, mediaType); the first that says yes (Jackson for application/json) deserializes the stream. Records deserialize through their canonical constructor. The failure modes are distinct: no converter for the content type → 415; malformed JSON or a type mismatch → HttpMessageNotReadableException, 400; an empty body with the default required = true → 400 "Required request body is missing".

Definition · single-read body

The body is a ServletInputStream straight off the socket. Once something reads it, it is at end-of-stream: there's no rewind. A filter that reads the body to log it leaves the controller with nothing. ContentCachingRequestWrapper solves this by copying bytes into a buffer as the downstream code reads them, so the cache is only filled after chain.doFilter returns.

class BodyLoggingFilter extends OncePerRequestFilter {
    private static final Logger log = LoggerFactory.getLogger(BodyLoggingFilter.class);

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        var wrapped = new ContentCachingRequestWrapper(req, 10_000);   // cache at most 10 kB
        chain.doFilter(wrapped, res);
        String body = new String(wrapped.getContentAsByteArray(), StandardCharsets.UTF_8);
        log.debug("{} {} body={}", req.getMethod(), req.getRequestURI(), body);
    }
}

ResponseEntity<T>

@RestController
@RequestMapping("/api/orders")
class OrderController {
    private final OrderService orders;
    OrderController(OrderService orders) { this.orders = orders; }

    @PostMapping
    ResponseEntity<OrderDto> create(@RequestBody CreateOrder cmd) {
        OrderDto created = orders.create(cmd);
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                .path("/{id}").buildAndExpand(created.id()).toUri();     // /api/orders/42
        return ResponseEntity.created(location).body(created);           // 201 + Location
    }

    @GetMapping("/{id}")
    ResponseEntity<OrderDto> get(@PathVariable long id) {
        return orders.find(id)
                .map(o -> ResponseEntity.ok()
                        .eTag(Long.toString(o.version()))
                        .cacheControl(CacheControl.maxAge(Duration.ofSeconds(30)).cachePrivate())
                        .body(o))
                .orElseGet(() -> ResponseEntity.notFound().build());
    }

    @PostMapping("/{id}/exports")
    ResponseEntity<Void> export(@PathVariable long id) {
        String jobId = orders.startExport(id);

Spring MVC never serializes anything itself: it negotiates a media type from the request, then walks an ordered list of HttpMessageConverters and lets the first one that can handle the (type, media type) pair do the work. Customizing JSON, adding XML or CSV, and fixing 406 errors all come down to changing that list or the negotiation inputs, preferably without replacing what Boot built.

How the response type is chosen

Acceptable types come from the ContentNegotiationManager; by default only the Accept header counts. Producible types come from the mapping's produces or, if absent, from every converter that can write the return type. Spring intersects the two, sorts by specificity and quality value, picks the first concrete type, and asks the converters in order. Because Jackson accepts application/*+json, a vendor type such as application/vnd.acme.order.v2+json works with no extra code, which is the basis of media-type versioning (L312).

Definition · the three levels

Properties (spring.jackson.*) for features, inclusion, naming and time zone. Data Binding, Formatters & @ModelAttribute

35m video40m practice

Query and form parameters are flat strings; WebDataBinder turns them into a typed object graph by matching parameter names to properties or constructor arguments and converting each value. That convenience is also an attack surface: whatever the binder can reach, a client can set, which is why the target should be a request DTO and never an entity.

How WebDataBinder works

Definition · WebDataBinder

A DataBinder created per request and per target. For a mutable class it uses a BeanWrapper and setter calls (property binding). For records and other classes with a single constructor it uses constructor binding, matching parameter names to constructor parameter names; since Spring 6.1 this also reaches nested records, lists and maps. Each value passes through the ConversionService (and any registered PropertyEditors). @ModelAttribute parameters and form-backed objects go through it; @RequestBody does not: Jackson handles bodies, and none of the binder's settings apply there.

@InitBinder methods run once per binder, so you can restrict them by name: @InitBinder("order"). StringTrimmerEditor(true) turns blank inputs into null, so @NotNull catches an empty text field. setDisallowedFields is a deny-list; setAllowedFields is the safer allow-list. A @ModelAttribute method adds a model attribute before every handler of the controller (dropdown values, the entity being edited); it costs a call per request, so keep it cheap or move it to the one handler that needs it.

The BindingResult parameter must come immediately after the object it describes. With it, errors are handed to you; without it, a failure throws (see L305). FieldError.isBindingFailure() separates a conversion failure (qty=abc, code typeMismatch) from a constraint violation (qty=0, code Positive); message lookup uses those codes, so typeMismatch.order.lines.qty=Quantity must be a number in messages.properties replaces the raw exception text.

Mass assignment: why request DTOs matter

Bind a form straight to a JPA entity with setters and every property is writable: a client adds &role=ADMIN or &id=17 and the binder sets it, and a later save persists it. The binder's reach is wider than it looks, too: Spring4Shell (CVE-2022-22965) used property paths starting at class.module.classLoader to reach Tomcat internals through ordinary data binding on JDK 9+. The defence is structural. Bind to a DTO that has exactly the fields this use case may set, then map it to the entity in the service; allow-lists on the binder are a second layer, not the first.

What breaks in production
  • Lambda converters. registry.addConverter(s -> …) loses its generic types to erasure and fails with "Unable to determine source type <S> and target type <T>". Use a class, or the overload that takes both Class arguments.
  • Thinking @InitBinder protects JSON endpoints. Allowed fields and editors don't apply to @RequestBody; only the DTO's shape does.
  • Misplaced BindingResult (not directly after the target): Spring throws instead of collecting errors.
  • Locale-dependent parsing. @NumberFormat and Formatters use the request locale, so 1,250.00 parses differently for a German browser. Use ISO formats for anything machine-sent.

Bean Validation I: Constraints, @Valid & Error Reporting

45m video50m practice

Bean Validation lets you declare input rules as annotations on the request DTO and have one engine check them before your code runs. The annotations are the easy part; the details that matter are null semantics, which exception each validation site raises, and therefore which HTTP status the client actually sees.

The specification and the starter

Definition · Jakarta Bean Validation

A specification (JSR 380 was version 2.0; Jakarta Bean Validation 3.0 moved it to the jakarta.validation package used by Boot 3) defining constraint annotations, a Validator API and message interpolation. Hibernate Validator is the reference implementation. Spring wraps it in LocalValidatorFactoryBean, which is both a jakarta.validation.Validator and a Spring Validator, and MVC calls it for @Valid arguments.

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

The web starter has not included it since Boot 2.3. Without it, @Valid compiles (if the API jar is present transitively) and silently does nothing, because no provider is on the classpath.

The built-in constraints

One rule governs almost all of them: null is valid. @Size, @Email, @Pattern, @Min and the rest only check non-null values, so an optional field needs no special handling and a required one needs an explicit null check.

@NotNull works on any type; @NotEmpty on strings, collections, maps and arrays (size > 0); @NotBlank on strings only (at least one non-whitespace character). For text input you almost always want @NotBlank.

  • Size and number: @Size(min, max) (string length, collection size); @Min/@Max take a long and suit integer types and BigDecimal; @DecimalMin("0.01")/@DecimalMax take a string and an inclusive flag; @Digits(integer = 7, fraction = 2) caps precision; @Positive, @PositiveOrZero, @Negative, @NegativeOrZero. double/float are not supported by the spec for the min/max family because of rounding.
  • Strings: @Email (deliberately permissive: a@b passes), @Pattern(regexp) (must match the whole value).
  • Time: @Past, @PastOrPresent, @Future, @FutureOrPresent on java.time types, evaluated against the validator's clock.
  • Booleans: @AssertTrue/@AssertFalse.
  • Hibernate Validator extras (org.hibernate.validator.constraints): @Length, @Range, @URL, @CreditCardNumber (Luhn check), @UniqueElements. They tie your DTOs to Hibernate Validator, which is usually fine.

Bean Validation II: Custom Constraints, Groups & Cross-Field Rules

45m video50m practice

A custom constraint is an annotation plus a ConstraintValidator; class-level constraints handle rules that span fields, and groups decide which rules apply in which use case. The harder skill is placement: request validation checks the shape of input, domain objects enforce invariants, and the database is the only place a uniqueness rule can actually hold.

Anatomy of a custom constraint

@Documented
@Constraint(validatedBy = UniqueEmailValidator.class)
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface UniqueEmail {
    String message() default "{customer.email.taken}";   // the three required members
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

class UniqueEmailValidator implements ConstraintValidator<UniqueEmail, String> {
    private final CustomerRepository customers;

    UniqueEmailValidator(CustomerRepository customers) { this.customers = customers; }   // Spring injects

    @Override
    public void initialize(UniqueEmail annotation) { }    // read annotation attributes here if any

    @Override
    public boolean isValid(String email, ConstraintValidatorContext ctx) {
        return email == null || !customers.existsByEmailIgnoreCase(email);   // null is someone else's job
    }
}
Definition · constraint annotation

An annotation meta-annotated with @Constraint(validatedBy = …) that declares the three members the specification requires: message, groups and payload (metadata such as a severity marker; rarely used). initialize runs once per constraint use, so parse annotation attributes there and keep isValid cheap and thread-safe. Spring's LocalValidatorFactoryBean creates validators through a SpringConstraintValidatorFactory, which is why constructor injection works.

Interview trap · uniqueness check

@UniqueEmail is a check-then-act race. Two concurrent sign-ups with the same address both pass existsByEmail, both insert, and you have a duplicate. Only a unique index in the database closes the window; catch the resulting DataIntegrityViolationException and return 409 (L307). Keep the validator for a friendly early message if you like, but on the request DTO only: JPA providers also run Bean Validation on persist and update, and that path may use a validator factory that can't inject Spring beans.

Cross-field rules with class-level constraints

@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = DateRangeValidator.class)

    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};

interface HasDateRange { LocalDate from(); LocalDate to(); }

class DateRangeValidator implements ConstraintValidator<ValidDateRange, HasDateRange> {
    @Override
    public boolean isValid(HasDateRange r, ConstraintValidatorContext ctx) {
        if (r == null || r.from() == null || r.to() == null || !r.to().isBefore(r.from())) return true;
        ctx.disableDefaultConstraintViolation();                      // replace the class-level violation
        ctx.buildConstraintViolationWithTemplate(ctx.getDefaultConstraintMessageTemplate())
           .addPropertyNode("to")                                     // report it on the "to" field
           .addConstraintViolation();
        return false;
    }
}

@ValidDateRange
record BookingRequest(@NotNull LocalDate from, @NotNull LocalDate to, @Positive int guests)
        implements HasDateRange {}

A field constraint sees one value; a constraint on the type sees the whole object, so it can compare from with to or password with confirmPassword (@PasswordsMatch has the same shape). By default its violation has an empty property path, which a form can't attach to any input; ConstraintValidatorContext lets you redirect it to a field so the client's error UI works unchanged. The interface lets one validator serve every DTO that has a date range.

Groups, sequences and composed constraints

  • Groups are marker interfaces. A constraint with no groups belongs to Default. Spring's @Validated(…) (unlike @Valid) accepts groups.
  • Naming groups replaces Default: @Validated(OnCreate.class) alone skips @NotBlank name. List Default.class explicitly or make OnCreate extends Default.
  • @GroupSequence validates groups in order and stops at the first group with violations, so the database-hitting @UniqueSku never runs on a blank SKU.
  • Redefining the default group: @GroupSequence({ProductForm.class, Expensive.class}) placed on the class itself makes plain @Valid use that order for this type (the list must include the class).

Validation at the right layer

Annotations on a DTO protect one endpoint. A rule such as "an order total is never negative" belongs in the domain type, where no code path can create a violating instance. Don't duplicate business rules into annotations that need a repository; that is service logic.

What breaks in production
  • User input in a message template. buildConstraintViolationWithTemplate("Unknown value " + input) lets Hibernate Validator evaluate ${…} expressions in attacker-supplied text: expression injection. Pass values as message parameters or escape them; never concatenate.
  • Groups that silently drop Default and skip half the rules on create.
  • A repository call in a validator runs on every validation, including bulk imports: 10,000 rows means 10,000 queries. Batch-check instead.
  • Class-level violations with an empty path are dropped by front ends that only render field errors.

Exception Handling: @ExceptionHandler & @ControllerAdvice

45m video50m practice

An exception that escapes a controller is passed down a chain of HandlerExceptionResolvers until one turns it into a response; if none does, the servlet container forwards to Boot's /error endpoint. A single @RestControllerAdvice at the front of that chain, which maps every exception you expect to a status and logs the ones you don't exactly once, is the backbone of a predictable API.

Boot's default: /error and BasicErrorController

When an exception is unresolved, or code calls response.sendError(404), Tomcat performs an ERROR dispatch to the configured error page, which Boot maps to BasicErrorController at /error. Browsers (Accept: text/html) get the "Whitelabel Error Page"; other clients get JSON built by DefaultErrorAttributes.

{"timestamp":"2025-03-14T10:15:30.120+00:00","status":500,"error":"Internal Server Error","path":"/api/orders/42"}

server:
  error:
    include-message: never          # never (default) | always | on_param
    include-stacktrace: never
    include-binding-errors: never
    whitelabel:
      enabled: false                # no HTML page for API services

The defaults are safe: no message, no stack trace, no binding errors. They are also useless to clients, which is why APIs handle exceptions before they reach /error. Note the cost of the fallback path, too: an ERROR dispatch re-enters the filter chain, so filters see the request twice unless they are OncePerRequestFilters.

@ExceptionHandler, local and global

Definition · handler resolution

For a thrown exception, Spring first searches the throwing controller's own @ExceptionHandler methods, then each @ControllerAdvice bean in @Order sequence (lowest value first). Within one class, the handler declared for the closest superclass of the exception wins, and a match on the exception itself beats a match on its cause. Across classes, order beats specificity: an earlier advice's Exception handler wins over a later advice's OrderNotFoundException handler. Handler methods can take the exception, WebRequest, HttpServletRequest, Locale and the HandlerMethod that failed, and can return ResponseEntity, ProblemDetail or any body object.

@RestControllerAdvice is @ControllerAdvice plus @ResponseBody. Scope it when one app serves different audiences: basePackages = "com.acme.api", assignableTypes = {OrderController.class}, or annotations = RestController.class keeps JSON handling away from server-rendered pages, which need an HTML error view instead.

One advice that owns the error contract

@RestControllerAdvice(basePackages = "com.acme.shop.api")
class ApiExceptionHandler extends ResponseEntityExceptionHandler {
    private static final Logger log = LoggerFactory.getLogger(ApiExceptionHandler.class);

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException ex) {
        log.debug("Not found: {}", ex.getMessage());                             // 4xx: debug, no trace
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }

    @ExceptionHandler({DataIntegrityViolationException.class, OptimisticLockingFailureException.class})
    ProblemDetail conflict(RuntimeException ex) {
        log.info("Conflict: {}", ex.getClass().getSimpleName());                // no SQL in the response
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
                "The resource already exists or was changed by someone else; reload and retry.");
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex, HttpServletRequest req) {
        log.error("Unhandled error on {} {}", req.getMethod(), req.getRequestURI(), ex);   // 5xx: once, with trace
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error.");
    }

    @Override                                                                     // Spring's own exception
    protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ProblemDetail body = ex.getBody();
        body.setProperty("violations", ex.getBindingResult().getFieldErrors().stream()
                .map(e -> Map.of("field", e.getField(), "message", String.valueOf(e.getDefaultMessage())))
                .toList());
        return handleExceptionInternal(ex, body, headers, status, request);
    }
}

ResponseEntityExceptionHandler already contains @ExceptionHandlers for Spring MVC's exceptions, each delegating to a protected method you can override: handleMethodArgumentNotValid, handleHttpMessageNotReadable (bad JSON), handleHttpRequestMethodNotSupported, handleNoHandlerFoundException, handleMissingServletRequestParameter, handleTypeMismatch and, from 6.1, handleNoResourceFoundException and handleHandlerMethodValidationException; handleExceptionInternal is the common exit. Extending it means Spring's exceptions and yours produce the same shape. Boot's own ProblemDetail advice (enabled by spring.mvc.problemdetails.enabled) backs off when you declare one.

Conflicts map to 409. A unique-index violation surfaces as Spring's DataIntegrityViolationException; a stale @Version arrives as ObjectOptimisticLockingFailureException, a subclass of OptimisticLockingFailureException, because Spring translates the JPA OptimisticLockException. Both mean "your view of the data is out of date", which the client can fix by re-reading.

@ResponseStatus vs ResponseEntity vs ResponseStatusException

  • @ResponseStatus(NOT_FOUND) on the exception class: one line, but the status is all you control. The response goes through sendError and /error, so the body is Boot's generic one, and you can't add headers or log.
  • An @ExceptionHandler returning ResponseEntity or ProblemDetail: full control over body, headers (Retry-After on 429/503), log level and metrics. The default choice for an API.
  • throw new ResponseStatusException(HttpStatus.FORBIDDEN, "Not your order"): no custom class, fine for one-offs and prototypes. In Spring 6 it is an ErrorResponse, so it renders as a problem detail. It couples service code to HTTP, so keep it in controllers.

Logging strategy and what never leaves the server

  • 5xx: log at ERROR with the stack trace, once, in the advice, with the trace id in the MDC so the log line matches the response.
  • 4xx: the client's problem. Log at DEBUG (or INFO for security-relevant ones such as 401/403), without stack traces; count them in metrics instead.
  • Never log and rethrow. Catching, logging and rethrowing at every layer prints the same trace three times and makes incidents harder to read. Either handle the exception or let it propagate to the one place that logs.
What breaks in production
  • Information leaks: stack traces, exception class names, SQL and constraint names (uk_customer_email tells an attacker the email exists), internal host names, file paths, framework versions. A 500 body says "unexpected error" plus a trace id, nothing else. Never set include-stacktrace=always in production.
  • A catch-all in a high-priority advice swallows the specific handlers of a later advice (order beats specificity).
  • Unmapped ConstraintViolationException from @Validated beans becomes a 500 and pages someone for a client error.
  • Exceptions thrown after the response is committed (mid-stream) can't change the status; the client sees a truncated body. Handle streaming errors in the stream.

Problem Details (RFC 9457) & Error Contract Design

40m video45m practice

Errors are part of your API contract, and clients write code against them. RFC 9457 gives the envelope (application/problem+json), Spring 6 gives first-class types for it, and your job is to fill it with a stable machine-readable code, a human explanation and a trace id, the same way for every error from every component.

The RFC 9457 format

Definition · problem details

A JSON object served as application/problem+json with five standard members. type: a URI identifying the problem type; about:blank (the default) means "nothing beyond the status code". title: a short summary of the type that doesn't change between occurrences except for localization. status: the HTTP status, advisory only. detail: an explanation of this occurrence, written to help the client fix it. instance: a URI for this occurrence. Any other member is an extension, and clients must ignore extensions they don't know. RFC 9457 (2023) obsoletes RFC 7807 with the same format plus a registry of common types and guidance for reporting several problems at once. It also says clients shouldn't parse detail; machine-readable facts go in extensions.

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://errors.acme.com/order-not-cancelable",
  "title": "Order cannot be cancelled",
  "status": 409,
  "detail": "Order 42 has already shipped.",
  "instance": "/api/orders/42/cancellation",
  "code": "ORDER_NOT_CANCELABLE",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2025-03-14T10:15:30Z"
}

Spring 6's built-in support

  • ProblemDetail: the body type. forStatus(…), forStatusAndDetail(…), setters for type, title, detail, instance, and setProperty(name, value) for extensions, which Jackson writes as top-level members. Return it from a handler and the status comes from it; the content type becomes application/problem+json, and Spring fills instance with the request path if you leave it empty.
  • ErrorResponse: an interface (status, headers, ProblemDetail body, message codes) that every Spring MVC exception implements in Spring 6.
  • ErrorResponseException: a RuntimeException implementing it, to extend for your own exceptions; ResponseStatusException is one.
  • spring.mvc.problemdetails.enabled=true: Boot registers a ResponseEntityExceptionHandler advice so Spring's own exceptions render as problem details. It backs off if you provide your own subclass, which you will.

An error catalogue in code

enum ErrorCode {
    ORDER_NOT_FOUND(HttpStatus.NOT_FOUND, "Order not found"),
    ORDER_NOT_CANCELABLE(HttpStatus.CONFLICT, "Order cannot be cancelled"),
    VALIDATION_FAILED(HttpStatus.BAD_REQUEST, "Request validation failed"),
    RATE_LIMITED(HttpStatus.TOO_MANY_REQUESTS, "Too many requests"),
    INTERNAL(HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error");

    final HttpStatus status;
    final String title;
    ErrorCode(HttpStatus status, String title) { this.status = status; this.title = title; }

    URI type() { return URI.create("https://errors.acme.com/" + name().toLowerCase(Locale.ROOT).replace('_', '-')); }

    ProblemDetail problem(String detail) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, detail);
        pd.setType(type());
        pd.setTitle(title);
        pd.setProperty("code", name());
        return pd;
    }
}

class ApiException extends ErrorResponseException {
    ApiException(ErrorCode code, String detail) { super(code.status, code.problem(detail), null); }
}

// in a service:  throw new ApiException(ErrorCode.ORDER_NOT_CANCELABLE, "Order " + id + " has already shipped.");

Because ApiException is an ErrorResponse, the ResponseEntityExceptionHandler renders it with no handler of its own. The catalogue is the enum plus a documentation page per type URI: what it means, whether retrying helps, what the client should do. Treat it as API surface. A code is never renamed or reused for a different meaning; adding a code is safe only if clients fall back to the status family for codes they don't know; and the catalogue is published with the OpenAPI spec (L313).

A ResponseBodyAdvice also sees bodies returned by @ExceptionHandler methods, so one class stamps every problem. The traceId must be the one in your logs and distributed traces; then a support ticket that quotes it leads straight to the failing span. Class-level violations go in the list with the object name as field.

Localization and consistency across components

Localize title and detail through the MessageSource using the request's Locale; never localize code or type. For Spring's own exceptions, ResponseEntityExceptionHandler looks up message keys of the form problemDetail.title.<exception class> and problemDetail.<exception class>, so overriding their text is a properties change.

Errors also come from places your advice never sees: Spring Security's filters (401/403), the servlet container's /error, WebFlux services, and the API gateway (429, 502, 504). Use the same shape everywhere. WebFlux has the same ProblemDetail types and its own ResponseEntityExceptionHandler; Security needs an AuthenticationEntryPoint and an AccessDeniedHandler that write problem JSON; the gateway needs a custom error handler. Shipping the ErrorCode catalogue and the problem factory as a small shared library is what keeps them aligned.

What breaks in production
  • Clients parsing detail because no code existed; rewording a message then breaks a mobile release.
  • Echoing rejectedValue for passwords, tokens or card numbers into responses and logs. Mask by field name or annotation.
  • Mismatched status: a ProblemDetail saying 404 inside a ResponseEntity with status 200. Let the problem drive the status.
  • Two error shapes: problem details from controllers, Boot's /error JSON from filters and Security. Test a 401, a 404 for an unknown path and a 500 from a filter, not only controller errors.

Interceptors, Filters & Request Logging

40m video45m practice

Filters and interceptors both run code around every request, at different layers. A filter belongs to the servlet container, sees everything and can wrap the request and response; an interceptor belongs to Spring MVC, sees only mapped requests but knows which handler method will run. Choose by what the code needs to see, and get the order right.

HandlerInterceptor semantics

Definition · the three callbacks

preHandle runs before the handler, in registration order; returning false stops the request, and the interceptor must then have written the response itself. postHandle runs after the handler returns, in reverse order, before view rendering; it is skipped if the handler threw, and for @ResponseBody methods the body is already written, so it can't change it. afterCompletion runs last, in reverse order, even after an exception, but only for interceptors whose preHandle returned true. Cleanup goes there.

class TenantInterceptor implements HandlerInterceptor {
    private final TenantDirectory tenants;
    TenantInterceptor(TenantDirectory tenants) { this.tenants = tenants; }

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) throws IOException {
        String id = req.getHeader("X-Tenant-Id");
        if (id == null || !tenants.exists(id)) {
            res.sendError(HttpServletResponse.SC_BAD_REQUEST, "Unknown tenant");
            return false;                                   // handler never runs
        }
        TenantContext.set(id);                              // ThreadLocal
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        TenantContext.clear();                              // pooled threads: always clear
    }
}

@Component
class HandlerTimingInterceptor implements HandlerInterceptor {
    private static final String START = HandlerTimingInterceptor.class.getName() + ".start";
    private final MeterRegistry registry;
    HandlerTimingInterceptor(MeterRegistry registry) { this.registry = registry; }

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        req.setAttribute(START, System.nanoTime());
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        if (!(handler instanceof HandlerMethod hm) || !(req.getAttribute(START) instanceof Long start)) return;
        Timer.builder("api.handler.duration")
             .tag("handler", hm.getBeanType().getSimpleName() + "." + hm.getMethod().getName())  // bounded
             .tag("status", Integer.toString(res.getStatus()))
             .register(registry)
             .record(System.nanoTime() - start, TimeUnit.NANOSECONDS);
    }
}

@Configuration
class InterceptorConfig implements WebMvcConfigurer {
    private final HandlerTimingInterceptor timing;
    private final TenantDirectory tenants;
    InterceptorConfig(HandlerTimingInterceptor timing, TenantDirectory tenants) { this.timing = timing; this.tenants = tenants; }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(timing).addPathPatterns("/api/**");
        registry.addInterceptor(new TenantInterceptor(tenants))
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/public/**", "/api/health");
    }
}

Interceptors run in registration order (or by .order(n)). Path patterns use the same syntax as mappings. The HandlerMethod argument is what makes interceptors useful: you can read annotations on the target method (hm.getMethodAnnotation(RequiresFeature.class)) and tag metrics by handler name, a bounded set, unlike raw URIs with ids in them. Boot already records http.server.requests for every request; add your own timer only for a dimension that one lacks.

Correlation ids and body logging

@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
class CorrelationIdFilter extends OncePerRequestFilter {
    static final String HEADER = "X-Request-Id";
    private static final Pattern SAFE = Pattern.compile("[A-Za-z0-9-]{8,64}");

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String incoming = req.getHeader(HEADER);
        String id = incoming != null && SAFE.matcher(incoming).matches() ? incoming : UUID.randomUUID().toString();
        MDC.put("requestId", id);
        res.setHeader(HEADER, id);                       // before anything commits the response
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.remove("requestId");
        }
    }
}

        } finally {
            log.info("{} {} -> {} in {} ms req={} res={}", req.getMethod(), req.getRequestURI(),
                    response.getStatus(), (System.nanoTime() - t0) / 1_000_000,
                    mask(request.getContentAsByteArray()), mask(response.getContentAsByteArray()));
            response.copyBodyToResponse();               // without this the client gets an empty body
        }
    }

    private static String mask(byte[] bytes) {
        String s = new String(bytes, 0, Math.min(bytes.length, MAX), StandardCharsets.UTF_8);
        return SECRET.matcher(s).replaceAll("$1***\"");
    }
}

The correlation filter accepts an upstream id only if it looks safe (no log injection through newlines), otherwise generates one, and puts it in the MDC so every log line of the request carries it. With Micrometer Tracing on the classpath, Boot already adds traceId/spanId to the MDC; a request id is still useful for clients and for systems outside your tracing.

Off-the-shelf options

  • CommonsRequestLoggingFilter: register it as a bean, configure setIncludeQueryString, setIncludePayload, setMaxPayloadLength, setIncludeHeaders, and set its logger to DEBUG. Fine for development; it has no masking.
  • Actuator httpexchanges (Boot 3's rename of httptrace): declare an HttpExchangeRepository bean such as InMemoryHttpExchangeRepository (keeps the last 100) and expose the endpoint. It records method, URI, status, timing and selected headers, not bodies. Not a substitute for logs.
What breaks in production
  • Forgetting copyBodyToResponse(): every response arrives empty with a 200.
  • Response caching on streams: SSE and large downloads get buffered in memory until they finish, which breaks streaming and costs heap.
  • ThreadLocal leaks: a tenant id set in preHandle and not cleared in afterCompletion leaks to the next request on that thread: one tenant sees another's data.
  • Filters registered twice (as a @Component and via a hand-built registration without Boot noticing) log every request twice.
  • Logging full bodies of every request: personal data in logs is a compliance problem, and log volume becomes a cost line. Log bodies at DEBUG, sampled, masked and capped.

File Upload & Download

40m video45m practice

An upload is untrusted bytes with an untrusted name and an untrusted content type, and a download is a stream that should never be loaded into memory whole. The Spring APIs (MultipartFile, Resource, StreamingResponseBody) are small; the work is in limits, validation, storage layout and keeping big payloads off your heap, or off your servers entirely.

multipart/form-data on the wire

POST /api/documents HTTP/1.1
Content-Type: multipart/form-data; boundary=XyZ123

--XyZ123
Content-Disposition: form-data; name="meta"
Content-Type: application/json

{"title":"Q3 report","tags":["finance"]}
--XyZ123
Content-Disposition: form-data; name="file"; filename="q3.pdf"
Content-Type: application/pdf

%PDF-1.7 ...binary bytes...
--XyZ123--

The body is a list of parts separated by a boundary string the client chooses. Each part has its own headers: a name (the form field), optionally a filename, and its own Content-Type. Both the filename and the content type are whatever the client says. Boot parses the body with the Servlet Part API via StandardServletMultipartResolver, writing large parts to temporary files.

Receiving files

record DocumentMeta(@NotBlank String title, List<String> tags) {}
record StoredDocument(UUID id, String title, String contentType, long size) {}

@RestController
@RequestMapping("/api/documents")
class DocumentController {
    private final DocumentStorage storage;
    DocumentController(DocumentStorage storage) { this.storage = storage; }

    @PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    ResponseEntity<StoredDocument> upload(@RequestPart("meta") @Valid DocumentMeta meta,   // JSON part
                                          @RequestPart("file") MultipartFile file) throws IOException {
        StoredDocument doc = storage.store(meta, file);
        return ResponseEntity.created(URI.create("/api/documents/" + doc.id())).body(doc);
    }

    @PostMapping(path = "/batch", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    List<StoredDocument> uploadMany(@RequestParam("files") List<MultipartFile> files) throws IOException {
        var result = new ArrayList<StoredDocument>();
        for (MultipartFile f : files) result.add(storage.store(new DocumentMeta(f.getOriginalFilename(), List.of()), f));
        return result;
    }
}
$ curl -F 'meta={"title":"Q3 report"};type=application/json' -F 'file=@q3.pdf' localhost:8080/api/documents
  • MultipartFile: getName() (part name), getOriginalFilename() and getContentType() (both client-supplied), getSize(), getInputStream() (stream it), getBytes() (loads it all into memory), transferTo(Path) (moves the temporary file when it can, otherwise copies).
  • @RequestPart vs @RequestParam: both bind file parts, but @RequestPart runs non-file parts through an HttpMessageConverter according to the part's Content-Type, which is how a JSON part becomes a validated record. A JSON part sent without a content type arrives as application/octet-stream and fails with 415.
  • Several files: List<MultipartFile> or MultipartFile[] for a repeated part name.

Limits

spring:
  servlet:
    multipart:
      max-file-size: 20MB          # per part; default 1MB
      max-request-size: 25MB       # whole body; default 10MB
      file-size-threshold: 1MB     # parts below this stay in memory; default 0B

Exceeding a limit raises MaxUploadSizeExceededException while the body is parsed, before your controller runs; Spring 6.1+'s ResponseEntityExceptionHandler maps it to 413, and on older versions you add an @ExceptionHandler in your advice. Enforce the same ceiling at the reverse proxy or gateway as well, so a 2 GB body is refused before it uses a worker thread and disk space on your instance.

Storing uploads safely

@Service
class DocumentStorage {
    private static final Map<String, byte[]> MAGIC = Map.of(
            "application/pdf", new byte[] {0x25, 0x50, 0x44, 0x46, 0x2D},                     // %PDF-
            "image/png", new byte[] {(byte) 0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A});
    private final Path root;                                  // outside any static/web directory

    DocumentStorage(@Value("${acme.uploads.root}") Path root) { this.root = root.toAbsolutePath().normalize(); }

    StoredDocument store(DocumentMeta meta, MultipartFile file) throws IOException {
        String type = sniff(file);                            // ignore the client's Content-Type
        UUID id = UUID.randomUUID();
        Path target = root.resolve(id.toString()).normalize(); // server-chosen name, no user input
        if (!target.startsWith(root)) throw new IllegalStateException("Path escapes upload root");
        file.transferTo(target);
        // record (id, original name, type, size, status=PENDING_SCAN) and queue a malware scan
        return new StoredDocument(id, meta.title(), type, file.getSize());
    }

    private static String sniff(MultipartFile file) throws IOException {
        byte[] head;
        try (InputStream in = file.getInputStream()) { head = in.readNBytes(8); }
        return MAGIC.entrySet().stream()
                .filter(e -> head.length >= e.getValue().length
                        && Arrays.equals(head, 0, e.getValue().length, e.getValue(), 0, e.getValue().length))
                .map(Map.Entry::getKey)
                .findFirst()
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.UNSUPPORTED_MEDIA_TYPE));
    }
}
Definition · upload hardening checklist
  • Type by content: check the leading magic bytes (or use Apache Tika) against an allow-list; the header and extension are client claims.
  • No user input in paths: a filename like ../../etc/cron.d/x is path traversal. Generate the stored name (UUID), keep the original only as metadata, and still check normalize().startsWith(root).
  • Store outside the web root (or in object storage) so an uploaded .jsp or .html can never be served or executed as code.
  • Scan before use: mark files pending, scan asynchronously (e.g. ClamAV), and only serve them once clean.
  • Size limits before buffering: proxy and multipart limits, and never getBytes() on an unbounded file.

Downloads: Resource, ranges and streaming

@GetMapping("/{id}/content")
ResponseEntity<Resource> download(@PathVariable UUID id) {
    StoredFile f = storage.find(id);
    return ResponseEntity.ok()
            .contentType(MediaType.parseMediaType(f.contentType()))
            .contentLength(f.size())
            .header(HttpHeaders.CONTENT_DISPOSITION, ContentDisposition.attachment()
                    .filename(f.originalName(), StandardCharsets.UTF_8)     // RFC 5987 filename*
                    .build().toString())
            .header("X-Content-Type-Options", "nosniff")
            .body(new FileSystemResource(f.path()));                       // streamed, supports Range
}

@GetMapping(path = "/export", produces = "text/csv")
ResponseEntity<StreamingResponseBody> export() {
    StreamingResponseBody body = out -> {                     // runs on an MVC async thread
        var w = new BufferedWriter(new OutputStreamWriter(out, StandardCharsets.UTF_8));
        w.write("id,title,size\n");
        for (StoredDocument d : storage.allInPages()) w.write(d.id() + "," + d.title() + "," + d.size() + "\n");
        w.flush();
    };
    return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"documents.csv\"")
            .body(body);
}

Content-Disposition: inline asks the browser to display (PDF viewer, image), attachment to save. Non-ASCII names need the RFC 5987 filename*=UTF-8''… form, which ContentDisposition.filename(name, charset) produces. Returning a file-backed Resource streams it through ResourceHttpMessageConverter in chunks, and Spring answers a Range: bytes=… request with 206 Partial Content (resumable downloads, video seeking). InputStreamResource wraps a one-shot stream (e.g. from object storage); Spring won't read it to compute a length, so set Content-Length yourself if you know it. StreamingResponseBody lets you write generated content (CSV, ZIP) directly to the socket from an async thread, subject to spring.mvc.async.request-timeout (L311).

Not proxying at all: presigned URLs

What breaks in production
  • Stored XSS through uploads: an uploaded HTML or SVG served inline from your origin runs script in your users' sessions. Serve user files as attachment with nosniff, or from a separate domain.
  • getBytes() on large files: ten concurrent 200 MB uploads are 2 GB of heap.
  • Temp directory cleanup: some Linux distributions periodically delete old files under /tmp, including Tomcat's temporary upload directory, and later multipart requests then fail. Set location explicitly.
  • Default 1 MB limit discovered by the first real user, as a 413 or a 500 if unhandled.

Async MVC, Streaming & Server-Sent Events

45m video45m practice

Servlet async processing separates the HTTP response from the thread that accepted the request: the container thread returns to the pool while the response stays open, and someone else completes it later. Spring MVC exposes this as Callable, DeferredResult, CompletableFuture and the emitters, and on Java 21 virtual threads remove the main reason most applications reached for it.

The servlet async model

Definition · async request processing

A servlet calls request.startAsync(), receives an AsyncContext and returns; the container thread goes back to the pool but the connection and response stay open. Later, any thread calls asyncContext.dispatch() to re-enter the container (an ASYNC dispatch) or complete() to finish. Spring starts async processing when a handler returns one of the async types, and when the value is ready it dispatches back, so DispatcherServlet can run message conversion and exception handling as usual. Filters and interceptors therefore see the request twice; OncePerRequestFilter skips the async dispatch by default, and interceptors implementing AsyncHandlerInterceptor get afterConcurrentHandlingStarted instead of postHandle on the first pass.

Callable, DeferredResult, CompletableFuture, WebAsyncTask

@RestController
@RequestMapping("/api")
class ReportController {
    private final ReportService reports;
    private final Map<String, DeferredResult<JobStatus>> waiting = new ConcurrentHashMap<>();
    ReportController(ReportService reports) { this.reports = reports; }

    @GetMapping("/reports/{id}")
    Callable<ReportDto> build(@PathVariable long id) {
        return () -> reports.buildSlowly(id);               // Spring runs it on the MVC AsyncTaskExecutor
    }

    @GetMapping("/reports/{id}/bounded")
    WebAsyncTask<ReportDto> bounded(@PathVariable long id) {
        WebAsyncTask<ReportDto> task = new WebAsyncTask<>(5_000L, () -> reports.buildSlowly(id));
        task.onTimeout(() -> ReportDto.pending(id));        // per-request timeout and fallback
        task.onError(() -> ReportDto.failed(id));
        return task;
    }

    @GetMapping("/reports/{id}/future")
    CompletableFuture<ReportDto> future(@PathVariable long id) {
        return reports.buildAsync(id);                      // completed by the service's own executor
    }

    @GetMapping("/jobs/{id}/status")                        // long polling
    DeferredResult<JobStatus> await(@PathVariable String id) {
        var result = new DeferredResult<JobStatus>(30_000L, JobStatus.unchanged(id));   // timeout value
        waiting.put(id, result);
        result.onCompletion(() -> waiting.remove(id, result));
        return result;
    }

    @EventListener
    void on(JobFinished event) {                             // any thread, any time later
        var result = waiting.get(event.jobId());
        if (result != null) result.setResult(JobStatus.done(event.jobId()));
    }
}
  • Callable<T>: Spring submits it to the configured AsyncTaskExecutor. Useful only if that pool is managed differently from Tomcat's (bounded, isolated per workload).
  • DeferredResult<T>: you keep the object and call setResult or setErrorResult from anywhere: a message listener, a scheduled check, another request. Made for long polling and event-driven completion.
  • CompletableFuture<T> (any CompletionStage): adapted to a DeferredResult; completes on whichever thread completes the future.
  • WebAsyncTask<T>: a Callable with its own timeout, executor and onTimeout/onError/onCompletion callbacks.
spring:
  mvc:
    async:
      request-timeout: 20s     # default is the container's (30s on Tomcat)
  threads:
    virtual:
      enabled: true            # Boot 3.2+ on Java 21: Tomcat and applicationTaskExecutor use virtual threads

Boot hands MVC the applicationTaskExecutor for async work; to use another, override WebMvcConfigurer.configureAsyncSupport(AsyncSupportConfigurer c) and call c.setTaskExecutor(executor) and c.setDefaultTimeout(ms). Without any executor Spring falls back to SimpleAsyncTaskExecutor and logs a warning that it is not suitable under load. A timeout with no fallback raises AsyncRequestTimeoutException, which becomes a 503.

ResponseBodyEmitter and SseEmitter

ResponseBodyEmitter keeps the response open and writes each send(object) through the message converters as a chunk; SseEmitter is the subclass that formats each send as a Server-Sent Event. You may send from any thread. complete() ends the response; completeWithError(ex) ends it through exception handling; onTimeout, onCompletion and onError register callbacks for cleanup.

@Component
class NotificationHub {
    private final Map<String, Set<SseEmitter>> byUser = new ConcurrentHashMap<>();

    SseEmitter subscribe(String userId) {
        var emitter = new SseEmitter(Duration.ofMinutes(30).toMillis());
        byUser.computeIfAbsent(userId, k -> ConcurrentHashMap.newKeySet()).add(emitter);
        Runnable remove = () -> byUser.computeIfPresent(userId, (k, set) -> {
            set.remove(emitter);
            return set.isEmpty() ? null : set;
        });
        emitter.onCompletion(remove);
        emitter.onTimeout(emitter::complete);
        emitter.onError(t -> remove.run());
        return emitter;
    }

    void publish(String userId, Notification n) {
        for (SseEmitter emitter : byUser.getOrDefault(userId, Set.of())) {
            try {
                emitter.send(SseEmitter.event().id(n.id()).name(n.type()).reconnectTime(5_000).data(n));
            } catch (IOException | IllegalStateException ex) {
                emitter.completeWithError(ex);                  // client went away
            }
        }
    }
}

A browser's EventSource dispatches by event name, waits retry milliseconds before reconnecting after a drop, and sends the last id it saw in a Last-Event-ID header so you can replay what it missed. Send a comment line (SseEmitter.event().comment("ping")) every 15–30 seconds so proxies don't close idle connections, and turn off proxy buffering for the path. StreamingResponseBody (L310) is the low-level option: you get the OutputStream on an async thread and write a large CSV or ZIP without buffering it.

The honest comparison

ApproachModelWhen it pays off
Async MVCBlocking code; container thread released, executor thread often still busyLong polling and SSE in a platform-thread app; isolating slow work into its own pool
WebFluxNon-blocking end to end; event loop; Mono/FluxVery high concurrency with reactive drivers throughout, streaming pipelines, back-pressure
Virtual threadsBlocking code; one cheap thread per requestThe default for new Java 21 MVC services: ordinary code that scales to many concurrent waits

Async MVC was mostly a way to avoid holding scarce platform threads during waits. With spring.threads.virtual.enabled=true, a blocked request costs a few kilobytes rather than a platform thread, so a plain blocking controller handles thousands of concurrent slow calls and Callable adds nothing. Still worth keeping: DeferredResult when completion is driven by an event, emitters for SSE and streaming, and explicit timeouts. Watch for pinning: on Java 21–23 a virtual thread blocking inside synchronized pins its carrier thread (JDK 24, JEP 491, removed most of this), and the downstream limits (connection pools, rate limits) still apply.

What breaks in production
  • Emitter leaks: never removing completed emitters grows the map and throws on every publish. Remove in onCompletion/onError.
  • Async timeouts shorter than the work return 503s while the work continues in the background and its result is discarded.
  • Lost context: SecurityContext, MDC and request-scoped beans are thread-bound; a CompletableFuture on your own executor doesn't carry them unless you propagate them (Micrometer context propagation, DelegatingSecurityContextExecutor).
  • Load balancers with 60-second idle timeouts silently cutting SSE streams without heartbeats.

API Versioning & Deprecation

40m video40m practice

You can't change a published API in a breaking way without breaking someone, so the first goal is to avoid needing a new version, and the second is to make versions cheap to run and possible to retire. The mechanism (path, parameter, header or media type) matters less than a clear definition of "breaking" and a deprecation process with dates, headers and telemetry.

Postponing versioning

Most change can be additive: new optional request fields with defaults, new response fields, new endpoints, new enum values. That only works if clients are tolerant readers (Fowler): they ignore unknown fields, don't depend on field order, and map unknown enum values to a fallback. Boot's Jackson already ignores unknown properties; in clients, add @JsonEnumDefaultValue with READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE. Publish this expectation in your API guidelines so additive changes really are safe.

Definition · breaking change

Any change after which a correct existing client can fail: removing or renaming a field or endpoint; changing a type or format (number to string, date format, id from numeric to UUID); tightening validation (shorter max length, a newly required field); changing semantics (an amount that now includes tax); changing error codes or statuses clients branch on (L308); changing defaults such as sort order or page size. Adding a response field or an optional parameter is not breaking, provided clients read tolerantly.

The four strategies

Header routing with a custom RequestCondition

The headers = "X-API-Version=2" attribute is exact-match: no default for clients that send nothing, and no way to say "introduced in v1, still valid in v2". A custom RequestCondition adds those rules to the mapping itself.

@Target({ElementType.TYPE, ElementType.METHOD}) @Retention(RetentionPolicy.RUNTIME)
@interface ApiVersion { int value(); }

record ApiVersionCondition(int version) implements RequestCondition<ApiVersionCondition> {
    static final String HEADER = "X-API-Version";
    static final int LATEST = 2;

    @Override
    public ApiVersionCondition combine(ApiVersionCondition other) { return other; }   // method beats class

    @Override
    public ApiVersionCondition getMatchingCondition(HttpServletRequest req) {
        String h = req.getHeader(HEADER);
        int requested;
        try { requested = h == null ? LATEST : Integer.parseInt(h.trim()); }
        catch (NumberFormatException e) { return null; }
        return requested >= version && requested <= LATEST ? this : null;   // valid from 'version' on
    }

    @Override
    public int compareTo(ApiVersionCondition other, HttpServletRequest req) {
        return Integer.compare(other.version, version);                   // highest version first
    }
}

class VersionedHandlerMapping extends RequestMappingHandlerMapping {
    @Override
    protected RequestCondition<?> getCustomTypeCondition(Class<?> type) { return condition(type.getAnnotation(ApiVersion.class)); }

    @Override
    protected RequestCondition<?> getCustomMethodCondition(Method method) { return condition(method.getAnnotation(ApiVersion.class)); }

    private static ApiVersionCondition condition(ApiVersion v) { return v == null ? null : new ApiVersionCondition(v.value()); }
}

@Configuration
class VersioningConfig implements WebMvcRegistrations {                  // keeps Boot's MVC setup
    @Override
    public RequestMappingHandlerMapping getRequestMappingHandlerMapping() { return new VersionedHandlerMapping(); }
}

With @ApiVersion(1) on get and @ApiVersion(2) on a new get for the same path, a v2 request matches both and compareTo picks v2; a v1 request matches only v1; an endpoint that never changed keeps its @ApiVersion(1) and serves every version. Add Vary: X-API-Version to responses so shared caches don't mix them.

Spring Framework 7 (Boot 4) builds this in: a version attribute on the mapping annotations (@GetMapping(path = "/orders/{id}", version = "2"), with "1.1+" meaning "this version and later"), a configureApiVersioning callback on WebMvcConfigurer to choose header, query parameter, path segment or media-type parameter, and a deprecation handler that adds the headers below. On Boot 3 the condition above is the equivalent.

Gateway or service?

At the gateway, /v1/** and /v2/** route to different deployments: v1 can be frozen and retired by deleting a deployment, but both versions still share the database, so schema changes must work for both, and fixes need two releases. In the service, one deployment serves both through version-specific DTOs and mappers: one codebase and one schema, at the cost of mapping code that lives until the old version dies. Use in-service versioning for representation changes and gateway routing for true rewrites.

Deprecating and removing a version

HTTP/1.1 200
Deprecation: @1767225600
Sunset: Thu, 31 Dec 2026 23:59:59 GMT
Link: <https://developer.acme.com/migrate/orders-v2>; rel="deprecation"

Sunset (RFC 8594) gives the date after which the resource may stop responding. Deprecation (RFC 9745, 2025) says the resource is deprecated, as a structured date (@ plus Unix seconds); early drafts used Deprecation: true, which you'll still see. Add them in an interceptor keyed on an annotation, set in preHandle so they're present before the body is written, and in the same place increment a counter tagged with the API version and client id. That counter tells you who to contact and when removal is safe. Brownouts, short announced windows where the old version returns 410, flush out the clients nobody knew about before the real removal.

What breaks in production
  • "Non-breaking" changes that break: a new enum value crashing a strict client, a field that used to be absent now null, a tightened @Size.
  • Caches serving v1 to v2 clients because header or media-type versions were not in Vary.
  • Version sprawl: five live versions, each with its own bugs. Cap supported versions (current and previous) and enforce sunsets.
  • Removing without telemetry: the "unused" v1 turns out to be a partner's nightly batch job.

OpenAPI & Swagger with springdoc

45m video50m practice

An OpenAPI document is a machine-readable contract: paths, operations, schemas and security, from which you can render docs, generate clients and lint designs. springdoc derives most of it from your controllers and DTOs at runtime; annotations fill the gaps, and exporting the result at build time turns it into a reviewable artifact instead of a web page.

The structure of an OpenAPI document

info (title, version, contact), servers (base URLs), paths (each path has operations keyed by HTTP method, with operationId, parameters in path/query/header/cookie, a requestBody, and responses keyed by status), and components (reusable schemas, responses, parameters and securitySchemes). OpenAPI 3.1 aligns schemas with JSON Schema 2020-12 (for example, type: [string, "null"] replaces nullable). Older springdoc 2.x releases emit 3.0 unless you set springdoc.api-docs.version=openapi_3_1; recent ones may default to 3.1, so check the openapi field at the top of the output.

Adding springdoc

<dependency>
  <groupId>org.springdoc</groupId>
  <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
  <version>${springdoc.version}</version>      <!-- the 2.x line for Boot 3 -->
</dependency>

That's all it takes for /v3/api-docs (JSON; /v3/api-docs.yaml for YAML) and /swagger-ui.html. At startup springdoc walks the RequestMappingHandlerMapping, so it sees the same mappings MVC uses. It infers paths, methods, path/query/header parameters and their types, request and response schemas from DTO classes and records (via Jackson's view of them, so @JsonProperty renames apply), enums as enum lists, and constraints from Bean Validation: @NotNull/@NotBlank make a property required, @Size becomes minLength/maxLength or minItems/maxItems, @Min/@Max become minimum/maximum, @Pattern becomes pattern. What it can't infer: prose, examples, which errors an operation returns, and security.

Annotations for the rest

HATEOAS with Spring HATEOAS

40m video40m practice

Hypermedia puts the next possible actions into each response as links, so the server, not the client, decides what is allowed now. Spring HATEOAS gives you model wrappers, link builders that point at controller methods, and HAL rendering; whether that is worth it depends on whether your clients will actually follow links instead of hard-coding URLs.

The case for and against

Definition · HATEOAS

"Hypermedia as the engine of application state", the REST constraint in which a client starts from an entry URL and moves through the API only by following links and forms the server provides. A response describes the resource and the transitions available from its current state: an open order has a cancel link, a shipped one doesn't.

  • For: discoverability (links double as live documentation), decoupling (URLs can change without breaking clients that follow links), and server-driven state: the business rule "only open orders can be cancelled" lives in one place, and a UI simply shows the buttons for the links present.
  • Against: clients must be written to follow links, and most aren't: SPA and mobile developers usually hard-code routes from the OpenAPI spec. Payloads get bigger, link generation costs some CPU, and the tooling is thinner than for plain JSON. For internal APIs with one known client, the benefit is often small.

The model types and link building

Add spring-boot-starter-hateoas. Responses become subclasses of RepresentationModel, which holds a list of Links: EntityModel<T> wraps one object, CollectionModel<T> a collection, and PagedModel<T> a page with page metadata and first/prev/next/last links. WebMvcLinkBuilder.linkTo(methodOn(OrderController.class).one(42)) records a call on a proxy of the controller and builds the URI from that method's mapping, so links follow your mappings when paths change. withSelfRel() and withRel("cancel") name the relation.

// import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.*;

@Relation(collectionRelation = "orders", itemRelation = "order")
record OrderDto(long id, String status, long totalCents) {}

@Component
class OrderModelAssembler implements RepresentationModelAssembler<OrderDto, EntityModel<OrderDto>> {
    private final OrderPolicy policy;
    OrderModelAssembler(OrderPolicy policy) { this.policy = policy; }

    @Override
    public EntityModel<OrderDto> toModel(OrderDto order) {
        EntityModel<OrderDto> model = EntityModel.of(order,
                linkTo(methodOn(OrderController.class).one(order.id())).withSelfRel(),
                linkTo(methodOn(OrderController.class).all()).withRel("orders"));
        if ("OPEN".equals(order.status()) && policy.currentUserMayCancel(order)) {   // state + permission
            model.add(linkTo(methodOn(OrderController.class).cancel(order.id())).withRel("cancel"));
        }
        return model;
    }
}

@RestController
@RequestMapping("/api/orders")
public class OrderController {                     // public, non-final: methodOn proxies it
    private final OrderService orders;
    private final OrderModelAssembler assembler;
    public OrderController(OrderService orders, OrderModelAssembler assembler) {
        this.orders = orders; this.assembler = assembler;
    }

    @GetMapping("/{id}")
    public EntityModel<OrderDto> one(@PathVariable long id) { return assembler.toModel(orders.get(id)); }

    @GetMapping
    public CollectionModel<EntityModel<OrderDto>> all() {
        return assembler.toCollectionModel(orders.all())
                .add(linkTo(methodOn(OrderController.class).all()).withSelfRel());
    }

    @GetMapping("/paged")
    public PagedModel<EntityModel<OrderDto>> paged(Pageable pageable, PagedResourcesAssembler<OrderDto> pages) {
        return pages.toModel(orders.page(pageable), assembler);
    }

    @PostMapping("/{id}/cancellation")
    public EntityModel<OrderDto> cancel(@PathVariable long id) { return assembler.toModel(orders.cancel(id)); }
}

A RepresentationModelAssembler keeps link logic out of controllers and gives you toCollectionModel for free. The conditional cancel link checks both the order's state and the caller's permission; the controller method must still enforce both, because a client can call any URL whether or not you offered it.

HAL, HAL-FORMS and affordances

Accept: application/hal+json

{
  "id": 42, "status": "OPEN", "totalCents": 1999,
  "_links": {
    "self":   { "href": "http://localhost:8080/api/orders/42" },
    "orders": { "href": "http://localhost:8080/api/orders" },
    "cancel": { "href": "http://localhost:8080/api/orders/42/cancellation" }
  }
}

GET /api/orders   →  { "_embedded": { "orders": [ { ..., "_links": {...} } ] },
                       "_links": { "self": { "href": "http://localhost:8080/api/orders" } } }

HAL (application/hal+json) is the default format Boot configures: links go under _links keyed by relation, and nested collections under _embedded, keyed by the @Relation name (without it you'd get a generated name like orderDtoList). Boot also renders HAL for plain application/json requests by default. HAL says where you can go but not how (method, fields). HAL-FORMS (application/prs.hal-forms+json) adds _templates describing the HTTP method and input properties, produced from affordances:

Link self = linkTo(methodOn(OrderController.class).one(id)).withSelfRel()
        .andAffordance(afford(methodOn(OrderController.class).changeAddress(id, null)));

Spring HATEOAS inspects changeAddress's mapping and @RequestBody type and emits a template with method and properties (including required flags from Bean Validation), so a generic client can render a form. Enable the format with @EnableHypermediaSupport(type = {HypermediaType.HAL, HypermediaType.HAL_FORMS}). The HAL Explorer (spring-data-rest-hal-explorer) is a browser UI for navigating HAL responses, served by Spring Data REST.

Spring Data REST

spring-boot-starter-data-rest exposes every repository as a hypermedia resource: CRUD at /orders, paging and sorting, derived queries under /orders/search, HAL and profile metadata, with no controller code. It is impressive in a demo and useful for internal admin tools or prototypes. As a public API it is usually a mistake: the persistence model becomes the contract (rename a column, break a client), business rules move into repository event handlers, every exported repository is reachable by default (spring.data.rest.detection-strategy=annotated makes it opt-in), and PUT/PATCH writes any entity field, which is mass assignment at the API level (L304).

What breaks in production
  • Wrong hosts in links behind a proxy (internal host, http) unless server.forward-headers-strategy is set; every link in every response is broken at once.
  • Links as authorization: hiding the cancel link without checking in cancel() protects nothing.
  • Final controllers or methods (or Kotlin defaults): methodOn can't proxy them and link building fails at runtime.
  • Expensive link logic: a permission check per link per item makes a 100-item page do hundreds of policy calls. Batch the checks.

HTTP Clients: RestClient, RestTemplate & @HttpExchange

45m video50m practice

Spring has three synchronous client styles over one engine: RestClient (fluent, the modern default), RestTemplate (template methods, in maintenance mode) and HTTP interfaces (declarative proxies). All delegate to a ClientHttpRequestFactory, and that factory's timeouts and connection pool decide whether a slow downstream service costs you one request or your whole service.

RestClient

record CustomerDto(long id, String name, String email) {}

@Component
class CustomerGateway {
    private final RestClient http;

    CustomerGateway(RestClient.Builder builder) {               // Boot's builder: its converters, customizers
        this.http = builder
                .baseUrl("https://customers.internal/api")
                .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
                .requestInterceptor((req, body, exec) -> {      // sees request and response
                    String id = MDC.get("requestId");
                    if (id != null) req.getHeaders().set("X-Request-Id", id);
                    return exec.execute(req, body);
                })
                .build();
    }

    CustomerDto get(long id) {
        return http.get().uri("/customers/{id}", id)
                .retrieve()
                .onStatus(s -> s.value() == 404, (req, res) -> { throw new CustomerNotFoundException(id); })
                .body(CustomerDto.class);
    }

    List<CustomerDto> search(String q) {
        return http.get().uri(u -> u.path("/customers").queryParam("q", q).build())
                .retrieve()
                .body(new ParameterizedTypeReference<List<CustomerDto>>() {});
    }

    ResponseEntity<CustomerDto> create(CreateCustomer cmd) {
        return http.post().uri("/customers")
                .contentType(MediaType.APPLICATION_JSON)
                .body(cmd)
                .retrieve()
                .toEntity(CustomerDto.class);                    // status + headers + body
    }

    Optional<CustomerDto> find(long id) {                        // full control, no default error handling
        return http.get().uri("/customers/{id}", id)
                .exchange((req, res) -> res.getStatusCode().is2xxSuccessful()
                        ? Optional.ofNullable(res.bodyTo(CustomerDto.class))
                        : Optional.empty());
    }
}

RestClient.create(baseUrl) or RestClient.builder() make standalone clients; in Boot, inject the auto-configured RestClient.Builder (a fresh copy per injection point) so your clients share Boot's message converters, observation (metrics and trace propagation) and any RestClientCustomizer. retrieve() throws HttpClientErrorException/HttpServerErrorException subclasses for 4xx/5xx unless an onStatus handler matches first; exchange hands you the raw response and does no status handling at all. RestClient.create(restTemplate) reuses an existing template's configuration during a migration.

RestTemplate

RestTemplate rt = new RestTemplate(requestFactory);
rt.getInterceptors().add(new BasicAuthenticationInterceptor("svc-orders", secret));
rt.setErrorHandler(new DefaultResponseErrorHandler() {
    @Override
    public boolean hasError(ClientHttpResponse res) throws IOException {
        return res.getStatusCode().is5xxServerError();          // treat 4xx as data, not exceptions
    }
});

CustomerDto one = rt.getForObject("https://customers.internal/api/customers/{id}", CustomerDto.class, 42);
ResponseEntity<CustomerDto> created = rt.postForEntity("https://customers.internal/api/customers", cmd, CustomerDto.class);
ResponseEntity<List<CustomerDto>> found = rt.exchange("https://customers.internal/api/customers?q={q}",
        HttpMethod.GET, null, new ParameterizedTypeReference<List<CustomerDto>>() {}, "ada");

It is in maintenance mode, not deprecated, and it is in most existing codebases, so you need to read it: getForObject/getForEntity, postForEntity, exchange for everything else, ParameterizedTypeReference for generic bodies (erasure again), a ResponseErrorHandler to decide what counts as an error, and ClientHttpRequestInterceptors for cross-cutting headers. In Boot, build it from the injected RestTemplateBuilder (root URI, interceptors, error handler, timeouts) rather than new, for the same reasons as the RestClient.Builder.

Declare the remote API as an interface with the same annotations you use on controllers, and HttpServiceProxyFactory generates an implementation backed by the RestClient: Feign-style clients with no extra dependency. Error handling, timeouts and interceptors come from the underlying client.

Timeouts and connection pools

Definition · the three client timeouts

Connection-request timeout: how long to wait for a free connection from the pool. Connect timeout: how long the TCP (and TLS) handshake may take. Read/response timeout: how long to wait for response bytes once the request is sent. The JDK HttpURLConnection behind the default SimpleClientHttpRequestFactory waits forever for a read, and the JDK HttpClient has no request timeout unless you set one. Every outbound call needs all three set explicitly.

@Bean
ClientHttpRequestFactory pooledRequestFactory() {                 // Apache HttpClient 5.2+
    var pool = PoolingHttpClientConnectionManagerBuilder.create()
            .setMaxConnTotal(100)
            .setMaxConnPerRoute(20)
            .setDefaultConnectionConfig(ConnectionConfig.custom()
                    .setConnectTimeout(Timeout.ofSeconds(2))
                    .setSocketTimeout(Timeout.ofSeconds(5))
                    .build())
            .build();
    CloseableHttpClient client = HttpClients.custom()
            .setConnectionManager(pool)
            .setDefaultRequestConfig(RequestConfig.custom()
                    .setConnectionRequestTimeout(Timeout.ofMillis(500))   // waiting for the pool
                    .setResponseTimeout(Timeout.ofSeconds(5))
                    .build())
            .build();
    return new HttpComponentsClientHttpRequestFactory(client);
}

@Bean
RestClientCustomizer useEngine(ClientHttpRequestFactory pooledRequestFactory) {
    return builder -> builder.requestFactory(pooledRequestFactory);   // applied to every injected builder
}

The alternatives: JdkClientHttpRequestFactory over java.net.http.HttpClient (no extra dependency; set connectTimeout on the client and setReadTimeout on the factory; little pool tuning), and the Reactor Netty factory (if WebFlux is already present). Size the pool per downstream: more connections than the callee can serve just queues inside it. Recent Boot 3 versions can also choose and configure the factory with spring.http.client.* properties.

Retries belong only on idempotent calls (GET, PUT, DELETE, or POST with an idempotency key), with exponential backoff, jitter and a cap, and never on 4xx except 429. Combined with timeouts and circuit breakers this is Resilience4j's territory (Day 408).

Timeouts, TLS and connection reuse need a real server, e.g. WireMock with injected delays.

What breaks in production
  • No timeouts: the most common root cause of cascading outages. Grep for every client and check all three values.
  • A new client per request (RestClient.create() in a method) discards pooling and keep-alive; every call pays a TCP and TLS handshake.
  • Pool too small: requests wait on the connection-request timeout, which looks like downstream latency in your metrics.
  • Retrying non-idempotent POSTs creates duplicate orders when the first attempt actually succeeded.

WebClient in a Blocking App, Static Resources & Views

45m video45m practice

An MVC application can borrow WebFlux's WebClient for the cases where a non-blocking client pays off, parallel fan-out and streamed responses, and block once at the edge. The same lesson closes the phase with the parts of Spring MVC that serve browsers rather than API clients: static resources with long-lived caching, and server-rendered Thymeleaf templates.

When WebClient is worth it in an MVC app

Adding spring-boot-starter-webflux next to the web starter does not turn the app reactive: when both are present Boot still starts a servlet application with Spring MVC, and you just gain WebClient and Reactor. It earns its place when one request must call several services at the same time, or consume a streamed response (Flux of server-sent events, NDJSON) without buffering. For one call at a time, RestClient is simpler and gives clearer stack traces. On Java 21 with virtual threads, parallel blocking calls through RestClient on a virtual-thread executor are a reasonable alternative to Reactor for fan-out.

@Service
class DashboardService {
    private final WebClient web;

    DashboardService(WebClient.Builder builder, TokenSource tokens) {
        this.web = builder
                .baseUrl("https://internal.acme.com")
                .defaultHeaders(h -> h.setAccept(List.of(MediaType.APPLICATION_JSON)))
                .filter((req, next) -> next.exchange(ClientRequest.from(req)            // auth filter
                        .headers(h -> h.setBearerAuth(tokens.current())).build()))
                .filter(ExchangeFilterFunction.ofRequestProcessor(req -> {              // logging filter
                    log.debug("{} {}", req.method(), req.url());
                    return Mono.just(req);
                }))
                .build();
    }

    Dashboard load(long customerId) {
        Mono<CustomerDto> customer = web.get().uri("/customers/{id}", customerId).retrieve()
                .onStatus(HttpStatusCode::is4xxClientError, res -> res.createException())
                .bodyToMono(CustomerDto.class);
        Mono<List<OrderDto>> orders = web.get().uri("/orders?customer={id}", customerId).retrieve()
                .bodyToFlux(OrderDto.class).collectList();
        Mono<LoyaltyDto> loyalty = web.get().uri("/loyalty/{id}", customerId)
                .exchangeToMono(res -> res.statusCode().is2xxSuccessful()
                        ? res.bodyToMono(LoyaltyDto.class)
                        : Mono.just(LoyaltyDto.none()));                              // degrade, don't fail
        return Mono.zip(customer, orders, loyalty)
                .map(t -> new Dashboard(t.getT1(), t.getT2(), t.getT3()))
                .block(Duration.ofSeconds(3));                                         // the one blocking point
    }

    private static final Logger log = LoggerFactory.getLogger(DashboardService.class);
}
  • retrieve() maps 4xx/5xx to WebClientResponseException unless an onStatus handler supplies another error; bodyToMono/bodyToFlux decode one value or a stream.
  • exchangeToMono gives you the ClientResponse for any status. You must consume or release the body inside the function; Spring releases it afterwards, which is why the older exchange() that leaked connections was removed.
  • block() is legitimate exactly here: at the boundary where reactive code returns to a blocking caller, on a servlet (or virtual) thread, with a timeout. Calling it on a Reactor Netty event-loop thread throws IllegalStateException, and calling it inside a reactive chain defeats the point.

Reactor Netty: pool, timeouts and retries

@Bean
WebClientCustomizer nettyEngine() {
    ConnectionProvider pool = ConnectionProvider.builder("internal")
            .maxConnections(50)
            .pendingAcquireTimeout(Duration.ofMillis(500))   // waiting for a pooled connection
            .maxIdleTime(Duration.ofSeconds(30))              // below the server's keep-alive timeout
            .metrics(true)                                    // pool gauges via Micrometer
            .build();
    HttpClient http = HttpClient.create(pool)
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2_000)
            .responseTimeout(Duration.ofSeconds(5));
    return builder -> builder.clientConnector(new ReactorClientHttpConnector(http));
}

Mono<CustomerDto> resilient(Mono<CustomerDto> call) {
    return call.retryWhen(Retry.backoff(3, Duration.ofMillis(200))      // 200, 400, 800 ms ± jitter
            .maxBackoff(Duration.ofSeconds(2))
            .jitter(0.5)
            .filter(ex -> ex instanceof WebClientRequestException
                    || ex instanceof WebClientResponseException w && w.getStatusCode().is5xxServerError()));
}

Reactor Netty's default pool is large and its default response timeout is none, so set both. With metrics(true) and Micrometer present, the pool publishes active, idle and pending connection counts; a growing pending count is the early signal that a downstream service is slowing. Retry.backoff doubles the delay each attempt and jitter randomizes it so a thousand clients don't retry in lockstep; the filter limits retries to connection errors and 5xx (and the call must be idempotent, L315).

Static resources

spring:
  web:
    resources:
      static-locations: classpath:/static/          # default also includes /public/, /resources/, /META-INF/resources/
      cache:
        cachecontrol:
          max-age: 365d
          cache-public: true
      chain:
        strategy:
          content:
            enabled: true                            # /css/app.css  ->  /css/app-5e1c0a2f….css
            paths: /**

Boot serves files from the static locations through a ResourceHttpRequestHandler mapped to /** (change with spring.mvc.static-path-pattern), with Last-Modified and conditional-request support. A one-year max-age is only safe when the URL changes whenever the content does: the content strategy adds an MD5 hash to the file name, and ResourceUrlProvider (with ResourceUrlEncodingFilter, registered for Thymeleaf) rewrites @{/css/app.css} in templates to the hashed URL. Deploy new CSS and browsers fetch it immediately; unchanged files stay cached.

@Controller
class SpaController {
    @GetMapping(path = {"/", "/app", "/app/**"}, produces = MediaType.TEXT_HTML_VALUE)
    String index() { return "forward:/index.html"; }     // client-side router takes over
}

An SPA needs every client-side route (/app/orders/42) to return index.html, while real files and /api/** keep their own handlers. Scoping the fallback to /app/** and text/html keeps API typos as proper 404s. Give index.html itself no-cache, since it references the hashed assets.

Definition · the four expression types

${…} evaluates against the model (Spring EL); *{…} evaluates against the object selected by th:object (form fields); #{…} looks up a message in messages.properties for the current locale; @{…} builds a URL with the context path and parameters (and, with the resource chain, the hashed asset name). Templates live in classpath:/templates/; the controller returns the view name.

spring-boot-starter-thymeleaf configures the engine and view resolver (set spring.thymeleaf.cache=false in development). th:text sets escaped text, th:each iterates, th:if/th:unless conditionally render, th:fragment defines a reusable piece and th:replace/th:insert include it. The layout dialect (thymeleaf-layout-dialect, auto-registered by Boot when present) inverts that: a page declares layout:decorate and fills the layout's layout:fragment slots. The same TemplateEngine renders HTML emails: engine.process("mail/order-shipped", context) returns the string to send.

What breaks in production
  • XSS through th:utext: unescaped output of user data. Use th:text, and th:inline="javascript" for values embedded in scripts.
  • A year-long cache on unversioned files: users run last month's JavaScript against today's API.
  • block() without a timeout: a hung downstream holds the request thread forever, exactly the failure L315 warned about.
  • Lost context in Reactor: MDC and the security context don't follow Reactor's threads unless context propagation is enabled; logs from inside filters lose the request id.
