Phase 24 · Days 457–472 · Lessons 457–472

Capstone Projects

Phase 24 puts the whole track to work in three deployable systems: an e-commerce microservices platform, a real-time collaboration and notification platform, and a fintech double-entry ledger with a payments engine. Each build day goes architecture, code, tests, deployment, and applies the architecture and domain-design patterns from Phase 23 to problems where correctness, latency and failure handling all matter. The results become the portfolio and the interview material for Phase 25.

By the end of this phase you can

  • Split a domain into bounded contexts with event storming, draw the context map, and set up a monorepo with database-per-service, API-first OpenAPI and AsyncAPI contracts, and CI for every service.
  • Build a checkout saga with a persisted orchestrator, per-step timeouts and compensations, idempotency keys and a transactional outbox, and prove each failure path with a test.
  • Run a STOMP-over-WebSocket tier that authenticates on CONNECT, authorizes every SUBSCRIBE, routes across nodes through a Redis backplane, and survives rolling restarts with no loss of acknowledged messages.
  • Model money with a double-entry ledger whose entries the database refuses to commit unless they sum to zero, exact Money arithmetic, and reversing entries instead of edits.
  • Make money movement effectively once: unique-key idempotency with exact replay, deadlock-free locking, outbox plus idempotent consumers, query-then-retry on external rails, and a chaos test that kills the service mid-transfer.
  • Write restartable Spring Batch jobs for settlement, statements and reconciliation, schedule them safely across replicas, and alert when they fail to run.
  • Take a system to production with burn-rate alerts, contract tests, Helm and canary rollouts, mTLS, field-level encryption, tamper-evident audit logs, and a restore you have actually tested.

Project A, Part 1: Requirements, Domain Model & Foundations

50m video150m practicecapstone project

Before any service exists, decide what the system must do, how good it must be, where the boundaries are and what each side promises the other. A day spent on event storming, context maps and API contracts saves weeks of untangling a distributed monolith.

Scope and non-functional targets

The product is a shop: customers browse and search a catalog, fill a cart, check out, pay, and track the order; staff manage products, stock and orders through an admin API. Seven days build it end to end. Write the targets down now, because every later trade-off is judged against them.

Event storming and bounded contexts

Run a big-picture event storm, even alone: write domain events in the past tense on a timeline (ProductPublished, ItemAddedToCart, CheckoutStarted, StockReserved, PaymentAuthorized, OrderPlaced, OrderShipped, RefundIssued), then add the commands that cause them, the aggregates that decide them, and the policies that react ("whenever PaymentAuthorized, confirm the reservation"). Places where the vocabulary changes, or where a different team or a different rate of change takes over, are boundaries. The result here is seven contexts: Identity, Catalog, Cart, Ordering, Payment, Inventory, Notification.

Definition · Database per service

Each service owns its schema and the only credentials that can reach it. No other service reads its tables; cross-context queries become API calls, or read models built from events. The cost is real (no joins, eventual consistency between contexts), and it is the price of deploying and scaling each service alone.

The coupling caveat

A shared library is shared deployment coupling: change it and every service must rebuild to pick it up, and a class added "for convenience" becomes a hidden contract. Keep common to metadata and error codes, never domain entities, and version it so services can lag behind safely. Errors use RFC 9457 ProblemDetail with a stable type URI per error code.

What breaks in production
  • The distributed monolith: services that share a database, or call each other synchronously in a chain for every request, fail together and deploy together. The context map is the check.
  • Entities in the common library: one shared Product class and every service now changes in lockstep.
  • Contracts written after code: they describe accidents. Generated interfaces and a CI lint make the spec the source of truth.

  • The monorepo with parent POM, common, eight empty services that boot, and Flyway baseline per service.
  • Compose stack up with one command; each service reaches its own database and nobody else's.
  • OpenAPI specs for Catalog and Ordering, the AsyncAPI catalogue, and generated interfaces compiling.

Project A, Part 2: Identity & Auth Service

50m video150m practicecapstone project

The Identity service is the one place that sees passwords and signs tokens; every other service only verifies signatures against its public keys. Build it so that a stolen database, a replayed refresh token or a password-guessing bot each hits a specific, tested defence.

Account flows

Registration, email verification, login, password reset and profile updates share one mechanism: a single-use secret sent out of band.

Algorithm · Single-use email token
  1. Generate 32 random bytes with SecureRandom; send the Base64url value in the link.
  2. Store only its SHA-256 hash with user id, purpose (verify or reset) and expiry (24 h for verify, 30 min for reset).
  3. On use: look up by hash, check purpose and expiry, delete the row in the same transaction that changes the account.
  4. A password reset also bumps the user's token version and revokes every refresh-token family.
  5. "Forgot password" always answers 202 with the same body, whether or not the email exists, so it cannot enumerate accounts.

Password storage and future migration

@Bean
PasswordEncoder passwordEncoder() {
    Map<String, PasswordEncoder> encoders = Map.of(
        "argon2", Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8(), // argon2id, 16 MiB, t=2
        "bcrypt", new BCryptPasswordEncoder(12));                         // legacy imports

Stored hashes carry their scheme as a prefix ({argon2}$argon2id$v=19$m=16384,t=2,p=1$…), so old bcrypt rows keep verifying. Implement UserDetailsPasswordService: after a successful login, DaoAuthenticationProvider asks upgradeEncoding and, if true, re-hashes the plaintext it just verified with the current scheme. Migration happens one login at a time, with no bulk job. Argon2 needs BouncyCastle on the classpath.

Access tokens, rotating refresh tokens and reuse detection

Access tokens are JWTs signed with RS256, valid for 10 minutes, with iss, aud, sub, jti, roles and ver (token version) claims. Refresh tokens are opaque random strings, stored hashed in a refresh_tokens row with family id, device label, user agent, IP, created and last-used times. Every refresh consumes the presented token and issues a successor in the same family, as in Day 348.

@Transactional(noRollbackFor = InvalidTokenException.class) // the revocation must commit
public TokenPair refresh(String presented, DeviceInfo device) {
    var token = refreshTokens.findByHashForUpdate(sha256(presented))
            .orElseThrow(InvalidTokenException::new);
    var now = clock.instant();
    if (token.isUsed() || token.isRevoked()) {
        refreshTokens.revokeFamily(token.familyId(), now);
        audit.publish(new RefreshReuseDetected(token.userId(), token.familyId(), device.ip()));
        throw new InvalidTokenException();
    }
    if (now.isAfter(token.expiresAt())) throw new InvalidTokenException();
    token.markUsed(now);
    var successor = RefreshToken.successorOf(token, device, now);  // same family, new secret
    refreshTokens.save(successor.row());
    return new TokenPair(accessTokens.issue(users.require(token.userId())), successor.rawValue());
}

Logout-everywhere increments users.token_version and revokes every family. Refresh stops immediately; access tokens already issued remain valid until exp unless the edge compares ver with a cached current version (one Redis read per request). Choose deliberately: a 10-minute window or one lookup. The session endpoints (GET /me/sessions, DELETE /me/sessions/{familyId}, POST /me/logout-all) list and revoke families by their device metadata.

Roles, permissions, social login and TOTP

Tables roles, permissions, user_roles and role_permissions keep the model editable without deploys. Tokens carry role names only, to stay small; each resource server maps them with a JwtAuthenticationConverter (authorities claim roles, prefix ROLE_) and checks fine-grained permissions such as catalog:write through its own role-to-permission map.

Social login uses spring-boot-starter-oauth2-client. Google is OpenID Connect and returns email_verified; GitHub is plain OAuth2, so fetch /user/emails and use only an address marked verified. An external_identities(provider, subject, user_id) table with a unique key on (provider, subject) finds returning users by the provider's subject, never by email. First login provisions a user just in time; if a local account already has that email, link only when both sides are verified. The success handler then issues our own token pair, so downstream services never see Google or GitHub tokens.

Optional two-factor uses TOTP (RFC 6238: HMAC-SHA1, 30-second steps, 6 digits). Accept one step of clock drift, store the last accepted counter so a code cannot be replayed, encrypt the shared secret at rest, and issue ten hashed recovery codes. A correct password with 2FA enabled yields only a 5-minute "MFA pending" token that is good for nothing but /mfa/verify.

Brute-force protection, audit and the JWKS endpoint

Rate-limit /login, /register and /password-reset per IP and per account (Bucket4j over Redis, or the gateway limiter from Day 462). After repeated failures on one account, apply growing delays and a temporary lock with a CAPTCHA, rather than a hard lockout that lets anyone lock a victim out. Every security decision (login success and failure, lockout, password change, reuse detection, 2FA enrolment) is an audit event on Kafka with user, IP, user agent and outcome.

What breaks in production
  • The revocation that rolls back: revoking the family and then throwing inside one @Transactional method undoes the revocation. Hence noRollbackFor, plus a test.
  • Two tabs refreshing at once trip reuse detection for a legitimate user. Allow a few seconds of grace where a just-used token from the same device returns the same successor.
  • Linking accounts on an unverified email is an account takeover: anyone can create a provider account with your address.

  • Google and GitHub login with just-in-time provisioning and verified-email linking; optional TOTP.

Project A, Part 3: Catalog Service

50m video150m practicecapstone project

Catalog is read-heavy and write-light, so it gets three read paths of increasing speed (Postgres, Elasticsearch, a two-level cache) fed from one write path. The job is to keep them consistent enough, and to say exactly how stale each one may be.

Domain model and JPA mapping

A product (title, brand, description, status) has variants (SKU, size and colour, price, currency), belongs to a category in a tree, and carries typed attributes (name, value, unit) used for facets. Categories are an adjacency list (parent_id); "everything under Shoes" is the recursive CTE from Day 209.

Admin write API

Writes are validated with Bean Validation on request records and domain checks in the aggregate (a published product needs at least one variant with a price). The response carries ETag: "7" (the version); updates must send If-Match, and a stale version returns 412, so two admins can't silently overwrite each other. The read path: keyset pagination, Specifications, a stable contract

static Specification<Product> published() { return (r, q, cb) -> cb.equal(r.get("status"), Status.PUBLISHED); }
static Specification<Product> inCategories(Set<Long> ids) { return (r, q, cb) -> r.get("category").get("id").in(ids); }
static Specification<Product> brandIs(String b) { return (r, q, cb) -> cb.equal(r.get("brand"), b); }

Window<ProductCardView> page(ProductFilter f, ScrollPosition position) {
    var spec = published().and(inCategories(categoryTree.subtree(f.categoryId())));
    if (f.brand() != null) spec = spec.and(brandIs(f.brand()));
    return products.findBy(spec, q -> q.as(ProductCardView.class)
            .sortBy(Sort.by(Sort.Direction.DESC, "createdAt", "id"))  // unique tie-breaker
            .limit(24)
            .scroll(position));                                        // KeysetScrollPosition
}

Keyset pagination costs the same on page 500 as on page 1, and inserts don't shift items between pages; it needs an index on (status, category_id, created_at DESC, id DESC). The contract is {"items": [...], "next": "<opaque cursor>"}: the cursor is the Base64 of the last keys, so clients can't build offsets you would later have to honour. Allowed sorts are a fixed enum. Fields are only ever added, never renamed, and clients are told to ignore unknown fields.

Caching, freshness rules and the load test

ProductDetail detail(long id) {
    return l1.get(id, k -> {                                  // Caffeine coalesces concurrent misses
        var cached = (ProductDetail) redis.opsForValue().get("product:" + k);
        if (cached != null) return cached;
        var fresh = repository.loadDetail(k);
        redis.opsForValue().set("product:" + k, fresh,
                Duration.ofMinutes(10).plusSeconds(ThreadLocalRandom.current().nextLong(120)));  // jitter
        return fresh;
    });
}

L1 is a Caffeine cache per node with a 60 s TTL; L2 is Redis with 10 minutes plus up to 2 minutes of jitter, so keys written together don't expire together. On update, an AFTER_COMMIT listener deletes the Redis key and publishes the id on a pub/sub channel that every node uses to evict L1. Redis pub/sub is fire-and-forget, so a node that misses a message serves stale data until its L1 TTL: that 60 s is the stated bound.

Definition · Freshness rules

Display price and coarse availability (in stock, low, out) may be stale by up to the cache bounds above. Checkout never trusts them: Ordering re-prices from Catalog's authoritative read at checkout (L460), and only an Inventory reservation (L461) means a unit is actually available. Pages may be stale; checkout may not.

What breaks in production
  • Dual writes (save to Postgres, then call Elasticsearch) drift silently whenever the second call fails or the transaction rolls back after it.
  • Invalidating before commit: a reader repopulates the cache with the old row in between. Evict after commit.
  • Offset pagination on a hot table: OFFSET 100000 scans and discards 100,000 rows, and pages shift under concurrent inserts.

Project A, Part 4: Cart & Ordering Service with Saga Orchestration

50m video150m practicecapstone project

Checkout touches three services that cannot share a transaction, so it is a saga: a persisted state machine that sends commands, waits for replies, times out and compensates. Correctness comes from the Order aggregate refusing illegal transitions and from every step being idempotent.

The cart and the checkout-time snapshot

A guest cart is a Redis hash cart:{id} (SKU to quantity) whose EXPIRE of 7 days is refreshed on every write; abandoned carts cost nothing. A logged-in user's cart is a Postgres row set, so it survives devices and outages. Merge on login adds guest quantities to the user cart (capped per SKU) and records the guest cart id in merged_from in the same transaction; a retried merge sees the id and does nothing, so a crash before the Redis delete can't double the quantities.

Prices in the cart are hints. At checkout Ordering asks Catalog for authoritative prices, applies promotions (rule engine over the cart: percentage, fixed amount, buy-X-get-Y, with a priority and stackability flag), computes tax for the shipping address, and snapshots everything onto the order lines: unit price, discount, tax, rule ids, and the tax rate used. A price change next week never alters this order's history, invoices or refunds.

The Order aggregate and its state machine

public enum OrderStatus {
    CREATED, PENDING_PAYMENT, PAID, FULFILLING, SHIPPED, COMPLETED, CANCELLED, REFUNDED;

Following Day 446, the root guards the invariants: at least one line, a single currency, total equal to the sum of line totals plus shipping, and lines frozen once the order leaves CREATED. Nothing outside the aggregate sets status.

The checkout saga orchestrator

Algorithm · Checkout saga
  1. Lock the cart semantically: UPDATE cart SET checkout_saga_id = :saga WHERE id = :cart AND checkout_saga_id IS NULL. Zero rows updated means a checkout is already running: return 409.
  2. Create the order (CREATED) and the saga row (step RESERVE_STOCK, deadline now + 10 s); outbox ReserveStock. All one local transaction.
  3. StockReserved: order to PENDING_PAYMENT, outbox AuthorizePayment, deadline + 30 s. StockRejected or timeout: order CANCELLED, unlock cart.
  4. PaymentAuthorized: order PAID, outbox ConfirmReservation, clear and unlock cart, publish OrderPaid.
  5. PaymentDeclined: compensate with ReleaseReservation, order CANCELLED. Payment timeout: the outcome is unknown, so send VoidAuthorization (Payment voids it if it exists, no-op otherwise), then release stock and cancel.
@Transactional
public void on(PaymentReply reply) {                       // sealed: PaymentAuthorized | PaymentDeclined
    var saga = sagas.findByIdForUpdate(reply.sagaId()).orElseThrow();
    if (!saga.awaits(Step.AUTHORIZE_PAYMENT, reply.commandId())) return;   // duplicate or late reply
    var order = orders.require(saga.orderId());
    switch (reply) {
        case PaymentAuthorized ok -> {
            order.markPaid(ok.paymentId());
            saga.advance(Step.CONFIRM_STOCK, clock.instant().plus(STEP_TIMEOUT));
            outbox.send(new ConfirmReservation(saga.id(), saga.reservationId()));
        }
        case PaymentDeclined no -> {
            order.cancel("payment declined: " + no.reason());
            saga.compensate(Step.RELEASE_STOCK);
            outbox.send(new ReleaseReservation(saga.id(), saga.reservationId()));
        }
    }
}

Per-step timeouts are a scheduled sweep: SELECT … FROM checkout_saga WHERE status = 'RUNNING' AND deadline < now() FOR UPDATE SKIP LOCKED LIMIT 100, so several Ordering instances can sweep without double-processing. Replies are matched on the saga's current step and command id; anything else is dropped, which makes replies idempotent.

Idempotent checkout, the outbox and read models

POST /checkout requires an Idempotency-Key header. The key, the user id and a hash of the request body are inserted under a unique constraint before any work. A repeat with the same body replays the stored response; one still in flight gets 409 with Retry-After; the same key with a different body gets 422. L470 does this rigorously for money transfers.

Every event Ordering publishes (OrderCreated, OrderPaid, OrderCancelled, …) and every saga command goes through the outbox table in the transaction that changed state, keyed by order id so per-order ordering holds on Kafka. Order history (order_summary per customer, newest first) and tracking (a status timeline plus the carrier number) are separate read models updated from those events. They are denormalised for the screen that reads them and never used for decisions.

Payment: a port, two adapters, and no card data

The Stripe-style adapter forwards idempotencyKey as the provider's idempotency header and translates its statuses and errors at the boundary. Definition · Payment-attempt ledger

An append-mostly table payment_attempts(id, order_id, kind, amount, currency, idempotency_key, status, provider_ref, created_at) where kind is AUTHORIZE, CAPTURE, REFUND or VOID and status is REQUESTED, SUCCEEDED, FAILED or UNKNOWN. The row is inserted as REQUESTED and committed before the provider call, then updated with the outcome. A crash mid-call therefore leaves evidence; a timeout becomes UNKNOWN, never FAILED.

Authorize at checkout, capture on shipment (at most the authorized amount), refund after capture, void before it. Retries back off exponentially with jitter, under one rule: query before retry.

Webhooks: verify, deduplicate, tolerate disorder

boolean verify(byte[] rawBody, String header, Instant now) {     // header "t=1712345678,v1=<hex>"
    var p = parseSignatureHeader(header);
    long t = Long.parseLong(p.get("t"));
    if (Math.abs(now.getEpochSecond() - t) > 300) return false;    // replay window
    try {
        var mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(webhookSecret, "HmacSHA256"));
        mac.update((t + ".").getBytes(StandardCharsets.UTF_8));
        byte[] expected = mac.doFinal(rawBody);                    // the raw bytes, not re-serialised JSON
        return MessageDigest.isEqual(expected, HexFormat.of().parseHex(p.get("v1"))); // constant time
    } catch (GeneralSecurityException | IllegalArgumentException e) {
        return false;
    }
}

After verification, insert the provider event id into webhook_events with ON CONFLICT DO NOTHING; a duplicate returns 200 at once. Respond 2xx quickly and process asynchronously. Providers don't guarantee order, so a late payment.succeeded must not undo a refunded: either apply only transitions that move forward in the payment's state order, or treat the event as a hint and re-fetch the object from the provider API. A nightly reconciliation job matches the provider's settlement report against payment_attempts by provider_ref and files every break (missing on our side, missing on theirs, amount or status mismatch) in an exceptions queue (L471).

Inventory: reservations and the locking benchmark

CREATE TABLE stock (
  sku text, warehouse_id text, on_hand int NOT NULL, reserved int NOT NULL, version bigint NOT NULL,
  PRIMARY KEY (sku, warehouse_id),
  CHECK (reserved >= 0 AND reserved <= on_hand)          -- oversell is impossible, not just unlikely
);
CREATE TABLE reservation (
  id uuid PRIMARY KEY, order_id uuid NOT NULL, sku text, warehouse_id text, qty int NOT NULL,
  status text NOT NULL,            -- HELD, CONFIRMED, RELEASED, EXPIRED
  expires_at timestamptz NOT NULL
);
CREATE INDEX reservation_expiry ON reservation (expires_at) WHERE status = 'HELD';
// A: pessimistic. Lock rows in sorted (sku, warehouse) order so two multi-line orders can't deadlock.
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from Stock s where s.id in :ids order by s.id.sku, s.id.warehouseId")
List<Stock> lockAll(Collection<StockId> ids);

// B: optimistic. @Version on Stock; on ObjectOptimisticLockingFailureException, retry up to 5 times.

// C: one conditional statement; the row lock lasts only for the statement.
@Modifying
@Query(value = """
    UPDATE stock SET reserved = reserved + :qty, version = version + 1
    WHERE sku = :sku AND warehouse_id = :wh AND on_hand - reserved >= :qty""", nativeQuery = true)
int tryReserve(String sku, String wh, int qty);   // 1 = reserved, 0 = insufficient

Benchmark A, B and C with 200 threads on one hot SKU and on 10,000 cold ones (throughput, p99, retries). Expect optimistic locking to shine on cold rows and drown in retries on the hot one; measure rather than trust this.

The release job runs every 30 s: UPDATE reservation SET status = 'EXPIRED' WHERE id IN (SELECT id FROM reservation WHERE status = 'HELD' AND expires_at < now() LIMIT 500 FOR UPDATE SKIP LOCKED) RETURNING sku, warehouse_id, qty, decrementing reserved in the same transaction. Confirmation is also conditional (WHERE id = ? AND status = 'HELD'); if it updates zero rows the reservation expired first, and Inventory replies ReservationExpired so the saga voids the payment.

Oversell attempts and the flash-sale admission queue

The CHECK constraint and conditional update make oversell impossible, but 50,000 buyers for 500 units would still aim 50,000 transactions at one row. An admission queue in front fixes that: arrivals enter a Redis sorted set by timestamp, a dispatcher admits users at a rate the database sustains, and a Redis counter preloaded with the stock answers sold-out without touching Postgres. Redis only filters; the row stays the source of truth.

Resilience on every outbound call

@Retry(name = "catalog")                                       // only because GET is idempotent
@CircuitBreaker(name = "catalog", fallbackMethod = "lastKnown")
@Bulkhead(name = "catalog")                                    // at most 20 concurrent calls to Catalog
public ProductView product(long id) {
    return catalog.get().uri("/products/{id}", id).retrieve().body(ProductView.class);
}

ProductView lastKnown(long id, Throwable cause) {               // meaningful: stale, flagged data
    return snapshotCache.find(id).map(ProductView::markStale)
            .orElseThrow(() -> new DependencyUnavailable("catalog", cause));
}
Definition · The resilience rules
  • Every call has a timeout: connect (1 s) and read (2 s) on the HTTP client itself. A TimeLimiter only applies to asynchronous returns (CompletableFuture, reactive types).
  • Breakers have fallbacks that mean something: a cached product marked stale; for checkout, 202 Accepted with the order in PENDING_PAYMENT while the saga waits for Payment, which is the "queued order".
  • One bulkhead per dependency, so a slow Catalog can't take the threads Payment needs.
  • Retry only idempotent operations: GETs, and POSTs that carry an idempotency key. Never retry inside a retry (client, gateway and mesh each retrying three times gives 27 attempts).

Definition · Burn rate

For a 99.9% SLO the error budget is 0.1% of requests. Burn rate is the observed error ratio divided by 0.001: at burn rate 1 the budget lasts exactly the 30-day window. Following the Google SRE Workbook, page when the burn rate exceeds 14.4 over both 1 h and 5 min (2% of the monthly budget gone in an hour), and open a ticket when it exceeds 6 over both 6 h and 30 min (5% gone).

The architecture

The gateway tier is the only stateful tier, and its state is just open sockets plus subscriptions, so any node can die and its clients reconnect elsewhere. Redis pub/sub is the cross-node router: fast, and allowed to lose a frame, because durability lives in Kafka and Postgres. Kafka could be the backplane instead, but then every gateway would consume every message; it is better used as the durable log. Redis also holds presence and other ephemeral state with TTLs.

Connection lifecycle, handshake authentication and resume

Algorithm · Connect, authenticate, resume
  1. HTTP GET /ws with Upgrade: websocket; the gateway checks Origin against an allow-list (cross-site WebSocket hijacking).
  2. The browser WebSocket API cannot set an Authorization header, so the client sends its JWT in the STOMP CONNECT frame headers, and an inbound interceptor validates it (Day 465). The token stays out of URLs and access logs.
  3. CONNECTED negotiates heartbeats (for example 10 s each way).
  4. The client subscribes first, then requests GET /channels/{id}/messages?afterSeq={lastSeen} for each open channel, and drops duplicates by message id. Fetching first would leave a gap between the fetch and the subscription.
  5. On disconnect: reconnect with exponential backoff and jitter, then repeat steps 1 to 4 with the stored lastSeen per channel.

Authentication on CONNECT, authorization on SUBSCRIBE

@Component
class AuthChannelInterceptor implements ChannelInterceptor {
    private final JwtDecoder jwt;                    // same JWKS as every HTTP service
    private final MembershipService members;
    private final JwtAuthenticationConverter toAuth = new JwtAuthenticationConverter();
    AuthChannelInterceptor(JwtDecoder jwt, MembershipService members) { this.jwt = jwt; this.members = members; }

    @Override
    public Message<?> preSend(Message<?> message, MessageChannel channel) {
        var acc = MessageHeaderAccessor.getAccessor(message, StompHeaderAccessor.class);
        if (acc == null || acc.getCommand() == null) return message;           // heartbeats
        switch (acc.getCommand()) {
            case CONNECT -> {
                var h = acc.getFirstNativeHeader("Authorization");
                if (h == null || !h.startsWith("Bearer ")) throw new MessagingException("missing token");
                acc.setUser(toAuth.convert(jwt.decode(h.substring(7))));      // the session's Principal
            }
            case SUBSCRIBE -> {
                var dest = Destinations.parse(acc.getDestination());          // default deny: unknown = reject
                if (!dest.isAllowedFor(acc.getUser(), members))
                    throw new AccessDeniedException("subscribe denied: " + acc.getDestination());
            }
            case SEND -> { if (acc.getUser() == null) throw new AccessDeniedException("not connected"); }
            default -> { }
        }
        return message;
    }
}

A thrown exception becomes a STOMP ERROR frame and the session closes. The SUBSCRIBE check is the one teams forget: authentication says who you are, but without it any logged-in user can subscribe to /topic/channels/42 and read a private channel. Persistence, ordering, history and ephemeral events

Algorithm · Message writer
  1. Consume chat.messages in batches. Keys are channel ids, so each channel has one partition and one consumer.
  2. On partition assignment, load max(seq) per channel; then assign seq in memory.
  3. Insert with ON CONFLICT (channel_id, client_msg_id) DO NOTHING; commit.
  4. Publish every row of the batch, new or already present, to Redis; then commit offsets.

A crash replays the batch: the unique key absorbs it and clients drop repeated ids. seq is strictly increasing per channel, but replays can leave gaps, so it is an ordering key, not a counter. PRIMARY KEY (channel_id, seq) stops a zombie writer reusing a number.

History is keyset on that primary key: GET /channels/{id}/messages?beforeSeq=…&limit=50 for scrollback and ?afterSeq=… for resume. Typing indicators go straight to Redis (chat:typing:{id}), are throttled to one per 3 s per user, are shown for 5 s unless refreshed, and are never stored. Read receipts update a Redis watermark at once and are flushed to Postgres every few seconds with last_read_seq = GREATEST(last_read_seq, :seq), which is monotonic and idempotent.

        return start.isBefore(end)

Algorithm · Coalescing window

Presence and connection count are where a real-time system meets operating-system limits: heartbeats, TTLs, file descriptors, idle timeouts and reconnect storms. The design goal is that every limit is known, measured, and hit by a load test before users find it.

Presence: heartbeats, TTLs and aggregation

private static final RedisScript<String> BEAT = RedisScript.of("""
    -- KEYS[1] presence:{uid}:conns  KEYS[2] presence:{uid}:status   (same hash slot)
    -- ARGV[1] connId  ARGV[2] 'active' or 'idle'  ARGV[3] now ms  ARGV[4] ttl ms
    local now = tonumber(ARGV[3])
    redis.call('ZREM', KEYS[1], ARGV[1] .. '|active', ARGV[1] .. '|idle')
    if ARGV[4] ~= '0' then redis.call('ZADD', KEYS[1], now + tonumber(ARGV[4]), ARGV[1] .. '|' .. ARGV[2]) end
    redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', now)
    local status = 'offline'
    for _, m in ipairs(redis.call('ZRANGE', KEYS[1], 0, -1)) do
      if string.sub(m, -7) == '|active' then status = 'online' break end
      status = 'away'
    end
    local old = redis.call('GET', KEYS[2])
    redis.call('SET', KEYS[2], status)
    if old == status then return '' end
    return status
    """, String.class);

void heartbeat(String uid, String connId, boolean active) {
    var keys = List.of("presence:{" + uid + "}:conns", "presence:{" + uid + "}:status");
    var changed = redis.execute(BEAT, keys, connId, active ? "active" : "idle",
                                String.valueOf(clock.millis()), "30000");
    if (!changed.isEmpty()) redis.convertAndSend("presence:" + uid, changed);
}

Clients heartbeat every 10 s with their state (idle after 5 minutes without input); the TTL is 30 s, so two lost beats are tolerated. A clean disconnect runs the script with TTL 0 and goes offline at once. A crashed gateway sends nothing, so a sweeper (one per gateway, owning a hash range of user ids) recomputes users whose latest expiry has passed. That is the only path that detects silent death.

Bounding the fan-out

A user in a 20,000-member channel who flaps between online and away could produce 20,000 deliveries per flap. The bounds: (1) clients subscribe to /topic/presence/{uid} only for users on screen (DM list, visible member list), capped at 200 per session; (2) changes are debounced to at most one per user per 30 s; (3) channels above 500 members show a periodically computed count ("1,204 online"), not per-member dots; (4) each gateway batches presence updates into one frame per second per session. Worst-case cost then grows with what is on screen, not with channel size.

Sticky sessions versus the backplane

An established WebSocket is pinned to one node anyway, so stickiness adds nothing to it; SockJS polling transports, though, send many HTTP requests per session and do need sticky routing. Stickiness can't solve delivery: the sender and the 300 members of a channel sit on different nodes whatever the routing. Only a backplane makes any node able to reach any subscriber, which is what lets the gateway tier scale horizontally and lets nodes die freely.

Deploying without dropping everyone

Algorithm · Drain and reconnect
  1. On SIGTERM, readiness fails, so the load balancer sends no new handshakes; existing sockets continue.
  2. Over a 60 s drain window, close sessions in small random batches with close code 1012 (CloseStatus.SERVICE_RESTARTED), not all at once.
  3. Clients reconnect after a full-jitter delay, land on other nodes, and resume with their last-seen seq per channel.
  4. Gateways cap handshakes per second; excess gets 1013 (SERVICE_OVERLOAD) and retries later. Rolling updates use maxSurge so new pods are ready before old ones drain.
final class Backoff {                                    // full jitter: random(0, min(cap, base * 2^n))
    private final Duration base = Duration.ofMillis(500), cap = Duration.ofSeconds(30);
    private int attempt;
    Duration next() {
        long ceiling = Math.min(cap.toMillis(), base.toMillis() << Math.min(attempt++, 16));
        return Duration.ofMillis(ThreadLocalRandom.current().nextLong(ceiling + 1));
    }
    void reset() { attempt = 0; }                        // after a connection that stayed up 60 s
}

Without jitter, 10,000 clients dropped by one pod reconnect in the same second, and so do their JWT validations, subscriptions and history fetches. That thundering herd can take down the node that survived. Resume requests are bounded too: at most 500 missed messages per channel; beyond that, the server answers "gap too large" and the client reloads the channel from history.

The model: accounts, journal entries, postings

Definition · Double-entry ledger

An account has a type: asset, liability, equity, revenue or expense. A journal entry is the atomic unit: one business event, committed entirely or not at all. It contains two or more postings, each a signed amount on one account; here debits are positive and credits negative. Invariant: for every entry and every currency, the postings sum to exactly zero. Assets and expenses are debit-normal (debits increase them); liabilities, equity and revenue are credit-normal. Since every entry sums to zero, all balances together sum to zero, which is the accounting equation: assets = liabilities + equity + (revenue − expenses).

To the company, a customer's wallet is a liability (money we owe) and cash at the bank an asset, so a deposit increases both.

The fixed scale also defuses a trap: new BigDecimal("2.0").equals(new BigDecimal("2.00")) is false, so without it the record's equals would be wrong. The alternative, minor units in a long, is exact and allocation-free but needs Math.addExact, the currency exponent alongside, and BigDecimal anyway for interest and FX. Here the domain uses Money and the database stores amount_minor bigint. Never double.

Multi-currency. Each currency must balance on its own, so a conversion goes through an FX position account per currency. Ana converts 100.00 EUR at 1.0850: Dr Ana EUR wallet 100.00 EUR, Cr FX position EUR 100.00 EUR, Dr FX position USD 108.50 USD, Cr Ana USD wallet 108.50 USD. The rate, its source and its timestamp are stored on the entry. When a converted amount isn't representable (100.00 × 1.08537 = 108.537 USD), round with a documented mode (HALF_EVEN) and leave the difference in the FX position account, where revaluation makes it an explicit FX gain or loss. Splits use largest-remainder allocation: 10.00 in three is 3.34 + 3.33 + 3.33.

BEGIN
  IF EXISTS (SELECT 1 FROM posting WHERE entry_id = NEW.entry_id

A balance is sum(amount_minor) over an account's postings: always right, slower as postings grow. Project C, Part 2: Money Movement, Idempotency & Exactly-Once

Moving money correctly means three guarantees: a retried request never moves money twice, two concurrent requests can't overdraw an account, and a crash at any instant leaves the books balanced. Each comes from a specific mechanism (a unique key, a lock order, a transaction boundary), and each gets a test that tries to break it.

The transfer API and its state machine

POST /transfers validates shape (positive amount, scale matching the currency, distinct accounts), authorization (the caller owns the source account, and the scope allows transfers), limits (per transaction, per day, per month in the customer's tier) and velocity (for example at most 10 transfers or 3 new payees per hour, from a sliding window). A rule failure is a FAILED transfer with a reason code; it is a normal outcome, stored and replayable, not an exception.

Idempotency, done rigorously

Algorithm · Idempotent transfer
  1. The client sends Idempotency-Key; the server computes a SHA-256 of method, path and canonical body.
  2. In the transaction that will move the money: INSERT INTO idempotency_record (client_id, key, request_hash) … ON CONFLICT DO NOTHING RETURNING key, with primary key (client_id, key).
  3. Row returned: we own the key; do the work, store the exact response (status and body bytes) in the same row, and commit once, so effect and record become visible together or not at all.
  4. No row: the key exists. A different hash gets 422. Otherwise return the stored response byte for byte.
  5. Concurrent in-flight duplicate: Postgres makes a conflicting insert wait for the first transaction to finish. If it commits, the duplicate sees the completed record and replays it; if it aborts, the duplicate's insert succeeds and it does the work. With lock_timeout = 5s, a stuck wait returns 409 with Retry-After.
@Transactional
public StoredResponse transfer(ClientId client, String key, TransferRequest req) {
    var hash = RequestHash.of(req);
    if (!idempotency.tryClaim(client, key, hash)) {                 // waits on an in-flight twin
        var prior = idempotency.find(client, key).orElseThrow();
        if (!prior.requestHash().equals(hash)) throw new IdempotencyKeyReuseException(key);  // 422
        return prior.response();                                    // byte-identical replay
    }
    var transfer = Transfer.initiate(req, clock.instant());         // INITIATED
    var verdict = policy.check(transfer, client);                   // limits, velocity, authorization
    var result = verdict.ok() ? ledger.tryPost(transfer.entry())    // locks, funds check, postings
                              : PostResult.rejected(verdict.reason());
    transfer.apply(result);                                         // POSTED or FAILED
    transfers.save(transfer);
    outbox.add(TransferEvent.of(transfer));                         // same transaction
    var response = StoredResponse.of(transfer);
    idempotency.complete(client, key, response);
    return response;
}

Keys are scoped per client and kept for 7 days; reuse after expiry is documented as undefined. External withdrawals can't finish inside one transaction, so their stored response is 202 Accepted with the transfer id, and that is replayed too.

Transaction boundaries and "exactly once"

Inside one local transaction: the idempotency record, the transfer row and its state, every posting, the balance updates, and the outbox rows. Through the outbox, afterwards: the rail command, customer notifications, webhooks to merchants, analytics.

Guarantee · Effectively once

No protocol can guarantee exactly-once delivery over an unreliable network. This system guarantees: (1) at-least-once delivery, because the outbox relay retries until the broker acknowledges; (2) idempotent effects, because each consumer records the event id in the same transaction as its effect; (3) detection of anything outside both, because reconciliation (L471) compares the ledger with the rail's records. "Exactly once" here means at least once plus idempotence, checked by reconciliation. Kafka transactions give exactly-once only for read-process-write within Kafka; they don't cover your database or a bank.

Unknown outcomes on an external rail

A withdrawal posts Dr customer wallet, Cr withdrawals in transit, then the rails adapter calls the bank with the transfer id as its reference. On a timeout the outcome is unknown, and the funds stay in transit: neither returned to the customer nor counted as settled. Query the rail by reference. Found and succeeded: post Dr in transit, Cr bank cash, and mark SETTLED. Found and failed: reversing entry, REVERSED. Not found: resend with the same reference, which the rail deduplicates; if it can't, only query. After N attempts the transfer goes to a manual-review queue. Never reverse on timeout alone: that is how money gets paid out twice.

The chaos test

Run 1,000 random transfers from 32 clients against two instances. A test-only fault hook calls Runtime.getRuntime().halt(1) at named points (after the claim, after postings before commit, after commit before the response, inside the relay). Restart, let clients retry every non-final request with the same key, then assert: per currency, all balances sum to zero; customer wallets plus in-transit equal deposits minus settled withdrawals minus net fees; each key maps to at most one entry; every transfer is final or resumable; materialised balances equal aggregated ones. The first two assertions are "no money created or destroyed".

What breaks in production
  • Check-then-insert idempotency (SELECT the key, then INSERT) lets two concurrent duplicates both see "absent". Only a unique constraint closes the race.
  • Committing the key and the effect separately: a crash in between either loses the response or makes a retry repeat the effect.
  • Reversing a withdrawal on timeout: the bank paid, you refunded, and the customer has the money twice.

Project C, Part 3: Reporting, Spring Batch & Scheduling

50m video150m practicecapstone project

Batch work in a ledger (settlement, statements, reconciliation) must be restartable from the middle, safe to run twice, and observable when it doesn't run at all. Spring Batch supplies the first, careful keys supply the second, and a "last success" metric with an alert supplies the third.

Spring Batch: the moving parts

Definition · Job instance and restart

A JobInstance is the job name plus its identifying JobParameters; each attempt to run it is a JobExecution. Launching a COMPLETED instance again throws JobInstanceAlreadyCompleteException; launching a FAILED one restarts it from the last commit. Non-identifying parameters (a run timestamp, a log level) don't create new instances. With businessDate as the identifying parameter, "settle 10 October" can succeed only once.

Chunk steps add faultTolerant() policies: retry transient errors (deadlocks, connection resets) a few times, and skip a bounded number of bad records into a skip listener that writes them to an errors table. Listeners (job, step, chunk, skip) feed metrics and logs. To scale, partition the step: a Partitioner splits account-id ranges into execution contexts, each restartable on its own. A multi-threaded step (.taskExecutor(…)) is simpler but needs thread-safe readers with saveState(false), so it gives up restartability.

The end-of-day settlement job

@Bean @StepScope
JdbcPagingItemReader<AccountDayTotal> dayTotals(DataSource ds,
        @Value("#{jobParameters['businessDate']}") LocalDate day) {
    return new JdbcPagingItemReaderBuilder<AccountDayTotal>()
            .name("dayTotals").dataSource(ds).pageSize(1_000)
            .selectClause("account_id, currency, sum(amount_minor) AS net_minor, count(*) AS postings")
            .fromClause("posting").whereClause("effective_date = :day")
            .groupClause("account_id, currency")              // one currency per account: account_id is unique
            .sortKeys(Map.of("account_id", Order.ASCENDING))  // keyset paging; restart resumes after last key
            .parameterValues(Map.of("day", day))
            .rowMapper(new DataClassRowMapper<>(AccountDayTotal.class))
            .build();
}

@Bean
Step settle(JobRepository repo, PlatformTransactionManager tx,
            JdbcPagingItemReader<AccountDayTotal> dayTotals, JdbcBatchItemWriter<AccountDayTotal> settlementWriter) {
    return new StepBuilder("settle", repo)
            .<AccountDayTotal, AccountDayTotal>chunk(1_000, tx)
            .reader(dayTotals).writer(settlementWriter)        // INSERT … ON CONFLICT (date, account_id) DO NOTHING
            .faultTolerant().retry(TransientDataAccessException.class).retryLimit(3)
            .build();
}

@Bean
Job eodSettlement(JobRepository repo, Step settle, Step checkTotals, Step report) {
    return new JobBuilder("eodSettlement", repo).start(settle).next(checkTotals).next(report).build();
}

checkTotals is a tasklet asserting that settlement nets sum to zero per currency, which must hold because every entry did; if it doesn't, the job fails loudly before the report goes anywhere. report writes the summary to a deterministic object key (settlement/2026-10-10.csv), so a rerun overwrites the file with identical content. Test restartability: fail the writer on chunk 7 of 20, relaunch with the same parameters, assert chunks 1–6 weren't rewritten and the totals are right.

Statements to CSV and PDF without running out of memory

@Bean @StepScope
JdbcCursorItemReader<StatementLine> statementLines(DataSource ds, @Value("#{jobParameters['month']}") String month) {
    var ym = YearMonth.parse(month);
    return new JdbcCursorItemReaderBuilder<StatementLine>()
            .name("statementLines").dataSource(ds)
            .sql(STATEMENT_SQL)                                // ORDER BY account_id, effective_date, id
            .preparedStatementSetter(ps -> { ps.setObject(1, ym.atDay(1)); ps.setObject(2, ym.plusMonths(1).atDay(1)); })
            .fetchSize(1_000)
            .connectionAutoCommit(false)                       // PostgreSQL streams with a fetch size only outside autocommit
            .rowMapper(new DataClassRowMapper<>(StatementLine.class))
            .build();
}

A FlatFileItemWriter appends CSV lines chunk by chunk, so 5 million rows flow through a constant-size window and heap stays flat. Running balances are computed in the processor from the opening balance as rows arrive, never by loading the month. For PDF, render per customer per month (thousands of rows, not millions) with a library that writes finished pages to the output stream, such as OpenPDF. Bulk exports stay CSV.

Reconciliation against the provider's file

Step 1 loads the provider's settlement file into recon_external with a FlatFileItemReader, recording the file's SHA-256 so the same file loaded twice is a no-op. Step 2 classifies breaks in one statement:

INSERT INTO recon_break (run_id, kind, reference, internal_minor, external_minor)
SELECT :run,
       CASE WHEN i.reference IS NULL THEN 'MISSING_INTERNAL'
            WHEN x.reference IS NULL THEN 'MISSING_EXTERNAL'
            ELSE 'AMOUNT_OR_CURRENCY_MISMATCH' END,
       coalesce(i.reference, x.reference), i.amount_minor, x.amount_minor
FROM (SELECT * FROM rail_movement WHERE value_date = :day) i
FULL OUTER JOIN (SELECT * FROM recon_external WHERE file_id = :file) x ON x.reference = i.reference
WHERE i.reference IS NULL OR x.reference IS NULL
   OR i.amount_minor <> x.amount_minor OR i.currency <> x.currency
ON CONFLICT (run_id, reference) DO NOTHING;

A further pass adds STATUS_MISMATCH (we hold FAILED, they show settled) and DUPLICATE (a reference twice in their file). MISSING_EXTERNAL becomes a break only after a one-business-day timing tolerance. Breaks go to an exceptions queue with owner, age and resolution. A resolution is either an adjusting journal entry or a written explanation, never an edit to postings.

Scheduling, and knowing that it ran

OptionBehaviour with three replicas
Plain @ScheduledRuns on all three. Spring Batch's repository rejects a second concurrent execution of the same instance, but other scheduled work just runs three times.
ShedLockA lock row per task: lockAtMostFor frees it if the holder dies, and lockAtLeastFor stops a fast node running it again because of clock skew. It prevents overlap; it is not a scheduler and remembers no missed runs.
Quartz, JDBC job storeTriggers persist in the database and each fires on exactly one cluster node. Missed fires (all nodes down) are handled by misfire instructions.
 
spring.quartz:
  job-store-type: jdbc
  properties:
    org.quartz.jobStore.isClustered: true
    org.quartz.scheduler.instanceId: AUTO
    org.quartz.jobStore.misfireThreshold: 60000      # later than this counts as a misfire
# EOD settlement: CronTrigger with MISFIRE_INSTRUCTION_FIRE_ONCE_NOW (yesterday must still settle)
# 09:00 reminder email: MISFIRE_INSTRUCTION_DO_NOTHING (a late reminder is worse than none)

A job that never starts raises no error, so alert on absence: a gauge of the last successful completion per job (from a JobExecutionListener), with an alert when time() - last_success > 26h, and a check that the output exists (a settlement row count above zero for the date). Safe reruns follow from four rules: identifying parameters equal to the business date, writers keyed on natural keys with ON CONFLICT, deterministic output locations, and no external side effect without its own idempotency key.

What breaks in production
  • A different datasource for the JobRepository: chunk commits and progress commits diverge, and a restart double-counts a chunk.
  • OFFSET paging over a table being written: rows shift between pages and are skipped or read twice. Use sort-key paging.
  • The silent cron: a misconfigured time zone or a disabled profile, and settlement hasn't run for three days before anyone notices.

public class EncryptedString implements AttributeConverter<String, String> {
    private final EnvelopeCrypto crypto;
    public EncryptedString(EnvelopeCrypto crypto) { this.crypto = crypto; }
    @Override public String convertToDatabaseColumn(String v) { return v == null ? null : crypto.encrypt(v); }
    @Override public String convertToEntityAttribute(String v) { return v == null ? null : crypto.decrypt(v); }
}

// EnvelopeCrypto.encrypt: AES-256-GCM under the current data key, key id bound as associated data
String encrypt(String plain) {
    var dek = keys.current();                              // unwrapped once via KMS, cached briefly
    try {
        var iv = new byte[12];
        random.nextBytes(iv);
        var c = Cipher.getInstance("AES/GCM/NoPadding");
        c.init(Cipher.ENCRYPT_MODE, dek.secretKey(), new GCMParameterSpec(128, iv));
        c.updateAAD(dek.id().getBytes(StandardCharsets.UTF_8));
        var ct = c.doFinal(plain.getBytes(StandardCharsets.UTF_8));
        return "v1:" + dek.id() + ":" + B64.encodeToString(iv) + ":" + B64.encodeToString(ct);
    } catch (GeneralSecurityException e) {
        throw new IllegalStateException("encryption failed", e);
    }
}

Fields such as tax id, date of birth and address use @Convert(converter = EncryptedString.class). Equality search goes through a blind index column (an HMAC of the normalised value), never by decrypting the table. GCM must never reuse an IV under one key; with random 96-bit IVs, NIST SP 800-38D caps a key at 232 encryptions, and monthly data keys stay far below that.

Audit logging an auditor will accept

String link(String prevHash, AuditRecord r) throws NoSuchAlgorithmException {
    var md = MessageDigest.getInstance("SHA-256");
    md.update(HexFormat.of().parseHex(prevHash));
    md.update(CanonicalJson.of(r).getBytes(StandardCharsets.UTF_8));   // fixed field order, no whitespace
    return HexFormat.of().formatHex(md.digest());                     // stored with the record
}

Each record says who (and on whose behalf), what, which resource, when, from where and the outcome, denied attempts included. The audit service is the single writer of its own append-only database, chains every record to the previous one, and hourly anchors the head hash in WORM storage (S3 Object Lock, compliance mode). That makes it tamper-evident, not tamper-proof: a rewrite no longer matches the anchors, and a daily job re-verifies the chain. Retention follows the regulation. Application logs, sampled and rotated, are never the record.

Access control, maker-checker and secrets

@PreAuthorize("hasAuthority('adjustment:approve')")
@Transactional
public JournalEntryId approve(ApprovalId id, Authentication checker) {
    var req = approvals.lockPending(id);                       // FOR UPDATE; rejects expired requests
    if (req.makerId().equals(checker.getName())) throw new SegregationOfDutiesViolation(id);
    req.approve(checker.getName(), clock.instant());           // DB CHECK (approved_by <> requested_by) too
    var entry = ledger.post(req.payload());                    // exactly the payload that was requested
    audit.record("adjustment.approved", id, checker, entry);
    return entry;
}

Adjustments, large transfers and limit changes need a maker and a different checker; the payload is fixed at request time.
