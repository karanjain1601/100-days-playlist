Spring Data

Phase 15 is about Spring Data, the repository layer that sits between the REST controllers of Phase 14 and the database: how an interface becomes a working repository, and how to choose between derived queries, @Query, Specifications, Querydsl and projections for each access pattern. It then applies the same programming model to Spring Data JDBC, MongoDB and Redis, and leads into Phase 16's transaction management. The milestone is a repository layer with derived queries, specifications, projections, keyset pagination and auditing, benchmarked against raw SQL.

By the end of this phase you can

  • Explain how Spring Data builds a repository proxy, what save() does for new and detached entities, and expose only the repository methods callers need.
  • Write derived queries, JPQL and native @Query methods (with countQuery, sorting, SpEL and hints), and recognise when a method name has become unreadable.
  • Run bulk updates and deletes safely, keeping the persistence context consistent, and put transaction boundaries on service methods rather than repositories.
  • Build optional-filter search with composable Specifications or Querydsl, without duplicate rows, broken count queries or unescaped LIKE patterns.
  • Return DTOs and interface projections instead of entities, and paginate with Page, Slice or keyset scrolling depending on whether the client needs a total.
  • Add auditing and custom repository fragments, and decide when Spring Data JDBC, MongoDB or Redis fits better than JPA.

L317 · DAY 317

Spring Data Architecture & Repository Interfaces

40m video45m practice

A Spring Data repository is an interface you declare and Spring implements at startup: a dynamic proxy that sends CRUD calls to a generic store-specific class and query methods to queries it built by parsing their names. Knowing that proxy, the interface hierarchy and what save() actually does explains most surprises, from extra SELECTs to methods you never meant to expose.

One programming model, many stores

Spring Data is an umbrella of modules (JPA, JDBC, MongoDB, Redis, Elasticsearch, Cassandra, R2DBC, Neo4j, plus Spring Data REST, which exports repositories over HTTP) built on a shared core, spring-data-commons. The core provides what feels the same everywhere: repository interfaces, query derivation from method names, Pageable/Sort, projections, auditing and Query by Example. Each module adds its own mapping annotations, a template for low-level access (MongoTemplate, RedisTemplate, JdbcAggregateTemplate…) and its own query language for @Query. The abstraction is shared; the semantics are not: a JPA save can be deferred until flush, while a JDBC or MongoDB save writes immediately.

How an interface becomes a bean

Algorithm · repository bootstrap
  1. @EnableJpaRepositories (applied by Boot's auto-configuration to the @SpringBootApplication package) imports a registrar derived from RepositoryBeanDefinitionRegistrarSupport.
  2. The registrar scans for interfaces extending Repository and registers a JpaRepositoryFactoryBean definition for each.
  3. When the bean is created, JpaRepositoryFactory instantiates the base class SimpleJpaRepository for the entity type and wraps it in a JDK dynamic proxy implementing your interface.
  4. It adds interceptors: transactions (from SimpleJpaRepository's annotations), persistence exception translation, and QueryExecutorMethodInterceptor, which at this point resolves every query method into a RepositoryQuery: a parsed derived query, an @Query or a named query.
  5. At call time the proxy routes each method: query methods to their RepositoryQuery, custom methods to fragments, everything else to SimpleJpaRepository.

Because step 4 happens at startup, a misspelled property in findByStatsu fails the application context on boot. spring.data.jpa.repositories.bootstrap-mode=deferred (or lazy) moves that work off the startup path, at the cost of finding errors later.

  • flush/saveAndFlush force pending SQL now, e.g. to surface a constraint violation inside the method that caused it.

save() is "persist or merge"

// SimpleJpaRepository.save, in essence
if (entityInformation.isNew(entity)) { em.persist(entity); return entity; }
else                                 { return em.merge(entity); }
Definition · isNew

By default an entity is new if its @Version property (of a wrapper type) is null; without a version, if its id is null (or 0 for a primitive). An entity whose id you assign yourself (a natural key, a UUID set in the constructor) is therefore never new, so save calls merge, and merge must first SELECT the row to find out whether to update or insert.

@Entity
class Sku implements Persistable<String> {
    @Id private String code;                       // assigned, not generated
    private String name;
    @Transient private boolean isNew = true;

    protected Sku() {}
    Sku(String code, String name) { this.code = code; this.name = name; }

    @Override public String getId() { return code; }
    @Override public boolean isNew() { return isNew; }

    @PostPersist @PostLoad
    void markNotNew() { this.isNew = false; }
}

-- same call, Persistable.isNew() == true: persist

Persistable lets the entity answer isNew itself; a wrapper @Version Long version field achieves the same and adds optimistic locking. Remember also that merge returns a different, managed instance: always use the value save returns.

Expose less, share more

interface OrderRepository extends Repository<Order, Long> {      // only what callers need
    Optional<Order> findById(Long id);
    Order save(Order order);
    List<Order> findByStatus(OrderStatus status);
}

@NoRepositoryBean                                                    // base, never instantiated
interface ReadOnlyRepository<T, ID> extends Repository<T, ID> {
    Optional<T> findById(ID id);
    List<T> findAll(Sort sort);
    long count();
}

interface CountryRepository extends ReadOnlyRepository<Country, String> {}

Extending JpaRepository hands every caller deleteAll(), deleteAllInBatch() and flush(). Declaring methods selectively on Repository gives the same implementations (signatures matching CRUD methods route to SimpleJpaRepository) with a deliberate surface: a reference-data repository that can't write, an audit log that can't delete. @NoRepositoryBean marks shared base interfaces so the scanner doesn't try to create a repository for them.

Scanning: Boot scans from the main application class's package. Use @EnableJpaRepositories(basePackages = …) for repositories elsewhere, or repositoryBaseClass to replace SimpleJpaRepository globally. With two Spring Data modules on the classpath (JPA and Redis, say) Spring Data enters strict configuration mode and only claims a repository for a store when the interface extends a store-specific type (JpaRepository) or the entity carries that store's annotation (@Entity); separate base packages per store keep it unambiguous.

What breaks in production
  • A SELECT before every insert for entities with assigned ids, doubling write latency in bulk imports.
  • Ignoring save's return value after a merge: later changes go to the detached copy and are silently lost.
  • Repositories silently not created when a second Spring Data module triggers strict mode; the log says "Multiple Spring Data modules found".
  • Repositories as the service layer: controllers calling deleteAll because it was available.

Practice · 45 min

  1. Set a breakpoint in a service on a repository call; inspect the proxy class, its target and interceptor list, and step into SimpleJpaRepository.save.
  2. Create Sku with an assigned id, enable SQL logging, save 1,000 rows, and count the SELECTs; repeat with Persistable and with a @Version field.
  3. Misspell a property in a derived query method and read the startup error; switch to deferred bootstrap and see when it fails instead.
  4. Replace a JpaRepository with a narrow Repository declaration and fix the call sites that relied on the extra methods.

L318 · DAY 318

Derived Query Methods

40m video50m practice

A derived query is a method name parsed at startup into a query: a subject, the keyword By, and a predicate of property paths joined by operators. It is the fastest way to write simple, fixed queries, and it stops being the right tool at the point where the name is harder to read than the JPQL would be.

The grammar

Definition · derived query

The subject picks the operation: find, read, get, query, search and stream all select; count counts; exists checks existence; delete/remove delete. Between the subject and By you may put Distinct, First/Top with an optional number, or any descriptive word (findSliceByStatus is just findByStatus). After By come property expressions, each a property path plus an optional operator keyword, joined with And/Or, and finally an optional OrderBy…Asc/Desc. PartTree parses the name, PartTreeJpaQuery turns it into a Criteria query, and both happen when the repository is created, so mistakes fail at startup.

Nested properties: for findByCustomerAddressCity the parser first looks for a property customerAddressCity, then splits the camel-case name from the right (customerAddress.city, then customer.addressCity, then customer.address.city) until a path resolves, joining as needed. If the entity also had a customerAddress property, the guess could be wrong; an underscore fixes the split points explicitly. That makes underscores reserved, which is another reason Java fields should be camelCase.

Return types

  • T (returns null when nothing matches) and Optional<T>: single result. More than one row throws IncorrectResultSizeDataAccessException; use findFirst… or make the predicate unique.
  • List<T>: everything that matches, so bound it with Top or a Pageable.
  • Page<T>: a page plus a COUNT query for totals; Slice<T>: fetches one extra row to know whether a next page exists; Window<T> (Spring Data 3.1): scrolling by offset or keyset with a ScrollPosition (L324).
  • Stream<T>: rows are read from an open cursor as you consume them. The caller must hold a transaction and close the stream.
  • CompletableFuture<T>/Future<T> with @Async on the method: runs on a task executor (needs @EnableAsync), outside the caller's transaction.
@Transactional(readOnly = true)
void exportOldOrders(Instant cutoff, Consumer<Order> sink) {
    try (Stream<Order> orders = repository.streamByCreatedAtBefore(cutoff)) {
        orders.forEach(o -> {
            sink.accept(o);
            entityManager.detach(o);              // keep the persistence context from growing
        });
    }
}

Derived deleteBy… loads every matching entity and calls remove on each, so cascades and callbacks run, at the price of one SELECT plus N DELETEs. For bulk deletes use a @Modifying query or deleteAllInBatch (L320).

When names stop working

findByStatusAndCustomerAddressCountryAndCreatedAtBetweenAndTotalCentsGreaterThanOrderByCreatedAtDesc is valid, and nobody can review it. Change tools when any of these appear:

  • More than two or three predicates, or names you have to read twice: write @Query with JPQL (L319).
  • Optional filters: derived queries can't skip a null argument (it becomes is null), so n optional filters need 2n methods. Use Specifications (L321) or Querydsl (L322).
  • Aggregates, grouping, conditions on joins, DTO results: @Query or projections (L323).

Validating at startup comes for free with the default bootstrap mode: derived queries are parsed and JPQL in @Query is compiled when the repository bean is created. A @DataJpaTest that only starts the context therefore checks every query method against the real mappings; keep one in the build.

What breaks in production
  • A single-result method that starts returning two rows when the data changes (a duplicated email) and throws on every call. Back uniqueness with a constraint or use findFirst.
  • IgnoreCase defeats indexes: upper(email) can't use a plain index on email. Add a function-based index or store a normalized column.
  • Unclosed streams hold a connection and cursor until the transaction ends, or leak outside one.
  • Unbounded List results that were fine with 1,000 rows and run out of memory at 10 million.

Practice · 50 min

  1. Write ten derived queries over an Order/Customer/Address model, enable SQL logging, and write down the SQL Hibernate generates for each.
  2. Insert two customers with the same email and call findByEmail; catch the exception, then fix it two ways.
  3. Add a customerAddress field to break findByCustomerAddressCity's resolution, then fix it with underscores.
  4. Stream 100,000 orders inside a read-only transaction with detaching, and compare heap use against findAll().
  5. Rewrite your longest derived query as @Query and decide which version you'd rather maintain.

L319 · DAY 319

@Query: JPQL, Native SQL & SpEL

40m video45m practice

@Query puts the query text next to the method that runs it: JPQL by default, which is validated at startup and portable across databases, or native SQL when you need a database feature JPQL lacks. Parameters, sorting, paging, SpEL and projections all work on top of it, with a few sharp edges, mostly on the native side.

How Spring Data finds a method's query

JPQL with parameters and sorting

interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("""
           select o from Order o
           where o.status = :status and o.createdAt >= :since
           order by o.createdAt desc""")
    List<Order> recent(@Param("status") OrderStatus status, @Param("since") Instant since);

    @Query("select o from Order o where o.customer.id = ?1 and o.status = ?2")   // positional
    List<Order> byCustomerAndStatus(long customerId, OrderStatus status);

    @Query("select o from Order o where o.status = :status")
    List<Order> byStatus(@Param("status") OrderStatus status, Sort sort);       // order by appended

    @Query("select o from Order o where o.note like %:fragment%")              // Spring Data LIKE syntax
    List<Order> noteContains(@Param("fragment") String fragment);
}

Named parameters (:status) bind by name, so reordering method parameters or adding one in the middle can't silently swap values, and the query reads on its own. Positional ones (?1) bind by index: rearrange the signature and two parameters of the same type trade places without any error. With -parameters (Boot's default) @Param can be omitted, but keeping it makes the binding independent of compiler flags. A trailing Sort or Pageable parameter is appended to JPQL as order by o.<property>; Spring Data checks that the names are plain property paths, so sorting by an expression requires JpaSort.unsafe("length(o.note)"), deliberately named to make you think about where that string came from.

Native SQL and countQuery

@Query(value = """
       select o.* from orders o
       where o.status = :status
         and to_tsvector('english', o.note) @@ plainto_tsquery('english', :q)""",
       countQuery = """
       select count(*) from orders o
       where o.status = :status
         and to_tsvector('english', o.note) @@ plainto_tsquery('english', :q)""",
       nativeQuery = true)
Page<Order> search(@Param("status") String status, @Param("q") String q, Pageable pageable);

Native queries reach what JPQL can't: full-text search, JSON operators, window functions, CTEs, database hints. The price is portability (this one is PostgreSQL-only), no validation at startup (the SQL is sent as-is and fails on first call), and mapping by column name. With a Pageable, Spring Data needs a count query: for JPQL it derives one reliably, but for native SQL it can only attempt a textual rewrite, which breaks on DISTINCT, GROUP BY, CTEs and subqueries. Always give countQuery for a paginated native query. Sort works by appending raw column names, so the API's sort keys must match column names exactly, which is fragile; map client sort fields to columns yourself.

SpEL in queries

@NoRepositoryBean
interface SoftDeleteRepository<T, ID> extends JpaRepository<T, ID> {
    @Query("select e from #{#entityName} e where e.deletedAt is null")    // resolved per entity
    List<T> findAllActive();
}

interface InvoiceRepository extends SoftDeleteRepository<Invoice, Long> {

    @Query("select i from Invoice i where i.tenantId = ?#{principal.tenantId}")
    List<Invoice> findMine();                                 // needs SecurityEvaluationContextExtension

    @Query("select i from Invoice i where i.reference like %?#{escape([0])}% escape ?#{escapeCharacter()}")
    List<Invoice> referenceContains(String fragment);         // user input with % or _ stays literal
}

// @Bean SecurityEvaluationContextExtension securityEvaluationContextExtension() {
//     return new SecurityEvaluationContextExtension();       // spring-security-data
// }
  • #{#entityName} expands to the entity name of the concrete repository, so one generic query in a @NoRepositoryBean base serves every entity with a deletedAt column.
  • ?#{principal.tenantId} evaluates against Spring Security's current Authentication (once the extension bean is registered) and binds the result as a parameter: a tenant filter the caller can't forget to pass. It is still a parameter, not string concatenation.
  • %:fragment% wraps the bound value in wildcards, but a user typing % matches everything; escape([0]) with escapeCharacter() escapes the wildcards in the argument.

A constructor expression (select new with the fully qualified class name) builds DTOs, records included, straight from the selected columns, with no entity loaded or managed. An interface projection does the same through aliases matching getter names, and also works for native queries. Both are covered in depth in L323.

Definition · named query vs @Query

A @NamedQuery on the entity is parsed by Hibernate when the EntityManagerFactory starts and is found by the repository through the Entity.method naming convention. A JPQL @Query is validated a little later, when Spring Data creates the repository. Both fail fast, so the real difference is locality: @Query keeps the query beside the method that uses it, while named queries centralize queries on the entity (and @NamedNativeQuery pairs with @SqlResultSetMapping for custom result mapping). Most teams prefer @Query.

@QueryHints pass provider hints to the query: org.hibernate.fetchSize controls how many rows the JDBC driver fetches per round trip (important for streaming; some drivers, such as PostgreSQL's, only stream with a fetch size inside a transaction), org.hibernate.readOnly skips dirty-checking snapshots, org.hibernate.cacheable uses the query cache, and jakarta.persistence.query.timeout (milliseconds) cancels runaway queries.

What breaks in production
  • Native query + Pageable without countQuery: wrong totals or a SQL error on the first page request.
  • join fetch of a collection + Pageable: Hibernate can't limit in SQL, logs HHH90003004 ("applying in memory") and loads every row before slicing the page.
  • String concatenation into a native query (in a custom implementation, say): SQL injection. Every value goes in as a parameter.
  • Positional parameters reordered during a refactor: same types, swapped values, wrong results, no error.

Practice · 45 min

  1. Rewrite three long derived queries as JPQL @Querys with named parameters; misspell an entity property and confirm startup fails.
  2. Write a paginated native full-text (or JSON) query; run it without countQuery, observe the result, then add it.
  3. Build SoftDeleteRepository with #{#entityName} and use it for two entities.
  4. Return OrderSummary via a constructor expression and OrderRow via an interface; compare the SQL with loading entities.
  5. Add a jakarta.persistence.query.timeout hint of 100 ms to a query that sleeps (pg_sleep) and handle the resulting exception.

Modifying Queries & Repository Transactions

35m video40m practice

A bulk UPDATE or DELETE runs directly in the database and bypasses the persistence context, so after it the entities in memory are stale and none of the JPA machinery (cascades, versions, callbacks) has run. Repository methods also carry their own transaction defaults, which is why transaction boundaries belong on service methods, where a use case starts and ends.

@Modifying for bulk updates and deletes

interface OrderRepository extends JpaRepository<Order, Long> {

    @Transactional
    @Modifying(flushAutomatically = true, clearAutomatically = true)
    @Query("""
           update Order o set o.status = :to
           where o.status = :from and o.createdAt < :before""")
    int expire(@Param("from") OrderStatus from, @Param("to") OrderStatus to, @Param("before") Instant before);

    @Transactional
    @Modifying
    @Query("delete from OrderEvent e where e.occurredAt < :cutoff")
    int purgeEventsBefore(@Param("cutoff") Instant cutoff);         // returns rows affected
}

Without @Modifying, Spring Data executes the query as a select and fails with InvalidDataAccessApiUsageException. Without a transaction, JPA refuses to run it (TransactionRequiredException: Executing an update/delete query). Query methods you declare get no transaction configuration by default, unlike the CRUD methods inherited from SimpleJpaRepository, so either annotate the method or call it from a transactional service. The return type int (or void) gives the number of affected rows.

The stale persistence context

@Transactional
OrderStatus demo(long id) {
    Order o = orders.findById(id).orElseThrow();         // managed: status OPEN
    orders.expire(OPEN, EXPIRED, Instant.now());         // database row is now EXPIRED
    return orders.findById(id).orElseThrow().getStatus();  // OPEN without clearAutomatically
}
Definition · the two flags

The persistence context is a cache: findById for an id it already manages returns the same instance without querying. A bulk statement changes rows behind its back, so the cached instance keeps the old state, and if it is dirty, its eventual flush can even overwrite the bulk change. clearAutomatically = true calls EntityManager.clear() after the statement so later reads hit the database. Clearing also discards changes that were never flushed, so flushAutomatically = true flushes pending changes before the statement. Use both together, and know that every previously loaded entity is now detached.

What bulk statements skip

  • Cascades: delete from Order doesn't remove OrderLines. You get a foreign-key violation, or orphans if the constraint is missing. Delete children first, or use ON DELETE CASCADE in the schema.
  • Optimistic locking: @Version is neither checked nor incremented, so concurrent editors won't notice the bulk change. Increment it in the statement (set o.version = o.version + 1) if others hold copies.
  • Lifecycle callbacks and listeners: @PreUpdate, @PreRemove, Spring Data auditing (@LastModifiedDate) and Envers revisions don't run. Set audit columns in the statement.
  • Domain events and any invariant enforced in entity methods. If a rule lives in Order.expire(), a bulk update ignores it.

That's the trade: one statement for a million rows instead of a million entity updates. It is right for maintenance jobs and data that carries no per-row behaviour; for business transitions, load the entities, ideally in chunks.

Transaction defaults in Spring Data

SimpleJpaRepository is annotated @Transactional(readOnly = true) at class level, and its write methods (save, delete…, flush) override that with @Transactional. A repository call outside any transaction therefore opens and commits a transaction of its own: a read-only one for findById, which still means a connection checkout, a read-only hint to Hibernate (no flush, no snapshots) and the driver, and a commit. Inside an existing service transaction the repository simply joins it (propagation REQUIRED).

@Service
class OrderService {
    private final OrderRepository orders;
    private final OutboxRepository outbox;
    OrderService(OrderRepository orders, OutboxRepository outbox) { this.orders = orders; this.outbox = outbox; }

    @Transactional(readOnly = true)
    OrderDetails details(long id) {
        Order o = orders.findById(id).orElseThrow(() -> new OrderNotFoundException(id));
        return OrderDetails.of(o, o.getCustomer(), o.getLines());      // lazy loads inside the tx
    }

    @Transactional
    void cancel(long id) {
        Order o = orders.findById(id).orElseThrow(() -> new OrderNotFoundException(id));
        o.cancel();                                        // dirty checking: UPDATE at commit
        outbox.save(OutboxEvent.orderCancelled(o));        // atomic with the update
    }
}

Declare transactions on the service: the service method is the unit of work, so it decides atomicity (the cancellation and its outbox event commit together or not at all), isolation and read-only-ness; it holds one connection for the use case instead of several; and lazy associations load inside it. Repositories stay reusable building blocks that join whatever transaction their caller started. Phase 16 covers propagation and isolation in depth.

saveAll and JDBC batching

saveAll is just a loop over save: it persists each entity, and only Hibernate's JDBC batching (the hibernate.jdbc.batch_size setting from Day 246) turns those inserts into batched round trips. Two things silently disable it: GenerationType.IDENTITY ids, because Hibernate must execute each insert immediately to learn the generated key (use a SEQUENCE with a pooled allocationSize instead), and assigned ids without Persistable, which turn each save into a merge with its own SELECT (L317). For very large loads, flush and clear every batch so the persistence context doesn't grow without bound.

What breaks in production
  • A bulk update followed by a stale read in the same transaction returns the old state and makes a decision on it.
  • clearAutomatically without flushAutomatically discards the caller's unflushed changes, with no error.
  • deleteAll() in a cleanup job loads millions of rows into memory first.
  • Missing service transactions: a "read, check, write" sequence spans three repository transactions, so another request can change the data between the check and the write.

Specifications & Dynamic Queries

45m video50m practice

A search screen with six optional filters can't be a derived query, because every combination would need its own method. A Specification is one reusable predicate built with the JPA Criteria API; you write one per filter, have each return null when its input is absent, and compose them at runtime into exactly the query the request asks for.

JpaSpecificationExecutor and the Specification interface

interface OrderRepository extends JpaRepository<Order, Long>, JpaSpecificationExecutor<Order> {}

@FunctionalInterface
public interface Specification<T> {                       // simplified
    Predicate toPredicate(Root<T> root, CriteriaQuery<?> query, CriteriaBuilder cb);
}
Definition · Specification

A function from the Criteria API's building blocks to a Predicate. root is the queried entity (navigate with get, join, fetch), query is the query being built (for distinct, subqueries and inspecting the result type), and cb creates expressions and predicates. Returning null means "no restriction". JpaSpecificationExecutor adds findAll(spec), findAll(spec, Pageable), findAll(spec, Sort), findOne, count(spec), exists(spec) and delete(spec), all of which run the same predicate.

Composition is built into the interface: Specification.where(a).and(b).or(c) and Specification.not(a) combine predicates, and both where and and accept null and skip it. That rule is the whole trick for optional filters. (Specification.allOf(…) and anyOf(…) combine lists; newer Spring Data versions steer away from where towards these.)

A reusable filter library

final class OrderSpecs {
    private OrderSpecs() {}

    static Specification<Order> hasStatus(OrderStatus status) {
        return status == null ? null : (root, q, cb) -> cb.equal(root.get("status"), status);
    }

    static Specification<Order> createdBetween(Instant from, Instant to) {
        if (from == null && to == null) return null;
        return (root, q, cb) -> {
            Path<Instant> created = root.get("createdAt");
            if (from == null) return cb.lessThan(created, to);
            if (to == null) return cb.greaterThanOrEqualTo(created, from);
            return cb.and(cb.greaterThanOrEqualTo(created, from), cb.lessThan(created, to));   // half-open
        };
    }

    static Specification<Order> customerNameContains(String text) {
        if (text == null || text.isBlank()) return null;
        String pattern = "%" + escapeLike(text.toLowerCase(Locale.ROOT)) + "%";
        return (root, q, cb) -> {
            Join<Order, Customer> customer = root.join("customer");
            return cb.like(cb.lower(customer.get("name")), pattern, '\\');
        };
    }

    static Specification<Order> hasLineWithSku(String sku) {              // to-many: EXISTS, no duplicates
        if (sku == null) return null;
        return (root, query, cb) -> {
            Subquery<Long> sub = query.subquery(Long.class);
            Root<OrderLine> line = sub.from(OrderLine.class);
            sub.select(line.get("id")).where(cb.equal(line.get("order"), root), cb.equal(line.get("sku"), sku));
            return cb.exists(sub);
        };
    }

    static Specification<Order> tenant(String tenantId) { return (root, q, cb) -> cb.equal(root.get("tenantId"), tenantId); }

    static Specification<Order> notDeleted() { return (root, q, cb) -> cb.isNull(root.get("deletedAt")); }

    private static String escapeLike(String s) {
        return s.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
    }
}
record OrderFilter(OrderStatus status, Instant from, Instant to, String customer, String sku) {}

@Transactional(readOnly = true)
Page<OrderDto> search(OrderFilter f, Pageable pageable) {
    Specification<Order> spec = Specification.where(OrderSpecs.tenant(tenants.current()))   // always on
            .and(OrderSpecs.notDeleted())                                                 // always on
            .and(OrderSpecs.hasStatus(f.status()))                                        // optional ...
            .and(OrderSpecs.createdBetween(f.from(), f.to()))
            .and(OrderSpecs.customerNameContains(f.customer()))
            .and(OrderSpecs.hasLineWithSku(f.sku()));
    return orders.findAll(spec, pageable).map(OrderDto::from);
}

String attribute names (root.get("status")) fail only at runtime. The JPA static metamodel (Order_.status, generated by Hibernate's annotation processor) makes them compile-checked: root.get(Order_.status).

Joins, fetch joins and the count query

static Specification<Order> fetchCustomer() {
    return (root, query, cb) -> {
        Class<?> type = query.getResultType();
        if (type != Long.class && type != long.class) {       // skip in the count query
            root.fetch("customer", JoinType.LEFT);
        }
        return null;                                          // fetch only, no restriction
    };
}

findAll(spec, pageable) runs your specification twice: once for the page and once inside a select count(…) for the total. A fetch join in the count query is invalid ("query specified join fetching, but the owner of the fetched association was not present in the select list"), so a fetching specification must check query.getResultType() and only fetch for the entity query. Fetch-joining a collection with paging brings back the in-memory pagination problem from L319; fetch to-one associations only, or load collections in a second query.

Duplicates: joining a to-many association for filtering (root.join("lines")) returns one row per matching line, so an order with three matching lines appears three times and page sizes come out wrong. Either call query.distinct(true), which makes the database deduplicate and can be expensive, or filter with an EXISTS subquery as hasLineWithSku does, which never multiplies rows.

Defaults for tenants and soft delete

Filters that must always apply, such as the tenant and deletedAt is null, are the dangerous ones to leave to each call site. Centralize them: compose them in one service method or a custom repository method that every search goes through, and never expose the raw findAll(spec) to controllers. Hibernate offers alternatives at the mapping level: @TenantId for discriminator-based multi-tenancy, @SoftDelete (Hibernate 6.4+) and @Filter, which apply to every query including ones that don't use specifications.

What breaks in production
  • Duplicate rows from a to-many join: pages with 17 items instead of 20 and totals that don't match.
  • Unescaped user input in like: a search for % or _ matches everything and scans the table.

  • Leading-wildcard like '%ada%' can't use a B-tree index; at scale use trigram or full-text indexes.

private static BooleanExpression statusEq(OrderStatus s) { return s == null ? null : o.status.eq(s); }
private static BooleanExpression createdFrom(Instant t)  { return t == null ? null : o.createdAt.goe(t); }
private static BooleanExpression customerContains(String q) {

}
private static BooleanExpression hasSku(String sku) {                     // subquery: EXISTS
    if (sku == null) return null;
    QOrderLine l = QOrderLine.orderLine;
    return JPAExpressions.selectOne().from(l).where(l.order.eq(o), l.sku.eq(sku)).exists();

Projections & DTO Mapping

40m video45m practice

A projection asks Spring Data for a shape instead of an entity: only the columns you need, no managed instance, no dirty-check snapshot, no lazy proxies. For read paths that is often the single biggest performance win available, but only if the projection is one Spring Data can push down into the SELECT; open and some nested projections quietly load the whole entity anyway.

Closed interface projections

Declare an interface whose getters match entity property names and use it as the return type. Spring Data knows every property the proxy will need, so for a derived query it builds a tuple query that selects exactly those paths, then wraps each jakarta.persistence.Tuple in a map-backed JDK proxy that implements your interface.

@Entity @Table(name = "orders")
class Order {
    @Id @GeneratedValue Long id;
    @Enumerated(EnumType.STRING) OrderStatus status;
    BigDecimal total;
    Instant createdAt;
    @ManyToOne(fetch = FetchType.LAZY) Customer customer;
    @OneToMany(mappedBy = "order") List<LineItem> items = new ArrayList<>();
}

interface OrderSummary {                 // closed: every getter is a property
    Long getId();
    OrderStatus getStatus();
    BigDecimal getTotal();
}

interface OrderRepository extends JpaRepository<Order, Long> {
    List<OrderSummary> findByStatus(OrderStatus status);
    <T> List<T> findByCreatedAtAfter(Instant from, Class<T> type);   // dynamic
}

Open projections and their catch

Definition · open projection

A projection interface with at least one getter annotated @Value holding a SpEL expression evaluated against target, the backing object. Because the expression can touch anything, Spring Data cannot know which columns it needs, so it loads the full entity and evaluates the expression on it.

interface CustomerLabel {
    @Value("#{target.firstName + ' ' + target.lastName}")
    String getFullName();

    default String getInitials() {                 // computed from closed getters
        return getFirstName().charAt(0) + "" + getLastName().charAt(0);
    }
    String getFirstName();
    String getLastName();
}

The @Value getter makes CustomerLabel open: you get a managed Customer with every column, a snapshot, and the proxy on top. A default method computed from closed getters keeps the projection closed, so prefer it for simple derivations. @Value("#{@formatter.format(target)}") can even call beans, which is powerful and a strong signal that the mapping belongs in Java code instead.

DTO classes, dynamic and nested projections

A class-based projection is a record or class whose constructor parameters match property names. For derived queries Spring Data JPA emits a JPQL constructor expression, so the result is a plain object: no proxy, no persistence context, cheap to serialize. Records are the natural fit; parameter names come from the record components.

record OrderRow(Long id, OrderStatus status, BigDecimal total) {}

// same method, three shapes, decided by the caller
var rows   = orders.findByCreatedAtAfter(since, OrderRow.class);
var views  = orders.findByCreatedAtAfter(since, OrderSummary.class);
var full   = orders.findByCreatedAtAfter(since, Order.class);

A dynamic projection (the Class<T> parameter) lets one query method serve several shapes; the query is derived per requested type at call time. A nested projection returns another projection from a getter:

interface OrderWithCustomer {
    Long getId();
    CustomerName getCustomer();
    interface CustomerName { String getFirstName(); String getLastName(); }
}

Spring Data cannot narrow a nested projection to the nested columns: it selects the association as an entity (a join that loads every Customer column), and depending on the version may fall back to loading the root entity too. A nested projection over a collection (List<ItemView> getItems()) is worse: the root is loaded as an entity and each proxy navigates the lazy collection, one SELECT per order. Flatten instead, with a DTO and a join in @Query.

       select o.id as id, count(i.id) as itemCount

With JPQL, a DTO needs an explicit constructor expression with the fully qualified class name; interface projections need aliases matching the getter names. Native queries have no constructor expressions, so use an interface projection keyed by column alias. When you want untyped rows (ad-hoc reports, a dynamic column list), drop to JPA in a custom fragment (L325): em.createQuery(jpql, Tuple.class) and read tuple.get("total", BigDecimal.class).

Why projections pay off, and how to prove it

@Transactional(readOnly = true) lets Hibernate skip snapshots and flushing, but it still hydrates full entities and tracks them. Projections remove the work rather than tuning it. To measure, seed 50,000 orders and compare findAll() entities, a closed projection and a record DTO: run each several times to warm up, then record wall time, allocated bytes (JFR, or ThreadMXBean.getThreadAllocatedBytes) and SQL from the log. Expect the projections to win clearly on allocation and time, with the gap widening as the entity gets wider; write down your own numbers rather than trusting anyone's.

MapStruct belongs after the query, not instead of it. Fetch the narrow shape, then let a generated mapper handle renames, formatting and nesting when the mapping is more than a constructor call:

@Mapper(componentModel = "spring")
interface OrderApiMapper {
    @Mapping(target = "customer", source = "lastName")
    @Mapping(target = "totalText", expression = "java(money(line.total()))")
    OrderResponse toResponse(OrderLine line);

    default String money(BigDecimal amount) { return amount.setScale(2, RoundingMode.HALF_UP).toPlainString(); }
}
record OrderLine(Long id, String lastName, BigDecimal total) {}
record OrderResponse(Long id, String customer, String totalText) {}

Mapping entities with MapStruct is fine for writes and small reads; mapping an entity list to DTOs for a large read keeps every cost the projection would have avoided, and a mapper touching order.getItems() triggers lazy loads.

What breaks in production
  • An innocent @Value getter turns a three-column query into a full entity load; review projections for SpEL.
  • Nested collection projections produce N+1 selects; the SQL log is the only reliable check.
  • Native alias case: some databases fold unquoted aliases (itemCount may come back as itemcount); if a getter returns null, check the alias.
  • Constructor mismatch: a JPQL constructor expression whose argument types do not match a constructor fails at startup (good) or, for dynamic projections, on first call.
  • Returning projection proxies from controllers works with Jackson, but the JSON shape follows getter names; renaming an entity field silently changes the API. Map to an explicit response record.

Definition · page vs slice

A page is a slice plus a total: Spring Data runs the content query, then a derived COUNT, skipping the count only when the answer is already known (a first page shorter than size, or a short last page). On a filtered join that count can cost as much as the page itself. A slice asks for size + 1 rows and drops the extra one: if it arrived, there is a next page.

interface OrderRepository extends JpaRepository<Order, Long> {
    Page<OrderRow>  findByStatus(OrderStatus status, Pageable pageable);
    Slice<OrderRow> findSliceByStatus(OrderStatus status, Pageable pageable);
    Window<Order> findFirst20ByStatusOrderByCreatedAtDescIdDesc(
            OrderStatus status, ScrollPosition position);
}

Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.asc("customer.lastName").ignoreCase().nullsLast(),
        Sort.Order.asc("id"));                                  // unique tie-breaker
Page<OrderRow> page = orders.findByStatus(PAID, PageRequest.of(0, 20, sort));

Sort.by("createdAt").descending() covers the simple case; Sort.Order adds per-property direction, ignoreCase() (wraps the column in a case function, which a plain index cannot serve) and null handling (nullsFirst()/nullsLast(); check the SQL, as support varies by query type and dialect). Always end with a unique property: two rows with the same createdAt may otherwise swap between requests and appear on two pages or none.

Do not serialize Page directly

Returning Page<T> from a controller serializes PageImpl's getters: pageable, sort, numberOfElements, first, empty and more. That structure is an implementation detail; Spring Data 3.3 started logging a warning that it is not guaranteed to be stable. serialization-mode: via-dto (or @EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)) switches to PagedModel, a stable content + page shape. Better still, own the contract:

                              long totalItems, int totalPages) {
    public static <T> PageResponse<T> from(Page<T> p) {
        return new PageResponse<>(p.getContent(), p.getNumber(), p.getSize(),
                                  p.getTotalElements(), p.getTotalPages());
    }
}

The deep-offset problem

Measure it yourself: load 5 million orders, index (created_at, id), and time pages at offsets 0, 100k, 1M and 4M with EXPLAIN ANALYZE. Latency grows roughly in proportion to the offset, while a keyset query stays flat. Offsets also drift: an insert at the head shifts every later page by one, so a user paging through a live table sees duplicates or misses rows.

Cursors: never expose raw keys as query parameters the client edits. Encode the last row's keys into an opaque token and decode it on the way in:

record Cursor(Instant createdAt, long id) {
    String encode() {
        var raw = createdAt.toEpochMilli() + ":" + id;
        return Base64.getUrlEncoder().withoutPadding().encodeToString(raw.getBytes(UTF_8));
    }
    static Cursor decode(String token) {
        var parts = new String(Base64.getUrlDecoder().decode(token), UTF_8).split(":");
        return new Cursor(Instant.ofEpochMilli(Long.parseLong(parts[0])), Long.parseLong(parts[1]));
    }
    ScrollPosition position() {
        return ScrollPosition.forward(Map.of("createdAt", createdAt, "id", id));
    }
}

Keep the timestamp's full precision in the token if the column stores microseconds, or rows sharing a millisecond are skipped. Add an HMAC or a version prefix if clients must not forge cursors or if the sort may change.

What breaks in production
  • A COUNT on every scroll of an infinite feed: switch to Slice or Window.
  • Non-unique sort: rows repeat or vanish between pages; add the id as the final key.
  • Unbounded size: the default cap of 2000 is still huge for wide entities; set your own.
  • Page JSON as API: an upgrade changes field names under your clients.
  • Paginating a fetch join over a collection: Hibernate applies the limit in memory after loading everything and logs a warning (HHH90003004).

Auditing, Custom Implementations & Fragment Composition

40m video45m practice

A Spring Data repository is not one class but a composition: your fragments first, then the base class, then the derived queries. Once you see it that way, auditing, hand-written EntityManager code, soft deletes and read replicas all become small, local additions instead of workarounds.

Auditing: who and when, filled in for you

Auditing is a JPA entity listener. AuditingEntityListener runs on @PrePersist and @PreUpdate and asks an AuditingHandler to fill fields marked @CreatedDate, @LastModifiedDate, @CreatedBy and @LastModifiedBy. The "who" comes from your AuditorAware bean, the "when" from a DateTimeProvider (the system clock by default).

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
    @Version private Long version;                             // optimistic locking + isNew
    @CreatedDate  @Column(nullable = false, updatable = false) private Instant createdAt;
    @LastModifiedDate @Column(nullable = false)                 private Instant updatedAt;
    @CreatedBy    @Column(updatable = false)                    private String createdBy;
    @LastModifiedBy                                             private String updatedBy;

    public Long getId() { return id; }
    public Instant getCreatedAt() { return createdAt; }
    public Instant getUpdatedAt() { return updatedAt; }
}

@Configuration
@EnableJpaAuditing(dateTimeProviderRef = "auditingDateTimeProvider")
class AuditConfig {
    @Bean Clock clock() { return Clock.systemUTC(); }

    @Bean DateTimeProvider auditingDateTimeProvider(Clock clock) {
        return () -> Optional.of(Instant.now(clock));
    }

    @Bean AuditorAware<String> auditorAware() {
        return () -> Optional.ofNullable(SecurityContextHolder.getContext().getAuthentication())
                .filter(Authentication::isAuthenticated)
                .filter(a -> !(a instanceof AnonymousAuthenticationToken))
                .map(Authentication::getName);
    }
}

An empty Optional leaves the "by" fields null (scheduled jobs, startup data), so either allow nulls or return a system user such as "system". @LastModifiedDate is also set on insert unless you configure modifyOnCreate = false. In tests, declare a @Primary Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC) bean and assert exact timestamps instead of "roughly now".

Listener, not trigger

Because it is a lifecycle callback, auditing only sees changes that go through the persistence context. A bulk @Modifying update or deleteAllInBatch (L320) skips it, as do JdbcTemplate writes and other services sharing the table. If the audit trail must be complete, set updated_at in the bulk statement too, or use a database trigger.

Custom implementations and the Impl suffix

When a method cannot be derived or written as one @Query (a criteria query built in loops, a stored procedure, a batch of native statements), put it in a fragment: an interface plus a class whose name is the interface name with the postfix Impl. Spring Data scans the repository packages for that name, registers it as a bean (so constructor injection works) and routes the interface's methods to it.

public interface OrderRepositoryCustom {
    List<Order> search(OrderFilter filter);
}

class OrderRepositoryCustomImpl implements OrderRepositoryCustom {
    private final EntityManager em;                         // shared, transaction-bound proxy
    OrderRepositoryCustomImpl(EntityManager em) { this.em = em; }

    @Override public List<Order> search(OrderFilter f) {
        var cb = em.getCriteriaBuilder();
        var q = cb.createQuery(Order.class);
        var o = q.from(Order.class);
        var where = new ArrayList<Predicate>();
        if (f.status() != null) where.add(cb.equal(o.get("status"), f.status()));
        if (f.minTotal() != null) where.add(cb.greaterThanOrEqualTo(o.get("total"), f.minTotal()));
        return em.createQuery(q.where(where.toArray(Predicate[]::new))).setMaxResults(500).getResultList();
    }
}

public interface OrderRepository extends JpaRepository<Order, Long>, OrderRepositoryCustom {}

The plan's naming, OrderRepositoryImpl (the repository name plus Impl), is the older single-custom-class convention and is still detected; the fragment-name form above scales to several fragments and lets you reuse one across repositories. Either way the suffix is the contract: rename the class to OrderSearchService and Spring Data no longer finds an implementation, tries to derive a query from search, and fails on startup with "No property 'search' found for type 'Order'". The postfix can be changed with repositoryImplementationPostfix, and the class must live under a scanned package.

Fragment composition and precedence

Algorithm · method dispatch
  1. At startup, collect fragments in extends order, each paired with its implementation bean; append the base class as the last fragment.
  2. On a call, take the first fragment that declares the invoked signature, so a fragment can override save or delete for one repository.
  3. If none does, the method is a query method and runs its prepared query.

Fragments can be generic and shared:

public interface Refreshable<T> { void refresh(T entity); }

class RefreshableImpl<T> implements Refreshable<T> {
    private final EntityManager em;
    RefreshableImpl(EntityManager em) { this.em = em; }
    @Override public void refresh(T entity) { em.refresh(entity); }
}

public interface OrderRepository
        extends JpaRepository<Order, Long>, OrderRepositoryCustom, OrderReports, Refreshable<Order> {}

Read/write splitting fits the same mechanism. Put heavy read-only queries in an OrderReports fragment whose implementation receives a replica-bound JdbcClient or EntityManager through a @Qualifier; writes keep using the primary through the base class. The split is explicit at the type level, which is easier to reason about than routing by readOnly flags, but replica lag still applies: never read your own write through the replica fragment.

Replacing the base class: soft delete everywhere

public class SoftDeleteJpaRepository<T, ID> extends SimpleJpaRepository<T, ID> {
    public SoftDeleteJpaRepository(JpaEntityInformation<T, ?> info, EntityManager em) {
        super(info, em);
    }

    @Override @Transactional
    public void delete(T entity) {
        if (entity instanceof SoftDeletable s) { s.markDeleted(); save(entity); }   // UPDATE, not DELETE
        else super.delete(entity);
    }
}

@SpringBootApplication
@EnableJpaRepositories(repositoryBaseClass = SoftDeleteJpaRepository.class)
class ShopApplication {}

The constructor signature (JpaEntityInformation, EntityManager) is required: the factory calls it reflectively for every repository. deleteById and deleteAll delegate to delete, so they follow; deleteAllInBatch issues SQL directly and does not. Hiding deleted rows on reads needs a separate mechanism: Hibernate's @SQLRestriction("deleted = false") on the entity, or a tenant-style filter. The same base-class hook is where teams add a mandatory tenant predicate, though Hibernate 6's @TenantId is usually the safer tool for that.

What breaks in production
  • Wrong class name for an implementation: startup fails with a property-not-found error that looks unrelated.
  • Missing audit fields after bulk updates, native writes or a second service writing the table.
  • Null createdBy on rows written by jobs and message listeners, where there is no security context; violates a NOT NULL column at 3 a.m.
  • Fragment without a transaction: custom methods are not covered by SimpleJpaRepository's annotations; add @Transactional where a fragment writes.
  • Soft-deleted rows reappearing because a native query or report ignores the restriction.

Spring Data JDBC: The Simpler Alternative

40m video45m practice

Spring Data JDBC keeps the repository programming model and drops the machinery that makes JPA surprising: there is no persistence context, so every save writes and every find reads, right now. In exchange you design around aggregates, and you reach for JdbcClient or jOOQ for everything else.

No session, no magic

Definition · the JDBC model

Spring Data JDBC maps an aggregate, a root entity plus the entities and values it owns, to tables with plain SQL. There is no persistence context (no first-level cache, no identity guarantee: two findById calls return two objects), no lazy loading (an aggregate is loaded whole, eagerly), and no dirty checking (changing a field does nothing until you call save). save inserts a new root, or updates an existing one and deletes and re-inserts its owned collections.

The re-insert rule follows from having no snapshot: without knowing what changed, the only correct write for a collection is "replace it". That is why aggregates must stay small. An order with five lines is cheap to rewrite; a "customer" aggregate holding ten thousand historical orders is a design error, not a tuning problem.

Aggregates and their mapping

@Table("purchase_order")
class PurchaseOrder {
    @Id private Long id;
    @Version private Integer version;
    @Column("customer_id") private AggregateReference<Customer, Long> customer;  // id only
    private OrderStatus status = OrderStatus.NEW;
    @Embedded.Nullable(prefix = "ship_") private Address shipTo;
    @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
    private List<LineItem> items = new ArrayList<>();

    PurchaseOrder() {}
    PurchaseOrder(long customerId, Address shipTo) {
        this.customer = AggregateReference.to(customerId);
        this.shipTo = shipTo;
    }

    void addItem(String sku, int quantity, BigDecimal price) {     // invariants live on the root
        if (status != OrderStatus.NEW) throw new IllegalStateException("order is " + status);
        items.add(new LineItem(sku, quantity, price));
    }
}

record LineItem(String sku, int quantity, BigDecimal price) {}
record Address(String street, String city, String zip) {}
create table purchase_order (id bigserial primary key, version int, customer_id bigint not null,
  status varchar(20) not null, total numeric(12,2) not null default 0, ship_street varchar(200), ship_city varchar(100), ship_zip varchar(20));
create table line_item (order_id bigint not null references purchase_order(id), line_no int not null,
  sku varchar(40) not null, quantity int not null, price numeric(12,2) not null,
  primary key (order_id, line_no));

@MappedCollection names the back-reference column (idColumn) and, for a List or Map, the column holding the index or key; a Set needs no key. @Embedded flattens a value object into the root's row with a column prefix, and requires you to say whether all-null columns mean null (Nullable) or an empty object (Empty). A new root is detected by a null id or null @Version; with assigned ids, use Persistable as in JPA.

Repositories and SQL queries

interface PurchaseOrderRepository extends ListCrudRepository<PurchaseOrder, Long> {
    List<PurchaseOrder> findByStatus(OrderStatus status);                  // derived

    @Query("select * from purchase_order where customer_id = :customerId order by id desc")
    List<PurchaseOrder> forCustomer(@Param("customerId") long customerId);

    @Modifying
    @Query("update purchase_order set status = :to where status = :from")
    int moveAll(@Param("from") OrderStatus from, @Param("to") OrderStatus to);
}

@Query takes SQL, not JPQL: table and column names, your dialect, named parameters. The query returns root columns; owned collections are then loaded with further selects. That is predictable, but it is still one extra query per collection per aggregate when you load many, so avoid findAll over large tables with collections (recent versions offer an opt-in single-query loading for simple aggregates).

A brief look at jOOQ

jOOQ generates Java classes from your schema (tables, columns, types) and gives you a SQL DSL checked by the compiler: a renamed column breaks the build, not production. spring-boot-starter-jooq auto-configures a DSLContext that joins Spring transactions.

The costs: a code-generation step in the build (usually against a Flyway-migrated database or Testcontainers), and a commercial licence for commercial databases such as Oracle or SQL Server; the open-source edition covers open-source databases.

What breaks in production
  • Expecting dirty checking: a modified aggregate that is never passed to save is never written.
  • Huge aggregates: every save deletes and re-inserts the whole collection; triggers and foreign keys pointing at child rows break.
  • Object references across aggregates: mapping Customer as a field makes it part of the order aggregate and saves it with every order. Use AggregateReference.
  • Ignoring the value save returns with immutable entities (records, withers): the old id and version stay in memory, so the next save inserts a duplicate or fails with OptimisticLockingFailureException.
  • queryForObject on maybe-empty results throwing at runtime.

Spring Data MongoDB

45m video50m practice

In MongoDB the document is the unit of atomicity, retrieval and design: you model for the queries you will run, embedding what is read together and referencing what grows without bound. Spring Data MongoDB gives you repositories for the easy cases and MongoTemplate with the aggregation pipeline for the rest; the mapping annotations decide whether that model performs.

When a document store fits

Documents fit data that is read as a whole and shaped like a tree: a product with variable attributes per category (flexible schema), an order with its lines and a snapshot of the shipping address (denormalized read model), a configuration with deep nesting, or event and telemetry streams with high write throughput across shards. They fit poorly where many entities reference each other and must stay consistent across documents; there a relational database with foreign keys and joins is less work.

@Document(collection = "orders")
@CompoundIndex(name = "status_created", def = "{'status': 1, 'createdAt': -1}")
public class OrderDoc {
    @Id private String id;                       // stored as ObjectId when the value is valid hex
    @Indexed @Field(targetType = FieldType.OBJECT_ID)
    private String customerId;                   // reference by id; same BSON type as customers._id
    private String status;
    @Field(name = "total", targetType = FieldType.DECIMAL128) private BigDecimal total;
    private Instant createdAt;
    private List<Line> items = new ArrayList<>();   // embedded: read and written with the order
    private CustomerSnapshot customer;            // copy of name and address at order time
    @TextIndexed private String notes;
    @Version private Long version;
    // getters and setters omitted
}

record Line(String sku, String name, int quantity,
            @Field(targetType = FieldType.DECIMAL128) BigDecimal lineTotal) {}
record CustomerSnapshot(String name, String city) {}
  • @Id: a String or ObjectId field maps to _id. An ObjectId is 12 bytes, roughly time-ordered and generated client-side; a String field holding valid hex is converted to an ObjectId automatically. Use @MongoId(FieldType.STRING) when you really want string ids.
  • @Field renames a field or fixes its BSON type; store money as Decimal128, because by default BigDecimal is written as a string, which sorts and compares as text.
  • @Indexed, @CompoundIndex, @TextIndexed declare indexes, but they are only created if auto-index-creation is on. In production prefer explicit creation through mongoTemplate.indexOps(OrderDoc.class) or a migration tool, so a deploy never builds a large index by surprise.
  • @Version adds optimistic locking: a save with a stale version throws OptimisticLockingFailureException.
Avoid DBRef

@DBRef Customer customer stores {$ref, $id} and resolves it with a separate query per reference, per document: loading 500 orders means 500 extra lookups. MongoDB has no joins for the driver to use, so this N+1 is by design. @DocumentReference(lazy = true) (Spring Data MongoDB 3.3+) stores only the id and can be lazy, which is better, but it is still a second query. Usually the right answer is a plain id field plus an embedded snapshot of the few fields you display.

updateFirst changes the first match, updateMulti every match; both send one update command and never load documents. findAndModify is atomic on the single document, which is enough for counters and claim-a-job patterns.

The aggregation pipeline

import static org.springframework.data.mongodb.core.aggregation.Aggregation.*;

Aggregation topSkus = newAggregation(
        match(where("status").is("PAID").and("createdAt").gte(since)),
        unwind("items"),
        group("items.sku").sum("items.quantity").as("units").sum("items.lineTotal").as("revenue"),
        sort(Sort.Direction.DESC, "units"),
        limit(10),
        project("units", "revenue").and("sku").previousOperation());
List<SkuSales> top = mongo.aggregate(topSkus, "orders", SkuSales.class).getMappedResults();

Aggregation pageWithTotal = newAggregation(
        match(where("status").is("PAID")),
        lookup("customers", "customerId", "_id", "customerDoc"),     // left outer join
        facet(count().as("total")).as("meta")
            .and(sort(Sort.Direction.DESC, "createdAt"), skip(0L), limit(20)).as("items"));

$lookup exists, but it runs per input document on the server; it is fine for reports and a smell on hot paths. $facet runs several sub-pipelines on the same input, here a total count and a page in one round trip. Blocking stages such as $group and $sort have a 100 MB memory limit; beyond it they need allowDiskUse (the default from MongoDB 6.0), and spilling is slow either way.

Transactions and schema design

Multi-document transactions need a replica set (or a sharded cluster), and Spring Boot does not register a transaction manager for MongoDB; declare new MongoTransactionManager(databaseFactory) yourself to make @Transactional work. Limits worth knowing: a transaction is aborted after a lifetime limit (60 seconds by default), write conflicts surface as errors labelled TransientTransactionError that you must retry, and long or large transactions put pressure on the cache. If you need them everywhere, the model is probably relational.

Definition · embed or reference

Embed when the child is owned, bounded and read with the parent (order lines, addresses). Reference when it is shared, large, or grows without bound (customers, comments, events). The hard limit is 16 MB per document; arrays that grow forever hit it eventually and slow every update long before. For time series, the bucket pattern stores one document per sensor per hour with an array of readings plus precomputed count and min/max; MongoDB 5.0+ also offers native time-series collections (@TimeSeries in Spring Data).

Index strategy: every query on a hot path needs an index; check with explain() that the plan is IXSCAN, not COLLSCAN. Order compound index keys by the ESR guideline (equality fields, then sort fields, then range fields), which is why the index above is {status: 1, createdAt: -1}.

What breaks in production
  • Indexes that were never created because @Indexed without auto-index creation is documentation only.
  • Money as strings: a BigDecimal without Decimal128 makes range queries and sums wrong.
  • Unbounded arrays (comments, events) embedded in one document: growing write cost, then the 16 MB wall.
  • @DBRef N+1 on list endpoints.

Spring Data Redis

45m video50m practice

Redis is a single-threaded server of data structures, so the decisions that matter are on the client side: how bytes are serialized, how many round trips you pay, which commands could block everyone, and when a key dies. Spring Data Redis wraps all of it in RedisTemplate; its defaults are the first thing to change.

Drivers and connection setup

spring-boot-starter-data-redis brings Lettuce, a Netty-based, non-blocking driver whose connections are thread-safe: one connection is shared and commands from many threads are multiplexed over it. Jedis is a simple blocking driver whose connections are not thread-safe, so it always needs a pool. With Lettuce a pool (via commons-pool2) is only worth it for blocking commands (BLPOP) and MULTI/EXEC transactions, which tie up a connection.

spring:
  data:
    redis:
      host: redis.internal
      port: 6379
      username: app
      password: ${REDIS_PASSWORD}
      database: 0                # standalone only; cluster has just database 0
      timeout: 2s
      ssl:
        enabled: true
      lettuce:
        pool:                    # requires org.apache.commons:commons-pool2
          enabled: true
          max-active: 16
      # sentinel: master: mymaster, nodes: s1:26379,s2:26379,s3:26379
      # cluster:  nodes: r1:6379,r2:6379,r3:6379, max-redirects: 3

Boot builds a LettuceConnectionFactory from these properties: standalone by default, Sentinel when sentinel.* is set (the client asks the sentinels which node is master and follows failovers), Cluster when cluster.nodes is set (the client learns the slot map and routes each key to its shard). Define your own LettuceConnectionFactory bean only for settings the properties do not expose, such as reading from replicas.

RedisTemplate, StringRedisTemplate and serializers

Definition · serializer

Redis stores bytes. A RedisTemplate<K, V> holds four RedisSerializers (key, value, hash key, hash value) that turn Java objects into those bytes. If none is set, all four default to JdkSerializationRedisSerializer: Java serialization, readable only by Java, broken by class changes, and unreadable in redis-cli (keys look like \xac\xed\x00\x05t\x00\x07cart:42). StringRedisTemplate uses StringRedisSerializer for all four.

@Configuration
class RedisConfig {
    @Bean
    RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory cf) {   // replaces Boot's
        var json = new GenericJackson2JsonRedisSerializer();     // JSON with an @class hint
        var t = new RedisTemplate<String, Object>();
        t.setConnectionFactory(cf);
        t.setKeySerializer(StringRedisSerializer.UTF_8);
        t.setHashKeySerializer(StringRedisSerializer.UTF_8);
        t.setValueSerializer(json);
        t.setHashValueSerializer(json);
        return t;
    }
}

String keys plus JSON values are readable from any language and survive refactoring better. GenericJackson2JsonRedisSerializer stores the class name so it can deserialize to the right type; Jackson2JsonRedisSerializer<T> is typed to one class and stores no hint. Use StringRedisTemplate for counters, flags and anything another service reads.

Each opsFor… interface maps to one family of commands: strings, hashes, lists, sets, sorted sets (rankings, time-ordered queues), streams (append-only logs with consumer groups), geo (sorted sets with geohash scores) and HyperLogLog (approximate distinct counts, standard error under 1%). TTL is either given at write time with set(key, value, Duration) or set afterwards with expire. A plain SET without a TTL clears any existing expiry, a classic source of keys that never die.

Each entity becomes a hash sessions:<id>, its id is added to a set sessions, and each @Indexed value gets its own set. Limitations follow from that layout: queries are equality-only on indexed properties (no ranges, no sorting in Redis), findAll reads the whole id set, and when a hash expires the index sets are only cleaned up if the application listens for keyspace events (enableKeyspaceEvents), which many managed Redis services restrict. Use repositories for small, simple lookups; use the template for everything else.

Fewer round trips: pipelines and Lua

List<Object> prices = str.executePipelined((RedisCallback<Object>) conn -> {
    for (String sku : skus) conn.stringCommands().get(("shop:price:" + sku).getBytes(UTF_8));
    return null;                        // results come back from the pipeline, in order
});

DefaultRedisScript<Long> reserve = new DefaultRedisScript<>("""
        local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
        if stock < tonumber(ARGV[1]) then return 0 end
        redis.call('DECRBY', KEYS[1], ARGV[1])
        redis.call('HINCRBY', KEYS[2], ARGV[2], ARGV[1])
        return 1
        """, Long.class);
Long ok = str.execute(reserve, List.of("shop:stock:{sku-1}", "shop:reserved:{sku-1}"), "2", "order-42");

A pipeline batches commands but is not atomic: other clients' commands can interleave. A Lua script runs atomically on the server, so check-then-act across several keys (here: reserve stock only if enough remains) needs no locks. Pass every key through KEYS, never build key names inside the script, and keep scripts short, because nothing else runs while one executes. DefaultRedisScript sends the script by SHA1 (EVALSHA) and falls back to loading it when the server does not have it cached.

Key naming and the KEYS rule

Name keys app:entity:id[:part] (shop:cart:42): colon-separated, lower case, short but readable, and give every cache-like key a TTL. In Cluster, keys used together by one command or script must live in the same slot, which a hash tag forces: only the part in braces is hashed, so shop:stock:{sku-1} and shop:reserved:{sku-1} land together. KEYS pattern is O(N) over the whole keyspace and blocks the server while it runs; on a large production instance that is an outage. Iterate with SCAN instead, which returns small batches and a cursor:

var opts = ScanOptions.scanOptions().match("shop:cart:*").count(500).build();
try (Cursor<String> keys = str.scan(opts)) {
    keys.forEachRemaining(k -> str.expire(k, Duration.ofDays(7)));
}

Caching with @Cacheable on Redis and distributed locks build on all of this and come on Days 386–390.

What breaks in production
  • JDK serialization by default: binary keys nobody can inspect, and a renamed class makes every cached value undeserializable.
  • JSON values with java.time fields failing because the serializer's internal ObjectMapper was not configured with the modules your application mapper has.
  • Keys without TTL, or a TTL silently removed by a later plain SET: memory grows until eviction or OOM.
  • KEYS * in an admin endpoint freezing the server; block it with ACLs.
  • Multi-key scripts in Cluster failing with CROSSSLOT because the keys lack a shared hash tag.
