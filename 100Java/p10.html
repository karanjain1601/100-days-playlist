JPA & Hibernate

This phase teaches JPA and Hibernate from the persistence context outwards, so you can predict every SQL statement the ORM sends instead of hoping it sends the right ones. It builds on the SQL, transactions and hand-written JDBC repository of Phase 9, and it is the foundation for Spring Data, transaction management and the persistence parts of every Spring service that follows. It ends with the JDBC data layer ported to JPA, with tests proving it issues the same number of queries or fewer.

By the end of this phase you can

  • Explain the four entity states, dirty checking and flush timing, and say which SQL a given service method will issue before you run it.
  • Map identifiers, value types, enums, time types, embeddables, inheritance and all four association types, with LAZY fetching, correct owning sides and sensible cascades.
  • Detect N+1 queries with a failing query-count test and fix them with fetch joins, entity graphs, batch fetching or projections, including the pagination-with-fetch-join trap.
  • Write JPQL, Criteria and native queries that return entities or DTO records, and know when to drop to SQL.
  • Paginate with offsets and keyset cursors on a stable sort, and stream large result sets without exhausting memory.
  • Prevent lost updates with optimistic and pessimistic locking, and surface conflicts as HTTP 409.
  • Own the schema with Flyway or Liquibase migrations that are safe under zero-downtime deploys, with auditing and history where needed, and tune Hibernate with its statistics and JDBC batching.

L223 · DAY 223

ORM Concepts: JPA vs Hibernate vs Spring Data

40m video35m practice

An ORM maps table rows to object graphs and tracks your changes so it can write them back. JPA is the standard API for doing that, Hibernate is the engine that implements it, and Spring Data JPA writes the repository boilerplate on top. When something goes wrong, you debug it faster if you know which of the three layers owns the behaviour.

The object-relational impedance mismatch

Objects and tables model the same domain with different primitives. Objects have references, identity, inheritance and behaviour. Tables have rows, keys, foreign keys and set-based queries. Every ORM feature exists to bridge one of five gaps:

MismatchIn JavaIn SQLHow JPA bridges it
Identitya == b (same instance) and a.equals(b) (same value) are two different notionsone notion: same primary keythe persistence context returns one instance per row (L227)
InheritanceCardPayment extends Payment, polymorphic callsno inheritance at allSINGLE_TABLE, JOINED, TABLE_PER_CLASS (L236)
Associationsreferences are directional; a two-way link is two pointersone foreign key, readable from both ends; M:N needs a junction tableowning side vs mappedBy (L230)
Granularityfine-grained value objects: Customer holds an Address and a Moneyone wide row; no user-defined types in practice@Embeddable (L235)
Navigationwalk the graph one hop at a time: order.getCustomer().getAddress()fetch everything needed in one joinlazy loading plus fetch joins and entity graphs (L234)

Navigation is where it hurts most. Following references one at a time is natural in Java and slow in SQL: one round trip per hop is the N+1 problem. Most of this phase is about loading a graph in a few well-chosen queries instead of hundreds of accidental ones.

What an ORM buys you and what it costs

An ORM is several of Fowler's enterprise patterns in one package: a Data Mapper (rows to objects and back), an Identity Map (one object per row), a Unit of Work (collect changes, write them at commit) and Lazy Load (fetch related data on first touch). The practical difference from the JDBC repository you built in L222:

// JDBC: you write and run every statement yourself
try (var ps = conn.prepareStatement("UPDATE orders SET status = ? WHERE id = ?")) {
    ps.setString(1, "SHIPPED");
    ps.setLong(2, orderId);
    ps.executeUpdate();
}

// JPA: load, mutate, and let the unit of work write the UPDATE at commit
em.getTransaction().begin();
Order order = em.find(Order.class, orderId);   // SELECT ... FROM orders WHERE id = ?
order.setStatus(OrderStatus.SHIPPED);          // no SQL here
em.getTransaction().commit();                  // flush: UPDATE orders SET ... WHERE id = ?

What you get: no hand-written row mapping, automatic change detection (dirty checking), statements reordered and batched at flush, optimistic locking with a single @Version field, a query language that works on your model, an optional shared cache, and startup schema validation. What it costs: SQL you didn't write and must learn to read, a stateful persistence context with real semantics to master, memory for change-tracking snapshots, slower startup, awkward bulk operations, and leaks such as N+1 and LazyInitializationException that only appear once you have real data.

Specification, implementation, convenience layer

Definition · The three names
  • Jakarta Persistence (JPA) is a specification: a document plus the API jar jakarta.persistence-api, which holds interfaces and annotations (EntityManager, @Entity, @OneToMany) and no working code.
  • Hibernate ORM is an implementation (a persistence provider). It generates the SQL, holds the persistence context, does dirty checking and proxies. Its native API is the Session, which extends EntityManager, and its SessionFactory extends EntityManagerFactory. Hibernate also has many features outside the spec: @BatchSize, @Formula, StatelessSession, Envers.
  • Spring Data JPA is a layer on top. You declare repository interfaces, and at startup it generates implementations (backed by SimpleJpaRepository) that call the injected EntityManager. It derives queries from method names, adds paging, projections, auditing and specifications. It does not talk to the database on its own.

Because Spring Data sits on the standard API, you can always reach the layers below: inject the EntityManager for anything a repository can't express, and call em.unwrap(Session.class) when you need a Hibernate-only feature.

Other implementations and the jakarta namespace

EclipseLink (which grew out of Oracle TopLink) is the reference implementation of the spec and ships in several Jakarta EE servers. Apache OpenJPA still exists but sees little activity. DataNucleus implements JPA as well. Hibernate is by far the most common provider, and it is what spring-boot-starter-data-jpa pulls in. The spec is portable only so far: code using Hibernate annotations or HQL extensions is tied to Hibernate. That is usually acceptable, because swapping providers is rare and swapping databases is rarer still.

History · From javax to jakarta

Oracle moved Java EE to the Eclipse Foundation in 2017, but the javax package names stayed Oracle's trademark. Jakarta EE 9 (2020) renamed every package, so JPA 2.2's javax.persistence became jakarta.persistence in Jakarta Persistence 3.0, which changed nothing but the name. 3.1 (Jakarta EE 10) added UUID as a basic type with GenerationType.UUID, plus new JPQL functions such as EXTRACT, CEILING and ROUND. 3.2 (Jakarta EE 11) adds, among other things, programmatic PersistenceConfiguration, runInTransaction on the factory, and set operations (UNION, INTERSECT) in JPQL. Hibernate 6 implements the jakarta API, Spring Boot 3.x ships Hibernate 6.x, and Hibernate 7 targets 3.2. The two namespaces don't mix: a javax.persistence.Entity annotation on a class is invisible to Hibernate 6.

When not to use an ORM, and is the ORM evil?

An ORM pays off for OLTP write paths over aggregates: load an order with its lines, change a few fields, commit. It is the wrong tool when objects add nothing:

  • Reporting and analytics: window functions, CTEs, GROUP BY ROLLUP, results that are not entities. Use SQL through JdbcClient, jOOQ or a native query mapped to a record.
  • Bulk ETL: loading 5 million rows as managed entities means 5 million snapshots in memory. Use JDBC batching, COPY, or at least a StatelessSession (L246).
  • Set-based updates: UPDATE ... WHERE touching thousands of rows should be one statement, not a loop of loaded entities.

The "ORM is evil" argument (Neward's 2006 essay "The Vietnam of Computer Science" is the classic) says the mismatch can't be fully solved, so the abstraction always leaks. That is true. Fowler's reply in "OrmHate" (2012) is also true: the mismatch is inherent, and a hand-rolled mapper ends up rebuilding half an ORM, badly. In practice most ORM horror stories are a short list of problems: N+1, EAGER associations, open-session-in-view, entities used as API DTOs, and ORMs used for batch work. Every one of them is covered in this phase. A sensible codebase mixes the tools: JPA for aggregate writes and simple reads, plain SQL for reports and bulk jobs, with SQL logging switched on everywhere.

What breaks in production
  • Nobody reads the SQL. The ORM is treated as invisible until a page that ran 3 queries in development runs 400 on production data. Log SQL from day one (L224).
  • Mixed namespaces after an upgrade. An old library still annotates with javax.persistence; Hibernate 6 ignores it, and you get "Not a managed type" or missing columns at runtime.
  • ORM for batch work. A nightly import through saveAll runs out of heap or takes hours, while the same job over JDBC batches finishes in minutes.
  • Assuming portability. JPA hides SQL syntax, not database behaviour. Locking, isolation, sequences and NULL ordering still differ from one database to another.

One starter dependency and a few properties give you a working EntityManagerFactory, but behind them sit choices about schema management, SQL logging and naming that decide whether production is safe and whether you can see what the ORM is doing. Make those choices on purpose, on day one.

The classic bootstrap: persistence.xml

Without Spring, a persistence unit is declared in META-INF/persistence.xml and turned into a factory by the provider. Write this once so you know what Boot does for you.

<persistence xmlns="https://jakarta.ee/xml/ns/persistence" version="3.0">
  <persistence-unit name="shop" transaction-type="RESOURCE_LOCAL">
    <class>com.shop.Order</class>
    <properties>
      <property name="jakarta.persistence.jdbc.url" value="jdbc:postgresql://localhost:5432/shop"/>
      <property name="jakarta.persistence.jdbc.user" value="shop"/>
      <property name="jakarta.persistence.jdbc.password" value="secret"/>
      <property name="jakarta.persistence.schema-generation.database.action" value="none"/>
    </properties>
  </persistence-unit>
</persistence>
import jakarta.persistence.EntityManagerFactory;
import jakarta.persistence.Persistence;

public class Bootstrap {
    public static void main(String[] args) {
        // Heavyweight: parses mappings, builds metamodel, opens pool. Create once per app.
        try (EntityManagerFactory emf = Persistence.createEntityManagerFactory("shop");
             var em = emf.createEntityManager()) {          // both AutoCloseable since JPA 3.1
            var tx = em.getTransaction();
            tx.begin();
            Order order = em.find(Order.class, 1L);
            order.setStatus(OrderStatus.PAID);
            tx.commit();                                     // flush + COMMIT
        }
    }
}

RESOURCE_LOCAL means you drive transactions through em.getTransaction(). The alternative, JTA, hands that job to a container transaction manager.

Dialects and ddl-auto

A dialect tells Hibernate how to speak one database: pagination syntax, sequence DDL, type names, function rendering, lock clauses. Hibernate 6 reads the product name and version from JDBC DatabaseMetaData at startup and picks the dialect itself. Setting hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect by hand now just logs a warning that it is unnecessary, and the old version-specific classes such as PostgreSQL95Dialect are deprecated. Set it explicitly only when the database cannot be reached at boot, or when you use a custom dialect subclass.

Definition · ddl-auto values
  • none: Hibernate never touches the schema. Boot's default when the database is not embedded.
  • validate: compares the mappings with the live schema at startup and fails fast on a missing table or column, or a wrong type. This is the production setting when Flyway or Liquibase owns the schema.
  • update: issues CREATE TABLE/ALTER TABLE ADD for whatever is missing.
  • create: drops and recreates the schema at startup. create-drop does the same and drops it again at shutdown. Boot defaults to this for embedded H2/HSQL/Derby when no migration tool is present.

Why update must never touch production: it only adds things. It never drops or renames, so renaming a field creates a second, empty column and the data stays in the old one. It cannot migrate data, has no ordering or history, and nobody reviews it before it runs. A typo in a mapping becomes a new column in the live schema, and an ALTER on a large table can take locks at startup with no warning. Environments drift apart with no record of how. Schemas belong to versioned migrations (L245).

Seeing the SQL: loggers, p6spy, datasource-proxy

spring.jpa.show-sql=true prints statements with System.out: no timestamps, no levels, no parameters, and it can't be switched off per environment by your logging config. Use the loggers instead. org.hibernate.SQL at DEBUG logs each statement, and parameter binding logs at TRACE. In Hibernate 5 that logger was org.hibernate.type.descriptor.sql.BasicBinder; Hibernate 6 renamed it to org.hibernate.orm.jdbc.bind, so many old tutorials no longer work.

DEBUG org.hibernate.SQL           : select o1_0.id,o1_0.status,o1_0.total from orders o1_0 where o1_0.id=?
TRACE org.hibernate.orm.jdbc.bind : binding parameter (1:BIGINT) <- [42]

Both loggers show what Hibernate prepared, not what reached the driver. They log a batched insert once per row and don't tell you whether batching happened. A DataSource proxy sits between Hibernate and the pool and records the real JDBC calls. p6spy logs each statement with parameters already inlined, so you can paste it into psql. datasource-proxy logs the batch size and timing, and exposes a listener API that you can use in tests to assert query counts (L234). Both have community Spring Boot starters that wrap the auto-configured DataSource.

Query:["insert into order_item (order_id,product_id,quantity,id) values (?,?,?,?)"],

Naming strategies: how firstName becomes first_name

Hibernate names tables and columns in two stages. The implicit naming strategy produces a logical name when you gave none: the field name for a column, customer_id for a join column (attribute name + _ + referenced key), the entity name for a table. The physical naming strategy then maps every logical name, including the ones you wrote in @Column(name = ...), to the identifier actually sent to the database. Plain Hibernate's physical strategy is the identity function. Boot sets CamelCaseToUnderscoresNamingStrategy, which lower-cases and inserts underscores, so firstName becomes first_name and OrderItem becomes order_item. Override it with spring.jpa.hibernate.naming.physical-strategy.

What breaks in production
  • ddl-auto: update shipped by accident through a shared profile. The first deploy after a field rename leaves the data in an orphaned column.
  • Explicit names rewritten. Under Boot, @Column(name = "firstName") still goes through the physical strategy and becomes first_name. With a legacy camel-case schema, validate fails, or worse, queries fail at runtime.
  • Bind logging in production writes passwords, tokens and personal data into your log pipeline. Keep TRACE binding to dev and test.
  • H2 with create-drop in tests passes while Postgres fails on jsonb, sequences, case sensitivity or locking. Test against the real database with Testcontainers.

@Entity, @Id & Identifier Generation

45m video45m practice

An entity's identifier decides how Hibernate writes rows. If the database assigns it, every insert runs immediately and alone. If Hibernate gets ids ahead of time from a pooled sequence, inserts can be batched. The identifier also decides whether equals and hashCode survive the moment an object becomes persistent.

Entities and their requirements

Definition · What makes a class an entity
  • Annotated @Entity (or listed in XML), with a primary key marked @Id or @EmbeddedId.
  • A public or protected no-arg constructor: the provider instantiates the class reflectively and then fills in its fields.
  • A top-level, non-final class with no final persistent fields or methods. Hibernate creates lazy proxies by subclassing the entity, and a final class or method silently disables that. Records are therefore not entities (they can serve as embeddables, L235).
  • The access type comes from where @Id sits: on a field means field access (recommended), on a getter means property access.
import jakarta.persistence.*;
import org.hibernate.annotations.NaturalId;

@Entity
@Table(name = "products", schema = "catalog",
       uniqueConstraints = @UniqueConstraint(name = "uk_products_sku", columnNames = "sku"),
       indexes = @Index(name = "ix_products_name", columnList = "name"))
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "product_seq")
    @SequenceGenerator(name = "product_seq", sequenceName = "catalog.product_seq", allocationSize = 50)
    private Long id;

    @NaturalId                                  // immutable business key, unique
    @Column(nullable = false, updatable = false, length = 32)
    private String sku;

    @Column(nullable = false)
    private String name;

    protected Product() { }                     // for Hibernate only
    public Product(String sku, String name) { this.sku = sku; this.name = name; }

    public Long getId() { return id; }
    public String getSku() { return sku; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Product other)) return false;  // instanceof also matches proxies
        return sku.equals(other.getSku());                 // getter: o may be an uninitialized proxy
    }
    @Override public int hashCode() { return sku.hashCode(); }
}

uniqueConstraints and indexes only affect generated DDL. Once Flyway owns the schema they are documentation, but useful documentation, and the explicit names make constraint-violation errors readable.

Why IDENTITY kills batching: a managed entity must have its id as soon as persist returns, because the persistence context is keyed by id. With IDENTITY the only way to learn the id is to run the INSERT, so Hibernate executes it at persist time, one statement per round trip, and cannot hold it back to batch at flush.

Sequences, allocationSize and the pooled optimizers

allocationSize (default 50) is how many ids Hibernate hands out from memory per nextval. It must equal the sequence's INCREMENT BY. Hibernate 6 checks this at startup and fails by default if they differ. Two optimizers turn one sequence value into a block of ids:

Algorithm · Pooled and pooled-lo
  1. pooled (Hibernate's default): the value returned by nextval is the upper end of the block. A return of 101 means Hibernate may use 52 to 101. On a brand-new sequence it calls nextval twice (1, then 51) to set up the first block.
  2. pooled-lo: the value is the lower end. A return of 101 means 101 to 150. It is easier to reason about. Enable it with hibernate.id.optimizer.pooled.preferred=pooled-lo.
  3. Both keep the database sequence in step with the ids actually used. A script or another service that calls nextval directly can never collide with a block that Hibernate holds, which was the flaw of the old hi/lo scheme. Restarts and rollbacks leave gaps, and that is harmless: ids are identifiers, not counters.
CREATE SEQUENCE catalog.product_seq START WITH 1 INCREMENT BY 50;

-- persist 3 products in a fresh JVM, pooled optimizer
select nextval('catalog.product_seq')     -- 1
select nextval('catalog.product_seq')     -- 51   block ready, ids 1..51 in memory
insert into catalog.products (name,sku,id) values (?,?,?)   -- x3, batched at flush
-- the next ~48 persists issue no nextval at all

UUID identifiers and index locality

@GeneratedValue(strategy = GenerationType.UUID) on a UUID field (JPA 3.1) generates a random version-4 UUID in Java. Ids exist before the insert, clients can create them offline, and they don't reveal row counts. The cost is in the B-tree: random keys land on random leaf pages, so inserts split pages all over the index, the working set no longer fits in cache, and the index grows. A key is also 16 bytes against 8 for a bigint, and 36+ if someone stores it as varchar. Always use Postgres's native uuid type, which Hibernate 6 maps by default. UUIDv7 fixes most of the locality problem: its first 48 bits are a Unix-millisecond timestamp, so new keys arrive in roughly ascending order, as a sequence would.

import org.hibernate.annotations.IdGeneratorType;
import org.hibernate.engine.spi.SharedSessionContractImplementor;
import org.hibernate.generator.BeforeExecutionGenerator;
import org.hibernate.generator.EventType;
import java.lang.annotation.*;
import java.security.SecureRandom;
import java.util.EnumSet;
import java.util.UUID;

@IdGeneratorType(UuidV7.Gen.class)
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.FIELD, ElementType.METHOD})
public @interface UuidV7 {
    final class Gen implements BeforeExecutionGenerator {
        private static final SecureRandom RND = new SecureRandom();
        @Override
        public Object generate(SharedSessionContractImplementor s, Object owner, Object current, EventType type) {
            long msb = (System.currentTimeMillis() << 16) | 0x7000L | (RND.nextInt() & 0x0FFF); // ts | ver 7 | rand
            long lsb = (RND.nextLong() & 0x3FFF_FFFF_FFFF_FFFFL) | 0x8000_0000_0000_0000L;      // variant 10
            return new UUID(msb, lsb);
        }
        @Override public EnumSet<EventType> getEventTypes() { return EnumSet.of(EventType.INSERT); }
    }
}
// usage:  @Id @UuidV7 private UUID id;

Composite keys (@EmbeddedId, @IdClass) come in L235. A natural id (@NaturalId, Hibernate-specific) marks a business key alongside the surrogate id. Hibernate adds a unique constraint for it and can load by it with session.bySimpleNaturalId(Product.class).load("SKU-1"), resolving it through the persistence context and, optionally, the second-level cache.

equals and hashCode for entities

The tempting implementation, Objects.equals(id, other.id) with Objects.hashCode(id), breaks Set semantics. A new entity added to a HashSet is stored in the bucket for a null id. At flush the id becomes 42 and the hash changes, but the set does not rehash, so contains and remove now miss an element that is still inside the set. There are three correct options:

  • Business key (as above): an immutable, unique field such as sku or email. This is the best choice when one exists.
  • Stable UUID assigned at construction (private UUID id = UUID.randomUUID();, or a v7 factory): equal from birth and never changes. With an assigned id, neither Hibernate nor Spring Data's save() can tell a new entity from a detached one by looking at the id, so add a nullable @Version (null means new) or call persist explicitly.
  • Generated id with a constant hash: equals is true only if both ids are non-null and equal, and hashCode returns getClass().hashCode(). It is correct, but every entity of the class lands in one hash bucket, which is fine for the small collections an entity holds.

Proxies make two more points matter. Use instanceof (or Hibernate.getClass), not getClass() != o.getClass(), and read the other object's state through getters, because the fields of an uninitialized proxy are all null.

What breaks in production
  • IDENTITY on a high-volume table: the import that "has batching enabled" still sends 100k single inserts. Switch to a sequence.
  • allocationSize 50 against INCREMENT BY 1 on an old schema: startup fails, or, with the check disabled, ids from two JVMs overlap and you get duplicate-key errors under load.
  • Lombok @Data or @EqualsAndHashCode on entities includes every field, lazy associations too. The result is unexpected loads, LazyInitializationException in toString, and stack overflows on bidirectional links.
  • Final entity classes (or Kotlin classes without the all-open plugin) quietly turn every lazy to-one association into an eager query.

Enums: STRING, never ORDINAL

Definition · The reordering disaster

EnumType.ORDINAL (the JPA default) stores ordinal(), the constant's position. Suppose a developer inserts SILVER between BRONZE and GOLD to keep the list "in order". Every stored 1, which used to mean GOLD, now reads back as SILVER. No error is raised and no migration runs: the data's meaning changes when the code is deployed. EnumType.STRING stores name(), which survives reordering. Renaming a constant still needs a data migration, but that is visible and reviewable.

Give the column an explicit length and a CHECK constraint in your migration. Hibernate 6's schema export generates one for enum columns. For a native Postgres enum type, Hibernate 6 offers @JdbcType(PostgreSQLEnumJdbcType.class). When stored codes differ from constant names ('G' for GOLD), use a converter.

LOBs and java.time

@Lob maps String/char[] to a CLOB and byte[] to a BLOB. Postgres has no CLOB or BLOB. Hibernate maps @Lob there to the oid large-object facility, which keeps the data out of the row, needs a transaction to read, and leaves orphaned objects behind when rows are deleted (clean them up with vacuumlo or lo_unlink). On Postgres, prefer text and bytea without @Lob for values up to a few MB. For genuinely large objects, map java.sql.Blob, create it with session.getLobHelper().createBlob(inputStream, length), and read it with getBinaryStream() inside the transaction so the bytes are streamed, not buffered. Often the best answer is object storage plus a key column.

Converters and JSON

public record Email(String value) {

        value = value.toLowerCase(java.util.Locale.ROOT);

@Converter(autoApply = true)            // every Email attribute, no @Convert needed
public class EmailConverter implements AttributeConverter<Email, String> {
    @Override public String convertToDatabaseColumn(Email e) { return e == null ? null : e.value(); }
    @Override public Email convertToEntityAttribute(String s) { return s == null ? null : new Email(s); }
}

An AttributeConverter<X, Y> maps one attribute to one column. With autoApply = true it applies to every attribute of type X. You can still opt out per field with @Convert(disableConversion = true). Typical uses are value types such as Email, codes stored differently from enum names, and encrypted strings (AES-GCM in the converter, so the database only ever sees ciphertext). Converters cannot be applied to @Id, @Version, associations or @Enumerated fields. JPQL parameters for a converted field take the Java type (:email must be an Email). A money value with amount and currency needs two columns, so it is an @Embeddable (L235), not a converter.

For JSON, Hibernate 6 needs no converter. @JdbcTypeCode(SqlTypes.JSON) on a Map, a record or a POJO serializes it with Jackson (if present) into native jsonb. Dirty checking compares the old and new values, so mutating the map in place is detected. Large documents make every flush pay for that comparison.

@Formula runs a SQL expression in every SELECT that loads the entity, including lists, so a correlated subquery there runs once per row. @ColumnTransformer puts SQL around reads and writes. With pgcrypto this gives column-level encryption at rest inside the database, but the key then travels in a session setting, so a converter that encrypts in Java often keeps the key safer.

What breaks in production
  • ORDINAL enums: a "harmless" reorder silently changes historical data. Grep for @Enumerated without STRING and for enums without any annotation.
  • @Lob String on Postgres creates oid columns, which fail outside transactions and leak large objects on delete.
  • LocalDateTime for "when did this happen": records are off by hours between servers in different zones, and duplicated or missing across DST changes.
  • Converter throws on legacy data: one bad row makes every query that loads it fail. Clean the data in a migration before tightening the converter.

EntityManager & The Persistence Context

50m video45m practice

An EntityManager is a handle on a persistence context: a map from (entity type, id) to exactly one managed instance, which records every change until flush. Once you think of JPA as "a map plus a change log", persist, merge, find and getReference all make sense.

The persistence context: first-level cache and unit of work

Definition · Persistence context

A set of managed entity instances in which, for any persistent identity, there is at most one instance. It plays two roles at once:

  • Identity map / first-level cache: find checks the map before going to the database, so loading the same id twice in one context returns the same object (==) after a single SELECT.
  • Unit of work: for each managed instance it keeps a snapshot of the loaded state, plus pending inserts and removals. At flush it turns the differences into SQL (L228).

It is always on and cannot be switched off. Its scope is normally one transaction.

@Transactional
public void identityDemo(long id) {
    Order a = em.find(Order.class, id);                    // SELECT ... where id = ?
    Order b = em.find(Order.class, id);                    // no SQL: map hit
    System.out.println(a == b);                            // true

    a.setNote("edited in memory");
    List<Order> all = em.createQuery("select o from Order o", Order.class)
                        .getResultList();                  // SQL runs (after an auto-flush)
    System.out.println(all.contains(a) && all.get(all.indexOf(a)) == a);   // true: same instance
}

The second point is subtle. A JPQL query always goes to the database, but for every row whose id is already in the context, Hibernate discards the fresh row data and returns the existing instance. Inside one persistence context you therefore get repeatable reads of entities even at READ COMMITTED: a concurrent committed update won't show through an entity you already hold. That protects consistency within the context, and it is also why a stale entity stays stale until you call refresh or clear.

persist vs merge: what happens to your reference

Order managed = em.merge(detachedFromLastRequest); // SELECT by id, copy fields onto managed

                                                   // (EntityExistsException or another PersistenceException)

Use persist for new objects and merge only to reattach state from outside the context, such as a detached object that came back from a session or a queue. In a normal service, entities are loaded and modified in the same transaction, and neither call is needed (L228). merge also cascades along CascadeType.MERGE associations, which can load a whole graph just to copy it.

getReference and proxies

getReference promises that a row exists without checking. If the id is already managed you get that instance. Otherwise you get a Hibernate proxy, a generated subclass that holds only the id. Its first non-id access runs the SELECT, and if the row is missing that access throws EntityNotFoundException, possibly far from the call site. It is the right tool for setting a foreign key without loading the parent:

var item = new OrderItem(productId, 2);
item.setOrder(em.getReference(Order.class, orderId));   // no SELECT, only the FK value is needed
em.persist(item);                                       // INSERT into order_item (order_id, ...)

Spring Data exposes this as getReferenceById. If the id is bad, the foreign key constraint rejects the INSERT at flush, which is the database doing the existence check for you.

Scopes, factories and Spring's shared EntityManager

How it works underneath
  • EntityManagerFactory is heavyweight and thread-safe: it holds the parsed mappings, the metamodel, generated SQL, the second-level cache and the connection provider. Create one per database per application.
  • EntityManager is cheap and not thread-safe: one per unit of work, never shared between threads.
  • Transaction-scoped (the default for container-managed EMs): the context opens on first use in a transaction and closes at commit or rollback, and its entities become detached. Extended (@PersistenceContext(type = EXTENDED)): the context outlives transactions, keeping entities managed across several requests in a stateful component. It is rare in Spring because it ties memory to a conversation.
  • Spring injects a shared proxy (built by SharedEntityManagerCreator) into your singleton. Each call looks up the EntityManager bound to the current thread's transaction, which JpaTransactionManager registered through TransactionSynchronizationManager. Every repository in one transaction therefore sees the same persistence context. Outside a transaction, each call gets a fresh EM that is closed right afterwards.
@Repository
class JpaOrderRepository {
    @PersistenceContext
    private EntityManager em;       // the shared proxy: safe in a singleton, resolves per transaction

    Optional<Order> findById(long id) { return Optional.ofNullable(em.find(Order.class, id)); }
}
What breaks in production
  • Changing the merge argument instead of the returned instance: the update never happens and no error is raised.
  • Stale reads in long transactions: a batch job holds an entity for minutes and another service's committed change is invisible to it (the repeatable read above), so the job overwrites that change on flush. Use @Version.
  • clear() before flush() in a batch loop throws away the pending inserts. The order is always flush, then clear.
  • EntityManager across threads: parallelStream() or CompletableFuture inside a transaction reaches a different (or no) bound EM, or corrupts a shared one.
  • Hand-made EMs from an injected factory that are never closed leak connections until the pool runs out.

Entity Lifecycle, Dirty Checking & Flush Modes

45m video45m practice

A managed entity writes itself. Hibernate keeps a snapshot of every entity it loads, compares the snapshot with the current state at flush, and issues UPDATEs for whatever changed. You don't save managed entities; you choose when flushes happen and keep the number of managed entities small.

The four states

Definition · Entity states
  • Transient (new): created with new, not associated with any context, no database row.
  • Managed (persistent): in a persistence context with a snapshot. Changes are detected at flush.
  • Detached: was managed, but its context closed or evicted it. It has an id and possibly a row, but nobody watches it.
  • Removed: managed and scheduled for DELETE at flush. Calling persist before the flush revives it.

Automatic dirty checking

When Hibernate hydrates an entity, it also stores the loaded state: an Object[] holding a copy of every mapped property value. At flush it walks every managed entity and compares each property with its snapshot using the type's equality (deep comparison for mutable types such as jsonb maps). If anything differs it schedules an UPDATE. So a setter inside a transaction is the write:

@Service
public class OrderService {
    private final OrderRepository orders;
    OrderService(OrderRepository orders) { this.orders = orders; }

    @Transactional
    public void ship(long id) {
        Order o = orders.findById(id).orElseThrow();   // SELECT, snapshot taken
        o.setStatus(OrderStatus.SHIPPED);              // plain field write, no SQL
        // no save() call: commit -> flush -> dirty check -> UPDATE
    }
}
select o1_0.id,o1_0.customer_id,o1_0.note,o1_0.status,o1_0.total,o1_0.version from orders o1_0 where o1_0.id=?
update orders set customer_id=?,note=?,status=?,total=?,version=? where id=? and version=?

Calling orders.save(o) here is harmless, because merge on a managed instance returns the same instance, but it is misleading: it suggests that leaving it out loses the change. The reverse is the real bug: modifying an entity outside any transaction and expecting the change to be stored.

The memory and CPU cost of snapshots

Each managed entity costs the object itself, a snapshot array of its values, an EntityEntry and map entries keyed by id. That is roughly twice the entity's footprint, and every flush is O(entities × properties). Load 100k entities "to process them" and you hold perhaps a few hundred MB. Worse, every JPQL query in the loop triggers an auto-flush that dirty-checks all 100k again, so the job slows down as it runs. For reads, use projections or read-only loading (@Transactional(readOnly = true) sets Hibernate's flush mode to MANUAL and loads entities read-only without snapshots). For writes, process in chunks of flush + clear(), or use a StatelessSession (L246).

When flush happens: AUTO, COMMIT, explicit

  • Before query execution (FlushModeType.AUTO, the default): a JPQL or Criteria query whose tables overlap with pending changes triggers a flush first, so the query sees your own writes. Hibernate cannot parse a native SQL query, so through the JPA API it flushes everything before one; through the native Session API it doesn't, unless you declare the synchronized entity classes.
  • At commit, always.
  • Explicitly, with em.flush(): to surface constraint violations at a known line, to force statement order, or before clear() in batches.

FlushModeType.COMMIT skips the pre-query flush. Queries may then return results that contradict your own unflushed changes, which you buy in exchange for fewer flushes. Hibernate adds FlushMode.MANUAL (flush only when asked), which is what read-only Spring transactions use. Flushing is not committing: flushed SQL is still inside the open transaction and is rolled back with it.

Statement ordering at flush

Hibernate does not replay your calls in order. Its action queue executes them by kind: orphan removals, then INSERTs (in persist order), then UPDATEs, then collection element removals and insertions, and DELETEs last. Deletes go last because inserted rows might still reference rows that are about to be deleted. The surprise comes with unique constraints:

@Transactional
public void replaceCoupon(long oldId) {
    Coupon old = em.find(Coupon.class, oldId);   // code = 'SUMMER', unique
    em.remove(old);
    em.persist(new Coupon("SUMMER"));
}   // flush runs INSERT 'SUMMER' before DELETE -> unique violation

// fix: em.remove(old); em.flush(); em.persist(new Coupon("SUMMER"));
// better: update the existing row instead of delete + insert

@DynamicUpdate, @DynamicInsert and callbacks

By default Hibernate's UPDATE lists every column, and its INSERT every column, so it can build each statement once at startup and reuse one prepared statement and one JDBC batch for all rows. @DynamicUpdate builds the SQL at flush time with only the changed columns, and @DynamicInsert leaves out null columns so database defaults apply.

Lifecycle callbacks run around state transitions: @PrePersist/@PostPersist, @PreUpdate/@PostUpdate (only when the entity is actually dirty at flush), @PreRemove/@PostRemove, and @PostLoad. Put them on entity methods, or in a listener class shared through @EntityListeners:

    }
}

}

Keep callbacks small and local. The spec says portable code must not call the EntityManager or run queries inside them, and Hibernate may misbehave if you do. Use them for timestamps, normalization and invariants, not for side effects such as sending email.

What breaks in production
  • Accidental writes: a "read" method normalizes a field (name.trim()) on a managed entity, and every request now issues an UPDATE and takes row locks.
  • Slow batch jobs: 100k managed entities plus a query per iteration means each auto-flush scans all 100k. Chunk with flush + clear, or don't load entities at all.
  • Delete-then-insert of a unique key fails because of flush ordering. The error shows up at commit, far from the code that caused it.
  • Exceptions at commit: constraint violations surface during the final flush, after your try/catch has exited. Flush explicitly where you need to handle them.

@OneToOne Mappings

40m video40m practice

A one-to-one is a foreign key with a uniqueness guarantee, and the side that holds the key is the only side Hibernate can load lazily without extra work. Put the key where you navigate from, or share the primary key with @MapsId, and the famous inverse-side N+1 never appears.

Three ways to store a one-to-one

Definition · Owning and inverse side

The owning side is the association whose entity's table holds the join column (or which declares the join table). Only the owning side's value is written to the database. The inverse side, @OneToOne(mappedBy = "user"), is a read-only mirror. Setting only the inverse reference writes nothing.

// Unidirectional, owning side holds a unique FK
@Entity @Table(name = "invoices")
public class Invoice {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;

    @OneToOne(fetch = FetchType.LAZY, optional = false)          // default would be EAGER
    @JoinColumn(name = "order_id", nullable = false, unique = true,
                foreignKey = @ForeignKey(name = "fk_invoice_order"))
    private Order order;

    @Column(nullable = false, unique = true, length = 20) private String number;
    protected Invoice() { }
    public Invoice(Order order, String number) { this.order = order; this.number = number; }
}

// From the order side, query instead of mapping the inverse:
//   select i from Invoice i where i.order.id = :orderId

Order ↔ Invoice fits this layout. An invoice has its own id and number (invoice numbers are legal sequences), it appears after the order, and many orders never get one. The owning side loads lazily for free: the order_id value is in the invoice row, so Hibernate can build a proxy from it, or use null when the column is null, without another query.

Shared primary key with @MapsId: the cleanest one-to-one

@Entity @Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
    @Column(nullable = false, unique = true) private String email;
    protected User() { }
    public User(String email) { this.email = email; }
    public Long getId() { return id; }
}

@Entity @Table(name = "user_profile")
public class UserProfile {
    @Id private Long id;                                     // copied from the user, no generator

    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @MapsId                                                  // PK column is also the FK
    @JoinColumn(name = "user_id")
    private User user;

    private String displayName;
    protected UserProfile() { }
    public UserProfile(User user, String displayName) { this.user = user; this.displayName = displayName; }
}

// No association on User is needed: the profile's id IS the user's id.
UserProfile p = em.find(UserProfile.class, user.getId());   // PK lookup, cached in the context

User ↔ UserProfile fits this layout. The profile can't exist without its user, there is one per user, and both share a lifetime. With @MapsId, Hibernate copies the user's id into the profile's id at persist. The table needs no second index, and every lookup is a primary-key lookup. Persist the user first (or cascade from it), because the profile has no id until the user does.

Bidirectional, and the inverse-side lazy problem

// On User, the inverse side: looks lazy, isn't (without bytecode enhancement)
@OneToOne(mappedBy = "user", fetch = FetchType.LAZY,
          cascade = CascadeType.ALL, orphanRemoval = true)
private UserProfile profile;

public void setProfile(UserProfile p) {                  // keep both sides in sync
    this.profile = p;
    if (p != null) p.setUser(this);                      // the owning side is what gets written
}

select p1_0.user_id,p1_0.display_name from user_profile p1_0 where p1_0.user_id=?  -- x 20
Why LAZY is ignored on the inverse side

A lazy to-one is either a proxy or null, and Hibernate must choose when the parent is loaded: user.getProfile() == null has to be correct before any proxy method runs. On the owning side, the FK column answers that for free. On the inverse side, the users row has no column saying whether a profile exists, so the only way to decide is to query user_profile. Hibernate therefore runs that query for every user it loads (one per row: an N+1 hidden behind LAZY), and usually loads the whole profile while it is there.

Three fixes, from simplest to most involved:

  1. Use @MapsId and don't map the inverse side. Load the profile by id when you need it. This is one line of code and the most predictable SQL.
  2. Bytecode enhancement with lazy initialization enabled. Hibernate then intercepts the field read itself instead of committing to proxy-or-null up front, and optional = false states that a profile always exists. Check the SQL log on your Hibernate version, because the exact behaviour has changed between releases.
  3. Move the FK to the side you navigate from, mapped as @ManyToOne(fetch = LAZY) with a unique join column (users.profile_id). A @ManyToOne always owns its FK, so it is always proxyable, and the unique constraint keeps it one-to-one.

Join tables, cascade and orphan removal

// In Order: one-to-one through a join table, both columns unique
@OneToOne(fetch = FetchType.LAZY)
@JoinTable(name = "order_invoice",
           joinColumns = @JoinColumn(name = "order_id", unique = true),
           inverseJoinColumns = @JoinColumn(name = "invoice_id", unique = true))
private Invoice invoice;

A join table keeps both entity tables free of nullable FK columns. That suits a link that is optional and rare, or a link added to two existing tables you can't alter. It costs an extra join on every navigation and an extra row per link, so it is rarely the best choice.

Cascade on a one-to-one follows ownership of lifecycle. A profile is part of its user, so cascading PERSIST and REMOVE from User is reasonable. An invoice is a legal record, so never cascade REMOVE from Order to it. orphanRemoval = true deletes the old child when you set the reference to null or replace it. Hibernate runs orphan deletes before inserts at flush, so swapping in a new profile does not trip the unique FK. Without orphan removal, the old row stays behind, and with a unique FK the replacement insert fails.

What breaks in production
  • Default EAGER: @OneToOne without fetch = LAZY joins or selects the other side on every load, including for every row of a list query.
  • Inverse-side N+1: a user search page runs 1 + N queries although every annotation says LAZY.
  • Only the inverse side set: user.setProfile(p) without p.setUser(user) inserts a profile with a null FK, or fails on NOT NULL.
  • JSON and toString loops: serializing a bidirectional pair recurses until StackOverflowError. Map to DTOs instead (L240).

@ManyToOne, @OneToMany & Bidirectional Sync

50m video50m practice

In a parent-child relationship the foreign key lives in the child row, so the child's @ManyToOne is the side that is written. The parent's @OneToMany collection is a convenience view that Hibernate never reads when writing. Keep both sides in sync with helper methods, or drop the collection entirely.

The owning side: @ManyToOne holds the FK

@Entity @Table(name = "order_item")
public class OrderItem {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)               // default is EAGER
    @JoinColumn(name = "order_id", nullable = false,
                foreignKey = @ForeignKey(name = "fk_order_item_order"))
    private Order order;

    private int lineNo;
    private long productId;
    private int quantity;

    protected OrderItem() { }
    public OrderItem(int lineNo, long productId, int quantity) {
        this.lineNo = lineNo; this.productId = productId; this.quantity = quantity;
    }
    void setOrder(Order order) { this.order = order; }                 // only Order calls this
}

@JoinColumn names the column, sets NOT NULL for generated DDL (optional = false also lets Hibernate use an inner join), and foreignKey names the constraint so that violation messages are readable. A @ManyToOne is the most efficient association in JPA. The FK is in the row being loaded, so a lazy proxy costs nothing, and setting it is a single column write.

The inverse side and the #1 beginner bug

@Entity @Table(name = "orders")
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    @OrderBy("lineNo ASC")
    private List<OrderItem> items = new ArrayList<>();

    public void addItem(OrderItem item) {      // the only way in: both sides, always
        items.add(item);
        item.setOrder(this);
    }
    public void removeItem(OrderItem item) {
        items.remove(item);
        item.setOrder(null);                   // with orphanRemoval: DELETE at flush
    }
    public List<OrderItem> getItems() { return Collections.unmodifiableList(items); }
}
Definition · The one-sided link bug
  • Only the inverse side set: order.getItems().add(item) with cascade PERSIST inserts the item with order_id = NULL. That is a constraint violation, or, if the column is nullable, a silently orphaned row.
  • Only the owning side set: item.setOrder(order) writes the correct FK, but order.getItems() in the same persistence context doesn't contain the item, so totals computed later in the request are wrong until a reload.

The helper methods make the mistake impossible, and returning an unmodifiable view means a stray getItems().add(...) fails at runtime instead of corrupting data.

Unidirectional @OneToMany: join column vs join table

Mapping only the collection, with no @ManyToOne back, looks simpler and produces worse SQL.

-- @OneToMany @JoinColumn(name = "order_id") on Order, nothing on OrderItem
insert into order_item (line_no,product_id,quantity,id) values (?,?,?,?)
update order_item set order_id=? where id=?        -- one extra UPDATE per child

-- @OneToMany with no @JoinColumn: Hibernate creates a join table orders_items
insert into order_item (...) values (...)
insert into orders_items (order_id,items_id) values (?,?)   -- extra table, extra index, extra join

With a join column, the collection is the owner, but the FK sits in the child table. Hibernate inserts the child first and then links it with an UPDATE. Recent versions can include the FK in the INSERT when the join column is nullable = false, but removing an element still costs an UPDATE that nulls the FK. Without a join column you get a join table, which is the many-to-many layout used for a one-to-many. The bidirectional mapping, or a plain @ManyToOne with no collection, is what you want almost every time.

@OrderBy("lineNo ASC") adds an ORDER BY when the collection is loaded. It uses entity property names, costs nothing extra to maintain, and is right when order derives from data. @OrderColumn(name = "position") persists the list index, which is right only when order is arbitrary user input (a playlist) and can't be derived. Every insert or move in the middle updates the position of each following row.

When to skip @OneToMany entirely

A mapped collection is loaded all at once: there is no paging inside customer.getOrders(). Map it only when the children are a bounded part of an aggregate that you load and save together, such as an order's 1–50 items. For unbounded or independently managed children (a customer's orders, a product's reviews, an account's transactions), map only the @ManyToOne on the child and query by parent id:

List<Order> recent = em.createQuery("""
        select o from Order o
        where o.customer.id = :customerId
        order by o.createdAt desc, o.id desc""", Order.class)
    .setParameter("customerId", customerId)
    .setMaxResults(20)
    .getResultList();

o.customer.id reads the FK column directly, with no join. The query is pageable, sortable and indexable, and it never pulls 40,000 orders into memory because someone called a getter.

What breaks in production
  • EAGER @ManyToOne by default: listing 500 order items also loads 500 orders, each with its own EAGER customer.
  • Collections on unbounded relations: customer.getOrders().size() loads every order the customer has ever placed. Use a count query.
  • Adding to a Set of new entities with id-based hashCode loses elements after flush, and remove stops working.
  • Exposed mutable collections: code outside the aggregate does getItems().clear(), and with orphanRemoval every line item is deleted.

@ManyToMany & Association Entities

40m video45m practice

@ManyToMany hides the join table, and that is its problem: the table can't carry any data of its own, and with a List Hibernate rewrites it on every removal. Most real many-to-many links become an entity in their own right, mapped as two @ManyToOne relations.

@ManyToMany and @JoinTable

@Entity
public class Student {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;

    @ManyToMany                                                  // owning side: writes the join table
    @JoinTable(name = "student_course",
               joinColumns = @JoinColumn(name = "student_id"),
               inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses = new HashSet<>();

    public void join(Course c)  { courses.add(c);    c.students().add(this); }
    public void leave(Course c) { courses.remove(c); c.students().remove(this); }
}

@Entity
public class Course {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
    @NaturalId private String code;

    @ManyToMany(mappedBy = "courses")                            // inverse: ignored when writing
    private Set<Student> students = new HashSet<>();
    Set<Student> students() { return students; }
}

As with one-to-many, exactly one side owns the association. Here Student.courses declares the @JoinTable, so only changes to it produce SQL. Course.students uses mappedBy and is a mirror that the helper methods keep in sync. Both sides default to LAZY. joinColumns refers to the owner's key and inverseJoinColumns to the other entity's key. Give the join table a composite primary key (student_id, course_id) in your migration, so that duplicates are impossible and the index covers lookups from the student side. Add a second index on course_id for lookups from the other side.

Why a List rewrites the join table

A List without @OrderColumn is a bag. Its elements have no identity in the join table: duplicates are allowed, and nothing says which row corresponds to which position. When you remove one element, Hibernate cannot target a single row, so it deletes all of the owner's rows and reinserts the survivors. A Set guarantees each (owner, element) pair appears once, so the pair is the row's identity and Hibernate can delete exactly that row.

-- List<Course> (bag): student leaves one of five courses
delete from student_course where student_id=?
insert into student_course (student_id,course_id) values (?,?)    -- x 4, the survivors

-- Set<Course>: the same change
delete from student_course where student_id=? and course_id=?

Appending to a bag is a plain INSERT. The rewrite happens on removals and on any change Hibernate can't express as an append. With a few elements nobody notices. With thousands of rows per owner, it means thousands of statements and lock churn on a hot table. If you keep @ManyToMany, always use a Set with a correct equals/hashCode (a business key such as Course.code).

The deeper problem: the link has data

Soon someone asks when the student enrolled, what grade they got, or which role a user has in a project. A @ManyToMany join table can hold only the two foreign keys, so there is nowhere in the mapping to put these attributes. Teams end up adding columns the ORM never fills, or keeping a parallel table. The relationship was an entity from the start. Its name is Enrollment.

The recommended pattern: an explicit association entity

@Embeddable
public class EnrollmentId implements Serializable {
    private Long studentId;
    private Long courseId;
    protected EnrollmentId() { }
    public EnrollmentId(Long studentId, Long courseId) { this.studentId = studentId; this.courseId = courseId; }
    @Override public boolean equals(Object o) {
        return o instanceof EnrollmentId e
            && Objects.equals(studentId, e.studentId) && Objects.equals(courseId, e.courseId);
    }
    @Override public int hashCode() { return Objects.hash(studentId, courseId); }
}

@Entity @Table(name = "enrollment")
public class Enrollment {
    @EmbeddedId private EnrollmentId id;

    @ManyToOne(fetch = FetchType.LAZY) @MapsId("studentId") @JoinColumn(name = "student_id")
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY) @MapsId("courseId") @JoinColumn(name = "course_id")
    private Course course;

    @Column(nullable = false) private Instant enrolledAt;
    @Column(length = 2)       private String grade;

    protected Enrollment() { }
    Enrollment(Student s, Course c, Instant at) {                 // both must already have ids
        this.id = new EnrollmentId(s.getId(), c.getId());
        this.student = s; this.course = c; this.enrolledAt = at;
    }
}

// In Student (Course gets the mirror-image mapping, often without a collection at all)
@OneToMany(mappedBy = "student", cascade = CascadeType.ALL, orphanRemoval = true)
private Set<Enrollment> enrollments = new HashSet<>();

public Enrollment enroll(Course c, Instant at) {
    var e = new Enrollment(this, c, at);
    enrollments.add(e);
    return e;
}

@MapsId("studentId") says that the studentId part of the embedded key is the same column as the student FK, so each column is mapped once. Composite keys are covered fully in L235. The alternative is a surrogate @Id on Enrollment plus a unique constraint on (student_id, course_id). That is simpler to code against, and it is better if enrollments are referenced from elsewhere (a Certificate pointing to one), at the cost of an extra index.

-- enroll, unenroll, list: one statement each, all addressable by key
insert into enrollment (enrolled_at,grade,course_id,student_id) values (?,?,?,?)
delete from enrollment where course_id=? and student_id=?
select e1_0.course_id,e1_0.student_id,e1_0.enrolled_at,e1_0.grade
  from enrollment e1_0 where e1_0.student_id=?

You also gain queries the hidden table could not support: "enrollments in the last 7 days", "average grade per course", "students with an incomplete grade". You can page through a course's enrollments instead of loading course.getStudents(), which might hold 10,000 students.

Cascades across a many-to-many

Rule · Never cascade REMOVE across many-to-many

The elements are shared: a course belongs to many students. CascadeType.REMOVE (or ALL) on Student.courses means that deleting one student deletes every course they took. That either fails on the other students' join rows or, with cascades on both sides, spreads through the graph and deletes most of the data. The most a many-to-many should cascade is PERSIST/MERGE, and usually nothing: courses have their own lifecycle. Deleting the owner itself is safe, because Hibernate removes the owner's join rows (not the courses) before deleting it. Deleting from the inverse side is not: remove a Course and its join rows stay put, so the FK fails unless you unlink the students first.

With an association entity, the rule becomes natural. Cascade ALL and orphanRemoval from Student to its Enrollment rows, which the student owns, and never from Enrollment to Course.

What breaks in production
  • List-based many-to-many on a hot table: unsubscribing one tag rewrites every tag row for that article, and concurrent edits deadlock on the join table.
  • CascadeType.ALL on @ManyToMany: deleting a user deletes the shared roles, and everyone else loses their permissions.
  • Columns added behind the ORM's back: an added_at column with a database default works until someone needs to set or read it from Java.
  • Inverse-side-only changes: course.getStudents().add(s) writes nothing, and the enrollment silently never happens.

Cascade Types & Orphan Removal

40m video40m practice

A cascade forwards an EntityManager operation from one entity to the entities it references. It belongs only on associations from an aggregate root to the parts it owns. Put it anywhere else and a delete spreads to shared data, or a simple remove loads and deletes thousands of rows one at a time.

What each cascade type propagates

TypePropagatesWhen it appliesTypical use
PERSISTpersistat the call and again at flush for new objects reachable from managed onessave an order with its new items
MERGEmergeat the call; copies the whole reachable graphreattach a detached aggregate

REFRESHrefreshat the call; reloads children toodiscard unflushed changes to a whole aggregate
DETACHdetachat the callevict an aggregate from the context

JPA has no cascades by default. Hibernate adds a few of its own (org.hibernate.annotations.Cascade with LOCK, REPLICATE), but you rarely need them.

Definition · Transitive persistence by reachability

At flush, Hibernate walks every managed entity's associations marked PERSIST (or ALL). Any new object it finds there is persisted, and the walk continues from that object. So order.addItem(new OrderItem(...)) on a managed order is enough to insert the item: no persist(item) call is needed. If a new object is reachable only through an association without PERSIST, the flush fails with TransientPropertyValueException: object references an unsaved transient instance. That error is a useful signal that you are referencing something you never meant to create.

orphanRemoval vs CascadeType.REMOVE

The two are often confused because both delete children. They respond to different events:

EventRemove cascade onlyorphanRemoval only
em.remove(order)items deleteditems deleted (orphan removal also implies remove on the parent)
order.removeItem(item)not deleted: if your helper nulls the item's FK, flush issues UPDATE ... order_id = NULL, which fails on NOT NULLitem deleted at flush
order.setInvoice(null) (one-to-one)nothingold invoice deleted
replace the collection: items = new ArrayList<>()nothingflush fails: "A collection with cascade=all-delete-orphan was no longer referenced by the owning entity instance". Use clear() + addAll.

So orphanRemoval = true says the child cannot exist outside this parent: unlinking it means deleting it. Use it with parts that have no meaning on their own, such as order lines, a profile or an address snapshot. Moving a child to another parent is then impossible, because removing it from the first collection deletes it at flush.

Composition vs aggregation

Composition (the part lives and dies with the whole) calls for cascade = ALL, orphanRemoval = true along parent-to-child @OneToMany/@OneToOne. Aggregation (a reference to something with its own life) calls for no cascade. Never cascade along a @ManyToOne: REMOVE on OrderItem.product would delete the product when one line is removed, and MERGE would copy a stale product snapshot from a client request over the catalogue.

@Entity @Table(name = "orders")
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();      // composition

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    private Customer customer;                               // aggregation: no cascade
}

@Entity @Table(name = "order_item")
public class OrderItem {
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    private Order order;                                     // child to parent: never cascade

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    private Product product;                                 // shared: no cascade
}

The cascade-remove performance trap

A remove cascade is implemented in Java, not SQL. To remove the children, Hibernate needs them as managed entities, so it loads the whole collection, runs their own cascades and callbacks, and schedules one DELETE per row:

-- em.remove(order), cascade = ALL, 3,000 items
select i1_0.order_id,i1_0.id,i1_0.product_id,i1_0.quantity from order_item i1_0 where i1_0.order_id=?
delete from order_item where id=?                 -- x 3,000 (batched if enabled, still 3,000 rows)
delete from orders where id=? and version=?

-- @OnDelete(action = CASCADE) on the FK, no REMOVE cascade on the collection
delete from orders where id=? and version=?       -- the database deletes the items itself

For aggregates with many or deep children, push the delete to the database. @OnDelete(action = OnDeleteAction.CASCADE) (Hibernate, placed on the child's @ManyToOne in Hibernate 6) generates FOREIGN KEY ... ON DELETE CASCADE, which you should also write in your Flyway migration, and tells Hibernate that the database removes the children. Map the collection with cascade = {PERSIST, MERGE} and without orphanRemoval (both REMOVE and orphan removal force the load), and delete single items explicitly. Children already loaded in the context become stale, so clear it or don't touch them afterwards. The other option is a bulk JPQL delete from OrderItem i where i.order.id = :id before removing the parent (L237).

  • MERGE cascading to shared entities: a stale product price inside a cart DTO overwrites the catalogue price on checkout.
  • Deleting a big aggregate times out: tens of thousands of single-row deletes inside one transaction, holding locks the whole time.

Fetch Types, Proxies & LazyInitializationException

50m video50m practice

A lazy association is a placeholder that loads itself through the persistence context that created it. Make every association lazy, decide in each use case what to fetch while the transaction is open, and treat LazyInitializationException as a sign that a fetch decision is missing, not as something to patch with configuration.

Default fetch types and why to override them

MappingJPA defaultSet it to
@ManyToOne, @OneToOneEAGERfetch = FetchType.LAZY
@OneToMany, @ManyToMany, @ElementCollectionLAZYleave as LAZY

EAGER is a static decision made for every use case at once, and it can't be undone per query: fetch joins and entity graphs can add data to a load, but nothing can remove an EAGER association from it. It also behaves differently depending on how you load. em.find typically joins the EAGER association into the same SELECT. A JPQL query, however, returns its own rows first, and Hibernate then loads each row's EAGER associations with extra SELECTs, one per distinct parent, which is an N+1 that nobody asked for. Make everything LAZY and fetch per use case (L234).

How proxies and collection wrappers work

Order ref = em.getReference(Order.class, 42L);   // or order.getCustomer() on a LAZY @ManyToOne
Hibernate.isInitialized(ref);                     // false
ref.getId();                                      // 42, no SQL
ref.getClass();                                   // Order$HibernateProxy$..., a subclass of Order
Hibernate.initialize(ref);                        // SELECT now
Order real = Hibernate.unproxy(ref, Order.class); // the target; real.getClass() == Order.class

Collections work the same way through wrappers. When Hibernate loads or flushes an entity, it swaps your ArrayList or HashSet for a PersistentBag, PersistentList, PersistentSet or PersistentMap. The wrapper holds the owner's key and a reference to the session, and initializes itself the first time you iterate, call size() or contains(). The wrapper is also how Hibernate detects collection changes: it records which elements were added and removed.

Reproducing LazyInitializationException

@Service
public class OrderQueries {
    private final EntityManager em;
    OrderQueries(EntityManager em) { this.em = em; }

    @Transactional(readOnly = true)
    public Order load(long id) { return em.find(Order.class, id); }   // context closes on return
}

// In a controller, with spring.jpa.open-in-view=false:
Order o = orderQueries.load(42);         // detached now
o.getItems().size();
// org.hibernate.LazyInitializationException: failed to lazily initialize a collection of
// role: com.shop.Order.items: could not initialize proxy - no Session
Definition · What the exception means

An uninitialized proxy or collection was accessed after the persistence context that created it had closed. The data was never loaded, and the object can no longer load it. The bug is not in the line that throws; it is in the use case that didn't fetch what it needed while it could.

Five correct responses

// 1. Fetch join: one query, data loaded with the parent
em.createQuery("select o from Order o join fetch o.items where o.id = :id", Order.class)
  .setParameter("id", id).getSingleResult();

// 2. Entity graph: same effect, declared separately from the query
EntityGraph<Order> g = em.createEntityGraph(Order.class);
g.addAttributeNodes("items");
em.find(Order.class, id, Map.of("jakarta.persistence.fetchgraph", g));

// 3. DTO projection: no entities, nothing lazy left
em.createQuery("select new com.shop.OrderLine(i.productId, i.quantity) from OrderItem i where i.order.id = :id",
               OrderLine.class).setParameter("id", id).getResultList();

// 4. Map to a view inside the service transaction, return the DTO
@Transactional(readOnly = true)
public OrderView view(long id) { return OrderView.from(em.find(Order.class, id)); }

// 5. Explicit initialization inside the transaction (fine for one association; an extra SELECT)
Hibernate.initialize(order.getItems());

Options 1–3 decide what SQL runs. Option 4 decides where the boundary is: the service returns data, never live entities. Avoid the two "fixes" that only hide the problem. Switching to EAGER makes every other use case pay. hibernate.enable_lazy_load_no_trans=true opens a throwaway session and connection for every lazy load, so you get N+1 outside any transaction with no consistency between the loads.

Open Session In View

What open-in-view = true does

Spring Boot registers an OpenEntityManagerInViewInterceptor by default and logs a warning at startup saying so. It opens an EntityManager when the request arrives and binds it to the thread until the response is written. Service transactions join that EM. After they commit, entities stay managed, so controllers, view templates and Jackson can trigger lazy loads, each running in auto-commit mode outside any transaction.

Why to disable it: it hides missing fetch decisions, which then show up as N+1 queries during JSON rendering where nobody looks for them. It holds the JDBC connection from the first query until the response is written, so a slow client or a remote call in the controller keeps a pool connection busy, and pool exhaustion arrives under load. It also allows non-transactional reads with no consistent snapshot. Set spring.jpa.open-in-view: false on day one. When you disable it in an existing app, every place that relied on it throws LazyInitializationException: controllers that navigate entities, Thymeleaf templates, and entities serialized straight to JSON. Fix each one with the five responses, ideally by returning DTOs from the service.

Entities in JSON and the ByteBuddyInterceptor error

Jackson serializes the proxy as a bean, finds the extra hibernateLazyInitializer property and fails. If OSIV is off, it throws LazyInitializationException instead, and if both sides of a bidirectional link are mapped, it recurses forever. The real fix is not to serialize entities at all. Return DTOs or records built inside the transaction (L240).

What breaks in production
  • OSIV + entity JSON: an endpoint that runs 2 queries in tests runs 300 in production while Jackson walks lazy associations, holding a pool connection the whole time.
  • Disabling OSIV without an audit: endpoints that were never covered by tests start returning 500s with LazyInitializationException.
  • enable_lazy_load_no_trans "fixes" the exception and makes every lazy access a new connection checkout.
  • getClass() comparisons fail on proxies. A LAZY proxy of an abstract Payment is never instanceof CardPayment: unproxy it first.

The N+1 Problem: Detection and Every Fix

50m video55m practice

N+1 is one query for a list of parents followed by one more query for each parent's children. It is invisible in the code and grows linearly with the data. Catch it with a query-count assertion in tests, then fix it per use case with a fetch join, an entity graph, batch fetching or a projection.

Reproducing it

        .map(o -> new OrderView(o.getId(), o.getItems().size()))                    // +1 per order

}

Definition · N+1 selects

A data access pattern in which 1 query returns N parent rows and the code then triggers 1 query per parent to load an association, for N + 1 round trips where 1 or 2 would do. The trigger is any lazy association initialized one owner at a time: a collection, a to-one proxy, or an EAGER to-one loaded after a JPQL query.

It is the most common ORM performance bug because nothing in the Java looks wrong: o.getItems() is a getter. With five rows in development it costs nothing. In production each extra query is a network round trip plus parse, plan and execute, so 100 orders × about a millisecond is 100 ms of pure waiting, and the cost rises with page size, nesting (items → product → category) and latency to the database. The same pattern appears through EAGER to-one associations, through toString, and through Jackson walking an entity graph.

Detection

  • SQL log counting: turn on org.hibernate.SQL and look for one statement repeated with different parameters. It is fine for exploring, but it can't fail a build.
  • hibernate.generate_statistics=true: the Statistics object counts prepared statements, entity loads and collection fetches per SessionFactory, and each session logs a summary.
  • datasource-proxy assertions: wrap the DataSource with a counting listener and assert the number of SELECTs per use case. This is the one that stops regressions.

Fetch vs load graphs. Passed as jakarta.persistence.fetchgraph, the attributes in the graph are fetched and every other association is treated as LAZY. Turn it on in every project. It doesn't make one-query fixes unnecessary, but it limits the damage from the N+1s nobody has found yet.

Pagination with fetch joins, and multiple bags

Paging a collection fetch join with setMaxResults can't be done in SQL: LIMIT 20 would cut off rows mid-order, after the third item of order 7. Hibernate therefore drops the limit, loads every matching row, and pages in memory, logging a warning (HHH000104 in Hibernate 5; HHH90003004, "firstResult/maxResults specified with collection fetch; applying in memory", in 6). With 200k matching orders, that is an outage. Set hibernate.query.fail_on_pagination_over_collection_fetch=true to make it an exception, and fix it one of three ways:

// 1. Two-step: page the ids in SQL, then fetch the graph for exactly those ids
List<Long> ids = em.createQuery(
        "select o.id from Order o where o.status = :s order by o.createdAt desc, o.id desc", Long.class)
    .setParameter("s", OrderStatus.PAID).setFirstResult(0).setMaxResults(20).getResultList();

        "select o from Order o join fetch o.items where o.id in :ids order by o.createdAt desc, o.id desc",
        Order.class).setParameter("ids", ids).getResultList();

// 2. Page the parents without a fetch join and let @BatchSize load the items: 1 + ceil(20/size) queries
// 3. Native SQL with a window function: dense_rank() over (order by o.created_at desc, o.id desc) <= 20

MultipleBagFetchException: cannot simultaneously fetch multiple bags appears when one query fetch-joins two List collections, such as items and payments. The SQL result is a Cartesian product (items × payments rows per order), and a bag cannot tell a duplicate produced by the join from a real duplicate. Switching to Set removes the exception but not the product: 50 items × 10 payments is 500 rows per order. The right fix is one collection per query. Fetch items in one query, then payments in a second query over the same orders; both run in the same persistence context, so they initialize collections on the same instances. Batch fetching also works.

What breaks in production
  • In-memory pagination: a list endpoint that is fast in staging loads the whole table in production and runs out of heap. Look for HHH90003004 in the logs.
  • Fix by EAGER: removes one N+1 and creates three more in every other query that loads the entity.
  • Nested N+1: the items are fixed, but each item's product and each product's category are still lazy proxies. Assert counts end to end, not per layer.
  • Cartesian fetch joins: two Sets fetched together multiply the row count, and the "one query" fix is slower than the N+1 it replaced.

Embeddables, Element Collections & Composite Keys

40m video45m practice

Not every object deserves a table and an id. Value objects such as an address or an amount of money belong in their owner's row as embeddables, small lists of values go in an element collection, and keys made of several columns become an embeddable id. Each is the right tool until the value starts needing an identity of its own.

@Embeddable value objects

Definition · Embeddable

A class whose instances have no identity (two equal addresses are interchangeable) and no lifecycle of their own: they are saved, loaded and deleted with the owning entity, and their fields become columns of the owner's table. Records work well as embeddables in Hibernate 6.2+ and officially in Jakarta Persistence 3.2, because value objects should be immutable anyway. If every column of an embedded value is NULL, Hibernate loads the field as null.

@Embeddable
public record Address(String street, String city, String zip) { }

@Embeddable
public class Money {                                        // a class, to put column details on the fields
    @Column(precision = 12, scale = 2) private BigDecimal amount;
    @Column(length = 3)                private String currency;
    protected Money() { }
    public Money(BigDecimal amount, String currency) { this.amount = amount; this.currency = currency; }
    // value semantics: equals/hashCode over both fields, no setters
}

@Entity @Table(name = "customers")
public class Customer {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;

    @Embedded
    @AttributeOverride(name = "street", column = @Column(name = "billing_street"))
    @AttributeOverride(name = "city",   column = @Column(name = "billing_city"))
    @AttributeOverride(name = "zip",    column = @Column(name = "billing_zip"))
    private Address billing;

    @Embedded
    @AttributeOverride(name = "street", column = @Column(name = "shipping_street"))
    @AttributeOverride(name = "city",   column = @Column(name = "shipping_city"))
    @AttributeOverride(name = "zip",    column = @Column(name = "shipping_zip"))
    private Address shipping;

    @Embedded private Money creditLimit;                    // columns amount, currency

    @ElementCollection
    @CollectionTable(name = "customer_tag", joinColumns = @JoinColumn(name = "customer_id"))
    @Column(name = "tag", length = 40)
    private Set<String> tags = new HashSet<>();

    @ElementCollection
    @CollectionTable(name = "customer_phone", joinColumns = @JoinColumn(name = "customer_id"))
    private List<Phone> phones = new ArrayList<>();      // record Phone(String number, String kind)
}

@AttributeOverride renames an embeddable's columns for one use. Without it, two Address fields would both map to street, city, zip, and Hibernate fails at boot with a repeated-column error. It is repeatable since JPA 2.2; @AttributeOverrides is the older container form. Nested embeddables work the same way: an Address holding a GeoPoint geo contributes geo.lat and geo.lng, which you override with dotted names, @AttributeOverride(name = "geo.lat", column = @Column(name = "billing_lat")). JPQL navigates them the same way: where c.billing.city = :city.

@ElementCollection and its rewrite behaviour

@ElementCollection maps a collection of basic values or embeddables into a @CollectionTable. It is lazy by default, it is always loaded and saved as a whole with its owner, and its rows can't be queried or referenced on their own. Because those rows have no primary key, Hibernate struggles to target one of them:

-- List<Phone> without @OrderColumn: remove one phone out of three
delete from customer_phone where customer_id=?
insert into customer_phone (customer_id,kind,number) values (?,?,?)    -- x 2, the survivors

-- Set<String> tags: remove one tag
delete from customer_tag where customer_id=? and tag=?

A bag is rewritten on every removal, as with @ManyToMany (L231). A Set deletes by matching every column of the element, and with nullable embeddable columns kind = NULL never matches, so the delete silently misses. @OrderColumn gives each row an addressable position at the cost of shifting updates. Element collections suit small, bounded sets of values (tags, a few phone numbers, allowed IP ranges). Once the collection grows or its rows need ids, querying or references, promote it to an entity with a @ManyToOne.

Composite keys: @EmbeddedId vs @IdClass

Definition · Composite primary key class

The spec requires the key class to be public, have a public or protected no-arg constructor, implement Serializable, and define equals/hashCode over every key field. The persistence context is a map keyed by id, so a key with identity equality would make two loads of the same row look like different entities. Keep key fields effectively immutable: changing a primary key means a new entity.

@Embeddable
public class OrderLineId implements Serializable {
    private Long orderId;
    private Integer lineNo;
    protected OrderLineId() { }
    public OrderLineId(Long orderId, Integer lineNo) { this.orderId = orderId; this.lineNo = lineNo; }
    @Override public boolean equals(Object o) {
        return o instanceof OrderLineId k && Objects.equals(orderId, k.orderId) && Objects.equals(lineNo, k.lineNo);
    }
    @Override public int hashCode() { return Objects.hash(orderId, lineNo); }
}

@Entity @Table(name = "order_line")
public class OrderLine {
    @EmbeddedId private OrderLineId id;

    @ManyToOne(fetch = FetchType.LAZY)
    @MapsId("orderId")                         // the orderId key part IS the FK column order_id
    @JoinColumn(name = "order_id")
    private Order order;

    private int quantity;
    protected OrderLine() { }
    public OrderLine(Order order, int lineNo, int quantity) {
        this.id = new OrderLineId(order.getId(), lineNo);
        this.order = order; this.quantity = quantity;
    }
}

@EmbeddedId is preferred: the key is a real object you can pass around and use as a repository id, and the mapping is in one place. @IdClass keeps flat paths in JPQL (l.lineNo), which makes it handy for legacy schemas, but the key's fields are declared twice and must match by name and type. When an @Id field is an association, as with order, the key class field holds the referenced entity's id type (Long). @MapsId makes one part of the key share its column with a @ManyToOne, so order_id is mapped once and Hibernate fills the key part from the associated entity. This is the same technique as Enrollment in L231.

What breaks in production
  • Element collection grows to thousands: every edit rewrites it, and every load pulls all of it. It should have been an entity.
  • Mutable shared embeddables: one Address instance assigned to two customers and then mutated changes both. Immutable records prevent this.
  • All-null embeddable: an entity whose optional Money columns are all null loads with creditLimit == null, and the next call on getCreditLimit() throws NPE.
  • Key class without equals/hashCode: find misses the first-level cache, duplicate instances appear, and merges insert instead of updating.

Inheritance Mapping Strategies

45m video45m practice

SQL has no inheritance, so JPA offers three ways to fake it, and each trades query speed against schema integrity. Use @MappedSuperclass for shared fields, SINGLE_TABLE when subtypes differ by a few columns, JOINED when constraints matter, and composition when the "type" can change.

@MappedSuperclass: sharing fields, not identity

@MappedSuperclass
public abstract class BaseEntity {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) protected Long id;
    @Version protected long version;
    @Column(nullable = false, updatable = false) protected Instant createdAt;
    public Long getId() { return id; }
}

A mapped superclass has no table and is not an entity. Its mappings are copied into each subclass's table. You can't write select b from BaseEntity b or point an association at it. That is exactly what you want for a BaseEntity with id, version and audit columns (L244): pure code reuse, no polymorphism in the database.

Three strategies for a real hierarchy

The running example is Payment with CardPayment (last four digits), BankTransfer (IBAN) and WalletPayment (wallet id), queried polymorphically ("all payments over 100").

@Entity @Table(name = "payment")
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "type", discriminatorType = DiscriminatorType.STRING, length = 16)
public abstract class Payment extends BaseEntity {
    @Column(precision = 12, scale = 2, nullable = false) private BigDecimal amount;
    public BigDecimal getAmount() { return amount; }
}

@Entity @DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    @Column(length = 4) private String cardLast4;          // cannot be NOT NULL in a shared table
}

@Entity @DiscriminatorValue("BANK")
public class BankTransfer extends Payment { @Column(length = 34) private String iban; }

@Entity @DiscriminatorValue("WALLET")
public class WalletPayment extends Payment { private String walletId; }

// JOINED instead: on Payment   @Inheritance(strategy = InheritanceType.JOINED)
//                 on each sub  @Table(name = "card_payment") @PrimaryKeyJoinColumn(name = "payment_id")
Definition · The three strategies
  • SINGLE_TABLE (the default): one table for the hierarchy, plus a discriminator column (@DiscriminatorColumn, values from @DiscriminatorValue, by default the entity name). Reads and writes touch one row and polymorphic queries need no joins. But subclass columns must be nullable, so the database can't require card_last4 for card payments unless you add a CHECK such as check (type <> 'CARD' or card_last4 is not null), and wide hierarchies give sparse rows.
  • JOINED: a base table plus one table per subclass whose primary key is also an FK to the base (@PrimaryKeyJoinColumn). The schema is normalized and every subclass column can be NOT NULL with its own FKs. An insert writes two rows, a subclass load is a join, and a polymorphic query outer-joins every subtable.
  • TABLE_PER_CLASS: one complete table per concrete class, with no shared table. Single-type queries are as fast as a plain table, but polymorphic queries become UNION ALL over every table. Ids must be unique across all of them, so IDENTITY is not allowed (Hibernate rejects it) and you need a shared sequence. And no other table can have an FK to "a payment".

Polymorphic queries and TYPE()

// all payments, as the right subclass instances

                       .setParameter("x", new BigDecimal("100")).getResultList();

em.createQuery("select p from Payment p where type(p) in (CardPayment, WalletPayment)", Payment.class);

// count per type
em.createQuery("select type(p), count(p) from Payment p group by type(p)", Object[].class);

Querying a subclass directly (from CardPayment c) needs no discriminator logic in Java. To filter on a subclass field while querying the base type, downcast with TREAT (L237). Associations can target the base (@ManyToOne Payment payment). A LAZY one gives you a proxy of the abstract Payment, which is never instanceof CardPayment (L233).

Why composition often beats entity inheritance

Entity inheritance fixes an object's class forever: a row cannot change subtype, so "convert this card payment to a bank transfer" becomes delete plus insert, with a new id and broken references. Hierarchies also attract shared columns that don't belong to every subtype, and adding a subtype means schema changes, a new table for JOINED, and new joins in every polymorphic query. Often the better model is one entity with a type field and a part that varies: Payment with @Enumerated PaymentMethod method and either nullable @Embedded details per method or a jsonb details column validated by method. Put type-specific behaviour in a strategy chosen by the enum (an EnumMap<PaymentMethod, PaymentProcessor>). Use inheritance when subtypes really are different things with stable, distinct data and you need polymorphic queries across them.

What breaks in production
  • SINGLE_TABLE without CHECKs: a card payment without card_last4 passes every constraint, and a bug writes thousands of them.
  • JOINED list pages on a 10-subtype hierarchy run 10 outer joins per query and get slower with every new subtype.
  • TABLE_PER_CLASS with IDENTITY fails at boot. With separate sequences per table, ids collide across subtypes and the persistence context mixes them up.
  • Changing type in place: updating the discriminator column with SQL produces an object Hibernate loads as the new class, with the old subtype's columns still set or the new subtype's rows missing.

JPQL: The Query Language

50m video50m practice

JPQL looks like SQL but works on your object model: entity names, field paths and associations, which Hibernate translates to tables, columns and joins through the mapping. Learn to predict the SQL behind every path and join, and remember that bulk statements go around the persistence context.

From JPQL to SQL

In select o from Order o where o.customer.name = :name, Order is the entity name, o an identification variable and o.customer.name a path. A path through a to-one association is an implicit join, and an implicit join is an inner join:

select o1_0.id,... from orders o1_0 join customers c1_0 on c1_0.id=o1_0.customer_id where c1_0.name=?

Two hidden costs: every path through an association adds a join you didn't write, and inner-join semantics silently drop rows whose association is null (orders with no customer vanish from where o.customer.name = :n or o.status = :s). o.customer.id is the exception: the FK column is in orders, so no join is needed. Paths through collections (o.items.quantity) are illegal; collections need an explicit join.

Explicit joins, ON and fetch joins

// inner join to a collection: one row per (order, item)
select o.id, i.productId from Order o join o.items i where i.quantity > 5

// left join keeps orders without items; ON adds a condition to the join itself
select o, count(i) from Order o left join o.items i on i.quantity > 5 group by o

// fetch join: load the association into the entity, no extra columns in the result
select o from Order o join fetch o.customer where o.status = :status

// entity join on an unmapped relationship (Hibernate; standard in Jakarta Persistence 3.2)
select i, p.name from OrderItem i join Product p on p.id = i.productId

A plain join introduces an alias for filtering and selecting, and loads nothing into the parent entity. join fetch initializes the association on the returned entities and is the one-query fix for N+1 (L234). Don't filter on a fetch-joined collection: join fetch o.items i where i.quantity > 5 leaves managed orders whose items collection contains only some of the items, and any code that later trusts order.getItems() is wrong.

Parameters, never concatenation

em.createQuery("select c from Customer c where c.email = :email", Customer.class)
  .setParameter("email", email);                         // named: preferred

em.createQuery("select c from Customer c where c.email = ?1", Customer.class)
  .setParameter(1, email);                               // positional: ?1, ?2 ... (1-based, numbered)

// NEVER: "... where c.email = '" + email + "'"   ->  JPQL injection, and a new plan per value

Hibernate binds parameters as JDBC parameters, so the value never becomes query text. Injection is as real in JPQL as in SQL: ' or '1'='1 works the same way. Identifiers such as sort fields cannot be parameters, so check them against an allowlist and then add them to the query (L241).

Definition · Constructor expression

select new FullyQualifiedName(args...) calls a matching constructor for each result row. The result is plain objects (records are ideal): not managed, no snapshots, no lazy associations, and only the selected columns travel over the wire. It is the cheapest way to read data you will display rather than modify (L240). Bulk UPDATE and DELETE bypass the persistence context

@Transactional
public int expireStale(Instant cutoff) {
    Order o = em.find(Order.class, 42L);                 // managed, status PENDING
    int n = em.createQuery("""
            update Order o set o.status = :expired, o.version = o.version + 1
            where o.status = :pending and o.createdAt < :cutoff""")
        .setParameter("expired", OrderStatus.EXPIRED)
        .setParameter("pending", OrderStatus.PENDING)
        .setParameter("cutoff", cutoff)
        .executeUpdate();                                // one SQL statement, n rows
    o.getStatus();                                       // still PENDING in memory: stale
    return n;
}
What a bulk statement skips

executeUpdate runs one SQL statement directly. The persistence context isn't told, so managed instances keep their old state, and a later flush of a dirty one can overwrite the bulk change. It also skips cascades, lifecycle callbacks and the @Version increment (bump it by hand as above, so concurrent optimistic writers notice). Hibernate does flush pending changes to the affected table first under AUTO flush. The fix is to run bulk statements at the start of a transaction, or clear() (or refresh) afterwards. In Spring Data, @Modifying(flushAutomatically = true, clearAutomatically = true) does both around a @Query.

@NamedQuery and choosing a query style

@Entity

            query = "select o from Order o where o.status = :status order by o.createdAt desc")
public class Order { /* ... */ }

Named queries are parsed and validated when the factory boots, so a typo fails startup instead of a request. Spring Data's @Query strings are validated at startup the same way, and a repository method named findByStatus picks up a named query called Order.findByStatus automatically. Text blocks keep inline JPQL readable, so the old argument for named queries ("keep long strings out of code") is weaker now. Validation at boot is still the reason to use them.

What breaks in production
  • Implicit inner joins in OR conditions drop rows with null associations, and a search silently returns fewer results than it should.

  • Filtered fetch joins leave partially loaded collections in the context, and an orphan-removal flush can then delete the "missing" children.
  • Concatenated sort or filter fields: JPQL injection, plus the query plan cache filling with one-off plans.

Criteria API & The Metamodel

45m video50m practice

The Criteria API builds a query as a tree of Java objects instead of a string, so filters can be added conditionally and checked by the compiler. Combined with the generated static metamodel, a renamed field breaks the build, not production. The price is verbosity, so use it where queries really are dynamic.

When Criteria earns its keep

A search screen with eight optional filters has 2⁸ possible WHERE clauses. In JPQL you end up concatenating fragments, tracking and placement and binding only the parameters that were used, which is error-prone and hard to read. Criteria makes each filter a Predicate object that you add to a list or not. Use it for runtime-shaped queries: optional filters, user-selected sort columns, generic admin search, and reusable predicate libraries. For fixed queries, JPQL is shorter and clearer.

The building blocks

Definition · Criteria types
  • CriteriaBuilder (from em.getCriteriaBuilder()): the factory for queries, predicates (equal, like, and) and expressions (lower, sum, coalesce).
  • CriteriaQuery<T>: the query itself, with select, where, orderBy, groupBy, having and distinct. T is the result type.
  • Root<X>: a FROM entry, the equivalent of from Order o. Join<X, Y>: a join from a root or another join. Both are Paths, which you navigate with get(...).
  • Predicate: a boolean expression. Several passed to where(...) are combined with AND.

Building a query step by step, with optional filters

public record OrderFilter(OrderStatus status, String customerName, Instant from, Instant to, BigDecimal minTotal) { }

public List<Order> search(OrderFilter f, int limit) {
    CriteriaBuilder cb = em.getCriteriaBuilder();
    CriteriaQuery<Order> q = cb.createQuery(Order.class);
    Root<Order> o = q.from(Order.class);                                   // from Order o
    Join<Order, Customer> c = o.join(Order_.customer);                     // join o.customer c

    List<Predicate> where = new ArrayList<>();
    if (f.status() != null)
        where.add(cb.equal(o.get(Order_.status), f.status()));
    if (f.customerName() != null)
        where.add(cb.like(cb.lower(c.get(Customer_.name)),
                          "%" + escapeLike(f.customerName().toLowerCase(Locale.ROOT)) + "%", '\\'));
    if (f.from() != null && f.to() != null)
        where.add(cb.between(o.get(Order_.createdAt), f.from(), f.to()));
    if (f.minTotal() != null)
        where.add(cb.ge(o.get(Order_.total), f.minTotal()));

    q.select(o)
     .where(where.toArray(Predicate[]::new))                               // AND; empty = no WHERE
     .orderBy(cb.desc(o.get(Order_.createdAt)), cb.desc(o.get(Order_.id)));
    return em.createQuery(q).setMaxResults(limit).getResultList();
}

static String escapeLike(String s) { return s.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_"); }

Values passed to cb.equal, cb.like and so on are bound as JDBC parameters by Hibernate's default, so this is injection-safe. Note the explicit LIKE escaping, though: without it, a user who types % matches every row. Combine with OR explicitly: cb.or(cb.equal(...), cb.isNull(...)). cb.and() with no arguments is a true conjunction, which is handy as a neutral starting value.

Functions, aggregates, fetch joins and bulk operations

// Tuple query: revenue per customer for paid or shipped, non-cancelled orders
CriteriaQuery<Tuple> t = cb.createTupleQuery();
Root<Order> o = t.from(Order.class);
Join<Order, Customer> c = o.join(Order_.customer);
t.multiselect(c.get(Customer_.name).alias("customer"),
              cb.count(o).alias("orders"),
              cb.sum(cb.coalesce(o.get(Order_.total), BigDecimal.ZERO)).alias("revenue"))
 .where(o.get(Order_.status).in(OrderStatus.PAID, OrderStatus.SHIPPED),
        cb.isNull(o.get(Order_.cancelledAt)))
 .groupBy(c.get(Customer_.name));
for (Tuple row : em.createQuery(t).getResultList())
    System.out.println(row.get("customer", String.class) + " " + row.get("revenue", BigDecimal.class));

// Fetch join: initialize items on the returned orders (no fetch in the count query!)
o.fetch(Order_.items, JoinType.LEFT);

// CriteriaUpdate / CriteriaDelete: bulk statements with the same caveats as JPQL bulk
CriteriaUpdate<Order> u = cb.createCriteriaUpdate(Order.class);
Root<Order> r = u.from(Order.class);

 .where(cb.equal(r.get(Order_.status), OrderStatus.PENDING), cb.lessThan(r.get(Order_.createdAt), cutoff));

Other CriteriaBuilder functions you'll use: like/notLike, between, in (or path.in(...)), isNull/isNotNull, lower/upper, coalesce, sum/avg/max/count/countDistinct, selectCase, and exists with a q.subquery(...). For a paged search, build the count query separately from the same predicate-building function. Reusing a root with a fetch join in a count query is an error.

An honest assessment

The search above is about 20 lines of Criteria. The equivalent fixed JPQL is 4. That ratio is the main complaint, and it is fair: Criteria reads like an AST because it is one. What you get for the verbosity is composition and type safety, and those only matter for dynamic queries. Two higher-level options keep the benefits with less ceremony. Spring Data Specifications (L321) wrap each predicate in a named, reusable Specification<T> lambda (hasStatus(s).and(createdBetween(a, b))) and still produce Criteria underneath. Querydsl (L322) generates its own QOrder metamodel and gives a fluent, much shorter API (order.status.eq(s).and(order.total.goe(min))), at the cost of another code generator and a library whose maintenance has slowed. In practice: Criteria or Specifications for dynamic filters, JPQL for everything fixed.

What breaks in production
  • String paths (o.get("staus")) compile fine and fail on the first request after a refactor. Use the metamodel.
  • Unescaped LIKE input: a search for % or _ matches everything and becomes a full scan.
  • Fetch join reused in the count query: an exception, or a wrong count from duplicated rows when joins multiply.
  • Missing processor path: adding annotationProcessorPaths for the metamodel silently disables Lombok, which was found on the classpath before. List every processor.

Native Queries, Result Mapping & Stored Procedures

40m video45m practice

JPA does not stop you from writing SQL. A native query runs your exact SQL through the same EntityManager and transaction, and a result mapping turns the rows into entities, scalars or DTOs. Reach for it whenever the database can do something JPQL cannot express.

createNativeQuery and @Query(nativeQuery = true)

Definition · Native query

A query whose text is sent to the database unchanged: no parsing against the metamodel, no dialect translation, no validation at boot. Hibernate still binds the parameters, joins the current transaction and connection, flushes before running it, and maps the result columns, either to entities (which become managed) or, through a result set mapping, to scalars and DTOs.

// Entities: select every mapped column of the table; the rows become MANAGED Orders
List<Order> recent = em.createNativeQuery(
        "select o.* from orders o where o.created_at > now() - interval '1 day'", Order.class)
    .getResultList();

// Scalars: each row is an Object[] (or a single value for one column)
List<Object[]> rows = em.createNativeQuery(
        "select status, count(*) from orders group by status").getResultList();

// Spring Data: same thing on a repository method; named parameters work in native SQL here
@Query(value = "select * from orders where details ->> 'channel' = :channel", nativeQuery = true)
List<Order> findByChannel(@Param("channel") String channel);

An entity result goes into the persistence context like any other load, with snapshots, dirty checking and the identity guarantee, so the SQL must return every column the entity maps, under the mapped names. Native queries take positional parameters (?1) per the spec. Hibernate and Spring Data also accept :name. Before running a native query, Hibernate flushes pending changes (through the JPA API it can't tell which tables the SQL reads, L228). Native bulk UPDATE/DELETE bypass the context exactly as JPQL bulk statements do.

Result set mappings: entity, column, constructor

public record TopOrder(Long customerId, Long orderId, BigDecimal total, Long rank) { }

@Entity @Table(name = "orders")
@SqlResultSetMapping(name = "TopOrderMapping",
    classes = @ConstructorResult(targetClass = TopOrder.class, columns = {
        @ColumnResult(name = "customer_id", type = Long.class),

        @ColumnResult(name = "total",       type = BigDecimal.class),

    select customer_id, order_id, total, rnk from (
        select o.customer_id, o.id as order_id, o.total,
               rank() over (partition by o.customer_id order by o.total desc) as rnk

    order by customer_id, rnk""")
public class Order { /* ... */ }

@EntityResult(entityClass = Order.class, fields = @FieldResult(...)) maps columns to an entity when the names differ. @ColumnResult alone returns scalars. @NamedNativeQuery, like @NamedQuery, keeps the SQL next to the mapping and registers it at boot. The SQL itself is not validated, though: the database sees it only when it runs.

Hibernate's own API: addScalar and TupleTransformer

List<TopOrder> rows = em.createNativeQuery(sql)
    .unwrap(NativeQuery.class)                                  // org.hibernate.query.NativeQuery
    .addScalar("customer_id", StandardBasicTypes.LONG)
    .addScalar("order_id",    StandardBasicTypes.LONG)
    .addScalar("total",       StandardBasicTypes.BIG_DECIMAL)
    .addScalar("rnk",         StandardBasicTypes.LONG)
    .setTupleTransformer((tuple, aliases) ->
        new TopOrder((Long) tuple[0], (Long) tuple[1], (BigDecimal) tuple[2], (Long) tuple[3]))
    .getResultList();

addScalar fixes each column's type, so you don't depend on what the driver happens to return (Postgres count(*) is bigint, sum(int) is also bigint, sum(numeric) is numeric). Hibernate 5's setResultTransformer(Transformers.aliasToBean(...)) is deprecated in 6. Its replacements are TupleTransformer (per row) and ResultListTransformer (whole list, for de-duplication or grouping), which are functional interfaces and so work well with lambdas and record constructors.

Database features JPQL can't express

-- recursive CTE: a category and all its descendants
with recursive tree as (
  select id, parent_id, name from category where id = :root
  union all
  select c.id, c.parent_id, c.name from category c join tree t on c.parent_id = t.id)
select * from tree;

-- jsonb operators and full-text search
select id from product where attributes @> '{"color":"red"}'::jsonb;
select id, ts_rank(search_vec, q) as score
from product, plainto_tsquery('english', :text) q
where search_vec @@ q order by score desc limit 20;

Window functions, recursive CTEs, jsonb containment, full-text ranking, DISTINCT ON, LATERAL, INSERT ... ON CONFLICT and FOR UPDATE SKIP LOCKED are all native-only in standard JPA. Hibernate 6's HQL has grown some of them (set operations, CTEs, window functions in recent releases), but not portably. One Postgres-specific catch: the jsonb operators ?, ?| and ?& clash with JDBC ? placeholders. Use the function forms (jsonb_exists(attributes, 'color')) or the driver's ?? escape.

When to stop fighting the ORM

Drop to native SQL, or to jOOQ for type-safe SQL, when the query is a report rather than an aggregate load: rankings, rollups, time-series buckets, recursive trees, or anything you would tune with EXPLAIN. Do the same when the JPQL version needs workarounds (two queries plus in-memory joins), or when performance requires a specific plan. Keep JPA for loading and changing aggregates. Both run on the same connection and transaction, so you can mix them in one service method.

Stored procedures

// Ad hoc: positional parameters are the most portable across drivers
StoredProcedureQuery q = em.createStoredProcedureQuery("calc_loyalty_points")
    .registerStoredProcedureParameter(1, Long.class, ParameterMode.IN)
    .registerStoredProcedureParameter(2, Integer.class, ParameterMode.OUT)
    .setParameter(1, customerId);
q.execute();
Integer points = (Integer) q.getOutputParameterValue(2);

// Declared once on an entity, validated at boot like other named queries
@NamedStoredProcedureQuery(name = "Customer.loyalty", procedureName = "calc_loyalty_points",
    parameters = {
        @StoredProcedureParameter(mode = ParameterMode.IN,  type = Long.class),
        @StoredProcedureParameter(mode = ParameterMode.OUT, type = Integer.class) })

Parameter modes are IN, OUT, INOUT (set a value and read it back), and REF_CURSOR for a procedure that returns a cursor, whose rows you read with getResultList(), optionally mapped through resultClasses or resultSetMappings. On Postgres, check whether the routine is a FUNCTION (called through select or the JDBC {call} escape) or a PROCEDURE (called with CALL, and allowed to commit). Cursor results require an open transaction, and driver behaviour differs here, so test against the real database. Spring Data offers @Procedure on repository methods for simple cases.

Keeping native SQL testable and dialect-aware

  • Test against the real engine with Testcontainers. H2's "Postgres mode" accepts SQL that Postgres rejects, and the reverse.
  • Name every column and alias computed ones, and map by name, not position. Avoid select * except for an entity's own table.
  • Keep SQL in one place (named queries, text blocks in a repository, or .sql resources), behind a repository interface, so a second database means a second implementation, not a hunt through services.
  • Assert on results and plans: one test per query with seeded data, and for hot queries, a check that EXPLAIN uses the intended index.
What breaks in production
  • Partial entity results: a native query selecting some of an entity's columns fails with a "column not found" error, or with aliasing tricks returns entities with null fields, which dirty checking then writes back as nulls.
  • Type drift: (Integer) row[1] on count(*) throws ClassCastException because it is a Long. Use addScalar or typed mappings.
  • Dialect lock-in by accident: Postgres-only SQL ends up in a module that also runs on MySQL in another deployment.
  • String-built native SQL: the injection risk is the same as JDBC's. Bind every value, and allowlist identifiers.

Projections, DTOs & MapStruct

45m video50m practice

Entities model your persistence, while DTOs describe what each API consumer is allowed to see and send. Read straight into DTOs with projections when you only display data, map entities to DTOs inside the service transaction when you need the domain logic, and let MapStruct generate the boring mapping code at compile time.

Never return entities from the API layer

  • Coupling: every field rename or new association changes your public JSON contract, and clients break.
  • Lazy-loading errors: serialization walks lazy associations after the transaction has ended, giving LazyInitializationException, or with OSIV, hidden N+1 (L233).
  • Over-fetching: a list page needs 4 columns, but you load 30 plus snapshots plus whatever is EAGER.
  • Accidental exposure: passwordHash, internal flags or another tenant's data reach the response. On input, binding request JSON to an entity allows mass assignment: a client sends "role": "ADMIN" and you save it.

Definition · Why projections are cheap

A projection result is not an entity. It never enters the persistence context, so there is no identity-map entry, no loaded-state snapshot, no dirty check at flush and no proxy that can fail later, and only the selected columns cross the network. For entities you must read but won't change, the hint org.hibernate.readOnly (HibernateHints.HINT_READ_ONLY) or a @Transactional(readOnly = true) service method makes Hibernate load them without snapshots. That saves real memory and CPU on large reads (L228).

Pagination & Sorting in JPA

35m video40m practice

Offset pagination is easy and gets slower the deeper you page, and it is only correct when the sort order is total. Use offsets for shallow, human-navigated lists, keyset cursors for deep or infinite scrolling, and streams for exports, and never combine a collection fetch join with a page limit.

setFirstResult, setMaxResults and the count query

int page = 3, size = 20;
List<Order> rows = em.createQuery("""
        select o from Order o where o.status = :s
        order by o.createdAt desc, o.id desc""", Order.class)
    .setParameter("s", OrderStatus.PAID)
    .setFirstResult(page * size)                 // OFFSET 60
    .setMaxResults(size)                         // LIMIT 20
    .getResultList();

long total = em.createQuery("select count(o) from Order o where o.status = :s", Long.class)
    .setParameter("s", OrderStatus.PAID).getSingleResult();
select ... from orders o1_0 where o1_0.status=? order by o1_0.created_at desc,o1_0.id desc
  offset ? rows fetch first ? rows only
select count(o1_0.id) from orders o1_0 where o1_0.status=?

The dialect renders the limit in the database's own syntax (LIMIT/OFFSET, FETCH FIRST, TOP). The count query is the hidden cost. To give "page 3 of 1,204", the database must count every matching row, and in Postgres that means scanning them (an index-only scan at best), so on a large filtered set the count can cost more than the page itself. Options: skip the total and return a Slice (fetch size + 1 rows to learn hasNext), cap it ("1,000+"), cache it briefly, or show an estimate from pg_class.reltuples for unfiltered lists.

Fetch joins and pagination

Adding join fetch o.items to the query above makes Hibernate drop the SQL limit and paginate in memory, with warning HHH000104 in Hibernate 5 and HHH90003004 in 6. A SQL LIMIT counts joined rows, not orders, so it would cut an order's items in half. Use one of the three fixes from L234: page the ids first and then fetch-join where o.id in :ids; page plain orders and let @BatchSize load the items; or use native SQL with dense_rank() over the parent key. Set hibernate.query.fail_on_pagination_over_collection_fetch=true so the mistake fails in tests.

Sorting by joined and computed columns

// sort by a joined column: needs an explicit join; LEFT keeps orders without a customer
select o from Order o left join o.customer c order by c.name asc nulls last, o.id asc

// sort by a computed value: aggregate in the select, then order by it
select new com.shop.OrderTotal(o.id, sum(i.quantity * i.unitPrice))
from Order o join o.items i group by o.id order by sum(i.quantity * i.unitPrice) desc, o.id desc

// user-chosen sort: map public names to JPQL fragments, never pass input through

    "newest",   "o.createdAt desc, o.id desc",

HQL supports nulls first/last and ordering by aggregate expressions. Each sortable column needs a supporting index, or every page is a sort of the whole filtered set. Spring Data packages all this as Sort and Pageable: PageRequest.of(3, 20, Sort.by("createdAt").descending().and(Sort.by("id").descending())) passed to a repository method returning Page<T> (runs a count query), Slice<T> (no count) or List<T>. Spring Data checks Sort property names against the entity, but still restrict which properties clients may sort by.

Definition · Stable sort key

An ORDER BY is total when no two rows compare equal, which means it ends with a unique column such as the id. Without that, SQL may return tied rows in any order, and that order can change between the query for page 2 and the query for page 3. Rows then appear on two pages or on none. "Newest first" must be created_at desc, id desc, not created_at desc. This is a correctness requirement, not tidiness.

Deep offsets and keyset pagination

Offsets also drift under writes: if a new order arrives while someone reads page 2, every row shifts by one, and page 3 repeats an item. Keyset (or "seek") pagination fixes both problems by filtering on the last row seen instead of counting rows. The cursor is the sort key of that row, in this case (createdAt, id). JPQL has no portable row-value comparison (a, b) < (?, ?), so expand it:

public record Cursor(Instant createdAt, long id) { }
public record OrderRow(Long id, Instant createdAt, BigDecimal total) { }

public List<OrderRow> page(Cursor after, int size) {
    String seek = after == null ? "" : "and (o.createdAt < :c or (o.createdAt = :c and o.id < :id))";
    var q = em.createQuery("""
            select new com.shop.OrderRow(o.id, o.createdAt, o.total) from Order o
            where o.status = :s %s
            order by o.createdAt desc, o.id desc""".formatted(seek), OrderRow.class)   // constant fragment only
        .setParameter("s", OrderStatus.PAID)
        .setMaxResults(size);
    if (after != null) q.setParameter("c", after.createdAt()).setParameter("id", after.id());
    return q.getResultList();                     // next cursor = last row's (createdAt, id)
}
create index ix_orders_status_created_id on orders (status, created_at desc, id desc);

Encode the cursor as an opaque token (Base64 of the two values) so that clients can't build arbitrary ones. The trade-offs: no "jump to page 400" and no page numbers, which is fine for feeds, APIs and infinite scroll. Spring Data 3.1+ offers this as ScrollPosition.keyset() with Window<T> results.

Streaming large result sets

// Spring Data: a Stream backed by a JDBC cursor
@QueryHints(@QueryHint(name = AvailableHints.HINT_FETCH_SIZE, value = "500"))
@Query("select o from Order o where o.createdAt < :before order by o.id")
Stream<Order> streamOlderThan(@Param("before") Instant before);

@Transactional(readOnly = true)                   // required: the cursor lives in the transaction
public void export(Instant before, Consumer<Order> sink) {
    try (Stream<Order> s = orders.streamOlderThan(before)) {   // MUST close: releases cursor + connection
        s.forEach(o -> { sink.accept(o); em.detach(o); });      // keep the persistence context small
    }
}

// Hibernate: ScrollableResults, the lower-level equivalent
try (ScrollableResults<Order> r = em.unwrap(Session.class)
        .createSelectionQuery("from Order o where o.createdAt < :b order by o.id", Order.class)
        .setParameter("b", before).setFetchSize(500).scroll(ScrollMode.FORWARD_ONLY)) {
    int n = 0;
    while (r.next()) { process(r.get()); if (++n % 500 == 0) em.clear(); }
}

Without a fetch size the Postgres driver reads the whole result into memory before returning the first row, and it only uses a server-side cursor when autocommit is off, which a transaction guarantees (L222). Streaming fixes the JDBC side. The persistence context still holds every entity read, so detach or clear as you go, or stream projections, which leave nothing in the context.

What breaks in production
  • Unstable sort: users report "duplicate items in the feed". The ORDER BY had no unique tiebreaker.
  • Bots at page 50,000: deep OFFSETs scan millions of index entries per request. Cap the page number, or switch to keyset.
  • Count query on every page of a 200M-row table dominates database CPU. Use Slice or cache the count.
  • Unclosed streams leak cursors and pool connections until the app stops serving requests.

Caching: First Level, Second Level & Query Cache

45m video45m practice

The first-level cache is the persistence context and always on. The second-level cache is an opt-in, shared store of entity state that saves primary-key lookups across transactions, but only if you can guarantee it is invalidated, and with more than one application instance that is the hard part. Cache read-mostly reference data, measure hit rates, and be sceptical of the query cache.

Where a lookup goes

First level, recap (L227): one per persistence context, always on, not configurable. It guarantees identity and repeatable reads of entities within a transaction. It is not a performance cache across requests: it disappears at commit.

The second-level cache

Definition · Second-level cache

A cache owned by the EntityManagerFactory (Hibernate's SessionFactory) and shared by all its sessions. It stores entities in dehydrated form: an array of property values (ids for associations) keyed by entity name and id, never the live objects. On a hit, Hibernate assembles a new managed instance from that array. It serves find, getReference initialization and lazy to-one loads by id. Ordinary JPQL queries still go to the database, unless the query cache is on.

The query cache

List<Country> all = em.createQuery("select c from Country c order by c.name", Country.class)
    .setHint(HibernateHints.HINT_CACHEABLE, true)                // org.hibernate.cacheable
    .getResultList();

With hibernate.cache.use_query_cache=true, a cacheable query's key (SQL, parameters, paging) maps to the list of result ids, or to scalar values for projections. A hit returns ids, which still have to be resolved through the entity cache, so the query cache is useless without the entity cache: each id would become a SELECT. Correctness comes from an update timestamps region. Any insert, update or delete on a table marks it, and every cached query touching that table becomes invalid. On tables that are written often, the cache is invalidated constantly, every write also updates the timestamps region, and lookups add overhead without hits. It is frequently a net loss. It pays off only for queries over tables that rarely change, such as lookup lists and configuration.

Measuring it

Statistics st = emf.unwrap(SessionFactory.class).getStatistics();   // hibernate.generate_statistics=true

A useful region has hits far above puts. If misses and puts track each other, entries are evicted (the region is too small or the TTL too short) or invalidated (the data is too volatile) before anyone reads them. Export these counters to your metrics system: with the hibernate-micrometer module on the classpath and statistics on, Spring Boot binds them for you.

Invalidation across instances and other writers

The hard part

With a local cache (Ehcache heap, Caffeine) on three instances, an update through instance A updates A's cache only. B and C serve the old value until TTL or eviction. That is stale data, and with optimistic locking it shows up as version conflicts on save. Your options: a clustered provider (Infinispan in invalidation mode broadcasts evictions; Redis is one shared store), short TTLs where staleness is acceptable, or caching only READ_ONLY data. Writers Hibernate doesn't see bypass every option: other services, SQL scripts, database triggers, or the native bulk updates you run yourself. Hibernate evicts the entity region after a bulk JPQL update, and after native SQL it evicts broadly unless you declare the affected query spaces. A script run from psql leaves the cache stale until TTL.

When Spring Cache is the better choice (L386): @Cacheable on a service method caches results, such as a rendered price list, a computed recommendation or a remote API response, with explicit keys, TTLs and @CacheEvict calls, in Redis shared by every instance. It is visible in the code and independent of the ORM. Hibernate's L2 cache is a transparent way to save id lookups. Spring Cache is an explicit way to save work. For most services the explicit cache, applied to a few hot DTOs, is easier to reason about.

What breaks in production
  • Local L2 cache behind a load balancer: users see their own update, then the old value on the next request, which another instance served.
  • Query cache on a hot table: hit rate near zero, plus extra writes to the timestamps region on every update. Turning it off makes the system faster.
  • Cached collection, uncached elements: one SELECT per element on every "hit".
  • Unbounded regions: a cache with no size limit is a memory leak with a hit counter.

Optimistic & Pessimistic Locking

45m video50m practice

Two users editing the same row will silently overwrite each other unless something detects the conflict. Optimistic locking detects it at write time with a version column and costs nothing until a conflict happens. Pessimistic locking prevents it by holding row locks and costs waiting. Use optimistic by default, pessimistic for short, hot critical sections, and turn conflicts into a clear HTTP 409.

The lost update, in two browser tabs

Database isolation alone doesn't prevent this. Each tab's read and write happen in different transactions (two HTTP requests), so no transaction ever sees a conflict. The conflict has to be detected at application level, across requests.

Optimistic locking with @Version

Definition · Version attribute

A field marked @Version (int/Integer, long/Long, short/Short, or a timestamp type; prefer numbers, because clocks tie and drift). Hibernate increments it on every UPDATE of the entity and adds the old value to the WHERE clause: update product set stock=?, version=4 where id=? and version=3. If the row count is 0, someone else changed or deleted the row: Hibernate throws OptimisticLockException (in native API terms, StaleObjectStateException), and Spring translates it to ObjectOptimisticLockingFailureException. Never set the version yourself.

@Entity
public class Product {
    @Id private Long id;
    private int stock;
    @Version private long version;
    public long getVersion() { return version; }
    public void setStock(int stock) { this.stock = stock; }
}

public record UpdateStock(int stock, long version) { }           // the version round-trips via the client

@Transactional
public ProductDto updateStock(long id, UpdateStock req) {
    Product p = products.findById(id).orElseThrow();
    if (p.getVersion() != req.version())                          // client edited an older copy
        throw new ObjectOptimisticLockingFailureException(Product.class, id);
    p.setStock(req.stock());
    products.flush();                                             // UPDATE ... where version = ? now
    return ProductDto.from(p);                                    // carries the NEW version
}

The explicit check matters. In a stateless REST flow, the PUT request loads a fresh entity that already carries the latest version, so @Version on its own only catches races inside that request's own short window. The version the user actually saw must travel with the request, in a DTO field or as an ETag/If-Match header, and be compared. Retries: for automatic, commutative operations (incrementing a counter, consuming a stock unit), retry the whole transaction with a fresh read, a few attempts with jittered backoff, for example with Spring Retry's @Retryable(retryFor = ObjectOptimisticLockingFailureException.class) placed outside the @Transactional boundary. Never auto-retry a human's edit: that is the lost update again. Return 409 and let the user decide.

Versionless and explicit optimistic modes

@OptimisticLocking(type = OptimisticLockType.ALL) (Hibernate, requires @DynamicUpdate) puts every column's old value in the WHERE clause, which works for legacy tables without a version column. DIRTY includes only the changed columns, so two transactions that change different columns of the same row both succeed. That is useful for wide rows with independent fields, but think about whether your invariants span columns before using it.

// OPTIMISTIC: verify at commit that an entity you only READ has not changed
em.lock(exchangeRate, LockModeType.OPTIMISTIC);                   // select version ... at commit

// OPTIMISTIC_FORCE_INCREMENT: bump the parent's version although the parent itself didn't change
Order order = em.find(Order.class, orderId, LockModeType.OPTIMISTIC_FORCE_INCREMENT);
order.addItem(new OrderItem(3, productId, 1));                    // concurrent edits to other items now conflict

Force-increment is how you protect an aggregate invariant such as "order total ≤ credit limit". Two transactions that each add a different item never touch the same row, so neither conflicts. Bumping the root's version on every child change makes them collide on the order row.

jakarta.persistence.lock.timeout is in milliseconds. Support depends on the database: Hibernate maps 0 to NOWAIT and its SKIP_LOCKED constant to SKIP LOCKED, but on PostgreSQL a positive timeout cannot be expressed in the FOR UPDATE clause, so also set SET LOCAL lock_timeout = '3s' or a role-level default. SKIP LOCKED job queues: each worker claims up to n unlocked READY rows, marks them RUNNING in the same transaction and commits. Workers never block each other and never claim the same job, which makes this a solid queue for moderate throughput without a broker.

Algorithm · Avoiding deadlocks
  1. Transaction 1 locks row A and then wants B, while transaction 2 holds B and wants A. Postgres detects the cycle after deadlock_timeout (1 s by default) and aborts one with SQLSTATE 40P01.
  2. Lock in a global order: sort ids before locking, or lock them all at once with where id in (:ids) order by id for update.
  3. Keep locking transactions short, with no remote calls or user think-time inside them, and lock as late as possible.
  4. Treat deadlocks and serialization failures as retryable: retry the whole transaction a bounded number of times.

What breaks in production
  • @Version without round-tripping: every PUT loads the latest version, so conflicts are never detected and the lost update happens anyway.
  • Retry inside the transaction: catching the exception and retrying in the same persistence context reuses stale state and a transaction already marked rollback-only.
  • Pessimistic locks across remote calls: a row lock held while calling a payment provider queues every other checkout behind it.
  • Bulk updates skipping the version: update Product set stock = 0 leaves versions unchanged, and stale optimistic writers overwrite it (L237).

Auditing & Envers

40m video45m practice

There are two levels of audit. "Who created or last changed this row, and when" is four columns that Spring Data fills automatically. "What did this row look like on 3 March, and who changed which field" is full history, which Hibernate Envers records as a versioned copy of every change. Choose by the questions you will have to answer, and remember that history costs a write per change, forever.

Why audit trails matter

Compliance regimes (financial, health, privacy) ask who accessed or changed a record and when. Support needs to answer "why is my order cancelled?" without guessing. Disputes and chargebacks need the state as it was at a point in time. Debugging a bad deploy needs to know which rows it touched. An updated_at column tells you that something changed. Only history tells you what.

Spring Data JPA auditing

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)          // the JPA callbacks that fill the fields
public abstract class BaseAuditableEntity {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) protected Long id;
    @Version protected long version;

    @CreatedDate      @Column(nullable = false, updatable = false) private Instant createdAt;
    @LastModifiedDate @Column(nullable = false)                    private Instant updatedAt;
    @CreatedBy        @Column(nullable = false, updatable = false, length = 100) private String createdBy;
    @LastModifiedBy   @Column(nullable = false, length = 100)      private String updatedBy;

    public Instant getUpdatedAt() { return updatedAt; }
}

@Configuration
@EnableJpaAuditing(auditorAwareRef = "auditorAware", dateTimeProviderRef = "auditingDateTimeProvider")
class AuditingConfig {
    @Bean Clock clock() { return Clock.systemUTC(); }

    @Bean DateTimeProvider auditingDateTimeProvider(Clock clock) {
        return () -> Optional.of(Instant.now(clock));      // testable time source
    }

    @Bean AuditorAware<String> auditorAware() {
        return () -> Optional.ofNullable(SecurityContextHolder.getContext().getAuthentication())
            .filter(Authentication::isAuthenticated)
            .filter(a -> !(a instanceof AnonymousAuthenticationToken))
            .map(Authentication::getName)
            .or(() -> Optional.of("system"));               // batch jobs, migrations, schedulers
    }
}
How it works underneath

AuditingEntityListener is a plain JPA entity listener (L228). In @PrePersist it sets all four fields, and in @PreUpdate it sets the two "last modified" ones, asking AuditorAware for the user and DateTimeProvider for the time. Because it runs on JPA lifecycle events, it sees only changes that go through the persistence context: bulk JPQL updates, native SQL and other services skip it entirely. @PreUpdate fires only when the entity is dirty, so a no-op save doesn't touch updatedAt.

The reusable BaseAuditableEntity is the classic @MappedSuperclass (L236): every entity extends it and gets id, version and audit columns without any inheritance in the database. In tests, inject a fixed clock so that timestamps are deterministic. Use a new bean name with @Primary, because Boot disables bean-definition overriding by default:

The cost of Envers

Writes: every insert, update or delete of an audited entity adds one INSERT into its _aud table, plus one REVINFO row per transaction. Write volume on audited tables roughly doubles, and the extra inserts share the transaction's latency and locks. Storage: audit tables only grow, a full row copy per change, so a row updated 50 times stores 51 versions. Plan for partitioning by revision or date and for archiving, and index (id, rev) (the PK) plus rev for date queries. Reads: "state at revision" queries use correlated subqueries (max(rev) <= ?) that slow down as history grows. The validity audit strategy (set org.hibernate.envers.audit_strategy to Envers' ValidityAuditStrategy class) stores an end revision so that these become range lookups, which makes reads faster and writes a little slower.

Flyway: Versioned Schema Migrations

45m video50m practice

The schema is code: every change is a numbered, reviewed, immutable script, applied in order and recorded in the database itself. Flyway does that bookkeeping. Your job is to write each migration so that the version of the application already running keeps working while it runs.

Why ddl-auto=update is not a migration strategy

  • No ordering or history: you can't tell which changes a given database has received, or reproduce its schema from scratch.
  • No data migration: it can add a column but never fill it, split it, or move data between tables.
  • No review: DDL is derived from annotations at startup, and nobody reads it before it runs against production.
  • No rollback, and additive only: a rename becomes a new empty column, and nothing is ever dropped.
  • Silent divergence: each environment drifts according to which builds happened to start against it.

The production setup is migrations for the schema plus spring.jpa.hibernate.ddl-auto: validate, so that the app refuses to start if the entities and the migrated schema disagree (L224).

flyway_schema_history and the immutability rule

Definition · Schema history table

flyway_schema_history has one row per applied migration: installed_rank, version, description, type (SQL, JDBC), script, checksum (a CRC32 of the file), installed_by, installed_on, execution_time and success. On each run Flyway compares the files on the classpath with this table: it applies pending versions in order, re-applies repeatables whose checksum changed, and, with validateOnMigrate, fails if an applied file's checksum differs.

Never edit an applied migration. Other databases (production, colleagues' machines, CI) already ran the old version, and editing the file changes nothing there. You only get a checksum failure, or worse, environments that disagree for good. Fix forward with a new version. Commands: baseline marks an existing, unmanaged database as already at version N, so that Flyway starts from N+1 (baseline-on-migrate does this automatically for a non-empty schema with no history table; use it deliberately). repair removes failed entries and realigns checksums after an intentional change such as whitespace or comments. clean drops every object in the schema, which is useful in a disposable dev database and catastrophic anywhere else, so keep clean-disabled: true. outOfOrder allows applying V5.1 after V6 has run, which helps hotfix branches but makes ordering between environments non-deterministic, so use it sparingly.

Java-based migrations for data backfills

package db.migration;

import org.flywaydb.core.api.migration.BaseJavaMigration;
import org.flywaydb.core.api.migration.Context;

public class V7__Backfill_order_totals extends BaseJavaMigration {
    @Override public boolean canExecuteInTransaction() { return false; }   // each batch commits on its own

    @Override
    public void migrate(Context context) throws Exception {
        var conn = context.getConnection();
        long maxId;
        try (var st = conn.createStatement(); var rs = st.executeQuery("select coalesce(max(id), 0) from orders")) {
            rs.next(); maxId = rs.getLong(1);
        }
        try (var ps = conn.prepareStatement("""
                update orders o set total = coalesce((select sum(i.quantity * i.unit_price)
                                                      from order_item i where i.order_id = o.id), 0)
                where o.id > ? and o.id <= ? and o.total is null""")) {
            for (long from = 0; from < maxId; from += 5_000) {      // small batches: short row locks
                ps.setLong(1, from);
                ps.setLong(2, from + 5_000);
                ps.executeUpdate();
            }
        }
    }
}

Java migrations live in the db.migration package (or are registered as Spring beans implementing JavaMigration, which Boot passes to Flyway). They follow the same naming and versioning, with the checksum taken from the class. By default the whole migration is one transaction, so a backfill of 50M rows becomes one huge, long-locking transaction. Opting out of the transaction lets each batch commit. Very large backfills belong in an application job that can pause, resume and be throttled, not in the startup path.

Zero-downtime patterns

-- add a required column without locking the table for a full scan (PostgreSQL 12+)
alter table orders add column currency char(3);                                   -- V8: instant, nullable
-- ... deploy code that writes currency; backfill old rows in batches (V9 or a job) ...
alter table orders add constraint orders_currency_nn check (currency is not null) not valid;  -- V10
alter table orders validate constraint orders_currency_nn;    -- scans, but allows concurrent writes
alter table orders alter column currency set not null;        -- uses the validated CHECK: no scan
alter table orders drop constraint orders_currency_nn;

-- rename without downtime: add new, write both, copy, switch reads, drop old (never RENAME COLUMN live)
-- indexes on big tables: CREATE INDEX CONCURRENTLY, alone in its own migration (it cannot run in a transaction)
-- every DDL migration: SET lock_timeout = '5s' so it fails fast instead of queueing behind a long transaction

What breaks in production
  • Edited applied migration: production fails to start with "Validate failed: checksum mismatch" during a deploy. Never "fix" it with repair unless the edit really changes nothing.
  • Lock queue outage: an ALTER TABLE waits behind a long-running query, and every following query on the table waits behind the ALTER. Set lock_timeout.
  • Drop before the code stopped reading: the old app version, still serving traffic in a rolling deploy, crashes on the missing column.
  • clean enabled in a shared environment: one misconfigured job wipes the database.

Definition · Liquibase's model
  • Changelog: an ordered list of changesets in XML, YAML, JSON or formatted SQL, usually a master file that includes others.
  • Changeset: the unit of change, identified by id + author + changelog path and applied once.
  • DATABASECHANGELOG: one row per applied changeset with an MD5 checksum. As with Flyway, editing an applied changeset fails validation. DATABASECHANGELOGLOCK: a single-row lock that keeps two instances from migrating at once. A crashed deploy can leave it set; clear it with releaseLocks once you are sure nothing is running.
  • Preconditions guard a changeset (tableExists, sqlCheck), with onFail set to HALT, MARK_RAN or CONTINUE. Contexts and labels filter which changesets run (spring.liquibase.contexts, label expressions). Rollback blocks define the undo; it is generated automatically for some change types and must be written for raw SQL.
  • generateChangeLog reverse-engineers an existing database into a changelog, and diff compares two databases. Use them to bootstrap a legacy schema, and review the output.

StatelessSession is Hibernate's thin layer over JDBC: each insert/update/delete runs straight away, you load associations yourself, and there is no snapshot memory. That makes it right for ETL and backfills that must still use your mappings. Avoid merge (and Spring Data save() on an entity with an assigned id, which means merge) where loading and modifying would do: merge copies a whole detached graph and costs a SELECT per entity it doesn't find in the context. Connection handling: by default a resource-local transaction takes a pool connection at begin, to switch off autocommit. With Hikari's auto-commit: false plus provider_disables_autocommit: true, Hibernate waits until the first SQL statement, so work done before it (validation, remote calls) holds no connection. hibernate.connection.handling_mode controls acquisition and release; under Spring, connections are released at transaction end unless OSIV keeps them (L233).
