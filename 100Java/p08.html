Testing

Phase 8 makes testing an engineering discipline: JUnit 5 and AssertJ for fast, readable unit tests, Mockito and hand-written fakes for isolation, and Testcontainers, WireMock and REST Assured for integration tests against real dependencies. It builds on Phase 7's build and quality gates and on the Phase 5 job engine, and the database, JPA and Spring phases that follow use these tools in every lesson.

By the end of this phase you can

  • Pick the cheapest test level that can catch a given bug, write FIRST tests named as specifications, and diagnose and fix flaky tests.
  • Structure JUnit 5 suites with lifecycle hooks, @Nested contexts, tags, parameterized and dynamic tests, and write your own extension.
  • Write AssertJ assertions with collection extraction, recursive comparison, soft assertions and a custom domain assertion class.
  • Isolate a unit with Mockito (stubbing, verification, captors, spies, strict stubs) and recognise when a fake, a Clock or a new seam is the better design.
  • Run integration tests against real Postgres, Kafka, Redis and LocalStack with Testcontainers, wired into Spring with @ServiceConnection and shared across the suite.
  • Stub external HTTP APIs with WireMock, including latency, faults and stateful scenarios, and test your own API over HTTP with REST Assured.
  • Gate a build on JaCoCo branch coverage and a PIT mutation score, and explain why the mutation score is the more honest signal.

The Testing Pyramid, TDD & What Makes a Good Test

40m video40m practice

A test is worth the confidence it buys divided by what it costs to run and maintain. Good suites rely on fast tests of observable behaviour, use slower integration tests where the real risk is, and treat every flaky test as a bug.

Unit, integration, end-to-end

The levels differ in how much real machinery a test drives. Moving up the table buys confidence that the system works and costs speed, stability, and the ability to say where it broke.

LevelExercisesTypical timeA failure tells youMain cost
Unitone class or a small cluster; slow collaborators replacedmillisecondsexactly which rule brokeover-mocked tests that pin the implementation
Integrationyour code plus a real database, broker, HTTP client or Spring context100 ms to seconds (after container startup)wiring, SQL, mapping, serialization or config is wrongneeds Docker; slower feedback
End-to-endthe deployed system through its public API or UIseconds to minutesa user journey is broken, somewhereslow, flaky, hard to localise, expensive environments

Khorikov names four properties no single test maximises at once: protection against regressions, resistance to refactoring, fast feedback, and maintainability.

Pyramid, trophy, ice-cream cone

The shapes mostly disagree about the middle layer. In a domain-heavy service (pricing rules, schedulers, state machines) the bugs are in logic, so unit tests should dominate. In a CRUD-heavy Spring service the bugs are in SQL, mappings, transactions and JSON, and a mocked repository can't catch any of them, so integration tests with real Postgres (L194) earn more. The rule that survives every shape: push each test down to the lowest level that can still catch the bug.

What a good test looks like

Definition · FIRST
  • Fast: milliseconds, so the suite runs on every change, not once a day.
  • Independent: no test relies on another's side effects or on execution order.
  • Repeatable: same result on any machine, in any time zone, offline, on the hundredth run.
  • Self-validating: pass or fail by assertion; nobody reads log output to decide.
  • Timely: written just before, or together with, the code it specifies.

Test behaviour, not implementation. Assert on what a caller can observe: the return value, state visible through the public API, or an interaction that crosses a boundary you own (an event was published, an email was queued). A test that calls a private helper through reflection, or verifies the exact sequence of internal calls, fails when you refactor and passes when the behaviour is wrong. That is a false alarm and a missed bug at once.

One logical assertion per test. A test checks one behaviour. Several assert statements are fine when together they describe one outcome ("rejected and nothing reserved"). If the name needs an "and" between two unrelated rules, split the test. When one outcome has several facets, report them all with assertAll (L185) or soft assertions (L189) so the first failure doesn't hide the rest.

Arrange–Act–Assert, names, and BDD vocabulary

class OrderServiceTest {

    private final InMemoryInventory inventory = new InMemoryInventory();
    private final OrderService service = new OrderService(inventory);

    @Test
    void shouldRejectOrderWhenInventoryInsufficient() {
        // Arrange (Given): two units on the shelf
        inventory.stock("SKU-1", 2);

        // Act (When): one call, the behaviour under test
        OrderResult result = service.place(new OrderRequest("SKU-1", 3));

        // Assert (Then): one logical outcome, two facets
        assertEquals(new OrderResult.Rejected("insufficient stock for SKU-1"), result);
        assertEquals(2, inventory.available("SKU-1"));
    }
}

Arrange builds the fixture, Act makes exactly one call, Assert checks the outcome. If Act needs several lines, the API is probably awkward; if Arrange runs to 30 lines, reach for a test data builder (L193). Given–When–Then is the same structure in BDD words.

Names are the documentation a failing build shows you, so state the rule. Common conventions: shouldRejectOrderWhenInventoryInsufficient (should + outcome + condition), place_insufficientStock_rejectsOrder (method, state, expectation), snake-case sentences such as rejects_order_when_stock_is_insufficient, or a @DisplayName (L186). Names like test1 or testPlace say nothing when they go red.

BDD (Dan North, 2006) recasts tests as specifications of behaviour: "should" instead of "test", Given a context, When an event, Then an outcome. Scenarios group into features, ideally phrased in the domain's own language; teams that want business readers write them in Gherkin and run them with Cucumber. In plain JUnit, BDD is a naming and structuring habit, and Mockito's BDDMockito offers matching given(...).willReturn(...) and then(mock).should() aliases (L191).

Red, green, refactor

Algorithm · TDD loop
  1. Red. Write the smallest test for the next behaviour. Run it and watch it fail, on an assertion, for the reason you expect.
  2. Green. Write the simplest code that passes, even a hard-coded value. Don't add behaviour no test asks for.
  3. Refactor. With everything green, remove duplication and improve names in both code and tests, re-running after each step.
Worked example · shipping cost

Rules: orders under 50.00 pay a flat 4.99; orders of 50.00 or more ship free; a negative subtotal is a bug. Amounts are in cents, so plain long arithmetic is exact.

class ShippingTest {
    private final Shipping shipping = new Shipping();

    @Test void chargesFlatFeeBelowThreshold() { assertEquals(499, shipping.costCents(1_000)); }
    @Test void isFreeAtThreshold()            { assertEquals(0, shipping.costCents(5_000)); }
    @Test void chargesFeeOneCentBelow()       { assertEquals(499, shipping.costCents(4_999)); }
    @Test void rejectsNegativeSubtotal() {
        assertThrows(IllegalArgumentException.class, () -> shipping.costCents(-1));
    }
}

final class Shipping {                         // after the refactor step
    static final long FREE_FROM_CENTS = 5_000;
    static final long FLAT_FEE_CENTS = 499;

    long costCents(long subtotalCents) {
        if (subtotalCents < 0) throw new IllegalArgumentException("negative subtotal");
        return subtotalCents >= FREE_FROM_CENTS ? 0 : FLAT_FEE_CENTS;
    }
}

A test that passes the moment you write it (cycle 3) adds no design pressure but may still earn its place as a boundary check. A test you have never seen fail might be testing nothing at all.

Flaky tests: causes and cures

A flaky test passes and fails on the same code. Each one teaches the team to ignore red builds, so fix or quarantine it as soon as it is found.

CauseTypical symptomCure
Timefails at midnight, at month end, in UTC on CI; Thread.sleep too short on a slow agentinject a Clock and fix it in tests; poll with Awaitility instead of sleeping (L198)
Orderingpasses in the full suite, fails when run alone (or the reverse)every test builds its own fixture; run with a random method order to expose it (L186)
Shared statestatic caches, singletons, system properties, one reused database rowfresh instances per test, unique ids, rollback or truncate between tests
Concurrencyasserting before async work finishes; 1-in-50 failures that get worse under loadlatches or Future.get with timeouts, Awaitility, shut executors down
Networkthird-party timeouts, rate limits, DNS, fixed ports already in useWireMock (L196); Testcontainers on random ports (L194)

Quieter sources: the unspecified iteration order of HashMap, HashSet and Set.of (randomised per JVM run for the immutable collections), and the machine's default locale.

What breaks in production
  • Retry until green. Surefire's rerunFailingTestsCount is a detector, not a fix. A test that fails one run in twenty is often a real race that production will hit at scale.
  • All mocks, no boundaries. Hundreds of unit tests pass while the SQL is wrong, the JSON field is misspelled, and the transaction never commits. Coverage looks great; confidence is low.
  • Implementation-locked suites. When every refactor breaks 40 tests that verify internal calls, people stop refactoring, or start deleting tests.

Practice · 40 min

  1. Write OrderRequest, OrderResult (a sealed interface with Accepted and Rejected records), InMemoryInventory and OrderService test-first: the test above, then a matching shouldReserveStockWhenInventorySufficient. Commit after each red, green and refactor step.
  2. Redo the shipping kata from an empty file without looking. Then add an express rule (999 regardless of subtotal) in one more cycle.
  3. Rename five tests from your Day 80 repository (L80) into should…When… sentences. For each, ask: would this name still be true after a rewrite of the internals?
  4. Write a deliberately flaky test that depends on LocalTime.now().getSecond() % 2. Fix it by injecting a Clock, and name the FIRST letter it violated.
  5. Classify the tests of the Day 152 job engine (L152) by level and sketch the suite's shape. Which risks have no test at the right level?

JUnit 5 Architecture & Your First Tests

40m video45m practice

JUnit 5 is three things: a Platform that launches tests, Jupiter, the programming model you write against, and Vintage, an engine that runs old JUnit 4 tests. IDEs and build tools only ever talk to the Platform; once you see that, dependency setup, build configuration and migration from JUnit 4 all follow.

Platform, Jupiter, Vintage

Definition · the three parts
  • JUnit Platform: the foundation for running any test framework on the JVM. It defines the TestEngine SPI and the Launcher API that IDEs, Maven Surefire/Failsafe and Gradle call to discover tests, execute them, and receive events for reports.
  • JUnit Jupiter: the annotations, assertions and extension model you write tests with (junit-jupiter-api), plus the engine that runs them (junit-jupiter-engine).
  • JUnit Vintage: a TestEngine that runs JUnit 3 and 4 tests on the Platform, so old and new tests share one build.

In the 5.x line the Platform is versioned 1.x and Jupiter and Vintage 5.x (Platform 1.12.2 ships with Jupiter 5.12.2), which is one reason to manage versions with the junit-bom. JUnit 6, released in 2025, puts all three on one version number, requires Java 17 and deprecates Vintage; the architecture and annotations in this phase carry over unchanged.

Dependencies

  • Aggregate: junit-jupiter pulls in junit-jupiter-api, junit-jupiter-params and junit-jupiter-engine. One line, the usual choice.
  • Split: -api (and -params) on the test compile classpath, -engine at test runtime only. Your code can then compile against the API alone and can't reach engine internals.
  • Spring Boot: spring-boot-starter-test bundles JUnit Jupiter, Mockito with its JUnit 5 extension, AssertJ, Hamcrest, Awaitility, JSONassert, JsonPath, XMLUnit, Spring Test and Spring Boot Test, all versioned by the Boot BOM (L175). Don't add versions; override one through its property (for example junit-jupiter.version). Since Boot 2.4 the starter no longer includes the Vintage engine.

Your first tests, and the visibility rules

final class Slugs {                       // src/main/java/com/acme/text/Slugs.java
    private Slugs() {}

    static String of(String title) {
        return title.strip()
                .toLowerCase(Locale.ROOT)
                .replaceAll("[^a-z0-9]+", "-")
                .replaceAll("(^-|-$)", "");
    }
}

class SlugsTest {                         // src/test/java/com/acme/text/SlugsTest.java

    @Test
    void lowercasesAndJoinsWordsWithHyphens() {
        assertEquals("hello-junit-5", Slugs.of("Hello JUnit 5"));
    }

    @Test
    void collapsesPunctuationAndTrimsEdges() {
        assertEquals("java-21-records", Slugs.of("  Java 21: records!  "));
    }
}
Rules Jupiter enforces
  • Test classes, test methods and lifecycle methods need not be public, but must not be private. The JUnit guide recommends omitting public unless a subclass in another package needs it.
  • A test class is any top-level, static nested or @Nested class with at least one test method. It must not be abstract and must have exactly one constructor.
  • A @Test method must not be static, private or abstract, and must return void. A method that breaks these rules is not run; recent versions report it as a discovery issue instead of skipping it silently.
  • Jupiter creates a new instance of the class for every test method (L186), so instance fields are fresh per test.

Running. In the IDE, the gutter icon runs a class, one method, or a @Nested group, through the IDE's own Platform launcher. With Maven, mvn test runs everything, mvn test -Dtest=SlugsTest one class and -Dtest='SlugsTest#collapses*' matching methods; reports land in target/surefire-reports. With Gradle, ./gradlew test --tests 'com.acme.text.SlugsTest', with an HTML report under build/reports/tests/test.

Source layout and naming

Tests live in src/test/java in the same package as the code under test, so they can reach package-private members; fixtures and test config go in src/test/resources. The suffix decides which plugin runs a class:

PluginDefault includesBound to phasesUse for
Surefire**/Test*.java, **/*Test.java, **/*Tests.java, **/*TestCase.javatestfast unit tests
Failsafe**/IT*.java, **/*IT.java, **/*ITCase.javaintegration-test, then verifycontainer and HTTP tests

Failsafe records failures during integration-test and only fails the build in verify, so post-integration-test teardown still runs. mvn test gives quick feedback; mvn verify runs both. Failsafe needs an explicit <execution> with the integration-test and verify goals. In Gradle, use a separate test suite (JVM Test Suite plugin) for the integration tests.

Why runners became extensions. A JUnit 4 class could have exactly one @RunWith, so Mockito and Spring runners couldn't be combined without rule workarounds. Jupiter extensions compose: one class can carry Mockito, Spring and your own timing extension at once.

Running both engines during migration. Add org.junit.vintage:junit-vintage-engine (test scope, with junit:junit 4.13.x) next to junit-jupiter. The Platform discovers both kinds of tests in one mvn test. Write every new test in Jupiter, convert old classes package by package (OpenRewrite's JUnit 4 to 5 migration recipe automates most of the mechanical rewrite), and use junit-jupiter-migrationsupport if a few rules must keep working for a while. When nothing imports org.junit.Test any more, ban the import with ArchUnit or Checkstyle (L182) and remove Vintage.

What breaks in production
  • Green build, zero tests. Surefire older than 2.22.0, Gradle without useJUnitPlatform(), a class named OrderServiceSpec that matches no include pattern, or JUnit 4 @Test imports without the Vintage engine. Read the test count in the log, and set Surefire's failIfNoTests where it helps.
  • Mixed annotations in one class. A Jupiter test class with a JUnit 4 @Before never runs the setup: Jupiter doesn't know that annotation. The test fails with a NullPointerException that looks like a real bug.
  • The silent upgrade. Moving a project to Spring Boot 2.4 or later removed Vintage from the starter; JUnit 4 tests stopped running and nobody noticed for months.
  • Version skew. Jupiter API and engine (or Platform) from different releases, added without the BOM, can fail at launch with linkage errors. Let one BOM own every JUnit version.

Practice · 45 min

  1. Create a Maven project with the BOM and junit-jupiter, write Slugs and four tests (add empty and all-punctuation inputs), and run them from the IDE, with mvn test, and one method at a time with -Dtest. Open the XML report.
  2. Rename SlugsTest to SlugsSpec and run mvn test. Note the test count, then fix it with a Surefire <include> instead of renaming.
  3. Add SlugsIT and the Failsafe plugin. Confirm mvn test skips it and mvn verify runs it.
  4. Add a JUnit 4 test with junit:junit 4.13.2. Run without and then with junit-vintage-engine and compare the counts. Then convert it with the mapping table, including a TemporaryFolder rule to @TempDir.
  5. Repeat item 1 in Gradle, then delete useJUnitPlatform() and record exactly what your Gradle version does.

Assertions, Assumptions, Exceptions & Timeouts

40m video40m practice

An assertion has two jobs: decide pass or fail, and, when it fails, tell you what went wrong without a debugger. Jupiter's Assertions class covers both, as long as you pass arguments in the right order, group related checks, and know which assertions run your code on another thread.

Equality, identity and collections

Definition · test outcomes

A test is successful if it returns normally, failed if it throws, and aborted (shown as skipped) if it throws TestAbortedException, which is what a failed assumption does. Assertions in org.junit.jupiter.api.Assertions fail by throwing org.opentest4j.AssertionFailedError; Surefire counts those as failures and any other exception as an error.

class AssertionTourTest {

    record Money(long cents, String currency) {}

    @Test
    void equality() {
        Money total = new Money(1_250, "EUR");
        assertEquals(new Money(1_250, "EUR"), total);     // expected first, actual second
        assertNotEquals(new Money(1_250, "USD"), total);
        assertEquals(0.3, 0.1 + 0.2, 1e-9);                // doubles: always give a delta
    }

    @Test
    void lazyMessage() {
        List<String> skus = List.of("A-1", "B-2");
        assertTrue(skus.stream().allMatch(s -> s.matches("[A-Z]-\\d")),
                () -> "malformed SKU in " + skus);        // built only if the check fails
    }

    @Test
    void identityArraysIterablesLines() {
        assertNull(System.getProperty("no.such.property"));
        assertNotNull(System.getProperty("java.version"));
        assertSame(Currency.getInstance("EUR"), Currency.getInstance("EUR"));   // one instance per code
        assertArrayEquals(new int[] {1, 2, 3}, new int[] {1, 2, 3});
        assertIterableEquals(List.of(1, 2, 3), new ArrayDeque<>(List.of(1, 2, 3)));
        assertLinesMatch(
                List.of("Started job \\d+", ">> workers polling >>", "Finished in \\d+ ms"),
                List.of("Started job 42", "worker-1 polling", "worker-2 polling", "Finished in 17 ms"));
    }
}
  • Argument order. assertEquals(expected, actual). The message is built from that order (expected: <1250> but was: <1200>), so swapped arguments produce a message that lies. The optional message goes last (in JUnit 4 it was first).
  • Lazy messages. Each assertion also accepts a Supplier<String>, evaluated only on failure: use it when building the message costs anything.
  • Identity and arrays. assertSame checks ==. Arrays don't override equals, so assertEquals on arrays compares references; assertArrayEquals compares elements (deeply) and reports the first differing index.
  • Iterables. assertIterableEquals walks both in iteration order, ignoring the concrete types. Not for a HashSet, whose order is unspecified.
  • Lines. assertLinesMatch matches each expected line by equality or as a regex; a >> … >> line fast-forwards over any number of actual lines (>> 2 >> skips exactly two). Ideal for log or CLI output.

Grouped assertions with assertAll

A plain sequence of assertions stops at the first failure, so you fix one field, rerun, and discover the next. assertAll runs every executable, collects all failures, and throws one MultipleFailuresError listing them.

class AddressParserTest {

    @Test
    void parsesEveryPart() {
        Address a = AddressParser.parse("221B Baker Street, London NW1 6XE, UK");

        assertAll("address",
                () -> assertEquals("221B Baker Street", a.street()),
                () -> assertEquals("London", a.city()),
                () -> assertEquals("NW1 6XE", a.postcode()),
                () -> assertEquals("UK", a.country()));
    }
}
org.opentest4j.MultipleFailuresError: address (2 failures)
	org.opentest4j.AssertionFailedError: expected: <London> but was: <London NW1 6XE>
	org.opentest4j.AssertionFailedError: expected: <NW1 6XE> but was: <null>

Inside one executable, assertions still run in sequence, which gives you dependent groups: () -> { assertNotNull(a); assertAll(...); } skips the inner checks when a is null instead of piling up NullPointerExceptions. Groups can nest as deep as the object graph.

Exceptions, and when fail() is legitimate

class ExceptionAssertionsTest {

    static final class InsufficientFundsException extends RuntimeException {
        private final long shortfallCents;
        InsufficientFundsException(long shortfallCents) {
            super("short by " + shortfallCents + " cents");
            this.shortfallCents = shortfallCents;
        }
        long shortfallCents() { return shortfallCents; }
    }

    static long withdraw(long balance, long amount) {
        if (amount > balance) throw new InsufficientFundsException(amount - balance);
        return balance - amount;
    }

    static String loadConfig(Path p) {
        try { return Files.readString(p); }
        catch (IOException e) { throw new UncheckedIOException(e); }
    }

    @Test
    void reportsTheShortfall() {
        var ex = assertThrows(InsufficientFundsException.class, () -> withdraw(1_000, 1_500));
        assertEquals("short by 500 cents", ex.getMessage());
        assertEquals(500, ex.shortfallCents());              // custom field, typed: no cast
    }

    @Test
    void wrapsTheIoCause() {
        var ex = assertThrows(UncheckedIOException.class, () -> loadConfig(Path.of("missing.yml")));
        assertInstanceOf(NoSuchFileException.class, ex.getCause());
    }

    @Test
    void exactBalanceIsFine() {
        long left = assertDoesNotThrow(() -> withdraw(1_000, 1_000));
        assertEquals(0, left);
    }
}

assertThrows returns the exception, typed, so you can check message, cause and custom fields. It accepts subclasses; assertThrowsExactly doesn't. Keep the lambda to the one call that should throw, or setup code throwing the same type makes the test pass for the wrong reason. assertDoesNotThrow returns the supplier's value and documents intent, though any unexpected exception fails a test anyway.

fail(message) is legitimate where reaching a line is the bug: a callback that must never run (listener = e -> fail("unexpected " + e)), or an Optional that must be present. fail is generic, so it works as an expression: repo.findById(id).orElseGet(() -> fail("order missing")). It is not a substitute for assertThrows (the old try { call(); fail(); } catch idiom), for assertTrue, or for @Disabled("reason") on an unwritten test.

Timeouts: same thread or preemptive

class TimeoutTest {

    @Test
    void sumsWithinBudget() {                 // same thread; result is returned
        long sum = assertTimeout(Duration.ofMillis(500),
                () -> LongStream.rangeClosed(1, 1_000_000).sum());
        assertEquals(500_000_500_000L, sum);
    }

    @Test
    void neverHangsOnTake() throws InterruptedException {
        var queue = new LinkedBlockingQueue<String>();
        queue.put("job-1");
        String job = assertTimeoutPreemptively(Duration.ofSeconds(1), queue::take);
        assertEquals("job-1", job);           // an empty queue would fail at 1 s, not hang
    }

    @Test
    @Timeout(value = 2, unit = TimeUnit.SECONDS)   // whole method; interrupts the test thread
    void wholeTestBudget() throws InterruptedException {
        Thread.sleep(10);
    }
}

The preemptive variant has a catch: anything in a ThreadLocal is missing on the worker thread, including Spring's test-managed transaction (the work is not rolled back), the security context and the logging MDC. @Timeout budgets a whole method by interrupting the test thread when time is up; junit.jupiter.execution.timeout.default sets a suite-wide ceiling.

Assumptions: abort instead of fail

class AssumptionTest {

    @Test
    void followsSymlinks(@TempDir Path dir) throws IOException {
        assumeFalse(System.getProperty("os.name").startsWith("Windows"),
                "symlinks need extra privileges on Windows");
        Path target = Files.writeString(dir.resolve("real.txt"), "hi");
        Path link = Files.createSymbolicLink(dir.resolve("link.txt"), target);
        assertEquals("hi", Files.readString(link));
    }

    @Test
    void stricterOnCi() {
        String report = "id,total\n1,12.50\n";
        assumingThat("true".equals(System.getenv("CI")),
                () -> assertTrue(report.length() < 1_024, "CI artefacts stay small"));
        assertTrue(report.startsWith("id,"));    // runs everywhere
    }
}

A failed assumeTrue/assumeFalse aborts the test: it doesn't apply here, which is different from being broken. assumingThat(condition, executable) makes only the executable conditional; the rest of the test always runs. Use assumptions for runtime facts (Docker reachable, a licence key present); prefer the @EnabledOn… annotations of L186 when the condition can be declared.

What breaks in production
  • Swapped arguments. "expected: <null> but was: <42>" when the code actually returned null: the message sends whoever is debugging the wrong way.
  • Preemptive timeouts around transactional code. The work runs outside the test's transaction, isn't rolled back, and leaks rows into later tests. The JUnit guide warns about exactly this.
  • Assumptions that abort half the suite. A missing CI variable turns 300 tests into "skipped" and the build stays green. Track the aborted count and fail the build when it jumps.
  • Over-wide exception lambdas. () -> { var o = new Order(null); o.submit(); } passes when the constructor throws, not the method under test.

Lifecycle, @Nested, Display Names, Ordering & Tags

40m video40m practice

Jupiter builds a fresh test-class instance for every test method, and nearly everything in this lesson either works with that default (setup hooks, nested contexts, readable names) or carefully opts out of it (shared setup, explicit ordering). Selecting which tests run (tags, conditions, repetitions) is a separate layer on top.

Lifecycle hooks and the per-method instance

Definition · test instance lifecycle

PER_METHOD (the default): for each test method Jupiter creates a new instance of the class, runs @BeforeEach methods, the test, then @AfterEach. @BeforeAll/@AfterAll run once per class and therefore must be static: there is no instance yet. PER_CLASS, enabled with @TestInstance(Lifecycle.PER_CLASS), creates one instance for all methods of the class, so @BeforeAll may be an instance method.

The default protects you: a test that forgets to reset a field can't break the next one, so tests stay independent (the I of FIRST, L183) and can run in any order or in parallel. Choose PER_CLASS deliberately, for an expensive, effectively immutable fixture, or when a @Nested class needs @BeforeAll. Setting it globally (junit.jupiter.testinstance.lifecycle.default = per_class) trades that safety away for every class. With inheritance, superclass @BeforeEach methods run before the subclass's, and @AfterEach in reverse.

@TestInstance(TestInstance.Lifecycle.PER_CLASS)
class CountryCodesTest {

    private Map<String, String> isoToName;          // loaded once, never mutated

    @BeforeAll
    void load() {                                    // non-static: allowed under PER_CLASS
        isoToName = Arrays.stream(Locale.getISOCountries())
                .collect(Collectors.toUnmodifiableMap(c -> c,
                        c -> Locale.of("", c).getDisplayCountry(Locale.ENGLISH)));
    }

    @Test void knowsGermany() { assertEquals("Germany", isoToName.get("DE")); }
    @Test void hasNoLowercaseKeys() {
        assertTrue(isoToName.keySet().stream().allMatch(k -> k.equals(k.toUpperCase(Locale.ROOT))));
    }
}

@Nested contexts and display names

A @Nested class is a non-static inner class whose tests share the outer class's setup. The outer @BeforeEach runs first, then the inner one, so each level adds one fact to the context. The test tree then reads like a specification.

@DisplayName("Shopping cart")
class CartTest {

    private Cart cart;

    @BeforeEach
    void newCart() { cart = new Cart(); }

    @Nested
    @DisplayNameGeneration(DisplayNameGenerator.ReplaceUnderscores.class)
    class WhenCartIsEmpty {
        @Test void total_is_zero()     { assertEquals(0, cart.totalCents()); }
        @Test void checkout_is_refused() { assertThrows(IllegalStateException.class, cart::checkout); }
    }

    @Nested
    @DisplayName("when the user is premium")
    class WhenUserIsPremium {
        @BeforeEach
        void premiumWithOneBook() {                  // runs after newCart()
            cart.setPremium(true);
            cart.add("BOOK", 2_000);
        }

        @Test
        @DisplayName("10% comes off the total")
        void discount() { assertEquals(1_800, cart.totalCents()); }
    }
}
Shopping cart
├─ WhenCartIsEmpty
│  ├─ total is zero              ✔
│  └─ checkout is refused        ✔
└─ when the user is premium
   └─ 10% comes off the total    ✔

@DisplayName sets one name (any characters, including spaces and emoji, though the latter don't help anyone). @DisplayNameGeneration derives names from method names: ReplaceUnderscores turns total_is_zero into "total is zero", Simple drops the trailing (), and IndicativeSentences joins the class and method names into a sentence. Set a project-wide generator with junit.jupiter.displayname.generator.default in junit-platform.properties. The generator only renames what has no explicit @DisplayName; the nested class itself keeps its class name here, as the tree shows.

Ordering, and why it is usually a smell

Without configuration, Jupiter orders methods with an algorithm that is "deterministic but intentionally nonobvious" (the user guide's words): stable from run to run, but not the source order. You can pick an orderer:

@TestMethodOrder(MethodOrderer.OrderAnnotation.class)
class AccountJourneyTest {
    private static final List<String> log = new ArrayList<>();   // shared on purpose

    @Test @Order(1) void opens()    { log.add("open"); }
    @Test @Order(2) void deposits() { log.add("deposit"); assertEquals(List.of("open", "deposit"), log); }
}

Other orderers are MethodName, DisplayName and Random; @TestClassOrder does the same for classes. The second test above passes only because the first ran: run it alone and it fails. That coupling is the smell. If steps really form one scenario, make it one test, or a @Nested chain where each level's setup performs the previous step. The useful ordering is the opposite one: set junit.jupiter.testmethod.order.default = org.junit.jupiter.api.MethodOrderer$Random on CI to expose hidden dependencies, and log the seed (junit.jupiter.execution.order.random.seed) so a failure can be reproduced.

Each annotation has a Disabled… twin, and @EnabledIf("methodName") takes a custom boolean method. What breaks in production
  • Global PER_CLASS to save setup time. Mutable fields now survive between tests; the suite passes in the default order and fails under random order or parallel execution.
  • A tag typo. @Tag("intergration") matches neither the fast job nor the integration job, so the test never runs anywhere. Composed annotations or constants make the typo a compile error.
  • Excluded with no job to include it. excludedGroups=slow on the PR build is fine only if a nightly job runs groups=slow. Check that every test runs in at least one pipeline.
  • Permanent @Disabled. A disabled test with no ticket is a deleted test that still looks like coverage. Count skipped tests in the build summary.
  • Conditions that hide failures. A test enabled only when CI=true is skipped on CI too if the runner doesn't set the variable.

Parameterized Tests & Argument Sources

40m video45m practice

When tests differ only in their data, write the logic once and put the cases in a table. A @ParameterizedTest takes rows from a source, converts each value to the parameter's type, and runs one named invocation per row, so the table is the specification.

How a parameterized test runs

Parameterized tests live in junit-jupiter-params, which the junit-jupiter aggregate already includes. Replace @Test with @ParameterizedTest and add at least one source. A source that yields zero rows fails the test by default rather than passing vacuously.

Simple sources: values, nulls, empties, enums

class SkuTest {

    static boolean isValid(String sku) {
        return sku != null && sku.matches("[A-Z]{2}-\\d{4}");
    }

    @ParameterizedTest
    @ValueSource(strings = {"AB-1234", "ZZ-0001", "QX-9999"})
    void acceptsWellFormed(String sku) { assertTrue(isValid(sku)); }

    @ParameterizedTest
    @NullAndEmptySource                              // adds null and ""
    @ValueSource(strings = {"  ", "ab-1234", "AB1234", "AB-12345"})
    void rejectsMalformed(String sku) { assertFalse(isValid(sku)); }

    enum Status {
        NEW, PAID, SHIPPED, DELIVERED, CANCELLED, REFUNDED;
        boolean isTerminal() { return this == DELIVERED || this == CANCELLED || this == REFUNDED; }
    }

    @ParameterizedTest
    @EnumSource(value = Status.class, names = {"DELIVERED", "CANCELLED", "REFUNDED"})
    void terminal(Status s) { assertTrue(s.isTerminal()); }

    @ParameterizedTest
    @EnumSource(value = Status.class, mode = EnumSource.Mode.EXCLUDE,
                names = {"DELIVERED", "CANCELLED", "REFUNDED"})
    void active(Status s) { assertFalse(s.isTerminal()); }

    @ParameterizedTest
    @EnumSource(value = Status.class, mode = EnumSource.Mode.MATCH_ANY, names = ".*ED$")
    void pastTense(Status s) { assertTrue(s.ordinal() >= Status.SHIPPED.ordinal()); }
}
  • @ValueSource supplies one argument per invocation from a literal array (ints, longs, doubles, strings, booleans, classes…).
  • @NullSource, @EmptySource and @NullAndEmptySource add the boundary cases that hand-written lists forget. "Empty" means "", an empty collection, map or array, depending on the parameter type.
  • @EnumSource runs every constant by default. names with mode selects a subset: INCLUDE (the default), EXCLUDE, or regex matching with MATCH_ANY/MATCH_ALL. Adding a constant later automatically adds a case, which is often the point.

Tables: @CsvSource and @CsvFileSource

Worked example · twelve tests become one

A discount rule: STANDARD pays full price, GOLD gets 10% off, PLATINUM 20%, rounded to cents; coupon SAVE5 then takes 5.00 off; the total never drops below 0.00. The suite had twelve methods like goldWithCouponGetsFifteenOff(), each a copy of the last with four values changed. As one table:

class DiscountTest {

    @ParameterizedTest(name = "{0} on {1} with coupon {2} pays {3}")
    @CsvSource(nullValues = "N/A", textBlock = """
        # tier    subtotal  coupon  expected
        STANDARD, 40.00,    N/A,    40.00
        STANDARD, 40.00,    SAVE5,  35.00
        STANDARD, 0.00,     N/A,    0.00
        STANDARD, 3.00,     SAVE5,  0.00
        GOLD,     100.00,   N/A,    90.00
        GOLD,     100.00,   SAVE5,  85.00
        GOLD,     0.01,     N/A,    0.01
        GOLD,     4.00,     SAVE5,  0.00

Each line is one invocation; Tier and BigDecimal are converted from text; lines starting with # are comments; nullValues = "N/A" turns that marker into null. A new edge case is now one line, and a reviewer can check the rules by reading the table. The equality works because both sides have scale 2; BigDecimal.equals treats 90.0 and 90.00 as different (AssertJ's isEqualByComparingTo in L189 doesn't).

  • Quoting. Values are separated by , (change with delimiter or delimiterString). Wrap a value containing the delimiter in single quotes: 'Smith, John'. An unquoted empty value is null; a quoted empty '' is "" (or whatever emptyValue says).
  • Headers. useHeadersInDisplayName = true treats the first row as column names and shows [1] tier = GOLD, subtotal = 100.00.
  • Files. @CsvFileSource(resources = "/discounts.csv", numLinesToSkip = 1) reads from the test classpath (files = … for the file system). Files default to " as the quote character. Move tables to files once they outgrow the screen or are maintained by someone who doesn't write Java.

Complex objects: @MethodSource and @ArgumentsSource

class CartTotalTest {

    record Line(String sku, int qty, long unitCents) {}

    static long total(List<Line> lines) {
        return lines.stream().mapToLong(l -> l.qty() * l.unitCents()).sum();
    }

    static Stream<Arguments> carts() {                         // static, unless PER_CLASS
        return Stream.of(
                Arguments.of(Named.of("empty cart", List.of()), 0L),
                Arguments.of(Named.of("one line", List.of(new Line("A", 2, 500))), 1_000L),
                Arguments.of(Named.of("two lines",
                        List.of(new Line("A", 1, 500), new Line("B", 3, 250))), 1_250L));
    }

    @ParameterizedTest(name = "{0} totals {1}")
    @MethodSource("carts")
    void totals(List<Line> lines, long expected) { assertEquals(expected, total(lines)); }

    static class LeapYears implements ArgumentsProvider {
        @Override
        public Stream<? extends Arguments> provideArguments(ExtensionContext context) {
            return IntStream.rangeClosed(1896, 2024).filter(Year::isLeap).mapToObj(Arguments::of);
        }
    }

    @ParameterizedTest
    @ArgumentsSource(LeapYears.class)
    void februaryHas29Days(int year) { assertEquals(29, YearMonth.of(year, 2).lengthOfMonth()); }
}

@MethodSource names a factory returning a Stream, Iterable or array of Arguments; with no name it looks for a method with the test's own name, and "com.acme.Fixtures#orders" reaches a shared fixture class. Named.of gives an argument a readable name for the report without changing the value passed in. Use @ArgumentsSource when the generation logic deserves a reusable, named class: every leap year, every file in a directory, every row of a fixture database.

Conversion, aggregation and display names

Definition · argument conversion

Implicit: a String becomes a primitive or wrapper, enum, BigDecimal, UUID, Locale, Currency, Path, URI, or a java.time type ("2025-01-31" to LocalDate); as a fallback JUnit uses a static factory method or a single-String constructor on the target type. Numbers widen (ints to a long parameter). Explicit: @ConvertWith(MyConverter.class) on the parameter, or @JavaTimeConversionPattern("dd.MM.yyyy") for dates.

class ConversionTest {

    static class Cents extends TypedArgumentConverter<String, Long> {
        Cents() { super(String.class, Long.class); }
        @Override protected Long convert(String s) {
            return new BigDecimal(s).movePointRight(2).longValueExact();
        }
    }

    @ParameterizedTest
    @CsvSource({"12.50, 1250", "0.99, 99", "100, 10000"})
    void parsesMoney(@ConvertWith(Cents.class) Long cents, long expected) {
        assertEquals(expected, cents);
    }

    record Customer(String name, int age, boolean premium) {}

    static class CustomerAggregator implements ArgumentsAggregator {
        @Override
        public Customer aggregateArguments(ArgumentsAccessor a, ParameterContext ctx) {
            return new Customer(a.getString(0), a.getInteger(1), a.getBoolean(2));
        }
    }

    @ParameterizedTest
    @CsvSource({"Ada, 36, true", "Linus, 17, false"})
    void premiumNeedsAdult(@AggregateWith(CustomerAggregator.class) Customer c) {
        assertEquals(c.premium(), c.age() >= 18);
    }
}

An aggregator turns a wide row into one domain object, so the signature stays short. An ArgumentsAccessor can also be declared directly as the test's parameter (void t(ArgumentsAccessor row)) for untyped access by index. Display names come from the name template: {index}, {0}, {1}…, {arguments}, {argumentsWithNames} and {displayName}. Names in {argumentsWithNames} come from the method's parameter names, which exist at runtime only if you compile with -parameters (Spring Boot's parent POM sets it); without the flag you just get the values.

What breaks in production
  • Extra columns are ignored by default. "Smith, John, 42" into (String last, String first) silently drops 42, and an unquoted comma shifts every column. Quote values, and since JUnit 5.12 set argumentCountValidation = ArgumentCountValidationMode.STRICT (or the matching configuration parameter) to make a column mismatch fail.
  • Null versus empty. , x passes null; '', x passes "". Code that treats them differently needs both rows.
  • Tables that hide the rule. Forty rows with a comment on each mean the test is doing too many things. Split by behaviour, and keep each table to one rule.
  • Logic in the source. A @MethodSource that computes expected values with the same formula as production code verifies nothing. Expected values should be literals someone checked by hand.

Dynamic Tests & The Extension Model

40m video40m practice

Two escape hatches turn Jupiter from a fixed set of annotations into a framework you can extend: @TestFactory creates tests at runtime, and extensions plug your own code into fixed points of the test lifecycle. Mockito, Spring, Testcontainers and WireMock all integrate through the second one.

Dynamic tests with @TestFactory

A @TestFactory method doesn't test anything itself; it returns a Stream, Collection or Iterable of DynamicNodes, and the engine runs each one. A DynamicTest is a display name plus an Executable; a DynamicContainer is a named group of further nodes, so you can build a tree.

class FixturesTest {

    @TestFactory
    Stream<DynamicTest> everyOrderFixtureIsAJsonObject() throws IOException {
        return Files.list(Path.of("src/test/resources/orders"))      // JUnit closes the stream
                .filter(p -> p.toString().endsWith(".json"))
                .sorted()
                .map(p -> DynamicTest.dynamicTest(p.getFileName().toString(), p.toUri(), () -> {
                    String json = Files.readString(p).strip();
                    assertTrue(json.startsWith("{") && json.endsWith("}"), () -> p + " is not an object");
                }));
    }

    @TestFactory
    Stream<DynamicContainer> currencies() {
        return Stream.of("EUR", "USD", "JPY").map(code -> DynamicContainer.dynamicContainer(code, Stream.of(
                DynamicTest.dynamicTest("is known", () -> assertNotNull(Currency.getInstance(code))),
                DynamicTest.dynamicTest("has 0 to 3 decimals", () -> {
                    int d = Currency.getInstance(code).getDefaultFractionDigits();
                    assertTrue(d >= 0 && d <= 3);
                }))));
    }
}

Drop a new file into orders/ and the suite gains a test with no code change; the URI argument lets the IDE jump from a failure to the file. One rule surprises people: @BeforeEach and @AfterEach run once around the factory method, not around each dynamic test, so dynamic tests must not mutate shared fixtures.

Writing extensions, and keeping state in the store

Definition · ExtensionContext store

Each extension context (engine root, class, method) has a Store, a key-value map partitioned by Namespace so extensions can't clobber each other's keys. Lookups fall through to parent contexts, so a method sees what was stored at class level. When a context finishes, values in its store that implement ExtensionContext.Store.CloseableResource are closed. Values stored in the root context's store live for the whole run.

One extension instance is reused for many tests, possibly on several threads, so keep per-test state in the store, never in fields.

class TimingExtension implements BeforeTestExecutionCallback, AfterTestExecutionCallback {
    private static final ExtensionContext.Namespace NS =
            ExtensionContext.Namespace.create(TimingExtension.class);

    @Override
    public void beforeTestExecution(ExtensionContext ctx) {
        ctx.getStore(NS).put("start", System.nanoTime());
    }

    @Override
    public void afterTestExecution(ExtensionContext ctx) {
        long ms = (System.nanoTime() - ctx.getStore(NS).remove("start", long.class)) / 1_000_000;
        ctx.publishReportEntry("durationMs", String.valueOf(ms));      // lands in the XML report
        if (ms > 200) System.err.printf("SLOW %s: %d ms%n", ctx.getDisplayName(), ms);
    }
}

@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
@interface Scratch {}

class ScratchDirExtension implements ParameterResolver, TestWatcher {
    private static final ExtensionContext.Namespace NS =
            ExtensionContext.Namespace.create(ScratchDirExtension.class);

    @Override
    public boolean supportsParameter(ParameterContext p, ExtensionContext ctx) {
        return p.isAnnotated(Scratch.class) && p.getParameter().getType() == Path.class;
    }

    @Override
    public Object resolveParameter(ParameterContext p, ExtensionContext ctx) {
        return ctx.getStore(NS).getOrComputeIfAbsent("dir", k -> new ScratchDir(), ScratchDir.class).path;
    }

    @Override
    public void testFailed(ExtensionContext ctx, Throwable cause) {
        System.err.println("FAILED " + ctx.getDisplayName() + ": " + cause.getMessage());
    }

    static final class ScratchDir implements ExtensionContext.Store.CloseableResource {
        final Path path;
        ScratchDir() {
            try { path = Files.createTempDirectory("scratch-"); }
            catch (IOException e) { throw new UncheckedIOException(e); }
        }
        @Override
        public void close() throws IOException {                        // runs when the test's context ends
            try (Stream<Path> walk = Files.walk(path)) {
                walk.sorted(Comparator.reverseOrder()).forEach(f -> f.toFile().delete());
            }
        }
    }
}

@ExtendWith({ScratchDirExtension.class, TimingExtension.class})
class ReportWriterTest {
    @Test
    void writesCsv(@Scratch Path dir) throws IOException {
        Path out = Files.writeString(dir.resolve("report.csv"), "id,total\n");
        assertEquals(List.of("id,total"), Files.readAllLines(out));
    }
}

That is the whole mechanism behind the built-in @TempDir: a parameter resolver plus a closeable value in the store. The TestWatcher half shows reporting: it sees the outcome after the test and its lifecycle methods have finished.

Registering extensions

  • Declarative: @ExtendWith(X.class) on a class, method, field or parameter, applied in declaration order. Put it on a composed annotation (@WithScratchDir) to give it a name, which is how @SpringBootTest brings in SpringExtension.
  • Programmatic: @RegisterExtension on a field holding a configured instance, for example static WireMockExtension wm = WireMockExtension.newInstance().options(...).build() (L196). A static field also receives class-level callbacks such as BeforeAllCallback; an instance field gets only method-level ones.
  • Automatic: list the class in META-INF/services/org.junit.jupiter.api.extension.Extension and set junit.jupiter.extensions.autodetection.enabled=true. It then applies to every test on that classpath, so keep it for truly global concerns.

junit.jupiter.execution.parallel.mode.classes.default = concurrent   # classes in parallel
junit.jupiter.execution.parallel.mode.default = same_thread          # methods of one class in sequence
junit.jupiter.execution.parallel.config.strategy = dynamic           # threads = cores x factor
junit.jupiter.execution.parallel.config.dynamic.factor = 1

Classes-concurrent, methods-sequential is the safe first step: no two tests of the same class overlap, so instance fields and @BeforeEach state stay private. Going fully concurrent requires that tests share no mutable statics, extensions keep state only in the store, and every test gets its own temp directory, port and data. Opt out where needed with @Execution(ExecutionMode.SAME_THREAD), serialise access to a shared resource with @ResourceLock("db") or @ResourceLock(Resources.SYSTEM_PROPERTIES), and run a test alone with @Isolated. This is thread-level parallelism inside one JVM; Surefire's forkCount runs separate JVMs and is an independent knob.

What breaks in production
  • Extension state in fields. private long start; works until parallel execution is switched on; then timings, or worse, transaction handles, belong to the wrong test.
  • Swallowing handlers. A TestExecutionExceptionHandler that logs and doesn't rethrow turns every failure in its scope into a pass.
  • Shared fixtures in dynamic tests. With no per-test @BeforeEach, the third dynamic test sees whatever the second left behind.
  • Invisible global extensions. An auto-detected extension in one module's resources makes tests behave differently depending on which module you run from. Document it next to the properties file.

AssertJ: Fluent Assertions

40m video45m practice

AssertJ's assertThat(actual) returns an assertion object chosen by the static type of actual, so the IDE's completion list is the documentation and every failure message knows what kind of value it is describing. You write fewer, more precise assertions and read better failures.

Why it beats plain JUnit assertions

assertTrue(names.contains("Grace"));          // JUnit
  org.opentest4j.AssertionFailedError: expected: <true> but was: <false>

assertThat(names).contains("Grace");          // AssertJ
  Expecting ArrayList:
    ["Ada", "Linus"]
  to contain:
    ["Grace"]
  but could not find the following element(s):
    ["Grace"]

Three gains. Discoverability: type assertThat(order.lines()). and the IDE lists only the list assertions. Messages: the failure shows the actual value, the expectation and the difference, without a hand-written message. Chaining: each assertion returns the assert object, so assertThat(sku).isNotBlank().startsWith("AB-").hasSize(7) reads as one sentence. AssertJ ships in spring-boot-starter-test; otherwise add org.assertj:assertj-core with test scope and import org.assertj.core.api.Assertions.* statically. Since there is no expected/actual argument pair, the order mistake from L185 disappears too.

Core, string and collection assertions

import java.util.List;
import org.junit.jupiter.api.Test;
import static org.assertj.core.api.Assertions.*;

class StaffTest {

    record Employee(String name, String dept, int age, List<String> skills) {}

    final List<Employee> staff = List.of(
            new Employee("Ada", "eng", 36, List.of("java", "math")),
            new Employee("Grace", "eng", 45, List.of("cobol", "java")),
            new Employee("Linus", "ops", 28, List.of("c", "git")));

    @Test
    void coreAndStrings() {
        Employee ada = staff.get(0);
        assertThat(ada.name()).isEqualTo("Ada").isIn("Ada", "Grace").startsWith("A").hasSize(3);
        assertThat(ada).isNotNull()
                .matches(e -> e.age() > 30, "is over 30")
                .satisfies(e -> assertThat(e.skills()).contains("java"));
        assertThat("Order #42 shipped").contains("#42").containsIgnoringCase("SHIPPED");
    }

    @Test
    void collections() {
        assertThat(staff).extracting(Employee::name).containsExactly("Ada", "Grace", "Linus");
        assertThat(staff).extracting(Employee::dept).containsExactlyInAnyOrder("ops", "eng", "eng");
        assertThat(staff).flatExtracting(Employee::skills).containsOnlyOnce("git", "math");
        assertThat(staff).extracting(Employee::name, Employee::age).contains(tuple("Grace", 45));
        assertThat(staff).filteredOn(e -> e.dept().equals("eng"))
                .hasSize(2)
                .allSatisfy(e -> assertThat(e.skills()).contains("java"));
        assertThat(staff).anyMatch(e -> e.age() < 30);
        assertThat(staff).filteredOn(e -> e.dept().equals("ops"))
                .singleElement()
                .extracting(Employee::name).isEqualTo("Linus");
    }
}
  • matches(predicate, description) checks a condition and names it in the message; satisfies(consumer) runs nested assertions on the value, so the failure comes from the inner, specific assertion.
  • containsExactly means these elements, in this order, nothing else; containsExactlyInAnyOrder drops the order but still counts duplicates; plain contains is a subset check.
  • extracting maps each element to a property (or several, as tuples) before asserting; flatExtracting flattens list-valued properties; filteredOn narrows the collection first; singleElement asserts there is exactly one and continues with it.

Object graphs and exceptions

Definition · recursive comparison

usingRecursiveComparison() walks both object graphs field by field, by reflection, and reports every differing field by its path (such as address.zip). It does not call the objects' own equals by default, so it works for entities whose equals compares only ids, and for classes with no equals at all. Configure it with ignoringFields, ignoringFieldsOfTypes, ignoringExpectedNullFields, ignoringCollectionOrder and withComparatorForType.

assertThatThrownBy fails if nothing is thrown, then continues with throwable assertions: type, message (hasMessage, hasMessageContaining), cause (hasCauseInstanceOf) and root cause. assertThatExceptionOfType(X.class).isThrownBy(...) reads better when the type is the point; its chain uses with… names.

A custom assertion for your domain

record Order(String id, String status, BigDecimal total) {}

class OrderAssert extends AbstractAssert<OrderAssert, Order> {

    private OrderAssert(Order actual) { super(actual, OrderAssert.class); }

    static OrderAssert assertThatOrder(Order actual) { return new OrderAssert(actual); }

    OrderAssert isShipped() {
        isNotNull();
        if (!"SHIPPED".equals(actual.status()))
            failWithMessage("Expected order %s to be SHIPPED but was %s", actual.id(), actual.status());
        return this;
    }

    OrderAssert hasTotal(String expected) {
        isNotNull();
        if (actual.total().compareTo(new BigDecimal(expected)) != 0)
            failWithMessage("Expected order %s to total %s but was %s", actual.id(), expected, actual.total());
        return this;
    }
}

class OrderAssertTest {
    @Test
    void readsLikeTheDomain() {
        var order = new Order("A-1", "SHIPPED", new BigDecimal("12.50"));
        OrderAssert.assertThatOrder(order).isShipped().hasTotal("12.5");
    }
}

The self type parameter (AbstractAssert<OrderAssert, Order>) lets inherited methods such as isNotNull() return OrderAssert, so chains keep working. Give the entry point a distinct name, or collect entry points in a DomainAssertions class, to avoid clashing with the static assertThat import. A custom assertion pays off once the same three-line check appears in many tests: it names the rule and gives one good message.

What breaks in production
  • The assertion that asserts nothing. assertThat(result); with no chained call compiles and always passes. Sonar's "assertions should be complete" rule and checkers that honour AssertJ's @CheckReturnValue flag it; review for it too.
  • Recursive comparison that ignores too much. Each ignoringFields is a hole in the test. If half the fields are ignored, assert the remaining ones explicitly instead.
  • isEqualTo on BigDecimal. Fails or passes depending on scale, which changes with arithmetic and database column definitions.
  • Forgotten assertAll(). A manually created SoftAssertions without the final call collects failures and then throws them away.

Mockito I: Mocks, Stubbing & Answers

45m video50m practice

A mock is a stand-in object that records every call made to it and answers with whatever you programmed. You use one to cut a unit off from collaborators that are slow, nondeterministic or hard to provoke, so the test controls every input and checks only the unit's own logic.

Why mocks exist, and what one is

A CheckoutService that loads an order, charges a card and saves the result depends on a database and a payment gateway. A unit test can't call the real gateway (money, rate limits, no way to make it decline on demand) and doesn't want a database. With mocks, each test decides what the collaborators say: the order exists, the card is declined, the save succeeds.

Definition · how a Mockito mock works

mock(PaymentGateway.class) creates an instance whose every method is intercepted (since Mockito 5 by the inline mock maker, which instruments bytecode through a Java agent; L192). Each call is recorded as an invocation (method plus arguments) and answered from the mock's stub list, or by the default answer when no stub matches.

when(x.charge("c-1", amt)) really calls charge on the mock; the call is recorded and returns the default, and when attaches your thenReturn to that last recorded invocation. Matchers such as any() are pushed onto a thread-local stack as they are evaluated and popped when the invocation is recorded.

Creating mocks, and the trouble with @InjectMocks

interface OrderRepository {
    Optional<Order> findById(long id);
    List<Order> findByCustomer(String customerId);
    Order save(Order order);
}
interface PaymentGateway {
    Receipt charge(String customerId, BigDecimal amount);
    void refund(String receiptId);
}
record Order(long id, String customerId, BigDecimal total, String status) {
    Order paid() { return new Order(id, customerId, total, "PAID"); }
}
record Receipt(String id, BigDecimal amount) {}
class PaymentDeclinedException extends RuntimeException {
    PaymentDeclinedException(String msg) { super(msg); }
}

final class CheckoutService {
    private final OrderRepository orders;
    private final PaymentGateway payments;

    CheckoutService(OrderRepository orders, PaymentGateway payments) {
        this.orders = orders;
        this.payments = payments;
    }

    Order pay(long orderId) {
        Order order = orders.findById(orderId)
                .orElseThrow(() -> new IllegalArgumentException("no order " + orderId));
        payments.charge(order.customerId(), order.total());
        return orders.save(order.paid());
    }
}
@ExtendWith(MockitoExtension.class)        // creates @Mock fields, validates usage after each test
class CheckoutServiceTest {

    @Mock OrderRepository orders;
    @Mock PaymentGateway payments;
    CheckoutService service;

    @BeforeEach
    void wire() { service = new CheckoutService(orders, payments); }   // explicit and compiler-checked

    @Test
    void chargesThenSavesAsPaid() {
        var order = new Order(7, "c-1", new BigDecimal("25.00"), "NEW");
        when(orders.findById(7)).thenReturn(Optional.of(order));
        when(payments.charge("c-1", new BigDecimal("25.00"))).thenReturn(new Receipt("r-1", order.total()));
        when(orders.save(any(Order.class))).thenAnswer(inv -> inv.getArgument(0));  // echo the argument

        assertEquals("PAID", service.pay(7).status());
    }

    @Test
    void unknownOrderIsRejected() {
        when(orders.findById(anyLong())).thenReturn(Optional.empty());
        assertThrows(IllegalArgumentException.class, () -> service.pay(99));
    }

    @Test
    void declinedCardPropagates() {
        when(orders.findById(7)).thenReturn(Optional.of(new Order(7, "c-1", BigDecimal.TEN, "NEW")));
        when(payments.charge(anyString(), any())).thenThrow(new PaymentDeclinedException("card declined"));
        assertThrows(PaymentDeclinedException.class, () -> service.pay(7));
    }
}

Create mocks with mock(PaymentGateway.class), with PaymentGateway p = mock(); (type inferred, Mockito 4.10+), or as @Mock fields initialised by MockitoExtension, which also enables strict stubs and validates matcher usage after every test (L191).

@InjectMocks CheckoutService service; would build the service for you: biggest constructor, else setters, else fields, matching mocks by type. It fails silently: a constructor argument with no matching mock gets null, an unmatched field stays null. Add a dependency in a refactor and the test dies with a NullPointerException deep in the service, or passes while skipping a code path. Calling the constructor yourself makes the compiler find every test to update.

Stubbing: return, throw, answer, and in sequence

@ExtendWith(MockitoExtension.class)
class StubbingTest {

    @Mock OrderRepository orders;
    @Mock PaymentGateway payments;

    @Test
    void consecutiveAndDefaults() {
        when(payments.charge(anyString(), any()))
                .thenThrow(new PaymentDeclinedException("timeout"))      // 1st call
                .thenReturn(new Receipt("r-2", BigDecimal.ONE));          // 2nd and every later call
        assertThrows(PaymentDeclinedException.class, () -> payments.charge("c", BigDecimal.ONE));
        assertEquals("r-2", payments.charge("c", BigDecimal.ONE).id());
        assertEquals("r-2", payments.charge("c", BigDecimal.ONE).id());

        assertEquals(Optional.empty(), orders.findById(1));    // unstubbed: empty Optional
        assertEquals(List.of(), orders.findByCustomer("c"));    // empty collection
        assertNull(orders.save(null));                          // other objects: null
    }

    @Test
    void answersComputeFromArguments() {
        AtomicLong ids = new AtomicLong(1000);
        when(orders.save(any(Order.class))).thenAnswer(inv -> {
            Order o = inv.getArgument(0);
            return o.id() == 0 ? new Order(ids.incrementAndGet(), o.customerId(), o.total(), o.status()) : o;
        });
        assertEquals(1001, orders.save(new Order(0, "c", BigDecimal.ONE, "NEW")).id());
        assertEquals(1002, orders.save(new Order(0, "c", BigDecimal.ONE, "NEW")).id());
        assertEquals(5, orders.save(new Order(5, "c", BigDecimal.ONE, "NEW")).id());
    }
}
  • Consecutive stubbing. thenReturn(a, b, c) or chained thenX calls answer in order, and the last answer repeats. Ideal for retry logic.
  • Defaults (RETURNS_DEFAULTS): 0/false for primitives and wrappers, empty collections, Optional and Stream; null for everything else, String included.
  • Other answers. mock(X.class, RETURNS_SMART_NULLS) returns placeholders whose use throws SmartNullPointerException naming the unstubbed call. RETURNS_DEEP_STUBS allows when(a.getB().getC()).thenReturn(x); needing it usually means the code reaches through too many objects.
  • Answer computes a response from the invocation (inv.getArgument(0), inv.callRealMethod()); AdditionalAnswers.returnsFirstArg() covers the echo case.

Argument matchers and the all-or-nothing rule

when(payments.charge(eq("c-1"), any(BigDecimal.class))).thenReturn(r);     // all matchers: OK
when(payments.charge("c-1", new BigDecimal("25.00"))).thenReturn(r);       // all raw values: OK
when(payments.charge("c-1", any())).thenReturn(r);                         // mixed: InvalidUseOfMatchersException
when(payments.charge(anyString(), argThat(a -> a.compareTo(LIMIT) > 0)))   // custom predicate
        .thenThrow(new PaymentDeclinedException("over limit"));
Rule · matchers are all or nothing

If any argument of a stubbed or verified call uses a matcher, every argument must. Each matcher pushes onto the stack and returns a dummy (null, 0), so with a mix Mockito sees two arguments but one matcher ("2 matchers expected, 1 recorded") and can't place the raw value. Wrap raw values in eq(...). Also: any() matches null, but any(Order.class) and anyString() don't.

Void methods: the do-family

when(payments.refund("r-1")) doesn't compile: there is no return value to pass to when. The do-family puts the answer first and the call second:

doThrow(new IllegalStateException("gateway down")).when(payments).refund("r-1");
doNothing().doThrow(new IllegalStateException()).when(payments).refund(anyString()); // ok, then fails
doAnswer(inv -> { refunded.add(inv.getArgument(0)); return null; })
        .when(payments).refund(anyString());

doNothing() is what a mock's void method does anyway; it matters in consecutive chains and on spies (L191), where the default is the real method. doReturn is the non-void member, mainly for spies.

What breaks in production
  • Near-miss stubs. A stub for new BigDecimal("25") doesn't match a call with 25.00 (equals compares scale), so the mock returns null. Strict stubs catch it as a PotentialStubbingProblem when the code under test makes the call; argThat with compareTo fixes it.
  • Mirror-image tests. Stubbing ten calls in the order the implementation makes them tests only that order. Stub what the scenario needs; assert on outcomes.
  • Mocked beliefs. A mock answers what you believe the collaborator does. If the real repository returns null rather than an empty Optional, every test passes and production fails. Back key assumptions with an integration test (L194).

Mockito II: Verification, Captors & Spies

45m video50m practice

Stubbing controls what goes into the unit; verification checks what comes out of it as calls to collaborators. Verify the commands that matter (money moved, email sent), not every query, and let strict stubs keep the setup honest.

verify and its modes

The service below refunds a payment, writes an audit entry and emails the customer. Its outputs are side effects, so the test has to look at the calls the mocks recorded. PaymentGateway and Order are the types from L190.

record Email(String to, String subject) {}
interface Mailer { void send(Email email); }
interface AuditLog { void record(String entry); }

final class RefundService {
    private final PaymentGateway payments;
    private final Mailer mailer;
    private final AuditLog audit;

    RefundService(PaymentGateway payments, Mailer mailer, AuditLog audit) {
        this.payments = payments; this.mailer = mailer; this.audit = audit;
    }

    void refund(Order order, String receiptId) {
        payments.refund(receiptId);
        audit.record("REFUND " + order.id());
        mailer.send(new Email(order.customerId() + "@example.com", "Refund for order " + order.id()));
    }

    void refundAll(List<Order> orders) {
        orders.forEach(o -> refund(o, "r-" + o.id()));
    }
}
@ExtendWith(MockitoExtension.class)
class RefundServiceTest {

    @Mock PaymentGateway payments;
    @Mock Mailer mailer;
    @Mock AuditLog audit;
    @Captor ArgumentCaptor<Email> email;
    RefundService service;

    final Order order = new Order(7, "c-1", new BigDecimal("25.00"), "PAID");

    @BeforeEach
    void wire() { service = new RefundService(payments, mailer, audit); }

    @Test
    void refundsOnceAndEmailsTheCustomer() {
        service.refund(order, "r-7");

        verify(payments).refund("r-7");                          // same as times(1)
        verify(payments, never()).charge(anyString(), any());
        verify(mailer, only()).send(email.capture());            // the only call on mailer
        assertEquals("c-1@example.com", email.getValue().to());
        assertEquals("Refund for order 7", email.getValue().subject());
    }

    @Test
    void refundComesBeforeAuditAndEmail() {
        service.refund(order, "r-7");

        InOrder inOrder = inOrder(payments, audit, mailer);
        inOrder.verify(payments).refund("r-7");
        inOrder.verify(audit).record("REFUND 7");
        inOrder.verify(mailer).send(any(Email.class));
    }

    @Test
    void batchEmailsEveryCustomer() {
        service.refundAll(List.of(order, new Order(8, "c-2", BigDecimal.ONE, "PAID")));

        verify(payments, times(2)).refund(startsWith("r-"));
        verify(mailer, atLeastOnce()).send(email.capture());
        assertEquals(List.of("c-1@example.com", "c-2@example.com"),
                email.getAllValues().stream().map(Email::to).toList());
    }

    @Test
    void failedRefundTouchesNothingElse() {
        doThrow(new IllegalStateException("gateway down")).when(payments).refund("r-7");

        assertThrows(IllegalStateException.class, () -> service.refund(order, "r-7"));
        verifyNoInteractions(mailer, audit);
    }
}
ModePasses when the call happened
verify(m) = times(1)exactly once with matching arguments
times(n), never()exactly n times; zero times
atLeast(n), atLeastOnce(), atMost(n)at least n; at least 1; no more than n
only()once, and it was the only call on that mock

A failed verification prints what was expected and every interaction actually recorded on the mock, with source locations; "wanted but not invoked" and "argument(s) are different" are the two you will read most. BDD-style code can write the same check as then(mailer).should(times(2)).send(any()) with BDDMockito, whose given(...).willReturn(...) mirrors when.

What to verify, and verifyNoMoreInteractions

Guideline · allow queries, expect commands

A query returns data and has no side effect (findById, getRate): stub it, and don't verify it, because the outcome already proves it was called. A command changes the world (charge, send, publish): verify it, since it is the behaviour. (Freeman and Pryce, Growing Object-Oriented Software.)

verifyNoInteractions(mailer) asserts a mock was never touched: right for "a failed refund must not email anyone". verifyNoMoreInteractions(m), called after your verifies, asserts that nothing else happened on that mock. Used everywhere, it turns every test into a full transcript of the implementation: add a metrics call or a cache lookup and dozens of tests fail without any behaviour having changed. Keep it for collaborators where an extra call really is a bug (a second charge), and prefer a targeted verify(payments, never()).charge(...).

ArgumentCaptor versus matchers

A captor is a matcher that matches anything and remembers what it saw: capture() inside a verify, then getValue() (the last capture) or getAllValues() (all, in call order). Create it with @Captor (which handles generics without an unchecked cast) or ArgumentCaptor.forClass(Email.class).

  • Use a matcher for one simple condition: verify(payments).refund(startsWith("r-")), or argThat(e -> e.to().endsWith("@example.com")).
  • Use a captor when you need several assertions on a built object, or the sequence of values across calls; then use AssertJ on the captured values for good messages (L189).
  • Don't capture while stubbing. when(x.save(captor.capture())) works, but the Mockito docs advise against it: the assertion moves away from the verify step and the test is harder to read.

Spies and partial mocks

class SpyTest {

    @Test
    void spyRunsRealMethodsUntilStubbed() {
        List<String> real = new ArrayList<>();
        List<String> spy = spy(real);        // a copy of real's state, wrapped

        spy.add("a");
        assertEquals(1, spy.size());          // real ArrayList behaviour
        assertEquals(0, real.size());         // the original object is not touched
        verify(spy).add("a");                 // and every call is recorded

        // when(spy.get(5)).thenReturn("x"); // would throw: when() calls the real get(5) first
        doReturn("x").when(spy).get(5);       // stubs without invoking the real method
        assertEquals("x", spy.get(5));
    }
}

A spy wraps a real object: unstubbed methods run the real code, and calls are recorded for verification. Because when(spy.get(5)) evaluates spy.get(5) first, it runs the real method, with its side effects or exceptions, before the stub exists. On spies, always stub with doReturn/doThrow/doNothing().when(spy).method(). A partial mock is the same idea from the other side: mock(X.class, withSettings().defaultAnswer(CALLS_REAL_METHODS)), or thenCallRealMethod() on chosen methods. Both are tools for legacy code. Spying on the class under test means it does two jobs; extract the part you want to replace into a collaborator and mock that.

Strict stubs, and why you shouldn't need reset

org.mockito.exceptions.misusing.UnnecessaryStubbingException:
Unnecessary stubbings detected.
Clean & maintainable test code requires zero unnecessary code.
Following stubbings are unnecessary (click to navigate to relevant line of code):
  1. -> at RefundServiceTest.refundsOnceAndEmailsTheCustomer(RefundServiceTest.java:31)

MockitoExtension runs with Strictness.STRICT_STUBS unless told otherwise (@MockitoSettings(strictness = Strictness.LENIENT) or WARN). Strict stubs fail a test that stubs something the code never calls, and fail fast with PotentialStubbingProblem when the code calls a stubbed method with different arguments. That is good for you: an unused stub misleads the reader about what the test depends on, and often means the code path changed and the test no longer exercises what its name claims. When one shared @BeforeEach stub really is needed by only some tests, mark just that stub lenient().when(...) rather than relaxing the whole class.

reset(mock) clears stubs and recorded calls. The Mockito docs say plainly that needing it is usually a sign of a poor test: a test that stubs, acts, resets and acts again is two tests. Mocks are cheap; JUnit gives every test fresh @Mock fields anyway. If setup itself triggers calls you don't want to count, clearInvocations(mock) forgets the calls but keeps the stubs. In Spring tests, @MockitoBean mocks are reset after each test for you (L294).

What breaks in production
  • when() on a spy of a real client. The stubbing line calls the real method: a real email goes out, or a real HTTP call fails the test before the stub exists.
  • Transcript tests. verifyNoMoreInteractions plus verifying every query makes harmless refactors break the build, and teams learn to update verifications without thinking.
  • Verifying stubbed queries. verify(orders).findById(7) after stubbing it adds nothing the result doesn't already prove, and couples the test to how the data is fetched.
  • Blanket lenience. Class-level LENIENT to silence one warning lets dead stubs pile up until nobody knows what a test depends on.

Mockito III: Static, Final, Construction & Boundaries

40m video40m practice

Modern Mockito can mock almost anything: final classes, static methods, even new. That it can is mostly useful for legacy code; in code you control, every static or construction mock is a pointer to a missing seam, and the better fix is a Clock, a constructor parameter, or a boundary interface you own.

The inline mock maker and final types

Before Mockito 5 the subclass mock maker was the default, and mocking finals needed the separate mockito-inline artifact. Since 5.0, mockito-core uses the inline mock maker, so this just works:

final class ExchangeRates {                          // final, no interface
    BigDecimal rate(String from, String to) {
        throw new UnsupportedOperationException("calls a remote API");
    }
}

class FinalMockTest {
    @Test
    void finalClassesMockLikeAnyOther() {
        ExchangeRates rates = mock(ExchangeRates.class);
        when(rates.rate("EUR", "USD")).thenReturn(new BigDecimal("1.08"));
        assertEquals(new BigDecimal("1.08"), rates.rate("EUR", "USD"));
    }
}

mockStatic, and why a Clock is better

final class Ids {
    static String next() { return UUID.randomUUID().toString(); }
}

class StaticMockTest {

    @Test
    void staticMockIsScopedToTheBlock() {
        try (MockedStatic<Ids> ids = mockStatic(Ids.class)) {
            ids.when(Ids::next).thenReturn("id-1");
            assertEquals("id-1", Ids.next());
            ids.verify(Ids::next);                       // times(1), like verify()
        }
        assertNotEquals("id-1", Ids.next());             // real method again after close()
    }

    @Test
    void mockingNowWorksButHurts() {
        LocalDateTime fixed = LocalDateTime.of(2026, 1, 31, 23, 59);   // build it before the mock exists
        try (MockedStatic<LocalDateTime> time = mockStatic(LocalDateTime.class, CALLS_REAL_METHODS)) {
            time.when(LocalDateTime::now).thenReturn(fixed);
            assertEquals(fixed, LocalDateTime.now());
        }
    }
}
Definition · static mock scope

A MockedStatic is active only on the thread that created it, and only until close(). Inside that scope every static method of the class answers from the mock, so with the default answer even LocalDateTime.of(...) returns null; pass CALLS_REAL_METHODS to keep the others real. Code the unit runs on another thread (an executor, CompletableFuture.supplyAsync, a parallel stream) sees the real methods. A mock that is never closed stays registered on that thread, and the next test that tries to create one fails with "static mocking is already registered in the current thread".

Mocking now() treats a symptom. The design problem is that the class reads a global clock. Make time an input:

final class InvoiceService {
    private final Clock clock;
    InvoiceService(Clock clock) { this.clock = clock; }          // Clock.systemUTC() in production

    LocalDate dueDate() { return LocalDate.now(clock).plusDays(30); }
}

class InvoiceServiceTest {
    @Test
    void dueThirtyDaysAfterIssue() {
        Clock clock = Clock.fixed(Instant.parse("2026-01-31T10:00:00Z"), ZoneOffset.UTC);
        assertEquals(LocalDate.of(2026, 3, 2), new InvoiceService(clock).dueDate());
    }
}

No agent, no thread-locality, no scope to forget, and the test reads as data. Every java.time now method has an overload that takes a Clock; for time that must move during a test, write a small mutable fake clock (L193).

mockConstruction, and why constructor injection is better

class GeoClient {
    GeoClient(String baseUrl) { }
    String lookup(String zip) { throw new IllegalStateException("network"); }
}

final class Geocoder {                                    // legacy: news up its own client
    String cityOf(String zip) { return new GeoClient("https://geo.example.com").lookup(zip); }
}

class ConstructionMockTest {
    @Test
    void interceptsNew() {
        try (MockedConstruction<GeoClient> geo = mockConstruction(GeoClient.class,
                (mock, context) -> when(mock.lookup("10115")).thenReturn("Berlin"))) {
            assertEquals("Berlin", new Geocoder().cityOf("10115"));
            assertEquals(1, geo.constructed().size());      // every instance made in scope is a mock
        }
    }
}

It works, and it is the right first step when you must characterise legacy code before changing it. The lasting fix is Geocoder(GeoClient client): the dependency becomes visible in the signature, production wiring (or Spring) passes the real one, and tests pass a mock or fake with plain new. A new of a collaborator inside business logic is the construction-time version of a hidden global.

What never to mock, and the two schools

  • Value objects. Records, Money, LocalDate, DTOs: construct them. A mocked value object has no real behaviour, so equals and calculations stop meaning anything.
  • Types you don't own. Mocking HttpClient, an AWS SDK client or a JDBC ResultSet encodes your guess of how a third-party API behaves, and the guess never fails when the library changes. Wrap the dependency in a small interface in your own vocabulary (RatesProvider.rate(from, to)), mock or fake that, and test the adapter against the real thing or WireMock (L196).
  • The JDK. Use a real ArrayList, HashMap or String. Mockito refuses some core classes outright, and mocking the rest buys nothing.

A fake often beats a mock: when the collaborator is stateful (save, then find), when dozens of tests need it, or when the behaviour spans several calls. An in-memory repository written once behaves consistently everywhere, while a mock must be re-taught the same behaviour in every test (L193).

PowerMock

PowerMock mocked statics, finals, constructors and private methods by loading test classes through its own bytecode-rewriting class loader. It has no JUnit Jupiter support, its last release dates from 2020, and the class-loader tricks clash with modern JDKs and with JaCoCo's agent. Mockito now covers static, final and construction mocking, and mocking private methods is something you shouldn't want: they are implementation details, tested through the public behaviour that uses them.

What breaks in production
  • Static mocks and threads. The service under test hands work to an executor; the worker thread calls the real static method; the test is flaky or silently tests nothing.
  • An unclosed MockedStatic. Created without try-with-resources, it leaks into later tests on the same thread and fails them with "already registered".
  • JDK upgrade breaks the suite. Relying on self-attach works until dynamic agent loading is disabled by default; configure -javaagent before that day.
  • Mocked third-party semantics. A mocked SDK client returns null where the real one throws; production gets the exception, the tests never did.

Test Doubles & Designing for Testability

40m video40m practice

Code is testable when its dependencies come in through the front door. Put the awkward ones (storage, messaging, time) behind ports you own, inject them, and in tests plug in simple hand-written doubles; most "hard to test" code is code that reaches for globals.

The five doubles, precisely

"Mock" is used loosely for any stand-in. Meszaros' xUnit Test Patterns gives the precise vocabulary; test double is the umbrella term.

One Mockito object can be a dummy, a stub or (verified afterwards) a spy. The words matter because they say what the test checks: stubs and fakes support state verification, spies and mocks behaviour verification.

Hand-rolled fakes

record Order(long id, String customerId, String status, Instant placedAt) {
    Order withId(long newId)       { return new Order(newId, customerId, status, placedAt); }
    Order withStatus(String s)     { return new Order(id, customerId, s, placedAt); }
}
record OrderExpired(long orderId) {}

interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(long id);
    List<Order> findByStatus(String status);
}
interface EventPublisher { void publish(Object event); }

final class InMemoryOrderRepository implements OrderRepository {      // fake
    private final Map<Long, Order> rows = new ConcurrentHashMap<>();
    private final AtomicLong ids = new AtomicLong();

    public Order save(Order o) {
        Order stored = o.id() == 0 ? o.withId(ids.incrementAndGet()) : o;
        rows.put(stored.id(), stored);
        return stored;
    }
    public Optional<Order> findById(long id) { return Optional.ofNullable(rows.get(id)); }
    public List<Order> findByStatus(String s) {
        return rows.values().stream().filter(o -> o.status().equals(s)).sorted(Comparator.comparing(Order::id)).toList();
    }
}

final class MutableClock extends Clock {                              // fake clock
    private volatile Instant now;
    private final ZoneId zone;
    MutableClock(Instant start, ZoneId zone) { this.now = start; this.zone = zone; }
    void advance(Duration d) { now = now.plus(d); }
    @Override public Instant instant() { return now; }
    @Override public ZoneId getZone() { return zone; }
    @Override public Clock withZone(ZoneId z) { return new MutableClock(now, z); }
}

final class RecordingPublisher implements EventPublisher {             // spy
    final List<Object> published = new CopyOnWriteArrayList<>();
    @Override public void publish(Object event) { published.add(event); }
}

final class ExpiryJob {
    private final OrderRepository orders;
    private final Clock clock;
    private final EventPublisher events;

    ExpiryJob(OrderRepository orders, Clock clock, EventPublisher events) {
        this.orders = orders; this.clock = clock; this.events = events;
    }

    void run() {
        Instant cutoff = clock.instant().minus(Duration.ofHours(24));
        for (Order o : orders.findByStatus("NEW")) {
            if (o.placedAt().isBefore(cutoff)) {
                orders.save(o.withStatus("EXPIRED"));
                events.publish(new OrderExpired(o.id()));
            }
        }
    }
}
class ExpiryJobTest {
    final InMemoryOrderRepository orders = new InMemoryOrderRepository();
    final MutableClock clock = new MutableClock(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC);
    final RecordingPublisher events = new RecordingPublisher();
    final ExpiryJob job = new ExpiryJob(orders, clock, events);

    @Test
    void expiresUnpaidOrdersOlderThanADay() {
        Order stale = orders.save(OrderBuilder.anOrder().unpaid().placedAt(clock.instant()).build());
        clock.advance(Duration.ofHours(25));
        Order fresh = orders.save(OrderBuilder.anOrder().unpaid().placedAt(clock.instant()).build());

        job.run();

        assertThat(orders.findById(stale.id())).get().extracting(Order::status).isEqualTo("EXPIRED");
        assertThat(orders.findById(fresh.id())).get().extracting(Order::status).isEqualTo("NEW");
        assertThat(events.published).containsExactly(new OrderExpired(stale.id()));
    }
}

No stubbing script and no verification of how the job queried: the test sets up a world, runs the job, and checks the world. With mocks it would need when(findByStatus("NEW")), a thenAnswer for save and a verify per call, and would break if the job switched query methods. The fake is written once and reused everywhere. Its risk is drift from the real adapter (duplicate keys, sort order); guard with a contract test, one abstract test class run against both the fake and the JDBC repository (L195).

Dependency injection, ports, and where to mock

Dependency injection makes this possible: ExpiryJob gets its collaborators through its constructor, so a test calls new ExpiryJob(fakeRepo, clock, events) with no framework; Spring is just one way to call that constructor. Mocking every class boundary pins the internal structure; doubling only at the ports pins only what the outside world sees.

Keep static, singleton and new out of business logic. A static TaxTables.rateFor(region) leaves only mockStatic as a seam; a singleton carries state between tests; a new SmtpMailer(...) in a method hides a dependency. new of value objects and pure static functions (no I/O, time or randomness) are fine.

Seams in legacy code

Definition · seam

"A seam is a place where you can alter behavior in your program without editing in that place" (Feathers, Working Effectively with Legacy Code, ch. 4). In Java the useful kind is the object seam: a call through a type whose implementation the test can choose. Link seams (swapping classes on the test classpath) exist too.

class ReportJob {
    private final ReportSource source;
    private final Clock clock;
    private final Mailer mailer;

    ReportJob() {                                         // old callers keep compiling
        this(LegacyDatabase.getInstance()::query, Clock.systemDefaultZone(), new SmtpMailer("smtp.corp"));
    }

    ReportJob(ReportSource source, Clock clock, Mailer mailer) {   // the seam tests use
        this.source = source; this.clock = clock; this.mailer = mailer;
    }

    void run() {
        List<String> rows = source.rows("select * from daily_sales");
        mailer.send("Sales " + LocalDate.now(clock) + ": " + rows.size() + " rows");
    }
}

Before the change, run() called LegacyDatabase.getInstance(), LocalDate.now() and new SmtpMailer(...) directly. Parameterize constructor added the seam without touching any caller. Other standard moves: extract interface; subclass and override (move the awkward call into a protected method a test subclass overrides); and wrapping a static behind an instance, as ReportSource does. Write characterisation tests through the seam, then refactor.

Test data: builders, mothers, generators, fixtures

final class OrderBuilder {                                 // test data builder
    private long id = 0;
    private String customerId = "c-1";

    private Instant placedAt = Instant.parse("2026-01-01T00:00:00Z");

}

A test data builder supplies valid defaults so each test states only the values it depends on (anOrder().unpaid().placedAt(t)). An Object Mother hands out named, canned objects; mothers read well but grow into a god class of near-identical fixtures shared by many tests. Mothers that return builders get the best of both.

Generators fill in what you don't care about: Instancio builds populated object graphs (Instancio.of(Order.class).set(field("status"), "NEW").create()) and its JUnit extension reports the seed of a failing run; EasyRandom is the older, no longer actively developed alternative. Never let an assertion depend on a generated value.

Fixtures. Prefer a fresh fixture per test. A shared fixture (static fields, a database seeded once) is faster but lets one test's writes become another's input. If you must share, keep it immutable or reset it, and avoid the mystery guest: essential data hidden in a file or table the test doesn't show.

What breaks in production
  • Fake drift. The in-memory repository accepts two orders with the same number; the database rejects the second. Run one contract test suite against both.
  • Global fixtures. One giant @BeforeEach building twenty objects, three per test used; nobody dares change it.
  • Unseeded randomness. A failure on random data without a logged seed can't be reproduced.
  • Mocks at every class. A purely internal refactor (splitting a class) breaks thirty tests although behaviour didn't change.

Testcontainers I: Real Dependencies in Tests

45m video50m practice

An integration test is only as honest as the dependency behind it. Testcontainers starts the real database, broker or service in a throwaway Docker container for the duration of the tests, on a random port, and removes it afterwards, so "works on H2" stops being mistaken for "works on Postgres".

Why H2 is not Postgres

H2 in MODE=PostgreSQL emulates part of Postgres's syntax. It is not Postgres's planner, type system, locking or extension ecosystem, and the gaps are exactly where production bugs live:

  • Dialect drift. jsonb operators (->>, @>), arrays, ON CONFLICT … DO UPDATE, partial and expression indexes, FOR UPDATE SKIP LOCKED, generate_series: each is missing, partial or subtly different. Flyway migrations written for Postgres either fail on H2 or end up maintained twice.
  • Missing features. Extensions (pgcrypto, PostGIS, pg_trgm), custom types, Postgres-specific error codes your code catches.
  • Different behaviour. Identifier case rules, sequence and default semantics, isolation and lock behaviour under concurrency.
  • False confidence. The suite is green, the deploy fails on the first query using a feature H2 faked or lacked.

The fix is to test against the same database engine and major version you run in production. Docker makes that cheap enough to do on every build.

How Testcontainers works

Definition · environment and cleanup

Testcontainers needs a Docker-API-compatible environment: Docker Desktop, Docker Engine on Linux, Colima, Podman with its Docker socket, a remote DOCKER_HOST, or Testcontainers Cloud. It discovers the environment from DOCKER_HOST, ~/.testcontainers.properties and the platform defaults. Every container it starts carries a session label. Ryuk, a small container started first, holds a socket connection from the JVM and, when that connection drops, removes containers, networks and volumes with the session's label. Ryuk itself needs access to the Docker socket; where that is forbidden, TESTCONTAINERS_RYUK_DISABLED=true turns it off and cleanup becomes your problem.

@Testcontainers registers the extension, which finds @Container fields and manages their lifecycle. GenericContainer, wait strategies, host and port

@Testcontainers
class RedisContainerIT {

    @Container
    static final GenericContainer<?> redis = new GenericContainer<>(DockerImageName.parse("redis:7.4-alpine"))
            .withExposedPorts(6379)
            .withEnv("TZ", "UTC")
            .waitingFor(Wait.forLogMessage(".*Ready to accept connections.*\\n", 1))
            .withStartupTimeout(Duration.ofSeconds(60));

    @Test
    void answersPing() throws IOException {
        try (var socket = new Socket(redis.getHost(), redis.getMappedPort(6379));
             var in = new BufferedReader(new InputStreamReader(socket.getInputStream(), StandardCharsets.US_ASCII))) {
            socket.getOutputStream().write("PING\r\n".getBytes(StandardCharsets.US_ASCII));
            assertEquals("+PONG", in.readLine());               // Redis inline-command reply
        }
    }
}
  • Image, ports, env. Pin a tag that matches production (redis:7.4-alpine, never latest). withExposedPorts names container ports; each is published on a random free host port. withEnv, withCommand, withCopyFileToContainer and withTmpFs cover most configuration.
  • Wait strategies. The default, Wait.forListeningPort(), waits until the mapped port accepts connections. An open port is not a ready service, so prefer Wait.forLogMessage(regex, times) or Wait.forHttp("/actuator/health").forStatusCode(200). PostgreSQLContainer already waits for "database system is ready to accept connections" to appear twice, because Postgres restarts once after running its init scripts.
  • Host and port. Always ask: getHost() (not necessarily localhost: remote Docker and Docker-in-Docker differ) and getMappedPort(6379) or getFirstMappedPort(). Modules wrap this, as in pg.getJdbcUrl().

static final PostgreSQLContainer<?> PG = new PostgreSQLContainer<>("postgres:16-alpine").withReuse(true);

With reuse enabled, a container whose configuration hash matches a running one is reattached instead of started, and it is not removed at the end, so the next local run skips startup entirely. It is meant for developer loops, not CI, and you are responsible for stale data in it.

Keeping the suite fast
  • Pull once. The first run downloads images; cache them on CI agents or use a registry mirror (hub.image.name.prefix).
  • Start rarely. Static containers per class, or one container per JVM for the whole suite (L195); never per method unless isolation demands it.
  • Start in parallel. Startables.deepStart(pg, redis).join() starts independent containers concurrently.
  • Make the database cheap. Small images and withTmpFs(Map.of("/var/lib/postgresql/data", "rw")) trade durability you don't need for speed; PostgreSQLContainer already starts Postgres with fsync=off.
  • Split the suite. Container tests are *IT classes run by Failsafe (L184), so mvn test stays fast.
What breaks in production
  • Hard-coded localhost:5432. Works on a laptop, fails on CI with remote Docker or a port already taken. Always use getHost() and the mapped port.
  • latest images. The suite's behaviour changes on the day a new major is published. Pin the version production runs.
  • Port-only waiting. "Connection refused" or "the database system is starting up" in 1 run out of 20: the port was open before the service was ready.
  • Skipped, not run. disabledWithoutDocker on a CI agent without Docker turns every integration test into "skipped" and the build stays green. Make CI fail if Docker is missing.
  • Zombie containers. Ryuk disabled plus crashed builds fill the agent's disk; clean up explicitly if you must disable it.

WireMock: Stubbing External HTTP APIs

40m video45m practice

Your HTTP client code is only half-tested until you have seen it handle a 503, a slow response and a dropped connection. WireMock is a real HTTP server whose answers you script, so the client runs its real networking code against exactly the responses, delays and faults each test needs.

Why not call the real API

A test that calls the real payment gateway moves money or needs a sandbox account, shares rate limits with everyone else, fails when the network does, needs credentials on CI, and can't be told "decline this card" or "take four seconds" on demand. Mocking the client class (L190) avoids all that but skips the code most likely to be wrong: URL building, headers, JSON serialization, status-code handling, timeouts and retries. WireMock sits in the middle: real HTTP on localhost, scripted behaviour.

Three ways to run it

  • JUnit 5 extension, in-process. Declarative @WireMockTest starts one server per test class on a random port, injects WireMockRuntimeInfo, and points the static DSL (stubFor, verify) at it. Programmatic @RegisterExtension WireMockExtension gives you a configurable instance, and several of them for several APIs.
  • Standalone: java -jar wiremock-standalone-3.x.jar --port 8089 or the wiremock/wiremock Docker image, configured through JSON files or the /__admin REST API. Useful for manual testing and for other teams.
  • Testcontainers module: WireMockContainer (from org.wiremock.integrations.testcontainers) runs the official image with your mapping files, for when the stub must be reachable from other containers.

Coordinates are org.wiremock:wiremock for 3.x (the old com.github.tomakehurst group is 2.x). In Spring Boot 3 projects prefer org.wiremock:wiremock-standalone, which shades its Jetty, to avoid clashes with the Jetty version Boot manages.

Stubbing, matching, and templating

class PaymentClientTest {

    @RegisterExtension
    static WireMockExtension gateway = WireMockExtension.newInstance()
            .options(wireMockConfig().dynamicPort())
            .failOnUnmatchedRequests(true)                  // a request no stub matched fails the test
            .build();

    PaymentClient client;

    @BeforeEach
    void setUp() {   // base URL, 500 ms timeout, up to 3 attempts on 5xx / timeout / connection error
        client = new PaymentClient(URI.create(gateway.baseUrl()), Duration.ofMillis(500), 3);
    }

    @Test
    void chargesAndParsesTheReceipt() {
        gateway.stubFor(post(urlEqualTo("/v1/charges"))
                .withHeader("Authorization", matching("Bearer .+"))
                .withHeader("Content-Type", containing("application/json"))
                .withRequestBody(matchingJsonPath("$.amount", equalTo("25.00")))
                .willReturn(okJson("""
                        {"id": "ch_1", "status": "succeeded"}""")));

        assertThat(client.charge("c-1", new BigDecimal("25.00"))).isEqualTo("ch_1");
        gateway.verify(exactly(1), postRequestedFor(urlEqualTo("/v1/charges")));
    }
}
Definition · stub mapping

A mapping pairs a request pattern (method, URL pattern, header, query and body matchers, optional scenario state) with a response definition (status, headers, body or body file, transformers, delay or fault). For each incoming request WireMock evaluates every mapping; if several match, the one with the highest priority wins (atPriority(1) beats atPriority(5)), and among equal priorities the most recently added. That is how a specific stub can override a broad default.

Match onBuilder
Method and URLget(urlEqualTo("/rates?base=EUR")) (path and query exactly), urlPathEqualTo("/rates") (path only), urlMatching("/orders/[0-9]+") (regex), urlPathTemplate("/orders/{id}")
Query parameters.withQueryParam("base", equalTo("EUR")), combined with urlPathEqualTo
Headers.withHeader("Authorization", matching("Bearer .+")), absent()
JSON bodyequalToJson(json, ignoreArrayOrder, ignoreExtraElements), matchingJsonPath("$.amount", equalTo("25.00"))
XML or text bodymatchingXPath("//amount[text()='25.00']"), matching(".*refund.*"), containing("refund")

Response templating builds the response from the request with Handlebars. In WireMock 3 templating is enabled per stub by naming the transformer (or for every stub with globalTemplating(true)):

stubFor(get(urlPathTemplate("/orders/{id}"))

                {"id": "{{request.pathSegments.[1]}}",

                 "echo": "{{jsonPath request.body '$.customer'}}"}""")

Latency, faults and stateful scenarios

    @Test
    void retriesOnceAfterA503() {
        gateway.stubFor(post("/v1/charges").inScenario("flaky")
                .whenScenarioStateIs(Scenario.STARTED)
                .willReturn(aResponse().withStatus(503).withHeader("Retry-After", "0"))
                .willSetStateTo("recovered"));
        gateway.stubFor(post("/v1/charges").inScenario("flaky")
                .whenScenarioStateIs("recovered")
                .willReturn(okJson("{\"id\": \"ch_2\", \"status\": \"succeeded\"}")));

        assertThat(client.charge("c-1", BigDecimal.TEN)).isEqualTo("ch_2");
        gateway.verify(exactly(2), postRequestedFor(urlEqualTo("/v1/charges")));
    }

    @Test
    void givesUpOnASlowGateway() {
        gateway.stubFor(post("/v1/charges").willReturn(okJson("{}").withFixedDelay(2_000)));
        assertThatThrownBy(() -> client.charge("c-1", BigDecimal.TEN))
                .isInstanceOf(GatewayUnavailableException.class);
    }

    @Test
    void connectionResetIsRetriedThenReported() {
        gateway.stubFor(post("/v1/charges").willReturn(aResponse().withFault(Fault.CONNECTION_RESET_BY_PEER)));
        assertThatThrownBy(() -> client.charge("c-1", BigDecimal.TEN))
                .isInstanceOf(GatewayUnavailableException.class);
        gateway.verify(exactly(3), postRequestedFor(urlEqualTo("/v1/charges")));
    }
  • Latency. withFixedDelay(ms), withUniformRandomDelay(lo, hi), withLogNormalRandomDelay(median, sigma), or withChunkedDribbleDelay to trickle the body. This is how you prove a timeout is set at all.
  • Faults. Fault.CONNECTION_RESET_BY_PEER, EMPTY_RESPONSE, MALFORMED_RESPONSE_CHUNK, RANDOM_DATA_THEN_CLOSE: failures below HTTP that a status code can't simulate.
  • Error statuses. serverError(), status(429) with Retry-After, unauthorized(): the retry, back-off and circuit-breaker paths.
  • Scenarios. A named state machine shared by its stubs: each stub applies only in one state and may move the scenario to another. Use it for "fail, then succeed", or for create-then-get flows where the second call must see the first. resetAllScenarios() returns every scenario to STARTED.

Verification, recording, and stub files

verify(exactly(2), postRequestedFor(urlEqualTo("/v1/charges")).withHeader("Idempotency-Key", matching(".+"))) checks the journal; moreThan, lessThanOrExactly and friends give other counts, and findAll(...) returns the requests for AssertJ. When nothing matched, WireMock answers 404 and logs the closest stubs with a diff; failOnUnmatchedRequests(true) turns that into a test failure.

Record and playback. Proxy to the real (sandbox) API once and save what comes back as mappings: startRecording("https://sandbox.pay.example"), exercise the client, stopRecording(); or run standalone with --proxy-all="https://sandbox.pay.example" --record-mappings. Review and trim the recordings (remove secrets, generalise URLs), then replay offline. aResponse().proxiedFrom(url) on a low-priority catch-all stub forwards everything you haven't stubbed.

                "queryParameters": { "base": { "equalTo": "EUR" } } },

In Spring tests, point the application's base-URL property at the server, for example registry.add("payments.base-url", gateway::baseUrl) in a @DynamicPropertySource.

What breaks in production
  • Stubs looser than the contract. any(anyUrl()) returning 200 lets a client with a wrong path or a missing header pass. Match what the real API requires, and verify the request.
  • Stubs that drift. The provider renames a field; your hand-written stub still returns the old one. Refresh by recording against the sandbox, and add consumer-driven contracts (L198).
  • Only the happy failure. Retries tested with 500s but never with a timeout or a reset; production's first slow day exhausts the thread pool.
  • Silent 404s. A client that maps 404 to "not found" passes a test whose stub never matched. Fail on unmatched requests.

REST Assured & API-Level Testing

40m video45m practice

An API test drives the service the way a client does: real HTTP in, real status, headers and JSON out. REST Assured makes those tests read like the request itself, and the same test can run against a server started by the test or against a deployed environment.

given, when, then

<dependency><groupId>io.rest-assured</groupId><artifactId>rest-assured</artifactId><scope>test</scope></dependency>
<dependency><groupId>io.rest-assured</groupId><artifactId>json-schema-validator</artifactId><scope>test</scope></dependency>
<!-- versions managed by the Spring Boot BOM; static imports: io.restassured.RestAssured.*, org.hamcrest.Matchers.* -->
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class OrderApiIT {

    @LocalServerPort int port;
    RequestSpecification api;

    @BeforeEach
    void spec() {
        api = new RequestSpecBuilder()
                .setBaseUri("http://localhost").setPort(port).setBasePath("/api")
                .setContentType(ContentType.JSON)
                .addHeader("Authorization", "Bearer " + TestTokens.forCustomer("c-1"))
                .build();
    }

    @Test
    void createsThenFetchesAnOrder() {
        var request = new CreateOrder("c-1", List.of(new LineRequest("SKU-1", 2)));

        String id =
            given().spec(api).body(request)                        // Jackson serializes the record
            .when().post("/orders")
            .then().log().ifValidationFails()
                .statusCode(201)
                .header("Location", containsString("/api/orders/"))
                .body("status", equalTo("NEW"))
                .body("lines", hasSize(1))
                .body("lines[0].sku", equalTo("SKU-1"))
                .body(matchesJsonSchemaInClasspath("schemas/order.json"))
            .extract().path("id");

        OrderDto fetched =
            given().spec(api).pathParam("id", id)
            .when().get("/orders/{id}")
            .then().statusCode(200)
            .extract().as(OrderDto.class);                         // Jackson again, into a record

        assertThat(fetched.lines()).extracting(LineDto::quantity).containsExactly(2);
    }
}

given() builds the request (spec, headers, params, body), when() sends it with a verb and path, and then() asserts on the response; extract() leaves the chain with a value for the next call. A RequestSpecification built once per test holds the base URI, port, base path, content type and auth, so tests carry only what is specific to them.

Requests: URI, params, headers, auth, cookies, bodies

Passing a String body sends it verbatim, which is how you test malformed input.

Assertions: Hamcrest, JSON paths, schemas

Definition · REST Assured paths

The path in body(path, matcher) is Groovy GPath, not JSONPath: data.items[0].id indexes, data.items.id collects the id of every item into a list, data.items.size() calls a method, and closures filter: data.items.find { it.price > 10 }.name, data.items.findAll { it.stock == 0 }. The extracted value is then checked with a Hamcrest matcher.

.body("data.items[0].id", equalTo(5))
.body("data.items.size()", is(3))
.body("data.items.id", hasItems(5, 7))
.body("data.items.find { it.price > 10 }.name", equalTo("Desk"))
.body("data.items.findAll { it.stock == 0 }", empty())
.body("data.total", equalTo(12.5f))                 // decimals parse as Float by default
.body(matchesJsonSchemaInClasspath("schemas/order.json"))

JSON numbers with a fraction are returned as Float unless you configure otherwise, so equalTo(12.5) (a Double) fails against a correct response. Either compare with 12.5f, or switch money fields to BigDecimal with config(RestAssuredConfig.config().jsonConfig(JsonConfig.jsonConfig().numberReturnType(JsonPathConfig.NumberReturnType.BIG_DECIMAL))). Schema validation (from json-schema-validator) checks the whole shape in one assertion: required fields, types, formats, no unexpected properties if the schema says so. It is the cheap first line of defence against accidental contract changes.

Debugging: logging and filters

given().log().all() prints the request; then().log().all() the response; log().ifValidationFails() and log().ifError() print only when there is something to look at. RestAssured.enableLoggingOfRequestAndResponseIfValidationFails() sets that globally. Logging and other cross-cutting behaviour are filters (RequestLoggingFilter, ResponseLoggingFilter, ErrorLoggingFilter, or your own Filter that adds a correlation id); add them to the spec. Mask secrets with LogConfig.logConfig().blacklistHeader("Authorization") before anything reaches CI logs.

Where the server comes from, and how it compares

Against the test's own server. @SpringBootTest(webEnvironment = RANDOM_PORT) starts the full application on a free port, injected with @LocalServerPort. Prefer a per-test RequestSpecification to the static RestAssured.port = …, which is global mutable state that parallel test classes overwrite. Combine with Testcontainers (L195) and WireMock (L196) for the dependencies.

Against a deployed environment. The same tests, with the base URI from configuration (System.getProperty("api.base")) and no Spring context, become post-deploy smoke tests. Tag them (@Tag("smoke")), keep them read-only or self-cleaning, and never rely on data you didn't create.

What breaks in production

  • Float versus Double. equalTo(12.5) fails against a correct 12.5 in JSON; worse, someone "fixes" the API instead of the assertion.

  • Shared-environment pollution. Smoke tests that create orders on staging and never delete them, or that assert on order 42 existing.

Coverage, Mutation Testing, Contract Testing & Phase 8 Capstone

Coverage tells you which code your tests executed, not whether they would notice it breaking. Mutation testing measures the second thing by breaking the code on purpose; together with contracts at service boundaries, it turns "we have lots of tests" into evidence. The capstone applies all of Phase 8 to the Day 80 repository and the Day 152 job engine.

JaCoCo: what the counters mean

JaCoCo's agent (added to Surefire's argLine by prepare-agent) records which bytecode probes ran; report renders target/site/jacoco/index.html.

Definition · JaCoCo counters
  • Instructions: bytecode instructions executed; the finest-grained counter, independent of formatting.
  • Branches: outcomes of if and switch; if (a && b) has four. A line where only some outcomes ran is partly covered.
  • Lines: a line counts as covered when at least one of its instructions ran.
  • Complexity: cyclomatic complexity, and "missed" complexity, roughly the number of additional tests needed to cover every path.

Reading the report. Drill from bundle to package to class to source. Lines are green (covered), yellow (partly: some instructions or branches missed) or red (never run); a margin diamond marks a branch point and its tooltip says "1 of 2 branches missed". Sort by missed branches: ten in the retry logic matter more than a hundred lines of generated toString.

Coverage is a floor, not a goal

class ShippingCoverageOnlyTest {             // 100% line and branch coverage of Shipping (L183)
    @Test
    void coversEverythingChecksNothing() {
        new Shipping().costCents(1_000);
        new Shipping().costCents(5_000);
        assertThrows(IllegalArgumentException.class, () -> new Shipping().costCents(-1));
    }
}

Every line and both outcomes of each condition ran, so JaCoCo reports 100%, yet the test would pass if shipping were always free. Low coverage is informative (that code is certainly untested); high coverage is not (executed, perhaps never checked). Use a gate to stop regressions; once people write tests to move the number, it stops measuring anything (Goodhart's law). This is why the threshold set up in L182 should stay modest.

Mutation testing with PIT

Algorithm · how PIT runs
  1. Run the test suite once, recording which tests cover which lines.
  2. Generate mutants by applying mutation operators to the bytecode of the target classes. Defaults include conditional boundaries (< to <=), negated conditionals, math, increments, removed void calls and replaced return values.
  3. For each mutant, run only the tests covering the mutated line, fastest first, stopping at the first failure.
  4. Classify: killed (a test failed or timed out), survived (all covering tests passed), no coverage (no test ran the line).
  5. Report mutation coverage (killed / all) and test strength (killed / covered), with survivors marked on their source lines.

    </dependency>

Mutation testing is CPU-heavy: scope it to the domain, use history for incremental runs, and run the full analysis nightly or on changed modules in pull requests. Not every survivor is a missing test; an equivalent mutant behaves exactly like the original, and the right response is to note it. The score beats coverage as a quality signal because a test can only kill a mutant by asserting something.

Consumer-driven contracts

WireMock stubs (L196) are a consumer's private beliefs about a provider, free to drift. In consumer-driven contract testing the consumer's tests record the interactions it relies on (the request, and the response fields it reads) into a contract; the provider's build replays every consumer's contract against the real provider and fails if one would break. Pact generates JSON contracts from consumer tests and shares them through a broker that answers "can I deploy this version?"; Spring Cloud Contract has contracts written provider-side in a DSL, generating provider tests and WireMock stub jars for consumers. Day 418 implements both (L418).

What breaks in production
  • Gaming the gate. Assertion-free tests written to reach 85% satisfy JaCoCo and fail PIT; that is why both gates exist.
  • A lost agent. A hand-written Surefire argLine without @{argLine} silently drops JaCoCo, and coverage drops to 0%.
  • Mutation runs nobody waits for. Unscoped PIT takes hours, gets disabled, and never comes back. Scope it; make it incremental.
  • Stubs without contracts. Green consumer tests against an API that changed last week.
