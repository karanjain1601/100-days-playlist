Spring Core

This phase opens up the Spring container: how bean definitions become objects, how injection is resolved, how scopes, lifecycle callbacks, post-processors, profiles and conditions shape the graph, and how proxies add transactions, caching and aspects. It follows the raw-servlet work of Phase 11. Its milestone project is a mini IoC container, built from scratch with @Component scanning, constructor injection and AOP proxies, which demystifies everything Spring Boot and Spring MVC do in the phases that follow.

By the end of this phase you can

  • Choose scopes deliberately, fix the scoped-proxy problem four ways, and break circular dependencies by redesign rather than by flags.
  • Write your own BeanPostProcessor, BeanDefinitionRegistryPostProcessor, Condition and auto-configuration, and debug them with the condition evaluation report.
  • Externalise configuration through property sources, profiles and conversion, keeping secrets out of the repository.
  • Write ordered @Aspect advice with precise pointcuts, and diagnose the self-invocation, final-method and @PostConstruct proxy traps.
  • Decouple modules with transactional events, and run scheduled and async work on bounded, correctly sized pools, safely across several instances.

L259 · DAY 259

The Spring Ecosystem: What It Is and Why It Won

40m video30m practice

Spring began as a bet that plain Java objects, wired by a container and decorated by proxies, could replace the heavyweight EJB component model. Twenty years on, the core is still the same: a dependency-injection container plus AOP. Boot, Data, Security and the rest of the portfolio are built on top of it.

The problem Spring solved

In J2EE 1.x and 2.x, a transactional business object was an EJB. You wrote a home interface, a remote or local interface, and a bean class implementing container callbacks. Every remote method declared RemoteException, XML deployment descriptors carried vendor-specific variants, and nothing ran outside a full application server, so a unit test meant a deploy. Finding collaborators meant JNDI lookups scattered through business code. Rod Johnson's Expert One-on-One J2EE Design and Development (2002) shipped a framework as sample code. His follow-up with Juergen Hoeller, J2EE Development without EJB (2004), argued that most applications needed EJB's services (transactions, pooling, security) but not its component model.

DefinitionSpring's thesis, as it shipped in 1.0 (2004): write POJOs (plain classes with no framework base class), let an IoC container construct and wire them through dependency injection, and add enterprise services declaratively with AOP proxies, for example @Transactional instead of container-managed EJB transactions. Business code stays testable with new and mocks.
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

interface Greeter { String greet(String name); }

record PoliteGreeter(String prefix) implements Greeter {     // a POJO: no Spring imports at all
    public String greet(String name) { return prefix + ", " + name; }
}

@Configuration
class AppConfig {
    @Bean
    Greeter greeter() { return new PoliteGreeter("Good morning"); }
}

public class HelloSpring {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class)) {
            System.out.println(ctx.getBean(Greeter.class).greet("Ada"));
        }
    }
}

Interview trap
  • "Spring Boot is a different framework from Spring." Boot is auto-configuration plus starters that set up Spring Framework beans; the container is identical.
  • "Spring replaced Java EE." It replaced the EJB component model for most teams, but it still builds on Java EE (now Jakarta EE) APIs: Servlet, JPA, Bean Validation and JMS.
  • "Spring is magic." Every annotation is processed by a named bean (a post-processor or a proxy creator) that you can find, debug and replace (L269).

Inversion of Control & Dependency Injection

45m video45m practice

A class that creates its own collaborators with new has chosen them forever. Dependency injection moves that choice outside the class, to a composition root or a container, so the same code runs against PostgreSQL in production and against a two-line fake in a unit test.

The problem with new

new JdbcOrderRepository(...) inside a service does three harmful things. It hard-codes the implementation, so switching to a cache or a remote API means editing the service. It hides the dependency: the constructor signature does not reveal that this class needs a database and an SMTP server. And it prevents substitution: a unit test cannot run without real infrastructure, so it becomes a slow, flaky integration test or is never written.

IoC, DI and the Hollywood Principle

DefinitionInversion of Control is the general principle that a framework or caller controls the flow and calls your code, instead of your code calling the library. Template methods, callbacks, servlet doGet and event listeners are all IoC. This is the Hollywood Principle: "don't call us, we'll call you". Dependency Injection is one specific form of IoC: an object receives its collaborators (through its constructor, a setter or a field) instead of creating or looking them up.

The same service three ways

import java.math.BigDecimal;
import java.util.Optional;

record Order(long id, String email, BigDecimal total) {}

// Abstractions owned by the business code
interface OrderRepository { Optional<Order> find(long id); }
interface Mailer { void send(String to, String body); }

// Real infrastructure (stubs here)
class JdbcOrderRepository implements OrderRepository {
    public Optional<Order> find(long id) { throw new IllegalStateException("needs PostgreSQL"); }
}
class SmtpMailer implements Mailer {
    public void send(String to, String body) { throw new IllegalStateException("needs SMTP"); }
}

// 1. new inside the class: hard-coded and invisible. Untestable without a DB and SMTP.
class ReceiptServiceV1 {
    private final OrderRepository repo = new JdbcOrderRepository();
    private final Mailer mailer = new SmtpMailer();
    void sendReceipt(long id) { var o = repo.find(id).orElseThrow(); mailer.send(o.email(), "Total " + o.total()); }
}

// 2. Manual factory: substitutable, but through mutable global state that tests must reset.
final class Factory {
    static OrderRepository orders = new JdbcOrderRepository();
    static Mailer mailer = new SmtpMailer();
}
class ReceiptServiceV2 {
    void sendReceipt(long id) {
        var o = Factory.orders.find(id).orElseThrow();
        Factory.mailer.send(o.email(), "Total " + o.total());
    }
}

// 3. Constructor injection: explicit, final, supplied from outside.
class ReceiptService {
    private final OrderRepository repo;
    private final Mailer mailer;
    ReceiptService(OrderRepository repo, Mailer mailer) { this.repo = repo; this.mailer = mailer; }
    void sendReceipt(long id) { var o = repo.find(id).orElseThrow(); mailer.send(o.email(), "Total " + o.total()); }
}
import static org.junit.jupiter.api.Assertions.assertEquals;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;
import org.junit.jupiter.api.Test;

class ReceiptServiceTest {
    @Test
    void mailsTheTotal() {                                     // no container, no mocks library
        var order = new Order(7, "ada@example.com", new BigDecimal("19.99"));
        List<String> sent = new ArrayList<>();
        var service = new ReceiptService(id -> Optional.of(order), (to, body) -> sent.add(to + ": " + body));
        service.sendReceipt(7);
        assertEquals(List.of("ada@example.com: Total 19.99"), sent);
    }
}

V1 can be tested only against real infrastructure. V2 can be tested by assigning Factory.orders and Factory.mailer before each test and restoring them afterwards; parallel tests then interfere through that shared static state. Version 3 is tested by passing lambdas. The interfaces are the seams: places where behaviour can be swapped without editing the code under test. Mockito, fakes and stubs all depend on those seams existing.

The Dependency Inversion Principle

Principle · Dependency inversion(Robert C. Martin) High-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions. The practical consequence: the interface lives with its client. OrderRepository belongs in the orders package and is shaped by what ReceiptService needs, not by what JDBC offers. DI is the mechanism that hands the implementation in. DIP is the design rule that decides where the interface lives.

Containers vs manual wiring, and the service locator

The place where objects are assembled is the composition root, usually main: new ReceiptService(new JdbcOrderRepository(), new SmtpMailer()). For a CLI tool, a library, a small Lambda function or a dozen classes, manual wiring is honestly fine: it is explicit, compile-checked and has no startup cost. A container earns its keep when the graph grows to hundreds of objects, lifecycles (singleton, request, prototype) and cross-cutting proxies (transactions, security), and when configuration varies by environment. That is the job of Spring's ApplicationContext (L261).

Service locator: the anti-pattern DI replacedA service locator is a registry that classes query for their collaborators: Locator.get(Mailer.class), or a JNDI lookup in EJB 2. It is also inversion of control, but dependencies vanish from the constructor. You discover them only by reading the method bodies, missing registrations fail at runtime in the middle of a request, and tests must configure a global registry. Calling applicationContext.getBean(...) inside business code is the same anti-pattern in Spring clothing.
Interview trap
  • "IoC and DI are the same thing." DI is one kind of IoC; callbacks and template methods are others.
  • "DIP means put an interface on every class." An interface with one implementation and no seam that tests or variants need is ceremony. DIP is about the direction of dependencies across layers.
  • "You need Spring to do DI." Constructor parameters are DI. The container only automates the wiring.
  • Injecting the ApplicationContext and calling getBean "to avoid circular dependencies" turns DI back into a service locator.

Practice · 45 min

  1. Write tests for all three ReceiptService versions. Record what each needs (real infrastructure, static resets, lambdas), and run the V2 tests in parallel to see them interfere.
  2. Add an AuditLog dependency to version 3 and watch the compiler point at every place that must supply it. Then do the same to V1 and note the difference.
  3. Reorganise the code into orders and orders.jdbc packages so that orders compiles without orders.jdbc. Check this with a module or ArchUnit rule.
  4. Write a manual composition root for 6–8 classes. Note where it starts to hurt; that is the point where a container helps.

The Container: BeanFactory, ApplicationContext & Context Hierarchy

40m video40m practice

Spring's container is a registry of bean definitions (recipes) plus a factory that turns them into objects. BeanFactory is that minimal machine, and ApplicationContext wraps it with eager startup, events, messages, resources and environment. Nearly every Spring mystery is explained by one method: refresh().

BeanFactory vs ApplicationContext

Use the bare factory only in frameworks or extremely constrained environments. Application code always gets an ApplicationContext.

Implementations

  • AnnotationConfigApplicationContext: standalone, from @Configuration classes or package scans. Used for tests, CLIs and learning.
  • ClassPathXmlApplicationContext: legacy XML files on the classpath (L262).
  • GenericApplicationContext / GenericWebApplicationContext: flexible contexts you feed definitions into programmatically; the web variant is bound to a ServletContext.
  • AnnotationConfigServletWebServerApplicationContext: what Spring Boot creates for a servlet web app. Its onRefresh() step creates and starts the embedded Tomcat.

The startup sequence inside refresh()

Algorithm · Refresh, simplified
  1. obtainFreshBeanFactory: load bean definitions (class, scope, constructor arguments, properties, init and destroy methods) from XML or from registered configuration classes.
  2. invokeBeanFactoryPostProcessors: run every BeanFactoryPostProcessor. ConfigurationClassPostProcessor parses @Configuration, @ComponentScan, @Import and @Bean into more definitions, and placeholder configurers resolve ${...}.
  3. registerBeanPostProcessors: instantiate the BeanPostProcessors first, because they must exist before any other bean is created.
  4. initMessageSource, initApplicationEventMulticaster, onRefresh (Boot starts Tomcat here), registerListeners.
  5. finishBeanFactoryInitialization: create every non-lazy singleton, injecting dependencies and running callbacks and post-processors (L268).
  6. finishRefresh: start SmartLifecycle beans and publish ContextRefreshedEvent.

Getting beans: by type, name and generics

import org.springframework.beans.factory.support.DefaultListableBeanFactory;
import org.springframework.beans.factory.support.RootBeanDefinition;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.ResolvableType;

interface Repo<T> { String name(); }
record Order(long id) {}
record User(long id) {}
class Noisy { Noisy() { System.out.println("Noisy constructed"); } }

@Configuration
class ParentConfig {
    @Bean Repo<Order> orderRepo() { return () -> "orders"; }
    @Bean Repo<User> userRepo() { return () -> "users"; }
}

@Configuration
class ChildConfig {
    @Bean Noisy noisy() { return new Noisy(); }
}

public class ContainerDemo {
    public static void main(String[] args) {
        var factory = new DefaultListableBeanFactory();          // bare factory: lazy
        factory.registerBeanDefinition("noisy", new RootBeanDefinition(Noisy.class));
        System.out.println("definition registered, nothing built yet");
        factory.getBean(Noisy.class);                            // constructed now

        try (var parent = new AnnotationConfigApplicationContext(ParentConfig.class);
             var child = new AnnotationConfigApplicationContext()) {
            child.setParent(parent);
            child.register(ChildConfig.class);
            child.refresh();                                     // eager: Noisy constructed here
            Repo<?> byName = child.getBean("userRepo", Repo.class);  // name + type check
            Repo<Order> byGeneric = child.<Repo<Order>>getBeanProvider(
                    ResolvableType.forClassWithGenerics(Repo.class, Order.class)).getObject();
            System.out.println(byName.name() + " " + byGeneric.name()
                    + " | parent sees child's bean? " + parent.containsBean("noisy")); // false
            // child.getBean(Repo.class) would throw NoUniqueBeanDefinitionException: two Repos
        }                                                        // closes child, then parent
    }
}

Inside application code you almost never call getBean; you inject instead (L260). These calls belong in tests, framework code and main.

Context hierarchies

A child context can see its parent's beans, while the parent never sees the child's. Lookups fall through to the parent when the child has no match. In a classic Spring MVC WAR, ContextLoaderListener builds the root context (services, repositories, data sources), and each DispatcherServlet builds a child servlet context (controllers, view resolvers). Several servlets can then share one service layer. Spring Boot uses a single context by default, and SpringApplicationBuilder.parent(...).child(...) builds a hierarchy when you really need one. Spring Cloud's legacy bootstrap context was a parent context that loaded remote configuration before the main context started. Since Spring Cloud 2020.0 it is off by default and replaced by spring.config.import.

Closing the context

close() publishes ContextClosedEvent, stops Lifecycle beans, then destroys singletons in reverse dependency order, running @PreDestroy, DisposableBean and destroy methods. ConfigurableApplicationContext is Closeable, so standalone apps should use try-with-resources or call registerShutdownHook(), which closes the context when the JVM exits on SIGTERM. Spring Boot registers that hook for you, which is how Kubernetes pod termination becomes a graceful shutdown.

What breaks in production
  • Duplicate beans across a hierarchy: defining services in both the root and servlet contexts (a component scan in each) creates two instances. @Transactional then works on one and not the other.
  • A standalone context never closed: connection pools and thread pools are not shut down, so the JVM does not exit or database connections leak.
  • kill -9 skips shutdown hooks entirely. Only SIGTERM gives the context a chance to close.

Configuration Styles: XML, Annotations & Java Config

40m video40m practice

XML, annotations and Java config are three front ends that produce the same thing: bean definitions in the container. Java config won because the wiring is ordinary, type-checked Java. Annotations remain the right tool for your own classes, and XML survives in codebases you will inherit.

One graph, three descriptions

import java.math.BigDecimal;
import java.time.Clock;
import java.time.LocalDate;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Import;
import org.springframework.context.annotation.ImportResource;

interface PriceRepository { BigDecimal basePrice(String sku); }

class InMemoryPriceRepository implements PriceRepository {
    private String currency = "EUR";
    public void setCurrency(String currency) { this.currency = currency; }   // for XML <property>
    public BigDecimal basePrice(String sku) { return new BigDecimal("10.00"); }
    public String currency() { return currency; }
}

class PricingService {
    private final PriceRepository repo;
    private final Clock clock;
    PricingService(PriceRepository repo, Clock clock) { this.repo = repo; this.clock = clock; }
    BigDecimal priceNow(String sku) {
        boolean weekend = LocalDate.now(clock).getDayOfWeek().getValue() >= 6;
        BigDecimal base = repo.basePrice(sku);
        return weekend ? base.multiply(new BigDecimal("0.90")) : base;
    }
}

@Configuration
class PricingConfig {                                   // Java config: wiring is plain Java
    @Bean Clock clock() { return Clock.systemUTC(); }
    @Bean PriceRepository priceRepository() {
        var repo = new InMemoryPriceRepository();
        repo.setCurrency("EUR");
        return repo;
    }
    @Bean PricingService pricingService(PriceRepository repo, Clock clock) {   // parameters = injection points
        return new PricingService(repo, clock);
    }
}

@Configuration
@Import(PricingConfig.class)                            // compose Java config classes
@ImportResource("classpath:legacy-billing.xml")         // pull in an old XML file unchanged
class AppConfig {}

XML configuration

You will meet XML in older codebases. Read it as a direct, string-based description of bean definitions:

<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:context="http://www.springframework.org/schema/context"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
           https://www.springframework.org/schema/beans/spring-beans.xsd
           http://www.springframework.org/schema/context
           https://www.springframework.org/schema/context/spring-context.xsd">
  <import resource="classpath:infra.xml"/>                      <!-- compose files -->
  <bean id="clock" class="java.time.Clock" factory-method="systemUTC"/>
  <bean id="priceRepository" class="com.acme.pricing.InMemoryPriceRepository">
    <property name="currency" value="EUR"/>                     <!-- calls setCurrency -->
  </bean>
  <bean id="pricingService" class="com.acme.pricing.PricingService">
    <constructor-arg ref="priceRepository"/>                    <!-- constructor injection -->
    <constructor-arg ref="clock"/>
  </bean>
  <!-- annotation style from XML: -->
  <context:component-scan base-package="com.acme.pricing"/>
</beans>
DefinitionEach <bean> becomes a BeanDefinition: id is the name, class (plus an optional factory-method) is the recipe, <constructor-arg> supplies constructor arguments by ref (another bean) or value (converted from a string), and <property> calls a setter. <import> merges another file. Everything is a string until the container resolves it at startup.

Annotation configuration

Annotation style puts the definition on the class itself: @Repository on InMemoryPriceRepository, @Service on PricingService, then a scan, either <context:component-scan> in XML or @ComponentScan on a configuration class (L264). A single constructor is used for injection automatically. Its limit is obvious once you try it: you cannot annotate java.time.Clock or a library's DataSource, so third-party objects still need @Bean methods (or XML).

Java configuration, and mixing all three

@Configuration plus @Bean is the modern default for infrastructure and third-party objects. Each method is a factory: its name becomes the bean name, its parameters are injection points, and its body is ordinary Java, so you can use conditionals, builders and loops. Composition uses @Import between configuration classes, and @ImportResource brings XML in. Going the other way, an XML file can declare a @Configuration class as a <bean> and enable <context:annotation-config/>. All three styles feed one registry, so a bean defined in XML can be injected into an annotated component and vice versa.

Organising configuration in a real project

A layout that scales
  • Annotate your own components (@Service, @Repository, @RestController) and let the scan find them.
  • Use @Configuration classes for infrastructure and third-party objects, one per concern: PersistenceConfig, WebConfig, MessagingConfig, SecurityConfig. Keep each one next to the feature it serves.
  • Keep the @SpringBootApplication class in the root package. Prefer Boot auto-configuration plus properties over hand-written beans, and write a bean only to override or extend.
  • Use no getBean calls and no giant AppConfig holding 80 beans. If a configuration class needs a long explanation, split it.
What breaks in production
  • Bean definition overriding: an XML bean and a @Bean with the same name. Plain Spring allows overriding by default, so one definition silently replaces the other; Boot (2.1+) refuses with BeanDefinitionOverrideException. Do not "fix" it with spring.main.allow-bean-definition-overriding=true without knowing which bean you get.
  • An XML class name left behind after a package move: the build passes and startup fails with ClassNotFoundException.
  • A scanned @Configuration that is also @Imported: harmless duplication until two versions of it diverge.

L263 · DAY 263

@Configuration, @Bean & proxyBeanMethods

45m video45m practice

A @Configuration class is not used as written. Spring subclasses it with CGLIB so that one @Bean method calling another gets the container's singleton instead of a new object. Turning that off (proxyBeanMethods = false) is faster and is what Boot does everywhere, but only if you stop making inter-bean calls.

Anatomy of a @Bean method

DefinitionA @Bean method is a factory method recorded as a bean definition. The bean's name is the method name unless you give @Bean("primaryDs"), or several names (name = {"a", "b"}), which creates aliases. initMethod and destroyMethod name lifecycle callbacks on the returned object. By default, destroyMethod is inferred: a public close() or shutdown() method is called when the context closes. Use destroyMethod = "" to turn that off. autowireCandidate = false keeps the bean out of by-type injection; it is still available by name.

The method's parameters are injection points, resolved exactly like constructor parameters, including @Qualifier, Optional, ObjectProvider and collections. The declared return type matters. Before a bean is created, the container knows only that type, so getBeanNamesForType, @ConditionalOnMissingBean and by-type injection all match against it. Declare the most specific type that callers may inject. If you declare Repository and inject JdbcOrderRepository, matching can fail, and with JDK proxies (L276) the runtime object is not that class anyway.

Inter-bean references and the CGLIB subclass

import java.util.concurrent.atomic.AtomicInteger;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

    @Bean UserDao userDao() { return new UserDao(pool()); }         // intercepted: the same one
}

@Configuration(proxyBeanMethods = false)          // lite mode: a plain class
class LiteConfig {
    @Bean Pool pool() { return new Pool(); }
    @Bean OrderDao orderDao() { return new OrderDao(pool()); }      // BUG: a second Pool
    @Bean UserDao userDao(Pool pool) { return new UserDao(pool); }  // correct lite style
}

    static void run(Class<?> config) {
        Pool.CREATED.set(0);
        try (var ctx = new AnnotationConfigApplicationContext(config)) {

        }
    }
    public static void main(String[] args) {

Full mode has two consequences. The configuration class and its @Bean methods must not be final or private, because CGLIB must subclass the class and override the methods. And the class needs a constructor that CGLIB can call. @Bean methods declared in a @Component class, or in a plain class, are always lite.

When lite mode is right

Use proxyBeanMethods = false whenever no @Bean method calls another, which is always achievable by taking dependencies as method parameters. You save the CGLIB subclass generation at startup, some memory, and reflection metadata, and the class becomes friendlier to AOT processing and GraalVM native images. Spring Boot's own auto-configuration classes all use lite mode. A good default: lite mode plus parameters everywhere, and full mode only for legacy configuration classes that rely on inter-bean calls.

Static @Bean methods for factory post-processors

BeanFactoryPostProcessors, such as PropertySourcesPlaceholderConfigurer, must run before ordinary beans are created (L261). If the @Bean method is an instance method, Spring must instantiate the configuration class very early just to call it. That instance then misses @Autowired and @Value processing, and Spring logs a warning. A static @Bean method can be called without an instance, so the configuration class is created later, normally. Static methods cannot be intercepted by CGLIB, so never call a static @Bean method from another one expecting a singleton.

Stereotypes & Component Scanning

Component scanning reads class files under some packages, keeps the ones that match its filters (by default, anything meta-annotated with @Component), and registers a bean definition for each. Stereotypes are mostly labels, but two of them change behaviour. The most common "bean not found" bug is a class that lives outside the scanned packages.

@Component and its specialisations

StereotypeWhat it adds beyond "this is a bean"
@ComponentThe base marker the default scan filter looks for, directly or as a meta-annotation
@ServiceNothing at runtime. It documents intent, and gives pointcuts and architecture tests something to target.
@RepositoryException translation: PersistenceExceptionTranslationPostProcessor proxies such beans, so JPA, JDBC and Hibernate exceptions become Spring's DataAccessException hierarchy

Configuring the scan

import java.io.IOException;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.FilterType;
import org.springframework.core.type.classreading.MetadataReader;
import org.springframework.core.type.classreading.MetadataReaderFactory;
import org.springframework.core.type.filter.TypeFilter;

interface OrdersModule {}                  // marker: its package is the scan root
interface CommandHandler {}                // implementations become beans with no annotation
class ExperimentalPricing {}

@Configuration
@ComponentScan(
    basePackageClasses = OrdersModule.class,                     // type-safe: survives renames
    includeFilters = @ComponentScan.Filter(type = FilterType.ASSIGNABLE_TYPE, classes = CommandHandler.class),
    excludeFilters = {
        @ComponentScan.Filter(type = FilterType.REGEX, pattern = ".*\\.legacy\\..*"),
        @ComponentScan.Filter(type = FilterType.ASSIGNABLE_TYPE, classes = ExperimentalPricing.class),
        @ComponentScan.Filter(type = FilterType.CUSTOM, classes = SkipDeprecated.class)
    },
    lazyInit = false)                                            // true: scanned beans become lazy
class ScanConfig {}

class SkipDeprecated implements TypeFilter {
    @Override
    public boolean match(MetadataReader reader, MetadataReaderFactory factory) throws IOException {
        // reads bytecode metadata through ASM; the class itself is never loaded
        return reader.getAnnotationMetadata().hasAnnotation(Deprecated.class.getName());
    }
}

basePackages takes strings; basePackageClasses takes a class whose package is used, which the compiler checks. useDefaultFilters = false drops the @Component rule, so only your includeFilters apply. Filter types: ANNOTATION (has, or is meta-annotated with, an annotation), ASSIGNABLE_TYPE (is a subtype of a class or interface), ASPECTJ (an AspectJ type pattern such as com.acme..*Stub; needs aspectjweaver), REGEX (on the fully-qualified class name), and CUSTOM (your TypeFilter). Exclude filters win over include filters.

Spring Boot's implicit scan, and the missing bean

The symptom is NoSuchBeanDefinitionException: No qualifying bean of type 'com.acme.common.AuditService' (or "Parameter 0 of constructor … required a bean … that could not be found") although the class is clearly annotated. The fixes, best first: move ShopApplication up to the common root package; or set @SpringBootApplication(scanBasePackages = {"com.acme.shop", "com.acme.common"}); or @Import the class explicitly. JPA entities and Spring Data repositories use the same root, through AutoConfigurationPackages, so outside it they also need @EntityScan and @EnableJpaRepositories. Never put the main class in the default (unnamed) package: Boot would then scan every jar on the classpath.

Bean names

A scanned component's default name is its simple class name with the first letter lowercased: OrderService becomes orderService. Following java.beans.Introspector, a name whose first two letters are capitals stays as is (URLParser stays URLParser). @Component("orders"), or the value of any stereotype, sets it explicitly. Two classes with the same simple name in different packages collide with ConflictingBeanDefinitionException. Rename one, name it explicitly, or configure FullyQualifiedAnnotationBeanNameGenerator for the scan.

Scanning cost, and composed stereotypes

The scan walks every .class resource under the base packages and parses its metadata with ASM, without loading the class. The cost therefore grows with the number of classes under the scanned roots. Keep roots narrow; never scan com or org. The old spring-context-indexer build-time index is deprecated as of Spring 6.1, and AOT processing is the forward path for startup-critical apps. Meta-annotations let you encode architecture in one place:

import java.lang.annotation.*;
import org.springframework.core.annotation.AliasFor;
import org.springframework.stereotype.Service;

@Transactional                               // and every public method is transactional

}

    void handle(String sku) { /* application logic */ }
}
DefinitionA meta-annotation is an annotation placed on another annotation. Spring's annotation model (MergedAnnotations) searches through them, so a class annotated with @UseCase counts as @Service, @Component and @Transactional. @AliasFor forwards attribute values down the chain. @RestController, @SpringBootApplication and @GetMapping are all composed this way.
What breaks in production
  • A module jar with a different package root: its components are silently ignored until an injection point fails at startup, or, worse, an Optional injection silently gets nothing.
  • @Repository replaced by @Component during a refactor: callers catching DataAccessException no longer catch anything.
  • Test configurations picked up by the main scan (a @Configuration under src/test in a scanned package), which replaces real beans in other tests. Boot's @TestConfiguration exists to avoid this.

Injection Types & Circular Dependencies

45m video45m practice

Use constructor injection by default. It makes dependencies explicit, final and checked at construction time, so a class can be tested with new. Setter injection is for the genuinely optional, and field injection is a shortcut that hides design problems. A circular dependency is a design smell: Spring can paper over some cycles, and since Boot 2.6 it refuses to by default.

Constructor, setter and field injection

import java.time.Clock;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

interface PaymentGateway { String id(); }
interface FraudCheck { boolean ok(long cents); }
interface Metrics { void count(String name); }
interface Notifier { Notifier NONE = msg -> { }; void send(String msg); }

@Service
class CheckoutService {
    private final Map<String, PaymentGateway> gateways;   // bean name -> bean
    private final List<FraudCheck> checks;                // every implementation, @Order-sorted
    private final ObjectProvider<Metrics> metrics;        // optional, resolved lazily on use
    private final Clock clock;
    private Notifier notifier = Notifier.NONE;            // optional, with a safe default

    // The only constructor, so no @Autowired is needed (Spring 4.3+)
    CheckoutService(Map<String, PaymentGateway> gateways, List<FraudCheck> checks,
                    ObjectProvider<Metrics> metrics, Optional<Clock> clock) {
        this.gateways = gateways;
        this.checks = checks;
        this.metrics = metrics;
        this.clock = clock.orElseGet(Clock::systemUTC);   // Optional: absent bean -> empty
    }

    @Autowired(required = false)                          // setter injection: skipped if no bean
    void setNotifier(Notifier notifier) { this.notifier = notifier; }

    String pay(String gateway, long cents) {
        if (!checks.stream().allMatch(c -> c.ok(cents))) return "rejected";
        metrics.ifAvailable(m -> m.count("checkout.pay"));
        notifier.send("paid " + cents + " at " + clock.instant());
        return gateways.get(gateway).id();
    }
}

@Service
class LegacyCheckoutService {
    @Autowired private PaymentGateway gateway;            // field injection: see below
}
DefinitionConstructor injection passes every dependency through the constructor. Fields can be final (immutable and safely published), a missing bean fails at construction rather than on first use, and a test simply calls new. Setter injection calls a setter after construction. It suits optional collaborators with a default, and dependencies you may legitimately reconfigure. Field injection sets a private field by reflection.

Field injection is convenient but wrong, for five reasons. Dependencies are hidden: the constructor says nothing. Fields cannot be final. new LegacyCheckoutService() in a test produces an object full of nulls, so tests need a container or reflection tricks. Adding the twelfth @Autowired field is painless, which encourages god classes, whereas a twelve-parameter constructor would warn you. And the class cannot work outside a DI container, which ties a domain object to framework reflection.

Optional dependencies: required=false, Optional, ObjectProvider

  • @Autowired(required = false) on a setter or field: if there is no candidate, the injection is skipped and your default stays.
  • Optional<T> as a parameter: empty if there is no bean. It is resolved once, at construction.
  • ObjectProvider<T>: a handle resolved on each use, with getIfAvailable(), getIfUnique(), ifAvailable(...), orderedStream() and getObject(). It is lazy, tolerates zero or several candidates, and also fetches prototype or scoped beans freshly (L267). Boot's auto-configuration uses it everywhere. In plain unit tests, new DefaultListableBeanFactory().getBeanProvider(Metrics.class) gives an empty provider.

Circular dependencies and the three-level cache

Algorithm · Resolving a field or setter cycle
  1. Create A by calling its constructor, then register in L3 a factory that returns A's early reference (through getEarlyBeanReference, so an AOP proxy can be created early if needed).
  2. Populate A: it needs B, so start creating B.
  3. Populate B: it needs A. Look up A: L1 misses, L2 misses, L3 hits. Call the factory, move the result to L2, and inject it into B.
  4. B finishes and goes into L1. A receives B, finishes initialisation, and goes into L1; its L2 entry is removed.

Constructor cycles fail outright with BeanCurrentlyInCreationException: to construct A you need B, and to construct B you need A, and there is no half-built object to share. Spring Boot 2.6+ sets spring.main.allow-circular-references=false, so even field and setter cycles fail at startup with a cycle diagram:

The dependencies of some of the beans in the application context form a cycle:
┌─────┐
|  orderService defined in file [.../OrderService.class]
↑     ↓
|  invoiceService defined in file [.../InvoiceService.class]
└─────┘
Action: Relying upon circular references is discouraged and they are prohibited by default. ...
The correct fixes, in order
  1. Extract a third collaborator. The cycle usually means both classes share a responsibility. Move it into PricingPolicy, and have both depend on that.
  2. Invert one edge with an event. OrderService publishes OrderPlaced, and InvoiceService listens, so neither references the other (L277).
  3. @Lazy on one constructor parameter as a last resort. Spring injects a lazy-resolution proxy, so the cycle still exists and is merely deferred to the first call.
Re-enabling allow-circular-references is not a fix. Early references also clash with proxies. Put an @Async bean in a cycle and startup fails with "has been injected into other beans … in its raw version as part of a circular reference, but has eventually been wrapped".

Injecting collections and generic types

List<FraudCheck> receives every FraudCheck bean, sorted by @Order or Ordered (L266). Map<String, PaymentGateway> is keyed by bean name, which makes a ready-made strategy registry: gateways.get("stripe"). Set<T> and arrays work too. With no candidates, a required collection field or setter fails, while a single constructor's collection parameter receives an empty collection. If empty is a valid state, say so explicitly with ObjectProvider<T>.orderedStream(). Generic parameters act as qualifiers: Repository<Order> and Repository<User> resolve to different beans with no annotations.

Interview trap
  • "Spring resolves circular dependencies." Only for field and setter injection on singletons, never for constructors or prototypes, and Boot forbids it by default since 2.6.
  • "Field injection is fine because Mockito's @InjectMocks handles it." @InjectMocks silently leaves fields null when it cannot match them. Constructor injection fails loudly.
  • "@Autowired is required on constructors." Not for a single constructor since Spring 4.3. With several constructors, mark the one to use.

@Autowired Resolution, @Qualifier & @Primary

40m video45m practice

Autowiring is a deterministic algorithm. Match by type (generics included), narrow by qualifiers, then break ties with primary, priority and finally the name. If you know the steps, every NoUniqueBeanDefinitionException tells you exactly which annotation is missing.

The resolution algorithm

Algorithm · Resolving one injection point
  1. Candidates by type: every bean whose type is assignable to the declared type, including generic parameters (Repository<Order> does not match Repository<User>). Beans with autowireCandidate = false are excluded.
  2. Qualifier filter: if the injection point carries @Qualifier("x") or a custom qualifier annotation, keep only candidates whose definition carries a matching qualifier. A string qualifier also matches the bean name.
  3. Exactly one left: inject it. None: NoSuchBeanDefinitionException (unless the point is optional).
  4. Several left: pick the single @Primary candidate. Spring 6.2 also added @Fallback, which marks beans to use only when nothing else qualifies.
  5. Otherwise, pick the candidate with the highest @Priority (jakarta.annotation.Priority).
  6. Otherwise, pick the candidate whose bean name equals the parameter or field name. Parameter names need the -parameters compiler flag, which Boot's parent POM sets; Spring 6.1 stopped reading debug info.
  7. Otherwise: NoUniqueBeanDefinitionException.

Note the order: a qualifier is a filter applied before the tie-breakers, so @Qualifier beats @Primary. Also, @Order does not select a single bean; it only sorts collections.

import java.lang.annotation.*;
import java.util.List;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.core.annotation.Order;

interface Cache { String name(); }

@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Qualifier                                       // this makes @Fast a qualifier
@interface Fast {}

record CacheReport(String any, String fast, String cold, List<String> all) {}

@Configuration(proxyBeanMethods = false)
class CacheConfig {
    @Bean @Primary @Order(2) Cache redisCache() { return () -> "redis"; }
    @Bean @Fast @Order(1) Cache localCache() { return () -> "caffeine"; }
    @Bean @Qualifier("archive") @Order(3) Cache s3Cache() { return () -> "s3"; }

    @Bean
    CacheReport report(Cache any,                          // several candidates: @Primary -> redis
                       @Fast Cache fast,                   // qualifier filter -> caffeine
                       @Qualifier("archive") Cache cold,   // string qualifier -> s3
                       List<Cache> all) {                  // all three, sorted by @Order
        return new CacheReport(any.name(), fast.name(), cold.name(),
                all.stream().map(Cache::name).toList());   // [caffeine, redis, s3]
    }
}
DefinitionA qualifier is metadata on both sides of an injection. On the bean definition, @Qualifier("archive"), or any annotation itself meta-annotated with @Qualifier, labels the bean. On the injection point, the same annotation requires that label. Custom qualifier annotations such as @Fast or @Postgres are type-safe: a typo is a compile error, the IDE can find usages, and they can carry attributes (@Region("eu")).

Without an explicit qualifier, every bean has an implicit qualifier equal to its name. That is why @Qualifier("redisCache") also works. It is fragile, though: renaming the method silently changes the name.

@Primary, ordering and generics

@Primary is right when one bean is the obvious default and the others are special-purpose. A typical case is two DataSources: the main one is primary and the reporting replica is qualified. It is a smell when it covers ambiguity nobody resolved, or when a test configuration uses it to override a production bean. In tests, prefer @MockitoBean or a dedicated profile. Two primaries among the same candidates is itself an error. Ordering of injected Lists and arrays follows Ordered/PriorityOrdered, @Order or @Priority, lowest value first, with unordered beans last. Map<String, T> is keyed by bean name and its iteration order is not something to rely on. Generic types act as implicit qualifiers: with Repository<Order> and Repository<User> beans, an injection point declaring Repository<Order> gets exactly one, and a raw Repository sees both.

Bean Scopes

40m video40m practice

A scope decides how many instances a bean definition produces and how long each one lives. The trap is the boundary between scopes: a singleton that holds a reference to a shorter-lived bean keeps the first instance forever, unless something such as a proxy or a provider fetches the right one on every call.

Singleton: one per container, and thread-safety

Definitionsingleton (the default) means one shared instance per bean definition per container. This is not the Gang of Four Singleton pattern. Nothing stops you defining two beans of the same class, two contexts each hold their own instance, and the class needs no static instance or private constructor. Every thread that calls the bean shares that one object.

That sharing creates an obligation: no mutable per-request state in instance fields. A private User currentUser or a SimpleDateFormat field in a @Service is a race condition, for the same reason as a servlet field (L254). Keep fields final and immutable, or thread-safe (ConcurrentHashMap, atomics), and keep per-call data in locals and parameters.

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

final class TenantContext {                            // bound by a servlet filter per request
    private static final ThreadLocal<String> CURRENT = new ThreadLocal<>();
    static void set(String tenant) { CURRENT.set(tenant); }
    static void clear() { CURRENT.remove(); }
    static String get() {
        String t = CURRENT.get();
        if (t == null) throw new IllegalStateException("no tenant bound to this thread");
        return t;
    }
}

class TenantScope implements Scope {
    private final Map<String, Map<String, Object>> byTenant = new ConcurrentHashMap<>();

    @Override
    public Object get(String name, ObjectFactory<?> factory) {
        Map<String, Object> beans = byTenant.computeIfAbsent(TenantContext.get(), t -> new ConcurrentHashMap<>());
        Object bean = beans.get(name);
        if (bean == null) {
            bean = factory.getObject();                // outside any map lock: may create other beans
            Object raced = beans.putIfAbsent(name, bean);
            if (raced != null) bean = raced;
        }
        return bean;
    }
    @Override public Object remove(String name) {
        Map<String, Object> beans = byTenant.get(TenantContext.get());
        return beans == null ? null : beans.remove(name);
    }
    @Override public void registerDestructionCallback(String name, Runnable callback) { } // simplified
    @Override public Object resolveContextualObject(String key) { return null; }
    @Override public String getConversationId() { return TenantContext.get(); }
}

        configurer.addScope("tenant", new TenantScope());
        return configurer;
    }
}

Scopes, virtual threads and reactive code

Request, session and custom thread-bound scopes all rest on a ThreadLocal. The bound value does not follow work handed to another thread. An @Async method, a CompletableFuture.supplyAsync or a parallel stream sees "No thread-bound request found". Virtual threads keep the thread-per-request model, so request scope works within the request's own virtual thread, but very many virtual threads each holding large ThreadLocal values cost memory. Scoped values (final in JDK 25) are the structured replacement. In WebFlux, a request hops between threads, so there is no request scope; per-request data travels in Reactor's Context instead.

What breaks in production
  • Per-user data in a singleton field: user A occasionally sees user B's cart, and only under load.
  • A prototype holding a connection or file: @PreDestroy never runs, so resources leak. Close them yourself, or do not make the bean a prototype.
  • A request-scoped bean touched from @Async or a scheduled job: IllegalStateException: No thread-bound request found. Pass the values explicitly.
  • Session-scoped beans that are not Serializable under session replication or Spring Session, so failover loses the session or throws.

Bean Lifecycle & Callbacks

45m video40m practice

Every singleton passes through a fixed sequence: constructed, populated, made aware, initialised, possibly wrapped in a proxy, used, destroyed. The one ordering fact that causes real bugs is that the proxy is created after @PostConstruct. Initialisation code therefore runs on the raw object, with no transactions, async or caching.

The full sequence

DefinitionLifecycle order for a singleton: instantiation (constructor injection) → population (field and setter injection, @Value) → BeanNameAware, BeanClassLoaderAware, BeanFactoryAware → ApplicationContextAware and the other context-aware interfaces (applied by an early post-processor) → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct → InitializingBean.afterPropertiesSet → custom initMethod → postProcessAfterInitialization (proxies are created here) → ready. On close: @PreDestroy → DisposableBean.destroy → custom destroyMethod.

Why @PostConstruct cannot use your own proxies

Suppose @PostConstruct void warmUp() { loadAll(); } calls a @Transactional or @Cacheable method on the same bean. this is the raw target, and the proxy does not exist yet. Even if it did, a self-call would bypass it (L276). So loadAll() runs with no transaction (lazy loading fails, writes are not committed atomically) and no caching. Other beans injected into this one are fully initialised, but they may still be early references in a cycle. Work that needs the finished, proxied application belongs in a later hook.

Lazy initialisation and destruction

@Lazy on a bean (or spring.main.lazy-initialization=true for all of them) defers creation to first use. Startup is faster, which helps in development and on serverless cold starts. The cost is that you lose fail-fast: a missing property or a broken bean surfaces on the first request in production, and that request pays the creation latency. Prefer eager singletons in services, with lazy initialisation for rarely used, expensive beans. On close, singletons are destroyed in reverse dependency order, so a bean is destroyed before the beans it depends on, and a repository can still use its DataSource in @PreDestroy. Prototype beans get no destruction callbacks, because the container does not track them after handing them out (L267).

What breaks in production
  • A transactional or cached call inside @PostConstruct: it works in a unit test and silently runs without a transaction in the app. Move it to an ApplicationRunner or a ready listener.
  • Slow @PostConstruct work, such as loading 2 GB of reference data: startup passes the liveness probe's timeout, Kubernetes restarts the pod, and you get a crash loop.
  • Global lazy initialisation in production: a misconfigured bean is discovered only by the first customer who hits that endpoint.
  • @PreDestroy that blocks (waiting for a queue to drain with no timeout): shutdown hangs until the orchestrator sends SIGKILL.

BeanPostProcessor & BeanFactoryPostProcessor

45m video45m practice

Spring has two extension points. Factory post-processors edit recipes (bean definitions) before any bean exists; bean post-processors edit or replace objects as each one is created. Every Spring annotation that "does something" (@Autowired, @Transactional, @Async) is implemented by one of them, and you can write your own the same way.

Two phases: definitions, then instances

DefinitionA BeanFactoryPostProcessor implements postProcessBeanFactory(ConfigurableListableBeanFactory). It runs after all definitions are loaded and before any regular bean is instantiated. PropertySourcesPlaceholderConfigurer is the classic example: it rewrites ${app.url} in definition values into real strings. A BeanDefinitionRegistryPostProcessor extends it with postProcessBeanDefinitionRegistry, which runs earlier and may register new definitions. ConfigurationClassPostProcessor is one: it turns @Configuration, @ComponentScan, @Import and @Bean into definitions. Spring Data's repository registrars produce a definition per repository interface in the same phase. A BeanPostProcessor implements postProcessBeforeInitialization and postProcessAfterInitialization on each instance, and whatever it returns is what the container stores and injects.

Writing your own: an auditor and a timing proxy

import java.lang.annotation.*;
import java.lang.reflect.*;
import org.springframework.beans.factory.BeanFactory;
import org.springframework.beans.factory.BeanFactoryAware;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.beans.factory.config.ConfigurableListableBeanFactory;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.AnnotationUtils;
import org.springframework.util.ClassUtils;

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.TYPE)
@interface Timed {}

/** Flags mutable instance fields in singletons: the race condition from L267. */
class MutableStateAuditor implements BeanPostProcessor, BeanFactoryAware {
    private ConfigurableListableBeanFactory factory;
    @Override public void setBeanFactory(BeanFactory bf) { factory = (ConfigurableListableBeanFactory) bf; }

    @Override
    public Object postProcessBeforeInitialization(Object bean, String name) {
        if (!factory.containsBeanDefinition(name) || !factory.getBeanDefinition(name).isSingleton()) return bean;
        Class<?> type = ClassUtils.getUserClass(bean);       // unwrap CGLIB subclasses
        if (!type.getPackageName().startsWith("com.acme")) return bean;
        for (Field f : type.getDeclaredFields()) {
            int mod = f.getModifiers();
            if (!Modifier.isStatic(mod) && !Modifier.isFinal(mod)) {
                System.out.println("AUDIT " + name + ": mutable field '" + f.getName() + "' in a singleton");
            }
        }
        return bean;
    }
}

/** Wraps @Timed beans in a JDK dynamic proxy that logs each call's duration. */
class TimingPostProcessor implements BeanPostProcessor, Ordered {
    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        Class<?> type = bean.getClass();
        if (AnnotationUtils.findAnnotation(type, Timed.class) == null) return bean;
        Class<?>[] interfaces = ClassUtils.getAllInterfacesForClass(type);
        if (interfaces.length == 0) return bean;            // JDK proxies need an interface
        InvocationHandler handler = (proxy, method, args) -> {
            long start = System.nanoTime();
            try {
                return method.invoke(bean, args);
            } catch (InvocationTargetException e) {
                throw e.getCause();                         // rethrow the real exception
            } finally {
                System.out.printf("%s.%s took %d us%n", name, method.getName(), (System.nanoTime() - start) / 1_000);
            }
        };
        return Proxy.newProxyInstance(type.getClassLoader(), interfaces, handler);
    }
    @Override public int getOrder() { return Ordered.LOWEST_PRECEDENCE; } // wrap last, outermost
}

Register both as static @Bean methods, or as scanned components. Note what the timing proxy changes: the bean is now a $Proxy implementing only the interfaces, so anyone injecting the concrete class fails. Spring's own proxy creators handle this by switching to CGLIB (L276).

Ordering, and the early-instantiation caveat

Post-processors run in tiers: PriorityOrdered, then Ordered (lower value first), then the rest. Within a tier, the order follows getOrder(). Because bean post-processors must exist before every other bean, the container creates them, and everything they depend on, at the start of bean creation, before most post-processors are registered. Those early beans miss the processors that come after them, and Spring logs:

Bean 'auditRepository' of type [com.acme.AuditRepository] is not eligible for getting processed
by all BeanPostProcessors (for example: not eligible for auto-proxying)

That bean will have no @Transactional proxy, and nothing else warns you. So keep post-processors dependency-free. Inject an ObjectProvider or a BeanFactory and look up lazily, and declare their @Bean methods static (L263). A post-processor itself is never advised by AOP.

Registering beans dynamically with the BeanDefinition API

import java.util.List;
import org.springframework.beans.factory.config.ConfigurableListableBeanFactory;
import org.springframework.beans.factory.support.AbstractBeanDefinition;
import org.springframework.beans.factory.support.BeanDefinitionBuilder;
import org.springframework.beans.factory.support.BeanDefinitionRegistry;
import org.springframework.beans.factory.support.BeanDefinitionRegistryPostProcessor;

record PartnerClient(String partner, String baseUrl) {}

/** One PartnerClient bean per configured partner, named "acmeClient", "globexClient", and so on. */
class PartnerClientRegistrar implements BeanDefinitionRegistryPostProcessor {
    private final List<String> partners;
    PartnerClientRegistrar(List<String> partners) { this.partners = List.copyOf(partners); }

    @Override
    public void postProcessBeanDefinitionRegistry(BeanDefinitionRegistry registry) {
        for (String p : partners) {
            AbstractBeanDefinition def = BeanDefinitionBuilder
                    .genericBeanDefinition(PartnerClient.class, () -> new PartnerClient(p, "https://" + p + ".example.com"))
                    .setLazyInit(true)
                    .getBeanDefinition();
            registry.registerBeanDefinition(p + "Client", def);
        }
    }

    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory factory) { }  // nothing to edit
}

A BeanDefinition describes the class or instance supplier, scope, lazy flag, primary flag, qualifiers, dependencies, and init and destroy methods. BeanDefinitionBuilder creates them fluently. At runtime, before refresh, GenericApplicationContext.registerBean(PartnerClient.class, supplier, customizer) does the same programmatically. After refresh, the registry should be treated as frozen: adding beans to a running context is not supported for normal application wiring.

What breaks in production
  • A post-processor injecting a repository: the repository and its whole dependency graph are created early, without transaction proxies, and only an INFO log line tells you.
  • Returning null from a post-processor method. Spring then keeps the bean it already had and skips the remaining post-processors, which surprises people who expected to remove the bean.
  • A post-processor that loads classes or does I/O for every bean: it runs thousands of times at startup and adds seconds.

DefinitionA placeholder ${key} is resolved against the Environment by a PropertySourcesPlaceholderConfigurer, which Boot registers automatically. ${key:default} supplies a fallback, and ${key:} an empty string. Defaults may themselves contain placeholders (${a:${b}}). An unresolvable placeholder without a default fails at startup with Could not resolve placeholder 'key'. @Value works on fields, setters, constructor parameters and @Bean method parameters. The parameter forms are preferable, because the value can be final.

Environment.getProperty(key) returns a string or null; getProperty(key, type, default) converts the value; getRequiredProperty throws if the key is missing; containsProperty tests presence. @PropertySource adds a file to the stack. It cannot read YAML without a custom PropertySourceFactory, it ranks below Boot's own config files, and it is processed too late to affect early auto-configuration. In Boot, prefer spring.config.import=classpath:partner.yml.

The property source hierarchy

Boot maps environment variables with relaxed binding: PARTNER_POOLSIZE or PARTNER_POOL_SIZE can satisfy partner.pool-size. Write @Value keys in canonical kebab-case so that this mapping works. /actuator/env (secured) shows every source and which one supplied each key, and is the fastest way to debug precedence.

Conversion: ConversionService, Converter, Formatter

import org.springframework.boot.convert.ApplicationConversionService;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.convert.ConversionService;
import org.springframework.core.convert.converter.Converter;

record Money(long minor, String currency) {}

class StringToMoney implements Converter<String, Money> {      // "19.99 EUR"
    @Override
    public Money convert(String source) {
        String[] parts = source.trim().split("\\s+");
        if (parts.length != 2) throw new IllegalArgumentException("expected '<amount> <currency>': " + source);
        long minor = new java.math.BigDecimal(parts[0]).movePointRight(2).longValueExact();
        return new Money(minor, parts[1]);
    }
}

@Configuration(proxyBeanMethods = false)
class ConversionConfig {
    @Bean
    ConversionService conversionService() {    // the bean NAME matters: the container uses it for @Value
        var service = new ApplicationConversionService();       // keeps Boot's Duration, DataSize, lists
        service.addConverter(new StringToMoney());
        return service;
    }
}
// now: @Value("${fees.minimum:0.50 EUR}") Money minimumFee

A Converter<S, T> is a stateless, one-way, locale-independent conversion. A Formatter<T> is a two-way, locale-aware print/parse pair, used for web form binding and display. A ConversionService holds both and picks one by source and target type. Boot installs ApplicationConversionService on the bean factory, which is why "30s" becomes a Duration, "10MB" a DataSize, and "a,b" a List of two elements. In plain Spring, without it, use String[] or SpEL (#{'${servers}'.split(',')}, L273) for lists. For MVC binding, Boot also registers Converter and Formatter beans automatically. For @ConfigurationProperties, mark them @ConfigurationPropertiesBinding.

Why @ConfigurationProperties wins, and where secrets go

Scattered @Value("${partner.timeout}") strings repeat keys in many places, hide typos until runtime, cannot be validated as a group, and give the IDE no metadata. A @ConfigurationProperties("partner") record (Day 282) binds the whole subtree to typed, immutable, @Validated fields with relaxed binding and generated metadata. Keep @Value for one-off values.

SecretsNever commit passwords, API keys or tokens in application.properties or YAML: they live in git history forever. Inject them at runtime instead. You can use environment variables set by the platform, files mounted by Kubernetes Secrets and read with spring.config.import=optional:configtree:/run/secrets/, or a secret manager (Vault, AWS Secrets Manager, Azure Key Vault) through its Spring Cloud integration. Keep only non-secret defaults in the repo, and make secret keys required with no default, so that a missing secret fails at startup.
What breaks in production
  • A default that hides a missing property: ${payments.url:http://localhost:8080} makes production silently call localhost. Give environment-specific keys no default.
  • An unexpected higher-precedence source: an old SPRING_DATASOURCE_URL in the deployment manifest overrides the carefully edited YAML.
  • @Value in a class created too early (a post-processor, or a static field): it stays null, because placeholders are resolved only for container-managed instance injection.

Profiles & Environment-Specific Wiring

35m video40m practice

A profile is a named switch, read from the Environment, that includes or excludes bean definitions and configuration documents. Use profiles for where the app runs (dev, test, prod). Use properties and conditions for what it does (features), or you end up with a combinatorial mess of profile expressions.

@Profile and profile expressions

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Profile;
import org.springframework.stereotype.Component;

interface PaymentGateway { String charge(long cents); }

@Component
@Profile("prod | staging")                       // either profile active
class StripeGateway implements PaymentGateway {
    public String charge(long cents) { return "stripe:" + cents; }   // real HTTP call in practice
}

@Component
@Profile("!prod & !staging")                     // dev, test, default: never charge real cards
class FakeGateway implements PaymentGateway {
    public String charge(long cents) { return "fake:" + cents; }
}

record DbSettings(String url) {}

@Configuration(proxyBeanMethods = false)
class DbConfig {
    @Bean @Profile("dev & !cloud")                 // a laptop without cloud services
    DbSettings embedded() { return new DbSettings("jdbc:h2:mem:orders"); }

    @Bean @Profile("cloud")
    DbSettings managed() { return new DbSettings("jdbc:postgresql://db.internal:5432/orders"); }
}

@Component
@Profile("default")                              // active only when NO profile was set
class RefuseToStartWithoutProfile {
    RefuseToStartWithoutProfile() {
        throw new IllegalStateException("set SPRING_PROFILES_ACTIVE (dev, test, staging or prod)");
    }
}
Definition@Profile is a condition (L272). It can sit on a @Component class, on a @Configuration class (gating every bean inside), or on a @Bean method. Its value is a profile expression: a name (prod), a negation (!prod), & (and), | (or) and parentheses. Mixing & and | requires parentheses: prod & (eu | us). Several values in an array are OR-ed. The default profile, named default (changeable with spring.profiles.default), is active only when no profile is explicitly active.

Activating profiles

SPRING_PROFILES_ACTIVE=prod java -jar orders.jar          # environment variable (containers)
java -Dspring.profiles.active=prod -jar orders.jar         # JVM system property
java -jar orders.jar --spring.profiles.active=prod,eu      # command-line argument
spring.profiles.active=dev                                 # in application.properties (weakest)

These follow the normal precedence (L270), so the command line beats the environment variable, which beats the file. Programmatically, call SpringApplication.setAdditionalProfiles("eu") before run, or ConfigurableEnvironment.setActiveProfiles(...) before a plain context's refresh(). When several profiles are active, their order matters: for profile-specific properties, the last active profile wins.

Profile-specific files, groups and include

# application.yml
spring:
  application:
    name: orders
  profiles:
    group:                       # Boot 2.4+: one name activates several
      prod: [proddb, prodmq]
      dev: [localdb]
payments:
  url: http://localhost:9999     # base value
---
spring:
  config:
    activate:
      on-profile: prod           # this document applies only when prod is active

  url: https://payments.example.com
---
spring:
  config:
    activate:
      on-profile: "dev | test"
logging:
  level:
    com.acme: debug

application-{profile}.yml files and on-profile documents override the base file for the keys they set; everything else is inherited. spring.profiles.include adds profiles on top of the active ones. Since Boot 2.4 it may not appear in profile-specific documents, and neither may spring.profiles.active. Groups are the clearer tool for "prod always means proddb and prodmq too".

Environments vs features

Environment profiles (dev, test, staging, prod) describe infrastructure: which database, which URLs, how much logging. Feature profiles (with-kafka, embedded-db) describe capabilities. Mixing the two multiplies cases. You soon write @Profile("prod & !with-kafka"), nobody knows which combinations are tested, and staging drifts from production. Prefer a small, fixed set of environment profiles, and express features as properties evaluated by conditions: @ConditionalOnProperty("features.kafka.enabled") (L272). A common, healthy pattern is to mock external services in dev (FakeGateway, WireMock, an in-memory mailer) and use real clients in staging and prod, with identical code paths above the gateway interface.

import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.ActiveProfiles;

@SpringBootTest
@ActiveProfiles("test")                             // activates test profile beans and documents
class CheckoutProfileTest {
    @Autowired PaymentGateway gateway;

    @Test
    void neverChargesRealCardsInTests() {
        assertThat(gateway.charge(100)).startsWith("fake:");
    }
}

Contexts with different active profiles are cached separately by the test framework. Ten profile combinations across a test suite mean ten application contexts started, so keep test profiles few.

What breaks in production
  • No profile set in production: default is active, !prod beans load, and the fake payment gateway "succeeds" at charging nobody. The RefuseToStartWithoutProfile pattern turns this into a startup failure.
  • A typo in a profile name (SPRING_PROFILES_ACTIVE=porduction) is not an error. Nothing matches, and you get default behaviour.
  • Secrets in application-prod.yml in the repo: profile files are still committed files (L270).
  • Staging with its own feature profiles that production lacks: tests pass against wiring that production never runs.

@Conditional & the @ConditionalOn* Family

40m video40m practice

A condition is a yes/no question asked while bean definitions are being registered: is this class on the classpath, is this property set, does the user already have such a bean? Spring Boot's auto-configuration is hundreds of ordinary @Configuration classes guarded by these questions. That is why adding a jar "turns on" a feature, and why your own bean replaces Boot's.

The Condition interface

Definition@Conditional(MyCondition.class) on a @Configuration class, a @Component or a @Bean method registers that definition only if MyCondition.matches(ConditionContext, AnnotatedTypeMetadata) returns true. The context offers the bean definition registry, the bean factory, the Environment, a ResourceLoader and the class loader. The metadata exposes the annotations on the annotated element, so a condition can read its own annotation's attributes. Conditions run during configuration parsing: definitions exist, but almost no beans do. A ConfigurationCondition can choose to run in the REGISTER_BEAN phase instead of PARSE_CONFIGURATION.
import java.lang.annotation.*;
import java.util.Map;
import org.springframework.context.annotation.Condition;
import org.springframework.context.annotation.ConditionContext;
import org.springframework.context.annotation.Conditional;
import org.springframework.core.type.AnnotatedTypeMetadata;

@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
@Documented
@Conditional(OnFeatureFlagCondition.class)
@interface ConditionalOnFeatureFlag {
    String value();                                  // checks features.<value>.enabled
    boolean enabledByDefault() default false;
}

class OnFeatureFlagCondition implements Condition {
    @Override
    public boolean matches(ConditionContext context, AnnotatedTypeMetadata metadata) {
        Map<String, Object> attrs = metadata.getAnnotationAttributes(ConditionalOnFeatureFlag.class.getName());
        if (attrs == null) return false;
        String key = "features." + attrs.get("value") + ".enabled";
        boolean byDefault = (Boolean) attrs.get("enabledByDefault");
        return context.getEnvironment().getProperty(key, Boolean.class, byDefault);
    }
}
// usage: @Bean @ConditionalOnFeatureFlag("recommendations") RecommendationService recommendations() {...}

The "user override wins" pattern

import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;

@AutoConfiguration                                               // lite-mode configuration, ordered
@ConditionalOnClass(name = "com.acme.audit.sdk.AuditSdk")       // only if the SDK jar is present
@ConditionalOnProperty(prefix = "acme.audit", name = "enabled", havingValue = "true", matchIfMissing = true)
public class AuditAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean                                    // the user's own AuditClient wins
    AuditClient auditClient(Environment env) {
        return new AuditClient(env.getProperty("acme.audit.endpoint", "https://audit.example.com"));

Every good auto-configuration has this shape: guarded by classpath and properties, it supplies defaults the user can replace simply by declaring a bean. You will build exactly this as a custom starter on Day 286.

Evaluation ordering hazards

@ConditionalOnBean and @ConditionalOnMissingBean check the definitions registered so far. In your own configuration classes the parse order is an implementation detail, so the same condition can flip between builds. Boot therefore documents these conditions as intended for auto-configuration classes only. Auto-configurations are loaded through a deferred import selector (L263) after all user configuration, and among themselves are ordered with @AutoConfiguration(after = DataSourceAutoConfiguration.class). A missing after makes a condition silently evaluate against an incomplete registry.

Spring Expression Language (SpEL)

35m video35m practice

SpEL is a small expression language that can call methods, navigate objects, filter collections and reach static types. That power makes annotations such as @Cacheable(key = "#id") and @PreAuthorize concise. It is also why evaluating an expression that came from a user is a remote-code-execution bug.

#{…} vs ${…}

Definition${key} is a property placeholder: plain text substitution from the Environment, with no logic (L270). #{expr} is a SpEL expression, evaluated against an evaluation context with access to beans, system properties and types. In @Value, placeholders are resolved first, and the resulting text is then evaluated as SpEL, so the two compose: #{'${app.servers}'.split(',')}. Placeholders cannot contain expressions, but expressions can contain placeholders.

The language in one program

import java.util.List;
import org.springframework.expression.ExpressionParser;
import org.springframework.expression.spel.standard.SpelExpressionParser;
import org.springframework.expression.spel.support.SimpleEvaluationContext;
import org.springframework.expression.spel.support.StandardEvaluationContext;

record Customer(String name, String tier) {}
record Order(long id, String status, long totalCents, Customer customer) {}

public class SpelDemo {
    public static void main(String[] args) {
        ExpressionParser parser = new SpelExpressionParser();
        List<Order> orders = List.of(new Order(1, "PAID", 4_500, new Customer("Ada", "GOLD")),
                                     new Order(2, "NEW", 900, null),
                                     new Order(3, "PAID", 12_000, new Customer("Lin", "SILVER")));
        var ctx = new StandardEvaluationContext(orders);            // #root is the list
        ctx.setVariable("min", 1_000);                              // referenced as #min

        List<?> big = parser.parseExpression("#root.?[status == 'PAID' and totalCents > #min]")
                            .getValue(ctx, List.class);             // selection: orders 1 and 3
        List<?> ids = parser.parseExpression("#root.![id]").getValue(ctx, List.class);  // projection: [1, 2, 3]
        Object firstPaid = parser.parseExpression("#root.^[status == 'PAID'].id").getValue(ctx);    // 1
        List<?> names = parser.parseExpression("#root.![customer?.name ?: 'guest']")   // safe nav + Elvis
                              .getValue(ctx, List.class);           // [Ada, guest, Lin]
        Object tier = parser.parseExpression("{'GOLD': 0.1, 'SILVER': 0.05}['GOLD']").getValue(ctx); // map: 0.1
        Object max = parser.parseExpression("T(java.lang.Math).max(3, 7)").getValue(ctx);           // static: 7
        Object sb = parser.parseExpression("new java.lang.StringBuilder('ab').reverse().toString()").getValue(ctx);
        Object label = parser.parseExpression("#root.size() > 2 ? 'many' : 'few'").getValue(ctx);   // ternary

        var restricted = SimpleEvaluationContext.forReadOnlyDataBinding().build();   // for untrusted input
        Object ok = parser.parseExpression("totalCents > 1000").getValue(restricted, orders.get(0)); // true
        // "T(java.lang.Runtime).getRuntime().exec('...')" against `restricted` throws: no type references
        System.out.println(big.size() + " " + ids + " " + firstPaid + " " + names + " "
                + tier + " " + max + " " + sb + " " + label + " " + ok);
    }
}

The syntax covers literals ('text', 42, true, null, inline lists {1,2} and maps {'k': v}), arithmetic, relational operators (also spelled lt, gt, eq), and/or/not, regex matches, the ternary a ? b : c, Elvis a ?: b (b if a is null) and safe navigation a?.b (null instead of an NPE). For collections, .?[cond] selects matching elements, .^[cond] and .$[cond] take the first and last match, .![expr] projects, and map['key'] indexes. T(Type) reaches static members and new constructs objects. In bean-aware contexts, @beanName references a bean; in @Value a bare bean name also works (#{pricingService.defaultCurrency}).

Parsing programmatically: two contexts

SpelExpressionParser.parseExpression compiles a string into an Expression, which is thread-safe and reusable, so cache parsed expressions. You can also enable compiled mode (SpelParserConfiguration) for hot paths. Evaluation needs an EvaluationContext. StandardEvaluationContext enables everything: type references, constructors, bean references and arbitrary method calls. SimpleEvaluationContext is the restricted subset meant for data binding. It offers property access, and method calls only if you opt in, but no T(), no new and no bean references.

SpEL injection is realIf attacker-controlled text reaches parseExpression(...).getValue(new StandardEvaluationContext()), the attacker can send T(java.lang.Runtime).getRuntime().exec('...'), and that is remote code execution. Real CVEs followed exactly this path: CVE-2022-22963 (Spring Cloud Function, a routing expression taken from an HTTP header) and CVE-2022-22947 (Spring Cloud Gateway, SpEL in routes created through the actuator). Rules: never build an expression from user input; never concatenate input into an annotation expression template you evaluate; if users must supply filters, parse them into your own small grammar or allow-list, and if SpEL is unavoidable, use SimpleEvaluationContext with read-only access.
What breaks in production
  • An expression typo inside an annotation (key = "#custmerId") surfaces only when the method first runs, often as a null cache key shared by every caller. Test cache and security expressions.
  • Missing -parameters: #id evaluates to null in @Cacheable and @PreAuthorize, which can let an authorisation check pass or fail silently. Use #p0, or keep the flag on.
  • A "flexible rules engine" built on StandardEvaluationContext, with rules editable from an admin UI: remote code execution for anyone who reaches that UI.

AOP Concepts & Terminology

40m video35m practice

Some concerns, such as transactions, security, metrics and retries, cut across every service. Without help they are copy-pasted around each method's real logic. Aspect-oriented programming declares them once and applies them at chosen points. Spring does this with proxies, which is both its strength (simple, no special compiler) and its limit (only calls that go through the proxy are advised).

Cross-cutting concerns: scattering and tangling

import io.micrometer.core.annotation.Timed;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

interface Security { void requireRole(String role); }
interface Tx { void begin(); void commit(); void rollback(); }
interface Metrics { void record(String name, long nanos); }
interface Ledger { void debit(String account, long cents); void credit(String account, long cents); }

class TransferServiceTangled {                       // two lines of business logic, ten of plumbing
    private final Security security; private final Tx tx; private final Metrics metrics; private final Ledger ledger;
    TransferServiceTangled(Security s, Tx t, Metrics m, Ledger l) { security = s; tx = t; metrics = m; ledger = l; }

    void transfer(String from, String to, long cents) {
        security.requireRole("TELLER");                                  // security
        long start = System.nanoTime();                                  // metrics
        tx.begin();                                                      // transactions
        try {
            ledger.debit(from, cents);
            ledger.credit(to, cents);
            tx.commit();
        } catch (RuntimeException e) {
            tx.rollback();
            throw e;
        } finally {
            metrics.record("transfer", System.nanoTime() - start);
        }
    }
}

@Service
class TransferService {                              // the same behaviour, declared
    private final Ledger ledger;
    TransferService(Ledger ledger) { this.ledger = ledger; }

    @PreAuthorize("hasRole('TELLER')")
    @Transactional
    @Timed("transfer")                               // applied by Micrometer's TimedAspect bean
    public void transfer(String from, String to, long cents) {
        ledger.debit(from, cents);
        ledger.credit(to, cents);
    }
}

The tangled version shows the two classic symptoms. Tangling: one method mixes four concerns. Scattering: the same security, timing and transaction code is repeated in every method of every service, so changing the rollback policy means editing hundreds of places, and missing one is a bug. The declared version has three annotations, and the behaviour lives in three reusable pieces of advice.

The vocabulary

Definition
  • Join point: a point in program execution where behaviour can be inserted. In Spring AOP, always a method execution.
  • Pointcut: a predicate selecting join points, for example "methods annotated with @Transactional" or execution(* com.acme..*Service.*(..)).
  • Advice: the code to run at the selected join points, with a kind: before, after returning, after throwing, after (finally) and around.
  • Aspect: a module grouping pointcuts and advice (a class annotated with @Aspect). An advisor is Spring's internal pair of one pointcut and one advice.
  • Target object: the real bean being advised. A proxy is the object that callers actually hold, which runs the advice and then delegates to the target.
  • Weaving: linking aspects into the code, at compile time, load time or (in Spring) at runtime through proxy creation.
  • Introduction: adding a new interface and its implementation to an existing bean (@DeclareParents). Rarely used.

When AOP clarifies, and when it hides

GuidelinesAOP clarifies when the concern is uniform and well known (transactions, metrics, auditing), when the join point is marked explicitly by an annotation on the method so that readers see that something happens, and when the advice contains no business decisions. It obscures when pointcuts match by package wildcards, so behaviour changes because a class moved; when aspects alter arguments or results in business-relevant ways; and when several aspects interact in an order nobody wrote down. If a debugger session requires stepping through six interceptors to reach your code, ask whether the concern is worth an aspect.
Interview trap
  • "Spring AOP can advise private methods and field access." It cannot: proxies see only calls coming through the proxy, and only to methods they can override or implement.
  • "Spring uses AspectJ." It uses AspectJ's annotations and pointcut parser. Weaving is done by proxies unless you configure load-time weaving explicitly.
  • "@Transactional needs spring-boot-starter-aop." It does not. The transaction advisor is infrastructure; the starter is for your own @Aspect classes.

@Aspect: Pointcuts, Advice Types & Ordering

An aspect is a bean with methods that say where (a pointcut expression) and when (an advice type) to run. Writing good aspects means choosing precise pointcuts, preferring explicit annotations to wildcards, using @Around only when you must control the call, and setting the order deliberately when several aspects wrap the same method.

Declaring aspects and named pointcuts

An aspect is any bean whose class carries @Aspect. @Aspect alone does not make it a component, so add @Component or declare it as a @Bean. @EnableAspectJAutoProxy registers the auto-proxy creator that turns aspects into advisors. Spring Boot enables it automatically when the AOP starter is present.

import org.aspectj.lang.annotation.Aspect;

Three real aspects

import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import java.lang.annotation.*;
import java.util.Arrays;
import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.AfterReturning;
import org.aspectj.lang.annotation.AfterThrowing;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD)
@interface Auditable { String action(); }

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD)
@interface RetryOnFailure {
    int attempts() default 3;
    long backoffMs() default 100;
    Class<? extends Throwable>[] on() default RuntimeException.class;
}

@Aspect @Component @Order(1)                                // outermost: each attempt is timed and audited
class RetryAspect {
    @Around("@annotation(retry)")                            // binds the annotation instance by name
    public Object retry(ProceedingJoinPoint pjp, RetryOnFailure retry) throws Throwable {
        for (int attempt = 1; ; attempt++) {
            try {
                return pjp.proceed();                        // around advice may proceed repeatedly
            } catch (Throwable t) {
                boolean retryable = Arrays.stream(retry.on()).anyMatch(type -> type.isInstance(t));
                if (!retryable || attempt >= retry.attempts()) throw t;
                Thread.sleep(retry.backoffMs() * attempt);   // linear backoff
            }
        }
    }
}

@Aspect @Component @Order(2)
class TimingAspect {
    private final MeterRegistry registry;
    TimingAspect(MeterRegistry registry) { this.registry = registry; }

    @Around("execution(public * com.acme..*Service.*(..))")
    public Object time(ProceedingJoinPoint pjp) throws Throwable {
        Timer.Sample sample = Timer.start(registry);
        String outcome = "success";
        try {
            return pjp.proceed();
        } catch (Throwable t) {
            outcome = t.getClass().getSimpleName();
            throw t;
        } finally {
            sample.stop(Timer.builder("service.calls")
                    .tag("method", pjp.getSignature().toShortString())
                    .tag("outcome", outcome)
                    .register(registry));
        }
    }
}

@Aspect @Component @Order(3)
class AuditAspect {
    private static final Logger audit = LoggerFactory.getLogger("AUDIT");

    @AfterReturning(pointcut = "@annotation(auditable)", returning = "result")
    public void onSuccess(JoinPoint jp, Auditable auditable, Object result) {
        audit.info("action={} method={} result={}", auditable.action(), jp.getSignature().toShortString(), result);
    }

    @AfterThrowing(pointcut = "@annotation(auditable)", throwing = "ex")
    public void onFailure(JoinPoint jp, Auditable auditable, RuntimeException ex) {
        audit.warn("action={} method={} failed: {}", auditable.action(), jp.getSignature().toShortString(), ex.toString());
    }
}

Binding forms such as @annotation(retry) and returning = "result" match by parameter name, so they need -parameters or an explicit argNames. The parameter's type also narrows the match: RuntimeException ex ignores checked exceptions.

Ordering and nesting

Aspects without @Order (or Ordered) have undefined relative order, so set it whenever two aspects can match the same method. Within one aspect class, advice of different kinds runs in a fixed precedence: @Around, @Before, @After, @AfterReturning, @AfterThrowing. Two pieces of advice of the same kind in one aspect have no defined order, so merge them or split them into separate ordered aspects. The ordering matters semantically. A retry inside the transaction re-runs work in a transaction that may already be marked rollback-only. A timer outside the retry measures the total time, while one inside measures each attempt.

What breaks in production
  • Package-wildcard pointcuts such as execution(* com.acme..*(..)), which also advise configuration classes, repositories and DTO beans. Startup slows, and odd failures appear on final classes.
  • An @Around that swallows the exception, or returns null for a primitive return type, which gives an NPE or AopInvocationException far from the cause.
  • Retrying non-idempotent work (charging a card) because the retry aspect matches every RuntimeException. Restrict it with on and annotate deliberately.
  • High-cardinality metric tags (user ids, raw URLs) added by a timing aspect, which can blow up the metrics backend.

Proxies: JDK Dynamic vs CGLIB & the Self-Invocation Trap

45m video45m practice

Every Spring AOP feature is a proxy object standing in front of your bean. A proxy can only intercept calls that arrive through it. A method calling another method on this never leaves the target, which is why @Transactional, @Cacheable, @Async and @PreAuthorize silently do nothing on self-calls.

Where proxies come from

Algorithm · Auto-proxy creation
  1. AbstractAutoProxyCreator is a BeanPostProcessor. Its subclass AnnotationAwareAspectJAutoProxyCreator is what @EnableAspectJAutoProxy and Boot register.
  2. In postProcessAfterInitialization (L268) it calls wrapIfNecessary(bean, name). Infrastructure beans and beans already proxied are skipped.
  3. It collects every advisor whose pointcut matches at least one method of the bean's class, from @Aspect beans and from infrastructure advisors (transactions, caching, security), and sorts them by order.
  4. If any match, it builds a ProxyFactory with the target and the advisors, chooses JDK or CGLIB, and returns the proxy instead of the bean.
  5. For beans in a circular reference, the same happens earlier, in getEarlyBeanReference (L265).

JDK dynamic proxies vs CGLIB

With proxyTargetClass = true, Spring always uses CGLIB. Spring Boot sets this by default (spring.aop.proxy-target-class=true), because with JDK proxies any injection point typed as the concrete class fails: BeanNotOfRequiredTypeException: Bean named 'orderService' is expected to be of type 'OrderServiceImpl' but was actually of type 'jdk.proxy2.$Proxy53'. CGLIB makes proxies transparent to injection by class, at the cost of the constraints below.

CGLIB's constraintsNo final classes: the class cannot be subclassed, so startup fails (Kotlin needs the all-open or kotlin-spring plugin). No final methods: they cannot be overridden, so they execute on the proxy instance itself with no advice. Instance fields are not copied: Spring creates the proxy through Objenesis without running your constructor, so the proxy's own fields are null or zero, and all of the state lives in the target. A final method that reads a field therefore runs on the proxy, sees null, and throws an NPE, which is a confusing bug. The constructor is not invoked for the proxy, so constructor side effects do not run twice.

The self-invocation problem

import org.springframework.aop.framework.AopContext;
import org.springframework.cache.annotation.Cacheable;
import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;

@Service
class ReportService {                                       // THE BUG
    public Report monthly(int month) { return load(month); } // this.load(): bypasses the proxy
    @Cacheable("reports") public Report load(int month) { return new Report(month); }
}

@Service
class ReportLoader {                                        // FIX 1 (best): a separate bean
    @Cacheable("reports") public Report load(int month) { return new Report(month); }
}
@Service
class ReportFacade {
    private final ReportLoader loader;
    ReportFacade(ReportLoader loader) { this.loader = loader; }
    public Report monthly(int month) { return loader.load(month); }   // crosses a proxy
}

@Service
class SelfInjecting {                                       // FIX 2: self-injection, lazily
    private final SelfInjecting self;
    SelfInjecting(@Lazy SelfInjecting self) { this.self = self; }     // a lazy proxy to our own proxy
    public Report monthly(int month) { return self.load(month); }
    @Cacheable("reports") public Report load(int month) { return new Report(month); }
}

@Service
class ExposedProxy {                                        // FIX 3: needs @EnableAspectJAutoProxy(exposeProxy = true)
    public Report monthly(int month) { return ((ExposedProxy) AopContext.currentProxy()).load(month); }
    @Cacheable("reports") public Report load(int month) { return new Report(month); }
}

The same trap hits every proxy-based feature. A @Transactional(propagation = REQUIRES_NEW) method called from a sibling method runs in the caller's transaction, or in none. An @Async method called internally runs synchronously. An internal call to a @PreAuthorize method skips the security check, which is a real authorisation hole. The fixes, ranked: (1) split the advised method into another bean, which is usually a better design anyway; (2) self-injection with @Lazy; (3) AopContext.currentProxy() with exposeProxy = true, which couples your code to Spring AOP and costs a ThreadLocal per call; (4) AspectJ load-time weaving (@EnableLoadTimeWeaving, plus mode = AdviceMode.ASPECTJ on @EnableTransactionManagement or @EnableCaching), which changes bytecode so that self-calls are advised, at the cost of a -javaagent and build complexity.

What can never be advised, and what proxies cost

private methods cannot be overridden or implemented by a proxy, and calls to them are always internal. static methods belong to the class, not the instance, so there is no object to stand in front of. Annotating either with @Transactional compiles fine and does nothing. Since Spring 6.0, class-based proxies also honour @Transactional on protected and package-visible methods. Overhead: a proxied call adds the interceptor chain (method lookup, a MethodInvocation object, each advice) on top of the call. That is typically nanoseconds to tens of nanoseconds, against microseconds to milliseconds for any I/O the method does. Measure it rather than guess:

Application Events & Decoupled Communication

45m video45m practice

Publishing an event lets one module announce "this happened" without knowing who cares. Spring's events are in-process method calls dispatched by type, synchronous unless you say otherwise, and tied to the publisher's transaction unless you choose a transaction phase. Picking the phase is the whole design decision.

Publishing and listening

import java.math.BigDecimal;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.context.event.EventListener;
import org.springframework.core.annotation.Order;
import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;

record OrderPlaced(long orderId, String email, BigDecimal total) {}      // a plain record
record LoyaltyPointsEarned(long orderId, long points) {}

interface OrderRepository { long save(String email, BigDecimal total); }

@Service
class OrderService {
    private final OrderRepository orders;
    private final ApplicationEventPublisher events;
    OrderService(OrderRepository orders, ApplicationEventPublisher events) { this.orders = orders; this.events = events; }

    @Transactional
    public long place(String email, BigDecimal total) {
        long id = orders.save(email, total);
        events.publishEvent(new OrderPlaced(id, email, total));          // no ApplicationEvent subclass
        return id;
    }
}

@Component
class OrderListeners {
    @EventListener @Order(1)
    public void reserveStock(OrderPlaced event) { }      // same thread and tx: a throw rolls back place()

    @EventListener(condition = "#event.total > 1000") @Order(2)
    public LoyaltyPointsEarned bigOrderBonus(OrderPlaced event) {        // return value = new event
        return new LoyaltyPointsEarned(event.orderId(), event.total().longValue() / 10);
    }

    @EventListener
    public void addPoints(LoyaltyPointsEarned event) { }                 // receives the follow-up

    @TransactionalEventListener                                          // AFTER_COMMIT by default
    public void sendConfirmation(OrderPlaced event) { }                  // only for committed orders

    @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
    public void countFailedOrder(OrderPlaced event) { }

    @Async                                                               // runs on a TaskExecutor thread
    @TransactionalEventListener
    @Transactional(propagation = Propagation.REQUIRES_NEW)               // its own, new transaction
    public void updateSearchIndex(OrderPlaced event) { }                 // slow work off the request path
}
DefinitionApplicationEventPublisher.publishEvent(Object) hands the event to the context's ApplicationEventMulticaster. Since Spring 4.2, any object can be an event. Non-ApplicationEvent payloads are wrapped in a PayloadApplicationEvent, and listeners still receive the payload type. @EventListener methods are matched by their parameter type, including generics and subtypes. condition is a SpEL expression over the arguments (#event by parameter name, or #p0). @Order sorts the listeners for one event. A non-void return value is published as a new event, and a collection or array is published element by element.

Synchronous by default, and what that implies

By default the multicaster calls every listener in the publisher's thread, one after another, before publishEvent returns. A synchronous listener therefore joins the publisher's transaction (its writes commit or roll back with the order), adds its latency to the request, and propagates its exceptions to the publisher, failing place(). That is right for invariants that must hold atomically. It is wrong for side effects such as email, which would be sent even when the order later rolls back.

@Async listeners

@Async on a listener (with @EnableAsync) moves it to a TaskExecutor. The publisher returns immediately, a listener failure no longer fails the request, and the listener runs without the publisher's transaction or its ThreadLocals (security context, MDC). Its exceptions are handled separately: void async methods go to the AsyncUncaughtExceptionHandler, which by default only logs, so add metrics and retries yourself. Configure a bounded executor (L278). Do not rely on the default.

@TransactionalEventListener phases

PhaseRunsUse for
AFTER_COMMIT (default)only if the publisher's transaction committedNotifications, cache invalidation, messages about facts that are now durable
AFTER_ROLLBACKonly if it rolled backFailure metrics, compensating notifications
AFTER_COMPLETIONafter commit or rollbackCleanup that must always happen
BEFORE_COMMITjust before commit, still inside the transactionLast-moment validation or flush-dependent work that can still veto the commit

The listener is registered as a transaction synchronisation, so the event is held until the phase is reached. If there is no active transaction, the event is dropped, unless you set fallbackExecution = true to run it immediately. In AFTER_COMMIT, the old transaction's resources are still bound to the thread, but it can no longer commit. Any database write in the listener therefore needs @Transactional(propagation = REQUIRES_NEW), and Spring 6.1+ rejects other propagation settings on such listeners. This phase is what stops the classic bug of sending "your order is confirmed" for an order that then rolled back.

Built-in events, and where events stop being enough

The context publishes ContextRefreshedEvent, ContextStartedEvent, ContextStoppedEvent and ContextClosedEvent. Boot adds lifecycle events, of which the useful ones are ApplicationStartedEvent, ApplicationReadyEvent (safe to start background work) and ApplicationFailedEvent. Inside a modular monolith, events are an excellent decoupling tool: orders publishes OrderPlaced, and billing, loyalty and search listen without orders depending on any of them. Spring Modulith formalises this and adds an event publication registry.

The limits of in-process eventsSpring events live in one JVM's memory. If the process crashes after commit but before an AFTER_COMMIT or async listener runs, the event is lost. There is no replay, no delivery to other services, and no back-pressure. When another service must reliably learn about the change, write the event to an outbox table in the same transaction and relay it to a broker. That is Kafka, on Day 382.
What breaks in production
  • Emails sent from a plain @EventListener: the order rolls back, and the customer still gets "confirmed".
  • A @TransactionalEventListener publishing from non-transactional code: the event is silently dropped, because nothing was listening for a commit that never comes.
  • Writes in an AFTER_COMMIT listener without REQUIRES_NEW: on older versions they were silently never committed.
  • A slow synchronous listener (an HTTP call) added by another team: your endpoint's latency doubles, and its failure rate now includes their dependency.

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executor;
import java.util.concurrent.ThreadPoolExecutor;
import net.javacrumbs.shedlock.spring.annotation.SchedulerLock;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.aop.interceptor.AsyncUncaughtExceptionHandler;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.annotation.*;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;
import org.springframework.stereotype.Service;

@Configuration
@EnableScheduling                                              // + spring.task.scheduling.pool.size=4
@EnableAsync
class TaskConfig implements AsyncConfigurer {
    private static final Logger log = LoggerFactory.getLogger(TaskConfig.class);

    @Bean
    ThreadPoolTaskExecutor asyncExecutor() {                   // bounded threads AND a bounded queue
        var executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(8);
        executor.setMaxPoolSize(16);
        executor.setQueueCapacity(500);
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy()); // back-pressure
        executor.setWaitForTasksToCompleteOnShutdown(true);
        return executor;
    }

    @Override public Executor getAsyncExecutor() { return asyncExecutor(); }   // full mode: the singleton

    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) -> log.error("@Async {} failed", method.getName(), ex);
    }
}

@Service
class Jobs {
    @Scheduled(fixedRate = 10_000)                             // every 10 s, start to start
    public void pollPartners() { }

    @Scheduled(fixedDelay = 30_000, initialDelay = 5_000)      // 30 s after the previous run ENDS
    public void retryFailedWebhooks() { }

    @Scheduled(cron = "0 0 2 * * MON-FRI", zone = "Europe/Paris")   // sec min hour day month weekday
    @SchedulerLock(name = "nightlyReport", lockAtMostFor = "PT30M", lockAtLeastFor = "PT1M")
    public void nightlyReport() { }

    @Async                                                     // the proxy returns at once
    public CompletableFuture<String> enrich(long orderId) {
        return CompletableFuture.completedFuture("enriched " + orderId);
    }
}

fixedRate runs start to start; an overrunning run delays the next, and runs of one job never overlap. fixedDelay waits after each run ends. initialDelay postpones the first run. Cron expressions have six fields: second, minute, hour, day of month, month, day of week. A five-field crontab line is rejected. Always set zone, or the JVM's default time zone decides when "02:00" is. Without a scheduler bean, Spring uses a local single-threaded scheduler, and Boot's auto-configured one defaults to spring.task.scheduling.pool.size=1. The fix is a bigger pool: set that property, or declare your own ThreadPoolTaskScheduler bean with setPoolSize(4).

@EnableAsync and @Async

An @Async proxy submits the call to an executor. A void method sends its exceptions to the AsyncUncaughtExceptionHandler; a Future or CompletableFuture completes exceptionally. Self-invocation runs synchronously (L276). The executor default is the trap. With no TaskExecutor bean, plain Spring uses SimpleAsyncTaskExecutor, which starts a new thread per call with no limit. Boot's auto-configured ThreadPoolTaskExecutor has 8 core threads but an unbounded queue, so overload becomes heap growth. Configure a bounded executor with a rejection policy you chose, as above. With virtual threads (Boot 3.2+), threads are cheap, but downstream concurrency still needs a bound.

Multi-instance scheduling with ShedLock

CREATE TABLE shedlock (name VARCHAR(64) NOT NULL, lock_until TIMESTAMP(3) NOT NULL,
                       locked_at TIMESTAMP(3) NOT NULL, locked_by VARCHAR(255) NOT NULL,
                       PRIMARY KEY (name));
-- plus @EnableSchedulerLock(defaultLockAtMostFor = "PT10M") and a JdbcTemplateLockProvider bean

With three replicas, every @Scheduled job runs three times. ShedLock takes a row lock in a shared store first, so only the instance that acquires nightlyReport runs it. lockAtMostFor frees the lock if that node dies mid-run. lockAtLeastFor stops a fast job from re-running on a node whose clock lags. Missed runs are not replayed, so exactly-once work still needs idempotency, or Quartz in cluster mode.

What breaks in production
  • resource.getFile() on a classpath resource: works in the IDE, and throws FileNotFoundException inside the fat jar. Use getInputStream().
  • A five-field Unix cron or a missing zone: the job is rejected at startup, or runs at the wrong hour after the server's time zone changes.
  • Unbounded async queues: under a traffic spike, millions of queued tasks fill the heap, and the work is lost on restart.
