Transaction Management

Phase 16 takes @Transactional apart: the transaction-manager abstraction and proxy underneath it, the exact semantics of propagation, isolation, timeouts, read-only and rollback rules, and the pitfalls that make annotated code silently non-transactional. It builds on the JDBC, JPA and Spring Data phases before it, and ends where single-database ACID ends, with the outbox, idempotent consumers and sagas that the microservices phases rely on.

By the end of this phase you can

  • Explain how a call to a @Transactional method reaches PlatformTransactionManager through a proxy, and how the connection is bound to the thread.
  • Predict the physical transactions and connections used by any combination of the seven propagation modes, and diagnose UnexpectedRollbackException.
  • Choose isolation, timeout, read-only and rollback settings deliberately, including retries around SERIALIZABLE transactions.
  • Use TransactionTemplate and after-commit callbacks to keep remote calls and side effects out of open transactions.
  • Recognize and fix self-invocation, private/final methods, swallowed exceptions, lazy-loading failures, @Async races and misleading rollback-only tests.
  • Replace dual writes with a transactional outbox, an at-least-once relay and an inbox-deduplicating consumer.
  • Ship a money-transfer service with correct propagation, retries, idempotency keys and an outbox, tested against real databases.

L329 · DAY 329

Spring's Transaction Abstraction

45m video45m practice

Spring puts one interface, PlatformTransactionManager, in front of every transactional resource, and implements @Transactional as a proxy that calls that interface around your method while parking the open connection in a thread-local. Once you can picture the proxy and the thread-bound resource holder, every propagation rule and every pitfall in this phase follows from it.

One abstraction over many transaction APIs

Each resource has its own way to demarcate a transaction: JDBC uses Connection.setAutoCommit(false) / commit(); JPA uses EntityManager.getTransaction(); JTA uses UserTransaction; JMS uses a transacted Session; Kafka uses producer transactions. Code written against one cannot move to another. Spring's answer is a strategy interface whose implementations adapt each API:

ImplementationResourceNotes
DataSourceTransactionManager / JdbcTransactionManagerOne JDBC DataSourceBoot auto-configures JdbcTransactionManager (a subclass that also translates commit exceptions) for plain JDBC apps. Supports savepoints, so NESTED works.
JpaTransactionManagerOne EntityManagerFactoryBoot's choice when JPA is on the classpath. Also exposes the underlying JDBC connection, so JdbcTemplate on the same DataSource joins the same transaction.
JtaTransactionManagerAny XA resources via a JTA providerDelegates to an application server or a standalone manager (Atomikos, Narayana). The only one that gives real two-phase commit (L334).
KafkaTransactionManagerA Kafka producer factoryFrom Spring for Apache Kafka; wraps producer beginTransaction/commitTransaction.
ChainedTransactionManagerSeveral managers in sequenceFrom Spring Data; deprecated since Spring Data 2.5. Starts each transaction in order and commits in reverse order. Not atomic.
Why chaining is not 2PC

A chained manager commits the database, then commits Kafka. If the process dies, or the second commit fails, after the first succeeded, the first is already durable and cannot be undone. There is no prepare phase and no recovery log. It is "best-effort one-phase commit": it narrows the failure window, it does not close it. The honest fix for database-plus-broker is the transactional outbox in L334.

TransactionDefinition, TransactionStatus and the three calls

The interface is tiny: getTransaction(TransactionDefinition) returns a TransactionStatus; commit(status) and rollback(status) finish it. The definition carries propagation, isolation, timeout, read-only flag and a name. The status says whether this call actually started a new physical transaction (isNewTransaction()), lets you mark it setRollbackOnly(), and (as a SavepointManager) create savepoints. Using it raw is what @Transactional does for you:

@Service
public class LedgerService {
    private final PlatformTransactionManager txManager;
    private final JdbcTemplate jdbc;

    public LedgerService(PlatformTransactionManager txManager, JdbcTemplate jdbc) {
        this.txManager = txManager;
        this.jdbc = jdbc;
    }

    public void post(long accountId, long cents) {
        var def = new DefaultTransactionDefinition();
        def.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRED);
        def.setIsolationLevel(TransactionDefinition.ISOLATION_READ_COMMITTED);
        def.setTimeout(5); // seconds
        TransactionStatus status = txManager.getTransaction(def);
        try {
            jdbc.update("update account set balance = balance + ? where id = ?", cents, accountId);
            jdbc.update("insert into ledger(account_id, cents) values (?, ?)", accountId, cents);
            txManager.commit(status);
        } catch (RuntimeException | Error ex) {
            txManager.rollback(status);
            throw ex;
        }
    }
}

Note that commit does not always commit: if the status was only a participant in an outer transaction, it does nothing physical, and if someone marked it rollback-only, it rolls back instead (the root of the trap in L330).

How @Transactional actually works

@EnableTransactionManagement (applied for you by Boot's TransactionAutoConfiguration) registers three infrastructure beans: an AnnotationTransactionAttributeSource that reads @Transactional into a TransactionAttribute, a TransactionInterceptor, and an advisor that matches beans having such annotations. A bean post-processor then replaces each matching bean with an AOP proxy (CGLIB subclass by default in Boot). Other beans receive the proxy, not your object.

Algorithm · Transaction interceptor
  1. Look up the transaction attribute for the invoked method (method annotation beats class annotation).
  2. Pick the transaction manager: the qualifier on the annotation, else the default bean.
  3. getTransaction(attribute): join, create, suspend or throw according to propagation.
  4. Invoke the target method.
  5. On exception: if rollbackOn(ex) (by default: RuntimeException or Error) call rollback, otherwise commit; rethrow.
  6. On normal return: commit, which may still roll back if the status is rollback-only.

Thread-bound resources and the shared EntityManager

TransactionSynchronizationManager keeps per-thread maps: resources keyed by factory (a DataSource maps to a ConnectionHolder, an EntityManagerFactory to an EntityManagerHolder), registered synchronizations, and the current transaction's name, read-only flag and isolation. JdbcTemplate obtains connections through DataSourceUtils.getConnection(ds), which returns the bound connection if there is one. Spring Data repositories and @PersistenceContext fields hold a shared EntityManager proxy that, on every call, looks up the EntityManager bound to the current thread.

This is why every repository call inside one transaction sees the same persistence context: findById(7) twice returns the same instance without a second query, an entity modified in one repository call is flushed at commit without a save, and JPA and JdbcTemplate writes on the same DataSource commit or roll back together under JpaTransactionManager. It is also why the binding is invisible to any other thread.

Declarative, programmatic and multiple managers

Declarative (@Transactional) is the default: boundaries sit on service methods, and the policy is readable at a glance. Programmatic (TransactionTemplate, L332) is for boundaries narrower than a method, settings decided at runtime, or code that is not a Spring bean. With two databases, define two managers and name the one you want; Boot's auto-configured manager backs off as soon as you declare your own.

@Configuration
class TxConfig {
    @Bean @Primary
    PlatformTransactionManager ordersTx(DataSource ordersDs) {
        return new JdbcTransactionManager(ordersDs);
    }

    @Bean
    PlatformTransactionManager reportingTx(@Qualifier("reportingDs") DataSource ds) {
        return new JdbcTransactionManager(ds);
    }
}

@Service
class ReportService {
    @Transactional("reportingTx")   // same as transactionManager = "reportingTx"
    public void rebuildDailyTotals() { /* writes through reportingDs */ }
}
What breaks in production
  • Wrong manager, silent autocommit. If the method's manager manages ordersDs but the code writes to reportingDs, those writes run in autocommit mode: each statement commits on its own and nothing rolls back.
  • Chained managers sold as atomic. A crash between the two commits leaves the database committed and the message unsent, or the reverse.
  • New threads see no transaction. Work handed to an executor gets a fresh thread with empty thread-locals, so it runs outside the caller's transaction and its persistence context.
  • Calling this.method(). The call never reaches the proxy, so no transaction starts (full treatment in L333).

Practice · 45 min

  1. Rewrite LedgerService.post with @Transactional, then set logging.level.org.springframework.transaction=TRACE and org.springframework.jdbc.datasource=DEBUG. Find the "Creating new transaction" and "Committing" lines.
  2. Inside a transactional method, print TransactionSynchronizationManager.isActualTransactionActive() and getCurrentTransactionName(); call the same code from a non-transactional method and compare.
  3. With JPA, load the same entity through two different repositories in one transaction and assert the two references are ==. Repeat without @Transactional and explain the difference.
  4. Configure two H2 databases with two managers. Annotate a method with the wrong one, throw after the write, and prove the write survived.

L330 · DAY 330

@Transactional Propagation

50m video50m practice

Propagation answers one question each time a transactional method is entered: is there already a transaction on this thread, and if so, do I join it, suspend it, nest inside it, or refuse? Distinguish the physical transaction (one database connection's commit) from the logical scopes that share it, and all seven modes and the rollback-only trap become predictable.

Physical and logical transactions

Definition

A physical transaction is a real resource transaction: one JDBC connection with autocommit off, ended by one COMMIT or ROLLBACK. A logical transaction is the scope of one @Transactional method invocation. Under REQUIRED, many logical scopes map onto one physical transaction; only the outermost scope (the one whose status has isNewTransaction() == true) actually commits. Inner scopes can only vote, by marking the shared transaction rollback-only.

All seven modes

PropagationTransaction existsNo transaction
REQUIRED (default)Join itCreate one
REQUIRES_NEWSuspend it, create an independent one on a second connectionCreate one
SUPPORTSJoin itRun without (but with transaction synchronization, so a shared EntityManager still lives for the scope)
NOT_SUPPORTEDSuspend it, run withoutRun without
MANDATORYJoin itThrow IllegalTransactionStateException
NEVERThrow IllegalTransactionStateExceptionRun without
NESTEDSet a savepoint in the same physical transactionCreate one (behaves like REQUIRED)

Suspension means the manager unbinds the outer connection from the thread-local, keeps it in a suspended-resources holder, and rebinds it after the inner scope completes. The outer connection stays open and keeps its locks the whole time. REQUIRES_NEW therefore needs a second pooled connection; under load with a pool of N connections, N threads each holding one and waiting for a second will starve the pool until connectionTimeout fires. NESTED issues SAVEPOINT; an inner failure runs ROLLBACK TO SAVEPOINT and the outer can continue and commit. It works with DataSourceTransactionManager/JdbcTransactionManager; JtaTransactionManager rejects it with NestedTransactionNotSupportedException; JpaTransactionManager only allows it when you set nestedTransactionAllowed, and then the savepoint rolls back JDBC state, not entities already changed in the persistence context.

The rollback-only trap

The classic bug: a REQUIRED inner method on another bean throws a runtime exception, the outer method catches it and carries on, and the commit at the end blows up.

@Service
class TransferService {
    private final AccountRepository accounts;
    private final FeeService fees;   // a different bean, so calls go through its proxy

    TransferService(AccountRepository accounts, FeeService fees) {
        this.accounts = accounts;
        this.fees = fees;
    }

    @Transactional
    public void transfer(long from, long to, long cents) {
        accounts.debit(from, cents);
        accounts.credit(to, cents);
        try {
            fees.charge(from);            // @Transactional (REQUIRED), throws FeeRuleException
        } catch (FeeRuleException e) {   // extends RuntimeException
            // "fee is optional, keep going"
        }
    }   // commit here throws UnexpectedRollbackException
}
Why it happens

The inner interceptor sees a RuntimeException, so it calls rollback(status). That status is a participant, not the owner, so the manager cannot roll back the physical transaction; instead it marks the shared transaction global rollback-only (globalRollbackOnParticipationFailure defaults to true). The outer method returns normally, its interceptor calls commit, the manager sees the mark, rolls back, and throws UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only, so the caller cannot believe the transfer succeeded.

Fixes, by intent: if the fee is genuinely independent, make charge REQUIRES_NEW (its failure stays in its own transaction); if it must be undoable but optional, use NESTED on a JDBC manager; if the exception is an expected business outcome, declare noRollbackFor = FeeRuleException.class on charge or, better, return a result instead of throwing; otherwise, do not catch it.

REQUIRES_NEW for audit records

Audit and security logs often must survive the business rollback ("user 42 attempted a withdrawal of $9,000 and was refused"). Put the write in a separate bean with its own transaction:

@Service
class AuditService {
    private final JdbcTemplate jdbc;
    AuditService(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String actor, String action, String detail) {
        jdbc.update("insert into audit_log(actor, action, detail, at) values (?, ?, ?, now())",
                actor, action, detail);
    }
}

// in a REQUIRED business method on another bean:
//   audit.record(user, "WITHDRAW_ATTEMPT", id + ":" + cents);  // commits now, on connection B
//   if (balance < cents) throw new InsufficientFundsException(id);  // outer rolls back, audit row stays

Two consequences: the audit row is visible to others before the outer transaction finishes, and an exception thrown by record propagates into the outer method like any other, so decide whether audit failure should abort the business operation.

Deadlocking yourself with REQUIRES_NEW

The outer transaction runs UPDATE account SET … WHERE id = 1 and holds the row lock. It then calls a REQUIRES_NEW method that updates the same row. The inner transaction waits for the outer's lock; the outer is waiting, in Java, for the inner method to return. The database's deadlock detector sees only one transaction waiting for another that is not itself blocked on a lock, so it never breaks the cycle: the thread hangs until a lock timeout (MySQL's innodb_lock_wait_timeout, PostgreSQL's lock_timeout, which is off by default) or the transaction timeout. Rule: a REQUIRES_NEW scope must never touch rows the suspended outer transaction has written or locked.

Decision guide

NeedUse
Normal service method, all or nothingREQUIRED
Must commit regardless of caller (audit, outbox sequence, failure counter)REQUIRES_NEW, separate bean, disjoint rows
Optional sub-step that may be undone alone, single JDBC databaseNESTED
Helper that must only run inside a caller's transaction (repository-style code)MANDATORY
Slow, non-transactional work you want off the caller's connectionNOT_SUPPORTED (but the outer connection is still held)
Read that works either waySUPPORTS (rarely worth it; prefer explicit REQUIRED + readOnly)
Assert "never call me inside a transaction" (e.g. code that calls a remote API)NEVER
What breaks in production
  • UnexpectedRollbackException in logs with no obvious cause: search for a caught runtime exception from a REQUIRED call on another bean.
  • REQUIRES_NEW in a loop or under high concurrency doubles connection demand and exhausts the pool.
  • Propagation on a method called via this is ignored entirely; there is no proxy in the path.
  • Assuming NESTED rolls back JPA entities: the savepoint undoes SQL, not managed objects in memory.

Practice · 50 min

  1. Build a demo with an outer and an inner bean and one test per propagation mode. Log isNewTransaction() and the connection's identity hash in each scope.
  2. Reproduce UnexpectedRollbackException, then fix it three ways (REQUIRES_NEW, NESTED, noRollbackFor) and write down which one matches each business intent.
  3. Implement the audit service and prove with a test that the audit row survives when the outer method throws.
  4. Reproduce the REQUIRES_NEW self-deadlock against PostgreSQL in Testcontainers with SET lock_timeout = '2s'; observe the error, then remove the overlap.
  5. Set the Hikari pool to 2 connections and run 4 concurrent outer transactions that each call REQUIRES_NEW. Explain the timeout you get.

Isolation, Timeout, readOnly & Rollback Rules

45m video45m practice

Besides propagation, a transaction definition carries isolation, timeout, a read-only flag and rollback rules. Each one is applied by the transaction manager at a specific moment and through a specific JDBC or Hibernate call, so each has exact limits: isolation applies only when a new transaction starts, timeout is checked only between statements, readOnly is an optimization rather than a lock, and checked exceptions commit.

Isolation per transaction

@Transactional(isolation = Isolation.REPEATABLE_READ) makes the manager call Connection.setTransactionIsolation(...) after acquiring the connection and restore the previous level before returning it to the pool. Isolation.DEFAULT (the default) leaves the connection as the pool configured it, which normally means the database default. The levels and anomalies are the ones from L217; what matters here is that databases implement them differently:

DatabaseDefaultNotes
PostgreSQLRead committedRead uncommitted behaves as read committed. Repeatable read is snapshot isolation (no phantoms, write skew possible). Serializable is SSI: it aborts conflicting transactions with SQLSTATE 40001.
MySQL InnoDBRepeatable readPlain reads use a consistent snapshot; locking reads take next-key locks. Serializable turns plain selects into shared-lock reads when autocommit is off.
OracleRead committedSupports only read committed and serializable (snapshot-based).
SQL ServerRead committedLock-based unless read committed snapshot is enabled; also offers a separate snapshot level.

Isolation is only applied when a scope creates the physical transaction. An inner REQUIRED method asking for SERIALIZABLE inside a READ_COMMITTED outer transaction silently gets READ_COMMITTED (set validateExistingTransaction on the manager to make that an error). With JPA, Boot's HibernateJpaDialect supports custom isolation; the plain DefaultJpaDialect rejects it.

The cost of SERIALIZABLE is not just locking: on PostgreSQL and other optimistic implementations, correct code still fails at random under contention, and Spring surfaces the failure as a ConcurrencyFailureException subclass. Serializable code is only correct with a retry around the whole transaction, from outside it:

@Service
class TransferFacade {
    private final TransferService transfers;   // its method is @Transactional(isolation = SERIALIZABLE)

    TransferFacade(TransferService transfers) { this.transfers = transfers; }

    public void transfer(long from, long to, long cents) {
        for (int attempt = 1; ; attempt++) {
            try {
                transfers.transfer(from, to, cents);   // each attempt is a fresh transaction
                return;
            } catch (ConcurrencyFailureException e) {
                if (attempt == 3) throw e;
                LockSupport.parkNanos(Duration.ofMillis(20L * attempt).toNanos());
            }
        }
    }
}

Retrying inside the transactional method is useless: the transaction is already marked for rollback. Spring Retry's @Retryable works too, as long as it sits on a different bean from the @Transactional method so that the retry proxy is outermost.

Timeout and the timeouts you also need

timeout = 5 (seconds) sets a deadline on the transaction. It is enforced cooperatively: each time JdbcTemplate creates a statement, DataSourceUtils.applyTransactionTimeout sets Statement.setQueryTimeout to the remaining time, or throws TransactionTimedOutException if the deadline has passed; with JPA the remaining time is passed to Hibernate as a query timeout. Java code running between statements, such as a slow HTTP call, is never interrupted, and an idle open transaction is not killed. Three more limits belong in every production setup:

# application.yml
spring:
  datasource:
    hikari:
      connection-timeout: 3000      # ms to wait for a free pooled connection (default 30000)
      max-lifetime: 1800000
  transaction:
    default-timeout: 10s            # applies when @Transactional sets no timeout

-- PostgreSQL, per role or per database
ALTER ROLE app SET statement_timeout = '5s';
ALTER ROLE app SET idle_in_transaction_session_timeout = '30s';
ALTER ROLE app SET lock_timeout = '3s';

The pool timeout protects callers from a starved pool, the database timeouts protect the database from runaway queries and from transactions left open by a stuck application thread, and the Spring timeout bounds the work between them.

readOnly = true

What readOnly actually does

Spring calls Connection.setReadOnly(true) on the new transaction's connection. With Hibernate, HibernateJpaDialect also sets the session's flush mode to MANUAL and makes loaded entities read-only by default, so Hibernate keeps no loaded-state snapshot and runs no dirty check at commit: a real saving in memory and CPU when a request reads thousands of entities. Some drivers and routing proxies send read-only connections to a replica; Spring's AbstractRoutingDataSource wrapped in LazyConnectionDataSourceProxy can do the same.

It is not an enforcement mechanism. Whether the database rejects writes depends on the driver: some turn the flag into a read-only database transaction, others treat it as a hint and ignore it. Under Hibernate, changing an entity in a read-only method is simply never flushed, so the change silently disappears. For hard guarantees, use a read-only database role or a replica, or set enforceReadOnly on DataSourceTransactionManager, which issues SET TRANSACTION READ ONLY.

Rollback rules

By default the interceptor rolls back on RuntimeException and Error and commits on checked exceptions. That mirrors the old EJB convention that checked exceptions are recoverable business outcomes, and it is the most surprising default in Spring: a method that throws IOException half-way through commits the half it did.

@Transactional(rollbackFor = Exception.class)                       // roll back on everything
public Receipt importStatement(Path file) throws IOException { /* ... */ }

@Transactional(noRollbackFor = DuplicatePaymentException.class)     // runtime, but commit anyway
public void applyPayment(Payment p) { /* ... */ }

@Transactional
public void cancel(long orderId) {
    if (!orders.cancellable(orderId)) {
        // roll back without throwing (couples this code to Spring)
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        return;
    }
    orders.markCancelled(orderId);
}

When several rules match, the one closest to the thrown type in the inheritance hierarchy wins. rollbackForClassName matches by substring, so "Exception" matches almost everything; prefer class literals. Spring Framework 6.2 also added a global switch, @EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS).

Where the annotation lives

The most specific location wins: a method annotation in the target class beats a class-level annotation, which beats an annotation on an interface method, which beats one on the interface. A method annotation replaces the class annotation entirely; attributes are not merged, so a class-level readOnly = true plus a method-level @Transactional gives a writable method. Annotations on interfaces have been honoured for both JDK and CGLIB proxies since Spring 5.0 (older articles saying CGLIB ignores them are out of date), but they are ignored by AspectJ weaving mode, so annotate concrete classes. The label attribute attaches free-form labels to the transaction definition that a custom manager or monitoring code may interpret; standard managers ignore them.

What breaks in production
  • A checked exception thrown after three of five inserts commits the three.
  • A write method added to a class annotated @Transactional(readOnly = true) without its own annotation inherits readOnly, and its entity changes are never flushed.
  • SERIALIZABLE deployed without a retry turns ordinary contention into user-visible 500s.
  • A 5-second transaction timeout does not stop a 60-second HTTP call made inside the transaction.

Practice · 45 min

  1. Write a test that throws a checked exception after an insert and shows the row committed; fix it with rollbackFor.
  2. On PostgreSQL (Testcontainers), run two concurrent SERIALIZABLE transfers that read each other's rows, catch the 40001 failure, and add the retry facade.
  3. Load 50,000 entities in a readOnly and a normal transaction and compare heap with a profiler or Runtime.totalMemory() deltas.
  4. Set timeout = 1, sleep 2 seconds between two queries, and show which statement throws TransactionTimedOutException.

L332 · DAY 332

Programmatic Transactions & Synchronization Callbacks

40m video45m practice

When a transaction boundary must be narrower than a method, decided at runtime, or used outside a Spring bean, TransactionTemplate gives you the same manager calls as @Transactional in a lambda. Synchronization callbacks are the other half: they let side effects such as messages, emails and cache evictions run only once the database has actually committed.

When declarative is not enough

  • Boundaries inside a method: read in one transaction, call a slow service with no connection held, write in a second transaction.
  • Dynamic settings: isolation or timeout chosen from configuration or per tenant.
  • Batch loops: commit every 1,000 rows rather than once at the end.
  • Code that is not a proxied bean: a static helper, a Runnable handed to an executor, a library callback, or a method that self-invokes.

TransactionTemplate

Definition

TransactionTemplate extends DefaultTransactionDefinition, so the template is the definition: set propagation, isolation, timeout and read-only once, then reuse it from many threads (it is thread-safe after configuration). execute(TransactionCallback<T>) returns the callback's value; executeWithoutResult(Consumer<TransactionStatus>) is the void form. Any RuntimeException or Error from the callback rolls back and is rethrown; there are no rollback rules, and a callback cannot throw checked exceptions, so to roll back quietly you call status.setRollbackOnly(). Boot registers one default TransactionTemplate bean when there is a single transaction manager; build your own for other settings.

@Service
class StatementImporter {
    private final TransactionTemplate batchTx;
    private final JdbcTemplate jdbc;

    StatementImporter(PlatformTransactionManager tm, JdbcTemplate jdbc) {
        this.batchTx = new TransactionTemplate(tm);
        batchTx.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
        batchTx.setIsolationLevel(TransactionDefinition.ISOLATION_READ_COMMITTED);
        batchTx.setTimeout(30);
        this.jdbc = jdbc;
    }

    /** Commits every chunk separately; returns the number of rows imported. */
    int importAll(List<List<Line>> chunks) {
        int total = 0;
        for (var chunk : chunks) {
            Integer n = batchTx.execute(status -> {
                if (chunk.stream().anyMatch(Line::invalid)) {
                    status.setRollbackOnly();          // skip this chunk, keep going
                    return 0;
                }
                chunk.forEach(l -> jdbc.update(
                        "insert into statement_line(ref, cents) values (?, ?)", l.ref(), l.cents()));
                return chunk.size();
            });
            total += n == null ? 0 : n;
        }
        return total;
    }

    record Line(String ref, long cents) { boolean invalid() { return cents == 0; } }
}

TransactionOperations is the interface TransactionTemplate implements; depend on it and tests can pass TransactionOperations.withoutTransaction(). For reactive code, thread-locals do not work because a pipeline hops threads; Spring's TransactionalOperator (with a ReactiveTransactionManager such as R2dbcTransactionManager) stores the transaction in the Reactor Context instead: repository.save(order).as(operator::transactional).

Synchronization callbacks

While a transaction is active, any code can register a TransactionSynchronization with TransactionSynchronizationManager.registerSynchronization(...). All its methods are defaults, so implement only what you need. The manager calls them in a fixed order:

@Component
class CacheEvictor {
    private final Cache cache;
    CacheEvictor(CacheManager cm) { this.cache = cm.getCache("accounts"); }

    void evictAfterCommit(Object key) {
        if (!TransactionSynchronizationManager.isSynchronizationActive()) {
            cache.evict(key);                       // no transaction: evict now
            return;
        }
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() { cache.evict(key); }
        });
    }
}
Three subtleties
  • registerSynchronization throws IllegalStateException when no synchronization is active; check first, as above.
  • In afterCommit the resources are still bound to the thread, so data access there "joins" a transaction that will never commit again. Any write from a callback must go through a REQUIRES_NEW method.
  • An exception from afterCommit reaches the caller even though the data is committed; exceptions from afterCompletion are logged and swallowed.

The declarative version is @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) from L277: publish an application event inside the transaction, and the listener runs as an afterCommit synchronization. If no transaction is active when the event is published, the listener does not run at all unless fallbackExecution = true.

Shrinking transaction scope

A transaction holds a pooled connection and any row locks for its whole duration. Never call an external HTTP API inside one: a 10-second provider stall becomes a 10-second lock and a missing connection for everyone else. Split the work into load, close, call, reopen and save, re-check the state in the second transaction, and keep a @Version column so two concurrent writers cannot both win:

public void capture(long paymentId) {
    Payment p = tx.execute(s -> payments.findById(paymentId).orElseThrow());       // tx 1
    CaptureResult r = gateway.capture(p.providerRef(), p.amountCents(),
                                      "capture-" + paymentId);                    // no tx, idempotency key
    tx.executeWithoutResult(s -> {                                                 // tx 2
        Payment fresh = payments.findById(paymentId).orElseThrow();
        fresh.markCaptured(r.captureId());   // throws unless still PENDING; @Version guards racers
    });
}

The gap between the call and the second transaction is a real failure window: if the process dies there, the provider captured the money and you have no record. Idempotency keys make the retry safe, and a reconciliation job or the outbox pattern (L334) closes the window.

What breaks in production
  • Sending the "order confirmed" email inside the transaction, then rolling back: the customer is told about an order that does not exist.
  • Treating afterCommit as guaranteed delivery: a crash right after the commit loses the message. It gives "only if committed", not "always if committed".
  • A TransactionTemplate bean you declare yourself replaces Boot's default one, which other code may have relied on.

Practice · 45 min

  1. Rewrite a @Transactional method with TransactionTemplate and prove identical behavior on success, runtime exception and setRollbackOnly.
  2. Implement chunked import with one transaction per 1,000 rows; kill the process mid-way and verify the committed chunks are intact.
  3. Register all four callbacks and log their order for a commit and for a rollback.
  4. Move an email send into a @TransactionalEventListener(phase = AFTER_COMMIT) and test that a rolled-back order sends nothing.

L333 · DAY 333

Transaction Pitfalls: The Complete List

50m video50m practice

Almost every @Transactional bug has one of three causes: the call never went through the proxy, the thread that did the work was not the thread holding the transaction, or the transaction lived for the wrong length of time. Learn to classify a symptom into one of these and to read Spring's transaction log, and the fix is usually obvious.

Self-invocation: the proxy is not in the path

Definition · self-invocation

The proxy wraps the bean from the outside. A call from one method of the bean to another is a plain Java call on this, the raw target, so the interceptor never runs and the annotation on the callee is ignored: no new transaction, no REQUIRES_NEW, no rollback rules, and no @PreAuthorize or @Async either.

@Service
public class OrderService {
    private final OrderRepository orders;
    private final OrderService self;          // the proxy, resolved lazily

    public OrderService(OrderRepository orders, @Lazy OrderService self) {
        this.orders = orders;
        this.self = self;
    }

    public void importAll(List<OrderDto> dtos) {
        // dtos.forEach(this::importOne);     // BUG: one failure is not isolated, no tx per item
        dtos.forEach(self::importOne);        // fix 2: call through the proxy
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void importOne(OrderDto dto) {
        orders.save(Order.from(dto));
    }
}

The four fixes, best first: (1) move the method to another bean (an OrderImporter) — the honest design fix; (2) self-injection as above; (3) programmatic boundaries with TransactionTemplate (L332), which need no proxy; (4) AspectJ mode, @EnableTransactionManagement(mode = AdviceMode.ASPECTJ) with compile- or load-time weaving, which puts the advice inside the class itself. AopContext.currentProxy() with exposeProxy = true also works but ties business code to Spring AOP.

Methods the proxy cannot see

  • private: a CGLIB subclass cannot override it, so the annotation is silently ignored. Since Spring 6.0, protected and package-private methods are intercepted on class-based proxies; interface-based proxies only intercept public interface methods.
  • final: cannot be overridden either. Worse, the call runs on the proxy instance itself, whose fields were never injected, so the usual symptom is a NullPointerException on a repository field. Kotlin classes are final by default, hence the kotlin-spring plugin.
  • static: no instance, no proxy, no transaction.
  • @PostConstruct: init callbacks run on the raw bean before the post-processor wraps it in a proxy, so a @Transactional init method has no transaction. Use a TransactionTemplate inside it, or do the work from an @EventListener(ApplicationReadyEvent.class) method, which is invoked through the proxy.

Exceptions that do not roll back

Checked exceptions commit by default (L331). The second variant is self-inflicted: catching inside the transactional method.

@Transactional
public void settle(Batch b) {
    try {
        b.items().forEach(ledger::post);
    } catch (RuntimeException e) {
        log.error("settlement failed", e);   // swallowed: the posted half COMMITS
    }
}

Either rethrow, or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() in the catch block. Note that the same pattern one level up, catching an exception thrown by a REQUIRED method of another bean, produces the opposite symptom, UnexpectedRollbackException (L330).

Wrong lifetime: lazy loading and long transactions

LazyInitializationException ("could not initialize proxy – no Session") appears when an entity leaves the service and something touches an unloaded association after the persistence context has closed, typically Jackson serializing a lazy collection. Spring Boot's default spring.jpa.open-in-view=true hides it by keeping the EntityManager open until the response is written, at the price of lazy queries issued from the web layer outside any transaction (each in autocommit), N+1 queries during serialization, and a connection that may stay checked out for the rest of the request. Boot logs a warning at startup for this reason. The better answer is to set it to false and load what the response needs inside the service: JOIN FETCH, @EntityGraph, or DTO projections.

Long transactions hold a pooled connection and every row lock they took. On PostgreSQL an old open transaction also pins the oldest visible snapshot, so VACUUM cannot remove dead rows anywhere and tables bloat. A remote HTTP call, a file upload or a user "think time" inside a transaction is the usual culprit; split the work as in L332.

Other threads: @Async and concurrency

The transaction lives in thread-locals, so it does not follow work onto another thread. An @Async method runs on an executor thread with no transaction (or a brand-new one if it is itself @Transactional), and it may start before the caller commits, so it cannot see the row the caller just inserted. The reliable pattern is to publish an event and handle it with @TransactionalEventListener(phase = AFTER_COMMIT) plus @Async. The same applies to CompletableFuture, parallel streams and virtual threads: each task must open its own transaction, and entities and the EntityManager must never be shared across threads, because neither is thread-safe.

Testing transactions honestly

A test class annotated @Transactional runs each test inside a transaction that the TestContext framework rolls back afterwards. That keeps the database clean but hides real behavior: nothing is flushed unless a query forces it, so constraint violations never fire; afterCommit callbacks and AFTER_COMMIT listeners never run; REQUIRES_NEW code cannot see the test's uncommitted data; lazy loading works in the test and fails in production. With @SpringBootTest(webEnvironment = RANDOM_PORT) the server handles requests on other threads, so the test's transaction does not even cover them.

@SpringBootTest
@Transactional
class TransferServiceTest {
    @Autowired TransferService transfers;

    @Test
    void commitsAndPublishes() {
        transfers.transfer(1, 2, 500);
        TestTransaction.flagForCommit();   // or annotate the test with @Commit
        TestTransaction.end();             // real commit: flush, constraints, afterCommit
        // assert on the outbox table here, then clean up explicitly
    }
}

For commit-sensitive code, prefer a non-transactional test with explicit cleanup (@Sql scripts or truncation in @AfterEach).

Reading what Spring actually did

logging.level.org.springframework.transaction=DEBUG
logging.level.org.springframework.orm.jpa.JpaTransactionManager=DEBUG

# typical lines (abridged)

If a method you annotated produces no "Creating new transaction" or "Participating" line, the proxy was bypassed.

What breaks in production
  • A batch import with this.importOne() runs in one giant transaction or none at all, depending on the caller.
  • An @Async notifier reads an order that has not committed yet and sends "order not found".
  • A green test suite, all @Transactional, while production fails on a unique constraint at flush time.
  • Open-in-view plus a slow client keeps connections checked out while bytes trickle over the network.

Practice · 50 min

  1. Reproduce self-invocation with REQUIRES_NEW, confirm it in the DEBUG log, then apply fixes 1, 2 and 3 and compare the logs.
  2. Make a @Transactional method final and observe the failure; then make it private and observe the silence.
  3. Disable open-in-view, trigger a LazyInitializationException from a controller, and fix it with an entity graph and with a DTO projection.
  4. Write an @Async listener that reads a just-inserted row, show the race, then fix it with an AFTER_COMMIT listener.
  5. Find a bug that a @Transactional test hides (a deferred unique violation) and expose it with TestTransaction.

L334 · DAY 334

Distributed Transactions, Sagas & the Outbox Pattern

50m video55m practicemilestone project

A database can make its own writes atomic because one log and one lock manager decide the outcome; the moment a second system (another database, a broker, a remote service) is involved, no single commit exists. Modern backends stop pretending otherwise: they keep each step a local ACID transaction, record outgoing events in the same transaction (the outbox), and make every consumer idempotent.

Two-phase commit and why services avoid it

Algorithm · Two-phase commit (XA)
  1. Prepare. The coordinator (the JTA transaction manager) asks every participant to prepare. Each one makes its changes durable enough to commit later, keeps its locks, and votes yes or no.
  2. Decide. If all vote yes, the coordinator writes "commit" to its own log; otherwise "rollback".
  3. Complete. The coordinator tells every participant the decision; each commits or rolls back and releases locks. After a crash, the coordinator replays its log to finish in-doubt transactions.

2PC is correct but blocking: a participant that voted yes may not decide on its own, so if the coordinator dies between the phases, the participant holds its locks "in doubt" until the coordinator recovers or an operator forces a heuristic decision (which can break atomicity). In Spring, JtaTransactionManager drives XA through a provider such as Atomikos or Narayana; Boot 3 no longer auto-configures one itself, so you use the provider's own starter. Microservices rarely use it: Kafka and most HTTP APIs are not XA resources, each service owns its database, locks held across network round trips cut throughput, and the availability of every participant multiplies.

CAP says that during a network partition a replicated system must give up either consistency (linearizable reads) or availability. Systems that choose availability adopt BASE: basically available, soft state, eventually consistent. The design job becomes making the inconsistent window short, visible and safe.

The dual-write problem

@Transactional
public void transfer(TransferCommand cmd) {
    accounts.debit(cmd.from(), cmd.cents());
    accounts.credit(cmd.to(), cmd.cents());
    kafka.send("transfers", cmd);   // BUG: not part of the DB transaction
}

If the commit fails after the send (constraint violation at flush, deadlock, lost connection), consumers act on a transfer that never happened. Moving the send after the commit (an afterCommit hook) fails the other way: a crash between commit and send loses the event forever. Kill the process with a debugger breakpoint between the two calls and both failure modes are easy to demonstrate. No ordering of two independent writes is atomic.

The transactional outbox

@Service
class TransferService {
    private final JdbcTemplate jdbc;
    private final ObjectMapper mapper;

    TransferService(JdbcTemplate jdbc, ObjectMapper mapper) { this.jdbc = jdbc; this.mapper = mapper; }

    @Transactional
    public UUID transfer(long from, long to, long cents) {
        int debited = jdbc.update(
            "update account set balance = balance - ? where id = ? and balance >= ?", cents, from, cents);
        if (debited == 0) throw new InsufficientFundsException(from);
        jdbc.update("update account set balance = balance + ? where id = ?", cents, to);

        UUID eventId = UUID.randomUUID();
        jdbc.update("""
            insert into outbox(id, aggregate_id, type, payload, created_at)
            values (?, ?, 'TransferCompleted', ?, now())""",
            eventId, String.valueOf(from), json(new TransferCompleted(eventId, from, to, cents)));
        return eventId;
    }

    private String json(Object o) {
        try { return mapper.writeValueAsString(o); }
        catch (JsonProcessingException e) { throw new IllegalStateException(e); }
    }
}

record TransferCompleted(UUID eventId, long from, long to, long cents) {}

The relay is either a poller or change data capture. A poller selects unpublished rows with FOR UPDATE SKIP LOCKED (so several instances can share the work), publishes each with the aggregate id as the Kafka key (preserving per-account order), waits for the broker acknowledgment, and marks the row published. CDC (Debezium reading the PostgreSQL WAL or MySQL binlog, with its outbox event router) avoids polling load and adds infrastructure. Either way the relay can crash after publishing and before marking, so delivery is at least once.

@Scheduled(fixedDelay = 500)
void relay() {
    tx.executeWithoutResult(status -> {
        List<OutboxRow> rows = jdbc.query("""
            select id, aggregate_id, payload from outbox
            where published_at is null order by created_at limit 100
            for update skip locked""",
            (rs, i) -> new OutboxRow(rs.getObject("id", UUID.class),
                                     rs.getString("aggregate_id"), rs.getString("payload")));
        for (OutboxRow r : rows) {
            kafka.send("transfers", r.aggregateId(), r.payload()).join();   // wait for the ack
            jdbc.update("update outbox set published_at = now() where id = ?", r.id());
        }
    });
}

Idempotent consumers, inboxes and idempotency keys

At-least-once delivery means every consumer must tolerate duplicates. The inbox pattern records each processed message id in the consumer's database, in the same local transaction as the effect, behind a unique constraint:

@Transactional
public void onTransferCompleted(TransferCompleted e) {
    int fresh = jdbc.update("insert into inbox(message_id) values (?) on conflict do nothing", e.eventId());
    if (fresh == 0) return;                 // already applied: duplicate delivery
    receipts.create(e.from(), e.cents());   // the effect commits together with the inbox row
}

The same idea protects HTTP endpoints from client retries. The client sends an Idempotency-Key header (an IETF draft standardizes it); the server stores the key, a hash of the request and the eventual response in a dedupe table with a unique key, and replays the stored response on a repeat. The draft suggests 409 when a request with the same key is still in flight and 422 when the key is reused with a different payload.

Sagas and eventual consistency

A saga is a sequence of local transactions, one per service, where each step has a compensating action that semantically undoes it: "reserve funds" is compensated by "release reservation", "charge card" by "refund". Compensations are new business operations, not rollbacks, and must themselves be idempotent and retryable. Orchestrated sagas have a coordinator that issues commands; choreographed sagas react to each other's events. Both are implemented in full on L414–L415.

To a product manager, eventual consistency is a set of visible states: "the transfer appears as pending immediately, becomes completed within a few seconds in normal operation, and if the receiving bank rejects it the money returns and the user is notified". Agree on those states, the expected delay and the failure messages before writing code.

What breaks in production
  • Publishing from inside @Transactional and rolling back: downstream systems act on phantom events.
  • A consumer without deduplication double-credits an account the first time the relay restarts.
  • An outbox that is never pruned grows without bound and slows the poller's query; index published_at and delete old rows.
  • Compensations that assume the forward step completed, when it may have timed out half-done.

Practice · 55 min

Milestone project: a transactional money-transfer service with correct propagation, retries and an outbox. Done means every box is ticked.

  • POST /transfers debits and credits in one REQUIRED transaction with a conditional update that cannot overdraw.
  • A REQUIRES_NEW audit record that survives a rejected transfer, on disjoint rows (no self-deadlock).
  • SERIALIZABLE or optimistic-locking conflicts retried up to three times from a facade outside the transaction.
  • An Idempotency-Key dedupe table: a retried request returns the original response and moves money once.
  • An outbox row written in the same transaction, a SKIP LOCKED poller relaying to Kafka, and an inbox-deduplicating consumer.
  • A crash test: kill the relay between publish and mark, restart, and show exactly one effect downstream.
  • Integration tests on Testcontainers PostgreSQL and Kafka that commit for real (no rollback-only test transactions).
