Build Tools & Project Structure

Phase 7 turns a folder of Java sources into a reproducible build that tests, packages and publishes itself, first with Maven, then with Gradle, and then with the release and quality tooling around both. Phase 6 covered what the JVM needs at run time. This phase covers how the artifact that runs there gets produced. It ends with the multi-module, CI-ready project skeleton that the testing work of Phase 8 and the Spring phases build on.

By the end of this phase you can

  • Read any pom.xml and its effective POM, and say where every version, plugin execution and property came from.
  • Predict which version Maven resolves in a dependency conflict, diagnose the resulting NoSuchMethodError, and fix it with dependencyManagement, a BOM import or an exclusion.
  • Choose the right phase and flags (verify rather than install, -pl -am, -T 1C) and configure the essential plugins: compiler processor paths, Surefire/Failsafe, resources filtering, shade and Spring Boot repackage.
  • Design a multi-module service with CI-friendly versions, inward-pointing dependencies and exactly one deployable module.
  • Write a Kotlin-DSL Gradle build with a version catalog, convention plugins, platform() and the build cache, and decide honestly whether a migration pays off.
  • Set up settings.xml, mirrors and profiles without committing credentials, and ship a signed, tag-driven release to Nexus, GitHub Packages or Maven Central.
  • Wire Spotless, Checkstyle, Error Prone, SpotBugs, PMD, JaCoCo, ArchUnit and a Sonar quality gate into a single ./mvnw verify.

L171 · DAY 171

Build Tools Overview & Installation

35m video35m practice

A build tool turns "these are my sources and these are the libraries I need" into a tested, packaged, publishable artifact, the same way on every machine. Most of that sameness comes from one habit: committing the wrapper, so the build pins its own tool version.

Why javac by hand stops working

With three classes and no libraries, javac and jar are enough. Then you add Jackson:

$ javac -d out -cp lib/jackson-databind-2.19.0.jar:lib/jackson-core-2.19.0.jar:lib/jackson-annotations-2.19.0.jar \
        $(find src/main/java -name '*.java')
$ cp -r src/main/resources/* out/
$ javac -d test-out -cp 'out:lib/*:lib-test/*' $(find src/test/java -name '*.java')
$ java -jar lib-test/junit-platform-console-standalone.jar execute -cp 'out:test-out:lib/*' --scan-classpath
$ jar --create --file app.jar --main-class com.acme.App -C out .

Problems pile up quickly. You had to find out yourself that jackson-databind needs jackson-core and jackson-annotations, and at which versions. Two libraries may want different versions of a third. The classpath separator is : on Unix and ; on Windows. Test libraries must not end up in the shipped jar. The resulting app.jar does not run anyway, because its manifest names no dependencies. And nobody else can reproduce exactly what you did. Around file twenty, the script becomes a second, untested codebase.

Ant, Maven, Gradle: three philosophies

The difference shows up in a build file. In Ant you write how: <javac srcdir="src" destdir="build"/>, then a jar task, in an order you choose. In Maven you state what the project is (coordinates, packaging, dependencies), and a fixed lifecycle decides what runs. Gradle is also declarative at the surface, but the build file is a program. That power is why Gradle builds can be fast, and also why they can be hard to read.

Installing, and why the wrapper matters more

For a workstation, SDKMAN manages JDKs and tools side by side (on Windows, use winget or Scoop):

$ sdk install java 21.0.7-tem        # any 21+ distribution
$ sdk install maven                   # 3.9.x line
$ sdk install gradle
$ mvn -v && gradle -v                 # prints the JDK each one will use (JAVA_HOME)

# then, once per project, generate wrappers and commit them
$ mvn wrapper:wrapper -Dmaven=3.9.9   # mvnw, mvnw.cmd, .mvn/wrapper/maven-wrapper.properties
$ gradle wrapper --gradle-version 8.14  # gradlew, gradlew.bat, gradle/wrapper/*
$ git add mvnw mvnw.cmd .mvn gradlew gradlew.bat gradle/wrapper
$ git update-index --chmod=+x mvnw gradlew
Definition · Build wrapper

A small script checked into the repo. The properties file next to it pins the exact tool version (distributionUrl, optionally a distributionSha256Sum). On first run, the script downloads that distribution into ~/.m2/wrapper or ~/.gradle/wrapper and runs it. After that, ./mvnw verify means the same thing on a laptop, in CI, and five years from now. All you need installed is a JDK. Always commit the wrapper and always invoke it, never a global mvn.

The local repository and offline mode

Maven caches every artifact it resolves in ~/.m2/repository. The path is the coordinates: dots in the groupId become directories.

~/.m2/repository/com/fasterxml/jackson/core/jackson-databind/2.19.0/
    jackson-databind-2.19.0.jar
    jackson-databind-2.19.0.pom          # its own dependencies, read for transitivity
    jackson-databind-2.19.0.jar.sha1     # checksum verified on download
    _remote.repositories                 # which repository it came from

mvn install also writes your own artifacts here, which is how one local project consumes another. Gradle keeps a separate cache under ~/.gradle/caches/modules-2 and does not read ~/.m2 unless you add mavenLocal(). Offline mode (mvn -o, gradle --offline) forbids network access and builds only from the cache. Run mvn dependency:go-offline first to pre-fetch, but it can miss plugins that are resolved lazily.

Which to choose in 2026

For a Spring Boot service, Maven is the default answer in most shops, and surveys have consistently shown it ahead of Gradle among Java developers. The reasons are practical. A POM is declarative data that every IDE, scanner and CI tool understands. Corporate parent POMs and BOMs (L175) standardize hundreds of services. There are few ways to be clever, so builds stay alike across teams. Pick Gradle when build speed across a large multi-project codebase matters, when you need custom build logic, or when the ecosystem already uses it (Android, Kotlin Multiplatform). L179–L180 cover Gradle on its own terms. This course uses Maven first.

What breaks in production
  • ./mvnw: Permission denied in CI. The script was committed from Windows without the executable bit. Fix it with git update-index --chmod=+x.
  • CRLF line endings in mvnw. The script then fails on Linux with /bin/sh^M. Add mvnw text eol=lf to .gitattributes.
  • No wrapper committed. CI uses whatever Maven the image ships. A plugin that needs a newer Maven then fails only on the build server.
  • The wrapper download is blocked by a corporate proxy. Point distributionUrl at the internal repository mirror (L177) instead of disabling the wrapper.

Practice · 35 min

  1. Write a two-class app that serializes a record with Jackson. Build and run it by hand with javac, jar and java -cp, and count the commands and jars you needed.
  2. Generate the same project from start.spring.io (Maven) and run ./mvnw -q package. Open the wrapper's properties file and find the pinned version.
  3. Clone the repo into a fresh directory on a machine (or container) with only a JDK and build it with the wrapper.
  4. Find jackson-databind in ~/.m2/repository. Delete its folder, run ./mvnw -o package, and read the error. Then run without -o and watch it come back.

Maven POM Anatomy & Coordinates

40m video40m practice

A POM is a description of a project, not a script: its coordinates, its packaging, what it depends on, and which plugin configuration to use. Maven merges it with every parent above it, and the result, the effective POM, is what actually runs.

The POM element by element

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>              <!-- POM format version, always 4.0.0 on Maven 3 -->

  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.0</version>
    <relativePath/>                                 <!-- resolve from repositories, not ../pom.xml -->
  </parent>

  <groupId>com.acme.orders</groupId>               <!-- the coordinates: G, A, V -->
  <artifactId>order-service</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>jar</packaging>                       <!-- default; decides the lifecycle bindings -->
  <name>Order Service</name>

  <properties>
    <java.version>21</java.version>               <!-- read by the Boot parent -->
    <mapstruct.version>1.6.3</mapstruct.version>  <!-- one place for each unmanaged version -->
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.mapstruct</groupId>
      <artifactId>mapstruct</artifactId>
      <version>${mapstruct.version}</version>
    </dependency>
  </dependencies>

  <build><plugins>…</plugins></build>
</project>

Other top-level elements you will meet: <dependencyManagement> (L175), <build><pluginManagement>, <profiles> and <repositories> (L177), <modules> (L178), and <distributionManagement>, <scm>, <licenses> and <developers> for publishing (L181). Appendix B of the plan shows a full production POM.

Coordinates and naming

Definition · Maven coordinates

An artifact is identified by groupId:artifactId:version, written in full as groupId:artifactId:extension[:classifier]:version. The groupId is a reverse domain you control (com.acme.orders), and it becomes a directory path in every repository. The artifactId is the lowercase, hyphenated module name (order-service), and it becomes the file name. The version follows the release scheme of L181. A classifier marks extra files built from the same project: -sources, -javadoc, -tests.

Maven compares versions by parsing them, not as strings: 1.10 > 1.9, and the qualifiers rank alpha < beta < milestone < rc < SNAPSHOT < (release) < sp. So 1.0-rc1 < 1.0-SNAPSHOT < 1.0. Odd version strings (1.0-final-2) still sort somehow, but rarely the way you expect.

SNAPSHOT versus release

A release version (1.4.2) is immutable. Repositories refuse to overwrite it, so anyone who resolves 1.4.2 gets the same bytes forever. A SNAPSHOT (1.5.0-SNAPSHOT) means "the latest build on the way to 1.5.0". Each deploy stores a timestamped file such as order-service-1.5.0-20261011.143015-7.jar and updates maven-metadata.xml to point at it. Consumers check for a newer snapshot according to the repository's update policy, daily by default, and -U forces a check now. That is useful between teams during development. A release build must never depend on a SNAPSHOT, because the same tag could build different code next week. L176 enforces this with the Enforcer plugin.

Packaging, properties and inheritance

  • Packaging selects the default plugin bindings (L173): jar (default, also used for Spring Boot apps), war for servlet containers, pom for parents, aggregators and BOMs (no code, only metadata), and maven-plugin for writing your own plugins.
  • Properties are referenced as ${name}. Built-ins include ${project.version}, ${project.basedir}, ${env.HOME} and Java system properties. -Dname=value on the command line overrides a POM property.
  • <parent> merges the parent's model into yours. Inherited: groupId and version (when omitted), properties, dependencies (every child really gets them), dependencyManagement, pluginManagement, build/plugins with their executions, repositories, distributionManagement, and scm/developers/licenses metadata. Not inherited: artifactId, name, packaging, modules, and profiles themselves (the effects of active parent profiles do come through). By default, Maven looks for the parent in ../pom.xml and then in repositories.

mvn help:effective-pom: see the truth

$ ./mvnw help:effective-pom -Doutput=effective.xml
$ grep -n -A2 "maven-compiler-plugin" effective.xml     # which version, which <release>?
$ grep -n "sourceDirectory\|<url>https://repo" effective.xml

When a build does something you did not write, such as a plugin running in the wrong phase, an odd version, or a property with an unexpected value, read the effective POM before you guess. With -Dverbose, recent versions of the help plugin annotate each line with the POM it came from.

The standard directory layout

order-service/
  pom.xml
  src/main/java/com/acme/orders/...      # production code
  src/main/resources/application.yml     # copied onto the classpath
  src/test/java/com/acme/orders/...      # tests, never shipped
  src/test/resources/
  target/                                # build output: classes/, test-classes/, *.jar (never commit)

Because these paths come from the Super POM, a new POM needs no configuration to compile, test and package. Every IDE, CI template and new teammate already knows where things are. You can override <sourceDirectory>, but each override is something every tool and person has to learn. Convention over configuration means you give up choices that don't matter so that all projects look alike.

What breaks in production
  • Dependencies in a corporate parent's <dependencies>. Every child inherits them, wanted or not. Shared versions belong in dependencyManagement.
  • A release that depends on a SNAPSHOT. The same git tag rebuilds differently next week, which makes it impossible to bisect.
  • A groupId you don't own. You cannot publish to Central under someone else's domain, and you risk colliding with their artifacts.
  • No <relativePath/> under a repository parent. Maven first tries ../pom.xml, which may be an unrelated POM in a monorepo, and warns or picks up the wrong parent.

  3. Create a pom-packaged parent with a property, a dependency, a <name> and a managed version. Check in the child's effective POM what came through.
  4. Sort 1.0, 1.10, 1.9, 1.0-SNAPSHOT, 1.0-rc1, 1.0.1 the way Maven does.
    Answer1.0-rc1 < 1.0-SNAPSHOT < 1.0 < 1.0.1 < 1.9 < 1.10. Check with java -jar maven-artifact-*.jar 1.0-rc1 1.0-SNAPSHOT 1.0, which prints the ordering.

Maven Lifecycles, Phases & Goals

40m video40m practice

Maven itself knows nothing about compiling or testing. It knows ordered lists of phases, and plugins bind goals to those phases. Ask for a phase and every earlier phase runs too. Ask for a goal and only that goal runs.

Three lifecycles

Definition · Lifecycle, phase, goal, plugin

A lifecycle is a fixed, ordered list of phases. Maven has three: clean (pre-clean, clean, post-clean), default (23 phases, below) and site (pre-site, site, post-site, site-deploy). A plugin is an artifact (maven-compiler-plugin) that contains one or more goals (mojos), named prefix:goal (compiler:compile). A phase does nothing by itself. All of its work comes from the goals bound to it, either by default for the project's packaging or explicitly in <executions>.

The default lifecycle's 23 phases, in order: validate, initialize, generate-sources, process-sources, generate-resources, process-resources, compile, process-classes, generate-test-sources, process-test-sources, generate-test-resources, process-test-resources, test-compile, process-test-classes, test, prepare-package, package, pre-integration-test, integration-test, post-integration-test, verify, install, deploy. You type seven of them. The rest exist as hooks: code generators bind to generate-sources, and test containers start in pre-integration-test.

Any other plugin joins the lifecycle through an execution. Binding a goal to a phase in your POM looks like this:

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-source-plugin</artifactId>
  <executions>
    <execution>
      <id>attach-sources</id>          <!-- ids let children override or extend it -->
      <phase>package</phase>
      <goals><goal>jar-no-fork</goal></goals>
    </execution>
  </executions>
</plugin>

When several goals share a phase, defaults run first, then executions in POM order. mvn help:describe -Dcmd=package lists the phases up to package with the default goals for the project's packaging. To see the full plan, including your own executions, run mvn buildplan:list (buildplan-maven-plugin).

mvn clean install, precisely

The command names two phases from two lifecycles. Maven runs the clean lifecycle up to clean, which deletes target/. Then it runs all 22 default phases up to and including install, which copies the jar and POM into ~/.m2/repository. That last step only matters if a separate project on the same machine needs your artifact. In a multi-module build, the reactor (L178) already passes sibling modules to each other. So ./mvnw verify is the right everyday command and the right CI command: it runs unit tests, integration tests and quality checks without writing to the shared local repository. Installing also leaves stale local SNAPSHOTs behind, and they can shadow newer remote ones. Use clean when you have a reason: renamed or deleted classes, or a plugin that does not track its outputs.

What breaks in production
  • Parallel CI jobs running install into one shared ~/.m2. Jobs overwrite each other's SNAPSHOTs, and one branch tests against another branch's jar. Use verify, and give each job its own repository cache.
  • Running a goal without its phases. mvn jar:jar on a clean checkout packages an empty target/classes. Goals do not trigger earlier phases. Phases do.
  • -T 1C with old plugins. Maven warns that a plugin is not marked thread-safe. Shared output directories then produce intermittent, unrepeatable failures.
  • Habitual -DskipTests in a "fast" deploy script. The tests stop running long before anyone notices.

Practice · 40 min

  1. Run help:describe -Dcmd=deploy on a jar project and on a pom project, and compare the bound goals.
  2. Bind maven-source-plugin as above, run package, and find the -sources.jar. Then run mvn source:jar-no-fork on a clean tree and explain the result.
  3. Run -DskipTests and then -Dmaven.test.skip=true, and compare target/test-classes each time.
  4. Time clean install, verify and -T 1C verify on any multi-module project. Which step did install add?

Dependencies: Scopes, Transitivity & Conflicts

45m video45m practice

You declare a handful of dependencies, and Maven computes a graph of a hundred or more. When two paths bring different versions of the same library, Maven keeps exactly one, the nearest. It doesn't pick the newest, and it doesn't warn you. Most NoSuchMethodErrors in Java are that choice going wrong.

The six scopes

ScopeMain compileTest compile + runRuntime (packaged)Passed on transitivelyTypical use
compile (default)yesyesyesyesSpring, Jackson, anything your code calls
providedyesyesno, the runtime supplies itnoServlet API in a WAR, Lombok

runtime scope keeps you honest. If your code compiles against the PostgreSQL driver, you have coupled to a vendor class by accident. With runtime scope, it fails to compile.

Transitivity and the scope table

Each dependency's POM lists its own dependencies, and Maven follows them recursively. The scope a transitive dependency ends up with depends on both the scope of your direct dependency (row) and the scope that dependency declared (column):

Provided and test dependencies of your dependencies never reach you. That is why a library's JUnit never shows up on your classpath.

Nearest-wins mediation

Definition · Dependency mediation

When several versions of one groupId:artifactId appear in the graph, Maven keeps the one closest to your project (fewest hops). If two are at the same depth, the one declared first wins. Version numbers are never compared. A version in dependencyManagement overrides mediation entirely. Gradle, by contrast, picks the highest requested version (L179).

$ ./mvnw dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson.core:jackson-databind
[INFO] com.acme:order-service:jar:1.0.0-SNAPSHOT
[INFO] +- com.vendor:legacy-sdk:jar:1.0:compile

Exclusions, optional, and pinning

<dependencyManagement>                     <!-- fix 1: pin the version everywhere in the tree -->
  <dependencies>
    <dependency>
      <groupId>com.fasterxml.jackson.core</groupId>
      <artifactId>jackson-databind</artifactId>
      <version>2.19.0</version>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependency>                                <!-- fix 2: cut the edge at its source -->
  <groupId>com.vendor</groupId>
  <artifactId>legacy-sdk</artifactId>
  <version>1.0</version>
  <exclusions>
    <exclusion>
      <groupId>com.fasterxml.jackson.core</groupId>
      <artifactId>jackson-databind</artifactId>
    </exclusion>
  </exclusions>
</dependency>

Pinning in dependencyManagement is the usual fix. It wins over mediation at any depth and documents the decision in one place. An exclusion removes one edge, which is right when the transitive artifact is unwanted altogether (such as a second logging backend). <optional>true</optional> is the library author's version of an exclusion: "I compile against this, but my consumers don't get it unless they declare it." A library that supports both Jackson and Gson marks both optional.

Keeping the graph honest

mvn dependency:analyze inspects bytecode and reports two lists. Used undeclared means you call classes you only get transitively: declare them, or an upgrade elsewhere will remove them. Unused declared means nothing references them. Treat that list with care, because runtime-only artifacts (drivers, starters, reflection and annotation users) show up as false positives. To fail the build on conflicts instead of finding them in production, use the Enforcer plugin:

<plugin>
  <artifactId>maven-enforcer-plugin</artifactId>
  <executions><execution>
    <id>enforce</id><goals><goal>enforce</goal></goals>
    <configuration><rules>
      <dependencyConvergence/>       <!-- two versions of one artifact in the graph: fail -->
      <requireUpperBoundDeps/>       <!-- resolved version lower than one requested: fail -->
      <banDuplicateClasses/>         <!-- same class in two jars; needs MojoHaus extra-enforcer-rules -->
    </rules></configuration>
  </execution></executions>
</plugin>

Diagnosing version skew

NoSuchMethodError and NoSuchFieldError mean the class was found, but at a different version than the caller was compiled against. ClassNotFoundException (reflective loading) and NoClassDefFoundError (linking) mean a jar is missing entirely, often because of an exclusion or a provided scope. First ask the JVM which jar it actually loaded:

public class WhichJar {
    public static void main(String[] args) throws ClassNotFoundException {
        var cls = Class.forName(args.length > 0 ? args[0] : "com.fasterxml.jackson.databind.ObjectMapper");
        var source = cls.getProtectionDomain().getCodeSource();
        System.out.println(cls.getName() + " loaded from " + (source == null ? "the JDK" : source.getLocation()));
        System.out.println("version: " + cls.getPackage().getImplementationVersion());
    }
}

Then find who brought that jar with dependency:tree -Dverbose -Dincludes=group:artifact, and pin or exclude it. java -verbose:class gives the same information for every class during a failing start-up.

What breaks in production
  • A minor bump of an unrelated library. Its new POM adds a shallower path to an old version of something you rely on, and nearest-wins silently downgrades it. Turn on dependencyConvergence before this happens to you.
  • Excluding something that is still needed. Tests pass because the test classpath has it through another route. In production you get NoClassDefFoundError at first use.
  • Explicit versions under a BOM. A <version> on a Boot-managed artifact overrides the tested set (L175).
  • Two artifacts with the same classes (javax vs jakarta, commons-logging vs jcl-over-slf4j). Which class loads depends on classpath order, which can differ between the IDE and the fat jar.

  1. In a Boot app, add jackson-databind with an explicit old version (2.12.7). Run dependency:tree -Dverbose, start the app, and record what fails. Remove the version and confirm the fix.
  2. Run dependency:analyze and classify every warning as a real problem or a false positive, with a reason.
  3. Add the three Enforcer rules above and fix each violation with either a pin or an exclusion. Note which fix you chose and why.
  4. Your module A has test-scoped B, and B has a compile dependency on C. Is C on A's main classpath? On its test classpath?

dependencyManagement, BOMs & the Spring Boot BOM

40m video40m practice

A BOM is a published list of versions known to work together. Import one and you stop choosing versions artifact by artifact. Spring Boot's BOM is the reason a Boot POM has almost no <version> tags, and knowing how it is wired tells you how to override it safely.

dependencyManagement and what a BOM is

Definition · dependencyManagement

A <dependencyManagement> entry says: if this artifact appears anywhere in the graph, use this version (and optionally this scope or these exclusions). It adds nothing to the classpath. It applies to your own versionless declarations and to transitive ones, overriding nearest-wins mediation (L174).

A Bill of Materials is an artifact with pom packaging whose only content is a dependencyManagement section. Library families publish one so their modules stay in step: jackson-bom, junit-bom, netty-bom, testcontainers-bom. Platforms publish one to curate third-party versions they have tested together.

Importing a BOM

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.5.0</version>
      <type>pom</type>
      <scope>import</scope>                <!-- copy its managed entries into this POM -->
    </dependency>
    <dependency>
      <groupId>org.springframework.cloud</groupId>
      <artifactId>spring-cloud-dependencies</artifactId>
      <version>${spring-cloud.version}</version>   <!-- 2025.0.0 for Boot 3.5 -->
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>                              <!-- no version: the BOM decides -->
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
  </dependency>
</dependencies>

Precedence rules: entries written directly in your dependencyManagement beat imported ones, and when two imported BOMs manage the same artifact, the one declared first wins. An explicit <version> on a <dependency> beats everything, which is exactly why you shouldn't write one for a managed artifact. It quietly takes that artifact out of the tested set.

spring-boot-dependencies: the BOM behind every starter

spring-boot-dependencies pins several hundred artifacts: all of Spring, plus Jackson, Hibernate, Tomcat, Netty, Micrometer, Flyway, the major JDBC drivers, Kafka clients, Testcontainers, JUnit and more. Each version sits in a named property (jackson-bom.version, hibernate.version, postgresql.version, flyway.version…), and the entries refer to those properties. Open ~/.m2/repository/org/springframework/boot/spring-boot-dependencies/3.5.0/spring-boot-dependencies-3.5.0.pom once and read it. Appendix A of the plan marks every artifact it manages as BOM.

Starter parent or imported BOM

spring-boot-starter-parent is itself a child of spring-boot-dependencies. On top of the versions, it adds: maven.compiler.release from java.version and -parameters for the compiler, UTF-8 source encoding, resource filtering of application*.yml/.properties with @…@ delimiters (L176), a preconfigured repackage execution for spring-boot-maven-plugin, and pinned versions for the common plugins. When you import the BOM instead, you get only dependencyManagement and must configure those plugins yourself, usually in the corporate parent.

Overriding a managed version, and the risks

<properties>                                  <!-- works only when Boot is your parent -->
  <postgresql.version>42.7.7</postgresql.version>
</properties>

With the starter parent, redefining the property is enough, because the BOM's entries are interpolated in your project's context. With an imported BOM it does nothing. The import is resolved with the BOM's own properties. In that case, declare the artifact (or the family's own BOM, such as jackson-bom) in your dependencyManagement before the Boot import. The risks are the same either way:

  • Patch bumps for a CVE are usually safe. Minor or major bumps of Hibernate, Jackson or Netty can break Boot's auto-configuration, which was compiled and tested against the managed version.
  • An override outlives its reason. Upgrade Boot a year later and the old property now downgrades the library. Every override needs a comment with a ticket and a removal condition.

Spring Cloud release trains and your own BOM

Spring Cloud publishes spring-cloud-dependencies as a release train: one version number (2025.0.x) covering Config, Gateway, OpenFeign, Stream and the rest, built against one Spring Boot minor (2025.0 targets Boot 3.5). A train that doesn't match your Boot version fails at start-up with Spring Cloud's compatibility check, or worse, half-works. Upgrade Boot and the train together, using the compatibility table on the Spring Cloud project page (Appendix D of the plan).

An organization with dozens of services publishes one more layer, its own platform BOM:

<groupId>com.acme.platform</groupId>
<artifactId>acme-platform-bom</artifactId>
<version>2026.10.0</version>
<packaging>pom</packaging>
<dependencyManagement><dependencies>
  <dependency><groupId>com.acme.platform</groupId><artifactId>acme-observability-starter</artifactId><version>3.2.1</version></dependency>
  <dependency><groupId>com.acme.platform</groupId><artifactId>acme-security-starter</artifactId><version>5.0.4</version></dependency>
  <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-dependencies</artifactId>
              <version>3.5.0</version><type>pom</type><scope>import</scope></dependency>

Services import one artifact and get a tested combination of internal libraries, Boot and Cloud. A bot (Renovate or Dependabot) proposes the bump, and the platform team owns compatibility. Keep versions in the BOM and plugin configuration in a parent, so teams can adopt one without the other.

What breaks in production
  • A property override under an imported BOM. It looks applied in the POM, but dependency:tree still shows Boot's version. Always verify an override in the tree.
  • BOM import order. Two BOMs manage netty and the first one silently wins. Put the BOM you trust most first, or pin the artifact explicitly.
  • A Boot upgrade without a Spring Cloud upgrade. The incompatible train fails at start-up, or breaks in odd ways after you disable the check.
  • Stale overrides that pin a library below the version the new Boot was tested with.

Essential Maven Plugins

45m video45m practice

Every useful thing a Maven build does is a plugin goal bound to a phase. A dozen plugins cover nearly all backend builds. For each one, learn which phase it runs in and the two or three settings that cause most of the trouble.

Compiler: release, preview, annotation processors

<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <release>${java.version}</release>          <!-- not source/target -->
    <parameters>true</parameters>               <!-- keep parameter names for Spring -->
    <compilerArgs><arg>--enable-preview</arg></compilerArgs>   <!-- only if you use preview features -->
    <annotationProcessorPaths>                  <!-- order matters -->
      <path><groupId>org.projectlombok</groupId><artifactId>lombok</artifactId><version>${lombok.version}</version></path>
      <path><groupId>org.projectlombok</groupId><artifactId>lombok-mapstruct-binding</artifactId><version>${lombok-mapstruct-binding.version}</version></path>
      <path><groupId>org.mapstruct</groupId><artifactId>mapstruct-processor</artifactId><version>${mapstruct.version}</version></path>
    </annotationProcessorPaths>
  </configuration>
</plugin>
  • <release> passes javac --release N. That fixes the language level, the bytecode version and the JDK API you may call. With source/target, a JDK 25 compiler happily links against 25-only methods and the code fails on a 21 runtime.
  • Preview features need --enable-preview at compile time and at run time, for Surefire too (<argLine>--enable-preview</argLine>), and they tie the class files to that exact JDK.
  • Processor paths. Once annotationProcessorPaths is set, javac looks for processors only there, not on the classpath. Lombok must come before MapStruct, and lombok-mapstruct-binding lets MapStruct see the getters Lombok generates. If the order is wrong, MapStruct reports "unknown property" for fields that clearly exist. Since JDK 23, javac no longer runs processors it merely finds on the classpath, so an explicit processor path is now the reliable option.

Spring Boot's parent sets the filtering delimiter to @ only, because ${…} would collide with Spring's own placeholders. So you write info.app.version: @project.version@ in application.yml, and the build replaces it. Uber-jars: shade, assembly, or Boot

Definition · Uber-jar

A single jar that contains the application and all of its runtime dependencies, so java -jar app.jar works with no classpath. The JVM's class loader cannot read a jar inside a jar, so there are only two options. You can unpack every dependency into one tree (shade, assembly), or ship a custom launcher that reads nested jars (Spring Boot).

  • maven-shade-plugin (package · shade) is right for plain libraries and CLIs. Relocation rewrites package names (com.google.common → acme.shaded.guava) so your copy of a dependency cannot clash with the user's. Transformers handle files that would otherwise overwrite each other: ServicesResourceTransformer merges META-INF/services (forget it and JDBC drivers or Jackson modules vanish), ManifestResourceTransformer sets Main-Class, and AppendingTransformer concatenates files like spring.handlers.
  • maven-assembly-plugin builds distribution archives: a tar.gz with bin/, lib/ and conf/. Its built-in jar-with-dependencies descriptor unpacks naively and clobbers service files. Prefer shade for a single jar.
  • Spring Boot apps use neither. repackage keeps every jar whole, so there is nothing to merge or relocate.

exec, enforcer and git-commit-id

  • exec-maven-plugin: exec:java -Dexec.mainClass=com.acme.tools.Seed runs a main class in the Maven JVM with the project classpath, and exec:exec runs an external program. Use it for code generators and one-off tooling, not for starting the app.

  • git-commit-id-maven-plugin (io.github.git-commit-id, the successor of pl.project13's plugin) writes git.properties with branch, commit id, time and dirty flag. Boot turns it into GitProperties, and the starter parent preconfigures it.
What breaks in production
  • A shaded jar without ServicesResourceTransformer. ServiceLoader finds one provider out of three, so you get "No suitable driver" only in the packaged app.
  • Integration tests named *Test run under Surefire, before the app is packaged, and fail or slow down every unit-test run. Name them *IT.
  • source/target instead of release builds on a newer JDK, then fails with NoSuchMethodError on the production JDK.
  • A filtered keystore.p12. TLS fails with "invalid keystore format" because filtering rewrote binary bytes.

Profiles, settings.xml & Private Repositories

35m video35m practice

The POM describes the project and gets committed and published with it. Anything that depends on the machine or the person running the build, such as credentials, mirrors and proxies, belongs in settings.xml. Profiles are the controlled way to vary a build, and they should change how you build, not what you ship.

Profiles and activation

<profiles>
  <profile>

  </profile>

  </profile>
  <profile>
    <id>docker-tests</id>

Definition · Profile activation

A profile is a partial POM (dependencies, plugins, properties, modules, repositories…) that is merged in when it is active. It can be activated by a property (present, absent with !name, or equal to a value), a JDK version range, an OS family/name/arch, a file that exists or is missing, or activeByDefault. When one profile lists several conditions, all of them must hold (Maven 3.2.2+). An activeByDefault profile turns off as soon as any other profile in the same POM becomes active, which surprises almost everyone.

$ ./mvnw -Prelease,ci verify          # activate explicitly
$ ./mvnw '-P!windows-dev' verify      # deactivate (quote it: ! is special in bash)
$ ./mvnw help:active-profiles         # what is active, and from where (POM or settings)
$ ./mvnw help:all-profiles

The ci / local / release pattern

  • Local (no profile): a fast inner loop with unit tests and formatting checks.
  • ci (activated by the CI environment): everything that gates a merge, meaning integration tests, coverage thresholds, enforcer rules and static analysis (L182).
  • release (explicit -Prelease): source and javadoc jars, GPG signatures, requireReleaseDeps. These are needed only for publishing (L181).

The rule underneath: a profile may add checks and extra artifacts, but the main jar must have the same content whichever profiles are active. A profile that swaps a dependency or a config file ("-Pprod includes the Oracle driver") produces artifacts nobody can reproduce from the tag alone. Runtime differences between environments belong in Spring profiles and external configuration, not Maven profiles.

settings.xml: servers, mirrors, proxies

Maven reads two files and merges them: the global ${maven.home}/conf/settings.xml and the user's ~/.m2/settings.xml, with the user file winning. Per-project command-line defaults go in .mvn/maven.config (for example -B -ntp), which is committed.

<settings>
  <mirrors>
    <mirror>
      <id>acme-all</id>
      <mirrorOf>*</mirrorOf>                          <!-- every repository goes through Nexus -->
      <url>https://nexus.acme.internal/repository/maven-all/</url>
    </mirror>
  </mirrors>
  <servers>
    <server>                                         <!-- matched by id to a mirror or repository -->
      <id>acme-all</id>
      <username>${env.NEXUS_USER}</username>
      <password>${env.NEXUS_TOKEN}</password>       <!-- injected by CI from its secret store -->
    </server>
    <server><id>acme-releases</id><username>…</username><password>{COQLCE6DU6GtcS5P=}</password></server>
  </servers>
  <proxies>
    <proxy><id>corp</id><active>true</active><protocol>https</protocol>
      <host>proxy.acme.internal</host><port>3128</port><nonProxyHosts>*.acme.internal</nonProxyHosts></proxy>
  </proxies>
  <activeProfiles><activeProfile>acme-repos</activeProfile></activeProfiles>
</settings>

Encrypting passwords. mvn --encrypt-master-password stores a master key in ~/.m2/settings-security.xml. mvn --encrypt-password then prints a {…} string to paste into <password>. Be clear about what this buys you: the master key sits on the same disk, so it protects against shoulder-surfing and accidental pastes, not against someone who can read your home directory. (Maven 4 replaces this mechanism.) In CI, inject tokens as environment variables, and prefer short-lived tokens over personal passwords.

Repositories and mirroring everything

A <repository> declares where to look for dependencies, with separate switches for releases and snapshots. A <pluginRepository> declares where to look for plugins. Central is predeclared in the Super POM with id central. In a company, these definitions usually sit in a settings profile (acme-repos above), not in each POM, and a mirror routes all traffic through one repository manager.

Maven 3.8.1+ also blocks plain-HTTP repositories by default, through a built-in mirror called maven-default-http-blocker. If an old POM declares an http:// repository, the fix is an HTTPS mirror, not unblocking.

Why credentials never go in pom.xml

The POM is committed, and it is published with every artifact you deploy, so anyone who can read your repository manager can read its contents. <distributionManagement> therefore carries only a repository id and URL, and Maven looks up the matching <server> in settings.xml at deploy time. The same id appearing in both places is the entire link between them.

What breaks in production
  • 401 Unauthorized on deploy. The <server><id> does not exactly match the repository id in distributionManagement. Ids are case-sensitive.
  • A token committed in a POM or .mvn/maven.config. It is in git history forever. Rotate it, then move it to the CI secret store.
  • Builds that work locally and fail in CI. The local ~/.m2/settings.xml has a repository or active profile the CI image lacks. Check help:effective-settings on both.
  • A profile that changes the shipped jar. Two builds of the same tag differ, and a bug reproduces in only one of them.

Multi-Module Maven Project Design

45m video55m practice

Splitting one service into modules turns architecture rules into compile errors. If domain doesn't declare a dependency on infrastructure, it cannot import a JPA class, however tempting that is. The reactor then builds the modules in dependency order as one build.

Aggregator and parent: two roles

RoleDeclared byDirectionGives you
Aggregator<packaging>pom</packaging> + <modules>points down to module directoriesone command builds them all, in the right order
Parenteach child's <parent>points upinherited properties, dependencyManagement, plugin configuration

In most repositories, the root POM plays both roles, and the two are easy to confuse. They are independent. A parent doesn't know its children, and an aggregator's modules need not inherit from it. Large codebases sometimes separate them: a build-parent module holds configuration, and a thin root POM only lists modules.

<!-- pom.xml (root): parent of all modules AND aggregator -->
<parent>
  <groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-parent</artifactId>
  <version>3.5.0</version><relativePath/>
</parent>
<groupId>com.acme.orders</groupId>
<artifactId>orders-parent</artifactId>
<version>${revision}</version>
<packaging>pom</packaging>
<properties><revision>1.4.0-SNAPSHOT</revision><java.version>21</java.version></properties>
<modules>
  <module>orders-api</module>   <module>orders-domain</module>   <module>orders-application</module>
  <module>orders-infrastructure</module>   <module>orders-web</module>   <module>orders-bootstrap</module>
</modules>
<dependencyManagement><dependencies>               <!-- sibling versions in one place -->
  <dependency><groupId>com.acme.orders</groupId><artifactId>orders-domain</artifactId><version>${project.version}</version></dependency>
  <!-- … one entry per module … -->
</dependencies></dependencyManagement>

<!-- orders-domain/pom.xml -->
<parent><groupId>com.acme.orders</groupId><artifactId>orders-parent</artifactId><version>${revision}</version></parent>
<artifactId>orders-domain</artifactId>                <!-- groupId and version inherited -->

A real service layout

  • api: request/response DTOs and the OpenAPI contract. Clients can depend on it, so keep it free of Spring.
  • domain: entities, value objects, domain services, plain Java. Its POM has almost no dependencies, which is the point.
  • application: use cases and the ports (interfaces) they need, such as OrderRepository and PaymentGateway.
  • infrastructure: adapters that implement those ports, such as JPA repositories, Kafka producers and HTTP clients.
  • web: controllers and exception handlers that map api DTOs to use cases.
  • bootstrap: the @SpringBootApplication class, application.yml, and the only module that declares spring-boot-maven-plugin in <build><plugins>. The parent has it only in pluginManagement, so the library modules stay plain jars.

Shared code across services goes in small, focused libraries or in a company starter (an auto-configuration module plus a dependency-only starter POM), versioned through the platform BOM (L175). Avoid a common module. It turns into a dumping ground that every module depends on, so every change to it rebuilds and retests everything.

Building a subset

$ ./mvnw -pl orders-web -am verify        # web plus everything it needs (also-make)
$ ./mvnw -pl orders-domain -amd verify    # domain plus everything that depends on it (also-make-dependents)
$ ./mvnw -pl :orders-web,:orders-api test # select by artifactId with a leading colon
$ ./mvnw verify -rf :orders-web           # resume from a failed module
$ ./mvnw -T 1C verify                     # independent modules (api, domain) build in parallel

Siblings are resolved from the reactor (their target/ output), not from ~/.m2. That is why verify works without install (L173). -pl x without -am resolves siblings from the local repository instead, and may silently use a stale jar.

Versioning and CI-friendly versions

Unified versioning (every module shares one version, released together) is right for the modules of one service, and it is what the root POM above does. Independent versioning fits a repository of libraries consumed separately, at the cost of tracking which module versions work together. To change a unified version everywhere: ./mvnw versions:set -DnewVersion=1.4.0 -DgenerateBackupPoms=false.

Definition · CI-friendly versions

Since Maven 3.5, <version> may use the properties ${revision}, ${sha1} and ${changelist}, so CI can set the version without editing files: ./mvnw -Drevision=1.4.0 deploy. The installed and deployed POMs must contain the resolved version, or consumers cannot resolve the parent. flatten-maven-plugin with flattenMode=resolveCiFriendliesOnly writes that resolved copy (Appendix B binds it to process-resources, and its clean goal to clean).

When a multi-module monolith beats microservices

Modules give you compile-time boundaries, one deployable, atomic refactors across layers, in-process calls without network failure modes, and one pipeline. Microservices give independent deploys and scaling, at the price of network calls, distributed data and a fleet to operate. For one team, or a domain whose boundaries are still moving, the modular monolith is usually the better start. When a module really needs its own release cadence or scaling, extract it along the boundary the modules already enforce. Spring Modulith offers a similar discipline inside a single module, using package conventions and tests instead of POMs.

What breaks in production
  • Depending on a repackaged Boot jar. If a library module also runs repackage, its classes move under BOOT-INF/classes, and dependents fail with ClassNotFoundException.
  • Deploying POMs with an unresolved ${revision}. Without flatten, consumers see a parent version of literally ${revision} and the build fails.
  • A common module everyone depends on. Every one-line change rebuilds and redeploys all of it, so the modules stop meaning anything.
  • -pl without -am in CI. The build compiles against yesterday's sibling jar from the cache and passes, and the next full build breaks.

Gradle Basics: DSLs, Tasks & Configurations

45m video45m practice

A Gradle build is a program that constructs a graph of tasks and then runs the parts of it that are out of date. Learn the three phases, what makes a task UP-TO-DATE, and how dependency configurations map to Maven scopes, and Gradle stops looking like magic.

Groovy DSL or Kotlin DSL

Both DSLs drive the same Gradle API. The Groovy DSL (build.gradle) is dynamic: typos and wrong types show up only when the script runs, and IDE completion is guesswork. The Kotlin DSL (build.gradle.kts) is statically typed. The IDE completes every block and property, shows documentation, and flags errors before you run anything. It is the default for gradle init since Gradle 8.2 and the right choice for new projects. Its cost is a slower first compilation of changed scripts. Most old Groovy answers on the web translate mechanically: "…" strings, id("…") instead of id '…', and = for assignments.

The build lifecycle

The configuration phase runs on every invocation, even ./gradlew help, so work done there is paid every time. Use tasks.register (lazy, created only if needed) rather than tasks.create, and never do I/O or network calls at the top level of a build script.

Tasks, inputs, outputs, up-to-date checks

Definition · Incremental task

A task that declares its inputs (files, properties, the classpath) and outputs (files or directories). Before it runs, Gradle fingerprints both. If nothing changed since the last run and the outputs are still there, the task is reported UP-TO-DATE and skipped. If the build cache holds a matching result, it is FROM-CACHE (L180). A task with no declared outputs is never up to date.

abstract class GenerateBuildStamp : DefaultTask() {
    @get:Input abstract val appVersion: Property<String>
    @get:OutputFile abstract val stampFile: RegularFileProperty

    @TaskAction
    fun write() {
        stampFile.get().asFile.writeText("version=${appVersion.get()}\n")
    }
}

val buildStamp = tasks.register<GenerateBuildStamp>("buildStamp") {
    appVersion = project.version.toString()
    stampFile = layout.buildDirectory.file("stamp/build-stamp.properties")
}

tasks.processResources { from(buildStamp) }   // wiring an output also wires the dependency

Run ./gradlew processResources twice: the second time buildStamp is UP-TO-DATE. Change the version and it runs again. Use explicit ordering only when no input/output link exists: dependsOn (must run first), mustRunAfter (ordering without dependency), finalizedBy (cleanup afterwards).

The daemon and incremental builds

What breaks in production

  • A custom task with undeclared outputs always runs, and it can never be cached. One with undeclared inputs is worse: it stays UP-TO-DATE when it shouldn't and ships stale files.
  • api everywhere recreates the compile problem. A transitive change then recompiles the whole build.
  • Lombok only in compileOnly. Without the annotationProcessor line it compiles nothing, and you get "cannot find symbol" for every getter.

Locking, migrating, and an honest evaluation

// build.gradle.kts
dependencyLocking { lockAllConfigurations() }

$ ./gradlew dependencies --write-locks                          # writes gradle.lockfile; commit it
$ ./gradlew --write-verification-metadata sha256 help          # checksums in gradle/verification-metadata.xml

Locking records every resolved version, transitive ones included, so a dynamic version (1.+) or a new release of a transitive dependency can't change the build without a visible lockfile diff. Verification metadata adds checksums so that a tampered artifact fails the build. Migration: gradle init run in a Maven project converts the POMs on a best-effort basis (dependencies, repositories, basic plugins), but custom plugin configuration and profile logic are yours to rewrite. Be honest about the payoff. Gradle wins clearly for large multi-project builds with a remote cache. For a single service whose Maven build takes three minutes, migrating rarely repays the retraining and the build code you then have to maintain. Maven also has an official build cache extension and Develocity support. Measure first.

  • enforcedPlatform in a published library. Consumers get their versions downgraded without asking.
  • A buildSrc change. Any edit invalidates the configuration of every project and makes the next build cold. Keep it small or move it to an included build.
  • A lockfile nobody updates. Security patches never arrive. Schedule --write-locks through your dependency bot.

Versioning, Releases & Artifact Repositories

40m video40m practice

A version number is a promise to whoever consumes the artifact. For a library, it promises compatibility. For a service, it identifies exactly which build is running. Releasing means producing an immutable artifact under that number, from a tag, automatically, and putting it somewhere others can trust.

Semantic versioning, and what breaks a Java library

Definition · Semantic Versioning 2.0.0

MAJOR.MINOR.PATCH: bump MAJOR for incompatible API changes, MINOR for backwards-compatible additions, PATCH for backwards-compatible fixes. A pre-release follows a hyphen (2.0.0-rc.1) and sorts before its release: 2.0.0-alpha < 2.0.0-alpha.1 < 2.0.0-beta < 2.0.0-rc.1 < 2.0.0. Build metadata follows a plus sign (+sha.5114f85) and is ignored for precedence. Under 0.y.z, anything may change at any time.

For a Java library, "incompatible" has two meanings (JLS ch. 13). Source compatibility asks whether consumers still compile. Binary compatibility asks whether already-compiled consumers still link and run. Changes that need a MAJOR bump:

  • removing or renaming a public type, method or field, or changing a parameter type. Even narrowing a return type changes the method descriptor, which breaks binary compatibility;
  • adding an abstract method to an interface that users implement (a default method avoids this), making a class final, or reducing visibility;
  • raising the minimum Java version, or bumping the major version of a dependency whose types appear in your API;
  • behavior and format changes, such as a different default, a stricter validation, or a new serialization format.

Some traps are subtle. Changing the value of a public static final constant does nothing for existing consumers until they recompile, because javac inlines the old value. Adding a checked exception breaks source compatibility but not binary compatibility. Run japicmp or Revapi in CI against the last release so these are checked automatically instead of by memory.

CalVer for services, and the danger of SNAPSHOTs

A deployable service has no compile-time consumers. Its compatibility contract is the HTTP or event API, which is versioned separately. So SemVer's promise means little there, and many teams use CalVer (2026.10.3) or {date}-{short sha}. The version then tells you what is running and when it was built, and it maps straight back to a commit.

SNAPSHOTs (L172) are mutable by design. That is convenient between teams mid-sprint, but every build that resolves one depends on when it ran. Tests can pass on Monday and fail on Tuesday with no change on your side, and a hotfix built from an old tag picks up today's snapshot. Keep them out of anything released (requireReleaseDeps, L176). If you need someone's unreleased work, ask for a real pre-release (1.5.0-rc.1) or a per-commit version.

maven-release-plugin versus tag-driven CI

release:prepare checks for SNAPSHOT dependencies, rewrites the version to 1.4.0, commits and tags, rewrites to 1.5.0-SNAPSHOT, and commits again. release:perform then checks out the tag and runs deploy. It works, but it makes two commits per release, needs CI to push to the main branch, builds twice, and leaves a half-done state when it fails midway. The modern alternative inverts the flow: the tag is the source of truth, and CI derives the version from it using CI-friendly versions (L178).

Layout, retention, and consuming from CI

Every Maven repository has the same layout as ~/.m2 (L171): group/path/artifact/version/artifact-version[-classifier].ext, plus .sha1/.md5 checksums and maven-metadata.xml files listing versions (and, for snapshots, the latest timestamp). A repository manager adds proxy repositories that cache remote ones, with a metadata TTL that decides how quickly new upstream versions appear, and retention policies. Delete snapshots older than N days or beyond the last K builds, never delete or redeploy releases, and alert on storage. To consume from CI, generate settings.xml with a read-only token from the secret store (as setup-java does above), route everything through the group mirror, and cache ~/.m2/repository keyed on a hash of the POMs. In Gradle, use the environment variables ORG_GRADLE_PROJECT_acmeUsername/…Password.

What breaks in production
  • A changed constant. Consumers keep the inlined old value until they recompile, so two services disagree about the same "constant".
  • Redeploying a release after a quick fix with the same number. Caches and proxies already hold the first build, so different machines run different code under one version.
  • A "patch" release that bumps a dependency's major version exposed in your API. Consumers hit NoSuchMethodError (L174).
  • No snapshot retention. The repository manager's disk fills up and every deploy across the company fails.

JaCoCo: what coverage measures

Definition · Coverage instrumentation

jacoco:prepare-agent sets the argLine property to -javaagent:jacocoagent.jar=…, and Surefire passes it to the test JVM. As each class loads, the agent inserts probes into its bytecode and records which ones executed, writing them to target/jacoco.exec. Line coverage counts lines with at least one executed instruction. Branch coverage counts the outcomes of each if/switch that ran, so if (a && b) has four branches. report renders HTML and XML (Sonar reads the XML), and check fails the build below thresholds.

<execution><id>check</id><phase>verify</phase><goals><goal>check</goal></goals>
  <configuration><rules><rule>
    <element>BUNDLE</element>
    <limits>
      <limit><counter>LINE</counter><value>COVEREDRATIO</value><minimum>0.80</minimum></limit>

    </limits>
  </rule></rules></configuration>
</execution>

Coverage shows what tests executed, not what they checked. A test with no assertions reaches 100% just as well. Treat a threshold of about 80% (Appendix B uses jacoco.branch.min = 0.80) as a floor that catches untested modules. Pushing toward 100% produces tests of getters and generated code and makes refactoring expensive. To measure test quality, use mutation testing (PIT, Phase 8).

Sonar, ArchUnit and Spotless

SonarQube (self-hosted) or SonarCloud runs its own analyzers, imports JaCoCo's XML, and evaluates a quality gate: a set of conditions such as coverage on new code at least 80%, duplication on new code at most 3%, no new issues, and all security hotspots reviewed. The key idea is the new-code period. The gate judges only code changed since a baseline (the previous version, or N days), so a legacy codebase can adopt it on day one without fixing ten years of debt first. Security hotspots are code that needs a human decision (is this regex exposed to user input?), not confirmed bugs. Technical debt is reported as the estimated time to fix all issues. Run it with ./mvnw sonar:sonar -Dsonar.qualitygate.wait=true so that a red gate fails the CI step.

            .should().haveSimpleNameEndingWith("Controller");
}

ArchUnit runs these rules as ordinary JUnit 5 tests, so a violation fails test with the offending class and line. Modules (L178) already enforce coarse boundaries at compile time. ArchUnit covers the finer rules modules cannot express, such as package layering inside a module, naming, "no field injection" and "no cycles between slices". Spotless with google-java-format ends formatting debates: spotless:apply rewrites files, and spotless:check fails CI. On an existing codebase, ratchetFrom origin/main limits it to files you touched.

Milestone: a reproducible, CI-ready multi-module build

  • Multi-module layout from L178 with ${revision} + flatten, only bootstrap repackaged, wrappers committed (L171)
  • Versions from the Boot BOM (or a platform BOM) with no stray <version> tags; Enforcer with dependencyConvergence, requireUpperBoundDeps, requireJavaVersion
  • Spotless, Checkstyle, Error Prone + NullAway, SpotBugs + find-sec-bugs, PMD + CPD, JaCoCo check at 80% branch, ArchUnit layering rules: all green in one ./mvnw verify
  • ci and release profiles (L177), credentials only in CI secrets
  • Reproducible output: project.build.outputTimestamp set, two clean builds producing byte-identical jars (verify artifact:compare after an install)
  • CI workflow running verify on every push, a Sonar gate on pull requests, and tag-driven deploy (L181)
What breaks in production
  • 0% coverage after adding a Surefire <argLine>. It replaced JaCoCo's agent. Write <argLine>@{argLine} -Xmx1g</argLine> so the agent is kept.
  • Every tool switched on at once on legacy code. Thousands of violations appear, and the team disables the gate within a week. Baseline first (Sonar new code, Spotless ratchet, SpotBugs exclude file), then fail only on new violations.
  • A Sonar step that doesn't wait for the gate. CI stays green while the dashboard is red, and nobody looks.
  • Gaming coverage with assertion-free tests. The number goes up while defect rates don't change.
