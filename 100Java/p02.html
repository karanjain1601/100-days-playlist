Phase 2 opens up the Collections Framework and the generics type system that holds it together, from the interface contracts down to the arrays, nodes, hash buckets, heaps and red-black trees underneath. L56 · DAY 56

The Collections Framework Map

40m video35m practice

The Collections Framework is a small set of interfaces, each a promise about ordering, duplicates and lookup, plus a larger set of implementations that keep those promises at different costs. Learn the interfaces first, code against them, and pick the implementation last.

The hierarchy

Everything that can be iterated with for-each implements Iterable<T>. Collection<E> adds size, membership and bulk operations, and splits into three families: List (positions), Set (uniqueness) and Queue (an order of removal). Map<K,V> stores key-value pairs and deliberately does not extend Collection: "add an element" has no meaning for a map, so it exposes three collection views instead (keySet, values, entrySet). Java 21 (JEP 431) inserted the sequenced interfaces: SequencedCollection (super-interface of List, Deque and SequencedSet) and SequencedMap, which give every collection with a defined encounter order getFirst, getLast, addFirst, removeLast and reversed().

What each interface guarantees

Definition · the contracts
  • Collection: a group of elements; nothing about order or duplicates. contains and remove use equals.
  • List: ordered by index, duplicates allowed, positional access get(i). Two lists are equal when they hold equal elements in the same order, whatever the implementation.
  • Set: no two elements e1.equals(e2). Equality is by membership only, so a HashSet can equal a TreeSet.
  • SortedSet/NavigableSet: iteration in comparator order, plus range and nearest-match queries.
  • Queue: a head from which elements are removed; FIFO for most implementations, priority order for PriorityQueue. Deque: insert and remove at both ends.
  • Map: each key maps to at most one value; key uniqueness follows the same equals/hashCode (or comparator) rule as sets.

Many methods are documented as optional operations: an implementation may throw UnsupportedOperationException from add or remove. That is how List.of, Collections.unmodifiableList and Arrays.asList (fixed size) satisfy the List type without being freely mutable. The type tells you the shape of the data, not whether you may change it.

List<String> list = new ArrayList<>(List.of("b", "a", "b"));
Set<String> set = new HashSet<>(list);                    // [a, b] in some order
SequencedSet<String> seen = new LinkedHashSet<>(list);     // [b, a] first-seen order
NavigableSet<String> sorted = new TreeSet<>(list);         // [a, b] comparison order
Deque<String> stack = new ArrayDeque<>();
stack.push("x"); stack.push("y");

System.out.println(list);             // [b, a, b]
System.out.println(seen.getFirst());  // b
System.out.println(sorted.ceiling("aa")); // b
System.out.println(stack.peek());     // y
System.out.println(set.equals(sorted));   // true: same members

Interface type, implementation instance

Declare fields, parameters and return types with the least specific interface that carries the guarantee you rely on, and name the concrete class only after new. Callers then depend on the contract, and you can swap ArrayList for CopyOnWriteArrayList or HashMap for LinkedHashMap by editing one line.

record Order(String id, long cents) {}

class OrderBook {
    private final List<Order> pending = new ArrayList<>();           // interface type
    private final SequencedMap<String, Order> byId = new LinkedHashMap<>(); // order matters, so say so

    void addAll(Collection<Order> orders) {                           // accept the widest useful type
        for (Order o : orders) { pending.add(o); byId.put(o.id(), o); }
    }
    List<Order> pending() { return List.copyOf(pending); }           // return an interface, not ArrayList
    Order oldest() { return byId.firstEntry().getValue(); }           // SequencedMap method, Java 21
}

Use the concrete type only when you need a method the interface lacks (ArrayList.ensureCapacity, TreeMap-specific tuning) or when the guarantee itself is the point. Before Java 21 "this map is insertion-ordered" could only be said with LinkedHashMap; now SequencedMap says it at the interface level. For local variables var is fine, since the scope is a few lines.

Legacy classes and why they persist

Java 1.0 shipped Vector, Stack, Hashtable and Enumeration. The framework arrived in 1.2 and retrofitted them: Vector implements List, Hashtable implements Map. They lock on every method (L59), Hashtable rejects null keys and values, and Enumeration (hasMoreElements/nextElement) has no remove. They survive because public APIs cannot change their signatures: Properties extends Hashtable<Object,Object>, ClassLoader.getResources and the Servlet API's getHeaderNames() return Enumeration, and StringTokenizer implements it. Bridge them at the boundary rather than spreading them.

Enumeration<URL> urls = ClassLoader.getSystemResources("META-INF/MANIFEST.MF");
List<URL> all = Collections.list(urls);                 // copy into an ArrayList
// or lazily: Iterator<URL> it = urls.asIterator();     // Java 9+
Enumeration<String> e = Collections.enumeration(List.of("a", "b")); // for old APIs that demand one

  • Relying on HashMap order. Output that "always" came out sorted in tests changes after a resize, a JDK upgrade or a different key set. If order is part of the contract, use LinkedHashMap or TreeMap and declare SequencedMap.

List & ArrayList Internals

45m video45m practice

An ArrayList is an Object[] plus a size counter. Reads by index are a single array access, appends are amortized O(1) because the array grows by half each time it fills, and anything that touches the middle pays for an System.arraycopy of everything after it.

The List contract and its core methods

A List is ordered by index (0 to size()-1), allows duplicates and nulls (implementation permitting), and defines equals as "same elements in the same order". Search methods use equals, so they are linear scans.

List<String> list = new ArrayList<>(List.of("a", "b", "c", "d"));
list.add("e");             // [a, b, c, d, e]      append
list.add(1, "x");          // [a, x, b, c, d, e]   insert: shifts b..e right
String old = list.set(0, "A"); // old = "a"; set is not a structural change
list.remove("c");          // [A, x, b, d, e]      first element equal to "c"
int i = list.indexOf("d"); // 3, or -1 if absent; lastIndexOf scans backwards
boolean has = list.contains("zz"); // false: indexOf(o) >= 0
String last = list.getLast();      // "e" (Java 21 SequencedCollection)

List<Integer> ids = new ArrayList<>(List.of(10, 20, 30));
ids.remove(1);                     // remove(int index): [10, 30]
ids.remove(Integer.valueOf(10));   // remove(Object):   [30]

The last two lines are the classic overload trap: with a List<Integer>, an int argument selects remove(int index) because no boxing is needed.

Inside ArrayList: elementData, size and growth

Definition · storage

The fields that matter are transient Object[] elementData and int size. Capacity is elementData.length; size is how many slots are in use. new ArrayList<>() starts with a shared empty array and allocates the default capacity of 10 on the first add. When an add finds the array full, grow computes newCapacity = oldCapacity + (oldCapacity >> 1) (about 1.5x; recent JDKs route this through ArraysSupport.newLength), allocates a new array and copies with Arrays.copyOf. Capacities therefore run 10, 15, 22, 33, 49, 73, 109…

Amortized O(1) append. Each grow copies the current capacity. If the final capacity is about n, the earlier copies total roughly n/1.5 + n/1.5² + … = 2n element moves, so n appends cost O(n) in total and O(1) each on average, even though an individual append that triggers a grow is O(n). The growth factor trades memory (up to a third of the array may be empty) against copy frequency.

ensureCapacity(n) grows once up front when you know the final size (or pass it to the constructor new ArrayList<>(n)); trimToSize() shrinks the array to exactly size for a long-lived list that will not grow again. Removing elements never shrinks the array by itself.

Insert and remove in the middle: System.arraycopy

System.arraycopy is an intrinsic (a fast memmove), so shifting a few thousand references is cheap in absolute terms, but it is still O(n): inserting at index 0 of a million-element list moves a million references every time. add(i, e) and remove(i) are O(n − i); get, set and appending are O(1); contains, indexOf and remove(Object) are O(n).

subList is a view

subList(from, to) (half-open) returns a window onto the same array, not a copy. Writes through it change the parent, and list.subList(a, b).clear() is the idiomatic way to delete a range in one shift. Two consequences bite in practice: a structural change to the parent (add/remove through the parent) invalidates the view, whose next use throws ConcurrentModificationException; and a small view keeps the entire parent array reachable.

List<Event> page = all.subList(0, 20);           // view: pins 'all' in memory
List<Event> safe = new ArrayList<>(all.subList(0, 20)); // independent copy, 20 slots
List<Event> frozen = List.copyOf(all.subList(0, 20));   // immutable copy

List<Integer> xs = new ArrayList<>(List.of(1, 2, 3, 4, 5));
List<Integer> mid = xs.subList(1, 4);   // [2, 3, 4]
mid.set(0, 20);                          // xs is now [1, 20, 3, 4, 5]
xs.add(6);                               // structural change to the parent
// mid.size();                           // ConcurrentModificationException

modCount, fail-fast iteration and safe removal

Definition · fail-fast

modCount (inherited from AbstractList) counts structural modifications: anything that changes the size, plus ensureCapacity (when it grows) and trimToSize. set does not count. An iterator copies it into expectedModCount and checks on every next(); a mismatch throws ConcurrentModificationException. This is a best-effort bug detector, not a thread-safety mechanism.

List<String> names = new ArrayList<>(List.of("ann", "abe", "bob"));
for (String n : names)
    if (n.startsWith("a")) names.remove(n);   // CME on the following next()

names.removeIf(n -> n.startsWith("a"));      // correct: [bob]

for (Iterator<String> it = names.iterator(); it.hasNext(); )
    if (it.next().isBlank()) it.remove();    // correct: iterator keeps modCount in sync

ArrayList.removeIf first evaluates the predicate on every element, recording matches in a bitset, then compacts the survivors in a single pass: O(n) total. Calling remove(i) in a loop is O(n²), and an index loop that removes must also step back (or iterate from the end) or it skips the element that slid into position i.

What breaks in production
  • The silent non-failure. Removing the second-to-last element inside for-each does not throw: hasNext() is cursor != size, which becomes false, and the last element is simply never visited.
  • Front-of-list queues. list.remove(0) as a queue pop is O(n) per call; with a 100k backlog a drain loop becomes quadratic. Use ArrayDeque.
  • subList pagination leaks. Caching results.subList(0, 10) keeps every result alive, and the cached page dies with CME when the source is refreshed.
  • Unsized bulk loads. Building a 5M-element list from a known count without presizing performs about 30 grow-and-copy cycles and leaves up to a third of the final array unused.

LinkedList Internals & When Not To Use It

40m video40m practice

LinkedList trades contiguous storage for a chain of separately allocated nodes. That makes the ends O(1) and the middle O(1) once you are already there, but getting there is a pointer chase through cold memory, so on real hardware ArrayList or ArrayDeque wins almost every workload.

The node structure

Definition · doubly linked list

LinkedList holds first, last and size. Each element lives in a private static Node<E> with three fields: item, next and prev. Linking a node at an end rewires at most four references; unlinking clears the node's fields to help the garbage collector. There is no capacity and no resizing, and nulls are permitted.

List and Deque in one class

LinkedList implements both List and Deque (and so SequencedCollection). The Deque side is where it is genuinely O(1):

Deque<String> d = new LinkedList<>();
d.addFirst("b");      // [b]
d.addLast("c");       // [b, c]
d.push("a");          // [a, b, c]   push == addFirst
String h = d.peek();  // "a"         head or null; never removes
String p = d.poll();  // "a"         remove head or return null if empty
String q = d.pop();   // "b"         removeFirst; NoSuchElementException if empty
d.offerLast("d");     // [c, d]      returns boolean instead of throwing

Index access is the weak side. get(i), set(i, e), add(i, e) and remove(i) all call node(i), which walks from first if i < size/2 and from last otherwise: at most n/2 hops, still O(n). A loop for (int i = 0; i < list.size(); i++) list.get(i) is therefore O(n²) on a LinkedList, a common accident when code accepts any List. (ArrayList implements the marker interface RandomAccess; LinkedList does not, and generic algorithms such as Collections.binarySearch check it.)

The middle is O(1) only through a ListIterator that is already positioned: it.add(x) and it.remove() relink neighbours without shifting anything. That is the one structural advantage over ArrayList, and it only pays when you were going to walk the list anyway.

The bigger cost is not bytes but locality. Iterating an ArrayList reads references sequentially, which the CPU prefetcher streams into cache. Iterating a LinkedList reads next, waits for that load, then reads the next node: a dependent chain of loads that may each miss cache. To insert into the middle of either list you must first find the position, and for the linked list that walk costs more than ArrayList's single System.arraycopy of contiguous memory. This is why benchmarks usually show ArrayList ahead even for middle insertions, often by a wide margin for large lists. Measure rather than trust either intuition.

When LinkedList is a reasonable choice

  • A queue or deque that must hold nulls: ArrayDeque rejects null; otherwise prefer ArrayDeque, which is a circular array and faster (L67).
  • Heavy insert/remove during a single traversal via ListIterator, for example splicing elements while scanning.
  • LRU chains are the textbook linked-list use, but java.util.LinkedList does not expose its nodes, so removing an arbitrary element is O(n). Real LRU structures keep their own node pointers in a hash map; LinkedHashMap does exactly that (L64).

Benchmarking it properly: a JMH preview

A hand-written timing loop measures JIT warm-up, dead-code elimination and GC noise. JMH (the OpenJDK microbenchmark harness) forks a JVM, warms up, and consumes results so the JIT cannot discard them. Generate a project with the archetype, then run the jar:

    }
    // insert then remove in the middle, so the size stays constant
    @Benchmark public int arrayMiddle()  { array.add(size / 2, -1);  return array.remove(size / 2); }

}

Returning the result hands it to JMH's blackhole. JMH is covered in depth later in the course; for now treat its numbers as relative, not absolute.

What breaks in production
  • Indexed loops over an injected List. Code written and tested with ArrayList goes quadratic when a caller passes a LinkedList. Use for-each or an iterator.
  • "Insert-heavy, so LinkedList." If inserts need a search to find their position, the search dominates and the linked list loses.
  • GC pressure. Millions of small nodes mean millions of objects to allocate, trace and promote; a 10M-element LinkedList costs roughly 240 MB in nodes alone with compressed oops.
  • Using LinkedList as a stack via push/pop works, but ArrayDeque does the same with one array and no per-element allocation.

Vector, Stack & CopyOnWriteArrayList

30m video30m practice

Making every method of a list synchronized does not make code that uses the list thread-safe, because real operations are compound. The useful thread-safe lists either give you the lock to hold (synchronizedList) or avoid locking readers entirely by copying on write (CopyOnWriteArrayList).

Vector: a synchronized ArrayList

Vector is structurally an ArrayList (an Object[] plus a count) in which nearly every public method is synchronized on the vector itself. Two differences remain: it doubles its capacity when full (or grows by capacityIncrement if you set one), and it still carries the 1.0 method names (addElement, elementAt, elements() returning an Enumeration).

The cost of per-method locking

Every call acquires and releases a monitor. Uncontended, that is cheap on modern HotSpot but not free: it adds atomic instructions and memory barriers on each get, and blocks optimizations across the call. Under contention, all readers serialize on one lock even though reads never conflict. The JIT can elide the lock only when escape analysis proves the vector never leaves its thread, which is exactly the case where you did not need synchronization.

Stack extends Vector: the design mistake

Stack adds push, pop, peek, empty and search, but because it extends Vector it also inherits every positional method. A stack that lets callers insert at index 0 does not enforce LIFO; this is the standard example of inheritance used where composition was needed (Effective Java Item 18). Its iteration order is also bottom-to-top, the opposite of what most people expect. The Stack Javadoc itself recommends Deque:

Stack<Integer> s = new Stack<>();
s.push(1); s.push(2); s.push(3);
s.add(0, 99);                 // compiles: inherited from Vector, breaks LIFO
System.out.println(s);        // [99, 1, 2, 3]   bottom first

Deque<Integer> d = new ArrayDeque<>();   // the replacement: no locks, no index access
d.push(1); d.push(2); d.push(3);
System.out.println(d);        // [3, 2, 1]       top first
System.out.println(d.pop());  // 3

Collections.synchronizedList and compound operations

Collections.synchronizedList(list) wraps any list in a decorator whose methods each run inside synchronized (mutex), where the mutex is the wrapper. Each single call is atomic. A sequence of calls is not:

List<String> ids = Collections.synchronizedList(new ArrayList<>());

// BROKEN: two threads can both see "absent" and both add
if (!ids.contains(id)) ids.add(id);

// FIXED: hold the wrapper's own lock across the compound action
synchronized (ids) {
    if (!ids.contains(id)) ids.add(id);
}

// Iteration is a compound action too; the Javadoc requires this block
synchronized (ids) {
    for (String s : ids) audit(s);
}

Check-then-act, read-modify-write (list.set(i, list.get(i) + 1)) and iterate-while-others-write all need the external lock. Synchronizing on anything other than the wrapper object gives no protection. Once you are writing those blocks anyway, a plain ArrayList behind a private lock object is clearer.

CopyOnWriteArrayList: snapshot semantics

Definition · copy-on-write

The list holds a volatile Object[]. Reads (get, size, contains, iteration) read the current array with no lock. Every mutation takes an internal lock, copies the array with the change applied, and publishes the new array by a single volatile write. An array, once published, is never modified.

var listeners = new CopyOnWriteArrayList<Consumer<String>>();
listeners.add(e -> System.out.println("log " + e));
Consumer<String> metrics = e -> {};
listeners.addIfAbsent(metrics);           // atomic check-then-act, built in

void fire(String event) {
    for (var l : listeners) l.accept(event); // safe even if a listener unsubscribes itself
}

Write cost. Each add, set or remove copies all n references, so n single adds cost O(n²) and momentarily need two arrays. Batch with addAll (one copy). The sweet spot is small lists that are read and iterated far more often than they change: event listeners, routing tables, feature-flag lists, configuration reloaded every few minutes.

Set & HashSet Internals

40m video40m practice

A HashSet is a HashMap whose keys are your elements and whose values are all one shared dummy object. Membership is decided by hashCode (which bucket) and then equals (which entry), so an element is only findable while both stay the same as when it was added.

The Set contract

A Set contains no two elements e1, e2 with e1.equals(e2), and at most one null if it allows null at all. It has no indices and, in the general contract, no order. Two sets are equal when they contain the same elements, regardless of implementation, and a set's hashCode is the sum of its elements' hash codes, so it is independent of iteration order. add returns true if the set changed and false if an equal element was already there; remove reports the same way. That return value is the cheapest duplicate detector you have:

Set<String> seen = new HashSet<>();
List<String> dupes = new ArrayList<>();
for (String id : List.of("a", "b", "a", "c", "b"))
    if (!seen.add(id)) dupes.add(id);      // one hash lookup, not contains() + add()
System.out.println(dupes);                 // [a, b]

HashSet is a HashMap with a dummy value

Definition · implementation

HashSet has one field that matters, transient HashMap<E,Object> map, and a constant static final Object PRESENT = new Object(). add(e) is map.put(e, PRESENT) == null; contains(o) is map.containsKey(o); remove(o) is map.remove(o) == PRESENT; the iterator is map.keySet().iterator(). Everything about buckets, resizing and treeification (L62, L63) therefore applies to sets unchanged, including the cost of about one HashMap.Node (roughly 32 bytes with compressed oops) per element.

How hashCode and equals decide membership

Algorithm · Lookup of an element
  1. Compute h = o.hashCode() and spread it: h ^ (h >>> 16) (null hashes to 0, which is why one null is allowed).
  2. Pick the bucket (table.length - 1) & h.
  3. Walk that bucket. A node matches when node.hash == h and (node.key == o or o.equals(node.key)).

Hash codes route the search; equals confirms it. Hence the contract (Object.hashCode Javadoc): equal objects must have equal hash codes. Override equals without hashCode and two equal objects land in different buckets, so the set happily stores both. Unequal objects may share a hash code; that only costs speed. Records generate a consistent pair from their components, which makes them good set elements.

The lost-element bug

The stored node caches the hash computed at insertion time. If a field used by hashCode changes afterwards, every lookup computes a different hash and goes to a different bucket (or fails the cached-hash comparison), while a fresh object equal to the original state finds the right bucket but fails equals.

final class Point {
    int x, y;                                  // mutable: the root cause
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) { return o instanceof Point p && p.x == x && p.y == y; }
    @Override public int hashCode() { return Objects.hash(x, y); }
}

Set<Point> set = new HashSet<>();
Point p = new Point(1, 2);
set.add(p);
p.x = 5;                                    // hash changes from 994 to 1118
System.out.println(set.contains(p));                // false
System.out.println(set.contains(new Point(1, 2)));  // false: equals fails
System.out.println(set.remove(p) + " " + set.size()); // false 1, the element is stuck
set.removeIf(q -> q == p);                  // only iteration can still reach it

The fix is to use immutable elements (a record Point(int x, int y)), or to remove the element, mutate it, and re-add it.

Set algebra, nulls and sizing

Set<String> a = Set.of("x", "y", "z"), b = Set.of("y", "z", "w");
Set<String> union = new HashSet<>(a); union.addAll(b);    // [w, x, y, z]
Set<String> inter = new HashSet<>(a); inter.retainAll(b); // [y, z]
Set<String> diff  = new HashSet<>(a); diff.removeAll(b);  // [x]
boolean sub = a.containsAll(inter);                          // true: inter ⊆ a

All three bulk operations mutate the receiver and return whether it changed, so copy first. Their cost depends on the argument's contains: retainAll(list) calls list.contains for every element of the set, which is O(n·m) for a List. Convert the argument to a HashSet when both sides are large. HashSet accepts one null; Set.of, TreeSet (natural ordering) and EnumSet reject it.

Capacity and load factor

The table has a power-of-two length (default 16) and resizes when size exceeds capacity × loadFactor (default 0.75). The constructor argument of new HashSet<>(1000) is a capacity: it becomes a 1024-slot table with threshold 768, so the 769th add triggers a rehash. Since Java 19, HashSet.newHashSet(1000) takes the expected element count and sizes the table so that 1000 elements fit without a resize (2048 slots). A lower load factor shortens chains at the cost of memory; a higher one does the reverse. Leave 0.75 alone unless you have measured.

What breaks in production
  • Mutable entities in sets. A JPA entity whose hashCode uses a generated ID changes hash when it is persisted, and vanishes from the HashSet it was added to before saving.
  • Overriding only equals. Deduplication silently stops deduplicating; size grows without bound.
  • Bulk operations against lists. set.retainAll(hugeList) becomes quadratic and looks like a hang.
  • Order assumptions. HashSet iteration order is unspecified and changes when the table resizes. Use LinkedHashSet or TreeSet (L61) if order is visible to anyone.

LinkedHashSet, TreeSet, SortedSet & NavigableSet

40m video40m practice

When a set's order matters you choose between two mechanisms: LinkedHashSet threads a linked list through a hash table to remember insertion order at O(1) cost, and TreeSet keeps a balanced search tree to maintain sorted order at O(log n) cost, which buys range and nearest-match queries. TreeSet judges duplicates by its comparator, never by equals.

LinkedHashSet: insertion order for free

LinkedHashSet extends HashSet but is backed by a LinkedHashMap, whose entries carry two extra references, before and after, forming a doubly linked list in insertion order. Lookups still hash; iteration follows the list, so it is proportional to size rather than table capacity. Re-adding an element that is already present does not move it. Java 21 adds SequencedSet methods: getFirst, getLast, reversed(), and addFirst/addLast, which relocate an existing element.

List<String> raw = List.of("b", "a", "b", "c", "a");
List<String> unique = new ArrayList<>(new LinkedHashSet<>(raw)); // [b, a, c] first-seen order
// same result as raw.stream().distinct().toList()

var tags = new LinkedHashSet<>(raw);   // [b, a, c]
tags.add("b");                          // false, order unchanged
tags.addLast("b");                      // Java 21: relocates -> [a, c, b]
System.out.println(tags.reversed());    // [b, c, a]  (a view, not a copy)

TreeSet: a red-black tree

Definition · TreeSet

TreeSet wraps a TreeMap (elements are keys, values the shared PRESENT). TreeMap is a red-black tree: a binary search tree in which each node is red or black, the root is black, no red node has a red child, and every root-to-leaf path has the same number of black nodes. Those rules bound the height at about 2 log2(n+1), so add, remove, contains, floor and friends are O(log n) worst case, and in-order traversal yields sorted iteration.

Natural ordering vs a Comparator

With the no-argument constructor elements must implement Comparable (or the first add throws ClassCastException), and order is compareTo. Pass a Comparator to sort by anything else. The comparator must be a total order over every element you insert, and it fully defines identity inside the set:

record Player(String name, int score) {}

Comparator<Player> byScore = Comparator.comparingInt(Player::score).reversed();
var broken = new TreeSet<>(byScore);
broken.add(new Player("ann", 90));
broken.add(new Player("bob", 90));        // compare == 0: treated as duplicate
System.out.println(broken.size());         // 1, bob is silently dropped

var board = new TreeSet<>(byScore.thenComparing(Player::name)); // tie-breaker
board.addAll(List.of(new Player("ann", 90), new Player("bob", 90), new Player("cy", 70)));
System.out.println(board.first().name());  // ann (highest score, then name)

SortedSet and NavigableSet

SortedSet (Java 1.2) gives first, last, comparator() and half-open range views. NavigableSet (Java 6) adds nearest-match queries, removal from the ends, inclusive/exclusive range flags and a descending view. Java 21 made SortedSet a SequencedSet, so getFirst and reversed() work too; addFirst/addLast throw UnsupportedOperationException because position is decided by the comparator.

NavigableSet<Integer> s = new TreeSet<>(List.of(10, 20, 30, 40, 50));
s.first();  s.last();        // 10, 50 (NoSuchElementException if empty)
s.floor(25);  s.ceiling(25); // 20, 30   greatest ≤ / least ≥
s.lower(20);  s.higher(20);  // 10, 30   strictly < / strictly >
s.floor(5);                  // null: nothing ≤ 5
s.headSet(30);               // [10, 20]           to, exclusive
s.headSet(30, true);         // [10, 20, 30]
s.tailSet(30);               // [30, 40, 50]       from, inclusive
s.subSet(20, 40);            // [20, 30]           [from, to)
s.subSet(20, false, 40, true); // [30, 40]
s.descendingSet();           // [50, 40, 30, 20, 10]
s.pollFirst();               // 10, and removes it; null if empty

Range views are live: they reflect later changes to the set, and inserting a value outside the view's range through the view throws IllegalArgumentException.

Compare, not equals: the consistency requirement

Rule · consistent with equals

A sorted set treats a and b as the same element when compare(a, b) == 0. If that disagrees with equals, the set still works as a sorted structure but violates the general Set contract, which is defined in terms of equals. The Comparable Javadoc strongly recommends natural orderings be consistent with equals; BigDecimal is the famous exception.

var a = new BigDecimal("1.0"); var b = new BigDecimal("1.00");
a.equals(b);       // false (different scale)
a.compareTo(b);    // 0
new HashSet<>(List.of(a, b)).size();   // 2
new TreeSet<>(List.of(a, b)).size();   // 1

var ci = new TreeSet<String>(String.CASE_INSENSITIVE_ORDER);
ci.addAll(List.of("Alice", "alice"));  // size 1; keeps "Alice"
ci.contains("ALICE");                  // true

Nulls. With natural ordering TreeSet rejects null with NullPointerException, because it calls compareTo on it (this is checked even for the first element). A comparator such as Comparator.nullsFirst(Comparator.naturalOrder()) can admit null, but most code is better off keeping nulls out.

What breaks in production
  • Comparators without a tie-breaker. Leaderboards and schedulers sorted only by score or time lose every element that ties. Always end with a unique key such as an ID.
  • Unboxing a missing match. int prev = set.floor(x); throws NPE when nothing qualifies. Keep the Integer and test for null.
  • Mutating a field the comparator reads after insertion corrupts the tree's ordering; contains and remove then miss elements that are present.
  • Mixed scales of BigDecimal deduplicate differently in HashSet and TreeSet; normalize with stripTrailingZeros() or pick one set type deliberately.

Map & HashMap Internals

50m video45m practice

A HashMap is an array of buckets; a key's hash code, scrambled and masked, picks the bucket, and equals picks the entry inside it. The modern Map API (computeIfAbsent, merge and friends) does lookup-and-update in a single traversal, which is both shorter and faster than get-then-put.

The Map contract, and why it is not a Collection

A Map<K,V> associates each key with at most one value. Key equality is equals/hashCode for hash maps and the comparator for sorted maps. Map does not extend Collection because the central operations do not line up: Collection.add(E) has no single-argument meaning for a pair, and "does it contain x" is ambiguous between key, value and entry. The Collections design FAQ puts it as "mappings are not collections and collections are not mappings". Instead a map offers three collection views. Two maps are equal when their entrySet()s are equal, whatever the implementations.

The method family

Map<String, Integer> stock = new HashMap<>();
stock.put("apple", 3);                  // returns previous value: null
stock.put("apple", 5);                  // returns 3
stock.get("pear");                      // null: absent, or present with a null value
stock.containsKey("pear");              // false: the only way to tell those apart
stock.getOrDefault("pear", 0);          // 0
stock.putIfAbsent("pear", 1);           // null (inserted); a second call returns 1, no change
stock.computeIfPresent("pear", (k, v) -> v + 1);        // 2
stock.compute("kiwi", (k, v) -> v == null ? 1 : v + 1); // 1: v is null when absent
stock.merge("apple", 10, Integer::sum);                 // 15: old + given
stock.computeIfPresent("kiwi", (k, v) -> null);         // a null result REMOVES the key
stock.remove("pear");                   // returns 2
stock.replaceAll((k, v) -> v * 2);      // {apple=30}
stock.forEach((k, v) -> System.out.println(k + "=" + v));
Idioms worth memorizing
  • Grouping: byCustomer.computeIfAbsent(o.customer(), k -> new ArrayList<>()).add(o); (it returns the existing or new value, so you can chain).
  • Counting: counts.merge(word, 1, Integer::sum);
  • In all of compute* and merge, returning null from the function removes the mapping (or skips adding it).
  • The function must not modify the same map. HashMap detects this in computeIfAbsent and compute and throws ConcurrentModificationException since Java 9; a recursive memoized Fibonacci written with computeIfAbsent is the classic way to hit it.

Views and Map.Entry

keySet(), values() and entrySet() are live views backed by the map, not copies: removals through them remove mappings, and Entry.setValue writes through. They do not support add, since a key alone (or a value alone) cannot make a mapping. Map.Entry is the pair interface with getKey, getValue, setValue; Map.entry(k, v) (Java 9) builds an immutable one, and Map.Entry.comparingByValue() sorts them.

Map<String, Integer> m = new HashMap<>(Map.of("a", 1, "b", 2, "c", 3));
m.keySet().remove("a");                       // mapping a=1 is gone
m.values().removeIf(v -> v > 2);              // mapping c=3 is gone
for (Map.Entry<String, Integer> e : m.entrySet())
    e.setValue(e.getValue() * 10);            // m is now {b=20}
// m.keySet().add("z");                       // UnsupportedOperationException

String top = m.entrySet().stream()
    .max(Map.Entry.comparingByValue()).map(Map.Entry::getKey).orElseThrow(); // "b"

Iterate entrySet() when you need both key and value; iterating keySet() and calling get repeats the hash lookup for every key.

Buckets and nodes

Definition · HashMap layout

The core fields are transient Node<K,V>[] table (length always a power of two, allocated lazily on the first put, default 16), size, threshold and modCount. Each bucket holds a singly linked chain of Nodes: final int hash (the spread hash, cached), final K key, V value, Node next. Long chains become red-black trees (L63).

Algorithm · put
  1. hash = (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16).
  2. If the table is null, allocate it (resize()). Index i = (n - 1) & hash.
  3. Empty bucket: place a new node. Otherwise walk the chain; a node with node.hash == hash && (node.key == key || key.equals(node.key)) gets its value replaced and the old value is returned.
  4. No match: append a node at the tail (Java 8+; Java 7 inserted at the head). If the chain now holds more than TREEIFY_THRESHOLD (8) nodes, treeify the bin.
  5. modCount++; if ++size > threshold, resize. get runs steps 1–3 without writing.

Why (n - 1) & hash, and why spread the hash

Because n is a power of two, n - 1 is a mask of low one-bits, and (n - 1) & hash equals Math.floorMod(hash, n) for every int, negative ones included: no division and never a negative index. The price is that only the low bits of the hash choose the bucket: in a 16-slot table, just 4 bits. Hash codes that differ only in their high bits would all collide. h ^ (h >>> 16) folds the high half into the low half at the cost of one shift and one XOR, so those bits take part.

static int spread(int h) { return h ^ (h >>> 16); }

int[] codes = {0x10000, 0x20000, 0x30000};       // differ only above bit 15
for (int h : codes)
    System.out.println((15 & h) + " vs " + (15 & spread(h)));
// 0 vs 1
// 0 vs 2
// 0 vs 3   without spreading, all three would share bucket 0

Such hash codes are not exotic: Float.hashCode of small whole numbers, for example, puts the varying bits high (it is the IEEE bit pattern).

Why keys must be immutable

The node caches the hash computed at put time and sits in the bucket that hash selected. Change a key field that feeds hashCode and the entry is orphaned: get with the mutated key computes a new hash and searches the wrong bucket, and get with an object equal to the old state finds the bucket but fails equals. The value is unreachable and leaks until the map dies. Use immutable keys: String (which also caches its hash code), boxed primitives, enums, records of immutable components. Never use a mutable List or an entity with a setter as a key.

Map<List<String>, Integer> m = new HashMap<>();
List<String> key = new ArrayList<>(List.of("x"));
m.put(key, 1);
key.add("y");                              // List.hashCode depends on contents
System.out.println(m.get(key));            // null
System.out.println(m.get(List.of("x")));   // null
System.out.println(m.size());              // 1
What breaks in production
  • get(k) == null as an absence test. It conflates "absent" with "mapped to null". Use containsKey, getOrDefault or avoid null values entirely.
  • Get-then-put races. if (!m.containsKey(k)) m.put(k, v) on a shared map is a race even in ConcurrentHashMap; use its atomic putIfAbsent/computeIfAbsent.
  • Modifying the map inside computeIfAbsent. Throws CME on HashMap; on older JDKs it could silently corrupt the map.
  • Poor hashCode. A hashCode that returns a constant, or ignores the distinguishing field, turns every operation into a chain walk.

HashMap Resizing, Treeification & Collision Attacks

45m video40m practice

HashMap keeps chains short in the average case by doubling its table whenever it is three-quarters full, and keeps them survivable in the worst case by turning any chain longer than eight into a red-black tree. Both mechanisms exist because hash codes come from user code, and sometimes from an attacker.

Load factor 0.75 and the math behind it

The load factor α is entries per bucket. HashMap resizes when size > threshold = capacity × 0.75, so between resizes α ranges from about 0.375 to 0.75. The implementation notes in HashMap.java justify the numbers: with well-distributed hash codes, the number of nodes in a bin follows a Poisson distribution with parameter about 0.5 at the default load factor, P(k) = e−0.5 · 0.5k / k!.

So almost every lookup inspects zero or one node, and a bin of 8 should essentially never occur by chance. A higher load factor saves table memory but lengthens chains; a lower one does the reverse. 0.75 is the documented compromise between time and space cost; there is rarely a reason to change it.

Threshold, doubling and the lo/hi split

A default map starts at capacity 16, threshold 12. The 13th put calls resize(): capacity and threshold double (32 and 24), a new table is allocated, and every node is moved. Because the capacity is a power of two and doubles, a node's new index depends on exactly one extra bit of its hash: the bit equal to oldCap.

Result · split rule

For a node in old bucket j: if (hash & oldCap) == 0 it stays at j (the "lo" list), otherwise it moves to j + oldCap (the "hi" list). No hash is recomputed, each chain is walked once, and both lists keep their original relative order.

The Java 7 infinite loop

Java 7's transfer re-inserted each moved node at the head of its new bucket, reversing chains. When two threads resized the same unsynchronized map concurrently, interleaved reversals could link two nodes to each other, and a later get spun forever at 100% CPU. Java 8's order-preserving lo/hi split removes that particular cycle. It does not make HashMap thread-safe: concurrent writers still lose updates and can corrupt the structure. Shared mutable maps need ConcurrentHashMap (L66).

Treeification: red-black buckets

When a chain grows beyond TREEIFY_THRESHOLD = 8, treeifyBin checks the table size first: below MIN_TREEIFY_CAPACITY = 64 it simply resizes, because a long chain in a small table is more likely crowding than a bad hash. Otherwise the chain becomes a red-black tree of TreeNodes. During a resize, a split tree half with UNTREEIFY_THRESHOLD = 6 or fewer nodes turns back into a plain chain; the gap between 8 and 6 prevents flapping. Removals can also untreeify a bin that has become very small.

Tree bins are ordered by hash first. Among equal hashes, if the keys are of the same class and implement Comparable (String, boxed numbers, many records you write), compareTo orders them and a lookup is O(log k) for a bin of k nodes. If keys are equal-hashed and not comparable, insertion uses an arbitrary tie-break, but a lookup may have to search both subtrees, so the worst case is still O(k). Treeification bounds the damage for comparable keys; it does not excuse a bad hashCode.

Hash collision denial of service

In 2011 Klink and Wälde (28C3) showed that many web platforms parsed request parameters into hash tables, and that colliding keys are easy to manufacture. In Java, "Aa" and "BB" both hash to 2112, and because String.hashCode is a polynomial, any concatenation of equal-length blocks with equal hashes collides too: n blocks give 2n distinct keys with one hash code. A single POST with tens of thousands of such parameters made each insertion walk a chain of all previous ones, quadratic CPU on one request.

static List<String> collidingKeys(int blocks) {        // 2^blocks keys, one hashCode
    List<String> keys = List.of("");
    for (int i = 0; i < blocks; i++) {
        List<String> next = new ArrayList<>(keys.size() * 2);
        for (String k : keys) { next.add(k + "Aa"); next.add(k + "BB"); }
        keys = next;
    }
    return keys;
}
var keys = collidingKeys(16);                            // 65,536 keys
System.out.println(keys.stream().map(String::hashCode).distinct().count()); // 1

The responses: servlet containers cap parameter counts (Tomcat's maxParameterCount), Java 7u6 briefly added alternative string hashing, and Java 8 replaced that with tree bins. Since String is Comparable, the attack now degrades each operation to O(log n) instead of O(n). Still limit request size, header count and JSON nesting at the edge: a bounded log factor is better than a quadratic, but parsing a million keys is still work.

Sizing correctly, and what an entry costs

Map<String, User> byId = HashMap.newHashMap(users.size());   // Java 19+: expected entries
Map<String, User> old  = new HashMap<>((int) Math.ceil(users.size() / 0.75)); // pre-19 idiom
Map<String, User> bad  = new HashMap<>(users.size());       // capacity, not expected size

For 1,000 entries, new HashMap<>(1000) builds 1,024 buckets with threshold 768 and resizes once more; newHashMap(1000) builds 2,048. Filling a default map with a million entries performs 17 resizes (16 up to 221 buckets).

  • Sharing a HashMap across threads because "Java 8 fixed the infinite loop". It fixed one symptom, not the data race.

LinkedHashMap & Building an LRU Cache

35m video45m practice

LinkedHashMap is a HashMap whose entries are also threaded onto a doubly linked list. In insertion-order mode that list makes iteration deterministic; in access-order mode every read moves an entry to the tail, so the head is always the least recently used entry, and one overridden hook turns the map into an LRU cache.

The doubly linked entry chain

Definition · LinkedHashMap.Entry

LinkedHashMap.Entry extends HashMap.Node with two references, before and after, and the map keeps head (eldest) and tail (youngest). Hashing, buckets and resizing are inherited unchanged; HashMap calls three hooks that LinkedHashMap overrides: afterNodeAccess (move to tail), afterNodeInsertion (maybe evict the head) and afterNodeRemoval (unlink). Iteration walks the list, so it costs O(size) regardless of table capacity, and each entry costs about 8 bytes more than a HashMap entry.

Insertion order vs access order

The default constructors produce insertion order: iteration follows the order keys were first added, and re-putting an existing key does not move it. The three-argument constructor LinkedHashMap(initialCapacity, loadFactor, accessOrder) with accessOrder = true produces access order: get, getOrDefault, put on an existing key, putIfAbsent, compute*, merge and replace move the touched entry to the tail. containsKey and iteration over the views do not count as access.

var ins = new LinkedHashMap<String, Integer>();
ins.put("a", 1); ins.put("b", 2); ins.put("a", 9);
System.out.println(ins);                  // {a=9, b=2}  re-put keeps position

var acc = new LinkedHashMap<String, Integer>(16, 0.75f, true);
acc.put("a", 1); acc.put("b", 2); acc.put("c", 3);
acc.get("a");
System.out.println(acc.keySet());         // [b, c, a]
System.out.println(acc.firstEntry());     // b=2  (SequencedMap, Java 21)

Java 21's SequencedMap methods work on both modes: firstEntry, lastEntry, pollFirstEntry, reversed(), and putFirst/putLast, which insert or relocate a mapping at an end.

The removeEldestEntry hook

After every insertion of a new key (put, putAll, computeIfAbsent, merge…), afterNodeInsertion calls protected boolean removeEldestEntry(Map.Entry<K,V> eldest). The default returns false. Return true and the head entry is removed. The hook may inspect eldest (to log, or to refuse eviction of pinned entries); the Javadoc permits it to modify the map directly, but then it must return false so the map does not evict a second time.

A working LRU cache in 20 lines

public final class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxEntries;

    public LruCache(int maxEntries) {
        super(16, 0.75f, true);                      // access order
        if (maxEntries <= 0) throw new IllegalArgumentException("maxEntries <= 0");
        this.maxEntries = maxEntries;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxEntries;                  // evict least recently used
    }
}

var cache = new LruCache<String, Integer>(3);
cache.put("a", 1); cache.put("b", 2); cache.put("c", 3);
cache.get("a");                                    // order: b, c, a
cache.put("d", 4);                                 // size 4 > 3: evicts b
System.out.println(cache.keySet());                // [c, a, d]

Every operation is O(1). Subclassing is the idiom the Javadoc itself shows; if you do not want callers to see the full Map API, wrap a private LinkedHashMap in a small class exposing only get and put.

Thread safety, and when to use Caffeine

In access-order mode get is a structural modification: it relinks nodes and increments modCount. So concurrent readers corrupt the list just as concurrent writers would, a read-write lock does not help (reads write), and calling get while iterating throws ConcurrentModificationException. The minimal fix is one global lock:

Map<String, Integer> shared = Collections.synchronizedMap(new LruCache<>(10_000));

That is correct but serializes every hit. When a cache is shared by many request threads, needs expiry (time-to-live), size by weight, statistics or asynchronous loading, use Caffeine (covered in depth around plan Day 387). It is concurrent, and its authors report that its W-TinyLFU policy achieves a near-optimal hit rate, generally better than pure LRU on real traces.

Cache<String, User> users = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofMinutes(5))
        .recordStats()
        .build();
User u = users.get(id, this::loadUser);    // load on miss, once per key

Deterministic serialization order

Jackson and most serializers write a Map in its iteration order. A HashMap payload has an unspecified field order, and Map.of order is randomized per JVM run. That breaks snapshot tests, makes diffs noisy, and changes hashes computed over the bytes (ETags, cache keys, request signatures). Build response maps with LinkedHashMap when the order you insert is the order you want, or TreeMap for sorted keys; Jackson can also sort with SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS.

Map<String, Object> body = new LinkedHashMap<>();
body.put("id", 42);
body.put("status", "PAID");
body.put("total", 1999);
// always {"id":42,"status":"PAID","total":1999}
What breaks in production
  • Unsynchronized LRU shared across threads. Corrupted before/after links can lose entries or loop iteration; it fails rarely and unreproducibly.
  • Iterating an access-ordered map and calling get (for example logging cache contents) throws CME.
  • Unbounded "cache" maps. A plain HashMap used as a cache with no eviction is a memory leak with a nice name.
  • Hit-rate collapse under scans. Pure LRU evicts the hot set when a batch job reads many keys once. Frequency-aware policies (Caffeine) resist this.

TreeMap, SortedMap & NavigableMap

40m video40m practice

A TreeMap costs O(log n) per operation where a HashMap costs O(1), and you pay that for one reason: questions about neighbouring keys. "Which bracket contains this value", "everything in the last five minutes" and "the top ten scores" are single calls on a NavigableMap and full scans on a hash map.

The red-black tree underneath

Definition · TreeMap

Each TreeMap.Entry holds key, value, left, right, parent and a color bit (about 40 bytes with compressed oops). Lookups descend from the root comparing with the comparator, or with compareTo when none was given. put attaches a new red leaf and then fixAfterInsertion restores the red-black rules by recolouring up the tree and doing at most two rotations; remove uses fixAfterDeletion with at most three. The height stays below 2 log2(n+1), so get, put, remove, containsKey and every navigation method are O(log n) in the worst case.

An in-order walk visits keys in ascending order, so keySet(), values() and entrySet() iterate sorted, and stepping to the successor is amortized O(1). In absolute terms a TreeMap lookup in a million keys is about 20 comparisons with a pointer dereference each; a HashMap lookup is usually one hash and one or two equals. Choose the tree only when you need order. Natural ordering rejects null keys (NullPointerException); null values are fine.

SortedMap and NavigableMap, method by method

SortedMap gives firstKey, lastKey and half-open headMap/tailMap/subMap views. NavigableMap (Java 6) adds nearest-match lookups in two flavours, …Key returning the key and …Entry returning the mapping, plus inclusive flags, descendingMap and poll…. Since Java 21 SortedMap is a SequencedMap; putFirst/putLast throw UnsupportedOperationException because the comparator decides position.

NavigableMap<Integer, String> m = new TreeMap<>(Map.of(10, "a", 20, "b", 30, "c", 40, "d"));
m.firstKey();  m.lastKey();          // 10, 40   (NoSuchElementException if empty)
m.floorKey(25);  m.ceilingKey(25);   // 20, 30   greatest ≤ / least ≥
m.higherEntry(30);                   // 40=d     strictly greater
m.lowerEntry(10);                    // null     nothing strictly less
m.headMap(30);                       // {10=a, 20=b}           exclusive bound
m.tailMap(30);                       // {30=c, 40=d}           inclusive bound
m.subMap(15, true, 35, false);       // {20=b, 30=c}
m.descendingMap();                   // {40=d, 30=c, 20=b, 10=a}
m.pollFirstEntry();                  // 10=a, and removes it
m.floorEntry(25).setValue("x");      // UnsupportedOperationException: snapshot entry

Entries returned by firstEntry, floorEntry, pollFirstEntry and friends are immutable snapshots. Range views are live, cost nothing to create, and support writes within their range; putting a key outside the range through a view throws IllegalArgumentException. m.headMap(k).clear() deletes a whole prefix in one call.

Interval lookup with floorEntry

Store non-overlapping intervals keyed by their start. The interval containing x, if any, is the one with the greatest start ≤ x; check its end. The same pattern covers tax and shipping brackets, IP-range ownership, versioned configuration ("which config was active at time t") and feature rollouts by user-ID range.

record IpRange(long start, long end, String owner) {}

final class IpIndex {
    private final NavigableMap<Long, IpRange> byStart = new TreeMap<>();
    void add(IpRange r) { byStart.put(r.start(), r); }   // ranges must not overlap
    Optional<IpRange> lookup(long ip) {
        var e = byStart.floorEntry(ip);
        return (e != null && ip <= e.getValue().end()) ? Optional.of(e.getValue()) : Optional.empty();
    }
}

Time series, rate windows and bucketing

Keyed by timestamp, a TreeMap is an ordered event log: tailMap(now - window) is "recent", headMap(cutoff).clear() is retention, and floorEntry(t) is "the last value at or before t" (sample-and-hold). A sliding-window rate limiter falls out directly:

final class SlidingWindowLimiter {
    private final NavigableMap<Long, Integer> hitsPerSecond = new TreeMap<>();
    private final long windowSeconds;
    private final int limit;

    SlidingWindowLimiter(long windowSeconds, int limit) {
        this.windowSeconds = windowSeconds; this.limit = limit;
    }
    synchronized boolean tryAcquire(long nowSecond) {
        hitsPerSecond.headMap(nowSecond - windowSeconds, true).clear(); // keep (now - w, now]
        int used = 0;
        for (int c : hitsPerSecond.values()) used += c;                 // at most w buckets
        if (used >= limit) return false;
        hitsPerSecond.merge(nowSecond, 1, Integer::sum);
        return true;
    }
}

To bucket a series (per-minute averages, hourly counts), group into a TreeMap so the result is already sorted: Collectors.groupingBy(e -> e.getKey().truncatedTo(ChronoUnit.MINUTES), TreeMap::new, Collectors.averagingDouble(Map.Entry::getValue)).

Comparator-based ordering and leaderboards

A comparator passed to the constructor defines both order and key identity. new TreeMap<>(String.CASE_INSENSITIVE_ORDER) makes "Content-Type" and "content-type" one key, a common choice for HTTP headers. new TreeMap<>(Comparator.reverseOrder()) puts the largest key first, which suits leaderboards. Because ties collapse, map scores to the set of players holding them:

NavigableMap<Integer, Set<String>> board = new TreeMap<>(Comparator.reverseOrder());
void record(String player, int score) {
    board.computeIfAbsent(score, s -> new TreeSet<>()).add(player);
}
List<String> top(int n) {
    return board.values().stream().flatMap(Set::stream).limit(n).toList();  // highest first
}
// players scoring at least 900 (reverse order, so "head" means higher):
// board.headMap(900, true)
What breaks in production
  • Score-keyed maps without a set of values. TreeMap<Integer, String> keyed by score keeps one player per score; the second put overwrites the first.
  • Inverted bounds under a reverse comparator. With reverseOrder(), subMap(10, 100) throws IllegalArgumentException (fromKey > toKey); bounds follow the map's order, not numeric order.
  • Unboxing a null navigation result. long start = map.floorKey(x); throws NPE when x is below every key.
  • Unbounded time-series maps. Without a headMap(cutoff).clear() retention step, an in-memory window grows forever.

Specialized Maps: ConcurrentHashMap, WeakHashMap, EnumMap, IdentityHashMap

40m video35m practice

Every specialized map changes exactly one assumption of HashMap: who may touch it concurrently, how strongly it holds its keys, what kind of key it stores, or what "equal key" means. Knowing which assumption you need to change tells you which map to use.

Hashtable, the legacy baseline

Hashtable (Java 1.0, retrofitted to Map in 1.2) is a hash table whose public methods are all synchronized on the table. It rejects null keys and values, extends the obsolete Dictionary class, and exposes keys()/elements() as Enumerations. Like Vector (L59), it serializes all readers on one lock and still leaves compound actions unprotected. It survives mostly through Properties. In new code it has no use.

ConcurrentHashMap: an overview

Definition · Java 8+ design

A table of bins much like HashMap, built for concurrent access. Reads take no lock: they use volatile reads of the table and node fields. A write into an empty bin is a single CAS. A write into a non-empty bin locks only that bin's first node with synchronized, so writers to different bins proceed in parallel. Resizing is cooperative: threads that arrive during a resize help move bins. The size is kept in striped counter cells (the LongAdder technique) to avoid a contended counter. Java 7 used a fixed array of lock segments instead. The full internals come later in the course (plan Day 145).

ConcurrentMap<String, LongAdder> hits = new ConcurrentHashMap<>();
hits.computeIfAbsent(path, k -> new LongAdder()).increment();  // atomic create, cheap increment

ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge(word, 1, Integer::sum);       // atomic read-modify-write for this key
long n = counts.mappingCount();            // long-valued; an estimate while updates run

Its rules: no null keys or values (a null from get must unambiguously mean "absent", since you cannot follow up with containsKey atomically); compute* and merge run the function atomically, at most once per call, while holding the bin, so keep the function short and never touch other keys of the same map inside it; iterators are weakly consistent and never throw CME; size() is a moment-in-time estimate under concurrency.

WeakHashMap: keys held weakly

Each entry is a WeakReference to its key, registered with a ReferenceQueue. Once the key is reachable only through the map, the collector may clear it; the next get, put or size calls expungeStaleEntries and drops the entry. Use it to attach data to objects whose lifetime someone else controls, so the data dies with the object.

Map<Object, String> meta = new WeakHashMap<>();
Object session = new Object();
meta.put(session, "metadata");
session = null;          // last strong reference gone
System.gc();             // only a hint; clearing is not guaranteed
// eventually meta.size() == 0, observed on a later map operation
Where it surprises people
  • Keys are compared with equals, but held weakly. String literals and small boxed integers are strongly reachable from elsewhere (constant pool, Integer cache), so those entries never disappear.
  • A value that references its own key keeps the key strongly reachable: the entry is never collected.
  • It is not a cache: entries vanish when the GC runs, not by size or recency. It is not thread-safe either. For concurrent weak-keyed caches use Caffeine's weakKeys(); for per-class data, ClassValue.

IdentityHashMap and EnumMap

IdentityHashMap compares keys with == and hashes with System.identityHashCode, deliberately breaking the Map contract. Internally it is a single Object[] with keys and values in alternating slots and linear probing, no node objects at all. It is the right tool when object identity is the question: visited sets in graph traversals, serializers and deep-copy routines that must detect cycles and shared references, proxies keyed by instance.

Map<String, Integer> byIdentity = new IdentityHashMap<>();
String a = new String("k"), b = new String("k");
byIdentity.put(a, 1); byIdentity.put(b, 2);
System.out.println(byIdentity.size());   // 2, although a.equals(b)

enum Status { NEW, PAID, SHIPPED, CANCELLED }
record Order(String id, Status status) {}

Map<Status, Long> byStatus = orders.stream().collect(Collectors.groupingBy(
        Order::status, () -> new EnumMap<>(Status.class), Collectors.counting()));
// iteration is always NEW, PAID, SHIPPED, CANCELLED

EnumMap stores values in an array indexed by key.ordinal(): no hashing, no nodes, no collisions, and iteration in declaration order. It is the fastest and most compact map whenever the keys are one enum type. Null keys are rejected; null values are allowed. Its sibling EnumSet is a bit vector (one long for up to 64 constants).

Properties and the immutable factories

Properties extends Hashtable<Object,Object> but should be used only through its string API: getProperty(key, default), setProperty, stringPropertyNames(), plus a chain of defaults. load(InputStream) assumes ISO-8859-1; load through a Reader for UTF-8 files.

var props = new Properties();
try (Reader r = Files.newBufferedReader(Path.of("app.properties"))) {  // UTF-8
    props.load(r);
}
int port = Integer.parseInt(props.getProperty("server.port", "8080"));

Map<String, Integer> small = Map.of("a", 1, "b", 2);                  // up to 10 pairs
Map<String, Integer> large = Map.ofEntries(Map.entry("a", 1), Map.entry("b", 2)); // any count
Map<String, Integer> snap  = Map.copyOf(counts);                      // immutable copy
// Map.of("a", 1, "a", 2)  -> IllegalArgumentException: duplicate key: a

Map.of, Map.ofEntries and Map.copyOf return truly immutable maps: every mutator throws UnsupportedOperationException, nulls are rejected, and iteration order is unspecified and varies between JVM runs.

Queue, Deque, ArrayDeque & PriorityQueue

45m video45m practice

A queue is defined by which element comes out next. ArrayDeque answers "the oldest" or "the newest" with a circular array and O(1) at both ends; PriorityQueue answers "the smallest" with a binary heap and O(log n) per operation, which is ordered at the head and nowhere else.

The Queue contract: two families of methods

Queue offers every operation twice: one version throws when it cannot proceed, the other returns a special value. Pick one family per code path and stick to it.

OperationThrows exceptionReturns special value
Insert at tailadd(e): IllegalStateException if a bounded queue is fulloffer(e): false
Remove headremove(): NoSuchElementException if emptypoll(): null
Examine headelement(): NoSuchElementExceptionpeek(): null

Because null is the "empty" signal, most queue implementations reject null elements. Deque doubles the table for both ends (addFirst/offerFirst, removeLast/pollLast, getFirst/peekLast…), adds the stack trio push/pop/peek working on the head, and descendingIterator(). Since Java 21 it is also a SequencedCollection with reversed().

ArrayDeque: a circular buffer

Definition · ArrayDeque

An Object[] elements with two indices, head (first element) and tail (next free slot), that move modulo the array length. addFirst decrements head with wrap-around, addLast writes at tail and increments it; removal reads, nulls the slot and moves the index. Nothing is ever shifted. When the indices would meet, the array grows (in current JDKs roughly doubling while small, then by half) and the wrapped segment is straightened. Null slots mean "empty", which is why null elements are forbidden.

capacity 8 (simplified), after addLast(a..f), pollFirst() x4, addLast(g..j):
index:   0   1   2   3   4   5   6   7
        [i] [j] [ ] [ ] [e] [f] [g] [h]
                 ^tail   ^head          iteration: e f g h i j

Compared with its rivals: Stack synchronizes every call and exposes indexed access (L59); LinkedList allocates a 24-byte node per element and chases pointers (L58). ArrayDeque has neither cost, so it is the default for FIFO queues, stacks, BFS frontiers, undo histories and sliding windows. Its Javadoc says as much: likely faster than Stack as a stack and than LinkedList as a queue.

static boolean balanced(String s) {             // ArrayDeque as a stack
    Deque<Character> st = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        switch (c) {
            case '(', '[', '{' -> st.push(c);
            case ')', ']', '}' -> {
                Character open = st.poll();             // null when empty
                if (open == null || "([{".indexOf(open) != ")]}".indexOf(c)) return false;
            }
            default -> { }
        }
    }
    return st.isEmpty();
}

PriorityQueue: a binary heap in an array

Definition · binary min-heap

A complete binary tree stored level by level in Object[] queue: the children of index i are 2i+1 and 2i+2, the parent is (i−1)/2. The heap property says every parent is ≤ its children under the comparator, so the minimum is always queue[0]. offer appends at the end and sifts up (swap with the parent while smaller); poll removes the root, moves the last element to the root and sifts down (swap with the smaller child while larger). Both are O(log n); peek is O(1); remove(Object) and contains are O(n) linear scans. Building from a collection uses bottom-up heapify, O(n).

PriorityQueue<Integer> pq = new PriorityQueue<>();
for (int x : new int[]{5, 3, 7, 1, 4, 2}) pq.offer(x);
System.out.println(pq);        // [1, 3, 2, 5, 4, 7]   array order
System.out.println(pq.poll()); // 1
System.out.println(pq);        // [2, 3, 7, 5, 4]      7 moved to root, sifted down
// sorted output means repeated poll(), O(n log n):
while (!pq.isEmpty()) System.out.print(pq.poll() + " "); // 2 3 4 5 7

Custom comparators and top-K

Pass a comparator to order by anything; Comparator.reverseOrder() gives a max-heap. Records with Comparator.comparing chains read well: new PriorityQueue<>(Comparator.comparing(Task::deadline).thenComparing(Task::id)). Unlike TreeSet, a priority queue keeps elements that compare equal, so ties are allowed, but their relative order is unspecified (it is not a stable sort).

Algorithm · Top K of n with a size-K min-heap
  1. Keep a min-heap holding the K largest elements seen so far; its head is the smallest of them, the current cut-off.
  2. For each element: if the heap has fewer than K elements, offer it; otherwise, if it beats the head, poll the head and offer it.
  3. At the end the heap holds the top K. Cost O(n log K) time, O(K) memory, one pass, works on a stream that does not fit in memory.
record Score(String user, int points) {}

static List<Score> topK(Iterable<Score> all, int k) {
    var heap = new PriorityQueue<Score>(Comparator.comparingInt(Score::points));
    for (Score s : all) {
        if (heap.size() < k) heap.offer(s);
        else if (s.points() > heap.peek().points()) { heap.poll(); heap.offer(s); }
    }
    var out = new ArrayList<>(heap);
    out.sort(Comparator.comparingInt(Score::points).reversed());   // best first
    return out;
}

BlockingQueue preview

java.util.concurrent.BlockingQueue adds a third family: put blocks while full and take blocks while empty, and offer(e, timeout, unit)/poll(timeout, unit) wait a bounded time. It is the standard hand-off between producer and consumer threads, and a bounded one provides backpressure. Implementations include ArrayBlockingQueue (bounded array), LinkedBlockingQueue (optionally bounded), PriorityBlockingQueue, DelayQueue and SynchronousQueue (no capacity at all). Thread pools are built on them; the concurrency phase covers them properly.

BlockingQueue<Job> jobs = new ArrayBlockingQueue<>(1_000);
jobs.put(job);                                  // producer: waits while full
Job next = jobs.poll(1, TimeUnit.SECONDS);      // consumer: null after 1 s of nothing
What breaks in production
  • Printing or iterating a PriorityQueue to show "the order". It is array order; dashboards built that way show nonsense rankings.
  • Mutating an element's priority while it is queued. The heap is not re-sifted, so the element sits in the wrong place. Remove, update, re-offer (O(n) for the remove), or use a lazy-deletion scheme.
  • Mixing families. Calling remove() where the queue may be empty throws in production while poll() in tests returned null quietly.
  • Unbounded work queues. A LinkedBlockingQueue without capacity behind a thread pool absorbs a traffic spike by consuming the heap until the JVM dies.

Iterator, ListIterator & ConcurrentModificationException

35m video40m practice

Every for-each loop over a collection is an Iterator in disguise, and the iterator, not the loop, decides what happens when the collection changes underneath it: standard collections fail fast with ConcurrentModificationException, concurrent ones keep going with a snapshot or a weakly consistent view. Modify through the iterator, or through a bulk method, and the problem disappears.

The Iterable and Iterator contracts

Definition · Iterator

Iterable<T> has one abstract method, iterator(), plus defaults forEach and spliterator. An Iterator<E> has hasNext() (true if next() would return an element; must have no side effects), next() (return it and advance; throw NoSuchElementException when exhausted), an optional remove() (delete the element last returned by next; at most once per next, else IllegalStateException; the default throws UnsupportedOperationException) and forEachRemaining.

JLS §14.14.2 defines the enhanced for statement by translation. For an Iterable it becomes an explicit iterator loop; for an array, an index loop over a copy of the array reference. There is no third case, which is why you cannot for-each over an Iterator or a Stream directly.

for (String s : names) process(s);

// is compiled as
for (Iterator<String> it = names.iterator(); it.hasNext(); ) {
    String s = it.next();
    process(s);
}

ListIterator: a cursor between elements

List.listIterator() (or listIterator(index)) returns a ListIterator, whose cursor sits between elements. It moves both ways (hasPrevious, previous, nextIndex, previousIndex) and can modify the list at the cursor: set(e) replaces the element last returned by next or previous, add(e) inserts at the cursor (so the next next() is unaffected and previous() would return the new element), and remove() deletes the last returned element. set and remove are illegal after an add until you move again.

List<String> xs = new ArrayList<>(List.of("a", "b", "c"));
ListIterator<String> it = xs.listIterator();
while (it.hasNext()) {
    if (it.next().equals("b")) {
        it.set("B");          // replace the element just returned
        it.add("b2");         // insert at the cursor, after "B"
    }
}
System.out.println(xs);       // [a, B, b2, c]
while (it.hasPrevious()) System.out.print(it.previous() + " "); // c b2 B a

Fail-fast iterators and modCount

As in L57, ArrayList, HashMap, TreeMap, LinkedList and the other unsynchronized collections keep a modCount of structural changes. Their iterators remember the value at creation and compare on each next() (and on remove); any change made other than through that iterator triggers ConcurrentModificationException. Two points are routinely misunderstood: the exception is about modification during iteration, almost always in single-threaded code, not about threads; and it is best-effort: the Javadoc forbids relying on it for correctness, and some sequences (removing the second-to-last element) slip through silently.

Reproducing and fixing ConcurrentModificationException

List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4, 5, 6));
// BROKEN, throws CME on the next call to next():
// for (Integer n : nums) if (n % 2 == 0) nums.remove(n);

// Fix 1: remove through the iterator
for (Iterator<Integer> it = nums.iterator(); it.hasNext(); )
    if (it.next() % 2 == 0) it.remove();

// Fix 2: a bulk operation (single O(n) pass on ArrayList)
nums.removeIf(n -> n % 2 == 0);

// Fix 3: iterate a snapshot, modify the original
for (Integer n : List.copyOf(nums))
    if (n % 2 == 0) nums.remove(n);          // remove(Object), since n is an Integer

// Fix 4: a collection whose iterators tolerate concurrent change
List<Integer> cow = new CopyOnWriteArrayList<>(nums);
for (Integer n : cow)
    if (n % 2 == 0) cow.remove(n);

For maps, the same tools apply to the views: map.entrySet().removeIf(e -> …), map.values().removeIf(…), or an explicit entry iterator with it.remove(); to change values while iterating, use entry.setValue or map.replaceAll, neither of which is structural. Prefer fix 2 for clarity and speed, fix 1 when the loop does other work, fix 3 when the modification is not a removal (adding related elements), and fix 4 only when other threads are really involved.

Fail-safe and weakly consistent iterators

"Fail-safe" is informal; the Javadoc distinguishes two behaviours. Snapshot iterators (CopyOnWriteArrayList, CopyOnWriteArraySet) traverse the array that existed when they were created: no CME, no later changes visible, no remove. Weakly consistent iterators (ConcurrentHashMap, ConcurrentSkipListMap, ConcurrentLinkedQueue, most of java.util.concurrent) never throw CME, return each element at most once, and reflect some, all or none of the modifications made after they were created. They trade a precise answer for the ability to iterate while other threads write.

var sessions = new ConcurrentHashMap<String, Long>(Map.of("a", 1L, "b", 99L));
for (var e : sessions.entrySet())
    if (e.getValue() < 10) sessions.remove(e.getKey());  // no CME; safe in CHM

Writing a custom Iterable, and a Spliterator teaser

Implement Iterable and any for-each loop, forEach call and (via spliterator()) stream can consume your type. A correct iterator keeps hasNext side-effect free, throws NoSuchElementException from an exhausted next, and leaves remove unsupported unless removal makes sense.

record Range(int from, int to) implements Iterable<Integer> {   // half-open [from, to)
    Range {
        if (from > to) throw new IllegalArgumentException(from + " > " + to);
    }
    @Override public Iterator<Integer> iterator() {
        return new Iterator<>() {
            private int cur = from;
            @Override public boolean hasNext() { return cur < to; }
            @Override public Integer next() {
                if (cur >= to) throw new NoSuchElementException();
                return cur++;
            }
        };
    }
}

for (int i : new Range(0, 3)) System.out.print(i);   // 012
int sum = StreamSupport.stream(new Range(1, 5).spliterator(), false)
                       .mapToInt(Integer::intValue).sum();   // 10

A Spliterator is the iterator streams use: tryAdvance consumes one element, forEachRemaining the rest, trySplit hands off a prefix of the remaining elements for another thread, and estimateSize plus characteristic flags (ORDERED, SIZED, SUBSIZED, SORTED, DISTINCT, NONNULL, IMMUTABLE, CONCURRENT) let the stream framework plan the work. The default Iterable.spliterator() knows nothing about size and splits poorly, which is why parallel streams over custom iterables are slow; ArrayList's spliterator splits an index range in half for free. Streams get their own phase later in the course.

Spliterator<Integer> sp = List.of(1, 2, 3, 4, 5, 6, 7, 8).spliterator();
Spliterator<Integer> first = sp.trySplit();     // first covers 1..4, sp keeps 5..8
first.forEachRemaining(System.out::print);      // 1234
sp.tryAdvance(System.out::print);               // 5
System.out.println(sp.estimateSize());          // 3
Interview trap
  • "CME means a threading bug." Usually it is one thread modifying the collection inside its own loop, often through a listener or a helper method called from the loop body.
  • "Catching CME is a fix." The collection state after the exception is whatever the loop had done so far; the detection is not guaranteed, so code that relies on it is broken.
  • Calling it.remove() twice, or before the first next(), throws IllegalStateException.
  • Iterating a Collections.synchronizedList without holding its lock can still throw CME when another thread writes.

Collections & List Utility Methods

35m video35m practice

java.util.Collections is a class of static algorithms and wrappers that work on any List, Set or Map through its interface. The algorithms are short and fast; the traps are in their preconditions (binarySearch needs sorted input) and in the wrappers, which are views over your collection, not copies of it.

Sorting: sort, comparators and reverseOrder

Since Java 8, Collections.sort(list) simply calls list.sort(null), and a null comparator means natural ordering (Comparable). The default List.sort copies the elements into an array, sorts the array, and writes them back through a ListIterator, so sorting a LinkedList is still O(n log n). ArrayList overrides it to sort its internal array in place and bumps modCount, so a live iterator fails afterwards (L68).

Definition · the sort guarantees

Object sorts use TimSort: stable (equal elements keep their relative order), O(n log n) worst case, close to O(n) on input that is already mostly sorted. Natural-order sorting requires every element to be mutually Comparable, otherwise it throws ClassCastException; a null element throws NullPointerException.

record Order(String id, int total) {}

List<Order> orders = new ArrayList<>(List.of(
        new Order("b", 30), new Order("a", 30), new Order("c", 10)));
Collections.sort(orders, Comparator.comparingInt(Order::total)
                                   .thenComparing(Order::id));   // c, a, b
Collections.sort(orders,
        Collections.reverseOrder(Comparator.comparingInt(Order::total))); // a, b, c (stable)

List<String> names = new ArrayList<>(List.of("bo", "al", "cy"));
names.sort(Collections.reverseOrder());          // [cy, bo, al]

Collections.reverseOrder() reverses natural ordering and is the same as Comparator.reverseOrder(); reverseOrder(cmp) is the same as cmp.reversed(). Because the sort is stable, the two orders with total 30 kept their previous relative order (a before b) in the reversed sort.

binarySearch and the sorted precondition

binarySearch(list, key) returns the index of the key if present, otherwise -(insertion point) - 1, where the insertion point is the index at which the key would go to keep the list sorted. The result is always negative for a miss, even when the insertion point is 0. If several elements equal the key, any one of them may be found.

List<Integer> xs = new ArrayList<>(List.of(10, 20, 30, 40));
Collections.binarySearch(xs, 30);          // 2
int i = Collections.binarySearch(xs, 25);  // -3  (insertion point 2)
if (i < 0) xs.add(-i - 1, 25);             // [10, 20, 25, 30, 40], still sorted
Collections.binarySearch(xs, 5);           // -1  (insertion point 0)

The list must be sorted by the same ordering you search with: use binarySearch(list, key, cmp) after sorting with cmp. On an unsorted list the result is undefined: no exception, just a wrong index. For RandomAccess lists the search is O(log n); for a large LinkedList it walks with an iterator, so it makes O(log n) comparisons but O(n) node hops.

Rearranging: reverse, shuffle, swap, rotate, fill, nCopies

List<String> s = new ArrayList<>(List.of("a", "b", "c", "d", "e"));
Collections.reverse(s);                  // [e, d, c, b, a]
Collections.swap(s, 0, 4);               // [a, d, c, b, e]
Collections.reverse(s.subList(1, 4));    // [a, b, c, d, e]  algorithms accept sub-lists
Collections.rotate(s, 2);                // [d, e, a, b, c]
Collections.rotate(s, -2);               // [a, b, c, d, e]
Collections.rotate(s.subList(1, 4), -1); // [a, c, d, b, e]  "b" moved from 1 to 3
Collections.shuffle(s, new Random(42));  // seeded: reproducible in tests
Collections.fill(s, "x");                // [x, x, x, x, x]  replaces, never resizes

List<Integer> slots = new ArrayList<>(Collections.nCopies(5, 0)); // mutable [0, 0, 0, 0, 0]

nCopies(n, o) returns an immutable list that stores o once plus a count, so it costs O(1) memory whatever n is. Its main use is as a constructor argument, as above. A common bug is new ArrayList<>(10) followed by fill or set(3, x): the argument is a capacity, the size is still 0, so fill does nothing and set throws IndexOutOfBoundsException.

Querying: frequency, disjoint, min, max, addAll

List<String> tags = List.of("java", "sql", "java", "k8s");
Collections.frequency(tags, "java");                        // 2 (uses equals, null-safe)
Collections.disjoint(tags, Set.of("go", "rust"));           // true: no common element
Collections.min(tags);                                      // "java"
Collections.max(tags, Comparator.comparingInt(String::length)); // "java" (first of the longest)
Set<String> seen = new HashSet<>();
Collections.addAll(seen, "a", "b", "a");                    // true; seen = {a, b}

All of these are single linear passes. min and max throw NoSuchElementException on an empty collection, so guard them or use stream().max(cmp), which returns an Optional. disjoint calls contains on one argument while iterating the other and prefers to call it on a Set: two lists cost O(n·m), a list against a HashSet costs O(n). addAll(c, elements...) is the varargs way to add several elements and avoids building an intermediate list.

Shared instances: emptyList and singletonList

Allocation

Collections.emptyList() (also emptySet, emptyMap) returns one shared, immutable, serializable instance cast to the type you need, so returning "no results" allocates nothing. singletonList(o) is a tiny immutable object holding a single reference and no array. Prefer the typed methods over the raw constants Collections.EMPTY_LIST, which produce unchecked warnings. Both throw UnsupportedOperationException on add; singletonList also rejects set. Unlike List.of(x), singletonList(null) is allowed.

List<Order> findByCustomer(String id) {
    List<Order> hits = index.get(id);
    return hits == null ? Collections.emptyList()            // never return null (EJ Item 54)
                        : Collections.unmodifiableList(hits);
}

Wrappers: synchronizedXxx, unmodifiableXxx and List.copyOf

synchronizedList, synchronizedMap and friends return a wrapper whose every method runs inside synchronized (mutex), where the mutex is the wrapper itself. Single calls are thread-safe; iteration and check-then-act sequences are not, and you must hold the same lock yourself:

List<String> log = Collections.synchronizedList(new ArrayList<>());
log.add("start");                 // locks the wrapper for this one call
synchronized (log) {              // required: an iteration is many calls
    for (String e : log) System.out.println(e);
    if (!log.contains("end")) log.add("end");
}

Every access contends on one lock, so for real concurrency prefer ConcurrentHashMap or CopyOnWriteArrayList (L66).

unmodifiableList(src) returns a read-only view: reads delegate to src, mutators throw UnsupportedOperationException, and changes made through src show through. List.copyOf(src) (Java 10) makes a real unmodifiable snapshot; it throws NullPointerException on null elements and, if src is already an unmodifiable list from List.of/copyOf, returns it without copying. L70 builds on this.

List<String> src  = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(src);
List<String> snap = List.copyOf(src);
src.add("c");
System.out.println(view);   // [a, b, c]  the view sees the change
System.out.println(snap);   // [a, b]     the snapshot does not
view.add("d");              // UnsupportedOperationException
What breaks in production
  • Searching an unsorted list. binarySearch on data sorted by a different comparator (or not sorted) silently returns a wrong or negative index; duplicate inserts follow.
  • Empty input to max. Collections.max(prices) on an empty result set throws NoSuchElementException the first night there are no orders.
  • Unlocked iteration of a synchronized wrapper. Another thread's add mid-loop throws ConcurrentModificationException, or worse, you read a half-updated state.
  • "Read-only" is not "frozen". Returning unmodifiableList(internal) lets callers see later mutations, and a caller iterating it while your code modifies internal gets a CME.
  • Mutating a returned empty list. service.tags().add(t) works until the method returns emptyList(), then throws UnsupportedOperationException.

Immutable Collections & Defensive Copying

35m video35m practice

Java has four things that look like "a read-only list" and behave differently: List.of, Arrays.asList, Collections.unmodifiableList and List.copyOf. Knowing which one is a snapshot, which is a view and which is a write-through wrapper over an array is what lets you build classes whose state cannot change behind their back.

List.of, Set.of, Map.of: what "immutable" means

Definition · unmodifiable collections (JEP 269, Java 9)

The factory methods return collections whose structure can never change: every mutator (add, remove, set, sort, clear, put) throws UnsupportedOperationException. They are null-hostile: a null element, key or value throws NullPointerException at creation, and so does querying for null. Set.of and Map.of reject duplicates with IllegalArgumentException, and their iteration order is randomized per JVM run (stable within one run) so that nobody can depend on it. Immutability is shallow: the elements themselves may still be mutable.

List<String> roles = List.of("ADMIN", "USER");
roles.add("OPS");                  // UnsupportedOperationException
roles.contains(null);              // NullPointerException, not false
List.of("a", null);                // NullPointerException at creation
Set.of("a", "a");                  // IllegalArgumentException: duplicate element
Map<String, Integer> limits = Map.of("free", 10, "pro", 100);   // up to 10 pairs
Map<String, Integer> big = Map.ofEntries(Map.entry("a", 1), Map.entry("b", 2));
System.out.println(Set.of("x", "y", "z"));   // order can differ on the next run

The look-alikes: asList, unmodifiable views and copyOf

Arrays.asList(arr) is a fixed-size list backed by the array: set writes into the array, writes to the array show up in the list, and only size-changing calls throw. Collections.unmodifiableList(src) is a read-only view that delegates every read to src, so it reflects later changes to the source. List.copyOf(src) is a real snapshot.

String[] arr = {"a", "b", "c"};
List<String> fixed = Arrays.asList(arr);
fixed.set(0, "z");          // arr[0] is now "z"
arr[1] = "y";               // fixed.get(1) is now "y"
fixed.add("d");             // UnsupportedOperationException

List<String> src  = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(src);
List<String> snap = List.copyOf(src);
src.add("c");               // view is [a, b, c]; snap is still [a, b]

Defensive copies in constructors and getters

A class that stores a caller's list stores a reference the caller still holds. Copy on the way in; on the way out, an immutable field can be returned as is.

record LineItem(String sku, int qty) {}

public final class Order {
    private final List<LineItem> items;

    public Order(List<LineItem> items) {
        this.items = List.copyOf(items);             // 1. copy
        if (this.items.isEmpty())                    // 2. validate the copy
            throw new IllegalArgumentException("order needs at least one item");
    }
    public List<LineItem> items() { return items; }  // immutable: no copy needed
}

record Invoice(String id, List<LineItem> lines) {
    Invoice { lines = List.copyOf(lines); }          // compact constructor
}
Why copy before validating

If you validate the caller's list and then copy it, another thread can change it between the check and the copy (a time-of-check/time-of-use race), and your object accepts data it rejected. Copy first, check the copy (Effective Java Item 50). A record without the compact constructor stores the caller's mutable list, so the record is not immutable. If the class must mutate its own list internally, keep an ArrayList field and return Collections.unmodifiableList(items) (O(1), live) or List.copyOf(items) (O(n), frozen) from the getter, and document which.

Immutable collections in API design

  • Accept broad, return narrow. Take Collection<? extends T> or List<T>; return an unmodifiable List, Set or Map, and say so in the Javadoc. Callers who need to mutate write new ArrayList<>(result).
  • Constants. public static final List<String> ALLOWED = List.of(...) is safe; a public static final String[] is not, since anyone can overwrite its slots (Item 15).
  • Builders freeze at the end. Accumulate into an ArrayList, publish with List.copyOf in build().
  • Sharing across threads. A fully built immutable collection held in a final field can be read by any number of threads with no locking.

Performance and memory benefits

Immutable collections are sized exactly: no 50% growth slack as in ArrayList. OpenJDK has special classes for 0, 1 and 2 elements that hold them in fields with no array at all. Set.of and Map.of store elements (and key/value pairs) in one flat array with open addressing, so there is no separate node object per entry as in HashMap; for small read-only maps it is roughly half the footprint or less. What breaks in production
  • Order-dependent tests. An assertion on Set.of(...).toString() or JSON built from Map.of passes on your laptop and fails on the next CI run.
  • Null probes. allowed.contains(param) throws NPE when allowed is a List.of and param is an absent optional field.
  • Sorting through asList. Collections.sort(Arrays.asList(arr)) reorders the caller's array, and a caller writing into its array later changes your "list".
  • Copy that throws. Switching a getter to List.copyOf starts throwing NPE the day a null slips into the internal list.

Contract Violations in Collections: A Bug Hunt

40m video45m practice

Collections trust the contracts of equals, hashCode, compareTo and Comparator without checking them. Break a contract and nothing fails at the line with the bug; instead entries vanish, sets hold duplicates, or a sort throws hours later. This session reproduces seven such bugs, explains each from the inside of the data structure, and fixes it.

Bugs 1 and 2: hash collections

Bug 1, the mutable key. HashMap computes the key's hash once, at put, picks a bucket from it and caches the hash in the entry node. Change a field that hashCode reads and the entry is stranded in the old bucket.

final class Point {                       // mutable, with value-based equals/hashCode
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) { return o instanceof Point p && x == p.x && y == p.y; }
    @Override public int hashCode() { return Objects.hash(x, y); }
}
Map<Point, String> m = new HashMap<>();
Point p = new Point(1, 2);
m.put(p, "home");
p.x = 5;
m.get(p);                       // null: wrong bucket, and the cached hash differs anyway
m.get(new Point(1, 2));         // null: right bucket, but equals now fails
m.size();                       // 1: the entry still exists and is unreachable

Fix: keys must be immutable in every field that equals/hashCode read. record Point(int x, int y) {} gives final fields and correct methods for free (but a record with a mutable List component has the same bug).

Bug 2, equals without hashCode. Object.hashCode is identity-based, so two equal objects land in different buckets and HashSet never even calls equals on them.

final class Email {
    private final String value;
    Email(String v) { value = v.toLowerCase(Locale.ROOT); }
    @Override public boolean equals(Object o) { return o instanceof Email e && value.equals(e.value); }
    // missing: @Override public int hashCode() { return value.hashCode(); }
}
Set<Email> s = new HashSet<>(List.of(new Email("a@x.io"), new Email("A@x.io")));
s.size();   // 2, although the two are equal

Bugs 3 and 4: ordering and equality that disagree

Bug 3, compareTo inconsistent with equals. TreeSet and TreeMap never call equals: two elements are duplicates when compareTo returns 0.

record Employee(String name, int salary) implements Comparable<Employee> {
    public int compareTo(Employee o) { return Integer.compare(salary, o.salary); }
}
Set<Employee> byPay = new TreeSet<>(List.of(new Employee("Ann", 100), new Employee("Bob", 100)));
byPay.size();   // 1: Bob was silently dropped as a "duplicate" of Ann

// The JDK has one too: equals compares scale, compareTo does not
new HashSet<>(List.of(new BigDecimal("1.0"), new BigDecimal("1.00"))).size(); // 2
new TreeSet<>(List.of(new BigDecimal("1.0"), new BigDecimal("1.00"))).size(); // 1

Fix: break ties on every field equals uses: Comparator.comparingInt(Employee::salary).thenComparing(Employee::name).

Bug 4, asymmetric equals across a hierarchy. A subclass adds a field and tightens equals:

class Pt { final int x, y; Pt(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) { return o instanceof Pt p && x == p.x && y == p.y; }
    @Override public int hashCode() { return 31 * x + y; } }
class ColorPt extends Pt { final String color; ColorPt(int x, int y, String c) { super(x, y); color = c; }
    @Override public boolean equals(Object o) { return o instanceof ColorPt c && super.equals(c) && color.equals(c.color); } }

Pt p = new Pt(1, 2);  ColorPt cp = new ColorPt(1, 2, "red");
p.equals(cp);                                  // true
cp.equals(p);                                  // false: not symmetric
new HashSet<Pt>(List.of(p)).contains(cp);      // false: calls cp.equals(p)
new HashSet<Pt>(List.of(cp)).contains(p);      // true:  calls p.equals(cp)

Membership now depends on which object is stored and which is asked about. Fix: there is no way to extend an instantiable class with a value field and keep the equals contract (Effective Java Item 10). Use composition (ColorPt has a Pt), make the base class final, or use records, which cannot be extended.

Bug 5: a comparator that is not a total order

Definition · comparator contract

For all x, y, z: sgn(compare(x, y)) == -sgn(compare(y, x)) (so compare(x, x) == 0); if x > y and y > z then x > z; and if compare(x, y) == 0 then x and y compare the same way against every z.

record Task(String id, int priority) {}
List<Task> tasks = new ArrayList<>();
var rnd = new Random(1);
for (int i = 0; i < 10_000; i++) tasks.add(new Task("t" + i, rnd.nextInt(5)));

tasks.sort((a, b) -> a.priority() >= b.priority() ? 1 : -1);  // never returns 0
// often: IllegalArgumentException: Comparison method violates its general contract!
Comparator<Integer> overflow = (a, b) -> a - b;   // MIN_VALUE - 1 wraps: not transitive

tasks.sort(Comparator.comparingInt(Task::priority));  // fix: Integer.compare underneath

TimSort assumes the contract while merging runs; when its bookkeeping detects a contradiction it throws. Detection is opportunistic: lists under 32 elements are insertion-sorted and never throw, they just come back in an arbitrary order. Other offenders: comparing doubles with < when NaN is possible, comparators reading mutable state, and random tie-breakers.

names.removeIf(n -> n.equals("a")); // match: UnsupportedOperationException (only now)

Generics: Why They Exist & Raw Types

35m video35m practice

Generics move the "what type is in this container?" question from run time to compile time: the compiler checks every insertion and inserts the casts on every read for you. Raw types are the backward-compatibility escape hatch that switches all of that checking off, which is why modern code should never write one.

Life before generics

Until Java 5 (2004) every collection held Object. Nothing stopped you inserting the wrong type, and every read needed a cast, so the error surfaced as a ClassCastException at the read, possibly in another module, long after the bad insertion.

// Java 1.4 style
List names = new ArrayList();
names.add("ann");
names.add(Integer.valueOf(7));           // compiles: it is a List of Object
String first  = (String) names.get(0);   // a cast on every read
String second = (String) names.get(1);   // ClassCastException, at run time
// Java 5+
List<String> names = new ArrayList<>();
names.add("ann");
names.add(7);                  // compile error: int cannot be converted to String
String first = names.get(0);   // no cast in source; the compiler inserts it

Compile-time type safety and the syntax

Definition · the vocabulary

A generic type is a class or interface declared with type parameters: interface List<E>. A parameterized type supplies type arguments: List<String>, Map<String, List<Order>>. Type arguments must be reference types (List<int> is illegal; use List<Integer>). The guarantee: if the whole program compiles without unchecked warnings, the casts the compiler inserts can never fail.

The checks happen at two points: writes (add, put, assignments) are checked against the type argument, and reads are typed, so names.get(0).length() compiles without a cast. The type information exists only for the compiler; at run time the object is just an ArrayList (type erasure, L77).

The diamond operator and inference

Since Java 7 the diamond <> tells the compiler to infer the type arguments of a constructor call from context, usually the target type of the assignment. Java 9 extended it to anonymous classes when the inferred type is denotable.

Map<String, List<Integer>> byUser = new HashMap<>();   // infers <String, List<Integer>>
List<String> copy = new ArrayList<>(Set.of("a"));       // infers <String> from target

var a = new ArrayList<String>();   // fine: var takes ArrayList<String>
var b = new ArrayList<>();         // ArrayList<Object>: no target, nothing to infer from
List<String> c = new ArrayList();  // RAW: forgot the diamond, unchecked warning

Comparator<String> byLen = new Comparator<>() {        // Java 9+: diamond on anonymous class
    @Override public int compare(String x, String y) { return Integer.compare(x.length(), y.length()); }
};

Raw types and unchecked warnings

A raw type is a generic type used without type arguments: List instead of List<E>. It exists only so that pre-generics code still compiles. Assigning between raw and parameterized types compiles with an unchecked warning; by default javac prints only a one-line note ("uses unchecked or unsafe operations"), and -Xlint:unchecked shows each site.

List<String> strings = new ArrayList<>();
List raw = strings;              // allowed, same object
raw.add(42);                     // warning: unchecked call to add(E) as a member of raw List
String s = strings.get(0);       // ClassCastException here, far from the bug

When you need "a list of unknown element type", write List<?>, not List. The only places raw types remain correct are class literals (List.class; List<String>.class is illegal) and instanceof tests, where o instanceof List is legal (though o instanceof List<?> is equally valid and reads better).

Why a raw type disables ALL generic checks

Definition · members of a raw type (JLS §4.8)

The type of every constructor, instance method and non-static field of a raw type C is the erasure of its declared type. That applies even to members whose signatures have nothing to do with C's own type parameter.

class Box<T> {
    T value;
    List<String> labels() { return List.of("fragile"); }
}
Box<Integer> typed = new Box<>();
for (String l : typed.labels()) { }   // fine

Box raw = new Box<>();
for (String l : raw.labels()) { }     // compile error: Object cannot be converted to String
List<String> ls = raw.labels();       // compiles, but only with an unchecked warning

Using Box raw erased List<String> to List, so one raw variable silently turns every generic signature on that class into its pre-2004 form.

@SuppressWarnings("unchecked"), responsibly

Some unchecked casts are genuinely safe, typically inside a generic container that stores elements in an Object[]. Prove it is safe, then suppress on the smallest possible scope (a local variable declaration, never a whole class) and write the proof as a comment (Effective Java Item 27).

public final class ArrayStack<E> {
    private Object[] elements = new Object[16];
    private int size;

    public void push(E e) {
        if (size == elements.length) elements = Arrays.copyOf(elements, size * 2);
        elements[size++] = e;
    }
    public E pop() {
        if (size == 0) throw new NoSuchElementException();
        // Safe: push(E) is the only way in, so every element is an E
        @SuppressWarnings("unchecked") E e = (E) elements[--size];
        elements[size] = null;           // let the GC reclaim it
        return e;
    }
}

Generics and backward compatibility

Java 5 had to run the millions of lines of existing collection code unchanged and let libraries adopt generics one at a time. The design choice was erasure: type arguments are checked by javac and then removed, so List<String> and List compile to the same bytecode and the same class file serves old and new callers. Raw types are the bridge between the two worlds. The price, paid in L77, is that the JVM cannot see type arguments at run time.

What breaks in production
  • A forgotten diamond. new ArrayList() produces a raw type whose warning drowns in build noise; treat -Xlint:unchecked warnings as errors in CI (-Werror).
  • Legacy APIs returning raw lists. Polluted data travels until a read fails. Wrap the result with Collections.checkedList(list, String.class) to fail at the insertion point instead.
  • Class-level suppression. @SuppressWarnings("unchecked") on a class hides the next real problem someone introduces there.

Generic Classes & Interfaces

40m video45m practice

A type parameter is a placeholder that the class body uses like a real type and that each use site fills in. Declaring one is easy; the skill is deciding where the parameters go, which ones an implementing class fixes and which it passes on, and when nested type arguments deserve a named type of their own.

Declaring a generic class

The parameter list follows the class name; inside the body T can type fields, constructor and method parameters, return values and local variables. Each use site supplies the argument, and the compiler checks every call against it.

public final class Box<T> {
    private T value;                                   // field
    public Box(T value) { this.value = value; }        // constructor parameter
    public T get() { return value; }                   // return type
    public void set(T value) { this.value = value; }   // method parameter
    public boolean holds(T candidate) { return Objects.equals(value, candidate); }
}

Box<String> b = new Box<>("hi");
String s = b.get();      // no cast
b.set(42);               // compile error: int cannot be converted to String
Definition · scope of a class type parameter

T belongs to each instance, so it is not visible in static members: static T fallback; fails with "non-static type variable T cannot be referenced from a static context". A static method that needs a type parameter declares its own (L74). A static nested class must also declare its own parameter, while an inner (non-static) class sees the outer one.

Multiple parameters and naming conventions

Separate parameters with commas: class Cache<K, V>, interface BiFunction<T, U, R>. By convention they are single uppercase letters, which makes them impossible to confuse with real class names.

Generic interfaces: fix the arguments or pass them on

record Order(Long id, String customer, int total) {}

interface Repository<T, ID> {
    T save(T entity);
    Optional<T> findById(ID id);
    List<T> findAll();
}

// 1. Fix both arguments: a concrete, non-generic class
final class OrderRepository implements Repository<Order, Long> {
    private final Map<Long, Order> store = new HashMap<>();
    @Override public Order save(Order o) { store.put(o.id(), o); return o; }
    @Override public Optional<Order> findById(Long id) { return Optional.ofNullable(store.get(id)); }
    @Override public List<Order> findAll() { return List.copyOf(store.values()); }
}

// 2. Stay generic: pass the parameters through
class InMemoryRepository<T, ID> implements Repository<T, ID> { /* … body implemented in L80 */ }

// 3. Fix some, keep others
abstract class LongIdRepository<T> implements Repository<T, Long> { }

When you fix the arguments, the overriding methods use the concrete types (save(Order)), and the compiler generates bridge methods to keep the erased interface signature working (L77). The JDK's most common case is class Money implements Comparable<Money>.

Nested generics

Read nested type arguments from the outside in: Map<String, List<Order>> is "a map from a string to a list of orders". Each level is checked: get returns a List<Order>, whose get returns an Order.

List<Order> orders = List.of(new Order(1L, "ann", 30), new Order(2L, "bob", 10), new Order(3L, "ann", 5));
Map<String, List<Order>> byCustomer = new HashMap<>();
for (Order o : orders)
    byCustomer.computeIfAbsent(o.customer(), k -> new ArrayList<>()).add(o);

int annTotal = byCustomer.getOrDefault("ann", List.of()).stream()
        .mapToInt(Order::total).sum();                       // 35
var same = orders.stream().collect(Collectors.groupingBy(Order::customer)); // Map<String, List<Order>>

Two levels are fine; at three (Map<String, Map<YearMonth, List<Order>>>) give the inner part a name, such as record CustomerHistory(Map<YearMonth, List<Order>> byMonth), so the type documents what it means and can grow methods.

From scratch: Pair, Result and Stack

public record Pair<A, B>(A first, B second) {
    public static <A, B> Pair<A, B> of(A a, B b) { return new Pair<>(a, b); }
    public <C> Pair<A, C> withSecond(C c) { return new Pair<>(first, c); }
}

sealed interface Result<T, E> {
    record Ok<T, E>(T value) implements Result<T, E> {}
    record Err<T, E>(E error) implements Result<T, E> {}

    static <T, E> Result<T, E> ok(T value)  { return new Ok<>(value); }
    static <T, E> Result<T, E> err(E error) { return new Err<>(error); }

    default <U> Result<U, E> map(Function<? super T, ? extends U> f) {
        return switch (this) {
            case Ok<T, E> o  -> new Ok<>(f.apply(o.value()));
            case Err<T, E> x -> new Err<>(x.error());
        };
    }
    default T orElse(T fallback) {
        return this instanceof Ok<T, E> o ? o.value() : fallback;
    }
}

Result<Integer, String> r = Result.ok(20);
int doubled = r.map(n -> n * 2).orElse(0);   // 40

Pair gets equals, hashCode and accessors from the record. Result is sealed, so the switch is exhaustive without a default; its records are implicitly static and therefore declare their own T and E. The <U> on map is a method-level parameter, the subject of L74, and the wildcards in its argument come from L76.

public final class LinkedStack<T> implements Iterable<T> {
    private record Node<T>(T value, Node<T> next) {}   // static nested: its own T
    private Node<T> head;
    private int size;

    public void push(T value) { head = new Node<>(value, head); size++; }
    public T pop() {
        T v = peek();
        head = head.next(); size--;
        return v;
    }
    public T peek() {
        if (head == null) throw new NoSuchElementException("empty stack");
        return head.value();
    }
    public boolean isEmpty() { return head == null; }
    public int size() { return size; }

    @Override public Iterator<T> iterator() {
        return new Iterator<>() {
            private Node<T> cur = head;
            @Override public boolean hasNext() { return cur != null; }
            @Override public T next() {
                if (cur == null) throw new NoSuchElementException();
                T v = cur.value(); cur = cur.next(); return v;
            }
        };
    }
}

Compare with ArrayStack from L72: the linked version needs no unchecked cast because it never stores elements in an Object[], at the cost of one node object per element.

Interview trap
  • Shadowed parameters. In class Box<T> { <T> void put(T t) {…} } the method's T is a new, unrelated variable, so Box<String> happily accepts put(42). Delete the method-level <T>.
  • A parameter named like a class. class Holder<String> declares a type variable called String; inside, String no longer means java.lang.String.
  • Equality across arguments. new Pair<>(1, "a").equals(new Pair<>(1, "a")) is true, and so is new Pair<Object, Object>(1, "a").equals(new Pair<Integer, String>(1, "a")): type arguments do not exist at run time.

Generic Methods & Type Inference

35m video40m practice

A generic method declares its own type parameters, and at each call the compiler solves for them from the arguments and from the type the result must fit into. Most of the time this inference is invisible; you need to understand it for the cases where it has nothing to go on, and you must say the type yourself.

Declaring a generic method

Definition · method-level type parameters

The type parameter list goes after the modifiers and before the return type: public static <T> void swap(T[] a, int i, int j). Its scope is that one method, and each call can bind it differently. Static and instance methods, and methods of non-generic classes, can all be generic. A static method can never use the class's own type parameter, so static utilities always declare their own.

final class Util {
    private Util() {}

    static <T> void swap(T[] a, int i, int j) {
        T tmp = a[i]; a[i] = a[j]; a[j] = tmp;
    }
    static <K, V> Map<V, K> invert(Map<K, V> m) {
        Map<V, K> out = new HashMap<>();
        m.forEach((k, v) -> out.put(v, k));
        return out;
    }
}

String[] names = {"ann", "bob"};
Util.swap(names, 0, 1);                                   // T = String
Map<Integer, String> byId = Util.invert(Map.of("ann", 1)); // K = String, V = Integer
Util.swap(new int[] {1, 2}, 0, 1);   // compile error: int[] is not a T[] (no primitive T)

Inference from the arguments

For each call, javac collects constraints (each argument's type must be compatible with its parameter type) and solves them for the type variables (JLS ch. 18). With swap(names, 0, 1) the only constraint is String[] → T[], so T = String. When the arguments disagree, the compiler picks the most specific type they all share, which can be an intersection type nobody wrote:

var mixed = List.of(1, "a");
// E is inferred as the common supertypes of Integer and String:
// Serializable & Comparable<…> (and, since Java 12, Constable & ConstantDesc)
List<Object> objs = List.of(1, "a");   // with a target, E = Object instead

Inference from the target type and the return context

When the arguments do not determine a type variable, Java looks at where the result goes. Since Java 8 (JEP 101) a generic method call used as an argument to another method is also typed from that method's parameter, which Java 7 could not do.

List<String> a = Collections.emptyList();              // T from the assignment target

static void printAll(List<String> xs) { xs.forEach(System.out::println); }
printAll(Collections.emptyList());                     // T from the parameter (Java 8+)

static List<Person> none() { return Collections.emptyList(); } // T from the return type

Comparator<String> byLen = Comparator.comparing(String::length); // T from target, U from method ref

Explicit type witnesses and the limits of inference

A type witness supplies the arguments by hand. It must follow a qualifier: Collections.<String>emptyList(), this.<T>helper(); a bare <String>emptyList() is a syntax error. You need it, or an equivalent hint, in three situations:

  • No target at all: var declarations and statement expressions. var e = Collections.emptyList(); is a List<Object>.
  • The receiver of a chained call. Target typing flows into a call's arguments, not into the expression the next method is called on.
  • Implicit lambdas whose parameter types come only from the call. If T is still unknown when the lambda body is checked, its parameter is typed Object.
record Person(String name, int age) {}
List<Person> people = new ArrayList<>(List.of(new Person("ann", 30), new Person("bob", 25)));

people.sort(Comparator.comparing(p -> p.name()).reversed());            // error: p is Object
people.sort(Comparator.<Person, String>comparing(p -> p.name()).reversed()); // witness
people.sort(Comparator.comparing((Person p) -> p.name()).reversed());   // typed lambda
people.sort(Comparator.comparing(Person::name).reversed());             // exact method ref

var empty = Collections.<String>emptyList();   // List<String>, not List<Object>

Without .reversed() the first line compiles, because then sort's parameter is the target. Prefer the method reference or typed lambda; reach for a witness when neither reads well.

Generic static factory methods

Static factories with their own type parameters let the call site skip type arguments entirely, which is why the JDK's modern APIs are built from them: List.of, Map.entry, Optional.of, EnumSet.noneOf(Class<E>), Collectors.groupingBy. static <K, V> Map<K, List<V>> multimap() { return new HashMap<>(); }

UnaryOperator<Integer> n = identity();               // same object, two types

Generic constructors

A constructor can declare type parameters of its own, independent of the class's. They are rare; the usual reason is to accept a range of argument types without making the class generic. Explicit constructor type arguments go right after new, and cannot be combined with a diamond.

final class Celsius {
    private final double value;
    <N extends Number> Celsius(N reading) { this.value = reading.doubleValue(); }
    double value() { return value; }
}
new Celsius(21);               // N = Integer
new Celsius(21.5f);            // N = Float
new <Double>Celsius(21.5);     // explicit constructor type argument

final class Bag<T> {
    private final List<T> items;
    <S extends T> Bag(Collection<S> source) { items = new ArrayList<>(source); }
}

Bounded Type Parameters

35m video40m practice

An unbounded T is only known to be an Object, so the body can call nothing but Object's methods. A bound such as <T extends Comparable<? super T>> trades some freedom at the call site for the right to call methods in the body, and the exact shape of that bound decides which real JDK types your method accepts.

Upper bounds and what they unlock

Definition · bounded type parameter

<T extends B> restricts the type arguments to B and its subtypes; extends is used for classes and interfaces alike. In the body, values of type T have every member of B. The compiler erases T to B (not to Object), so the bound also shapes the bytecode signature (L77). There is no <T super B>: lower bounds exist only on wildcards (L76).

static <T> double half(T x)                 { return x.doubleValue() / 2; } // error: no such method in Object
static <T extends Number> double half(T x)   { return x.doubleValue() / 2; } // fine

half(10);                 // T = Integer
half(new BigDecimal("3")); // T = BigDecimal
half("10");               // compile error: String is not within the bound Number

Bounds enable arithmetic and comparison

Java has no operator overloading, so a bound cannot make a + b or a < b legal on T. What it gives you is methods: arithmetic goes through Number's conversions, and ordering goes through compareTo.

static <N extends Number> double sum(Collection<N> xs) {
    double total = 0;
    for (N x : xs) total += x.doubleValue();
    return total;
}
static <T extends Comparable<? super T>> T clamp(T value, T lo, T hi) {
    if (value.compareTo(lo) < 0) return lo;
    if (value.compareTo(hi) > 0) return hi;
    return value;
}
sum(List.of(1, 2, 3));                      // 6.0
clamp(LocalTime.of(23, 30), LocalTime.of(9, 0), LocalTime.of(18, 0)); // 18:00

Converting through doubleValue is lossy: long values above 253 and every BigDecimal with more digits than a double holds lose precision. For money, write a BigDecimal-specific method instead of a "generic" one.

Multiple bounds

Join bounds with &: <T extends Number & Comparable<T>> or <T extends Comparable<T> & Serializable>. The type argument must satisfy all of them, and the body may use members of each.

Rules

At most one bound may be a class, and if present it must come first; the rest must be interfaces. <T extends Comparable<T> & Number> does not compile. The erasure of T is the leftmost bound, which is how the JDK kept old binary signatures when it generified: Collections.max is declared <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll). The redundant-looking Object & makes the erased return type Object, exactly as it was in Java 1.4, instead of Comparable.

Recursive bounds and why the JDK writes ? super T

<T extends Comparable<T>> is a recursive (F-bounded) bound: "T can be compared with other Ts". Enum<E extends Enum<E>> uses the same idea. It fails for classes that inherit compareTo from a supertype. LocalDate implements ChronoLocalDate, which extends Comparable<ChronoLocalDate>; so a LocalDate is not a Comparable<LocalDate>.

<T extends Comparable<? super T>> accepts any T comparable to itself or to one of its supertypes. That is why Collections.sort, Collections.max, Collections.binarySearch and Comparator.naturalOrder all use it.

Writing a generic max

// v1: too strict
static <T extends Comparable<T>> T maxV1(List<T> xs) { /* same loop */ return xs.get(0); }

// v2: the JDK shape
static <T extends Comparable<? super T>> T max(Iterable<? extends T> xs) {
    Iterator<? extends T> it = xs.iterator();
    if (!it.hasNext()) throw new NoSuchElementException("max of empty input");
    T best = it.next();
    while (it.hasNext()) {
        T x = it.next();
        if (x.compareTo(best) > 0) best = x;
    }
    return best;
}
// with an explicit comparator, no bound is needed at all
static <T> T max(Iterable<? extends T> xs, Comparator<? super T> cmp) {
    Iterator<? extends T> it = xs.iterator();
    if (!it.hasNext()) throw new NoSuchElementException("max of empty input");
    T best = it.next();
    while (it.hasNext()) { T x = it.next(); if (cmp.compare(x, best) > 0) best = x; }
    return best;
}

List<LocalDate> dates = List.of(LocalDate.of(2024, 1, 5), LocalDate.of(2023, 7, 1));
LocalDate a = maxV1(dates);   // compile error: LocalDate is not a Comparable<LocalDate>
LocalDate b = max(dates);     // 2024-01-05
String c = max(List.of("kiwi", "fig"), Comparator.comparingInt(String::length)); // "kiwi"

Each piece of v2's signature has a job: the bound lets the body call compareTo; ? super T admits inherited comparisons; Iterable<? extends T> lets you pass a List<LocalDate> and get back a ChronoLocalDate if you ask for one. Ties keep the first maximum, like the JDK.

What breaks in production
  • Bounds change binary signatures. Adding extends Comparable<T> to a published method's type parameter changes its erasure, and code compiled against the old jar fails with NoSuchMethodError. This is why the JDK wrote Object &.
  • Too-strict comparable bounds. A utility with <T extends Comparable<T>> works on String and Integer in tests and rejects LocalDate, java.sql.Timestamp and your own subclass hierarchies later.
  • "Generic" money maths. Summing BigDecimal amounts through doubleValue() produces cents-level rounding errors.

Wildcards & PECS

45m video45m practice

Generic types are invariant: a List<Integer> is not a List<Number>. Wildcards restore flexibility in a controlled way: ? extends T for a source you read from, ? super T for a sink you write into. "Producer extends, consumer super" (PECS) is the whole rule, and it explains almost every signature in java.util.

Invariance, covariant arrays and ArrayStoreException

List<String> strings = new ArrayList<>();
List<Object> objects = strings;   // compile error. If it were legal...
objects.add(42);                  // ...an Integer would now sit in a List<String>

Object[] arr = new String[1];     // arrays are covariant: this compiles
arr[0] = 42;                      // ArrayStoreException at run time

Arrays are covariant (String[] is a subtype of Object[]) and reified: each array object knows its component type, so the JVM checks every store and throws ArrayStoreException. Generic type arguments are erased, so there is nothing to check at run time; the only safe choice is to forbid the assignment at compile time. That is why generics are invariant, and why Effective Java Item 28 says to prefer lists to arrays: the error moves from production to the compiler.

The unbounded wildcard

List<?> means "a list of some specific type I don't know". You may call anything that does not depend on the element type (size, isEmpty, clear, contains, remove(Object)), read elements as Object, and add only null. Unlike raw List, it keeps every generic check on.

static int countNulls(Collection<?> c) {
    int n = 0;
    for (Object o : c) if (o == null) n++;
    return n;
}
List<?> any = new ArrayList<>(List.of("a", "b"));
Object first = any.get(0);   // reads are Object
any.add("c");                // compile error: "c" is not a capture of ?
any.add(null);               // the one value that fits every type

Upper bounds: ? extends T is for reading

List<? extends Number> accepts a List<Integer>, List<Double> or List<Number> (covariant). Whatever it is, every element is a Number, so reading as Number is safe. Writing is not: the list might be a List<Double>, so the compiler refuses to add even an Integer.

static double sum(Collection<? extends Number> xs) {
    double s = 0;
    for (Number n : xs) s += n.doubleValue();
    return s;
}
sum(List.of(1, 2));           // List<Integer>
sum(List.of(1.5, 2.5));       // List<Double>
List<? extends Number> nums = new ArrayList<Integer>();
nums.add(3);                  // compile error: it might be a List<Double>

Lower bounds: ? super T is for writing

List<? super Integer> accepts a List<Integer>, List<Number> or List<Object> (contravariant). Whatever it is, it can hold an Integer, so adding one is safe. Reading gives back only Object, since that is all the compiler knows.

static void addRange(List<? super Integer> out, int n) {
    for (int i = 0; i < n; i++) out.add(i);
}
List<Number> numbers = new ArrayList<>();
List<Object> objects = new ArrayList<>();
addRange(numbers, 3);  addRange(objects, 3);
List<? super Integer> sink = numbers;
Object o  = sink.get(0);      // fine
Integer i = sink.get(0);      // compile error: only Object is known

PECS: Collections.copy and real API signatures

Definition · producer extends, consumer super

For each parameter of a generic type: if the method only reads Ts from it, it is a producer, so declare ? extends T. If it only writes Ts into it (or passes Ts to it, like a comparator or consumer), it is a consumer, so declare ? super T. If it does both, use the exact type. Never put a wildcard in a return type; it pushes the uncertainty onto every caller (Effective Java Item 31).

// java.util.Collections
public static <T> void copy(List<? super T> dest, List<? extends T> src)

List<Integer> src  = List.of(1, 2, 3);
List<Number>  dest = new ArrayList<>(List.of(0, 0, 0, 0));
Collections.copy(dest, src);   // dest = [1, 2, 3, 0]: overwrites, never grows
Collections.copy(new ArrayList<Number>(), src);  // IndexOutOfBoundsException: Source does not fit in dest

src produces Ts, dest consumes them, so a list of integers can be copied into a list of numbers. With exact types (List<T> twice) that call would not compile.

Wildcard capture and helper methods

Capture conversion

Each time an expression of type List<?> is used, the compiler gives the unknown a fresh name, shown in errors as capture#1 of ? (JLS §5.1.10). Two uses of the same variable get different captures, so the compiler cannot prove that an element read from the list may be written back. A generic method can bind its T to a capture, which gives the unknown type a usable name.

// Before: does not compile
public static void swap(List<?> list, int i, int j) {
    list.set(i, list.set(j, list.get(i)));   // error: incompatible capture types
}

// After: delegate to a capture helper
public static void swap(List<?> list, int i, int j) { swapHelper(list, i, j); }
private static <T> void swapHelper(List<T> list, int i, int j) {  // T = capture of ?
    list.set(i, list.set(j, list.get(i)));
}

The public signature stays simple (any list), and the private helper does the typed work. OpenJDK's own Collections.swap takes a shortcut instead, copying the argument into a raw List local and suppressing the warnings.

Interview trap
  • Exact types where a wildcard belongs. double sum(List<Number> xs) rejects List<Integer>; callers then copy lists just to satisfy the signature.
  • Covariant arrays in the wild. Before Java 9, Arrays.asList("a").toArray() returned the backing String[] typed as Object[], and storing any non-string into it threw ArrayStoreException.
  • "Write-only" is not literal. You can read from ? super T, but only as Object; you can write null into ? extends T.

Type Erasure, Bridge Methods & Generic Limitations

40m video35m practice

Generics are a compile-time feature: javac checks the types, then erases them to their bounds and inserts casts, so at run time a List<String> is just a List. Every generic limitation (no new T(), no T[], no instanceof List<String>) follows from that one fact, and so do the workarounds.

What the compiler actually emits

Definition · type erasure (JLS §4.6)

A type variable is replaced by its leftmost bound (Object if unbounded); a parameterized type List<String> becomes the raw List. Where an erased value flows into a more specific type, the compiler inserts a checkcast. Where erasure makes an override's signature differ from the method it overrides, it generates a bridge method. Declarations keep their generic signatures in a class-file Signature attribute (JVMS §4.7.9) for the compiler and reflection; what is lost is the type argument of each object at run time.

A javap demonstration

Bridge methods

Comparable<T>.compareTo(T) erases to compareTo(Object), but Money declares compareTo(Money). To keep virtual dispatch working, javac adds a synthetic bridge:

record Money(long cents) implements Comparable<Money> {
    public int compareTo(Money o) { return Long.compare(cents, o.cents); }
    // generated, flags ACC_BRIDGE | ACC_SYNTHETIC:
    // public int compareTo(Object o) { return compareTo((Money) o); }
}
Comparable raw = new Money(100);

The same mechanism handles covariant overrides: if a subclass overrides Object get() with String get(), or a class implements Supplier<String> with String get(), the class file holds both methods and the Object one forwards. javap -p Money lists the bridge, and reflection reports it with Method.isBridge().

Reifiable types, heap pollution and @SafeVarargs

Definition · reifiable type (JLS §4.7)

A type whose full information is available at run time: primitives, non-generic classes, raw types, parameterizations with only unbounded wildcards (List<?>), and arrays of these. List<String>, T and List<? extends Number> are non-reifiable. Heap pollution is a variable of a parameterized type referring to an object that is not of that type.

A varargs parameter is an array, so T... or List<String>... creates an array of a non-reifiable type and draws a "possible heap pollution" warning. The danger is real when the array escapes (Effective Java Item 32):

static <T> T[] toArray(T... args) { return args; }          // leaks the varargs array
static <T> T[] pickTwo(T a, T b, T c) { return toArray(a, b); } // T erased: creates Object[]
String[] two = pickTwo("a", "b", "c");  // ClassCastException: Object[] cannot be cast to String[]

@SafeVarargs   // safe: never stores into the array, never lets it escape
static <T> List<T> flatten(List<? extends T>... lists) {
    List<T> out = new ArrayList<>();
    for (List<? extends T> l : lists) out.addAll(l);
    return out;
}

@SafeVarargs is a promise, not a check. It is allowed only on methods that cannot be overridden: static, final and (since Java 9) private methods, and constructors.

String s = String.class.cast(obj);   // checked cast, unlike (T) obj

A class literal cannot express List<String>. But the generic superclass of a class is recorded in its Signature attribute, so an anonymous subclass captures a full type (Neal Gafter's "super type token"):

abstract class TypeRef<T> {
    final Type type;

        type = ((ParameterizedType) getClass().getGenericSuperclass()).getActualTypeArguments()[0];

This is exactly Jackson's TypeReference, Spring's ParameterizedTypeReference and Guava's TypeToken. The trailing {} is essential: without the subclass there is no superclass signature to read.

  • Name clashes in evolution. Adding an overload that differs only in type arguments fails to compile, and changing a published bound changes the erased descriptor (L75).

Amortized analysis of ArrayList growth

Proof · amortized constant-time add

Each resize from capacity c copies c elements and leaves capacity 1.5c. After n adds, the last resize copied at most n elements, the one before at most n/1.5, and so on. Total copies ≤ n·(1 + 2/3 + (2/3)² + …) = n · 1/(1 − 2/3) = 3n. Adding the n stores themselves, n adds cost at most 4n element writes, so the amortized cost per add is O(1). A doubling policy gives ≤ 2n copies but leaves up to half the array empty: the growth factor trades copying against slack.

Amortized is not worst case: the add that triggers a resize of a 10-million-element list copies 40 MB of references in one call. Pre-size with new ArrayList<>(expected) or ensureCapacity; the list never shrinks on its own (trimToSize does that).

Measurement versus theory

Big-O hides the constants that dominate real programs. An ArrayList stores references contiguously, so iteration streams through memory and the hardware prefetcher keeps up; a LinkedList chases a pointer per element, and every node can be a cache miss. Inserting in the middle of an ArrayList is O(n), but it is one System.arraycopy (a memory move), while the LinkedList must first walk O(n) nodes to find the position. In practice ArrayList and ArrayDeque win almost every list and queue workload. Likewise, for a handful of entries a linear scan of a small array can beat hashing. Measure with JMH; hand-written nanoTime loops are distorted by JIT warm-up and dead-code elimination.

Arrays ↔ Collections Conversions

30m video35m practice

Every conversion between an array, a collection and a stream answers three questions: is the result a copy or a view, can it be modified, and what happens to primitives and nulls? The JDK gives a different answer for almost every method, so knowing the answers is the difference between a clean one-liner and a production bug.

Arrays.asList and its three surprises

Definition · copy versus view

A copy owns its elements, so later changes to the source are invisible: List.of(arr), new ArrayList<>(c), every toArray. A view reads and writes through to another object's storage: Arrays.asList, subList, a map's keySet, values and entrySet. Views cost O(1) to create; copies cost O(n) time and memory but isolate you from the source.

String[] arr = {"b", "a", "c"};
List<String> list = Arrays.asList(arr);

list.add("d");                 // 1. fixed size: UnsupportedOperationException
Collections.sort(list);        // 2. backed by the array: arr is now {"a", "b", "c"}
arr[0] = "z";                  //    and writes to arr show in list: list.get(0) is "z"

int[] nums = {3, 1, 2};
var oops = Arrays.asList(nums);   // 3. List<int[]> with ONE element
oops.size();                      //    1
oops.contains(3);                 //    false: the only element is the array itself

Surprise 3 is generic inference at work (L74): asList(T... a) needs T to be a reference type, an int[] is one, so the whole array becomes the single varargs element. asList does accept nulls, and since Java 9 its toArray() returns a true Object[].

List.of from varargs

List.of(E... elements) also accepts an existing array as its varargs argument, but it copies the elements into an unmodifiable list: later writes to the array are invisible, any null element throws NullPointerException, and every mutator throws (L70). The primitive trap is the same: List.of(nums) is a List<int[]>.

List<String> snap = List.of(arr);   // copy of arr's current elements
arr[1] = "y";                         // snap is unchanged
List.of(new String[] {"a", null});    // NullPointerException

Back to arrays: the three toArray forms

List<String> names = List.of("ann", "bob");
Object[] a = names.toArray();                    // always Object[]
String[] b = names.toArray(new String[0]);       // typed: a new String[2] is allocated
String[] c = names.toArray(String[]::new);       // Java 11+, same as b underneath
String[] d = names.toArray(new String[names.size()]); // pre-sized: filled in place
The performance myth

Old advice said to pre-size the array to avoid a reflective allocation. On modern HotSpot the zero-length form is as fast or faster: the JVM can allocate the right-sized array and skip zeroing it before the copy, while a pre-sized array is zeroed and then overwritten (Shipilëv, "Arrays of Wisdom of the Ancients"). Pre-sizing is also racy on concurrent collections, whose size can change between size() and toArray, leaving trailing nulls. Use toArray(String[]::new) or new String[0].

Primitive arrays, boxing, and Arrays.stream versus Stream.of

There is no List<int>, so getting from an int[] to a list means boxing every element, and back means unboxing. Streams do both directions in one line.

int[] nums = {3, 1, 2};
List<Integer> boxed = Arrays.stream(nums).boxed().toList();      // [3, 1, 2]
int[] back = boxed.stream().mapToInt(Integer::intValue).toArray(); // NPE if an element is null

Arrays.stream(nums);        // IntStream of 3, 1, 2
IntStream.of(nums);         // the same
Stream.of(nums);            // Stream<int[]> with ONE element: the trap again
Arrays.stream(nums, 1, 3);  // IntStream of 1, 2 (a range, no copy)
Stream.of("a", "b");        // for objects, Stream.of and Arrays.stream agree

Arrays.stream has overloads for int[], long[], double[] and T[] only. For a char[] use CharBuffer.wrap(chars).chars() or new String(chars).chars(); for byte[], short[] and float[] loop over indices with IntStream.range. Boxing costs about 16 bytes per element plus a reference (L78), so keep large numeric data in primitive arrays.

        .collect(Collectors.toMap(Order::customer, o -> o,

Collectors.toMap without a merge function throws IllegalStateException ("Duplicate key …") on the first collision, and throws NullPointerException for a null value (it follows Map.merge semantics, which reject null values). The views keySet(), values() and entrySet() write through: byId.keySet().remove(1L) removes the entry from the map.

What breaks in production
  • Always-false membership. Arrays.asList(allowedIds).contains(id) with an int[] compiles and never matches; use Arrays.stream(allowedIds).anyMatch(x -> x == id) or a Set<Integer>.
  • toMap on real data. Unit tests have unique keys; the first production batch with a duplicate e-mail or a null name throws.
  • Order lost in a set. Deduping with new HashSet<>(list) scrambles the order the UI or the API response relied on; use LinkedHashSet.
  • Sorting the caller's array. Sorting Arrays.asList(param) reorders the array the caller passed in.

Phase 2 Capstone: A Generic In-Memory Repository

45m video150m practice

One generic class that stores any entity by any ID type, keeps secondary indexes in sync under concurrent writes, answers predicate queries with stable sorting and pagination, and documents the cost of every operation. It uses every Phase 2 tool at once, and it is the mock persistence layer the course reuses until Day 223.

The contract

Entities are immutable records that expose their ID; a null ID means "not saved yet". The shape mirrors Spring Data repositories, so code written against it moves to JPA later with few changes.

// Entity.java, Repository.java, PageRequest.java, Page.java

Storage, atomic writes and optimistic ID generation

public final class InMemoryRepository<T extends Entity<ID>, ID extends Comparable<? super ID>>
        implements Repository<T, ID> {

    private final ConcurrentHashMap<ID, T> store = new ConcurrentHashMap<>();
    private final Map<String, Map<Object, Set<ID>>> indexes = new ConcurrentHashMap<>();
    private final Map<String, Function<? super T, ?>> indexFns;
    private final Supplier<? extends ID> ids;
    private final BiFunction<? super T, ? super ID, ? extends T> withId;
    private final Comparator<T> byId = Comparator.comparing(e -> e.id());

    public InMemoryRepository(Supplier<? extends ID> ids,
                              BiFunction<? super T, ? super ID, ? extends T> withId,
                              Map<String, Function<? super T, ?>> indexFns) {
        this.ids = ids;
        this.withId = withId;
        this.indexFns = Map.copyOf(indexFns);
        this.indexFns.keySet().forEach(name -> indexes.put(name, new ConcurrentHashMap<>()));
    }

    @Override public T save(T entity) {
        if (entity.id() != null) return upsert(entity.id(), entity, false);
        while (true) {                                  // optimistic: assume a fresh id is free
            ID id = ids.get();
            T fresh = withId.apply(entity, id);
            if (upsert(id, fresh, true) != null) return fresh;  // collided: retry
        }
    }

    private T upsert(ID id, T entity, boolean insertOnly) {
        boolean[] lost = {false};
        store.compute(id, (k, old) -> {                 // atomic per id
            if (old != null && insertOnly) { lost[0] = true; return old; }
            if (old != null) unindex(k, old);
            index(k, entity);
            return entity;
        });
        return lost[0] ? null : entity;
    }

    @Override public Optional<T> findById(ID id) { return Optional.ofNullable(store.get(id)); }

    @Override public boolean deleteById(ID id) {
        boolean[] removed = {false};
        store.computeIfPresent(id, (k, old) -> { unindex(k, old); removed[0] = true; return null; });
        return removed[0];
    }

    @Override public long count() { return store.mappingCount(); }
    // index, unindex, findBy, query, page, sortedBy: below
}
Definition · optimistic ID generation

Take an ID from a lock-free Supplier (AtomicLong::incrementAndGet, a compare-and-set, or UUID::randomUUID), assume it is unused, and let an insert-only compute verify that atomically; on the rare collision with an ID a caller saved explicitly, retry. No lock spans generation and insert, and compute serializes all writers of one ID, so their index updates never interleave.

Secondary indexes

Each named index maps a key (say, a city) to the IDs whose entity has it. Index functions are fixed at construction, so no index is ever added mid-write. Buckets are concurrent sets because readers iterate them while writers change them.

    private void index(ID id, T e) {
        indexFns.forEach((name, fn) -> {
            Object key = fn.apply(e);
            if (key != null) indexes.get(name).compute(key, (k, set) -> {
                Set<ID> s = (set != null) ? set : ConcurrentHashMap.newKeySet();
                s.add(id);
                return s;
            });
        });
    }
    private void unindex(ID id, T e) {
        indexFns.forEach((name, fn) -> {
            Object key = fn.apply(e);
            if (key != null) indexes.get(name).computeIfPresent(key, (k, set) -> {
                set.remove(id);
                return set.isEmpty() ? null : set;          // drop empty buckets atomically
            });
        });
    }

    @Override public List<T> findBy(String index, Object key) {
        Function<? super T, ?> fn = indexFns.get(index);
        if (fn == null) throw new IllegalArgumentException("unknown index: " + index);
        if (key == null) return List.of();
        return indexes.get(index).getOrDefault(key, Set.of()).stream()
                .map(store::get)
                .filter(e -> e != null && key.equals(fn.apply(e)))  // re-check: a write may be in flight
                .sorted(byId)
                .toList();
    }

Predicate queries, sorted views and pagination

    @Override public List<T> query(Predicate<? super T> filter, Comparator<? super T> order) {
        return store.values().stream().filter(filter).sorted(total(order)).toList();
    }

    @Override public Page<T> page(Predicate<? super T> filter, Comparator<? super T> order, PageRequest req) {
        List<T> all = query(filter, order);
        int from = (int) Math.min(req.offset(), all.size());
        int to = (int) Math.min((long) from + req.size(), all.size());
        return new Page<>(all.subList(from, to), req.page(), req.size(), all.size());
    }

    public <K extends Comparable<? super K>> NavigableMap<K, List<T>> sortedBy(Function<? super T, ? extends K> key) {
        TreeMap<K, List<T>> tree = new TreeMap<>();
        for (T e : store.values()) {
            K k = key.apply(e);
            if (k != null) tree.computeIfAbsent(k, x -> new ArrayList<>()).add(e);
        }
        tree.replaceAll((k, list) -> List.copyOf(list));
        return Collections.unmodifiableNavigableMap(tree);
    }

    private Comparator<T> total(Comparator<? super T> order) {  // tie-break on id: a total order
        Comparator<T> base = order::compare;
        return base.thenComparing(byId);
    }

Scanning store.values() is weakly consistent (L68): no ConcurrentModificationException, and concurrent writes may or may not be seen. The ID tie-break makes the sort a total order (L71), which is what keeps pages disjoint. sortedBy returns a frozen snapshot, so repo.sortedBy(Customer::score).subMap(50, true, 80, false) costs O(log n + k) after one O(n log n) build.

What breaks in production
  • Paging with ties. Sorting only by score lets equal rows swap between requests: duplicates and missing rows. End every sort with a unique key.
  • Mutable entities. Index keys are computed at save time; mutating a stored object desynchronizes the indexes (L71, bug 1).
  • Heavy work inside compute. It holds a bin lock; slow code stalls other writers, and touching the same map inside it can throw IllegalStateException: Recursive update.
  • Offsets over moving data. An insert between page requests shifts later rows; real APIs often use keyset pagination ("after ID x").
