Architecture, Patterns & System Design

Phase 23 turns the Spring, data and microservices skills of the previous phases into design judgement: object-level patterns, application architecture, and system design for workloads of millions of users. It moves from SOLID and the Gang of Four through Fowler's enterprise patterns, hexagonal architecture, DDD, CQRS and event sourcing, GraphQL and gRPC, to three end-to-end case studies, and it sets up the capstone projects of Phase 24, where every one of these decisions has to be made for real.

By the end of this phase you can

  • Recognise the classic creational, structural and behavioral patterns in Spring and JDK code, and replace Visitor-style code with sealed interfaces and pattern-matching switch.
  • Lay out a Spring project as layered or hexagonal modules, keep the domain free of framework imports, and enforce the boundaries with ArchUnit or Spring Modulith tests in CI.
  • Model a domain with self-validating value-object records, small aggregates referenced by id, and domain events published after commit.
  • Decide when lightweight CQRS, full CQRS or event sourcing is justified, and implement an event store with optimistic concurrency on Postgres.
  • Build and secure a GraphQL API with batch loading and query limits, and a gRPC service with deadlines, mapped status codes and working load balancing.
  • Run a system design from requirements and back-of-the-envelope numbers through replication, sharding, caching, queues and availability targets.
  • Design a URL shortener, a distributed rate limiter, a payment-safe checkout and a real-time chat system, and defend each trade-off out loud.

SOLID Principles in Real Java

45m video50m practice

SOLID is a set of heuristics for one goal: code you can change cheaply. Each principle names a specific way a design resists change, and each has a cost when applied where nothing is going to change.

Single Responsibility: one reason to change

"Responsibility" means a reason to change, which in practice means a group of people who ask for changes. A 600-line OrderService that validates input, applies pricing rules, persists the order, sends the confirmation email and writes a sales report changes when the product team edits validation, when marketing adds a promotion, when the DBA renames a column, when legal changes the email footer and when finance wants a new report column. Five owners, one file, constant merge conflicts, and a test that needs an SMTP stub to check a discount.

// After the split: the use case orchestrates, collaborators own one concern each
@Service
public class PlaceOrderService {
    private final OrderValidator validator;          // product rules
    private final PriceCalculator pricing;           // marketing rules
    private final SaveOrder orders;                  // persistence port
    private final ApplicationEventPublisher events;  // email and reporting listen

    public PlaceOrderService(OrderValidator validator, PriceCalculator pricing,
                             SaveOrder orders, ApplicationEventPublisher events) {
        this.validator = validator; this.pricing = pricing;
        this.orders = orders; this.events = events;
    }

    @Transactional
    public OrderId place(PlaceOrder command) {
        validator.validate(command);
        Money total = pricing.total(command.cart());
        Order order = orders.save(Order.create(command, total));
        events.publishEvent(new OrderPlaced(order.id(), total));
        return order.id();
    }
}

The email sender and the report writer become @EventListener (or @TransactionalEventListener) beans. The use case still reads top to bottom as the business process, which is the point: splitting must not scatter the story.

Open/Closed: extend by adding, not by editing

A module is open for extension and closed for modification when new behaviour arrives as new code rather than another branch in an existing method. The classic smell is a pricing switch that grows a case every sprint, each edit risking the others.

public interface PricingRule {
    boolean appliesTo(Cart cart);
    Money apply(Cart cart, Money running);
}

@Component @Order(10)
class BulkDiscount implements PricingRule {
    public boolean appliesTo(Cart cart) { return cart.itemCount() >= 10; }
    public Money apply(Cart cart, Money running) { return running.percentOff(5); }
}

@Service
class PriceCalculator {
    private final List<PricingRule> rules;   // Spring injects every rule bean, sorted by @Order
    PriceCalculator(List<PricingRule> rules) { this.rules = rules; }

    Money total(Cart cart) {
        Money running = cart.subtotal();
        for (PricingRule rule : rules) {
            if (rule.appliesTo(cart)) running = rule.apply(cart, running);
        }
        return running;
    }
}

Adding a loyalty discount is a new class; PriceCalculator and its tests are untouched. The opposite trade-off is a sealed interface with a pattern-matching switch: closed to new types (the compiler forces every switch to be updated) but open to new operations. Choose by asking which axis actually changes.

Liskov Substitution: subtypes must keep the contract

DefinitionA subtype is substitutable when every caller written against the supertype stays correct with the subtype. Concretely: preconditions may not be strengthened, postconditions may not be weakened, invariants must be preserved, and the subtype may not throw exceptions the supertype's contract does not allow.
class Rectangle {
    protected int width, height;
    void setWidth(int w)  { width = w; }
    void setHeight(int h) { height = h; }
    int area() { return width * height; }
}
class Square extends Rectangle {               // "a square is a rectangle"... in geometry
    @Override void setWidth(int w)  { width = w; height = w; }
    @Override void setHeight(int h) { width = h; height = h; }
}

static void stretch(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    if (r.area() != 20) throw new AssertionError("area " + r.area());  // Square: 16
}

Rectangle.setWidth has an implicit postcondition: height is unchanged. Square weakens it, so code that was correct breaks. The fix is to remove the mutators, not to add instanceof checks: sealed interface Shape permits Rect, Square with record Rect(int w, int h) and record Square(int side), each computing its own area. An override that throws UnsupportedOperationException is the same violation in another costume: every caller now has to know which subtype it holds. The JDK does this deliberately with the "optional operations" of Collection (List.of(1).add(2) throws), documented in the Javadoc, and it is a known compromise rather than a model to copy.

Interface Segregation and Dependency Inversion

A fat interface forces implementers to write empty or throwing methods and forces clients to depend on methods they never call. Split by client need: a reporting job needs search, the checkout needs load and save, and a test fake for either should be a few lines.

public interface LoadOrder    { Optional<Order> byId(OrderId id); }
public interface SaveOrder    { Order save(Order order); }
public interface SearchOrders { List<OrderSummary> search(OrderQuery query); }

@Repository   // one adapter can implement all three ports
class JpaOrderAdapter implements LoadOrder, SaveOrder, SearchOrders { /* ... */ }

Dependency Inversion says high-level policy should not depend on low-level detail; both depend on an abstraction, and the abstraction is owned by the policy. The interface lives in the domain or application package, named in domain terms (PaymentGateway, not StripeClientWrapper); the adapter in the infrastructure package implements it. If the interface sits next to the adapter, the domain imports infrastructure and nothing has been inverted.

The limits of SOLID, and the principles around it

Applied mechanically, SOLID yields an IOrderService/OrderServiceImpl pair for every class, a thousand five-line types, and stack traces you scroll through. An interface with one implementation and no test fake is ceremony. Introduce a seam when there is a second implementation, a test that needs one, or a boundary (database, network, vendor) you expect to swap or isolate.

  2. Replace a switch on customer type with PricingRule beans. Add a new rule without editing PriceCalculator and confirm the order with @Order.
  3. Write a JUnit test for stretch that passes for Rectangle and fails for Square, then redesign with a sealed interface and two records.
  4. Split a fat repository interface into read and write ports, move the ports into the domain package, and write an in-memory fake of one port in under ten lines.

Creational Patterns

45m video50m practice

Creational patterns decide who constructs an object and when. In a Spring application the container already answers that for services, so the patterns that survive are the ones for values: builders, static factories and copies.

Singleton: three correct versions, and the Spring answer

public enum IdGenerator {                       // Effective Java Item 3
    INSTANCE;
    private final AtomicLong next = new AtomicLong();
    public long nextId() { return next.incrementAndGet(); }
}

public final class Settings {
    private Settings() {}
    private static final class Holder { static final Settings INSTANCE = new Settings(); }
    public static Settings get() { return Holder.INSTANCE; }   // Holder initialised on first call
}

public final class Registry {
    private static volatile Registry instance;    // volatile is not optional
    private Registry() {}
    public static Registry get() {
        Registry r = instance;
        if (r == null) {
            synchronized (Registry.class) {
                r = instance;
                if (r == null) instance = r = new Registry();
            }
        }
        return r;
    }
}
Definition · Safe publicationAn object is safely published when every thread that obtains the reference also sees its fully constructed state. Static initialisers, volatile fields, final fields, and a lock held by both writer and reader all give this guarantee; a plain field does not.

The enum is serialization-safe and reflection-proof (Constructor.newInstance refuses enum types). The holder idiom relies on class initialisation being lazy and run under a JVM lock (JLS §12.4.2). Double-checked locking needs volatile because the first check reads instance outside the lock:

In Spring you rarely write any of these. A bean has singleton scope by default: one instance per ApplicationContext, created and published safely by the container, injectable, and replaceable in tests. A static singleton is hidden global state that every test shares.

Factory Method and Abstract Factory

A factory method returns an interface and hides which class is built. An abstract factory builds a family of objects that must match: a Stripe charger with a Stripe webhook verifier, never a mix.

public interface PaymentKit {                     // abstract factory
    PaymentProvider provider();
    WebhookVerifier webhookVerifier();
}

@Configuration
class PaymentConfig {
    @Bean                                         // a @Bean method is a factory method
    PaymentKit paymentKit(@Value("${payments.provider}") String name,
                          StripeProperties stripe, AdyenProperties adyen) {
        return switch (name) {
            case "stripe" -> new StripeKit(stripe);
            case "adyen"  -> new AdyenKit(adyen);
            default -> throw new IllegalStateException("Unknown provider: " + name);
        };
    }
}

FactoryBean<T> is the container-level version: the bean registered under a name is the result of getObject(), not the factory (ask for &name to get the factory). LocalContainerEntityManagerFactoryBean is the one you meet most. Write a @Bean method unless you are building a library that must hide complex construction.

Builder: many parameters, some required

Telescoping constructors (new Call(uri), new Call(uri, method), new Call(uri, method, timeout)…) make call sites unreadable and let two int arguments swap silently. A builder names every argument, takes required ones up front, and validates once in build():

public record HttpCall(URI uri, String method, Duration timeout, Map<String, String> headers) {
    public HttpCall {
        Objects.requireNonNull(uri, "uri");
        if (timeout.isNegative() || timeout.isZero()) throw new IllegalArgumentException("timeout");
        headers = Map.copyOf(headers);                       // defensive, immutable copy
    }
    public static Builder to(URI uri) { return new Builder(uri); }   // required argument

    public static final class Builder {
        private final URI uri;
        private String method = "GET";
        private Duration timeout = Duration.ofSeconds(5);
        private final Map<String, String> headers = new LinkedHashMap<>();
        private Builder(URI uri) { this.uri = uri; }
        public Builder method(String m)            { method = m; return this; }
        public Builder timeout(Duration t)         { timeout = t; return this; }
        public Builder header(String k, String v)  { headers.put(k, v); return this; }
        public HttpCall build() { return new HttpCall(uri, method, timeout, headers); }
    }
}
Lombok builders@Builder ignores field initialisers: without @Builder.Default a field declared = new ArrayList<>() arrives as null. It validates nothing, so required fields are not enforced unless the constructor checks them (putting @Builder on a record keeps checks in the compact constructor). It generates an all-args constructor, which collides with the no-arg constructor JPA needs. For class hierarchies you need @SuperBuilder on every class in the chain, and it does not mix with @Builder.

Prototype, copies and object pools

Prototype means "make a new object by copying an existing one". Object.clone() is the JDK's version and is best avoided (Effective Java Item 13): shallow by default, bypasses constructors, and fights final fields. Prefer copy constructors, static copy factories (List.copyOf), and, for records, small "wither" methods such as withCity(String c) { return new Address(street, c, zip); }. A derived-record with expression has been proposed (JEP 468); check its status before relying on it. Defensive copying (Item 50) is the same idea at a boundary: copy mutable inputs on the way in and never hand out internal mutable state.

Object pools only pay when creation is expensive and the object is safely reusable: database connections (TCP, TLS and authentication per connection) and platform threads. That is why HikariCP and ThreadPoolExecutor exist. Pooling ordinary objects is a loss on a modern JVM: allocation is a pointer bump in a thread-local buffer, while pooled objects live long, need reset logic, and leak state. Virtual threads should not be pooled at all (JEP 444).

DI, static factories, and spotting patterns in the source

Dependency injection absorbed most of the catalogue for services: the container is the factory, singleton scope is the singleton, @Profile and @ConditionalOnProperty choose the family. Note that Spring's prototype scope means "new instance per lookup", not "copy of a prototype". A static factory method (Effective Java Item 1) beats a constructor when it helps to have a name (Duration.ofSeconds), to cache (Integer.valueOf, Boolean.valueOf), or to return a hidden subtype (EnumSet.noneOf picks an implementation by enum size; List.of returns a private class).

Structural Patterns

45m video50m practice

Structural patterns are all ways of wrapping or composing objects. What separates them is intent: change an interface (adapter), add behaviour behind the same interface (decorator), control access to it (proxy), or simplify many interfaces into one (facade).

Adapter: your interface, their client

Never let a vendor SDK's types leak through your code. Define the interface you wish the vendor had, in your own terms, and write one class that translates. When the SDK ships a breaking major version, or you change vendors, one class changes.

public interface ExchangeRates { BigDecimal rate(Currency from, Currency to); }   // your port

@Component
class AcmeFxAdapter implements ExchangeRates {
    private final AcmeFxClient client;                          // third-party SDK
    AcmeFxAdapter(AcmeFxClient client) { this.client = client; }

    public BigDecimal rate(Currency from, Currency to) {
        AcmeQuote q = client.getQuote(from.getCurrencyCode() + to.getCurrencyCode());
        if (q.getStatus() != AcmeStatus.OK) throw new RateUnavailableException(from, to);
        return new BigDecimal(q.getMid());                      // their String, your BigDecimal
    }
}

In DDD this is an anti-corruption layer: the same structure, applied at the boundary between your bounded context and another system's model, so their naming and invariants do not seep into your domain.

Decorator: same interface, added behaviour

DefinitionA decorator implements an interface and holds another implementation of the same interface, delegating to it and adding behaviour before or after. Decorators stack, and the caller cannot tell how many are present.

new BufferedInputStream(new FileInputStream(f)) is the canonical case: both are InputStream, and the outer one batches the inner one's reads. The same shape builds cross-cutting behaviour around a repository:

final class RetryingProducts implements ProductRepository {
    private final ProductRepository next;
    private final int attempts;
    RetryingProducts(ProductRepository next, int attempts) { this.next = next; this.attempts = attempts; }

    public Optional<Product> byId(ProductId id) {
        for (int i = 1; ; i++) {
            try { return next.byId(id); }
            catch (TransientDataAccessException e) { if (i >= attempts) throw e; }
        }
    }
}

@Bean @Primary
ProductRepository products(JdbcProducts jdbc, Cache<ProductId, Product> cache) {
    return new LoggingProducts(new CachingProducts(new RetryingProducts(jdbc, 3), cache));
}

Spring AOP builds exactly this at runtime. @Transactional, @Cacheable and @Retryable each become an interceptor in a chain around your bean: decorators by intent, proxies by mechanism.

Proxy: controlling access

A proxy has the same interface as its subject but decides whether, when or where the real call happens. A virtual proxy delays expensive work: Hibernate's getReferenceById returns a generated subclass that loads the row on first access (and throws LazyInitializationException if the session is gone). A protection proxy checks rights first: @PreAuthorize method security. A remote proxy turns a local call into a network call: an OpenFeign client or a Spring @HttpExchange interface.

@SuppressWarnings("unchecked")
static <T> T timed(T target, Class<T> type) {
    return (T) Proxy.newProxyInstance(type.getClassLoader(), new Class<?>[] { type },
        (proxy, method, args) -> {
            long t0 = System.nanoTime();
            try { return method.invoke(target, args); }
            catch (InvocationTargetException e) { throw e.getCause(); }   // unwrap the real exception
            finally { System.out.printf("%s %d us%n", method.getName(), (System.nanoTime() - t0) / 1_000); }
        });
}

A JDK dynamic proxy needs an interface; CGLIB generates a subclass, so it cannot handle final classes or methods. Spring Boot proxies classes with CGLIB by default, and in both cases a call from this bypasses the proxy (L276).

Facade, Composite, Bridge and Flyweight

Facade: one simple entry point over a subsystem. An application service such as CheckoutService.checkout(cartId) hides inventory, pricing, payment and notification; SLF4J is literally a "Simple Logging Facade". Composite treats a tree of parts and wholes uniformly, and sealed interfaces make it concise:

sealed interface Permission permits Single, Group {}
record Single(String name) implements Permission {}
record Group(String name, List<Permission> members) implements Permission {
    Group { members = List.copyOf(members); }      // immutable, so no cycles can be built later
}

static Set<String> flatten(Permission p) {
    return switch (p) {
        case Single s -> Set.of(s.name());
        case Group g  -> g.members().stream()
                          .flatMap(m -> flatten(m).stream())
                          .collect(Collectors.toSet());
    };
}

Bridge splits two dimensions that vary independently. Notifications vary by message type (order shipped, password reset) and by channel (email, SMS, push). Subclassing both gives N×M classes; a Notification hierarchy that holds a Channel gives N+M. JDBC is the textbook bridge: one API, many vendor drivers. Flyweight shares immutable instances: Integer.valueOf caches −128 to 127, string literals are interned, enum constants and Boolean.TRUE are shared. That cache is why Integer comparison with == "works" in tests and fails for 128.

Each layer adds stack frames ($$SpringCGLIB$$, ReflectiveMethodInvocation, interceptor chains), makes "step into" land somewhere unexpected, and can change identity: a Hibernate proxy's getClass() is not the entity class, so equals written with getClass() fails. The CPU cost is usually negligible next to I/O; the debugging cost is not.

What breaks in productionA decorator chain assembled in the wrong order (retry outside a circuit breaker, caching outside authorisation) passes unit tests of each piece and misbehaves together. Test the assembled bean. An unbounded ConcurrentHashMap used as a cache decorator is a slow memory leak; use a bounded cache such as Caffeine.

  2. Build logging, caching and retrying decorators for a repository. Write a test that proves a cache hit does not trigger a retry, then swap the order and watch it fail.
  3. Write the timed JDK proxy, then remove the InvocationTargetException unwrap and observe what callers receive instead.
  4. Model a permission tree with the sealed Composite and add a depth-limited flatten.
  5. Sketch the N×M class explosion for three notifications and three channels, then refactor to a bridge.

Behavioral Patterns I

45m video50m practice

Behavioral patterns decide where a decision lives and how a request travels. Spring already implements most of them for you, so the skill is recognising them, extending them correctly, and knowing which coupling each one buys.

Strategy: let the container build the registry

A strategy is an interchangeable algorithm behind one interface. Injecting Map<String, PricingStrategy> gives every implementing bean keyed by its bean name, so a switch on plan names becomes a lookup and a new plan becomes a new class.

public interface PricingStrategy {
    Plan plan();                      // explicit key instead of relying on bean names
    Money price(Cart cart);
}

@Service
class Pricing {
    private final Map<Plan, PricingStrategy> byPlan;

    Pricing(List<PricingStrategy> all) {
        // toMap throws IllegalStateException on a duplicate key: fail at startup, not at checkout
        this.byPlan = all.stream().collect(Collectors.toMap(PricingStrategy::plan, s -> s));
    }

    Money price(Cart cart, Plan plan) {
        PricingStrategy s = byPlan.get(plan);
        if (s == null) throw new IllegalArgumentException("No strategy for " + plan);
        return s.price(cart);
    }
}

Bean-name keys (@Component("member")) work, but the key then lives in an annotation string that nothing type-checks. An explicit plan() method keeps the key next to the behaviour. Comparator, PasswordEncoder and RowMapper are strategies you pass every day.

Template Method: fixed skeleton, overridable steps

public abstract class ImportJob<T> {
    public final ImportReport run(Path file) throws IOException {   // final: the order is invariant
        List<String> lines = Files.readAllLines(file);
        List<T> items = lines.stream().map(this::parse).toList();
        items.forEach(this::validate);
        return new ImportReport(lines.size(), save(items));
    }
    protected abstract T parse(String line);
    protected void validate(T item) {}                              // hook with a default
    protected abstract int save(List<T> items);
}

Spring uses this shape in AbstractRoutingDataSource (you override only determineCurrentLookupKey(), for example to route read-only transactions to a replica) and OncePerRequestFilter.doFilterInternal. JdbcTemplate is the callback variant: the skeleton (get connection, prepare, execute, translate SQLException, release) is fixed and you pass a RowMapper lambda. That variant avoids the cost of the classic one: subclasses depend on the base class's internals and call order, and a change to the skeleton can break every subclass (the fragile base class).

Observer, and why it is not a message broker

public record OrderPlaced(OrderId id, Money total) {}       // any object can be an event

@Component
class ConfirmationEmail {
    @TransactionalEventListener                 // default phase: AFTER_COMMIT
    void on(OrderPlaced event) { /* send email */ }
}
// publisher: applicationEventPublisher.publishEvent(new OrderPlaced(id, total));
DefinitionSpring application events are in-process, synchronous by default, and not durable. A plain @EventListener runs on the publisher's thread inside its transaction, and its exception propagates to the publisher. A broker (Kafka, RabbitMQ) is a separate durable process: events survive crashes, cross service boundaries, can be replayed, and are delivered at least once.

Use events to decouple modules inside one deployable. If losing the event on a crash is unacceptable, write it to an outbox table in the same transaction and relay it to a broker.

Chain of Responsibility and Command

Each link in a chain either handles the request, passes it on, or stops it. Servlet filters are the model: chain.doFilter means "continue", returning without calling it means "stop". Spring Security's FilterChainProxy holds ordered SecurityFilterChains, each a list of filters.

@Component @Order(1)
class CorrelationIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String id = Optional.ofNullable(req.getHeader("X-Correlation-Id"))
                            .orElseGet(() -> UUID.randomUUID().toString());
        MDC.put("correlationId", id);
        try { chain.doFilter(req, res); }       // pass to the next link
        finally { MDC.remove("correlationId"); }
    }
}

The same shape works for business rules: inject List<CheckoutRule> ordered with @Order, where each rule returns Optional<Rejection>, and stop at the first rejection; or run every discount link in sequence, each receiving the previous total. A Command turns a request into an object, which makes it storable, queueable and reversible:

sealed interface CartCommand permits AddItem, RemoveItem { CartCommand inverse(); }
record AddItem(Sku sku, int qty)    implements CartCommand { public CartCommand inverse() { return new RemoveItem(sku, qty); } }

State: making illegal transitions impossible

public enum OrderStatus {
    NEW, PAID, SHIPPED, DELIVERED, CANCELLED;

    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = Map.of(
        NEW, EnumSet.of(PAID, CANCELLED),
        PAID, EnumSet.of(SHIPPED, CANCELLED),
        SHIPPED, EnumSet.of(DELIVERED),
        DELIVERED, EnumSet.noneOf(OrderStatus.class),
        CANCELLED, EnumSet.noneOf(OrderStatus.class));

    public OrderStatus to(OrderStatus target) {
        if (!NEXT.get(this).contains(target)) throw new IllegalStateException(this + " -> " + target);
        return target;
    }
}

The enum checks at run time. A sealed interface can check at compile time when each state is a record carrying the data valid in that state, and transitions are methods only on states that allow them: record Paid(PaymentId payment) has Shipped ship(TrackingNo t), and New has no ship method, so the illegal call does not compile. Spring Statemachine (StateMachineConfigurerAdapter, withExternal().source(NEW).target(PAID).event(PAY)) earns its weight only with guards, actions, hierarchical states and persisted machines. Whatever the model, enforce the transition in the database as well: UPDATE orders SET status = 'SHIPPED' WHERE id = ? AND status = 'PAID' and treat zero updated rows as a conflict.

A status changed with a read-check-write in Java, without a guarded UPDATE or a version column, lets two concurrent requests ship and cancel the same order.

Behavioral Patterns II & Anti-Patterns

45m video45m practice

Several classic patterns exist to work around missing language features; modern Java makes Visitor and most Interpreter code obsolete. The anti-patterns are the more useful half of the day: naming a smell is the first step to the refactoring that fixes it.

Iterator, Mediator and Memento

Iterable gives the for-each loop; Iterator walks once with hasNext/next; Spliterator adds trySplit, estimateSize and characteristics (SIZED, ORDERED, IMMUTABLE) so streams can split work for parallelism. A custom iterator is the clean way to hide paging behind a loop:

record Page<T>(List<T> items, String nextToken) {}      // nextToken == null on the last page

final class Paged<T> implements Iterable<T> {
    private final Function<String, Page<T>> fetch;            // null token = first page
    Paged(Function<String, Page<T>> fetch) { this.fetch = fetch; }

    public Iterator<T> iterator() {
        return new Iterator<>() {
            Iterator<T> current = Collections.emptyIterator();
            String token;
            boolean started;
            public boolean hasNext() {
                while (!current.hasNext() && (!started || token != null)) {
                    Page<T> p = fetch.apply(token);
                    started = true; current = p.items().iterator(); token = p.nextToken();
                }
                return current.hasNext();
            }
            public T next() {
                if (!hasNext()) throw new NoSuchElementException();
                return current.next();
            }
        };
    }
}
// StreamSupport.stream(paged.spliterator(), false): sequential; the default spliterator splits poorly

A Mediator replaces many-to-many object conversations with one coordinator: n components need n links instead of up to n(n−1)/2. A saga orchestrator is a mediator across services; the risk in both cases is the mediator growing into a god class. A Memento captures state without exposing internals so it can be restored: an editor's save() returning record Snapshot(String text, int cursor), an undo stack of snapshots, or an event-sourcing snapshot that saves replaying a long stream.

Visitor, double dispatch, and the sealed replacement

Definition · Double dispatchJava chooses an overload from the static types of the arguments at compile time and an override from the runtime type of the receiver only. Visitor fakes dispatch on two runtime types: expr.accept(visitor) picks the element's method, which calls visitor.visit(this) with a precise static type.
sealed interface Expr permits Num, Add, Mul, Neg {}
record Num(double v) implements Expr {}
record Add(Expr l, Expr r) implements Expr {}
record Mul(Expr l, Expr r) implements Expr {}
record Neg(Expr e) implements Expr {}

static double eval(Expr e) {
    return switch (e) {                       // no default: exhaustiveness is checked
        case Num n            -> n.v();
        case Add(var l, var r) -> eval(l) + eval(r);
        case Mul(var l, var r) -> eval(l) * eval(r);
        case Neg(var inner)   -> -eval(inner);
    };
}

Record patterns arrived with Java 21 (L119). That function is also the whole Interpreter pattern for a toy language. For a real grammar (precedence, error recovery, helpful messages) use a parser generator such as ANTLR, or an existing expression language such as SpEL, rather than hand-rolling one class per grammar rule.

Null Object, Optional and Specification

A Null Object is a real implementation with neutral behaviour: NoDiscount.apply(total) returns total, so callers never branch. Optional is a return type that forces the caller to decide what absence means (Effective Java Item 55); do not use it for fields, parameters or collections. Prefer the Null Object when a neutral behaviour exists, and Optional when the caller must react. A Specification is a composable business rule:

@FunctionalInterface
interface Spec<T> {
    boolean isSatisfiedBy(T t);
    default Spec<T> and(Spec<T> o) { return t -> isSatisfiedBy(t) && o.isSatisfiedBy(t); }
    default Spec<T> or(Spec<T> o)  { return t -> isSatisfiedBy(t) || o.isSatisfiedBy(t); }
    default Spec<T> negate()       { return t -> !isSatisfiedBy(t); }
}
Spec<Order> freeShipping = isPremium.or(totalAtLeast(Money.eur(50))).and(isRemoteRegion.negate());

Spring Data's Specification<T> is the same idea compiled to a JPA Criteria predicate, so the rule runs in SQL instead of in memory (L321).

Repository, Unit of Work, Identity Map and Lazy Load

A Repository behaves like an in-memory collection of aggregates, in domain terms: orders.byId(id), orders.add(order). Spring Data's JpaRepository is a generator for that pattern with persistence leaking through (flush, saveAndFlush, deleteAllInBatch, getReferenceById). To keep the pure shape, extend the marker interface Repository<Order, Long> and declare only the methods you want; Spring Data implements exactly those.

JPA's persistence context implements three Fowler patterns at once:

@Transactional
public void rename(long id, String name) {
    Customer c = em.find(Customer.class, id);     // SELECT; instance registered in the context
    c.rename(name);                               // no save() call
    Customer again = em.find(Customer.class, id); // Identity Map: same instance, no second SELECT
    assert c == again;
}   // commit: flush, dirty check against the loaded snapshot, UPDATE (Unit of Work)
DefinitionUnit of Work: tracks every object loaded or changed in a business transaction and writes the changes out together at the end. Identity Map: guarantees each row is loaded once per unit of work, so two lookups return the same object. Lazy Load: an object that does not contain all its data but knows how to fetch it, which in Hibernate is a generated proxy or a persistent collection wrapper.

Data Mapper keeps objects ignorant of the database and puts a separate mapper in charge; Active Record gives each object save() and delete() and one row's worth of fields. JPA is a data mapper (the EntityManager saves, the entity never does) with its mapping metadata written as annotations on the domain class. jOOQ's UpdatableRecord.store() is an active record.

Service layer: application services vs domain services

An application service is the boundary of one use case: it opens the transaction, loads aggregates through ports, calls domain methods, saves, and publishes events. It contains no business rules of its own. A domain service holds domain logic that does not belong to one entity, such as a transfer between two accounts or a pricing calculation, and has no transaction or framework awareness. Put @Transactional on application service methods: controllers are too high (the transaction spans serialisation) and repositories too low (two repository calls become two transactions).

DTOs, assemblers and the mapping cost

Keep three models apart: the request (what the client may send, validated), the response (what the client may see, versioned with the API) and the internal model. Never bind a request to a JPA entity: clients could set fields you did not intend (mass assignment), and returning entities triggers lazy-loading errors, infinite recursion on bidirectional relations, and leaks of internal columns. The assembler is a static from/to method on the record or a MapStruct mapper generated at compile time.

The cost is real: request, command, domain object, JPA entity and row means up to four mappings per field, each a place for a forgotten field. Collapse layers when the service is CRUD-shaped and internal: a request record mapped straight to an entity, and the entity mapped to a response, is honest and enough.

Definition · The dependency ruleNothing in an inner circle may name anything in an outer circle: no imports, no annotations, no types. Domain-Driven Design: Tactical Patterns

50m video60m practice

Tactical DDD is about making invalid states impossible to construct: value objects validate themselves, aggregates guard invariants behind one root, and each transaction changes exactly one aggregate. Records and sealed types make all of it cheap in Java 21.

Entities and value objects

An entity has identity that persists while its attributes change: order 42 is the same order after its address changes, so equality is by id. A value object is defined entirely by its attributes, is immutable, and has side-effect-free operations: two Money(10.00, EUR) are interchangeable. Records give value semantics for free; the compact constructor makes them self-validating.

public record Money(BigDecimal amount, Currency currency) {
    public Money {
        int digits = currency.getDefaultFractionDigits();
        if (digits < 0 || amount.scale() > digits) throw new IllegalArgumentException("bad amount " + amount);
        amount = amount.setScale(digits);       // normalise so equals() ignores 10.0 vs 10.00
    }
    public Money plus(Money o) {
        if (!currency.equals(o.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(amount.add(o.amount), currency);
    }
}
public record EmailAddress(String value) {
    private static final Pattern SHAPE = Pattern.compile("[^@\\s]+@[^@\\s]+\\.[^@\\s]+");
    public EmailAddress { value = value.strip(); if (!SHAPE.matcher(value).matches()) throw new IllegalArgumentException("email"); }
}
public record Quantity(int value) {
    public Quantity { if (value < 1 || value > 999) throw new IllegalArgumentException("quantity " + value); }
}
public record DateRange(LocalDate start, LocalDate endExclusive) {
    public DateRange { if (!start.isBefore(endExclusive)) throw new IllegalArgumentException("empty range"); }
    public boolean overlaps(DateRange o) { return start.isBefore(o.endExclusive) && o.start.isBefore(endExclusive); }
}

Compare book(String email, int nights, long cents, LocalDate from, LocalDate to) with book(EmailAddress guest, DateRange stay, Money price). The second cannot receive swapped dates, a negative price or a malformed email, because those objects cannot exist; validation happens once, at construction, instead of in every service that might forget it.

Aggregates: the consistency boundary

Definition · AggregateA cluster of entities and value objects treated as one unit for changes. Outside code holds references only to the root, all changes go through the root's methods, and the root guarantees the cluster's invariants at the end of every method. Other aggregates are referenced by id only.
@Entity
public class Order extends AbstractAggregateRoot<Order> {
    @Id private UUID id;
    private UUID customerId;                                  // an id, not @ManyToOne Customer
    @Enumerated(EnumType.STRING) private OrderStatus status = OrderStatus.NEW;
    @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true) @JoinColumn(name = "order_id")
    private List<OrderLine> lines = new ArrayList<>();
    @Version private long version;

    protected Order() {}                                      // for JPA only

    public void addLine(UUID productId, Quantity qty, Money unitPrice) {
        if (status != OrderStatus.NEW) throw new IllegalStateException("order is " + status);
        if (lines.size() == 50) throw new IllegalStateException("at most 50 lines");
        lines.add(new OrderLine(productId, qty.value(), unitPrice));
    }
    public void place() {
        if (lines.isEmpty()) throw new IllegalStateException("empty order");
        status = OrderStatus.PLACED;
        registerEvent(new OrderPlaced(id, customerId));      // published when the repository saves
    }
    public List<OrderLine> lines() { return List.copyOf(lines); }   // no mutation from outside
}

One transaction per aggregate is the rule that keeps a monolith splittable: if placing an order also decrements stock in the same transaction, Order and Inventory can never live in different services. Instead, Order commits and publishes OrderPlaced; Inventory reacts in its own transaction and accepts eventual consistency. Keep aggregates small. A Product holding every review, or a Customer holding every order, is slow to load and turns unrelated edits into optimistic-lock conflicts on the same version column.

Domain events, published after commit

AbstractAggregateRoot collects events with registerEvent; Spring Data publishes them through its @DomainEvents and @AfterDomainEventPublication methods when the aggregate is passed to a repository save method (not on dirty checking alone). }

Repositories, services, factories and specifications

Repositories exist for aggregate roots only: there is an OrderRepository and never an OrderLineRepository, because loading a line directly would bypass the root's invariants. A domain service holds domain logic that belongs to no single entity (a TransferService moving money between two accounts, a ShippingCostPolicy); an application service orchestrates a use case and owns the transaction (L444). A factory handles creation that needs more than a constructor, such as building an order from a cart, a price list and a customer's tier. A specification captures a reusable rule (OverdueInvoice, EligibleForFreeShipping) that can validate, select and be combined (L443).

Invariants in the constructor; module boundaries with Spring Modulith

If an object can be created invalid, every method must re-check it. Enforce invariants in constructors and in the root's mutators, keep JPA's no-arg constructor protected, and expose no setters. At the next level up, Spring Modulith treats each direct sub-package of the application's main package as a module, treats nested packages as internal, and fails a test on cycles or on access to another module's internals:

CQRS & Event Sourcing in Practice

50m video60m practice

CQRS separates the model that changes state from the model that answers questions; event sourcing stores the changes themselves instead of the current state. The first is often worth it in its lightweight form; the second is a long-term commitment that pays off only in specific domains.

CQRS: two models for two jobs

The command model is behaviour-rich, normalised and transactional: aggregates that enforce invariants (L446). The query model is denormalised and shaped for a screen: no invariants, just rows. Forcing one model to do both gives entities full of @JsonIgnore and N+1 queries for list pages. The lightweight version keeps one database: entities for writes, projections or SQL for reads.

                FROM orders o JOIN customers c ON c.id = o.customer_id
                LEFT JOIN order_lines l ON l.order_id = o.id
                WHERE o.customer_id = :cid

            .param("cid", customerId)
            .query(OrderSummaryView.class)          // snake_case columns map to record components
            .list();
    }
}

That version needs no new infrastructure and is all most services need. Commands become records (PlaceOrder, CancelOrder), each with exactly one handler that returns at most an id or a version; queries become records with handlers that return views and never change state.

The full version and eventual consistency in the UI

The full version keeps separate stores (Postgres for writes, Elasticsearch or a denormalised table for reads) synchronised by events, usually through an outbox. Each side scales and is indexed independently. The cost is the user who saves and immediately sees the old value. Mitigations for read-your-own-writes: return the new state from the command and render it directly; have the command return the new version and let the query wait or poll until the projection reaches it; route the author's reads to the write model for a few seconds; or update the UI optimistically and reconcile.

Event sourcing: the log is the source of truth

Definition · Event sourcingState is stored as an append-only sequence of immutable events per aggregate (a stream). Current state is a left fold of the stream; a command loads the stream, decides which new events to emit, and appends them only if the stream is still at the version it read (optimistic concurrency by expected version).
sealed interface AccountEvent permits Opened, Deposited, Withdrawn {}
record Opened(UUID id) implements AccountEvent {}
record Deposited(long cents) implements AccountEvent {}
record Withdrawn(long cents) implements AccountEvent {}

record Account(UUID id, long balance, int version) {
    static Account replay(List<AccountEvent> history) {
        Account a = null;
        for (AccountEvent e : history) a = apply(a, e);
        return a;
    }
    static Account apply(Account a, AccountEvent e) {
        return switch (e) {
            case Opened o    -> new Account(o.id(), 0, 1);
            case Deposited d -> new Account(a.id(), a.balance() + d.cents(), a.version() + 1);
            case Withdrawn w -> new Account(a.id(), a.balance() - w.cents(), a.version() + 1);
        };
    }
    List<AccountEvent> withdraw(long cents) {          // decide; never mutate
        if (cents <= 0 || cents > balance) throw new IllegalArgumentException("cannot withdraw " + cents);
        return List.of(new Withdrawn(cents));
    }
}
CREATE TABLE events (
  global_position BIGSERIAL PRIMARY KEY,
  stream_id   UUID        NOT NULL,
  version     INT         NOT NULL,
  type        TEXT        NOT NULL,
  payload     JSONB       NOT NULL,
  metadata    JSONB       NOT NULL DEFAULT '{}',
  recorded_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (stream_id, version)           -- expected-version check: a duplicate means a concurrent writer
);
CREATE TABLE snapshots (stream_id UUID PRIMARY KEY, version INT NOT NULL, state JSONB NOT NULL);

Appending inserts rows with version = expected + 1, + 2, …; a unique violation becomes a concurrency-conflict error that the caller retries after reloading. A snapshot every few hundred events lets loading start from the snapshot and replay only the tail.

Projections, and the hard parts honestly

A projection is a consumer that folds events into a read table. Because the log is complete, you can drop a projection and rebuild it from position zero, which means a new report or a fixed bug in a view is a replay, not a data migration. That is the superpower. The costs:

  • Schema evolution. Events written five years ago must still deserialise. Add fields with defaults, never change meaning, and use versioned event types with upcasters that translate old shapes on read.
  • GDPR deletion. An immutable log conflicts with erasure. The common answer is crypto-shredding: encrypt personal fields with a per-person key held elsewhere and delete the key. Keep personal data out of events where you can.
  • Debugging and tooling. "Why is the balance wrong" means reading a stream, not a row; ad-hoc SQL against current state is gone unless a projection provides it.
  • Learning curve. The team must think in commands, events and eventual consistency everywhere.

Axon Framework provides aggregates, command and query buses, event processors and upcasting for Java, with its own server optional. EventStoreDB (now marketed as KurrentDB) is a database built around streams, expected-version appends and subscriptions. Use event sourcing for audit-critical domains (ledgers, claims), for temporal queries ("what did we know on 1 March?"), and for complex collaborative domains. For a product catalogue or a user profile it is architectural theatre.

What breaks in productionA projector that reads the log by global_position > last_seen can skip events: BIGSERIAL values are assigned at insert time, so a transaction holding position 101 may commit after another transaction's 102 has been read. Track positions with a gap-aware reader or commit-ordered mechanism, or consume through an outbox relay. A projection handler that is not idempotent double-counts when it restarts after a crash.

Refactoring discipline and the core moves

Definition · RefactoringA change to the internal structure of code that does not change its observable behaviour, made as a sequence of small steps, each leaving the test suite green. A commit is either a refactoring or a behaviour change, never both, so a reviewer can verify the refactoring mechanically and a bisect points at one kind of change.
// Before: nested conditionals, magic numbers

Working with legacy code

Feathers defines legacy code as code without tests. You cannot refactor safely until it is under test, and you often cannot test it without changing it. The way out:

  • Characterization tests pin down what the code does today, bugs included: call it, record the output, assert that output. They protect behaviour you have not yet understood.
  • Seams are places where behaviour can change without editing the code there. In Java the useful one is the object seam: pass a different implementation through a constructor or interface.
  • Breaking dependencies: parameterize constructor (the class stops calling new SmtpClient() and receives one), extract interface on a concrete collaborator, subclass and override a method that touches the network.
  • Sprout method / class: write new behaviour as a new, fully tested unit and call it from the legacy method. Wrap class: a decorator around the legacy class adds behaviour without touching it.

GraphQL with Spring for GraphQL

45m video55m practice

GraphQL moves the choice of response shape from the server to the client. That removes over-fetching and endpoint sprawl, and it moves performance and security problems onto the server, where you must solve them deliberately with batching, limits and persisted queries.

What GraphQL fixes, and the schema language

A mobile list needs a book's title; a desktop detail page needs title, author, reviews and stock. With REST you either over-fetch (one fat endpoint), under-fetch (three calls per screen), or add endpoints per client. GraphQL exposes one typed graph and each query selects exactly the fields it needs.

# src/main/resources/graphql/schema.graphqls
type Query {
  book(id: ID!): Book
  books(first: Int, after: String): BookConnection!
  search(text: String!): [SearchResult!]!
}
type Mutation { addReview(input: ReviewInput!): Review! }
type Subscription { reviewAdded(bookId: ID!): Review! }

interface Node { id: ID! }
type Book implements Node {
  id: ID!
  title: String!
  format: Format
  author: Author!
  reviews: [Review!]!                  # non-null list of non-null items
  isbn: String @deprecated(reason: "Use isbn13")
  isbn13: String
}
type Author implements Node { id: ID!  name: String! }
type Review { stars: Int!  text: String }
union SearchResult = Book | Author
enum Format { HARDCOVER PAPERBACK EBOOK }
input ReviewInput { bookId: ID!  stars: Int!  text: String }

! means non-null; [T] is a list. [Review!]! promises a list that is never null and contains no nulls, while plain Review may be null. Scalars are Int, Float, String, Boolean and ID, plus custom ones (DateTime) you register. input types are the only object types allowed as arguments.

Controllers in Spring for GraphQL

Definition · Data fetchergraphql-java executes a query field by field: every field in the selection has a data fetcher that receives its parent object and arguments and returns the value. Fields without a registered fetcher read a property of the parent. Spring's annotated controller methods are registered as data fetchers.
@Controller
class BookController {
    private final BookRepository books;          // ListCrudRepository<Book, String>
    private final AuthorRepository authors;
    private final ReviewService reviews;
    BookController(BookRepository books, AuthorRepository authors, ReviewService reviews) {
        this.books = books; this.authors = authors; this.reviews = reviews;
    }

    @QueryMapping                                // Query.book
    Optional<Book> book(@Argument String id) { return books.findById(id); }

    @BatchMapping                                // Book.author for every book in the response, one call
    List<Author> author(List<Book> bookList) {
        Map<String, Author> byId = authors.findAllById(bookList.stream().map(Book::authorId).distinct().toList())
            .stream().collect(Collectors.toMap(Author::id, a -> a));
        return bookList.stream().map(b -> byId.get(b.authorId())).toList();   // same order as input
    }

    @MutationMapping
    @PreAuthorize("hasRole('USER')")             // field-level authorization
    Review addReview(@Argument ReviewInput input) { return reviews.add(input); }

    @SubscriptionMapping
    Flux<Review> reviewAdded(@Argument String bookId) { return reviews.stream(bookId); }
}
record ReviewInput(String bookId, int stars, String text) {}

Schema files under src/main/resources/graphql are loaded automatically, and at startup Spring logs a schema-mapping report listing fields with no data fetcher. @SchemaMapping(typeName = "Book") resolves one field on one parent object; @QueryMapping and @MutationMapping are shortcuts for the root types. @Argument binds an argument (input types bind onto records); @ProjectedPayload on an interface binds arguments as a projection. Enable the GraphiQL playground in development with spring.graphql.graphiql.enabled=true.

N+1 is worse in GraphQL

In REST you write the query for each endpoint, so you see the N+1. In GraphQL the client composes the nesting, so a harmless-looking query of 50 books with their authors and each author's books becomes thousands of lookups. @BatchMapping is built on graphql-java's DataLoader: keys are collected while a level resolves, then one batch function runs. For loaders shared across controllers, register them with BatchLoaderRegistry and accept a DataLoader argument in @SchemaMapping methods.

Pagination, errors, security and subscriptions

Pagination follows the Relay cursor connection spec: a BookConnection has edges { cursor node } and pageInfo { hasNextPage endCursor }, and clients pass first/after. Spring for GraphQL can generate the connection types and adapt Spring Data Window results with a ScrollSubrange argument. Errors travel in the response's errors array, usually with HTTP 200:

gRPC & Protocol Buffers

45m video55m practice

gRPC trades JSON's readability for a compiled contract, a compact binary encoding and streaming over HTTP/2. It shines between your own services; it needs deliberate handling of deadlines, load balancing and browser access.

When binary RPC beats JSON over HTTP

Choose gRPC for internal service-to-service calls where both sides are yours, where a strict schema shared by many languages beats hand-written DTOs, and where you need streaming in either direction. Keep REST/JSON for public APIs, browser clients, HTTP caching, and anything a human debugs with curl.

gRPC: four call types on HTTP/2

The plugin generates three client stubs: a blocking stub (simple, one thread per call, fine with virtual threads), an async stub taking a StreamObserver (required for client and bidirectional streaming), and a future stub returning ListenableFuture for unary calls.

Spring Boot integration, deadlines and errors

@GrpcService                                   // net.devh grpc-spring-boot-starter
class InventoryGrpc extends InventoryServiceGrpc.InventoryServiceImplBase {

        out.onCompleted();
    }
}

                case NOT_FOUND -> 0;

gRPC has no default deadline: a call to a hung server waits forever and holds its thread. Deadlines propagate through grpc-java's Context, so a server that calls another service inside a handler passes on the remaining budget, and when the client cancels or the deadline passes the server's context is cancelled (check it in long loops). Metadata carries headers such as authorization and trace ids; ClientInterceptor/ServerInterceptor (registered globally with @GrpcGlobalServerInterceptor) handle auth, logging and tracing. Map domain exceptions in one place with @GrpcAdvice and @GrpcExceptionHandler: not found to NOT_FOUND, validation to INVALID_ARGUMENT, business-rule refusals to FAILED_PRECONDITION, overload to RESOURCE_EXHAUSTED. Retry only UNAVAILABLE (and idempotent calls). The Spring team's newer Spring gRPC project offers similar integration; check which one your stack standardises on.

Load balancing, browsers and testing

An L4 (TCP) load balancer balances connections. gRPC opens one long-lived HTTP/2 connection and multiplexes every call over it, so all traffic from a client pod lands on one server pod while new pods sit idle. Fixes: client-side balancing (a dns:/// target pointing at a Kubernetes headless service plus round_robin), an L7 proxy such as Envoy that balances per request, a service mesh (Istio, Linkerd), or proxyless gRPC configured over xDS. Browsers cannot speak raw gRPC: use gRPC-Web through a proxy (Envoy) or grpc-gateway, which generates a REST/JSON front from annotations in the .proto. Test without a network using InProcessServerBuilder.forName(name).directExecutor().addService(impl).build().start() and InProcessChannelBuilder.forName(name).directExecutor().build(), shutting both down after each test.

What breaks in productionNo deadline plus one slow dependency equals every thread blocked and a cascading outage. A deleted field whose number is reused months later makes old clients read a price as a quantity. Ten client pods behind a TCP load balancer pinning to two of twenty servers looks like "gRPC is slow".

System Design I: Fundamentals & Scaling

50m video45m practice

System design starts with numbers, not boxes: agree what the system must do and how well, estimate the load, and only then choose components. Most scaling comes from making the application tier stateless and putting redundancy behind every single point of failure.

A framework for interviews and for real designs

Algorithm · Design in six steps
  1. Clarify requirements. Functional: what users can do (shorten a URL, see a timeline). Non-functional: availability target, latency (p99, not average), consistency (may a user see stale data, for how long?), durability (may we ever lose a write?).
  2. Estimate scale: QPS, peak, storage, bandwidth.
  3. Define the API: the handful of endpoints or messages, with their key fields.
  4. Sketch the high-level design: clients, load balancer, services, stores, caches, queues.
  5. Deep-dive the bottleneck the numbers point to: usually the database, a hot key, or fan-out.
  6. State the trade-offs: what you chose, what you gave up, and what you would change at ten times the load.

Pinning the non-functional targets first is what separates a design from a diagram. "99.9% available, p99 under 200 ms, stale reads acceptable for 5 seconds, no lost payments" rules out some designs and permits others before anyone draws a box.

Back-of-the-envelope estimation

A day has 86,400 seconds, close enough to 105: one million events a day is about 12 per second. Multiply the average by a peak-to-average ratio (2–3 for consumer traffic is a common assumption; spikier for ticketing or flash sales).

Worked example10 M daily active users, 20 reads and 2 writes each per day, 1 KB per written record, 5-year retention. Reads: 200 M/day ÷ 86,400 ≈ 2,300 QPS average, ≈ 7,000 at a 3× peak. Writes: 20 M/day ≈ 230 QPS, ≈ 700 peak. Storage: 20 M × 1 KB = 20 GB/day, ≈ 7.3 TB/year, ≈ 37 TB over 5 years before replication (≈ 110 TB with three copies). Egress at peak with 10 KB responses: 7,000 × 10 KB ≈ 70 MB/s. Conclusion: reads dominate 10:1, so caching and replicas matter more than write throughput.

Vertical vs horizontal scaling, and statelessness

Vertical scaling (a bigger machine) needs no code changes and is often the right first step for a database, but it has a ceiling, a price curve that steepens near the top, and the machine remains a single point of failure. Horizontal scaling (more machines) has no hard ceiling and gives redundancy, but only works when any instance can serve any request.

Definition · Stateless serviceAn instance keeps nothing between requests that another instance would need: no in-memory sessions, no local file uploads, no per-user caches that must be consistent. State lives in the database, a shared cache (Redis), an object store (S3) or a signed client token, so instances can be added, removed or replaced at any time.

Load balancing, local and global

An L4 balancer forwards TCP/UDP connections by address and port: fast, protocol-agnostic, blind to HTTP. An L7 balancer terminates HTTP and routes per request by path, header or cookie, can retry, and balances HTTP/2 and gRPC per call. Algorithms: round robin (fine for uniform requests), least connections (better when request cost varies), and consistent hashing on a key (sends a user or cache key to the same backend, useful for local caches and WebSocket routing). Health checks remove failed instances: active probes against a readiness endpoint, and passive outlier detection on error rates.

Session affinity (sticky sessions) pins a user to an instance. Avoid it: load becomes uneven, a crash logs users out, and deployments must wait for sessions to drain. Store sessions in Redis or use a signed token instead. Across regions, DNS-based routing (GeoDNS) is simple but slow to fail over because resolvers cache records; anycast announces one IP from many locations and lets BGP route to the nearest; a GSLB combines DNS answers with health and geography.

Single points of failure and availability math

Every component with one instance (the primary database, a lone NAT gateway, one availability zone) is a single point of failure. Redundancy means at least two of everything on the request path, spread across failure domains, with N+1 capacity: lose any one instance and the rest still carry peak load.

System Design II: Caching, CDN, Queues & Async

45m video45m practice

Two moves fix most latency and load problems: serve repeated reads from somewhere closer and cheaper than the database, and take slow work off the request path. Both trade freshness or immediacy for speed, so the design must say how much staleness and delay users can accept.

Where the cache goes, and the hit-ratio math

Caches stack from the user inward: browser, CDN edge, gateway, in-process (Caffeine), distributed (Redis), and the database's own buffer pool. Each layer closer to the user saves more work and is harder to invalidate. The strategies and invalidation rules are in L385; here is the arithmetic that decides whether a cache is worth it.

Worked exampleWith hit ratio h, cache latency 0.5 ms and database latency 10 ms, mean read latency is about 0.5 + (1 − h) × 10 ms: 1.5 ms at h = 0.9, 0.6 ms at h = 0.99. The database sees only the misses: at 7,000 read QPS, 700 QPS at 90% and 70 QPS at 99%. Going from 90% to 99% looks like a small gain in the ratio and is a tenfold cut in database load. That is why the key design (what you cache, at what granularity, for how long) matters more than the cache product.

CDNs and static assets

A CDN caches responses at edge locations near users. The cache key is normally the URL plus any request headers named in Vary; a Vary: Cookie makes almost every request unique and kills the hit ratio. An origin shield is a designated mid-tier cache that edges ask before your origin, so a cache miss across hundreds of edges becomes one origin request. Freshness comes from headers; purging by URL or tag removes content early. Signed URLs (or S3 presigned URLs) let the CDN serve private files to whoever holds an expiring signature.

# HTML shell: always revalidate (cheap 304 with ETag)

# shared API response: CDN may keep 60 s, then serve stale for 30 s while refetching

The static-asset strategy is content-hashed file names with year-long TTLs, plus a short-lived HTML entry point that references them; a deploy changes the names, so nothing needs purging. Spring Boot does the fingerprinting with spring.web.resources.chain.strategy.content.enabled=true. Images are resized and re-encoded at the edge or by a pipeline into a few fixed sizes; video is segmented for adaptive-bitrate streaming (HLS or DASH) so the segments cache like any static file. Keep off the CDN, or mark private, anything personalised, anything behind authentication without a key that includes the user, and all writes.

Read replicas and replication lag

Replicas scale reads and give a failover candidate, but asynchronous replication lags, normally by milliseconds and sometimes by seconds under load. The visible bug is read-your-own-writes: a user saves a profile, the next page reads a replica, and the old value appears. Mitigations: read from the primary for that user for a few seconds after a write; read from the primary for anything the user just edited; or record the primary's log position at write time and read only from a replica that has caught up to it.

Definition · BackpressureA signal from a slower downstream stage that tells upstream stages to slow down, buffer, or reject. In a queue-based design the signal is the backlog itself: depth or consumer lag that keeps growing means producers outpace consumers, and something must scale out, shed load, or push back to callers.

Queues also level load: a spike of 10,000 orders a minute becomes a backlog that workers drain at a steady rate instead of a database melting. Queue depth (or consumer lag) is the backpressure signal: alert on its growth and use it as the autoscaling trigger for workers, since CPU on an idle-waiting worker says nothing.

System Design III: Data at Scale

50m video45m practice

Replication copies data for availability and read scale; partitioning splits it for write scale and size. Each choice fixes which failures you survive, which queries stay cheap, and which consistency guarantees you can still offer, and the shard key is the one decision that is almost impossible to undo.

Replication: leaders, quorums and fencing

ModelWrites go toTypical failure modeConflict handling
Single-leaderOne leader; followers replay its logFailover loses writes not yet replicated (async); two leaders after a bad failoverNone needed: the leader orders all writes
Multi-leaderA leader per region or deviceConcurrent edits to the same row in two regionsLast-write-wins (loses data), merge functions, CRDTs
Leaderless (quorum)Any w of n replicas; reads ask rStale reads when w + r ≤ n or during sloppy quorumsVersion vectors, read repair, last-write-wins

Synchronous replication waits for a follower before acknowledging, so an acknowledged write survives the leader's loss, at the cost of latency and of stalling when that follower is slow; asynchronous is fast and can lose the tail of the log on failover. Most systems use one synchronous follower and the rest asynchronous. With n = 3, w = 2, r = 2, every read quorum overlaps every write quorum (w + r > n), so a read reaches at least one replica with the latest acknowledged write.

Definition · Split-brain and fencingSplit-brain is two nodes both believing they are leader, typically after a network partition or a long GC pause outlasting a lease. A fencing token is a number that increases with every leadership grant; storage rejects any write carrying a token lower than one it has already seen, so the stale leader's writes bounce even though it does not know it was replaced.

Partitioning and consistent hashing

Partition by key range (efficient range scans, but sequential keys such as timestamps pile onto one partition), by hash (even spread, no range scans), or by directory (a lookup service maps each key or tenant to a shard: flexible, and the directory itself must be highly available). With plain hash(key) mod N, changing N from 10 to 11 moves about 10/11 of all keys. Consistent hashing moves only about 1/(N+1).

final class HashRing<N> {
    private final NavigableMap<Long, N> ring = new TreeMap<>();
    private final int vnodes;
    HashRing(Collection<N> nodes, int vnodes) { this.vnodes = vnodes; nodes.forEach(this::add); }

    void add(N node)    { for (int i = 0; i < vnodes; i++) ring.put(hash(node + "#" + i), node); }
    void remove(N node) { for (int i = 0; i < vnodes; i++) ring.remove(hash(node + "#" + i)); }

    N nodeFor(String key) {
        Map.Entry<Long, N> e = ring.ceilingEntry(hash(key));          // next position clockwise
        return (e != null ? e : ring.firstEntry()).getValue();        // wrap around
    }

    private static long hash(String s) {                              // MD5 for spread, not security
        try {
            byte[] d = MessageDigest.getInstance("MD5").digest(s.getBytes(StandardCharsets.UTF_8));
            return ByteBuffer.wrap(d).getLong();
        } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}

Choose a shard key with high cardinality, even access, and present in most queries (tenant id, user id). A hot key (a celebrity, a flash-sale product) overloads one shard whatever the scheme; split it with a suffix (product#0…product#7) and merge on read, or cache it. Resharding is why the choice is near-permanent: data layout, unique constraints, and every query's routing depend on the key. Pre-splitting into many logical partitions (say 1,024) mapped onto fewer physical nodes lets you move whole partitions later instead of rehashing rows.

Cross-shard work and secondary indexes

A query without the shard key must scatter-gather: ask every shard and merge. Its latency is the slowest shard's, so tail latency grows with shard count. Cross-shard transactions need two-phase commit (a blocking coordinator) or a saga; the better fix is a key that keeps each transaction on one shard. A local secondary index lives with each partition: writes stay local, queries by that index scatter. A global index is partitioned by the indexed value: reads hit one partition, but each write touches several, so global indexes are usually updated asynchronously and can be briefly stale.

CAP, PACELC and the consistency you actually need

CAP: during a network partition, a replicated store must either refuse some requests (consistency) or answer them with possibly stale data (availability). PACELC adds the normal case: else, trade latency against consistency. A single-leader Postgres with a synchronous standby is PC/EC; Cassandra reading and writing at ONE is PA/EL, and raising both to QUORUM buys consistency with latency; DynamoDB offers eventually consistent reads by default and strongly consistent reads on request.

  • Linearizable: behaves like one copy; once a write completes, every later read sees it. Needed for unique usernames, locks, and balance checks before a debit.
  • Causal: effects never appear before their causes (a reply never shows before the message). Enough for comments and chat.
  • Eventual: replicas converge once writes stop. Fine for like counts, view counts and recommendations.

Consensus, exactly-once, analytics and deletion

Raft in one paragraph: nodes are followers until an election timeout (randomised) fires; a candidate asks for votes for a new term and wins with a majority, and nodes only vote for candidates whose log is at least as up to date as their own. The leader appends client commands to its log and replicates them; an entry is committed once a majority store it. Five nodes tolerate two failures. Do not build this: use etcd (behind Kubernetes), ZooKeeper (which uses its own ZAB protocol), or Kafka's KRaft controller quorum, and take leader election and locks from them.

Exactly-once delivery over an unreliable network is not achievable; exactly-once effect is: at-least-once delivery plus an idempotent consumer that records the message id in the same transaction as its effect, or Kafka transactions for read-process-write within Kafka. Analytics does not belong on the OLTP database: time-series data goes to a store built for it (TimescaleDB, InfluxDB, Prometheus for metrics); raw files land in a data lake on object storage, curated tables in a warehouse. CDC (Debezium reading the write-ahead log) streams every committed change to Kafka and on to both, with no dual writes. Retention is cheapest with time partitions: dropping last year's partition is instant, deleting its rows is not. GDPR erasure must reach every copy (shards, caches, search indexes, the warehouse, compacted Kafka topics via tombstones, and backups by expiry or crypto-shredding), which is far easier when data is partitioned by user id and a data inventory lists where each user's data lives.

What breaks in productionSharding by creation date sends every new write to the newest shard. Failover on an asynchronous replica silently loses the last seconds of acknowledged orders. A lock held in Redis without a fencing token lets a paused process wake up and write after its lease has been handed to someone else.

Case Study: URL Shortener & Distributed Rate Limiter

50m video60m practice

A URL shortener is a read-heavy key-value lookup whose hard decisions are key generation and keeping the redirect fast while still counting clicks. A distributed rate limiter is a tiny piece of shared state whose hard part is atomicity and deciding what happens when that state is unreachable.

Shortener: requirements and estimation

Functional: create a short link (optionally with a custom alias and expiry), redirect, and report clicks. Non-functional: 100:1 reads to writes, 100 M new URLs a month, redirects under 100 ms, highly available reads; a lost click event is tolerable, a wrong redirect is not.

Worked exampleWrites: 100 M ÷ 2.6 M seconds per month ≈ 40 per second (≈ 120 at a 3× peak). Reads: ≈ 4,000 per second, ≈ 12,000 at peak. Five years: 100 M × 60 = 6 billion links; at roughly 500 bytes per row including indexes, about 3 TB. Key length: 62⁶ ≈ 5.7 × 10¹⁰ and 62⁷ ≈ 3.5 × 10¹² (7 characters leave ample headroom). Hot set: caching the most-clicked 20% of one month's links is 20 M × 500 B ≈ 10 GB, which fits in one Redis node.
POST   /api/urls            {"longUrl": "...", "alias": "spring-sale", "expiresAt": "..."}  → 201 {"key", "shortUrl"}
GET    /{key}               → 302 Location: longUrl   (404 if unknown, 410 if expired)
GET    /api/urls/{key}/stats → clicks by day, referrer, country
DELETE /api/urls/{key}       → 204

301 vs 302: a 301 is permanent and browsers may cache it indefinitely, so repeat clicks never reach you: less load, but no click counts and no way to change or expire the destination for that browser. A 302 (or 307) is not cached by default, so every click is counted. Choose 302 when analytics or expiry matter; if load forces caching, a 302 with a short Cache-Control: max-age bounds the staleness.

Distributed rate limiter

Per API key: a sustained rate with short bursts, one limit across all instances, negligible added latency. A token bucket fits (the algorithm comparison is in L355). The naive Redis version races: two instances GET 99, both see room under a limit of 100, both allow. Another classic bug is INCR then EXPIRE as separate calls; a crash between them leaves a key with no TTL and a client blocked forever. A Lua script runs atomically on the Redis server:

Algorithm · Token bucket
  1. Refill: tokens = min(capacity, tokens + elapsed × rate).
  2. If tokens ≥ cost, subtract cost and allow; otherwise reject.
  3. Store tokens and timestamp with a TTL equal to the time to refill fully.
-- token_bucket.lua   KEYS[1] = bucket key; ARGV = capacity, refill per second, cost
local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local t = redis.call('TIME')                          -- Redis clock: no app-server skew
local now = t[1] * 1000 + math.floor(t[2] / 1000)
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return { allowed, math.floor(tokens) }
@Component
class RedisRateLimiter {
    @SuppressWarnings("rawtypes")
    private static final RedisScript<List> SCRIPT =
        RedisScript.of(new ClassPathResource("token_bucket.lua"), List.class);
    private final StringRedisTemplate redis;
    RedisRateLimiter(StringRedisTemplate redis) { this.redis = redis; }

    @SuppressWarnings("unchecked")
    Decision tryAcquire(String apiKey, Plan plan) {
        try {
            List<Long> r = redis.execute(SCRIPT, List.of("rl:{" + apiKey + "}"),
                String.valueOf(plan.capacity()), String.valueOf(plan.refillPerSecond()), "1");
            return new Decision(r.get(0) == 1L, r.get(1));
        } catch (RedisConnectionFailureException e) {
            return plan.failOpen() ? Decision.allowUnmetered() : Decision.reject();
        }
    }
}

Redis down: fail open or closed? Failing closed turns a Redis outage into a full API outage; failing open removes protection exactly when something is already wrong. A common split: fail open (with a per-instance in-memory limiter at limit ÷ instances as a fallback) for general traffic, fail closed for security limits such as login and OTP attempts. Sharding is natural: one key per client spreads across Redis Cluster slots, and the script touches one key so it never crosses slots. At extreme scale, count locally in each instance and sync to Redis every 100 ms or so, accepting overshoot of up to instances × sync interval × rate. Tell clients where they stand with 429 Too Many Requests, Retry-After, and the remaining-quota headers (RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset from the IETF draft, or the older X-RateLimit-* names).

Case Study: E-Commerce Checkout & Payments

50m video60m practice

Checkout is the design where correctness beats latency: never oversell, never charge twice, and never lose track of money. The tools are atomic inventory updates, idempotency at every hop, a saga with a clear pivot point, and reconciliation against the payment provider as the final word.

Requirements and the domain

No double charges, no overselling, every payment matched to an order, and a checkout that keeps working when recommendations, reviews or loyalty points are down (they are called with tight timeouts and fallbacks, or not called on the checkout path at all). The domain splits into cart (cheap, mutable, can live in Redis), inventory (available and reserved quantities per SKU), pricing and promotions (computed server-side, never trusted from the client), tax (often an external service), order (the record of what was bought at what price), payment, and fulfilment.

Inventory correctness and the flash sale

The naive version reads available, checks it in Java, and writes it back: two buyers read 1, both buy, stock goes to −1. Three correct options:

  • Pessimistic lock: SELECT … FOR UPDATE on the inventory row, then update. Correct, simple, and serialises buyers of the same SKU.
  • Optimistic / conditional update: one atomic statement, with zero rows updated meaning "sold out".
  • Reservation table with expiry: decrement and insert a hold in one transaction; a sweeper returns holds that were never paid.
UPDATE inventory SET available = available - :qty
WHERE sku = :sku AND available >= :qty;                  -- 0 rows: sold out, no race

INSERT INTO reservations (id, sku, qty, order_id, status, expires_at)
VALUES (:id, :sku, :qty, :orderId, 'HELD', now() + interval '15 minutes');   -- same transaction

WITH expired AS (
  DELETE FROM reservations WHERE status = 'HELD' AND expires_at < now() RETURNING sku, qty)
UPDATE inventory i SET available = i.available + e.qty
FROM (SELECT sku, sum(qty) AS qty FROM expired GROUP BY sku) e WHERE i.sku = e.sku;

A flash sale breaks all three in a new way: 50,000 buyers for 1,000 units all queue on one row lock, transactions time out, the connection pool drains, and the whole shop goes down, not only the sale item. The answer is admission before the database: a waiting room or queue that lets through roughly as many buyers as there are units (plus a margin for abandonment), an atomic Redis DECR as a front gate, or inventory split across several sub-rows so locks spread.

Payment integration and webhooks

Never let card numbers touch your servers. With the provider's hosted fields or payment page, the browser sends card data straight to the provider and you receive a token, which keeps your PCI DSS scope minimal. Authorize then capture: authorization reserves funds on the card at checkout; capture moves them later, typically at shipment, and an uncaptured authorization can be voided instead of refunded. 3-D Secure may send the customer through a bank challenge and back via redirect, so the result arrives asynchronously, and the webhook, not the browser redirect, is the reliable signal.

@Component
class WebhookVerifier {
    private static final Duration TOLERANCE = Duration.ofMinutes(5);
    private final byte[] secret;
    private final Clock clock;
    WebhookVerifier(@Value("${payments.webhook-secret}") String secret, Clock clock) {
        this.secret = secret.getBytes(StandardCharsets.UTF_8); this.clock = clock;
    }

    void verify(String rawBody, long timestampSeconds, String signatureHex) {
        Instant sent = Instant.ofEpochSecond(timestampSeconds);
        if (Duration.between(sent, clock.instant()).abs().compareTo(TOLERANCE) > 0)
            throw new InvalidWebhook("stale timestamp");                         // replay window
        byte[] expected = hmac(timestampSeconds + "." + rawBody);
        if (!MessageDigest.isEqual(expected, HexFormat.of().parseHex(signatureHex)))
            throw new InvalidWebhook("bad signature");                           // constant-time compare
    }
    private byte[] hmac(String data) {
        try {
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(new SecretKeySpec(secret, "HmacSHA256"));
            return mac.doFinal(data.getBytes(StandardCharsets.UTF_8));
        } catch (GeneralSecurityException e) { throw new IllegalStateException(e); }
    }
}

Follow your provider's documented signing scheme exactly; the shape above (HMAC-SHA256 over timestamp and raw body) is a common one. Verify against the raw body, before JSON parsing reformats it. Webhooks are delivered at least once and in any order: deduplicate by event id, and apply them to a payment state machine that only moves forward, so a late "authorized" after "captured" is ignored. When in doubt, fetch the current state from the provider's API. Finally, reconcile daily against the provider's settlement reports: their ledger is the source of truth for money, and every charge must match exactly one order.

Idempotency end to end

Definition · Idempotency keyA client-chosen unique value sent with a request (Idempotency-Key header) so the server can recognise a retry and return the original result instead of performing the operation again.

Three layers: the client key on POST /checkout, stored with a hash of the request and the final response (same key and same body returns the stored response; same key with a different body is rejected; a key still in progress returns 409); the provider key, derived from the order id and attempt, so retrying the charge call after a timeout never charges twice; and an internal dedupe table of processed webhook and message ids, written in the same transaction as their effect.

CREATE TABLE idempotency_keys (
  key          TEXT PRIMARY KEY,
  request_hash TEXT NOT NULL,
  status       TEXT NOT NULL,             -- IN_PROGRESS | DONE
  response     JSONB,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);  -- INSERT ... ON CONFLICT (key) DO NOTHING decides who processes the request

The checkout saga and its pivot

This is the orchestrated saga from L414–L415: the orchestrator records each step's outcome, and each participant is idempotent. The worst case is "charged but order failed": money captured, order write failed or timed out. Forward recovery retries the confirmation; if it keeps failing, the saga parks in a manual-intervention queue with an alert, where operations can complete or refund it. Reconciliation catches whatever slipped past both.

Synchronous on the checkout request: price, tax, reservation, authorization (including 3-D Secure), order creation. Deferred: capture at shipment, emails, invoices, loyalty points, analytics, search indexing. Read models are separate: an order-history projection per customer and an admin search index fed by events or CDC, so neither queries the transactional tables.

What breaks in productionA retry after a payment timeout without a provider idempotency key charges the customer twice. A webhook handler that parses JSON before verifying the signature, or verifies a re-serialised body, either accepts forgeries or rejects every real event. Trusting the browser's 3-D Secure redirect as proof of payment lets a customer who closes the tab end up with a paid order you never confirm.

  2. Add the idempotency-key table and a filter around POST /checkout; test a retry with the same body, a different body, and one still in progress.
  3. Build the webhook endpoint with WebhookVerifier, event-id dedupe and a forward-only payment state machine; send events out of order and twice.
  4. Write the saga orchestrator for the five steps with compensations, and simulate a failure at each step, including after capture.

Case Study: Real-Time Chat & Notifications

50m video60m practice

Chat is a routing problem on top of a storage problem: millions of long-lived connections spread across nodes, a backplane that finds the node holding each recipient, and a write-heavy message log partitioned by conversation. Delivery is at-least-once everywhere, so every message carries an id the client can deduplicate.

Requirements and transport

One-to-one and group messages, delivery and read receipts, presence, offline delivery with mobile push, and full history. Messages must never be lost once acknowledged; presence may be a few seconds stale.

TransportDirectionStrengthsWeaknesses
WebSocketFull duplexLow overhead per message; one connection for send and receiveStateful connections to balance; some proxies interfere
Server-Sent EventsServer to clientPlain HTTP, automatic reconnect with Last-Event-IDSends need separate HTTP requests; text only
Long pollingSimulated pushWorks through anythingA request per message batch; higher latency and load

Use WebSocket, with long polling (or SSE plus POST for sends) as the fallback when the upgrade fails; SockJS in Spring provides that fallback chain for browsers. Mobile apps generally use WebSocket in the foreground and push notifications in the background.

Connection scaling and routing

With non-blocking I/O (Netty, or Tomcat's NIO connector behind Spring WebSocket), an idle connection costs a socket, buffers and session objects, not a thread, so a single JVM can hold tens of thousands of connections; the exact figure depends on buffer sizes and per-session state, so measure rather than assume. With one platform thread per connection the limit is threads and their stacks, which is why virtual threads or an event-loop server matter here. Raise the file-descriptor limit and watch heap per session. The routing problem follows: user A is connected to pod 1 and user B to pod 3, so pod 1 must find B.

Sticky sessions or consistent hashing on user id can put a user's connections on a predictable node, but both members of a conversation still land on different nodes, so a backplane is needed either way. A connection registry (conn:{user} → set of node ids, refreshed by heartbeat) plus one channel per node keeps each node's traffic proportional to its own users.

The pub/sub backplane

Redis pub/sub is sub-millisecond and simple, but fire-and-forget: a node that is restarting misses messages published meanwhile. That is acceptable when the message store is the source of truth and clients fetch "everything after my last id" on reconnect. Kafka is durable and replayable with per-partition ordering, at higher latency and with the awkwardness that consumers are assigned partitions, not users; it fits better as the pipeline to push notifications, search and analytics than as the per-message routing hop. Redis Streams sit in between.

@Controller
class ChatController {
    private final MessageStore store;
    private final Router router;
    ChatController(MessageStore store, Router router) { this.store = store; this.router = router; }

    @MessageMapping("/send")                                   // client SENDs to /app/send
    void send(@Payload SendMessage cmd, Principal from) {
        ChatMessage saved = store.append(cmd.conversationId(), from.getName(), cmd.clientMsgId(), cmd.text());
        router.deliver(saved);                                 // append is idempotent on clientMsgId
    }
}

@Component
class Router {
    private final StringRedisTemplate redis;
    private final Members members;
    private final PushQueue push;
    private final Json json;
    Router(StringRedisTemplate redis, Members members, PushQueue push, Json json) {
        this.redis = redis; this.members = members; this.push = push; this.json = json;
    }

    void deliver(ChatMessage m) {
        for (String user : members.of(m.conversationId())) {
            Set<String> nodes = redis.opsForSet().members("conn:" + user);
            if (nodes == null || nodes.isEmpty()) { push.enqueue(user, m); continue; }   // offline
            for (String node : nodes) redis.convertAndSend("node:" + node, json.write(new Envelope(user, m)));
        }
    }
}
// each node subscribes to "node:{its id}" and calls
// messagingTemplate.convertAndSendToUser(envelope.user(), "/queue/messages", envelope.message())

For large groups, group recipients by node and publish one envelope per node with the list of users, instead of one per member. Spring's simple broker is in-memory per node, which is why routing between nodes is done here explicitly (the alternative is a STOMP broker relay to RabbitMQ).

Presence, storage and history

Presence: clients heartbeat every 30 seconds; the server sets presence:{user} with a 90-second TTL, and expiry means offline, so a crashed node needs no cleanup. Fan presence out only to users who have that conversation open, not to every contact. After a deploy, every client reconnects at once: the thundering herd. Clients must reconnect with exponential backoff plus random jitter, servers should drain connections in batches during rollout, and connection admission should be rate-limited.

Storage is write-heavy and read by conversation, newest first. Partition by conversation id and order by a per-conversation monotonic sequence, or a time-sortable id (Snowflake, ULID) when a central sequence is too costly:

CREATE TABLE messages (                         -- Cassandra
  conversation_id uuid,
  message_id      bigint,                       -- time-sortable, unique
  sender_id       uuid,
  client_msg_id   uuid,                         -- for idempotent retries
  body            text,
  PRIMARY KEY ((conversation_id), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
-- scrollback: WHERE conversation_id = ? AND message_id < ? LIMIT 50

Very large or very old conversations add a time bucket (month) to the partition key so no partition grows without bound.

Offline push, delivery semantics and abuse

Definition · At-least-once with client dedupeEvery hop may retry, so a message can arrive twice. The client generates a clientMsgId when composing; the server stores it under a uniqueness constraint (a retry returns the existing message), and the receiving client ignores ids it has already rendered. The effect is exactly-once display without exactly-once delivery.

A device registry maps users to push tokens per platform. The push worker fans out to FCM (Android) and APNs (iOS), retries transient failures with backoff, and deletes tokens the provider reports as invalid or unregistered. Before sending it applies preferences: muted conversations, mentions-only settings, and quiet hours evaluated in the user's time zone, collapsing a burst into one notification. Receipts are their own event stream: "delivered" when a device acknowledges, "read up to message N" as a watermark per conversation, rather than one event per message. Abuse prevention: per-user and per-new-account send rate limits, message size limits, block lists enforced on the server, and asynchronous spam scoring that can retract messages.

Build the core with Spring WebSocket and STOMP (L465 goes further), Redis for the registry and backplane, and Postgres or Cassandra for messages. Load-test with Gatling or k6 WebSocket scenarios: ramp to 10,000 concurrent connections, send a steady message rate, and record p99 end-to-end delivery latency, heap per connection, and reconnect behaviour when a pod is killed.

What breaks in productionDelivering over the socket before persisting means a node crash loses acknowledged messages. A deploy that restarts every pod at once, with clients reconnecting without jitter, produces a reconnect storm that looks like an outage. Stale push tokens that are never deleted waste most of the push budget and can get the sender throttled.
