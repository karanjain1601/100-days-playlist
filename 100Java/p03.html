Phase 3 · Days 81–98 · Lessons 81–98

Functional Java, Lambdas & Streams

Phase 3 teaches you to pass behaviour around as values and to express data processing as declarative stream pipelines: lambdas, method references, the java.util.function toolkit, and the Streams API from its pipeline model through collectors, parallelism, Optional and gatherers. It builds directly on the collections and generics of Phase 2, and the functional style it establishes is what the I/O APIs of Phase 4, CompletableFuture in Phase 5 and most of Spring's APIs assume you already read fluently.

By the end of this phase you can

  • Turn anonymous classes into lambdas and method references, and explain target typing, effectively final capture, lexical this and the invokedynamic translation.
  • Pick the right standard functional interface, including primitive specializations, compose functions and predicates into readable rules, and handle checked exceptions with a reusable ThrowingFunction or Result.
  • Predict which elements a pipeline reads, in what order and how often, from laziness, fusion, short-circuiting and stateful operations.
  • Write reductions and collectors that are correct in parallel, including multi-level groupingBy reports and a custom Collector with a tested combiner.
  • Decide from measurements, not guesses, whether a parallel stream helps, and keep parallel stream work off request-handling threads.
  • Use Optional as a return type only, and avoid the eager orElse, get() and field/parameter anti-patterns.
  • Build a streams-only analytics engine over a million rows, and write custom gatherers for windows, running totals and stateful stops on Java 24+.

L81 · DAY 81

Lambda Expressions: Syntax, Capture & Semantics

45m video45m practice

A lambda is not a shorter anonymous class. It is a value whose functional interface type comes from context, whose body lives in the scope of the enclosing method, and whose implementation the JVM builds on first use through invokedynamic. The rules about types, capture and this all follow from those three facts.

From anonymous class to lambda

An anonymous class implementing a one-method interface (L49) spells out the interface, the method name and the parameter types, all of which the compiler can infer. Delete them and what remains is a lambda.

// 1. anonymous class
names.sort(new Comparator<String>() {
    @Override public int compare(String a, String b) {
        return Integer.compare(a.length(), b.length());
    }
});
// 2. keep parameters and body
names.sort((String a, String b) -> { return Integer.compare(a.length(), b.length()); });
// 3. types come from Comparator<String>; 4. one expression needs no braces or return
names.sort((a, b) -> Integer.compare(a.length(), b.length()));
// 5. often a library combinator says it better (L45, L82)
names.sort(Comparator.comparingInt(String::length));

This works only because Comparator is a functional interface with exactly one abstract method (L41); the equals it redeclares doesn't count. With one candidate method, the shortening is unambiguous.

Every syntax form

Runnable hello                          = () -> System.out.println("hi");
Function<String, Integer> len           = s -> s.length();
BinaryOperator<Integer> add             = (a, b) -> a + b;
BinaryOperator<Integer> addTyped        = (Integer a, Integer b) -> a + b;
BiFunction<String, String, String> join = (var a, var b) -> a + "," + b;   // Java 11
Comparator<String> byLenThenAlpha       = (a, b) -> {
    int c = Integer.compare(a.length(), b.length());
    return c != 0 ? c : a.compareTo(b);
};
  • Parentheses can be dropped only for exactly one untyped parameter.
  • All or nothing: parameters are all implicit, all typed, or all var; (var a, b) doesn't compile. var exists so you can write (@Nonnull var s) or (final var s) without the full type.
  • Bodies: an expression body is its own result; a block body must return on every path for a non-void method. A statement expression such as list.add(x) is both void- and value-compatible, so it fits Runnable and Supplier<Boolean>.

Target typing

Definition · target type

A lambda has no type of its own. It may appear only in an assignment, invocation, return or cast context whose expected type is a functional interface; that target type becomes the lambda's type, and the compiler checks arity, parameter types, return type and checked exceptions against the interface's single abstract method (JLS §15.27.3).

Callable<String> c = () -> "done";        // same text, two different types
Supplier<String> s = () -> "done";
// Object o = () -> "done";               // error: Object is not a functional interface
// var v = () -> "done";                  // error: lambda needs an explicit target type
Object o = (Supplier<String>) () -> "done";        // a cast supplies one
Runnable r = (Runnable & Serializable) () -> {};   // intersection cast

Overload resolution uses the lambda's shape: executor.submit(() -> work()) picks submit(Callable) if work() returns a value and submit(Runnable) if it is void. An implicitly typed lambda cannot help choose between overloads, because its body can't be typed until the parameter types are known (JLS §15.12.2.2). With overloads run(Function<String, Integer>) and run(ToIntFunction<String>), run(s -> s.length()) is ambiguous, while run((String s) -> s.length()) and run(String::length) both choose ToIntFunction.

Capturing locals: effectively final, and why

int min = 2;
names.removeIf(s -> s.length() < min);      // fine: min is never reassigned
int count = 0;
// names.forEach(n -> count++);             // error: must be final or effectively final
long longOnes = names.stream().filter(n -> n.length() > min).count();   // the real fix

A lambda may read a local or parameter only if it is final or effectively final, never assigned after initialisation (JLS §4.12.4). The captured value is copied when the lambda is created: javap shows the body above compiled to private static boolean lambda$main$1(int, String), with min as the first argument. The lambda can outlive the stack frame (stored in a field, run on another thread), so allowing writes would mean moving locals to the heap and accepting races on them. Fields are not restricted, because they are reached through a captured this. Smuggling writes through an int[] or AtomicInteger holder compiles, and brings back the shared mutable state the rule kept out.

this and scope

An anonymous class body is a new class: this is the anonymous instance and its members may shadow outer names. A lambda body is lexically scoped: this means the enclosing instance, and a lambda parameter may not reuse the name of a local in scope.

class Greeter {
    private final String name = "outer";
    @Override public String toString() { return "Greeter"; }
    void demo() {
        Runnable lambda = () -> System.out.println(this + " " + name);
        Runnable anon = new Runnable() {
            private final String name = "inner";             // legal shadowing
            @Override public void run() { System.out.println(this + " " + name); }
        };
        lambda.run();                 // Greeter outer
        anon.run();                   // Greeter$1@1b6d3586 inner
        String label = "x";
        // Function<String, String> f = label -> label;   // error: already defined
    }
}

A lambda captures this only if its body uses an instance member. An anonymous class in an instance method has historically always held a reference to the enclosing object.

Under the hood: invokedynamic, not $1 classes

Anonymous classes produce Sorter$1.class files. Lambdas produce none: each body becomes a private synthetic method (static unless it uses this), and the expression becomes an invokedynamic instruction.

$ javap -c -p Sorter
  20: invokedynamic #24,  0   // InvokeDynamic #0:compare:()Ljava/util/Comparator;
  32: invokedynamic #32,  0   // InvokeDynamic #1:test:(I)Ljava/util/function/Predicate;
  private static boolean lambda$main$1(int, java.lang.String);
  private static int lambda$main$0(java.lang.String, java.lang.String);

The generated class is a hidden class (JEP 371) with a name like Sorter$$Lambda/0x000002a01b000a08. Choosing the strategy at run time lets the JDK change how lambdas are built without anyone recompiling. On current JDKs a non-capturing lambda evaluates to the same object each time and a capturing one allocates; the JLS guarantees neither, so never compare lambdas with == or rely on their equals.

Serialization, debugging and readability

Serialization. A lambda is serializable only if its target type is, hence (Runnable & Serializable). It is written as a SerializedLambda naming the synthetic method, and those names depend on the compiler and on source order, so an unrelated edit can break old data. Oracle's tutorial calls serializing lambdas "strongly discouraged" (see L102).

Debugging. Stack traces show the synthetic method and the right line, e.g. Sorter.lambda$main$2(Sorter.java:9); the hidden-class frame is omitted unless you run with -XX:+UnlockDiagnosticVMOptions -XX:+ShowHiddenFrames. IDEs can break inside a lambda on a line that holds several.

Readability. Effective Java Item 42: one line is ideal, three a reasonable maximum. Use a named method and a method reference when the body branches, lambdas nest, the parameter types aren't obvious, or the lambda exists only for a side effect. orders.removeIf(this::isExpired) reads as a sentence.

What breaks in production
  • Unregistering a fresh lambda. bus.unregister(e -> onEvent(e)) passes a new object, nothing is removed, and the listener leaks. Keep the reference in a field. this::onEvent evaluated twice is also two objects.
  • Accidental capture of this. One field access keeps the whole enclosing object alive; in a static cache or scheduler, a request-scoped object lives forever.
  • Mutable holders. total[0] += x inside parallelStream().forEach gives a different wrong answer per run (L95).

  3. Run Greeter, predicting each line first. Then try the shadowing lambda and read the error.
  4. Return a non-capturing and a capturing Supplier from factory methods; print == for two calls of each and getClass().isHidden().
  5. Build an event bus with register/unregister, reproduce the unsubscribe leak, and fix it.

Method References: All Four Kinds

35m video40m practice

A method reference is a lambda whose whole body is one call to an existing method, written by naming the method instead of the call. The four kinds differ in one question: where does the receiver come from, and when is it evaluated?

The four kinds at a glance

Definition · method reference

An expression X::name (or X::new) that, like a lambda, is target-typed to a functional interface. The compiler finds the method named name whose parameters fit the interface's function type; the resulting object calls it (JLS §15.13).

KindExampleEquivalent lambdaReceiver
StaticInteger::parseInts -> Integer.parseInt(s)none
Bound instanceSystem.out::printlnx -> System.out.println(x)fixed, evaluated once
Unbound instanceString::toUpperCases -> s.toUpperCase()first argument
ConstructorArrayList::new, String[]::new() -> new ArrayList<>(), n -> new String[n]new object

Static and bound references

Function<String, Integer> parse = Integer::parseInt;            // static
Comparator<Integer> cmp          = Integer::compare;             // static, two args
Consumer<Object> print           = System.out::println;          // bound: receiver = System.out
String prefix = "order-";
Function<String, String> tag     = prefix::concat;               // bound: receiver = prefix
Predicate<String> known          = Set.of("EU", "US")::contains; // bound to a new Set
Runnable flush                   = this::flushBuffers;           // bound to the current object

A bound reference has a receiver expression on the left. That expression is evaluated once, when the reference is created, not each time it is called (JLS §15.13.3). Three consequences follow, and the lambda equivalents behave differently on all three:

  • Null fails early. javac emits Objects.requireNonNull(receiver) before the invokedynamic, so prefix::concat with a null prefix throws at creation. s -> prefix.concat(s) throws only when called.
  • The value is frozen. System.out::println keeps the PrintStream that was current at creation; a later System.setOut doesn't affect it, while the lambda reads System.out on every call.
  • Side effects happen once. In Set.of("EU", "US")::contains the set is built once. s -> Set.of("EU", "US").contains(s) builds it on every call.

Unbound references: the first parameter becomes the receiver

When the left side is a type and the method is an instance method, there is no receiver yet. The first parameter of the function type becomes the receiver, and the remaining parameters become the arguments. The same text can therefore mean different things for interfaces of different arity.

The examples use record Order(String id, long cents) {} and a List<Order> orders.

Function<String, String> upper            = String::toUpperCase;       // s.toUpperCase()
Comparator<String> ci                     = String::compareToIgnoreCase; // a.compareToIgnoreCase(b)
BiFunction<String, Integer, Character> at = String::charAt;            // s.charAt(i)
Function<Order, Long> cents               = Order::cents;              // accessor, unbound
orders.sort(Comparator.comparing(Order::cents).reversed());

That last line is also a practical reason to prefer method references: Comparator.comparing(o -> o.cents()).reversed() does not compile, because the receiver of .reversed() is typed before the lambda, so o is inferred as Object. Order::cents names its type, so inference has something to work with.

Constructor, array-constructor and super references

Supplier<List<String>> fresh            = ArrayList::new;   // ArrayList()
Function<Integer, List<String>> sized   = ArrayList::new;   // ArrayList(int initialCapacity)
Function<String, BigDecimal> money      = BigDecimal::new;  // BigDecimal(String)
IntFunction<String[]> arr               = String[]::new;    // n -> new String[n]
String[] ids = orders.stream().map(Order::id).toArray(String[]::new);
Map<String, List<Order>> byId = new TreeMap<>();
byId.computeIfAbsent("A", k -> new ArrayList<>());           // the key is ignored

The constructor is chosen by the function type, exactly like an overloaded call: Supplier selects the no-arg constructor, Function<Integer, …> the int one. That is a trap in computeIfAbsent: with String keys, ArrayList::new doesn't compile (there is no ArrayList(String)), but on a Map<Integer, List<Order>> it compiles and silently uses each key as an initial capacity. The lambda that ignores its key says what you mean. Array constructor references exist mostly for toArray(String[]::new) and IntFunction-based generators (L79).

super::method refers to the superclass implementation of a method from inside an override, useful when handing the inherited behaviour to someone else. For an interface default method the form is Iface.super::method.

class AuditedService extends BaseService {
    @Override void save(Order o) {
        retry(3, () -> super.save(o));      // lambda form
    }
    @Override void flush() {
        executor.submit(super::flush);      // runs BaseService.flush, not this override
    }
}

When a reference is clearer, and when it isn't

Effective Java Item 43: use the method reference where it is shorter and clearer, otherwise the lambda. References win when the method name says everything (map(Order::id), filter(Objects::nonNull), forEach(repo::save)) and when they make inference work. Lambdas win when the class name is long and the method is local (() -> action() beats VeryLongServiceName::action), when the parameter names carry meaning ((oldPrice, newPrice) -> …), when you need to reorder or fix arguments, and when you want the receiver re-read on each call.

Resolving ambiguity errors

Function<Integer, String> f = Integer::toString;
error: incompatible types: invalid method reference
    reference to toString is ambiguous
      both method toString(int) in Integer and method toString() in Integer match

An unbound and a static interpretation both fit: Integer.toString(i) (static, unboxed) and i.toString() (instance). The compiler refuses to guess. Fixes, in order of preference: name an unambiguous method (String::valueOf picks valueOf(Object), or Object::toString); write the lambda (i -> i.toString()); or give an explicit target type with a cast. The same strategy fixes overload ambiguity on the receiving side, as in the Function versus ToIntFunction example from L81: an exact method reference such as String::length carries enough type information to choose.

What breaks in production
  • Eager null receivers. Building config::get during startup, before config is injected, throws NullPointerException at that line rather than at first use. That is usually what you want, but it surprises people refactoring from a lambda.
  • Frozen receivers. currentTenant()::lookup captures the tenant at creation; stored in a singleton, every later request uses the first tenant. A lambda k -> currentTenant().lookup(k) re-reads it.
  • Silent overload changes. Adding an overload to a method that is used as a method reference can make old call sites ambiguous or select a different method, a source-incompatible change in a library.

  2. Demonstrate eager evaluation: create out::println for a PrintStream variable, then reassign System.setOut and compare a bound reference with a lambda. Repeat with a null receiver.
  3. Reproduce the Integer::toString error and fix it three ways.
  4. Sort a list of records by two keys descending with Comparator.comparing(...).thenComparing(...).reversed(); write it once with lambdas (it will fail) and once with method references.

Function, BiFunction, compose & andThen

35m video40m practice

Function<T, R> is the general shape "take one value, return another", and its two default methods turn functions into building blocks: andThen and compose glue small, testable transformations into a pipeline without writing a new class. The only thing to get right is the order they run in.

The interface, read closely

Definition · java.util.function.Function 
@FunctionalInterface
public interface Function<T, R> {
    R apply(T t);

    default <V> Function<V, R> compose(Function<? super V, ? extends T> before) {
        Objects.requireNonNull(before);
        return (V v) -> apply(before.apply(v));
    }
    default <V> Function<T, V> andThen(Function<? super R, ? extends V> after) {
        Objects.requireNonNull(after);
        return (T t) -> after.apply(apply(t));
    }
    static <T> Function<T, T> identity() { return t -> t; }
}

This is essentially the JDK source. One abstract method makes it a functional interface; the defaults don't count. Each combinator returns a new lambda that captures both functions and calls one inside the other, which matters for very long chains (see the box at the end). The wildcards are PECS from L76: after consumes our R, so it may accept any supertype of R; it produces a V, so it may return any subtype. That is why a Function<Object, String> such as String::valueOf can follow a Function<Order, Long>.

Function<String, Integer> length = String::length;
Function<Integer, Integer> square = n -> n * n;
int nine = length.andThen(square).apply("abc");   // square(length("abc")) = 9

andThen vs compose: evaluation order

f.andThen(g) runs f first, then feeds its result to g: x -> g.apply(f.apply(x)). f.compose(g) runs g first: x -> f.apply(g.apply(x)). andThen reads left to right, like a stream pipeline; compose reads like mathematical composition f∘g. Most code only ever needs andThen.

Function.identity()

identity() returns a function that returns its argument. Its main use is as the "value mapper" when a collection becomes a map keyed by some property, and as the seed when reducing a list of functions:

Map<String, Order> byId = orders.stream()
        .collect(Collectors.toMap(Order::id, Function.identity()));   // L91

List<Function<String, String>> steps =
        List.of(String::strip, String::toLowerCase, s -> s.replaceAll("\\s+", "-"));
Function<String, String> slugify = steps.stream().reduce(Function.identity(), Function::andThen);
slugify.apply("  Hello Big World ");   // "hello-big-world"

x -> x works too and is shorter; Bloch prefers it (Item 43). One difference matters: Function.identity() is typed Function<T, T>, so it cannot be passed where a UnaryOperator<T> is required. Use UnaryOperator.identity() there (L85).

BiFunction<T, U, R>

R apply(T t, U u) takes two arguments. It has andThen(Function) to post-process the result but no compose, since a single function can't produce two arguments. The collections API uses it wherever a new value is computed from a key or an old value:

Map<String, Integer> stock = new HashMap<>(Map.of("apple", 3));
stock.merge("apple", 2, Integer::sum);                       // BiFunction<Integer, Integer, Integer>
stock.computeIfPresent("apple", (k, v) -> v > 4 ? v - 4 : null);   // null removes the entry
stock.replaceAll((k, v) -> v * 10);

BiFunction<Long, Integer, Long> lineTotal = (cents, qty) -> cents * qty;
BiFunction<Long, Integer, String> shown =
        lineTotal.andThen(c -> "$%d.%02d".formatted(c / 100, c % 100));
shown.apply(1999L, 3);                                       // "$59.97"

Primitive specializations, and why they exist

Type arguments must be reference types (L77), so Function<Integer, Integer> boxes every input and output. Outside the Integer cache of -128 to 127 (L54), each box is a heap allocation. java.util.function therefore adds specializations for int, long and double, named by a fixed scheme:

Name patternShapeExample
IntFunction<R>int → RIntFunction<String[]> mk = String[]::new
ToIntFunction<T>T → intToIntFunction<String> len = String::length
IntToDoubleFunctionint → doublei -> i * 0.5
ToIntBiFunction<T, U>(T, U) → int(s, c) -> s.indexOf(c)
IntUnaryOperatorint → inti -> i + 1

There is no IntToIntFunction (that is IntUnaryOperator), no float, short, byte or char versions, and most specializations have no andThen; IntUnaryOperator does have andThen, compose and identity. The stream API is built on these: mapToInt takes a ToIntFunction, and IntStream.mapToObj takes an IntFunction (L94).

Composition as a design tool: normalise, then validate

Composition earns its place when each step is a named, separately testable function and the pipeline is assembled in one visible spot. A typical request flow is "normalise the input, then validate it":

record Signup(String email, String name) {}

@FunctionalInterface
interface Validator<T> extends Function<T, List<String>> {
    static <T, F> Validator<T> check(Function<T, F> field, Predicate<F> ok, String msg) {
        return t -> ok.test(field.apply(t)) ? List.of() : List.of(msg);
    }
    default Validator<T> and(Validator<T> next) {
        return t -> Stream.concat(apply(t).stream(), next.apply(t).stream()).toList();
    }
}

UnaryOperator<Signup> trim  = s -> new Signup(s.email().strip(), s.name().strip());
UnaryOperator<Signup> lower = s -> new Signup(s.email().toLowerCase(Locale.ROOT), s.name());
Validator<Signup> rules = Validator.<Signup, String>check(Signup::email, e -> e.contains("@"), "bad email")
        .and(Validator.check(Signup::name, n -> !n.isBlank(), "name required"));

Function<Signup, List<String>> errorsFor = trim.andThen(lower).andThen(rules);
errorsFor.apply(new Signup("  Ada@Example.COM ", " "));   // [name required]

Each rule is one line and testable alone, the order is explicit in errorsFor, and adding a rule touches nothing else. Collecting all messages instead of stopping at the first is a design choice the and method makes; L85 shows a fail-fast Result type.

What breaks in production
  • Wrong order. compose where andThen was meant gives the 95.0 instead of the 94.5 above: a pricing bug that passes any test using commuting steps.
  • Very deep chains. Every andThen wraps the previous function, so applying a chain of n functions recurses n frames deep. Reducing a list of 100,000 functions this way throws StackOverflowError on the first apply; a few thousand is fine. For long, data-driven pipelines, loop over the list instead.
  • Boxing in hot loops. Function<Integer, Integer> in a per-element loop over millions of values allocates millions of objects; use IntUnaryOperator.
  • A null in the middle. A step that returns null causes a NullPointerException in the next step, far from the cause. Steps should return values or Optional (L96), never null.

  2. Build the slug pipeline from a List read from configuration, then add a step that strips accents with java.text.Normalizer.
  3. Replace a Function<Integer, Integer> in a 10-million-iteration loop with IntUnaryOperator and compare time and allocation (use -verbose:gc for a rough view; L168 does it properly).
  4. Extend Validator with a forEach combinator that validates every element of a list field, and write tests for each rule separately.

Predicate, Consumer & Supplier

35m video40m practice

Three shapes cover most of the behaviour you pass around: a Predicate answers yes or no, a Consumer does something and returns nothing, and a Supplier produces a value only when asked. Predicates compose into business rules, consumers are side effects by definition, and suppliers are how Java spells "lazy".

Predicate<T>: test, and, or, negate, isEqual, not

Definition · Predicate

boolean test(T t), plus defaults and, or (both short-circuit like && and ||: the second predicate is not called if the first decides), negate(), and statics isEqual(Object target), which tests with Objects.equals and is therefore null-safe, and not(Predicate) (Java 11), which exists so that negating a method reference reads well.

List<String> lines = List.of("a", " ", "", "b");
lines.stream().filter(Predicate.not(String::isBlank)).toList();      // [a, b]
lines.stream().filter(Predicate.isEqual("a")).count();               // 1, no NPE on null elements
Predicate<String> shortWord = s -> s.length() < 4;
Predicate<String> longWord  = shortWord.negate();

Composing business rules

A rule that lives in one long if is hard to test and impossible to reuse. Written as named predicates it becomes data you can combine, list, log and unit-test one by one.

record Order(String customer, long cents, String country, boolean flagged) {}

Predicate<Order> large    = o -> o.cents() > 100_000;
Predicate<Order> domestic = o -> o.country().equals("US");
Predicate<Order> flagged  = Order::flagged;

Predicate<Order> needsReview = large.and(domestic.negate()).or(flagged);

Map<String, Predicate<Order>> rules = new LinkedHashMap<>();
rules.put("large-foreign", large.and(domestic.negate()));
rules.put("flagged", flagged);
Order o = new Order("c1", 250_000, "DE", false);
List<String> why = rules.entrySet().stream()
        .filter(e -> e.getValue().test(o)).map(Map.Entry::getKey).toList();   // [large-foreign]

BiPredicate<T, U> is the two-argument form, with the same and/or/negate. The JDK uses it in Files.find(start, depth, (path, attrs) -> attrs.size() > 1_000_000) (L103).

Consumer<T> and BiConsumer<T, U>

void accept(T t) returns nothing, so a consumer is useful only for its side effect: printing, saving, sending, adding to something. andThen(Consumer<? super T>) runs a second consumer on the same argument after the first. If the first throws, the second does not run, so a chain of side effects can stop half done.

Consumer<Order> audit = ord -> System.out.println("audit " + ord.customer());
Consumer<Order> save  = ord -> { /* repository.save(ord) */ };
Consumer<Order> persistAndAudit = save.andThen(audit);   // save first; no audit if save throws

Map<String, Integer> stock = new TreeMap<>(Map.of("pear", 2, "apple", 5));

Supplier<T>: deferring work until it is needed

T get() takes nothing. Passing a supplier instead of a value moves the decision about whether to compute the value to the receiver. The JDK uses this in several places where an argument is often not needed:

import java.util.logging.Logger;

Logger log = Logger.getLogger("orders");
log.fine(() -> "state: " + expensiveDump());     // built only if FINE is enabled
String name = Optional.ofNullable(cache.get(key)).orElseGet(() -> lookupDefault());  // only on a miss
String url = Objects.requireNonNull(settings.get("db.url"),
        () -> "db.url missing; keys = " + settings.keySet());   // message built only on failure
Set<String> sorted = Stream.of("b", "a").collect(Collectors.toCollection(TreeSet::new));
ThreadLocal<StringBuilder> buf = ThreadLocal.withInitial(StringBuilder::new);

The orElse versus orElseGet difference is the classic bug: orElse(lookupDefault()) calls lookupDefault() every time, even when the optional has a value (L96). The same goes for log.fine("state: " + expensiveDump()), which pays for the string even when the level is off. Log4j 2 and SLF4J 2's fluent API also accept suppliers.

For "compute once, on first use", wrap the supplier. A lambda can't hold mutable state (L81), so the memoizer is an anonymous class; synchronized makes it safe to share across threads:

static <T> Supplier<T> memoize(Supplier<? extends T> source) {
    return new Supplier<>() {
        private T value;
        private boolean done;
        @Override public synchronized T get() {
            if (!done) { value = source.get(); done = true; }
            return value;
        }
    };
}
Supplier<Map<String, String>> config = memoize(() -> loadConfigFromDisk());

Guava has Suppliers.memoize, and JDK 25 previews a StableValue API for this job (JEP 502).

UnaryOperator, BinaryOperator & Custom Functional Interfaces

35m video40m practice

The operator interfaces are Function and BiFunction with all types equal, which is exactly the shape of "transform in place" and "combine two into one". When no JDK interface fits, usually because of a third argument or a checked exception, you write your own, and checked exceptions are the case that needs a real design decision.

UnaryOperator<T> and List.replaceAll

UnaryOperator<T> extends Function<T, T> and adds only a static identity(). Its point is the narrower contract "same type in and out", which APIs that transform in place require:

List<String> names = new ArrayList<>(List.of(" ada ", "linus "));
names.replaceAll(String::strip);                         // List.replaceAll(UnaryOperator<E>)
UnaryOperator<String> trim = String::strip, upper = String::toUpperCase;
// UnaryOperator<String> both = trim.andThen(upper);    // error: andThen returns Function
UnaryOperator<String> both = trim.andThen(upper)::apply; // adapt with a method reference
names.replaceAll(both);

BinaryOperator<T>, minBy, maxBy and reduce

BinaryOperator<T> extends BiFunction<T, T, T>: two values of one type in, one out. That is the accumulator shape of reduce (L90) and the merge function of toMap (L91). Its two static factories turn a Comparator into a "keep the smaller/larger" operator.

record Order(String id, long cents) {}
List<Order> orders = List.of(new Order("a", 500), new Order("b", 1_200));

BinaryOperator<Order> bigger = BinaryOperator.maxBy(Comparator.comparingLong(Order::cents));
Optional<Order> largest = orders.stream().reduce(bigger);           // Order[id=b, cents=1200]
BinaryOperator<BigDecimal> add = BigDecimal::add;                   // unbound: a.add(b)
int total = IntStream.of(3, 4, 5).reduce(0, Integer::sum);          // IntBinaryOperator

Primitive operators mirror these: IntBinaryOperator (applyAsInt(int, int)), LongBinaryOperator, DoubleBinaryOperator, and the unary IntUnaryOperator family. Outside streams they appear in Arrays.setAll(int[], IntUnaryOperator), Arrays.parallelPrefix(int[], IntBinaryOperator) and AtomicInteger.accumulateAndGet(int, IntBinaryOperator).

Writing your own functional interface

Effective Java Item 44: use a standard interface when one fits. Write your own when none has the right arity or exception signature, or when a domain name and contract are worth having (as Comparator is, despite being structurally a ToIntBiFunction). Always annotate it @FunctionalInterface, so the compiler rejects a second abstract method, and don't overload a method on different functional interfaces in the same argument position (L81 showed the ambiguity).

@FunctionalInterface
interface TriFunction<A, B, C, R> {
    R apply(A a, B b, C c);

    default <V> TriFunction<A, B, C, V> andThen(Function<? super R, ? extends V> after) {
        Objects.requireNonNull(after);
        return (a, b, c) -> after.apply(apply(a, b, c));
    }
}
TriFunction<Long, Integer, Double, Long> gross =
        (cents, qty, taxRate) -> Math.round(cents * qty * (1 + taxRate));

Past three parameters, a record of the inputs is usually clearer than a QuadFunction.

Checked exceptions in lambdas

Function.apply declares no checked exceptions, so a lambda whose body throws one doesn't fit:

paths.stream().map(Files::readString).toList();
error: incompatible thrown types IOException in functional expression
Definition · four strategies
  1. Catch inside the lambda and rethrow unchecked (UncheckedIOException). Correct but noisy when repeated.
  2. A throwing interface plus an adapter that does the wrapping once: map(unchecked(Files::readString)).
  3. Sneaky throw: use erasure to rethrow the checked exception without declaring it. Short, and it defeats the compiler's checking.
  4. Return a result value (Result/Either): failures become data that flows down the pipeline, so one bad file doesn't abort a batch.
@SuppressWarnings("unchecked")
static <E extends Throwable> RuntimeException sneaky(Throwable t) throws E {
    throw (E) t;   // E is inferred as RuntimeException at the call site; the cast is erased
}
// usage: catch (IOException e) { throw sneaky(e); }   -- IOException escapes undeclared

Sneaky throws are what Lombok's @SneakyThrows generates. The cost is that callers can no longer write catch (IOException e) around the call (the compiler says it is never thrown), and code that inspects exception types gets surprised (see the box below).

A reusable ThrowingFunction and Result

@FunctionalInterface
public interface ThrowingFunction<T, R, E extends Exception> {
    R apply(T t) throws E;

    static <T, R> Function<T, R> unchecked(ThrowingFunction<? super T, ? extends R, ?> f) {
        return t -> {
            try {
                return f.apply(t);
            } catch (Exception e) {
                throw switch (e) {
                    case RuntimeException re -> re;
                    case IOException io -> new UncheckedIOException(io);
                    case InterruptedException ie -> {
                        Thread.currentThread().interrupt();     // never swallow an interrupt
                        yield new IllegalStateException(ie);
                    }
                    default -> new IllegalStateException(e);  // keep the cause
                };
            }
        };
    }
}

sealed interface Result<T> {
    record Ok<T>(T value) implements Result<T> {}
    record Err<T>(Exception error) implements Result<T> {}

    static <T, R> Function<T, Result<R>> lift(ThrowingFunction<? super T, ? extends R, ?> f) {
        return t -> {
            try { return new Ok<>(f.apply(t)); }
            catch (Exception e) { return new Err<>(e); }
        };
    }
}
List<Path> paths = List.of(Path.of("a.txt"), Path.of("missing.txt"));
List<String> texts = paths.stream().map(ThrowingFunction.unchecked(Files::readString)).toList();
                                                   // fails fast with UncheckedIOException
for (Result<String> r : paths.stream().map(Result.lift(Files::readString)).toList()) {
    String line = switch (r) {                     // exhaustive: Result is sealed
        case Result.Ok<String>(var text) -> "ok, " + text.length() + " chars";
        case Result.Err<String>(var e)   -> "skipped: " + e;
    };
    System.out.println(line);
}

Choose by what the caller should experience. A request handler where any failure is a 500 wants fail-fast unchecked. A batch import that must report every bad row wants Result, ideally the generic Result<T, E> you built in L73. Keep both in your utility package; later lessons reuse them.

What breaks in production
  • Casting a composed operator. (UnaryOperator<String>) trim.andThen(upper) compiles and throws ClassCastException at run time: the lambda returned by andThen implements only Function. Adapt with ::apply.
  • Sneaky throws and transactions. Spring rolls back a @Transactional method by default only on RuntimeException and Error. A sneakily thrown IOException is neither, so the transaction commits the half-finished work.
  • Lost interrupts and causes. Wrapping InterruptedException without re-setting the flag makes a thread pool ignore shutdown; wrapping without passing the cause leaves a stack trace that ends at the wrapper.

Streams: The Pipeline Model

45m video45m practice

A stream is a one-shot description of a computation over a source, not a container. Intermediate operations only build the description; the terminal operation runs it, pushing each element through every stage before touching the next one. Laziness, short-circuiting and the "use once" rule all come from that design.

What a stream is, and what it is not

Definition · stream

A java.util.stream.Stream<T> is "a sequence of elements supporting sequential and parallel aggregate operations" (Javadoc). Unlike a collection it:

  • stores nothing. Elements come from a source (a collection, an array, a generator function, a file) as they are needed;
  • doesn't modify its source. filter produces a new stream; the list it came from is unchanged;
  • is lazy and may be unbounded: Stream.iterate(1, n -> n * 2) is fine as long as something stops it;
  • is consumable. Each stream can be traversed once, like an Iterator.

A pipeline is always source → zero or more intermediate operations → exactly one terminal operation. Intermediate operations (filter, map, sorted…) return a new Stream. Terminal operations (toList, count, forEach, findFirst…) return a result or void, and are the only thing that makes work happen.

How a pipeline executes underneath

In OpenJDK each intermediate call appends a stage object to a linked list: Stream.of("x") is a ReferencePipeline$Head, and .map(...) returns another ReferencePipeline subclass that points back to it. Nothing is iterated. When the terminal operation is called, it asks each stage, from the last back to the first, to wrap a Sink (an extended Consumer), so the result is one chain of sinks. Then it pulls elements from the source's Spliterator and pushes each one down the whole chain.

Laziness, fusion and short-circuiting, proven with peek

Optional<String> first = Stream.of("a", "bb", "ccc", "dddd")
        .peek(s -> System.out.println("source   " + s))
        .filter(s -> s.length() > 1)
        .peek(s -> System.out.println("filtered " + s))
        .map(String::toUpperCase)
        .findFirst();
// source   a
// source   bb
// filtered bb          -- "ccc" and "dddd" are never read
System.out.println(first);   // Optional[BB]

Delete .findFirst() and the program prints nothing: without a terminal operation, there is nothing to run. Replace it with .toList() and the output interleaves (source a, source bb, filtered bb, source ccc…), which shows the fusion. findFirst is short-circuiting: once it has a result, the pipeline stops pulling. Short-circuiting is what makes infinite sources usable:

int firstPowerOver1000 = Stream.iterate(1, n -> n * 2).filter(n -> n > 1000).findFirst().orElseThrow(); // 1024

Short-circuiting operations are findFirst, findAny, anyMatch, allMatch, noneMatch (terminal) and limit, takeWhile (intermediate). peek is here only as a probe; L88 explains why it is unreliable for anything else.

Stream sources

Stream<String>  a = List.of("x", "y").stream();                     // any Collection
IntStream       b = Arrays.stream(new int[] {3, 1, 2});                // primitive arrays too
Stream<String>  c = Stream.of("x", "y", "z");                         // varargs
Stream<Integer> d = Stream.iterate(1, n -> n * 2);                    // infinite, ordered
Stream<Integer> e = Stream.iterate(1, n -> n <= 1000, n -> n * 2);   // Java 9: a for loop
Stream<UUID>    f = Stream.generate(UUID::randomUUID);                // infinite, unordered
IntStream       g = new Random(42).ints(5, 0, 100);                   // 5 ints in [0, 100)
IntStream       h = "hello".chars();                                  // IntStream of char values
Stream<String>  i = Stream.empty();
try (Stream<String> lines = Files.lines(Path.of("orders.csv"))) {     // holds an open file
    long rows = lines.skip(1).count();
}
  • iterate has two forms: the 2-argument one is infinite; the 3-argument one (Java 9) stops when the predicate fails, exactly like for (n = 1; n <= 1000; n *= 2).
  • generate is infinite and unordered, so it needs limit or another short-circuit.
  • String.chars() returns IntStream, not Stream<Character>; printing it shows numbers until you cast (L94).
  • Files.lines keeps a file handle open until the stream is closed. BaseStream extends AutoCloseable, and streams over I/O resources are the ones you must close (L103). Others: BufferedReader.lines(), Pattern.splitAsStream, map.entrySet().stream(), Stream.concat, Stream.builder().

One use only, and don't touch the source

Stream<String> s = names.stream();
s.forEach(System.out::println);
s.count();   // IllegalStateException: stream has already been operated upon or closed

Supplier<Stream<String>> fresh = () -> names.stream().filter(n -> n.length() > 3);
long n = fresh.get().count();                // each get() builds a new pipeline
List<String> top = fresh.get().limit(3).toList();

Linking a second operation to an already-linked stage also throws, so s.filter(...) followed by s.map(...) fails on the second call. If you need the data twice, collect it into a List, or keep a Supplier of the pipeline. Effective Java Item 47 says the same for APIs: return a Collection rather than a Stream when callers may iterate more than once.

The source must not change while the pipeline runs (the Javadoc calls this non-interference). list.stream().forEach(x -> list.add(x)) on an ArrayList throws ConcurrentModificationException; on other sources the result is simply undefined.

What breaks in production
  • Unclosed I/O streams. Files.lines(p).filter(...).count() without try-with-resources leaks a file descriptor per call; a busy service eventually fails with "Too many open files" (L106). The same goes for Spring Data repository methods returning Stream<T>: they hold a database cursor, must run inside a transaction, and must be closed.
  • Infinite streams that never short-circuit. Stream.iterate(0, i -> i + 1).filter(i -> i < 10).forEach(...) prints 0 to 9 and then runs forever: filter cannot know no later element will pass. Use the 3-argument iterate or takeWhile. sorted() on an infinite stream never returns either.
  • Streams stored in fields. A Stream cached in a bean and consumed by the second caller throws IllegalStateException on every request after the first.

Intermediate Operations: filter, map, flatMap, mapMulti

45m video50m practice

Four stateless operations do most of the shaping in real pipelines: filter keeps or drops, map turns one element into one element, and flatMap and mapMulti turn one element into any number. Because each element passes through the whole chain, the order of these steps decides how much work the pipeline does.

The examples use a small order model:

record Line(String sku, int qty, long unitCents) {}
record Order(String id, String customer, List<Line> lines) {}

List<Order> orders = List.of(
        new Order("o1", "ada", List.of(new Line("pen", 2, 150), new Line("ink", 1, 900))),
        new Order("o2", "bob", List.of(new Line("pad", 3, 400))),
        new Order("o3", "ada", List.of()));

filter, and ordering filters for performance

filter(Predicate<? super T>) passes an element to the next stage only if the predicate is true. It is stateless (the decision depends only on the element) and keeps encounter order. Several filters in a row cost the same as one combined predicate, since they are fused into one pass, so split them when that reads better.

Order matters when predicates differ in cost or selectivity. Put the cheap and selective test first, so the expensive one (a regex, a lookup, a remote call) runs on fewer elements, and filter before sorted or distinct, which must buffer what reaches them (L88).

Pattern sku = Pattern.compile("[A-Z]{3}-\\d{4}");
List<String> valid = codes.stream()
        .filter(c -> c.length() == 8)                 // cheap, rejects most input
        .filter(c -> sku.matcher(c).matches())        // expensive, sees the survivors
        .toList();

map: one-to-one, and it may change the type

<R> Stream<R> map(Function<? super T, ? extends R>) replaces each element with the function's result, so Stream<Order> becomes Stream<String> after map(Order::customer). A map should be a pure transformation; logging, saving, or calling remote services inside map turns a pipeline into a hidden loop of side effects.

List<String> customers = orders.stream().map(Order::customer).distinct().toList(); // [ada, bob]
Map<String, Integer> lineCounts = orders.stream()
        .collect(Collectors.toMap(Order::id, o -> o.lines().size()));

flatMap: one-to-many

Definition · flatMap

<R> Stream<R> flatMap(Function<? super T, ? extends Stream<? extends R>> mapper) maps each element to a stream and splices that stream's elements into the output in its place. Each mapped stream is closed after its contents have been placed into the output, and a mapper that returns null is treated as returning an empty stream (Javadoc).

long units = orders.stream()
        .flatMap(o -> o.lines().stream())             // orders → line items
        .mapToInt(Line::qty).sum();                   // 6

Map<String, String> names = Map.of("a", "Ada");
List<String> found = Stream.of("a", "b")
        .map(k -> Optional.ofNullable(names.get(k)))  // Stream<Optional<String>>
        .flatMap(Optional::stream)                    // Java 9: empty → nothing
        .toList();                                    // [Ada]

Pattern ws = Pattern.compile("\\s+");
List<String> words = Stream.of(" hello  world", "a b")
        .flatMap(ws::splitAsStream)                   // lines → words
        .filter(Predicate.not(String::isEmpty))       // leading space gives ""
        .toList();                                    // [hello, world, a, b]

Optional::stream (Java 9) turns a present value into a one-element stream and an empty optional into an empty one, so flatMap(Optional::stream) is the idiom for "keep the hits". Splitting with a regex that matches leading whitespace yields an empty first token, both with String.split and splitAsStream, hence the extra filter.

mapMulti (Java 16): flatMap without a stream per element

<R> Stream<R> mapMulti(BiConsumer<? super T, ? super Consumer<R>> mapper) hands your code a sink; you call sink.accept(r) zero or more times per element. No intermediate Stream object is created, which is why the Javadoc recommends it when each element maps to a small (possibly zero) number of results, and when the logic is easier to write imperatively.

List<String> skus = orders.stream()
        .<Line>mapMulti((o, sink) -> o.lines().forEach(sink))   // type witness needed
        .map(Line::sku).toList();                               // [pen, ink, pad]

List<Integer> parsed = Stream.of("1", "x", "3")
        .<Integer>mapMulti((s, sink) -> {
            try { sink.accept(Integer.parseInt(s)); }           // 0 or 1 outputs
            catch (NumberFormatException ignored) { }
        }).toList();                                            // [1, 3]

The compiler usually cannot infer R from the lambda, so you write the type witness .<Line>mapMulti (L74). Primitive versions mapMultiToInt, mapMultiToLong and mapMultiToDouble avoid boxing too. For simple flattening of an existing collection, flatMap(o -> o.lines().stream()) remains the clearer choice; measure before switching for speed.

Boxing transitions: mapToInt, mapToObj, boxed

map(Line::qty) gives a Stream<Integer>: every int is boxed, and there is no sum(). mapToInt(Line::qty) gives an IntStream, with no boxing and with sum, average and summaryStatistics. Going back, IntStream.mapToObj(IntFunction) or boxed() returns to objects. Each primitive stream has flatMapToInt-style variants as well; L94 covers the costs.

long revenueCents = orders.stream()
        .flatMap(o -> o.lines().stream())
        .mapToLong(l -> l.qty() * l.unitCents())      // LongStream, no Long boxes
        .sum();                                       // 2,400
List<String> labels = IntStream.rangeClosed(1, 3).mapToObj(i -> "row-" + i).toList();

Chaining order and the work done

AtomicInteger calls = new AtomicInteger();
Function<String, String> enrich = s -> { calls.incrementAndGet(); return s.toUpperCase(); };
List<String> in = List.of("a", "bb", "ccc", "dddd");

in.stream().map(enrich).filter(s -> s.length() > 3).toList();   // calls = 4
calls.set(0);
in.stream().filter(s -> s.length() > 3).map(enrich).toList();   // calls = 1

Moving a filter ahead of a map is valid only when the predicate doesn't need the mapped value (here, upper-casing doesn't change length). With a million orders and a 1% filter, the difference is a million enrich calls versus ten thousand. The same reasoning puts limit as early as the logic allows.

What breaks in production
  • N+1 queries in map. ids.stream().map(repo::findById) issues one database round trip per id. Batch it (findAllById(ids)) and then stream over the result.
  • map where flatMap was meant. orders.stream().map(Order::lines).count() counts orders, not lines, and the type Stream<List<Line>> only fails to compile further down, if at all.
  • Silent drops. mapMulti or flatMap(Optional::stream) that discards bad rows without logging or counting them makes a report quietly wrong. Count rejects, or use Result from L85.

Most of these operations are stateful: to decide what to emit for one element they must remember others. That memory is what makes sorted a full barrier, distinct a growing hash set, and limit expensive in parallel, and it is the main thing to reason about when a pipeline is slow.

distinct: equals, hashCode and memory

distinct() removes duplicates according to equals, using hashCode to find them. For an ordered stream it keeps the first occurrence. It holds every distinct element seen so far, so on a large stream with few duplicates it is a hash set as big as the data.

class Box { final int v; Box(int v) { this.v = v; } }      // no equals/hashCode
record Tx(String id, int amount) {}                          // records have both

Stream.of(new Box(1), new Box(1)).distinct().count();        // 2: identity comparison
Stream.of(new Tx("a", 1), new Tx("a", 1)).distinct().count(); // 1

// distinct by key, keeping the first element per key and the encounter order
Collection<Tx> firstPerId = Stream.of(new Tx("a", 1), new Tx("a", 2), new Tx("b", 3))
        .collect(Collectors.toMap(Tx::id, Function.identity(), (first, later) -> first,
                                  LinkedHashMap::new))
        .values();                                           // [Tx[a,1], Tx[b,3]]

There is no distinctBy(key) in the JDK. The toMap form above works everywhere; a gatherer is the modern answer (L97). Broken equals/hashCode (L43) breaks distinct the same way it breaks HashSet.

sorted: natural order, comparators, stability, buffering

sorted() uses natural order and needs Comparable elements; otherwise a ClassCastException is thrown when the terminal operation runs, not where sorted() is written. sorted(Comparator) takes any comparator (L45). For ordered streams the sort is stable: equal elements keep their encounter order.

List<Tx> txs = List.of(new Tx("a", 5), new Tx("b", 3), new Tx("c", 5), new Tx("d", 3));
txs.stream().sorted(Comparator.comparingInt(Tx::amount)).map(Tx::id).toList();  // [b, d, a, c]

Optional<Tx> smallest = txs.stream().min(Comparator.comparingInt(Tx::amount)); // O(n), no buffer
List<Tx> top2 = txs.stream()
        .sorted(Comparator.comparingInt(Tx::amount).reversed()).limit(2).toList(); // sorts all n

sorted is a full barrier: it cannot emit its first element until it has seen the last, so it buffers the whole stream (O(n) memory, O(n log n) time) and breaks laziness for everything after it. sorted().findFirst() still sorts everything; use min or max. sorted().limit(k) for top-k sorts all n elements; for large n and small k, a size-k PriorityQueue does it in O(n log k). OpenJDK skips the sort when the source already reports natural-order SORTED, as a TreeSet does.

limit and skip, ordered and unordered

limit(n) passes the first n elements and then short-circuits; skip(n) discards the first n. On an ordered stream "first" means encounter order, which is cheap sequentially but, in the Javadoc's words, "can be quite expensive on ordered parallel pipelines", because the threads must agree on which elements came first. If you only need some n elements, unordered() relaxes the constraint.

int page = 3, size = 20;
List<Tx> pageRows = txs.stream()
        .sorted(Comparator.comparing(Tx::id))
        .skip((long) page * size)                    // walks past 60 elements first
        .limit(size)
        .toList();

skip + limit pagination still visits every skipped element, so page 10,000 is slow. Against a database, push paging into the query, preferably as keyset pagination ("WHERE id > last"), which later phases use.

takeWhile and dropWhile (Java 9) vs filter

They only make sense when the data is ordered by the thing you test: lines of a log sorted by time, readings until a sentinel. On an unordered stream the Javadoc allows any matching subset, so the result is nondeterministic.

// record Event(Instant at, String msg) {}; events is sorted by time
Instant cutoff = Instant.parse("2026-01-01T00:00:00Z");
List<Event> beforeCutoff = events.stream()
        .takeWhile(e -> e.at().isBefore(cutoff))
        .toList();

peek: for debugging only

peek(Consumer) runs an action on each element as it passes and changes nothing. The Javadoc says it "exists mainly to support debugging". It is unreliable for real work for three reasons: short-circuiting means it sees only some elements; in parallel it runs on many threads in no particular order; and the library may skip it entirely. Since Java 9, count() may compute its answer from the source size without running the pipeline:

List<String> l = List.of("a", "b", "c");
l.stream().peek(System.out::println).count();                      // prints nothing; 3
l.stream().map(String::toUpperCase).peek(System.out::println).count();   // nothing either
l.stream().filter(s -> true).peek(System.out::println).count();    // prints a, b, c

With only size-preserving stages, the size is known, so neither map nor peek runs. Add a filter or flatMap and the elements flow again. This is allowed: the stream contract only promises the result, not which behavioural parameters get called.

What breaks in production
  • Work done in peek. users.stream().peek(repo::save).count() saves nothing on Java 9 and later. Side effects belong in forEach or a plain loop.
  • Sorting to find one element. sorted(byDate).findFirst() over ten million rows buffers and sorts all of them to return one; min(byDate) is a single pass.
  • Deduplicating entities with identity equality. distinct() on JPA entities without equals removes nothing, or worse, uses a hashCode that changes once the id is assigned.
  • takeWhile on unsorted input. A report built with takeWhile(e -> e.at().isBefore(cutoff)) stops at the first late event and silently omits everything after it.

Terminal Operations: forEach, count, match, find, toArray

35m video40m practice

The terminal operation is the one that runs the pipeline, and it decides how much of the source gets read, in what order, on which threads, and what comes back. Each one has a precise contract, and the bugs live in the edge cases of those contracts: empty streams, nulls, parallel execution and unmodifiable results.

The families of terminal operations

Definition · terminal operation

An operation that produces a result or a side effect and consumes the stream; afterwards the stream can't be used again. The JDK's terminal operations fall into five groups:

  • side effects: forEach, forEachOrdered;
  • reductions: count, min, max, reduce (L90), collect (L91);
  • short-circuiting searches: anyMatch, allMatch, noneMatch, findFirst, findAny;
  • materialisers: toArray, toList;
  • escape hatches: iterator, spliterator.

forEach vs forEachOrdered, and count

forEach(action) is "explicitly nondeterministic" (Javadoc): on a parallel stream the action runs on several threads, in any order, possibly at the same time. forEachOrdered(action) runs the action in encounter order, one element at a time, which serialises the last step of a parallel pipeline. Sequential forEach does follow encounter order in practice, but the specification doesn't promise it, so code that depends on order should say forEachOrdered.

IntStream.range(0, 5).parallel().forEach(i -> System.out.print(i + " "));        // e.g. 2 4 3 0 1
IntStream.range(0, 5).parallel().forEachOrdered(i -> System.out.print(i + " ")); // 0 1 2 3 4

For a List, list.forEach(...) (from Iterable) is simpler than list.stream().forEach(...) and is ordered. Either way, a forEach that fills a collection should be a collector.

count() returns a long. As shown in L88, it may return the source size without running the pipeline when no stage can change the number of elements, so behavioural parameters such as peek and map may never be called.

Matching: short-circuits and vacuous truth

record Shipment(String id, boolean delivered) {}
List<Shipment> shipments = List.of();                          // order not shipped yet
boolean done = shipments.stream().allMatch(Shipment::delivered);   // true!
boolean reallyDone = !shipments.isEmpty() && shipments.stream().allMatch(Shipment::delivered);

The vacuous true from allMatch is mathematically right and often the business opposite of what you meant. Decide explicitly what "empty" means and test it.

findFirst vs findAny, and min/max

Both return an Optional and short-circuit. findFirst returns the first element in encounter order; in parallel the threads must coordinate to be sure no earlier element matches. findAny may return any element: sequentially it is usually the first, in parallel it is whichever a thread finds first, which is cheaper. A run of IntStream.range(0, 1000).parallel().boxed().findAny() returned 656. Use findAny when any match will do, and never assert on its value in a test.

Both throw NullPointerException if the selected element is null, because an Optional can't hold one. min(Comparator) and max(Comparator) also return Optional (empty for an empty stream); on primitive streams, OptionalInt and friends.

Optional<Shipment> anyLate = shipments.stream().filter(s -> !s.delivered()).findAny();
int maxQty = IntStream.of(3, 9, 4).max().orElseThrow();                  // 9
String longest = Stream.of("ab", "abcd", "abc")
        .max(Comparator.comparingInt(String::length)).orElse("");      // "abcd"

toArray, toList and collect(toList())

toArray() returns Object[]. toArray(IntFunction<A[]> generator) lets you choose the array type; the generator receives the size. The type is checked only at run time, so Stream.of(1, "a").toArray(Integer[]::new) compiles and throws ArrayStoreException. Primitive streams return primitive arrays: IntStream.toArray() is an int[].

String[] ids = shipments.stream().map(Shipment::id).toArray(String[]::new);
List<String> a = Stream.of("x", "y").toList();                          // Java 16
List<String> b = Stream.of("x", "y").collect(Collectors.toList());
List<String> c = Stream.of("x", "y").collect(Collectors.toUnmodifiableList());

If you need a mutable list, say so with Collectors.toCollection(ArrayList::new) rather than relying on what Collectors.toList() happens to return.

The iterator() escape hatch

iterator() and spliterator() are terminal operations that hand control back to you: elements are pulled lazily on each hasNext/next, so they work on infinite streams. Use them for what streams can't express directly, such as walking two streams in lock-step, feeding an API that expects an Iterator, or stopping on a condition that depends on outside state.

Iterator<Integer> ids = Stream.iterate(1, i -> i + 1).iterator();
Iterator<String> names = Stream.of("ada", "bob").iterator();
while (names.hasNext()) System.out.println(ids.next() + ": " + names.next());   // 1: ada, 2: bob

Stream<String> lines = Stream.of("a", "b");
for (String s : (Iterable<String>) lines::iterator) {   // one-shot Iterable, use exactly once
    System.out.println(s);
}
What breaks in production
  • Migrating to toList(). Replacing collect(Collectors.toList()) with toList() across a code base is a behaviour change: any caller that later calls add or sort on the result now throws UnsupportedOperationException, possibly in a different module.
  • Vacuous truth in workflows. "Close the order when all shipments are delivered" closes orders that have no shipments yet.
  • Parallel forEach into a shared list. parallelStream().forEach(results::add) on an ArrayList loses elements or throws ArrayIndexOutOfBoundsException. Collect instead.
  • Null elements. findFirst() on a stream whose first element is null throws NullPointerException; filter with Objects::nonNull first.

reduce: Fold Semantics Done Right

40m video45m practice

reduce folds a stream into one value by repeatedly combining two values into one. It is correct only if the identity really is neutral and the operation is associative, because a parallel stream folds each chunk separately from the identity and then merges the partial results. Code that breaks those laws often still passes sequential tests.

The three overloads

interface Stream<T> {                                   // excerpt of java.util.stream.Stream
    Optional<T> reduce(BinaryOperator<T> accumulator);                       // 1-arg
    T reduce(T identity, BinaryOperator<T> accumulator);                     // 2-arg
    <U> U reduce(U identity, BiFunction<U, ? super T, U> accumulator,
                 BinaryOperator<U> combiner);                                // 3-arg
}
  • 1-arg has no starting value, so an empty stream has no answer: the result is an Optional. A one-element stream returns that element without calling the accumulator.
  • 2-arg starts from the identity and returns it for an empty stream, so no Optional.
  • 3-arg lets the result type U differ from the element type T. The accumulator folds one element into a partial result; the combiner merges two partial results and is what parallel execution needs.
int sum             = IntStream.rangeClosed(1, 100).boxed().reduce(0, Integer::sum);       // 5050
Optional<Integer> m = Stream.of(3, 9, 4).reduce(Integer::max);                              // Optional[9]
BigDecimal total    = Stream.of("19.99", "5.01").map(BigDecimal::new).reduce(BigDecimal.ZERO, BigDecimal::add);
int chars           = Stream.of("ab", "cde").reduce(0, (acc, w) -> acc + w.length(), Integer::sum); // 5
int sameChars       = Stream.of("ab", "cde").mapToInt(String::length).sum();                // clearer

As the last two lines show, a 3-arg reduce that maps and then sums is usually clearer as map followed by a 2-arg reduce or a built-in like sum(); the Javadoc says the same.

The laws: identity, associativity, compatibility

Theorem · when a reduction is parallel-safe

Write the accumulator as ⊕. The Javadoc requires:

  • Identity: for every t, identity ⊕ t = t. (0 for +, 1 for ×, "" for concatenation, Long.MIN_VALUE for max.)
  • Associativity: (a ⊕ b) ⊕ c = a ⊕ (b ⊕ c) for all a, b, c.
  • Compatibility (3-arg form): combiner.apply(u, accumulator.apply(identity, t)) equals accumulator.apply(u, t).
  • The functions must also be stateless and non-interfering.

Under these conditions every way of splitting the input and merging the pieces gives the same result as the sequential fold, so the library is free to split however it likes.

What breaks without them

// identity 1 is not neutral for +
IntStream.rangeClosed(1, 100).boxed().reduce(1, Integer::sum);             // 5051
IntStream.rangeClosed(1, 100).boxed().parallel().reduce(1, Integer::sum);  // 5114 on one 12-core run

// subtraction is not associative
IntStream.rangeClosed(1, 100).boxed().reduce(0, (a, b) -> a - b);             // -5050
IntStream.rangeClosed(1, 100).boxed().parallel().reduce(0, (a, b) -> a - b);  // 0 on the same machine

The parallel results above were measured once on a 12-core laptop; on another machine they will differ, which is exactly the problem. 5114 is 5050 plus one extra 1 for each of the 64 leaf chunks. Floating-point addition is also not exactly associative: summing a million doubles gave 1.000000000499632E12 sequentially and 1.0000000004997917E12 in parallel. DoubleStream.sum() uses compensated summation to reduce this error, but for money, use long cents or BigDecimal, whose addition is exact.

Why reduce with a mutable container is wrong

// WRONG: one ArrayList is the identity for every chunk
List<Integer> bad = IntStream.range(0, 10_000).boxed().parallel()
        .reduce(new ArrayList<>(),
                (list, x) -> { list.add(x); return list; },
                (a, b) -> { a.addAll(b); return a; });       // ArrayIndexOutOfBoundsException

// RIGHT: mutable reduction gives each chunk a fresh container
List<Integer> good = IntStream.range(0, 10_000).boxed().parallel()
        .collect(ArrayList::new, ArrayList::add, ArrayList::addAll);   // size 10000

reduce assumes values are immutable: the identity object is shared, so every thread adds to the same ArrayList at once. In three runs it threw ArrayIndexOutOfBoundsException each time; sequentially it "works", which is why this survives code review. collect(supplier, accumulator, combiner) is the mutable counterpart: the supplier creates a new container per chunk, the accumulator mutates it, and the combiner merges two containers. Collectors (L91–L93) package that pattern.

Concatenation is the performance version of the same mistake: reduce("", String::concat) copies the growing string on every step, O(n²) in total. Over 50,000 four-letter words it took about 11 seconds where String.join took 16 ms. Use Collectors.joining().

Custom aggregations with an immutable value

An aggregation that tracks several quantities fits the 3-arg form when the partial result is an immutable value with an "add one element" method and a "merge two partials" method:

record Stats(long count, long sum, long min, long max) {
    static final Stats EMPTY = new Stats(0, 0, Long.MAX_VALUE, Long.MIN_VALUE);

    Stats add(long x) {
        return new Stats(count + 1, sum + x, Math.min(min, x), Math.max(max, x));
    }
    Stats combine(Stats o) {
        return new Stats(count + o.count, sum + o.sum, Math.min(min, o.min), Math.max(max, o.max));
    }
    double mean() { return count == 0 ? Double.NaN : (double) sum / count; }
}

record Order(String id, long cents) {}
List<Order> orders = List.of(new Order("a", 500), new Order("b", 1_200), new Order("c", 300));
Stats s = orders.parallelStream().reduce(Stats.EMPTY, (st, o) -> st.add(o.cents()), Stats::combine);
// Stats[count=3, sum=2000, min=300, max=1200]

Check the laws: EMPTY is neutral for combine (the min of Long.MAX_VALUE and anything is the anything), combine is associative because each field is, and EMPTY.add(t) combined into u equals u.add(t). The cost is one allocation per element; for hot paths, a mutable collector does the same with one object per chunk (L93), and the JDK already ships LongSummaryStatistics (L94).

What breaks in production
  • Results that depend on the hardware. A wrong identity or a non-associative accumulator gives correct numbers in tests on a laptop running sequential streams and different numbers once someone adds .parallel() or the code runs on a 64-core server.
  • Shared mutable identities. reduce(new HashMap<>(), …) or reduce(new StringBuilder(), …) is a data race the moment the stream goes parallel. Use collect.
  • Floating-point money. Parallel and sequential sums of double amounts disagree in the last digits, and reconciliation reports flag the difference.

Collectors I: toList, toSet, toMap, joining, counting

40m video45m practice

A Collector is a packaged recipe for mutable reduction: make a container, add each element, merge containers from parallel chunks, optionally finish. The basic collectors in java.util.stream.Collectors are those recipes for the usual containers, and each has one contract detail (ordering, duplicates, nulls, empty input) that production data will eventually test.

Examples use:

record Emp(String name, String dept, int salary, String email) {}   // email may be null
List<Emp> staff = List.of(new Emp("ada", "eng", 120, "ada@x"),
                          new Emp("bob", "ops", 90, null),
                          new Emp("cy", "eng", 100, "cy@x"));

Collections: toList, toSet, toCollection, toUnmodifiable*

Definition · collector

Collector<T, A, R> bundles a supplier of a mutable container A, an accumulator that adds a T to it, a combiner that merges two containers, and a finisher that turns A into the result R. stream.collect(collector) runs it; in parallel, each chunk gets its own container. L93 builds one by hand.

List<String> names     = staff.stream().map(Emp::name).collect(Collectors.toList());
Set<String> depts      = staff.stream().map(Emp::dept).collect(Collectors.toSet());
TreeSet<String> sorted = staff.stream().map(Emp::name).collect(Collectors.toCollection(TreeSet::new));
Deque<Emp> queue       = staff.stream().collect(Collectors.toCollection(ArrayDeque::new));
List<String> frozen    = staff.stream().map(Emp::name).collect(Collectors.toUnmodifiableList());
  • toList() / toSet() promise nothing about the implementation, mutability or thread safety. Today they return ArrayList and HashSet; treat that as an accident. toSet has no order, so never print or compare its iteration order in a test.
  • toCollection(supplier) is how you ask for a specific type: TreeSet::new for sorted, LinkedHashSet::new for ordered unique, () -> EnumSet.noneOf(Day.class).
  • toUnmodifiableList/Set/Map (Java 10) return the null-hostile immutable collections of L70: a null element throws NullPointerException. toUnmodifiableSet silently drops duplicates like any set. For lists, Stream.toList() (L89) is shorter and allows nulls.

toMap: key mapper, value mapper, and duplicate keys

Map<String, Integer> salaryByName = staff.stream()
        .collect(Collectors.toMap(Emp::name, Emp::salary));         // {ada=120, bob=90, cy=100}

Map<String, String> nameByDept = staff.stream()
        .collect(Collectors.toMap(Emp::dept, Emp::name));
// IllegalStateException: Duplicate key eng (attempted merging values ada and cy)

The two-argument toMap assumes keys are unique and throws as soon as one repeats. That is a feature: it refuses to guess. When duplicates are legitimate, pass a merge function that says what to do with two values for one key:

Map<String, String> firstPerDept = staff.stream()
        .collect(Collectors.toMap(Emp::dept, Emp::name, (first, later) -> first));  // {eng=ada, ops=bob}
Map<String, Integer> payroll = staff.stream()
        .collect(Collectors.toMap(Emp::dept, Emp::salary, Integer::sum));           // {eng=220, ops=90}
TreeMap<String, Integer> sortedPayroll = staff.stream()
        .collect(Collectors.toMap(Emp::dept, Emp::salary, Integer::sum, TreeMap::new));
Map<String, Emp> byNameInOrder = staff.stream()
        .collect(Collectors.toMap(Emp::name, Function.identity(), (a, b) -> a, LinkedHashMap::new));

The four-argument form adds a map supplier: LinkedHashMap::new keeps encounter order, TreeMap::new sorts by key, () -> new EnumMap<>(Day.class) for enum keys. Without it you get a HashMap, whose iteration order is not insertion order. Assign the result to a typed variable: passing a four-argument toMap straight into an overloaded method such as println can defeat type inference.

The null-value trap

Map<String, String> emails = staff.stream()
        .collect(Collectors.toMap(Emp::name, Emp::email));   // NullPointerException (bob)

HashMap accepts null values, but toMap doesn't: it inserts through putIfAbsent/merge and rejects a null value explicitly, with an exception that has no message and a stack trace ending inside Collectors. Decide what a missing value means and say it in code:

Map<String, String> known = staff.stream().filter(e -> e.email() != null)
        .collect(Collectors.toMap(Emp::name, Emp::email));                     // drop them
Map<String, Optional<String>> maybe = staff.stream()
        .collect(Collectors.toMap(Emp::name, e -> Optional.ofNullable(e.email())));  // keep them
Map<String, String> withNulls = staff.stream()
        .collect(HashMap::new, (m, e) -> m.put(e.name(), e.email()), Map::putAll); // last one wins!

The last form allows nulls but silently overwrites duplicate keys, so use it only when keys are known to be unique. (Optional as a map value is debatable; L96 discusses it.)

joining

String csv  = staff.stream().map(Emp::name).collect(Collectors.joining(","));            // ada,bob,cy
String list = staff.stream().map(Emp::name).collect(Collectors.joining(", ", "[", "]")); // [ada, bob, cy]
String none = Stream.<String>empty().collect(Collectors.joining(", ", "[", "]"));         // []

joining accepts only CharSequence elements, so map to strings first. It builds through a StringBuilder, so it is linear, unlike reduce("", String::concat) (L90). Prefix and suffix are added even when the stream is empty.

Counting and numeric summaries

long n                    = staff.stream().collect(Collectors.counting());           // Long, boxed
int total                 = staff.stream().collect(Collectors.summingInt(Emp::salary)); // 310
double avg                = staff.stream().collect(Collectors.averagingDouble(Emp::salary));
IntSummaryStatistics st   = staff.stream().collect(Collectors.summarizingInt(Emp::salary));
// IntSummaryStatistics{count=3, sum=310, min=90, average=103.333333, max=120}
Optional<Emp> topEarner   = staff.stream().collect(Collectors.maxBy(Comparator.comparingInt(Emp::salary)));
int viaReducing           = staff.stream().collect(Collectors.reducing(0, Emp::salary, Integer::sum));

As top-level collectors these are longer than the stream methods they mirror (count(), mapToInt(...).sum(), max(...)). They exist to be downstream collectors inside groupingBy, where "count per department" has no stream-method equivalent (L92). Two details: counting() produces a boxed Long, and averagingInt/averagingDouble return 0.0 for empty input, whereas IntStream.average() returns an empty OptionalDouble.

What breaks in production
  • Duplicates that only exist in production. toMap(User::email, …) passes every test with clean fixtures and throws IllegalStateException the first time two accounts share an email with different case. Add the merge function deliberately, or normalise the key.
  • A null value in one row. An optional column turns a nightly export into a NullPointerException with no message.
  • "Average: 0.00". averagingDouble over a filtered-to-empty stream reports zero instead of "no data".
  • Order assumptions. JSON built from a toMap or toSet result changes field order between runs or JDK versions and breaks snapshot tests and caches keyed by the serialised text.

Collectors II: groupingBy & partitioningBy

45m video50m practice

groupingBy is SQL's GROUP BY as a collector: a classifier picks each element's bucket, and a downstream collector reduces each bucket independently. Nesting downstream collectors is how a few lines produce a "sales by region by month" report, and knowing which keys appear, in what order, is how that report stays correct.

record Sale(String region, String product, LocalDate date, long cents) {}
List<Sale> sales = List.of(
        new Sale("EU", "pen", LocalDate.of(2026, 1, 5), 300),
        new Sale("EU", "ink", LocalDate.of(2026, 1, 9), 900),
        new Sale("US", "pen", LocalDate.of(2026, 2, 1), 450),
        new Sale("EU", "pen", LocalDate.of(2026, 2, 3), 300),
        new Sale("US", "pad", LocalDate.of(2026, 2, 7), 1_200));

groupingBy with a classifier

Definition · groupingBy

groupingBy(classifier, mapFactory, downstream): for each element, compute key = classifier.apply(t), find or create that key's downstream container, and accumulate t into it. When the stream ends, each container is finished into the map's value. The one-argument form means groupingBy(classifier, HashMap::new, toList()), giving a Map<K, List<T>> whose lists keep encounter order.

Map<String, List<Sale>> byRegion = sales.stream().collect(Collectors.groupingBy(Sale::region));

A classifier that returns null throws NullPointerException: element cannot be mapped to a null key. Map missing values to an explicit key such as "UNKNOWN" first.

Downstream collectors

Map<String, Long> count            = sales.stream().collect(groupingBy(Sale::region, counting()));
Map<String, Long> revenue          = sales.stream().collect(groupingBy(Sale::region, summingLong(Sale::cents)));
Map<String, Set<String>> products   = sales.stream().collect(groupingBy(Sale::region, mapping(Sale::product, toSet())));
Map<String, String> productList    = sales.stream().collect(groupingBy(Sale::region, mapping(Sale::product, joining("|"))));
Map<String, Optional<Sale>> biggest = sales.stream().collect(groupingBy(Sale::region,
        maxBy(Comparator.comparingLong(Sale::cents))));
// count = {EU=3, US=2}; productList = {EU=pen|ink|pen, US=pen|pad}

(With import static java.util.stream.Collectors.*.) This is where the collectors from L91 earn their keep: "count per region" has no stream-method equivalent. Prefer a reducing downstream (counting, summingLong) over toList() followed by .size(): the former keeps one number per key, the latter holds every element in memory. maxBy yields Optional values even though a bucket is never empty; L93 unwraps them with collectingAndThen.

To rank groups, stream the result map's entries:

Map<String, Long> freq = Stream.of("a", "b", "a", "c", "a", "b")
        .collect(groupingBy(Function.identity(), counting()));
List<Map.Entry<String, Long>> top2 = freq.entrySet().stream()
        .sorted(Map.Entry.<String, Long>comparingByValue().reversed()
                .thenComparing(Map.Entry.comparingByKey()))
        .limit(2).toList();                                       // [a=3, b=2]

Multi-level grouping and map factories

The downstream collector can itself be a groupingBy, which gives nested maps. The map-factory argument controls the map type at each level: TreeMap::new for sorted keys, LinkedHashMap::new for first-seen order, () -> new EnumMap<>(Region.class) for enum keys.

Map<String, Map<YearMonth, Long>> report = sales.stream().collect(
        groupingBy(Sale::region, TreeMap::new,
                   groupingBy(s -> YearMonth.from(s.date()), TreeMap::new,
                              summingLong(Sale::cents))));
// {EU={2026-01=1200, 2026-02=300}, US={2026-02=1650}}

report.forEach((region, months) -> months.forEach((ym, cents) ->
        System.out.printf("%-3s %s %10.2f%n", region, ym, cents / 100.0)));

Notice what is missing: US has no January row, because a bucket exists only if an element lands in it. A report that must show every month needs the full key set from elsewhere, for example by iterating YearMonths from the first to the last month and using months.getOrDefault(ym, 0L). Beyond two levels, a record key (record RegionMonth(String region, YearMonth month)) is easier to read and to sort than maps of maps.

partitioningBy: two buckets, always both

Map<Boolean, List<Sale>> split = sales.stream().collect(partitioningBy(s -> s.cents() > 500));
Map<Boolean, Long> bigCount     = sales.stream().collect(partitioningBy(s -> s.cents() > 500, counting()));
// bigCount = {false=3, true=2}
Map<Boolean, List<Sale>> none  = Stream.<Sale>empty().collect(partitioningBy(s -> s.cents() > 500));
// {false=[], true=[]}  -- both keys present

partitioningBy(predicate) is a grouping with a boolean classifier, but its result always contains both true and false, each with the downstream collector's empty result. groupingBy(pred::test) would leave out a key nobody mapped to, so get(true) could return null. Use partitioning for "valid vs invalid", "paid vs unpaid", and anything you then read with get(true).

groupingByConcurrent

groupingByConcurrent returns a ConcurrentMap (a ConcurrentHashMap by default) and is a concurrent, unordered collector: on a parallel stream, all threads accumulate into one shared map instead of building per-thread maps and merging them at the end. With many keys and large parallel inputs that can be faster. The price is that elements within each group arrive in no particular order, so use it with order-insensitive downstreams such as counting or summingLong, and benchmark before choosing it (L95).

ConcurrentMap<String, Long> perRegion = sales.parallelStream()
        .collect(groupingByConcurrent(Sale::region, counting()));
What breaks in production
  • Missing rows read as zero, or not at all. Dashboards built straight from groupingBy skip days with no sales, and charts connect the points across the gap.
  • Null classifier keys. One record with a null region aborts the whole job with "element cannot be mapped to a null key".
  • Memory from toList() buckets. Grouping ten million rows into lists to count them holds all ten million in the heap; counting() holds one Long per key.
  • Unordered output. The default HashMap factory produces reports whose row order changes with the data; pass TreeMap::new when order matters.

Collectors III: mapping, flatMapping, filtering, teeing & Custom Collectors

45m video50m practice

Collectors compose: adapters such as mapping, filtering and collectingAndThen wrap one collector in another, and teeing runs two side by side. When nothing in Collectors fits, the five-part Collector interface is small enough to implement in a few lines, provided the combiner is as correct as the accumulator.

record Sale(String region, String product, long cents) {}
List<Sale> sales = List.of(new Sale("EU", "pen", 300), new Sale("EU", "ink", 900),
                           new Sale("US", "pen", 450), new Sale("APAC", "pad", 200));

Adapters: mapping, flatMapping, filtering

Each adapter changes what reaches a downstream collector, the way map, flatMap and filter change what reaches a terminal operation. They matter inside groupingBy, where you can't put a stream operation between the grouping and the per-group reduction.

Map<String, Set<String>> productsByRegion = sales.stream().collect(
        groupingBy(Sale::region, mapping(Sale::product, toCollection(TreeSet::new))));

record Order(String customer, List<String> skus) {}
Map<String, Set<String>> skusByCustomer = Stream.of(new Order("ada", List.of("pen", "ink")),
                                                  new Order("ada", List.of("pen")))
        .collect(groupingBy(Order::customer, flatMapping(o -> o.skus().stream(), toSet())));
// {ada=[ink, pen]}   -- Java 9

filtering (Java 9) looks redundant until you compare it with an upstream filter:

Map<String, Long> upstream = sales.stream()
        .filter(s -> s.cents() > 400)
        .collect(groupingBy(Sale::region, TreeMap::new, counting()));          // {EU=1, US=1}
Map<String, Long> downstream = sales.stream()
        .collect(groupingBy(Sale::region, TreeMap::new,
                            filtering(s -> s.cents() > 400, counting())));     // {APAC=0, EU=1, US=1}

Filtering upstream removes APAC's only sale before grouping, so APAC never gets a bucket. Filtering downstream groups first, so every region appears and the count of matches can be zero. Reports usually want the second.

Post-processing with collectingAndThen

collectingAndThen(downstream, finisher) applies one function to the finished result. Two uses cover most code: making a result unmodifiable, and unwrapping the Optional that maxBy/minBy produce inside a grouping, where a bucket is never empty.

Map<String, Integer> counts = sales.stream().collect(collectingAndThen(
        toMap(Sale::product, s -> 1, Integer::sum), Collections::unmodifiableMap));

Map<String, Sale> biggestPerRegion = sales.stream().collect(groupingBy(Sale::region, TreeMap::new,
        collectingAndThen(maxBy(Comparator.comparingLong(Sale::cents)), Optional::orElseThrow)));

Two results in one pass: teeing (Java 12)

teeing(c1, c2, merger) sends every element to both collectors and combines their two results with merger. It replaces two passes over the data, or a hand-written accumulator, for paired statistics.

record Range(long min, long max) {}
Range range = sales.stream().collect(teeing(
        mapping(Sale::cents, minBy(Comparator.naturalOrder())),
        mapping(Sale::cents, maxBy(Comparator.naturalOrder())),
        (mn, mx) -> new Range(mn.orElse(0L), mx.orElse(0L))));                // Range[min=200, max=900]

double mean = sales.stream().collect(teeing(summingLong(Sale::cents), counting(),
        (sum, n) -> n == 0 ? Double.NaN : (double) sum / n));                  // 462.5

The Collector interface

Definition · Collector<T, A, R>
  • Supplier<A> supplier(): creates a new, empty mutable container.
  • BiConsumer<A, T> accumulator(): folds one element into a container.
  • BinaryOperator<A> combiner(): merges two containers (may mutate and return the left one).
  • Function<A, R> finisher(): converts the final container into the result.
  • Set<Characteristics> characteristics(): IDENTITY_FINISH (the finisher is the identity, so it is skipped and A is cast to R), UNORDERED (the result doesn't depend on encounter order), CONCURRENT (one container may be accumulated from several threads at once).

Collector.of and a toImmutableSortedMap from scratch

Collector.of(supplier, accumulator, combiner, [finisher,] characteristics...) builds a collector from lambdas. The JDK has no collector that yields an immutable sorted map and rejects duplicate keys and nulls, so here is one:

static <T, K extends Comparable<? super K>, V> Collector<T, ?, SortedMap<K, V>> toImmutableSortedMap(
        Function<? super T, ? extends K> keyFn, Function<? super T, ? extends V> valueFn) {
    return Collector.of(
            TreeMap<K, V>::new,                                       // supplier
            (map, t) -> {                                             // accumulator
                K k = Objects.requireNonNull(keyFn.apply(t), "null key");
                V v = Objects.requireNonNull(valueFn.apply(t), "null value for key " + k);
                if (map.putIfAbsent(k, v) != null) throw new IllegalStateException("Duplicate key " + k);
            },
            (left, right) -> {                                        // combiner
                right.forEach((k, v) -> {
                    if (left.putIfAbsent(k, v) != null) throw new IllegalStateException("Duplicate key " + k);
                });
                return left;
            },
            Collections::unmodifiableSortedMap,                       // finisher
            Collector.Characteristics.UNORDERED);                     // sorted result: order irrelevant
}

SortedMap<String, Long> byKey = sales.stream()
        .collect(toImmutableSortedMap(s -> s.region() + "/" + s.product(), Sale::cents));
// {APAC/pad=200, EU/ink=900, EU/pen=300, US/pen=450}; put(...) throws UnsupportedOperationException

Design notes: the return type Collector<T, ?, SortedMap<K, V>> hides the container type, as the JDK's own factories do. The unmodifiable view is safe because nothing else holds a reference to the TreeMap. It is not IDENTITY_FINISH (there is a finisher) and not CONCURRENT (TreeMap isn't thread-safe). A test over IntStream.range(0, 100_000).boxed().parallel() confirms the combiner: 100,000 entries, first key 0, last 99,999.

A mutable accumulator class is the other common pattern, here for a weighted average (the capstone, L98, uses it):

static <T> Collector<T, ?, Double> weightedAverage(ToDoubleFunction<? super T> value,
                                                   ToDoubleFunction<? super T> weight) {
    final class Acc { double sum, weights; }
    return Collector.of(Acc::new,
            (a, t) -> { double w = weight.applyAsDouble(t); a.sum += value.applyAsDouble(t) * w; a.weights += w; },
            (a, b) -> { a.sum += b.sum; a.weights += b.weights; return a; },
            a -> a.weights == 0 ? Double.NaN : a.sum / a.weights);
}
What breaks in production
  • Untested combiners. A combiner that returns right without merging left into it, or that ignores one side, is invisible in sequential tests and drops data the day someone parallelises the pipeline. Always test custom collectors on a large parallel stream.
  • Lying characteristics. Declaring IDENTITY_FINISH with a real finisher makes the library skip it and cast the container, giving a ClassCastException or a mutable map where an immutable one was promised. Declaring CONCURRENT on a HashMap container corrupts it.
  • Upstream filtering in reports. Regions or products with no matching rows disappear instead of showing zero.

Primitive Streams & Boxing Costs

35m video40m practice

IntStream, LongStream and DoubleStream exist because a Stream<Integer> carries a heap object per element. Use them for numeric work, know the handful of methods only they have, and measure: sometimes the JIT removes the boxes for you, and sometimes it can't.

Three primitive streams and why they exist

Definition · boxing cost

A Stream<Integer> element is a reference to an Integer object: on a typical 64-bit JVM with compressed references, a 4-byte pointer to a 16-byte object, versus 4 bytes for an int. Creating one is an allocation (outside the -128..127 cache, L54), reading it is a pointer dereference, and millions of them are GC work. IntStream, LongStream and DoubleStream pass raw int, long and double values through specialised sinks, with no objects at all.

There are only three: short, byte and char widen to IntStream, and float to DoubleStream. Each has the usual intermediate operations with primitive functional interfaces (IntUnaryOperator, IntPredicate, from L83 and L84) plus numeric terminals the object stream lacks.

Creating them: range, rangeClosed, Arrays.stream

IntStream.range(0, 3);                              // 0, 1, 2      half-open, like a for loop
IntStream.rangeClosed(0, 3);                        // 0, 1, 2, 3   inclusive
LongStream.rangeClosed(1, 1_000_000_000L);
IntStream.of(3, 1, 2);
Arrays.stream(new int[] {3, 1, 2});                 // IntStream
Arrays.stream(new double[] {1.5, 2.5}, 0, 1);       // a slice
Stream.of(new int[] {3, 1, 2}).count();             // 1 -- a Stream<int[]> with one element!
orders.stream().mapToInt(Order::qty);               // from objects
new Random(7).ints(1_000, 0, 6);                    // dice rolls

DoubleStream has no range; build one with IntStream.range(0, n).mapToDouble(i -> i * 0.1) rather than accumulating a floating-point step. Stream.of(int[]) is the classic mistake: generics can't bind T to int, so the whole array becomes one element (L79).

Numeric terminals and IntSummaryStatistics

int[] qty = {3, 9, 4};
int sum           = Arrays.stream(qty).sum();                    // 16 -- an int, can overflow
OptionalDouble av = Arrays.stream(qty).average();                // OptionalDouble[5.333...]
OptionalInt max   = Arrays.stream(qty).max();                    // OptionalInt[9]
IntSummaryStatistics st = Arrays.stream(qty).summaryStatistics();
// IntSummaryStatistics{count=3, sum=16, min=3, average=5.333333, max=9}
long n = st.getCount(); long total = st.getSum(); double mean = st.getAverage();

IntStream.of(Integer.MAX_VALUE, 1).sum();                        // -2147483648: overflow
IntStream.of(Integer.MAX_VALUE, 1).asLongStream().sum();         // 2147483648
IntStream.empty().summaryStatistics();   // count=0, sum=0, min=2147483647, average=0.0, max=-2147483648
  • sum() on an IntStream returns int and wraps silently; widen first with asLongStream() or mapToLong. IntSummaryStatistics.getSum() is a long, so it doesn't overflow for int inputs.
  • average, max, min return OptionalDouble/OptionalInt, empty for an empty stream.
  • summaryStatistics() computes count, sum, min, max and average in one pass. On empty input it reports min = Integer.MAX_VALUE, max = Integer.MIN_VALUE and average 0: check getCount() before trusting the others. It is a mutable accumulator with accept and combine, so it also works as collect(IntSummaryStatistics::new, IntSummaryStatistics::accept, IntSummaryStatistics::combine).

Crossing over: boxed, mapToObj, asDoubleStream

List<Integer> list = IntStream.range(0, 5).boxed().toList();              // boxes on purpose
List<String> rows  = IntStream.rangeClosed(1, 3).mapToObj(i -> "row-" + i).toList();
double avgPrice    = IntStream.of(199, 250).asDoubleStream().map(c -> c / 100.0).average().orElse(0);
long bigTotal      = IntStream.of(3, 9, 4).asLongStream().map(q -> q * 1_000_000L).sum();

boxed() is mapToObj(Integer::valueOf): use it when an API needs objects (a List, a collector). asLongStream() and asDoubleStream() widen without boxing.

String.chars() and the (char) cast

"hé".chars().forEach(c -> System.out.print(c + " "));    // 104 233   -- ints, not letters
List<Character> cs = "hé".chars().mapToObj(c -> (char) c).toList();   // [h, é]
long units  = "a😀".chars().count();                      // 3 UTF-16 code units
long points = "a😀".codePoints().count();                 // 2 characters
List<String> glyphs = "a😀".codePoints().mapToObj(Character::toString).toList();  // [a, 😀]

chars() returns an IntStream of UTF-16 code units, so printing, collecting or appending the values gives numbers until you cast with (char). Characters outside the Basic Multilingual Plane, such as emoji, are two code units; codePoints() keeps them whole, and Character.toString(int) (Java 11) turns a code point into a String (L11).

Boxing in hot loops: evidence, and when the JIT removes it

Sum of squares over 10 million ints, measured with ThreadMXBean.getCurrentThreadAllocatedBytes and the best of 10 timed runs after warm-up, on one 12-core laptop with JDK 25. These are rough numbers from a hand-written harness, not JMH (L168); compare ratios, not absolute times.

VariantBest timeAllocated
Arrays.stream(arr).asLongStream().map(x -> x * x).sum()3.3 ms0 MB
plain for loop with a long accumulator3.8 ms0 MB
List<Integer>.stream().map(x -> (long) x * x).reduce(0L, Long::sum)70 ms240 MB

Boxed pipelines were 20 to 35 times slower here and allocated hundreds of megabytes per call. But not every box survives. HotSpot's C2 compiler uses escape analysis: if an allocated object provably never escapes the compiled code (it isn't stored in a field, returned, or passed to code that wasn't inlined), C2 can replace it with its fields in registers, and boxes are its favourite target. In the same harness, a box created and immediately unboxed (Integer b = i; s += b;), a Function<Integer, Integer> called in a loop, and IntStream.range(0, n).boxed().mapToInt(Integer::intValue).sum() all allocated 0 MB. Rerun with -XX:-DoEscapeAnalysis and they allocated 160 to 320 MB and took about ten times longer.

What defeats it: a box that is carried across iterations (the Long accumulator, or the running value inside reduce), stored in a collection (List<Integer>), or passed through a call the JIT didn't inline, which is common in long pipelines whose lambdas are called from many places. The practical rule: write mapToInt/IntStream for numeric pipelines because it is clearer and guaranteed, and don't assume the JIT will rescue a boxed design; profile allocation instead (L167).

What breaks in production
  • Silent int overflow. orders.stream().mapToInt(Order::cents).sum() wraps negative once revenue passes about 21 million dollars in cents. Use mapToLong.
  • Empty statistics. A dashboard shows a minimum of 2,147,483,647 because summaryStatistics() ran over an empty filter.
  • Characters as numbers. sb.append(c) inside chars().forEach appends digits, because append(int) is chosen; and splitting on code units mangles emoji in usernames.
  • GC pressure from boxed analytics. A boxed reduction over tens of millions of rows per request can allocate gigabytes per minute and turn into GC pauses under load.

L95 · DAY 95

Parallel Streams, Spliterator & When NOT To Use Them

50m video45m practice

Adding .parallel() asks the library to split the source with its Spliterator, run the chunks on the JVM-wide common ForkJoinPool, and merge the results. It pays off only when the source splits cheaply, the per-element work is large enough, and nothing in the pipeline forces ordering or shares mutable state. Otherwise it is slower, wrong, or harmful to the rest of the server, and only a measurement tells you which.

Turning it on, and where the threads come from

collection.parallelStream() or stream.parallel() sets one flag for the whole pipeline. Whichever of parallel() and sequential() is called last wins, so s.parallel().filter(f).sequential().map(m) runs entirely sequentially; you cannot make one stage parallel.

Definition · the common pool

Parallel streams run on ForkJoinPool.commonPool(), a single static pool shared by the whole JVM, also used by CompletableFuture.supplyAsync without an executor. Its parallelism defaults to Runtime.availableProcessors() - 1 (11 on a 12-thread laptop), because the thread that starts the terminal operation also takes chunks: one run of a parallel pipeline recorded 12 distinct threads, main plus 11 workers. Override it with -Djava.util.concurrent.ForkJoinPool.common.parallelism=N. Inside containers, availableProcessors follows the CPU limit.

Spliterator: how a source splits

A Spliterator<T> ("splittable iterator") is what every stream source provides:

  • boolean tryAdvance(Consumer<? super T>) feeds one element to the action, or returns false at the end; forEachRemaining does the rest in bulk.
  • Spliterator<T> trySplit() hands off a prefix of the remaining elements as a new spliterator and keeps the rest, or returns null if it can't split.
  • long estimateSize() is the remaining count, exact if SIZED; Long.MAX_VALUE means unknown.
  • int characteristics(): bit flags ORDERED, DISTINCT, SORTED, SIZED, SUBSIZED (splits are sized too), NONNULL, IMMUTABLE, CONCURRENT. An ArrayList reports ORDERED | SIZED | SUBSIZED.

The framework calls trySplit recursively until chunks are small, forks a task per chunk, and runs forEachRemaining on each. Balanced, cheap splits are the precondition for any speedup.

The NQ model, and measured numbers

Doug Lea's guidance on parallel streams frames the decision as N × Q: N elements times Q, the cost of processing each. Parallelism has fixed overheads (splitting, forking, merging, waking threads), so it needs enough total work to amortise them. The rule of thumb usually quoted from it is that N×Q should reach roughly 10,000 simple operations before parallel is even worth measuring. Source splittability and pipeline shape then decide how much of the core count you actually get.

The pattern: tiny N loses; cheap Q over a big array gains a little, because memory bandwidth, not the CPU, is the limit; expensive Q gains most, though rarely the full core count, because prime tests on larger numbers cost more (uneven chunks) and laptop cores aren't identical; and poor sources cap the gain or erase it.

Ordering costs and shared mutable state

Operations that depend on encounter order make parallel threads coordinate: findFirst, limit, skip and forEachOrdered must respect "first", and sorted and stable distinct are full barriers that buffer (L88). When order doesn't matter, say so with findAny, unordered(), or an unordered collector. Side effects on shared state are simply wrong:

List<Integer> unsafe = new ArrayList<>();
IntStream.range(0, 100_000).parallel().forEach(unsafe::add);
// three runs: size=12161, ArrayIndexOutOfBoundsException, size=19672

int[] counter = {0};
IntStream.range(0, 100_000).parallel().forEach(i -> counter[0]++);
// three runs: 32881, 38074, 40928 -- lost updates, never 100000

List<Integer> safe = IntStream.range(0, 100_000).parallel().boxed().toList();   // collect instead
long count = IntStream.range(0, 100_000).parallel().count();

Lambdas in a parallel pipeline must be stateless and non-interfering; the library makes reductions and collections safe by giving each chunk its own container (L90, L93). Locks or synchronized collections make the result correct and the pipeline slow, since every thread then queues on one lock.

Why parallel streams don't belong in request handlers

A web server already runs many requests in parallel, one thread each. If each handler calls parallelStream(), all of them share the same 11 common-pool workers: under load the workers are saturated, tasks queue, and each request waits for others' chunks. Throughput doesn't improve, because the cores were already busy, and tail latency gets worse. A parallel stream that does blocking I/O (an HTTP call or a query per element) is worse still: it ties up the few workers while they wait, starving every other user of the common pool, including CompletableFuture code elsewhere in the application. Concurrency for I/O is a job for executors and virtual threads (L137, L150); parallel streams are for CPU-bound batch work.

A known workaround runs a pipeline in a pool you own: tasks forked from inside a ForkJoinPool worker stay in that pool.

try (ForkJoinPool pool = new ForkJoinPool(4)) {             // AutoCloseable since Java 19
    long primes = pool.submit(() ->
            IntStream.range(0, 2_000_000).parallel().filter(Primes::isPrime).count()
    ).get();
}   // the run above used only ForkJoinPool-1-worker-1 … worker-4

This isolates batch work from the common pool, but it relies on an implementation detail that the Javadoc doesn't promise, so wrap it in one helper and keep a test that checks which threads ran.

What breaks in production
  • A "free speedup" that slows the service. .parallel() added to small collections in hot request paths adds overhead per call and contends for the common pool; p99 latency rises while CPU usage goes up.
  • Blocking I/O in parallel streams. ids.parallelStream().map(client::fetch) blocks common-pool workers and stalls unrelated CompletableFuture chains in the same JVM.
  • Wrong totals. Shared counters, HashMaps or ArrayLists mutated from forEach give different results per run and sometimes throw.
  • Benchmarks on a laptop, deployment on two vCPUs. With availableProcessors() == 2 the common pool has one worker, and the speedup measured on a developer machine is gone.

Optional: Correct Usage & Anti-Patterns

45m video45m practice

Optional<T> is a return type that says "there may be no result, and that is normal", so the caller can't forget to handle it. Used that way it removes a whole class of NullPointerExceptions; used as a field, a parameter or a collection element, it adds allocation and ceremony and solves nothing.

What problem it solves

Definition · Optional

A container holding either one non-null value or nothing. The Javadoc's API note states the intent: Optional "is primarily intended for use as a method return type where there is a clear need to represent 'no result,' and where using null is likely to cause errors. A variable whose type is Optional should never itself be null." It is a value-based class: don't compare instances with == or synchronise on them. It is not Serializable.

It arrived in Java 8 with streams, because findFirst, max and reduce must be able to say "empty input". A method returning User might return null, and nothing in the signature warns the caller; a method returning Optional<User> can't be used as a User without a decision about the empty case.

record Address(String city) {}
record User(long id, String name, Address address, Long managerId) {}   // used below

Optional<String> a = Optional.of("x");             // NullPointerException if the argument is null
Optional<String> b = Optional.ofNullable(maybe);    // empty if null
Optional<String> c = Optional.empty();

Getting the value out: get is a smell

Optional<User> u = repo.findById(42);
if (u.isPresent()) { greet(u.get()); }               // a null check with extra steps
u.ifPresent(this::greet);                             // better
u.ifPresentOrElse(this::greet, () -> log.info("no user 42"));   // Java 9
boolean missing = u.isEmpty();                        // Java 11

get() throws NoSuchElementException when empty, so isPresent() + get() is the old if (x != null) pattern, now with an object allocation. Java 10 added the no-argument orElseThrow(), which does exactly what get() does with a name that admits it, and the get() Javadoc calls it "the preferred alternative".

Transforming: map, flatMap, filter

String city = repo.findById(42)
        .map(User::address)                          // empty if address is null
        .map(Address::city)
        .filter(Predicate.not(String::isBlank))
        .orElse("unknown");

Optional<User> manager = repo.findById(42)
        .flatMap(usr -> Optional.ofNullable(usr.managerId()))
        .flatMap(repo::findById);                    // mapper already returns Optional

Fallbacks: or, orElse, orElseGet, orElseThrow

User fromCacheOrDb = cache.findById(42).or(() -> repo.findById(42)).orElseThrow();   // or: Java 9

User a = repo.findByEmail(email).orElse(createUser(email));          // BUG: always creates
User b = repo.findByEmail(email).orElseGet(() -> createUser(email)); // creates only if absent
User c = repo.findById(id).orElseThrow(() -> new UserNotFoundException(id));

orElse(x) takes a value, so Java evaluates x before the call, whether or not the optional is empty. With a constant (orElse("unknown")) that's fine. With a method call it is the classic bug: line a inserts a new user into the database on every call, including when one exists, and then throws the new one away. orElseGet(Supplier) runs the supplier only when empty (L84). or chains to another Optional-returning lookup; orElseThrow(Supplier) turns absence into your domain exception.

stream() (Java 9) gives a zero- or one-element stream, which is what makes ids.stream().map(repo::findById).flatMap(Optional::stream) work (L87). The primitive variants OptionalInt, OptionalLong and OptionalDouble avoid boxing but have no map, flatMap or filter.

Anti-patterns, and the rule: return types only

  • Optional fields. An extra object per field, not Serializable (a Serializable class with one fails with NotSerializableException), and not mappable as a JPA column. Keep the field nullable and expose an Optional getter: Optional<String> nickname() { return Optional.ofNullable(nickname); }.
  • Optional parameters. search(String q, Optional<Integer> limit) forces every caller to wrap, and still admits three states: present, empty and null. Use an overload, a default, or a parameter object.
  • Optional in collections. List<Optional<T>> should be the list of present values; Map<K, Optional<V>> duplicates what a missing key already means.
  • Optional of a container. Return an empty List, not Optional<List<T>> (Effective Java Items 54–55).
  • Serializing it. Java serialization rejects it, and Jackson handles it only with the jackson-datatype-jdk8 module (registered automatically by Spring Boot's JSON starter). DTOs should use nullable fields.
  • Returning null from an Optional method. The worst of both worlds; never do it.

The rule from the Javadoc and Effective Java Item 55: use Optional as a return type for queries whose "no result" is an expected outcome, and nowhere else by default.

Null vs Optional in a real service layer

interface UserRepository { Optional<User> findById(long id); Optional<User> findByEmail(String e); }

class UserNotFoundException extends RuntimeException {
    UserNotFoundException(long id) { super("user " + id + " not found"); }
}

class UserService {
    private final UserRepository repo;
    UserService(UserRepository repo) { this.repo = repo; }

    Optional<User> findByEmail(String email) {          // absence is normal: Optional
        return repo.findByEmail(email.strip().toLowerCase(Locale.ROOT));
    }
    User get(long id) {                                  // absence is an error: throw
        return repo.findById(id).orElseThrow(() -> new UserNotFoundException(id));
    }
}

Spring Data repositories already return Optional from findById. In the service, decide per method: a lookup whose miss is routine returns Optional; an operation that requires the entity (get, update) throws, and the web layer maps the exception to 404. Spring MVC's ResponseEntity.of(optional) turns an Optional into 200 or 404 directly. Inside a class, plain nullable fields and local null checks are fine; Optional is for the boundary.

What breaks in production
  • Eager orElse. orElse(createUser(e)), orElse(fetchRemoteDefault()): duplicate rows, wasted remote calls, unique-constraint violations under load.
  • get() without a check. findById(id).get() throws NoSuchElementException, which becomes a 500 with a message nobody understands. Use orElseThrow with a domain exception.
  • Optional in a cached or session object. Adding an Optional field to a Serializable class breaks session replication or a distributed cache at run time.

Stream Gatherers & Modern Stream Additions

40m video40m practice

For ten years the set of intermediate operations was closed: if map, filter and friends couldn't express it, you collected and started again, or hid state in a lambda. Stream.gather(Gatherer), final in Java 24, is the missing extension point: a user-defined intermediate operation that can keep state, emit any number of elements, stop early, and optionally run in parallel.

The gap gatherers fill

Collectors made terminal operations extensible (L93), but intermediate ones were fixed. "Running total", "batches of 100", "sliding average of the last 5", "first event per user", "take until the budget runs out" all need state that lives between elements, and the old workarounds were all poor: collect to a list and post-process (loses laziness, breaks on infinite streams), capture an AtomicLong in a map (wrong in parallel, L88), or write a custom Spliterator. Gatherers arrived as a preview in JDK 22 (JEP 461), a second preview in JDK 23, and became final in JDK 24 (JEP 485), so JDK 25 is the first LTS release that has them.

Definition · Gatherer<T, A, R>

Consumes Ts, keeps private state of type A, and pushes Rs downstream. Four functions, mirroring a collector:

  • initializer(): creates the state (optional for stateless gatherers);
  • integrator(): boolean integrate(A state, T element, Downstream<? super R> down), which may call down.push(r) zero or more times and returns false to stop the stream (short-circuit);
  • combiner(): merges two states, making the gatherer parallel-capable; without it, the gather stage runs sequentially;
  • finisher(): (state, down) runs at the end and may push remaining output, such as a partial last window.

Build them with Gatherer.ofSequential(...) or Gatherer.of(...); Integrator.ofGreedy marks an integrator that never short-circuits, which lets the library optimise. Gatherers compose with a.andThen(b) or by chaining .gather(a).gather(b).

Built-in gatherers

List<List<Integer>> batches = Stream.of(1, 2, 3, 4, 5).gather(Gatherers.windowFixed(2)).toList();
List<Double> movingAvg = Stream.of(10.0, 12.0, 14.0, 13.0)
        .gather(Gatherers.windowSliding(3))
        .map(w -> w.stream().mapToDouble(Double::doubleValue).average().orElseThrow())
        .toList();                                                     // [12.0, 13.0]
List<Integer> running = Stream.of(1, 2, 3, 4, 5).gather(Gatherers.scan(() -> 0, Integer::sum)).toList();

List<String> bodies = urls.stream()
        .gather(Gatherers.mapConcurrent(16, this::fetch))   // at most 16 in flight, order kept
        .toList();

mapConcurrent(maxConcurrency, mapper) runs the mapper on virtual threads with a concurrency cap and emits results in encounter order. Twenty 100 ms tasks with a cap of 10 took about 217 ms in one run. It is the right tool for bounded I/O fan-out, where a parallel stream is the wrong one (L95, L150).

Custom gatherers: running totals, dedupe by key, a stateful stop

static Gatherer<Long, long[], Long> runningTotal() {
    return Gatherer.ofSequential(
            () -> new long[1],                                   // state: one mutable long
            Gatherer.Integrator.ofGreedy((state, x, down) -> {
                state[0] += x;
                return down.push(state[0]);                      // false if downstream is done
            }));
}

static <T, K> Gatherer<T, ?, T> distinctBy(Function<? super T, ? extends K> key) {
    return Gatherer.ofSequential(
            HashSet<K>::new,
            Gatherer.Integrator.ofGreedy((seen, t, down) -> seen.add(key.apply(t)) ? down.push(t) : true));
}

static Gatherer<Long, long[], Long> takeWithinBudget(long budget) {
    return Gatherer.ofSequential(() -> new long[1], (spent, x, down) -> {
        spent[0] += x;
        return spent[0] <= budget && down.push(x);              // returning false stops the stream
    });
}

record Event(String userId, String action) {}
List<Long> totals = Stream.of(5L, 10L, 20L).gather(runningTotal()).toList();      // [5, 15, 35]
List<Event> firstPerUser = Stream.of(new Event("u1", "login"), new Event("u2", "login"),
        new Event("u1", "click")).gather(distinctBy(Event::userId)).toList();     // u1 and u2 logins
List<Long> affordable = Stream.iterate(1L, x -> x + 1).gather(takeWithinBudget(10)).toList(); // [1, 2, 3, 4]

The state lives inside the gatherer, created fresh by the initializer for each stream evaluation, so these are safe where a captured AtomicLong isn't. Because they are built with ofSequential, they also work inside a parallel pipeline: the gather stage simply runs sequentially there.

takeWhile vs a gatherer

takeWhile(pred) decides from each element alone. "Stop when the running total exceeds the budget" depends on all previous elements, which a stateless predicate can't see without smuggling in outside state. takeWithinBudget above is the honest version. Use takeWhile when the element suffices; use a gatherer when the decision needs memory.

On Java 17 LTS you have everything above except gatherers, and javac --release 21 or older reports cannot find symbol: Gatherer. Until you can move to 25, keep windowing and scans in small, well-tested helpers that take and return lists, or use a library such as StreamEx, and mark them for replacement. Don't ship the preview versions (JDK 22–23) to production: preview APIs carry no compatibility promise, and every JVM that runs the code needs --enable-preview. When you upgrade, the migration targets are hand-rolled running totals, "collect then batch" code, and filter(seen::add) dedupes.

What breaks in production
  • Shared state in a gatherer. A gatherer that keeps state in a field of the enclosing object, or in a captured collection, instead of in the initializer's state, leaks results between requests and breaks under concurrency.
  • Ignoring push's result. An integrator that keeps pushing after down.push(...) returned false wastes work, and on infinite sources may never finish.
  • Type inference in compositions. Gatherers.windowFixed(2).andThen(...) infers Object elements; write Gatherers.<Integer>windowFixed(2).
  • Unbounded windows of the whole stream. windowFixed(Integer.MAX_VALUE) or a gatherer that buffers everything until the finisher turns a lazy pipeline back into "load it all into memory".

Build an in-memory analytics engine over a million order lines using streams only: parse, reshape, aggregate, rank, and report. The point is not that streams are faster (sometimes they aren't) but that each metric becomes a short, independently testable pipeline whose correctness you can argue and whose parallel speedup you can measure.

The dataset and the shape of the engine

Loading: parse, reject, reshape

record LineItem(long orderId, String customerId, LocalDate date, String category,
                String sku, int qty, long unitCents) {
    long cents() { return qty * unitCents; }
    static Optional<LineItem> parse(String line) {
        String[] f = line.split(",", -1);
        if (f.length != 7) return Optional.empty();
        try {
            return Optional.of(new LineItem(Long.parseLong(f[0]), f[1], LocalDate.parse(f[2]), f[3], f[4],
                                            Integer.parseInt(f[5]), Long.parseLong(f[6])));
        } catch (RuntimeException e) { return Optional.empty(); }   // bad number or date
    }
}
record Order(long id, String customerId, LocalDate date, List<LineItem> lines) {
    long totalCents() { return lines.stream().mapToLong(LineItem::cents).sum(); }
}
record Quarter(int year, int q) implements Comparable<Quarter> {
    static Quarter of(LocalDate d) { return new Quarter(d.getYear(), (d.getMonthValue() - 1) / 3 + 1); }
    public int compareTo(Quarter o) { return year != o.year ? Integer.compare(year, o.year) : Integer.compare(q, o.q); }
}

static List<Order> load(Path csv) throws IOException {
    try (Stream<String> lines = Files.lines(csv)) {                  // close the file (L86)
        return lines.skip(1).map(LineItem::parse).flatMap(Optional::stream)
                .collect(groupingBy(LineItem::orderId)).values().stream()
                .map(ls -> new Order(ls.get(0).orderId(), ls.get(0).customerId(), ls.get(0).date(), ls))
                .toList();
    }
}

Money stays in long cents throughout (L90). A real engine also counts rejected rows (rows read minus items parsed) and fails the job if the reject rate passes a threshold, rather than dropping data silently (L87).

static long percentile(long[] sorted, double p) {            // nearest-rank method
    if (sorted.length == 0) throw new IllegalArgumentException("no data");
    int rank = (int) Math.ceil(p / 100.0 * sorted.length);
    return sorted[Math.max(rank, 1) - 1];
}
static String bucket(long months) {
    return switch ((int) months) {
        case 0 -> "M0"; case 1 -> "M1"; case 2, 3 -> "M2-3"; case 4, 5, 6 -> "M4-6"; default -> "M7+";
    };
}
Algorithm · Cohort retention
  1. For each customer, find the month of the first order: toMap with a "keep the earlier month" merge function. That month is the customer's cohort.
  2. For each order, compute the offset in months from its customer's cohort to the order's month, and map it to a bucket (M0, M1, M2-3, M4-6, M7+).
  3. Group by cohort, then by bucket, collecting the distinct customer ids (toSet(), then size), since one customer with five orders in a month is one retained customer.
  4. Retention for a bucket is its count divided by the cohort's M0 count. In the reference data the 2024-01 cohort had 1,352 customers in M0 and 1,060 active in M1.

Two more choices to defend in your write-up: nearest-rank percentiles return an actual order value (for an even count, p50 is the lower middle), and weightedAverage weights unit price by quantity, which is what "average price paid" means.

Imperative vs declarative

static Map<String, Map<Quarter, Long>> imperativeRevenue(List<Order> orders) {
    Map<String, Map<Quarter, Long>> rev = new TreeMap<>();
    for (Order o : orders) {
        for (LineItem l : o.lines()) {
            Map<Quarter, Long> byQ = rev.get(l.category());
            if (byQ == null) { byQ = new TreeMap<>(); rev.put(l.category(), byQ); }
            Quarter q = Quarter.of(l.date());
            Long cur = byQ.get(q);
            byQ.put(q, cur == null ? l.cents() : cur + l.cents());
        }
    }
    return rev;
}

Equal results, verified with equals on the two maps. On the reference machine the loop took 132 ms, the sequential stream 155 ms and the parallel stream 34 ms. That is the honest summary: a well-written loop is usually as fast as a sequential stream, sometimes a little faster. The stream version's advantages are elsewhere: it states the grouping instead of encoding it, it has no mutable intermediate state to get wrong, and it parallelises with one call. Scale that up and you have the refactoring this capstone asks for: an imperative engine with parsing, five metrics, null checks and manual map updates is typically a couple of hundred lines, and the goal is to bring it down to about 30 lines of pipelines plus small helpers, then compare the two for readability and speed.

What breaks in production
  • Heap. In the reference run the loaded orders retained about 267 MB, and with -Xmx256m the load failed with OutOfMemoryError. Size the heap from a measurement, or aggregate straight from the line stream without materialising orders.
  • Silent row loss. flatMap(Optional::stream) hides every malformed row. Count and log rejects.
  • Parallel in the wrong place. Running this engine with .parallel() inside a web request competes for the common pool with every other request (L95). Run it as a batch job or in its own pool.
