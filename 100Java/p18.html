L357 · DAY 357

Why Reactive: Blocking vs Non-Blocking & Backpressure

45m video35m practice

Reactive programming swaps "one blocked thread per request" for a few event-loop threads that never block, plus a demand protocol (backpressure) that stops fast producers from drowning slow consumers. It pays off only when concurrency is high, the work is I/O-bound, and every link in the chain is non-blocking. In 2026, virtual threads cover most of the remaining cases with ordinary blocking code.

What thread-per-request really costs

Classic Spring MVC on Tomcat gives each request a platform thread (an OS thread) from a pool of 200 by default (server.tomcat.threads.max). The thread runs your controller, calls the database, and then waits. Each platform thread reserves its stack up front (1 MB by default on 64-bit Linux HotSpot, committed lazily as it is touched) and has kernel bookkeeping. When there are many more runnable threads than cores, the scheduler context-switches between them; each switch costs on the order of microseconds plus cache and TLB pollution.

Worked example

Little's law: requests in flight = throughput × latency. A service doing 5,000 req/s with 100 ms latency, of which 95 ms is waiting on a downstream call, holds 5,000 × 0.1 = 500 requests in flight. Thread-per-request needs 500 threads, and each of them spends 95% of its life parked. The CPU is mostly idle while the pool runs out: the limit is the thread count, not the hardware.

C10K, C10M and the event loop

Dan Kegel's 1999 essay "The C10K problem" asked how one server could handle 10,000 concurrent connections. The answer was not more threads but non-blocking sockets plus readiness notification (epoll on Linux, kqueue on BSD/macOS): the kernel tells you which sockets are ready, and one thread services many of them. The later "C10M" discussion (Robert Graham, around 2013) pushed to ten million connections and moved the bottleneck into the kernel itself (kernel-bypass networking), which is beyond what a Java service needs, but the lesson is the same: waiting must not cost a thread.

Definition · Event loop

A thread that repeatedly asks a selector for ready I/O events and runs the registered handler for each one. Handlers must return quickly: they read what is available, start the next asynchronous operation, register a callback for its completion, and return. Netty (and Reactor Netty under WebFlux) runs a small group of loops, by default one per CPU core with a minimum of four, each owning many connections. The single rule: never block an event-loop thread, because every connection it owns stalls with it.

Asynchronous streams with non-blocking backpressure

Reactive programming models a computation as an asynchronous stream of signals: zero or more onNext items, then one terminal onComplete or onError. Operators (map, filter, flatMap) build a pipeline that runs when data arrives instead of a thread that waits for it. The part that makes it more than callbacks is backpressure: the consumer tells the producer how much it can handle with request(n), and the producer may never send more than has been requested.

A real example: a sensor feed emits 1,000 readings per second and the sink writes 100 per second to a database. Without backpressure the gap of 900 per second piles up in a buffer until the heap runs out. With it, the slow sink requests small batches, and the source must slow down, buffer within a bound, or drop by policy.

import java.time.Duration;
import org.reactivestreams.Subscription;
import reactor.core.publisher.BaseSubscriber;
import reactor.core.publisher.Flux;
import reactor.core.scheduler.Schedulers;

public class BackpressureDemo {
    public static void main(String[] args) {
        // Cold, demand-driven source: emits only what is requested.
        Flux.range(1, 6)
            .doOnRequest(n -> System.out.println("request(" + n + ")"))
            .subscribe(new BaseSubscriber<Integer>() {
                @Override protected void hookOnSubscribe(Subscription s) { request(2); }
                @Override protected void hookOnNext(Integer v) {
                    System.out.println("got " + v);
                    if (v % 2 == 0) request(2);          // ask for more only when ready
                }
            });

        // Time-driven source that cannot slow down: choose an overflow policy.
        Flux.interval(Duration.ofMillis(1))              // 1,000 ticks per second
            .onBackpressureDrop(n -> System.out.println("dropped " + n))
            .publishOn(Schedulers.boundedElastic(), 16)  // demand in batches of 16
            .doOnNext(n -> sleep(10))                    // slow consumer: 100 per second
            .take(30)
            .blockLast();
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

Remove onBackpressureDrop and Flux.interval fails with an OverflowException ("Could not emit tick … due to lack of requests"): Reactor refuses to buffer silently. The alternatives are onBackpressureBuffer(maxSize) and onBackpressureLatest().

Push, pull, and push-pull

ModelWho sets the paceExampleFailure mode

In push-pull the demand signal travels upstream asynchronously, so asking for more never blocks a thread. A fast consumer requests Long.MAX_VALUE and the stream behaves like pure push; a slow one requests a few at a time and it degrades smoothly towards pull.

The honest cost

  • Debugging. A stack trace shows Reactor operator internals on whatever thread delivered the signal, not the call path that assembled the pipeline. You need checkpoint("name"), Hooks.onOperatorDebug() (costly, dev only) or the ReactorDebugAgent from reactor-tools.
  • Learning curve. Nothing happens until you subscribe; map vs flatMap; cold vs hot; operator threading. Code review gets harder.
  • The whole chain must be non-blocking. One JDBC call, one Thread.sleep, one legacy SDK call on an event loop stalls every connection on that loop. Thread-local tools (MDC logging, SecurityContextHolder, @Transactional bound to a thread) need reactive replacements that use the subscriber Context.

When reactive wins, and the virtual-thread question

Reactive genuinely wins for high concurrency with I/O-bound work, streaming where backpressure matters (large exports, event feeds), SSE and WebSocket fan-out to many idle clients, and gateways that mostly shuffle bytes (Spring Cloud Gateway is built on WebFlux). It does not help CPU-bound work (you need cores, not fewer threads), simple CRUD at modest load, or stacks with blocking drivers: wrapping JDBC in Schedulers.boundedElastic() just rebuilds a thread pool with extra steps.

Virtual threads (JDK 21, JEP 444; see L151) change the default. A blocking call on a virtual thread unmounts it from its carrier thread, so a million mostly-waiting requests cost heap-allocated stack chunks, not OS threads. In Spring Boot 3.2+ one property, spring.threads.virtual.enabled=true, moves Tomcat request handling onto them, and you keep readable stack traces, ThreadLocals and JDBC. What they do not give you is backpressure or stream composition; limiting concurrency towards a fragile downstream still needs a semaphore or a bulkhead. Pinning inside synchronized blocks was a real problem until JDK 24 (JEP 491).

How to decide in 2026

Default to Spring MVC on virtual threads. Choose WebFlux when the problem is a stream (SSE, WebSocket, backpressured pipelines), when you are building a gateway, or when the whole stack is already non-blocking (WebClient, R2DBC, reactive Redis or MongoDB). Do not mix: a half-reactive service has the costs of both models and the benefits of neither.

What breaks in production
  • A blocking call on reactor-http-nio-*: latency spikes for every connection that loop owns. Run BlockHound in tests to turn this into a failure.
  • Calling block() inside a reactive handler: Reactor throws IllegalStateException ("block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-2").
  • onBackpressureBuffer() with no bound: you have moved the overflow to the heap, then to an OutOfMemoryError.
  • publishOn(boundedElastic()) on every call: thread-per-request again, with worse stack traces.

The Reactive Streams Specification

35m video35m practice

Reactive Streams is four tiny interfaces plus a set of rules, and the rule that matters is "never send more onNext signals than were requested". Every library you will use (Reactor, RxJava, Mutiny, Akka/Pekko Streams) implements this contract, which is why they interoperate and why you never write a Publisher by hand in production.

Four interfaces

InterfaceMethodsRole
Publisher<T>subscribe(Subscriber<? super T>)A possibly unbounded source of items. Does nothing until subscribed.
Subscriber<T>onSubscribe, onNext, onError, onCompleteReceives signals. All four return void.
Subscriptionrequest(long n), cancel()The link between one publisher and one subscriber; carries demand upstream.
Processor<T,R>both of the aboveA stage that is a subscriber upstream and a publisher downstream.

The package is org.reactivestreams (artifact org.reactivestreams:reactive-streams, version 1.0.4). Nothing in it says how to build pipelines; that is the job of a library. The interfaces only define how two stages talk.

The protocol and the request-n contract

A subscription moves through a fixed sequence: publisher.subscribe(s), then exactly one s.onSubscribe(subscription), then any number of subscription.request(n) calls from the subscriber, each allowing up to n more onNext signals, and finally at most one terminal signal, onComplete() or onError(t). Demand is cumulative: request(2) then request(3) means five outstanding.

This is the whole backpressure mechanism: the subscriber cannot be overwhelmed because it controls the only counter that permits delivery, and asking for more is an ordinary non-blocking method call. Long.MAX_VALUE means unbounded demand: the rules say demand of 263−1 or more may be treated as "effectively infinite", and that is what Reactor's plain subscribe(consumer) requests. Accumulated demand that would overflow is capped at Long.MAX_VALUE.

The rules implementations must obey

Definition · Key rules (spec 1.0.4)
  • 1.1 A publisher never signals more onNext than the total requested.
  • 1.3 Signals to a subscriber are serialized: never two at once, even from different threads, and each happens-before the next.
  • 1.7 After onComplete or onError, no further signals.
  • 2.13 Subscriber methods must return normally; a subscriber reports trouble by cancelling, not throwing. Signals never carry null.
  • 3.9 request(n) with n <= 0 must lead to onError(IllegalArgumentException).
  • Cancellation is idempotent and thread-safe, makes later request calls no-ops, and asks the publisher to eventually stop signalling and drop its reference to the subscriber. Items already in flight may still arrive.
  • Recursion: request may be called from inside onNext, and the publisher must bound the resulting synchronous recursion.

java.util.concurrent.Flow

JDK 9 (JEP 266) copied the same four interfaces, method for method, as nested types of java.util.concurrent.Flow: Flow.Publisher, Flow.Subscriber, Flow.Subscription, Flow.Processor, with the same rules. They are semantically equivalent but different types, so you need a bridge: org.reactivestreams.FlowAdapters (in the reactive-streams jar) or Reactor's JdkFlowAdapter.flowPublisherToFlux and publisherToFlowPublisher. The JDK ships one implementation, SubmissionPublisher, and the java.net.http.HttpClient body APIs are written against Flow.

A publisher and subscriber by hand, once

The publisher below emits a range of integers. The AtomicLong it extends is the outstanding demand, and also a lock-free "someone is already emitting" flag: only the call that moves demand from 0 to positive enters the drain loop, which gives serialized signals and no unbounded recursion.

import java.util.concurrent.Flow;
import java.util.concurrent.atomic.AtomicLong;

public record RangePublisher(int start, int count) implements Flow.Publisher<Integer> {
    @Override public void subscribe(Flow.Subscriber<? super Integer> s) {
        s.onSubscribe(new RangeSubscription(s, start, start + count));
    }

    static final class RangeSubscription extends AtomicLong implements Flow.Subscription {
        private final Flow.Subscriber<? super Integer> downstream;
        private final int end;
        private int index;                        // touched only by the draining thread
        private volatile boolean cancelled, badRequest;

        RangeSubscription(Flow.Subscriber<? super Integer> s, int from, int end) {
            this.downstream = s; this.index = from; this.end = end;
        }

        @Override public void request(long n) {
            if (n <= 0) { badRequest = true; n = 1; }   // report rule 3.9 from the drain loop
            long prev, next;
            do {
                prev = get();
                next = prev + n < 0 ? Long.MAX_VALUE : prev + n;   // cap overflow
            } while (!compareAndSet(prev, next));
            if (prev == 0) drain(next);           // 0 -> n transition wins the right to emit
        }

        private void drain(long n) {
            long e = 0;
            while (true) {
                while (e != n && index != end) {
                    if (cancelled) return;
                    if (badRequest) {
                        cancelled = true;
                        downstream.onError(new IllegalArgumentException("request must be > 0"));
                        return;
                    }
                    downstream.onNext(index++);
                    e++;
                }
                if (cancelled) return;
                if (index == end) { cancelled = true; downstream.onComplete(); return; }
                n = get();
                if (n == e) {                     // no new demand arrived while emitting
                    n = addAndGet(-e);
                    if (n == 0) return;
                    e = 0;
                }
            }
        }

        @Override public void cancel() { cancelled = true; }
    }
}
import java.util.concurrent.Flow;

final class TwoAtATime implements Flow.Subscriber<Integer> {
    private Flow.Subscription subscription;
    private int received;

    @Override public void onSubscribe(Flow.Subscription s) {
        if (subscription != null) { s.cancel(); return; }   // one active subscription only
        subscription = s;
        s.request(2);
    }
    @Override public void onNext(Integer item) {
        System.out.println("onNext " + item);
        if (++received % 2 == 0) subscription.request(2);   // re-entrant request is legal
    }
    @Override public void onError(Throwable t) { System.err.println("error " + t); }
    @Override public void onComplete() { System.out.println("complete"); }

    public static void main(String[] args) {
        new RangePublisher(1, 5).subscribe(new TwoAtATime());
    }
}

Now never do it again. Flux.range(1, 5) does the same thing, has been tested against the official TCK, and composes with every operator. If you ever must write a publisher (an adapter for some callback API), use Flux.create or Flux.push, and run the reactive-streams-tck verification against anything you hand-roll.

What breaks in production
  • Hand-rolled publishers that call onNext from two threads at once: corrupted operator state, lost items, heisenbugs. Rule 1.3 is the one people break.
  • Throwing from onNext: the exception escapes into the publisher's thread, often an event loop. Catch, cancel, and report.
  • "Backpressure" that is really unbounded: a plain subscribe() requests Long.MAX_VALUE, so a slow side effect inside it gets no protection.
  • Passing a Flow.Publisher where an org.reactivestreams.Publisher is expected: a compile error at best, a raw-type cast at worst. Use the adapters.

Reactor: Mono, Flux & Subscription Lifecycle

45m video50m practice

A Mono or Flux is a recipe, not a running computation: nothing happens until something subscribes, and each subscription to a cold publisher runs the recipe again. Most Reactor bugs come from forgetting one of those two facts, either by doing work eagerly while building the recipe or by subscribing twice without noticing.

Mono or Flux

Mono<T> emits zero or one item and then completes (or errors): a single HTTP response, findById, a computed result. Flux<T> emits 0..N items: query results, a message stream, ticks. Mono<Void> means "tell me when it is done". Choose Flux<T> when the consumer can process items as they arrive (streaming JSON, SSE); choose Mono<List<T>> only when the whole collection is needed at once, because it buffers everything in memory. Both implement org.reactivestreams.Publisher, and conversions are explicit: flux.next(), flux.collectList(), mono.flux(), mono.flatMapMany(...).

Creating publishers

import java.io.BufferedReader;
import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.time.Duration;
import java.util.List;
import reactor.core.publisher.Flux;
import reactor.core.publisher.FluxSink;
import reactor.core.publisher.Mono;

public class Creation {
    record Price(String symbol, double value) {}
    interface PriceListener { void onPrice(Price p); }
    interface Feed { void register(PriceListener l); void unregister(PriceListener l); }

    static void catalogue(Path path) {
        Mono<String> a = Mono.just("ready");                         // value already computed
        Mono<String> b = Mono.empty();
        Mono<String> c = Mono.error(new IllegalStateException("no stock"));
        Mono<String> d = Mono.fromCallable(() -> Files.readString(path)); // lazy, may throw checked
        Mono<Long>   e = Mono.fromSupplier(System::nanoTime);
        Flux<String> f = Flux.fromIterable(List.of("a", "b"));
        Flux<String> g = Flux.fromStream(() -> List.of("x", "y").stream()); // supplier: a Stream is single-use
        Flux<Integer> h = Flux.range(1, 10);
        Flux<Long>   i = Flux.interval(Duration.ofSeconds(1));         // runs on Schedulers.parallel()
    }

    static Flux<Long> fibonacci() {                 // generate: synchronous, one next() per call
        return Flux.generate(() -> new long[] {0, 1}, (st, sink) -> {
            sink.next(st[0]);
            long n = st[0] + st[1]; st[0] = st[1]; st[1] = n;
            return st;
        });
    }

    static Flux<Price> prices(Feed feed) {          // create: bridge a callback API (any thread)
        return Flux.create(sink -> {
            PriceListener l = sink::next;
            feed.register(l);
            sink.onDispose(() -> feed.unregister(l)); // cancel or terminate unregisters
        }, FluxSink.OverflowStrategy.LATEST);
    }

    static Flux<String> lines(Path p) {             // using: resource scoped to one subscription
        return Flux.using(() -> Files.newBufferedReader(p),
                          r -> Flux.fromStream(r.lines()),
                          Creation::closeQuietly);
    }

    static void closeQuietly(BufferedReader r) {
        try { r.close(); } catch (IOException e) { throw new UncheckedIOException(e); }
    }
}

Mono.fromFuture(() -> client.sendAsync(...)) takes a supplier so the future starts per subscription; the overload that takes a ready CompletableFuture has already started. Flux.push is create for a single producer thread. generate pulls one item per downstream request, so it honours backpressure naturally; create is push-based and needs an overflow strategy.

defer vs just: the eager-evaluation bug

Mono<Quote> eager = Mono.just(pricing.fetchQuote(id));               // runs NOW, on this thread
Mono<Quote> lazy  = Mono.fromCallable(() -> pricing.fetchQuote(id));  // runs per subscription
Mono<Quote> lazy2 = Mono.defer(() -> pricing.quoteMono(id));          // builds the inner Mono per subscription

repo.findById(id).switchIfEmpty(Mono.just(createDefault(id)));       // createDefault ALWAYS runs
repo.findById(id).switchIfEmpty(Mono.defer(() -> Mono.just(createDefault(id)))); // only when empty

Java evaluates arguments before the call, so Mono.just(x()) calls x() while assembling, even if nobody subscribes, and retry() on it replays the same captured value instead of calling again. just is for values you already have; defer, fromCallable and fromSupplier are for work.

Nothing happens until you subscribe

Assembly builds a chain of operator objects. subscribe walks it upstream, creating a subscriber per operator, then demand flows up and data flows down. The variants: subscribe() requests unbounded and ignores values; subscribe(onNext); subscribe(onNext, onError, onComplete). Each returns a Disposable whose dispose() cancels. Without an error consumer, an error is logged as ErrorCallbackNotImplemented. For manual demand, extend BaseSubscriber and call request(n) from hookOnSubscribe/hookOnNext (see L357). In WebFlux you almost never subscribe yourself: you return the publisher and the framework subscribes.

Definition · Lifecycle hooks

Side-effect operators that observe signals without changing them: doOnSubscribe, doOnRequest, doOnNext, doOnError, doOnComplete, doOnCancel, and doFinally(SignalType), which runs once after completion, error or cancellation, and so is the place for cleanup and metrics. log() prints every signal, including request(n), which makes it the fastest way to see backpressure.

Flux.range(1, 3)
    .doOnSubscribe(s -> System.out.println("subscribed"))
    .doOnNext(i -> System.out.println("next " + i))
    .doOnComplete(() -> System.out.println("complete"))
    .doOnCancel(() -> System.out.println("cancel"))
    .doFinally(sig -> System.out.println("finally " + sig))
    .take(2)
    .subscribe();
// subscribed, next 1, next 2, cancel, finally CANCEL   (take cancels upstream; no "complete")

Cold vs hot publishers

A cold publisher starts fresh for each subscriber: two subscriptions to a WebClient Mono send two HTTP requests. A hot publisher emits whether or not you listen, and late subscribers see only what comes after they join.

  • share() is publish().refCount(): connects on the first subscriber, cancels the source when the last one leaves. publish().refCount(2) waits for two; publish().autoConnect(n) never disconnects.
  • cache() replays everything (cache(n) or cache(Duration) to bound it). On a Mono it memoizes the result, including an error, unless you use the TTL overload cache(valueTtl, errorTtl, emptyTtl).
  • Sinks are the programmatic hot source: Sinks.many().multicast().onBackpressureBuffer(), .replay().limit(100), .unicast(), plus Sinks.one(). Expose sink.asFlux(). tryEmitNext returns an EmitResult: two threads emitting at once gets FAIL_NON_SERIALIZED, which drops the item if you ignore the result.

block() and BlockHound

block(), blockFirst() and blockLast() subscribe and park the calling thread until a result arrives. They are fine in main, a batch job or a test. Inside a reactive chain they are a production-stopping mistake: on an event loop the thread that would deliver the result may be the one you just parked, so throughput collapses or the request deadlocks. Reactor marks its event-loop and parallel() threads as non-blocking and throws IllegalStateException if you call block() on them. For everything else (Thread.sleep, JDBC, file I/O) add io.projectreactor.tools:blockhound to tests: BlockHound.install() instruments JDK blocking methods and throws BlockingOperationError when one runs on a non-blocking thread (on JDK 13+ run with -XX:+AllowRedefinitionToAddDeleteMethods).

What breaks in production
  • switchIfEmpty(Mono.just(save(...))): the save runs on every request, empty or not.
  • A cold Mono subscribed twice, for example once in a doOnNext side branch and once by the framework: duplicate HTTP calls or duplicate writes.
  • Mono.cache() on a token fetch: the first transient error is cached forever.
  • Flux.fromStream(stream) re-subscribed by retry(): "stream has already been operated upon or closed". Use the supplier overload.
  • A forgotten subscribe(): the code "runs" and nothing happens, with no error.

Reactor Operators I: Transform, Combine & Flatten

45m video55m practice

The flattening operators decide two things at once: how many inner publishers run concurrently, and whether results keep the source order. flatMap is concurrent and unordered, concatMap is sequential and ordered, flatMapSequential is concurrent and ordered, and switchMap keeps only the latest. Pick by those two properties, not by habit.

map vs the flattening family

map(f) is synchronous and 1:1: f returns a value and must not block. When f returns a publisher (a database call, an HTTP call), map would give you a Flux<Mono<T>> that nobody subscribes to. Flattening operators subscribe to each inner publisher and merge their outputs into one stream.

Definition · Flattening

A flattening operator maps each source item to an inner publisher, subscribes to it, and forwards the inner items downstream as one sequence. The variants differ in three ways only: how many inners may be subscribed at once, whether the output follows source order, and what happens to a running inner when the next source item arrives. An error from any inner terminates the whole result unless you handle it inside the inner.

import java.time.Duration;
import java.util.List;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

public class FlattenTimings {
    static Mono<String> lookup(int id) {               // id 1 slowest (300 ms), id 3 fastest (100 ms)
        return Mono.just("user-" + id).delayElement(Duration.ofMillis(400 - 100L * id));
    }

    static void time(String name, Flux<String> flux) {
        long t0 = System.nanoTime();
        List<String> out = flux.collectList().block();   // block() is fine in main
        System.out.printf("%-18s %s in %d ms%n", name, out, (System.nanoTime() - t0) / 1_000_000);
    }

    public static void main(String[] args) {
        var ids = Flux.range(1, 3);
        time("flatMap",           ids.flatMap(FlattenTimings::lookup));           // [user-3, user-2, user-1] ~300
        time("concatMap",         ids.concatMap(FlattenTimings::lookup));         // [user-1, user-2, user-3] ~600
        time("flatMapSequential", ids.flatMapSequential(FlattenTimings::lookup)); // [user-1, user-2, user-3] ~300
        time("switchMap",         ids.switchMap(FlattenTimings::lookup));         // [user-3] ~100
        time("flatMap(f, 1)",     ids.flatMap(FlattenTimings::lookup, 1));        // like concatMap ~600
    }
}

flatMap(f, concurrency) caps how many inners are subscribed at once (default 256). That cap is your backpressure towards a downstream service: flatMap(this::callInventory, 16) never has more than 16 calls in flight. flatMapSequential pays for ordering with a buffer: fast results wait for slow predecessors. switchMap cancels the previous inner when a new source item arrives, which is exactly typeahead search.

Filtering and defaults

filter(p); take(n) (cancels upstream after n and, since Reactor 3.5, also limits the request to n); takeUntil(p) (emits the matching item, then completes) vs takeWhile(p) (stops before it); skip(n); distinct(), which remembers every key it has seen and therefore grows without bound on an infinite stream; distinctUntilChanged(), which only drops consecutive repeats in constant memory; defaultIfEmpty(value); and switchIfEmpty(publisher), whose argument should be lazy (L359).

Aggregating and splitting

  • collectList(), collectMap(keyFn, valueFn): a Mono of the whole stream; only for bounded streams.
  • reduce(acc) emits the final accumulation; scan(acc) emits every intermediate one (running totals).
  • buffer(n), buffer(Duration), bufferTimeout(n, d) give Flux<List<T>> for batch inserts; window(n) gives Flux<Flux<T>> without materializing lists.
  • groupBy(keyFn) gives Flux<GroupedFlux<K,T>>. Every group must be consumed, and the number of live groups must stay below the downstream flatMap concurrency, or the pipeline stalls.
Flux<Item> allItems(ApiClient client) {
    return client.fetchPage(null)                           // Mono<Page>
        .expand(page -> page.nextToken() == null
                ? Mono.empty()
                : client.fetchPage(page.nextToken()))       // recursion, driven by demand
        .flatMapIterable(Page::items);
}

Flux<Map.Entry<String, Long>> perRegion(Flux<Order> orders) {
    return orders.groupBy(Order::region)                    // a handful of regions
                 .flatMap(g -> g.count().map(n -> Map.entry(g.key(), n)));
}

expand is breadth-first (expandDeep is depth-first); for a linear page chain they behave the same. Because it is demand-driven, allItems(client).take(7) fetches only the pages it needs.

Reusable chains: transform and transformDeferred

Function<Flux<Order>, Flux<Order>> cleaned =
    f -> f.filter(Order::valid).distinctUntilChanged(Order::id).log("orders");

orders.transform(cleaned);                                  // applied once, at assembly
orders.transformDeferred(CircuitBreakerOperator.of(breaker)); // applied per subscription

transform runs the function once while building the pipeline. transformDeferred runs it for every subscriber, so the operator can hold per-subscription state or read the subscriber's Context; Resilience4j's reactor operators are designed to be used this way.

What breaks in production
  • flatMap where the client expected order: paginated API results shuffle under load and only under load.
  • flatMap with the default concurrency of 256 against a service with a 20-connection pool: pending-acquire timeouts. Set the concurrency explicitly.
  • Mono.zip with an empty source: the whole response silently disappears (an empty 200).
  • groupBy on a high-cardinality key (order id) followed by flatMap(..., 4): a hang with no error.
  • collectList() or distinct() on an unbounded stream: a slow memory leak.

Reactor Operators II: Errors, Retries & Timeouts

45m video50m practice

In Reactor an error is a terminal signal that travels down the pipeline like data, so error handling is just more operators: replace, translate, retry or time out. Request-scoped data cannot live in a ThreadLocal because the thread changes under you, so it travels up the pipeline in the subscriber's Context instead.

Errors as signals

Mono.error(e) and Flux.error(e) create a publisher that only signals onError; an exception thrown inside map or filter is converted into the same signal. After onError the sequence is over. Every recovery operator therefore replaces the failed sequence; none of them can "continue" the original source.

OperatorEffectUse for
onErrorReturn(v)Emit a static fallback, completeNon-critical data: an empty recommendation list
onErrorResume(fn)Switch to a fallback publisherCache or secondary service; conditional handling by type
onErrorMap(fn)Translate the exception, still an errorTurning WebClientResponseException into a domain exception
doOnError(c)Observe only; error continuesLogging and metrics without handling
onErrorContinue(c)Drop the failing element upstream and keep goingAlmost never (see below)

All of these accept a Class or Predicate filter, as in onErrorResume(TimeoutException.class, e -> cache.get(id)). Why onErrorContinue is dangerous: it does not wrap anything below it; it puts a flag in the Context that tells supporting upstream operators to swallow errors and skip the element. That breaks the rule that errors are terminal, silently loses data, works only with some operators, and changes the behaviour of code far from where it is written. The safe pattern is to handle the error inside the inner publisher:

Flux<Result> processAll(Flux<Command> commands) {
    return commands.flatMap(cmd -> process(cmd)
        .doOnError(e -> System.err.println("failed " + cmd.id() + ": " + e))
        .onErrorResume(e -> Mono.empty()));          // drop just this element, explicitly
}

Retry with backoff, done properly

retry(n) resubscribes immediately up to n times. For a cold publisher, resubscribing re-runs the work (a new HTTP request), which is what you want; but immediate retries hammer a struggling service. retryWhen(Retry spec) adds delays, jitter, a filter and a custom exhaustion error.

import java.time.Duration;
import java.util.concurrent.TimeoutException;
import org.springframework.web.reactive.function.client.WebClient;
import org.springframework.web.reactive.function.client.WebClientRequestException;
import org.springframework.web.reactive.function.client.WebClientResponseException;
import reactor.core.publisher.Mono;
import reactor.util.retry.Retry;

public class QuoteClient {
    public record Quote(String sku, long cents) {}
    public static class QuoteUnavailableException extends RuntimeException {
        QuoteUnavailableException(String sku, Throwable cause) { super("quote unavailable: " + sku, cause); }
    }
    public static class UnknownSkuException extends RuntimeException {
        UnknownSkuException(String sku) { super("unknown sku: " + sku); }
    }

    private final WebClient web;
    public QuoteClient(WebClient web) { this.web = web; }

    public Mono<Quote> quote(String sku) {
        return web.get().uri("/quotes/{sku}", sku)
            .retrieve()
            .bodyToMono(Quote.class)
            .timeout(Duration.ofSeconds(2))                       // per attempt
            .retryWhen(Retry.backoff(3, Duration.ofMillis(200))   // ~200, 400, 800 ms
                .maxBackoff(Duration.ofSeconds(2))
                .jitter(0.5)                                      // each delay +/- up to 50%
                .filter(QuoteClient::isRetryable)
                .doBeforeRetry(s -> System.out.println("retry " + (s.totalRetries() + 1) + ": " + s.failure()))
                .onRetryExhaustedThrow((spec, s) -> new QuoteUnavailableException(sku, s.failure())))
            .onErrorMap(WebClientResponseException.NotFound.class, e -> new UnknownSkuException(sku))
            .timeout(Duration.ofSeconds(6))                       // overall budget, retries included
            .checkpoint("QuoteClient.quote");
    }

    static boolean isRetryable(Throwable t) {
        return t instanceof TimeoutException
            || t instanceof WebClientRequestException            // connect / I/O failures
            || (t instanceof WebClientResponseException r && r.getStatusCode().is5xxServerError());
    }
}
Definition · Backoff schedule

Delay before retry k is minBackoff × 2^k (k from 0), randomized by the jitter factor and capped by maxBackoff. A failure rejected by filter propagates unchanged and at once, so a 404 is never retried. Without onRetryExhaustedThrow, exhaustion raises an IllegalStateException ("Retries exhausted: 3/3") with the last failure as its cause. Position matters: a timeout above retryWhen limits each attempt; one below limits the total. Only retry operations that are safe to repeat; a retried POST /payments without an idempotency key charges twice.

Timeouts, repeat vs retry, and resource cleanup

timeout(Duration) errors with java.util.concurrent.TimeoutException and cancels upstream if no item arrives in time; on a Flux the timer restarts after every item. timeout(duration, fallback) switches to a fallback instead. Timers run on Schedulers.parallel() by default.

retry resubscribes after an error; repeat resubscribes after completion, which makes it a polling primitive: Mono.defer(this::poll).repeatWhenEmpty(10, f -> f.delayElements(Duration.ofSeconds(1))) polls until a value appears.

using(supplier, body, cleanup) ties a synchronous resource to one subscription. usingWhen is the reactive version: the resource is itself a publisher and cleanup returns a publisher, with optional separate handlers for complete, error and cancel, which is how reactive transactions commit or roll back.

Flux<String> names(io.r2dbc.spi.ConnectionFactory cf) {
    return Flux.usingWhen(cf.create(),
        conn -> Flux.from(conn.createStatement("SELECT name FROM customer").execute())
                    .flatMap(r -> r.map((row, meta) -> row.get("name", String.class))),
        io.r2dbc.spi.Connection::close);                  // runs on complete, error or cancel
}

Context instead of ThreadLocal

One request may run on several event-loop and scheduler threads, so a ThreadLocal set at the start is gone (or, worse, belongs to another request) a few operators later. Reactor's Context is an immutable map attached to the subscriber. contextWrite adds entries, and they are visible to operators above it in the code, because the context propagates upstream during subscription. You read it as a ContextView with Mono.deferContextual.

@Component
class TenantFilter implements WebFilter {
    @Override public Mono<Void> filter(ServerWebExchange ex, WebFilterChain chain) {
        String tenant = ex.getRequest().getHeaders().getFirst("X-Tenant");
        return chain.filter(ex)                            // everything the handler does is upstream
                    .contextWrite(Context.of("tenant", tenant == null ? "public" : tenant));
    }
}

Mono<String> currentTenant() {
    return Mono.deferContextual(ctx -> Mono.just(ctx.getOrDefault("tenant", "public")));
}

Spring uses the same mechanism: ReactiveSecurityContextHolder and reactive transactions live in the Context. Logging is the gap: SLF4J's MDC is thread-local. The Micrometer context-propagation library bridges it: register a ThreadLocalAccessor and turn on automatic propagation (Hooks.enableAutomaticContextPropagation(), or spring.reactor.context-propagation=auto in Spring Boot 3.2+), and Reactor restores the thread-locals from the Context around each operator. Micrometer Tracing already registers accessors for trace and span ids.

ContextRegistry.getInstance().registerThreadLocalAccessor(
    "tenant", () -> MDC.get("tenant"), v -> MDC.put("tenant", v), () -> MDC.remove("tenant"));

Readable stack traces

A reactive stack trace shows where the error was delivered, not where the pipeline was assembled. Three tools, in increasing cost: checkpoint("description") adds a named marker to any error that passes through (cheap; checkpoint(desc, true) also captures a stack trace); the ReactorDebugAgent.init() from reactor-tools rewrites operator call sites at class-load time to record assembly locations, cheap enough for production; Hooks.onOperatorDebug() captures a stack trace at every operator assembly, which is expensive and for development only.

What breaks in production
  • Retrying without a filter: validation errors and 401s are retried four times, multiplying load during an incident.
  • Retrying a non-idempotent call: duplicate orders or payments.
  • onErrorReturn(List.of()) with no logging: a downstream outage becomes an invisible "empty" result. Pair fallbacks with a metric.
  • contextWrite placed above the operator that reads it: the value is simply not there.
  • Hooks.onOperatorDebug() left on in production: a large throughput drop.

Schedulers, publishOn & subscribeOn

45m video45m practice

Reactor does not pick threads for you: a pipeline runs on whatever thread delivers its signals until an operator moves it. publishOn moves the signals flowing down from that point; subscribeOn moves the subscription flowing up, and with it the thread the source runs on. Knowing which one you need is how you keep blocking work off the event loop.

The default: no thread switching

Assembling a Flux creates no threads. When you call subscribe on main, a synchronous source such as Flux.range emits on main and every map runs there too. Thread changes come only from the source itself (Flux.interval and delayElements emit on Schedulers.parallel(); WebClient and R2DBC responses arrive on Netty event-loop threads) or from publishOn/subscribeOn. Operators after an asynchronous source simply continue on the thread that delivered the signal.

subscribeOn vs publishOn

Definition · The two operators

subscribeOn(s) runs the subscribe call on s as it travels upstream, so the source starts on s and, if the source is synchronous, emits there. Its position in the chain does not matter, and when there are several, the one closest to the source (the first in reading order) determines where the source runs.

publishOn(s) takes onNext/onComplete/onError signals from upstream, queues them (prefetch 256 by default), and re-emits them on s. Everything below it runs on s, until the next publishOn. You can use it as many times as you like.

import reactor.core.publisher.Flux;
import reactor.core.scheduler.Schedulers;

public class Threads {
    static int log(String stage, int v) {
        System.out.printf("%-5s %d on %s%n", stage, v, Thread.currentThread().getName());
        return v;
    }

    public static void main(String[] args) {
        Flux.range(1, 2)
            .map(i -> log("map1", i))                  // boundedElastic-1 (subscribeOn below decides)
            .publishOn(Schedulers.parallel())
            .map(i -> log("map2", i))                  // parallel-1
            .subscribeOn(Schedulers.boundedElastic())  // position irrelevant: moves the source
            .publishOn(Schedulers.single())
            .map(i -> log("map3", i))                  // single-1
            .blockLast();
    }
}

Wrapping a blocking call correctly

Mono<Customer> findCustomer(long id) {
    return Mono.fromCallable(() -> jdbc.queryForObject(
                "SELECT id, name FROM customer WHERE id = ?",
                (rs, n) -> new Customer(rs.getLong("id"), rs.getString("name")), id))
               .subscribeOn(Schedulers.boundedElastic());   // the callable runs off the event loop
}

Three details make this right. fromCallable defers the call to subscription time (with Mono.just it would already have run on the caller's thread). subscribeOn, not publishOn, is needed because the blocking work happens in the source. And downstream operators now run on the elastic thread; that is fine for light mapping, and WebFlux writes the response back through Netty regardless. Remember the real ceiling: with 8 cores, boundedElastic allows 80 threads but HikariCP may have 10 connections, so 70 threads queue on the pool.

True parallelism: parallel() and runOn()

List<String> hashes = Flux.fromIterable(documents)
    .parallel(Runtime.getRuntime().availableProcessors())   // split into rails
    .runOn(Schedulers.parallel())                           // without this, rails share one thread
    .map(Hashing::sha256)                                   // CPU-bound work, one rail per core
    .sequential()                                           // merge back (order not preserved)
    .collectList()
    .block();

parallel(n) alone only divides items round-robin into a ParallelFlux; runOn gives each rail its own worker. For I/O-bound fan-out, flatMap(..., concurrency) is usually simpler and keeps one pipeline.

Metrics and a starved boundedElastic

Wrap a scheduler with Micrometer.timedScheduler(scheduler, registry, "jdbc") from reactor-core-micrometer to get task counts, queue time and run time (the old Schedulers.enableMetrics() was deprecated in Reactor 3.5). Starvation looks like rising latency with idle CPUs; a thread dump shows every boundedElastic-* thread blocked (often inside the connection pool), and once queues fill, submissions fail with RejectedExecutionException ("Task capacity of bounded elastic scheduler reached"). Fixes, in order: make the work non-blocking, cap concurrency with flatMap(..., n) matched to the pool, isolate the dependency on its own newBoundedElastic.

What breaks in production
  • publishOn(boundedElastic()) placed after a blocking source: the block already happened on the event loop. Blocking sources need subscribeOn.
  • Blocking (JDBC, Thread.sleep) on parallel(): only a handful of threads exist, so all CPU work and timers stall.
  • Schedulers.newParallel(...) created per request and never disposed: a thread leak.
  • Assuming subscribeOn also moves downstream work off an asynchronous source: once the source hops to its own thread (Netty, a timer), downstream follows it.

Spring WebFlux Architecture

WebFlux reuses Spring MVC's annotations on top of a completely different runtime: a non-blocking server, a DispatcherHandler that returns a Mono<Void> instead of finishing on a thread, and codecs that read and write byte streams. The price of entry is that every link in the request path must be non-blocking.

DispatcherHandler and its three strategies

The server adapter (for Netty, ReactorHttpHandlerAdapter) turns each connection's request into a call to one HttpHandler. Spring builds that handler as a chain: WebFilters, then WebExceptionHandlers, then the DispatcherHandler, which delegates to three kinds of beans.

  • HandlerMapping finds the handler: RequestMappingHandlerMapping for @RequestMapping methods, RouterFunctionMapping for functional routes, SimpleUrlHandlerMapping for WebSocket and static resources.
  • HandlerAdapter invokes it, resolving arguments (reading the body through codecs) and producing a HandlerResult.
  • HandlerResultHandler turns the result into a response: ResponseEntityResultHandler, ResponseBodyResultHandler, ServerResponseResultHandler, ViewResolutionResultHandler.

Servers and the event loop

Reactor Netty is the default and the most common choice. WebFlux also runs on Undertow, and on Tomcat or Jetty through Servlet 3.1+ non-blocking I/O, which Spring adapts to its own HttpHandler contract (Spring Boot 4 dropped Undertow support). Reactor Netty's worker group defaults to one thread per core with a minimum of four (-Dreactor.netty.ioWorkerCount=N overrides it); the threads are named reactor-http-nio-N (or -epoll- with native transport). The absolute rule: never block one. Each event loop multiplexes many connections, so a 200 ms blocking call stalls every connection on that loop for 200 ms.

Exchange, filters and the classpath rule

@Component

    @Override public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        long start = System.nanoTime();

A WebFilter wraps the rest of the chain as a Mono<Void>, so "after" logic goes in operators on the returned Mono, not in code after a call. To change the request, build a new exchange with exchange.mutate().request(r -> r.header("X-Trace", id)).build(); the original is immutable.

Customize it with a WebFluxConfigurer bean; adding @EnableWebFlux switches Boot's configuration off, just as @EnableWebMvc does.   1. Database: R2DBC, reactive MongoDB or Cassandra, not JDBC or JPA.

Annotated Controllers in WebFlux

40m video50m practice

A WebFlux controller looks like an MVC controller that returns Mono and Flux, and the return type plus the media type decide how the response is written: one buffered JSON document, or a stream flushed item by item. The annotations are familiar; what is new is that the method must return quickly and never block.

Return types and the same annotations

@RestController, @GetMapping, @PathVariable, @RequestParam, @RequestBody and @Valid all work as in MVC. The method returns a publisher and WebFlux subscribes to it:

@RestController
@RequestMapping("/api/orders")
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    @GetMapping("/{id}")
    Mono<ResponseEntity<OrderDto>> get(@PathVariable UUID id) {
        return service.find(id)
                      .map(ResponseEntity::ok)
                      .defaultIfEmpty(ResponseEntity.notFound().build());   // empty Mono = 404
    }

    @GetMapping                                              // application/json: one JSON array
    Flux<OrderDto> list(@RequestParam(defaultValue = "OPEN") Status status) {
        return service.byStatus(status);
    }

    @GetMapping(value = "/export", produces = MediaType.APPLICATION_NDJSON_VALUE)
    Flux<OrderDto> export() {                              // one JSON object per line, flushed as rows arrive
        return service.streamAll();
    }

    @GetMapping(value = "/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    Flux<ServerSentEvent<OrderDto>> events() {
        return service.updates().map(o -> ServerSentEvent.builder(o)
                .id(o.id().toString()).event("order-updated").build());
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    Mono<OrderDto> create(@Valid @RequestBody CreateOrder body,
                          @AuthenticationPrincipal Jwt jwt) {
        return service.create(body, jwt.getSubject());
    }
}

With a plain @RequestBody CreateOrder, WebFlux decodes the body before calling you; with @RequestBody Mono<CreateOrder> you receive the decoding (and validation errors) as a signal and can compose on it. A Mono<Void> return means "200 with no body when done".

JSON array vs a stream

Definition · How a Flux is written

With application/json, the Jackson encoder collects the Flux into a list and writes one JSON array: the client sees nothing until the last element, and the whole result sits in memory. With a streaming media type, application/x-ndjson (APPLICATION_NDJSON_VALUE) or text/event-stream (TEXT_EVENT_STREAM_VALUE), each element is encoded and flushed individually, and backpressure from a slow client propagates through Netty into the Flux. SSE adds framing (id, event, retry, data) and browser auto-reconnect via EventSource; NDJSON is better for machine-to-machine exports.

Streaming a large result set: return the repository's Flux directly with NDJSON, as in export(). With R2DBC, rows are decoded as they arrive and memory stays flat whatever the row count; avoid collectList(), and add a timeout or take so a stuck client cannot hold a cursor open forever.

Exchange, principal and the security context

Any handler can declare a ServerWebExchange parameter for raw access to request, response, attributes and session. @AuthenticationPrincipal resolves the current principal (a Jwt, a UserDetails). Outside controllers, read it through ReactiveSecurityContextHolder.getContext(), which returns a Mono<SecurityContext> read from the Reactor Context that Spring Security's WebFilter wrote. It is a Context key, not a ThreadLocal, so it only works inside the request's reactive chain; SecurityContextHolder.getContext() is empty here.

Mono<String> currentUser() {
    return ReactiveSecurityContextHolder.getContext()
        .map(ctx -> ctx.getAuthentication().getName())
        .defaultIfEmpty("anonymous");
}

Exception handling, inside and outside the handler

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }

    @ExceptionHandler(WebExchangeBindException.class)        // @Valid failures in WebFlux

        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "validation failed");
        pd.setProperty("errors", e.getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage()).toList());

    }
}

@Component
@Order(-2)                                                    // before Boot's DefaultErrorWebExceptionHandler (-1)
class LastResortErrorHandler implements ErrorWebExceptionHandler {
    @Override public Mono<Void> handle(ServerWebExchange ex, Throwable t) {
        var res = ex.getResponse();
        if (res.isCommitted()) return Mono.error(t);          // too late to change status
        HttpStatusCode status = t instanceof ResponseStatusException r ? r.getStatusCode()
                                                                       : HttpStatus.INTERNAL_SERVER_ERROR;
        res.setStatusCode(status);
        res.getHeaders().setContentType(MediaType.APPLICATION_PROBLEM_JSON);
        byte[] body = ("{\"status\":" + status.value() + ",\"title\":\"request failed\"}")
                .getBytes(StandardCharsets.UTF_8);
        return res.writeWith(Mono.just(res.bufferFactory().wrap(body)));
    }
}

@ExceptionHandler methods (and the @RestControllerAdvice that hosts them) handle errors from controller methods, including error signals from the returned publisher. Errors raised outside a handler, in a WebFilter, in security, in a 404 with no matching route, reach WebExceptionHandler beans; Spring Boot registers a DefaultErrorWebExceptionHandler, and a custom ErrorWebExceptionHandler with higher precedence replaces it.

Correlation ids in a WebFilter

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class CorrelationIdFilter implements WebFilter {
    static final String HEADER = "X-Correlation-Id";

    @Override public Mono<Void> filter(ServerWebExchange ex, WebFilterChain chain) {
        String id = Optional.ofNullable(ex.getRequest().getHeaders().getFirst(HEADER))
                            .orElseGet(() -> UUID.randomUUID().toString());
        ex.getResponse().getHeaders().set(HEADER, id);
        ServerWebExchange mutated = ex.mutate().request(r -> r.header(HEADER, id)).build();
        return chain.filter(mutated).contextWrite(Context.of("correlationId", id));
    }
}

Downstream code reads the id from the Context, and with automatic context propagation (L361) logging can put it into MDC for every line of the request.

The classic mistake, measured

Worked example

A controller returns Mono.just(jpaRepository.findById(id).orElseThrow()). The JPA call runs on the event loop and takes 50 ms. With 4 event-loop threads, each can complete at most 1 / 0.05 = 20 requests per second, so the service tops out near 80 req/s whatever the concurrency, with CPU nearly idle. Load-test it with hey -z 30s -c 200 http://localhost:8080/api/blocking/42: throughput is flat and latency grows with the queue. Swap in an R2DBC repository and the same machine is limited by the database instead. Wrapping the call in fromCallable(...).subscribeOn(boundedElastic()) lifts the cap to 10 × cores threads: 40 threads on 4 cores, so about 40 / 0.05 = 800 req/s, and then the connection pool becomes the bound.

What breaks in production
  • A blocking repository behind a reactive controller (above). It passes every functional test and fails the first load test.
  • Returning a huge Flux as application/json and expecting streaming: it is buffered in full.
  • SSE behind a proxy that buffers responses or closes idle connections: add periodic heartbeat events and check the proxy's timeouts.
  • An ErrorWebExceptionHandler that writes to an already committed response: a second error and a truncated body.

Functional Endpoints: RouterFunction & HandlerFunction

40m video45m practice

Functional endpoints replace annotation scanning with two plain functions: a RouterFunction that maps a request to a handler, and a HandlerFunction that maps a ServerRequest to a Mono<ServerResponse>. Routing becomes ordinary code you can read top to bottom, compose, and unit-test without starting a server.

The two functions

Definition · Router and handler

HandlerFunction<T extends ServerResponse> is Mono<T> handle(ServerRequest), the equivalent of a controller method body. RouterFunction<T> is Mono<HandlerFunction<T>> route(ServerRequest): it returns the matching handler or an empty Mono. A RequestPredicate is a boolean test on the request (GET("/x"), accept(...), contentType(...), queryParam(...)) and composes with and, or, negate. Spring's RouterFunctionMapping picks up every RouterFunction bean and tries them in order.

Routes with the builder

import static org.springframework.web.reactive.function.server.RequestPredicates.accept;
import static org.springframework.web.reactive.function.server.RequestPredicates.contentType;
import static org.springframework.web.reactive.function.server.RequestPredicates.queryParam;

@Configuration
class OrderRoutes {
    @Bean
    RouterFunction<ServerResponse> orderRouter(OrderHandler h) {
        return RouterFunctions.route()
            .path("/api/orders", b -> b
                .GET("/{id}", accept(MediaType.APPLICATION_JSON), h::get)
                .GET(queryParam("status", s -> !s.isBlank()), h::byStatus)
                .GET(h::all)                                       // catch-all GET
                .POST(contentType(MediaType.APPLICATION_JSON), h::create))
            .filter((request, next) ->                               // applies to every route of this builder
                request.headers().firstHeader("X-Api-Key") == null
                    ? ServerResponse.status(HttpStatus.UNAUTHORIZED).build()
                    : next.handle(request))
            .after((request, response) -> {
                System.out.println(request.method() + " " + request.path() + " -> " + response.statusCode());
                return response;
            })
            .onError(OrderNotFoundException.class,
                     (e, request) -> ServerResponse.notFound().build())
            .build();
    }
}

Order matters: the first matching route wins, so the GET that requires a status parameter must come before the catch-all GET. path(prefix, builder) and nest(predicate, builder) group routes under a shared prefix or predicate. Without the builder, the static style composes the same way: route(GET("/a"), h1).andRoute(POST("/a"), h2).and(otherRouter), with RouterFunctions.nest(path("/api"), ...) for nesting. before(request -> ...) can replace the request (adding an attribute or header) before the handler runs; after sees both request and response; filter can short-circuit, as the API-key check does.

Handlers as plain beans

@Component
class OrderHandler {
    private final OrderService service;
    private final Validator validator;                       // jakarta.validation.Validator
    OrderHandler(OrderService service, Validator validator) { this.service = service; this.validator = validator; }

    Mono<ServerResponse> get(ServerRequest req) {
        UUID id = UUID.fromString(req.pathVariable("id"));
        return service.find(id)
            .flatMap(o -> ServerResponse.ok().contentType(MediaType.APPLICATION_JSON).bodyValue(o))
            .switchIfEmpty(ServerResponse.notFound().build());
    }

    Mono<ServerResponse> byStatus(ServerRequest req) {
        Status status = Status.valueOf(req.queryParam("status").orElseThrow());
        return ServerResponse.ok().body(service.byStatus(status), OrderDto.class);   // Flux body
    }

    Mono<ServerResponse> all(ServerRequest req) {
        return ServerResponse.ok().contentType(MediaType.APPLICATION_NDJSON)
                             .body(service.streamAll(), OrderDto.class);
    }

    Mono<ServerResponse> create(ServerRequest req) {
        return req.bodyToMono(CreateOrder.class)
            .doOnNext(this::validate)                             // no @Valid here: validate explicitly
            .flatMap(service::create)
            .flatMap(o -> ServerResponse.created(URI.create("/api/orders/" + o.id())).bodyValue(o));
    }

    private void validate(CreateOrder body) {
        var violations = validator.validate(body);
        if (!violations.isEmpty())
            throw new ServerWebInputException(violations.iterator().next().getMessage());
    }
}

ServerRequest exposes pathVariable, queryParam (an Optional), headers(), cookies(), attribute, principal() and the body as bodyToMono/bodyToFlux. ServerResponse is built with ok(), created(uri), status(...), notFound(), then header, contentType, and finally bodyValue(object) for a ready value, body(publisher, Class) for a Mono/Flux, or build() for no body. Handlers are normal beans: no reflection to resolve arguments, no annotation proxies, and constructor injection like anything else.

WebClient In Depth

45m video50m practice

WebClient is easy to call and easy to misconfigure: its defaults have no response timeout, generous pool waits and no idle eviction, which is exactly how one slow dependency becomes a cascading outage. Configure the connection layer explicitly, map errors with onStatus, and keep cross-cutting concerns in ExchangeFilterFunctions.

Building clients

WebClient.create() and WebClient.create(baseUrl) are for scripts. In Spring Boot, inject the auto-configured WebClient.Builder (it carries Boot's codecs and observation) and build one client per downstream service: baseUrl, defaultHeader, defaultUriVariables(Map), filter, codecs. A built WebClient is immutable and thread-safe; client.mutate() returns a builder seeded with its settings, for a variant with an extra header or filter.

@Configuration
class InventoryClientConfig {
    @Bean
    WebClient inventoryWebClient(WebClient.Builder builder) {
        ConnectionProvider pool = ConnectionProvider.builder("inventory")
            .maxConnections(50)                              // default 2 x max(cores, 8)
            .pendingAcquireMaxCount(200)                     // bounded wait queue
            .pendingAcquireTimeout(Duration.ofSeconds(2))    // default 45 s
            .maxIdleTime(Duration.ofSeconds(30))             // below the server / LB idle timeout
            .maxLifeTime(Duration.ofMinutes(5))
            .evictInBackground(Duration.ofSeconds(30))
            .build();
        HttpClient http = HttpClient.create(pool)
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2_000)  // default 30 s
            .responseTimeout(Duration.ofSeconds(3))               // default: none at all
            .doOnConnected(c -> c.addHandlerLast(new ReadTimeoutHandler(5, TimeUnit.SECONDS))
                                 .addHandlerLast(new WriteTimeoutHandler(5, TimeUnit.SECONDS)));
        return builder.baseUrl("https://inventory.internal")
            .clientConnector(new ReactorClientHttpConnector(http))
            .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
            .codecs(c -> c.defaultCodecs().maxInMemorySize(1024 * 1024))
            .filter(Filters.logging())
            .build();
    }
}

The settings whose absence causes outages

Definition · Pool and timeout settings
  • maxConnections: concurrent connections to one host. Requests beyond it wait in a queue bounded by pendingAcquireMaxCount for at most pendingAcquireTimeout, then fail with PoolAcquireTimeoutException.
  • maxIdleTime / maxLifeTime: close connections before a load balancer silently drops them. Without them you get PrematureCloseException: Connection prematurely closed BEFORE response on the first request after an idle period.
  • CONNECT_TIMEOUT_MILLIS: TCP connect.
  • responseTimeout: per request, the maximum gap between network reads once the request is sent, so it covers the wait for headers. ReadTimeoutHandler and WriteTimeoutHandler are the channel-level equivalents.

Why missing timeouts cascade: a dependency that hangs never fails, so callers hold connections and pending acquires until their callers time out and retry, which doubles the load on a service that is already stuck. A short, explicit timeout turns a hang into a fast, countable failure that a retry or circuit breaker can act on.

retrieve() vs exchangeToMono()

Mono<Stock> stock(String sku) {
    return web.get().uri("/stock/{sku}", sku)
        .retrieve()                                               // 4xx/5xx become WebClientResponseException
        .onStatus(s -> s.value() == 404, r -> Mono.error(new UnknownSkuException(sku)))
        .onStatus(HttpStatusCode::is5xxServerError, r -> r.bodyToMono(String.class).defaultIfEmpty("")
            .flatMap(body -> Mono.error(new InventoryUnavailableException(r.statusCode(), body))))
        .bodyToMono(Stock.class);
}

Mono<Optional<Stock>> stockIfKnown(String sku) {
    return web.get().uri("/stock/{sku}", sku)
        .<Optional<Stock>>exchangeToMono(r -> switch (r.statusCode().value()) {
            case 200 -> r.bodyToMono(Stock.class).map(Optional::of);
            case 404 -> r.releaseBody().thenReturn(Optional.empty());   // consume or release, always
            default  -> r.createError();                                 // WebClientResponseException
        });
}

retrieve() is the default: it decodes the body and turns error statuses into exceptions, which onStatus lets you map. exchangeToMono hands you the raw ClientResponse (status, headers, cookies) for status-dependent decoding. The body is a network stream: every branch must decode it or call releaseBody(). Spring releases an unconsumed body once the returned Mono completes (the old exchange() did not, and leaked connections), but never let the response escape the function.

Request bodies: bodyValue(obj) for an object you have, body(publisher, Type.class) for a Mono/Flux, BodyInserters.fromFormData("grant_type", "client_credentials").with("scope", "inventory") for forms, and BodyInserters.fromMultipartData(new MultipartBodyBuilder()...build()) for file uploads.

ExchangeFilterFunction: tokens, logging, metrics, resilience

final class Filters {
    static ExchangeFilterFunction bearer(Mono<String> token) {        // token: a cached, refreshing Mono
        return (request, next) -> token
            .map(t -> ClientRequest.from(request).headers(h -> h.setBearerAuth(t)).build())
            .flatMap(next::exchange);
    }

    static ExchangeFilterFunction logging() {
        return ExchangeFilterFunction.ofRequestProcessor(req -> {
            System.out.println(req.method() + " " + req.url());
            return Mono.just(req);
        });
    }

    static ExchangeFilterFunction circuitBreaker(CircuitBreaker cb) {    // Resilience4j
        return (request, next) -> next.exchange(request)
            .flatMap(r -> r.statusCode().is5xxServerError()
                    ? r.createException().flatMap(e -> Mono.<ClientResponse>error(e))  // count 5xx as failures
                    : Mono.just(r))
            .transformDeferred(CircuitBreakerOperator.of(cb));
    }
}

Filters wrap every call of a client, like servlet filters around a server. For OAuth2 client credentials, Spring Security's ServerOAuth2AuthorizedClientExchangeFilterFunction does the token caching for you. Metrics come for free when the client is built from Boot's builder: an http.client.requests observation per call. Keep retries at the call site (retryWhen with backoff and jitter, and a timeout, as in L361), because only the caller knows whether the operation is idempotent; a circuit breaker can sit in a filter because it is a property of the dependency.

R2DBC & Reactive Data Access

45m video55m practice

R2DBC makes SQL access non-blocking by changing the API, not the database: every call returns a Publisher. What you give up is the ORM. Spring Data R2DBC maps rows to objects and nothing more: no lazy loading, no dirty checking, no relationship mapping, so aggregates are assembled by hand.

Why JDBC blocks, and what R2DBC changes

JDBC is blocking by contract: executeQuery() returns a ResultSet and next() returns a boolean, so the calling thread must wait until the bytes arrive, whatever the driver does underneath. The R2DBC SPI returns publishers at every step: ConnectionFactory.create() gives Publisher<Connection>, Statement.execute() gives Publisher<Result>, and Result.map((row, meta) -> ...) gives Publisher<T>. Drivers are built on Netty, so a waiting query costs no thread, and demand can flow to the driver (r2dbc-postgresql switches to cursor-based fetching when a fetch size is set).

Programmatically, the same thing is ConnectionFactories.get(ConnectionFactoryOptions.builder().option(DRIVER, "postgresql").option(HOST, "db").option(DATABASE, "shop")...build()); in Boot, add options with a ConnectionFactoryOptionsBuilderCustomizer bean. Flyway and Liquibase have no R2DBC support, so give them a JDBC URL and the JDBC driver; they run once at startup, before traffic.

@Table("orders")
public record Order(@Id Long id,
                    @Column("customer_id") Long customerId,
                    String status,
                    BigDecimal total,
                    @Version Integer version) {}

public interface OrderRepository extends R2dbcRepository<Order, Long> {
    Flux<Order> findByCustomerIdAndStatus(Long customerId, String status);   // derived query

    @Query("SELECT * FROM orders WHERE total > :min ORDER BY total DESC LIMIT :n")
    Flux<Order> biggest(BigDecimal min, int n);                             // SQL, not JPQL

    @Modifying
    @Query("UPDATE orders SET status = :status WHERE id = :id")
    Mono<Long> updateStatus(Long id, String status);                       // rows updated
}
Definition · What Spring Data R2DBC is not

It is a row mapper with repositories, not an ORM. There is no JPQL, no persistence context, so no dirty checking (change a field and nothing is written until you call save), no lazy loading, and no relationship mapping: a field of type List<OrderLine> is not a join, it is a mapping error. save inserts when @Id is null and updates otherwise; @Version adds optimistic locking. Custom types need a @WritingConverter/@ReadingConverter pair registered in an R2dbcCustomConversions bean.

Relationships by hand

This is the biggest practical difference from JPA. Model each table as its own entity holding foreign-key ids, and assemble aggregates in the service. Load children for a page of parents with one IN query, not one query per parent:

record OrderView(Order order, List<OrderLine> lines) {}

Flux<OrderView> withLines(List<Order> page) {
    List<Long> ids = page.stream().map(Order::id).toList();
    return lineRepo.findByOrderIdIn(ids)                          // 1 query, not N
        .collectMultimap(OrderLine::orderId)
        .flatMapMany(byOrder -> Flux.fromIterable(page)
            .map(o -> new OrderView(o, List.copyOf(byOrder.getOrDefault(o.id(), List.of())))));
}

Transactions live in the Context

@Transactional                                  // R2dbcTransactionManager, auto-configured
public Mono<Order> place(Order order, List<OrderLine> lines) {
    return orders.save(order)
        .flatMap(saved -> lineRepo.saveAll(lines.stream().map(l -> l.withOrderId(saved.id())).toList())
                                  .then(Mono.just(saved)));
}

Mono<Order> placeProgrammatic(Order order, List<OrderLine> lines) {
    return place0(order, lines).as(transactionalOperator::transactional);   // TransactionalOperator
}

The transaction is bound to the subscription through the Reactor Context, not a ThreadLocal: it begins when the returned Mono is subscribed and commits when it completes (rolls back on error or cancel). So @Transactional only works on methods that return a publisher, and any work you subscribe() to separately inside the method runs outside the transaction.

Benchmarking R2DBC vs JDBC vs virtual threads

Run the same endpoint three ways (JDBC on platform threads, JDBC on virtual threads, R2DBC) against the same database with the same pool size, and measure throughput, p99 latency, thread count and heap under 200 to 2,000 connections. Published comparisons disagree, but the common pattern is that once the pool and the database are the bottleneck, all three reach similar throughput; platform threads lose first as concurrency grows; virtual threads and R2DBC stay flat in memory. JDBC drivers are more mature (batching, types, tooling), and recent pgjdbc versions avoid virtual-thread pinning. Treat any single result, including yours, as specific to driver, query shape and pool.

What breaks in production
  • JPA habits: mutating an entity and expecting it saved, or expecting order.getLines() to load.
  • N+1 through flatMap(o -> lineRepo.findByOrderId(o.id())) on a page of 500 orders: 501 queries and a drained pool.
  • A pool of 10 behind flatMap with concurrency 256: acquire timeouts. Match concurrency to max-size.
  • Using ConnectionFactory.create() directly and forgetting to close: leaked connections. Use DatabaseClient or usingWhen.

StepVerifier: scripting the signals

class StepVerifierBasicsTest {
    @Test void itemsThenComplete() {
        StepVerifier.create(Flux.just("a", "b", "c").map(String::toUpperCase))
            .expectNext("A")
            .expectNextMatches(s -> s.startsWith("B"))
            .assertNext(s -> assertThat(s).isEqualTo("C"))   // any assertion library
            .verifyComplete();                                // = expectComplete().verify()
    }

    @Test void manyItems() {
        StepVerifier.create(Flux.range(1, 1_000)).expectNextCount(1_000).verifyComplete();
    }

    @Test void translatedError() {
        Mono<String> failing = Mono.<String>error(new IllegalStateException("boom"))
            .onErrorMap(e -> new OrderException("order failed", e));
        StepVerifier.create(failing)
            .expectErrorMatches(e -> e instanceof OrderException && e.getCause().getMessage().equals("boom"))
            .verify(Duration.ofSeconds(1));                  // a timeout guards against hangs
    }
}

expectError(Class) checks only the type; expectErrorMatches takes a predicate. The rule people forget: a StepVerifier chain is only a description. Nothing runs until verify() (or a verifyXxx() shortcut) subscribes, so a test that ends at expectComplete() passes without testing anything.

Virtual time and backpressure

@Test void dailyTickInMilliseconds() {
    StepVerifier.withVirtualTime(() -> Flux.interval(Duration.ofHours(24)).take(3))  // build INSIDE the supplier
        .expectSubscription()
        .expectNoEvent(Duration.ofHours(24))     // advances the clock, asserts silence
        .expectNext(0L)
        .thenAwait(Duration.ofHours(48))         // advances the clock
        .expectNext(1L, 2L)
        .verifyComplete();
}

@Test void honoursDemand() {
    StepVerifier.create(Flux.range(1, 10), 0)    // initial request: 0
        .expectSubscription()
        .expectNoEvent(Duration.ofMillis(50))    // no demand, no items
        .thenRequest(3)
        .expectNext(1, 2, 3)
        .thenRequest(7)
        .expectNextCount(7)
        .verifyComplete();
}

The supplier matters: the publisher must be created after the virtual scheduler is installed, or interval grabs the real parallel scheduler and the test waits a real day. expectNoEvent treats the subscription itself as an event, hence the leading expectSubscription(). Passing an initial request of 0 and stepping with thenRequest(n) is how you prove an operator honours backpressure.

Binding options: bindToController(new OrderController(service)) for a pure unit test, bindToRouterFunction(routes) for functional endpoints (L365), bindToApplicationContext(ctx) for the full configuration, and bindToServer().baseUrl(...) for any running server, Spring or not. The closing comparison

Algorithm · A fair load test
  1. Build the same endpoint twice: Spring MVC + JDBC on virtual threads (spring.threads.virtual.enabled=true) and WebFlux + R2DBC + WebClient. Same JSON, same SQL, same 100 ms downstream call.
  2. Equalize the hidden limits: identical DB pool sizes; downstream HTTP pools large enough for 10,000 in flight; raise Tomcat's server.tomcat.max-connections (default 8192) and the OS file-descriptor limit.
  3. Drive 10,000 concurrent connections from a separate machine with a constant-rate tool (wrk2, k6, Gatling) so latency is not hidden by coordinated omission.
  4. Record throughput, p50/p99/p99.9 latency, heap and RSS, CPU, and live thread count, after warm-up, for at least five minutes per run.
  5. Repeat with a CPU-heavy variant and with a deliberately blocking call in each stack.

The honest verdict for a new project in 2026: start with Spring MVC on virtual threads; choose WebFlux when the product is a stream, a gateway, or heavy fan-out where backpressure and per-connection memory dominate, and when the whole stack can be non-blocking.

What breaks in production
  • Tests that never call verify(), or that subscribe with .subscribe() and assert before anything arrived: green builds, untested code.
  • A publisher built outside withVirtualTime's supplier: a CI job that hangs for a day.
  • Benchmarks that compare a 10-connection pool with a 50-connection pool and call it "reactive vs blocking".
