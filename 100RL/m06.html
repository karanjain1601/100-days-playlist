Planning, Models & Search

Modules 3–5 sat at two extremes: dynamic programming assumed a perfect model and never touched the world, while Monte Carlo and TD learned from the world and never used a model. This module fills in the middle. The agent learns a model from its own experience and plans with it (Dyna), chooses which imagined updates are worth the computation (prioritized sweeping, trajectory sampling, RTDP), and finally spends its computation at decision time on the state in front of it (Monte Carlo Tree Search). Everything is still tabular. Module 7 replaces the table with a function approximator, and Module 10 comes back to planning with learned deep models.

DAY 54

Models, Planning & Learning

35m video60m practice

A model is anything the agent can consult to predict how the environment will respond to an action. Planning is any computation that turns a model into a better policy, and it uses exactly the same update rules as learning. The only difference is whether the experience came from the world or was imagined.

Distribution models and sample models

Given a state and an action, a model predicts the next state and reward. Models come in two strengths, and which one you have decides which algorithms you can run.

Definition
  • A distribution model returns every possible outcome with its probability: \(\hat p(s', r \mid s, a)\) for all \(s', r\).
  • A sample model returns one outcome \((S', R)\) drawn from \(\hat p(\cdot \mid s, a)\).

Sutton & Barto's example is the sum of a dozen dice. A distribution model lists every sum from 12 to 72 with its probability; a sample model rolls twelve dice and reports one total. A distribution model can always generate samples, but recovering the distribution from a sample model means averaging many samples. In exchange, sample models are often far easier to build: a physics simulator, a game engine, or a learned network that outputs one plausible next state never has to enumerate anything. Dynamic programming (Module 3) needs a distribution model, because its expected update sums over all next states. Monte Carlo, TD, Dyna and tree search need only samples.

A model you learn by counting can serve both ways at once:

import random
from collections import Counter, defaultdict

class TabularModel:
    """Counts outcomes of each (s, a). Answers as a distribution model or as a sample model."""
    def __init__(self, seed=0):
        self.counts = defaultdict(Counter)       # (s, a) -> Counter{(s', r, terminal): n}
        self.rng = random.Random(seed)

    def update(self, s, a, r, s2, terminal):
        self.counts[(s, a)][(s2, r, terminal)] += 1

    def distribution(self, s, a):                # every outcome with its estimated probability
        c = self.counts[(s, a)]
        n = sum(c.values())
        return [(outcome, k / n) for outcome, k in c.items()]

    def sample(self, s, a):                      # one outcome drawn from p_hat(. | s, a)
        outcomes, weights = zip(*self.counts[(s, a)].items())
        return self.rng.choices(outcomes, weights)[0]

def expected_target(model, s, a, V, gamma):      # exact average over the model: costs b terms
    return sum(p * (r + (0.0 if term else gamma * V[s2]))
               for (s2, r, term), p in model.distribution(s, a))

def sample_target(model, s, a, V, gamma):        # one draw: noisy, but costs one term
    s2, r, term = model.sample(s, a)
    return r + (0.0 if term else gamma * V[s2])

Store the terminal flag in the model. A simulated transition obeys the same terminated-vs-truncated rule as a real one (Day 8): only true termination removes the bootstrap.

Planning is computation on a model

Sutton & Barto define planning as any computational process that takes a model as input and produces or improves a policy. This course only uses state-space planning, which searches through states and computes value functions, as opposed to plan-space planning, which searches over whole plans. All state-space planning methods share one pipeline, and learning shares most of it.

Learning and planning share the updates

Because the update doesn't care where its transition came from, any learning method becomes a planning method once you feed it simulated experience. The simplest example replaces the environment in Q-learning with a sample model:

Algorithm · Random-sample one-step tabular Q-planning
  1. Loop forever:
    1. Select a state \(S\) and an action \(A \in \mathcal A(S)\) at random.
    2. Send \(S, A\) to the sample model and obtain a next reward \(R\) and next state \(S'\).
    3. Apply one-step Q-learning: \(Q(S, A) \leftarrow Q(S, A) + \alpha\big[R + \gamma \max_a Q(S', a) - Q(S, A)\big]\).
Result · S&B §8.1

Random-sample one-step tabular Q-planning converges to the optimal policy for the model under the same conditions under which one-step tabular Q-learning converges to the optimal policy for the real environment: every state–action pair is selected infinitely often, and \(\alpha\) decreases according to the Robbins–Monro conditions (Day 5).

The phrase "for the model" carries the whole risk of model-based RL. If the model is wrong, the planner converges, reliably and efficiently, to the wrong answer. The rest of this module keeps the update fixed (almost always Q-learning) and varies everything around it: where the model comes from, which simulated transitions to generate (search control), and when to do the computation.

A chess engine is a decision-time planner: only the position on the board matters, and it has seconds to think. A controller running at 100 Hz can't search at every tick and needs its planning done in the background. Strong systems often do both. AlphaZero (Day 100) trains a value and policy network in the background and runs MCTS at decision time, with each improving the other.

Why plan at all: sample efficiency

Real experience is expensive: robot time, money, wear, risk, or simply the wall-clock of a slow simulator. Computation is cheap by comparison. A tabular Q-update costs microseconds; a real robot step can take a large fraction of a second. If a model lets every real transition be replayed in tens or hundreds of updates, you trade cheap computation for expensive data. Tomorrow's Dyna Maze makes this concrete: 50 planning updates per real step reduce the number of episodes needed from about 25 to about 3.

Intuition · a replay buffer is a model

TD learning already reuses experience a little: bootstrapping moves information one step back per update. A model lets you revisit any remembered transition, as often as you like, in any order. The replay buffer in DQN (Day 72) is exactly a non-parametric sample model that can only answer for transitions it has seen. "Model-based" vs "model-free" is a spectrum, not a binary.

What breaks · planning with a wrong model
  • The planner exploits model errors. It optimizes the model, not the world, and any error that makes some action look better than it is will be found and used. In deep model-based RL this is called model exploitation (Days 97–98).
  • Learned models are worst where data is thinnest, and the planner tends to steer exactly there, because that is where optimistic errors survive.
  • Distribution models scale badly. Storing \(\hat p\) costs up to \(|\mathcal S|^2|\mathcal A|\) entries, and every expected update pays the branching factor \(b\) (Day 58).
  • Long imagined rollouts compound errors. One-step tabular models avoid this, which is part of why Dyna is so robust. Day 97 measures how quickly errors grow with rollout length.

DAY 55

Dyna-Q

40m video105m practice

Dyna-Q is Q-learning with a memory. Each real transition is used once for a direct update, stored in a model, and then replayed as simulated experience in \(n\) further updates. On the Dyna Maze, \(n = 50\) learns the task in about three episodes where plain Q-learning needs about twenty-five.

Direct and indirect reinforcement learning

Real experience can improve the policy by two routes. Direct RL uses it to update values immediately, as Q-learning does. Indirect RL uses it to improve a model, and the model then improves the values through planning. Indirect methods squeeze more out of each real step. Direct methods are simpler and cannot be misled by a biased model. Dyna runs both routes at once with the same update rule.

The tabular model and search control

For a deterministic environment the model is a lookup table: after taking \(A\) in \(S\) and observing \(R, S'\), set \(\mathit{Model}(S, A) \leftarrow (R, S')\). The model can only answer for pairs it has seen, so search control samples a previously observed state uniformly at random and then an action previously taken in it. Two details matter in code. Store a terminal flag with each entry, so planning updates never bootstrap from a terminal state. And in a stochastic environment, don't store only the last outcome: keep counts and sample from them (the TabularModel of Day 54), or the model believes whatever happened most recently.

Algorithm · Tabular Dyna-Q (S&B §8.2)
  1. Initialize \(Q(s, a)\) and \(\mathit{Model}(s, a)\) for all \(s, a\).
  2. Loop forever:
    1. \(S \leftarrow\) current (non-terminal) state.
    2. \(A \leftarrow \varepsilon\text{-greedy}(S, Q)\).
    3. Take action \(A\); observe reward \(R\) and next state \(S'\).
    4. \(Q(S, A) \leftarrow Q(S, A) + \alpha\big[R + \gamma \max_a Q(S', a) - Q(S, A)\big]\) (direct RL)
    5. \(\mathit{Model}(S, A) \leftarrow R, S'\) (model learning, deterministic environment)
    6. Repeat \(n\) times: (planning)
      1. \(S \leftarrow\) a random previously observed state; \(A \leftarrow\) a random action previously taken in \(S\).
      2. \(R, S' \leftarrow \mathit{Model}(S, A)\).
      3. \(Q(S, A) \leftarrow Q(S, A) + \alpha\big[R + \gamma \max_a Q(S', a) - Q(S, A)\big]\).

Steps (d) and (f) are literally the same line of code. With \(n = 0\), Dyna-Q is one-step Q-learning.

The Dyna Maze

S&B Example 8.1 is a 6 × 9 grid with seven wall cells, so 47 states. There are four actions, the dynamics are deterministic, and moving into a wall or off the edge leaves the agent in place. Every reward is 0 except the transition into G, which gives +1 and ends the episode; the agent then restarts at S. The settings are \(\gamma = 0.95\), \(\alpha = 0.1\), \(\varepsilon = 0.1\), initial \(Q = 0\), and ties broken at random. The shortest path from S to G is 14 steps.

S&B's Figure 8.2 plots steps per episode, averaged over 30 repetitions, for \(n = 0, 5, 50\). The first episode is identical for every \(n\) (about 1,700 steps in their runs, since the seed was shared): nothing can be learned before the goal is first reached, because every reward until then is zero. After that the difference is large. The non-planning agent took about 25 episodes to reach \(\varepsilon\)-optimal performance, even though \(\alpha\) and \(\varepsilon\) were tuned for it; the \(n = 5\) agent took about 5; the \(n = 50\) agent took about 3.

Intuition · why planning helps this much

One-step Q-learning moves value back by one state per real visit, so a 14-step path needs many passes before the start state learns anything. In Dyna-Q, every real step is followed by \(n\) replays of remembered transitions, so value propagates back along the stored path without the agent walking it again. The direct update tells the model-free half the news; planning tells every predecessor the agent has ever seen.

import numpy as np

H, W = 6, 9
WALLS = {(1, 2), (2, 2), (3, 2), (4, 5), (0, 7), (1, 7), (2, 7)}
START, GOAL = (2, 0), (0, 8)
MOVES = [(-1, 0), (1, 0), (0, -1), (0, 1)]              # up, down, left, right

def env_step(s, a):
    r, c = s[0] + MOVES[a][0], s[1] + MOVES[a][1]
    if not (0 <= r < H and 0 <= c < W) or (r, c) in WALLS:
        r, c = s                                        # bumped into a wall: stay put
    return (r, c), float((r, c) == GOAL), (r, c) == GOAL

def dyna_q(n, episodes=50, alpha=0.1, gamma=0.95, eps=0.1, seed=0):
    rng = np.random.default_rng(seed)
    Q = np.zeros((H, W, 4))
    model, seen = {}, []                                # (s, a) -> (r, s', terminal)
    def backup(s, a, r, s2, done):                      # one update rule for real and simulated
        target = r + (0.0 if done else gamma * Q[s2].max())
        Q[s][a] += alpha * (target - Q[s][a])
    def greedy(s):                                      # random tie-breaking matters with Q = 0
        return int(rng.choice(np.flatnonzero(Q[s] == Q[s].max())))
    lengths = []
    for _ in range(episodes):
        s, t, done = START, 0, False
        while not done:
            a = int(rng.integers(4)) if rng.random() < eps else greedy(s)
            s2, r, done = env_step(s, a)                # (c) one real step
            backup(s, a, r, s2, done)                   # (d) direct RL
            if (s, a) not in model:
                seen.append((s, a))
            model[(s, a)] = (r, s2, done)               # (e) model learning
            for _ in range(n):                          # (f) planning
                ps, pa = seen[rng.integers(len(seen))]  # search control: uniform over seen pairs
                backup(ps, pa, *model[(ps, pa)])
            s, t = s2, t + 1
        lengths.append(t)
    return lengths

for n in (0, 5, 50):
    print(n, np.mean([dyna_q(n, seed=k) for k in range(30)], axis=0)[:10].round())

About 30 seconds in pure Python. The first episode is a random walk until the goal is found, so its length varies a lot across seeds (several hundred to a few thousand steps); after it, the ordering \(n = 50 < 5 < 0\) is unmistakable, and all three settle near 16 steps (the 14-step path plus \(\varepsilon\)-exploration).

What \(n\) buys and what it costs

Each real step now costs \(n + 1\) updates. Plotted against real experience, more planning is almost always better. Plotted against total computation, the picture changes: once the values on the remembered transitions have converged, further planning changes nothing until new experience arrives, and uniform search control spends most updates on pairs whose values are already right (Day 57 measures this). Report both axes when you compare planning agents.

Practical settings
  • In a deterministic environment the model gives the exact target, so \(\alpha = 1\) is safe for planning updates and speeds things up.
  • In a stochastic environment, sample planning outcomes from counts, or use the expected target over the counted distribution.
  • Always break ties at random. With all-zero initial values, np.argmax picks action 0 every time and the agent can bump into the same wall for thousands of steps.
What breaks
  • A last-outcome model in a stochastic world. The model believes the most recent outcome is certain, and planning amplifies that noise into the values.
  • No terminal flag in the model. Planning updates bootstrap from the goal's (meaningless) action values, and episodic values leak past the end of the episode.
  • Storing a time-limit truncation as termination. The model then contains a fake terminal transition that planning will replay forever.
  • The world changes. The model keeps describing the old world, and the planner confidently optimizes it. That is Day 56.

DAY 56

Dyna-Q+ & Changing Environments

35m video90m practice

A learned model is a memory of how the world used to be. If the world gets worse, following the model exposes the error and Dyna-Q repairs it. If the world gets better, nothing makes the agent look, and Dyna-Q never notices. Dyna-Q+ adds a bonus \(\kappa\sqrt{\tau}\) that makes long-untested transitions attractive to the planner.

Model staleness

When the environment changes, the model is wrong until the agent experiences the change. Model errors come in two kinds, and they behave completely differently.

  • Optimistic errors: the model promises more than the world delivers (a path it remembers has been blocked). The planner sends the agent down that path, the agent meets the wall, the model is corrected. These errors are self-correcting.
  • Pessimistic errors: the world has improved somewhere the model says nothing good happens (a shortcut has opened). The planner never sends the agent there, so the model is never corrected. These errors can last forever.

The second kind is an exploration problem, but one that planning makes worse: the better the planner, the more faithfully it avoids the region its model calls useless.

The blocking maze

In S&B Example 8.2 a barrier runs across the grid with a gap at its right end, giving a short path from S to G. After 1,000 time steps the gap moves to the left end: the short path is blocked and a longer one opens. S&B plot cumulative reward against time steps (Figure 8.4). Both Dyna-Q and Dyna-Q+ find the short path within the first 1,000 steps. When the change happens both curves go flat, a period with no reward while each agent wanders behind the barrier, following a plan that no longer works. Each walk into the wall corrects the model, the planner propagates the corrections, and both agents eventually find the new opening. Dyna-Q+ does better in both phases.

The shortcut maze

S&B Example 8.3 reverses the situation. Initially the only gap is on the left. After 3,000 steps a second gap opens on the right, creating a shorter path without disturbing the old one. In S&B's Figure 8.5, the regular Dyna-Q agent never switched to the shortcut. In S&B's words, it "never realized that it existed. Its model said that there was no shortcut, so the more it planned, the less likely it was to step to the right and discover it." Dyna-Q+ finds the shortcut and its cumulative reward pulls away.

Why ε-greedy doesn't rescue Dyna-Q

To discover the right-hand gap the agent has to walk about five cells to the right along the barrier, against a greedy policy that points left at every one of them. With \(\varepsilon = 0.1\) and four actions, one particular exploratory action has probability \(0.025\) per step, and five consecutive ones about \(0.025^5 \approx 10^{-8}\). Undirected, one-step dithering almost never produces a deliberate multi-step excursion. (This is a rough estimate, but the order of magnitude is the point.)

The exploration bonus κ√τ

Definition · Dyna-Q+ bonus

For each state–action pair keep \(\tau(s, a)\), the number of time steps since \((s, a)\) was last tried in the real environment. In planning updates, a modelled transition with reward \(r\) is backed up as if its reward were

$$r + \kappa\sqrt{\tau(s, a)},$$

for some small \(\kappa > 0\). Actions never tried from a visited state are added to the model as leading back to the same state with reward 0, so they collect the bonus too.

The bonus lives in the planning update, and that is what makes it work. A transition that hasn't been tried for a long time looks rewarding; planning propagates that value backwards, so the whole route towards it looks rewarding; the greedy policy then walks the route deliberately, several steps in a row. Exploration happens by planning rather than by dithering. S&B's Exercise 8.4 asks you to put the bonus only in action selection, \(\arg\max_a \big[Q(S_t, a) + \kappa\sqrt{\tau(S_t, a)}\big]\), instead: the bonus then stops propagating and the agent can only be tempted one step at a time.

Where √τ comes from (a heuristic, not a theorem)

Suppose a transition's true value drifts like a random walk, gaining independent noise of variance \(\sigma^2\) each step. After \(\tau\) steps without checking, its change has variance \(\tau\sigma^2\) and standard deviation \(\sigma\sqrt\tau\). Adding \(\kappa\sqrt\tau\) is an optimistic bonus proportional to that uncertainty: optimism in the face of uncertainty, as in UCB (Day 14), with uncertainty that grows with time since the last visit instead of shrinking with the visit count. S&B present Dyna-Q+ as a heuristic, and it carries no optimality guarantee.

Algorithm · Dyna-Q+ (changes to Dyna-Q)
  1. Keep \(\mathit{last}(s, a)\), the time step at which \((s, a)\) was last taken for real.
  2. When a state is visited for the first time, add \(\mathit{Model}(s, b) \leftarrow (0, s)\) and \(\mathit{last}(s, b) \leftarrow t\) for every action \(b\) not yet tried there.
  3. Planning samples among all modelled pairs and uses the target \(R + \kappa\sqrt{t - \mathit{last}(S, A)} + \gamma \max_a Q(S', a)\).
  4. Acting and the direct update are unchanged.
# Inside the real-step loop of the Day 55 code. t counts real steps; last = {}.
s2, r, done = env_step(s, a)
backup(s, a, r, s2, done)                              # direct RL: no bonus
if not any((s, b) in model for b in range(4)):         # first visit to s: model untried actions
    for b in range(4):                                 #   as "stay in s, reward 0"
        model[(s, b)], last[(s, b)] = (0.0, s, False), t
        seen.append((s, b))
model[(s, a)], last[(s, a)] = (r, s2, done), t         # the real outcome overwrites the guess
for _ in range(n):
    ps, pa = seen[rng.integers(len(seen))]
    pr, ps2, pdone = model[(ps, pa)]
    bonus = kappa * np.sqrt(t - last[(ps, pa)])        # kappa * sqrt(tau)
    backup(ps, pa, pr + bonus, ps2, pdone)

The price is a permanent exploration tax. In a world that never changes, Dyna-Q+ keeps re-checking transitions that are fine, and each check costs reward. S&B's Exercise 8.3 notes that the gap between the two agents narrows slightly during the first part of the shortcut experiment. In the course's reference runs with \(\kappa = 10^{-3}\), Dyna-Q+ actually collected somewhat less reward than Dyna-Q before the shortcut opened, then overtook it once it found the shortcut. How large the tax is depends on \(\kappa\).

What breaks
  • κ is on the reward scale. To pull the agent onto a detour, the bonus has to beat the value it gives up by detouring. Too small and nothing happens; too large and the agent spends its life re-checking. Rescale \(\kappa\) whenever you rescale rewards.
  • The bonus never stops growing. In a large state space there are always long-untried pairs somewhere, and the agent can be dragged around indefinitely. This is a tabular idea; Module 11 covers exploration bonuses that scale.
  • Noise looks like change. In a stochastic environment the bonus can't distinguish "this transition changed" from "this transition is noisy".
  • Q now includes the bonus. The values are no longer estimates of real return, so don't report them as such. Keep a separate bonus-free table for evaluation if you need one.

DAY 57

Prioritized Sweeping

40m video90m practice

Uniform search control spends almost every planning update on a transition whose value cannot change. Prioritized sweeping works backwards from wherever a value just changed: it keeps a queue of state–action pairs ordered by how much their values would move, and after each update it re-scores the predecessors of the state it touched.

Uniform sampling wastes updates

At the start of the second Dyna Maze episode exactly one action value is non-zero: the step into G. A planning update changes \(Q(s, a)\) only if its target \(r + \gamma \max_{a'} Q(s', a')\) differs from \(Q(s, a)\). For almost every remembered transition both are zero, so the update does nothing. With well over a hundred remembered pairs, a uniformly chosen planning update is useful roughly once in a hundred tries at this stage. As values spread, the useful updates stay concentrated on a thin frontier next to the states that most recently changed. In larger state spaces the useful fraction shrinks towards zero, so Dyna-Q's planning budget is mostly burned on no-ops.

Backward focusing

When the value of a state \(s\) changes, the only targets that change are those of transitions leading into \(s\): its predecessors. So planning should work backwards from any state whose value changed, which Sutton & Barto call backward focusing. The predecessors of a changed state may themselves change by different amounts. Those whose values would move most should go first, so we rank pairs by the magnitude of their TD error, the size of the change an update would make.

The algorithm

Algorithm · Prioritized sweeping, deterministic environment (S&B §8.4)
  1. Initialize \(Q(s, a)\), \(\mathit{Model}(s, a)\) for all \(s, a\), and an empty priority queue \(\mathit{PQueue}\).
  2. Loop forever:
    1. \(S \leftarrow\) current (non-terminal) state; \(A \leftarrow \text{policy}(S, Q)\).
    2. Take action \(A\); observe \(R, S'\). Set \(\mathit{Model}(S, A) \leftarrow R, S'\).
    3. \(P \leftarrow \big|R + \gamma \max_a Q(S', a) - Q(S, A)\big|\).
    4. If \(P > \theta\), insert \(S, A\) into \(\mathit{PQueue}\) with priority \(P\). (if already queued, keep only the higher priority)
    5. Repeat \(n\) times, while \(\mathit{PQueue}\) is not empty:
      1. \(S, A \leftarrow \text{first}(\mathit{PQueue})\); \(R, S' \leftarrow \mathit{Model}(S, A)\).
      2. \(Q(S, A) \leftarrow Q(S, A) + \alpha\big[R + \gamma \max_a Q(S', a) - Q(S, A)\big]\).
      3. For all \(\bar S, \bar A\) predicted to lead to \(S\): \(\bar R \leftarrow\) predicted reward; \(P \leftarrow \big|\bar R + \gamma \max_a Q(S, a) - Q(\bar S, \bar A)\big|\); if \(P > \theta\), insert \(\bar S, \bar A\) with priority \(P\).

Two new data structures appear. The predecessor table maps each state to the set of remembered pairs that lead into it, and is filled in as the model is learned. The priority queue holds pairs ordered by priority, and the threshold \(\theta\) keeps negligible changes out of it.

Implementation: one queue entry per pair

Python's heapq is a min-heap without a decrease-key operation. Push \((-p, s, a)\), keep a dictionary of each pair's live priority, and skip any popped entry whose priority no longer matches (lazy deletion). The parenthetical "keep only the higher priority" in the algorithm is not an optimization you can skip, as the trap box below explains.

import heapq
from collections import defaultdict

class PrioritizedSweeping:
    """Deterministic-model prioritized sweeping (S&B §8.4) with one live queue entry per pair."""
    def __init__(self, Q, n=5, alpha=1.0, gamma=0.95, theta=1e-4):
        self.Q, self.n, self.alpha, self.gamma, self.theta = Q, n, alpha, gamma, theta
        self.model, self.preds = {}, defaultdict(set)  # (s,a) -> (r,s',done);  s' -> {(s,a)}
        self.heap, self.prio = [], {}                  # heap of (-p, s, a); live priority per pair

    def _push(self, s, a, p):
        if p > self.theta and p > self.prio.get((s, a), 0.0):   # keep only the higher priority
            self.prio[(s, a)] = p
            heapq.heappush(self.heap, (-p, s, a))

    def _target(self, s, a):
        r, s2, done = self.model[(s, a)]
        return r + (0.0 if done else self.gamma * self.Q[s2].max())

    def observe(self, s, a, r, s2, done):              # call once per real transition
        self.model[(s, a)] = (r, s2, done)
        self.preds[s2].add((s, a))
        self._push(s, a, abs(self._target(s, a) - self.Q[s][a]))
        updates = 0
        while self.heap and updates < self.n:
            negp, ps, pa = heapq.heappop(self.heap)
            if self.prio.get((ps, pa)) != -negp:       # stale: superseded or already updated
                continue
            del self.prio[(ps, pa)]
            self.Q[ps][pa] += self.alpha * (self._target(ps, pa) - self.Q[ps][pa])
            updates += 1
            for qs, qa in self.preds[ps]:              # V(ps) may have moved: re-score predecessors
                self._push(qs, qa, abs(self._target(qs, qa) - self.Q[qs][qa]))
        return updates

Drop-in for steps (d)–(f) of the Day 55 loop: act ε-greedily on Q, step the environment, call ps.observe(s, a, r, s2, done). There is no separate direct update; the real transition enters the queue like any other. With a deterministic model, \(\alpha = 1\) makes each update exact.

How much it saves

S&B's Example 8.4 reports results (from Peng & Williams, 1993) on a sequence of mazes with the same structure as the Dyna Maze at increasing grid resolution, from 47 to roughly 6,000 states. Both prioritized sweeping and Dyna-Q were limited to \(n = 5\) updates per real step, and the measure was the number of updates until an optimal solution was found. Prioritized sweeping kept a decisive advantage at every size. S&B summarise its effect on maze tasks as speeding up the discovery of optimal solutions "often by a factor of 5 to 10".

The size of the factor depends on details: \(\alpha\), \(\varepsilon\), the optimality test, and how the larger mazes are built. In the course's reference runs of the code above (each Dyna Maze cell blown up into a \(k \times k\) block, deterministic model, \(\alpha = 1\), \(n = 5\), \(\varepsilon = 0.1\), five seeds, stopping when the greedy path from S is a shortest path), prioritized sweeping needed roughly 30 times fewer updates than Dyna-Q at 47 states and roughly 50 times fewer at 1,692 states. That is the "orders of magnitude" effect, but it is a count of updates, not of seconds: each prioritized update also pays for a heap operation and a scan of the predecessors.

Stochastic environments

With stochastic dynamics, keep counts for each \((s, a)\) and the outcomes seen after it (the Day 54 TabularModel), and replace the sample update with an expected one over the estimated distribution:

$$Q(s, a) \leftarrow \sum_{s', r} \hat p(s', r \mid s, a)\Big[r + \gamma \max_{a'} Q(s', a')\Big].$$

Priorities become the magnitude of the change this expected update would make, and every pair with a non-zero estimated probability of reaching \(s\) counts as a predecessor of \(s\). The weakness is cost: each expected update sums over all \(b\) observed successors, including very unlikely ones, so a large branching factor makes every update expensive. Van Seijen & Sutton (2013) proposed "small backups", which fold in one successor's change at a time and make the cost independent of \(b\). Day 58 makes the expected-vs-sample trade-off precise.

Beyond tables

Prioritized experience replay (Day 77) keeps "prioritize by \(|\delta|\)" but drops the predecessor structure. With function approximation there is no table of "pairs that lead into this state" to re-score, so PER only refreshes the priorities of transitions it happens to sample, and it corrects the sampling bias with importance weights.

What breaks
  • No de-duplication. If every re-score pushes a fresh entry, each stale duplicate that is later popped re-pushes all of its still-pending predecessors. The number of entries then grows with the number of backward paths, which in a grid is combinatorial. In the course's reference implementation this bug made prioritized sweeping worse than Dyna-Q on a 188-state maze: the queue grew to tens of thousands of entries and no value reached the start state for dozens of episodes.
  • Fast planning on a partial model commits early. Prioritized sweeping computes exact values for the transitions it knows, so the greedy policy locks onto the first route it found, and ε-dithering rarely discovers a better one. Two of the five 752-state reference runs never found the shortest path within 300,000 steps. Combine it with optimistic initial values or a Dyna-Q+ bonus.
  • θ too large. Priorities shrink geometrically with distance from the change (\(1, \gamma, \gamma^2, \dots\)), so a coarse threshold stops the sweep before it reaches the far side of a large maze.
  • Memory. The predecessor table is as large as the model, and in stochastic environments each pair can have many predecessors.

Expected vs Sample Updates & Trajectory Sampling

35m video60m practice

An expected update is exact but costs as much as the branching factor \(b\); a sample update costs one successor and is noisy. When \(b\) is large, a few dozen sample updates remove most of the error for a small fraction of the price of one expected update. And spending updates where the policy actually goes (trajectory sampling, RTDP) beats sweeping states that never matter.

The space of one-step updates

Every one-step update in Modules 3–5 is fixed by three binary choices: state values or action values; evaluating a policy \(\pi\) or the optimal policy (an expectation over \(\pi\) or a max); and an expected update over all successors or a sample update from one.

$$\text{expected:}\quad Q(s, a) \leftarrow \sum_{s', r} \hat p(s', r \mid s, a)\Big[r + \gamma \max_{a'} Q(s', a')\Big],$$ $$\text{sample:}\quad Q(s, a) \leftarrow Q(s, a) + \alpha\Big[R + \gamma \max_{a'} Q(S', a') - Q(s, a)\Big], \qquad (S', R) \sim \hat p(\cdot \mid s, a).$$

Comparing them under a compute budget

Count computation in evaluations of \(\max_{a'} Q(s', a')\). An expected update of a pair with \(b\) possible successors costs \(b\) of them and has no sampling error; a sample update costs one and has sampling error. In the time of one expected update you could do \(b\) sample updates, possibly spread over \(b\) different pairs. Which is better?

Derivation · error of sample updates (S&B §8.5)

Take one pair with \(b\) equally likely successors and suppose the successors' values are already correct, so the expected update gives the exact answer. Write \(x_i = r_i + \gamma \max_{a'} Q(s'_i, a')\) for the \(b\) possible targets; the true value is their mean \(\bar x\). Start from an estimate whose error is 1 and use sample averages, \(\alpha_t = 1/t\). The first sample update replaces the initial estimate entirely, and after \(t\) updates the estimate is the mean of \(t\) targets drawn uniformly, with replacement, from \(\{x_1, \dots, x_b\}\). One draw has variance \(s^2 = \frac1b \sum_i (x_i - \bar x)^2\), so the mean of \(t\) independent draws has

$$\E\big[(\hat Q_t - \bar x)^2\big] = \frac{s^2}{t}.$$

If the \(b\) targets are themselves spread with unit variance (independent draws with variance 1), then \(\E[s^2] = \frac{b-1}{b}\), the usual bias of the \(1/b\)-normalized sample variance. The RMS error after \(t\) sample updates is therefore

$$\sqrt{\frac{b-1}{b\,t}},$$

which is the curve S&B plot in Figure 8.7. An expected update drives the error from 1 to 0, but only once all \(b\) computations are done.

For moderately large \(b\), the error falls dramatically after a tiny fraction of \(b\) sample updates. In the time one pair receives an expected update, many pairs can each be brought to within a few percent of what an expected update would achieve. There is a second advantage the figure leaves out: in a real problem the successors' values are estimates being updated too, and because sample updates spread computation around, those successors become accurate sooner, which makes the values backed up from them better. S&B suggest that the figure therefore understates the case for sample updates.

Expected updates win when \(b\) is small (with \(b = 2\), two computations give an exact answer while two samples leave error 0.5), when the dynamics are nearly deterministic (with \(b = 1\) the two updates coincide), when you need exact final values, or when the distribution model is cheap to sum over.

Distributing updates: uniform vs on-policy

Classical DP sweeps the whole state space and gives every state equal time, including states no good policy ever visits. The alternative is to sample states or pairs from some distribution. Uniform sampling is a randomized sweep. The on-policy distribution instead samples states as often as the current policy visits them. Writing that distribution down explicitly would be hard, but trajectory sampling produces it for free: simulate trajectories from the start states under the current policy and update the states and pairs encountered along the way.

S&B test this in Figure 8.8 on randomly generated episodic tasks with 1,000 and 10,000 states. Each state has two actions, each leading to one of \(b\) equally likely next states (\(b = 1, 3, 10\)), every transition ends the episode with probability 0.1, and expected rewards are drawn from a standard normal. The uniform planner cycles through all pairs with in-place expected updates; the on-policy planner simulates episodes from one start state and applies expected updates to the pairs visited under an \(\varepsilon\)-greedy policy with \(\varepsilon = 0.1\). The measure is the value of the start state under the current greedy policy. On-policy sampling planned faster at first and more slowly in the long run. The early advantage was larger and lasted longer when \(b\) was small and when the state space was larger.

Intuition

Early on, what matters for the start state is the states a few steps downstream of it, and trajectories visit exactly those. Later, the commonly visited states already have correct values and updating them again is wasted, while uniform updates still improve the rarely visited states that occasionally matter. For planning from a known start state in a large problem, the early phase is usually the one you care about.

Real-Time Dynamic Programming

RTDP (Barto, Bradtke & Singh, 1995) is the on-policy, trajectory-sampling version of value iteration. It is asynchronous DP (Day 33) in which the order of updates is set by real or simulated trajectories.

Algorithm · RTDP
  1. Initialize \(V(s)\) optimistically (for example 0 in a cost-to-go problem), with \(V = 0\) at goal states.
  2. For each episode, start at a start state \(s\), and until a goal is reached:
    1. For every action, compute \(Q(s, a) = \sum_{s', r} p(s', r \mid s, a)\big[r + \gamma V(s')\big]\).
    2. \(V(s) \leftarrow \max_a Q(s, a)\) (the value-iteration update, at the visited state only)
    3. Take a greedy action \(a \in \arg\max_a Q(s, a)\) and sample \(s' \sim p(\cdot \mid s, a)\); set \(s \leftarrow s'\).
Theorem · RTDP convergence (Barto, Bradtke & Singh 1995; S&B §8.7)

Consider an undiscounted episodic task with absorbing goal states that generate zero reward. If (1) every goal state has initial value 0, (2) there is at least one policy that reaches a goal with probability 1 from any start state, (3) every reward from a non-goal state is strictly negative, and (4) every initial value is at least its optimal value (initializing everything to 0 satisfies this), then RTDP converges with probability 1 to a policy that is optimal on all relevant states, those reachable from a start state under some optimal policy, without necessarily visiting every state infinitely often, or at all.

Optimism is what makes it work. Unvisited states look at least as good as they really are, so the greedy policy is drawn to try them, and each update can only lower a value towards the truth. Irrelevant states, those off every good path, eventually stop being tried. In S&B's racetrack example (Example 8.6), only a small fraction of the reachable states were relevant, and RTDP reached policies as good as those of sweeping value iteration with roughly half the updates, and most states were updated far fewer times than a sweep would have updated them.

import numpy as np

N, SLIP, START = 30, 0.1, (0, 0)
GOAL = (0, N - 1)
MOVES = [(-1, 0), (1, 0), (0, -1), (0, 1)]

def outcomes(s, a):
    """(prob, next state) pairs: the intended move w.p. 1 - SLIP, plus SLIP spread over all four."""
    out = []
    for b, (dr, dc) in enumerate(MOVES):
        p = (1 - SLIP) * (b == a) + SLIP / 4
        out.append((p, (min(max(s[0] + dr, 0), N - 1), min(max(s[1] + dc, 0), N - 1))))
    return out

def q_value(V, s, a):                       # expected update: reward -1 per step, gamma = 1
    return sum(p * (-1.0 + V[s2]) for p, s2 in outcomes(s, a))

def rtdp(episodes=500, seed=0):
    rng = np.random.default_rng(seed)
    V = np.zeros((N, N))                    # 0 >= v* everywhere: optimistic, as the theorem needs
    n_updates = np.zeros((N, N), dtype=int)
    for _ in range(episodes):
        s = START
        while s != GOAL:                    # V[GOAL] stays 0: the absorbing goal
            qs = [q_value(V, s, a) for a in range(4)]
            a = int(np.argmax(qs))          # greedy with respect to the current values
            V[s] = qs[a]                    # value-iteration update at the visited state only
            n_updates[s] += 1
            probs, nexts = zip(*outcomes(s, a))
            s = nexts[rng.choice(4, p=probs)]
    return V, n_updates

V, n_updates = rtdp()
print(V[START], n_updates.sum(), np.median(n_updates))

A 30 × 30 grid with 10% slip and a cost of 1 per step. In the course's reference run, RTDP's start-state value was within 0.1 of \(v_*\) after about 34,000 updates, while in-place value iteration needed about 63,000 to converge to \(10^{-4}\). Optimism made RTDP touch every state at least once on this open grid, but the median state was updated about 24 times, against roughly 70 times for every state under value iteration, while states along the main route were updated hundreds of times. The saving comes from where the updates go, not from skipping states.

What breaks
  • Starved states. On-policy focusing leaves rarely visited states with poor values. If the start distribution changes, or you need a policy for every state, those values are unusable.
  • RTDP without its conditions. With pessimistic initial values (below \(v_*\)) or positive rewards, greedy RTDP can settle on a bad policy and never update the states that would reveal a better one. The guarantee leans on all four conditions.
  • Expected updates on a thin model. With a learned \(\hat p\) built from two or three samples, an "expected" update is a sample update in disguise, at \(b\) times the price.
  • Counting updates, not computation. One expected update costs \(b\) successor evaluations. Comparisons should count those, as Figure 8.7 does.

Monte Carlo Tree Search

45m video105m practice

MCTS is decision-time planning with a sample model. From the current state it runs many simulated games, keeps statistics in a tree that grows towards the most promising lines, and then picks a move. UCT makes the choice inside the tree by treating every node as a bandit and applying UCB1.

Decision-time planning: from rollouts to trees

Heuristic search (S&B §8.9) is the classical form of decision-time planning: expand a tree of continuations from the current state, evaluate the leaves with a heuristic or value function, back the values up to the root with max and expectation, act, and throw the tree away. Rollout algorithms (S&B §8.10) replace the heuristic with simulation. For each action available now, run many simulated trajectories that start with that action and then follow a fixed rollout policy, average their returns, and take the action with the highest average. This is one step of policy improvement on the rollout policy: by the policy improvement theorem (Day 29), acting greedily on accurate rollout estimates is at least as good as the rollout policy itself. Tesauro & Galperin (1997) used rollouts of a backgammon program to improve substantially on the program's own play.

A rollout algorithm wastes what it learns: statistics live only at the root, so every simulation re-plays the second move as blindly as the first. MCTS keeps statistics for every node it has visited, so later simulations follow better moves deeper into the tree.

The four phases

Algorithm · MCTS (one iteration, repeated until the budget runs out)
  1. Selection. From the root, follow the tree policy through nodes whose actions have all been tried, until reaching a node with an untried action or a terminal state.
  2. Expansion. Add a child for one untried action.
  3. Simulation. From the new node, play to the end of the game (or to a depth limit, then evaluate) with the rollout policy, often uniformly random. Nothing from this part is stored.
  4. Backup. Walk back up the path to the root, incrementing each node's visit count \(N\) and adding the result to its total value \(W\).

When the budget is spent, play the root action whose child has the most visits.

Tree policy vs rollout policy

The two policies do different jobs. The tree policy acts where statistics exist, and at every node it faces a bandit problem: exploit the child that looks best, or explore one whose estimate is still uncertain. The rollout policy acts where there are no statistics, and its main requirement is speed, because most of the computation goes into rollouts. Domain knowledge in the rollout policy usually helps, but not always: Gelly & Silver (2007) found in Go that a stronger rollout policy can produce a weaker search, because what matters is whether the rollouts give unbiased evaluations, not whether they play well.

UCT: UCB1 at every node

UCT (Kocsis & Szepesvári, 2006) is MCTS whose tree policy is UCB1 (Day 14) applied at every node. With \(N(s)\) the visits of the current node, and \(N(s, a)\), \(W(s, a)\) the visits and total value of the child reached by \(a\):

$$a^* = \argmax_a \left[\frac{W(s, a)}{N(s, a)} + c\,\sqrt{\frac{\ln N(s)}{N(s, a)}}\,\right].$$
Derivation · where the bonus comes from

For rewards in \([0, 1]\), Hoeffding's inequality bounds the chance that an average of \(n\) samples overestimates its mean by \(\varepsilon\): \(\Pr(\bar X_n \ge \mu + \varepsilon) \le e^{-2n\varepsilon^2}\). Choose \(\varepsilon\) so that this probability is \(t^{-4}\) at time \(t\):

$$e^{-2n\varepsilon^2} = t^{-4} \iff \varepsilon = \sqrt{\frac{2\ln t}{n}}.$$

That is UCB1's bonus (Auer et al. 2002), the case \(c = \sqrt 2\). Kocsis & Szepesvári write the bonus as \(2C_p\sqrt{\ln n / n_j}\), so \(C_p = 1/\sqrt 2\) recovers UCB1. The bonus shrinks like \(1/\sqrt{N(s, a)}\) for a child that keeps being chosen and grows slowly, like \(\sqrt{\ln N(s)}\), for one that is neglected, so every child is tried infinitely often, but suboptimal ones only logarithmically often.

Theorem · UCT consistency (Kocsis & Szepesvári 2006)

In finite-horizon problems with rewards in \([0, 1]\), and with a suitable exploration constant, the probability that UCT selects a suboptimal action at the root converges to zero, at a polynomial rate, as the number of simulations grows, and the estimated value at the root converges to the optimal value. The analysis has to handle the fact that each child's reward distribution drifts as the subtree below it improves; plain UCB1 analysis assumes stationary arms.

The guarantee is asymptotic and the constant matters in practice. Treat \(c\) as a hyperparameter tied to the scale of the rewards and to the budget, and tune it per game; Project 5 does exactly that. In a two-player zero-sum game, store each node's \(W\) from the point of view of the player who made the move into it. The parent then simply maximizes, and the same code serves both players.

import math
import random

class Node:
    def __init__(self, state, parent=None, action=None):
        self.state, self.parent, self.action = state, parent, action
        self.children, self.untried = [], list(state.legal_actions())
        self.N, self.W = 0, 0.0      # visits; total result for the player who moved INTO this node

    def select_child(self, c):       # UCB1 over the children
        log_n = math.log(self.N)
        return max(self.children, key=lambda ch: ch.W / ch.N + c * math.sqrt(log_n / ch.N))

def mcts(root_state, n_sims=1000, c=1.4, rng=random):
    root = Node(root_state)
    for _ in range(n_sims):
        node = root
        while not node.untried and node.children:          # 1. selection
            node = node.select_child(c)
        if node.untried:                                   # 2. expansion: one new child
            a = node.untried.pop(rng.randrange(len(node.untried)))
            node.children.append(Node(node.state.play(a), node, a))
            node = node.children[-1]
        state = node.state                                 # 3. simulation: random rollout
        while not state.is_terminal():
            state = state.play(rng.choice(state.legal_actions()))
        while node is not None:                            # 4. backup
            node.N += 1
            if node.parent is not None:
                node.W += state.result(node.parent.state.to_move)
            node = node.parent
    return max(root.children, key=lambda ch: ch.N).action # most-visited ("robust") child
class TicTacToe:
    LINES = [(0, 1, 2), (3, 4, 5), (6, 7, 8), (0, 3, 6), (1, 4, 7), (2, 5, 8), (0, 4, 8), (2, 4, 6)]

    def __init__(self, board=(None,) * 9, to_move=0):
        self.board, self.to_move = board, to_move

    def winner(self):
        for i, j, k in self.LINES:
            if self.board[i] is not None and self.board[i] == self.board[j] == self.board[k]:
                return self.board[i]
        return None

    def is_terminal(self):
        return self.winner() is not None or None not in self.board

    def legal_actions(self):           # must be empty at terminal states
        return [] if self.is_terminal() else [i for i, x in enumerate(self.board) if x is None]

    def play(self, a):                 # returns a new state: the tree keeps the old ones
        b = list(self.board)
        b[a] = self.to_move
        return TicTacToe(tuple(b), 1 - self.to_move)

    def result(self, player):          # 1 win, 0.5 draw, 0 loss, from `player`'s point of view
        w = self.winner()
        return 0.5 if w is None else float(w == player)

print(mcts(TicTacToe(), n_sims=2000))  # usually 4, the centre

In the course's reference test, 1,000 simulations per move won 96 and drew 4 of 100 games against a random player (alternating who starts) and lost none; MCTS against itself drew 19 of 20 games. Tic-Tac-Toe is a draw under perfect play, so self-play draws are the expected outcome.

Anytime behaviour and the final move

MCTS is an anytime algorithm: you can stop after any number of simulations and get a move, and more simulations give a better one. That makes it easy to fit into a time budget. Which child to play is a separate choice from the tree policy. Browne et al. (2012) list several rules: the max child (highest mean value), the robust child (most visits), and combinations. The robust child is the usual default. UCB1 sends most visits to the child it believes is best, and a child with few visits may have a high mean by luck.

Tree reuse between moves

After you play \(a\) and the opponent replies \(b\), the subtree below \((a, b)\) is still valid: its statistics were gathered from exactly the position you are now in. Make that node the new root and discard the rest (S&B §8.11 describes this). The inherited simulations are a head start. Early in a game with seven legal replies the inherited share is modest, since the old budget was split across the opponent's options; in forcing lines, where one reply dominates, most of the previous search carries over.

Handling stochasticity

Dice, card draws and random transitions add chance nodes. After an action, the environment's outcome is sampled from the model instead of being chosen, and the chance node keeps one child per outcome it has seen. Its value is the visit-weighted average of its children, which converges to the expectation, as in expectimax. Selection at a chance node samples an outcome rather than applying UCB. When outcomes are numerous or continuous, almost every sample would create a new child and no node would gather statistics; progressive widening allows a new child only while the number of children is below \(k N^\alpha\) for constants \(k\) and \(\alpha < 1\) (Coulom 2007; Couëtoux et al. 2011 apply it to both actions and outcomes). The simplest alternative is open-loop MCTS, where nodes are action sequences and statistics average over whatever outcomes occurred; it is easy, but it estimates the value of a fixed plan rather than of a policy that reacts to outcomes. Hidden information (cards in an opponent's hand) is usually handled by determinization, sampling the hidden state, as in Information Set MCTS (Cowling, Powley & Whitehouse 2012).

class ChanceNode:
    """Sits between (state, action) and its random outcomes; one child per outcome seen."""
    def __init__(self):
        self.children, self.N, self.W = {}, 0, 0.0      # outcome key -> decision Node

    def select(self, state, action, rng):
        nxt = state.sample_next(action, rng)            # the sample model rolls the dice
        if nxt.key() not in self.children:              # new outcome: expand it
            self.children[nxt.key()] = Node(nxt)
        return self.children[nxt.key()]

A fragment: sample_next and key are methods your stochastic game would provide. Backup through a chance node is the same as through any other node.

What breaks
  • Perspective bugs. Back up a result from the wrong player's point of view and the engine plays to lose, often convincingly. Test against a random player first; anything short of near-total domination means a sign error.
  • \(c\) is on the reward scale. Moving from rewards in \([0, 1]\) to \([-1, 1]\) doubles the spread of the means, so the same \(c\) explores half as much.
  • Random rollouts mislead in tactical positions. A move that loses by force in a few plies can look fine when averaged over random replies: Ramanujan, Sabharwal & Selman (2010) call these shallow traps and show UCT struggles with them in chess-like games, where minimax search does not.
  • UCT has bad worst cases. Coquelin & Munos (2007) construct trees on which UCT needs an enormous (hyper-exponential) number of simulations to find the best move. The consistency theorem says nothing about how many is enough.
  • Terminal states that still list moves. If legal_actions() returns moves after the game is won, the engine expands past the end of the game and miscounts results.
  • Transpositions. The same position reached by different move orders gets separate nodes and split statistics. Graph-based variants share them, at the cost of more complicated backups.

The engine's contract

Keep the game interface from Day 59: to_move, legal_actions() (empty at terminal states), play(a) returning a new state, is_terminal(), and result(player) in \(\{0, \tfrac12, 1\}\). Immutability is the important part. The tree stores states, so a play that mutates its state in place silently corrupts every node that shares it.

Connect Four is played on 7 columns of 6 rows; a piece drops to the lowest empty cell of the chosen column, and four in a row horizontally, vertically or diagonally wins. The game is solved: the first player wins with perfect play by starting in the centre column (shown independently by James Allen and Victor Allis in 1988). There are at most 7 moves per position and at most 42 plies per game, so random rollouts are cheap, but immediate threats are everywhere, so random rollouts are also noisy evaluators. That combination makes it a good test of MCTS.

Bitboards

Why the shift test works

Bit \(i\) of \(m = b \mathbin{\&} (b \gg s)\) is set exactly when bits \(i\) and \(i + s\) of \(b\) are both set: \(m\) marks the start of every pair spaced \(s\) apart. Bit \(i\) of \(m \mathbin{\&} (m \gg 2s)\) is set exactly when pairs start at both \(i\) and \(i + 2s\), that is, when bits \(i, i+s, i+2s, i+3s\) are all set: four in a row in direction \(s\). Because row 6 is never occupied, any run that would cross from the top of one column to the bottom of the next must pass through a zero, so the test has no false positives. Connect Four has 69 lines of four (24 horizontal, 21 vertical, 24 diagonal), a good unit test.

class ConnectFour:
    """Bitboards: bit 7*col + row (row 0 = bottom). Row 6 of each column is an always-empty sentinel."""
    def __init__(self, boards=(0, 0), heights=tuple(7 * c for c in range(7)), to_move=0, last=None):
        self.boards, self.heights, self.to_move, self.last = boards, heights, to_move, last

    @staticmethod
    def four(b):                                   # any four in a row in bitboard b?
        for shift in (1, 7, 6, 8):                 # vertical, horizontal, the two diagonals
            m = b & (b >> shift)
            if m & (m >> 2 * shift):
                return True
        return False

    def winner(self):                              # only the player who just moved can have won
        return self.last if self.last is not None and self.four(self.boards[self.last]) else None

    def is_terminal(self):
        return self.winner() is not None or all(h == 7 * c + 6 for c, h in enumerate(self.heights))

    def legal_actions(self):
        return [] if self.is_terminal() else [c for c in range(7) if self.heights[c] < 7 * c + 6]

    def wins_with(self, c, player):                # would `player` dropping in column c make four?
        return self.four(self.boards[player] | (1 << self.heights[c]))

    def play(self, c):
        boards, heights = list(self.boards), list(self.heights)
        boards[self.to_move] |= 1 << heights[c]
        heights[c] += 1
        return ConnectFour(tuple(boards), tuple(heights), 1 - self.to_move, self.to_move)

    def result(self, player):
        w = self.winner()
        return 0.5 if w is None else float(w == player)

The engine: reuse and pluggable rollouts

import random
# Node is Day 59's class.

def random_rollout(state, rng):
    while not state.is_terminal():
        state = state.play(rng.choice(state.legal_actions()))
    return state

def heuristic_rollout(state, rng):
    """Win now if you can; else block the opponent's immediate win; else play at random."""
    while not state.is_terminal():
        moves, me = state.legal_actions(), state.to_move
        wins = [c for c in moves if state.wins_with(c, me)]
        blocks = [c for c in moves if state.wins_with(c, 1 - me)]
        state = state.play(rng.choice(wins or blocks or moves))
    return state

class MCTS:
    def __init__(self, state, c=1.4, rollout=random_rollout, seed=0):
        self.root, self.c, self.rollout, self.rng = Node(state), c, rollout, random.Random(seed)

    def search(self, n_sims):
        for _ in range(n_sims):
            node = self.root
            while not node.untried and node.children:               # selection
                node = node.select_child(self.c)
            if node.untried:                                        # expansion
                a = node.untried.pop(self.rng.randrange(len(node.untried)))
                node.children.append(Node(node.state.play(a), node, a))
                node = node.children[-1]
            final = self.rollout(node.state, self.rng)              # simulation
            while node is not None:                                 # backup
                node.N += 1
                if node.parent is not None:
                    node.W += final.result(node.parent.state.to_move)
                node = node.parent
        return max(self.root.children, key=lambda ch: ch.N).action

    def advance(self, action):
        """Tree reuse: re-root at the child for the move just played, by either side."""
        for ch in self.root.children:
            if ch.action == action:
                ch.parent, self.root = None, ch
                return
        self.root = Node(self.root.state.play(action))              # never expanded: start fresh

Call advance on both engines after every move, yours and the opponent's. To switch reuse off for an ablation, reset engine.root = Node(state) before each search.

What to expect

  • Speed. Pure Python manages roughly 2,000 simulations per second from the Connect Four opening with random rollouts. A heuristic rollout costs about three times as much as a random one, because it checks every column for wins and blocks at every step.
  • Budget. Larger budgets win consistently, with diminishing returns: the score of \(2n\) against \(n\) simulations is well above 0.5 at small budgets and drifts towards 0.5 as both grow. In a 20-game reference match, 400 simulations scored 0.70 against 100; your larger samples will tighten that.
  • c. Expect a broad optimum below \(\sqrt 2\) with rewards in \([0, 1]\), and clearly worse play at the extremes. In a reference sweep at 200 simulations (40 games per point, so intervals of roughly \(\pm 0.15\)), \(c = 0.5\) and \(c = 1.0\) scored about 0.70 and 0.66 against \(c = 1.4\), while \(c = 0.25\), 2 and 4 all lost to it. The best value shifts with the budget, so re-check it at 3,200 simulations.
  • Reuse. A modest gain at a fixed budget. Early in the game only a small share of the previous search survives (the old budget was split across seven replies); in forcing sequences much more does.
  • Heuristic. A large gain at equal simulations: in a 20-game reference match at 200 simulations the heuristic engine scored 0.90. At equal wall-clock time the gap narrows because it runs roughly a third as many simulations. Report both; the comparison at equal time is the honest one.
  • Against you. A few thousand random-rollout simulations per move usually see every immediate threat, but can still misjudge long-term structure, such as the odd/even threat patterns that strong players and solvers rely on. Expect to win by setting up threats several moves deep, not by tactics.
Common bugs
  • Scoring every game from player 0's point of view while alternating colours, so half the results have the wrong sign.
  • Calling advance only on the engine that moved, so the other engine's root no longer matches the board.
  • Sharing one random.Random across both engines, which correlates their play and narrows your intervals artificially.
