Range versus precision

FormatExponent / mantissaMax valueDecimal digitsVerdict
fp328 / 233.4e38~7The reference. Master weights live here.
fp165 / 1065,504~3Good precision, terrible range. Needs loss scaling.
bf168 / 73.4e38~2fp32's exponent, fp16's size. Just works. Ampere and newer.

That table is the whole story. bf16 sacrifices mantissa bits to keep fp32's exponent, so it cannot overflow where fp32 would not, and it needs no loss scaling. fp16 keeps precision but its maximum is 65,504 — and gradients routinely underflow below its minimum normal value of \(6\times10^{-5}\), silently flushing to zero. If your GPU supports bf16, use bf16.

Why fp16 needs loss scaling

Gradients are small — typically \(10^{-3}\) to \(10^{-7}\). Much of that range falls below fp16's smallest normal number and rounds to exactly zero. The fix is to multiply the loss by a large constant \(S\) before the backward pass. By linearity every gradient is scaled by \(S\) too, lifting it into representable range; you then divide by \(S\) before the optimizer step.

GradScaler chooses \(S\) dynamically: start at 65,536, and whenever any gradient comes back non-finite, skip that step and halve \(S\); after 2000 consecutive clean steps, double it. This is why an AMP run legitimately skips a handful of early steps — that is the scaler calibrating, not a bug.

scaler = torch.amp.GradScaler("cuda")          # a no-op if you use bf16
ACC = 4                                        # micro-batches per optimizer step

for i, (xb, yb) in enumerate(loader):
    with torch.autocast("cuda", dtype=torch.bfloat16):
        loss = criterion(model(xb), yb) / ACC   # DIVIDE — see the pitfall below

    scaler.scale(loss).backward()

    if (i + 1) % ACC == 0:
        scaler.unscale_(opt)                    # unscale BEFORE clipping, or you clip the scale
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(opt)
        scaler.update()
        opt.zero_grad(set_to_none=True)
        sched.step()
Pitfall · four ways to get accumulation wrong

Forgetting to divide the loss. Accumulating 4 micro-batches without / ACC gives you a gradient 4× too large, which is equivalent to quietly quadrupling your learning rate.

Clipping before unscaling. With fp16, gradients are inflated by \(S\approx 65{,}536\). Clip to norm 1.0 at that point and you have effectively clipped to \(1.5\times10^{-5}\), destroying the update. Always scaler.unscale_(opt) first.

Stepping the scheduler per micro-batch. The schedule then runs \(ACC\times\) too fast.

Expecting BatchNorm to be fooled. As in Lesson 36 — accumulation gives you the gradient of a large batch, but normalisation statistics of the small one. Under DDP, also wrap the non-stepping micro-batches in model.no_sync(), or you pay a full all-reduce on every micro-batch and lose most of the benefit.

Where the memory actually goes

For a model with \(P\) parameters trained in mixed precision with AdamW, the fixed cost per parameter is roughly:

\[ \underbrace{2}_{\text{bf16 weights}}+\underbrace{4}_{\text{fp32 master}}+\underbrace{4}_{\text{fp32 grad}}+\underbrace{8}_{\text{Adam }m,v} \;=\; \mathbf{18\ \text{bytes/param}} \]

A 7B model therefore needs about 126 GB before a single activation is stored — which is why an 80 GB A100 cannot fine-tune 7B naively, and why ZeRO, FSDP, LoRA and 8-bit optimizers all exist (Lessons 94 and 96). Activations are the variable part, and they scale with batch size × sequence length × depth.

Activation checkpointing

Backprop needs the forward activations (Lesson 22). Checkpointing keeps only a few and recomputes the rest during the backward pass. Storing every \(\sqrt n\)-th activation in an \(n\)-layer network cuts activation memory from \(O(n)\) to \(O(\sqrt n)\) at the cost of one extra forward pass — about 30% more compute for a memory reduction that is frequently the difference between running and not running.

from torch.utils.checkpoint import checkpoint

class Block(torch.nn.Module):
    def forward(self, x):
        return x + self.mlp(self.norm(x))

# use_reentrant=False is the modern implementation; the old one breaks with some autograd features
for blk in model.blocks:
    blk.forward = lambda x, b=blk: checkpoint(b._forward, x, use_reentrant=False)
OOM triage, in order of what to try first
  1. Reduce batch size and add gradient accumulation to keep the effective batch — costs nothing but time.
  2. Turn on mixed precision if it is not already on — halves activations.
  3. Turn on gradient checkpointing — the biggest single lever for deep models.
  4. Switch to an 8-bit optimizer — saves 6 bytes/param.
  5. Check for accidental retention: are you appending loss instead of loss.item() to a list? That keeps the entire graph alive (Lesson 12).
  6. torch.cuda.memory_summary() and torch.cuda.max_memory_allocated() before guessing further.
  7. Only then: a smaller model, or LoRA, or more GPUs.
