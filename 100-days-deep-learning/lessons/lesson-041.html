The problem tracking solves

By your twentieth run you will have twenty models, and no reliable way to answer "which one was the good one, and what was different about it?" Notebook cells get edited in place. Filenames like model_v3_final_REAL.pt accumulate. The purpose of a tracker is to make the answer to that question mechanical rather than archaeological.

What to log

Loss and accuracy are the obvious ones and the least diagnostic. The list that actually saves you:

  • Learning rate at every step — so you can align loss drops with schedule events.
  • Gradient norm, global and per-layer group. A spike here precedes a loss spike; a norm collapsing to \(10^{-8}\) is a dead layer.
  • Update-to-weight ratio \(\eta\|\Delta w\|/\|w\|\) — should sit near \(10^{-3}\) (Lesson 28).
  • Throughput in examples/sec and the GPU utilisation. A run at 30% utilisation is a data-loading problem, and you will not notice it from the loss curve.
  • The full config, the git commit hash, and whether the working tree was dirty.
  • A sample of predictions — a grid of the worst-scoring validation examples each epoch. This is the single most informative artifact and almost nobody logs it.

def git_state():
    h = subprocess.check_output(["git", "rev-parse", "HEAD"]).decode().strip()
    dirty = bool(subprocess.check_output(["git", "status", "--porcelain"]).strip())
    return {"commit": h, "dirty": dirty}

def grad_norm(model):
    total = 0.0
    for p in model.parameters():
        if p.grad is not None:
            total += p.grad.detach().pow(2).sum().item()
    return total ** 0.5

Seeding — and the bug in every tutorial

import os, random, numpy as np, torch

def seed_everything(seed: int):
    os.environ["PYTHONHASHSEED"] = str(seed)
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)

def seed_worker(worker_id):
    # torch gives each worker a distinct base seed; derive python/numpy seeds FROM it
    s = torch.initial_seed() % 2**32
    np.random.seed(s)
    random.seed(s)

loader = DataLoader(ds, batch_size=64, num_workers=8, shuffle=True,
                    worker_init_fn=seed_worker,
                    generator=torch.Generator().manual_seed(seed))
Pitfall · every DataLoader worker generating the same "random" numbers

When PyTorch forks worker processes, each inherits the parent's NumPy random state unchanged. If your Dataset.__getitem__ uses np.random for augmentation — which is extremely common — then with 8 workers, examples 0–7 of every batch receive identical augmentation, as do 8–15, and so on. Your augmentation diversity silently drops by a factor of 8. This has been found in published codebases. The worker_init_fn above is the fix; alternatively use torch's RNG inside the dataset, which PyTorch seeds per-worker correctly.

How much determinism is worth paying for

Full bitwise determinism requires torch.use_deterministic_algorithms(True) and cudnn.benchmark=False, and costs real throughput — some ops have no deterministic kernel and will simply raise. It is worth it while chasing a specific bug, and rarely worth it otherwise.

What you actually need is reproducible conclusions, not reproducible bits. That means: run every important comparison with 3 seeds and report mean ± std. If your improvement is 0.3% and your seed-to-seed standard deviation is 0.4%, you have not measured an improvement — you have measured noise, and no amount of determinism flags will change that.
