What problem it was solving

Not accuracy. In 2017 attention-augmented seq2seq (Lesson 75) already produced good translations. The problem was that the RNN made training sequential: timestep \(t\) could not start until \(t-1\) finished, so a machine with thousands of parallel cores processed one word at a time. The paper's claim was that if attention is doing the heavy lifting anyway, you can delete the recurrence entirely and compute every position at once. The result trained in 12 hours on 8 GPUs where the previous state of the art took days.

How to read an ML paper — three passes

Pass 1 (5 minutes). Title, abstract, figures, conclusion. Answer one question: what is the claim, and against what baseline? If you cannot state the baseline, you have not understood the claim.

Pass 2 (30 minutes). Method and results. Read the figures properly, check the axes, look for what is not plotted. Read the ablation table before the headline number — it tells you which component actually mattered, and often the answer is "not the one in the title".

Pass 3 (hours). Reimplement the core idea on a toy problem. This is the only pass that produces real understanding, and it routinely surfaces details the paper omitted. Lesson 120 covers the workflow properly; the transformer is an excellent first candidate, which is what Lessons 85 and 86 are.

One formula

\[ \text{Attention}(Q,K,V)=\softmax\!\left(\frac{QK\T}{\sqrt{d_k}}\right)V \]

The database analogy: each position emits a query ("what am I looking for?"), a key ("what do I offer?") and a value ("what do I pass on if selected?"). Compatibility is the dot product of query and key, softmax turns compatibilities into weights, and the output is the weighted average of values. It is the score–normalise–average shape from Lesson 75, with all three roles derived from the same input by learned projections:

\[ Q=XW_Q,\qquad K=XW_K,\qquad V=XW_V,\qquad X\in\R^{n\times d} \]
X (n, d)→Q, K (n, dk)→QKᵀ (n, n)→softmax (n, n)→out (n, dv)
Why \(\sqrt{d_k}\) — the variance argument

Suppose the components of \(\mathbf q\) and \(\mathbf k\) are independent with mean 0 and variance 1. Their dot product is a sum of \(d_k\) independent products:

\[ \E\big[\mathbf q\cdot\mathbf k\big]=0,\qquad \Var\big[\mathbf q\cdot\mathbf k\big]=\sum_{i=1}^{d_k}\Var[q_ik_i]=d_k \]

So the scores have standard deviation \(\sqrt{d_k}\). With \(d_k=64\) that is 8; with \(d_k=128\) it is 11.3. Feed scores of that magnitude into a softmax and it saturates — one weight goes to ~1 and the rest to ~0.

Saturation is fatal for a different reason than you might expect. A saturated softmax has a vanishing gradient: \(\partial p_i/\partial z_j=p_i(\delta_{ij}-p_j)\), which is near zero when any \(p_i\approx1\). At initialisation the model would be unable to learn which positions to attend to, because the gradient telling it so is gone. Dividing by \(\sqrt{d_k}\) restores unit variance and keeps the softmax in its responsive range. It is the same numerical-stability reasoning as Lesson 27's initialisation derivation, applied to a different layer.

Scaled dot-product attention · what the \(\sqrt{d_k}\) is actually protecting

Masking

Two different masks, often confused:

MaskShapePurpose
Causal\((n,n)\) lower triangularPosition \(t\) must not see \(t+1\). Required for any generative decoder — without it the model trivially copies the answer.
Padding\((B,n)\) broadcast to \((B,1,1,n)\)Real tokens only. Per-example, unlike the causal mask which is shared.
 
import torch, torch.nn.functional as F

def attention(q, k, v, mask=None, scale=True):
    """q,k,v: (B, h, n, d_k). Returns (B, h, n, d_v) and the weights."""
    d_k = q.size(-1)
    scores = q @ k.transpose(-2, -1)                    # (B, h, n, n)
    if scale:
        scores = scores / (d_k ** 0.5)
    if mask is not None:
        # -inf BEFORE softmax. finfo(...).min keeps fp16 finite (Lesson 75)
        scores = scores.masked_fill(~mask, torch.finfo(scores.dtype).min)
    w = scores.softmax(dim=-1)
    return w @ v, w

Pitfall · a fully-masked row produces NaN

If an example is entirely padding — an empty sequence in a batch, or a query position masked against every key — every score in that row is \(-\infty\). The softmax then computes \(e^{-\infty}/\sum e^{-\infty}=0/0=\text{NaN}\), which propagates through the whole batch and kills training with no useful error message. Guard against empty sequences at the data-loading stage, or clamp the row to a uniform distribution. This is a genuinely common source of "my transformer NaNs after a few hundred steps".

The quadratic cost, made concrete

The score matrix is \(n\times n\) per head per layer. Memory for the attention weights alone:

\[ \text{bytes}=B\cdot h\cdot n^2\cdot\text{sizeof(dtype)} \]

With \(B=8\), \(h=32\), \(n=8192\) in bf16: \(8\times32\times8192^2\times2\approx\mathbf{34\ \text{GB}}\) — per layer. That number is why FlashAttention exists, and why every long-context method in Lesson 90 exists. It is also why attention is often described as \(O(n^2)\) when the parameter count does not depend on \(n\) at all: the cost is in the activations, not the weights.

What self-attention actually buys

Compare path lengths from Lesson 77. An RNN needs \(O(n)\) sequential steps for information to travel from position 1 to position \(n\), and every step is a chance to lose it. A dilated CNN needs \(O(\log n)\) layers. Self-attention needs one — every position is directly connected to every other. That is the property that makes long-range dependency learnable rather than merely possible, and it is what you are paying \(O(n^2)\) for.

Why one head is not enough

A single softmax produces one distribution per position, so one attention operation can express exactly one relationship — and averaging over values blurs everything it attends to. But a word relates to its context in several independent ways at once: syntactically to its verb, semantically to a topic word, positionally to its neighbour. Multi-head attention runs \(h\) attention operations in parallel on subspaces of the representation:

\[ \text{head}_i=\text{Attention}(XW_Q^i,XW_K^i,XW_V^i),\qquad \text{MHA}(X)=\big[\text{head}_1;\dots;\text{head}_h\big]W_O \]

with \(d_k=d_v=d_{\text{model}}/h\), so the total compute is the same as one head at full width. Eight heads of 64 dimensions cost what one head of 512 would — you get the diversity for free.

class MultiHeadAttention(nn.Module):
    def __init__(self, d_model, n_heads, dropout=0.0):
        super().__init__()
        assert d_model % n_heads == 0
        self.h, self.dk = n_heads, d_model // n_heads
        self.qkv = nn.Linear(d_model, 3 * d_model, bias=False)   # one GEMM for all three
        self.proj = nn.Linear(d_model, d_model, bias=False)
        self.p = dropout

    def forward(self, x, is_causal=True):
        B, n, D = x.shape
        q, k, v = self.qkv(x).split(D, dim=2)
        # (B,n,D) -> (B,h,n,dk). This reshape IS the multi-head split.
        q, k, v = (t.view(B, n, self.h, self.dk).transpose(1, 2) for t in (q, k, v))
        o = F.scaled_dot_product_attention(q, k, v, is_causal=is_causal,
                                           dropout_p=self.p if self.training else 0.0)
        o = o.transpose(1, 2).contiguous().view(B, n, D)          # concat the heads back
        return self.proj(o)
Pitfall · view without contiguous

After transpose(1,2) the tensor's memory layout no longer matches its shape, so view raises "view size is not compatible with input tensor's size and stride". The fix is .contiguous().view(...) or simply .reshape(...). The more dangerous version of this bug is silent: transposing the wrong pair of axes gives a tensor of the right shape whose head and sequence dimensions are swapped. Training proceeds, loss falls slowly, and nothing errors. Always assert your shapes at each step when writing attention by hand.

What heads learn

Probing trained models finds recognisable specialisations: heads that attend to the previous token, heads that attend to the next occurrence of a delimiter, heads that link a verb to its subject, heads that attend to rare tokens.

Induction heads — the most important one

Some heads implement a specific algorithm: seeing the pattern [A][B] … [A], they attend from the second A to the token that followed the first one, and predict B. That is in-context copying — a general "if this happened before, it will happen again" rule, learned from nothing but next-token prediction.

Induction heads matter because their formation coincides with a visible phase change in the loss curve — a small bump where the model abruptly acquires in-context learning. It is one of the few cases where a specific circuit has been tied to a specific capability and a specific moment in training. Lesson 117 covers the mechanistic interpretability programme this belongs to.

Head redundancy is real: Michel et al. showed that many heads can be pruned at inference with little loss, and that a large fraction of layers work fine with a single head. This is one motivation for Multi-Query and Grouped-Query Attention in Lesson 90 — if the heads are partly redundant, they need not each carry their own keys and values.

The problem

Attention computes a weighted sum over a set. Permute the input tokens and every output permutes identically — the operation contains no notion of order at all. Without positional information, "the dog bit the man" and "the man bit the dog" produce identical representations. Position must be injected explicitly.

Sinusoidal

\[ PE_{(pos,2i)}=\sin\!\left(\frac{pos}{10000^{2i/d}}\right),\qquad PE_{(pos,2i+1)}=\cos\!\left(\frac{pos}{10000^{2i/d}}\right) \]

Each dimension is a sinusoid of a different wavelength, from \(2\pi\) up to \(10000\cdot2\pi\) — a binary-like positional code in continuous form. The stated motivation was that \(PE_{pos+k}\) is a fixed linear function of \(PE_{pos}\), so relative offsets are linearly recoverable. In practice sinusoidal and learned absolute embeddings perform about equally, and both have the same fatal flaw.

RoPE — rotate instead of add

Absolute encodings are added to the embedding, which means the model must infer relative distance from a sum. RoPE instead rotates the query and key vectors by an angle proportional to their position. Treat consecutive dimension pairs as complex numbers and multiply by \(e^{i m\theta}\):

\[ \tilde{\mathbf q}_m=R_m\mathbf q,\qquad \tilde{\mathbf k}_n=R_n\mathbf k \qquad\Longrightarrow\qquad \tilde{\mathbf q}_m\T\tilde{\mathbf k}_n=\mathbf q\T R_{n-m}\mathbf k \]

The absolute positions cancel and only \(n-m\) survives. The attention score depends on relative distance only, exactly and by construction, with no extra parameters and no lookup table. That is why RoPE is in Llama, Mistral, Qwen, Gemma, DeepSeek and essentially every current open-weight model.

NoPE is worth pausing on. A causal decoder is not permutation-invariant even without positional encoding, because the mask gives position 1 a different number of visible tokens than position 50 — the model can count. That it works at all is a useful check on how much of the machinery is truly necessary.

Extending context after training

A model trained at 4k tokens degrades sharply at 8k, because RoPE angles at unseen positions are out of distribution. Three fixes, in increasing sophistication:

  • Position interpolation. Compress positions into the trained range: use \(m\cdot L_{\text{train}}/L_{\text{new}}\) instead of \(m\). Every angle is now in-distribution. Costs some fine-grained resolution; needs a little fine-tuning.
  • NTK-aware scaling. Increase the RoPE base \(\theta\) instead. High-frequency dimensions (which encode local order) are barely changed, low-frequency ones (which encode long range) stretch. Often works with no fine-tuning at all.
  • YaRN. Combines both, interpolating only the low-frequency dimensions and correcting the attention temperature. The current standard for large context extensions.
Pitfall · applying RoPE to the values

RoPE rotates Q and K only. The derivation depends on the rotation cancelling inside the \(\mathbf q\T\mathbf k\) product; \(V\) is not part of that product, and rotating it corrupts the content the attention is meant to retrieve. A related trap: RoPE must be applied after the head split, per head, and with the correct pairing of dimensions — implementations differ on whether they pair \((0,1),(2,3),\dots\) or \((0,d/2),(1,d/2{+}1),\dots\). Both are valid, but a checkpoint trained with one and served with the other produces fluent-sounding output with subtly wrong long-range behaviour, which is a miserable bug to find.

The feedforward network is most of the model

Between attention layers sits an MLP applied independently at every position:

\[ \text{FFN}(\mathbf x)=W_2\,\phi(W_1\mathbf x+\mathbf b_1)+\mathbf b_2,\qquad W_1\in\R^{4d\times d},\ W_2\in\R^{d\times 4d} \]

Count the parameters per block: attention holds \(4d^2\) (the Q, K, V and output projections), the FFN holds \(8d^2\). Two-thirds of a transformer's parameters are in the feedforward layers, not in attention. That surprises people, and it explains why Mixture of Experts (Lesson 91) targets the FFN specifically — it is where the capacity lives.

What the FFN is doing

Attention moves information between positions; the FFN processes it in place. A productive reading is that the FFN acts as a key-value memory: the rows of \(W_1\) are keys matched against the residual stream, and the corresponding columns of \(W_2\) are values written back when a key fires. Probing work has found individual FFN neurons that activate on specific, human-legible patterns. The 4× expansion gives the layer \(4d\) such slots — width is memory capacity.

SwiGLU, and the two-thirds correction

Modern models replace the FFN with a gated variant:

\[ \text{SwiGLU}(\mathbf x)=\big(\text{SiLU}(W_{\text{gate}}\mathbf x)\odot W_{\text{up}}\mathbf x\big)W_{\text{down}} \]

Three matrices instead of two, so to keep the parameter count equal the hidden dimension is set to \(\frac{2}{3}\cdot4d=\frac{8}{3}d\) — which is where Llama's odd 11008 for \(d=4096\) comes from (rounded to a multiple of 256). Gating buys roughly the same quality gain as a modest increase in depth, for free. The paper introducing it famously attributed its success to "divine benevolence", which is an unusually honest way of saying nobody has a satisfying explanation.

Hence the standard estimate \(P\approx12Ld^2\) for a model's parameter count, and the rule of thumb that a forward pass costs about \(2P\) FLOPs per token, a full training step about \(6P\) (forward, backward, and the backward's second matmul). Those two numbers are the basis of every compute-budget calculation in Lesson 93.

Pitfall · the missing final norm, and dropout at scale

In a pre-norm stack nothing normalises the residual stream on its way out of the last block, so it grows roughly as \(\sqrt L\). Forget the final RMSNorm before the output projection and training still works, badly, with an odd loss curve — as flagged in Lesson 37. Separately: the 2017 recipe uses dropout 0.1 everywhere, and copying that into a large-scale pretraining run is usually wrong. When your model sees each token once, there is nothing to overfit; dropout just adds noise and costs throughput. Most large pretraining runs use dropout 0, then reintroduce it for fine-tuning on small data.

A complete decoder-only transformer in about 90 lines. This is the nanoGPT shape, and it is genuinely all of it — every production LLM is this code plus engineering.

from dataclasses import dataclass
import math, torch, torch.nn as nn, torch.nn.functional as F

@dataclass
class Config:
    vocab_size: int = 50304      # 50257 rounded up to a multiple of 64 — see the pitfall
    n_layer: int = 12
    n_head: int = 12
    d_model: int = 768
    block_size: int = 1024       # max context
    dropout: float = 0.0         # 0 for pretraining (Lesson 84)

class CausalSelfAttention(nn.Module):
    def __init__(self, c):
        super().__init__()
        self.h, self.d = c.n_head, c.d_model
        self.qkv  = nn.Linear(c.d_model, 3 * c.d_model, bias=False)
        self.proj = nn.Linear(c.d_model, c.d_model, bias=False)
        self.drop = c.dropout

    def forward(self, x):
        B, T, D = x.shape
        q, k, v = self.qkv(x).split(D, dim=2)
        q, k, v = (t.view(B, T, self.h, D // self.h).transpose(1, 2) for t in (q, k, v))
        y = F.scaled_dot_product_attention(
            q, k, v, is_causal=True,
            dropout_p=self.drop if self.training else 0.0)
        y = y.transpose(1, 2).reshape(B, T, D)
        return self.proj(y)

class MLP(nn.Module):
    def __init__(self, c):
        super().__init__()
        self.fc   = nn.Linear(c.d_model, 4 * c.d_model, bias=False)
        self.proj = nn.Linear(4 * c.d_model, c.d_model, bias=False)
        self.drop = nn.Dropout(c.dropout)

    def forward(self, x):
        return self.drop(self.proj(F.gelu(self.fc(x), approximate="tanh")))

class Block(nn.Module):
    def __init__(self, c):
        super().__init__()
        self.ln1, self.ln2 = nn.LayerNorm(c.d_model), nn.LayerNorm(c.d_model)
        self.attn, self.mlp = CausalSelfAttention(c), MLP(c)

    def forward(self, x):
        x = x + self.attn(self.ln1(x))       # PRE-norm: norm inside, add outside
        x = x + self.mlp(self.ln2(x))
        return x

class GPT(nn.Module):
    def __init__(self, c):
        super().__init__()
        self.c = c
        self.tok = nn.Embedding(c.vocab_size, c.d_model)
        self.pos = nn.Embedding(c.block_size, c.d_model)
        self.blocks = nn.ModuleList([Block(c) for _ in range(c.n_layer)])
        self.ln_f = nn.LayerNorm(c.d_model)                  # the final norm — do not omit
        self.head = nn.Linear(c.d_model, c.vocab_size, bias=False)
        self.head.weight = self.tok.weight                   # weight tying

        self.apply(self._init)
        # scale the residual-projection init by 1/sqrt(2L): L blocks each add TWICE
        for name, p in self.named_parameters():
            if name.endswith("proj.weight"):
                nn.init.normal_(p, 0.0, 0.02 / math.sqrt(2 * c.n_layer))

    def _init(self, m):
        if isinstance(m, nn.Linear):
            nn.init.normal_(m.weight, 0.0, 0.02)
            if m.bias is not None:
                nn.init.zeros_(m.bias)
        elif isinstance(m, nn.Embedding):
            nn.init.normal_(m.weight, 0.0, 0.02)

    def forward(self, idx, targets=None):
        B, T = idx.shape
        assert T <= self.c.block_size, f"sequence {T} exceeds context {self.c.block_size}"
        pos = torch.arange(T, device=idx.device)
        x = self.tok(idx) + self.pos(pos)                    # (B,T,D)
        for blk in self.blocks:
            x = blk(x)
        x = self.ln_f(x)
        logits = self.head(x)                                # (B,T,V) — raw logits
        loss = None
        if targets is not None:
            loss = F.cross_entropy(logits.view(-1, logits.size(-1)),
                                   targets.view(-1), ignore_index=-1)
        return logits, loss

The three details that are easy to skip

Weight tying

The input embedding maps token → vector; the output head maps vector → token scores. These are inverse operations over the same vocabulary, and sharing one matrix for both is both principled and cheap: for \(V=50257\) and \(d=768\) it saves 38.6M parameters, about 30% of a 124M model. It also acts as a regulariser and consistently improves perplexity on small models. One line, and every GPT does it.

Residual init scaling by \(1/\sqrt{2L}\)

In a pre-norm stack the residual stream accumulates the output of every sublayer. With \(L\) blocks each contributing two additions, the variance of the stream grows like \(2L\) if every sublayer is initialised identically — so a deep model starts with enormous activations at the top. Scaling the output projection of each sublayer by \(1/\sqrt{2L}\) keeps the stream at roughly unit variance regardless of depth. This is Lesson 27's variance argument applied to the residual stream, and it is what makes a 48-layer model trainable without a fragile warmup.

Pitfall · vocabulary size 50257

GPT-2's real vocabulary is 50257, a prime-ish number that is terrible for GPU tiling. Padding it to 50304 (a multiple of 64, and of 128) makes the final matmul land on tensor-core-friendly shapes and buys roughly a 25% throughput improvement for 47 extra rows that are never used — the model simply learns to assign them negligible probability. Free speed for a one-character change, and one of the most cost-effective tricks in the whole of LLM engineering.

Why masking, and why 15%

A causal decoder sees only leftward context. For classification and tagging you want both sides — but a bidirectional model cannot be trained on next-token prediction, because the answer is in its input. BERT's solution: corrupt 15% of tokens and predict them from the rest.

The 80/10/10 rule

Of the 15% selected: 80% become [MASK], 10% become a random token, 10% are left unchanged.

The reason is a train/test mismatch. [MASK] never appears during fine-tuning or inference, so a model trained only on masked positions would have a large distribution shift at deployment. Leaving 10% unchanged forces the model to build a good representation of every token, not just masked ones, since it cannot tell which positions it will be graded on. The 10% random substitution prevents it from simply copying the input at unchanged positions. The 15% rate itself is a trade-off: too low and each pass provides little signal, too high and there is not enough context left to predict from. Later work found the optimum is task- and scale-dependent, with 40% working better for large models.

MLM is far less sample-efficient than causal LM — you get a learning signal from 15% of positions instead of 100%. That inefficiency is one reason the field moved to decoder-only models for large-scale pretraining.

Pitfall · using [CLS] as a sentence embedding

The [CLS] token of an off-the-shelf BERT is a poor sentence representation — cosine similarity between two [CLS] vectors correlates worse with human similarity judgements than averaging GloVe vectors. It was trained for next-sentence prediction, not for similarity, and its geometry is anisotropic (all vectors crowd into a narrow cone). If you need sentence embeddings, use a model trained for them: Sentence-BERT fine-tunes with a siamese architecture and a contrastive or triplet objective (Lesson 61), and the difference is not marginal.

When an encoder is still the right choice in 2026

Encoder-only models are not obsolete — they are just no longer the frontier. For a fixed classification, NER or retrieval task with training data, a fine-tuned DeBERTa or ModernBERT is faster, cheaper and often more accurate than prompting a large decoder, and it runs on a CPU. Reach for an LLM when you need generation, few-shot flexibility, or an open-ended task. Reach for an encoder when you have 5,000 labelled examples and a fixed label set — which describes an enormous amount of real production NLP.

In-context learning is the strange one

Emergence, and the argument about it

Plot accuracy on multi-step arithmetic against model scale and you see a flat line near zero, then a sharp jump. Dozens of tasks show this shape, and it was widely described as emergent — a capability that appears discontinuously and cannot be predicted from smaller models.

The mirage argument, and what survives it

Schaeffer et al. (2023) pointed out that most "emergent" results use discontinuous metrics. Exact-match accuracy on a 5-digit multiplication is 0 until every digit is right. If per-digit accuracy improves smoothly from 0.1 to 0.9, exact-match stays near zero and then leaps — the discontinuity is in the metric, not the model. Swapping to per-token log-likelihood makes the same curves smooth.

This is a genuine and important correction, and it does not dissolve the phenomenon entirely. Smooth underlying improvement still produces discontinuous usefulness: a system that gets 4 of 5 digits right is worthless and one that gets 5 of 5 is valuable, and that threshold is real for anyone deploying it. The honest position is that capabilities improve predictably in loss and unpredictably in utility, and that you should be suspicious of any scaling claim resting on a thresholded metric.

Everything is text-to-text

T5's framing: classification, translation, summarisation, regression and question answering are all "given this string, produce that string". Prefix the input with a task description and use one model, one objective and one decoding procedure for all of them.

Span corruption

BERT masks individual tokens. T5 masks contiguous spans and replaces each with a single sentinel, then asks the decoder to emit the spans in order:

input: Thank you <X> me to your party <Y> week.
target: <X> for inviting <Y> last <Z>

Two advantages over token masking. The target sequence is much shorter than the input, so training is cheaper per example. And predicting a multi-token span requires modelling the joint distribution over the span, not \(k\) independent marginals — a harder and more useful task. T5 uses 15% corruption with mean span length 3.

BART takes a different route: corrupt the input with an arbitrary noising function — token masking, deletion, span infilling, sentence permutation, document rotation — and train a full seq2seq model to reconstruct the original. Because the decoder is a standard autoregressive LM, BART is directly usable for generation in a way BERT is not. Their ablation found text infilling plus sentence shuffling worked best.

The KV cache — the most important optimisation in inference

Generating token \(t\) recomputes attention over all previous tokens. But the keys and values of tokens \(1..t-1\) do not change — only the new query does. Cache them and each new token costs \(O(n)\) instead of \(O(n^2)\), turning generation from quadratic to linear.

The cost is memory, and it is substantial:

\[ \text{KV bytes}=2\cdot B\cdot n\cdot L\cdot h_{kv}\cdot d_{\text{head}}\cdot\text{sizeof(dtype)} \]

For Llama-2-70B (\(L=80\), \(h=64\), \(d_{\text{head}}=128\)) at 4096 tokens with batch 1 in fp16, full multi-head attention would need 10.7 GB of cache for a single sequence — more than the weights of a 7B model, for one user. Serve 32 concurrent users and the cache dwarfs everything else. That number is why the next idea exists.

KV cache calculator · why long context is a memory problem, not a compute problem
FlashAttention — the same maths, a different memory schedule

FlashAttention computes exactly standard attention. It is not an approximation. The insight is that GPUs are bottlenecked by memory bandwidth, not arithmetic: a naive implementation writes the \(n\times n\) score matrix to high-bandwidth memory, reads it back for the softmax, writes it again, and reads it for the value multiply. That traffic dominates the runtime.

Instead, tile the computation and keep each tile in on-chip SRAM, using the online softmax trick — a running maximum and running normaliser (Lesson 10's log-sum-exp, made incremental) that lets you finish a tile before seeing the rest of the row. The \(n\times n\) matrix is never materialised. Memory drops from \(O(n^2)\) to \(O(n)\) and wall-clock improves 2–4×, with bit-identical outputs. FlashAttention-2 improved the work partitioning; FlashAttention-3 exploits Hopper's asynchrony and FP8.

Why exact beat approximate

Between 2020 and 2022 there were dozens of sub-quadratic attention papers, and almost none are in production. FlashAttention is the reason: by removing the memory bottleneck from exact attention, it moved the practical crossover point so far out that the approximations no longer paid for their quality loss and implementation complexity. The lesson generalises — a constant-factor improvement to the exact method can defeat an asymptotic improvement to an approximate one, for any problem size people actually run.

PagedAttention (vLLM) applies operating-system virtual memory to the KV cache. Naive serving pre-allocates a contiguous block per request sized to the maximum possible length, wasting 60–80% of it. PagedAttention stores the cache in fixed-size blocks with a page table, allowing non-contiguous allocation, near-zero waste, and copy-on-write sharing of a common prompt prefix across requests. It raised serving throughput by 2–4× with no model change at all.

Decouple parameters from compute

In a dense model, every parameter participates in every token's forward pass, so capacity and cost rise together. MoE breaks that link: replace the FFN with \(N\) parallel expert FFNs and a router that sends each token to only the top \(k\) of them.

\[ \mathbf g=\softmax\big(W_r\mathbf x\big),\qquad \mathcal T=\text{top-}k(\mathbf g),\qquad \mathbf y=\sum_{i\in\mathcal T}\frac{g_i}{\sum_{j\in\mathcal T}g_j}\,E_i(\mathbf x) \]

Mixtral 8×7B holds 46.7B parameters but activates only 12.9B per token — the quality of a much larger model at the compute of a much smaller one. The catch is that all 46.7B must still fit in memory, because any token might route anywhere. MoE saves FLOPs, not VRAM.

The load-balancing loss

Left alone, routing collapses: an expert that is slightly better early gets more tokens, trains faster, becomes more attractive, and the feedback loop starves the others. Switch Transformer adds an auxiliary loss:

\[ \mathcal L_{\text{aux}}=\alpha\,N\sum_{i=1}^{N}f_i\,P_i \]

where \(f_i\) is the fraction of tokens actually dispatched to expert \(i\) and \(P_i\) is the mean router probability for it. The product is minimised when both are uniform at \(1/N\), and using \(P_i\) rather than \(f_i\) alone is what makes it differentiable — \(f_i\) comes from a hard top-k and carries no gradient. Typically \(\alpha=0.01\). Too large and the router balances instead of specialising; too small and you get collapse.

DeepSeek-MoE refined this with two ideas that are now widely copied: fine-grained experts — many more, each smaller, so top-k gives combinatorially more specialisation paths — and shared experts that every token always visits, capturing common knowledge so the routed experts need not each relearn it.

Pitfall · assuming MoE is cheap to deploy

"Mixtral 8×7B activates only 13B parameters" is often read as "it runs like a 13B model". It does not. All 47B parameters must be resident, so you need roughly 94 GB in fp16 — two 80GB GPUs, versus one for a dense 13B. At small batch sizes it is also memory-bandwidth-bound rather than compute-bound, so the FLOP saving does not convert to a proportional latency win. MoE pays off for high-throughput batched serving where the FLOP saving dominates, and is often a poor choice for single-user local inference. Expert-parallel sharding also puts an all-to-all communication step in the critical path, which needs real interconnect.

The recurrence, back again

A continuous state space model is a linear ODE, discretised:

\[ \mathbf h_t=\bar A\mathbf h_{t-1}+\bar B\mathbf x_t,\qquad \mathbf y_t=C\mathbf h_t \]

That is an RNN with no non-linearity in the recurrence — which is precisely what makes it different. Because the recurrence is linear, the whole sequence can be computed as a convolution with a kernel derived from \(\bar A\), and therefore in parallel during training. You get an RNN's \(O(1)\) inference state and a CNN's parallel training. The obstacle was always that a linear recurrence forgets: \(\bar A^t\) decays. HiPPO solved that by deriving a specific \(A\) that provably maintains an optimal polynomial compression of the entire history, and S4 made it computationally practical.

Mamba's selectivity, and what it costs

S4's \(\bar A,\bar B,C\) are fixed, so the model compresses every input the same way — it cannot decide that this token matters and that one does not. Attention can, trivially, because its weights are computed from the content. Mamba makes the SSM parameters functions of the input: \(B_t=s_B(\mathbf x_t)\), \(C_t=s_C(\mathbf x_t)\), and a input-dependent step size \(\Delta_t\).

That restores content-based reasoning and immediately breaks the convolution: with time-varying parameters there is no fixed kernel. Mamba recovers parallelism with a hardware-aware parallel scan — an associative scan kept in SRAM, fusing discretisation, scan and multiplication into one kernel so the large hidden state is never written to HBM. The architectural idea and the kernel are equally essential; without the kernel it would be too slow to matter.

Look at the last row, because it is the one that decides architectures. A transformer keeps every past token and can retrieve any of them exactly — that is what the KV cache is. Loss is predictable

Test loss follows a power law in parameters, data and compute, over many orders of magnitude:

\[ L(N,D)=E+\frac{A}{N^{\alpha}}+\frac{B}{D^{\beta}} \]

\(E\) is the irreducible entropy of language, \(N\) is parameters, \(D\) is tokens. Chinchilla fit \(\alpha\approx0.34\), \(\beta\approx0.28\). Being able to predict a large model's loss from small runs is what makes multi-million-dollar training decisions defensible instead of speculative.

The Chinchilla result

Training compute is \(C\approx6ND\). Minimise \(L(N,D)\) subject to that constraint, and because \(\alpha\approx\beta\), the optimum has \(N\) and \(D\) scaling at roughly the same rate — giving the famous ratio:

\[ D^\ast\approx 20\,N^\ast\quad\text{tokens per parameter} \]

This was a correction with real consequences. GPT-3 used 175B parameters on 300B tokens — a ratio of 1.7, more than ten times too few tokens. Chinchilla trained 70B on 1.4T tokens at the same compute budget and beat GPT-3 across the board. A model four times smaller, better, and vastly cheaper to serve. Almost every model since has been trained on far more tokens per parameter.

Compute budget · how to spend a fixed number of FLOPs
Why Llama ignored Chinchilla, deliberately

Chinchilla optimises training compute. It says nothing about inference. If you will serve a model trillions of times, a smaller model trained past the compute-optimal point is better overall — you pay more once to save forever. Llama-3-8B was trained on 15T tokens, a ratio of 1875 tokens per parameter, roughly 90× "optimal". The loss gain per token was small, but the deployment saving was enormous. The rule to carry: Chinchilla-optimal is the right answer to the wrong question unless training cost dominates your total spend.

ZeRO, stage by stage

From Lesson 44: mixed-precision AdamW costs about 18 bytes per parameter, and in plain DDP every GPU holds a full copy of all of it. ZeRO observes that this is redundant and shards it across \(P\) devices:

Stage 1 shards optimizer state (12 of the 18 bytes) → 4× memory reduction. Stage 2 also shards gradients → 8×. Stage 3 also shards parameters, gathering each layer just in time for its forward pass and releasing it after → \(P\times\), i.e. essentially unlimited. Stage 3 (FSDP) adds roughly 50% more communication volume than DDP but makes memory a non-issue. Rule of thumb: use stage 2 while it fits, stage 3 when it does not.

The pipeline bubble

Split \(L\) layers across \(P\) stages and stage 2 sits idle until stage 1 finishes. With naive scheduling the idle fraction is:

\[ \text{bubble}=\frac{P-1}{m+P-1} \]

where \(m\) is the number of micro-batches. With \(P=8\) and \(m=1\), 87.5% of your cluster is idle. With \(m=64\) it falls to 10%. This is why pipeline parallelism requires many micro-batches, and why interleaved schedules (1F1B, and Megatron's virtual pipeline stages) exist. Get this wrong and you will buy eight GPUs to run at the speed of one.

3D parallelism

Large runs compose all three, matched to the hardware topology: tensor parallelism within a node (8 GPUs over NVLink, ~900 GB/s), pipeline parallelism across nodes (InfiniBand, ~50 GB/s), and data parallelism across the resulting replicas. The ordering is not arbitrary — it puts the chattiest communication on the fastest link. Getting the mapping backwards is one of the most expensive misconfigurations in the field.

Pitfall · four ways a distributed run silently wastes money

Wrapping the whole model as one FSDP unit. It then gathers all parameters at once and you get no memory saving. Wrap per transformer block.

Forgetting no_sync() during gradient accumulation. You pay a full all-reduce on every micro-batch instead of once per step — with \(ACC=8\) that is 8× the communication for no benefit.

Uneven data across ranks. If one rank has more batches, the others block forever on the next collective. Every rank must call every collective the same number of times, or the job hangs with no error.

No checkpoint resumption. A 1000-GPU job will lose a node — hardware failure at that scale is routine, not exceptional. Checkpoint every 30–60 minutes, save model, optimizer, scheduler and data-loader position, and test that resumption actually reproduces the loss curve before you need it.

What a base model actually is

A pretrained model is a document completer, not an assistant. Prompt it with "What is the capital of France?" and a plausible continuation is another question — because in its training data, questions frequently appear in lists of questions. It knows the answer. It has not been given any reason to produce it.

Pitfall · training on the prompt tokens

If you compute loss over the full sequence, the model spends most of its capacity learning to generate user messages — which is not the job, and which is a large fraction of the tokens in a multi-turn conversation. Symptoms are distinctive: the model starts inventing the user's next question, or continues past its own answer with a fabricated follow-up turn. Mask everything that is not an assistant response. A second, equally common failure is using a chat template that does not match the one the model was trained with — the special tokens differ between Llama, ChatML, Mistral and Gemma, and mismatching them degrades quality substantially while producing output that looks superficially fine.

Quality beats quantity, by a lot

The LIMA result

LIMA fine-tuned Llama-65B on 1,000 carefully curated examples — no RLHF, no preference data — and reached quality competitive with models tuned on tens of thousands. The paper's framing, the "superficial alignment hypothesis", is that essentially all knowledge is acquired during pretraining, and alignment only teaches which format and style to surface it in. Teaching a format needs far fewer examples than teaching knowledge. The practical implication is direct: 100 excellent examples beat 50,000 scraped ones, and time spent reading and fixing your SFT data has a better return than almost anything else you could do with it.

Sequence packing

Instruction data varies wildly in length. Padding every example to the maximum wastes most of the batch. Packing concatenates multiple short examples into one full-length sequence, raising throughput 2–5×. The correctness requirement is that attention must not cross document boundaries — otherwise example B attends to example A and learns spurious continuations. Use a block-diagonal attention mask (FlashAttention supports variable-length packing natively via cumulative sequence lengths), and never rely on an EOS token alone to separate them.

Evaluating an SFT model

Validation loss is nearly useless here — it measures agreement with one particular reference response when many good answers exist. Use instead: a held-out set scored by a strong judge model with a written rubric (Lesson 100); pairwise comparison against the base model and against your previous checkpoint; a small hand-written set of cases you care about, read personally; and a check that capabilities have not regressed — run MMLU or a code benchmark before and after, because aggressive SFT on a narrow distribution causes exactly the catastrophic forgetting from Lesson 45.

LoRA, derived

Fine-tuning updates \(W_0\to W_0+\Delta W\). The hypothesis is that \(\Delta W\) has low intrinsic rank — adapting a pretrained model to a new task is a small, structured change, not an arbitrary one. So constrain it to be low-rank:

\[ \Delta W=BA,\qquad B\in\R^{d\times r},\ A\in\R^{r\times k},\ r\ll\min(d,k) \] \[ \mathbf h=W_0\mathbf x+\frac{\alpha}{r}BA\mathbf x \]

\(W_0\) stays frozen; only \(A\) and \(B\) train. For a \(4096\times4096\) matrix at \(r=8\): \(2\times4096\times8=65{,}536\) trainable parameters instead of 16.8M — 0.39%. This is Lesson 4's low-rank approximation, used in the opposite direction: not to compress an existing matrix, but to constrain a new one.

The three details that make it work

Initialisation. \(A\sim\mathcal N(0,\sigma^2)\) and \(B=\mathbf 0\). So \(BA=\mathbf 0\) at step zero and the model starts exactly as the pretrained one — no random perturbation to recover from. If both were random, you would be injecting noise into a carefully trained model before it had learned anything.

The \(\alpha/r\) scaling. It decouples the learning rate from the rank: change \(r\) from 8 to 64 and the update magnitude stays comparable, so you do not have to re-tune the LR. Common practice sets \(\alpha=2r\) or \(\alpha=r\).

Zero inference cost. After training, compute \(W=W_0+\frac{\alpha}{r}BA\) once and fold it in. The deployed model is architecturally identical to the original — unlike adapter layers, which insert extra modules and add latency to every forward pass. That property is why LoRA won over adapters.

LoRA budget · rank, target modules, and what actually gets trained

QLoRA

Three techniques that together put 65B fine-tuning on a single 48GB GPU:

  • NF4 — a 4-bit data type whose 16 quantisation levels are placed at the quantiles of a normal distribution, so each level is equally likely for normally-distributed weights. It is information-theoretically optimal for that distribution, and neural network weights are approximately normal.
  • Double quantization — the per-block quantisation constants are themselves quantised, saving another ~0.4 bits per parameter.
  • Paged optimizers — optimizer state pages to CPU RAM on a memory spike rather than crashing, using NVIDIA unified memory.

Gradients flow through the frozen 4-bit base (dequantised on the fly for each matmul) into the bf16 LoRA weights. The base is never updated, so its quantisation error is a fixed property of the forward pass rather than something that compounds.

Pitfall · targeting only q and v

The LoRA paper applied adapters to the query and value projections, and that became the default in most tutorials. Later work — including QLoRA's own ablations — found that applying LoRA to all linear layers, including the MLP, matters more than increasing the rank. Recall from Lesson 84 that two-thirds of the parameters live in the FFN; leaving it entirely untouched constrains adaptation severely. If your LoRA is underperforming full fine-tuning, widen the target modules before you raise the rank.

Settings that work, and when to skip LoRA

Style, format or tone adaptation: \(r=8\text{–}16\), \(\alpha=2r\), all linear layers, LR \(1\times10^{-4}\) to \(3\times10^{-4}\) (roughly 10× higher than full fine-tuning, because the adapters start at zero). Learning a new domain or capability: \(r=64\text{–}128\). Serving many variants: keep adapters separate and swap at request time — multi-LoRA serving runs hundreds of task-specific adapters against one base model in memory, which is the real deployment advantage.

When not to use it: if you are teaching genuinely new knowledge at scale, or continuing pretraining on a large corpus, full fine-tuning still wins. LoRA is excellent at redirecting existing capability and merely adequate at installing new capability. DoRA narrows that gap by decomposing the update into magnitude and direction and applying LoRA only to the direction.

The problem SFT leaves behind

SFT teaches the model to imitate demonstrations. But for most prompts there is no single correct response, and it is far easier for a human to compare two responses than to write the ideal one. RLHF exploits that asymmetry: collect preferences, fit a reward model to them, then optimise the policy against that reward.

The Bradley-Terry reward model

Model the probability that a human prefers \(y_c\) over \(y_r\) as a logistic function of the reward difference:

\[ P(y_c\succ y_r\mid x)=\sigma\big(r_\theta(x,y_c)-r_\theta(x,y_r)\big) \]

Maximum likelihood gives the training loss \(\mathcal L=-\log\sigma\big(r_\theta(x,y_c)-r_\theta(x,y_r)\big)\), which is exactly binary cross-entropy on the difference (Lesson 17). The reward model is usually the SFT model with the LM head replaced by a scalar head.

Note that only differences are identified — adding a constant to every reward changes nothing. The absolute scale is meaningless, which is why reward values are never comparable across reward models and why reward numbers in papers should be read as ordinal.

Why the KL penalty is not optional

The full objective is:

\[ \max_\pi\ \E_{x\sim\mathcal D,\,y\sim\pi}\Big[r_\theta(x,y)\Big]-\beta\,\mathrm{KL}\big(\pi(\cdot\mid x)\,\|\,\pi_{\text{ref}}(\cdot\mid x)\big) \]

The reward model is a learned approximation of human preference, accurate only near the distribution it was trained on. Optimise hard against it and the policy finds inputs where the approximation is wrong — outputs with enormous predicted reward that humans dislike. That is Goodhart's law in its exact form: the measure ceases to be a good measure once it becomes a target. The KL term keeps the policy inside the region where the reward model is trustworthy. Set \(\beta\) too low and you get reward hacking; too high and the model barely changes. It is the most important hyperparameter in the pipeline.

What reward hacking looks like

The failures are consistent and recognisable: responses become steadily longer (annotators mildly prefer thorough answers, so the reward model over-learns length); the model hedges and refuses more (safe answers are rarely rated worst); it repeats the question back; it adopts flattering openers; it produces confident-sounding formatting — bullet lists, bold headings — regardless of content. Watch the KL divergence and the mean output length during training; both climbing together is the signature.

Pitfall · the length bias, and the alignment tax

Length is the single most reliable confound in preference data. Always report reward alongside response length, and consider length-normalising the reward or explicitly de-biasing the reward model — otherwise a chunk of your measured "improvement" is just verbosity. Separately, expect an alignment tax: RLHF often reduces performance on capability benchmarks even as human preference improves. Mixing pretraining gradients into the RL phase (as InstructGPT did) mitigates it. Measure both, or you will optimise one into the ground without noticing.

DPO — the reward model was never necessary

The KL-constrained objective from Lesson 97 has a known closed-form optimum:

\[ \pi^\ast(y\mid x)=\frac{1}{Z(x)}\,\pi_{\text{ref}}(y\mid x)\exp\!\Big(\tfrac{1}{\beta}r(x,y)\Big) \]

Rearrange for the reward:

\[ r(x,y)=\beta\log\frac{\pi^\ast(y\mid x)}{\pi_{\text{ref}}(y\mid x)}+\beta\log Z(x) \]

Now substitute this into the Bradley-Terry likelihood. The intractable \(\log Z(x)\) depends only on \(x\), so it cancels in the difference between chosen and rejected. What remains is a supervised loss on the policy itself:

\[ \mathcal L_{\text{DPO}}=-\log\sigma\!\left(\beta\log\frac{\pi_\theta(y_c\mid x)}{\pi_{\text{ref}}(y_c\mid x)}-\beta\log\frac{\pi_\theta(y_r\mid x)}{\pi_{\text{ref}}(y_r\mid x)}\right) \]

No reward model, no sampling, no value head, no RL loop. Two models in memory instead of four, and a training loop that looks like ordinary supervised fine-tuning. The language model is secretly its own reward model — that is the paper's title and it is an accurate summary.

def dpo_loss(policy_chosen_lp, policy_rejected_lp,
             ref_chosen_lp, ref_rejected_lp, beta=0.1):
    """All arguments are SUMMED log-probs of the response tokens only."""
    pi_logratios  = policy_chosen_lp - policy_rejected_lp
    ref_logratios = ref_chosen_lp    - ref_rejected_lp
    logits = beta * (pi_logratios - ref_logratios)
    loss = -F.logsigmoid(logits).mean()
    # log these: implicit rewards, for diagnosing what the model actually learned
    chosen_r   = beta * (policy_chosen_lp   - ref_chosen_lp).detach()
    rejected_r = beta * (policy_rejected_lp - ref_rejected_lp).detach()
    return loss, chosen_r, rejected_r

Verifiable rewards — where RL stopped needing humans

For maths and code you do not need a learned reward model at all: check the answer. Run the unit tests, evaluate the final numeric result. The reward is then exact, unhackable in the usual sense, and infinitely available. Train with GRPO against it and models learn to produce long chains of reasoning, backtrack, and verify their own work — behaviours nobody demonstrated, which emerged because they raise the probability of a correct final answer. This is the most significant development in post-training since RLHF itself, and its limitation is equally clear: it only applies where correctness is cheaply checkable. Nobody has an automatic verifier for "is this essay good".

Constitutional AI / RLAIF replaces the human labeller with a model guided by an explicit written set of principles. The model critiques and revises its own outputs against the constitution, and those revisions become preference data. It scales far better than human annotation and makes the value judgements auditable — the constitution is a document you can read and argue with, rather than being implicit in a labelling workforce's aggregate behaviour.

Pitfall · DPO on a distribution the model never produces

DPO is off-policy: the chosen and rejected responses come from a dataset, not from the model being trained. If they were generated by some other model, you are teaching yours to prefer outputs it would never have produced, and the gradient signal is largely irrelevant to its actual behaviour. Best practice is to generate the candidate responses with your own SFT model and have them ranked. Also watch the implicit rewards during training: a common and confusing failure is that both \(r_c\) and \(r_r\) fall, with \(r_r\) falling faster — the loss goes down while the model gets worse at everything, because it is learning to assign low probability to all long responses rather than to prefer good ones.

Why decode wastes your GPU

Generating one token at batch size 1 requires reading every weight from memory to perform a handful of matrix-vector products. For a 70B model in fp16 that is 140 GB of reads per token. An A100 has 2 TB/s of bandwidth, so the floor is 70 ms/token ≈ 14 tokens/sec — and arithmetic intensity is about 1 FLOP per byte, against hardware built for 100+. You are using roughly 1% of the GPU's compute. Every serving optimisation that follows is an attempt to reuse those expensive weight reads across more work: batching amortises them over many sequences, speculative decoding over many candidate tokens, and quantization simply makes the reads smaller.

Pitfall · activation outliers

Weights are well-behaved and easy to quantise. Activations are not: beyond roughly 6.7B parameters, transformers develop systematic outlier features in a small number of channels, with magnitudes 20–100× the rest. Quantise per-tensor and those outliers set the scale for everything, crushing all normal values into a couple of levels. This is why naive INT8 quantization collapses at scale, and why LLM.int8() keeps outlier channels in fp16 while quantising the rest, and why SmoothQuant shifts the difficulty into the weights instead. Always evaluate perplexity after quantising — the failure is abrupt and size-dependent, so a method that worked on your 1B test model may destroy your 13B one.

Speculative decoding — free tokens from an idle GPU

Since decode is bandwidth-bound, verifying \(k\) tokens costs almost the same as generating one. So: let a small fast draft model propose \(k\) tokens, then run the large model once over all \(k\) in parallel and accept the longest prefix consistent with what it would have sampled.

With the right acceptance rule the output distribution is provably identical to sampling from the large model alone — this is exact, not an approximation. Typical speedups are 2–3×. Medusa avoids the separate draft model by adding extra prediction heads to the model itself; EAGLE drafts in feature space and achieves higher acceptance rates.

Continuous batching is the other large win. Static batching waits for every sequence in a batch to finish, so one long generation stalls seven short ones. Continuous (in-flight) batching evicts finished sequences and admits new ones at every decoding step, raising throughput by 5–20× under realistic mixed traffic. It is why vLLM, TGI and TensorRT-LLM exist rather than a plain model.generate loop.

Costing it out

Estimate cost per million tokens as \(\dfrac{\text{GPU \$/hour}}{\text{tokens/sec}\times3600}\times10^6\). At \$2/hour and 800 tok/s aggregate throughput that is about \$0.69 per million output tokens. Now compare against an API's list price before you build anything — self-hosting wins on volume, privacy and control, and loses on engineering time, idle capacity and the fact that you must keep a GPU warm. Run this arithmetic first; it frequently changes the decision.

Prompting, briefly

Chain-of-thought — asking for step-by-step reasoning before the answer — works because the model can only spend a fixed amount of computation per token. Reasoning aloud gives it more forward passes to work with, effectively turning tokens into serial compute. Self-consistency samples several chains and takes the majority answer, trading compute for accuracy. ReAct interleaves reasoning with tool calls, which is the foundation of every agent framework.

RAG, honestly

The pipeline is: chunk documents → embed → index → retrieve top-\(k\) for a query → put them in the prompt → generate. The parts that decide whether it works are not the parts people tune.

StageWhat actually matters
ChunkingRespect document structure — split on headings and paragraphs, not every 512 characters. Overlap 10–20%. Prepend the section heading to each chunk so it is self-contained.
RetrievalHybrid: dense embeddings plus BM25 keyword search, fused. Dense retrieval alone fails badly on exact identifiers, product codes, and rare proper nouns — precisely the queries where users expect exactness.
RerankingRetrieve 50, rerank with a cross-encoder, keep 5. A cross-encoder reads query and document together and is far more accurate than a bi-encoder's cosine similarity. Usually the single highest-return addition.

Pitfall · the five ways RAG fails

Retrieval missed it. The answer exists but the query embedding did not match. Measure retrieval recall@k separately from end-to-end quality — otherwise you cannot tell whether to fix the retriever or the generator, and most people blame the generator.

Chunk boundaries split the answer. A table separated from its header, a definition split from its term.

Lost in the middle. Models attend most strongly to the beginning and end of a long context and reliably underuse the middle. Put the highest-ranked chunk first, or last — not buried at position 7 of 12.

Conflicting sources. Retrieved chunks disagree — an old policy and its replacement — and the model silently picks one. Include document dates and instruct it to prefer recency.

The model ignores the context and answers from parametric memory, which is how you get confident, well-cited, wrong answers. This is the most dangerous failure because it looks exactly like success.

Long context did not kill RAG

With million-token contexts, why retrieve at all? Cost and latency: attention over 1M tokens is expensive per query, and you pay it every time. Retrieval is cheap and reusable. Accuracy also degrades within very long contexts — needle-in-a-haystack tests look good, but performance on tasks requiring several facts scattered through the context falls off sharply. And retrieval gives you provenance, access control and freshness, none of which a stuffed context provides. The two compose: retrieve aggressively, then use the long context to include more of what you retrieved.

Agents

An agent is a loop: observe, decide, act with a tool, observe the result, repeat until done. What makes agents hard is not the loop but error compounding — at 95% per-step reliability, a 20-step task succeeds 36% of the time. The engineering is therefore mostly about reducing step count, making each step verifiable, and failing loudly rather than continuing on a bad state.

Evaluation — the part people skip

Build a regression suite before you start iterating: 50–200 real inputs with expected properties, run on every change. Use LLM-as-judge with a written rubric and pairwise comparison, and calibrate the judge against human labels on a subset — judges are biased towards longer answers, towards their own outputs, and towards whichever response is presented first, so randomise position. Track cost and latency alongside quality; a 2% quality gain for 5× the cost is usually a bad trade. And keep a small set of examples you read yourself, every time. Automated evaluation tells you whether things changed; reading the outputs tells you how. Phase 7 begins on Day 87 with generative models.
