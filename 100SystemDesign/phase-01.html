OSI & TCP/IP Models

24 min · Phase 1 · Prereq: D010 · Homework: 30 min

Hook — watch it break A team puts a Layer 4 load balancer in front of their API and enables "least connections". Traffic distributes evenly, but one backend melts. The reason: the clients use HTTP/2, so each client opens one TCP connection and multiplexes 200 requests over it. The L4 balancer counts connections; it cannot see requests. It is balancing the wrong unit, because the unit it needs to see lives two layers above where it operates.

Deep dive — MTU, MSS and fragmentation

Maximum segment size, derived
\[ \text{MSS} \;=\; \text{MTU} - \text{IP header} - \text{TCP header} \] \[ 1500 - 20 - 20 = \mathbf{1460\ \text{bytes}}\quad(\text{IPv4, no options}) \]
  • Ethernet MTU is 1500 bytes almost everywhere on the public internet.
  • Tunnels shrink it. VPN/IPsec/VXLAN/GRE encapsulation eats 20–80 bytes. A path MTU of 1400 or 1436 is common inside clouds and Kubernetes overlays.
  • Jumbo frames (9000 B) exist inside datacenters and cut per-byte CPU cost substantially for bulk transfer. They must be enabled end to end, or you get black-holed traffic.
  • Fragmentation is the failure mode: if a packet exceeds the path MTU and the Don't Fragment bit is set, the router drops it and sends ICMP "fragmentation needed". If a firewall blocks ICMP — which many do — the sender never learns, and you get a connection that completes the handshake and then hangs on the first large response. This is the classic PMTUD black hole, and it presents as "small requests work, large ones time out".

Diagnostic worth memorising: if TLS handshakes complete but the first big response stalls, suspect MTU before you suspect the application. Test with ping -M do -s 1472 <host> and walk the size down.

Where TLS sits

TLS runs on top of TCP (L4) and beneath the application protocol — so nominally L5/L6, practically "just under HTTP". Two facts that come up constantly: (1) the SNI field in the ClientHello is sent in the clear, which is how one IP can host many HTTPS sites and how L4 proxies route TLS without decrypting it; (2) once you terminate TLS at the edge you can do L7 routing, and everything behind it is either plaintext inside a trusted network or re-encrypted (mTLS, Day 101).

War story Kubernetes clusters using overlay networks (VXLAN adds 50 bytes) frequently ship with a pod MTU of 1450 while nodes use 1500. Applications that work in staging fail in production for large payloads, and the symptom is a hung request rather than an error. The fix is trivial — set the correct MTU on the CNI — but finding it takes days because every layer of observability reports "the request was sent" and "no response received". Network problems that present as application hangs are the most expensive class of bug on this list.
Interview angle The layers themselves are rarely asked directly. What is asked: "L4 or L7 load balancer, and why?", "how does one IP serve many HTTPS domains?", "why did large uploads fail after we added a VPN?"
  • Reciting all seven layers when asked about load balancers. Answer the question in terms of what each layer can see.
  • Saying an L7 balancer is always better. It costs latency, CPU, and forces TLS termination.
  • Not knowing that SNI is unencrypted — it is central to how CDNs and L4 TLS routing work.
Homework Capture one HTTPS request in Wireshark. Find the TCP handshake, the ClientHello, and identify the SNI value in plaintext. Then label the bytes of one data packet by layer, and compute what fraction of that packet was headers.
D014

IP, Subnets, NAT & Network Topology

24 min · Phase 1 · Prereq: D013 · Homework: 35 min

Hook — watch it break A service behind a NAT gateway starts failing outbound calls at exactly 3 p.m. every weekday. No error in the application, no CPU spike, just connection timeouts to a partner API. The cause: every outbound connection from the whole subnet is source-NATed to one IP, and one IP has about 64,000 ports. With connections held in TIME_WAIT for 60 seconds after close, the effective limit to a single destination IP and port is far lower. They ran out of ports. The fix was more NAT gateway IPs, not more servers.

Deep dive — NAT and port exhaustion, with the arithmetic

Source NAT rewrites the private source IP and port to the gateway's public IP and a chosen port, recording the mapping so replies can be reversed. A TCP connection is identified by a 5-tuple:

The 5-tuple
\[ (\text{proto},\; \text{src IP},\; \text{src port},\; \text{dst IP},\; \text{dst port}) \]

Behind NAT, three of those are fixed for a given destination: protocol, source IP (the gateway), and destination IP+port. Only source port varies — roughly 64,000 values, and typically the ephemeral range is ~28,000 by default.

Sustainable connection rate to one destination endpoint
\[ \text{rate}_{\max} \;=\; \frac{\text{available ports}}{T_{\text{TIME\_WAIT}}} \] \[ \frac{28{,}000}{60\ \text{s}} \approx 470\ \text{new connections/s} \quad(\text{per NAT IP, per dest}) \]

Four hundred and seventy per second sounds like a lot until you realise a fleet of 40 pods each making 20 outbound API calls per second gets there instantly. Mitigations, in order of preference:

  1. Connection reuse. HTTP keep-alive, connection pools, HTTP/2 multiplexing. This removes the problem rather than raising the ceiling.
  2. More NAT IPs. Each additional public IP multiplies the port space.
  3. VPC endpoints / private links for cloud-internal destinations, so the traffic never traverses NAT.
  4. Tuning tcp_tw_reuse and the ephemeral range — real, but a smaller win and easy to get wrong.

IPv6, briefly, and why it matters now

  • 128 bits, written as eight hex groups; :: collapses one run of zeros.
  • No NAT by design — every device gets a globally routable address. That removes port exhaustion entirely and simplifies peer-to-peer.
  • Practical driver: mobile carriers are IPv6-only with translation at the edge, and cloud providers now charge for IPv4 addresses. Dual-stack is the pragmatic answer; IPv6-only internally is increasingly viable.
  • Design consequence: never store an IP in a VARCHAR(15) or a 32-bit int. Use 45 characters or a native inet type. This bug is still being written today.

War story The most common cloud networking incident is not exotic: it is a company that allocated 10.0.0.0/16 to every environment because that was the default, then tried to peer production and staging, or acquired a company that had done the same thing. There is no fix except renumbering an entire network, which cannot be done without downtime. Spend an hour on an address plan before you create the first VPC; it is the cheapest hour in infrastructure.
Interview angle Expect: "walk me through your network layout", "how do you stop the app tier reaching the internet?", "why did outbound calls start failing at scale?"

  • Not knowing NAT gateways are per-AZ and cost both an hourly rate and a per-GB processing fee — a common surprise line on the bill (D120).
  • Forgetting that cross-AZ traffic is charged in both directions in most clouds.
  • Sizing subnets from current instance count, with no headroom for a rolling deploy that doubles pods.

D015

TCP Deep Dive

32 min · Phase 1 · Prereq: D013 · Homework: 30 min

Hook — watch it break A team moves their API behind a new proxy and p50 latency doubles for small requests, from 40 ms to 95 ms. The proxy adds under a millisecond of processing. The cause: the proxy did not enable keep-alive to the backend, so every request paid a fresh TCP handshake plus a TLS handshake. On a 2 ms intra-DC RTT that is small; over a 45 ms WAN link it is 135 ms of pure waiting before a single byte of application data moves.

Core concept — the handshake and the teardown

Deep dive — flow control vs congestion control

Two independent mechanisms, constantly confused:

  • Flow control protects the receiver. The receiver advertises a window (rwnd) — "I have this much buffer left". Sender must not exceed it.
  • Congestion control protects the network. The sender maintains its own estimate (cwnd) of what the path can carry, based on loss and delay signals.
What the sender may have in flight
\[ \text{in flight} \;\le\; \min(\text{rwnd},\ \text{cwnd}) \]
Bandwidth-delay product — the window you actually need
\[ \text{BDP} \;=\; \text{bandwidth} \times \text{RTT} \] \[ 1\ \text{Gbps} \times 100\ \text{ms} \;=\; 10^{9}\times0.1/8 \;=\; \mathbf{12.5\ \text{MB}} \]

This is the number that explains "why is my transfer slow on a fast link?" To keep a 1 Gbps, 100 ms path full you must have 12.5 MB unacknowledged at all times. The classic TCP window field is 16 bits — 64 KB maximum — so without window scaling your throughput ceiling is:

Throughput ceiling from window size
\[ \text{throughput}_{\max} = \frac{\text{window}}{\text{RTT}} = \frac{65{,}536\ \text{B}}{0.1\ \text{s}} = 655\ \text{KB/s} \approx 5\ \text{Mbps} \]

Five megabits on a gigabit link. Window scaling (RFC 7323) multiplies the window by up to 214, and is negotiated in the SYN — which is why middleboxes that strip TCP options destroy long-fat-network performance.

Slow start — it is exponential, and the name is a lie
\[ \text{cwnd}_{n} = \text{IW}\cdot 2^{\,n} \quad\text{(per RTT, until ssthresh or loss)} \]

Initial window is 10 MSS ≈ 14.6 KB (RFC 6928). So the bytes deliverable after \(n\) round trips are ~14.6 KB, 29 KB, 58 KB, 117 KB, 234 KB…

Design consequence: a 100 KB page needs roughly 4 RTTs to transfer on a fresh connection, no matter how much bandwidth exists. At 150 ms RTT that is 600 ms of protocol, and it is why (a) getting your critical CSS under ~14 KB genuinely matters, (b) connection reuse is worth more than compression for small responses, and (c) TLS 1.3's saved round trip is measurable.

Deep dive — retransmission, RTO and fast retransmit

  • RTO (retransmission timeout) is computed from a smoothed RTT estimate and its variance (Jacobson/Karels). The minimum RTO in Linux is 200 ms — so a single lost packet on a 1 ms intra-DC path can cost 200 ms if the loss is detected by timeout.
  • Fast retransmit avoids that: three duplicate ACKs trigger immediate resend without waiting for the timer. It requires subsequent packets to arrive, so it does not help at the tail of a transfer — which is why tail loss is disproportionately painful and why Tail Loss Probe exists.
  • SACK lets the receiver report exactly which blocks arrived, so the sender resends only the gaps instead of everything after the loss.

The number to remember: 200 ms minimum RTO. If you see a bimodal latency distribution with a cluster near 200 ms or 400 ms above your p50, you are almost certainly looking at packet loss and timeout-based recovery, not at your application.

Head-of-line blocking, TIME_WAIT, and Nagle

Head-of-line blocking (the TCP kind)

TCP guarantees in-order delivery to the application. If segment 5 is lost, segments 6–20 sit in the receiver's buffer, received but undeliverable, until 5 arrives. With HTTP/2 multiplexing many streams over one TCP connection, one lost packet stalls every stream — the problem HTTP/3 exists to solve (D016).

TIME_WAIT is not a bug

The side that closes first holds the 5-tuple for 2×MSL (60 s on Linux) so that delayed duplicates from the old connection cannot be accepted by a new one reusing the same tuple. Practical guidance:

  • Let the client close where possible, so TIME_WAIT accumulates on machines that have fewer connections.
  • Use keep-alive so you close far fewer connections.
  • tcp_tw_reuse (safe for outbound with timestamps) is fine; tcp_tw_recycle was removed from Linux because it broke NAT'd clients badly.
  • SO_LINGER 0 sends RST and skips TIME_WAIT — it also discards unsent data. Use it only when you know what you are throwing away.
Nagle × delayed ACK — a 40 ms trap

Nagle's algorithm buffers small writes until the previous data is acknowledged, to avoid flooding the network with tiny packets. Delayed ACK holds acknowledgements up to ~40 ms hoping to piggyback them on a response. Combine them and you get a standoff: the sender waits for an ACK before sending the rest, and the receiver waits ~40 ms before ACKing. The result is a reproducible 40 ms stall on request/response protocols that write headers and body separately.

Fix: set TCP_NODELAY (disable Nagle) on latency-sensitive sockets, and write your request in one write() call. Every RPC framework does the first; not all application code does the second.

War story The 40 ms Nagle/delayed-ACK interaction has been rediscovered independently by dozens of teams — Ruby on Rails, Node, various RPC stacks — always presenting as "exactly 40 ms of unexplained latency, only on some requests". It is the best-documented example of two individually reasonable optimisations producing a pathological interaction, and a good argument for reading protocol RFCs before tuning.
Interview angle Expect: "why is our API slow over WAN?", "what does keep-alive buy you?", "why is throughput low on a fast link?"
  • "TCP is reliable so packets never get lost." TCP recovers from loss; recovery costs time.
  • Not knowing the handshake costs an RTT before TLS. This is the entire reason for connection pooling.
  • Blaming bandwidth for a throughput problem that is actually window-limited. Compute BDP first.
  • Treating TIME_WAIT accumulation as a leak to be tuned away rather than a signal that connections are not being reused.
Homework Measure the same request twice: once with keep-alive enabled and once with Connection: close. Do it against a host at least 3,000 km away. Record the difference, then compute how many RTTs that difference represents, and check it matches handshake + TLS + slow start.
D016

UDP, QUIC & HTTP/3

28 min · Phase 1 · Prereq: D015 · Homework: 25 min

Hook — watch it break A video call over TCP: one packet is lost. TCP retransmits it, and the receiver holds every packet that arrived afterwards until the missing one shows up 200 ms later. The user sees the video freeze and then fast-forward. But the frame that was lost is now 200 ms stale and worthless — the correct behaviour was to skip it and keep going. TCP's reliability guarantee, which is exactly what you want for a database, is actively harmful here.

Core concept — QUIC, and what it actually fixes

QUIC is a transport protocol built on UDP that reimplements the useful parts of TCP in user space, plus TLS 1.3, plus multiplexing. The reason it lives on UDP is not technical superiority — it is deployability: middleboxes on the internet understand UDP and would drop a genuinely new IP protocol.

0-RTT's replay caveat is a real security constraint, not a footnote. An attacker who captures 0-RTT early data can replay it. Servers must only accept idempotent requests in early data — GET, not POST /transfer. If your framework puts arbitrary requests in early data, you have a replay vulnerability.

Where HTTP/3 does not help

  • Clean, low-latency networks. With no loss, HTTP/2's head-of-line problem does not manifest. Inside a datacenter, gRPC over HTTP/2 remains the norm.
  • CPU cost. QUIC processing happens in user space with per-packet syscalls; measured CPU per byte has historically been ~2× TCP, though GSO/GRO and kernel offloads have narrowed it.
  • Networks that block or throttle UDP. Some corporate firewalls do. Clients must fall back to HTTP/2, which means you maintain both.
  • Observability. Encrypted transport headers mean your existing packet-level tooling sees much less. You need application-level telemetry (Phase 8).

The clear wins are mobile (connection migration across networks) and lossy/high-latency links (last-mile, emerging markets, satellite). If your users are on phones or far away, HTTP/3 is worth it. If they are your own services in the same rack, it is not.

War story QUIC began as an experiment at Google, deployed first between Chrome and Google's own servers, which let them iterate on the protocol without waiting for standards or kernels. That deployment model — a transport protocol shipped as part of an application, upgraded on the application's release cadence — is arguably the most important thing QUIC demonstrated. TCP evolves at the speed of operating system upgrades and middlebox replacement, which is to say, barely.
Interview angle Expect: "would you use UDP here?", "what does HTTP/3 give you over HTTP/2?", "how do you handle packet loss for live video?"
  • "UDP is faster than TCP." UDP is thinner. If you need reliability you will reimplement TCP, badly.
  • Claiming HTTP/3 solves head-of-line blocking without saying which head-of-line blocking — HTTP/1.1's was at the application layer and HTTP/2 already fixed that one.
  • Proposing 0-RTT for non-idempotent requests.
  • Forgetting UDP has no congestion control, so a naive UDP flood harms every other flow on the path — including your own.
Homework Load the same site over HTTP/2 and HTTP/3 (Chrome DevTools shows the protocol per request; you can force h2 with a flag). Compare time-to-first-byte on a fast connection, then repeat with network throttling that adds 2% packet loss. The second measurement is where the difference lives.

DNS Deep Dive

30 min · Phase 1 · Prereq: D014 · Homework: 25 min

Hook — watch it break A team fails over to their standby region by changing a DNS record. They set the TTL to 60 seconds the morning of the migration. Traffic moves… about 70% of it. The rest keeps hitting the dead region for hours. Corporate resolvers ignore short TTLs, some Java clients cached the first resolution for the lifetime of the JVM, and the record they changed was a CNAME pointing at another record whose TTL was 3,600. DNS is a distributed cache with no invalidation, and you cannot recall an answer you already gave.

Deep dive — TTL is a failover budget, not a config value

Worst-case propagation delay
\[ T_{\text{cutover}} \;\le\; \text{TTL}_{\text{record}} \;+\; \text{TTL}_{\text{parent chain}} \;+\; T_{\text{noncompliant clients}} \]

The third term is unbounded, which is the uncomfortable truth. Practical policy:

"DNS propagation" is a myth. Nothing propagates. Records are pulled on demand and expire from caches independently. If someone says "waiting for propagation", they mean "waiting for the previous TTL to elapse everywhere", and that number was fixed before you made the change.

Failure modes

  • Dependency you forgot you had. Every service call, every database connection, every S3 put resolves a name first. DNS is on the critical path of everything.
  • Resolver overload. Losing your resolvers takes down services whose backends are perfectly healthy.
  • Negative caching. Deploy with a typo, fix it in 30 seconds, and clients keep getting NXDOMAIN until the SOA minimum expires.
  • JVM's networkaddress.cache.ttl historically defaulted to caching forever with a security manager. Long-running JVMs pinned to a dead IP after failover is a genuinely common outage.
  • Kubernetes ndots:5. The default search-domain config makes external lookups try five internal suffixes first — five failed queries per external resolution, which has caused CoreDNS saturation in many clusters. Fix by using fully-qualified names with a trailing dot or lowering ndots.
War story The October 2016 attack on Dyn's managed DNS used the Mirai botnet — largely compromised IoT cameras and routers — to flood Dyn's infrastructure. Users could not reach Twitter, Reddit, Spotify, GitHub and many others, even though those services were themselves healthy. The lesson taken by the industry afterwards was concrete: use two independent DNS providers with NS records delegated to both, so no single provider's outage removes your name from the internet. It is one of the few architectural lessons from an outage that became a near-universal practice.
Interview angle DNS appears whenever failover or global routing is discussed.

  • Putting a CNAME at the zone apex. It is invalid; you need ALIAS/ANAME.
  • Forgetting DNS is a hard dependency when computing composite availability (D006).
  • Ignoring that latency-based routing sees the resolver, not the user.

Deep dive — HTTP/1.1's pipelining failure

Pipelining lets a client send request 2 before response 1 arrives. It was specified and it essentially never worked, because responses must be returned in order: a slow first response blocks the rest, and any buggy proxy in the path corrupts the sequence. Browsers disabled it. The consequence was six parallel connections per origin as the concurrency mechanism, and every HTTP/1-era frontend optimisation — sprite sheets, file concatenation, inlining, domain sharding — existed to work around that limit.

Why HTTP/1.1 page load was RTT-bound
\[ T_{\text{load}} \;\approx\; \left\lceil \frac{N_{\text{assets}}}{6} \right\rceil \times \text{RTT} \;+\;\text{transfer} \]

80 assets ÷ 6 connections ≈ 14 sequential rounds. At 100 ms RTT that is 1.4 s before bandwidth even matters.

Deep dive — HPACK, and the reason header compression matters

A typical request carries 400–800 bytes of headers, almost all identical to the previous request: the same User-Agent, the same cookies, the same Accept values. HPACK keeps a shared, indexed table on both ends: a static table of 61 common header entries, plus a dynamic table of recently seen ones. A repeated header becomes a single index byte.

Header cost at scale
\[ 100\ \text{requests}\times 700\ \text{B} = 70\ \text{KB}\;\longrightarrow\;\text{HPACK}\;\approx 2\text{–}5\ \text{KB} \]

HPACK's own head-of-line problem is why QPACK exists: because the dynamic table is order-dependent, a lost header block would block later ones. QPACK adds a mechanism to decouple table updates from stream order, at the cost of some compression efficiency.

Headers with architectural consequences

  • Cache-Control, ETag, Vary — the whole CDN story (D026). Vary: Cookie silently destroys your cache hit ratio.
  • Content-Encoding — gzip is universal; Brotli is ~15–20% smaller for text at higher compression cost. Compress text, never re-compress JPEG/PNG/video.
  • Transfer-Encoding: chunked vs Content-Length — chunked lets you stream before you know the size, which is how streaming APIs and SSE work.
  • CORS — Access-Control-Allow-Origin plus a preflight OPTIONS for non-simple requests. Preflights add an RTT; cache them with Access-Control-Max-Age.
  • Cookies — Secure, HttpOnly, SameSite. Cookies are sent on every request to the domain, so a fat cookie taxes every asset fetch. This is one reason static assets historically lived on a cookie-free domain.
War story HTTP/2 Server Push was specified to let a server send resources before the client asks. The lesson is a general one — a protocol feature that requires the sender to guess the receiver's state usually fails.

TLS, HTTPS & PKI

32 min · Phase 1 · Prereq: D015 · Homework: 25 min

Hook — watch it break At 00:00 UTC an entire product goes dark. Every client gets a certificate error. The certificate did not expire — the intermediate certificate in the chain did, and the server had been serving a chain that clients could no longer validate. Monitoring watched the leaf certificate's expiry date and reported 60 days remaining. Certificate expiry remains one of the most common causes of self-inflicted outages, and it is entirely preventable by automation.

Core concept — what TLS actually provides

PropertyMechanismWhat breaks without it
ConfidentialitySymmetric AEAD cipher (AES-GCM, ChaCha20-Poly1305)Anyone on the path reads everything
IntegrityThe AEAD tagAnyone on the path modifies content silently

Asymmetric crypto authenticates and establishes a shared secret; symmetric crypto does the bulk work. RSA/ECDSA operations cost ~0.1–1 ms; AES-GCM with hardware acceleration runs at gigabytes per second. That asymmetry is why the handshake is the expensive part and session resumption matters.

Deep dive — the TLS 1.3 handshake

Certificates, chains and where they break

A certificate binds a public key to a name, signed by a Certificate Authority. Browsers trust root CAs; roots sign intermediates; intermediates sign your leaf. The server must send the leaf and all intermediates — clients are not required to fetch missing ones, though some do.

The common production answer: terminate at the edge for the public internet (latency), then re-encrypt to origin, and use mTLS between internal services. "Encrypted at the edge, plaintext inside the VPC" was acceptable when the network perimeter was the security boundary; it is not the assumption modern designs make.

mTLS in one paragraph

Mutual TLS means the client also presents a certificate, so both ends authenticate. For service-to-service traffic this replaces shared secrets and API keys with cryptographic workload identity: the certificate says "I am the checkout service in namespace prod", and authorisation policies key off that. The hard part is not the protocol — it is issuing and rotating short-lived certificates for every workload, which is exactly what SPIFFE/SPIRE and service meshes automate.

Performance facts worth knowing

  • Session resumption (session tickets / PSK) turns a full handshake into a resumed one, eliminating asymmetric operations. Ticket keys must be shared across your LB fleet or resumption silently fails.
  • ECDSA over RSA: a P-256 signature is roughly an order of magnitude cheaper to compute than RSA-2048 on the server side and the certificate is smaller. Dual-cert setups serve ECDSA to modern clients and RSA to legacy ones.
  • ChaCha20-Poly1305 beats AES-GCM on devices without AES hardware — most relevant for older phones.
  • HSTS (Strict-Transport-Security) tells browsers to refuse plaintext for your domain, eliminating the initial HTTP → HTTPS redirect and the downgrade attack that lives there. Preloading is a one-way door; test with a short max-age first.
War story Heartbleed (2014) was a buffer over-read in OpenSSL's heartbeat extension that let any client read up to 64 KB of server memory — including private keys — leaving no trace in logs. The remediation was not just patching: every affected certificate had to be revoked and reissued, and every session token and password had to be treated as compromised. The architectural takeaway is the one that keeps mattering: plan for key compromise as an operational scenario. Short-lived certificates and automated rotation exist so that this is a Tuesday, not a company-wide emergency.
Interview angle Expect: "where do you terminate TLS?", "how do services authenticate each other?", "what happens if a cert expires?"

  • Pinning a leaf certificate in a mobile app. You will eventually rotate it and brick every installed copy.
  • Not accounting for the handshake in latency budgets — 1–2 RTTs is often the largest single term for a cold connection.
  • Assuming internal traffic does not need encryption because it is "inside the network".

FROM posts
WHERE feed_id = $1

-- index: (feed_id, created_at DESC, id DESC)

Hook — watch it break A GraphQL endpoint serves a list of 50 posts, each with an author. The resolver for Post.author runs one query per post. The client sent one request; the database received 51. Then someone requests each author's last 10 posts, and each of those posts' authors. One innocuous query becomes 5,000 database round trips and the database CPU pegs. GraphQL moved the cost from the network to your data layer, and made it invisible in your HTTP logs.

Core concept — what GraphQL actually changes

The honest framing: GraphQL trades server-side simplicity for client-side flexibility. It is a strong fit when many heterogeneous clients need different slices of a graph-shaped domain, and a poor fit for a public API with untrusted callers, or for a service with two consumers and simple data.

Schema, resolvers, execution

type Post {
  id: ID!
  title: String!
  author: User!          # each field has its own resolver
  comments(first: Int = 10, after: String): CommentConnection!
}
type Query {
  feed(first: Int = 20, after: String): PostConnection!
}
type Mutation {
  publishPost(input: PublishPostInput!): PublishPostPayload!
}

Execution walks the query tree, calling a resolver per field per object. That per-field, per-object model is what makes GraphQL flexible and what makes N+1 the default rather than the exception.

Deep dive — N+1 and DataLoader batching

Query count without batching
\[ Q \;=\; 1 \;+\; \sum_{d=1}^{D} \prod_{i=1}^{d} n_i \]

\(n_i\) = fan-out at depth \(i\). Feed of 50 posts, each with an author, each author with 10 posts: \(1 + 50 + 50 + 500 = 601\) queries for one HTTP request.

DataLoader fixes this with two mechanisms: it defers loads until the end of the event-loop tick, batching all keys requested in that window into one query; and it memoises per request so the same key is never fetched twice.

const userLoader = new DataLoader(async (ids) => {
  // one query for all ids collected in this tick
  const rows = await db.query('SELECT * FROM users WHERE id = ANY($1)', [ids]);
  const byId = new Map(rows.map(r => [r.id, r]));
  // MUST return results in the same order as ids, nulls included
  return ids.map(id => byId.get(id) ?? null);
});

// resolver becomes:  Post.author = (post) => userLoader.load(post.author_id)
// 601 queries -> 4 queries (one per depth level)

Create loaders per request, never globally. A global loader caches across users and will leak one user's data into another's response — a real and repeatedly-shipped vulnerability.

Deep dive — query cost analysis

A single legal query can be catastrophically expensive. You need three defences:

  1. Depth limit — reject queries nested beyond ~10 levels. Stops trivially recursive attacks (author { posts { author { posts { … } } } }).
  2. Complexity/cost limit — assign a cost to each field, multiply by requested list sizes, and reject above a budget. This is also the unit your rate limiter should consume.
  3. Persisted queries — clients register queries at build time and send a hash at runtime. The server executes only known queries. This eliminates arbitrary-query risk entirely, makes GETs (and therefore CDN caching) possible, and shrinks request size.
A workable cost model
\[ \text{cost}(f) = c_f + m_f \sum_{c\,\in\,\text{children}(f)} \text{cost}(c) \]

\(c_f\) is the field's own cost; \(m_f\) is its list multiplier (the requested first: value). Reject when the root cost exceeds the caller's budget, and return the cost in a response header so clients can self-regulate.

Caching, which is the real cost of adopting GraphQL

  • HTTP layer: lost by default. Recoverable with persisted queries over GET plus Cache-Control, which lets a CDN cache responses again.
  • Client layer: normalised caches (Apollo, Relay, urql) key objects by __typename:id and share them across queries. This is genuinely excellent — and it is why returning globally unique IDs matters.
  • Server layer: cache per-resolver, keyed by the underlying entity, not by the query. This is where DataLoader and a distributed cache combine (Phase 3).

Federation, briefly

With microservices, each team owns a slice of the schema and a gateway composes them into one graph. Subgraphs declare which types they own and which they extend by key. The gateway builds a query plan and fans out. The tradeoffs are real: the gateway is a new critical dependency and a latency hop, the query plan can hide expensive cross-service joins, and schema composition becomes a CI concern. It is the right tool when many teams must present one API; it is heavy machinery for three services.

War story GraphQL came out of Facebook's mobile rewrite, where the problem was concrete: a news feed screen needed data from many places, and each REST round trip on a 2G connection cost hundreds of milliseconds. One request that returns exactly the screen's data was a large win in that context. That context — many device types, hostile networks, one company owning both ends — is the one where GraphQL pays off most clearly. Adopting it for a service-to-service API inside a datacenter inherits the costs without the benefit.

  • "GraphQL avoids over-fetching, so it is faster." It moves work to your resolvers and gives up HTTP caching.
  • Not mentioning N+1 when asked about GraphQL performance. It is the first thing an interviewer is listening for.
  • Proposing GraphQL for a public API without depth limits, cost analysis or persisted queries.
  • Forgetting that a 200 response can contain errors, so your monitoring must parse bodies.

Deep dive — the wire format, and why field numbers are sacred

Each field is encoded as a tag followed by a value. The tag packs the field number and the wire type:

Deadlines, cancellation and metadata — the part people skip

  • Deadlines, not timeouts. A gRPC deadline is an absolute time propagated across every hop. Service A calls B with 300 ms remaining; B calls C and C sees the remaining budget, not a fresh 300 ms. This prevents the classic failure where a 5-hop chain each with a 1 s timeout waits 5 s. Deadline propagation is the single best feature gRPC gives you for free (D100).
  • Cancellation is real. When a client goes away, the server's context is cancelled and it can stop working. In HTTP/1.1 this information is largely unavailable.
  • Metadata is the header equivalent: auth tokens, trace context, tenant IDs. Binary values use a -bin suffix.
  • Interceptors are the middleware layer — auth, logging, metrics, retries — and belong there, not in handlers.

The load balancing problem

gRPC runs over HTTP/2, and HTTP/2 keeps one long-lived connection per backend. A classic L4 balancer assigns that connection once and then every subsequent request goes to the same backend forever — so scaling out adds capacity that receives no traffic. Three answers:

ApproachHowCost
L7 proxyEnvoy/nginx terminates HTTP/2 and balances per requestExtra hop, extra latency
Client-side (proxyless)Client resolves all endpoints and balances itselfNo hop; needs service discovery + xDS (D061)
Service mesh sidecarSidecar does L7 balancing locallyMesh complexity (D101)

gRPC-Web exists because browsers cannot speak raw gRPC — no access to HTTP/2 frames. It needs a proxy to translate, and does not support client streaming. For browser clients, REST or GraphQL is usually the simpler answer; keep gRPC for service-to-service.

When JSON still wins

  • Public APIs where third parties must integrate with curl and no toolchain.
  • Debuggability — you can read a JSON body in a log; you cannot read a protobuf one.
  • Browser clients without a translating proxy.
  • Small-scale internal services where codegen and build integration cost more than they save.
War story gRPC descends from Stubby, Google's internal RPC system, which handled a reported tens of billions of requests per second across the fleet. The features that look like over-engineering at small scale — deadline propagation, per-call cancellation, structured status codes, interceptors — are exactly the features that make a large mesh of services debuggable. If you adopt gRPC, adopt those; the wire format is the least interesting part of the package.
Interview angle Expect: "REST or gRPC between services?", "how do you evolve a schema without downtime?"
  • "gRPC is faster." Say why: parse cost, header compression, connection reuse, deadline propagation.
  • Not knowing that an L4 balancer in front of gRPC pins connections and defeats scale-out.
  • Reusing or renumbering field numbers.
  • Proposing gRPC for a browser-facing API without mentioning gRPC-Web and its proxy.
Homework Define a service, generate stubs in two languages, and exchange a message. Then evolve the schema three times — add a field, deprecate one with reserved, add an enum value — and verify an old client still works against the new server each time.

Realtime: WebSockets, SSE, Long Polling, WebRTC

32 min · Phase 1 · Prereq: D015, D016 · Homework: 45 min

The reconnect storm exhausts the accept queue, so half fail and retry immediately, and each successful reconnect triggers a full message-history fetch. The deploy took four seconds. The outage took forty minutes. Stateful connections turn every restart into a thundering herd unless you design for it.

Deep dive — WebSocket mechanics

  • Handshake: an HTTP GET with Upgrade: websocket and Sec-WebSocket-Key; the server replies 101 Switching Protocols. From then on the TCP connection carries WebSocket frames, not HTTP.
  • Framing: 2–14 byte header, opcode (text/binary/close/ping/pong), and a mask that client→server frames must apply. Frames can be fragmented.
  • Ping/pong: the only reliable way to detect a dead peer. TCP keep-alive defaults to two hours; intermediaries drop idle connections in 30–120 seconds. Send an application-level heartbeat every 20–30 s, and treat two missed pongs as dead.
  • Reconnection must have exponential backoff with full jitter, or you build the outage in the hook. And it must be resumable: the client sends the last message ID it saw and the server replays the gap from a per-conversation log.

Deep dive — scaling one million connections

Capacity per gateway node
\[ N_{\text{conns}} \;=\; \min\!\left(\frac{\text{RAM}}{\text{bytes per conn}},\ \text{fd limit},\ \frac{\text{CPU}}{\text{msg rate}\times\text{cost per msg}}\right) \]

Usually memory or fd-bound when idle, CPU-bound when chatty. 50k–200k connections per node is a realistic planning range; above that, tail latency during GC or reconnect storms gets ugly.

WebRTC, in the detail you need for an interview

  • Signalling is not part of WebRTC. You must build it — usually a WebSocket channel — to exchange SDP offers/answers and ICE candidates.
  • NAT traversal: STUN tells a peer its public address (cheap, works for ~80% of networks). TURN relays media when direct connectivity fails (expensive — you pay for all that bandwidth). ICE is the algorithm that tries candidate pairs and picks one. Budget for TURN; it is the line item people forget.
  • Group calls: mesh (each peer sends to every other) is \(O(n^2)\) uplink and dies past 4–5 participants. SFU (selective forwarding unit) receives each stream once and forwards it — scales well, no transcoding, each client still decodes \(n-1\) streams. MCU mixes into one stream — cheapest for clients, very expensive in server CPU. SFU is the standard answer today.
Why mesh does not scale
\[ \text{uplink streams per peer} = n-1,\qquad \text{total streams} = n(n-1) \]

At \(n=10\): 90 streams and each participant uploads 9 copies of their video. With an SFU each peer uploads once — 10 total uploads.

War story Slack's published account of their WebSocket architecture describes a problem specific to this design: when a large team's connections reconnect, each client historically re-downloaded a large amount of state, so a mass reconnect produced a load spike far larger than the connection count implied. Their work focused on making reconnection incremental — resume from a sequence number rather than refetch. That is the general lesson: for stateful connections, the cost of reconnecting matters more than the cost of connecting.
Interview angle Expect: "how do you push updates to clients?", "how do you scale to a million connections?", "what happens on deploy?"
  • Reaching for WebSockets when the requirement is one-directional. SSE is simpler and reconnects itself.
  • Forgetting the pub/sub backplane. Without it, a message can only reach users connected to the same node.
  • No heartbeat, so half-open connections accumulate and messages vanish silently.
  • Reconnect without jitter — you have designed a self-inflicted DDoS.
  • Proposing a mesh for a 10-person video call.
Homework Build a two-node chat where each node holds WebSocket connections and messages route between them via Redis pub/sub. Then kill one node while a client is connected, and make the client reconnect with jittered backoff and replay every message it missed using a sequence number. The replay is the part that teaches you something.

Proxies, Reverse Proxies, API Gateways & BFF

28 min · Phase 1 · Prereq: D013, D020 · Homework: 30 min

Hook — watch it break An API gateway grows over three years. First it did auth and rate limiting. Then someone added a response transformation. Then a small piece of pricing logic, because "it's just a lookup". Then request enrichment from a third service. Now the gateway is the highest-traffic service in the company, it is owned by no team, it cannot be deployed without a change-advisory meeting, and it is a single point of failure for every product. The gateway did not fail. It succeeded at absorbing responsibilities that never belonged to it.

Core concept — forward vs reverse proxy

Core concept — what a gateway should and should not do

Belongs in the gateway
  • Authentication (validate the token, reject early)
  • Rate limiting and quota enforcement
  • Routing by path, host, header, version
  • Request/response logging, tracing, correlation IDs
  • TLS termination and mTLS to upstreams
  • Protocol translation (REST → gRPC at the edge)
  • Payload size limits, timeouts, circuit breaking
  • CORS, security headers, WAF integration
Does not belong in the gateway
  • Business rules of any kind
  • Data access or joins across services
  • Complex orchestration and sagas
  • Per-customer bespoke logic
  • Anything requiring a database of its own
  • Anything one product team needs to deploy weekly

The test: if a change to the gateway requires understanding a domain concept, it belongs in a service.

Deep dive — the gateway as a single point of failure

Every request traverses it, so its availability multiplies against everything behind it (D006). Mitigations, in order of value:

  1. Run it stateless and horizontally, at least N+2 per AZ, behind an L4 balancer or anycast.
  2. Keep it dumb. Fewer features means fewer deploys means fewer incidents.
  3. Separate edge and internal gateways. The edge handles hostile traffic; internal service-to-service calls should not traverse it at all — that creates a hairpin and a shared fate.
  4. Fail open where safe. If the rate-limiter store is down, decide deliberately: fail open (accept traffic, risk overload) or fail closed (reject, guarantee outage). For rate limiting, fail open with a local fallback limit. For authentication, always fail closed.
  5. Config changes are deploys. Route config has caused more gateway outages than code. Version it, review it, canary it (D108).

Gateway vs service mesh — the boundary

North–south traffic (external clients → your system) belongs to the gateway: it handles untrusted callers, authentication, quotas, and public contracts. East–west traffic (service → service) belongs to the mesh: mTLS, retries, circuit breaking, per-service authorisation. They overlap technically — both are often Envoy — but they have different threat models and different owners. Using the edge gateway for internal calls creates a hairpin through your most contended component.

War story The "gateway accretes logic" pattern is the most common architectural failure in service-oriented organisations, and it happens for a rational reason: the gateway is the one place a change can be made without coordinating across teams. That convenience is exactly the danger. The countermeasure is organisational rather than technical — a written charter for what the gateway does, and a named owner empowered to say no.

  • Only authenticating at the gateway and trusting everything behind it — services should still verify identity (D101, D117).
  • Forgetting the gateway multiplies into every service's availability.
  • One BFF for all clients. That is just a gateway with extra steps.

Rate Limiting Algorithms

34 min · Phase 1 · Prereq: D024 · Homework: 45 min

Hook — watch it break An API enforces 100 requests per minute with a fixed window. A client sends 100 requests at 11:59:59 and another 100 at 12:00:01. Both windows are within their limit. The backend saw 200 requests in two seconds — twice the intended rate, delivered as a burst. The rate limiter reported full compliance while the database fell over.

Deep dive — token bucket, with the maths

Lazy refill — no background timer needed
\[ \text{tokens} \;\leftarrow\; \min\bigl(B,\; \text{tokens} + r\,(t_{\text{now}}-t_{\text{last}})\bigr) \]

\(B\) = bucket capacity (max burst), \(r\) = refill rate (sustained requests/second). Allow the request if \(\text{tokens} \ge 1\), then decrement.

Two parameters give you two independent controls: \(r\) sets the sustained rate, \(B\) sets how much burst you tolerate. A client that has been idle accumulates up to \(B\) tokens and can spend them at once — which is usually what you want, because idle clients bursting briefly is normal and harmless.

Worst-case burst and recovery
\[ \text{max instantaneous} = B,\qquad t_{\text{refill}} = \frac{B}{r} \]

Deep dive — doing it correctly in a distributed system

The naive Redis implementation — GET, check, SET — has a race: two gateway instances both read 99, both allow, and the counter ends at 101. Under load this is not rare; it is constant. The fix is atomicity, which means a Lua script (Redis executes scripts atomically) or the newer CL.THROTTLE-style modules.

-- KEYS[1] = bucket key   ARGV = capacity, refill_rate, now_ms, cost
local b   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local cap = tonumber(ARGV[1])
local rate= tonumber(ARGV[2])      -- tokens per ms
local now = tonumber(ARGV[3])
local cost= tonumber(ARGV[4])
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now

tokens = math.min(cap, tokens + (now - ts) * rate)   -- lazy refill
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate) * 2)  -- self-cleaning
return { allowed and 1 or 0, math.floor(tokens), math.ceil((cost - tokens) / rate) }

Note the PEXPIRE. Without it you accumulate one key per client forever and eventually run out of memory. Every rate-limit key must expire.

Always send Retry-After. Without it, well-behaved clients guess, and guessing means retrying immediately, which means your rate limiter is now generating the load it exists to prevent.

Throttling vs shedding vs quotas
  • Rate limiting / throttling — fairness and abuse prevention. Policy-driven, per-caller, predictable, returns 429.
  • Load shedding — self-preservation. Triggered by your health, not their behaviour; drops cheap or low-priority traffic first; returns 503 (D063).
  • Quotas — business limits over long windows (per day, per month). Billing concern, not a latency concern.

They are different systems with different triggers, and conflating them means you shed traffic from your best customer during an incident while a scraper stays inside its limit.

War story Stripe published a description of their rate-limiting design that separates limiters by purpose: a request-rate limiter, a concurrency limiter for expensive in-flight operations, and a fleet-usage load shedder that reserves capacity for critical traffic during incidents. The important idea is the separation — one limiter cannot express "this caller is over their fair share" and "the whole system is in trouble" at the same time, because those need different keys and different responses.

D026

CDNs & Edge Delivery

32 min · Phase 1 · Prereq: D004, D018 · Homework: 35 min · Phase 1 finale

Hook — watch it break A team puts a CDN in front of their API and celebrates. Two weeks later the origin bill is unchanged and hit ratio is 4%. The cause: every response carries Vary: Cookie and every visitor has a unique session cookie, so every response is a unique cache entry. The CDN is working perfectly. It is caching a million objects that will each be requested exactly once.

Core concept — what a CDN is made of

ComponentRole
PoP (point of presence)A cluster of caching servers in a city, close to users. Hundreds worldwide.
AnycastOne IP announced from every PoP; BGP routes each user to the nearest one. This is why CDN failover is fast — no DNS TTL involved (D017).
Tiered / shield cacheA regional mid-tier between edge PoPs and origin. Without it, 300 PoPs each miss independently and hammer origin 300×.
Origin shieldA single designated PoP that all others fetch through — collapses origin requests to one per object.
Request collapsingMany simultaneous misses for the same object become one origin fetch. This is stampede protection (D055) built into the CDN.

Deep dive — the hit-ratio economics

Origin traffic and effective latency
\[ \text{origin bytes} = (1-h)\cdot B_{\text{total}} \qquad L_{\text{eff}} = h\,L_{\text{edge}} + (1-h)\,L_{\text{origin}} \]

The nonlinearity is the point. Going from 90% to 95% hit ratio does not cut origin load by 5% — it halves it, because you are cutting the miss fraction from 10% to 5%.

Miss reduction from a hit-ratio improvement
\[ \frac{\text{misses after}}{\text{misses before}} = \frac{1-h_2}{1-h_1} \qquad \frac{1-0.95}{1-0.90} = 0.5 \]

Beyond static: dynamic acceleration, private media, edge compute

  • Dynamic acceleration — even uncacheable requests benefit: the user's TCP and TLS handshakes terminate at a nearby PoP, and the PoP holds a warm, tuned, long-lived connection to origin. You can save 100–200 ms on a cross-continent request with a 0% hit ratio.
  • Signed URLs / token auth — private media (a paid video, a user's document) is cached at the edge but access is gated by a signature with an expiry and often a client-IP binding. The object is public to the cache and private to the world.
  • Edge compute (Workers, Lambda@Edge, edge middleware) — good for A/B assignment, auth checks, redirects, header manipulation, request routing, personalisation of otherwise-cacheable pages. Bad for anything needing a database, because your database is not at the edge (D104).

War story Netflix's Open Connect takes the CDN idea to its endpoint: rather than renting capacity, they build storage appliances and place them inside ISP networks, then pre-position content overnight based on predicted regional demand. Because their catalogue is finite and their viewing patterns are predictable, they can push content before anyone requests it — turning a pull cache into a push distribution network. It only works because of that predictability, which is the general lesson: the right caching strategy is a function of how well you can predict demand.
