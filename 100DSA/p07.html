L103 · DAY 72

Sparse Table and O(1) Range Minimum

45m video

When the array never changes, precompute the answer for every window whose length is a power of two. Any range is the union of two such windows, and when the operation is idempotent the overlap does no harm, so a range-minimum query costs two lookups.

Static ranges and the doubling table

Static means the array is fixed and only queries arrive. Prefix sums (L12) handle sums this way, but they need subtraction, and min has no inverse. The sparse table stores, for every level \(k\) and start \(i\),

$$st[k][i] = \min(a_i, \dots, a_{i+2^k-1}), \qquad st[k][i] = \min\big(st[k-1][i],\ st[k-1][i+2^{k-1}]\big),$$

because a window of length \(2^k\) is two adjacent windows of length \(2^{k-1}\). Row \(k\) has \(n - 2^k + 1\) entries and there are \(\lfloor \log_2 n\rfloor + 1\) rows, so building it costs \(O(n \log n)\) time and memory.

Why overlap is safe: idempotence

Theorem · two-window query

Let \(\circ\) be associative and idempotent (\(x \circ x = x\)). For \(l < r\) put \(k = \lfloor \log_2 (r-l) \rfloor\). Then \(a_l \circ \dots \circ a_{r-1} = st[k][l] \circ st[k][r-2^k]\).

Proof

From \(2^k \le r-l < 2^{k+1}\), both windows \(A = [l, l+2^k)\) and \(B = [r-2^k, r)\) lie inside \([l, r)\), and they overlap because \(r - 2^k < l + 2^k\). Split the range into \(P = [l, r-2^k)\), \(O = [r-2^k, l+2^k)\), \(S = [l+2^k, r)\). Then \(f(A) = f(P)\circ f(O)\) and \(f(B) = f(O) \circ f(S)\), so by associativity \(f(A)\circ f(B) = f(P)\circ \big(f(O)\circ f(O)\big)\circ f(S) = f(P)\circ f(O)\circ f(S)\), using idempotence once on the middle. If \(P\) or \(S\) is empty, drop it. Commutativity is never used.

Min, max, gcd, bitwise and, and bitwise or are idempotent. Sum, product and xor are not. For those, decompose \(r - l\) into its binary digits and take disjoint blocks left to right: \(O(\log n)\) per query, valid for any associative operation. For plain sums this is pointless, because prefix sums answer in \(O(1)\) and a BIT (L104) adds updates.

def query_disjoint(t, op, e, l, r):        # any associative op, O(log n)
    res = e
    for k in range((r - l).bit_length() - 1, -1, -1):
        if l + (1 << k) <= r:
            res = op(res, t[k][l])
            l += 1 << k
    return res

Floor-log2, the log table, and memory

(r - l).bit_length() - 1 is exactly \(\lfloor \log_2(r-l) \rfloor\) for a positive int, computed in C. Do not use int(math.log2(x)): for \(x = 2^{53}-1\) the float result rounds to 53.0. The classic alternative is a precomputed table, lg[i] = lg[i >> 1] + 1 for \(i \ge 2\). It is the right call in C++, but in a quick CPython 3.12 test bit_length was slightly faster than the table lookup (the table took about 20% longer over \(10^6\) calls), so keep bit_length unless your own measurement says otherwise.

Store one list per level. Each row is one map(op, prev, prev[h:]) call: the loop runs in C, though min is still called once per element. For min specifically, [x if x < y else y for x, y in zip(prev, prev[h:])] built about twice as fast in the same test at \(n = 2\cdot10^5\); a hand-written double index loop was no faster than map. Because min returns one of its arguments, the rows hold pointers to existing int objects rather than new ones. At \(n = 2\cdot 10^5\) that is 18 rows of about \(2\cdot10^5\) pointers, roughly 27 MB. At \(n = 10^6\) it is 20 rows and about 160 MB, which is over many limits. Switch the rows to array('i'), or use a different structure.

Implementation

from math import gcd
from operator import and_
import random

class SparseTable:
    """O(1) query for an associative, idempotent op (min, max, gcd, and_, or_).
    query(l, r) = op over a[l:r], half-open, needs l < r. Build O(n log n)."""
    def __init__(self, a, op=min):
        self.op = op
        self.t = t = [list(a)]
        h = 1
        while 2 * h <= len(a):
            prev = t[-1]
            t.append(list(map(op, prev, prev[h:])))   # level k from level k-1, in C
            h *= 2

    def query(self, l, r):
        k = (r - l).bit_length() - 1
        row = self.t[k]
        return self.op(row[l], row[r - (1 << k)])

for op in (min, max, gcd, and_):                       # stress test vs brute force
    a = [random.randrange(1, 100) for _ in range(random.randrange(1, 60))]
    st = SparseTable(a, op)
    for _ in range(300):
        l = random.randrange(len(a)); r = random.randrange(l + 1, len(a) + 1)
        want = a[l]
        for x in a[l + 1:r]: want = op(want, x)
        assert st.query(l, r) == want

Applications

  • LCA as the minimum-depth node in an Euler-tour range (L58).
  • LCP of any two suffixes as the minimum of a range of the LCP array (L45).
  • Range gcd, and with it "how many elements of the range divide all the others".
  • Static max in every window of width \(w\): only level \(k = \lfloor\log_2 w\rfloor\) is needed, answer max(row[i], row[i + w - 2**k]). The monotonic deque is \(O(n)\), but this is a one-liner once the table exists.

Disjoint sparse table. At each level, split the array into blocks of size \(2^{j+1}\) and store aggregates running outward from each block's midpoint: suffixes to the left, prefixes to the right. A query \([l, r]\) with \(l \ne r\) uses the level given by the highest set bit of \(l \oplus r\) and returns suf[j][l] ∘ pre[j][r]: \(O(1)\) for any associative operation, including sums mod \(p\) and matrix products. The sqrt tree goes further and supports updates; it is rarely worth it in Python.

Problems

CSES — Static Range Minimum Queries. Direct use, with \(n, q \le 2\cdot10^5\). Input parsing costs more than the lookups, so read every token at once and pair them with zip(it, it). Inlining the query body into the loop measured no faster than calling the method under CPython 3.12, so keep the method.

import sys

def main():

    n = int(data[0])
    st = SparseTable(list(map(int, data[2:2 + n])))
    it = map(int, data[2 + n:])
    out = [st.query(a - 1, b) for a, b in zip(it, it)]   # [a, b] 1-indexed to half-open

CSES — Static Range Sum Queries (for contrast). pre = [0, *accumulate(a)] and answer pre[b] - pre[a-1]. Sum is invertible, so no table is needed.

LeetCode 1521 — Find a Value of Mysterious Function Closest to Target. The function is the AND of a subarray. AND is idempotent, and for a fixed right end the AND of arr[l:r] can only grow as \(l\) moves right. Binary search for the first \(l\) whose AND reaches the target and compare it with its left neighbour: \(O(n \log n)\) total. The alternative framing keeps the set of distinct ANDs ending at each index, which has at most about 30 elements because each step can only clear bits.

def closest_to_target(arr, target):
    st = SparseTable(arr, and_)
    best = abs(arr[0] - target)
    for r in range(1, len(arr) + 1):
        lo, hi = 0, r - 1                       # first l with AND(arr[l:r]) >= target
        while lo < hi:
            mid = (lo + hi) // 2
            if st.query(mid, r) >= target: hi = mid
            else: lo = mid + 1
        best = min(best, abs(st.query(lo, r) - target))
        if lo: best = min(best, abs(st.query(lo - 1, r) - target))
    return best

Range gcd (Codeforces — Ant colony). An element divides every other element of the range exactly when it equals the range gcd. Answer each query with a gcd sparse table plus a count of that value in the range, using bisect on that value's sorted list of positions.

What breaks
  • Overlap with a non-idempotent op. A "sparse table for sums" that double-counts the overlap passes small tests where the overlap is one cell of value 0.
  • Inclusive versus half-open. Judges give \([a, b]\) 1-indexed. Convert once at input, to \(l = a - 1\) and \(r = b\), and never think about it again.
  • Float logs. int(math.log2(x)) is wrong near powers of two for large \(x\). Use bit_length.
  • Line-by-line input. Calling input() \(2\cdot10^5\) times costs more than every table lookup put together. Read the whole input once (L2).
  • Memory at 10⁶. \(n \log n\) list slots exceed 256 MB. Measure before you submit.

Fenwick Tree (BIT) I: Point Update, Prefix Query

50m video

A Fenwick tree gives every index \(i\) responsibility for the block of length \(\text{lowbit}(i)\) that ends at \(i\). Prefix queries peel blocks off the right end and updates climb to the blocks that contain a position. Both loops come out of the binary representation of \(i\), so each costs \(O(\log n)\) and fits in four lines.

Responsibility ranges

A sparse table (L103) cannot absorb an update, and prefix sums pay \(O(n)\) per update. A BIT pays \(O(\log n)\) for both operations.

Definition · Fenwick tree

For a 1-indexed array \(a_1..a_n\), let \(\text{lowbit}(i) = i \mathbin{\&} (-i)\), the value of the lowest set bit. In two's complement \(-i = \lnot i + 1\), which flips every bit above the lowest 1, so the AND keeps only that bit. The tree stores

$$t[i] = \sum_{j = i - \text{lowbit}(i) + 1}^{i} a_j, \quad\text{the block } (i - \text{lowbit}(i),\ i].$$

Deriving the two loops

Query. Block \(i\) ends at \(i\) and starts just after \(i - \text{lowbit}(i)\), which is \(i\) with its lowest bit cleared. So \(\text{prefix}(i) = t[i] + \text{prefix}(i - \text{lowbit}(i))\). Each step clears one set bit, so there are at most \(\lfloor\log_2 n\rfloor + 1\) steps. i &= i - 1 clears the lowest bit directly.

Theorem · update path

The blocks that contain position \(i\) are exactly \(i,\ i + \text{lowbit}(i),\ \dots\), continuing while the index is \(\le n\).

Proof

Write \(i = m\cdot 2^{p+1} + 2^p\), where \(2^p = \text{lowbit}(i)\). Every \(j\) with \(i < j < i + 2^p\) has the form \(i + s\) with \(0 < s < 2^p\), so \(\text{lowbit}(j) = \text{lowbit}(s) \le s\) and its block starts after \(j - s = i\). It does not contain \(i\). Now \(j = i + 2^p = (m+1)\cdot 2^{p+1}\) has \(\text{lowbit}(j) = 2^q\) with \(q \ge p+1\). Since \(2^q\) divides \(j\), the start \(j - 2^q\) is a multiple of \(2^{p+1}\) below \(j\), so it is at most \(m \cdot 2^{p+1} < i\). Block \(j\) therefore contains \(i\). It is the next such block, and it contains all of block \(i\), so the argument repeats from \(j\). Each step at least doubles the lowbit, so the path has \(O(\log n)\) steps.

A range sum is \(\text{prefix}(r) - \text{prefix}(l-1)\), so the operation needs an inverse: sums, xor, and sums mod \(p\) work, but min and max do not (L105 covers the restricted max version). 1-indexing is mandatory, because \(\text{lowbit}(0) = 0\) and i += i & -i would loop forever at index 0. The class below shifts by one at the boundary so callers stay 0-indexed.

O(n) construction

Calling add \(n\) times costs \(O(n \log n)\). Instead, copy the array into t[1..n] and, for \(i = 1, 2, \dots\), add t[i] into its parent t[i + lowbit(i)]. When \(i\) is reached, every block nested inside it has a smaller index and has already been pushed into it, so t[i] is complete. Each node is pushed once, so the build is \(O(n)\).

A BIT over values: counting inversions

Index the BIT by value instead of position and it counts how many elements seen so far are \(\le x\). Scan left to right, and for each \(x\) add the number of earlier elements greater than \(x\), which is seen - prefix(rank(x) + 1). Coordinate compression (L24) maps values to ranks \(0..m-1\). Total cost: \(O(n \log n)\). This "BIT over values" is a different idea from "BIT over positions", and most of the problems below use it.

Implementation

class BIT:
    """Fenwick tree for sums. Public API is 0-indexed; the tree is 1-indexed inside."""
    def __init__(self, n_or_list):
        if isinstance(n_or_list, int):
            self.n, self.t = n_or_list, [0] * (n_or_list + 1)
        else:
            t = [0, *n_or_list]
            n = len(t) - 1
            for i in range(1, n + 1):          # O(n) build: push each node into its parent
                j = i + (i & -i)
                if j <= n: t[j] += t[i]
            self.n, self.t = n, t

    def add(self, i, v):                       # a[i] += v
        t, n = self.t, self.n
        i += 1
        while i <= n:
            t[i] += v
            i += i & -i

    def prefix(self, i):                       # a[0] + ... + a[i-1]
        t, s = self.t, 0
        while i:
            s += t[i]
            i &= i - 1                         # clear the lowest set bit
        return s

    def range(self, l, r):                     # a[l] + ... + a[r-1]
        return self.prefix(r) - self.prefix(l)

def count_inversions(a):
    rank = {v: i for i, v in enumerate(sorted(set(a)))}
    bit, inv = BIT(len(rank)), 0
    for seen, x in enumerate(a):
        r = rank[x]
        inv += seen - bit.prefix(r + 1)        # earlier elements strictly greater than x
        bit.add(r, 1)
    return inv

for _ in range(300):

The next three are all "BIT over compressed values":

  • LeetCode 315 — Count of Smaller Numbers After Self. Scan right to left; the answer at \(i\) is prefix(rank(nums[i])), then insert.
  • LeetCode 493 — Reverse Pairs. Count earlier values greater than \(2x\): seen - prefix(bisect_right(vals, 2*x)). The threshold \(2x\) need not be in the compressed list, and bisect handles that.
  • LeetCode 327 — Count of Range Sum. Over prefix sums \(P\), count \(i < j\) with \(P_j - U \le P_i \le P_j - L\). That is a value-range count, two bisects and one range call per \(j\).
from bisect import bisect_left, bisect_right

def count_range_sum(nums, lower, upper):     # LeetCode 327, O(n log n)
    pre = [0]
    for x in nums: pre.append(pre[-1] + x)
    vals = sorted(set(pre))
    bit, ans = BIT(len(vals)), 0
    for s in pre:
        ans += bit.range(bisect_left(vals, s - upper), bisect_right(vals, s - lower))
        bit.add(bisect_left(vals, s), 1)
    return ans

BIT or segment tree?

A BIT is about a quarter of the code of a lazy segment tree, and it is faster. In a quick CPython 3.12 test with \(2\cdot10^5\) mixed updates and range sums, the running times of the BIT, an iterative segment tree and a recursive one came out in the ratio 1 : 1.3 : 3. So the BIT is about 3 times faster than the recursive tree but only about 1.3 times faster than the iterative one. Absolute times vary a lot between machines and judges, so compare ratios. What a BIT cannot do directly is non-invertible operations (range min with updates), custom merged nodes, or general range assignment. Those need the segment tree of L106.

What breaks
  • Index 0. add(0, v) on a raw 1-indexed tree loops forever, because \(0 \mathbin{\&} -0 = 0\). Shift at the boundary, as the class does.
  • Size off by one. The tree needs \(n+1\) slots. The update loop runs while i <= n; writing < n silently drops updates to the last block.
  • Set versus add. A "set" query applied as add(k, u) passes the samples whenever the old value was 0.
  • Compression gaps. Querying with a value that is not in the compressed list: use bisect on the sorted values, never rank[x].
  • Per-call overhead. Hoist self.t into a local inside both loops, as the class does. Attribute lookups inside a loop that runs 18 times per call add up.

L105 · DAY 73

Fenwick Tree II: Range Updates, 2D, and k-th Element

50m video

Three tricks extend the BIT. Store differences and you get range updates. Store a second, index-weighted copy and you get range sums under range updates. Walk the implicit tree top-down and you find the k-th element in \(O(\log n)\), which turns a BIT over values into the ordered multiset Python does not ship.

Range update, point query

Keep a BIT over the difference array \(d_i = a_i - a_{i-1}\). Adding \(v\) to a[l:r] is two point updates, add(l, v) and add(r, -v), and \(a_i\) is the prefix sum prefix(i + 1). With the L104 class, add(n, …) is a no-op, so \(r = n\) needs no special case.

Range update, range query: two BITs

Derivation · the two-BIT formula

With 1-indexed \(a_j = \sum_{i \le j} d_i\), the prefix sum is

$$S(x) = \sum_{j=1}^{x} \sum_{i=1}^{j} d_i = \sum_{i=1}^{x} d_i\,(x - i + 1) = (x+1)\sum_{i \le x} d_i \;-\; \sum_{i \le x} i\, d_i .$$

The first sum depends on \(x\) only through a constant factor; the second does not depend on \(x\) at all. So keep \(B_1\) over \(d_i\) and \(B_2\) over \(i \cdot d_i\). A range add of \(v\) on \([L, R]\) is \(d_L \mathrel{+}= v\) and \(d_{R+1} \mathrel{-}= v\), mirrored into \(B_2\) with weights \(L\) and \(R+1\). Then \(S(x) = (x+1)\,B_1(x) - B_2(x)\).

class RangeBIT:
    """Range add and range sum in O(log n); 0-indexed half-open ranges."""
    def __init__(self, n):
        self.n, self.b1, self.b2 = n, [0] * (n + 1), [0] * (n + 1)

    def _add(self, i, v):                      # d[i] += v, i is 1-indexed
        n, b1, b2, w = self.n, self.b1, self.b2, v * i
        while i <= n:
            b1[i] += v; b2[i] += w
            i += i & -i

    def range_add(self, l, r, v):              # a[l:r] += v
        self._add(l + 1, v); self._add(r + 1, -v)

    def _prefix(self, x):                      # a[0] + ... + a[x-1]
        b1, b2, s1, s2, i = self.b1, self.b2, 0, 0, x
        while i:
            s1 += b1[i]; s2 += b2[i]
            i &= i - 1
        return (x + 1) * s1 - s2

    def range_sum(self, l, r):
        return self._prefix(r) - self._prefix(l)

2D BIT

Nest the loops: t[i][j] covers the block of rows \((i - \text{lowbit}(i), i]\) times columns \((j - \text{lowbit}(j), j]\). A point update or a prefix rectangle costs \(O(\log n \log m)\), and any rectangle follows from four prefixes by inclusion–exclusion, exactly as with 2D prefix sums (L13). Memory is \(nm\), so it fits a \(1000 \times 1000\) grid but not sparse \(10^9\)-coordinate points; for those, go offline.

class BIT2D:
    """Point add; sum over the rectangle [r1, r2) x [c1, c2)."""
    def __init__(self, n, m):
        self.n, self.m, self.t = n, m, [[0] * (m + 1) for _ in range(n + 1)]

    def add(self, r, c, v):
        i = r + 1
        while i <= self.n:
            row, j = self.t[i], c + 1
            while j <= self.m:
                row[j] += v; j += j & -j
            i += i & -i

    def prefix(self, r, c):                    # sum over [0, r) x [0, c)
        s, i = 0, r
        while i:
            row, j = self.t[i], c
            while j:
                s += row[j]; j &= j - 1
            i &= i - 1
        return s

    def rect(self, r1, c1, r2, c2):
        return (self.prefix(r2, c2) - self.prefix(r1, c2)
                - self.prefix(r2, c1) + self.prefix(r1, c1))

The k-th element by descent

To find the smallest index whose prefix count reaches \(k\), you could binary search over prefix in \(O(\log^2 n)\). The descent does it in \(O(\log n)\) by building the answer one bit at a time, from the top.

Theorem · descent invariant

Start with pos = 0 and steps \(2^{\lfloor \log_2 n\rfloor}, \dots, 2, 1\). Before each step, pos is a multiple of \(2 \cdot \text{step}\), so \(\text{lowbit}(\text{pos} + \text{step}) = \text{step}\) and t[pos + step] is exactly the count in \((\text{pos}, \text{pos} + \text{step}]\). Move forward when that count is below the remaining \(k\), and subtract it. Then \(\text{prefix}(\text{pos}) < k_0\) always holds, and at the end pos is the largest index with that property, so the answer is pos + 1. This needs non-negative counts, so that the prefix function is monotone.

Put the descent on a BIT over compressed values and you have insert, erase, k-th and rank, each in \(O(\log n)\). This is the main substitute for a balanced BST in Python. It needs the value universe in advance, so read all operations first (offline compression).

from bisect import bisect_left

class SortedMultiset:
    """BIT over a value universe known in advance: insert, erase, kth, rank."""
    def __init__(self, universe):
        self.vals = sorted(set(universe))
        self.idx = {v: i for i, v in enumerate(self.vals)}
        self.n, self.size = len(self.vals), 0
        self.t = [0] * (self.n + 1)
        self.top = 1 << self.n.bit_length() >> 1   # largest power of two <= n

    def _add(self, i, v):
        t, n, i = self.t, self.n, i + 1
        while i <= n:
            t[i] += v; i += i & -i

    def insert(self, x): self._add(self.idx[x], 1); self.size += 1
    def erase(self, x): self._add(self.idx[x], -1); self.size -= 1   # x must be present

    def rank(self, x):                         # number of elements < x
        t, s, i = self.t, 0, bisect_left(self.vals, x)
        while i:
            s += t[i]; i &= i - 1
        return s

    def kth(self, k):                          # k-th smallest, 1 <= k <= size
        t, pos, step = self.t, 0, self.top
        while step:
            if pos + step <= self.n and t[pos + step] < k:
                pos += step; k -= t[pos]
            step >>= 1
        return self.vals[pos]

BIT for max works with two restrictions: queries must be prefixes, because max has no inverse, and stored values may only increase (t[i] = max(t[i], v) up the update path). That is enough for LIS-style DPs over sorted values (L85). Median maintenance is kth((size + 1) // 2) after each insert.

def josephus2(n, k):                           # CSES Josephus Problem II
    t = [0] + [1] * n                          # BIT of ones, O(n) build
    for i in range(1, n + 1):
        j = i + (i & -i)
        if j <= n: t[j] += t[i]
    top, out, cur = 1 << n.bit_length() >> 1, [], 0
    for m in range(n, 0, -1):
        cur = (cur + k) % m                    # 0-indexed among the m remaining
        pos, need, step = 0, cur + 1, top
        while step:
            if pos + step <= n and t[pos + step] < need:
                pos += step; need -= t[pos]
            step >>= 1
        out.append(pos + 1)
        i = pos + 1
        while i <= n: t[i] -= 1; i += i & -i
    return out

  • Weights in the second BIT. \(B_2\) must receive \(v \cdot i\) at the 1-indexed position \(i\). With 0-indexed weights every prefix sum comes out too large by exactly the current \(a_x\).
  • Descent on signed data. The descent assumes non-negative counts. With negative values the prefix function is not monotone and the "k-th" is meaningless.
  • Top step. Start at the largest power of two \(\le n\), not \(\lfloor\log_2 n\rfloor\). Guard with pos + step <= n when \(n\) is not a power of two.
  • Online values. A value BIT needs every value in advance. If values truly arrive online, use sqrt blocks (L110) or a treap (L112).
  • 2D memory. [[0]*(m+1)]*(n+1) aliases one row \(n+1\) times. Build it with a comprehension.

Segment Tree I: The Universal Range Structure

60m video

A segment tree stores the merged value of every block produced by recursively halving the array. Any range is a disjoint union of \(O(\log n)\) of those blocks, so any associative operation with an identity can be queried and updated in \(O(\log n)\). The real skill is designing a node that can be merged.

The exact requirement: a monoid

Definition · monoid

A set \(M\) with an operation \(\oplus\) that is associative, \((x \oplus y) \oplus z = x \oplus (y \oplus z)\), and has an identity \(e\) with \(e \oplus x = x \oplus e = x\). Associativity lets the tree cut a range anywhere. The identity is what a disjoint subtree returns. Commutativity is not required, but then the left child must always be merged before the right.

Examples: sum with 0, min with \(+\infty\), max with \(-\infty\), gcd with 0, "min and its count" with \((\infty, 0)\), \(2\times 2\) matrix product with \(I\) (not commutative), and the best-subarray node below.

Structure, build, update, query

Node 1 covers \([0, n)\). Node \(v\) covering \([lo, hi)\) with \(hi - lo \ge 2\) has children \(2v\) and \(2v+1\), which cover \([lo, mid)\) and \([mid, hi)\) with \(mid = \lfloor (lo+hi)/2 \rfloor\). The height is \(h = \lceil \log_2 n \rceil\) and indices stay below \(2^{h+1}\); since \(2^h < 2n\), that is below \(4n\), hence the classic array size. Build is a post-order pass over \(2n - 1\) nodes, \(O(n)\). An update rewrites one leaf and re-merges ("pulls") each ancestor, \(O(\log n)\).

Theorem · query cost

A range query visits at most 4 nodes per level, so \(O(\log n)\) nodes in total.

Proof

The nodes at one depth are disjoint intervals. A node is partial when it meets \([l, r)\) without being inside it, so it must contain one of the two boundaries strictly inside: \(lo < l < hi\) or \(lo < r < hi\). Each boundary lies in at most one node per depth, so there are at most 2 partial nodes per depth. Only partial nodes recurse, and each has 2 children, so at most 4 nodes are visited at the next depth. With \(\lceil\log_2 n\rceil + 1\) depths, the total is \(O(\log n)\).

Implementation: one tree, any monoid

class SegTree:
    """Recursive segment tree over a monoid (merge, identity). Teaching version;
    the iterative tree of L109 is the fast one."""
    def __init__(self, a, merge, identity):
        self.n, self.merge, self.e = len(a), merge, identity
        self.t = [identity] * (4 * max(1, self.n))
        if self.n: self._build(1, 0, self.n, a)

    def _build(self, v, lo, hi, a):
        if hi - lo == 1:
            self.t[v] = a[lo]; return
        mid = (lo + hi) // 2
        self._build(2 * v, lo, mid, a); self._build(2 * v + 1, mid, hi, a)
        self.t[v] = self.merge(self.t[2 * v], self.t[2 * v + 1])

    def update(self, i, x, v=1, lo=0, hi=None):          # a[i] = x
        if hi is None: hi = self.n
        if hi - lo == 1:
            self.t[v] = x; return
        mid = (lo + hi) // 2
        if i < mid: self.update(i, x, 2 * v, lo, mid)
        else: self.update(i, x, 2 * v + 1, mid, hi)
        self.t[v] = self.merge(self.t[2 * v], self.t[2 * v + 1])   # pull

    def query(self, l, r, v=1, lo=0, hi=None):           # merge over a[l:r]
        if hi is None: hi = self.n
        if r <= lo or hi <= l: return self.e              # disjoint
        if l <= lo and hi <= r: return self.t[v]          # contained
        mid = (lo + hi) // 2                              # partial
        return self.merge(self.query(l, r, 2 * v, lo, mid),
                          self.query(l, r, 2 * v + 1, mid, hi))

Designing the node: store more than the answer

The maximum subarray sum of a range cannot be computed from the two children's answers alone: the best subarray may cross the cut. Ask what a crossing subarray needs. It needs the best suffix of the left half and the best prefix of the right half, and to update those after a merge you also need each side's total. Four fields close under merging:

$$\text{sum} = s_a + s_b,\quad \text{pre} = \max(p_a,\ s_a + p_b),\quad \text{suf} = \max(u_b,\ s_b + u_a),\quad \text{best} = \max(b_a,\ b_b,\ u_a + p_b).$$ 
NEG = float("-inf")
EMPTY = (0, NEG, NEG, NEG)          # (sum, best prefix, best suffix, best); identity
def leaf(x): return (x, x, x, x)
def merge_best(a, b):
    return (a[0] + b[0], max(a[1], a[0] + b[1]),
            max(b[2], b[0] + a[2]), max(a[3], b[3], a[2] + b[1]))

def merge_min_count(a, b):          # (min, count of min); identity (inf, 0)
    if a[0] != b[0]: return a if a[0] < b[0] else b
    return (a[0], a[1] + b[1])

Check the identity before trusting it: merging EMPTY on either side returns the other node unchanged, because \(-\infty\) loses every max and \(0\) adds nothing. The same reasoning gives a node for any "best contiguous something" question.

Recursive or iterative in Python

Recursion depth is only \(\lceil\log_2 n\rceil \approx 18\), so the recursion limit is not the problem. Call overhead is: every visited node is a Python function call with argument passing. In the L104 benchmark (\(2\cdot10^5\) mixed operations under CPython 3.12) the recursive tree was about 2.3 times slower than the iterative bottom-up tree. Learn the three cases on the recursive version, and submit the iterative one from L109, or the recursive one under PyPy.

What breaks
  • Wrong identity. 0 for min, or None that later reaches max(). A disjoint branch must return something that leaves every value unchanged.
  • Swapped merge order with a non-commutative node (matrices, best-subarray): merge(right, left) passes on symmetric tests.
  • Forgotten pull. Updating the leaf without re-merging ancestors answers queries from stale nodes.
  • Array too small. \(2n\) is enough only for the iterative layout. The recursive layout needs up to \(4n\).
  • Tuple churn. A 4-tuple per merge allocates \(O(\log n)\) objects per operation. For hot problems, store each field in its own list.

Segment Tree II: Lazy Propagation

60m video

A range update can stop at the \(O(\log n)\) blocks that cover the range and leave a tag on each: "this whole block has changed this way, and the children have not been told yet". It works when tags compose with each other and a tag can be applied to a node's value using only that value and the block length.

The naive disaster and the lazy idea

Applying a range add as point updates costs \(O(n \log n)\) per operation, so \(10^5\) updates on \(10^5\) elements never finish. Lazy propagation spends \(O(\log n)\) instead: the update descends exactly like a query (L106), and at each fully covered node it changes the stored aggregate immediately and records a pending tag.

Definition · the four operations
  • apply(v, len, f): update node \(v\)'s aggregate as if \(f\) had been applied to every element of its block, and compose \(f\) into \(v\)'s tag.
  • push(v): apply \(v\)'s tag to both children, then reset it to the identity tag. Do this before descending into \(v\).
  • pull(v): recompute \(v\)'s aggregate from its children. Do this after the recursive calls return.
  • Invariant: each node's aggregate is correct for its block, given every update except those still pending in tags at its strict ancestors.

Range add with range sum, then range assign

Add. The tag is a number \(x\). apply does sum += x * len and tag += x. The block length is what turns "add to each element" into a change of the aggregate, and it is the most commonly forgotten factor. For range min under add, min += x needs no length.

Assign. The tag is a value or None. apply does sum = s * len, min = s, tag = s. An assignment overwrites whatever was pending, so composition is "the newer assignment wins".

Composing add and assign: the lazy monoid

Supporting both means a tag must describe any sequence of adds and assigns. Every such sequence collapses to one normal form, "set to \(s\) (optional), then add \(x\)". Composing a new tag \((s_2, x_2)\) after an old \((s_1, x_1)\) gives \((s_2, x_2)\) if \(s_2\) is set, because the assignment erases history, and otherwise \((s_1, x_1 + x_2)\).

Theorem · when lazy propagation is correct

Let node values form a monoid \((M, \oplus)\) and tags a set \(F\) of maps \(M \to M\) that (1) contains the identity, (2) is closed under composition, and (3) distributes over the merge: \(f(a \oplus b) = f(a) \oplus f(b)\). Then storing \(f\) at a node and pushing it later gives the same answers as applying it eagerly to every leaf. For sum-like aggregates, make the length part of \(M\) (store pairs (sum, len)), so that "add \(x\)" becomes a map on \(M\).

Condition (3) is what to check for a new problem. Add distributes over min and sum (given lengths). Assign distributes over both. Multiplication by a constant distributes over sum. "Set each element to \(\max(a_i, x)\)" does not distribute over sum, because the result depends on how many elements are below \(x\). That gap is exactly what segment tree beats (L114) fills.

Implementation

class LazySegTree:
    """Range assign / range add; query returns (sum, min) of a[l:r]."""
    def __init__(self, a):
        n = self.n = len(a)
        self.sm, self.mn = [0] * (4 * n), [0] * (4 * n)
        self.st, self.ad = [None] * (4 * n), [0] * (4 * n)   # tag: set st, then add ad
        self._build(1, 0, n, a)

    def _build(self, v, lo, hi, a):
        if hi - lo == 1:
            self.sm[v] = self.mn[v] = a[lo]; return
        mid = (lo + hi) // 2
        self._build(2 * v, lo, mid, a); self._build(2 * v + 1, mid, hi, a)
        self._pull(v)

    def _pull(self, v):
        self.sm[v] = self.sm[2 * v] + self.sm[2 * v + 1]
        self.mn[v] = min(self.mn[2 * v], self.mn[2 * v + 1])

    def _apply(self, v, length, s, x):         # compose tag (s, x) onto node v
        if s is not None:
            self.sm[v], self.mn[v], self.st[v], self.ad[v] = s * length, s, s, 0
        if x:
            self.sm[v] += x * length; self.mn[v] += x; self.ad[v] += x

    def _push(self, v, lo, mid, hi):
        if self.st[v] is not None or self.ad[v]:
            self._apply(2 * v, mid - lo, self.st[v], self.ad[v])
            self._apply(2 * v + 1, hi - mid, self.st[v], self.ad[v])
            self.st[v], self.ad[v] = None, 0

    def update(self, l, r, s=None, x=0, v=1, lo=0, hi=None):   # a[l:r] = s, then += x
        if hi is None: hi = self.n
        if r <= lo or hi <= l: return
        if l <= lo and hi <= r:
            self._apply(v, hi - lo, s, x); return
        mid = (lo + hi) // 2
        self._push(v, lo, mid, hi)
        self.update(l, r, s, x, 2 * v, lo, mid); self.update(l, r, s, x, 2 * v + 1, mid, hi)
        self._pull(v)

    def query(self, l, r, v=1, lo=0, hi=None):
        if hi is None: hi = self.n
        if r <= lo or hi <= l: return 0, float("inf")
        if l <= lo and hi <= r: return self.sm[v], self.mn[v]
        mid = (lo + hi) // 2
        self._push(v, lo, mid, hi)
        s1, m1 = self.query(l, r, 2 * v, lo, mid)
        s2, m2 = self.query(l, r, 2 * v + 1, mid, hi)
        return s1 + s2, min(m1, m2)

The checklist that kills most lazy bugs
  1. Push before descending, in both update and query.
  2. Pull after the recursive calls in update.
  3. apply uses the length of that node: left child \(mid - lo\), right child \(hi - mid\).
  4. Write the composition rule on paper first, including which tag is older.
  5. The empty tag must be a true no-op. Here that is (None, 0); assigning 0 is not "nothing".
  6. Stress-test against a list with all operation types interleaved. A single operation type hides composition bugs.

Segment Tree III: Descent, Trees on Values, Merge-Sort Trees

55m video

Many range questions are not "aggregate this range" but "where is the first position such that…" or "how many values in this range are below x". The first kind is answered by walking down the tree once. The second has four standard solutions, and in Python the offline one is usually the fastest.

Descent: binary search inside the tree

Binary searching over prefix queries costs \(O(\log^2 n)\). The tree already contains the binary search: at a node, look at the left child's aggregate, decide whether the answer lies there, and go to one child only. That is \(O(\log n)\). With a power-of-two size, the iterative layout makes the walk a three-line loop.

Theorem · descent correctness

For a max tree, "the leftmost index with \(a_i \ge x\) lies in the left child" holds exactly when the left child's max is \(\ge x\). So the walk keeps the invariant "the answer is in the current node's block" from the root (checked once: t[1] >= x) down to a leaf. For sums, "first prefix with sum \(\ge k\)" goes left if the left sum is \(\ge k\), and otherwise subtracts it and goes right. That needs non-negative entries.

class MaxDescent:
    """Point assign; first index i with a[i] >= x in O(log n). Iterative, size 2^k."""
    def __init__(self, a):
        size = 1
        while size < len(a): size *= 2
        t = [float("-inf")] * (2 * size)
        t[size:size + len(a)] = a
        for v in range(size - 1, 0, -1):
            t[v] = max(t[2 * v], t[2 * v + 1])
        self.size, self.t = size, t

    def set(self, i, x):
        t, v = self.t, i + self.size
        t[v] = x
        v >>= 1
        while v:
            l, r = t[2 * v], t[2 * v + 1]
            t[v] = l if l > r else r
            v >>= 1

    def first_at_least(self, x):               # -1 if no element is >= x
        t, v = self.t, 1
        if t[1] < x: return -1
        while v < self.size:
            v = 2 * v if t[2 * v] >= x else 2 * v + 1
        return v - self.size

def hotel_queries(free, groups):              # CSES Hotel Queries
    tree, out = MaxDescent(free), []
    for r in groups:
        i = tree.first_at_least(r)
        out.append(i + 1)                     # 0 when no hotel fits
        if i >= 0:
            free[i] -= r; tree.set(i, free[i])
    return out

Segment trees on values

Index the leaves by value (after compression) and store counts. Then the tree is a multiset: insert and erase are point updates, "how many are \(< x\)" is a prefix sum, and the k-th smallest is the sum descent above. This is the BIT descent of L105 generalised: the tree can carry richer nodes (sum of values, max) at the same leaves, and it can answer range questions over the value axis that a BIT cannot.

Merge-sort trees, and "count < x in a range"

A merge-sort tree stores at each node the sorted list of its block. A range splits into \(O(\log n)\) nodes and each contributes one bisect, so a query costs \(O(\log^2 n)\). Memory is \(n(\log_2 n + 1)\) list slots: 1.8 million at \(n = 10^5\). sorted(left + right) is a linear-time merge, because Timsort detects the two sorted runs.

from bisect import bisect_left

class MergeSortTree:
    def __init__(self, a):
        size = 1
        while size < len(a): size *= 2
        t = [[] for _ in range(2 * size)]
        for i, x in enumerate(a): t[size + i] = [x]
        for v in range(size - 1, 0, -1):
            t[v] = sorted(t[2 * v] + t[2 * v + 1])
        self.size, self.t = size, t

    def count_less(self, l, r, x):             # #{i in [l, r): a[i] < x}
        t, res, l, r = self.t, 0, l + self.size, r + self.size
        while l < r:
            if l & 1: res += bisect_left(t[l], x); l += 1
            if r & 1: r -= 1; res += bisect_left(t[r], x)
            l >>= 1; r >>= 1
        return res

def count_less_offline(a, queries):            # queries (l, r, x); sweep x upward
    n, t = len(a), [0] * (len(a) + 1)
    order = sorted(range(n), key=a.__getitem__)
    ans, p = [0] * len(queries), 0
    for qi in sorted(range(len(queries)), key=lambda i: queries[i][2]):
        l, r, x = queries[qi]
        while p < n and a[order[p]] < x:          # activate positions with value < x
            i = order[p] + 1; p += 1
            while i <= n: t[i] += 1; i += i & -i
        s, i = 0, r
        while i: s += t[i]; i &= i - 1
        i = l
        while i: s -= t[i]; i &= i - 1
        ans[qi] = s
    return ans

The offline version sorts the elements and the queries by value and sweeps: when a query with threshold \(x\) arrives, exactly the positions with value \(< x\) are active in a BIT over positions, so the answer is a range count. On \(n = q = 10^5\) random data under CPython 3.12, the merge-sort tree took about twice as long as the whole offline sweep, and most of its time went to the queries, not the build.

A wavelet tree answers range k-th smallest and range rank in \(O(\log C)\) with \(O(n \log C)\) bits. It is powerful in C++ and rarely worth the constant factor in Python; know that it exists.

def distinct_values(a, queries):             # CSES Distinct Values Queries, offline
    n, t, last = len(a), [0] * (len(a) + 1), {}
    def add(i, v):
        i += 1
        while i <= n: t[i] += v; i += i & -i
    def pre(i):
        s = 0
        while i: s += t[i]; i &= i - 1
        return s
    ans, by_r = [0] * len(queries), sorted(range(len(queries)), key=lambda i: queries[i][1])

What breaks

Segment Tree IV: Iterative, Dynamic, and Persistent

55m video

Three changes of layout fix three Python problems. A bottom-up array removes the recursion overhead. Nodes created on demand handle coordinates up to \(10^9\). Copying only the \(O(\log n)\) nodes on an update's path keeps every past version queryable, and that makes "k-th smallest in a range" an online \(O(\log n)\) query.

The iterative bottom-up tree

Put leaf \(i\) at t[n + i] and node \(v\)'s children at \(2v\) and \(2v+1\), so \(2n\) slots suffice for any \(n\). A query walks two pointers up from the leaves. Whenever the left pointer is a right child, its node is the next block of the range and is merged in, and symmetrically on the right. There are no function calls per node: in the L104 benchmark this tree ran about 2.3 times faster than the recursive one.

Theorem · safe for non-commutative merges

Keep two accumulators. The left one only ever has blocks appended on its right, resl = op(resl, t[l]), and the right one only has blocks prepended on its left, resr = op(t[r], resr). The blocks taken are disjoint and, on each side, are met in left-to-right and right-to-left order respectively. So at every step resl is the merge of a prefix of the range and resr the merge of a suffix, in order. When the pointers meet, the range is covered and op(resl, resr) is the ordered merge. Using a single accumulator silently assumes commutativity.

class SegTree:
    """Bottom-up segment tree over any monoid (commutative or not). Query a[l:r]."""
    def __init__(self, a, op, e):
        n = self.n = len(a)
        self.op, self.e = op, e
        t = self.t = [e] * n + list(a)
        for i in range(n - 1, 0, -1):
            t[i] = op(t[2 * i], t[2 * i + 1])

    def set(self, i, x):
        t, op = self.t, self.op
        i += self.n
        t[i] = x
        while i > 1:
            i >>= 1
            t[i] = op(t[2 * i], t[2 * i + 1])

    def query(self, l, r):
        t, op = self.t, self.op
        resl = resr = self.e
        l += self.n; r += self.n
        while l < r:
            if l & 1: resl = op(resl, t[l]); l += 1
            if r & 1: r -= 1; resr = op(t[r], resr)
            l >>= 1; r >>= 1
        return op(resl, resr)

With arbitrary \(n\), some internal nodes merge blocks that are not contiguous, but a query never reads them. Descent (L108) does need meaningful internal nodes, so pad to a power of two when you descend.

Dynamic (implicit) segment trees

When indices range over \([0, 10^9)\) and you cannot read the queries in advance to compress them, create nodes only when an update reaches them. Each update creates at most \(\lceil \log_2 10^9 \rceil = 30\) new nodes, and a query treats a missing child as the identity. Store nodes as parallel lists, with index 0 meaning "no child". A Python object per node measured over 300 bytes with its __dict__, against 24 bytes of list slots.

class DynSeg:
    """Point add, range sum over [0, N); nodes are created on first touch."""
    def __init__(self, N):
        self.N, self.L, self.R, self.S = N, [0, 0], [0, 0], [0, 0]   # 0 = null, 1 = root

    def add(self, i, x):
        L, R, S = self.L, self.R, self.S
        v, lo, hi = 1, 0, self.N
        while True:
            S[v] += x
            if hi - lo == 1: return
            mid = (lo + hi) // 2
            side = L if i < mid else R
            if not side[v]:
                side[v] = len(S); L.append(0); R.append(0); S.append(0)
            if i < mid: v, hi = L[v], mid
            else: v, lo = R[v], mid

    def query(self, l, r):                      # sum over [l, r)
        L, R, S = self.L, self.R, self.S
        res, stack = 0, [(1, 0, self.N)]
        while stack:
            v, lo, hi = stack.pop()
            if not v or r <= lo or hi <= l: continue
            if l <= lo and hi <= r: res += S[v]; continue
            mid = (lo + hi) // 2
            stack.append((L[v], lo, mid)); stack.append((R[v], mid, hi))
        return res

Persistent segment trees: path copying

To keep old versions, never modify a node. An update copies the root-to-leaf path, \(O(\log n)\) new nodes, and points the copies at the untouched subtrees of the previous version. roots[v] is version \(v\). Every version is a complete, valid tree, and versions share almost all of their nodes.

The killer application: k-th smallest in a range

Compress the values. Version \(i\) is a count tree over values containing the first \(i\) elements. The counts of a[l:r] are then version \(r\) minus version \(l\), node by node, so you descend on both roots at once. That gives \(O(\log n)\) per query, online, after \(O(n \log n)\) preprocessing.

Theorem · version difference

For every node position \(p\) in the value tree, \(C_r(p) - C_l(p)\) is the number of elements of a[l:r] whose rank lies in \(p\)'s value interval. Both versions have the same shape, and counts are additive over insertions. So the k-th smallest descent of L105 runs on the difference without ever building it.

def build_kth(a):
    """kth(l, r, k) = k-th smallest of a[l:r] (1 <= k <= r - l), O(log n) each."""
    vals = sorted(set(a)); rank = {v: i for i, v in enumerate(vals)}; m = len(vals)
    L, R, C, roots = [0], [0], [0], [0]      # node 0 = empty tree, its own children
    for x in a:
        pos, prev = rank[x], roots[-1]
        cur = len(C); roots.append(cur)
        L.append(L[prev]); R.append(R[prev]); C.append(C[prev] + 1)
        lo, hi = 0, m
        while hi - lo > 1:                   # copy the path, share everything else
            mid, nxt = (lo + hi) // 2, len(C)
            if pos < mid: old = L[cur]; L[cur] = nxt; hi = mid
            else: old = R[cur]; R[cur] = nxt; lo = mid
            L.append(L[old]); R.append(R[old]); C.append(C[old] + 1)
            cur = nxt
    def kth(l, r, k):
        u, w, lo, hi = roots[r], roots[l], 0, m
        while hi - lo > 1:
            mid = (lo + hi) // 2
            c = C[L[u]] - C[L[w]]            # ranks in [lo, mid) inside a[l:r]
            if k <= c: u, w, hi = L[u], L[w], mid
            else: k -= c; u, w, lo = R[u], R[w], mid
        return vals[lo]
    return kth

Persistence in general, and the memory budget

Persistent arrays are persistent segment trees with values at the leaves. Persistent binary tries answer "max \(x \oplus a_i\) over \(i \in [l, r)\)" with the same version-difference idea. Rollback (an undo stack, as in DSU with rollback, L71) is cheaper but only goes back in LIFO order. Persistence gives random access to every version. Choose rollback when the algorithm's control flow is itself a stack, as in D&C over time.

Budget: \(10^5\) insertions over \(10^5\) values create about \(10^5 \times 18 \approx 1.8\cdot10^6\) nodes, times three lists. As Python lists, that is roughly 43 MB of pointers plus an int object (28 bytes) for most indices and counts. build_kth on \(10^5\) elements measured about 120 MB. array('i') stores 4 bytes per field, about 22 MB, at the cost of slightly slower element access. Preallocate when you know the node count.

Problems

  • CSES — Range Queries and Copies. A persistent point-assign, range-sum tree. "Copy array \(k\)" appends roots[k] again (a new name for an existing version, \(O(1)\)), and "set in array \(k\)" replaces roots[k] with a fresh path copy.
  • CSES — Distinct Values Queries (online). Let prev[i] be the previous index holding the same value, or \(-1\). The answer for \([l, r)\) is \(\#\{i \in [l, r) : \text{prev}[i] < l\}\): count \(< x\) in a range, by the version difference over a count tree indexed by prev + 1. The offline BIT of L108 is faster; this version answers online.
  • SPOJ — K-th Number, and other "k-th smallest in range" classics: build_kth as written.
  • LeetCode 1146 — Snapshot Array. The warm-up "fat node" persistence: each index keeps a list of (snap_id, value), and get bisects it. That is \(O(\log)\) per read, with no tree.
What breaks
  • Mutating a shared node. One in-place C[v] += 1 on an old node corrupts every version that shares it. Every write goes to a freshly appended node.
  • Forgetting the null node. Node 0 must be a valid empty tree (count 0, children 0). Then descents through missing parts need no special cases.
  • Single accumulator. res = op(res, t[r]) on the right side reverses the order for matrix or string merges.
  • Coordinate bound off by one. N must exceed the largest index. With indices up to \(10^9\) inclusive, use \([0, 10^9 + 1)\).
  • MLE from lists. Estimate nodes × fields × 8 bytes, plus int objects, before you submit.

Sqrt Decomposition

50m video

Split anything of size \(n\) into about \(\sqrt n\) chunks of about \(\sqrt n\), handle whole chunks with a summary and the two ragged ends by brute force, and every operation costs \(O(\sqrt n)\). The idea applies to arrays, to sequences of queries, to the value axis and to vertex degrees, and it keeps working when the operation is too awkward for a segment tree.

Blocks over an array

With block size \(B\), keep the array plus one summary per block (here, the block sum). A point update changes one element and one summary, \(O(1)\). A range query adds the partial elements at both ends (at most \(2B\)) and the full blocks in between (at most \(n/B\)), so it costs \(O(B + n/B)\), which is minimised at \(B = \sqrt n\).

Choosing B, and lazy blocks

The \(\sqrt n\) rule assumes equal costs for an element step and a block step. In Python they differ: sum(a[l:e]) and slice comprehensions run at C speed, while a Python for over blocks does not. With costs \(c_e\) per element and \(c_b\) per block, the optimum is \(B = \sqrt{n\,c_b/c_e}\), so tune it empirically. For range add plus range sum at \(n = q = 2\cdot10^5\), \(B = 150\) and \(B = \sqrt n \approx 450\) performed about the same, and \(B = 1000\) was about 60% slower.

Range add, range sum. Add a tag per block. Partial blocks update their elements and their sum. Full blocks only bump the tag, and the value of a full block is sum[b] + B * tag[b].

class SqrtAddSum:
    """Range add and range sum in O(sqrt n), using C-speed slices where possible."""
    def __init__(self, a, B=None):
        n = len(a)
        self.B = B = B or max(1, int(n ** 0.5))
        self.a = list(a)
        self.sm = [sum(a[i:i + B]) for i in range(0, n, B)]
        self.tag = [0] * len(self.sm)

    def add(self, l, r, x):                    # a[l:r] += x
        B, a, sm, tag = self.B, self.a, self.sm, self.tag
        bl, br = l // B, (r - 1) // B
        if bl == br:
            a[l:r] = [v + x for v in a[l:r]]; sm[bl] += x * (r - l); return
        e, s = (bl + 1) * B, br * B
        a[l:e] = [v + x for v in a[l:e]]; sm[bl] += x * (e - l)
        a[s:r] = [v + x for v in a[s:r]]; sm[br] += x * (r - s)
        tag[bl + 1:br] = [t + x for t in tag[bl + 1:br]]

    def query(self, l, r):                     # sum of a[l:r]
        B, a, sm, tag = self.B, self.a, self.sm, self.tag
        bl, br = l // B, (r - 1) // B
        if bl == br: return sum(a[l:r]) + tag[bl] * (r - l)
        e, s = (bl + 1) * B, br * B
        return (sum(a[l:e]) + tag[bl] * (e - l) + sum(a[s:r]) + tag[br] * (r - s)
                + sum(sm[bl + 1:br]) + B * sum(tag[bl + 1:br]))

Sqrt is not the fastest tool for plain add and sum. It is the tool that stays simple when the operation gets strange.

Sqrt on queries: the rebuild trick

Keep a static structure that is cheap to query and expensive to build, plus a buffer of the last few updates. A query asks the static structure and then corrects for each buffered update by brute force. When the buffer reaches \(K\) items, rebuild. With rebuild cost \(R\) and per-item correction cost \(c\), the total is \(O(qR/K + qKc)\), minimised at \(K = \sqrt{R/c}\). This amortises the hard dynamic part away, and it turns many dynamic problems into static ones.

Worked example · Codeforces — Xenia and Tree

Paint a vertex red, or ask the distance from \(v\) to the nearest red vertex (vertex 0 starts red). The static structure is a BFS distance array D from all reds, rebuilt in \(O(n)\). A query is min(D[v], dist(v, u) for u in buffer) with LCA distances, each \(O(\log n)\). The centroid-decomposition solution is harder to write; this one is BFS plus LCA.

from collections import deque
from math import isqrt

def xenia(n, edges, ops):
    adj = [[] for _ in range(n)]
    for u, v in edges: adj[u].append(v); adj[v].append(u)
    par, dep, order, seen = [0] * n, [0] * n, [0], [False] * n
    seen[0] = True
    for u in order:                              # BFS order from root 0
        for w in adj[u]:
            if not seen[w]:
                seen[w] = True; par[w] = u; dep[w] = dep[u] + 1; order.append(w)
    up = [par]
    for _ in range(n.bit_length()):
        p = up[-1]; up.append([p[p[v]] for v in range(n)])
    def dist(u, v):                              # binary-lifting LCA (L57)
        a, b = (u, v) if dep[u] >= dep[v] else (v, u)
        d, k = dep[a] - dep[b], 0
        while d:
            if d & 1: a = up[k][a]
            d >>= 1; k += 1
        if a != b:
            for k in range(len(up) - 1, -1, -1):
                if up[k][a] != up[k][b]: a, b = up[k][a], up[k][b]
            a = par[a]
        return dep[u] + dep[v] - 2 * dep[a]
    D, pending, out = [n] * n, [0], []
    K = max(1, isqrt(n // max(1, n.bit_length())))   # K = sqrt(R / c)
    def rebuild():                               # BFS from the new reds only
        q = deque(pending)
        for s in pending: D[s] = 0
        while q:
            u = q.popleft()
            for w in adj[u]:
                if D[w] > D[u] + 1: D[w] = D[u] + 1; q.append(w)
        pending.clear()
    rebuild()
    for typ, v in ops:
        if typ == 1:
            pending.append(v)
            if len(pending) >= K: rebuild()
        else:
            out.append(min([D[v]] + [dist(v, u) for u in pending]))
    return out

The rebuild seeds BFS with only the new reds: old distances stay valid upper bounds, so it lowers exactly the entries that improve.

Sqrt on values and on degrees

Value blocks. Over a bounded value range, keep a count per value and per block of \(\sqrt V\) values. Insert and erase cost \(O(1)\), and k-th or rank costs \(O(\sqrt V)\). It is an ordered multiset that needs no offline compression. Frequent versus rare values. At most \(\sqrt n\) values occur more than \(\sqrt n\) times. Precompute answers for those "heavy" values and brute-force the occurrences of light ones.

Theorem · heavy/light by degree

Orient every edge from the endpoint with smaller (degree, id) to the larger. Then every out-degree is at most \(\sqrt{2m}\), so for each vertex, scanning its out-neighbours' out-lists costs \(O(m\sqrt m)\) in total. Proof: all out-neighbours of \(u\) have degree \(\ge \deg u \ge \text{out}(u)\). If \(\text{out}(u) > \sqrt{2m}\), those neighbours alone have total degree \(> 2m\), which is impossible.

def count_triangles(n, edges):               # O(m sqrt m)
    deg = [0] * n
    for u, v in edges: deg[u] += 1; deg[v] += 1
    out = [[] for _ in range(n)]
    for u, v in edges:
        if (deg[u], u) < (deg[v], v): out[u].append(v)
        else: out[v].append(u)
    mark, tri = [-1] * n, 0
    for u in range(n):
        for v in out[u]: mark[v] = u
        for v in out[u]:
            for w in out[v]:
                if mark[w] == u: tri += 1
    return tri

When sqrt beats a segment tree

  • Complex per-block invariants. Keep each block sorted plus an add-tag, and "count elements \(\ge x\) in a range after range adds" becomes one bisect per block. No standard lazy monoid does that.
  • Operations that do not compose into tags (L107, condition 3): rebuilding a whole block after a partial update still costs only \(O(B)\).
  • Python constants. \(n\sqrt n\) steps inside sum(), slicing and sorted() run in C, while \(n \log^2 n\) steps in a recursive tree are Python calls. At \(n = 2\cdot10^5\), about 320 Python-level operations per element can lose to about 450 C-level ones.

Problems

CSES — Range Updates and Sums (sqrt version). Each block needs both tags, "set then add", composed exactly as in L107; a partial block pushes its tags to the elements first. Time it against your lazy tree. Codeforces — Xenia and Tree: the rebuild trick above. Heavy-vertex problems: triangle counting, and "sum of values over neighbours of \(v\)" under point updates, where heavy vertices keep a running total that each update pushes into, and light vertices are summed on demand.

What breaks
  • Last block shorter than B. It is never a "full" block in the middle of a range, but code that multiplies a tag by \(B\) for the last block is wrong. Use its true length.
  • Pending tag on a partial block. Before editing elements in a block whose tag is nonzero, either fold the tag in or keep using a[i] + tag[b] consistently. Mixing the two conventions double-counts.
  • Element-wise Python loops. A for i in range(l, e): a[i] += x over a partial block measured about twice as slow as the slice comprehension.
  • K fixed at \(\sqrt q\) for any cost. Balance the actual costs: \(K = \sqrt{R/c}\). If a rebuild is \(O(n)\) and a correction is \(O(\log n)\), \(K \approx \sqrt{n/\log n}\).

Mo's Algorithm

50m video

If you can add or remove one element of a window in \(O(1)\) but cannot merge two windows, answer the queries offline in a clever order. Sort them by the block of the left end, then by the right end, and two pointers sweeping through that order move only \(O((n+q)\sqrt n)\) times in total.

The setting and the ordering

"How many distinct values are in \(a[l:r]\)?" has no useful merge: the distinct counts of two halves don't give the count of the whole. But a window with a count array cnt[] and a running total updates in \(O(1)\) when one element enters or leaves. Mo's algorithm keeps one window \([cl, cr)\) and moves its ends from query to query. Everything depends on the order of the queries.

Algorithm · Mo's ordering
  1. Choose a block size \(B\) (about \(n/\sqrt q\)). Sort queries by \((\lfloor l/B \rfloor,\ r)\), with \(r\) descending in odd blocks (the odd–even trick).
  2. For each query in that order, move cr to \(r\) and cl to \(l\), calling add or remove per step. Expand before you shrink, so the window never inverts.
  3. Record the answer under the query's original index.

Why the order alone gives the bound

Theorem · Mo's complexity

With block size \(B\), the total pointer movement is \(O(n \cdot n/B + q B)\). Choosing \(B = n/\sqrt q\) gives \(O(n\sqrt q)\), which is \(O(n\sqrt n)\) when \(q \approx n\).

Proof

Right pointer: inside one block of left ends, the queries are sorted by \(r\), so cr moves monotonically, at most \(n\) steps per block, plus at most \(n\) to reposition at a block change. There are \(\lceil n/B\rceil\) blocks, so \(O(n^2/B)\). Left pointer: consecutive queries in the same block have left ends within \(B\) of each other, so each query costs \(O(B)\). A block change costs at most \(2B\) extra, and there are \(O(n/B)\) changes, so \(O(qB + n)\). Balancing \(n^2/B = qB\) gives \(B = n/\sqrt q\). The odd–even trick does not change the bound; it removes the return sweep of \(r\), which halved the measured \(r\) moves.

Classic applications

  • Distinct values: cnt[x], with a counter that changes when a count goes \(0 \leftrightarrow 1\).
  • Range mode: also keep freq[c], the number of values with count \(c\). On add, mode = max(mode, cnt[x]). On remove, if freq[mode] becomes 0 then mode -= 1. A removal lowers the maximum by at most 1, so this stays \(O(1)\).
  • Sum of \(K_s^2 \cdot s\) (Codeforces — Powerful array): when the count of \(x\) goes from \(c\) to \(c+1\), the total grows by \((2c+1)x\).
def mo_distinct(a, queries):
    """Distinct count of a[l:r] for each (l, r), half-open, offline."""
    comp = {v: i for i, v in enumerate(set(a))}
    a = [comp[v] for v in a]
    n, q = len(a), len(queries)
    B = max(1, int(n / max(1, q) ** 0.5))
    def key(i):
        l, r = queries[i]; b = l // B
        return (b, r if b % 2 == 0 else -r)       # odd-even trick
    cnt, distinct, cl, cr, ans = [0] * len(comp), 0, 0, 0, [0] * q
    for qi in sorted(range(q), key=key):
        l, r = queries[qi]
        while cr < r:                             # expand first ...
            x = a[cr]; cnt[x] += 1; distinct += cnt[x] == 1; cr += 1
        while cl > l:
            cl -= 1; x = a[cl]; cnt[x] += 1; distinct += cnt[x] == 1
        while cr > r:                             # ... then shrink
            cr -= 1; x = a[cr]; cnt[x] -= 1; distinct -= cnt[x] == 0
        while cl < l:
            x = a[cl]; cnt[x] -= 1; distinct -= cnt[x] == 0; cl += 1
        ans[qi] = distinct
    return ans

Mo's on trees

Flatten the tree with an Euler tour that records each vertex twice, at entry (tin) and at exit (tout). For a path \(u\)–\(v\) with \(\text{tin}[u] \le \text{tin}[v]\): if \(u\) is an ancestor of \(v\), the path is the tour range \([\text{tin}[u], \text{tin}[v]]\). Otherwise it is \([\text{tout}[u], \text{tin}[v]]\) plus the LCA, which that range misses. In either range, vertices off the path appear exactly twice and cancel, so the window toggles a vertex on each occurrence instead of adding it.

def mo_tree_distinct(n, edges, colour, queries):
    """Distinct colours on each path (u, v), via Mo's over the entry/exit Euler tour."""
    adj = [[] for _ in range(n)]
    for u, v in edges: adj[u].append(v); adj[v].append(u)
    flat, tin, tout, par, stack = [], [0] * n, [0] * n, [0] * n, [0]
    while stack:                                  # iterative DFS from 0; ~u marks the exit
        u = stack.pop()
        if u >= 0:
            tin[u] = len(flat); flat.append(u); stack.append(~u)
            for w in adj[u]:
                if w != par[u]: par[w] = u; stack.append(w)
        else:
            tout[~u] = len(flat); flat.append(~u)
    up = [par]
    for _ in range(n.bit_length()): p = up[-1]; up.append([p[p[v]] for v in range(n)])
    anc = lambda x, y: tin[x] <= tin[y] and tout[y] <= tout[x]
    def lca(x, y):
        if anc(x, y): return x
        for k in range(len(up) - 1, -1, -1):
            if not anc(up[k][x], y): x = up[k][x]
        return par[x]
    rng = []
    for u, v in queries:
        if tin[u] > tin[v]: u, v = v, u
        w = lca(u, v)
        rng.append((tin[u], tin[v] + 1, -1) if w == u else (tout[u], tin[v] + 1, w))
    comp = {c: i for i, c in enumerate(set(colour))}
    col = [comp[c] for c in colour]
    cnt, vis, ans, distinct = [0] * len(comp), [False] * n, [0] * len(rng), 0
    def toggle(x):                                # a vertex is on the path iff seen once
        nonlocal distinct
        c = col[x]; vis[x] = not vis[x]
        if vis[x]: cnt[c] += 1; distinct += cnt[c] == 1
        else: cnt[c] -= 1; distinct -= cnt[c] == 0
    B = max(1, int(len(flat) / max(1, len(rng)) ** 0.5))
    cl = cr = 0
    for qi in sorted(range(len(rng)), key=lambda i: (rng[i][0] // B, rng[i][1])):
        l, r, w = rng[qi]
        while cr < r: toggle(flat[cr]); cr += 1
        while cl > l: cl -= 1; toggle(flat[cl])
        while cr > r: cr -= 1; toggle(flat[cr])
        while cl < l: toggle(flat[cl]); cl += 1
        if w >= 0: toggle(w)                      # the LCA, for this query only
        ans[qi] = distinct
        if w >= 0: toggle(w)
    return ans

Mo's with updates, and Python honesty

Mo's with updates adds a time coordinate: sort queries by \((\lfloor l/B\rfloor, \lfloor r/B\rfloor, t)\) with \(B \approx n^{2/3}\), and move a third pointer that applies or undoes point updates, swapping the value in and out of the window when the position lies inside it. The total cost is \(O(n^{5/3})\) for \(n \approx q\).

Honesty. At \(n = q = 2\cdot10^5\), the measured \(7.5\cdot10^7\) pointer moves each cost several bytecode operations. That is far over a CPython time limit and borderline even in PyPy. Use Mo's in Python when \(n, q \le 5\cdot10^4\), when PyPy is available and the add/remove bodies are a few integer operations, or when no offline sort-and-BIT reformulation exists. For distinct values, the BIT sweep of L108 is \(O((n+q)\log n)\) and wins by a wide margin.

Problems

What breaks
  • Shrinking before expanding. With cl > cr transiently, counts go negative and "distinct" breaks on the next query.
  • Forgetting the LCA on non-ancestor paths, or adding it permanently instead of only for that query.
  • Adding instead of toggling on trees. A vertex seen twice in the tour range is not on the path.
  • Sort-key overhead. A lambda key over \(2\cdot10^5\) queries is fine. A cmp_to_key comparator measured more than ten times slower.

Treaps and Implicit Treaps (Sequence Surgery)

55m video

An implicit treap is a randomised binary search tree keyed by position, where the key is never stored but recomputed from subtree sizes. Two primitives, split and merge, each \(O(\log n)\) expected, give insert and erase anywhere, cut-and-paste of a block, and, with one lazy flag, reversal of any subarray.

What a segment tree cannot do

A segment tree's shape is fixed by \(n\). Inserting in the middle, deleting a block, moving a subarray to the front, or reversing a range all change positions wholesale. Python lists do these with C-level copying, but that is still \(O(n)\) per operation: \(2\cdot10^5\) cut-and-pastes on a string of \(2\cdot10^5\) is about \(4\cdot10^{10}\) byte copies, which is too slow.

Treaps: split and merge

A treap (L54) is a BST on keys and a max-heap on random priorities. Random priorities make its shape that of a random BST, whatever the insertion order.

Algorithm · split and merge
  1. split(t, k) returns \((A, B)\) with keys \(< k\) in \(A\) and the rest in \(B\). If t.key < k, then t and its left subtree belong to \(A\): split t.right into \((A', B)\), set t.right = A', and return \((t, B)\). Otherwise do the mirror image.
  2. merge(A, B), where every key of \(A\) is below every key of \(B\): the higher-priority root wins. If it is \(A\)'s root, set A.right = merge(A.right, B); otherwise B.left = merge(A, B.left).
  3. After changing a node's children, pull to recompute its size and aggregates.

Both walk one root-to-leaf path, and both preserve the two invariants. Split only reattaches subtrees on the correct side of \(k\), and a node's priority is never compared with anything except its ancestors on the path. Merge always puts the larger priority on top. As an ordered multiset, insert \(x\) is split at \(x\) followed by merge(merge(A, node), B). Erase splits off the run of keys equal to \(x\) and drops one node. k-th, rank and lower_bound walk down using subtree sizes. Each is \(O(\log n)\) expected.

Implicit keys and lazy flags

Store no key at all. A node's position is the size of everything to its left: the left subtree, plus the left parts accumulated on the way down. split(t, k) becomes "the first \(k\) elements, and the rest": go left if size(t.left) >= k, otherwise go right with \(k - \text{size}(t.left) - 1\). Then:

  • Reverse \([l, r)\): split into three, toggle a rev flag on the middle root, and merge back. push swaps a flagged node's children and passes the flag down. That is lazy propagation (L107) on a tree whose shape changes.
  • Range add: an add tag with sum += x * size, pushed the same way.
  • Cut and paste: split into \(A, B, C\) and merge them as \(A, C, B\).

Implementation

import random

class ImplicitTreap:
    """Sequence with split/merge by position, lazy reversal, and subtree sums."""
    def __init__(self, a=()):
        self.L, self.R, self.val, self.sm = [0], [0], [0], [0]     # node 0 = empty
        self.sz, self.pri, self.rev = [0], [0.0], [False]
        self.root = 0
        for x in a:
            self.root = self.merge(self.root, self.new(x))

    def new(self, x):
        self.L.append(0); self.R.append(0); self.val.append(x); self.sm.append(x)
        self.sz.append(1); self.pri.append(random.random()); self.rev.append(False)
        return len(self.sz) - 1

    def _pull(self, t):
        l, r = self.L[t], self.R[t]
        self.sz[t] = 1 + self.sz[l] + self.sz[r]
        self.sm[t] = self.val[t] + self.sm[l] + self.sm[r]

    def _push(self, t):
        if self.rev[t]:
            l, r = self.L[t], self.R[t]
            self.L[t], self.R[t], self.rev[t] = r, l, False
            if l: self.rev[l] = not self.rev[l]
            if r: self.rev[r] = not self.rev[r]

    def split(self, t, k):                     # (first k elements, the rest)
        if not t: return 0, 0
        self._push(t)
        if self.sz[self.L[t]] >= k:
            a, b = self.split(self.L[t], k)
            self.L[t] = b; self._pull(t)
            return a, t
        a, b = self.split(self.R[t], k - self.sz[self.L[t]] - 1)
        self.R[t] = a; self._pull(t)
        return t, b

    def merge(self, a, b):                     # all of a precedes all of b
        if not a or not b: return a or b
        if self.pri[a] > self.pri[b]:
            self._push(a); self.R[a] = self.merge(self.R[a], b); self._pull(a); return a
        self._push(b); self.L[b] = self.merge(a, self.L[b]); self._pull(b); return b

    def _cut3(self, l, r):
        a, b = self.split(self.root, l)
        b, c = self.split(b, r - l)
        return a, b, c

    def reverse(self, l, r):                   # reverse positions [l, r)
        a, b, c = self._cut3(l, r)
        if b: self.rev[b] = not self.rev[b]
        self.root = self.merge(self.merge(a, b), c)

    def range_sum(self, l, r):
        a, b, c = self._cut3(l, r)
        s = self.sm[b]
        self.root = self.merge(self.merge(a, b), c)
        return s

    def move_to_end(self, l, r):               # CSES Cut and Paste
        a, b, c = self._cut3(l, r)
        self.root = self.merge(self.merge(a, c), b)

    def to_list(self):                         # in-order, pushing flags on the way
        out, stack, t = [], [], self.root
        while stack or t:
            while t:
                self._push(t); stack.append(t); t = self.L[t]
            t = stack.pop(); out.append(self.val[t]); t = self.R[t]
        return out

Complexity, and the Python question

Theorem · expected depth

With independent uniform priorities, the treap has the distribution of a random BST. The expected depth of the element of rank \(k\) is \(H_k + H_{n-k+1} - 2 \le 2\ln n\), about \(1.39 \log_2 n\). So split, merge, and every operation built from a constant number of them take \(O(\log n)\) expected time. The worst case is \(O(n)\), but only with vanishing probability, and the input order does not matter.

The recursion depth is \(O(\log n)\) with high probability: a measured treap of \(2\cdot10^5\) nodes had height 46, far below the recursion limit. Speed is the problem: on that treap, one reversal made about 260 split, merge, push and pull calls, so \(2\cdot10^5\) operations mean around \(5\cdot10^7\) Python calls. That is beyond a one-second CPython budget; submit with PyPy. Building by repeated merge costs \(O(n \log n)\); a stack-based Cartesian-tree build is \(O(n)\) if construction dominates.

Try these first in Python. sortedcontainers.SortedList is available on LeetCode, but on few contest judges. A BIT over values with descent (L105) handles offline multisets. A block list, meaning a list of Python lists of about \(\sqrt n\) elements each, rebuilt when a block grows too large, does insert, erase and cut-and-paste in \(O(\sqrt n)\). Its inner work is C-level slicing, which makes it a strong CPython alternative; measure it against the treap on your judge.

Heavy-Light Decomposition

60m video

Cut a tree into vertical chains by always continuing into the largest child. Any path then crosses only \(O(\log n)\) chains, and if each chain occupies a contiguous block of one array, a path query becomes \(O(\log n)\) range queries on an ordinary segment tree.

Path queries, heavy children, and the light-edge bound

"Add \(x\) to every vertex on the path \(u\)–\(v\)" and "max on the path \(u\)–\(v\)", interleaved and online, are beyond LCA with lifting (L57), which handles static path data, and beyond Euler-tour tricks (L55), which handle subtrees. HLD handles both.

Definition · heavy child, heavy chain

The heavy child of \(v\) is a child with the largest subtree. The edge to it is heavy, and the edges to the other children are light. Following heavy edges down from any vertex that is not itself a heavy child traces a heavy chain, and every vertex lies on exactly one chain.

Theorem · light-edge bound

Every root-to-vertex path contains at most \(\log_2 n\) light edges, so any path \(u\)–\(v\) meets at most \(2\log_2 n + 2\) chains.

Proof

Let \((p, c)\) be light and let \(h\) be \(p\)'s heavy child, so \(\text{size}(h) \ge \text{size}(c)\). Then \(\text{size}(p) \ge 1 + \text{size}(h) + \text{size}(c) > 2\,\text{size}(c)\). Each light edge on the way down at least halves the subtree size, which starts at \(n\) and stays \(\ge 1\), so there are at most \(\log_2 n\) of them. A path \(u\)–\(v\) is two root-ward paths joined at the LCA, and each light edge on them begins a new chain.

The decomposition: heavy, head, pos

Two passes. The first computes parents, depths and subtree sizes, and picks heavy[v]. The second assigns positions so that each chain is contiguous: walk an entire chain first, numbering its vertices consecutively, and push the light children met along the way onto a stack to start their own chains later. Because the light subtrees of a chain vertex are numbered right after the rest of its chain, every subtree is also contiguous: [pos[v], pos[v] + size[v]). That is the same property as the DFS order of L55, so subtree queries come for free.

The climbing loop, written once

While \(u\) and \(v\) are on different chains, take the one whose chain head is deeper, emit the range from its head to it, and jump to the head's parent. When they share a chain, emit the range between them; the shallower one is the LCA. Each iteration crosses a light edge, so the loop runs \(O(\log n)\) times, and with a segment tree behind each range a path query costs \(O(\log^2 n)\). Return the ranges and let the caller fold them: one loop then serves sums, max, lazy updates and anything else.

class HLD:
    """Heavy-light decomposition; vertices 0..n-1, adjacency lists, any root."""
    def __init__(self, adj, root=0):
        n = len(adj)
        parent, depth, order = [-1] * n, [0] * n, [root]
        for u in order:                                  # BFS order
            for w in adj[u]:
                if w != parent[u]:
                    parent[w] = u; depth[w] = depth[u] + 1; order.append(w)
        size, heavy = [1] * n, [-1] * n
        for u in reversed(order):                        # children before parents
            if parent[u] >= 0: size[parent[u]] += size[u]
        for u in order[1:]:
            p = parent[u]
            if heavy[p] < 0 or size[u] > size[heavy[p]]: heavy[p] = u
        head, pos, cur, stack = [0] * n, [0] * n, 0, [root]
        while stack:
            h = v = stack.pop()                          # h starts a new chain
            while v >= 0:
                head[v], pos[v] = h, cur; cur += 1
                for w in adj[v]:
                    if w != parent[v] and w != heavy[v]: stack.append(w)
                v = heavy[v]
        self.parent, self.depth, self.size = parent, depth, size
        self.heavy, self.head, self.pos = heavy, head, pos

    def path(self, u, v, edges=False):
        """Half-open pos ranges covering path u-v. edges=True drops the LCA."""
        head, pos, parent, depth = self.head, self.pos, self.parent, self.depth
        out = []
        while head[u] != head[v]:
            if depth[head[u]] < depth[head[v]]: u, v = v, u
            out.append((pos[head[u]], pos[u] + 1))
            u = parent[head[u]]
        if depth[u] > depth[v]: u, v = v, u
        out.append((pos[u] + edges, pos[v] + 1))          # u is the LCA here
        return out

    def subtree(self, v):
        return self.pos[v], self.pos[v] + self.size[v]

    def lca(self, u, v):                         # same climb, O(log n)
        head, parent, depth = self.head, self.parent, self.depth
        while head[u] != head[v]:
            if depth[head[u]] < depth[head[v]]: u, v = v, u
            u = parent[head[u]]
        return u if depth[u] < depth[v] else v

With any segment tree st laid out by pos: path_query folds st.query(l, r) over hld.path(u, v); path_update calls the lazy tree's range update on each range (L107); subtree_query and subtree_update use the single range hld.subtree(v). For a non-commutative monoid, the ranges come in climbing order from both ends, so keep separate left and right accumulators and reverse one side.

Edge weights. Store the weight of edge (parent(\(v\)), \(v\)) at pos[v], the child's position. A path then covers the right edges except the LCA's own slot, which holds the edge above the LCA. edges=True drops exactly that slot.

Frontier Structures: Segment Tree Beats, Link-Cut Trees, Euler Tour Trees

45m video

A few problems need structures beyond the standard toolkit. Segment tree beats handles "clamp a range to at most \(x\)" with an amortised potential argument. Link-cut trees and Euler tour trees maintain forests that change shape. You implement the first one; for the other two, you learn to recognise the problems that need them, and usually find an offline method instead.

Scope: when the standard toolkit fails

Range \(a_i \leftarrow \min(a_i, x)\) with range sums breaks lazy propagation: the change in a block's sum depends on how many elements exceed \(x\), so the update is not a map on (sum, length) (condition 3 of L107). Linking and cutting tree edges online breaks HLD, whose chains are fixed at build time. These are the gaps the three structures fill.

Segment tree beats: chmin with sum

Each node stores the maximum \(m_1\), the strict second maximum \(m_2\), the count \(c\) of elements equal to \(m_1\), and the sum. A chmin by \(x\) at a node falls into one of three cases.

Theorem · Ji's bound for chmin and sum

With the break and tag conditions above, any sequence of \(q\) range-chmin and range-sum operations on \(n\) elements costs \(O((n+q)\log n)\) in total. If range add is mixed in, the bound becomes \(O((n+q)\log^2 n)\); that proof is longer and is omitted here.

Proof sketch (chmin and sum)

Let \(\Phi = \sum_v d(v)\), where \(d(v)\) is the number of distinct values in \(v\)'s block. Initially \(\Phi \le n(\lceil\log_2 n\rceil + 1)\). A chmin visits the usual \(O(\log n)\) nodes of a range decomposition, plus extra nodes inside fully covered blocks where the tag test failed (\(x \le m_2\)). At an extra node, \(m_1\) and \(m_2\) both become \(x\), so \(d(v)\) drops by at least 1: each extra visit is paid for by a unit of \(\Phi\). A tag replaces \(m_1\) by \(x\) and so cannot raise \(d\). Only the \(O(\log n)\) partially covered ancestors can gain the new value \(x\), raising \(\Phi\) by \(O(\log n)\) per operation. So the extra visits total at most \(\Phi_0 + O(q \log n)\).

NEG = float("-inf")

class Beats:
    """Range a[i] = min(a[i], x) and range sum, amortised O((n + q) log n)."""
    def __init__(self, a):
        n = self.n = len(a)
        self.mx, self.mx2 = [0] * (4 * n), [NEG] * (4 * n)
        self.cnt, self.sm = [0] * (4 * n), [0] * (4 * n)
        self._build(1, 0, n, a)

    def _build(self, v, lo, hi, a):
        if hi - lo == 1:
            self.mx[v], self.cnt[v], self.sm[v] = a[lo], 1, a[lo]; return
        mid = (lo + hi) // 2
        self._build(2 * v, lo, mid, a); self._build(2 * v + 1, mid, hi, a)
        self._pull(v)

    def _pull(self, v):
        l, r, mx, mx2, cnt = 2 * v, 2 * v + 1, self.mx, self.mx2, self.cnt
        self.sm[v] = self.sm[l] + self.sm[r]
        if mx[l] == mx[r]:
            mx[v], cnt[v], mx2[v] = mx[l], cnt[l] + cnt[r], max(mx2[l], mx2[r])
        elif mx[l] > mx[r]:
            mx[v], cnt[v], mx2[v] = mx[l], cnt[l], max(mx2[l], mx[r])
        else:
            mx[v], cnt[v], mx2[v] = mx[r], cnt[r], max(mx[l], mx2[r])

    def _cap(self, v, x):                      # tag case: valid when mx2[v] < x
        if x < self.mx[v]:
            self.sm[v] -= (self.mx[v] - x) * self.cnt[v]; self.mx[v] = x

    def chmin(self, l, r, x, v=1, lo=0, hi=None):
        if hi is None: hi = self.n
        if r <= lo or hi <= l or self.mx[v] <= x: return          # break
        if l <= lo and hi <= r and self.mx2[v] < x:                # tag
            self._cap(v, x); return
        self._cap(2 * v, self.mx[v]); self._cap(2 * v + 1, self.mx[v])   # push
        mid = (lo + hi) // 2
        self.chmin(l, r, x, 2 * v, lo, mid); self.chmin(l, r, x, 2 * v + 1, mid, hi)
        self._pull(v)

    def query(self, l, r, v=1, lo=0, hi=None):
        if hi is None: hi = self.n
        if r <= lo or hi <= l: return 0
        if l <= lo and hi <= r: return self.sm[v]
        self._cap(2 * v, self.mx[v]); self._cap(2 * v + 1, self.mx[v])
        mid = (lo + hi) // 2
        return self.query(l, r, 2 * v, lo, mid) + self.query(l, r, 2 * v + 1, mid, hi)

The push needs no separate tag array: a child's max can never legitimately exceed its parent's, so "cap each child at the parent's max" is the pending update. The cap is valid because each child's \(m_2\) is at most the parent's \(m_2\), which is below the new parent max.

Link-cut trees

A link-cut tree maintains a forest under link(u, v) (add an edge between two trees) and cut(u, v), while answering connectivity and path aggregates, each in amortised \(O(\log n)\). It splits each tree into preferred paths, and stores each path as a splay tree keyed by depth. Everything rests on access(v), which makes the root-to-\(v\) path a single preferred path.

access(v):                 # parent pointers double as path-parent pointers
    last = null; u = v
    while u != null:
        splay(u)           # u becomes the root of its preferred path's splay tree
        u.right = last     # drop the deeper part, attach the path coming up from v
        pull(u)
        last = u; u = u.parent
    splay(v)               # now v's splay tree is exactly the root-to-v path
make_root(v):   access(v); v.rev ^= 1          # reversing the path re-roots at v
find_root(v):   access(v); walk left (pushing flags); splay the node found
link(u, v):     make_root(u); u.parent = v     # u, v in different trees
cut(u, v):      make_root(u); access(v); v.left = null; u.parent = null; pull(v)
path_sum(u, v): make_root(u); access(v); return v.aggregate

Use cases: connectivity and path aggregates in forests whose edges change, online LCA under re-rooting, and a minimum spanning forest maintained as edges arrive. The amortised bound combines the splay access lemma with a heavy-light counting argument. In Python, avoid it unless forced. Each access performs several splay rotations of about a dozen pointer updates each, so a few hundred Python operations per call.

Euler tour trees and offline connectivity

An Euler tour tree stores each tree's Euler tour (the sequence of directed edges a DFS walks) in a balanced BST, such as the implicit treap of L112. A link re-roots one tour (a rotation: split and merge) and splices it into the other. A cut removes the segment between an edge's two occurrences. Connectivity is "same BST?", and subtree aggregates are range aggregates, all in \(O(\log n)\). ETTs underlie fully dynamic connectivity in general graphs, which is far beyond contest scope.

What you actually submit for CSES — Dynamic Connectivity (add and remove edges in a general graph, report the component count after each event) is the offline method of L71. Each edge lives during some time intervals. Insert each interval into the \(O(\log k)\) nodes of a segment tree over time, then DFS that tree with a DSU with rollback: union on entry, roll back on exit, and read the component count at each leaf. That is \(O(k \log k \log n)\), no splay trees, and it is fast enough in PyPy.

What to learn next

Offline techniques first: CDQ divide and conquer and query reordering (L136) replace many online structures. Beyond this series lie top trees, wavelet matrices, kinetic segment trees and beats with historical-value queries. Read KACTL to see how a mature ICPC team keeps a link-cut tree to a few dozen lines.

  • Codeforces — The Child and Sequence. Range \(a_i \bmod x\) with sums. Recurse only where the max is \(\ge x\); each effective mod at least halves a value, the same amortised spirit as beats.
  • CSES — Dynamic Connectivity. Offline segment tree over time plus a rollback DSU.
What breaks
  • Non-strict second max. If \(m_2\) may equal \(m_1\), the tag case also lowers values it must not touch. Second max means the largest value strictly below the max, with \(-\infty\) at leaves.
  • Forgetting the push in query. Children can hold values above the parent's max until they are capped.
  • Mixing chmin and chmax without handling the min/max collision when a node has only one or two distinct values. The general version needs care at exactly those nodes.
  • Reaching for a link-cut tree in Python. First check whether the operations are known in advance; if so, D&C over time almost always works.

Bitsets in Python: Big Integers as Word-Parallel Arrays

50m video

A Python int is an arbitrary-length bit array whose |, &, ^, shifts and bit_count() run in C over machine words. Rewriting an inner loop over booleans as one big-integer operation removes the Python interpreter from the loop, and the measured gains are often over 100×.

The int as a bitset, and its cost model

Definition · the cost model

CPython stores an int as an array of 30-bit digits. A bitwise operation on two \(N\)-bit ints is one C loop over \(\lceil N/30\rceil\) digits plus a fixed overhead for the call and the allocation of the result. So "bits per Python-level operation" goes from 1 (a list of booleans) to \(N\). The speed-up is the word width plus the interpreter loop you deleted, which is why it beats the textbook 64×.

  • Membership: x >> i & 1. Set: x |= 1 << i. Count: x.bit_count() (Python 3.10+).
  • Iterate set bits: while x: low = x & -x; i = low.bit_length() - 1; x ^= low. That is one Python step per set bit, so keep it for sparse masks.
  • Immutable: x |= y builds a new int. Every operation costs \(O(N/30)\) even if it changes one bit.

Subset sum in O(n·S/w)

Bit \(s\) of mask means "sum \(s\) is reachable". Adding weight \(w\) maps every reachable \(s\) to \(s + w\), which is a single shift, and keeping the old sums is an OR. This finishes the 0/1 knapsack of L83.

def subset_sums(weights, cap):
    """Bit s of the result is 1 iff some sub-multiset of weights sums to s (s <= cap)."""
    mask, full = 1, (1 << (cap + 1)) - 1
    for w in weights:
        mask |= (mask << w) & full           # truncate so the int stays cap bits wide
    return mask

def lcs_bitparallel(a, b):
    """LCS length in O(|a| * |b| / w): bit-parallel row update (Allison-Dix, Hyyro)."""
    m = len(a)
    if m == 0: return 0
    match = {}
    for i, ch in enumerate(a):
        match[ch] = match.get(ch, 0) | (1 << i)
    full = v = (1 << m) - 1                    # zero bits mark LCS columns used so far
    for ch in b:
        u = v & match.get(ch, 0)
        v = ((v + u) | (v - u)) & full
    return m - v.bit_count()

assert subset_sums([3, 5], 10) == 0b100101001 and lcs_bitparallel("ABCBDAB", "BDCABA") == 4

Measured under CPython 3.12: subset sum with 100 weights and cap \(5\cdot10^4\) ran about 170 times faster than the list DP, and LCS of two 3000-character strings about 120 times faster than the row DP of L85.

Bit-parallel LCS and edit distance

Theorem · one row of the LCS table in a few word operations

Let \(L_j(i) = \text{LCS}(a_{<i}, b_{<j})\). For fixed \(j\), \(L_j(i) - L_j(i-1) \in \{0, 1\}\), so a row is determined by the set of columns where it steps up. Encode the steps as the zero bits of \(V_j\), starting from all ones. With \(U = V_j \mathbin{\&} M[b_j]\), where \(M[c]\) marks the positions of \(c\) in \(a\), the next row is \(V_{j+1} = (V_j + U) \mid (V_j - U)\), truncated to \(|a|\) bits, and the LCS length is the number of zero bits. The carry of the addition is what carries the DP's "max" along the row. The proof is in Hyyrö (2004).

Myers' algorithm (1999) does the same for edit distance. Its rows change by \(-1\), 0 or \(+1\), encoded as two bit vectors of positive and negative deltas, again \(O(nm/w)\).

Transitive closure and reachability

Warshall's algorithm with rows as ints: for each pivot \(k\), every row that reaches \(k\) absorbs row \(k\), so reach[i] |= reach[k]. That is \(V^2\) Python-level steps over \(V\)-bit rows, \(O(V^3/w)\) overall. At \(V = 2000\) the list-comprehension form below took about 1.4 s on a slow test machine; the plain triple loop would be \(8\cdot10^9\) steps.

def transitive_closure(rows):
    """rows[i] = bitmask of i's direct successors. Returns reachability rows (Warshall)."""
    reach = list(rows)
    for k in range(len(reach)):
        rk, bit = reach[k], 1 << k
        reach = [r | rk if r & bit else r for r in reach]
    return reach

def reachable_counts(n, edges, batch=8192):
    """CSES Reachable Nodes: nodes reachable from each u in a DAG, u included."""
    adj, indeg = [[] for _ in range(n)], [0] * n
    for a, b in edges: adj[a].append(b); indeg[b] += 1
    order = [u for u in range(n) if indeg[u] == 0]
    for u in order:                            # Kahn's algorithm; the list grows as we go
        for v in adj[u]:
            indeg[v] -= 1
            if indeg[v] == 0: order.append(v)
    total = [0] * n
    for lo in range(0, n, batch):              # only targets lo .. lo+batch-1 this pass
        reach = [0] * n
        for u in reversed(order):
            r = 1 << (u - lo) if lo <= u < lo + batch else 0
            for v in adj[u]: r |= reach[v]
            reach[u] = r
        for u in range(n): total[u] += reach[u].bit_count()
    return total

Batching rows. In a DAG with \(n = 5\cdot10^4\), full rows are 6 KB each, and 50,000 of them is about 300 MB. Restricting each pass to a block of 8192 target columns caps the rows at 1 KB (about 50 MB in total) and costs one extra pass over the edges per block.

Matching, cliques and popcount counting

  • Bipartite matching (L77) on dense graphs: in Kuhn's DFS, "unvisited neighbours of \(u\)" is adj[u] & ~visited, so you iterate only those set bits.
  • Cliques: Bron–Kerbosch keeps its candidate and excluded sets \(P\) and \(X\) as ints; P & adj[v] is the whole recursive step.
  • Counting pairs: rows sharing \(c\) common ones contribute \(\binom{c}{2}\) rectangles, where \(c\) is (row[i] & row[j]).bit_count(). Triangles in a dense graph number \(\frac13\sum_{(u,v)\in E} |\text{adj}(u) \cap \text{adj}(v)|\).
  • Hamming distance between \(k\)-bit vectors: (x ^ y).bit_count().

Problems

  • CSES — Hamming Distance. Up to \(2\cdot10^4\) strings of \(k \le 30\) bits, so \(2\cdot10^8\) pairs. Pure Python cannot do it. With numpy: np.bitwise_count(arr[i+1:] ^ arr[i]).min() per row, or use PyPy.
  • CSES — Reachable Nodes. reachable_counts above.
  • CSES — Reachability Queries. Condense the SCCs, then use DAG bitsets, batched by target block, answering each query in the pass that owns its target.
  • CSES — One Bit Positions. For each shift \(k\), the answer is (x & (x >> k)).bit_count(). That is \(n\) operations on \(n\)-bit ints, \(O(n^2/w)\), so borderline; the intended solution is a convolution (L126).
  • LeetCode 1310 — XOR Queries of a Subarray (alternative framing). Prefix xor, the bitwise cousin of prefix sums.
What breaks
  • Unbounded growth. mask << w without the & full truncation lets the int grow to \(\sum w\) bits, which makes every later step slower.
  • Testing bits with shifts in a loop. for i in range(n): if x >> i & 1 is \(O(n^2/w)\) over a long int, because each shift copies. Iterate with x & -x instead.
  • Hidden allocation. reach[i] |= reach[k] allocates a new row each time, so peak memory can be twice the live rows. Batch the target columns.
  • Negative ints. ~x is negative, with infinitely many leading ones in Python's model. Always AND with a full mask before counting or shifting right.

P1 — Pashmak and Parmida's problem. Let \(\text{pre}_i\) be the number of occurrences of \(a_i\) in \(a_1..a_i\), and \(\text{suf}_j\) the number in \(a_j..a_n\). Count pairs \(i < j\) with \(\text{pre}_i > \text{suf}_j\). Both arrays come from one dictionary pass each (the "compression" is the dictionary). Then sweep \(i\) from right to left, querying a BIT over suffix counts (values \(1..n\)) for how many \(j > i\) have \(\text{suf}_j < \text{pre}_i\), and insert \(\text{suf}_i\). \(O(n \log n)\).

def pashmak(a):                                # pairs i < j with pre[i] > suf[j]
    n, seen = len(a), {}
    pre, suf = [0] * n, [0] * n
    for i, x in enumerate(a):
        seen[x] = seen.get(x, 0) + 1; pre[i] = seen[x]
    seen.clear()
    for j in range(n - 1, -1, -1):
        seen[a[j]] = seen.get(a[j], 0) + 1; suf[j] = seen[a[j]]
    t, ans = [0] * (n + 1), 0                  # BIT over suffix counts 1..n
    for i in range(n - 1, -1, -1):
        k = pre[i] - 1                         # suf[j] <= pre[i] - 1, for j > i
        while k > 0: ans += t[k]; k &= k - 1
        k = suf[i]
        while k <= n: t[k] += 1; k += k & -k
    return ans

assert pashmak([1, 2, 1, 1, 2, 2, 1]) == 8

P2 — Sereja and Brackets. Longest correct bracket subsequence of \(s[l..r]\). The node is (matched pairs, unmatched (, unmatched )). Merging matches the left's spare opens with the right's spare closes: \(m = \min(o_x, c_y)\). With \(n\) up to \(10^6\), a tuple tree is heavy in Python. The same node collapses into prefix balances \(P\): unmatched closes are \(P_{l-1} - \min P[l-1..r]\), and unmatched opens are \(P_r - \min P[l-1..r]\). That is one range-minimum query per question, on an array-based min tree. A sparse table at \(10^6\) would need about 170 MB of list slots.

def merge_brackets(x, y):                      # (pairs, open left, close left)
    m = min(x[1], y[2])
    return (x[0] + y[0] + m, x[1] + y[1] - m, x[2] + y[2] - m)

P3 — XOR on Segment. "XOR a range with \(x\)" does not act on sums directly, but it does act on per-bit counts: in bit \(b\), xor with a set bit maps ones to len - ones. Keep one lazy flip tree per bit (values \(< 10^6\), so 20 bits), or one tree whose node stores 20 counts and a tag mask. The sum is \(\sum_b 2^b \cdot \text{ones}_b\). That is \(O(20 \log n)\) per operation, which needs PyPy.

P4 — D-query. Distinct values in a range, \(n \le 3\cdot10^4\), \(q \le 2\cdot10^5\). Mo's costs about \(n\sqrt q \approx 1.3\cdot10^7\) pointer moves. The offline sweep of L108 (sort by right end, keep a 1 at each value's last occurrence) costs \(O((n+q)\log n)\), about \(4\cdot10^6\) BIT steps. Both are correct; in CPython, only the sweep is comfortable. This is the slot's lesson: when a BIT reformulation exists, it wins in Python.

P5 — Water Tree. Fill a subtree, empty a vertex and all its ancestors, ask about one vertex. Timestamp everything. Filling \(w\) at time \(t\) fills \(v\) iff \(v\) is in \(w\)'s subtree, which is an Euler-tour range (L55): a range "max-assign" with point queries. Emptying \(u\) empties \(v\) iff \(u\) is in \(v\)'s subtree: a point set with a range-max query. So \(v\) is full iff its last fill time exceeds the largest empty time in its subtree. Since times only grow, the range assign needs no push: store the time at the canonical nodes and take the max along the leaf-to-root path. No HLD is required, at \(O((n + q)\log n)\).

P6 — Little Elephant and Array. Count values \(x\) occurring exactly \(x\) times in \(a[l..r]\).

Theorem · few candidates

Only values \(x\) whose total count in the whole array is at least \(x\) can ever qualify. If there are \(k\) such distinct values, the smallest possible total is \(1 + 2 + \dots + k \le n\), so \(k \le \sqrt{2n}\), about 450 for \(n = 10^5\).

For each candidate, take a prefix count and test every query: \(O(\sqrt n\,(n + q))\), about \(9\cdot10^7\) elementary steps. That is impossible as Python loops and fast as numpy array operations, where the judge provides numpy; otherwise use PyPy loops.

import numpy as np
from collections import Counter

def little_elephant(a, queries):               # queries: 1-indexed inclusive (l, r)
    arr = np.array(a, dtype=np.int64)
    L = np.array([l - 1 for l, _ in queries]); R = np.array([r for _, r in queries])
    ans = np.zeros(len(queries), dtype=np.int64)
    for x, c in Counter(a).items():
        if x <= c:                             # at most about sqrt(2n) candidates
            pc = np.concatenate(([0], np.cumsum(arr == x)))
            ans += (pc[R] - pc[L]) == x
    return ans.tolist()

assert little_elephant([3, 1, 2, 2, 3, 3, 7], [(1, 7), (3, 4)]) == [3, 1]

Will this pass? A two-minute estimate

Multiply operations by the Python-level steps each costs, and divide by about \(10^7\) per second for CPython (about \(10^8\) for PyPy, per Appendix C of the plan). A BIT query at \(n = 2\cdot10^5\) is about 18 loop iterations, so \(2\cdot10^5\) queries are \(4\cdot10^6\) steps: fine. A recursive segment tree query visits up to \(4\log n \approx 70\) nodes, each a function call worth several steps, so the same load is \(10^8\)-ish: PyPy only. Mo's at \(n = q = 2\cdot10^5\) is \(7.5\cdot10^7\) pointer moves: no. These are estimates; time a worst-case generator before you trust one.
