Randomisation as a Technique

50m video

Randomness is a design tool with a price you can compute. Random choices defeat adversarial inputs, random samples find heavy elements, random 64-bit ids compare whole collections in \(O(1)\). Each comes with a failure probability that you bound explicitly, against a budget, before you submit.

Two kinds of randomised algorithm

Definition
  • Las Vegas: always correct, running time is random. Quicksort and quickselect with random pivots, treaps (L54), Welzl's minimum enclosing circle (L132): expected bounds hold for every input.
  • Monte Carlo: bounded running time, answer wrong with small probability. Hashing (L37), Miller–Rabin (L118), random sampling with a fixed number of trials. Often the error is one-sided: "found" is always right, "not found" may be wrong.

A Monte Carlo algorithm whose answers can be verified becomes Las Vegas: repeat until the check passes. That is how the majority search below behaves when a majority is guaranteed to exist.

Shuffling against adversaries

A deterministic algorithm has a worst-case input, and on hackable judges someone will submit it. Randomising the algorithm, not the input, moves the bad case out of the adversary's control. Quicksort with a fixed pivot is \(O(n^2)\) on sorted input, while a random pivot gives expected \(O(n\log n)\) on every input. Treaps take their balance from random priorities. Hash tables: CPython hashes an int to itself modulo \(2^{61}-1\), so keys can be chosen to collide in a dict. Store x ^ SALT with a random salt drawn at start-up (L26). Polynomial string hashes with a fixed base can be broken by precomputed collisions; a random base modulo the prime \(2^{61}-1\) cannot be targeted in advance.

Random sampling: finding a majority

If some value occupies more than half of a range, a uniformly random position hits it with probability above \(1/2\). Check the candidate's frequency exactly and return it if it qualifies. If \(t\) samples all miss, report "none". The error is one-sided: a reported value is always right, and a true majority is missed with probability below \(2^{-t}\). For range queries, keep each value's sorted list of positions, so the frequency check is two binary searches: \(O(t\log n)\) per query, with no segment tree. (The deterministic alternative is a segment tree storing Boyer–Moore candidate/count pairs per node, which merge associatively.)

import math, random
from bisect import bisect_left, bisect_right

class RangeMajority:
    """Value occurring >= need times in a[l..r] (inclusive); need > half the length."""
    def __init__(self, a, queries, budget=1e-9):
        self.a, self.pos = a, {}
        for i, x in enumerate(a):
            self.pos.setdefault(x, []).append(i)
        self.t = max(1, math.ceil(math.log2(max(1, queries) / budget)))   # trials per query

    def query(self, l, r, need=None):
        need = (r - l + 1) // 2 + 1 if need is None else need
        for _ in range(self.t):
            x = self.a[random.randint(l, r)]
            p = self.pos[x]
            if bisect_right(p, r) - bisect_left(p, l) >= need:
                return x                           # verified: never wrong
        return -1                                  # wrong with probability < 2**-t

rm = RangeMajority([1, 1, 2, 2, 1, 1], queries=2)
print(rm.t, rm.query(0, 5, 4), rm.query(2, 3, 2))  # 31 1 2

The trial count comes from the budget, not from habit. With \(q = 10^4\) queries and a total failure budget of \(10^{-9}\), each query may fail with probability \(10^{-13}\), so \(t = \lceil\log_2 10^{13}\rceil = 44\). Twenty trials, a common choice, would give a total failure chance near \(10^{-2}\).

XOR and sum hashing of collections

Give every distinct value a random 64-bit id. The XOR of the ids of a collection depends only on which values occur an odd number of times, so it identifies sets (and parity patterns). The sum modulo \(2^{64}\) depends on the full counts, so it identifies multisets. Both are invertible, so prefix arrays give the hash of any subarray in \(O(1)\), and two collections are compared by comparing two integers. The same works for the multiset of colours in a subtree after Euler flattening, or the set of edges around a vertex.

import random
from itertools import accumulate
from operator import xor

M64 = (1 << 64) - 1

def make_ids(*arrays):                             # one random 64-bit id per value
    return {v: random.getrandbits(64) for arr in arrays for v in arr}

def sum_prefix(a, ids):                            # multiset hashes of all prefixes
    return [0] + [s & M64 for s in accumulate(ids[x] for x in a)]

def xor_prefix(a, ids):                            # set / parity hashes of all prefixes
    return [0] + list(accumulate((ids[x] for x in a), xor))

def same_multiset(P, l1, r1, Q, l2, r2):           # a[l1:r1] vs b[l2:r2], half-open
    return (P[r1] - P[l1]) & M64 == (Q[r2] - Q[l2]) & M64

a, b = [3, 1, 4, 1, 5, 9], [1, 1, 3, 4, 2, 6]
ids = make_ids(a, b)
P, Q = sum_prefix(a, ids), sum_prefix(b, ids)
print(same_multiset(P, 0, 4, Q, 0, 4), same_multiset(P, 1, 5, Q, 0, 4))   # True False

Codeforces 1175F (The Number of Subpermutations) is the standard XOR-hashing exercise. A window of length \(L\) is a permutation of \(1..L\) exactly when its XOR hash equals \(id(1) \oplus \dots \oplus id(L)\), up to hash collisions. Equal XOR forces every value \(1..L\) to occur an odd number of times, and with only \(L\) elements in the window that means exactly once each.

Zobrist hashing for game states

For boards, take one random 64-bit number \(Z[cell][piece]\) per (cell, piece) pair. A position's key is the XOR of the numbers of its occupied cells. Placing or removing a piece XORs a single number, so the key is maintained in \(O(1)\) per move, and the search can cache results in a dict keyed by it. Include the side to move in the key whenever the position does not determine it.

import random
Z = [[random.getrandbits(64) for _ in range(2)] for _ in range(9)]   # Z[cell][player]
LINES = [(0, 1, 2), (3, 4, 5), (6, 7, 8), (0, 3, 6), (1, 4, 7), (2, 5, 8), (0, 4, 8), (2, 4, 6)]
board, cache = [-1] * 9, {}

def negamax(p, key):                               # +1 win, 0 draw, -1 loss for player p
    if key in cache:
        return cache[key]
    if any(board[i] == board[j] == board[k] == 1 - p for i, j, k in LINES):
        res = -1                                   # the previous move won
    elif -1 not in board:
        res = 0
    else:
        res = -2
        for c in range(9):
            if board[c] < 0:
                board[c] = p
                res = max(res, -negamax(1 - p, key ^ Z[c][p]))   # O(1) key update
                board[c] = -1
    cache[key] = res
    return res

print(negamax(0, 0), len(cache))                   # 0 5478: a draw; every legal position once

Budgeting the failure probability

Two bounds cover nearly every case. Comparing given pairs: if a solution makes \(q\) equality tests between hashes of collections that differ, each wrongly reports "equal" with probability \(2^{-64}\), so the union bound gives at most \(q\cdot2^{-64}\). Looking for any equal pair among \(m\) items (counting equal subarrays, deduplicating states): the birthday bound \(\approx m^2/2^{65}\). Set a budget, say \(10^{-9}\) per test file, multiply by the number of tests, and check that the bound fits. This is also why random.getrandbits(64) matters. Ids drawn from randint(1, 10**6) collide with probability near 1 once there are a few thousand distinct values.

Seeding

On the judge, leave Python's default seeding (from os.urandom), or seed from time.time_ns(). A fixed seed is visible in your source after the contest, and on Codeforces anyone can then hack it. For debugging, make the seed reproducible: read it from the command line when given, and print the seed you used to stderr, so a failing stress test can be replayed exactly.

import os, random, sys, time
SEED = int(os.environ["SEED"]) if "SEED" in os.environ else time.time_ns()
random.seed(SEED)
print("seed", SEED, file=sys.stderr)              # replay with SEED=... python sol.py

Problems

Codeforces 1175F: XOR hashing of windows (above), iterating over the position of the 1 in each candidate window. LeetCode 1157 (Online Majority Element In Subarray): RangeMajority.query(l, r, threshold); the guarantee \(2\cdot threshold > length\) is exactly what makes sampling work. Codeforces 840D (Destiny): smallest value occurring more than \((r-l+1)/k\) times, \(k \le 5\). A random position hits such a value with probability above \(1/k\), so scale the trial count by \(k\) and keep the smallest verified candidate. To be sure you found the smallest, the deterministic segment tree of \(k-1\) candidates is the safer choice. Hack-resistant rewrite: take an earlier solution that keys a dict by input integers, or hashes strings with a fixed base, and add a random salt or base.

What breaks
  • XOR when you need counts. XOR cancels pairs: \(\{1, 1, 2\}\) and \(\{2\}\) have the same XOR hash. Use the modular sum for multisets.
  • Small id ranges and 32-bit hashes: the birthday bound bites at around \(\sqrt{\text{range}}\) items.
  • Trials chosen by habit. Twenty samples per query over \(10^5\) queries fails somewhere about one run in ten.
  • Fixed seeds on hackable judges, and random.seed() calls left inside loops, which reset the stream.
  • Zobrist keys without side-to-move (or castling, or any state not visible on the board) merge different positions in the cache.

  3. Stress same_multiset against sorted(a[l1:r1]) == sorted(b[l2:r2]), then replace the ids by randint(1, 8) and watch it fail.
  4. Goal: use randomness deliberately, with a probability budget.

Offline Processing, Query Reordering, and CDQ Divide & Conquer

55m video

If every query is known before you must answer any of them, you choose the order in which to answer them. Pick the order that sorts away one dimension of the problem, and a hard online data structure usually becomes a sweep with a Fenwick tree.

The strategic question: must this be online?

A problem is forced online only when a query depends on earlier answers (inputs "decoded" by XOR with the last answer, interactive judges), or when updates and queries are genuinely interleaved in a way you cannot replay. Otherwise read everything, then decide the order. The design question is always which dimension do I sort away? Each of the four standard reorderings removes one:

Sort by right endpoint + Fenwick tree

Distinct values in \(a[l..r]\), many queries. Sweep \(r\) from left to right, keeping a 1 in a Fenwick tree at the last occurrence of each value seen so far and 0 elsewhere. Every distinct value in \([l, r]\) has exactly one last occurrence \(\le r\), and it lies in \([l, r]\) exactly when the value occurs there, so the answer is a range sum. \(O((n + q)\log n)\). The same skeleton counts pairs inside ranges: process right endpoints in order and let each new element add its contributions at the positions of its partners. This is the formal version of the pattern from L108.

def distinct_in_ranges(a, queries):            # queries: (l, r), inclusive, 0-indexed
    n = len(a)
    bit = [0] * (n + 1)
    def add(i, v):
        i += 1
        while i <= n:
            bit[i] += v; i += i & -i
    def pref(i):                               # sum over positions < i
        s = 0
        while i:
            s += bit[i]; i &= i - 1
        return s
    last, ans, r = {}, [0] * len(queries), -1
    for k in sorted(range(len(queries)), key=lambda k: queries[k][1]):
        l, qr = queries[k]
        while r < qr:                          # extend the sweep to qr
            r += 1
            if a[r] in last:
                add(last[a[r]], -1)            # the old last occurrence stops counting
            last[a[r]] = r; add(r, 1)
        ans[k] = pref(qr + 1) - pref(l)
    return ans

print(distinct_in_ranges([1, 2, 1, 3, 2], [(0, 4), (1, 3), (2, 2)]))   # [3, 3, 1]

Offline dynamic connectivity: D&C over time

Algorithm · segment tree over time + rollback DSU
  1. Each edge is alive on some time intervals \([t_{add}, t_{remove})\). Insert each interval into the \(O(\log k)\) nodes of a segment tree over the \(k\) time points that exactly cover it.
  2. DFS the segment tree. On entering a node, union its edges in a DSU and remember how many unions you did. At a leaf (one time point), the DSU holds exactly the edges alive then, so record the answer (the component count).
  3. On leaving a node, roll back its unions. Use union by size without path compression, so each union changes \(O(1)\) fields and each find is \(O(\log n)\).

Each edge interval is applied \(O(\log k)\) times, so the total is \(O((m + k)\log k\log n)\). This is the rollback DSU of L71 put to its main use, and it answers CSES Dynamic Connectivity. The DSU is the only part that differs from a normal one:

class RollbackDSU:
    def __init__(self, n):
        self.p, self.sz, self.hist, self.comps = list(range(n)), [1] * n, [], n
    def find(self, x):
        while self.p[x] != x:                  # no path compression: undo stays O(1)
            x = self.p[x]
        return x
    def union(self, a, b):
        a, b = self.find(a), self.find(b)
        if a == b:
            self.hist.append(-1); return
        if self.sz[a] < self.sz[b]:
            a, b = b, a
        self.p[b] = a; self.sz[a] += self.sz[b]; self.comps -= 1
        self.hist.append(b)
    def rollback(self):                        # undo the most recent union call
        b = self.hist.pop()
        if b >= 0:
            a = self.p[b]
            self.sz[a] -= self.sz[b]; self.p[b] = b; self.comps += 1

CDQ divide and conquer

CDQ is divide and conquer over the sequence of operations, not over the data. Split the operations (or points, in some fixed order) at the middle. Recursively handle the pairs that lie inside each half. Then handle the cross pairs, "left-half updates affecting right-half queries", in one sweep. The cross step has one ordering already settled (left comes before right), so it is a 2D problem: sort by the second coordinate and use a Fenwick tree for the third.

3D dominance counting: for each point \((a, b, c)\), count the other points with \(a' \le a\), \(b' \le b\), \(c' \le c\). First merge identical points into one with a multiplicity, since they dominate each other. Sort the distinct points lexicographically. A point that dominates another distinct point is lexicographically larger, so every dominating pair has the dominated point on the left. In the cross step, walk the right half in order of \(b\), inserting left points with \(b' \le b\) into a Fenwick tree keyed by the rank of \(c\), then query. Undo the insertions afterwards, so the cost stays proportional to the range.

from collections import Counter

def dominance_counts(points):
    """For each input point, the number of OTHER points that are <= it in all 3 coordinates."""
    mult = Counter(points)
    uniq = sorted(mult)                        # lexicographic: a, then b, then c
    crank = {c: i + 1 for i, c in enumerate(sorted({p[2] for p in uniq}))}
    B = [p[1] for p in uniq]
    C = [crank[p[2]] for p in uniq]
    W = [mult[p] for p in uniq]
    res, bit, idx = [0] * len(uniq), [0] * (len(crank) + 1), list(range(len(uniq)))
    def add(i, v):
        while i < len(bit):
            bit[i] += v; i += i & -i
    def ask(i):
        s = 0
        while i:
            s += bit[i]; i &= i - 1
        return s
    def cdq(lo, hi):                           # afterwards idx[lo:hi] is sorted by b
        if hi - lo <= 1:
            return
        mid = (lo + hi) // 2
        cdq(lo, mid); cdq(mid, hi)
        left, i = idx[lo:mid], 0
        for j in idx[mid:hi]:                  # right half in b order
            while i < len(left) and B[left[i]] <= B[j]:
                add(C[left[i]], W[left[i]]); i += 1
            res[j] += ask(C[j])
        for t in left[:i]:
            add(C[t], -W[t])                   # undo: keep the tree clean
        idx[lo:hi] = sorted(idx[lo:hi], key=B.__getitem__)
    cdq(0, len(uniq))
    where = {p: k for k, p in enumerate(uniq)}
    return [res[where[p]] + mult[p] - 1 for p in points]

print(dominance_counts([(1, 1, 1), (2, 2, 2), (2, 1, 3), (2, 2, 2)]))   # [0, 2, 1, 2]

Parallel binary search

Some queries ask "at which step of a fixed process does my condition first hold?", for example "after which road is \(u\) connected to \(v\)?". One query alone is a binary search, replaying the process \(O(\log m)\) times. With \(q\) queries, run all the binary searches together. In each round, put every unfinished query in the bucket of its midpoint, replay the process once from the start, and at step \(t\) resolve the queries in bucket \(t\). That is \(O(\log m)\) replays in total instead of \(O(q\log m)\), so \(O((m + q)\log m)\) times the cost of a step.

def earliest_connected(n, roads, queries):     # CSES New Roads Queries, 0-indexed
    m, q = len(roads), len(queries)
    lo = [0] * q                               # invariant: not connected after day lo
    hi = [m + 1] * q                           # connected after day hi (m + 1 = never)
    for i, (u, v) in enumerate(queries):
        if u == v:
            lo[i], hi[i] = -1, 0
    while True:
        bucket = [[] for _ in range(m + 1)]
        for i in range(q):
            if hi[i] - lo[i] > 1:
                bucket[(lo[i] + hi[i]) // 2].append(i)
        if not any(bucket):
            break
        p = list(range(n))
        def find(x):
            while p[x] != x:
                p[x] = p[p[x]]; x = p[x]       # path halving
            return x
        for day in range(1, m + 1):
            a, b = find(roads[day - 1][0]), find(roads[day - 1][1])
            if a != b:
                p[a] = b
            for i in bucket[day]:
                if find(queries[i][0]) == find(queries[i][1]): hi[i] = day
                else: lo[i] = day
    return [h if h <= m else -1 for h in hi]

print(earliest_connected(4, [(0, 1), (2, 3), (1, 2)], [(0, 2), (0, 1), (3, 3), (0, 0)]))   # [3, 1, 0, 0]

The meta-lesson

Offline solutions are usually simpler than the online structure they replace (a sweep and a Fenwick tree instead of a persistent segment tree; a rollback DSU instead of a link-cut tree), and in Python they are faster, because they do their work in sorted passes over flat lists. Before reaching for an advanced structure, ask whether the queries can be reordered.

Problems

CSES — Dynamic Connectivity: the segment tree over time with RollbackDSU, printing comps at each leaf. CSES — New Roads Queries: earliest_connected. That is about 18 replays at \(n, m, q = 2\cdot10^5\); a measured CPython run took about 25 s, so in Python learn it here and submit something else. The one-pass alternative uses union by size and stores on each DSU edge the day it was added; the answer is then the maximum such day on the tree path between \(u\) and \(v\), with depth \(O(\log n)\). LeetCode 1697 (Checking Existence of Edge Length Limited Paths): sort the edges by length and the queries by limit, add edges below each limit, answer by find. Parallel binary search classics: POI 2011 Meteors is the standard first problem. CDQ: 3D partial-order counting, and "points inserted over time, count those in a quadrant" (time, \(x\), \(y\)), which is exactly dominance_counts with time as the first coordinate.

What breaks
  • Path compression in a rollback DSU. It rewrites many pointers per find, and rollback no longer restores the old structure.
  • Duplicate points in CDQ. Identical points dominate each other in both directions, but the sweep counts only one direction. Merge them with multiplicities first.
  • Ties on the sweep coordinate. With \(\le\), left points with equal \(b\) must be inserted before right points query; the <= in the while-loop is that rule.
  • Answers in sorted order. After reordering, write each answer to its original index; printing in processing order is the most common offline bug.
  • Forced-online inputs (each query XORed with the previous answer) cannot be reordered; read the input format before designing.

Practice

  1. CSES: Dynamic Connectivity, New Roads Queries (both ways: parallel binary search and timestamped DSU).
  2. LeetCode 1697.
  3. Stress dominance_counts and distinct_in_ranges against \(O(n^2)\) brute force, with many duplicates.
  4. One parallel-binary-search problem (POI 2011 Meteors) and one CDQ problem from the Codeforces problemset.
  5. Goal: convert online problems to offline ones deliberately.

Constructive Algorithms and Ad-Hoc Problems

55m video

"Output any valid X, or −1" problems have no standard algorithm, but they have a standard procedure. Write the checker first, brute-force small cases, guess a pattern, prove it by construction or induction, and use an invariant when the answer is −1.

The procedure

Algorithm · attacking a constructive problem
  1. Checker. Write valid(input, output) straight from the statement. It is short, it is obviously correct, and everything else is tested against it.
  2. Brute force. For tiny inputs, enumerate all outputs and print which inputs have answers and what the answers look like (lexicographically first, or all of them).
  3. Pattern. Read the table: which \(n\) are impossible? Is there a regular shape: blocks, alternation, a recursive structure?
  4. Construction and proof. Generalise, then prove validity: directly, by induction ("solve \(n\) from \(n-1\)" or "from \(n-2\)"), or by a greedy plus an exchange argument. Prove impossibility with an invariant.
  5. Verify in the loop. Run the construction through the checker for every \(n\) up to a few hundred before submitting.

The checker-first discipline matters most in this genre because samples are weak. A special judge accepts many outputs, so the sample output rarely matches yours, and "passes samples" carries almost no information.

Worked example: a permutation with no adjacent neighbours

CSES Permutations: output a permutation of \(1..n\) in which no two adjacent entries differ by 1, or report that none exists. The brute force says \(n = 2, 3\) are impossible and everything else is possible. The first idea, odd numbers then even numbers, looks right and fails, which the checker catches immediately:

from itertools import permutations

def valid(p):
    return sorted(p) == list(range(1, len(p) + 1)) and all(abs(x - y) != 1 for x, y in zip(p, p[1:]))

def odds_then_evens(n):
    return list(range(1, n + 1, 2)) + list(range(2, n + 1, 2))

def evens_then_odds(n):
    return list(range(2, n + 1, 2)) + list(range(1, n + 1, 2))

def exists(n):                                 # brute force, tiny n only
    return any(valid(list(p)) for p in permutations(range(1, n + 1)))

possible = [n for n in range(1, 9) if exists(n)]
print("no solution for", [n for n in range(1, 9) if n not in possible])           # [2, 3]
for build in (odds_then_evens, evens_then_odds):
    print(build.__name__, "fails for", [n for n in possible if not valid(build(n))])
# odds_then_evens fails for [4]      (1 3 | 2 4: the junction 3, 2 differs by 1)
# evens_then_odds fails for []
assert all(valid(evens_then_odds(n)) for n in range(4, 500))

Impossibility: invariants and monovariants

Method · invariant

Find a quantity that every allowed operation preserves (or that every valid output must satisfy) and that differs between the start and the target. Then no sequence of operations, and no output, can succeed, and the answer is \(-1\). A monovariant is a quantity that changes in only one direction. It proves that a process terminates, and bounds how many steps it takes.

Grid parity. Fill an \(n\times m\) grid with 0/1 so that every row has an odd number of ones and every column an even number. Summing all cells by rows gives \(\equiv n\), by columns \(\equiv 0 \pmod 2\), so it is impossible for odd \(n\). For even \(n\), ones down the first column work. Permutation parity. Every swap changes the number of inversions by an odd amount, so a permutation reachable by an even number of swaps must have even inversion parity. This is the argument behind unsolvable 15-puzzle positions. Sums. If \(1 + \dots + n\) is odd, it cannot be split into two equal halves (Two Sets, below). In contests, try parity first, then sums modulo small numbers, then sorted-order or GCD invariants.

Induction and greedy: Two Sets

CSES Two Sets, promised in L47: split \(1..n\) into two sets with equal sums. When \(n(n+1)/2\) is even, take numbers from \(n\) downwards whenever they fit in the remaining target \(T = n(n+1)/4\).

Proof · the greedy never gets stuck

Claim: if \(0 \le T \le i(i+1)/2\), the greedy over \(i, i-1, \dots, 1\) reaches exactly 0. Induct on \(i\); for \(i = 0\), \(T = 0\). If \(T \ge i\), take \(i\): the new target satisfies \(0 \le T - i \le i(i+1)/2 - i = (i-1)i/2\). If \(T < i\), skip \(i\): then \(T \le i - 1 \le (i-1)i/2\) for \(i \ge 2\), and for \(i = 1\), \(T = 0\). Either way the hypothesis holds for \(i - 1\).

def two_sets(n):
    total = n * (n + 1) // 2
    if total % 2:
        return None                            # parity invariant: impossible
    rem, A = total // 2, []
    for i in range(n, 0, -1):
        if i <= rem:
            A.append(i); rem -= i
    return A                                   # rem == 0 by the lemma

assert all((two_sets(n) is None) == (n * (n + 1) // 2 % 2 == 1) for n in range(1, 2000))
assert all(sum(two_sets(n)) * 2 == n * (n + 1) // 2 for n in range(1, 2000) if two_sets(n))

Pairing gives a second construction: for \(n \equiv 0 \pmod 4\), group \(1..n\) into quadruples \(\{4k+1, 4k+2, 4k+3, 4k+4\}\) and send \(4k+1, 4k+4\) left and \(4k+2, 4k+3\) right. Symmetry and pairing (\(i\) with \(n + 1 - i\)) are the first things to try when the target is "balanced". Extremal arguments ("look at the largest element: where can it go?") are the first things to try when the target is "possible at all".

A graph with given degrees

Theorem · Erdős–Gallai

A non-increasing sequence \(d_1 \ge \dots \ge d_n \ge 0\) is the degree sequence of a simple graph iff \(\sum d_i\) is even and, for every \(k\), $$\sum_{i \le k} d_i \;\le\; k(k-1) + \sum_{i > k}\min(d_i, k).$$

Erdős–Gallai decides; Havel–Hakimi constructs. Repeatedly take a vertex of largest remaining degree \(d\) and join it to the \(d\) other vertices of largest remaining degree. The sequence is graphic iff this never runs out of vertices. Its correctness is an exchange argument: if a graph realises the sequence, edges can be swapped so that the top vertex is adjacent to the next \(d\) largest. With a heap this takes \(O(m\log n)\) for \(m\) edges.

import heapq

def havel_hakimi(deg):
    """Edges of a simple graph with these degrees, or None if the sequence is not graphic."""
    heap = [(-d, v) for v, d in enumerate(deg) if d > 0]
    heapq.heapify(heap)
    edges = []
    while heap:
        d, v = heapq.heappop(heap)
        if -d > len(heap):
            return None                        # not enough other vertices left
        taken = [heapq.heappop(heap) for _ in range(-d)]
        for e, u in taken:
            edges.append((v, u))
            if e + 1 < 0:
                heapq.heappush(heap, (e + 1, u))   # u's remaining degree drops by one
    return edges

def check_graph(deg, edges):                   # the checker: degrees and simplicity
    got = [0] * len(deg)
    for u, v in edges:
        got[u] += 1; got[v] += 1
    return got == list(deg) and all(u != v for u, v in edges) and \
        len({frozenset(e) for e in edges}) == len(edges)

print(havel_hakimi([3, 3, 2, 2, 2]), havel_hakimi([3, 3, 1, 1]))

Ad-hoc problems: fail fast

Ad-hoc problems are the ones with no named technique. Give them a time box (20 minutes in a contest, L139). Spend the first five writing the brute force and printing a table of small cases, since a visible pattern is the most common way in. If no pattern and no invariant appears by the end of the box, move to another problem and come back. The worst outcome is an hour of staring at one statement.

Problems

CSES — Permutations and Two Sets: above. Degree-sequence construction: havel_hakimi plus check_graph in a stress loop over random sequences, compared with the Erdős–Gallai test. What breaks
  • Trusting the samples. Special-judge samples show one answer among many; a construction that matches them can still fail for half of all \(n\).
  • Small-\(n\) exceptions. Constructions usually start working at some \(n_0\); \(n = 1, 2, 3\) and boundary shapes (one row, one column) need explicit cases. Run the checker from \(n = 1\).
  • Printing −1 too eagerly. An invariant must be proved, not felt. If the brute force finds an answer where you claim −1, the invariant is wrong.
  • Output format. "Any valid answer" still means the exact format: counts before lists, 1-indexed vertices, YES/NO casing.

Interactive Problems and Special Judges

45m video

In an interactive problem your program holds a conversation with the judge. Getting it accepted takes three things: flush every query, derive the query budget from information theory, and test against a local judge, including an adversarial one, before submitting.

How the conversation works

The judge's interactor and your program run as two processes, with your stdout wired to its stdin and its stdout to yours. You print a query (commonly ? x), read the reply, and eventually print the answer (! x) and exit. Exceeding the query limit, or sending a malformed query, usually earns a reply of \(-1\). At that point exit immediately, because reading further blocks forever and turns a Wrong Answer into a confusing timeout.

Flushing and reading

Use print(..., flush=True) or call sys.stdout.flush() after every query, and read replies with input() or sys.stdin.readline(). The bulk reader from L2, sys.stdin.buffer.read(), waits for end-of-file, which never comes in an interactive problem, so the template you use everywhere else deadlocks here. Keep a separate interactive template.

The query budget is information

Bound · counting information

If the hidden object is one of \(N\) possibilities and each reply has at most \(r\) distinct values, any strategy needs at least \(\lceil\log_r N\rceil\) queries in the worst case. After \(k\) queries the replies form at most \(r^k\) distinct transcripts, and two possibilities with the same transcript cannot be told apart.

Read the limit backwards to find the intended algorithm. "20 queries, \(n \le 10^6\)" with yes/no replies: \(2^{20} \approx 1.05\cdot10^6\), so binary search with no slack. Sorting \(n\) items by comparisons needs \(\lceil\log_2 n!\rceil\) queries. In AtCoder's practice task Interactive Sorting, \(N = 26\) with \(Q = 100\) allows merge sort, whose worst case \(n\lceil\log_2 n\rceil - 2^{\lceil\log_2 n\rceil} + 1\) is 99 for \(n = 26\). \(N = 5\) with \(Q = 7\) is tight: \(\lceil\log_2 120\rceil = 7\), so you need the optimal 7-comparison sort of 5 items (the Ford–Johnson merge-insertion order), and generic sorts fail. Replies with more outcomes carry more bits: a three-way reply (<, =, >) gives up to \(\log_2 3\) bits, and a numeric reply can carry much more, as below.

Write the solution against an interface

Write solve(n, ask), where ask is a function. On the judge, ask prints, flushes and reads. Locally, it is a method of a mock judge that counts queries, asserts the limit, and can play an adversary: it never commits to a hidden value, and answers each query so that the larger set of candidates survives. An adaptive judge does exactly this, so your algorithm must be correct against every reply sequence consistent with some answer, not just against a fixed hidden value.

import sys

def guess(n, ask):                             # hidden x in 1..n; ask(m) -> is x >= m ?
    lo, hi = 1, n                              # invariant: lo <= x <= hi
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if ask(mid): lo = mid
        else: hi = mid - 1
    return lo

def judge_ask(m):                              # the real judge, over stdin/stdout
    print("?", m, flush=True)
    reply = sys.stdin.readline().strip()
    if reply == "-1":
        sys.exit(0)                            # limit exceeded or bad query: stop now
    return reply == ">="

class MockJudge:
    """Local judge: fixed hidden x, or an adversary if x is None. Counts queries."""
    def __init__(self, n, x=None, limit=None):
        self.lo, self.hi, self.x, self.q, self.limit = 1, n, x, 0, limit
    def ask(self, m):
        self.q += 1
        assert self.limit is None or self.q <= self.limit, "query limit exceeded"
        if self.x is not None:
            return self.x >= m
        if self.hi - m + 1 >= m - self.lo:     # keep the larger half of the candidates
            self.lo = max(self.lo, m); return True
        self.hi = m - 1; return False

for n in (1, 2, 10, 10**6):
    for x in {1, n, (n + 1) // 2}:
        assert guess(n, MockJudge(n, x, limit=20).ask) == x
    A = MockJudge(n)
    g = guess(n, A.ask)
    assert A.lo == A.hi == g                   # the adversary's last candidate
    print(n, "adversary forced", A.q, "queries; ceil(log2 n) =", (n - 1).bit_length())

The adversary output is the lower bound made concrete: on \(n = 10^6\) it forces exactly 20 queries, and no algorithm can do better against it. In the contest, the submission is print("!", guess(n, judge_ask), flush=True) after reading \(n\).

A hidden permutation with numeric replies

Codeforces 1407C (Chocolate Bunny): a hidden permutation \(p\) of \(1..n\), the query ? i j returns \(p_i \bmod p_j\), and at most \(2n\) queries are allowed. Asking both orders of a pair reveals one value exactly.

Proof · two queries pin down the smaller value

If \(p_i < p_j\), then \(p_i \bmod p_j = p_i\), while \(p_j \bmod p_i < p_i\). So the larger of the two replies equals \(\min(p_i, p_j)\), and it comes from the query whose first index holds that minimum. Keep one "unknown" candidate \(c\). For each new \(i\), query both orders: one of \(c, i\) is resolved, and the other becomes the candidate. After \(n - 1\) rounds the last candidate must hold \(n\). That is \(2(n-1)\) queries.

import random

def find_permutation(n, ask):                  # ask(i, j) returns p[i] % p[j]
    p, c = [0] * n, 0                          # c: index whose value is still unknown
    for i in range(1, n):
        a, b = ask(c, i), ask(i, c)
        if a > b:
            p[c], c = a, i                     # p[c] was the smaller one
        else:
            p[i] = b
    p[c] = n
    return p

for n in (1, 2, 7, 1000):
    hidden, calls = random.sample(range(1, n + 1), n), [0]
    def ask(i, j):
        calls[0] += 1
        return hidden[i] % hidden[j]
    assert find_permutation(n, ask) == hidden and calls[0] <= 2 * n

A local interactor with two processes

The mock-judge class tests the logic. To test the actual I/O (flushing, parsing, exit codes), write the interactor as its own script and connect the two processes. This runner was used to reproduce the deadlock in the figure:

import subprocess, sys
# usage: python run_interactive.py sol.py interactor.py

The interactor reads queries, answers them, counts them, and reports the verdict on stderr. Run it under a timeout, so a hang shows up as a hang rather than an endless wait.

Special judges: "print any valid answer"

When many outputs are correct, the judge runs a checker instead of comparing text. Your local tests must do the same: stress-test with valid(input, output) (as in L137) plus a brute force that decides only whether an answer exists, never diff against a reference output. Special judges also accept floating-point answers within a tolerance. Check whether the tolerance is absolute or relative, and print enough digits.

What breaks
  • No flush: Idleness limit exceeded, or a TLE that has nothing to do with speed.
  • Bulk input (sys.stdin.read(), sys.stdin.buffer.read()): waits for EOF and deadlocks.
  • Ignoring \(-1\): continuing after the judge has given up turns WA into a hang.
  • Off-by-one in the budget: \(\lceil\log_2 n\rceil\) vs \(\lfloor\log_2 n\rfloor + 1\) differ exactly at powers of two; the adversary finds this instantly.
  • Assuming a fixed hidden answer when the statement says the interactor is adaptive, for example a "random" guess that is only fast on average.
  • Debug prints to stdout: the judge reads them as queries. Print debugging output to stderr.

The Codeforces formula, as documented by the platform: for a round of \(d\) minutes, a problem worth \(x\) solved at minute \(t\) after \(w\) rejected attempts scores \(\max\!\big(0.3x,\ x - \lfloor 120\,x\,t/(250\,d)\rfloor - 50w\big)\). The opening and the clock

Read A, B and C immediately and solve them in order: they are the guaranteed points, and every minute of delay costs points (or penalty) on every later problem too. Then skim the rest: constraints first (they reveal the intended complexity), then the samples, then the story. Short statements with small samples tend to be easier; bigger letters are harder on Codeforces; in ICPC-style contests, watch which problems the standings show being solved. The 20-minute rule: if 20 minutes pass with no new idea and no code, write one line about where you are stuck and switch problems. You return with fresh eyes, and the other problem might be easier than its letter suggests. Guess and submit only when the cost is small: in ICPC a rejection on a problem you never solve costs nothing, and in the last minutes a plausible pattern backed by a brute force on small cases is worth a try.

Penalty math: is a risky submit worth it?

Derivation · ICPC-style expected cost

You have a solution that is right with probability \(p\), and testing would take \(t\) more minutes. Suppose you will solve \(k\) more problems including this one. Every minute spent now delays all \(k\) acceptance times, so testing costs \(t\cdot k\) penalty minutes. Submitting untested costs \(20(1-p)\) in expectation, the rejection penalty; the debugging after a rejection happens in both plans. Submit first when

$$20\,(1 - p) < t\cdot k.$$

With \(p = 0.8\), \(t = 5\), \(k = 3\): \(4 < 15\), so submit. With \(p = 0.5\), \(t = 3\), \(k = 1\) (the last problem): \(10 > 3\), so test first. On Codeforces the same logic compares 50 points against \(t\) minutes of decay on all remaining problems, and pretests add a twist: a rejection is visible now, but a failed system test costs the whole problem after the contest.

Reading statements accurately

Most "wrong algorithm" verdicts are misread statements. Before coding, underline: the constraints, especially "the sum of \(n\) over all test cases does not exceed …"; whether the input has multiple test cases; the exact output format (one line or many, YES or Yes); "if there are several answers, print any" (a special judge, L138); the modulus (\(998244353\) vs \(10^9+7\)); strict vs non-strict inequalities; 0- vs 1-indexing of the output; and what to print when no answer exists.

The pre-submit checklist

Checklist · before every submit (print it)
  1. All samples pass, pasted exactly from the statement.
  2. Edge cases: \(n = 1\); all elements equal; already sorted and reverse sorted; the extremes of every value range.
  3. A maximum-size test, generated and timed locally; the right interpreter selected (PyPy or CPython).
  4. Multiple test cases: no state survives between tests; every test prints exactly one answer.
  5. Fast I/O: bulk read, one write at the end (not for interactive problems).
  6. Recursion: none deeper than about 1000, or run in a big-stack thread.
  7. Output format, modulus, and the "no answer" case checked against the statement once more.

The multi-test state bug

This single bug costs more rating than any missing algorithm. It survives the samples whenever the first test is the only one that matters, or the samples have a single test case.

The structural fix is a solve() function that takes one test's input and returns its answer, with nothing at module level except constants. Global arrays sized for the maximum \(n\) are the other version of the bug: either reset them over the whole range (too slow when there are \(10^4\) tests) or reset only the entries the test touched.

Mental state and the post-contest routine

After a rejection, do not resubmit with a guessed fix. Re-read the statement first: it is the cause more often than the code is. Then run the checklist, then a brute-force stress test (L10). Tilt: two rejections in a row, or the feeling that the problem "should be easy", is the signal to stand up for 60 seconds, breathe, and re-read the current problem's statement from the top. After the contest: upsolve within 48 hours, while the problems are fresh, and write a one-paragraph editorial for yourself for each problem: the key observation, why you missed it, and the technique's lesson number in this series.

What breaks
  • Spending the first half hour on the most interesting problem while A–C lose value.
  • Testing small and submitting large: a solution correct on samples but quadratic at \(n = 2\cdot10^5\). Always time a generated maximum test.
  • Hidden multi-test state, including functools.lru_cache decorators whose caches depend on per-test globals.
  • Locking a Codeforces problem to hack others, then finding your own bug, which can no longer be resubmitted.
  • No written protocol: under time pressure, nobody remembers a checklist they have not printed.

Deliberate practice, not grinding

Deliberate practice means working at the edge of your ability, with immediate feedback and a specific weakness as the target. Grinding means repeating what you can already do. The difference shows in one number: problems solved without editorial help at around your current rating + 200.   1. Pick problems that should take 20–40 minutes of real effort, starting around your rating + 200.
  2. Solved in under 10 minutes: too easy, so move up 100–200 points.
  3. No idea after 40–60 minutes: read one line of the editorial (below), not the whole thing.
  4. Each week, if more than half the problems needed the editorial, drop 100 points; if fewer than a quarter did, raise 100.

    with urllib.request.urlopen(url, timeout=30) as r:
        data = json.load(r)
    if data["status"] != "OK":
        raise RuntimeError(data.get("comment"))
    return data["result"]

    for s in sorted(subs, key=lambda s: s["creationTimeSeconds"]):
        p = s["problem"]
        key = (p.get("contestId"), p["index"])
        meta[key] = p
        if key in solved:
            continue                           # ignore resubmissions after AC
        tries[key] += 1
        if s.get("verdict") == "OK":
            solved.add(key); first[key] = tries[key] == 1
    stats = defaultdict(lambda: [0, 0, 0, []])
    for key, p in meta.items():
        for tag in p.get("tags") or ["(untagged)"]:

            if key in solved:
                st[1] += 1; st[2] += first[key]

    return sorted((ok / tried, tag, tried, ok, ft, sum(r) // len(r) if r else None)

Spaced repetition for algorithms

Re-reading your segment tree feels like understanding it; writing it from a blank file in 15 minutes is understanding it. The learning literature agrees. Retrieval practice (testing yourself) improves long-term retention more than restudying, and spaced sessions beat massed ones (Roediger & Karpicke 2006; Cepeda et al. 2006). Turn that into a rota: BIT on day 3, segment tree on day 7, HLD on day 21, then each component again at roughly three times the previous gap. The interview protocol

Protocol · one problem, about 45 minutes
  1. Clarify. Input sizes, value ranges, empty input, duplicates, sortedness, what to return when there is no answer. Repeat the problem back in one sentence.
  2. Examples. Work one normal and one edge example by hand; they become your tests later.
  3. Approach, out loud. Brute force first, with its complexity, then the improvement and the reason it works (the invariant, the exchange argument). Get agreement before coding.
  4. Complexity before code. State time and space; it shows you know where you are going.
  5. Code, narrating intent rather than syntax ("this window never contains a repeat").
  6. Test by tracing your examples through the code, then the edge cases. Fix bugs calmly and say what you found.
  7. Optimise and follow up: memory, streaming input, a distributed or concurrent version, if asked.

Interview-grade Python

Contest code optimises for typing speed. Interview code optimises for the reader. Use descriptive names, a typed signature, a docstring that states the contract and the complexity, guard clauses instead of nested ifs, small helper functions, and no clever one-liners. def length_of_longest_substring(s: str) -> int:
    """Longest substring of s without repeated characters. O(n) time, O(alphabet) space."""
    last_seen: dict[str, int] = {}
    window_start = 0
    best = 0
    for i, ch in enumerate(s):
        if last_seen.get(ch, -1) >= window_start:
            window_start = last_seen[ch] + 1   # jump past the previous copy of ch
        last_seen[ch] = i
        best = max(best, i - window_start + 1)
    return best

def test_length_of_longest_substring() -> None:
    cases = {"": 0, "a": 1, "abcabcbb": 3, "bbbbb": 1, "pwwkew": 3, "abba": 2}
    for s, want in cases.items():
        assert length_of_longest_substring(s) == want == f(s), (s, want)

from collections import deque
from dataclasses import dataclass, field

@dataclass
class SlidingWindowRateLimiter:
    """Allow at most `limit` requests per client in any `window`-second interval."""
    limit: int
    window: float
    _log: dict[str, deque] = field(default_factory=dict)

    def allow(self, client: str, now: float) -> bool:
        times = self._log.setdefault(client, deque())
        while times and times[0] <= now - self.window:
            times.popleft()                    # forget requests that left the window
        if len(times) >= self.limit:
            return False
        times.append(now)
        return True

Editorial: P1–P4

P1 — Number Spiral. With \(z = \max(y, x)\), layer \(z\) holds \((z-1)^2 + 1 \dots z^2\); even layers run down column \(z\) then left, odd layers run right along row \(z\) then up. Check against a brute-force spiral first, because parity mix-ups are the whole difficulty.

def spiral(y, x):
    z = max(y, x)
    if z % 2 == 0:
        return (z - 1) ** 2 + y if x == z else z * z - x + 1
    return (z - 1) ** 2 + x if y == z else z * z - y + 1

P2 — Tasks and Deadlines (reward \(d - f\) for finishing at time \(f\)). The total reward is \(\sum d - \sum f\), and \(\sum d\) is fixed, so minimise the sum of finishing times: shortest task first. Exchange argument: swapping an adjacent longer-then-shorter pair lowers the shorter task's finishing time by the longer's duration and raises the longer's by the shorter's, a net gain. One line: sum(d) - sum(accumulate(sorted(a))). (L22)

P3 — Hotel Queries (each group takes the first hotel with enough free rooms). Build a max segment tree over the hotels; descend from the root, going left whenever the left child's maximum is enough. That finds the first fitting hotel in \(O(\log n)\); then update the leaf and its ancestors. (L108)

def hotel_queries(h, groups):
    size = 1
    while size < len(h):
        size *= 2
    t = [0] * (2 * size)
    t[size:size + len(h)] = h
    for i in range(size - 1, 0, -1):
        t[i] = max(t[2 * i], t[2 * i + 1])
    out = []
    for r in groups:
        if t[1] < r:
            out.append(0); continue
        i = 1
        while i < size:                        # descend: leftmost child that fits
            i = 2 * i if t[2 * i] >= r else 2 * i + 1
        out.append(i - size + 1)
        t[i] -= r; i //= 2
        while i:
            t[i] = max(t[2 * i], t[2 * i + 1]); i //= 2
    return out

P4 — Flight Discount (halve the price of one flight). Run Dijkstra on \(2n\) states \((v, used)\). A flight \(u \to v\) of cost \(c\) gives \((u,0)\to(v,0)\) at \(c\), \((u,0)\to(v,1)\) at \(\lfloor c/2\rfloor\), and \((u,1)\to(v,1)\) at \(c\). The answer is \(dist(n, 1)\). Layering the state graph is the general trick for "\(k\) special moves" (L67).

P6 — Sum of Divisors (\(\sum_{i\le n}\sigma(i) \bmod 10^9+7\), \(n \le 10^{12}\)).

Derivation · the hyperbola split

Swap the order of summation: \(\sum_{i \le n}\sigma(i) = \sum_{d \le n} d\lfloor n/d\rfloor = \sum_{dk \le n} d\), a sum over lattice points under the hyperbola \(dk = n\). With \(s = \lfloor\sqrt n\rfloor\), every such point has \(d \le s\) or \(k \le s\). Count the first set by rows, the second by columns (summing \(d\) up to \(\lfloor n/k\rfloor\)), and subtract the \(s \times s\) square counted twice:

$$\sum_{dk\le n} d = \sum_{d\le s} d\left\lfloor \tfrac nd\right\rfloor + \sum_{k\le s} T\!\left(\left\lfloor \tfrac nk\right\rfloor\right) - s\,T(s), \qquad T(m) = \tfrac{m(m+1)}2.$$ 
from math import isqrt

def sum_of_divisors(n, M=10**9 + 7):
    s = isqrt(n)
    a = sum(d * (n // d) for d in range(1, s + 1))
    b = sum((q := n // k) * (q + 1) // 2 for k in range(1, s + 1))
    return (a + b - s * (s * (s + 1) // 2)) % M

That is \(2\cdot10^6\) generator steps at \(n = 10^{12}\), about a second in CPython on the test machine, with no overflow concerns (L120). P8 — Planets Queries II (fewest teleports from \(a\) to \(b\) in a functional graph). Each component is a cycle with in-trees. Find the cycles with an iterative walk, recording positions and lengths, and give each in-tree Euler times rooted at its cycle vertex (L55). If \(b\) is on a cycle, \(a\) walks \(depth(a)\) steps to its entry \(e\), then \((pos(b) - pos(e)) \bmod len\) around, provided \(e\) is on \(b\)'s cycle. If \(b\) is a tree vertex, \(a\) reaches it iff \(a\) is in \(b\)'s subtree. Otherwise the answer is \(-1\).

def planets_queries_2(succ, queries):          # 0-indexed successor array
    n = len(succ)
    state, cyc, pos, clen = [0] * n, [-1] * n, [0] * n, []
    for s in range(n):                         # 0 new, 1 on the current walk, 2 done
        path, v = [], s
        while state[v] == 0:
            state[v] = 1; path.append(v); v = succ[v]
        if state[v] == 1:                      # the walk closed a new cycle
            k = path.index(v)
            for i, u in enumerate(path[k:]):
                cyc[u], pos[u] = len(clen), i
            clen.append(len(path) - k)
        for u in path:
            state[u] = 2
    children = [[] for _ in range(n)]
    for v in range(n):
        if cyc[v] < 0:
            children[succ[v]].append(v)
    entry, depth, tin, tout, timer = list(range(n)), [0] * n, [0] * n, [0] * n, 0
    for r in range(n):
        if cyc[r] < 0:
            continue
        st = [(r, False)]                      # Euler times in r's in-tree
        while st:
            v, done = st.pop()
            if done:
                tout[v] = timer; continue
            tin[v] = timer; timer += 1
            st.append((v, True))
            for c in children[v]:
                entry[c], depth[c] = r, depth[v] + 1
                st.append((c, False))
    out = []
    for a, b in queries:
        e = entry[a]
        if cyc[b] >= 0:
            out.append(depth[a] + (pos[b] - pos[e]) % clen[cyc[b]] if cyc[e] == cyc[b] else -1)
        elif entry[b] == e and tin[b] <= tin[a] < tout[b]:
            out.append(depth[a] - depth[b])
        else:
            out.append(-1)
    return out
